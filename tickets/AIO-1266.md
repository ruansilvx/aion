# New Project Onboarding

# Proposal: New-project onboarding — attach-to-existing-project flow

## Source

`aion-arch/ideas/new-project-onboarding.md` (`status: specced`, five brainstorm
sessions between 2026-07-20 and 2026-07-24). That idea covers three pieces;
this proposal implements only the first, per the idea's own `next_action`:
the attach-to-existing-project flow (gitignore-confirmation gate + opt-in
codebase summarization). The "Inbox" app-level feature is deliberately
deferred to its own future `/propose` — it's a materially larger, separate
surface (new nav slot, `isAlwaysRoot` matrix exception, four chat purposes)
and bundling it here risks a sprawling review for no shared mechanism beyond
"starting a project." Release-ticket-type (the idea's third piece) already
shipped separately via `sdd-ticket-foundation` and needs no further work.

## Problem

Confirmed empirically while dogfooding (`new-project-onboarding.md`'s
"New, empirical (2026-07-23)" note): `CreateProjectCubit._initializeDesktopProject`
unconditionally writes `.aion/manifest.json` and a `tickets/` directory into
whatever `rootPath` is chosen, and always runs `git init` there — with no
check for a pre-existing `.git`. Point today's "New Project" flow at a real,
already-git-tracked codebase, and Aion's own bookkeeping commits become
indistinguishable from that project's actual source history unless the
developer manually gitignores `.aion/`/`tickets/` first. Nothing in the app
prompts for or does this automatically.

Separately: nothing in the app helps a user get from "I just pointed Aion at
my existing codebase" to a starting backlog. Tickets have to be created by
hand, one at a time, with no assistance from what's already in the repo.

## What's building

1. **Gitignore-confirmation gate.** The moment a chosen directory is
   detected as an existing git repository (a new check, run at
   directory-selection time — not post-submit, where stack detection
   currently runs), an inline banner appears on `NewProjectScreen` with a
   checkbox to auto-append `.aion/`/`tickets/` to that repo's `.gitignore`
   (creating one if absent). Checked by default. Applies uniformly to every
   directory chosen through this one form — there is no separate "Attach"
   entry point (see design.md for why). Declining doesn't block creation;
   it proceeds with a one-shot warning toast, consistent with Aion's
   existing inform-don't-block posture. Desktop only, matching the existing
   desktop-only scope of per-project git repos.

2. **Discoverability for attaching to an existing codebase.** Today's
   `CreateProjectCubit.submit` already accepts a non-empty `rootPath` — the
   only missing piece was the gate above. This proposal adds copy to
   `NewProjectScreen` clarifying that the chosen folder can be an existing
   codebase, not just an empty one to start fresh in.

3. **Opt-in codebase summarization.** Immediately after creating a project
   whose `rootPath` was already a git repository, a dismissible banner on
   the (now-empty) ticket list offers to scan the codebase and draft
   starting `signal` tickets. The user picks a depth — a cheap structural
   pass (directory listing + detected stack, no tool-enabled model turn) or
   a full agentic read (worktree-isolated, tool-enabled, mirrors the
   existing coding-execution pattern) — or dismisses the offer entirely.
   Either depth writes plain `signal` tickets into the already-shipped
   signal→epic promotion pipeline; no ticket schema changes, no automatic
   ticket generation without this explicit, one-time, per-project consent.

## Non-goals (this proposal)

- The Inbox app-level feature (separate future `/propose`, sequenced
  independently now that its `chat-transcript-ux-redesign` dependency has
  shipped).
- `Ticket.suggestedType` and Epic-vs-Bug promotion classification — that's
  scoped to the Inbox's brain-dump purpose in the source idea, not to
  codebase summarization here. `bug-ticket-type` itself remains unshipped
  (`status: explored`), so promotion here targets Epic only, unchanged.
- A genuinely restricted (read-only) agentic tool tier. No such tier exists
  anywhere in Aion today — `agent_bridge/index.mjs` is binary
  (`toolsEnabled: false` → zero tools, `toolsEnabled: true` → full
  bypass-permissions access). The "full" summarization depth reuses the
  existing full-access tier inside a worktree, the same trust model
  coding-execution already relies on — not a new capability class.
- A re-triggerable "analyze codebase" action from Settings. The offer is
  shown once, right after creation, matching the idea's own scoping; a
  standing re-triggerable entry point is left for a later change if
  real need shows up.
- Any change to `Project`/`RegistryDatabase`'s schema. The "shown once"
  behavior is in-memory only (see design.md), not persisted.
- Model-initiated "dive deeper on demand" from a shallow scan's flag — the
  idea describes this as a later chat's own model deciding to read further
  files; no such chat surface exists yet (that's Inbox's Q&A purpose). The
  shallow-scan flag is written into signal descriptions now so that future
  work has something to read; nothing consumes it yet.
- A baseline-version picker (still a hardcoded, read-only field on
  `NewProjectScreen` — unrelated to this proposal's scope).

## Design gate

status: APPROVED

Approved: 2026-07-27. No Material-widget violations found (every
forbidden-widget match in design.md is either Aion's own `*Banner`-suffixed
custom component, an explicit "we do not use X" disclaimer, or a reuse of
Aion's existing `AppCheckbox`/`AppButton`/`AppSpinner` atoms). 4 new
derived-tint helper methods to add to `AionColorsHubTokens` in
`aion/lib/design_system/tokens/aion_colors.dart` before `/apply` —
`noticeIconTint`, `pendingIconTint`, `dangerIconTint`, and the four
`signal*` tints (`signalFill`/`signalBorderTint`/`signalIconTint`/
`signalChipTint`). All four are alpha-only derived tints on existing base
colors (`primary`/`danger`/`typeSignal`), matching the established
`AionColorsHubTokens` pattern — no new hex values, no new `AionColors`
constructor fields. See this change's `/design-sync` output for the exact
Dart to add (note: design.md's spec text writes these using the
deprecated `Color.withOpacity(x)` — transcribe as `.withValues(alpha: x)`
instead, per this project's Bootstrap notes). `tasks.md` tasks 3.1, 6.1,
and 6.2 are annotated with the relevant design.md section references.
