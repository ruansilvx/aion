# Manual QA pass — critical bug found and fixed

Found by driving the real Windows desktop build end-to-end (not caught by
any unit/widget test, including the ones above): **chaining a branch to a
newly created condition always failed to save**, both for the "continue
to condition" flow on an existing node and for the empty-graph "Add first
condition" flow — the two flows every multi-node graph has to go through
at least once.

- **`DecisionGraphConfigCubit.createNode`** persists the new node, then
  calls `load()` to refresh state — but `DecisionGraphRepository
  .getAllNodes` only returns nodes reachable from the graph's root (by
  design, since an unattached node isn't part of the tree yet), so the
  reload silently dropped the brand-new orphan back out of
  `DecisionGraphConfigLoaded.nodesById`. The immediate follow-up call
  every caller makes — `updateNode` (attach as an existing node's branch
  target) or `setRoot` (attach as the graph's first node) — then saw the
  just-returned id as absent from state and rejected with
  `danglingBranchTarget`/`nodeNotFound`, discarding the whole edit (and
  leaving the orphan row persisted-but-invisible in the DB). Fixed by
  having `createNode` re-merge the new node into the reloaded state
  whenever the reload didn't already pick it up, so it stays visible to
  the very next Cubit call until it's actually attached (or abandoned,
  matching `deleteNode`'s existing "cleanup is the editor UI's
  responsibility" precedent).
- [x] `lib/features/providers/presentation/cubit/decision_graph_config_cubit.dart`
      — `createNode` fix described above.
- [x] `test/features/providers/presentation/cubit/decision_graph_config_cubit_test.dart`
      — two regression tests: chaining a new node onto an existing
      node's branch via `updateNode`, and attaching a freshly created
      node as the graph's first node via `setRoot`. Both reproduced the
      failure against the pre-fix code (verified by temporarily
      reverting the fix and re-running) before the fix was reapplied.
