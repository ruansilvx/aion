# Automation Decision Graphs

# Proposal: Automation Decision Graphs

Originates from [`aion-arch/ideas/automation-confidence-decisions.md`](../../ideas/automation-confidence-decisions.md).

## Problem

`AutomationConfidence.auto` today means "apply the decision silently, no
user interaction" — but *how* the model decides an action is warranted
under `auto` is pure free-form prompt judgment, with nothing structural
constraining it. Three of the eight `AutomationContext` consumers
(`codingExecutionRetry`, `codingExecution`, `chatBranching`) already have
a hand-written, ad hoc "deterministic condition forces a stricter
outcome" check bolted on (`_effectiveCodingExecutionRetryConfidence`'s
retry-count cap, `_effectiveCodingExecutionConfidence`'s overage flag,
`_canBranch`'s depth cap) — proof the pattern is worth having, but today
it's three one-off, non-reusable, code-only implementations that a
project can't see or edit, and the other five consumers
(`sddStage`, `codingExecutionResume`, `ticketCreation`, `ticketLinking`,
`specAutoLink`) have no such structure at all.

## What this builds

For each of the eight `AutomationContext` decision points, a
project-authored, project-editable **decision graph**: a strict binary
tree of conditions, each with a "matched" and "unmatched" branch, each
branch either leading to another condition or terminating in an outcome
(`proceed` / `gated` / `decline` / `modelJudgment`). Aion ships a
baseline graph per context (empty/always-`proceed` for five contexts;
the three existing ad hoc checks re-expressed as baseline graph data for
the other three, so out-of-the-box behavior is unchanged) — a project
can edit any context's graph without touching code, the same
baseline-preset-with-override pattern already shipped for
`TicketStatus`/`SddStage` (`configurable-workflow-and-automation-engine`)
and for skills (`ProjectOverride`/`BaselineAsset`).

The graph is only ever consulted once a context has already resolved to
`AutomationConfidence.auto` — `gated`/`manual` are completely unaffected
by this proposal. `AutomationConfidence` itself is not touched: still a
plain, user-set three-state preference.

Authoring is a dual-pane editor per context: a visual node-graph canvas
(default view, built as a new `GraphCanvas` design-system primitive —
`InteractiveViewer` + `Stack` + `CustomPainter` edges, no new
dependency) alongside a synchronized nested/indented list view (mirrors
the tree structurally, same shape as a Markdown nested bullet list).
Both panes are independently editable and kept in bidirectional sync;
the list exists specifically as the faster surface for simple edits.

## Why a graph and not a computed confidence score

This is explicitly **not** a reopening of
`configurable-workflow-and-automation-engine`'s earlier decision that
skill-attachment confidence-gating reuses the static `AutomationConfidence`
enum with no new computed signal. That decision stands, and this proposal
doesn't touch it. What's being added here is orthogonal: a structural aid
to the model's judgment *within* `auto`, not a new mechanism for choosing
between `auto`/`gated`/`manual` in the first place.

## Non-goals (deliberately deferred)

- **Retrofitting `TicketStatus`/`SddStage` transition preconditions onto
  this same engine.** `configurable-workflow-and-automation-engine`'s
  Phase 3 originally scoped "pluggable gate behaviors" around transition
  preconditions specifically. A grounded `/explore` pass
  (`aion-arch/ideas/automation-confidence-decisions.md`'s "Explore
  findings") found the two systems share the same interception *shape*
  but not shareable node *content* — `_sddStageAdvanceCheck`'s five
  branches each query fundamentally different data with no common
  vocabulary. This proposal builds the graph engine generically enough
  to be reused for that retrofit later, but doing the retrofit itself is
  left as a distinct future proposal.
- **A shared canvas primitive with `obsidian-style-graph-view-for-ticket-links`.**
  That idea wants force-directed/physics auto-layout for visualizing
  `ticket_links` relationships — a different problem from this tree's
  deterministic, edge-driven layout. `GraphCanvas` is built scoped to
  this feature's actual needs; that idea is still `raw` and unexplored.
- **A real model-in-the-loop round trip for `modelJudgment` leaves.** No
  mechanism anywhere in the codebase pauses mid-tool-call to ask the
  model a follow-up and resume (`gated`'s existing pause waits on a
  *human* UI click, never a second model turn). A `modelJudgment` leaf
  behaves identically to `proceed` at evaluation time; its condition's
  description is instead surfaced as context in the system prompt before
  the model acts, informing its original decision rather than
  intercepting it afterward.
- **New condition types for the five contexts with no existing ad hoc
  check** (`sddStage`, `codingExecutionResume`, `ticketCreation`,
  `ticketLinking`, `specAutoLink`). Their baseline graphs ship empty
  (always `proceed`, matching today's behavior exactly); this proposal's
  condition catalog only covers the two conditions needed to reproduce
  `codingExecutionRetry`'s and `codingExecution`'s existing ad hoc
  checks as data. The engine is built to make adding new condition
  types straightforward later — a catalog entry plus an evaluator case,
  no schema change — but authoring new conditions for these five is a
  follow-up, not part of this slice.
- **Migration/versioning** of a project's edited graph when Aion's own
  baseline graph for a context changes in a later release. Not
  addressed here — flagged as an open question in the idea file.
- **True DAG support** (branches reconverging on a shared node). The
  graph is a strict tree by design — simpler to author on the canvas,
  and it's what lets the list pane be an honest indented outline.
