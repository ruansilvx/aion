# Design: storage-embedding-git-sync

## Architecture overview

```
core/
  contracts/
    embedding_provider.dart          <-- interface only
  embeddings/
    bundled_embedding_provider.dart  <-- ONNX (native) / WASM (web) impl
  git/
    git_repository_client.dart       <-- git init/add/commit/status wrapper
  markdown/
    ticket_markdown_template.dart    <-- frontmatter schema constants
    ticket_markdown_serializer.dart  <-- Ticket <-> Markdown, deterministic
    ticket_markdown_parse_result.dart <-- success | partiallyInvalid | unparseable

features/
  tickets/
    domain/
      enums/
        ticket_sync_status.dart      <-- synced | pendingReconcile | needsRepair
      entities/
        ticket.dart                  <-- + syncStatus field
      repositories/
        ticket_repository.dart       <-- + updateSyncStatus()

    data/
      models/ticket_model.dart       <-- + syncStatus column (schema v3->v4)
      daos/ticket_dao.dart
      repositories/drift_ticket_repository.dart
      services/
        ticket_git_projector.dart          <-- one-way DB -> file writer
        active_ticket_view_registry.dart   <-- "which ticket is on screen"
        ticket_markdown_watcher_service.dart  <-- focus-lifecycle + debounce
        ticket_markdown_reconciler.dart       <-- bidirectional reconcile
        ticket_repair_service.dart            <-- DB-aware repair actions
        ticket_db_reconstruction_service.dart <-- rebuild DB from git

    presentation/
      cubit/
        tickets_cubit.dart            <-- + embedding/git-sync triggers
        ticket_repair_cubit.dart      <-- drives repair UI actions
      widgets/
        ticket_sync_status_badge.dart
        ticket_needs_repair_banner.dart
      screens/
        ticket_detail_screen.dart     <-- + badge/banner, view registration

bin/
  ticket_lint.dart                    <-- standalone CLI, pure Dart

aion-arch/.claude/skills/ticket-lint/SKILL.md   <-- skill source
aion/assets/baseline/0.2.0/...                  <-- new baseline version
```

Follows `project.md`'s Pattern 1 (dependency inversion via `core/`)
throughout: `EmbeddingProvider` is a `core/contracts/` interface so
any future feature needing embeddings (not just tickets) depends
downward on `core`, never on the tickets feature directly.
`GitRepositoryClient` is plain `core/` infrastructure (no interface
needed — one implementation, used by both `projects` and `tickets`
features, each importing it directly since it has no feature-specific
logic to invert).

## Domain layer

### `TicketSyncStatus` (new enum)

```dart
enum TicketSyncStatus {
  /// DB and file (if applicable) agree. Default for every ticket type;
  /// the only state work-item types (epic/story/task/chat) ever have,
  /// since they have no file to fall out of sync with.
  synced,

  /// A resource/page ticket has a reconcile in flight (background,
  /// non-blocking) — surfaced as a subtle indicator, not a blocker.
  pendingReconcile,

  /// A resource/page ticket's file failed to parse on reconcile.
  /// Neither the DB nor the file was overwritten. Requires a manual
  /// reformat or restore-from-last-known-good action.
  needsRepair,
}
```

### `Ticket` entity (modified)

Adds one field: `TicketSyncStatus syncStatus` (non-nullable, defaults
to `synced`). Existing `embedding` field's doc comment updates from
"population deferred to a future change" to describe the
`EmbeddingProvider` trigger.

### `TicketRepository` (interface, modified)

Adds:
```dart
/// Updates only [syncStatus], independent of [updateTicket] — sync
/// state changes originate from the reconciler/watcher, not user edits,
/// and must not perturb [Ticket.updatedAt] the way a content edit does.
Future<void> updateSyncStatus(String ticketId, TicketSyncStatus status);
```

## Data layer

### Drift migration (schema v3 -> v4)

`TicketsTable` gains `IntColumn get syncStatus => intEnum<TicketSyncStatus>().withDefault(const Constant(0))();` (0 = `synced`). Migration step in `AppDatabase.migration`:
```dart
if (from < 4) {
  await m.addColumn(ticketsTable, ticketsTable.syncStatus);
}
```

### `TicketMarkdownTemplate` / `TicketMarkdownSerializer`

Frontmatter fields (YAML, via the `yaml` package for parsing;
hand-written deterministic key ordering for serializing — never rely on
a YAML emitter's own key ordering, since diffs must reflect real
changes only):

```yaml
---
ticketId: TCK-142
type: resource
status: open
priority: medium
parentId: TCK-100
estimate: null
timeSpent: null
createdAt: 2026-07-18T10:00:00.000Z
updatedAt: 2026-07-18T10:00:00.000Z
---
<description body, verbatim>
```

`TicketMarkdownSerializer.serialize(Ticket) -> String` is pure and
deterministic (same ticket in, byte-identical string out).

`TicketMarkdownSerializer.parse(String) -> TicketMarkdownParseResult`,
a sealed result type:

```dart
sealed class TicketMarkdownParseResult {}

/// Every field parsed and validated.
class ParsedOk extends TicketMarkdownParseResult {
  final Map<String, Object?> fields;
  final String body;
}

/// Frontmatter parsed as YAML, but one or more fields failed
/// validation (e.g. bad `status` enum value). Valid fields are usable;
/// invalid ones are named so the caller can keep the DB's last value
/// for just those fields.
class ParsedPartial extends TicketMarkdownParseResult {
  final Map<String, Object?> validFields;
  final Set<String> invalidFieldNames;
  final String body;
}

/// Frontmatter block itself is missing or not valid YAML. Nothing is
/// usable — caller must not write to DB or overwrite the file.
class Unparseable extends TicketMarkdownParseResult {
  final String reason;
}
```

This type, the template, and the serializer are pure Dart with no
Flutter dependency — deliberately, so `bin/ticket_lint.dart` (a plain
Dart CLI entry point) can import them directly without pulling in
Flutter.

### `GitRepositoryClient`

```dart
class GitRepositoryClient {
  Future<void> init(String rootPath);
  Future<void> add(String rootPath, String relativePath);
  Future<bool> hasChanges(String rootPath); // `git status --porcelain`
  Future<void> commit(String rootPath, String message);
}
```

Thin wrapper around `Process.run('git', [...], workingDirectory:
rootPath)`. `CreateProjectCubit._initializeDesktopProject` switches
from its inline `Process.run('git', ['init'], ...)` call to
`GitRepositoryClient.init(rootPath)`, and additionally creates the
`tickets/` subdirectory that projection writes into.

### `TicketGitProjector` (one-way writer)

```dart
class TicketGitProjector {
  Future<void> project(Ticket ticket, String rootPath, String eventLabel);
}
```

Only called for `epic`/`story`/`task`/`chat` tickets. Serializes,
writes `<rootPath>/tickets/<ticket.ticketId>.md`, then
`GitRepositoryClient.add` + `hasChanges` + `commit` (message:
`ticket: <ticketId> <eventLabel>`, e.g. `ticket: TCK-142 status-changed`).
Skips the commit if `hasChanges` is false (e.g. a status change that
doesn't alter the serialized content — avoids empty commits).

### `ActiveTicketViewRegistry`

```dart
class ActiveTicketViewRegistry {
  final ValueNotifier<String?> activeTicketId = ValueNotifier(null);
}
```

One instance per app session, provided via the same
`RepositoryProvider` tree as other services in `main.dart`.
`TicketDetailScreen` sets `activeTicketId.value = ticket.ticketId` in
`initState` and clears it (`null`, guarded by an identity check so a
second screen mounting doesn't clobber a different active id) in
`dispose`. The reconciler reads this value to decide blocking vs.
background-with-indicator (see below).

### `TicketMarkdownWatcherService`

Wraps the `watcher` package's `DirectoryWatcher` scoped to
`<rootPath>/tickets/`, filtered to `.md` files whose corresponding
ticket is `resource`/`page` (checked via a ticketId -> type lookup, not
by re-parsing the file). Debounces per-file events (~1.5s default,
exposed as a constructor parameter so `/apply` can tune it) before
invoking the reconciler.

Lifecycle: started in `main.dart`'s root widget via
`WidgetsBindingObserver.didChangeAppLifecycleState` — `resumed` starts
the watcher (and immediately triggers one reconcile pass per
`resource`/`page` ticket, covering edits made while backgrounded),
`paused`/`inactive`/`hidden` stops it. No watcher runs at all on
mobile/web (desktop-only, matching git projection's existing scope —
`resource`/`page` types still sync one-way DB->file there, just never
watch for external edits back).

### `TicketMarkdownReconciler`

```dart
class TicketMarkdownReconciler {
  Future<void> reconcile(String ticketId, String rootPath);
}
```

1. Reads `<rootPath>/tickets/<ticketId>.md`.
2. Parses via `TicketMarkdownSerializer.parse`.
3. If `Unparseable`: calls `TicketRepository.updateSyncStatus(ticketId,
   needsRepair)`. Does not touch the DB row's content or the file.
4. If `ParsedPartial`: applies `validFields` to the DB via
   `updateTicket` (keeping the DB's existing value for each name in
   `invalidFieldNames`), leaves `syncStatus` at `synced`.
5. If `ParsedOk`: applies all fields to the DB via `updateTicket`.
6. Before steps 4/5 apply, checks
   `ActiveTicketViewRegistry.activeTicketId.value == ticketId`:
   - If **not** active: sets `pendingReconcile` briefly, applies the
     update, sets back to `synced` — this is the "subtle sync
     indicator" path, entirely non-blocking to the user.
   - If **active**: defers — queues the pending file content and
     re-attempts once `activeTicketId` changes away from this ticket
     (listener on the `ValueNotifier`), so the user's in-progress view
     is never overwritten mid-edit.
7. A DB-side content change (via steps 4/5) feeds into the same
   embedding-regeneration trigger as any other edit (see below) — one
   unified trigger path regardless of which surface changed the
   content.

### `TicketRepairService`

```dart
class TicketRepairService {
  /// Re-validates the current file, applying whatever the linter can
  /// safely fix (whitespace/ordering normalization) without touching
  /// content it can't confidently interpret. Returns whether the
  /// ticket is now synced.
  Future<bool> reformat(String ticketId, String rootPath);

  /// Overwrites the file with a fresh serialization of the ticket's
  /// current DB row — the "last known good" state, since the DB was
  /// never touched by a failed reconcile. Always resolves to `synced`.
  Future<void> restoreFromLastKnownGood(String ticketId, String rootPath);
}
```

Both actions are explicit, user- or agent-triggered — never run
automatically, matching the deep-dive's "flag, don't silently fix"
rule. `reformat` delegates the actual parse/repair heuristics to a
DB-agnostic `core/markdown` linter function so the same logic is
reachable from `bin/ticket_lint.dart` without a `TicketRepository`.

### `TicketDbReconstructionService`

```dart
class TicketDbReconstructionService {
  /// Reads every `tickets/*.md` file under [rootPath], parses each,
  /// and inserts/upserts the corresponding row via [TicketRepository].
  /// Unparseable files are skipped and reported, not fatal to the run.
  /// After import, triggers [EmbeddingProvider] in bulk for every
  /// imported ticket lacking a local embedding.
  Future<TicketReconstructionReport> reconstruct(String rootPath);
}
```

Built and unit-tested standalone. Not called from any UI flow yet (see
proposal's Non-goals) — the natural future caller is whatever
"open/clone an existing project" flow eventually ships.

## Embedding pipeline

### `EmbeddingProvider` (core contract)

```dart
abstract interface class EmbeddingProvider {
  Future<Uint8List> embed(String text);
}
```

### `BundledEmbeddingProvider` (impl)

Platform-conditional, following `AppDatabase`'s existing
`_openConnection()` split pattern:
- **Native (desktop/mobile):** loads a bundled, int8-quantized
  all-MiniLM-L6-v2 ONNX model from `assets/models/`, run via an ONNX
  runtime Flutter plugin (evaluate `flutter_onnxruntime` at
  implementation time — swap for the closest maintained equivalent if
  it doesn't fit; this is the one piece of this design most likely to
  need a substitution based on what's actually usable on pub.dev when
  `/apply` runs).
- **Web:** same weights, exported to a WASM build, run via the
  platform's WASM ONNX runtime bindings.
- Both paths share a bundled WordPiece tokenizer (vocab shipped
  alongside the model asset) so tokenization is identical across
  platforms — embedding vectors must be comparable regardless of which
  platform created them.

### Trigger point

`TicketsCubit.createTicket()` and `TicketsCubit.updateTicket()` compare
the new `title`/`description` against the previous value (on update;
always regenerate on create). If changed, fire-and-forget an async call:
embed `"$title\n\n$description"` -> `TicketRepository.updateTicket`
with just the `embedding` field populated, once the future resolves.
Ticket save itself never awaits this — matches the deep-dive's
"generation is async, never blocks save" decision.

## BLoC/Cubit states

### `TicketsCubit` (modified, no new states)

No new `TicketsState` subclasses — embedding regeneration and git
projection are side effects fired alongside existing state transitions
(`TicketCreated`, `TicketUpdated`, etc.), not states of their own. Both
side effects are triggered from the same methods that already call
`_repository.createTicket`/`updateTicket`, immediately after those
calls resolve.

### `TicketRepairCubit` (new)

```dart
sealed class TicketRepairState extends Equatable {}

/// Initial / no repair action in flight.
class TicketRepairIdle extends TicketRepairState {}

/// Reformat or restore is running.
class TicketRepairInProgress extends TicketRepairState {}

/// Action completed; carries the resulting [TicketSyncStatus] so the
/// UI can confirm the banner should disappear.
class TicketRepairCompleted extends TicketRepairState {
  final TicketSyncStatus resultStatus;
}

/// Action failed (e.g. file became unreadable mid-action).
class TicketRepairFailed extends TicketRepairState {
  final String message;
}
```

Constructed with a `TicketRepairService` and the target `ticketId`/
`rootPath`; exposes `reformat()` and `restoreFromLastKnownGood()`
methods mirroring the service.

## CLI

`aion/bin/ticket_lint.dart` — plain Dart entry point (no Flutter SDK
dependency, importing only `core/markdown/*`, which is itself
Flutter-free):

```
dart run bin/ticket_lint.dart <project-root> [--fix]
```

Walks `<project-root>/tickets/*.md`, runs the same parse/lint used by
`TicketRepairService.reformat`, prints a report (path, status: ok /
reformatted / needs-repair-untouched). `--fix` applies safe
reformatting in place; without it, the command only reports. Never
touches the DB (no drift dependency at all) — purely a file-level tool,
matching the "mechanical, cheap" intent from the deep-dive.

## Skill

`aion-arch/.claude/skills/ticket-lint/SKILL.md` — new baseline skill,

`aion-arch/.claude/skills/what-next/SKILL.md` for the pattern this

isn't sufficient (a `needsRepair` ticket whose issue is genuinely

# Aion — Ticket Sync Status & Repair: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing` by name. **No Material widgets anywhere** — every surface below is `DecoratedBox` / `Container` / `GestureDetector` / `CustomPaint` / `AnimatedFoo`, never `Card`, `Chip`, `Banner`, `ElevatedButton`, `TextButton`, `CircularProgressIndicator`, `Tooltip`, `ColorScheme`, or `ThemeData`.

Two additions to the existing `TicketDetailScreen`, visible **only for `resource`/`page` tickets** whose content mirrors to a Markdown file:

1. `TicketSyncStatusBadge` — a low-key state indicator in the detail header (§2).
2. `TicketNeedsRepairBanner` — an inline recovery banner at the top of the detail body, shown only in the `needsRepair` state (§3).

No new screens. Insertion points into the existing header/body are described in §4. Mockups: [Aion Sync Status and Repair Mockups](./Aion%20Sync%20Status%20and%20Repair%20Mockups.dc.html).

## 1. Foundations added

### 1.1 Sync-state enum

```dart
enum TicketSyncStatus { synced, pendingReconcile, needsRepair }
```

Only meaningful for `resource`/`page` tickets; for all other types the badge and banner are not built at all (`SizedBox.shrink()` — no reserved space).

### 1.2 New derived tint tokens

Follow the established `AionColorsHubTokens` derived-tint pattern (compute from a base token + theme-dependent alpha; never a standalone hex). Add to that helper class:

```dart
// warning family — needsRepair is an EXPECTED, recoverable state, not a crash,
// so it uses `warning`, not `danger`. danger stays reserved for destructive/error.
Color needsRepairTint(bool isDark)       => warning.withOpacity(isDark ? 0.20 : 0.14); // banner / badge fill
Color needsRepairBorderTint(bool isDark) => warning.withOpacity(isDark ? 0.42 : 0.34); // banner / badge border
Color needsRepairIconTint(bool isDark)   => warning.withOpacity(isDark ? 0.24 : 0.18); // icon chip fill

// primary family — pendingReconcile: active but calm
Color pendingTint(bool isDark)           => primary.withOpacity(isDark ? 0.18 : 0.12); // badge fill
Color pendingSpinnerTrack(bool isDark)   => primary.withOpacity(isDark ? 0.32 : 0.24); // spinner track ring

// success family — brief post-repair confirmation
Color repairedTint(bool isDark)          => success.withOpacity(isDark ? 0.20 : 0.14);
Color repairedBorderTint(bool isDark)    => success.withOpacity(isDark ? 0.42 : 0.34);
Color repairedIconTint(bool isDark)      => success.withOpacity(isDark ? 0.24 : 0.18);
```

**No new hex values, no new color tokens.** All three families reuse existing `AionColors.warning` / `primary` / `success`.

### 1.3 Type token

`isDark` throughout = `theme.brightness == Brightness.dark` (Obsidian). No new radius, spacing, or type tokens are required — the badge reuses `AionText.chip`; the banner reuses `AionText.bodySm` and `AionText.button`.

## 2. `TicketSyncStatusBadge`

A small icon+label indicator placed in the detail header's trailing cluster, immediately left of the `⋮` overflow button. Non-interactive except for a hover tooltip. `resource`/`page` only.

### 2.0 Shared geometry (all states)

- Layout: `Row`, `mainAxisSize: min`, `crossAxisAlignment: center`, `gap: 6` (7 in `pendingReconcile`).
- Radius: `AionRadius.pill` (22).
- Label: `AionText.chip` (10.5px / w700 / +0.53 tracking), **UPPERCASE string**, color per state below.
- Leading glyph box: intrinsic, sizes per state below.
- Height: intrinsic (~24px). No shadow in any state.
- The badge is a `MouseRegion` (desktop) wrapping the row; `onEnter`/`onExit` toggle the tooltip (§2.4). No tap/press behavior — it is a status readout, not a control.

### 2.1 `synced` — default, recedes

The "nothing to see here" state. Quiet, no fill, no border.

| Property | Value |
|---|---|
| Padding | `EdgeInsets.fromLTRB(8, 5, 10, 5)` |
| Fill | none (transparent) |
| Border | none |
| Icon | `check` (✓), **14px**, color `textMuted` |
| Label | `"SYNCED"`, `AionText.chip`, color `textMuted` |

Identical structure in both themes; only token values differ (they resolve from the active `AionColors`). Reads as muted grey in both.

### 2.2 `pendingReconcile` — active, calm

Transient state while a background reconcile applies an external edit. Reads active but not alarming — primary family.

| Property | Value |
|---|---|
| Padding | `EdgeInsets.fromLTRB(9, 5, 11, 5)` |
| Fill | `pendingTint(isDark)` |
| Border | none |
| Icon | animated spinner (§2.2.1), **12px**, color `primary` |
| Label | `"SYNCING"`, `AionText.chip`, color `primary` |

**2.2.1 Spinner** — no Material `CircularProgressIndicator`. A `CustomPaint` (or `AnimatedBuilder` + `Transform.rotate` over a `CustomPaint`) driven by a repeating `AnimationController` (period **750ms**, `linear`, `..repeat()`):
- Draw a `12×12` ring, `strokeWidth: 2`, `StrokeCap.round`.
- Track arc: full circle, color `pendingSpinnerTrack(isDark)`.
- Head arc: ~90° sweep, color `primary`, rotating.
- Dispose the controller when the badge leaves `pendingReconcile`.

### 2.3 `needsRepair` — attention, not alarm

Recoverable, expected-occasional state. Uses the **`warning`** family, deliberately not `danger`: a parse failure after an external edit is not a destructive action or a crash — `danger` stays reserved for delete/error per the base spec, and reusing it here would over-signal alarm. Warning reads "needs attention" while staying calm.

| Property | Value |
|---|---|
| Padding | `EdgeInsets.fromLTRB(9, 5, 11, 5)` |
| Fill | `needsRepairTint(isDark)` |
| Border | `1px solid needsRepairBorderTint(isDark)` |
| Icon | `warning` (triangle), **12px**, color `warning` |
| Label | `"NEEDS REPAIR"`, `AionText.chip`, color `warning` |

### 2.4 Tooltip / hover (desktop-first)

One-line explanation on pointer hover. **No Material `Tooltip`** — a manually-positioned `OverlayEntry` (or a `Stack` child positioned by `CompositedTransformFollower` on a `CompositedTransformTarget` wrapping the badge), anchored **top-right of the badge, growing down**, offset `(0, 6)`.

- Container: fill `textPrimary`; radius `AionRadius.md` (10); padding `EdgeInsets.fromLTRB(11, 9, 11, 9)`; max width `220`; shadow `BoxShadow(color: rgba(0,0,0, isDark ? 0.55 : 0.30), blurRadius: 30, spreadRadius: -12, offset: Offset(0, 14))`.
- Text: `AionText.bodySm` with `height: 1.45`, color `background` (inverted-surface text on the dark tooltip body — legible in both themes).
- Small `8–10px` caret (rotated square, same fill as container) at the top edge.
- Entrance: fade 0→1 + 2px rise, 120ms `Curves.easeOut`. Exit: fade, 90ms.
- Copy per state:

| State | Tooltip |
|---|---|
| `synced` | `"File and record agree. Any external edit is already reflected here."` |
| `pendingReconcile` | `"Applying an external edit to this ticket — this takes a moment."` |
| `needsRepair` | `"The file couldn't be parsed after an external edit. Use the banner below to recover."` |

### 2.5 State summary — badge

| State | Fill | Border | Icon (12–14px) | Label color | Hover |
|---|---|---|---|---|---|
| `synced` | none | none | `check` `textMuted` | `textMuted` | tooltip §2.4 |
| `pendingReconcile` | `pendingTint` | none | spinner `primary` | `primary` | tooltip §2.4 |
| `needsRepair` | `needsRepairTint` | `needsRepairBorderTint` | `warning` `warning` | `warning` | tooltip §2.4 |

There is no hover/pressed/focused *fill change* on the badge — it is non-interactive; the only pointer affordance is the tooltip. No disabled state (it is never disabled; it simply isn't built for non-file ticket types).

## 3. `TicketNeedsRepairBanner`

Inline banner at the top of the detail body, present **only** while `syncStatus == needsRepair`. Not user-dismissible — it clears itself when the underlying state resolves (to `synced` after a successful action, via a brief success confirmation §3.4). Both recovery actions are **equally weighted, non-destructive-feeling** choices — this is not a primary/destructive-confirm pattern.

### 3.1 Container — default state

- Width: fills the body content column (respects the body's horizontal padding; the banner adds its own `AionSpacing.sp20` (20) left/right margin to match the header/body gutter, and `2px` top / `4px` bottom margin so it sits just under the header and above the title block).
- Padding: `EdgeInsets.fromLTRB(15, 14, 15, 14)`.
- Fill: `needsRepairTint(isDark)`.
- Border: `1px solid needsRepairBorderTint(isDark)`.
- Radius: `AionRadius.lg` (12).
- Shadow: none.
- Structure: `Column`, `crossAxisAlignment: stretch`, `gap: 13` — (a) message row, (b) actions row.

### 3.2 Message row

- Layout: `Row`, `crossAxisAlignment: start`, `gap: 11`.

### 3.4 In-progress and success states

**In-progress** (either action running):
- The tapped button enters its *in-progress* look (§3.3 last row): inline spinner + present-tense label (`"Reformatting"` / `"Restoring"`).
- The **other** button is `disabled` (opacity 0.45, gestures ignored) — only one recovery runs at a time.
- The message row is unchanged. Container fill/border unchanged (still `needsRepair` warning tint).

**Success confirmation** (action resolved OK, before the banner disappears):
- Container animates fill → `repairedTint(isDark)`, border → `repairedBorderTint(isDark)` (200ms cross-fade).
- Icon chip fill → `repairedIconTint(isDark)`, glyph → `check` **14px** color `success`.
- Message row collapses to a single centered-start line (`crossAxisAlignment: center`, no second paragraph): title `"File repaired — back in sync"` (`AionText.bodySm` w700, `textPrimary`); sub `"The banner clears on its own in a moment."` (`AionText.bodySm`, `textSecondary`).
- **Actions row is removed** (`AnimatedSize` collapse, 180ms).
- Hold **~1200ms**, then the whole banner collapses out: `AnimatedSize` height→0 + fade, 220ms `Curves.easeInCubic`, as `syncStatus` transitions to `synced` (which also flips the header badge to §2.1).

**Failure** (action could not fix the file): the banner returns to its default state (§3.1), buttons re-enabled, and an `AppToast` (base spec, unchanged container) appears with icon `warning` color `warning` and copy `"Couldn't repair automatically — try Restore from last known good, or edit the file directly."`. No new banner error styling; the toast carries the failure and the banner stays available for a second attempt.

### 3.5 Theme parity

Structure identical across Arctic and Obsidian; every color resolves from the active `AionColors` + the §1.2 tints, so a single widget serves both. No per-theme layout differences.

## 4. `TicketDetailScreen` insertion context

Out of scope to redesign; only the two insertion points change. Both are gated on `ticket.type ∈ {resource, page}` — for every other type the header trailing cluster and body are exactly as today.

### 4.1 Badge — header trailing cluster

The existing header row (base spec §3.3: `back button · mono key · … more`) gains the badge between the mono key's trailing space and the `⋮` button:

```
[‹ back]  AIO-31            … existing spacer …  [SyncStatusBadge]  [⋮ more]
```

- Insert as the child immediately before the overflow `⋮` in the header `Row`, with `gap: 12` to the `⋮` (matches the row's existing gap rhythm).
- The badge participates in the row's `mainAxisAlignment` so it hugs the trailing edge; on very narrow widths the mono key ellipsizes first, the badge never wraps.

### 4.2 Banner — top of scroll body

The banner is the **first child of the detail scroll body**, above the existing priority-badge → title → type/status block, pushing that content down when present:

```
[header row]                     ← §4.1
──────────────────────────────
[NeedsRepairBanner]              ← §3, present only when needsRepair; margin 2/20/4/20
[priority badge]                 ← existing body, unchanged
[title  (AionText.h2)]
[type chip · status]
[Content / File blocks …]
```

When `syncStatus != needsRepair` the banner is not in the tree at all (no reserved gap); its appearance/disappearance animates via the `AnimatedSize` described in §3.4.
