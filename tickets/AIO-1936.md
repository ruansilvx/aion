# Sddstage Transition Preconditions

# Proposal: SddStage Transition Preconditions

Originates from [`aion-arch/ideas/configurable-workflow-and-automation-engine.md`](../../ideas/configurable-workflow-and-automation-engine.md) — the `SddStage` half of that idea's Phase 3 ("pluggable gate behaviors"), scoped down via a 2026-08-31 `/brainstorm` + `/explore` pair.

## Problem

`_sddStageAdvanceCheck` gates every `SddStage` advancement (`exploring`→`verifying`→`proposed`→`designBrief`→`designSync`) through a 5-branch `switch`, each branch running genuinely different, hardcoded Dart precondition logic. A project can reorder, relabel, or skip among these five stages (Phase 1, shipped), but cannot define what it actually takes to *leave* one — the checks themselves are fixed and unconfigurable, unlike `TicketStatus`, `SkillAttachment`, and every `AutomationContext` decision point, all of which are now project-editable.

## What this builds

A project-editable **transition-precondition graph** for each of the 5 `SddStage` values that has a real precondition today (`exploring`, `verifying`, `proposed`, `designBrief`, `designSync` — `null` and `archived` have none and stay untouched). Each graph is a strict binary tree of field checks — structurally the same shape as `automation-decision-graphs`'/`pluggable-decision-graph-conditions`' engine, but **a smaller, parallel set of types**, not a reuse of `DecisionOutcome`/`DecisionNode` themselves (see "Why parallel types, not shared ones" below).

- **Outcome: binary** (`allowed`/`blocked`), not `DecisionOutcome`'s four confidence-shaped values — there is no `AutomationConfidence` involved in a transition precondition at all; it's an unconditional structural gate, evaluated regardless of any confidence setting.
- **Blocking reason: auto-derived**, not a fixed enum. When blocked, the "Not ready" hint shows text built directly from the failing node's own field name (e.g. *"Waiting on: chat reply"*) — no `SddStageBlockReason` enum to maintain, no free-text authoring UI, no override.
- **Fields, not open-ended catalog conditions.** Every check this stage needs is a plain boolean ("does the linked design page have content," "has the most recent chat gotten a terminal reply") — there's no equivalent to `automation-decision-graphs`' fixed-catalog-vs-rule-builder-vs-`agentJudgment` split here, because there's exactly one shape of check. A node is simply "which field, which branch on true/false."
- **Baseline preset, as always.** Each of the 5 stages ships a seeded default graph reproducing today's exact hardcoded check. A project that never opens the new editor sees byte-for-byte identical behavior.

## Why parallel types, not shared ones

A 2026-08-31 `/explore` pass against the actual shipped decision-graph engine found reuse is real but partial:

- **Genuinely reusable:** the `GraphCanvas<T>` primitive (confirmed generic — `class GraphCanvas<T> extends StatefulWidget`, [graph_canvas.dart:95](../../aion/lib/design_system/molecules/graph_canvas.dart:95)) and the dual-pane bidirectional-sync *pattern* `automation-decision-graphs` established.
- **Not reusable as-is:** `TerminalBranch.outcome` is hardcoded `DecisionOutcome` ([decision_node.dart:57](../../aion/lib/core/automation/decision_node.dart:57)); `DecisionFieldSpec.contexts` is hardcoded `List<AutomationContext>` ([decision_field_catalog.dart:52](../../aion/lib/core/automation/decision_field_catalog.dart:52)); `DecisionOutlineList` is concrete, built directly against `AutomationContext`/`DecisionGraphConfigCubit` ([decision_outline_list.dart:26](../../aion/lib/features/providers/presentation/widgets/decision_outline_list.dart:26)), not generic at all.

Generifying those shipped types to serve a second, structurally different consumer (2 outcomes instead of 4, boolean-only fields instead of a fixed-catalog/rule-builder/round-trip split, `SddStage`-keyed instead of `AutomationContext`-keyed) would ripple through code shipped across three already-archived changes for a narrower need. This project has already chosen that tradeoff once — `pluggable-decision-graph-conditions` accepted two separate node catalogs rather than one shared vocabulary — so this proposal builds a small parallel entity/evaluator set (`TransitionOutcome`/`TransitionBranch`/`TransitionNode`, ~2 dozen lines each) and a new, much simpler outline/form pair, while genuinely reusing `GraphCanvas<T>` and the sync pattern.

## Non-goals (deliberately deferred)

- **`TicketStatus`'s design-review gate** (`_codingExecutionGateCheck`). Structurally identical to this proposal and cheap to add later — it reuses the exact same `storyNeedsDesignReview`/`designSyncApproved` fields this proposal already instruments — but deferred as its own fast-follow proposal to keep this one reviewable, per this project's repeated precedent.
- **Non-boolean fields** (e.g. an integer threshold). None of the 5 stages' checks need one; the field-vocabulary-grows-incrementally precedent applies here too.
- **Project-authored new fields.** The 7-field catalog is Aion-authored and fixed for this proposal, same as `automation-decision-graphs`' initial 2-condition catalog was.
- **An `agentJudgment`-equivalent round trip.** Confirmed structurally inapplicable (2026-08-31 `/explore`) — `SddStage` advancement is triggered by UI clicks or automatic status-flip code, never from inside a blocked tool call, so there's no in-flight session to fork.
- **True DAG support.** Strict tree only, matching the sibling engine's own choice and for the same reason (simpler authoring, honest indented-outline rendering).
