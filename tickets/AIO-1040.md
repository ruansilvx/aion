# Kanban Board View

# Proposal: Kanban Board View

## What We Are Building

An alternate **Board** view for the existing `/tickets` screen: tickets
grouped into columns by `TicketStatus`, filtered to `task`/`story` tickets,
with drag-and-drop — plus a keyboard/screen-reader-accessible fallback — to
move a ticket between columns. Reachable via a List/Board toggle inside the
existing `TicketsListScreen` header. No new route, no new screen-level
navigation.

## Why

`TicketsListScreen` today is a single flat list sorted by creation time.
As the ticket count grows, seeing work distributed across its workflow
stages at a glance (todo vs. in-progress vs. done) — the core promise of a
Jira-like tool — is currently impossible without opening tickets one at a
time. This change is also the first to require *editing* an existing
ticket field: every prior slice has been create-and-read only
(`openspec/specs/tickets.md` "Known gaps": *"No ticket editing or
deletion"*). That gap is closed here narrowly — status only, not general
editing.

## Scope

### In

- `TicketRepository.updateTicketStatus(String id, TicketStatus status)` —
  new write path, deliberately narrow (status only, not a general
  ticket-edit capability).
- `TicketDao` UPDATE method + `DriftTicketRepository` implementation.
- `Ticket.copyWith({status, updatedAt})` — minimal, scoped to only the two
  fields this change mutates.
- `TicketsCubit.updateTicketStatus(...)` with two new states
  (`TicketStatusUpdating`, `TicketStatusUpdated`) following the existing
  `ing`/`ed` state-pair convention. The `Updating` state carries an
  optimistically-updated list (instant drag feedback); the `Updated` state
  carries the list re-fetched from the repository.
- New widgets in `presentation/screens/tickets_board_view.dart`:
  `TicketBoardView`, `BoardColumn`, `TicketBoardCard`,
  `MoveToStatusMenu`. All consume the same `TicketsCubit`/`TicketsLoaded`
  stream `TicketsListScreen` already reads — no new repository read method.
- Columns: fixed to `TicketStatus.values` declaration order
  (`backlog, todo, inProgress, inReview, done, cancelled`), all 6 always
  rendered, no configurable order, no new persisted config.
- Type scope: the board renders `TicketType.task` and `TicketType.story`
  tickets only, via a client-side filter over the already-loaded list.
  `epic`, `resource`, `page`, `chat` are excluded from the board (still
  visible in List view, unaffected).
- Drag-and-drop via `Draggable<Ticket>`/`DragTarget<Ticket>`
  (`flutter/widgets.dart`, non-Material); mobile uses
  `LongPressDraggable<Ticket>` instead of `Draggable`, branched via the
  existing `isDesktop`/`isMobile`/`isWeb` helpers in `platform_utils.dart`.
- Non-drag fallback: a "Move to ▸" icon button on every card, opening an
  `AppDropdown`-style `OverlayEntry` listing the other 5 statuses. Required
  so status changes remain keyboard- and screen-reader-operable — a
  drag-only interaction would regress the accessibility bar the rest of
  the app already holds (`Semantics` + `FocusableActionDetector` on every
  interactive primitive).
- An in-screen List/Board view toggle added to `TicketsListScreen`'s
  existing header (next to the avatar). Local widget state — not
  persisted; the screen always opens in List view.
- Unit tests: `TicketsCubit.updateTicketStatus` (`mocktail` + `bloc_test`),
  `DriftTicketRepository.updateTicketStatus` (in-memory Drift).

### Out

- Configurable or persisted column order or per-column visibility/collapse.
- Board support for ticket types other than task/story (no filter UI to
  re-enable them in this change).
- General ticket editing (title, description, priority, type, parent) —
  this change adds status mutation only.
- Persisting the last-used view mode (List vs Board) across app restarts.
- Swimlanes, WIP limits.
- Any change to `TicketDetailScreen` — no status editing is added there.
- Drag autoscroll near column edges, multi-select drag.

## Non-Goals

- Production-quality drag polish beyond the platform (`Draggable` vs.
  `LongPressDraggable`) split already scoped in.
- A settings surface for board configuration — none exists yet and this
  change doesn't introduce one.
- Reordering tickets within a column (position is insertion/creation order,
  same as the list view — no manual card reordering in this change).
