# Spec Delta: Automation Decision Graphs

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/providers.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (65/70 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Relative to `aion-arch/specs/providers.md` (`core/automation/`) and
`aion-arch/specs/tickets.md` (`TicketsCubit`'s `AutomationContext`
consumers). See `proposal.md`/`design.md` for full rationale.

## ADDED

- `DecisionOutcome` (`core/automation/decision_outcome.dart`) —
  `proceed | gated | decline | modelJudgment`.
- `DecisionNode`/`DecisionBranch` (`core/automation/decision_node.dart`)
  — a strict-tree condition node: `id`, `conditionId`, `conditionParams`,
  `matchedBranch`/`unmatchedBranch` (each either a pointer to another
  node or a terminal `DecisionOutcome`). A node may be referenced as a
  child from at most one branch in its graph (strict tree, no
  reconvergence), enforced by `DecisionGraphConfigCubit`.
- `DecisionGraph` (`core/automation/decision_graph.dart`) — `context`
  (`AutomationContext`), `rootNodeId` (`String?`; `null` = always
  `proceed`).
- `DecisionConditionSpec`/`decisionConditionsFor`
  (`core/automation/decision_condition_catalog.dart`) — per-context
  condition catalog. Ships two entries: `attemptExceedsMax`
  (`codingExecutionRetry`), `sessionOverageDetected`
  (`codingExecution`).
- `DecisionGraphRepository` (`core/automation/decision_graph_repository.dart`)
  — `getGraph`/`getNode`/`getAllNodes`/`upsertNode`/`deleteNode`/
  `setRoot`/`seedDefaultsIfEmpty`/`onChanged`. Implemented by
  `DriftDecisionGraphRepository` (`core/automation/data/`), backed by
  two new drift tables: `AutomationDecisionGraphsTable`,
  `AutomationDecisionNodesTable` (schema version 17 → 18, additive
  migration, no FK constraints — matches every other table in this
  schema).
- `evaluateDecisionGraph`/`DecisionEvalContext`
  (`core/automation/decision_graph_evaluator.dart`) — pure evaluator,
  no I/O, unit-testable independent of `TicketsCubit`.
- `DecisionGraphConfigCubit`/`DecisionGraphConfigState`
  (`features/providers/presentation/cubit/`) — CRUD + strict-tree
  invariant enforcement for the editor.
- `GraphCanvas` (`design_system/molecules/graph_canvas.dart`) — Aion's
  first pan/zoom/node-graph widget primitive (`InteractiveViewer` +
  `Stack` + `CustomPainter` edges, no new dependency), generic over a
  node/edge model.
- `DecisionGraphEditorScreen`/`DecisionOutlineList`/`DecisionNodeForm`
  (`features/providers/presentation/screens/`,
  `features/providers/presentation/widgets/`) — dual-pane (canvas +
  nested-outline list) editor per `AutomationContext`, reached from
  `SettingsScreen`'s existing `_AutomationSection`.
- Seeded baseline `DecisionGraph` rows for all eight `AutomationContext`
  values on fresh install and on the schema-18 upgrade path: `null`
  root for `sddStage`/`codingExecutionResume`/`ticketCreation`/
  `ticketLinking`/`specAutoLink`; a single-node graph reproducing the
  pre-existing ad hoc check for `codingExecutionRetry`/
  `codingExecution` (see MODIFIED below).

## MODIFIED

- **Every `AutomationContext` call site's `case AutomationConfidence.auto:`
  branch** (`TicketsCubit._handleCreateTicketToolCall`,
  `_handleAddLinkToolCall`, `_handleBranchToolCall`,
  `_handleCloseBranchToolCall`, the `codingExecution`/
  `codingExecutionRetry` completion/retry paths, and
  `_maybeAutoLinkToSpec`; plus `TicketDetailScreen`'s direct
  `sddStage` confidence read) — now consults
  `_evaluateDecisionGraph(context, ...)` before proceeding.
  `DecisionOutcome.proceed`/`.modelJudgment` behave as `auto` always
  has; `.gated`/`.decline` route through that call site's existing
  gated/decline surfacing mechanism (`_awaitProposalConfirmation`,
  `executionAwaitingReview`, or an outright decline reason) — no new
  surfacing mechanism. `gated`/`manual`-resolved confidence is
  completely unaffected; the graph is only ever consulted once a
  context has already resolved to `auto`.
- **`TicketsCubit._effectiveCodingExecutionRetryConfidence`** — the
  hardcoded `if (attempt > _maxVerifyRetries) return
  AutomationConfidence.gated;` override is removed; the function
  becomes a plain `getConfidence(AutomationContext.codingExecutionRetry)`
  passthrough. The equivalent behavior is now expressed as that
  context's seeded baseline `DecisionGraph` (an `attemptExceedsMax`
  node), evaluated from the new `case auto:` step above. Net behavior
  for a project that never edits its configuration: unchanged.
- **`TicketsCubit._effectiveCodingExecutionConfidence`** — same
  treatment for `_overageDetectedThisSession`, now the
  `sessionOverageDetected` baseline node on `codingExecution`'s graph.
- **`AppDatabase`** (`core/database/app_database.dart`) — schema version
  17 → 18, registering the two new tables.
- **`SettingsScreen`**'s `_AutomationSection` — each `AutomationContext`
  row gains a "Configure decision graph" affordance alongside its
  existing confidence `SelectionMenu`.
- **`TicketsCubit` constructor** — gains an optional
  `DecisionGraphRepository?` parameter, following
  `WorkflowStatusRepository`'s own optional-dependency convention.
  Omitting it pins every context's graph outcome to `proceed`,
  reproducing pre-change behavior exactly.

## Explicitly NOT modified

- `AutomationConfidence`, `AutomationContext`,
  `AutomationSettingsRepository` — unchanged in every respect.
- `TicketsCubit._canBranch`'s branch-depth cap — stays an unconditional
  pre-check, independent of `AutomationConfidence`/this graph mechanism
  entirely (see `design.md` §4 for why this one specifically isn't
  migrated).
- `TicketStatus`/`SddStage` transition preconditions
  (`_interceptTaskExecutionTrigger`, `_sddStageAdvanceCheck`,
  `_codingExecutionGateCheck`) — out of scope; deferred to a future
  proposal under `configurable-workflow-and-automation-engine`'s
  Phase 3.

## REMOVED

- None. The two ad hoc hardcoded checks described under MODIFIED are
  relocated into baseline data, not removed as behavior — a project
  that changes nothing sees byte-for-byte identical results.
