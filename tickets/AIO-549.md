# Configurable Ticket Workflow

# Proposal: Configurable Ticket Workflow (Phase 1)

## Why

`aion-arch/ideas/configurable-workflow-and-automation-engine.md` (status:
`explored`) captured the vision of a project-defined workflow-automation
engine, then explicitly phased it after a grounded `/explore` pass found
the two axes aren't equally feasible to build at once. This proposal is
**Phase 1 only**: making `TicketStatus` and `SddStage` project-configurable
data instead of fixed Dart enums, with every existing gate/trigger
(coding-execution start, the review-ready transition, the blocked-
dependency check, the design gate) remapped onto whatever a project
configures — no new gate *types*, no skill attachment. Those are Phase 2
(any-named-skill attachment) and Phase 3 (pluggable gate behaviors),
each its own future proposal.

Today, `TicketStatus` (`backlog | todo | inProgress | inReview | done |
cancelled`) and `SddStage` (`exploring | proposed | designBrief |
designSync | verifying | archived`) are fixed enums baked into
`TicketsCubit`. A project that doesn't want a review column, wants a
"Needs repro" status for bugs, or never wants a design-review stage at
all (a backend-only project has no UI to design-review) has no way to
express that — it's stuck with Aion's own opinionated defaults forever.
[[not-all-projects-will-require-design]] and this idea's own status
history exist precisely because that's a real, previously-raised gap.

## What

### `TicketStatus` — genuinely project-defined, shared base + per-type extensions

- `Ticket.status` changes from the fixed `TicketStatus` enum to a plain
  `String` (a project-defined status name) — the storage column was
  already a raw `TextColumn`, so this needs no database schema change to
  the `tickets` table itself, only a Dart-side type change.
- A new per-project `WorkflowStatus` list (new drift table) replaces the
  enum: each entry has a `name` (the string written to `Ticket.status`),
  a `displayName`, an optional `ticketType` (`null` = shared base, applies
  to every type; non-`null` = an extension scoped to one type, e.g. a
  `bug`-only "Needs repro"), a `sortOrder`, and an optional **role**.
- Exactly three semantic roles exist, matching every place `TicketsCubit`
  gates on a literal `TicketStatus` value today: `executionTrigger` (today's
  `inProgress` — starts coding execution, is what the blocked-dependency
  gate checks against), `reviewReady` (today's `inReview` — where a
  successful coding-execution run auto-lands), and `done` (today's `done`
  — what the blocked-dependency gate's blocker-resolution and both
  `SddStage.proposed`/`designSync` children-completion checks require).
  Roles are restricted to the **shared base set only** in Phase 1 — a
  per-type extension status can never hold a role, because "done"/
  "executionTrigger" must resolve consistently for a blocker or child of
  *any* type, not just the type an extension was added for.
- A project's actual current hardcoded behavior ships as the seeded
  default baseline (`backlog`/`todo`/`inProgress`[`executionTrigger`]/
  `inReview`[`reviewReady`]/`done`[`done`]/`cancelled`) — a project that
  never opens the new settings screen behaves exactly as Aion does today.
- **Correction carried over from `/explore`:** "blocked" is not, and will
  not become, a configurable status. It's already a derived, type-agnostic
  UI state computed from unresolved `blocks`/`blockedBy` dependencies,
  layered on top of whatever status a ticket is in — untouched by this
  change.

### `SddStage` — narrowed from the idea file's "reorder/relabel/skip"

The idea file's Phase 1 conclusion allowed reorder/relabel/skip. This
proposal narrows that to **toggle + relabel only, no reorder**, and flags
it here explicitly for review rather than deciding it silently:

`_sddStageAdvanceCheck`'s five branches are bespoke, hand-written
precondition code chained to each other's *specific* prior-stage
artifacts (`designSync`'s check needs `designBrief`'s design Page to
already exist; `proposed`'s check needs specific child-ticket shapes).
Reordering them isn't safe without first decomposing that chain into
reusable primitives — real design work this proposal doesn't do, and
realistically Phase 3 (pluggable gates) territory. Removing/reordering
`exploring`/`proposed`/`verifying`/`archived` is out of scope for the same
reason; they're structural anchors other code depends on.

What Phase 1 *does* deliver for `SddStage`:

- A project-level `designStagesEnabled` toggle (default `true`, matching
  today's behavior). When `false`, every Story skips `designBrief`/
  `designSync` unconditionally — generalizing today's automatic
  per-Story-child-signal heuristic (`_storyNeedsDesignReview`) from
  "detected automatically, no override" to "detected automatically by
  default, or turned off project-wide." This alone fully satisfies
  [[not-all-projects-will-require-design]]'s original want.
  When `true` (the default), today's existing per-Story heuristic is
  completely unchanged.
- Per-stage display-name overrides (a project can relabel "Verifying" to
  whatever it prefers), stored the same way `AutomationSettingsRepository`
  already stores `AutomationConfidence` — a small `shared_preferences`-backed
  repository keyed by the existing fixed `SddStage` enum. This is the
  correct-fit precedent per `/explore` (not `ProjectOverride`, which only
  shadows bundled files).

### New Settings surface

One new screen, `WorkflowStatusSettingsScreen`, reached from the same
secondary-actions popover as the existing provider `SettingsScreen`
(`WorkspaceNavShell`), with two sections: **Ticket Statuses** (add/rename/
reorder/delete base statuses and per-type extensions; reassign the three
required roles, with a Cubit-level invariant blocking a delete/
reassignment that would leave a role unfilled) and **SDD Stages** (the
`designStagesEnabled` toggle + the five display-name override fields).

## Non-goals

- **No skill attachment of any kind** — Phase 2's entire scope
  (`configurable-workflow-and-automation-engine.md`'s Phase 2). A status
  can be configured, but nothing can be attached to fire automatically
  when a ticket enters it.
- **No new computed-confidence signal** — already resolved during
  brainstorm; not revisited here since nothing in Phase 1 needs it.
- **No pluggable gate *types*.** A project chooses *which* configured
  status/stage occupies an existing semantic role or toggle; it cannot
  invent a new kind of precondition (e.g. reviewer approval) — that's
  Phase 3.
- **No `SddStage` reordering, removal, or brand-new stages** — narrowed
  from the idea file per the flagged reasoning above. Only toggle
  (design stages on/off) + relabel.
- **No per-type role assignment** for `TicketStatus` — roles live on the
  shared base set only, per the "done" cross-type-resolution constraint
  above.
- **No migration UI** for what happens to existing tickets when a
  project later renames/removes a status they're sitting on — this
  proposal seeds the baseline default and lets a project *add* to it, but
  doesn't yet handle the destructive-edit case. Left as an explicit open
  question in the idea file; may need its own follow-up proposal once a
  project actually attempts it.
