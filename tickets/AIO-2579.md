# V1 Ticket Slice

# Proposal: v1 Ticket Slice

## What We Are Building

The first vertical slice of Aion: a working Ticket List + Create flow that
touches every architectural layer end-to-end. Users can create tickets, view
a list of all tickets, and tap into a ticket detail view.

## Why

The codebase is a blank Flutter scaffold. Before adding any breadth (agent
chat, watcher system, agentic coding), the foundational architecture must be
validated with a real feature. The Ticket is the central concept of the entire
app — every other entity (epic, story, task, resource, page, chat) is a
ticket variant. Getting the schema, repository pattern, and BLoC conventions
right here unblocks everything that follows.

## Scope

### In
- `Ticket` domain entity with fields: id, ticketId (human-readable), type
  (enum), title, description, status (enum), parent_id (nullable
  self-reference for linking), embedding (nullable BLOB for future semantic
  memory), created_at, updated_at.
- Human-readable ticket identifier: configurable prefix (e.g. `AIO`) +
  auto-incrementing integer sequence, one sequence per project, not per type.
  Stored as a separate `ticket_id` column (e.g. `AIO-1`). Internal UUID
  `id` remains the primary key used for all relations. Both present in the
  initial schema; no migration path needed if included from the start.
- Drift `tickets` table + DAO.
- `TicketRepository` interface (domain layer).
- `DriftTicketRepository` implementation (data layer).
- `TicketsCubit` — list all tickets, create a ticket.
- Three screens: Ticket List, Create Ticket, Ticket Detail.
- go_router wiring with clean-path URL strategy (web default).
- Platform-aware shell (guard hook ready for desktop-only features).
- Design system foundation: a single `lib/core/theme/` source of truth for
  color, typography, spacing, radii, and shadow tokens — defined as plain
  Dart classes, not as Material tokens or extensions on `ThemeData`. Theme
  accessed via `ThemeScope` (an `InheritedWidget`) — not `Theme.of(context)`.
  All v1 widgets consume tokens from this source; no hardcoded values in
  widget code. Minimal scope; a fuller design system is a future epic.
- No Material dependency in the theme layer or widget code. App root uses
  `WidgetsApp` (or `CupertinoApp` if Cupertino scroll physics are desired).
  Widgets are built from Flutter primitives (`Container`, `GestureDetector`,
  `CustomPaint`, `RawKeyboardListener`, etc.) or a thin in-house component
  layer. Any unavoidable Material coupling (e.g. `TextField` internals) is
  explicitly flagged in `design.md` with the chosen mitigation.
- Priority field: `priority` enum (`critical | high | medium | low | none`,
  default `none`) on the base ticket table. Surfaced in the create form and
  as a visible priority indicator on ticket cards in the list.
- Generic link table (`ticket_links`): `id`, `source_ticket_id`,
  `target_ticket_id`, `link_type` enum (`blocks | blocked_by | relates_to |
  duplicates | duplicated_by`). Non-hierarchical relationships only — the
  structural parent/child hierarchy remains exclusively on the `parent_id`
  column of the ticket table. No link UI in this slice; schema and domain
  layer only.
- Subtask convention: no dedicated subtask ticket type. A `task` with a
  `parent_id` pointing to another `task` or `story` is the subtask pattern.
  Documented in design.md; no schema change.
- Estimate and time-spent fields: nullable `estimate` and `time_spent`
  (integers, units: minutes) on the base ticket table. No UI in this slice.
  Rollup invariant documented: parent totals are always derived from
  structural children (`parent_id` tree), never from linked tickets
  (`ticket_links` table).
- Comments table (`ticket_comments`): `id`, `ticket_id`, `content` (plain
  text), `author_type` enum (`human | ai`), `ai_model` (nullable string),
  `created_at`. Append-only in this slice. Rendered as a list + text input
  at the bottom of the ticket detail view. Human vs. AI comments visually
  distinguishable. Comments bypass the watcher scheduled-changes gate —
  documented as a core semantic invariant.
- Basic accessibility: semantic labels on all interactive elements (buttons,
  form fields), adequate color contrast in both theme variants, and working
  keyboard/focus navigation on list and forms. Built in from the start, not
  retrofitted.
- Unit tests: `TicketsCubit`, `DriftTicketRepository` (in-memory Drift),
  `CommentRepository` (in-memory Drift).
- Drift web WASM init path verified.
- `project.md` updated: web clean-path Firebase Hosting requirement documented.

### Out
- Agent chat, watcher system, agentic coding engine.
- Embedding generation (column present, population deferred).
- Ticket editing or deletion.
- Search, filtering, sorting.
- Any cloud/AI model calls.
- Git versioning of tickets.
- Multi-project support (prefix is configurable but a single project is
  assumed in v1; multi-project sequencing is a future concern).
- Fuller design system (component library, motion tokens, etc.).

## Non-Goals
- Production-quality UI polish beyond the design token discipline.
- Full WCAG audit (basic a11y is in scope; exhaustive audit is not).
- CI/CD setup.
- Replicating the full Material component set in-house (this slice builds
  only what v1 screens need).
