# `decision_field_catalog.dart` (new) — `DecisionFieldType` enum

(`integer | boolean`); `DecisionFieldSpec` (`id`, `displayName`,
`type`, `contexts`); `decisionFieldCatalog` (two entries:
`attemptField`, `sessionOverageDetectedField` — see design.md §1
for exact field values); `decisionFieldsFor(AutomationContext)`.
`DecisionRuleOperator` enum (`equals | notEquals | greaterThan |
greaterThanOrEqual | lessThan | lessThanOrEqual`);
`operatorsFor(DecisionFieldType)`. `ruleBuilderConditionId`
constant; `ruleBuilderConditionSpec(AutomationContext)`;
`defaultRuleConditionParams(AutomationContext)`;
`isRecognizedConditionId(String, AutomationContext)`;
`decisionNodeTitle(DecisionNode)`; `decisionNodeSummary(DecisionNode)`.
File header + dartdoc on every public symbol, per design.md §1.
**Scope note:** `decisionFieldCatalog` ships exactly the two
entries above (`attemptField`/`sessionOverageDetectedField`) —
design.md (Component Spec) §1.1's field table illustrates a much
larger 12-field vocabulary (`attemptCount`, `estimatedCost`,
`filesTouched`, `diffLines`, `modelConfidence`, `ticketDepth`,
`elapsedMinutes`, `protectedPath`, `outsideWorkHours`,
`budgetOverage`, `openQuestions`, `ticketBlocked`) for visual/menu
reference only. None of those ten additional fields have a backing
`DecisionEvalContext` signal today — building them is explicitly
out of scope per proposal.md's Non-goals ("Expanding
`DecisionEvalContext` to the other 6 `AutomationContext` values").
Do not add catalog entries beyond the two this task lists; the
picker UI is generic over `decisionFieldsFor(context)`; so it
renders correctly with just these two rows even though the
Component Spec's mockups show a fuller menu. Note also the id
naming mismatch: the Component Spec's illustrative ids
(`attemptCount`, `budgetOverage`) are not the real Dart identifiers
— use `attempt`/`sessionOverageDetected` as specified above,
matching `DecisionEvalContext`'s actual field names.
