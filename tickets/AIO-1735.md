# Reconciler Applies Hand Edited Parentid Deletedat

# Proposal: Reconciler applies hand-edited parentId/deletedAt changes

## What

`TicketMarkdownReconciler` — the background service that reconciles a
hand-edited `resource`/`page` Markdown file back into the database —
currently parses `parentId` and `deletedAt` from the file's frontmatter
but never applies either: a hand-edited `parentId` (reparent) or
`deletedAt` (trash/restore) is silently ignored, and the ticket ends up
`synced` regardless.

This change makes the reconciler actually apply both:

- A changed `parentId` is validated and applied through the same
  cycle-prevention/type-compatibility rules `TicketsCubit` already
  enforces for an in-app reparent.
- A changed `deletedAt` (`null` → timestamp = trash; timestamp → `null`
  = restore) is applied through the same repository calls that already
  carry ancestor/descendant cascade logic for trash/restore.
- If either is rejected (e.g. a hand-edited `parentId` would create a
  cycle), the ticket's `syncStatus` flips to `needsRepair` instead of
  silently keeping the database's old value, so the rejection is visible
  instead of invisible.

## Why

Two known gaps, documented in `aion-arch/specs/tickets.md`'s Known Gaps
section and explored in
`aion-arch/ideas/reconciler-applies-hand-edited-parentid-deletedat.md`:
reparenting via a hand-edited file's `parentId` is not applied by the
reconciler, and restoring/trashing via a hand-edited file's `deletedAt`
is not applied either. Both fields already round-trip through
`TicketMarkdownSerializer`'s frontmatter — a user editing a ticket's
`.md` file directly (the primary workflow for `resource`/`page` tickets)
has every reason to expect these edits to take effect the same way a
title or priority edit already does, and today they silently don't.

## Why now, and why this shape

Domain logic for both operations (cycle-prevention for reparenting,
cascade logic for trash/restore) needs to run wherever these values are
applied, but it lives in the UI-facing `TicketsCubit`/`TrashCubit`
methods today, which are unsuitable for a background caller to reuse
directly:

- `TicketsCubit.updateTicketParent`/`.trashTicket` are UI-state-coupled
  — `trashTicket` reads the cubit's current `state` to decide what to
  emit next, and both emit states (`TicketDetailLoaded`, `TicketsError`,
  `TicketsLoaded`, `TicketTrashing`/`Trashed`) meant to drive whichever
  screen is currently open. Calling them from the reconciler risks
  visibly disrupting an unrelated open screen.
- `TrashCubit` (which owns `restore`) is route-scoped — it's only
  constructed while the `/workspace/tickets/trash` route is mounted, so
  the reconciler, a workspace-lifecycle background service, can't hold a
  stable reference to it.

Per this codebase's existing precedent for exactly this dual-caller
shape — `PageWikilinkIndexer`, a plain (non-`Cubit`) `data/services/`
class shared by `TicketsCubit.updateTicket` (in-app edits) and
`TicketMarkdownReconciler` (external file edits) — this change follows
the same pattern: a new plain service, `TicketParentTrashService`, holds
the parentId/trash/restore domain logic and is injected into both
`TicketsCubit`/`TrashCubit` (which keep their own UI-state-emitting
wrappers around it) and `TicketMarkdownReconciler` (which has no UI
state to emit). This keeps domain logic in a Cubit-adjacent, non-widget
layer rather than pushing it down into `TicketRepository` — consistent
with this project's Cubit-holds-domain-logic convention — while giving
the reconciler (and, as a side benefit below, `TicketRepairService`) a
call shape that's safe for a non-widget caller.

Because the shared logic lives in a plain service rather than requiring
a `TicketsCubit`/`TrashCubit` reference, no restructuring of
`WorkspaceShell`'s provider/build order is needed — the new service is
constructed at the same DI scope `TicketMarkdownReconciler` already sits
at in `app_router.dart`, alongside `TicketGitProjector`.

**Side effect requiring a fix in scope:** `TicketRepairService.reformat`
(the "Reformat" repair action for a `needsRepair` ticket) currently
assumes the only way a `resource`/`page` ticket becomes `needsRepair` is
`Unparseable` content — its success check is "does the file re-parse
after trimming trailing whitespace." Once a rejected `parentId`/
`deletedAt` becomes a second cause of `needsRepair`, that file *already*
re-parses fine (`ParsedOk`/`ParsedPartial`) — `reformat` would trim
whitespace, mark the ticket `synced`, and silently leave the file's
parentId/deletedAt value permanently mismatched with the database until
some unrelated future edit re-triggers reconcile. This change fixes
`reformat` to also re-run the same parentId/deletedAt check (via the new
`TicketParentTrashService.applyFromParsedFields`, shared with the
reconciler) before declaring success, falling back to
`restoreFromLastKnownGood` — already correct, since it unconditionally
overwrites the file from the database — when the value is still
rejected.

## Non-goals

- No new UI. `needsRepair`'s existing sync-status badge and repair
  banner/actions (`sync_status_badge.dart`,
  `ticket_needs_repair_banner.dart`, `TicketRepairCubit`) already cover
  this cause the same way they cover `Unparseable` — this change adds a
  second trigger for an existing, already-designed state, not new
  screens or copy.
- No change to batch trash (`TicketsCubit.trashTickets`) — the
  reconciler only ever reconciles one ticket (one file) at a time, so
  only the single-ticket `trashTicket`/`restoreTicket` paths are in
  scope.
- No change to `bin/ticket_lint.dart` (the standalone, DB-less CLI) —
  it never sets `syncStatus` itself, so the `reformat` fix above doesn't
  apply to it.
- No change to `getValidParentCandidates`/`getValidParentCandidatesForType`
  (picker-list queries) — unrelated to applying a change, left untouched.
