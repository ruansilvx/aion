# Design: sdd-design-gate

## 1. `SddStage` enum

`lib/features/tickets/domain/enums/sdd_stage.dart` grows two new values,
inserted in cycle order:

```dart
enum SddStage {
  exploring,
  proposed,
  designBrief,  // NEW
  designSync,   // NEW
  verifying,
  archived,
}
```

Dartdoc on the enum itself is rewritten to describe the full 6-stage
cycle and note that `designBrief`/`designSync` are skippable — only
`TicketType.story` tickets whose child Tasks indicate UI work pass
through them; every other Story, and every Epic, goes `proposed` →
`verifying` directly, unchanged from today. `SddStage` is persisted as
plain `.name` text (`sdd_stage` column) with no DB-level constraint, so
this needs **no drift migration**.

## 2. `TicketsCubit._nextSddStage` — becomes ticket-aware and async

Today:

```dart
SddStage? _nextSddStage(SddStage? current) => switch (current) {
  null => SddStage.exploring,
  SddStage.exploring => SddStage.proposed,
  SddStage.proposed => SddStage.verifying,
  SddStage.verifying => SddStage.archived,
  SddStage.archived => null,
};
```

Becomes:

```dart
/// The next [SddStage] after [ticket]'s current one, or `null` if
/// already [SddStage.archived]. Async because the `proposed → ?`
/// branch must inspect [ticket]'s child Tasks (via
/// [TicketRepository.getTicketsByParent]) to decide between
/// [SddStage.designBrief] and [SddStage.verifying] — see
/// [_storyNeedsDesignReview].
Future<SddStage?> _nextSddStage(Ticket ticket) async {
  switch (ticket.sddStage) {
    case null:
      return SddStage.exploring;
    case SddStage.exploring:
      return SddStage.proposed;
    case SddStage.proposed:
      if (ticket.type != TicketType.story) return SddStage.verifying;
      final tasks = await _repository.getTicketsByParent(
        ticket.id,
        types: const [TicketType.task],
      );
      return _storyNeedsDesignReview(tasks)
          ? SddStage.designBrief
          : SddStage.verifying;
    case SddStage.designBrief:
      return SddStage.designSync;
    case SddStage.designSync:
      return SddStage.verifying;
    case SddStage.verifying:
      return SddStage.archived;
    case SddStage.archived:
      return null;
  }
}
```

Every call site (`advanceSddStage`, `_sddStageAdvanceCheck`) updates to
`await _nextSddStage(ticket)` instead of the old sync
`_nextSddStage(ticket.sddStage)`.

### `_storyNeedsDesignReview`

```dart
/// Whether any of [tasks] indicates UI work, using the same keyword
/// heuristic `/propose`'s own design-gate block already applies to a
/// change's touched files — here applied to each Task's title +
/// description instead of a file path. Case-insensitive substring match
/// against: "widget", "screen", "component", "ui". Computed fresh every
/// time, not persisted — mirrors how the existing `proposed` precondition
/// already re-fetches children on every check rather than caching.
bool _storyNeedsDesignReview(List<Ticket> tasks) {
  const keywords = ['widget', 'screen', 'component', 'ui'];
  return tasks.any((t) {
    final text = '${t.title} ${t.description ?? ''}'.toLowerCase();
    return keywords.any(text.contains);
  });
}
```

This only runs once `proposed`'s existing precondition (all Tasks exist
and are `done`) already passed — it decides *where* to advance to, not
*whether* advancing out of `proposed` is allowed. That existing
precondition is unchanged.

### `_linkedDesignPage`

```dart
/// The `page`-type ticket linked to [storyId] whose title matches the
/// deterministic "Design — <title>" naming [_spawnStageChat] gives it —
/// the same identify-by-naming-convention approach used nowhere else in
/// the codebase today, adopted here specifically to avoid a new schema
/// field just to mark "this is the design page." Returns `null` if
/// constructed without a [TicketLinkRepository], or if no such link
/// exists yet.
Future<Ticket?> _linkedDesignPage(String storyId) async {
  final linkRepo = _linkRepository;
  if (linkRepo == null) return null;
  final links = await linkRepo.getLinksForTicket(storyId);
  for (final link in links) {
    final otherId = link.sourceTicketId == storyId
        ? link.targetTicketId
        : link.sourceTicketId;
    final other = await _repository.getTicketById(otherId);
    if (other != null &&
        other.type == TicketType.page &&
        other.title.startsWith('Design — ')) {
      return other;
    }
  }
  return null;
}
```

### `_designSyncApproved`

```dart
/// Whether [storyId]'s `designSync`-stage chat's most recent comment is
/// an [CommentAuthorType.ai] reply whose content contains the literal
/// line `DESIGN GATE: APPROVED` — mirrors `/design-sync`'s own
/// final-summary line format (`SKILL.md`'s Step 4). Unlike
/// `_mostRecentChatHasTerminalReply` (any AI reply = ready), this checks
/// the reply's *content*, since a `PENDING` verdict must not unblock
/// advancement — see [retryDesignSync] for how a fresh verdict gets
/// produced after a `PENDING` result.
Future<bool> _designSyncApproved(String storyId) async {
  final commentRepo = _commentRepository;
  if (commentRepo == null) return false;
  final chats = await _repository.getTicketsByParent(
    storyId,
    types: const [TicketType.chat],
  );
  final designSyncChat = chats
      .where((c) => c.title.startsWith('Design Sync — '))
      .toList()
    ..sort((a, b) => b.createdAt.compareTo(a.createdAt));
  if (designSyncChat.isEmpty) return false;
  final comments = await commentRepo.getCommentsForTicket(
    designSyncChat.first.id,
  );
  if (comments.isEmpty) return false;
  final mostRecent = comments.reduce(
    (a, b) => a.createdAt.isAfter(b.createdAt) ? a : b,
  );
  return mostRecent.authorType == CommentAuthorType.ai &&
      mostRecent.content.contains('DESIGN GATE: APPROVED');
}
```

### `_readTokenFilesForContext`

```dart
/// Reads `aion_colors.dart`/`aion_text.dart`/`aion_radius.dart`'s
/// contents off disk for inclusion as plain-text context — the same
/// static-injection approach `/design-brief`/`/design-sync`'s own
/// `SKILL.md` `cat`s these files for, ported to Dart `File.readAsString`.
/// No tool access involved; this is [TicketsCubit] reading files for
/// context assembly, the same category of desktop-only capability
/// [_gitProjector]/[_projectRootPath] already gates. Returns an empty
/// string (not an error) if [_projectRootPath] is unset or a file is
/// missing — mobile/web has neither a filesystem root nor UI Story
/// design-gate stages triggering in practice (Task/Story execution is
/// desktop-only already), so this degrades gracefully rather than
/// throwing.
Future<String> _readTokenFilesForContext() async {
  final root = _projectRootPath;
  if (root == null) return '';
  const relativePaths = [
    'lib/design_system/tokens/aion_colors.dart',
    'lib/design_system/tokens/aion_text.dart',
    'lib/design_system/tokens/aion_radius.dart',
  ];
  final buffer = StringBuffer();
  for (final relativePath in relativePaths) {
    final file = File(p.join(root, relativePath));
    if (await file.exists()) {
      buffer
        ..writeln('### $relativePath')
        ..writeln(await file.readAsString());
    }
  }
  return buffer.toString();
}
```

(`dart:io File` and `package:path` as `p` are new imports in
`tickets_cubit.dart` — both already transitive Flutter/pub dependencies,
neither needs adding to `pubspec.yaml`.)

## 6. `TicketsCubit.retryDesignSync` — new public method

```dart
/// Re-runs `designSync`'s validation in place, after the human has
/// edited the linked design Page to address a `PENDING` verdict.
/// Re-assembles fresh context (the Page's *current* content — unlike a
/// plain user chat reply, which wouldn't automatically pick up an
/// edit made outside the chat) and posts another turn to the existing
/// `designSyncChat`, via the same [ChatCubit.runChatTurn] helper
/// [_spawnStageChat] uses. No-ops (returns without posting) if
/// [designSyncChat] isn't a `chat` ticket, its parent isn't at
/// [SddStage.designSync], or the cubit was constructed without an
/// [AgentModelClient]/[CommentRepository].
Future<void> retryDesignSync(Ticket designSyncChat) async {
  if (designSyncChat.type != TicketType.chat) return;
  final client = _agentClient;
  final commentRepo = _commentRepository;
  if (client == null || commentRepo == null) return;
  final parentId = designSyncChat.parentId;
  if (parentId == null) return;
  final parent = await _repository.getTicketById(parentId);
  if (parent == null || parent.sddStage != SddStage.designSync) return;

  final context = await _assembleStageContext(parent, SddStage.designSync);
  await commentRepo.addComment(
    TicketComment(
      id: '',
      ticketId: designSyncChat.id,
      content: context,
      authorType: CommentAuthorType.system,
      createdAt: DateTime.now(),
    ),
  );
  await ChatCubit.runChatTurn(
    client: client,
    commentRepo: commentRepo,
    chatTicketId: designSyncChat.id,
    prompt: context,
    model: AgentModel.sonnet,
  );
}
```

# Aion — SDD Design Gate: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and the [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TicketDetailScreen`, and the existing `_SddStageSection` by name.

This change ports a CLI design-review round-trip into Aion's ticket-driven SDD cycle. For a Story whose work touches UI, it inserts **two new stages** — **Design Brief** and **Design Sync** — between Propose and Verify, growing the stage tracker from 4 nodes to 6. A Story confirmed not to need design work keeps the existing 4-node tracker unchanged. It also adds one small **"Retry validation"** control to a Design-Sync `chat`-ticket's detail screen.

It **adds no new screens** — it extends two existing surfaces:

- **`TicketDetailScreen`** (`story` tickets) — the existing `_SddStageSection` becomes variable-length (§1), gains two new not-ready hint messages (§2), a parameterized gated banner (§3), and an optional linked-design-page chip (§5).
- **`TicketDetailScreen`** (`chat` tickets) — a new "Retry validation" button above the composer (§4).

**No Material widgets anywhere.** Every surface is `DecoratedBox` / `Padding` / `Row` / `Column` / `GestureDetector` / `AnimatedContainer` / `AnimatedSize` / `CustomPaint` / `SingleChildScrollView`. No `Card`, `ElevatedButton`, `TextButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `DropdownButton`, `InkWell`, or `Chip`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` with the theme's `fillAlpha` (Arctic `0.11`, Obsidian `0.16`) unless another alpha is stated.

**No new color, typography, or radius tokens are required for the tracker, hints, banner, or button.** Two design-system tokens the base spec references are used here for the first time in the SDD surface — `typePage` (`#B0499E / #D98CE6`) and `typeChat` (`#4C6FDE / #7C93FF`); if they are not yet present in `AionColors`, add them per §6. One small structural addition: the `SddStage` enum gains `designBrief` and `designSync` values, and each Story carries a `needsDesign` bool. See §6.

## 1. Variable-length stage tracker

Extends the existing `_SddStageSection` tracker (SDD Ticket Execution spec §2.1). The stage set is no longer fixed at four; it is derived from the Story's `needsDesign` flag:

- `needsDesign == false` → `[explore, propose, verify, archive]` (4 nodes — unchanged from today).
- `needsDesign == true` → `[explore, propose, designBrief, designSync, verify, archive]` (6 nodes).

All node/connector/label **visual language is identical to the existing tracker** — only the node count, the per-node cell width, and the label font size change with count (§1.4). Nodes keep their three states (Complete / Current / Future) exactly as specified in the base SDD spec §2.1; those are restated in §1.2 for completeness.

### 1.1 Row structure

- Layout: `Row`, `crossAxisAlignment: start`, alternating **step cells** and **connectors**.
- Each **step cell** = `SizedBox(width: cellW)` → `Column`, `crossAxisAlignment: center`, `gap: 6`:
  - **Node:** `18×18` circle (`DecoratedBox`, `BoxShape.circle`).
  - **Label:** the step name, `AionText.time` (JetBrains Mono, w400) at the per-count size (§1.4), `SizedBox(width: cellW)`, `TextAlign.center`, `height: 1.18`, wrapping to a second line when needed ("Design Brief" → "Design" / "Brief"). Nodes are top-aligned, so an unequal label height between cells never shifts a node.
- Each **connector** = `Expanded` → `Container(height: 2, margin: EdgeInsets.only(top: 8, left: connGap, right: connGap))`. Sits at the vertical center of the `18` node (`top: 8`).

### 1.2 Node + connector visuals by state

Identical to base SDD spec §2.1:

| Step relation | Node fill | Node border | Node glyph | Connector to its right | Label color / weight |
|---|---|---|---|---|---|
| **Complete** (past) | `primary` (`#2E86D4 / #9366FF`) | none | `check` `10px` `#FFFFFF` | `primary`, 2px solid | `textSecondary`, w400 |
| **Current** | `primary` | none | filled `6×6` inner dot `#FFFFFF` | `border` (`#D6E0EA / #232C40`), 2px solid | `primary`, **w700** |
| **Future** | `surface` (`#FBFCFE / #131A29`) | `1.5px solid borderStrong` (`#BAC8D6 / #35415C`) | none | `border`, 2px solid | `textMuted` (`#8496A6 / #6B7690`), w400 |

Connector color rule: solid `primary` for every connector whose **left** node is Complete or Current (`index < currentIndex`), else `border`. Design Brief and Design Sync are ordinary stages in this scheme — no special node treatment; they read as Complete / Current / Future like any other node.

### 1.3 Current-stage line (extends base §2.1)

Below the rail (`gap: 14` from it), the existing current-stage line: `Row`, `gap: 8` — an `8×8` filled `primary` dot + text, `AionText.body` (15 / w500), color `textPrimary`. The stage→display-name map gains two entries; the two new stages use their **plain name** (they read naturally as-is, unlike the present-progressive forms of the original stages):

| Stage | Line text |
|---|---|
| `explore` | `"Exploring"` |
| `propose` | `"Proposed"` |
| `designBrief` | `"Design Brief"` |
| `designSync` | `"Design Sync"` |
| `verify` | `"Verifying"` |
| `archive` | `"Archived"` |
| `null` | `"Not started"` |

### 1.4 6-node vs 4-node layout + overflow behavior

The section's inner content width on the narrowest supported phone is `380 − 2×22 = 336`. Node spacing **shrinks** with count; it does not scroll at supported phone widths.

| Count | `cellW` | Label size | `connGap` | Total cells | Result |
|---|---|---|---|---|---|
| **4** (unchanged) | `54` | `11` (`AionText.time`) | `4` | `216` | connectors take the remaining `~120` (≈`40` each); labels single-line. |
| **6** | `46` | `10` | `3` | `276` | connectors take the remaining `~60` (≈`14` each after `connGap`); labels wrap to 2 lines. |

- The 6-node label drops from `11` to `10` (still `AionText.time` family/weight) purely to keep two-word labels legible at `46` width — the only per-count typography change. If a strict single `AionText.time` size is required, keep `11` and reduce `cellW` to `44`; the mockup uses `10` for cleaner wrapping.
- **Narrow-width fallback (below `336` content width, e.g. a split-view pane):** wrap the tracker `Row` in a horizontal `SingleChildScrollView` (`physics: ClampingScrollPhysics`, no scrollbar chrome) so the 6-node row scrolls horizontally rather than compressing nodes below `44` or clipping labels. On first build for a Story whose current stage is off-screen, jump the offset so the **current** node is visible (via `ScrollController.jumpTo`, not `animateTo` — no entrance animation). At all supported phone widths (`≥ 336`) the full row fits and no scroll occurs.

## 3. Design-gate footer banner (gated confidence) — parameterized (extends base §2.3)

One **minimal distinguishing accent** ties the design stages to the linked design Page: the banner's leading glyph.

### 3.1 Container, button, dismiss — unchanged

Identical to base §2.3: fill `primary.withOpacity(fillAlpha)` (`0.11 / 0.16`); border `1px solid primary.withOpacity(isDark ? 0.42 : 0.28)`; radius `BorderRadius.circular(12)` (`AionRadius.lg`); padding `EdgeInsets.fromLTRB(14, 12, 12, 12)`; `Row`, `gap: 12`, `crossAxisAlignment: center`. Text column `Expanded`, `gap: 2`. Compact primary **Advance** button (`primary` fill, `#FFFFFF` `AionText.button`, `EdgeInsets.symmetric(horizontal: 15, vertical: 9)`, radius `AionRadius.md`, FAB glow `primary.withOpacity(isDark ? 0.60 : 0.45)`). Dismiss `26×26` `close` glyph `13px` `textMuted`, radius `AionRadius.iconBtnSm`.

### 3.2 Leading glyph — stage-aware

- When the current stage is `designBrief` or `designSync`: leading glyph is a `pencil` / page-edit motif (`✎`), `18px`, color **`typePage`** (`#B0499E / #D98CE6`). This is the sole visual signal that the banner belongs to a design stage — it echoes the linked design Page's accent (§5). The banner fill/border and the confirm button stay `primary` (the universal action color), so the accent reads as a quiet tint on one glyph, not a competing color scheme.
- For every other stage (`explore`, `propose`, `verify`): leading glyph is the existing `sparkle` (`✦`), `18px`, color `primary` — unchanged.

### 3.3 Copy — parameterized by target stage

Title = `"Ready to advance to " + nextStageDisplayName`. Sub = the met precondition, `AionText.time` (mono 11 / w400) color `textSecondary`.

| Current stage | Title | Sub-line |
|---|---|---|
| `propose` → `designBrief` | `"Ready to advance to Design Brief"` | `"Precondition met · proposal accepted"` |
| `designBrief` → `designSync` | `"Ready to advance to Design Sync"` | `"Linked design page has content"` |
| `designSync` → `verify` | `"Ready to advance to Verification"` | `"Design Sync approved the pasted design"` |

Manual (§2.4) and Auto (§2.5) footers from the base SDD spec are likewise reused as-is with the target name parameterized (e.g. manual outlined button `"Advance to Design Sync"`, auto note `"Automatically advanced to Design Sync"`). No new treatment needed for those.

**Verdict:** the existing banner pattern is sufficient; Design Brief / Design Sync need only (a) parameterized copy and (b) the one `typePage` leading-glyph accent in §3.2. No distinct banner container is warranted.

## 4. "Retry validation" button (new)

A small, always-available plain control on a **`chat`-type** ticket's `TicketDetailScreen` — shown **only** for a chat titled `"Design Sync — <Story>"` whose most recent AI reply ends in `DESIGN GATE: PENDING`. It offers no proactive framing (not a banner) — it is a recovery utility, so it is styled as the **quiet outlined button**, matching the manual-confidence "Advance" button (base SDD spec §2.4), **not** a filled primary CTA. A filled button would compete with the composer's circular send button directly below it and over-emphasize a routine re-run.

### 4.1 Placement

- A thin bar directly above the composer (base spec §2.10), inside the same bottom-pinned `Column`, above the composer `Row`.
- Bar: `Padding(EdgeInsets.fromLTRB(20, 10, 20, 0))` → `Align(alignment: Alignment.centerLeft)` → the button. Left-aligned, hugging its content width (`MainAxisSize.min`) — not full-width.
- Rendered only while `latestAiReply.designGate == DesignGateStatus.pending`; on a passing re-run it is removed (via `AnimatedSize`, 160ms) as the gate flips to approved.

### 4.2 Button — default

- `GestureDetector` → `DecoratedBox` → `Padding` → `Row`.
- Fill `surfaceHover` (`#E4EDF6 / #1C2436`); border `1px solid borderStrong` (`#BAC8D6 / #35415C`); radius `AionRadius.md` (10); shadow none.
- Padding `EdgeInsets.symmetric(horizontal: 15, vertical: 9)`.
- Content `Row`, `gap: 7`, `crossAxisAlignment: center`: leading `arrows-clockwise` / refresh glyph (`↻`) `14px` color `primary` + label `"Retry validation"` `AionText.button` (14 / w700) color `primary`.

### 4.3 States (both themes)

| State | Fill | Border | Glyph / text | Extra |
|---|---|---|---|---|
| **Default** | `surfaceHover` | `1px borderStrong` | `primary` | — |
| **Hover** | `border` (`#D6E0EA / #232C40`) | `1px borderStrong` | `primary` | `MouseRegion` click cursor |
| **Focused** (keyboard) | `surfaceHover` | `1px borderStrong` | `primary` | 3px focus ring `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` |
| **Pressed** | `border` | `1px borderStrong` | `primary` | `AnimatedScale` to `0.98` over 80ms on `onTapDown` |
| **Disabled** (re-validation in flight) | `surfaceHover` @ `0.45` opacity | `1px borderStrong` @ `0.45` | `textMuted` | `IgnorePointer`; the leading glyph spins (`RotationTransition`, 900ms linear loop) as the in-flight indicator — never a Material `CircularProgressIndicator` |

No error state on the button itself — a failed re-run simply produces a new AI reply ending in `DESIGN GATE: PENDING`, which re-shows the (re-enabled) button.

## 6. New enums / tokens

```dart
// SddStage gains two values, inserted between propose and verify:
enum SddStage { explore, propose, designBrief, designSync, verify, archive }
//   nullable (null = "Not started"); story tickets only.
//   designBrief/designSync are only ever reached when the Story's needsDesign == true.

// Each Story carries:
//   final bool needsDesign;   // false → 4-node tracker; true → 6-node tracker + design Page

// Design-gate result on an AI reply within a "Design Sync — <Story>" chat:
enum DesignGateStatus { none, pending, approved }   // §4 — pending ⇒ show Retry validation

// Stage → current-stage-line display name (§1.3):
String stageDisplayName(SddStage? s) {
  switch (s) {
    case SddStage.explore:     return 'Exploring';
    case SddStage.propose:     return 'Proposed';
    case SddStage.designBrief: return 'Design Brief';
    case SddStage.designSync:  return 'Design Sync';
    case SddStage.verify:      return 'Verifying';
    case SddStage.archive:     return 'Archived';
    case null:                 return 'Not started';
  }
}
```

**Color tokens.** No *new* semantic colors are invented. Two existing base-spec type accents are used in this surface for the first time — add them to `AionColors` if not already present:

```dart
typeChat: Color(0xFF4C6FDE),
// Obsidian

typeChat: Color(0xFF7C93FF),
```

No new `AionText` or `AionRadius` members. Every text style is an existing `AionText.*`; every radius is `AionRadius.sm`/`md`/`lg`/`iconBtnSm` or `BoxShape.circle`; all spacing is a 4-multiple (the `10` label size in §1.4 is a font size, not spacing).
