# Decision Graph Agentjudgment Condition

# Proposal: Decision graph `agentJudgment` condition

## Origin

Originates from `aion-arch/ideas/decision-graph-agentjudgment-condition.md`
— Phase B of the archived `decision-graph-rule-builder` change (Phase A,
which shipped the deterministic rule-builder). That idea file's whole
design was conditional on one unresolved technical question: whether the
Claude Agent SDK can cheaply continue an existing conversation thread
rather than fully reconstructing context on every call. `/explore`
resolved that question empirically (see design.md §1) — this proposal
builds the **guaranteed, Dart-forced round-trip** variant the idea file
described as the outcome if resumption turned out to be cheap, not the
best-effort tool-offer fallback.

This also resolves `aion-arch/ideas/confirm-decision-tool-for-modeljudgment-leaves.md`'s
"pending convergence" status: that file's optional `confirm_decision` tool
was designed as `agentJudgment`'s fallback for a world where session
resumption wasn't available. Since it is, that fallback isn't needed —
whoever next touches that idea file should mark it superseded again, this
time on solid footing.

## What we're building

A third way to author a `DecisionNode`'s condition, alongside today's
fixed catalog (`attemptExceedsMax`, `sessionOverageDetected`) and the
rule-builder shipped by `decision-graph-rule-builder`: **`agentJudgment`**
— a free-text prompt (e.g. "is this fix expensive?") that a project
author types directly into the node, with no fixed vocabulary. At
evaluation time, Aion asks the model this exact question as a small,
scoped side-question **inside the same conversation the model is already
running** (via the Claude Agent SDK's session-resume mechanism), gets a
yes/no answer, and deterministically routes the graph's `matchedBranch`/
`unmatchedBranch` on it — a real round trip, not the advisory-only
prompt-surfacing `DecisionOutcome.modelJudgment` already does.

This only ever fires for `AutomationConfidence.auto`-resolved decisions
that already consult a decision graph (see `providers.md`'s "Decision
graphs" section) — never a new automation surface, never anything that
changes when `auto` decides to ask a question versus proceed silently.

### Why this only works for 3 of the 8 `AutomationContext` values

An `agentJudgment` round trip needs a **live, resumable session** to ask
its side-question inside — session resumption only makes sense while the
original conversation is still open. Of the 8 `AutomationContext` values,
exactly 3 are evaluated from inside a live tool-call handler with an
in-flight model turn still blocked awaiting that very tool call's result:
`ticketCreation`, `ticketLinking`, `chatBranching`. The other 5
(`sddStage`, `codingExecution`, `codingExecutionRetry`,
`codingExecutionResume`, `specAutoLink`) are consulted from Aion's own
orchestration code with no model turn in flight at all — there is nothing
to resume.

`agentJudgment` is therefore only offered in `DecisionNodeForm`'s
condition picker for those 3 contexts (mirroring how `attemptExceedsMax`
is already scoped to `codingExecutionRetry` alone). If an
`agentJudgment` node somehow gets evaluated with no live session
available (e.g. a stale graph authored before this restriction, or a run
under a provider that doesn't support session resumption at all — see
design.md §2), it defensively resolves to its `unmatched` branch, the
same fail-open behavior every other decision-graph edge case already
uses (a dangling node reference, an unrecognized `conditionId`, a `null`
rule-builder field value).

## Why now

Every real judgment call `auto` mode faces — "two warnings and one
critical verify finding: fix critical only, fix everything, or fix
warnings only if not expensive?" — has a genuinely subjective half
(`is this expensive?`) that no fixed vocabulary or rule-builder field can
express. The rule-builder (already shipped) covers the objective half
(finding severity, counts); `agentJudgment` is the missing piece for the
subjective remainder, and is what actually lets a project express
"split into two" / "fix warnings only if not expensive"-shaped decisions
as data instead of leaving them entirely to the model's own unstructured
judgment.

## Non-goals

- **Not a new automation gate.** Doesn't change when `auto`/`gated`/
  `manual` is chosen — only how an already-`auto`-resolved decision's
  graph can be authored.
- **Not building resumable-session support for `AnthropicMessagesApiProvider`.**
  That provider has no server-side resumable-session concept (see
  design.md §2) — `agentJudgment` simply can't do a real round trip under
  it and defensively resolves `unmatched`, same as a no-live-session
  context. A future change could teach that provider to fake resumption
  by replaying its own message history, but that's a separate, harder
  problem this change doesn't take on.
- **Not deprecating `DecisionOutcome.modelJudgment`.** It stays exactly
  as-is — a distinct, zero-I/O mechanism usable at *any* node regardless
  of live-session availability. Whether it becomes redundant now that a
  real round trip exists is a real open question, deliberately left for
  a future idea rather than decided here as a side effect of this change.
- **Not extending the rule-builder's field vocabulary.** Unrelated to
  this change — still only 2 of 8 contexts have any `DecisionEvalContext`
  signals instrumented, unchanged by this proposal.
- **Not adding a new "lightweight" model tier.** The round trip reuses
  the exact model the in-flight run is already using, not a cheaper
  tier — see design.md §3 for why that's a deliberate constraint, not an
  oversight.
