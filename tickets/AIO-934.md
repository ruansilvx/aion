# Idea Gap Question Ticket Types

# Proposal: Idea, Known Gap, and Open Question ticket types

## What

Eliminates `TicketType.signal`, replacing it with three distinct types:

- **`idea`** — inherits `signal`'s exact current behavior: freestanding
  (no required target), always a subtree root, promotable into an `epic`
  or `bug` via the existing promotion mechanism (renamed
  `promoteSignal` → `promoteIdea`, otherwise unchanged). Every existing
  `signal` producer — the Inbox brain-dump purpose and the codebase-
  analysis scan — now creates `idea` tickets instead.
- **`known gap`** and **`open question`** — never promotable. Each
  *must* be created already linked (`TicketLinkType.relatesTo`) to an
  existing ticket — enforced as a hard rule in `TicketsCubit`, not a
  convention. Creation is only reachable from that target ticket's own
  detail screen (a new "Raise a gap"/"Raise an open question" affordance
  inside a new **Gaps & Open Questions** section), never from the
  generic global New Ticket flow. Creating one writes the ticket and its
  `relatesTo` link in a single atomic Cubit call.

The new Gaps & Open Questions section is added everywhere Documentation-
mode already exists — `epic`/`story`/`task`/`bug`/`resource` (via
`ticket_metadata_section.dart`) and `page` (via `PageDetailScreen`) — not
scoped to pages only, widening the original design in
`aion-arch/ideas/sdd-workflow-in-ticket-system.md`. Its list is not a
flat per-ticket link query: it recursively aggregates every `known gap`/
`open question` raised on the ticket itself **or on any descendant**
(Epic → Story → Task/Bug), so an Epic's section shows everything raised
anywhere in its subtree, however deep, each row naming which specific
ticket it was raised on.

Because `signal` already shipped (`sdd-ticket-foundation`) and may have
real existing tickets under that type, this change also adds a manual
reclassification action — an existing `idea` ticket (including one that
used to be a pre-migration `signal`) can be turned into a `known gap` or
`open question` by picking a target ticket, going through the exact same
hard-rule validation as fresh creation. No automatic heuristic infers
which of the three an old `signal` ticket "should" become.

## Why

Grounded in `aion-arch/ideas/idea-known-gap-and-open-question-as-distinct-ticket-types.md`'s
`/brainstorm` session (status: `explored`, next_action: `/propose
idea-known-gap-and-open-question-as-distinct-ticket-types`). The core
finding: `known gap`/`open question` are structurally different from
`idea` in a way one shared type obscures — an idea is freestanding and
grows into new work via promotion, while a gap or open question is
inherently *about* something that already exists and its only real
action is being visible from that thing, recursively, up the ticket
hierarchy. `aion-arch/specs/tickets.md`'s existing gap note ("No way to
enumerate 'known gaps' or 'open questions' against a Documentation page
programmatically") already named the missing mechanism; this proposal
builds it, generalized past pages, and reverses the earlier
`sdd-workflow-in-ticket-system` decision to keep all three meanings
under one `signal` type now that gaps/questions need dedicated
visibility idea itself doesn't.

Resolving the idea file's open questions here, so `design.md` has single
answers to build from:

1. **`signal` → `idea` is a rename in place, not a new type migrating
   old data into a new column.** `type` is a plain `TextColumn` storing
   `TicketType.name` (`ticket_model.dart`) — no schema shape changes for
   the field itself. The only real migration risk is that removing
   `signal` from the enum would make every existing `type = 'signal'`
   row unparseable. A schema v11 migration blanket-reclassifies every
   existing `signal` row to `idea` (a safe default landing spot, not a
   heuristic guess at gap-vs-question-vs-idea) so the app never crashes
   deserializing pre-existing data; the new manual reclassification
   action is how a user then moves any of those into `known gap`/`open
   question` by hand, if they choose to.
2. **The target relationship reuses `TicketLinkType.relatesTo`, not a
   new field.** Consistent with the original design in
   `sdd-workflow-in-ticket-system` and with how `release` already
   relates to `epic`/`story`/`task`/`bug` — no new column, no new
   parent/child rule (`known gap`/`open question` stay `isAlwaysRoot`,
   same as `signal` was).
3. **Recursive rollup reuses `TicketsCubit._descendantIds`** (the same
   `parentId`-walk helper `getValidParentCandidates`/`updateTicketParent`
   already share) plus `TicketLinkRepository.getLinksByTypes` (the same
   bulk-query shape the Board's blocked-badge computation already uses)
   — no new DAO query, no N+1 per-descendant lookup.
4. **Creation is a compact overlay, not a screen navigation.** Aion has
   no Material `Dialog`; every existing multi-step "pick, then act" flow
   (`TicketOverflowMenu`'s promote rows, `TicketLinkPicker`) is an
   `Overlay`-anchored popover. The new "+ Add" trigger on the Gaps &
   Open Questions section follows the same pattern: a small popover
   offering "Raise a known gap" / "Raise an open question", which
   swaps in a compact title+description form on selection — new
   component, but not a new interaction pattern.
5. **`startWhatNextGuidance`'s existing "Known gaps" markdown-section
   scan is retired**, not kept alongside the new ticket-native gaps.
   That scan was already the exact thing `sdd-workflow-in-ticket-system`
   said was "considered and rejected" in favor of ticket-native tracking
   — this change is what finally replaces it. The Inbox context
   assembly now queries `known gap`/`open question` tickets directly for
   its priority-2 tier, and open `idea` tickets (renamed from "open
   signals") for priority-3.

## Scope

In scope:
- `TicketType` domain enum: remove `signal`, add `idea`/`knownGap`/
  `openQuestion` — all three keep `signal`'s exact `_rank` (`null`),
  `canParent` (`chat` only), and `isAlwaysRoot` (`true`) treatment.
- Drift schema v10 → v11: no new column, one data-migration statement
  reclassifying every pre-existing `type = 'signal'` row to `'idea'`.
- `TicketsCubit`:
  - `promoteSignal` → `promoteIdea` (rename only, same signature/guards,
    now checking `TicketType.idea`).
  - New `createGapOrQuestion(TicketType type, {required String title,
    String? description, required String targetTicketId})` — hard-rule
    validated (rejects anything but `knownGap`/`openQuestion`, rejects a
    missing/nonexistent target), creates the ticket and its `relatesTo`
    link atomically.
  - New `reclassifyIdea(Ticket idea, {required TicketType targetType,
    required String targetTicketId})` — same validation, mutates an
    existing `idea` ticket's `type` in place via `updateTicket` and
    creates the `relatesTo` link. Never operates on any type but `idea`.
  - `loadDocumentRelations` extended (not replaced) to also populate a
    new `gapsAndOpenQuestions` field: every `knownGap`/`openQuestion`
    ticket linked via `relatesTo` to the viewed ticket or to any
    descendant of it, each entry naming which specific subtree member it
    was raised on.
- New `GapOrQuestionRef` domain record (mirrors `LinkedTicketRef`'s
  shape) and a new `TicketDetailLoaded.gapsAndOpenQuestions` state field.
- New `design_system/molecules/gaps_and_open_questions_section.dart` —
  the section itself (empty state, row list, per-row navigation) — and
  a new creation popover (type choice + compact title/description form)
  as its header "+ Add" trigger.
- New `design_system/molecules/reclassify_idea_menu.dart` (or folded
  into `TicketOverflowMenu`) — "Change to Known Gap"/"Change to Open
  Question" rows, `idea`-tickets-only, alongside the existing "Promote
  to Epic"/"Promote to Bug" rows.
- Wiring the new section into `ticket_metadata_section.dart`'s
  Documentation-mode block (widening its current `chat`/`signal`/
  `release`-excluded gate's replacement values) and into
  `page_detail_screen.dart`.
- `create_ticket_screen.dart`: excludes `knownGap`/`openQuestion` from
  the type dropdown (keeps `idea`, matching `signal`'s current
  inclusion).
- `ticket_filter_popover.dart`, `type_chip.dart`,
  `linked_tickets_section.dart`'s `_typeColor`: exhaustive-switch
  updates for the enum change (compiler-mandated regardless of scope).
- Two new `AionColors` tokens (`typeKnownGap`, `typeOpenQuestion`, both
  themes) plus a renamed `typeSignal` → `typeIdea` (and its
  `signalFill`/`signalBorderTint`/`signalIconTint`/`signalChipTint` tint
  family → `ideaFill`/`ideaBorderTint`/`ideaIconTint`/`ideaChipTint`),
  consumed by `codebase_analysis_banner.dart` (idea-branded, not
  signal-branded, since a scan's findings are ideas).
- `inbox_cubit.dart`: `_brainDumpPrompt`/`_parseBrainDumpBlocks`/
  `_materializeBrainDumpSignals` produce `idea` tickets (internal
  renames to match); `_assembleWhatNextContext` drops the markdown
  "Known gaps" page-scanning path entirely, querying `knownGap`/
  `openQuestion` tickets directly for priority tier 2 and open,
  not-yet-promoted `idea` tickets for tier 3.
- `app_en.arb`: new/renamed `ticketType*`, promote/reclassify action
  labels, section labels, empty-state and creation-form copy.
- Unit tests: `TicketTypeHierarchy` matrix coverage for the three new
  values, `TicketsCubit` coverage for `promoteIdea` (renamed-behavior
  regression), `createGapOrQuestion`'s hard-rule rejection paths,
  `reclassifyIdea`'s type/target validation, and
  `loadDocumentRelations`'s recursive-rollup aggregation.

Out of scope:
- Any change to `known gap`/`open question` *resolution* — closing one,
  archiving it, or any lifecycle beyond plain `TicketStatus` transitions
  every ticket already has. This proposal only builds visibility and
  creation; what "done" means for a raised gap/question is left to
  ordinary status workflow, unchanged.
- A generic, editable "Type" field/picker for every ticket type.
  `reclassifyIdea` is a narrow, purpose-built action scoped to
  `idea → knownGap|openQuestion` only — not a general type-change
  feature (which would need to reconcile parent/child rank rules,
  execution eligibility, and type-specific fields for arbitrary
  from/to pairs, none of which this change touches).
- Bulk/automatic reclassification tooling for pre-existing `signal`
  (now `idea`) tickets — the idea file explicitly rejected an automatic
  heuristic; this change gives the manual per-ticket action only.
- Adding `idea`/`knownGap`/`openQuestion` to the Board view's status
  columns or any board-specific rendering — these three types have no
  board presence today (`signal` didn't either) and none is proposed.
- Any change to how `known gap`/`open question` tickets themselves
  render their own detail screen's Documentation-mode section beyond
  showing which ticket they're raised on (see design.md §3) — they stay
  excluded from the generic Linked Tickets/Backlinks gate exactly as
  `signal` was, since their one relationship is fixed at creation.
