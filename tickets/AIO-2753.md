# Scope Exploring Stage Instructions

# Proposal: Scope the exploring-stage system prompt to read-only investigation

Originates from `aion-arch/ideas/decommission-aion-arch-cli-workflow.md`'s
`next_action` — gate (b) blocking step 3 (cutover) of that idea's six-step
retirement plan. Not itself a standalone idea file; it's a narrow,
already-root-caused carve-out flagged during that idea's 2026-09-08 step-2
proof run.

## Problem

`TicketsCubit._assembleStageContext`
(`lib/features/tickets/presentation/cubit/tickets_cubit.dart`, ~line 7054)
builds the system-comment prompt posted to a Story/Epic's spawned SDD-stage
chat. It has an explicit `else if (stage == SddStage.X)` branch appending
stage-specific instructional text for `SddStage.verifying`,
`.designBrief`, `.designSync`, and `.proposed` — each telling the model
exactly what that stage's turn should produce (a verify-gate verdict, a
design-brief prompt, a design-sync check, a decomposition block).

**There is no branch for `SddStage.exploring`.** A ticket advancing into
`exploring` gets only the generic top-of-method context (title,
description, related tickets) with zero stage-specific instruction — the
model is left entirely to its own judgment about what "explore" means for
that turn.

This is a real, observed gap, not a hypothetical one. During the
2026-09-08 step-2 proof run (see the idea file's dated Amendment for full
narrative), a real `exploring`-stage AI turn on `AIO-2708` — unprompted, no
manual chat steering — did genuine tool-grounded-reading investigation,
then drafted a concrete file-by-file implementation plan and asked in-chat
for write access to the `aion` repo to start writing code. A human in the
loop declined and redirected in one message with no lasting effect
(`git status` stayed clean throughout) — not a real incident, but a real
gap in the system prompt itself. `aion-arch`'s own `/explore` skill
(`aion-arch/.claude/skills/explore/SKILL.md`) explicitly states "Do not
edit, create, or delete any project files. This stage is purely for
brainstorming and analysis" — the ticket-native `exploring` stage has no
equivalent rule anywhere, prompt or otherwise.

This matters more with each step of `decommission-aion-arch-cli-workflow`:
step 5 of that plan retires `aion-arch/.claude/skills/` entirely, at which
point the ticket-native `exploring` stage becomes the *only* "explore"
mechanism left, with no guarantee a human is watching every turn to
redirect it the way this session's proof run happened to.

## Goals

- Add explicit stage-scoped instructional text for `SddStage.exploring` in
  `_assembleStageContext`, mirroring `aion-arch/.claude/skills/explore
  /SKILL.md`'s own read-only rule as closely as makes sense for a
  ticket-chat context: no file edits/creates/deletes, no implementation
  plan, no code, no request for repo write access — investigate and
  produce a written exploration summary instead.
- Keep the fix minimal and text-only, consistent with every other branch
  in this method (`designBrief`/`designSync`/`proposed`/`verifying` are
  all pure prompt text, no tool-surface changes).

## Non-goals / investigated and deferred

The originating task asked this proposal to also investigate whether the
`exploring` stage chat's *tool access* should be restricted via a
read-only `ToolAccessTier`, not just its prompt wording — since a prompt-
only fix is weaker than an actual capability restriction if one is cheaply
available. Investigated directly in the code; conclusion is **defer, prompt-
only fix is the right scope for this change**:

- `ToolAccessTier` (`lib/core/contracts/tool_access_tier.dart`) already
  declares a `readOnly` value, but its own dartdoc says plainly: "Not
  supported by any provider today." `ClaudeAgentSdkProvider
  .supportedToolAccessTiers` confirms this — only `{noTools, full}`, with
  an explicit comment: "`agent_bridge/index.mjs` has no allowlist tier
  today, only `allowedTools: []` or the SDK's full default set." Wiring a
  real read-only tier would mean building a new allowlist capability into
  the underlying agent bridge itself — a separate, nontrivial change, not
  a cheap wire-up.
- More importantly: for the actual code path that produced the observed
  drift (no `SkillAttachment` configured on `exploring` for that project —
  confirmed via `_attachmentForStage`), the `exploring`-stage chat **already
  runs with `toolsEnabled: false`** (`TicketsCubit._runStageChatTurn`,
  `toolsEnabled: attachment == null ? false : attachmentToolsEnabled`) —
  the SDK's own file/git/bash tool set is already off, exactly equivalent
  to `ToolAccessTier.noTools`. Per `AgentRequest.toolsEnabled`'s own
  dartdoc: "Every existing caller (SDD-stage chats, Settings' connection
  test) leaves this `false` ... only ever set by `TicketsCubit`'s
  coding-execution path." The only tools available to a default
  `exploring`-stage turn are the app-defined `create_ticket`/
  `branch_ticket`/`add_link` triad (`_toolsFor`), independent of
  `toolsEnabled` and unrelated to file access.
- So there is no live filesystem/bash capability to strip from the default
  `exploring` path — the observed drift (drafting an implementation plan,
  asking for write access) was a pure text-generation/instruction-following
  gap, not a tool-misuse incident. A tool-tier restriction would add
  defense-in-depth for a capability that isn't actually granted today, not
  fix the reported gap.
- A project with a `SkillAttachment` explicitly configured on `exploring`
  (pointing at a `delegatedSkill`, which does get `toolsEnabled: true`) is
  a separate, deliberate per-project opt-in outside this gap's scope —
  restricting that path isn't part of what broke here and isn't touched by
  this change.

If a future incident ever shows a default `exploring`-stage turn with real
tool access misbehaving, that would justify its own proposal to build a
real `ToolAccessTier.readOnly` bridge capability — not folded into this
one.
