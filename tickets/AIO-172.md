# Automatic Trash Purge On Launch

# Proposal: Automatic Trash Purge on Launch

## What

Run the existing `TicketRepository.purgeTrashOlderThan` sweep automatically,
once, every time the app cold-starts — fire-and-forget, before the first
frame is even required to paint — instead of only when a user opens the
Trash screen and taps "Purge old." Nothing about the purge's *rules*
changes (still a fixed 30-day age threshold, still cascades exactly like
"Empty trash"); only *when* it runs changes: automatically, in the
background, on launch, in addition to (not instead of) the existing manual
button.

## Why

`aion-arch/specs/tickets.md`'s Known Gaps section calls this out directly:

> No automatic/timed purge of Trash — the Trash screen shows each ticket's
> age and offers a manual "Purge old" action (removes everything trashed
> more than a fixed 30 days ago), but nothing runs on its own: trash still
> accumulates indefinitely if the user never opens the Trash screen and
> taps the button.

The `ticket-trash` change (archived) deliberately deferred this exact
gap, anticipating it as follow-up work:

> Automatic/timed purge of trash (e.g. auto-delete after 30 days, like
> Azure DevOps). Trash is manual-only for v1 ... An auto-purge policy can
> be layered on later without restructuring anything here.

That prediction holds: `TicketRepository.purgeTrashOlderThan(Duration
age)` already exists, is already fully implemented in
`DriftTicketRepository`, and is already covered by unit tests
(`drift_ticket_repository_test.dart`). The only missing piece is a
*trigger* — something that calls it without a human opening the Trash
screen first.

## Scope

**In scope:**

- `main()` (`lib/main.dart`) calls a new private `_purgeOldTrashOnLaunch`
  helper right after `AppDatabase()` is constructed and before/alongside
  `runApp(...)`. The helper builds its own short-lived
  `DriftTicketRepository` (same constructor already used by
  `AionApp.build`'s `RepositoryProvider`) and calls
  `purgeTrashOlderThan(TrashCubit.purgeAgeThreshold)` — reusing the
  existing fixed 30-day constant rather than duplicating the literal.
- The call is unawaited in `main()` (wrapped in `unawaited()` per
  `flutter_lints`' `unawaited_futures` rule) so app startup and first
  paint are never delayed by it.
- Failures are swallowed silently inside the helper (`try`/`catch`,
  no rethrow). A missed purge on one launch has no user-visible
  consequence — trash simply stays a little longer and gets another
  chance on the next launch — so there is nothing to surface to the
  user and no existing logging infrastructure in this codebase to wire
  into.
- Runs unconditionally on every cold start. No new persisted "last run"
  timestamp or throttling — `purgeTrashOlderThan` is already a cheap,
  idempotent query (no-ops returning `0` when nothing qualifies), and at
  this project's personal-use scale an extra per-launch DELETE query is
  negligible, consistent with this project's existing "sufficient at
  personal scale" stance on other brute-force operations (e.g. embedding
  similarity search).

**Out of scope (explicitly deferred):**

- Any OS-level background execution while the app is *not* running
  (WorkManager on Android, BGTaskScheduler on iOS, a desktop daemon/cron
  entry, etc.). This proposal only changes what already happens the next
  time the user opens the app; it does not make trash disappear while
  Aion is closed. No scheduling primitive exists anywhere in this
  codebase today, and building one purely for a low-stakes housekeeping
  task is disproportionate to the gap (per `/explore`'s analysis: being
  purged "a few days late because the app wasn't opened" has no real
  user impact).
- Making the 30-day threshold or the on/off behavior user-configurable.
  `TrashCubit.purgeAgeThreshold` is explicitly documented as "Fixed, not
  user-configurable" today; this proposal doesn't touch that decision in
  either direction. If it's ever revisited, it should be a separate
  change (and would plug into the existing `AutomationConfidence`
  auto/ask-first pattern from `project.md` rather than a bespoke toggle).
- Any change to the manual "Purge old"/"Empty trash" buttons on the Trash
  screen — both keep working exactly as they do today, as an
  always-available manual override alongside the new automatic sweep.
- Any change to `purgeTrashOlderThan`'s cascade semantics, the 30-day
  value itself, or any other trash/repository behavior.

## Known gaps this closes

From `aion-arch/specs/tickets.md`:
> No automatic/timed purge of Trash ... nothing runs on its own: trash
> still accumulates indefinitely if the user never opens the Trash
> screen and taps the button.

Closed for the "user never opens the app at all in a long time" case is
still possible (see Out of scope), but the specific failure mode quoted
— opening the app regularly but never visiting the Trash screen
specifically — is fully closed: the purge now runs on every launch
regardless of which screen the user navigates to.
