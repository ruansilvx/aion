# Spec Delta: storage-embedding-git-sync

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/projects.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (6/7 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Relative to current-state `aion-arch/specs/tickets.md` and
`aion-arch/specs/projects.md`. See `proposal.md`/`design.md` for
reasoning; this file states only the behavior delta.

## ADDED

### Embeddings

- Whenever a ticket is created, or an existing ticket's `title` or
  `description` changes, Aion asynchronously generates a semantic
  embedding for `"$title\n\n$description"` and stores it in the
  existing `Ticket.embedding` column. Generation never blocks the
  ticket save that triggered it.
- Embedding generation runs fully on-device via a bundled model (no
  external server, no cloud call, no user-configured provider) — the
  same model weights on every platform (desktop native, mobile native,
  web WASM), so embedding vectors are comparable regardless of which
  platform created them.
- Embeddings are never written to the project's git repository, in any
  form (not the vector, not a hash of it).

### Ticket sync status

- Every ticket has a `syncStatus`: `synced`, `pendingReconcile`, or
  `needsRepair`. `epic`/`story`/`task`/`chat` tickets are always
  `synced` (they have no externally-editable file to fall out of sync
  with). `resource`/`page` tickets can occupy any of the three states.

### Git projection (desktop only, per project)

- On a desktop project, the following ticket events each write a
  Markdown file to `<project rootPath>/tickets/<ticketId>.md` and
  commit it to the project's git repository: ticket created, status
  changed, moved to trash, restored from trash.
- For `epic`/`story`/`task`/`chat` tickets, this file is a **one-way,
  generated projection**: it is never read back into the database.
  Hand-editing it has no persistent effect — the next projection event
  overwrites it.
- For `resource`/`page` tickets, this file is a **bidirectional, live
  input**. A filesystem watcher (active only while Aion is focused on
  desktop) detects external edits, waits for edits to pause (debounced,
  default ~1.5s), then reconciles the file's content into the database.
- On reconcile, if the file being reconciled belongs to the ticket the
  user is currently viewing, reconciliation blocks until the user
  navigates away from that ticket, rather than overwriting an
  in-progress view. Otherwise, reconciliation happens in the
  background, non-blocking, surfaced only via a subtle sync indicator
  (`pendingReconcile`, returning to `synced` once applied).
- If both the database (via Aion's own UI) and the file (via an
  external edit) change in the same window, for `resource`/`page`
  tickets **the file wins** — Aion's own UI is effectively a
  write-through client of the file for these two ticket types.
- If a `resource`/`page` file's frontmatter is entirely unparseable on
  reconcile, the database is left untouched, the file is left
  untouched, and the ticket's `syncStatus` becomes `needsRepair`. If
  only specific fields within otherwise-valid frontmatter are invalid,
  those individual fields are rejected (their last database value is
  kept) while the rest of the update is applied normally, and
  `syncStatus` stays `synced`.
- A `needsRepair` ticket surfaces a banner in its detail view offering
  two explicit, user-triggered actions: **reformat** (apply safe,
  mechanical formatting fixes without touching content the tool can't
  confidently interpret) and **restore from last known good**
  (overwrite the file with a fresh serialization of the ticket's
  current database row). Neither action ever runs automatically.

### Lint/repair tooling

- The reformat/validate logic above is available through three
  surfaces sharing one implementation: an in-app action on the ticket
  detail screen (for `needsRepair` tickets), a standalone CLI
  (`dart run bin/ticket_lint.dart <project-root> [--fix]`), and a new
  baseline skill (`ticket-lint`) available to projects pinned to
  baseline version `0.2.0` or later.
- The CLI operates purely at the file level — it has no database
  dependency and does not require Aion to be running.

### DB reconstruction

- A project's database is fully reconstructable from its git-tracked
  `tickets/*.md` files: every ticket's structured fields (frontmatter)
  and content (body) round-trip. After reconstruction, every imported
  ticket lacking a local embedding is bulk-backfilled via the same
  on-device embedding pipeline used for normal edits.
- This reconstruction capability exists as a callable service; no UI
  flow invokes it yet (no "open/clone existing project" flow exists to
  call it from).

## MODIFIED

- `Ticket.embedding` — was documented as "population deferred to a
  future change"; now actively populated per the Embeddings behavior
  above.
- `CreateProjectCubit._initializeDesktopProject` — previously ran a
  bare `Process.run('git', ['init'], ...)`; now additionally creates
  the project's `tickets/` subdirectory and routes git invocation
  through the shared `GitRepositoryClient` rather than an inline
  `Process.run` call.
- Baseline: a new version `0.2.0` exists alongside `0.1.0`, adding the
  `ticket-lint` skill. New projects pin whichever version is current at
  creation time (per existing baseline-pinning behavior); this change
  does not alter that pinning behavior itself, only adds a version for
  it to select.

## REMOVED

- `aion-arch/specs/tickets.md`'s known-gap line: *"`embedding` remains
  unpopulated/unexposed — system-only, no UI planned."* — superseded by
  the Embeddings behavior above (embedding generation is now built;
  the "no UI planned" part remains true — there is still no direct
  embedding-value UI, only the derived `syncStatus`/repair UI).
- `aion-arch/specs/projects.md`'s known-gap line: *"The bundled
  on-device embedding model and ticket↔Markdown git sync mechanics
