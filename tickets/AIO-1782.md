# Release Preparation And Tagging

# Proposal: Release preparation and tagging

Originates from
[`aion-arch/ideas/aion-native-release-preparation-and-tag-management.md`](../../ideas/aion-native-release-preparation-and-tag-management.md).

## What

Give Aion a built-in "Prepare Release" capability, generic for any project
it manages (including Aion itself), so drafting a release never depends on
Claude Code or the `/prepare-release` skill:

- A **Release** section on a `release` ticket's own detail screen — today
  this ticket type renders no Documentation-mode content at all (see
  `aion-arch/specs/tickets.md`'s "Documentation-mode sections" — `release`
  is one of the excluded types), so there is currently no way to see what a
  `release` ticket bundles from its own screen. This section lists every
  `relatesTo`-linked `epic`/`story`/`task`/`bug` and hosts the new
  **Prepare Release** action.
- **Curated mode** — for a planned minor/major release: open an existing,
  manually-populated `release` ticket (built via the existing Release
  Planning inbox chat, or hand-linked) and run Prepare Release on it.
- **Auto mode** — for a lightweight patch (e.g. one bug fix): a new "Cut a
  release" launcher on the Inbox screen, alongside the existing "Plan a
  release" card, auto-creates a `release` ticket and auto-links every
  `epic`/`story`/`task`/`bug` whose status fills the project's `done` role
  and isn't yet linked to any release, then goes straight into Prepare
  Release on it — no manual curation required.
- **Prepare Release** itself (shared by both modes once a populated
  `release` ticket exists): drafts changelog prose and a suggested semver
  bump from the linked tickets, using Aion's own per-project model routing
  (`ModelPhase.capable` — the same tier `TicketsCubit._createEpicSpec`
  already uses for comparable "write up finished work" tasks, not a fresh
  judgment call). The draft is shown for review/edit, and only on explicit
  confirmation does Aion bump the project's version file, write the
  changelog, commit, tag, and push.

## Why

`aion-arch/specs/release.md`'s known gaps note the release pipeline has
never been exercised by a real tag push, and the pre-tagging step
(`/prepare-release`) only exists as a Claude Code skill — which conflicts
with Aion's agent-agnostic design (`project.md`: "no user-facing text,
docs, or naming should hardcode a specific vendor or model provider").
Confirmed during `/explore` and this proposal's own investigation that the
actual gap is real: `aion/lib/core/build/project_stack_detector.dart`'s
`DetectedStack` is genuinely guidance-text-only today (its own dartdoc:
"nothing in Aion's own Dart code runs `checkCommand`"), and nothing in
Aion writes a `CHANGELOG.md` entry, bumps a version file, or creates a git
tag anywhere today.

## Scope

In scope:
- Extending `ProjectStackDetector` to also locate and parse/rewrite a
  project's version file (`pubspec.yaml`/`package.json`/`Cargo.toml`/
  `go.mod` do not all carry a version field the same way — see
  `design.md` for exactly which stacks get real support this round).
- `GitRepositoryClient.tag`/`.pushTag` — the actual tag creation/push.
- `TicketsCubit` additions: drafting a release (curated and auto
  population), and confirming one (write + commit + tag + push).
- UI: the release ticket's new Release section, a review/confirm screen
  for the AI draft, and the Inbox's new "Cut a release" launcher.

Out of scope (per the originating idea's own open questions, left
unresolved deliberately):
- Scaffolding a new project's own CI reaction to a pushed tag. This change
  stops at creating and pushing the tag; what (if anything) builds/
  publishes off it remains the target project's own concern — exactly
  Aion's own existing `aion/.github/workflows/release.yml` for Aion
  itself.
- Deprecating/removing the `/prepare-release` Claude Code skill. It keeps
  working unmodified; this change gives Aion an independent, native path,
  not a replacement wired to remove the old one.
- Any changes to the existing Release Planning inbox chat
  (`InboxCubit.startReleasePlanning`/`handleReleasePlanningReply`) —
  curated mode's population already works today and needs no changes,
  confirmed during brainstorming.

## Decision made during this proposal (not settled by the brainstorm)

The brainstorm resolved *that* auto mode needs a lightweight entry point
but not *where*. Settings screen (`features/providers/`) was considered
and rejected: it would need to call into `TicketsCubit`
(`features/tickets/`), violating `project.md`'s hard cross-feature-import
rule. The Inbox screen already lives inside `features/tickets/` and is
already the established launcher surface for release-adjacent actions
("Plan a release" is one of its four existing purposes) — a fifth
"Cut a release" card there is the natural, rule-compliant home. Flagging
this explicitly since it wasn't discussed in the brainstorm session.
