  - **Found and fixed a CRITICAL bug during this pass** (not caught by
    `flutter analyze`/`flutter test`, exactly the class of bug this task
    exists to catch): `InlineEditableField` rendered two structurally
    different widget subtrees for view vs. edit mode, each with its own
    `FocusableActionDetector`/hover-tracking. Toggling between them while
    the pointer was still over that exact spot (guaranteed, since a tap
    is what triggers the toggle) crashed Flutter's `MouseTracker`
    (repeated `RenderBox`/`MouseTracker` assertion failures in the
    browser console) — the framework disposed the old hover-tracked
    `RenderObject` while `MouseTracker` still held a reference to it.
    Fixed by restructuring `build()` to keep one stable outer
    `Semantics`/`FocusableActionDetector` wrapper across both modes,
    swapping only the inner child. Verified the fix with `flutter
    analyze` (clean) immediately after.
  - **Found and fixed a second bug**: `PriorityBadge` renders
    `SizedBox.shrink()` for `TicketPriority.none`, which made the
    `SelectionMenu` trigger a zero-size, untappable widget — there was no
    way to ever set an initial priority from this screen. Fixed with a
    `'+ PRIORITY'` text fallback trigger when priority is `none`.
  - **Found and fixed a third bug, reported live by the user tapping
    Estimate on their own `flutter run`**: the first `MouseTracker` fix
    above addressed a real symptom but not the actual root cause. An
    intermediate fix attempt (removing `InlineEditableField`'s hover cue,
    on the theory that `FocusableActionDetector.onShowHoverHighlight`
    triggering `setState` was re-entering `MouseTracker`'s own
    device-update dispatch) did **not** resolve the crash — the user
    re-tested with a fresh `flutter run` and got the same failure. A
    fuller stack trace subsequently obtained from the user's terminal
    revealed the true root cause, buried above the repeated
    `!_debugDuringDeviceUpdate` assertions: `An InputDecorator, which is
    typically created by a TextField, cannot have an unbounded width`,
    thrown from `app_text_field.dart:128` the moment Estimate entered
    edit mode. The Estimate/Time Spent meta row
    (`ticket_detail_screen.dart` ~L172-231) places each
    `InlineEditableField<int?>` inside a `Column(mainAxisSize:
    MainAxisSize.min)` which is itself a child of a `Row` — a `Row` hands
    each child unconstrained (infinite) max width unless wrapped in
    `Expanded`/`Flexible`. View-mode `Text` tolerates infinite width
    fine (title/description never hit this because their ambient parent
    is already width-bound), but `TextField`'s `InputDecorator` asserts
    against it. That one failed layout pass left the render tree in a
    corrupted intermediate state, which is what cascaded into the long
    run of repeated `MouseTracker` `!_debugDuringDeviceUpdate` assertions
    on every subsequent frame/pointer event — those were downstream
    wreckage, not an independent hover-reentrancy bug. Fixed by wrapping
    `InlineEditableField`'s single-line edit-mode subtree in
    `IntrinsicWidth`, so it sizes to its own content instead of relying
    on the ambient constraint, regardless of what layout it's embedded
    in. (The hover-state removal from the intermediate fix attempt was
    left in place since it's a legitimate simplification, just not the
    fix for this crash.) Re-verified with `flutter analyze` (clean) and
    `flutter test` (57 passing) after the fix — **still pending live
    re-confirmation** that tapping Estimate/Time Spent no longer crashes,
    since this fix has not yet been tested in a running browser/app.
