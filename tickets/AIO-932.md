# Design: git-projection-commit-visibility

## Architecture overview

No new files, no BLoC/state changes, no widgets. Three existing files
change:

```
core/
  markdown/
    ticket_markdown_template.dart      <-- + deletedAt field constant
    ticket_markdown_serializer.dart    <-- + deletedAt serialize/parse

features/tickets/data/services/
  ticket_db_reconstruction_service.dart <-- + deletedAt on rebuild
  ticket_markdown_reconciler.dart       <-- + doc-only "known limitation" note
```

`TicketGitProjector`, `GitRepositoryClient`, `TicketsCubit`, and
`TrashCubit` are all unchanged — the fix is entirely in what gets
serialized, not in when a commit fires. Once `deletedAt` is part of
the serialized content, the existing `hasChanges`-gated commit in
`TicketGitProjector.project` fires correctly on its own for the exact
same reason it already does for `'status-changed'`.

## `ticket_markdown_template.dart`

```dart
/// Frontmatter key for [Ticket.deletedAt].
static const deletedAt = 'deletedAt';

static const List<String> fieldOrder = [
  ticketId,
  type,
  status,
  priority,
  parentId,
  estimate,
  timeSpent,
  createdAt,
  updatedAt,
  deletedAt, // appended, not inserted — see below
];
```

`deletedAt` is appended at the very end of `fieldOrder`, not placed
next to `createdAt`/`updatedAt` where it would read more naturally.
`fieldOrder` drives `serialize`'s literal key-write order — inserting
a new key in the middle would reorder every key after it on every
existing ticket's *next* write, producing a whole-file diff (and a
commit) unrelated to any real content change the next time any
already-tracked ticket is touched at all. Appending avoids that
entirely: existing keys keep their exact position, and `deletedAt`
only ever appears as a genuinely new line.

## `ticket_markdown_serializer.dart`

**`serialize`** — add one more entry to the existing `values` map,
same shape as `createdAt`/`updatedAt`:

```dart
TicketMarkdownTemplate.deletedAt: ticket.deletedAt?.toIso8601String(),
```

(`_yamlScalar` already renders `null` as the literal `null` for any
nullable field — no change needed there.)

**`_convertField`** — add a case mirroring `createdAt`/`updatedAt`'s
`DateTime.tryParse` handling, but nullable like `parentId`/`estimate`/
`timeSpent`:

```dart
case TicketMarkdownTemplate.deletedAt:
  if (value == null) return (null,);
  if (value is! String) return null;
  final parsed = DateTime.tryParse(value);
  return parsed == null ? null : (parsed,);
```

A file written before this change (no `deletedAt:` key at all) parses
identically to one with an explicit `deletedAt: null` — `parsedYaml[key]`
already returns `null` for an absent key, and the `value == null`
branch above treats that as a valid, non-trashed ticket. No migration
path needed for existing files; they simply gain the key the next time
`TicketGitProjector` rewrites them for any other event.

## `ticket_db_reconstruction_service.dart`

`_buildTicket` gains one more field read, following the exact
`fields.containsKey(...)` pattern already used for `parentId`/
`estimate`/`timeSpent` (distinguishes "key absent, keep existing/
default" from "key present and explicitly `null`"):

```dart
return Ticket(
  // ...existing fields unchanged...
  deletedAt: fields.containsKey(TicketMarkdownTemplate.deletedAt)
      ? fields[TicketMarkdownTemplate.deletedAt] as DateTime?
      : existing?.deletedAt,
  createdAt: createdAt,
  updatedAt: updatedAt,
);
```

This is safe here specifically because `_buildTicket` constructs a
fresh `Ticket` value from scratch for `TicketRepository.importTicket`/
`.updateTicket` to persist wholesale — there's no cascade logic to
bypass the way there would be going through `trashTicket`/
`restoreTicket` directly. A reconstructed DB now correctly reflects
which tickets were trashed at the time of the last commit touching
each file, rather than silently reviving every ticket as non-trashed
regardless of its real state (the previous, undocumented behavior —
`_buildTicket` never set `deletedAt` at all, so every constructed
`Ticket` used its constructor default).

## `ticket_markdown_reconciler.dart`

Doc-only change: adds a second "Known limitation" paragraph to the
class dartdoc, immediately after the existing `parentId` one, in the
same voice:

```dart
/// **Known limitation**: does not apply a `deletedAt` change from a
/// hand-edited file either, for the same reason as `parentId` above —
/// `TicketRepository.trashTicket`/`.restoreTicket` carry cascade logic
/// (trashing cascades to descendants; restoring revives trashed
/// ancestors/descendants too) that a bare field write from this
/// background service would bypass, risking a corrupted trash state.
/// `deletedAt` round-trips through `TicketMarkdownSerializer` (needed
/// by `TicketDbReconstructionService`, which builds a fresh `Ticket`
/// with no existing row to protect), but `_apply` below has no case
/// for it and none is planned.
```

`_apply` itself needs no code change — it already only reads specific
named fields off the parsed map rather than looping over all of them,
so a new field that never gets its own `case`/read in `_apply` is
already excluded by construction. This dartdoc note exists purely so a
future reader doesn't mistake the omission for an oversight.

## Testing strategy

- `ticket_markdown_serializer_test.dart` (existing file): add
  round-trip cases — serializing a ticket with `deletedAt: null`
  produces `deletedAt: null` in the frontmatter and parses back to
  `null`; serializing one with a real `deletedAt` produces the
  ISO-8601 string and parses back to the identical `DateTime`; a
  pre-existing fixture file/string with no `deletedAt` key at all still
  parses as `ParsedOk` with a `null` value for that field (backward
  compatibility).
- `ticket_git_projector_test.dart` (existing file): add a case
  confirming `project` actually calls `GitRepositoryClient.commit` (not
  skipped) when only `deletedAt` differs from the previously-written
  file — the actual bug this whole change fixes, verified at the
  layer closest to the real defect rather than only re-asserting it via
  the serializer.
- `ticket_db_reconstruction_service_test.dart` (existing file): add a
  case — a ticket file with `deletedAt` set reconstructs to a `Ticket`
  with that same `deletedAt` (new import case), and updating an
  existing row from a file with `deletedAt` present overwrites the
  row's previous value (mirrors the existing `parentId`/`estimate`
  update-case tests).
- No `TicketMarkdownReconciler` test changes — `_apply`'s behavior is
  unchanged, only its class dartdoc gained a paragraph.

## Manual verification

Re-run `trash-restore-git-projection`'s own T4 scratch-script method
(real `AppDatabase`/`DriftTicketRepository`, real `GitRepositoryClient`
against a real temp git repo, real `TrashCubit`) — same GUI-automation
constraint applies in this environment, so the same substitution is
expected going in, not a fallback discovered mid-task this time. Assert
`git log` now actually contains a `<ticketId> trashed` commit and a
`<ticketId> restored` commit, with the file's frontmatter `deletedAt`
correctly reflecting each state.
