## `aion-arch/specs/providers.md`

### MODIFIED — `AgentRequest`

ADDED field `runId` (`String?`, default `null`) — caller-supplied
correlation id for a later `AgentModelClient.cancel(runId)` call.
Every existing caller that omits it is unaffected.

### MODIFIED — `AgentModelClient` contract

ADDED method: `void cancel(String runId)` — cancels the in-flight run
identified by `runId`, if still active on this client instance; no-op if
unknown. Implemented by both `ClaudeAgentSdkClient` and
`AnthropicMessagesApiClient`.

### MODIFIED — `AgentEvent`

ADDED variant: `AgentCancelledEvent()` — the run was cancelled via
`AgentModelClient.cancel` before reaching a normal terminal event. The
contract's "finished by exactly one terminal event" rule now reads
`AgentDoneEvent | AgentErrorEvent | AgentCancelledEvent`. Not a failure —
callers must not treat it as one.

### MODIFIED — `ClaudeAgentSdkClient`

ADDED: tracks each active `Process` in a `runId`-keyed map (entries only
for requests carrying a non-null `runId`); `cancel(runId)` sends
`SIGTERM` (escalating to `SIGKILL` after a grace period if the process
hasn't exited) and emits `AgentCancelledEvent` as the stream's terminal
event. The existing "only the first terminal event counts" guard governs
a cancel racing a genuine in-flight terminal NDJSON line.

### MODIFIED — `AnthropicMessagesApiClient`

ADDED: tracks each active request's Dio `CancelToken` in a `runId`-keyed
map, shared across every re-POST inside one logical run's own
tool-calling loop; `cancel(runId)` calls `token.cancel()`. The resulting
`DioException(type: cancel)` is caught and translated to
`AgentCancelledEvent` rather than `AgentErrorEvent`.

### MODIFIED — `core/automation/AutomationContext`

ADDED value: `codingExecutionResume`. Governs whether an interrupted
in-flight/queued coding-execution run, found in the persisted execution-
queue snapshot at app launch, is silently re-triggered (`auto`),
proactively offered with a confirm/dismiss prompt (`gated`), or left for
the existing orphaned/stalled failure-banner retry path with no
proactive surfacing (`manual`). Defaults to `gated` if unset, same as
every other `AutomationContext`. `SharedPrefsAutomationSettingsRepository`
gains the key `automation_settings.coding_execution_resume_automation`.

### ADDED — `ExecutionSchedulingMode` (`lib/features/providers/domain/enums/`)

New enum: `strictFifo | parallel | hybrid`. `strictFifo` reproduces
today's shipped single-slot FIFO behavior exactly (the default, so this
change ships with zero behavior change for a user who never touches the
new Settings section). `parallel` runs up to a configurable ceiling of
coding-execution runs concurrently. `hybrid` does the same, additionally
never running two same-parent sibling Tasks/Bugs concurrently against
each other (skip-ahead scheduling: a sibling-blocked queued ticket is
skipped in favor of the next eligible one when a slot frees, keeping its
own queue position).

### ADDED — `ExecutionSchedulingRepository` / `SharedPrefsExecutionSchedulingRepository`

New repository: `getMode()`/`setMode(ExecutionSchedulingMode)`
(persisted under `execution_scheduling.mode`, defaults to `strictFifo`),
`getConcurrencyCeiling()`/`setConcurrencyCeiling(int)` (persisted under
`execution_scheduling.concurrency_ceiling`, defaults to `2`, clamped to
`>= 1`). Registered app-level (not per-project), same tier as
`ExecutionContextCapRepository`.

### ADDED — `ExecutionSchedulingCubit`

New Settings-screen cubit, structurally identical to
`ExecutionContextCapCubit`. States: `ExecutionSchedulingLoading`
(initial), `ExecutionSchedulingReady` (`mode`, `concurrencyCeiling`).
Methods: `load()`, `selectMode(ExecutionSchedulingMode)`,
`setConcurrencyCeiling(int)`.

### MODIFIED — Settings screen (`/workspace/settings`)

ADDED: `_ExecutionSchedulingSection` row, directly below the existing
`_ExecutionContextCapSection` in the "MODELS" eyebrow group — a
`SelectionMenu<ExecutionSchedulingMode>` plus a concurrency-ceiling
`AppTextField`, the latter shown only when the selected mode isn't
`strictFifo`.

ADDED: a fifth "AUTOMATION" row, "Resume After Restart"
(`AutomationContext.codingExecutionResume`), reusing the section's
existing reusable `AutomationContext`-parameterized widget — sub-labels
"Resumes interrupted runs on launch" / "Asks before resuming" / "You
retry interrupted runs yourself".

### MODIFIED — Known gaps (providers.md)

REMOVED (superseded): none of providers.md's existing Known gaps
concerned scheduling/cancellation directly — no removal here; see
tickets.md's Known gaps below for the entry this change resolves.

## `aion-arch/specs/tickets.md`

### MODIFIED — `ChatCubit` / `ChatState`

`ChatLoaded` ADDED field: `activeRunId` (`String?`, default `null`) —
set while a reply is streaming, cleared on any terminal `ChatTurnResult`.
Drives the transcript's new stop button.

`runChatTurn`'s return type CHANGES from `Future<bool>` to
`Future<ChatTurnResult>` — a new sealed type
(`ChatTurnSuccess`/`ChatTurnFailure`/`ChatTurnCancelled(String
accumulatedText)`). On `AgentCancelledEvent`, `runChatTurn` persists no
comment itself (unlike the success/failure cases) — every caller decides
what, if anything, to record. Every existing call site
(`ChatCubit.sendMessage`, `TicketsCubit._spawnStageChat`,
`TicketsCubit._runCodingExecution`) is updated to switch on the result
instead of a bool; behavior for `ChatTurnSuccess`/`ChatTurnFailure` is
unchanged from today's `true`/`false`.

`sendMessage` ADDED behavior: generates a `runId` per turn, passes it
through to the underlying `AgentRequest`, stores it on `ChatLoaded.
activeRunId`. On `ChatTurnCancelled(accumulatedText)`: persists
`accumulatedText` as one `ai` comment if non-empty, then reloads the
thread with `streamingText`/`currentToolUse`/`activeRunId` all cleared.

ADDED method: `cancelReply(String chatTicketId)` — cancels the chat's
current in-flight AI reply via the resolved provider's
`client.cancel(runId)`, reading `runId` off `ChatLoaded.activeRunId`.
No-op if nothing is active.

### MODIFIED — Coding execution (`task` and `bug` tickets)

**Single-slot FIFO queue** section RENAMED/REPLACED by scheduling-mode
behavior:

- `_inFlightExecutionTaskId` (`String?`) REPLACED by
  `_inFlightExecutionIds` (`Set<String>`) and a parallel
  `_inFlightRuns` (`Map<String, _InFlightExecutionRun>` — bundles
  `runId` + resolved `AgentProvider` per in-flight Task/Bug id, for
  targeted cancellation).
- ADDED `_preExecutionStatus` (`Map<String, TicketStatus>`) — captures
  each Task/Bug's status immediately before a coding-execution trigger,
  read and cleared on cancellation to revert it.
- The old always-single-slot dequeue logic is REPLACED by
  `_tryStartNextQueuedExecutions()`, consulting
  `ExecutionSchedulingRepository`'s configured mode and concurrency
  ceiling (capped to 1 for the rest of the session once
  `AgentOverageDetectedEvent` fires, same existing reactive-override
  precedent): `strictFifo` behaves exactly as today (ceiling 1, plain
  FIFO pop); `parallel` pops the queue's front repeatedly while slots
  are free, no relationship awareness; `hybrid` scans the queue for the
  first ticket not sharing a `parentId` with an already-in-flight
  ticket, skipping (not removing) any that are, so a sibling-blocked
  ticket at the queue's front never idles a free slot.
- The queue (`_executionQueue`, unchanged `List<String>` shape) and
  in-flight set are now ADDITIONALLY persisted after every mutation via
  a new `ExecutionQueueRepository` (below), instead of being purely
  in-memory.

**ADDED — Cancellation.** New public `TicketsCubit` method,
`cancelCodingExecution(Ticket task)`: if `task.id` is only queued,
removes it from `_executionQueue`, reverts its status via
`_preExecutionStatus`, and posts a `system` comment ("Execution
cancelled before it started.") on its execution chat. If `task.id` is
in flight, calls `cancel(runId)` on the resolved provider; the run's own
`_runCodingExecution` call observes `ChatTurnCancelled`, stops without
running a verify turn, posts a `system` comment noting the run was
cancelled and that work up to that point is preserved on its
`aion/task-<id>` branch (the worktree itself is still always removed —
unchanged from today), reverts status via `_preExecutionStatus`, and
calls `_tryStartNextQueuedExecutions()` to backfill the freed slot.
No-op if `task.id` is neither queued nor in flight.

**ADDED — Restart persistence and resume.** New method,
`restoreExecutionQueue()`, called once by `WorkspaceShell` right after
constructing a project's `TicketsCubit`: reads the persisted
`ExecutionQueueRepository` snapshot, drops any entry whose ticket is no
longer live/`inProgress`, then resolves
`AutomationContext.codingExecutionResume`'s confidence — `manual` clears
the snapshot and changes nothing further (today's exact restart
behavior: surviving entries fall through to the existing orphaned/
stalled `executionFailureReason` detection, unchanged); `gated` surfaces
one proactive prompt offering to resume every surviving entry, declining
behaves like `manual`; `auto` resumes every surviving entry with no
prompt. "Resume" re-triggers via the same code path
`retryCodingExecution` already uses (fresh worktree/branch, chat
reused) — there is no live process to reattach to.

**MODIFIED — `getTicketById` additions.** `isExecuting` now reads
`_inFlightExecutionIds.contains(ticket.id)` instead of an equality check
against a scalar; `executionQueuePosition` is otherwise unchanged
(still the Task's 1-based position in `_executionQueue`).
`executionFailureReason`/`executionCanRetry`/`executionAwaitingReview`
are unchanged.

### ADDED — `ExecutionQueueRepository` / `DriftExecutionQueueRepository`

New repository, project-scoped (constructed with that project's
`AppDatabase`, threaded into `TicketsCubit`'s existing project-scoped
`create` call): `getSnapshot() → List<ExecutionQueueEntry>`,
`replaceSnapshot(List<ExecutionQueueEntry>)` (full wipe-and-rewrite in
one DAO transaction). `ExecutionQueueEntry` (`Equatable`): `taskId`,
`inFlight` (`bool`), `queuePosition` (`int?`, null iff `inFlight`).

### ADDED — Drift table `ExecutionQueueTable` → `ExecutionQueueEntryData`

`id` (TEXT PK), `task_id` (TEXT), `in_flight` (BOOLEAN), `queue_position`
(INTEGER, nullable). No FK constraints, consistent with every other
table. `ExecutionQueueDao` registered on `AppDatabase` alongside the
existing five DAOs. Schema version bumps **12 → 13**: `if (from < 13)`
creates the table, no backfill (no meaningful pre-existing queue state to
reconstruct).

### ADDED — `lib/features/tickets/domain/utils/sibling_cluster.dart`

New pure function, `List<Ticket> clusterSiblingsAdjacently(List<Ticket>
tickets)` — stably regroups a list so any ticket sharing a non-null
`parentId` with an earlier ticket moves to sit immediately after it,
preserving every other relative ordering. No-op for a list with no
shared `parentId`s.

### MODIFIED — Board view

`BoardColumn` ADDED behavior: when `ExecutionSchedulingReady.mode ==
ExecutionSchedulingMode.hybrid`, applies `clusterSiblingsAdjacently` to
its already-status-filtered ticket list before rendering. Every other
mode's column order is unchanged — exactly `TicketsCubit.currentSort`'s
output.

`TicketBoardCard`'s existing status badge (rotating-gear "Running" /
stack-glyph "Queued #N") ADDED behavior: a small inline cancel (×)
affordance alongside those two states only, calling
`TicketsCubit.cancelCodingExecution(ticket)` directly — no confirmation
dialog.

### MODIFIED — Screens (Task/Bug detail)

The existing execution-status section ADDED behavior: a labeled cancel
button alongside `isExecuting`/`executionQueuePosition` display, calling
the same `cancelCodingExecution`.

### MODIFIED — Known gaps (not yet built)

REMOVED (resolved): "Coding execution ... runs one Task or Bug at a
time, FIFO — no concurrent execution, and no way to cancel a queued or
in-flight run. The queue is in-memory only and does not survive an app
restart."

ADDED (replacement known-gaps, narrower in scope than what was removed):
- Hybrid mode's sibling-conflict signal is `parentId` only — two Tasks
  under different Stories but the same Epic are never treated as
  related, even though they share a grandparent.
- No persistent notification center — `board-execution-indicators-and-
  notifications.md`'s deferred-until-parallel-execution precondition is
  now met, but the notification center itself remains unbuilt.
- Switching scheduling mode mid-session, while runs are already queued/
  in-flight under the previous mode, is not specially reconciled — the
  new mode simply applies to scheduling decisions from that point
  forward.
