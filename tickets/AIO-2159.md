# Design: Ticket Delete Entry Points

## 1. Widget extraction — `TicketOverflowMenu`

Move the `TicketOverflowMenu` class (currently defined inline near the
end of `ticket_detail_screen.dart`) into a new file:
`lib/features/tickets/presentation/widgets/ticket_overflow_menu.dart`.
No behavior change — same `Overlay`/`LayerLink`/
`CompositedTransformFollower`/`mounted`-guard mechanics, same "Delete
ticket" row, same `showAppConfirmDialog` → `TicketsCubit.deleteTicket`
call. This mirrors the existing precedent of `inline_editable_field.dart`
living in `presentation/widgets/` as a cross-screen shared component,
rather than importing one screen file into another.

One behavior change: its semantic label moves from the fixed
`context.l10n.ticketDetailOverflowMenuLabel` ("More actions") to a new
parameterized `context.l10n.ticketOverflowMenuLabel(widget.ticket.ticketId)`
("More actions for {ticketId}"), matching `MoveToStatusMenu`'s existing
`ticketsBoardMoveTicketLabel(widget.ticket.ticketId)` pattern — needed
because the board and list views can render many triggers on screen
simultaneously; without a per-ticket label they're indistinguishable to
a screen reader.

`ticket_detail_screen.dart` drops its inline `TicketOverflowMenu`
definition and imports the new file instead; its own usage
(`TicketOverflowMenu(ticket: state.ticket)` in the header) is
unchanged.

## 2. Widget tree — list view

`TicketListTile` (`tickets_list_screen.dart`): add
`TicketOverflowMenu(ticket: ticket)` to the top `Row`, after the
`PriorityBadge` slot:

```
Row(
  children: [
    <id badge>,
    Expanded(<title>),
    if (priority != none) PriorityBadge(...),
    const SizedBox(width: AionSpacing.sp8),
    TicketOverflowMenu(ticket: ticket),
  ],
)
```

The whole row is already wrapped in an outer
`GestureDetector(onTap: () => context.go('/tickets/${ticket.id}'))`.
`TicketOverflowMenu`'s own inner `GestureDetector` (the trigger icon)
is proven to correctly capture taps ahead of an ancestor
`GestureDetector` in this exact codebase already — `MoveToStatusMenu`
sits inside `_CardVisual`'s row, itself wrapped by `TicketBoardCard`'s
navigate-on-tap `GestureDetector`, and that already ships correctly.
No new gesture-arena handling needed; same nesting shape.

## 3. Widget tree — board view

`_CardVisual` (`tickets_board_view.dart`): add
`TicketOverflowMenu(ticket: ticket)` next to the existing
`MoveToStatusMenu(ticket: ticket)`, inside the same `if (interactive)`
guard (so drag-feedback/placeholder renderings stay non-interactive,
matching `MoveToStatusMenu`'s existing treatment):

```
Row(
  children: [
    <id badge>,
    const Spacer(),
    if (interactive) ...[
      TicketOverflowMenu(ticket: ticket),
      const SizedBox(width: AionSpacing.sp4),
      MoveToStatusMenu(ticket: ticket),
    ],
  ],
)
```

Same nesting precedent as §2 — `MoveToStatusMenu` already proves
inner-`GestureDetector`-wins-over-outer-navigate-tap inside this exact
card.

## 4. Cubit — context-aware `deleteTicket`

Current `TicketsCubit.deleteTicket` unconditionally re-emits
`TicketDetailLoaded(ticket)` on the "blocked by children" path, and
emits a bare `TicketDeleted()` (no list) on success — both are correct
only when the caller is `TicketDetailScreen`. Called from a list/board-
shaped state, these would either render blank (`TicketDetailLoaded`
falls through the list screen's state switch to `SizedBox.shrink()`)
or leave the list stale.

Fix: capture the state active *before* the delete call, and branch the
recovery/success path on it:

```dart
Future<void> deleteTicket(String id) async {
  final previousState = state;
  emit(const TicketDeleting());
  try {
    await _repository.deleteTicket(id);
    if (previousState is TicketDetailLoaded) {
      emit(const TicketDeleted());
    } else {
      emit(TicketsLoaded(await _repository.getAllTickets()));
    }
  } on TicketHasChildrenException catch (e) {
    emit(
      TicketsError(
        '',
        reason: TicketsErrorReason.hasChildren,
        childCount: e.childCount,
      ),
    );
    if (previousState is TicketDetailLoaded) {
      final ticket = await _repository.getTicketById(id);
      if (ticket != null) emit(TicketDetailLoaded(ticket));
    } else {
      emit(TicketsLoaded(await _repository.getAllTickets()));
    }
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

`TicketDetailScreen`'s existing `BlocListener` pattern-matches with
`if (state is TicketDeleted)` / `if (state is TicketsError && ...)` —
type checks only, ignoring any fields — so this is fully backward
compatible with the shipped detail-screen flow. No new `TicketsState`
subclasses needed; `TicketDeleting`/`TicketDeleted`/`TicketsError` are
reused exactly as they are today.

## 5. UI — list screen reacts to delete

`TicketsListScreen`'s `BlocBuilder<TicketsCubit, TicketsState>` switch
needs one new arm:

```dart
TicketDeleting() => const Center(child: AppSpinner()),
```

placed alongside the existing `TicketsLoading()` arm. Because §4
routes list/board-context deletes to `TicketsLoaded(tickets)` on
success, the existing `TicketsLoaded` arm already handles the
refreshed list — no new success-arm needed. The brief `TicketDeleting`
frame is a local SQLite write (near-instant); a one-frame spinner is
consistent with how `loadTickets()` already renders elsewhere in this
screen, not a new UX pattern.

Wrap the existing `BlocBuilder` in a
`BlocListener<TicketsCubit, TicketsState>` (same shape as
`ticket_detail_screen.dart`'s existing listener, minus the
`TicketDeleted`-navigates branch, which doesn't apply here) that shows
the count-aware `AppToast` on `TicketsError(reason: hasChildren)`:

```dart
BlocListener<TicketsCubit, TicketsState>(
  listener: (context, state) {
    if (state is TicketsError &&
        state.reason == TicketsErrorReason.hasChildren) {
      AppToast.show(
        context,
        context.l10n.ticketDeleteBlockedByChildren(state.childCount ?? 0),
      );
    }
  },
  child: <existing BlocBuilder tree>,
)
```

This covers both list and board rendering — `TicketBoardView`/
`BoardColumn`/`TicketBoardCard` are all stateless widgets driven by the
`tickets` list `TicketsListScreen._buildTicketsBody` passes down; they
have no `BlocBuilder` of their own, so this one wrapper covers both
view modes.

## 6. Localization

`app_en.arb`: rename `ticketDetailOverflowMenuLabel` →
`ticketOverflowMenuLabel`, add a `{ticketId}` placeholder (same shape
as `ticketsBoardMoveTicketLabel`):

```json
"ticketOverflowMenuLabel": "More actions for {ticketId}",
"@ticketOverflowMenuLabel": {
  "placeholders": { "ticketId": { "type": "String" } }
},
```

No other new strings — `ticketDeleteMenuItem`,
`ticketDeleteConfirmTitle/Message/Action`,
`ticketDeleteBlockedByChildren` are all reused unchanged from the
`ticket-deletion` change.

## 7. No new design tokens

No new colors, radii, spacing, or shadow tokens — every widget reused
here (`TicketOverflowMenu`, `AppConfirmDialog`, `AppToast`) already
exists and ships with its own tokens from the `ticket-deletion` change.
This change is pure composition + one Cubit branch, not new visual
surface.

# Aion — Ticket List &amp; Board Delete Entry Points: Component Spec

Extends the [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and the [Ticket Deletion Spec](./Aion%20Ticket%20Deletion%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing` by name. **No Material widgets anywhere.**

Adds an **overflow trigger** to `TicketListTile` and `TicketBoardCard`. The trigger is the same `dots-three` ("⋯") "more" affordance used on `TicketDetailScreen`; tapping it opens the **existing, unmodified** overflow menu (single "Delete ticket" row) and confirm dialog from the Ticket Deletion Spec (§2–§4 there). This document specifies only the new trigger icon in its two contexts — the menu, dialog, and delete flow are reused as-is. No new screens, no new overlay components.

**Glyph:** `dots-three` in every context, identical to the detail-screen trigger — the delete action is not surfaced as a bare trash icon on the surface; it is one row inside the dropdown the trigger opens. This keeps the entry point consistent across all three surfaces (detail, list, board) and leaves room for the menu to gain more actions later without changing the trigger.

## 1. Overflow trigger — list row (`TicketListTile`)

Added to the row's top line, after the priority badge (or after the title if no priority): `id badge → title → priority badge (if any) → trigger`.

### 1.1 Dimensions &amp; position

- Hit target: `26×26`, radius `AionRadius.iconBtnSm` (8) — a new token added alongside `AionRadius.iconBtn` (11, header-level icon buttons) for this smaller inline-trigger footprint.
- Glyph: `dots-three` (⋯), **16px**, centered.
- Gap from the preceding element (priority badge or title): `AionSpacing.sp8` (8).
- `mainAxisSize.min` — the trigger never causes the row to wrap or grow in height; the `gap: 8` between top/meta lines is unaffected by the trigger's hit-target height.

### 1.2 States

Mirrors the detail-screen trigger (Ticket Deletion Spec §1) exactly — a neutral "more" control, **not** danger-colored. The destructive color appears only on the "Delete ticket" row inside the opened menu.

| State | Fill | Glyph color | Extra |
|---|---|---|---|
| Default | transparent | `textSecondary` | no chrome at rest |
| Hover | `surfaceHover` | `textSecondary` | radius `8`, 100ms fade |
| Focused (keyboard) | `surfaceHover` | `textSecondary` | + `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` |
| Pressed | `border` | `textSecondary` | scale `0.96`, 80ms |
| Open (menu showing) | `surfaceHover` | `textSecondary` | stays in active look while the overflow menu (Ticket Deletion Spec §2) is anchored to it |
| Disabled | transparent | `textSecondary.withOpacity(0.5)` | inert; reserved, not used by any current flow |

Anchor the menu to this trigger via `CompositedTransformTarget`/`CompositedTransformFollower`, offset `(0, 6)`, **top-right growing down-left** (trigger sits at the row's trailing edge — the menu must not overflow the screen's right side).

### 1.3 Differentiation from the link-count label

The link-count icon+label (existing, unchanged) lives on the row's **second line** alongside the type chip, uses the `link` glyph at 12–13px in `textSecondary`, and is not interactive by itself. The new trigger lives only on the **first line** and uses `dots-three`, not `link` — no visual or positional overlap.

## 2. Overflow trigger — board card (`TicketBoardCard` / `_CardVisual`)

Added to the card's existing top row, alongside the current move-status trigger: `id badge … move-status trigger, gap 4, overflow trigger` (overflow sits outermost/rightmost).

### 2.1 Dimensions &amp; position

- Hit target: `26×26`, radius `AionRadius.iconBtnSm` — identical size to the list-row trigger and to the existing move-status trigger, for visual parity in the pair.
- Glyph: `dots-three` (⋯), **16px**.
- Gap between the two triggers: `AionSpacing.sp4` (4).
- Both triggers sit in a trailing `Row` (`gap: 4`) pinned to the card's top-right, vertically centered against the id badge.

### 2.2 Differentiation between the two triggers

Because both are icon-triggers of the same size, they must not read as duplicates:

- **Move-status trigger (existing, unchanged):** a `arrows-down-up` / status-swap glyph — it moves the card between columns. Keep its current glyph; do **not** change it to `dots-three`.
- **Overflow trigger (new):** `dots-three`, matching the detail screen. Distinct glyph, so the pair reads as "move" + "more" rather than two identical dots.

If the shipped move-status trigger currently also uses a dots glyph, change it to the status-swap glyph as part of this work — two identical `dots-three` triggers side by side is not acceptable.

### 2.3 States

Same table as §1.2 — same neutral "more" control, same fills, focus ring, scale, and the same anchored menu. The move-status trigger's own states are unchanged (not respecified here).

### 2.4 Hit-target isolation

- Each trigger's `26×26` `GestureDetector` sits inside the card's top row but **outside** the card's own drag-handle region and outside the tap-to-navigate `GestureDetector` — wrap the trailing pair (or each icon) in its own `GestureDetector` so `onTap` does not bubble to the card's navigate/drag behavior. This matches how the move-status trigger already isolates itself today.
- The 4px gap is sufficient to avoid mis-taps at default hit-target size on both mobile and desktop pointer precision.

## 3. State summary

| Component | Default | Hover | Focused | Pressed/Open | Disabled |
|---|---|---|---|---|---|
| List-row trigger | transparent, `dots-three` `textSecondary` | `surfaceHover` fill | `surfaceHover` + primary focus ring | pressed `border` fill, scale 0.96 → menu opens (stays `surfaceHover` while open) | 50%-opacity glyph, inert |
| Board-card trigger | transparent, `dots-three` `textSecondary` | `surfaceHover` fill | `surfaceHover` + primary focus ring | pressed `border` fill, scale 0.96 → menu opens | 50%-opacity glyph, inert |

The opened menu and confirm dialog are the **existing** components (Ticket Deletion Spec §2–§4) — the "Delete ticket" row (trash icon + `danger` label) and the confirm dialog are unchanged. No new overlay, animation, or copy is introduced. No new color or spacing tokens required. One new radius token: `AionRadius.iconBtnSm` (8), added to `aion_radius.dart` for the smaller icon-button footprint (§1.1).
