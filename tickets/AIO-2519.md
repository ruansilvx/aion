**New text:**

> On a desktop project (`WorkspaceShell`'s `rootPath != null` gate —
> see `projects.md`), four ticket events each write a Markdown file to
> `<project rootPath>/tickets/<ticketId>.md` and commit it via
> `core/git/git_repository_client.dart`'s `GitRepositoryClient`
> (`init`/`add`/`hasChanges`/`commit`, wrapping `Process.run('git',
> ...)`): ticket created, status changed, moved to trash, restored
> from trash. `TrashCubit` receives the same
> `TicketGitProjector`/`rootPath` pair `TicketsCubit` does (provided by
> `WorkspaceShell`, consumed the same way `InboxCubit` already consumes
> its own git fields), and `restore(id)` projects only the
> explicitly-restored ticket — not any currently-trashed
> ancestors/descendants `restoreTicket` also revives, matching
> `trashTickets`' existing scope for the symmetric trash-side case.
> `Ticket.deletedAt` is part of the serialized frontmatter (nullable
> ISO-8601, appended after `updatedAt`), so both trashing and restoring
> a ticket genuinely change its file's content and both events reliably
> produce a commit — trashing sets `deletedAt` to a timestamp,
> restoring clears it back to `null`, and each write differs from the
> commit before it. Content edits via `updateTicket` do not trigger a
> commit — only the four events above do, so editing a ticket doesn't
> produce a commit per keystroke-adjacent save.
