## Domain Layer

### TicketType (enum)
```
epic | story | task | resource | page | chat
```

### TicketStatus (enum)
```
backlog | todo | in_progress | in_review | done | cancelled
```

### TicketPriority (enum)
```
critical | high | medium | low | none
```
Default value at creation: `none`. Stored as `.name` string. Surfaced in the
create form (`AppDropdown<TicketPriority>`) and as a priority indicator badge
on `TicketListTile`.

### TicketLinkType (enum)
```
blocks | blockedBy | relatesTo | duplicates | duplicatedBy
```
Used exclusively by the `ticket_links` table. These are non-hierarchical
relationship types only. Parent/child hierarchy is modelled exclusively by
`parent_id` on the ticket table — never as a link type.

### CommentAuthorType (enum)
```
human | ai
```
Stored as `.name` string. Used to drive visual distinction between human and
AI comments in the comment list UI.

### Ticket (entity)
```dart
class Ticket extends Equatable {
  final String id;            // UUID v4 — internal primary key, used for all relations
  final String ticketId;      // Human-readable ID, e.g. "AIO-42" — display + search key
  final TicketType type;
  final String title;
  final String? description;
  final TicketStatus status;
  final TicketPriority priority; // default: TicketPriority.none
  final String? parentId;     // self-reference for structural parent/child (UUID)
  final Uint8List? embedding; // nullable BLOB — populated later
  final int? estimate;        // nullable minutes — no UI in v1
  final int? timeSpent;       // nullable minutes — no UI in v1
  final DateTime createdAt;
  final DateTime updatedAt;
}
```

### TicketComment (entity)
```dart
class TicketComment extends Equatable {
  final String id;               // UUID v4
  final String ticketId;         // FK → Ticket.id (UUID)
  final String content;          // plain text
  final CommentAuthorType authorType;
  final String? aiModel;         // nullable — set only when authorType == ai
  final DateTime createdAt;
}
```
Comments are append-only. No `updatedAt` field; immutability is structural,
not just a UI constraint. No edit or delete in this slice or planned for
future slices without an explicit change proposal.

### TicketRepository (interface)

```dart
abstract interface class TicketRepository {

  Future<Ticket?> getTicketById(String id);
  Future<void> createTicket(Ticket ticket);

```

### TicketLinkRepository (interface)
```dart

```
No link UI in this slice. Schema and domain layer only. Link data is read/write
ready for a future change.

### CommentRepository (interface)
```dart

  Future<List<TicketComment>> getCommentsForTicket(String ticketId);
  /// Append-only. Throws if attempting to modify an existing comment id.
  Future<void> addComment(TicketComment comment);
}
```

### Subtask Convention (no schema change)
A `task` ticket with a `parent_id` referencing another `task` or `story`
ticket is the Aion subtask pattern. There is no dedicated "subtask" ticket
type. The `type` enum stays as-is. This is a convention enforced by the
application layer, not the database schema. Documented here as the canonical
definition so all future feature work references this spec.

### Rollup Invariant (estimate / time_spent)
`estimate` and `time_spent` are nullable integer fields (units: minutes) on
every ticket. They exist to support future rollup-aggregation features.

**Core invariant:** parent totals are always derived from the structural
`parent_id` tree. They are **never** derived from `ticket_links`. A ticket
linked via `blocks`, `relates_to`, etc., does not contribute to any parent's
estimate or time_spent rollup. This distinction is permanent — any future
rollup implementation must enforce it.

## Data Layer

### Drift Table: `TicketsTable`
| Column       | Type      | Constraints                              |
|--------------|-----------|------------------------------------------|
| id           | TEXT      | PRIMARY KEY (UUID)                       |
| ticket_id    | TEXT      | NOT NULL, UNIQUE (e.g. "AIO-42")         |
| type         | TEXT      | NOT NULL (TicketType name)               |
| title        | TEXT      | NOT NULL                                 |
| description  | TEXT      | nullable                                 |
| status       | TEXT      | NOT NULL (TicketStatus name)             |
| priority     | TEXT      | NOT NULL, DEFAULT 'none' (TicketPriority name) |
| parent_id    | TEXT      | nullable, no FK enforced (self-ref UUID) |
| embedding    | BLOB      | nullable                                 |
| estimate     | INTEGER   | nullable (minutes)                       |
| time_spent   | INTEGER   | nullable (minutes)                       |
| created_at   | INTEGER   | NOT NULL (Unix ms)                       |
| updated_at   | INTEGER   | NOT NULL (Unix ms)                       |

> Note: `ticket_id` is the human-readable identifier (prefix + sequence number).
> The sequence number is derived at insert time by querying `MAX(seq)` from a
> separate `ticket_id_sequence` table (schema version 1), incrementing by 1.
> This keeps sequencing deterministic and avoids race conditions in a
> single-writer SQLite environment. The prefix is read from app configuration
> (stored in `shared_preferences`, defaulting to `"AIO"`).
>
> `parent_id` is a self-referencing nullable text field (UUID). No FK
> constraint enforced at the DB level (Drift SQLite FK support is opt-in and
> adds complexity). Integrity enforced at the repository layer.
>
> `priority` defaults to `'none'`. All ticket inserts that omit the field
> receive this default. The `TicketPriority` enum maps directly to/from
> its `.name` string.
>
> `estimate` and `time_spent` are nullable. No UI reads or writes them in
> this slice. See Rollup Invariant in the Domain Layer section.

### Drift Table: `TicketLinksTable`
| Column            | Type    | Constraints                                    |
|-------------------|---------|------------------------------------------------|
| id                | TEXT    | PRIMARY KEY (UUID)                             |
| source_ticket_id  | TEXT    | NOT NULL (UUID — FK to tickets.id, not enforced) |
| target_ticket_id  | TEXT    | NOT NULL (UUID — FK to tickets.id, not enforced) |
| link_type         | TEXT    | NOT NULL (TicketLinkType name)                 |

> No FK constraints enforced at the DB level (consistent with tickets table
> policy). Integrity enforced at the repository layer.
> This table is for non-hierarchical relationships only. Parent/child
> structure is exclusively modelled via `parent_id` on `TicketsTable`.
> No link UI is built in this slice — the schema and domain/data layers are
> ready for a future change.

### Drift Table: `TicketCommentsTable`
| Column       | Type    | Constraints                                        |
|--------------|---------|----------------------------------------------------|
| id           | TEXT    | PRIMARY KEY (UUID)                                 |
| ticket_id    | TEXT    | NOT NULL (UUID — FK to tickets.id, not enforced)   |
| content      | TEXT    | NOT NULL (plain text)                              |
| author_type  | TEXT    | NOT NULL (CommentAuthorType name: 'human' or 'ai') |
| ai_model     | TEXT    | nullable (set only when author_type = 'ai')        |
| created_at   | INTEGER | NOT NULL (Unix ms)                                 |

> Append-only by design — no `updated_at` column. No UPDATE or DELETE
> operations are ever issued against this table in v1 or in any future
> slice without an explicit new change proposal. This structural immutability
> is the canonical enforcement of the append-only semantic.
>
> **Watcher gate bypass invariant:** Comments are explicitly NOT subject to
> the scheduled-changes review flow. They are append-only facts (human or AI
> authored) and must always bypass the watcher gate. This is a core semantic
> distinction — watcher-gated writes represent "proposed changes to ticket
> state", whereas comments are "observations or narrations about ticket state".
> Any future watcher implementation must explicitly exclude
> `TicketCommentsTable` writes from the review queue.

### Drift Table: `TicketIdSequenceTable`
| Column       | Type      | Constraints                              |
|--------------|-----------|------------------------------------------|
| id           | INTEGER   | PRIMARY KEY (always row 1 — singleton)   |
| seq          | INTEGER   | NOT NULL, DEFAULT 0                      |

Single-row table. The DAO reads `seq`, increments, writes back, and returns
the new value — all within the same Drift transaction as the ticket insert.
Schema version 1 includes both tables.

```dart
  Future<String> insertTicket(TicketsTableCompanion entry, String prefix);

```

### TicketLinkDao
```dart

  Future<void> insertLink(TicketLinksTableCompanion entry);

```

### CommentDao
```dart
@DriftAccessor(tables: [TicketCommentsTable])
class CommentDao extends DatabaseAccessor<AppDatabase> {
  Future<List<TicketCommentData>> getCommentsForTicket(String ticketId);
  /// Append-only. No UPDATE or DELETE methods exposed.
  Future<void> insertComment(TicketCommentsTableCompanion entry);

```

### DriftTicketRepository
Maps between `TicketData` (Drift DataClass) and `Ticket` (domain entity).
All enum conversions happen here — including `priority` (default fallback:
`TicketPriority.none`). Throws typed domain exceptions on failure.
Reads the configured prefix from `SharedPreferences` (key: `ticket_id_prefix`,
default: `"AIO"`) before calling `dao.insertTicket`.

### DriftTicketLinkRepository
Maps between `TicketLinkData` and the domain-level representation.
Generates UUID for `id` at insert time. Enum conversion for `link_type` with
safe fallback. No link UI in this slice — data layer only.

### DriftCommentRepository
Maps between `TicketCommentData` (Drift DataClass) and `TicketComment`
(domain entity). Generates UUID for `id` at insert time. Enum conversion
for `author_type`. `addComment` calls `dao.insertComment` — no UPDATE/DELETE
path exposed.

## Design System Foundation

**Hard constraint:** The design system does not extend or depend on Material.
No `ThemeData`, `ColorScheme`, `Theme.of(context)`, or Material widget
classes anywhere in `lib/core/theme/` or in any v1 widget file.

All v1 widgets consume tokens exclusively via `ThemeScope.of(context)`.
No hardcoded color values, font sizes, spacing, radii, or shadow values
in widget code. This is a minimal foundation — a future epic will expand
it into a full component library.

# Aion — Design System Specification

A spec-based AI coding assistant. One semantic token set, two cold themes: **Arctic** (celestial light) and **Obsidian** (abyssal dark). The contrast between themes is light vs dark — both are cold.

This document is implementation-ready: every component lists exact dimensions, token references, radii, padding, and states. Colors are Flutter `Color(0xFFRRGGBB)` constants; type is `TextStyle`. Translucent fills are expressed as `token.withOpacity(x)` so they track the theme automatically.

- Font families: **Manrope** (UI / display), **JetBrains Mono** (keys, captions, code)
- Base unit: **4px**. All spacing is a multiple of 4.
- `letterSpacing` values below are in logical pixels (already converted from em).


## 2. Components

All measurements exact. `c` = active `AionColors`; `a` = theme `fillAlpha` (Arctic 0.11 / Obsidian 0.16).

### 2.1 Button

Height driven by padding. Radius `AionRadius.md` (10). Text `AionText.button`.

| Variant | Fill | Text | Border | Padding (V×H) | Shadow |
|---|---|---|---|---|---|
| Primary | `primary` | `#FFFFFF` | none | 10 × 17 | FAB glow (blur 18, spread −9) |

| Ghost | transparent | `primary` | none | 10 × 8 | none |
| Destructive | `danger` | `#FFFFFF` | none | 10 × 17 | none |

**States:** hover → primary fill becomes `primaryHover`; secondary fill becomes `border`. Pressed → scale 0.98. Disabled → opacity 0.45, no shadow. Full-width submit (e.g. Create ticket): padding `15` all around, radius `13`, text 15px w700, centered.

Inline label with a leading solid square.

Dot + label, no fill.

## 4. Implementation notes

- Expose `AionColors` via a `ThemeExtension<AionColors>` so `Theme.of(context).extension<AionColors>()!` returns the active faction palette; swap `arctic` / `obsidian` at the `ThemeData` level.
- Never hard-code the tinted fills — always `token.withOpacity(...)` with the theme's `fillAlpha`, so the same widget code serves both themes.
- Keep `warning` out of priority and type usage; it is reserved for genuine warning states.
- All uppercase label text is uppercased in Dart strings; do not rely on a text-transform.
- Icon set is thin-line at 1.5px stroke; ship as a custom `IconData` font or an SVG set — sizes 20–24px, color `textSecondary` unless active.


### RULE — No Material theme access in widget code
- No `Theme.of(context)` anywhere in `lib/`.
- No `ThemeData`, `ColorScheme`, `TextTheme` imports in widget files.
- No raw `Color(0x...)` literals, numeric font sizes, or numeric padding
  in widget files.
- Violations fail T26 grep check.

## Accessibility

All v1 widgets must meet these requirements at build time, not as a retrofit:

### Semantic labels
- Every `IconButton`, `FloatingActionButton`, and `GestureDetector` has a
  `Tooltip` or `Semantics(label: ...)` wrapping it.
- Every form field (`TextField`, `DropdownButton`) has a descriptive
  `labelText` (shown to the user) which Flutter's accessibility tree exposes
  automatically. No additional `Semantics` wrapper needed if `labelText` is set.
- `TicketListTile`: the tile itself gets `Semantics(label: '${ticket.ticketId} ${ticket.title}', button: true)`.

### Color contrast
- All color token pairs in `AppColors` verified at WCAG AA (4.5:1 normal
  text, 3:1 large/UI). Both light and dark variants checked.
- Status chips use sufficient contrast between chip background and label.

### Keyboard and focus navigation
- All interactive elements are reachable via Tab key on desktop and web.
- `CreateTicketScreen` form fields have a logical `FocusNode` order: title →
  type dropdown → description → submit button.
- List items in `TicketsListScreen` are individually focusable and activate
  on Enter/Space.
- No focus traps introduced. Modal/dialog patterns deferred to future slices.

## Material Coupling Audit

This section catalogues every place where a Flutter built-in carries
unavoidable or optional Material coupling, and states the v1 decision.

| Widget / API | Material coupling | v1 decision |
|---|---|---|
| `MaterialApp` | Pulls in Material localizations, `Theme`, `Navigator` overlay | **Replaced** with `WidgetsApp.router` + `go_router`. |
| `Scaffold` | Material chrome (AppBar, Drawer, FAB slot, background color from `Theme`) | **Replaced** with plain `ColoredBox` + `Stack`/`Column` layout per screen. |
| `AppBar` | Material theming, elevation from `ThemeData` | **Replaced** with a custom `AppHeader` widget built from `Container` + `Text` + `GestureDetector`. |
| `FloatingActionButton` | Material ink splash, elevation, `Theme` color | **Replaced** with a custom `AppFab` widget: `GestureDetector` wrapping a `DecoratedBox` (border-radius from `AppRadii`, color from `ThemeScope`, shadow from `AppShadows`). |
| `ListTile` | Material ink, `Theme`-driven colors, fixed height constraints | **Replaced** with a custom `TicketListTile` widget: `GestureDetector` + `Padding` + `Row`/`Column` of `Text`. |
| `Card` | Material elevation + `Theme` surface color | **Replaced** with `DecoratedBox` using `BoxDecoration(color, borderRadius, boxShadow)` from tokens. |
| `ElevatedButton` / `TextButton` | Material ink, `ButtonStyle` from `ThemeData` | **Replaced** with `AppButton`: `GestureDetector` + `DecoratedBox` + `Text`. Focus handled via `FocusableActionDetector`. |
| `TextField` | Material `InputDecoration`, underline/outline from `Theme` | **Kept with mitigation.** `TextField` is used directly but with `InputDecoration` fully explicit (no reliance on `Theme` defaults): `border`, `focusedBorder`, `labelStyle`, `fillColor`, `filled` all set from `ThemeScope` tokens. `ThemeData` is **not** used to style it — values are passed inline from tokens. Flag: if future design needs diverge further, replace with a custom `FocusableActionDetector` + `EditableText` wrapper. |
| `DropdownButton` | Material ink, overlay, `Theme`-driven colors | **Replaced** with a custom `AppDropdown<T>`: `GestureDetector` opens an `OverlayEntry` (`CompositedTransformFollower`) containing a `DecoratedBox` list of tappable `AppDropdownItem` widgets. |
| `SnackBar` / `ScaffoldMessenger` | Requires `Scaffold` ancestor | **Replaced** with a custom `AppToast`: an `OverlayEntry` inserted directly into `Overlay.of(context)`, auto-dismissed after a duration. |
| `CircularProgressIndicator` | Material animation, `Theme` color | **Replaced** with a custom `AppSpinner`: `AnimatedBuilder` + `CustomPaint` arc. |
| `Semantics` | Framework-level, no Material coupling | **Kept as-is.** |
| `Focus` / `FocusNode` | Framework-level, no Material coupling | **Kept as-is.** |
| `GestureDetector` | Framework-level, no Material coupling | **Kept as-is.** |
| `InkWell` | Material ink splash | **Replaced** with `GestureDetector` + `MouseRegion` for hover state on desktop/web. |
| `PriorityBadge` (new) | No Material coupling — in-house | **Built** as `DecoratedBox` (rounded, priority color token from `ThemeScope`) + `Text` (labelSmall). Used on `TicketListTile` and `TicketDetailScreen`. |
| `CommentTile` (new) | No Material coupling — in-house | **Built** as `DecoratedBox` (background from `commentHumanBg` / `commentAiBg` tokens) + `Column` with `Text` (author label) + `Text` (content). No Material import. |

> Any new widget added in a future change that uses a Material component
> not listed here must add an entry to this table before implementation.
