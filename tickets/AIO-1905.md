# Sdd Verify Quality Gate

# Proposal: Verify-stage quality gate

Originates from `aion-arch/ideas/verify-stage-has-no-quality-gate.md`
(brainstormed conclusion, `status: resolved` → `explored` as of this
proposal).

## Problem

The `verifying → archived` SDD-stage transition has no content quality
gate. `TicketsCubit._sddStageAdvanceCheck`'s precondition for `verifying`
today only requires "the stage's most recently created chat child has an
AI reply" (`mostRecentChatHasTerminalReplyField`) — the same bar
`exploring → proposed` clears. Unlike `designSync → verifying`, which
hard-requires a literal `DESIGN GATE: APPROVED` line before advancing, a
Story/Epic can advance straight to `archived` even if the Verify-stage
chat's prose reports CRITICAL issues. The CLI `/archive` skill's rule
("only archive a change that has been through `/verify` with no
outstanding CRITICAL findings") has no enforcement counterpart in the
ticket-native SDD workflow.

Since `aion-arch/changes/sddstage-transition-preconditions` shipped, every
`SddStage` precondition — `designSync`'s included — is expressed as a
project-configurable `TransitionGraph` of boolean `TransitionFieldSpec`
checks, not a hardcoded rule. `verifying`'s seeded default graph today is
a single node checking only `mostRecentChatHasTerminalReply`
(`transition_precondition_dao.dart:100`) — confirming the gap is real at
the mechanism level, and that no `verifyGateApproved`-equivalent field
exists in the catalog yet for a project to opt into even by hand-editing
its graph via the Workflow config UI.

## What we're building

1. A new `verifyGateApproved` field in the transition-field catalog,
   populated by a `TicketsCubit._verifyGateApproved` accessor that checks
   the Verifying-stage chat's most recent AI reply for the literal line
   `VERIFY GATE: APPROVED` — mirroring `designSyncApproved`/
   `_designSyncApproved` field-for-field, wired through the same
   `TransitionEvalContext` → `evaluateTransitionGraph` pipeline every
   other stage precondition already uses.
2. `verifying`'s default seeded graph upgraded to a two-node tree
   (`mostRecentChatHasTerminalReply` → `verifyGateApproved` → allowed/
   blocked), mirroring `designSync`'s existing two-node default shape —
   plus a one-time migration that upgrades any *existing* project's
   `verifying` graph still at its original single-node default (a fresh
   install gets the new shape automatically via `seedDefaultsIfEmpty`; an
   existing one does not, since that method only seeds an empty table).
   A project that already customized its `verifying` graph is left alone.
3. The Verifying-stage chat's assembled prompt (`_assembleStageContext`)
   updated to request the reply end with `VERIFY GATE: APPROVED`/
   `PENDING`, and — on `PENDING` — optionally a `## Fixes Needed` fenced
   block (mirroring `proposed`'s `## Decomposition` block) that
   `TicketsCubit._materializeVerifyFixes` parses into new `task`/`bug`
   children under the Epic/Story, the same way `_materializeDecomposition`
   already turns a `proposed`-stage reply into child tickets.
4. A fix to `TicketsCubit._designSyncApproved`, folded into this change
   rather than filed separately: it hardcodes the `"Design Sync — "`
   chat-title prefix instead of resolving it through the override-aware
   `_stagePresentName(SddStage.designSync)` helper `_createStageChat`
   already titles every stage chat with. A project that renames the
   Design Sync stage's display name via `SddStageConfigRepository`
   would otherwise find `_designSyncApproved` permanently unable to
   locate its own chat, silently blocking `designSync → verifying`
   forever. Folded in because `_verifyGateApproved` (item 1) is built as
   its direct sibling and must not copy the same bug forward — fixing
   both together, the same way, in one pass is cheaper and safer than
   fixing one now and the other as a later ad hoc patch.
5. A `TicketsCubit.retryVerify` method mirroring `retryDesignSync` exactly
   — re-assembles context and posts a fresh turn on the existing
   Verifying-stage chat — reachable two ways:
   - A manual "Retry validation" bar in the Verifying-stage chat itself
     (reuses the existing generic `_RetryValidationButton` widget
     verbatim, gated only on the chat's most recent reply containing
     `VERIFY GATE: PENDING` — mirrors the Design Sync chat's identical
     retry bar exactly, available regardless of automation confidence).
   - A new "ready to retry verification" tier in the Epic/Story detail
     screen's SDD-stage section, shown once every fix Task/Bug the
     `PENDING` verdict spawned reaches `done`, rendered per a new
     `AutomationContext.verifyGateRetry` confidence the same
     auto/gated/manual three ways `advanceSddStage`'s own confidence tier
     already renders (silent auto-retry, a confirm banner, or a plain
     button) — not collapsed to a two-way auto/manual split, since this
     screen's existing stage-advance tiers already establish a real
     three-way UX and this action deserves the same treatment.

## Non-goals

- No automated/tool-based re-verification (e.g. re-running `flutter
  analyze`/tests) backing the `APPROVED`/`PENDING` verdict — this stays
  self-attested, the same trust model `designSync`'s gate already uses.
  Aion's coding-execution loop already does automated tool verification
  at the Task level (`_executionSucceededWithPr`'s `EXECUTION: PR_OPENED`
  marker, itself now sometimes system-posted rather than only
  AI-claimed) — hardening the SDD-level verify gate the same way is a
  reasonable future follow-up, not part of this slice.
- No changes to coding-execution's own internal implement/verify retry
  loop (`AutomationContext.codingExecutionRetry`) — a distinct, already-
  gated mechanism at the Task level, unrelated to this Story/Epic-level
  gate.
- No dedicated Settings row for `AutomationContext.verifyGateRetry` —
  mirrors the existing `specAutoLink` precedent (added to the
  exhaustive per-context switches with no dedicated `_AutomationSection`
  row of its own); reachable via the generic decision-graph editor route
  like every other context is.
- No retroactive Task/Bug tagging scheme distinguishing "original
  decomposition Tasks" from "verify-fix Tasks" beyond what
  `_materializeVerifyFixes` creates going forward — a Story/Epic's
  retry-readiness is computed from "every current child Task/Bug is
  done," the same aggregate check `designSync`'s `allTasksComplete`
  field already uses, not from tracking fix-Task provenance.
