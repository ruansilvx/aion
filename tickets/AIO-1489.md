# Design: Editable Ticket Parent (`parentId`)

## Layer-by-layer changes

### Domain — `ticket_repository.dart`

No changes to `Ticket` entity or `copyWith` — `parentId` reassignment is
modeled as an isolated structural operation, exactly like `status`
already is via `updateTicketStatus`. Add one interface method,
positioned next to `updateTicketStatus`:

```dart
/// Updates only the [parentId] (and `updatedAt`) of the ticket with id
/// [id]. Does not touch any other field, and performs no validation —
/// callers (see [TicketsCubit.updateTicketParent]) are responsible for
/// rejecting self-parenting and cycles before calling this. Pass `null`
/// to clear the parent. Throws if [id] does not exist.
Future<void> updateTicketParent(String id, String? parentId);
```

The "performs no validation" line is deliberate and matches
[[project.md's Cubit-level domain logic convention]]: this repository
method is a dumb column write, mirroring `updateTicketStatus`'s shape
exactly. It is documented so a future repository-level caller (if one is
ever added outside `TicketsCubit`) isn't misled into assuming safety
that isn't there.

### Data — `drift_ticket_repository.dart` / `ticket_dao.dart`

`DriftTicketRepository.updateTicketParent`:

```dart
@override
Future<void> updateTicketParent(String id, String? parentId) {
  return _db.ticketDao.updateFields(
    id,
    TicketsTableCompanion(
      parentId: Value(parentId),
      updatedAt: Value(DateTime.now().millisecondsSinceEpoch),
    ),
  );
}
```

No `TicketDao` change needed — `updateFields` already accepts any
`TicketsTableCompanion` subset (see `ticket_dao.dart:63-67`). No schema
migration needed — the `parent_id` column already exists and is
nullable.

### Presentation — `TicketsCubit`

Two additions to `tickets_cubit.dart`, both holding the domain logic
(cycle/self-reference checks) per the Cubit-level-domain-logic
convention:

```dart
/// Returns every ticket that [ticket] could validly be reparented under:
/// all tickets except [ticket] itself and any of its descendants
/// (reachable by walking `parentId` forward). Setting either as the new
/// parent would create a cycle. Performs a query only — does not emit a
/// state, since this feeds a picker overlay rather than driving the
/// detail screen's own render state.
Future<List<Ticket>> getValidParentCandidates(Ticket ticket) async {
  final all = await _repository.getAllTickets();
  final descendantIds = _descendantIds(ticket.id, all);
  return all
      .where((t) => t.id != ticket.id && !descendantIds.contains(t.id))
      .toList();
}

/// Reassigns [ticket]'s parent to [newParentId] (`null` clears it).
/// Rejects self-parenting and cycles locally — without calling the
/// repository — by re-deriving the same descendant set
/// [getValidParentCandidates] would, then emits
/// [TicketsError(reason: TicketsErrorReason.invalidParent)] followed
/// immediately by a re-emitted [TicketDetailLoaded] (same pattern as
/// [deleteTicket]'s `hasChildren` handling), so the detail screen shows
/// a toast rather than collapsing to the generic error view. On a valid
/// reparent, persists via [TicketRepository.updateTicketParent] and
/// emits the refreshed [TicketDetailLoaded].
Future<void> updateTicketParent(Ticket ticket, String? newParentId) async {
  if (newParentId != null) {
    if (newParentId == ticket.id) {
      await _emitInvalidParent(ticket.id);
      return;
    }
    final all = await _repository.getAllTickets();
    final descendantIds = _descendantIds(ticket.id, all);
    if (descendantIds.contains(newParentId)) {
      await _emitInvalidParent(ticket.id);
      return;
    }
  }

  try {
    await _repository.updateTicketParent(ticket.id, newParentId);
    final refreshed = await _repository.getTicketById(ticket.id);
    if (refreshed != null) {
      emit(TicketDetailLoaded(refreshed));
    }
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}

Future<void> _emitInvalidParent(String ticketId) async {
  emit(const TicketsError('', reason: TicketsErrorReason.invalidParent));
  final ticket = await _repository.getTicketById(ticketId);
  if (ticket != null) {
    emit(TicketDetailLoaded(ticket));
  }
}

/// Builds the full descendant-id set of [rootId] by walking `parentId`
/// forward through [all]. Shared by [getValidParentCandidates] and
/// [updateTicketParent] so both apply the identical cycle definition.
Set<String> _descendantIds(String rootId, List<Ticket> all) {
  final childrenByParent = <String, List<Ticket>>{};
  for (final t in all) {
    final p = t.parentId;
    if (p != null) {
      childrenByParent.putIfAbsent(p, () => []).add(t);
    }
  }
  final result = <String>{};
  void walk(String id) {
    for (final child in childrenByParent[id] ?? const []) {
      if (result.add(child.id)) walk(child.id);
    }
  }
  walk(rootId);
  return result;
}
```

`ticketsErrorMessage` (`tickets_board_view.dart:77-83`) gets a matching

### Presentation — `TicketParentPicker` widget (new)

`SelectionMenu<T>` is not reused here: it renders every item in a
non-scrolling `Column` with no search, which is fine for priority/type's
fixed ~5-item enums but not for an open-ended ticket list. Instead, a
new widget is added to `ticket_detail_screen.dart` (same file as
`TicketOverflowMenu`, following its exact `Overlay` /
`CompositedTransformFollower` / `LayerLink` / `mounted`-guard mechanics
— the third instance of that pattern is already precedented there):

```dart
class TicketParentPicker extends StatefulWidget {
  const TicketParentPicker({super.key, required this.ticket});
  final Ticket ticket;
  // ... State<TicketParentPicker>
}
```

Behavior:
- **Trigger**: a text row — `"Parent: AIO-12 — Fix login bug"` if
  `ticket.parentId` is set (resolved via a lookup among loaded
  candidates/all tickets), or a muted `"+ PARENT"` placeholder
  (mirroring the existing `ticketDetailAddPriority` "+ PRIORITY"
  pattern) when `null`.
- **On open**: calls `context.read<TicketsCubit>().getValidParentCandidates(ticket)`
  (a plain `Future`, not a `BlocBuilder` rebuild — same "query, don't
  emit" reasoning as the cubit method itself) to populate the overlay.
  Shows `AppSpinner` in the overlay while that future is in flight.
- **Overlay contents**: a search `AppTextField` at top (filters the
  candidate list client-side by `ticketId`/`title` substring, case-
  insensitive) above a scrollable `ListView` (bounded height, unlike
  `SelectionMenu`'s unbounded `Column` — necessary once the candidate
  list can exceed a screenful) of candidates, each rendered as
  `"AIO-12 — Fix login bug"`. A `"No parent"` row always appears first,
  above the search results, to let the user clear the field.
- **On select**: calls
  `context.read<TicketsCubit>().updateTicketParent(ticket, selected?.id)`
  and dismisses the overlay immediately (optimistic dismissal — matches
  every other picker in this screen; the cubit's toast-on-`invalidParent`
  path covers the rejection case).

Placement in `ticket_detail_screen.dart`: directly below the
`Row([TypeChip picker, StatusIndicator])` block (after line ~244's
`SizedBox(height: AionSpacing.sp12)`), as its own row, before the
estimate/timeSpent row.

## Testing

- `TicketsCubit` unit tests (`tickets_cubit_test.dart`, mocktail-mocked
  `TicketRepository`): `getValidParentCandidates` excludes self and the
  full descendant chain (2+ levels deep, to prove `_descendantIds`
  recurses correctly, not just one hop); `updateTicketParent` — valid
  reparent persists and emits `TicketDetailLoaded`; self-parent and
  descendant-parent both short-circuit *without* calling
  `_repository.updateTicketParent` (verify via `verifyNever`) and emit
  `TicketsError(reason: invalidParent)` then `TicketDetailLoaded`;
  clearing to `null` persists and emits.
- `DriftTicketRepository` unit tests
  (`drift_ticket_repository_test.dart`): `updateTicketParent` writes
  only `parent_id`/`updated_at`, leaves other columns untouched — same
  shape as the existing `updateTicketStatus` test.
- No widget test suite exists yet for `ticket_detail_screen.dart`'s
  pickers (`SelectionMenu` usages aren't unit-tested either) — follow
  existing precedent and skip a dedicated widget test for
  `TicketParentPicker`; its overlay mechanics are exercised manually
  (see flutter-conventions.md's guidance on `Overlay`-managing widgets
  needing an interactive pass, not just automated tests).

## Risks / assumptions carried forward from `/explore`

- **Enforcement boundary is `TicketsCubit`, not the repository.** This
  is the explicit tradeoff from `proposal.md`'s Approach section: if any
  future code path calls `TicketRepository.updateTicketParent` directly
  (bypassing `TicketsCubit`), no cycle protection applies. Acceptable
  today since `TicketsCubit` is the sole caller, but worth a comment (see
  interface doc above) so it isn't rediscovered the hard way later.
- **No rollup invalidation** — none exists yet to invalidate.
- **No full ticket-list refresh on reparent** — acceptable since nothing
  renders `parentId` in list/board views today (confirmed via grep).

# Aion — Editable Ticket Parent: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AppTextField`, `AppSpinner`, `AppToast` by name. **No Material widgets anywhere** — the picker is an `OverlayEntry` built from `DecoratedBox`, `GestureDetector`, `CompositedTransformTarget`/`Follower`, `Positioned`, and `Container`. `TextField` wrapped in a transparent `Material` is the one narrow exception already used by `AppTextField`, referenced unchanged.

No new screens. Adds one new inline trigger row to `TicketDetailScreen` and one new overlay component, `TicketParentPicker`. No new color, radius, spacing, or type tokens required.

---

## 1. TicketParentPicker trigger

Inline row on the ticket detail screen, placed per §1.1. Wrapped in `CompositedTransformTarget` (`LayerLink`) so the overlay (§2) anchors to it.

### 1.1 Placement

Directly **below the type chip + status indicator row** (base spec §3.3, block "(1)") and **above the estimate/time-spent row** (Ticket Editing Spec §4). Order within block (1), top to bottom:

1. Priority badge
2. Title
3. Type chip + status indicator (row)
4. **Parent row — new**
5. Estimate + Time Spent (row)

Spacing: `8px` gap above (tighter than the `12px` used before the estimate row, since this reads as a continuation of the identity/meta cluster) and `12px` gap below, before the estimate row.

### 1.2 Parent set — default state

- Layout: `Row`, `gap: 6`, `crossAxisAlignment: center`, `MainAxisSize.min`.
- Leading glyph: `git-branch` (or `link`), **14px**, color `textMuted`.
- Text: single `Text.rich` — mono ticket key (`AionText.key`, color `textSecondary`) + `"  —  "` separator (`AionText.bodySm`, `textMuted`) + title (`AionText.bodySm`, color `textPrimary`), e.g. `"AIO-12 — Fix login bug"`.
- Constrain to a single line: `maxLines: 1`, `TextOverflow.ellipsis`, `ConstrainedBox(maxWidth: 320)` (falls back to available row width on narrow viewports).
- No container chrome at rest — transparent fill, no border, matching the un-chromed read state of every other inline field (Ticket Editing Spec §1.1).
- Cursor: `SystemMouseCursors.click`.

### 1.3 Parent set — hover state (pointer devices only)

- Fill: `surfaceHover`, `BorderRadius(AionRadius.md)` (10).
- Padding compensation: identical technique to Ticket Editing Spec §1.3 — `EdgeInsets.symmetric(horizontal: 8, vertical: 4)` inset with a matching `Transform.translate(-8, -4)` so hovering doesn't shift the row's position in the layout.
- Leading glyph color steps up to `textSecondary`.

### 1.4 Parent set — focused state (keyboard nav)

- Same fill as hover (`surfaceHover`) plus focus ring: `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)`.

### 1.5 Parent set — pressed state

- Fill steps to `border` (one step darker than `surfaceHover`).
- Scale `0.98` (`AnimatedScale`, 80ms).
- On release: opens the overlay (§2), prefilled to the current parent's position in context (no row pre-selected — see §2.4, the field is just cleared to browse).

### 1.6 No parent set — default state

- Text: `"+ PARENT"`, styled identically to the existing "+ PRIORITY" affordance: `AionText.label` (12px w700), color `textMuted`, letter-spacing unchanged from the token.
- Layout: `Row`, `gap: 5` — a small `plus` glyph (12px, `textMuted`) + label. `MainAxisSize.min`.
- No container chrome at rest.

### 1.7 No parent set — hover / focused / pressed

- Identical mechanics to §1.3–1.5 (fill `surfaceHover` → focus ring → `border` + scale 0.98), with the glyph and label both stepping from `textMuted` to `textSecondary` on hover (brightening slightly to read as newly interactive, matching the "+ PRIORITY" precedent) and back to `textMuted` at rest.

## 2. TicketParentPicker overlay panel

Anchored below the trigger via `CompositedTransformFollower`, offset `(0, 6)`, growing top-left (same anchoring family as the priority/type menus and overflow menu).

### 2.1 Container

- Fill: `surface`.
- Border: `1px solid borderStrong`.
- Radius: `AionRadius.lg` (12).
- Shadow: `BoxShadow(color: rgba(0,0,0, isDark ? 0.55 : 0.16), blurRadius: 28, offset: Offset(0, 12))` — same formula as every other overlay in the app (base spec selection menus, deletion overflow menu).
- Width: fixed `320`, clamped to `viewport width − 32` on narrow viewports.
- Max-height: `400` total (search field + list), so the panel never exceeds a reasonable overlay footprint even on a tall list.
- Padding: `0` on the container itself — search field and list each own their internal padding.
- Entrance: scale-in `0.96 → 1.0` + fade, 120ms, anchored top-left.

### 2.2 Search field

- Built on the existing `AppTextField` pattern (`TextField` in a transparent `Material`), not a new input.
- Position: pinned to the top of the panel, `padding: EdgeInsets.all(12)`, bottom `1px solid border` divider separating it from the list.
- Fill: `surface`. Border: `1px solid border` default → `1.5px solid primary` focused, focus ring `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` — identical formula to every other text field in the app.
- Radius: `AionRadius.md` (10).
- Padding (inner): `EdgeInsets.symmetric(horizontal: 12, vertical: 9)`.
- Leading `magnifying-glass` glyph, **14px**, color `textMuted`, `margin-right: 8`.
- Placeholder: `"Search tickets…"`, `AionText.bodySm`, color `textMuted`.
- Input text: `AionText.bodySm`, color `textPrimary`.
- Autofocus on overlay open (desktop/web); on touch, focuses on explicit tap (standard soft-keyboard behavior).
- Debounce: 200ms after last keystroke before filtering/re-querying candidates.

### 2.3 "No parent" row

Always the first row in the list, **not affected by the search filter** (always visible regardless of query, since clearing the parent is a distinct action from searching).

- Height: `40`. Padding: `EdgeInsets.symmetric(horizontal: 13, vertical: 9)`.
- Layout: `Row`, `gap: 9` — leading `prohibit` (or `x-circle`) glyph, **14px**, color `textMuted` + label `"No parent"`, `AionText.bodySm`, color `textMuted`.
- **Default:** fill transparent.
- **Hover:** fill `surfaceHover`.
- **Pressed:** fill `border`.
- **Current state indicator:** if the ticket currently has no parent, this row shows a trailing `check` glyph (14px, `primary`) and its label color steps to `primary` — treated the same as a "selected" row (§2.4), just muted-styled at rest.
- Bottom `1px solid border` divider separates this row from the candidate list below.
- Tap → commits `parentId: null`, closes overlay. No toast on success (low-stakes, reversible action, consistent with the priority/type menus' silent-success pattern).

### 2.4 Candidate list

- Scrollable `ListView`, bounded `max-height: 320px` (panel max-height 400 minus search field ~64 minus "No parent" row 40, rounded).
- Each candidate row:
  - Height: `44`. Padding: `EdgeInsets.symmetric(horizontal: 13, vertical: 8)`.
  - Layout: `Row`, `gap: 10` — mono ticket ID (`AionText.key`, color `textSecondary`, fixed-width `56` so titles align across rows) + title (`AionText.bodySm`, color `textPrimary`, flexible, `maxLines: 1`, `TextOverflow.ellipsis`).
  - Optional trailing type-chip square (base spec §2.2's leading swatch alone, `8×8`, radius `2`, that type's base color) at the row's trailing edge, `margin-left: 8`, to carry a sliver of the type/priority hierarchy into the list without full chip chrome — omit if not needed; not required for the picker to function.
  - **Default:** fill transparent.
  - **Hover:** fill `surfaceHover`.
  - **Pressed:** fill `border`.
  - No divider between candidate rows (matches the priority/type menu convention — vertical padding alone provides separation).
- Tap a row → validates client-side against the excluded set (self + descendants — already filtered server-side, but re-checked defensively) → commits `parentId`, closes overlay, trigger updates immediately, no success toast.

### 2.5 Loading state

- While candidates are being fetched (initial open, or mid-search re-query): the list area (below the "No parent" row) shows a single centered `AppSpinner` at its default small size, `padding: EdgeInsets.symmetric(vertical: 32)`, no other content.
- "No parent" row (§2.3) remains visible and interactive during loading — it never depends on the fetch.
- Search field remains interactive during loading (typing further just re-debounces).

### 2.6 Empty state (no search results)

- Centered text row, `padding: EdgeInsets.symmetric(vertical: 32)`.
- Text: `"No matching tickets"`, `AionText.bodySm`, color `textMuted`, centered.
- "No parent" row (§2.3) remains visible above it.

### 2.7 Dismissal

- Tap outside (invisible full-screen `GestureDetector` inserted into the same `Overlay`, beneath the panel) → closes, no change.
- `Esc` (desktop/web) → closes, no change.
- Selecting a row (§2.3 or §2.4) → commits and closes in one step; no separate "confirm" action.

## 3. Validation & error toast

Reuses **`AppToast` unchanged** — same container, padding, radius, shadow, layout, and 3.2s auto-dismiss as every other toast in the app (base spec / Ticket Editing Spec §5 / Ticket Deletion Spec §4). No new visual component.

- Trigger: user selects a candidate that the client-side check (§2.4) or the server rejects as the ticket itself or one of its own descendants (a cycle). In the normal case this never surfaces, since invalid candidates are filtered out of the list before it renders — this toast is the defensive fallback for a race (e.g. the ticket tree changed between fetch and selection).
- Icon: `warning-circle`, **18px**, color `danger`.
- Copy: `"Can't set that ticket as its own parent or a descendant."`
- Message style: `AionText.bodySm`, color `textPrimary`.
- On rejection: overlay stays open (does not close), selection is not applied, so the user can immediately pick a different candidate.
