# Bare `dart run` scripts touching `AppDatabase` crash the Dart SDK's FFI compiler

Any standalone `dart run bin/*.dart` script that constructs the real
`AppDatabase` (not a toy/minimal drift database) crashes at compile time:

```
Crash when compiling:
type 'InvalidType' is not a subtype of type 'FunctionType' in type cast
```

raised in `_FfiUseSiteTransformer._verifyAndReplaceNativeCallable`
(`package:vm/modular/transformations/ffi/use_sites.dart`). Confirmed
reproducible with zero arguments: `dart run bin/migrate_aion_arch.dart`
alone (no real work attempted) crashes identically.

## Investigation so far

- **Not `drift_flutter`/`path_provider`**: extracted `AppDatabase`'s
  connection-opening code (`_openConnection`, `DriftWebOptions`/
  `DriftNativeOptions`) into a separate file so a bare-CLI caller's
  compiled unit never needs to import `drift_flutter` at all — crash
  persisted identically. That change was discarded (see Attempted fix
  below) since it didn't fix anything.
- **Not `sqlite3`/`drift`/FFI in general**: a minimal standalone
  `@DriftDatabase` with one table, `NativeCallable.isolateLocal`,
  `NativeDatabase.createInBackground`, and bare `package:sqlite3`
  `openInMemory()` all compile and run fine in this same environment.
- So the crash is specific to something within the real `AppDatabase`'s
  actual 14-table/11-DAO schema (`lib/core/database/app_database.dart` +
  its DAO/table imports) — not yet isolated to which table/DAO.
  Bisecting further requires modifying `@DriftDatabase(tables:[...],
  daos:[...])` and running `build_runner` per iteration (~15-20s each).
- Superficially resembles a currently-open Dart SDK issue,
  [dart-lang/sdk#62626](https://github.com/dart-lang/sdk/issues/62626)
  ("dart2wasm dry-run crash on FFI usage: InterfaceType not a subtype of
  FunctionType") — same error shape, same package family (drift/sqlite3)
  named as triggers — but that issue is specifically about
  `WasmFfiNativeTransformer`/`dart2wasm`; this crash is in the native
  VM's own `_FfiUseSiteTransformer`, a different (if related)
  transformer. Not confirmed to be the exact same bug.
- `sqlite3_flutter_libs` (a transitive dependency) is at `0.6.0+eol` —
  explicitly end-of-life/inert as of that version, since `sqlite3` 3.x
  moved native library provisioning onto Dart's new build-hooks system
  (hence the "Running build hooks..." lines preceding the crash). A
  plausible contributing factor, not confirmed as root cause; upgrading
  `sqlite3`/`drift`/`drift_flutter` within existing `pubspec.yaml`
  constraints (`flutter pub upgrade`) did not fix it.

## Impact

Blocks any standalone `bin/*.dart` script that needs the real ticket
database outside the Flutter app — currently only
`bin/migrate_aion_arch.dart` (the aion-arch decommission migration
tool), which ran successfully for real during that change's `/apply`
pass, so this is a regression since then (SDK/dependency versions have
moved since). `bin/ticket_lint.dart` is unaffected — it deliberately has
no drift/database dependency.

## Current workaround

None at the Dart/tooling level. The 88-ticket spec-reconciliation
content this bug blocked was instead written directly to
`.aion/data/app.db` via Python's stdlib `sqlite3` module, matching
`TicketDbReconstructionService`'s own update semantics (upsert by
`ticket_id`, same columns) — a one-off, not a repeatable fix.

## Attempted fix (discarded, didn't work)

Extracted `_openConnection` into
`lib/core/database/app_database_connection.dart`
(`openAppDatabaseConnection`), made `AppDatabase`'s `executor` parameter
required instead of defaulted, updated the two call sites
(`app_router.dart`, `app_router_test.dart`). Verified this doesn't fix
the crash (see Investigation above) and discarded it rather than land
an incomplete fix — worth revisiting only alongside real table/DAO
bisection.
