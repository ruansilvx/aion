# Define Type Compatibility Matrix

# Proposal: Define type-compatibility matrix

## What

Add a structural type-compatibility rule to ticket reparenting: which
`TicketType` may parent which other `TicketType`. Today, reparenting only
validates self-parenting, cycles, and the one hardcoded rule that an
`epic` can never receive a parent — there is no rule at all governing
which *types* may sit under which other types. A `resource` can currently
become the child of a `story`, a `chat` can parent a `task`, etc., with
nothing preventing it.

This change introduces a single strict hierarchy:

- **epic** may parent anything except another epic (story, task,
  resource, page, chat).
- **story** may parent task, resource, page, or chat — not another
  story, not an epic.
- **task** may parent resource, page, or chat — not another task, not a
  story, not an epic.
- **resource / page / chat** are always leaves — they may never parent
  anything, of any type.

Same-type nesting is blocked everywhere (no story-under-story, no
task-under-task); same-type relationships are expressed via ticket
linking instead of parenting. Any of the three work types (epic, story,
task) may parent any of the three leaf types (resource, page, chat)
directly — leaf attachment isn't restricted to epics only.

## Why

Grounded in `aion-arch/ideas/define-type-compatibility-matrix.md`'s
`/brainstorm` session: the motivation is proactive, not reactive — lock
down the domain model's structural rules before more ticket types or
features make retrofitting painful. This directly resolves two items
already flagged in `aion-arch/specs/tickets.md`'s `## Known gaps`
section:

- "Reparenting enforces structural validity (no self-parent, no cycles)
  ... but there is no general type-compatibility matrix beyond that."
- "`TicketsCubit.getValidParentCandidates` and `TicketParentPicker` ...
  still load every ticket into memory and filter/search client-side" —
  this change adds a new filter dimension to that existing client-side
  filter, it doesn't change its DB-scaling characteristics (out of
  scope here).

## Scope

In scope:
- A pure type-compatibility rule (`TicketType.canParent`) in the domain
  layer.
- Wiring that rule into `TicketsCubit.getValidParentCandidates`,
  `TicketsCubit.updateTicketParent`, and a new
  `TicketsCubit.getValidParentCandidatesForType` for the create-ticket
  flow (which has no existing ticket to derive descendants from).
- `TicketParentPicker` re-fetching its candidate list when the ticket's
  type changes (previously fetched once at mount — a latent bug this
  change surfaces, since `CreateTicketScreen`'s type dropdown can now
  change which candidates are valid).
- `CreateTicketScreen` clearing the selected parent whenever the type
  dropdown changes (extending its existing epic-only clear to a general
  clear, since a type change can invalidate the previously chosen
  parent under the new rule).
- Correcting `TicketType.task`'s dartdoc, which currently documents
  task-under-task as "the Aion subtask convention" — that claim is now
  false and must be corrected as part of this change.
- Unit test coverage for the new rule in `TicketsCubit`.

Out of scope:
- Any new `TicketType` values.
- Configurability of the matrix (it's a fixed, hardcoded rule set — see
  the idea file's open question, resolved here as "hardcode, revisit
  later if ever needed").
- Server-side/DB-level filtering (candidates stay client-side, matching
  existing behavior).
- Any UI to *display* the matrix to the user (e.g. a settings/help
  screen) — not requested, not needed for the rule to function.

## Design gate

status: NOT REQUIRED
reason: no new visual components — this is a validation-logic change to
  existing widgets (`TicketParentPicker`, `CreateTicketScreen`), with no
  new screens, no new widget types, and no visual/token changes. The
  picker's existing empty-state ("no valid candidates") already covers
  the case where a type-compatibility filter leaves zero results.
