# Persistent Navigation Shell

# Proposal: Persistent Navigation Shell

## What

A persistent navigation shell wrapping every `/workspace/*` route, replacing
today's ad hoc per-screen header icon buttons with real shared chrome:

- **Wide layouts** (`> 900px`): a left sidebar, always visible, listing
  Tickets and Documentation as top-level destinations plus a secondary
  actions trigger.
- **Narrow layouts** (`<= 900px`): a bottom tab bar with the same two
  destinations plus the same secondary actions trigger.
- **Secondary actions** ("Switch Project", "Trash") move into a small
  popover menu behind a single trigger (reusing the existing, currently
  decorative avatar circle), shared by both layouts and both sections —
  they're not content sections, so they don't get top-level nav slots.
- The current per-screen buttons this replaces —
  `_SwitchProjectButton`/`_DocumentationEntryButton`/`_TrashEntryButton`
  and the decorative avatar circle, all currently local to
  `TicketsListScreen`, plus `DocumentationScreen`'s own copy of the
  avatar circle — are deleted, not duplicated alongside the new shell.

## Why

Board and Documentation are separate top-level routes today
(`/workspace/tickets`, `/workspace/documentation`) reached via a single
header icon button on `TicketsListScreen`, with no shared chrome between
them. Concretely, this means:

- **`DocumentationScreen` has no way back** to Tickets on any platform —
  it never received a copy of the switch-project/trash/back chrome
  `TicketsListScreen` has. This is the immediate bug the user reported
  ("if I go to the documentation there is no way to go back to the
  tickets, using other platforms besides web").
- The pattern doesn't scale — every future section (e.g. a Chat section,
  per `project.md`'s still-open "Agentic Engine" work) would need its own
  hand-rolled copy of these buttons, as `DocumentationScreen` already
  demonstrates by lacking them entirely.
- `ProjectSwitcherMenu` (`features/projects/presentation/widgets/project_switcher_menu.dart`)
  already exists, is fully built, and its own dartdoc says it's "designed
  for a full-width sidebar row" — but no sidebar has ever existed to put
  it in. It's dead code today, only reachable from its own file.

Source idea: `aion-arch/ideas/persistent-navigation-shell.md` (status:
explored).

## Scope

**In scope:**

- New `WorkspaceNavShell` widget owning the sidebar/bottom-tab chrome and
  the secondary-actions popover.
- Wiring it into the existing `WorkspaceShell` (`core/routing/app_router.dart`),
  which already wraps every `/workspace/*` route via a `ShellRoute` but
  today renders no persistent UI of its own — only provider wiring.
- Removing the per-screen buttons and avatar circles this makes redundant
  from `TicketsListScreen` and `DocumentationScreen`.
- Reusing `ProjectSwitcherMenu` (currently unused) and the existing
  `SelectionMenu<T>` overlay primitive (already used by
  `MoveToStatusMenu`/priority-and-type editors) — no new overlay
  mechanism, no new generic design-system component beyond what's needed
  to assemble the shell itself.

**Out of scope (non-goals):**

- The companion "consistent max-width content layout" idea
  (`aion-arch/ideas/consistent-max-width-content-layout.md`) — a
  separate, independently-proposable change. This shell change does not
  constrain per-screen content width.
- The three bugs the user flagged and explicitly deferred out of the
  brainstorm session (childless-page chevron, markdown checkbox
  rendering, clipped "synced" info bubbles) — unrelated to navigation.
- Per-section navigation-state preservation (e.g. `StatefulShellRoute`'s
  independent per-branch navigation stacks). The current app uses a
  plain `ShellRoute`; switching sections today already drops the
  previous section's scroll position/state via `context.go`, and this
  change doesn't alter that — only where the destination buttons live.
  Worth a future idea if it becomes a felt problem, not bundled in here.
- Any change to `TicketsListScreen`'s internal List/Board view-mode
  toggle (`_ViewModeToggle`) or `_SelectModeToggle` — both stay exactly
  as they are, screen-local concerns unrelated to section-level nav.
- Any new top-level sections beyond Tickets/Documentation. The shell is
  built to make adding one easy later (see design.md), but no new
  section ships in this change.

## Naming decision

The Tickets destination is labelled **"Tickets"**, not "Board" — even
though the user's original framing called it "board". `TicketsListScreen`
itself is titled "Tickets" (`ticketsListTitle`) and defaults to List mode;
"Board" is only one of its two internal view modes
(`_TicketViewMode.list`/`.board`). Labelling the persistent nav item
"Board" would mismatch the screen it lands on. Reusing the existing
`ticketsListTitle`/`documentationTitle` strings for the nav labels keeps
one source of truth for both.
