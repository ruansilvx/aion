# Spec Delta: Tickets — DB reconstruction preserves `ticketId`

**Reconciled 2026-09-03:** confirmed against the current `aion-arch/specs/tickets.md` "DB reconstruction" section — the `ticketId`-preservation mechanism this delta describes (`TicketRepository.importTicket`, `TicketDao.insertTicketPreservingId`, the second-machine import-vs-update split) still matches current text exactly. No drift.

## ADDED behaviors

- **`TicketRepository.importTicket(Ticket ticket)`** — persists `ticket`
  with its own `ticketId` preserved verbatim, instead of generating a
  fresh sequential one the way `createTicket` does. Used only by
  `TicketDbReconstructionService`'s true-import path (a `.md` file whose
  `ticketId` has no matching existing row). Throws if `ticket.ticketId`
  already exists on another row (`TicketsTable.ticketId` is `unique()`).

- **`TicketDao.insertTicketPreservingId(TicketsTableCompanion entry)`** —
  inserts `entry` as-is, with whatever `ticketId` it already carries, in
  a single transaction. After inserting, advances
  `TicketIdSequenceTable.seq` to the numeric suffix of `entry.ticketId`
  (the substring after its last `-`) when that suffix parses as an
  integer and is greater than the current `seq` — so a later
  `TicketDao.insertTicket` call on the same device can never mint an id
  that collides with the one just inserted. A `ticketId` whose suffix
  doesn't parse as an integer still inserts successfully; only the
  sequence bump is skipped for it.

## MODIFIED behaviors

- **DB reconstruction** (`TicketDbReconstructionService.reconstruct`) —
  on its true-import branch (parsed file's `ticketId` has no matching row
  in `existingByTicketId`), now calls `TicketRepository.importTicket`
  instead of `TicketRepository.createTicket`. The imported row's
  `ticketId` now matches the file it was read from — the file/DB naming
  correspondence that the git-projection/sync mechanism depends on is
  preserved on a true import, not just on the update branch (which
  already preserved it, since it reuses the existing row's internal
  `id`).

  The update branch (file's `ticketId` already has a matching existing
  row) is unchanged — it still calls `TicketRepository.updateTicket`.

## Known limitation removed

`aion-arch/specs/tickets.md`'s "DB reconstruction" section currently
documents: *"`TicketRepository.createTicket` always assigns a fresh
sequential `ticketId`, ignoring the one on the passed `Ticket` — so
importing a file with no matching existing DB row does not actually
preserve the `ticketId` the file is named after."* This change resolves
that limitation for reconstruction specifically; `createTicket` itself is
unchanged and still always ignores the passed `ticketId` for every other
caller (ticket creation UI, `TicketsCubit`, `ChatCubit`, `InboxCubit`).
This paragraph should be removed from `tickets.md`'s "DB reconstruction"
section when this change's delta spec is merged at `/archive`.
