# Design: per-phase-tier-based-model-routing

Read alongside [proposal.md](proposal.md) for the *why*; this file covers
the *how* — exact types, call-site changes, and the Settings widget tree.

## 1. Domain layer

### 1.1 `ModelPhase` (new — `lib/features/providers/domain/enums/model_phase.dart`)

```dart
/// The three capability tiers Aion buckets model calls into, by how much
/// reasoning weight the job needs — independent of the separate
/// tool-access axis (`no-tools | read-only | full`) established by
/// `sdd-design-gate`/`task-to-coding-execution-trigger`. A stage's tool
/// access and its model tier are configured separately.
enum ModelPhase {
  /// Epic/story-level judgment calls: `SddStage.exploring`, `.proposed`,
  /// `.verifying`.
  frontier,

  /// Comparatively mechanical work: `SddStage.designBrief`, `.designSync`,
  /// `.archived` — prompt generation, checklist-style validation, doc
  /// updates.
  capable,

  /// Task coding-execution runs (`TicketsCubit._runCodingExecution`).
  execution,
}
```

Placed beside `AgentModel` in `features/providers/domain/enums/`, not
`core/`, because it exists purely to key into `ModelRoutingRepository`
(§1.3, below), which returns `AgentModel` — a providers-feature type
`core/contracts/agent_model_client.dart` deliberately never depends on
(`AgentRequest.model` is a plain `String`, keeping the provider-agnostic
boundary intact). Splitting the enum into `core/` while its repository
stays in `features/providers/` would separate one concept across two
layers for no benefit — unlike `AutomationContext`/`AutomationConfidence`,
which are genuinely typeless and freely belong in `core/automation/`.

### 1.2 `SddStage.modelPhase` (new extension — `lib/features/tickets/domain/enums/sdd_stage.dart`)

```dart
import 'package:aion/features/providers/domain/enums/model_phase.dart';

/// Maps each [SddStage] to the [ModelPhase] that drives its spawned
/// chat's model choice, per `per-phase-tier-based-model-routing.md`'s
/// confirmed split.
extension SddStageModelPhase on SddStage {
  ModelPhase get modelPhase => switch (this) {
    SddStage.exploring || SddStage.proposed || SddStage.verifying =>
      ModelPhase.frontier,
    SddStage.designBrief || SddStage.designSync || SddStage.archived =>
      ModelPhase.capable,
  };
}
```

Tickets-feature code already imports `features/providers/domain/enums/agent_model.dart`
directly at the presentation layer (`tickets_cubit.dart`, `chat_cubit.dart`)
— this adds the same cross-feature import one layer down, at the domain
layer, which is a new but consistent direction (tickets → providers, never
the reverse).

### 1.3 `ModelRoutingRepository` (new — `lib/features/providers/domain/repositories/model_routing_repository.dart`)

```dart
/// Persists which [AgentModel] each [ModelPhase] currently resolves to.
/// Replaces [AgentSettingsRepository] (removed by this change) — a
/// single global model selection no longer exists, only a per-phase one.
abstract interface class ModelRoutingRepository {
  /// The currently configured [AgentModel] for [phase].
  Future<AgentModel> getModelForPhase(ModelPhase phase);

  /// Persists [model] as [phase]'s selection.
  Future<void> setModelForPhase(ModelPhase phase, AgentModel model);
}
```

Plain reads/writes only, no validation — matches `AgentSettingsRepository`'s
original split (validation, if any, belongs in the consuming Cubit, per
`project.md`'s Cubit-vs-repository convention). There is none needed here:
any `AgentModel` value is valid for any phase.

### 1.4 `SharedPrefsModelRoutingRepository` (new — `lib/features/providers/data/repositories/shared_prefs_model_routing_repository.dart`)

```dart
class SharedPrefsModelRoutingRepository implements ModelRoutingRepository {
  static const _frontierKey = 'model_routing.frontier_model_id';
  static const _capableKey = 'model_routing.capable_model_id';
  static const _executionKey = 'model_routing.execution_model_id';

  /// The pre-existing single-model key `SharedPrefsAgentSettingsRepository`
  /// used, read (never written) as a fallback so a user's already-chosen
  /// model survives into all three tiers the first time this repository
  /// runs, instead of silently resetting to `AgentModel.sonnet`. Mirrors
  /// `SharedPrefsAutomationSettingsRepository`'s precedent of preserving
  /// `AutomationContext.sddStage`'s pre-generalization key.
  static const _legacySelectedModelKey = 'agent_settings.selected_model_id';

  String _keyFor(ModelPhase phase) => switch (phase) {
    ModelPhase.frontier => _frontierKey,
    ModelPhase.capable => _capableKey,
    ModelPhase.execution => _executionKey,
  };

  @override
  Future<AgentModel> getModelForPhase(ModelPhase phase) async {
    final prefs = await SharedPreferences.getInstance();
    final storedId = prefs.getString(_keyFor(phase)) ??
        prefs.getString(_legacySelectedModelKey);
    return AgentModel.values.firstWhere(
      (model) => model.id == storedId,
      orElse: () => AgentModel.sonnet,
    );
  }

  @override
  Future<void> setModelForPhase(ModelPhase phase, AgentModel model) async {
    final prefs = await SharedPreferences.getInstance();
    await prefs.setString(_keyFor(phase), model.id);
  }
}
```

No `flutter_secure_storage` — same reasoning as the repository it
replaces (nothing secret is stored).

## 2. `features/providers/presentation/`

### 2.1 `ModelRoutingState` (new — `presentation/cubit/model_routing_state.dart`)

Structurally identical to `AutomationSettingsState`:

```dart
sealed class ModelRoutingState extends Equatable {
  const ModelRoutingState();
  @override
  List<Object?> get props => [];
}

class ModelRoutingLoading extends ModelRoutingState {
  const ModelRoutingLoading();
}

class ModelRoutingReady extends ModelRoutingState {
  const ModelRoutingReady(this.modelByPhase);

  /// The currently selected [AgentModel] for each [ModelPhase], keyed
  /// rather than split into named fields — same reasoning as
  /// `AutomationSettingsReady.confidenceByContext`: a future phase slots
  /// in with no state-shape change.
  final Map<ModelPhase, AgentModel> modelByPhase;

  @override
  List<Object?> get props => [modelByPhase];
}
```

### 2.2 `ModelRoutingCubit` (new — `presentation/cubit/model_routing_cubit.dart`)

Structurally identical to `AutomationSettingsCubit`:

```dart
class ModelRoutingCubit extends Cubit<ModelRoutingState> {
  ModelRoutingCubit(this._repository) : super(const ModelRoutingLoading());

  final ModelRoutingRepository _repository;

  Future<void> load() async {
    final results = await Future.wait(
      ModelPhase.values.map(_repository.getModelForPhase),
    );
    if (isClosed) return;
    emit(ModelRoutingReady(Map.fromIterables(ModelPhase.values, results)));
  }

  Future<void> selectModel(ModelPhase phase, AgentModel model) async {
    await _repository.setModelForPhase(phase, model);
    if (isClosed) return;
    final current = state;
    final updated = current is ModelRoutingReady
        ? Map<ModelPhase, AgentModel>.of(current.modelByPhase)
        : <ModelPhase, AgentModel>{};
    updated[phase] = model;
    emit(ModelRoutingReady(updated));
  }
}
```

Kept as its own Cubit, separate from `ProviderSettingsCubit`/
`AutomationSettingsCubit`, following the same one-cubit-per-concern split
`AutomationSettingsCubit`'s dartdoc already documents.

### 2.3 `ProviderSettingsCubit` changes

Constructor changes from `(AgentModelClient, AgentSettingsRepository)` to
`(AgentModelClient, ModelRoutingRepository)`. `ProviderSettingsReady.selectedModel`
keeps its name (it's still accurate: "the model the connection test is
currently pinging") but its dartdoc changes to note it always mirrors
`ModelPhase.frontier`'s configured value:

```dart
Future<void> load() async {
  final model = await _repository.getModelForPhase(ModelPhase.frontier);
  // ...unchanged from here — emits ProviderSettingsReady, runs the test.
}

Future<void> testConnection() async {
  final current = state;
  if (current is! ProviderSettingsReady) return;
  if (current.status == ProviderConnectionStatus.checking) return;
  final model = await _repository.getModelForPhase(ModelPhase.frontier);
  await _runConnectionTest(model);
}
```

`selectModel` is deleted outright — model selection now happens
exclusively through `ModelRoutingCubit`'s three tier dropdowns, not a
standalone control `ProviderSettingsCubit` owns. Re-reading the Frontier
model fresh on every `load()`/`testConnection()` call (rather than
trusting a cached value) means `ProviderSettingsCubit` never needs to
listen to `ModelRoutingCubit` for the two cubits to stay consistent — the
next connection test after a Frontier-tier change simply picks it up.

`_runConnectionTest` itself is unchanged.

## 3. `features/tickets/presentation/cubit/tickets_cubit.dart`

### 3.1 Constructor

New optional named parameter, following the existing `agentClient`/
`commentRepository`/`automationSettingsRepository` pattern exactly:

```dart
TicketsCubit(
  this._repository, {
  // ...existing params...
  ModelRoutingRepository? modelRoutingRepository,
}) : super(const TicketsInitial()) {
  // ...existing assignments...
  _modelRoutingRepository = modelRoutingRepository;
}

late final ModelRoutingRepository? _modelRoutingRepository;
```

`null` (the default, and every existing test construction site) makes
model resolution fall back to `AgentModel.sonnet` — today's behavior,
unchanged for any caller that doesn't opt in. Real usage
(`app_router.dart`) always supplies it.

### 3.2 New private helper

```dart
/// Resolves [phase] to its currently configured [AgentModel], via
/// [_modelRoutingRepository]. Falls back to [AgentModel.sonnet] — the
/// hardcoded default every call site used before this change — when the
/// cubit was constructed without a [ModelRoutingRepository] (see the
/// constructor's dartdoc).
Future<AgentModel> _resolveModel(ModelPhase phase) async {
  final repo = _modelRoutingRepository;
  if (repo == null) return AgentModel.sonnet;
  return repo.getModelForPhase(phase);
}
```

### 3.3 Call-site changes

- `_spawnStageChat(Ticket parent, SddStage stage)` — the `ChatCubit.runChatTurn`
  call's `model: AgentModel.sonnet` becomes `model: await _resolveModel(stage.modelPhase)`.
- `retryDesignSync(Ticket designSyncChat)` — becomes
  `model: await _resolveModel(SddStage.designSync.modelPhase)` (always
  resolves to `ModelPhase.capable`, since `retryDesignSync` only ever
  runs at that stage — see its existing early-return guard).
- `_runCodingExecution(Ticket task)` — becomes
  `model: await _resolveModel(ModelPhase.execution)`, and the
  `// Out of scope: per-phase-tier-based-model-routing.` comment above it
  is deleted (no longer true).

No other change to any of the three methods' control flow, gating, or
queueing logic — this only changes where the `model:` argument's value
comes from.

## 4. `features/tickets/presentation/cubit/chat_cubit.dart`

### 4.1 Constructor

```dart
ChatCubit(
  this._repository,
  this._client,
  this._ticketRepository,
  this._modelRoutingRepository,
) : super(const ChatInitial());

final CommentRepository _repository;
final AgentModelClient _client;
final TicketRepository _ticketRepository;
final ModelRoutingRepository _modelRoutingRepository;
```

Both new dependencies are required, not optional — unlike `TicketsCubit`,
`ChatCubit` has no existing "constructed without full dependencies"
precedent; every construction site (`app_router.dart`, tests) always
wires it fully.

### 4.2 New private helper

```dart
/// Infers which [ModelPhase] governs [chatTicketId]'s model calls, from
/// its parent ticket: an `epic`/`story` parent's current [Ticket.sddStage]
/// (via [SddStageModelPhase.modelPhase]), or [ModelPhase.execution] for a
/// `task` parent. Every chat ticket in the app is spawned exclusively by
/// `TicketsCubit._spawnStageChat`/`_runCodingExecution` (confirmed: the
/// only two `createTicket` call sites for `TicketType.chat` in the
/// codebase), so a chat always has a resolvable parent in real usage —
/// the [ModelPhase.capable] fallback below only matters defensively
/// (a malformed/orphaned chat in tests).
Future<ModelPhase> _phaseForChat(String chatTicketId) async {
  final chat = await _ticketRepository.getTicketById(chatTicketId);
  final parentId = chat?.parentId;
  if (parentId == null) return ModelPhase.capable;
  final parent = await _ticketRepository.getTicketById(parentId);
  if (parent == null) return ModelPhase.capable;
  if (parent.type == TicketType.task) return ModelPhase.execution;
  return parent.sddStage?.modelPhase ?? ModelPhase.capable;
}
```

### 4.3 `sendMessage` signature change

Drops its `required AgentModel model` parameter; resolves the model
internally before calling the (unchanged) static `runChatTurn`:

```dart
Future<void> sendMessage({
  required String chatTicketId,
  required String content,
}) async {
  try {
    // ...unchanged: post the human comment, emit ChatLoaded...

    final phase = await _phaseForChat(chatTicketId);
    final model = await _modelRoutingRepository.getModelForPhase(phase);

    final succeeded = await runChatTurn(
      client: _client,
      commentRepo: _repository,
      chatTicketId: chatTicketId,
      prompt: content,
      model: model,
      onChunk: (textSoFar) => emit(ChatLoaded(afterHuman, streamingText: textSoFar)),
    );
    // ...unchanged from here.
  } catch (e) {
    emit(ChatError(e.toString()));
  }
}
```

`runChatTurn` itself (the static helper `TicketsCubit` also calls) is
**unchanged** — it stays a "run with whatever `AgentModel` the caller
already resolved" primitive, so `TicketsCubit`'s three call sites (which
already know their phase directly, with no inference needed) and
`ChatCubit.sendMessage` (which must infer it) can each resolve the model
their own way without duplicating `runChatTurn`'s accumulate/persist
logic.

### 6.3 `_ModelPhaseSection` (new widget)

Mirrors `_AutomationSection`'s structure (label + description + control),
but reuses the plain `AppDropdown<AgentModel>` the old single-model
picker already used — no `SelectionMenu`/mode-dot treatment needed here,
since `AgentModel` has no notion of "mode" the way `AutomationConfidence`
does; a dropdown of three plain model names is exactly what the old
Settings dropdown already rendered, just parameterized by phase now:

```dart
class _ModelPhaseSection extends StatelessWidget {
  const _ModelPhaseSection({
    required this.phase,
    required this.label,
    required this.description,
  });

  final ModelPhase phase;
  final String label;
  final String description;

  @override
  Widget build(BuildContext context) {
    final c = ThemeScope.of(context).colors;

    return BlocBuilder<ModelRoutingCubit, ModelRoutingState>(
      builder: (context, state) {
        if (state is! ModelRoutingReady) return const SizedBox.shrink();
        final model = state.modelByPhase[phase] ?? AgentModel.sonnet;
        return Column(
          crossAxisAlignment: CrossAxisAlignment.start,
          children: [
            Text(label, style: AionText.label.copyWith(color: c.textSecondary)),
            const SizedBox(height: AionSpacing.sp4),
            Text(description, style: AionText.bodySm.copyWith(color: c.textMuted)),
            const SizedBox(height: AionSpacing.sp8),
            AppDropdown<AgentModel>(
              value: model,
              items: AgentModel.values,
              itemLabel: (m) => m.label,
              semanticsLabel: label,
              onChanged: (m) => context
                  .read<ModelRoutingCubit>()
                  .selectModel(phase, m),
            ),
          ],
        );
      },
    );
  }
}
```

This is the one genuinely new visual component this change introduces —
hence the Design gate (proposal.md) is `PENDING`, not `NOT REQUIRED`.
Everything else in this change is domain/data/cubit-layer routing logic
with no new UI.

# Aion — Per-Phase-Tier Model Routing: Settings Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and the [Provider Configuration Spec](./Aion%20Provider%20Configuration%20Spec.md) (whose `SettingsScreen`, `ProviderStatusCard`, and `AppDropdown<AgentModel>` this change modifies). Sits directly beside the [Task Execution Trigger Spec](./Aion%20Task%20Execution%20Trigger%20Spec.md)'s generalized `_AutomationSection` on the same screen. References `AionColors`, `AionText`, `AionRadius`, `AionSpacing` by name.

This feature turns Aion's single hardcoded model into **per-phase-tier routing**: model calls are grouped into three capability tiers, and each tier is independently pointed at one of Aion's three configurable models. It is delivered **entirely on the existing `SettingsScreen`** — no new screens, no new popover, no navigation change:

- The existing single **"Model"** picker (Provider Configuration Spec §6 — one label + one `AppDropdown<AgentModel>`) is **removed**.
- In the same visual slot — **directly below the `ProviderStatusCard`, directly above the "AUTOMATION" section** — a new **"MODELS"** section is inserted: a `"MODELS"` eyebrow followed by three stacked instances of one new repeated component, **`_ModelPhaseSection`** (§2), one per tier (Frontier / Capable / Execution).

Mockups: [Aion Per-Phase Model Routing Mockups](./Aion%20Per-Phase%20Model%20Routing%20Mockups.dc.html).

**No Material widgets or types anywhere.** Every surface below is `DecoratedBox` / `Container` / `Column` / `Row` / `Padding` / `GestureDetector` / `MouseRegion` / `AnimatedScale` / `CustomPaint` — never `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `ListTile`, `AppBar`, `DropdownButton`, or `InkWell`.

Themes: **Arctic** (light, celestial cold) and **Obsidian** (dark, abyssal cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is quoted `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` — never hardcoded ARGB.

**No new color, typography, radius, or spacing tokens are required.** The only structural additions are two enums (`ModelTier`, `AgentModel`) and a tier→model routing map (§6).

## 2. `_ModelPhaseSection` — the one new component

The single new visual component, rendered **three times** (Frontier / Capable / Execution). It is deliberately built to be **byte-identical in geometry to `_AutomationSection`** (Task Execution Trigger §4.2) so the two section families read as one consistent Settings pattern where they sit adjacent — the only difference is that its control is a plain `AppDropdown<AgentModel>` (no leading mode dot, §2.4).

### 2.1 Widget contract

```dart
class _ModelPhaseSection extends StatelessWidget {
  final String label;         // "Frontier Model" | "Capable Model" | "Execution Model"
  final String description;   // one-line tier description (§5)
  final AgentModel value;     // currently routed model for this tier
  final ValueChanged<AgentModel> onChanged;
  const _ModelPhaseSection({ required this.label, required this.description, required this.value, required this.onChanged });
}
```

### 2.2 Block structure & internal spacing

`Column`, `crossAxisAlignment: stretch`, three children with fixed gaps (mirrors `_AutomationSection` §4.2 exactly):

| Element | Style | Color | Gap below |
|---|---|---|---|
| **Label** | `AionText.label` (Manrope 12 / w700) | `textSecondary` (`#46586A / #A2AEC6`) | `6` |
| **Description** | `AionText.bodySm` (Manrope 13.5 / w400), `height: 1.5`, wraps | `textMuted` (`#8496A6 / #6B7690`) | `10` |
| **Dropdown** | `AppDropdown<AgentModel>` (§2.4), full-width | — | — |

No fill, no border, no radius, no padding box on the block itself — it sits flush in the body `Column`, exactly like `_AutomationSection`.

### 2.3 Spacing between the three instances

## 6. New enums / types (no new design tokens)

```dart
/// The three capability tiers model calls are grouped into.
enum ModelTier { frontier, capable, execution }

/// Aion's three configurable models.
enum AgentModel { opus48, sonnet5, haiku45 }

extension AgentModelDisplay on AgentModel {
  String get displayName {
    switch (this) {
      case AgentModel.opus48:  return 'Opus 4.8';
      case AgentModel.sonnet5: return 'Sonnet 5';
      case AgentModel.haiku45: return 'Haiku 4.5';
    }
  }
}

/// Persisted routing: which model handles each tier.
/// Replaces the single `AgentModel selectedModel` the old "Model" picker bound to.
typedef ModelRouting = Map<ModelTier, AgentModel>;

const ModelRouting kDefaultRouting = {
  ModelTier.frontier:  AgentModel.opus48,
  ModelTier.capable:   AgentModel.sonnet5,
  ModelTier.execution: AgentModel.sonnet5,
};
```

Each `_ModelPhaseSection` reads `routing[tier]` for its `value` and writes back through `onChanged`, which updates that single tier's entry in the `ModelRouting` map. Every model call site resolves its model by asking the routing map for its tier instead of reading the removed single-model field.

**No new `AionColors`, `AionText`, `AionRadius`, or `AionSpacing` members.** Every color is an existing token; every text style is an existing `AionText.*`; every radius/spacing is an existing scale value or a stated 4-multiple.
