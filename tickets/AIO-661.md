# Decision Graph Rule Builder

# Proposal: Decision Graph Rule Builder

Originates from [`aion-arch/ideas/pluggable-decision-graph-conditions.md`](../../ideas/pluggable-decision-graph-conditions.md)
(Phase A of that idea — the deterministic half only; see that file's
"/explore findings" section for why `agentJudgment`/the round-trip half
is deliberately excluded here).

## Problem

`automation-decision-graphs` (archived) gave projects a project-editable
decision graph per `AutomationContext`, but its condition catalog
(`decisionConditionsFor`, `decision_condition_catalog.dart`) ships
exactly two hardcoded entries — `attemptExceedsMax` (fixed at `>`,
`codingExecutionRetry` only) and `sessionOverageDetected` (a flag,
`codingExecution` only). A project that wants a different comparison on
an already-exposed signal (e.g. `attempt >= 2` instead of `attempt > 3`,
or `attempt == 1`) has no way to express it without an Aion developer
adding a new catalog entry and a matching `decision_graph_evaluator.dart`
case — real pluggability doesn't exist yet, only two fixed presets.

## What this builds

A third way to define a `DecisionNode`'s condition, alongside today's
fixed catalog: a **rule builder** — pick a field, an operator, and a
value, entirely from the existing `DecisionNodeForm` condition picker,
no code. A project can now express any comparison the exposed field
vocabulary supports (`attempt >= 2`, `attempt == 1`, `session overage is
false`, ...) without touching Dart.

This is deliberately **not** a big-bang expansion of what's checkable.
Per the idea file's own conclusion, the field vocabulary grows
incrementally as real cases come up — this slice exposes exactly the two
signals `DecisionEvalContext` already carries (`attempt`,
`sessionOverageDetected`), covering the same two contexts today's fixed
catalog already covers (`codingExecutionRetry`, `codingExecution`). The
new capability is the *operator*, not new data: a project picks from six
comparisons on `attempt` (was fixed at `>`) instead of one, and two on
`sessionOverageDetected` (was implicitly `== true`, unable to gate on
`false`).

Rule-builder conditions coexist freely with catalog conditions in the
same graph, node by node — a project can mix `attemptExceedsMax` at one
node and a custom `attempt <= 1` rule at another. Both are instant and
synchronous; a rule-builder match hard-overrides exactly like a catalog
condition does today.

### Why this is safe to ship standalone

No schema change. `DecisionNode.conditionParams` is already a free-form
`Map<String, dynamic>` (JSON column, `conditionParamsJson`) — a rule's
`{field, operator, value}` fits inside it exactly as a catalog
condition's parameters do today, no new drift table or column.
`DecisionGraphConfigCubit`'s CRUD and strict-tree invariant enforcement
are already condition-agnostic (they never inspect `conditionId`/
`conditionParams` semantically) — zero changes there. The only new
surface is: one new evaluator registry case, one new catalog file
(field/operator vocabulary), and the `DecisionNodeForm`/`GraphCanvas`/
`DecisionOutlineList` UI to author and display a rule instead of a fixed
catalog entry.

## Non-goals (deliberately deferred)

- **`agentJudgment` and any round-trip mechanic.** Phase B of the same
  idea, intentionally excluded — its round-trip design isn't settled
  (see the idea file's "/explore findings": no session/resume concept
  exists on `AgentModelClient`, and the contexts that would want it call
  `_evaluateDecisionGraph` from inside an already-pending tool-call
  handler, so "reuse the live session" doesn't have a mechanism to hang
  on to).
- **Expanding `DecisionEvalContext` to the other 6 `AutomationContext`
  values.** Only `attempt`/`sessionOverageDetected` exist today; this
  slice exposes exactly those two as rule-builder fields. Wiring new
  signals for `sddStage`, `ticketCreation`, `ticketLinking`,
  `codingExecutionResume`, `specAutoLink`, `chatBranching` is real,
  separate instrumentation work per context, left for when a concrete
  case needs it — matches the idea file's "grow incrementally" guidance.
- **Reusable/named custom conditions.** A rule is authored inline, per
  node, exactly like the idea file concluded — no shared rule library.
- **Retiring the two existing catalog entries.** `attemptExceedsMax`/
  `sessionOverageDetected` stay exactly as they are (including as the
  seeded baseline graphs) — the rule builder is an additional picker
  option, not a replacement.
- **Visual cost/latency differentiation between node kinds.** That open
  question from the idea file is about `agentJudgment` (a live model
  call) vs. instant nodes — moot here, since a rule-builder node is just
  as instant/synchronous as a catalog condition.
