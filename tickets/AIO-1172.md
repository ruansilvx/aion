# Design: Model-Agnostic Naming in `project.md`

No BLoC states, widget tree, or Dart architecture applies — this change
edits Markdown prose only. This document specifies the exact before/after
wording for each passage so `/apply` can execute it without needing to
make independent judgment calls.

## Guiding rule

Every passage that names an agentic tier states the **role** first. The
vendor/provider currently filling that role is demoted to a parenthetical
example ("e.g. Claude Agent SDK") rather than the tier's identity. This
mirrors the pattern `project.md` already applies to the
conversational-reasoning tier ("Messages API (or any configured
provider)") — this change extends the same treatment to the
coding-execution tier and its downstream references.

No new Dart type is introduced. `AgentModelClient` remains the single
shared interface for all tiers, as already documented in §3's code
snippet — that snippet is unchanged.

## Edits to `aion-arch/project.md`

### 1. "What Is Aion" section

Remove the trailing caveat sentence, since the drift it points at will
no longer exist:

Before:
> Aion is agent/model-agnostic by design — no user-facing text, docs, or
> naming should hardcode a specific vendor or model provider (Claude,
> Anthropic, GPT, Gemini, etc.). Provider identity is a user-configured
> setting (see "Provider configuration" under Foundational Decisions §5),
> not part of Aion's own branding or architecture naming. This is not yet
> fully true of this document — see `aion-arch/specs/README.md`'s "Known
> gaps" for the current state of the retrofit.

After:
> Aion is agent/model-agnostic by design — no user-facing text, docs, or
> naming should hardcode a specific vendor or model provider (Claude,
> Anthropic, GPT, Gemini, etc.). Provider identity is a user-configured
> setting (see "Provider configuration" under Foundational Decisions §5),
> not part of Aion's own branding or architecture naming.

### 2. §3 Agentic Engine — "Desktop — coding execution" subsection

Before (header + body):
> #### Desktop — coding execution (Claude Agent SDK)
> Claude Agent SDK (Node.js subprocess, controlled via dart:io Process).
> Exposes the full Claude Code agent loop: file edits, git, bash, MCP,
> subagents, permission system. Authenticated via the user's Claude plan.
> Only invoked when a Task ticket is ready for coding execution (/apply
> equivalent). Not used for ticket management, watcher reviews, or spec work.

After:
> #### Desktop — coding execution
> Delegated to the user's configured coding-execution provider (currently
> only Claude Agent SDK: a Node.js subprocess, controlled via dart:io
> Process, exposing the full Claude Code agent loop — file edits, git,
> bash, MCP, subagents, permission system — authenticated via the user's
> Claude plan). Only invoked when a Task ticket is ready for coding
> execution (/apply equivalent). Not used for ticket management, watcher
> reviews, or spec work.

### 3. §3 Agentic Engine — "conversational reasoning" subsection header

Before:
> #### All platforms — conversational reasoning (Messages API)

After (drop the vendor-named parenthetical; body already says "or any
configured provider" one line down, so the header shouldn't repeat a
single vendor's API name):
> #### All platforms — conversational reasoning

Body text is unchanged.

### 4. §3 Agentic Engine — Watcher implementation note

Before:
> The Claude Agent SDK only enters the picture if the watcher's delegation
> decision results in a Task ready for coding execution — at that point
> Aion hands off to the SDK subprocess.

After:
> The coding-execution provider (e.g. Claude Agent SDK) only enters the
> picture if the watcher's delegation decision results in a Task ready
> for coding execution — at that point Aion hands off to it.

### 5. §5 Model Routing — Capability tiers

Before:
> - Tier 3 — Execution: file edits, mechanical task implementation.
>   On desktop: backed by Claude Agent SDK subprocess.
>   On mobile/web: not available (no filesystem/subprocess access).

After:
> - Tier 3 — Execution: file edits, mechanical task implementation.
>   On desktop: backed by the configured coding-execution provider (e.g.
>   Claude Agent SDK).
>   On mobile/web: not available (no filesystem/subprocess access).

### 6. §5 Model Routing — Orchestration pattern

Before:
> Tier 1 watchers decompose Epics/Stories into Tasks dispatched
> downward. Tier 1 is always the architect for its own decomposition;
> Tier 3 (Claude Agent SDK on desktop) is the executor for leaf-level
> coding work. If Tier 3 fails repeatedly, the escalation mechanism
> hands the Task back to Tier 1, which fixes it directly or determines
> the Task was mis-scoped and needs splitting.

After:
> Tier 1 watchers decompose Epics/Stories into Tasks dispatched
> downward. Tier 1 is always the architect for its own decomposition;
> Tier 3 (the configured coding-execution provider, e.g. Claude Agent
> SDK, on desktop) is the executor for leaf-level coding work. If Tier 3
> fails repeatedly, the escalation mechanism hands the Task back to
> Tier 1, which fixes it directly or determines the Task was mis-scoped
> and needs splitting.

### Unchanged (out of scope)

§5 Provider configuration's bullet list (Anthropic API, Claude Agent
SDK, Ollama / local, OpenAI, OpenAI-compatible / custom, Firebase AI
Logic) stays exactly as-is — it's the user-facing enumeration of
concrete provider options, which is supposed to name vendors.
