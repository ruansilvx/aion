# Parallel Work

# Proposal: Concurrent, cancellable, restart-safe coding execution

## What we're building

Coding execution (`task`/`bug` tickets moving to `TicketStatus.inProgress`)
today runs exactly one model turn at a time, off an in-memory FIFO queue,
with no way to cancel a queued or in-flight run and no memory of that
queue across an app restart. This change replaces that fixed behavior
with a **user-selectable scheduling mode**, a **real cancellation
mechanism**, and **persisted, confidence-gated restart recovery**:

1. **Scheduling mode** — a new Settings choice, "Coding execution
   scheduling": **Strict FIFO** (today's shipped behavior, unchanged),
   **Parallel** (up to a configurable number of runs execute
   concurrently, each already isolated in its own `git worktree`), or
   **Hybrid** (parallel, but Tasks/Bugs sharing a parent Story never run
   concurrently against each other — same-parent siblings serialize
   automatically to avoid the two of them touching overlapping code at
   once). A configurable concurrency ceiling applies under
   Parallel/Hybrid, additionally capped to 1 for the rest of the session
   the first time `AgentOverageDetectedEvent` fires (reusing that
   existing reactive signal, same precedent as coding-execution's
   existing gated-on-overage behavior).
2. **Real cancellation** — a cancellation handle threaded through
   `AgentModelClient` → `ClaudeAgentSdkClient`/`AnthropicMessagesApiClient`
   → `ChatCubit`, surfaced as a cancel action on a running or queued
   coding-execution Task/Bug, and as a stop button on any streaming chat
   reply. Cancelling reverts the ticket to whatever status it had
   immediately before the trigger, preserves any artifacts already
   created (the worktree's branch and commits — never the worktree
   directory itself, which is always removed, cancelled or not), and
   posts a visible comment so the ticket doesn't look untouched. This
   fully absorbs `cancel-in-flight-agent-reply.md`'s scope — a plain
   chat's stop button and coding-execution's cancel action both become
   callers of the same underlying mechanism.
3. **Restart persistence** — queue and in-flight execution state moves
   off pure in-memory `TicketsCubit` fields onto a new Drift table. On
   the next app launch, Aion detects any interrupted runs and offers to
   resume them, gated by a new `AutomationConfidence` consumer
   (`AutomationContext.codingExecutionResume`): `auto` resumes silently,
   `gated` asks first, `manual` just leaves them for the existing
   failure-banner retry path.

Additionally, in Hybrid mode, the Board visually clusters sibling
Tasks/Bugs adjacently within their status column, so the serialization
this mode enforces is visible, not just inferred from behavior.

## Why

Filed directly against a Known gap already documented in
`aion-arch/specs/tickets.md`'s Known gaps section (coding execution
"runs one Task or Bug at a time, FIFO — no concurrent execution, and no
way to cancel a queued or in-flight run. The queue is in-memory only and
does not survive an app restart"). Explored across two `/brainstorm`
sessions, persisted at `aion-arch/ideas/parallel-work.md`
(`status: explored`) — see that file for the full question-by-question
reasoning trail, including the grounding check that Aion's existing
`blocks`/`blockedBy` hard-gate already prevents two explicitly-linked
tickets from ever running concurrently (this change doesn't touch that
gate; Hybrid mode's sibling serialization is a *softer*, automatic
signal on top of it, for tickets that aren't explicitly linked but are
still likely to conflict).

Worktree isolation (`coding-execution-reliability-and-safety`, shipped)
already gives every run its own isolated checkout — the one thing
standing between that and genuine concurrency is `TicketsCubit`'s own
single-slot bookkeeping (`_inFlightExecutionTaskId` as a scalar, not a
set) and the complete absence of a cancellation primitive anywhere in
the `AgentModelClient` stack. This change spends that existing
investment rather than leaving it unused.

## Non-goals

- **No new dependency-tracking data.** Hybrid mode's serialization
  signal is `Ticket.parentId` only — no new field, no user-authored
  "conflicts with" relationship. Explicit `blocks`/`blockedBy` links
  keep hard-gating `inProgress` exactly as they do today, unchanged by
  this proposal.
- **No persistent notification center.** `board-execution-indicators-
  and-notifications.md` explicitly deferred that "until Aion invests in
  parallel execution" — that precondition is now met, but building the
  notification center itself is a separate, later idea, not part of
  this slice.
- **No predictive budget gate.** The concurrency ceiling's overage
  cap-down reuses the existing reactive `AgentOverageDetectedEvent`
  signal; no cost-estimate-based proactive gate is introduced here.
- **No cross-provider cancellation semantics beyond what's needed.**
  Cancellation is added to both existing `AgentModelClient`
  implementations (`ClaudeAgentSdkClient`, `AnthropicMessagesApiClient`)
  since both are reachable from `ChatCubit`, but no new provider is
  added or changed in shape beyond the cancellation method itself.
- **No change to the blocked-dependency gate, design-review gate, or
  verify/retry mechanics** coding execution already has — this proposal
  only changes *how many* runs can be in flight, *whether* one can be
  stopped, and *whether* the queue survives a restart.
- **No deeper hierarchy for Hybrid's sibling signal.** Two Tasks under
  different Stories but the same Epic are not treated as related, even
  though they share a grandparent — scoped to direct same-parent
  siblings only, per the brainstorm session's explicit scoping.
