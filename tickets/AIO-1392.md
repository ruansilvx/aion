# Spec Delta: Page Content Markdown Editor (restructured — dedicated `features/pages/` module)

**Reconciled 2026-09-03:** checked against the current `aion-arch/specs/tickets.md's Pages module section` — the mechanism/behavior this delta describes is still present and architecturally coherent with current text. Identifiers the automated screen flagged as missing are private-method requalification, line-wrapped tokens, or names covered in a neighboring section rather than repeated here — not behavioral drift. PageTicketProvider/PagesCubit and the create/edit/link mechanisms this delta introduces all confirmed current.

Relative to `aion-arch/specs/tickets.md`.

## ADDED

- A new `markdown` package dependency (`pubspec.yaml`) — the `dart-lang`-
  maintained, pure-Dart CommonMark parser, used with `ExtensionSet.gitHubWeb`
  for GFM tables/strikethrough/task-lists/autolinks. Parsing only; no
  Flutter/Material dependency, no rendering pieces of the package are used.
- `MarkdownView` (`design_system/molecules/markdown_view.dart`) — a
  read-only, non-Material widget rendering the `markdown` package's parsed
  AST (full CommonMark + GFM extensions: headings, paragraphs with inline
  emphasis/links, bullet/ordered/nested/task lists, fenced/indented code
  blocks, blockquotes, horizontal rules, tables) using `AionText`/
  `AionColors` tokens. Inline images render as alt text only (full image
  display deferred). Any unrecognized node falls back to a plain-text
  paragraph rather than erroring.
- `MarkdownEditor` (`design_system/molecules/markdown_editor.dart`) — a
  responsive Markdown content editor:
  - On screens `constraints.maxWidth <= 640`: a view/edit toggle — rendered
    Markdown by default, an explicit edit affordance switches to a raw-text
    editor, with explicit Save/Cancel to commit.
  - On screens wider than that: a live split view — raw Markdown editor and
    rendered preview side by side, updating live as the user types, still
    committing only via explicit Save/Cancel.
  - Never auto-commits on blur or on a timer, matching
    `InlineEditableField`'s existing multiline commit discipline.
- A new `features/pages/` feature module:
  - `PageDetailScreen` (`/workspace/pages/:id`) — renders a page's title,
    the new `MarkdownEditor` content editor, sub-pages tree, linked
    tickets, and backlinks. No priority/estimate/time-spent/status fields
    and no comment thread (both explicitly out of scope for pages).
  - `PageCreateScreen` (`/workspace/pages/new`) — a trimmed creation form:
    title, optional parent, optional initial content. Navigates into the
    new page's `PageDetailScreen` on success.
  - `PagesCubit` — the module's data-orchestration Cubit, built entirely
    on the new `PageTicketProvider` contract (never on `TicketsCubit`/
    `TicketRepository` directly).
- `core/contracts/page_ticket_provider.dart` — a new cross-feature
  contract (`PageTicketProvider` + `PageRelations`), per `project.md`'s
  Pattern 1. Implemented by `PageTicketProviderImpl`
  (`features/tickets/data/page_ticket_provider_impl.dart`): reads
  (`getPage`, `loadPageRelations`, `getValidParentCandidatesForPage`) go
  directly to `TicketRepository`/`TicketLinkRepository`; writes
  (`createPage`, `updatePage`, `trashPage`) delegate to `TicketsCubit`'s
  existing `createTicket`/`updateTicket`/`trashTicket` methods, reusing
  their validation/invariant logic rather than duplicating it.
- `core/routing/ticket_navigation.dart` — a `ticketDetailRoute(Ticket)`
  resolver returning `/workspace/pages/:id` for `page` tickets and
  `/workspace/tickets/:id` for every other type, used by every call site
  that navigates to a ticket generically by id.
- New promoted `design_system/molecules/` widgets: a sub-pages section, a
  linked-tickets section, a backlinks section, and a sync-status
  badge/repair banner — generalized (if not already) from their current
  `tickets`-owned equivalents, since `features/pages/` cannot import
  `features/tickets/` internals directly.
- New `app_en.arb` strings under `pageDetail*`/`pageCreate*` prefixes
  (replacing the `ticketDetail*`-prefixed names from the original
  proposal, since these now belong to `pages`' own screens):
  `pageDetailContentPlaceholder`, `pageDetailEditContent`,
  `pageDetailMarkdownEditToggle`, `pageDetailMarkdownViewToggle`,
  `pageDetailMarkdownSave`, `pageDetailMarkdownCancel`,
  `pageDetailTitlePlaceholder`, `pageCreateTitlePlaceholder`,
  `pageCreateParentFieldPlaceholder`.

## MODIFIED

- `page`-type tickets no longer use `TicketDetailScreen`/
  `CreateTicketScreen` — they use the new `PageDetailScreen`/
  `PageCreateScreen` instead. Every other ticket type (`epic`, `story`,
  `task`, `resource`, `chat`) is unaffected; `TicketDetailScreen` keeps its
  existing plain-text `InlineEditableField<String?>` description editor
  for all of them.
- `TicketsCubit.createTicket`/`.updateTicket`: both now return
  `Future<Ticket>` (the persisted/refreshed ticket) instead of
  `Future<void>`, in addition to still emitting the same Bloc state as
  before. Backward compatible — existing callers may ignore the return
  value.
- `AppTextField` (`design_system/atoms/app_text_field.dart`): `maxLines`
  now explicitly accepts `null` (unbounded/expanding textarea), passed
  through to the underlying `TextField` as-is. Existing callers (which all
  pass a finite `maxLines`) are unaffected.
- `CreateTicketScreen`'s type picker no longer offers `page` as an option.
- `DocumentationScreen`'s "+ New page" action and page-node taps now
  navigate to the new `/workspace/pages/*` routes instead of the shared
  `/workspace/tickets/*` routes. "+ New resource" and resource-node taps
  are unchanged.

## REMOVED

- `page`-type tickets' use of `TicketDetailScreen`/`CreateTicketScreen`
  (superseded by `PageDetailScreen`/`PageCreateScreen` above).

`ticket.description` remains the same nullable `String` field for every
ticket type, including `page` — no data model, drift schema, or
sync-pipeline change. The type-compatibility matrix, Markdown git-sync/
embeddings pipeline, trash flow, and linked-tickets/backlinks
infrastructure are all unchanged; only which screens render a `page` and
which module owns them changes.

## Not in scope (explicitly deferred)

- A draggable/reorderable block-based editor (custom content data model
  beyond a plain Markdown string) — may be revisited later.
- A formatting toolbar (bold/heading/list buttons) — v1 requires typing raw
  Markdown syntax; the toolbar is a possible fast-follow.
- Full inline image display — renders alt text only in v1; better scoped
  alongside the file-visualization work already owned by the
  `upload-and-visualize-files-for-resource-tickets` idea.
- Interactive GFM task-list checkboxes — rendered read-only; toggling one
  to mutate the underlying Markdown source is out of scope for this change.
- Any change to `resource`-ticket editing — resources stay on the shared
  `TicketDetailScreen`/`CreateTicketScreen`, covered separately by the
  `upload-and-visualize-files-for-resource-tickets` idea.
- A comment thread on `PageDetailScreen` — not ported from
  `TicketDetailScreen` in this slice, to keep the widget-promotion list
  bounded. May be revisited later.
- Any change to the Markdown file-sync pipeline
  (`TicketMarkdownSerializer`/`TicketMarkdownReconciler`/
  `TicketMarkdownWatcherService`), the `Ticket` entity, or the
  type-compatibility matrix — content stays a plain string round-tripped
  exactly as it already is today.
