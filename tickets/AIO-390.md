# Design: Board execution/activity indicators and app-wide notifications

All file paths are relative to the `aion` repo. Line numbers below are as of this proposal's `/explore` verification pass and will drift once `/apply` starts editing — treat them as locators, not guarantees.

## 1. `TicketsCubit` (`lib/features/tickets/presentation/cubit/tickets_cubit.dart`)

### 1.1 New in-memory field

```dart
/// Epic/Story ids currently mid-advance (their `advanceSddStage` chat
/// spawn hasn't finished its first AI turn yet), plus — once known — the
/// id of the chat ticket that spawn is running against. Both ids for the
/// same in-flight advance are added/removed together, so `getTicketById`
/// can compute `isAdvancingStage` uniformly whether the currently loaded
/// ticket is the Epic/Story itself or its freshly spawned stage chat.
/// Unlike `_inFlightExecutionTaskId`, this is a `Set`, not a single
/// nullable id plus a FIFO queue — stage chats share no exclusive
/// resource (no git worktree, unlike coding-execution), so multiple
/// Epic/Story advances can run fully concurrently. In-memory only, does
/// not survive an app restart (mirrors `_inFlightExecutionTaskId`).
final Set<String> _inFlightStageAdvanceIds = {};
```

### 1.2 `advanceSddStage` — split into fast-awaited + backgrounded

Current shape (`tickets_cubit.dart:723-750`) persists the stage, re-emits, then `return await _spawnStageChat(refreshed, nextStage)` — one call that blocks on the full chat turn. New shape:

```dart
Future<String?> advanceSddStage(Ticket ticket) async {
  if (ticket.type != TicketType.epic && ticket.type != TicketType.story) {
    await _emitSddStagePreconditionNotMet(ticket.id);
    return null;
  }
  if (_inFlightStageAdvanceIds.contains(ticket.id)) {
    // Already mid-advance — a double-tap/rebuild race. No-op rather than
    // starting a second concurrent spawn for the same ticket.
    return null;
  }

  final nextStage = await _nextSddStage(ticket);
  if (nextStage == null) {
    await _emitSddStagePreconditionNotMet(ticket.id);
    return null;
  }
  if (!(await _sddStageAdvanceCheck(ticket)).canAdvance) {
    await _emitSddStagePreconditionNotMet(ticket.id);
    return null;
  }

  try {
    await _repository.updateTicketSddStage(ticket.id, nextStage);
    final refreshed = await _repository.getTicketById(ticket.id);
    if (refreshed == null) return null;
    if (nextStage == SddStage.archived) {
      emit(TicketDetailLoaded(refreshed));
      return null;
    }

    _inFlightStageAdvanceIds.add(ticket.id);
    emit(TicketDetailLoaded(refreshed, isAdvancingStage: true));
    _refreshInFlightBoardState();

    final chatId = await _createStageChat(refreshed, nextStage);
    if (chatId == null) {
      _inFlightStageAdvanceIds.remove(ticket.id);
      _refreshInFlightBoardState();
      return null;
    }
    _inFlightStageAdvanceIds.add(chatId);
    unawaited(_runStageChatTurn(refreshed, nextStage, chatId));
    return chatId;
  } catch (e) {
    _inFlightStageAdvanceIds.remove(ticket.id);
    emit(TicketsError(e.toString()));
    return null;
  }
}
```

Notes:
- The caller-visible contract barely changes: still `Future<String?>`, still resolves to the spawned chat's id once it's safe to navigate there. It now resolves **after chat-ticket creation** instead of **after the first AI reply** — faster, and it's what makes `_advanceSddStage` in `ticket_detail_screen.dart` (below) not need to change its own shape at all.
- `_inFlightStageAdvanceIds.add(ticket.id)` happens *before* the `_createStageChat` await, so a Board card watching this Epic/Story flips to "Advancing" immediately, even during the brief window before the chat ticket itself exists.

### 1.3 `_spawnStageChat` → `_createStageChat` + `_runStageChatTurn`

`_spawnStageChat` (`tickets_cubit.dart:2148-2214`) currently does chat-ticket creation, the design-Page side effect, the context-comment post, *and* the `ChatCubit.runChatTurn` call, all `await`ed in sequence, returning the chat id only at the very end. Split at the existing natural seam — chat creation is already `await`ed before `runChatTurn` is even reached today:

- **`_createStageChat(Ticket parent, SddStage stage)`** — everything `_spawnStageChat` did up through `return persistedChat.id`, *except* the trailing `ChatCubit.runChatTurn` call. Same guards (`null` if no `AgentModelClient`/`CommentRepository`), same design-Page side effect for `designBrief`, same context-comment post (needed before the AI turn regardless of when the turn itself runs).
- **`_runStageChatTurn(Ticket parent, SddStage stage, String chatId)`** — calls `ChatCubit.runChatTurn(...)` with the same arguments `_spawnStageChat` used, reusing `_assembleStageContext`'s already-computed prompt (pass it through rather than recomputing). Wrapped in a `catch` that posts a `"Stage advance failed: <e>"` system comment (mirrors `_runCodingExecution`'s `"Execution failed: ..."` catch-comment shape, `tickets_cubit.dart:1283-1287`) so a hard error surfaces in the chat transcript instead of silently vanishing into a discarded `unawaited` future. On completion (success or failure), removes both `parent.id` and `chatId` from `_inFlightStageAdvanceIds` and calls `_refreshInFlightBoardState()`.

`retryDesignSync` (`tickets_cubit.dart:979-990`) is unaffected — it already posts directly to an existing chat via the same `ChatCubit.runChatTurn` helper, not through `_spawnStageChat`; leave it `await`ed as today (re-validation is meant to be quick feedback after a design edit, not a long-running turn the idea file asked to background).

### 1.4 Board-wide reactive signal — `TicketsLoaded` gains in-flight fields

The core gap: `_triggerOrQueueCodingExecution`/`_dequeueNext` mutate `_inFlightExecutionTaskId`/`_executionQueue` with **no accompanying `emit`**, so nothing reaches the Board's `TicketsLoaded` state at all today. Fix: extend `TicketsLoaded` with three additive fields, and add a private helper that re-emits it (using its own already-known `tickets`/`hasMore`, unchanged) whenever the in-flight sets change *and* a list-shaped state is currently active:

```dart
// tickets_state.dart — TicketsLoaded
const TicketsLoaded(
  this.tickets, {
  required this.hasMore,
  this.inFlightExecutionIds = const {},
  this.executionQueuePositions = const {},
  this.inFlightAdvanceIds = const {},
});

final Set<String> inFlightExecutionIds;
final Map<String, int> executionQueuePositions;
final Set<String> inFlightAdvanceIds;
```

```dart
// tickets_cubit.dart
/// Re-emits the current list-shaped state (`TicketsLoaded` only — a
/// no-op while a detail screen or a mutation-in-flight state is active,
/// since there's no Board to refresh in that case) with
/// `inFlightExecutionIds`/`executionQueuePositions`/`inFlightAdvanceIds`
/// recomputed from `_inFlightExecutionTaskId`/`_executionQueue`/
/// `_inFlightStageAdvanceIds`. Called at every mutation site of those
/// three — `_triggerOrQueueCodingExecution`, `_dequeueNext`,
/// `_runCodingExecution`'s completion paths, and every
/// `_inFlightStageAdvanceIds` mutation in `advanceSddStage`/
/// `_runStageChatTurn` — so `TicketBoardCard` never needs to poll.
void _refreshInFlightBoardState() {
  final current = state;
  if (current is! TicketsLoaded) return;
  emit(
    TicketsLoaded(
      current.tickets,
      hasMore: current.hasMore,
      inFlightExecutionIds: _inFlightExecutionTaskId == null
          ? const {}
          : {_inFlightExecutionTaskId!},
      executionQueuePositions: {
        for (var i = 0; i < _executionQueue.length; i++)
          _executionQueue[i]: i + 1,
      },
      inFlightAdvanceIds: Set.unmodifiable(_inFlightStageAdvanceIds),
    ),
  );
}
```

Call sites needing a `_refreshInFlightBoardState()` added: `_triggerOrQueueCodingExecution` (after setting `_inFlightExecutionTaskId`/appending to `_executionQueue`), `_dequeueNext` (after popping), `_runCodingExecution`'s two `_inFlightExecutionTaskId = null` completion points (`tickets_cubit.dart:1466`, `1487`) and its catch-path clear (`1681`), plus every `_inFlightStageAdvanceIds` mutation from §1.2/§1.3 above.

This is deliberately a **separate reactive channel from `TicketDetailLoaded`** — the Board never calls `getTicketById` per card (that would be its own N-query problem), so it can't reuse that computation path. `TicketsLoaded`'s existing `Equatable` props already do structural (not reference) comparison via the `equatable` package's `DeepCollectionEquality`, so BLoC's own `emit`/rebuild-skipping stays correct with `Set`/`Map` fields; widget-level `context.select` (§3.1) reads *derived primitive values* off these fields, not the raw collections, so per-card rebuilds stay precise (see §3.1 for why that distinction matters).

### 1.5 `getTicketById` — `isAdvancingStage` computation

Extends the existing `task`/`bug`-only block (`tickets_cubit.dart:2439-2470`) with a parallel `epic`/`story`-*and*-`chat` block:

```dart
final isAdvancingStage = _inFlightStageAdvanceIds.contains(ticket.id);

String? sddStageFailureReason;
var sddStageCanRetry = false;
if ((ticket.type == TicketType.epic || ticket.type == TicketType.story) &&
    !isAdvancingStage &&
    ticket.sddStage != null) {
  final (reason, canRetry) = await _computeStageAdvanceFailure(ticket.id);
  sddStageFailureReason = reason;
  sddStageCanRetry = canRetry;
}
```

`isAdvancingStage` applies to **both** an Epic/Story ticket (drives the "Advancing to `<stage>`" banner replacing `_SddStageSection`'s Advance button/hint, §3.2) and a `chat`-type ticket that is itself the in-flight stage chat (drives the "Waiting for reply…" indicator when the human navigates straight to it, §3.3) — both check membership in the same `_inFlightStageAdvanceIds` set, per §1.1's "both ids added/removed together" design. `sddStageFailureReason`/`sddStageCanRetry` are Epic/Story-only (a chat ticket doesn't itself have a "failed" state — its parent does).

### 1.6 `_computeStageAdvanceFailure(String epicOrStoryId)`

Mirrors `_computeExecutionFailure(String taskId)`'s shape: finds the ticket's most recently created `chat`-type child (same "most recent" lookup pattern as `_mostRecentExecutionChat`, scoped to stage-chat titles rather than `"Coding Execution — "`-prefixed ones), inspects its most recent comment:
- Most recent comment starts with `"Stage advance failed: "` (posted by `_runStageChatTurn`'s catch block, §1.3) → `(that comment's content, true)`.
- No `chat` child exists yet, or the most recent comment is `ai`-authored (the turn completed normally) → `(null, false)`.
- A `chat` child exists, its most recent comment is *not* `ai`-authored, and the ticket is **not** in `_inFlightStageAdvanceIds` (i.e., orphaned — most likely an app restart happened mid-turn) → a fixed "Stage advance ended without a clear result." message, `canRetry: true`, mirroring `_computeExecutionFailure`'s own orphaned/stalled fallback.

No auto-retry loop, no new `AutomationContext` — retry is always a manual action (a button re-calling `advanceSddStage`, since a failed/stalled stage-chat ticket already exists but never got its reply; re-running `advanceSddStage` for the same still-current `ticket.sddStage` re-enters `_createStageChat`/`_runStageChatTurn` and will reuse-or-create as appropriate — no special-cased retry method needed, unlike `retryCodingExecution`, since there's no worktree/verify-gate state to resume).

### 1.7 `TicketsErrorReason` — new value

```dart
/// A spawned SDD-stage chat's turn (see `TicketsCubit._runStageChatTurn`)

sddStageAdvanceFailed,
```

Emitted from `_runStageChatTurn`'s catch block alongside the system comment (§1.3), the same "comment for the transcript + one-shot toast" pairing `executionVerificationFailed` already uses.

## 3. Widget layer

### 3.1 `TicketBoardCard`/`_CardVisual` (`tickets_board_view.dart`)

`_CardVisual` is a plain `StatelessWidget` today with zero `TicketsCubit` subscription. Add a small selector, evaluated per-card, reading only primitive derived values off `TicketsLoaded` (never the raw `Set`/`Map` fields themselves) so `context.select`'s value-equality check stays meaningful and each card only rebuilds when *its own* ticket's status changes, not on every in-flight-state emission board-wide:

```dart
final _CardExecutionState execState = context.select(
  (TicketsCubit cubit) => _cardExecutionState(cubit.state, ticket),
);
```

```dart
/// Compact per-card status derived from `TicketsLoaded`'s in-flight
/// fields (see design.md §1.4) for `ticket` specifically. `none` when
/// `cubitState` isn't `TicketsLoaded` (e.g. a detail screen is the last
/// thing that ran) or nothing about `ticket` is in flight.
enum _CardExecutionState { none, running, queued, advancing }

(_CardExecutionState, int?) _cardExecutionState(TicketsState s, Ticket t) {
  if (s is! TicketsLoaded) return (_CardExecutionState.none, null);
  if (s.inFlightExecutionIds.contains(t.id)) {
    return (_CardExecutionState.running, null);
  }
  final queuePos = s.executionQueuePositions[t.id];
  if (queuePos != null) return (_CardExecutionState.queued, queuePos);
  if (s.inFlightAdvanceIds.contains(t.id)) {
    return (_CardExecutionState.advancing, null);
  }
  return (_CardExecutionState.none, null);
}
```

(`context.select` needs the selected value itself to have proper `==`; a record `(_CardExecutionState, int?)` does, since both components are enum/primitive.)

Rendered as a small leading badge in `_CardVisual`'s existing `Row` (the one currently holding `TypeChip`/`PriorityBadge`, `tickets_board_view.dart:415-423`) — a filled pill: rotating-gear glyph + "Running" (`running`), stack glyph + "Queued #N" (`queued`), pencil glyph + "Advancing" (`advancing`, Epic/Story only — `running`/`queued` are Task/Bug only, `advancing` is Epic/Story only, so exactly one of the two ever applies to a given card's type). `none` renders nothing — the row looks exactly as it does today. Exact glyph choice, color treatment, and pill shape are a `/design-brief` question (design gate above), not decided here; this section fixes the *data flow and states*, not the visual spec.

### 3.3 `ticket_detail_screen.dart` — Advance handlers and chat-waiting indicator

`_maybeAutoAdvanceSddStage` (lines 143-154) and `_advanceSddStage` (lines 161-166) are **unchanged in shape** — both already call `context.read<TicketsCubit>().advanceSddStage(ticket)` and either fire-and-forget (`auto`) or `await` it before navigating (explicit gated/manual). Per §1.2, the returned `Future<String?>` now resolves after chat-ticket creation instead of the full AI turn, so the explicit-click path lands the human on the new chat ticket sooner, with its reply still streaming in server-side.

New: the chat-ticket rendering branch (`ticket.type == TicketType.chat`, around line 477) needs a "Waiting for reply…" indicator for the case where `TicketDetailLoaded.isAdvancingStage` is `true` for *this* chat ticket (per §1.5/§2, a chat ticket's own `isAdvancingStage` means it's the live target of `_runStageChatTurn`). Placed where the comment list would show the AI's reply once it lands — a pulsing-dot + text row, reusing `_ExecutionLiveToolLine`'s existing pulsing-dot animation treatment (`ticket_metadata_section.dart`) rather than inventing a new one, with fixed text ("Waiting for reply…") since there's no `executionLiveActivity`-equivalent live tool-use string for a stage chat. Disappears (comment list shows the real reply instead) once `isAdvancingStage` flips `false` for this ticket and the screen's own `ChatCubit` re-loads messages — wire a `BlocListener<TicketsCubit, TicketsState>` case that calls `context.read<ChatCubit>().loadMessages(ticket.id)` when `TicketDetailLoaded.isAdvancingStage` transitions `true` → `false` for the currently-viewed chat ticket, since the screen's own `ChatCubit` instance never initiated this particular turn (`_runStageChatTurn` calls the static `ChatCubit.runChatTurn` helper directly from `TicketsCubit`, not through this screen's `ChatCubit`) and so has no other way to learn the reply landed.

## 4. Notification relocation — `WorkspaceNavShell` (`core/routing/workspace_nav_shell.dart`)

Confirmed (`app_router.dart:92-233`) that `WorkspaceShell`'s single `ShellRoute` wraps every `/workspace/*` route including `/workspace/settings` and `/workspace/settings/overrides*`, and that `BlocProvider<TicketsCubit>` sits *above* `WorkspaceNavShell` in the tree (`app_router.dart:493-529`) — so `TicketsCubit` is reachable from `WorkspaceNavShell.build` via `context.read`/`BlocListener` without any new provider wiring.

Wrap `WorkspaceNavShell.build`'s returned `LayoutBuilder` in a `BlocListener<TicketsCubit, TicketsState>`:

```dart
return BlocListener<TicketsCubit, TicketsState>(
  listenWhen: (previous, current) => current is TicketsError,
  listener: (context, state) {
    final reason = (state as TicketsError).reason;
    if (reason == null) return; // raw, unclassified errors stay screen-local
```

One exhaustive `switch`-backed `ticketsErrorMessage` (already exists, `tickets_board_view.dart:53-67`) now covers all seven `TicketsErrorReason` values uniformly (six existing + `sddStageAdvanceFailed`), fixing the `executionVerificationFailed` gap as a side effect of consolidation. `notFound`/`sddStagePreconditionNotMet`/`invalidParent` staying screen-local behavior (e.g. `notFound` navigating back, or a form re-enabling its submit button) is unaffected — this listener only ever calls `AppToast.show`, nothing state-mutating, so it composes safely alongside each screen's own existing `BlocListener` (both fire independently on the same `emit`).

**Removed**: the three `TicketsErrorReason`-branches in `ticket_detail_screen.dart:245-259`'s `BlocListener` (its `TicketTrashed`/`TicketDetailLoaded` branches stay — those are navigation/local-state concerns, not toasts). **Removed**: `create_ticket_screen.dart:153-164`'s `state is TicketsError` toast branch — its `TicketCreated` navigation stays; a raw unclassified `TicketsError` (the `reason == null` case, e.g. a generic repository-write failure) still needs *some* screen-local toast, so `create_ticket_screen.dart` keeps a narrowed listener for `reason == null` only, complementing (not duplicating) the shell-level classified-reason listener.

## 5. Explicitly unchanged

- `AutomationContext` (`sddStage | codingExecution | codingExecutionRetry`) and `AutomationSettingsRepository` — no new enum value, no new persisted setting. `advanceSddStage`'s trigger semantics (whether/when a stage advances) are governed entirely by the existing `AutomationConfidence` read at the `ticket_detail_screen.dart` widget layer, exactly as today — this change only touches *how* the resulting chat turn executes (backgrounded) and *what becomes visible* while it runs.
- `_runCodingExecution`/`_triggerOrQueueCodingExecution`'s own control flow — only gains `_refreshInFlightBoardState()` calls at existing state-mutation points, no behavioral change to the run itself.
- `TicketRepository`/DAO/drift schema — no new persisted column anywhere in this change.

# Aion — Board Execution/Advance Indicators & Stage-Chat Waiting State: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md), the [Task-to-Coding-Execution Trigger Spec](./Aion%20Task%20Execution%20Trigger%20Spec.md), and the [Coding-Execution Reliability Spec](./Aion%20Coding%20Execution%20Reliability%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TicketBoardCard`, `TicketDetailScreen`, `TypeChip`, `CommentTile`, `CodingRunState`, `AutomationConfidence`, `SddStage`, and the existing `_ExecutionRunningHint`, `_ExecutionActionBanner`, `_ExecutionLiveToolLine`, the SDD-stage section (§2 of SDD Ticket Execution), and the chat streaming pulsing-dot line (§2.3a of Chat Transcript) — by name.

This change makes two kinds of already-running background work **visible on the surfaces where a human first looks** — the Kanban board and a ticket's detail screen — without introducing new screens or touching ticket data modeling. It is purely live, in-memory status becoming visible.

Two work families are surfaced:

1. **A Task/Bug coding-execution run** — already has a full-detail section on the Task's own screen (Coding-Execution Reliability spec §0). This pass adds a **compact Board-card badge** for its `running` / `queued` states (§1), so a run is visible from the board without opening the ticket.
2. **An Epic/Story SDD-stage-advance** — a spawned AI stage-chat turn that used to block the UI and is now backgrounded. This pass adds a **Board-card badge** (`advancing`, §1), a **detail-screen hint** (`StageAdvancingHint`, §2) that occupies the SDD-stage section's action slot while the advance is in flight, a **failure/retry banner** (`StageAdvanceFailureBanner`, §3) in the same slot, and a **chat-thread waiting indicator** (`WaitingForReplyIndicator`, §4) for the moment a human opens the freshly-spawned stage chat before its first reply arrives.

It **adds no new screens**. It extends three existing surfaces:

- **`TicketBoardCard`** (Kanban board, every ticket type) — a new non-interactive `BoardCardStatusBadge` (§1) in the card's meta-chip row, beside the existing `TypeChip`.
- **`TicketDetailScreen`** (epic/story tickets) — the SDD-stage section (SDD Ticket Execution spec §2). Its action slot (the `§2.2`–`§2.4` hint/Advance-button area, below the current-stage line) now resolves one additional pair of states: **`StageAdvancingHint`** (§2) while an advance is running, and **`StageAdvanceFailureBanner`** (§3) when the last advance failed.
- **`TicketDetailScreen`** (chat tickets) — a **`WaitingForReplyIndicator`** (§4) row at the tail of the comment thread, shown while a freshly-spawned stage chat has no reply yet.

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (non-Material) / `Padding` / `Row` / `Column` / `GestureDetector` / `MouseRegion` / `AnimatedScale` / `AnimatedOpacity` / `RotationTransition` / `SingleChildScrollView` / `CustomPaint`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `LinearProgressIndicator`, `InkWell`, `DropdownButton`, `Chip`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token or documented derivation that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` / `token.withValues(alpha: x)`, never a hardcoded ARGB. The default tinted-chip fill alpha is `fillAlphaArctic = 0.11` / `fillAlphaObsidian = 0.16`, exposed at the call site as `ThemeScope.of(context).fillAlpha`.

**New tokens: none.** No new `AionColors`, `AionText`, or `AionRadius` member is required. The badge label reuses `AionText.chip` with `letterSpacing` relaxed and **no** uppercase transform (§1.2). Every color is an existing token or an existing derivation: `pendingTint(isDark)` / `pendingIconTint(isDark)` (running/advancing badge), `secondary.withOpacity(fillAlpha)` (queued badge), `dangerTint(isDark)` / `dangerBorderTint(isDark)` (failure banner — added in Coding-Execution Reliability spec §4), and the Retry-button `secondary` fill + `Color.lerp` hover shade (Coding-Execution Reliability spec §1.5–§1.6, reused verbatim). One structural addition: two nullable, in-memory status enums (§5) that carry no persisted data.

**Action-slot state resolution (Epic/Story SDD-stage section).** The section container, eyebrow (`"SDD STAGE"`), 4-step tracker, and current-stage line are **unchanged** from SDD Ticket Execution §2.1. Only the action slot below the current-stage line gains two states:

| Stage-advance status | Action slot renders |
|---|---|
| idle, precondition unmet | §2.2 Not-ready hint (unchanged) |
| idle, ready, `confidence == gated` | §2.3 gated banner (unchanged) |
| idle, ready, `confidence == manual` | §2.4 manual Advance button (unchanged) |
| **`advancing`** (a stage-advance chat is running) | **`StageAdvancingHint` (§2)** — replaces whatever button/hint would otherwise show |
| **`advanceFailed`** (the last advance attempt failed) | **`StageAdvanceFailureBanner` (§3)** |

When `advancing`, no Advance button is offered regardless of `confidence` (a run is already in flight). When `advanceFailed` under `confidence == auto`, a retry is spawned silently and the slot shows `StageAdvancingHint` again, not the banner (mirrors Coding-Execution Reliability §1.6).

## 1. `BoardCardStatusBadge`

A small, **non-interactive** filled pill added to `TicketBoardCard`, showing exactly one of four states. `none` renders nothing (`SizedBox.shrink()` / omitted from the row); the other three are specified below. Exactly one state applies per card: Task/Bug cards resolve to `running`/`queued`/`none`; Epic/Story cards resolve to `advancing`/`none`; the two families never co-occur on one card.

```dart
enum BoardCardStatus { none, running, queued, advancing }

class BoardCardStatusBadge extends StatelessWidget {
  final BoardCardStatus status;
  final int? queuePosition; // required iff status == queued; renders as "Queued #N"
  // non-interactive: no onTap, no MouseRegion cursor change
}
```

### 1.1 Container — shared geometry (all three visible states)

- `DecoratedBox` → `Padding` → `Row` (`mainAxisSize: min`, `crossAxisAlignment: center`, `gap: 4`).
- **Padding:** `EdgeInsets.symmetric(horizontal: 7, vertical: 3)` → visual height ≈ `19px`, sitting flush with the `TypeChip` on the same row.
- **Radius:** `AionRadius.pill` (22) → a stadium pill (height-clamped). Matches the `TypeChip`'s pill-family radius so the two read as one chip family.
- **Border:** none on `running` / `advancing`; `1px solid secondary.withOpacity(isDark ? 0.24 : 0.18)` on `queued` (a hairline that keeps the neutral pill legible on `surface`). See per-state table.
- **Shadow:** none.
- **Placement in card:** appended to the meta-chip `Row` (the row that already holds the `TypeChip` + optional priority chip). Insert an `Expanded`/spacer before it so it right-aligns to the card's trailing edge; the badge is `mainAxisSize: min` and never grows. It sits on the meta row (not the title row), so it cannot crowd a two-line title.

### 1.2 Label text style

Reuse `AionText.chip` (Manrope 10.5 / w700) **but do not uppercase the string** and relax tracking:

```dart
// Not a new named style — a documented copyWith at the call site.
AionText.chip.copyWith(letterSpacing: 0.2, height: 1.0) // rendered mixed-case: "Running", "Queued #2", "Advancing"
```

`TextOverflow` is irrelevant — labels are fixed and short; the pill sizes to content.

### 1.3 Per-state specification

| | `running` | `queued` | `advancing` |
|---|---|---|---|
| **Applies to** | Task / Bug | Task / Bug | Epic / Story |
| **Leading glyph** | `gear` (`cog` / `gear-six` fallback) | `stack` (three stacked bars — `stack` / `list` fallback) | `pencil` (`pencil-simple` / `pen` fallback) |
| **Glyph size** | `11px` | `11px` | `11px` |
| **Glyph motion** | slow `RotationTransition`, 2400ms linear, `repeat()` — the "spinner". Static under reduced motion (§1.5). | none | none |
| **Fill** | `pendingTint(isDark)` = `primary.withValues(alpha: isDark ? 0.18 : 0.12)` | `secondary.withOpacity(fillAlpha)` (`0.11 / 0.16`) | `pendingTint(isDark)` (same as running) |
| **Border** | none | `1px solid secondary.withOpacity(isDark ? 0.24 : 0.18)` | none |
| **Glyph + label color** | `primary` (`#2E86D4 / #9366FF`) | `secondary` (`#5E7183 / #57608A`) | `primary` (`#2E86D4 / #9366FF`) |
| **Label** | `"Running"` | `"Queued #N"` (`queuePosition`) | `"Advancing"` |

**Color-family decision.** Active work (`running`, `advancing`) shares the **primary/`pendingTint`** family — the app's existing "active but calm" fill (SDD/sync-pending states) — and is distinguished only by glyph (spinning gear vs. static pencil), never by color, because the two never appear on the same card type and a shared active color reads as one consistent "this card is working" signal across the board. Waiting work (`queued`) is the **neutral `secondary`** family with a hairline border — visibly quieter than active, signalling "nothing is happening yet." No `typeTask`/`typeStory`/`typeEpic`/`typeBug` accent is used for the badge; keeping the badge off the type-accent palette prevents it from being confused with the `TypeChip` beside it.

### 1.4 Dimensions recap

- Height ≈ `19px` (from `vertical: 3` padding + 11px glyph / 10.5px cap). Width sizes to content.
- Inner gap glyph→label: `4`. Padding `EdgeInsets.symmetric(horizontal: 7, vertical: 3)`. Radius `AionRadius.pill` (22). Glyph `11px`. Icon color = label color (per state, §1.3).

### 1.5 States

**Non-interactive** — no hover / focused / pressed / disabled / error states. The only motion is the `running` gear rotation (2400ms). Under `MediaQuery.disableAnimations` (reduced motion) the gear renders static at full opacity and the controller is not started. The badge updates reactively as the card's live status changes (plain rebuild, no entrance/exit animation).

## 2. `StageAdvancingHint`

The Epic/Story detail-screen hint shown in the SDD-stage section's action slot (§0) while a stage-advance chat is running. Reads as a **sibling of `_ExecutionRunningHint`** (Task Trigger spec §1 — the rotating-gear informational row), scoped to a stage-advance context: same family, **no** live tool-use sub-line (a stage chat has no tool access, unlike a coding run — Coding-Execution Reliability §2 does not apply here).

### 2.1 Layout

- Informational row — **no** background, border, or padding box; sits directly in the section flow, `gap: 12` below the current-stage line (the same offset the §2.4 manual Advance button uses).
- `Row`, `gap: 8`, `crossAxisAlignment: center`.
- **Leading glyph:** `gear` (`cog` / `gear-six` fallback), `15px`, color `primary` (`#2E86D4 / #9366FF`), wrapped in a continuous `RotationTransition`, **2400ms** linear, `repeat()` — identical to `_ExecutionRunningHint`'s gear. Static under reduced motion.
- **Text:** `Expanded(Text(…))`, `AionText.bodySm` (13.5 / w400), color `textSecondary` (`#46586A / #A2AEC6`), `maxLines: 2`, `softWrap: true`.
  - Copy: `"Advancing to Verifying — running the stage chat."` — `"Verifying"` is the **target** (next) stage's present name (stage → present name map, SDD Ticket Execution §2.1: `explore→"Exploring"`, `propose→"Proposed"`, `verify→"Verifying"`, `archive→"Archived"`). Emphasize the target stage name in `textPrimary` (`#142230 / #E7EDF7`) via a `TextSpan`, matching the version-pair emphasis pattern used elsewhere.

### 2.2 States

Purely informational; **no** hover / focused / pressed / disabled / error states. The only motion is the gear rotation (§2.1). Default is the only visual state. The hint is not dismissible — it clears itself when the advance resolves (to the advanced tracker + §2.5 auto-note on success, or to `StageAdvanceFailureBanner` §3 on failure).

## 3. `StageAdvanceFailureBanner`

The Epic/Story failure banner shown in the same action slot when the last stage-advance attempt failed. Reads as a **sibling of `_ExecutionActionBanner` failure tone** (Coding-Execution Reliability §1): `danger`-toned tinted container, warning glyph + short title, a fixed-height scrollable mono well for the reason text, and a full-width `secondary` Retry button — same family, adapted copy.

```dart
class StageAdvanceFailureBanner extends StatelessWidget {
  final String targetStageName;   // e.g. "Verifying" — the stage the failed advance was heading to
  final String reasonDetail;      // raw reason text for the scroll well (§3.3)
  final VoidCallback? onRetry;     // null → disabled (§3.4), retry already spawning
}
```

### 3.1 Container

- `DecoratedBox` → `Padding` → `Column` (`crossAxisAlignment: stretch`, `gap: 11`) — three children: (1) header `Row` (§3.2), (2) reason well (§3.3), (3) Retry button (§3.4).
- **Radius:** `AionRadius.lg` (12), both themes.
- **Padding:** `EdgeInsets.fromLTRB(14, 13, 14, 14)`.
- **Fill:** `dangerTint(isDark)` = `danger.withValues(alpha: isDark ? 0.16 : 0.11)` (`#CE3D54 / #F1546C` base). (Reuses the helper added in Coding-Execution Reliability §4.)
- **Border:** `1px solid dangerBorderTint(isDark)` = `danger.withValues(alpha: isDark ? 0.42 : 0.28)`.
- **Shadow:** none.
- **Placement:** the action slot, `gap: 12` below the current-stage line (same offset as §2.1).

### 3.2 Header row

- `Row`, `gap: 12`, `crossAxisAlignment: start` (title may wrap to 2 lines above a sub-line, so the glyph pins to the top).
- **Leading glyph:** `warning` (`warning-triangle` / `warning-circle` fallback), `17px`, color `danger` (`#CE3D54 / #F1546C`).
- **Text column** (`Expanded`, `Column`, `crossAxisAlignment: start`, `gap: 2`):
  - **Title:** `"Stage advance failed"`, `AionText.cardTitle` (14 / w600), color `textPrimary` (`#142230 / #E7EDF7`).
  - **Sub-line:** `"Propose → Verify · attempt 2"` (short one-line summary; the full reason goes in the well), `AionText.time` (mono 11 / w400), color `textSecondary` (`#46586A / #A2AEC6`).

### 3.3 Reason well — fixed-height scrollable mono well

Identical geometry/behavior to the Coding-Execution Reliability §1.4 error well, so a one-line reason and a long dump occupy the same banner height.

- **Container:** `DecoratedBox` → `ConstrainedBox(maxHeight: 96)` → `SingleChildScrollView(primary: false, physics: ClampingScrollPhysics())` → `Padding` → `Text`.
- **Fill:** `background` (`#EDF2F8 / #0A0E18`) — one step off `surface`, a recessed well against the `danger`-tinted banner. **Not** a `danger` tint (the reason must stay legible).
- **Border:** `1px solid border` (`#D6E0EA / #232C40`).
- **Radius:** `8` (nested-well radius, explicit — as §1.4).
- **Padding:** `EdgeInsets.fromLTRB(11, 10, 11, 10)`.
- **Max height:** `96` (≈ 5 mono lines). Taller content scrolls inside the well; the banner does not grow. Shorter content sizes to fit.
- **Text:** the raw reason, `AionText.time` re-sized to **11.5 / w400** mono (JetBrains Mono, via `AionText.time.copyWith(fontSize: 11.5, height: 1.55)`), color `textSecondary`, `softWrap: true`, `overflow: TextOverflow.clip`.
- **Scroll indicator:** no Material `Scrollbar`. A `RawScrollbar` (widgets layer) is permitted (`thickness: 4`, `radius: Radius.circular(2)`, `thumbColor: textMuted.withOpacity(0.4)`) if a persistent thumb is desired.
- **Bottom fade:** an `IgnorePointer` overlay `Container` pinned to the well's bottom edge, `height: 20`, `decoration: BoxDecoration(gradient: LinearGradient(begin: topCenter, end: bottomCenter, colors: [background.withOpacity(0), background]))`, clipped to the well's bottom radius; above the scroll content, below the well border. Static bottom fade acceptable; scroll-position-aware hide at `maxScrollExtent` is a nice-to-have (not required).

### 3.4 Retry button — full-width, solid `secondary`

Same button geometry as the Coding-Execution Reliability §1.5 Retry button (which is itself the Task Trigger §3.4 button geometry). Full container width (`crossAxisAlignment: stretch` parent), content centered.

- `GestureDetector` → `MouseRegion` → `AnimatedScale` → `DecoratedBox` → `Padding` → centered `Row` (glyph + label, `MainAxisAlignment.center`).
- **Padding:** `EdgeInsets.symmetric(horizontal: 15, vertical: 10)`.
- **Radius:** `AionRadius.md` (10).
- **Fill:** `secondary` (`#5E7183 / #57608A`).
- **Leading glyph** (`gap: 7` before label): `arrow-clockwise` / `arrows-counter-clockwise`, `15px`, `#FFFFFF`.
- **Label:** `"Retry advance"`, `AionText.button` (14 / w700), color `#FFFFFF`, `TextAlign.center`.
- **Glow (default):** `secondary.withOpacity(isDark ? 0.55 : 0.40)`, blur 18, spread −9, offset (0, 8).

**Why `secondary`, not `danger` or `primary`:** identical rationale to Coding-Execution Reliability §1.5 — Retry is a calm, non-destructive recovery action at the same solid weight as the app's other confirm buttons. `danger` would read as "destroy"; `primary` is the app's "Advance the SDD stage" CTA (wrong meaning, and over-weights a recovery). The `danger` identity of the situation is carried entirely by the banner frame + warning glyph + reason text.

### 3.5 Button states — both themes

`{fill}` = `secondary`; `{glow}` = §3.4 glow.

| State | Fill | Glow | Extra |
|---|---|---|---|
| **Default** | `secondary` | tone glow, blur 18, spread −9, offset (0,8) | — |
| **Hover** | `Color.lerp(secondary, isDark ? const Color(0xFFFFFFFF) : const Color(0xFF000000), 0.10)` (derived shade — no new token; `Color(0xFFFFFFFF)`/`Color(0xFF000000)` per `AionColorsHubTokens.warningText`'s existing precedent, not `Colors.white`/`Colors.black` — `Colors` is a `package:flutter/material.dart` symbol) | glow blur → 22 | `MouseRegion` click cursor |
| **Focused** (keyboard) | `secondary` | default glow | 3px focus ring `BoxShadow(color: secondary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` |
| **Pressed** | `secondary` | glow suppressed (blur → 0) | `AnimatedScale` → `0.98` over 80ms on `onTapDown` |
| **Disabled** (`onRetry == null` — a retry is already spawning) | `secondary` @ `0.45` opacity | none | `IgnorePointer`; label + glyph `#FFFFFF` @ `0.55` |
| **Error** | n/a | — | a failed retry re-enters this same banner in its Default state (reason text updated); surfaced via the existing app toast, out of scope |

No `×` dismiss (mirrors §1.6 of Coding-Execution Reliability): a failed advance is a non-dismissible outcome — the only forward move is Retry or an automation-driven transition.

## 4. `WaitingForReplyIndicator`

The chat-thread row shown at the tail of a chat ticket's comment list when a human has opened a freshly-spawned stage chat before its first AI reply has arrived. Matches the existing live-activity **pulsing-dot** treatment used for the streaming reply's pre-text line (Chat Transcript spec §2.3a) — reused verbatim so "something is happening in the background" reads identically everywhere.

### 4.1 Layout

- Left-aligned row at the tail of the comment thread, where the next AI reply bubble would render. Precede it with the thread's normal inter-comment `gap` (SDD Ticket Execution §3/§4 spacing); no bubble frame, no avatar, no author label — it is a bare activity line, not a `CommentTile`.
- Small leading inset only: `Padding(EdgeInsets.only(left: 2))` to align the dot with the thread's content edge.
- `Row`, `gap: 8`, `crossAxisAlignment: center`.
- **Pulsing dot:** a `7×7` filled circle, `BoxShape.circle`, color `primary` (`#2E86D4 / #9366FF`), `AnimatedOpacity`/`AnimatedScale` loop `0.35 → 1.0 → 0.35` opacity **and** scale `0.8 → 1.0` over `1100ms` ease-in-out, `repeat(reverse: true)` — the exact `ctPulseDot` treatment from Chat Transcript §2.3a.
- **Text:** `"Waiting for reply…"`, `AionText.streamStatus` (JetBrains Mono 12.5 / w400), color `textSecondary` (`#46586A / #A2AEC6`). Fixed string; no `{tool}` emphasis.

### 4.2 States

Purely informational; **no** hover / focused / pressed / disabled / error states. The only motion is the dot pulse. **Reduced-motion fallback** (`MediaQuery.disableAnimations`): the dot renders **static at full opacity** (1.0), no controller started — the row still reads as a distinct "waiting" affordance via the dot + text. The row is removed (plain rebuild, no exit animation) the instant the first reply token arrives and the streaming bubble (Chat Transcript §2.3) takes its place.

## 5. New / changed enums (no new design tokens)

```dart
// §1 — Board-card badge. Live, in-memory; not persisted on the ticket.
enum BoardCardStatus { none, running, queued, advancing }
// running/queued resolve from the Task/Bug CodingRunState; advancing from the Epic/Story
// stage-advance status below. Card type gates which family can appear (§0).

// §0/§2/§3 — Epic/Story stage-advance status. Live, in-memory; drives the SDD-stage
// section's action slot and the 'advancing' board badge.
enum StageAdvanceStatus { idle, advancing, advanceFailed }
```

Both are transient runtime status derived from existing in-flight state — **no ticket-data-model change, no persistence, no new stored field.** `CodingRunState` (Coding-Execution Reliability §5), `AutomationConfidence`, and `SddStage` (SDD Ticket Execution §7) are reused unchanged.

**No new `AionColors`, `AionText`, or `AionRadius` members.** Every color is an existing token or documented derivation: badge fills `pendingTint(isDark)` / `secondary.withOpacity(fillAlpha)`; banner `dangerTint(isDark)` / `dangerBorderTint(isDark)` (Coding-Execution Reliability §4); Retry `secondary` + `Color.lerp(…, white/black, 0.10)` hover; well fill `background`; pulse/rotation via animation opacity, not color. Every text style is an existing `AionText.*` (two documented `copyWith`s: `chip` mixed-case for the badge label §1.2, `time` re-sized to 11.5 mono for the reason well §3.3). Every radius is `AionRadius.pill` / `lg` / `md` / `8` / `BoxShape.circle`.
