# Design: Ticket CRUD Tool Calls

## 1. Overview

Extends the existing `AgentRequest.tools`/`onToolCall` mechanism
(`core/contracts/agent_tool_definition.dart`,
`core/contracts/agent_model_client.dart`) — already proven by
`branch_ticket`/`close_branch` — with three more `AgentToolDefinition`s,
dispatched through the same `TicketsCubit` pattern:
`_toolsFor`/`_toolCallParamsFor`/`_onToolCallFor`. No new plumbing between
`AgentProvider` and the chat-turn call sites; only new tool definitions,
new dispatch cases, and new handlers.

## 2. New tool definitions

New file `lib/features/tickets/presentation/cubit/ticket_crud_tool_definitions.dart`,
mirroring `chat_branch_tool_definitions.dart`'s shape exactly (module
header, one `const AgentToolDefinition` per tool, full dartdoc on each
naming its handler).

```dart
const createTicketToolDefinition = AgentToolDefinition(
  name: 'create_ticket',
  description:
      'Create a new top-level ticket for follow-up work discovered '
      'mid-conversation — e.g. an unrelated bug spotted while working on '
      'something else, or a new task worth tracking separately. The new '
      'ticket has no parent; call add_link afterward to relate it to the '
      'ticket you\'re currently working on, if relevant.',
  inputSchema: {
    'type': 'object',
    'properties': {
      'title': {'type': 'string', 'description': 'A short, clear title.'},
      'type': {
        'type': 'string',
        'enum': ['story', 'task', 'bug'],
        'description': 'The kind of ticket to create.',
      },
      'description': {
        'type': 'string',
        'description': 'Optional 1-3 sentence description.',
      },
    },
    'required': ['title', 'type'],
  },
);

const addLinkToolDefinition = AgentToolDefinition(
  name: 'add_link',
  description:
      'Relate the ticket you\'re currently working on to another ticket by '
      'its ticket id (e.g. "TASK-42") — mark it as blocking, blocked by, '
      'related to, or a duplicate of the target.',
  inputSchema: {
    'type': 'object',
    'properties': {
      'targetTicketId': {
        'type': 'string',
        'description': 'The other ticket\'s human-readable id, e.g. "TASK-42".',
      },
      'linkType': {
        'type': 'string',
        'enum': ['blocks', 'blockedBy', 'relatesTo', 'duplicates'],
        'description': 'How the current ticket relates to the target.',
      },
    },
    'required': ['targetTicketId', 'linkType'],
  },
);

const logTimeToolDefinition = AgentToolDefinition(
  name: 'log_time',
  description:
      'Log time spent (in minutes) against the ticket you\'re currently '
      'working on.',
  inputSchema: {
    'type': 'object',
    'properties': {
      'minutes': {
        'type': 'integer',
        'minimum': 1,
        'description': 'Minutes to add to the ticket\'s time spent.',
      },
    },
    'required': ['minutes'],
  },
);
```

`linkType`'s enum deliberately omits `duplicatedBy` — same reasoning
`TicketLinkPicker.linkTypeOptions` already applies to its own creation
picker (per that field's existing dartdoc: `duplicatedBy` is never offered
as a raw creation choice, only ever read as a relative view of a stored
`duplicates` row). The model always expresses "the other ticket duplicates
mine" the same way a human picker would: `duplicates` from its own
perspective, or by naming the correct source/target — never `duplicatedBy`
directly.

## 3. `TicketsCubit` changes

### 3.1 `_toolsFor` — combined list, not exactly-one

Current behavior (`_toolsFor`, tickets_cubit.dart:4872) returns exactly one
of `branch_ticket`/`close_branch`. New behavior: the branch/close-branch
choice stays exactly as-is (still mutually exclusive on its own), but the
three new tools are *appended unconditionally* — every chat this method is
called for offers `create_ticket`, `add_link`, and `log_time` regardless of
branch depth or position:

```dart
Future<List<AgentToolDefinition>> _toolsFor(String chatTicketId) async {
  final chat = await _repository.getTicketById(chatTicketId);
  final parentId = chat?.parentId;
  final branchTool = parentId == null
      ? branchTicketToolDefinition
      : (await _repository.getTicketById(parentId))?.type == TicketType.chat
      ? closeBranchToolDefinition
      : branchTicketToolDefinition;
  return [
    branchTool,
    createTicketToolDefinition,
    addLinkToolDefinition,
    logTimeToolDefinition,
  ];
}
```

### 3.2 `_onToolCallFor` — real dispatch, not a binary ternary

Current behavior dispatches by `toolName == closeBranchToolDefinition.name
? close : branch` — anything not `close_branch` falls through to the
branch handler. That's only safe while exactly two tools exist. Replaced
with a name-keyed `switch`:

```dart
Future<Map<String, dynamic>> Function(
  String toolCallId,
  String toolName,
  Map<String, dynamic> arguments,
)
_onToolCallFor(Ticket chat) {
  return (toolCallId, toolName, arguments) => switch (toolName) {
    closeBranchToolDefinition.name => _handleCloseBranchToolCall(chat, arguments),
    createTicketToolDefinition.name => _handleCreateTicketToolCall(chat, arguments),
    addLinkToolDefinition.name => _handleAddLinkToolCall(chat, arguments),
    logTimeToolDefinition.name => _handleLogTimeToolCall(chat, arguments),
    _ => _handleBranchToolCall(chat, arguments),
  };
}
```

(`_` falling through to the branch handler preserves today's exact
behavior for `branch_ticket` itself — it's still the unnamed default,
just now alongside three other named cases instead of one.)

### 3.3 New handlers

All three resolve "the ticket being worked" the same way `_canBranch`
already does — `chat.parentId` — since a chat ticket is always attached to
the ticket it discusses. Each returns the same `{'accepted': bool,
'reason'?: string, ...}` shape `_handleBranchToolCall` already returns, so
the model gets a real result back.

```dart
Future<Map<String, dynamic>> _handleCreateTicketToolCall(
  Ticket chat,
  Map<String, dynamic> arguments,
) async {
  final title = arguments['title'] as String?;
  final typeArg = arguments['type'] as String?;
  final type = TicketType.values.where((t) => t.name == typeArg).firstOrNull;
  if (title == null || title.isEmpty) {
    return {'accepted': false, 'reason': 'Missing title.'};
  }
  if (type == null || !{TicketType.story, TicketType.task, TicketType.bug}.contains(type)) {
    return {'accepted': false, 'reason': 'type must be story, task, or bug.'};
  }
  final description = arguments['description'] as String?;

  final automationRepo = _automationSettingsRepository;
  final confidence = automationRepo == null
      ? AutomationConfidence.gated
      : await automationRepo.getConfidence(AutomationContext.ticketCreation);

  Future<Map<String, dynamic>> create() async {
    final now = DateTime.now();
    final ticket = Ticket(
      id: _uuid.v4(),
      ticketId: '',
      type: type,
      title: title,
      description: description,
      status: _defaultCreationStatus,
      parentId: null,
      createdAt: now,
      updatedAt: now,
    );
    await _repository.createTicket(ticket);
    return {'accepted': true, 'createdTicketId': ticket.id};
  }

  switch (confidence) {
    case AutomationConfidence.manual:
      return {'accepted': false, 'reason': 'Ticket creation is set to manual.'};
    case AutomationConfidence.auto:
      return create();
    case AutomationConfidence.gated:
      return _awaitProposalConfirmation(
        chat,
        PendingToolProposal.createTicket(
          title: title,
          type: type,
          description: description,
        ),
        onConfirm: create,
      );
  }
}
```

`_handleAddLinkToolCall` mirrors this shape: resolves `targetTicketId` via
the new `TicketRepository.getTicketByTicketId` (§4), declines with
`{'accepted': false, 'reason': 'No ticket found with id "...".'}` if not
found, parses `linkType` the same defensive way, resolves
`AutomationContext.ticketLinking`'s confidence, and on `auto`/confirmed
`gated` calls `TicketLinkRepository.createLink(sourceTicketId: chat.parentId!,
targetTicketId: target.id, linkType: linkType)`.

`_handleLogTimeToolCall` has no confidence branch at all — parses
`minutes` (declining non-positive/missing values the same defensive way),
and calls the new `TicketRepository.addTimeSpent(chat.parentId!, minutes)`
(§4) unconditionally.

## 4. Repository changes

Two additions to `TicketRepository` (domain interface), implemented in
`DriftTicketRepository`/`TicketDao`:

- **`Future<Ticket?> getTicketByTicketId(String ticketId)`** — equality
  lookup on the human-readable `ticketId` column (what the model actually
  sees in projected ticket files/context — never the internal uuid `id`).
  No such lookup exists anywhere in the codebase today; every existing
  caller resolves tickets by internal `id`.
- **`Future<void> addTimeSpent(String id, int minutesDelta)`** — an atomic
  `timeSpent = timeSpent + ?` SQL update at the DAO level, not a
  read-modify-write through `updateTicket`. `updateTicket` persists the
  *whole* `Ticket` object (title/description/priority/type/estimate/
  timeSpent/complexity) — a model-called `log_time` racing a human editing
  the same ticket in the UI would silently clobber whichever side lost the
  race. An atomic increment removes that race entirely; it's a narrower,
  purpose-built method rather than a new `updateTicket` code path.

## 5. `PendingToolProposal` additions

`create_ticket` and `add_link` both need a `gated`-tier confirmation
banner, so `PendingToolProposal` (currently `BranchProposal`/
`CloseBranchProposal`) gains two more variants, same shape:

```dart
const factory PendingToolProposal.createTicket({
  required String title,
  required TicketType type,
  String? description,
}) = CreateTicketProposal;

const factory PendingToolProposal.addLink({
  required String targetTicketId,
  required String targetTicketTitle,
  required TicketLinkType linkType,
}) = AddLinkProposal;
```

`targetTicketTitle` is resolved once by the handler before constructing the
proposal (from the `getTicketByTicketId` lookup already performed to
validate the call), so the banner never needs its own follow-up fetch —
mirrors how `BranchProposal.title` is already the AI-supplied string with
no extra lookup.

`confirmPendingToolProposal`/`rejectPendingToolProposal` need no changes —
both are already generic over `PendingToolProposal`'s stored `onConfirm`
callback and don't switch on which variant they're holding.

## 6. Widget tree changes — `_ToolProposalBanner`

`ticket_detail_screen.dart`'s `_ToolProposalBanner` currently switches on
`PendingToolProposal` to pick its icon/headline/body copy for
`BranchProposal`/`CloseBranchProposal`. Two more `case` arms, same
structure (existing `AionColors`/`AionText`/`AionRadius` tokens, existing
Confirm/Reject button row wired to `confirmPendingToolProposal`/
`rejectPendingToolProposal` — no new component):

- `CreateTicketProposal` → headline names the ticket type + title (e.g.
  "Create task: <title>"), body shows the description if present.
- `AddLinkProposal` → headline names the relationship (e.g. "Mark as
  duplicate of TASK-42: <targetTicketTitle>"), reusing
  `TicketLinkTypeDisplay.label`'s existing localized copy so the banner's
  relationship wording matches `LinkedTicketsSection`'s elsewhere in the
  app rather than inventing new phrasing.

## 7. `AutomationContext`/Settings additions

Two new `AutomationContext` enum values (`core/automation/automation_context.dart`),
each with full dartdoc naming its governed handler, mirroring
`chatBranching`'s existing doc shape:

```dart
/// Model-initiated ticket creation via the `create_ticket` tool call.
ticketCreation,

/// Model-initiated ticket linking via the `add_link` tool call
/// (including duplicate-flagging, expressed as `linkType: duplicates`).
ticketLinking,
```

`settings_screen.dart` gets two new `_AutomationSection` rows, inserted
after the existing `chatBranching` row and before `codingExecutionResume`
(automation-decision rows are otherwise unordered by dependency, so this
is purely "keep the two new ticket-CRUD rows adjacent to
`chatBranching`, the precedent they extend"), plus two new
`_confidenceSubLabel` switch arms following the exact existing per-context
shape (auto/gated/manual sub-labels each). New `app_en.arb` entries:
`settingsAutomationTicketCreationLabel`/`Description`, three
`...AutoSubLabel`/`GatedSubLabel`/`ManualSubLabel` for each of
`ticketCreation`/`ticketLinking` — eight new strings total, generated via
the project's normal `flutter gen-l10n` step rather than hand-edited into
the generated files.

## 8. Non-goals / explicitly deferred

- No change to `_awaitProposalConfirmation`/`_pendingProposals` — both are
  already generic over any `PendingToolProposal` variant and any chat id;
  reused as-is.
- No change to `AgentRequest`/`AgentModelClient`/either provider client —
  the tool-calling wire format is untouched; this change only adds more
  entries to the app-defined `tools` list already threaded through it.
- No retroactive backfill of `getTicketByTicketId` callers elsewhere in the
  codebase — it's a new method added for this change's own need, not a
  refactor of existing `getTicketById`-by-uuid call sites.

# Aion — Ticket CRUD Tool Calls (`create_ticket` / `add_link` / `log_time`): Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Chat Transcript UX Spec](./Aion%20Chat%20Transcript%20Spec.md), the [Mid-Task Chat Branching Spec](./Aion%20Chat%20Branching%20Spec.md) (which shipped the `_ToolProposalBanner` shell this feature extends), and the [Link Type & Blocked Badge Spec](./Aion%20Link%20Type%20and%20Blocked%20Badge%20Spec.md) (which shipped the `TicketLinkType` enum + relationship glyph set reused here). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AionColorsHubTokens`, `TicketDetailScreen`, `SettingsScreen`, `ChatTranscriptPane`, `ChatComposeField`, `_ToolProposalBanner`, `ToolProposalKind`, `_AutomationSection` / `_AutomationTrigger` / `_AutomationMenuRow`, `AutomationConfidence`, `TicketType`, `TicketLinkType`, and `TicketLinkTypeDisplay.glyph` by name. Mockups: [Aion Ticket CRUD Tool Calls Mockups](./Aion%20Ticket%20CRUD%20Tool%20Calls%20Mockups.dc.html).

**What's being built.** Three new app-defined AI tools act on the ticket graph from **any tool-enabled chat turn** (coding-execution, SDD-stage, design-sync — not only `chat`-type tickets):

- **`create_ticket`** — spins up a new top-level `story` / `task` / `bug`.
- **`add_link`** — relates the current ticket to another by id, using one of the four existing `TicketLinkType` relationships (`blocks` / `blockedBy` / `relatesTo` / `duplicates`).
- **`log_time`** — adds minutes of work to the current ticket. **Always applies silently — no UI, ever** (§0.2).

`create_ticket` and `add_link` can be set to `AutomationConfidence.gated`, in which case the model's proposed call pauses the turn behind a confirmation surface before it is applied. **That surface is the existing `_ToolProposalBanner`** (Chat Branching spec §1–§5) — this spec adds **two new content variants** inside that shell (`createTicket`, `addLink`) and nothing else visual. It also adds **two new `_AutomationSection` rows** to Settings that are **copy-only** (§6).

**No new screens, no new container, no redesign of the banner shell.** The banner's fill (`chatTint`), border (`chatBorderTint`), glow (`chatGlow`), 32×32 glyph tile + breathing halo, `dialogTitle` headline, paused status line, and the Confirm/Reject button pair with their full state set are all **inherited unchanged** from the Chat Branching spec. Every place this spec says "inherited" or "unchanged," implement against that spec's section, not a new definition.

**Hard constraint — no Material widgets or types anywhere.** Plain Flutter primitives only: `DecoratedBox` / non-Material `Container` / `Padding` / `Row` / `Column` / `Stack` / `GestureDetector` / `MouseRegion` / `AnimatedContainer` / `AnimatedOpacity` / `AnimatedScale` / `CustomPaint` / `SingleChildScrollView`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `ListTile`, `AppBar`, `SnackBar`, `CircularProgressIndicator`, `DropdownButton`, `InkWell`, `Chip`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` — never a hardcoded ARGB.

**New tokens:** **none** — no color, type, or radius member is added. One structural addition: two new members on the existing `ToolProposalKind` enum (§7). Two documented tint derivations reuse the existing `fillAlpha` pattern on the already-defined `typeTask` / `typeStory` / `typeBug` accents (§4). Settings (§6) introduces **no** new visual states.

## 0. Decisions up front

### 0.1 Identity — both new variants stay keyed to `typeChat`

The banner is the app's **tool-proposal** surface, keyed to `typeChat` (`#4C6FDE / #7C93FF`) because a tool proposal is a *chat*-originated action (Chat Branching spec §0). `create_ticket` and `add_link` are more of the same — model-proposed tool calls awaiting confirmation — so they reuse the **same identity**: fill `chatTint`, border `chatBorderTint`, glyph-tile fill `pressedAccentTint(typeChat)`, breathing halo + Confirm glow `chatGlow`, Confirm button solid `typeChat`.

The **ticket type accents** (`typeTask` / `typeStory` / `typeBug`) and the **relationship glyphs** (`TicketLinkTypeDisplay.glyph`) appear only **inside the content well** — as the small `TypeChip` on the create variant (§3.1) and the directional glyph on the link variant (§3.2). They label *what* the tool will do; they never re-color the banner frame, headline, or buttons. This keeps every tool-proposal banner reading as one consistent surface while the well carries the specifics.

### 0.2 `log_time` has **no visual surface** — confirmed

`log_time` **always applies silently** regardless of automation setting — it appends minutes to the current ticket's time log and never pauses a turn. It therefore has **no `_ToolProposalBanner` variant, no `ToolProposalKind` member, no Settings row, and no other UI in this spec.** Its effect surfaces only through already-shipped, out-of-scope chrome (the ticket's existing time-log readout / estimate rollup). Implementers should add **nothing** for `log_time`. This section is the deliberate record of that decision.

## 1. `_ToolProposalBanner` — two new content variants

The shell is unchanged (Chat Branching spec §2.1). `ToolProposalKind` gains two members (§7); the shell selects the well and header copy off `kind` exactly as it already does for `branch` / `close`.

- **`createTicket`** (`create_ticket` awaiting confirm) — proposes a new top-level ticket. Shows the ticket **type** (as a `TypeChip`) and **title** and an optional **description**.
- **`addLink`** (`add_link` awaiting confirm) — proposes relating the current ticket to another. Shows the **relationship** (name + directional glyph) and the **target ticket** (id + title).

```dart
class _ToolProposalBanner extends StatelessWidget {
  final ToolProposalKind kind;

  // createTicket
  final TicketType? newTicketType;   // task | story | bug
  final String? newTicketTitle;
  final String? newTicketDescription; // optional 1–3 sentence rationale/body

  // addLink
  final String? currentTicketKey;    // the chat's own ticket, e.g. "AIO-88"
  final TicketLinkType? linkType;    // blocks | blockedBy | relatesTo | duplicates
  final String? targetTicketKey;     // e.g. "AIO-42"
  final String? targetTicketTitle;

  final VoidCallback? onConfirm;     // null → Confirm disabled (request posting)
  final VoidCallback? onReject;      // null → Reject disabled
  // ...inherited branch/close fields omitted
}
```

Both variants share the inherited geometry, fill/border, glyph tile + breathing halo, paused status line, and Confirm/Reject action row. They differ only in the **leading glyph** (§2), the **headline copy** (§3.3), and the **content well** (§3.1 / §3.2).

## 2. Container, leading glyph & header — inherited, two new glyphs

- **Container, header layout, glyph-tile geometry, breathing halo, status line** — **inherited unchanged** from Chat Branching spec §2.1–§2.3. `EdgeInsets.fromLTRB(14, 13, 14, 14)`, radius `AionRadius.lg` (12), fill `chatTint`, border `chatBorderTint`, inner `Column` gap `12`. Glyph tile `32×32`, `AionRadius.md` (10), fill `pressedAccentTint(typeChat)` (`typeChat @ 0.176 / 0.256`), halo `chatGlow` looping `0.35 ↔ 0.85` over `2000ms` (`tpBreathe`). Status dot `6×6` `typeChat` pulsing `1400ms` (`tpPulseDot`). Reduced-motion: both static.

### 2.1 Leading glyph — new per variant (distinct from `branch` / `close`)

| Kind | Phosphor glyph (fallback) | Reads as | Mockup stand-in |
|---|---|---|---|
| `createTicket` | `PhosphorIcons.filePlus` (`plusSquare`) | a new ticket being created | `＋` (heavy plus) |
| `addLink` | `PhosphorIcons.link` (`linkSimple`) | two tickets being linked | `⋈` (join / U+22C8) |

- **Glyph size/color:** `18px`, color `typeChat` (`#4C6FDE / #7C93FF`), both variants — identical to the `branch` / `close` glyphs.
- These are deliberately *not* directional (unlike the branch/close mirror pair): `create` is an additive act (a plus), `link` is an associative act (a join). The **direction** semantics for `addLink` live on the *relationship* glyph inside the well (§3.2), not the tile.
- The tile glyph for `addLink` is the **generic** link mark; the **specific** relationship (`blocks` etc.) is shown by the `TicketLinkTypeDisplay.glyph` inline in the well diagram (§3.2), never on the tile.

### 2.2 Header title / status — inherited style, new copy

- **Title:** `AionText.dialogTitle` (18 / w800), color `textPrimary` (`#142230 / #E7EDF7`), `maxLines: 2`, ellipsis, `letter-spacing: -0.01em`, line-height `1.2`. Copy patterns per variant in §3.3.
- **Status line:** unchanged — `AionText.streamStatus` (mono 12.5 / w400), color `textSecondary`, preceded by the pulsing dot: **`"Paused — waiting for your decision"`** (both variants), identical to `branch` / `close`.

## 3. Content wells, headline copy & actions

### 3.1 `createTicket` variant — new-ticket preview well

A recessed well that reads as "the ticket about to be created," echoing an Aion ticket row (a `TypeChip` + a title + body). Same well container as the branch well (Chat Branching spec §3.1):

- **Well container:** `DecoratedBox` → `Padding` → `Column`.
  - **Fill:** `surface` (`#FBFCFE / #131A29`) — recessed against the `chatTint` banner.
  - **Border:** `1px solid border` (`#D6E0EA / #232C40`).
  - **Radius:** `AionRadius.md` (10).
  - **Padding:** `EdgeInsets.fromLTRB(11, 10, 11, 11)`.
  - **Layout:** `Column`, `crossAxisAlignment: start`, `gap: 8` (`AionSpacing.sp8`).
- **Type-chip row** (`Row`, `gap: 7`, `crossAxisAlignment: center`): a standard **`TypeChip`** for `newTicketType` — the existing chip (Chat Transcript spec §0.1 / Bug Ticket Type spec), reused verbatim:
  - Chip fill `typeTint(newTicketType, isDark)` (§4), inner `9×9` square `AionRadius` `2` in the type accent, label `AionText.chip` (10.5 / w700, pre-uppercased, `+0.53` tracking) in the type accent. Label + accent per §3.1.1.
  - Padding `EdgeInsets.fromLTRB(6, 3, 8, 3)`, radius `5`, `gap: 5` square→label.
  - `Spacer` (trailing).
- **Title:** `AionText.cardTitle` (14 / w600), color `textPrimary`, `maxLines: 2`, ellipsis — `newTicketTitle`.
- **Description** (optional — omit the node entirely if `newTicketDescription == null`): `AionText.bodySm` (13.5 / w400, line-height 1.55), color `textSecondary`, `maxLines: 3`, ellipsis — the AI's one-to-three-sentence rationale/body for the ticket.

#### 3.1.1 Type accent + chip label per `TicketType`

Reused unchanged from the ticket-type system — **no new hue, no new copy**:

| `TicketType` | Accent token | Arctic / Obsidian | Chip label |
|---|---|---|---|
| `task` | `AionColors.typeTask` | `#2E86D4 / #9366FF` | `"TASK"` |
| `story` | `AionColors.typeStory` | `#1E9E76 / #33D19B` | `"STORY"` |
| `bug` | `AionColors.typeBug` | `#5E8C1E / #98D13C` | `"BUG"` |

`create_ticket` only ever creates a top-level `story` / `task` / `bug` (never `epic`, `chat`, `page`, or `resource`), so only these three accents appear.

### 3.2 `addLink` variant — relationship well (directional mini-diagram)

Same well container geometry as §3.1 (fill `surface`, `1px border`, radius `AionRadius.md` (10)), padding `EdgeInsets.fromLTRB(11, 10, 11, 11)`, `Column` `crossAxisAlignment: start`, `gap: 9`. Its body is a **directional link diagram**, not a title+description — it visualizes *which two tickets* are being related and *in which direction*, so the relationship reads at a glance without repeating the target title (which is in the headline, §3.3):

- **Eyebrow row** (`Row`, `gap: 7`, center): a `9×9` square `AionRadius` `2` fill `typeChat`; a relationship eyebrow `AionText.caption` (mono 11 / w600, tracked, UPPERCASE) re-sized to **9.5**, color `typeChat` — the relationship name (§3.2.1). Keyed to `typeChat` (banner identity), consistent with the `NEW CHAT` / `RESOLUTION` eyebrows; it names *the well*, not a ticket type.
- **Diagram row** (`Row`, `gap: 10`, `crossAxisAlignment: center`):
  - **Source chip** — the current ticket's key, `currentTicketKey`: `AionText.key` (JetBrains Mono 11 / w600, `+0.11`), color `textSecondary`, in a `surfaceHover` (`#E4EDF6 / #1C2436`) pill, `EdgeInsets.symmetric(horizontal: 7, vertical: 3)`, radius `AionRadius.sm` (6).
  - **Relationship glyph** — `TicketLinkTypeDisplay.glyph(linkType)` (§3.2.1), `18px`, color **`textSecondary`** (`#46586A / #A2AEC6`) — **monochrome**, per the Link Type spec §1.4 rule that relationship glyphs are never type-accent-colored. The glyph carries the direction (arrow-right / arrow-left / arrows-left-right / copy).
  - **Target chip** — `targetTicketKey`, same pill treatment as the source chip but with a **1px `borderStrong`** hairline (`#BAC8D6 / #35415C`) to read as the "other" ticket, `textPrimary` label.
- **Target title:** `AionText.bodySm` (13.5 / w400, line-height 1.5), color `textSecondary`, `gap: 2` below the diagram row, `maxLines: 2`, ellipsis — `targetTicketTitle`. (The headline already leads with it; the well repeats it small only when it would otherwise ellipsize in the headline — implementers may omit if identical and untruncated. Mockups show it for realism.)

#### 3.2.1 Relationship glyph + eyebrow + headline verb per `TicketLinkType`

Glyphs are `TicketLinkTypeDisplay.glyph` — reused verbatim from the Link Type spec §1.4 (monochrome). Source = the current ticket; target = `targetTicketKey`.

| `TicketLinkType` | Glyph (Phosphor / fallback) | Mockup stand-in | Well eyebrow | Headline verb (§3.3) | Direction |
|---|---|---|---|---|---|
| `blocks` | `arrow-right` (`arrow-line-right`) | `→` | `"BLOCKS"` | `"Mark as blocking"` | source → target |
| `blockedBy` | `arrow-left` (`arrow-line-left`) | `←` | `"BLOCKED BY"` | `"Mark as blocked by"` | source ← target |

### 3.3 Headline copy patterns

`AionText.dialogTitle`, `textPrimary`, `maxLines: 2`, ellipsis (§2.2).

- **`createTicket`:** `"Create {type}: {title}"` where `{type}` is the lowercase type word (`task` / `story` / `bug`) and `{title}` is `newTicketTitle`.
  - e.g. `"Create task: Fix login retry bug"` · `"Create story: Offline draft sync"` · `"Create bug: Board drag drops card on wrong column"`.
- **`addLink`:** `"{verb} {targetKey}: {targetTitle}"` using the §3.2.1 verb.
  - e.g. `"Mark as duplicate of AIO-42: Retry button double-fires"` · `"Mark as blocking AIO-51: Ship session-store migration"` · `"Mark as blocked by TASK-42: Vault token rotation"` · `"Link as related to AIO-19: Auth telemetry dashboard"`.
- If `{title}`/`{targetTitle}` would overflow two lines it ellipsizes; the well (§3.1 / §3.2) still carries the full specifics.

No copy change.

### 3.5 Button states — **inherited unchanged**

All six states for both buttons (default / hover / focused / pressed / disabled; error n/a → toast) are **exactly** Chat Branching spec §3.5. Confirm hover = `Color.lerp(typeChat, white/black, 0.10)`, focus ring `typeChat @ 0.16 / 0.30`, pressed `AnimatedScale 0.98`, disabled `typeChat @ 0.45` + `IgnorePointer`.
