**Implementation note (T15, post-`/verify`):** T15's first pass wired
`LinkedTicketsSection.linkTypeOptions: const []` on `page_detail_screen
.dart`, which — via `_LinkRow._editable`'s "≥1 *other* option" rule —
meant a page's linked-ticket rows could be removed but never retyped;
`onChangeType` was wired but unreachable. Corrected to the same widened
`[blocks, blockedBy, relatesTo, duplicates]` set
`ticket_metadata_section.dart` uses for every non-`resource` type, since
proposal.md's Non-goals scope out page-side link *creation* only, not
in-place *editing* of an already-authored row.

**Implementation note (T14/T15, post-`/verify`):** `toCanonical` ended up
called from inside `TicketsCubit.updateTicketLinkType` itself, not from
either widget call site as originally written above. `LinkedTicketRef`
deliberately doesn't carry the underlying row's `sourceTicketId`/
`targetTicketId` (see `linked_ticket_ref.dart`'s dartdoc), so a widget-
layer `toCanonical` call would need a second repository round-trip the
Cubit already makes for its blocking-state check
(`_linkInvolvesBlocking`). Doing the translation there instead is one
fetch, one write — and keeps the relative→canonical mapping, which is
domain logic, inside the Cubit rather than the widget, per project.md's
Cubit-owns-domain-logic convention. `updateTicketLinkType`'s third
parameter is therefore `newRelativeType` (not a pre-translated
canonical value); `T14`/`T15`'s widget call sites pass the editor's
relative selection straight through unmodified.
