# Design: Ticket Deletion

## Overview

Four layers, mirroring the existing `updateTicket`/`updateTicketStatus`
pattern already in the codebase:

```
TicketDetailScreen (⋮ menu → confirm dialog)
        │
        ▼
TicketsCubit.deleteTicket(id)
        │
        ▼
TicketRepository.deleteTicket(id)   ← domain interface
        │
        ▼
DriftTicketRepository.deleteTicket(id)   ← checks children, cascades, deletes
        │
        ├─ TicketDao.countChildTickets / deleteTicketRow
        ├─ TicketLinkDao.deleteLinksForTicket
        └─ CommentDao.deleteCommentsForTicket
```

## Domain layer

### `TicketHasChildrenException`

New file: `lib/features/tickets/domain/exceptions/ticket_has_children_exception.dart`.

```dart
/// Thrown by [TicketRepository.deleteTicket] when the target ticket has
/// one or more structural children (other tickets whose `parentId` points
/// at it). Deletion is blocked rather than cascading to children, so the
/// caller must reparent or delete them first.
class TicketHasChildrenException implements Exception {
  /// Creates a [TicketHasChildrenException] for a ticket with [childCount]
  /// structural children.
  const TicketHasChildrenException(this.childCount);

  /// How many tickets have `parentId` pointing at the ticket that failed
  /// to delete.
  final int childCount;

  @override
  String toString() => 'TicketHasChildrenException($childCount children)';
}
```

A plain `implements Exception` class, not `Equatable` — it's thrown and
caught, never compared or stored in state beyond its `childCount`.

### `TicketRepository.deleteTicket`

```dart
/// Deletes the ticket with internal id [id], cascading to its comments
/// and any `ticket_links` rows that reference it in either direction.
///
/// Throws [StateError] if [id] does not exist. Throws
/// [TicketHasChildrenException] — without deleting anything — if any
/// other ticket has `parentId == id`; the caller must reparent or delete
/// those children first. Structural children are never cascade-deleted.
Future<void> deleteTicket(String id);
```

`StateError` for "not found" matches no existing precedent exactly
(`updateTicket`/`updateTicketStatus` docs just say "throws if id doesn't
exist" without naming a type), so `StateError` is chosen as the standard
Dart type for "this method was called in an invalid state" — consistent
with there being no bespoke `TicketNotFoundException` anywhere in the
codebase today.

## Data layer

### `TicketDao` additions

```dart
/// Returns how many tickets have `parent_id == parentId`. Used by
/// [DriftTicketRepository.deleteTicket] to block deletion of tickets
/// with structural children.
Future<int> countChildTickets(String parentId) {
  final query = selectOnly(ticketsTable)
    ..addColumns([ticketsTable.id.count()])
    ..where(ticketsTable.parentId.equals(parentId));
  return query.map((row) => row.read(ticketsTable.id.count()) ?? 0).getSingle();
}

/// Deletes the ticket row with primary key [id]. Callers are responsible
/// for cascading to dependent rows (comments, links) first.
Future<void> deleteTicketRow(String id) {
  return (delete(ticketsTable)..where((t) => t.id.equals(id))).go();
}
```

### `TicketLinkDao` addition

```dart
/// Deletes every link row where [ticketId] is the source or the target.
Future<void> deleteLinksForTicket(String ticketId) {
  return (delete(ticketLinksTable)
        ..where((t) =>
            t.sourceTicketId.equals(ticketId) |
            t.targetTicketId.equals(ticketId)))
      .go();
}
```

### `CommentDao` addition

```dart
/// Deletes every comment row for [ticketId]. The one exception to this
/// DAO's append-only-by-construction rule (see class doc) — ticket
/// deletion is the sole caller.
Future<void> deleteCommentsForTicket(String ticketId) {
  return (delete(ticketCommentsTable)..where((t) => t.ticketId.equals(ticketId))).go();
}
```

Update `CommentDao`'s class-level dartdoc — it currently says "No UPDATE
or DELETE methods are exposed — append-only by construction." That
sentence becomes inaccurate; reword to note the single cascade-delete
exception.

### `DriftTicketRepository.deleteTicket`

```dart
@override
Future<void> deleteTicket(String id) async {
  final existing = await _db.ticketDao.getTicketById(id);
  if (existing == null) {
    throw StateError('Ticket $id does not exist');
  }

  final childCount = await _db.ticketDao.countChildTickets(id);
  if (childCount > 0) {
    throw TicketHasChildrenException(childCount);
  }

  await _db.transaction(() async {
    await _db.commentDao.deleteCommentsForTicket(id);
    await _db.ticketLinkDao.deleteLinksForTicket(id);
    await _db.ticketDao.deleteTicketRow(id);
  });
}
```

The children check happens *before* the transaction so no partial
cascade can occur if it fails — nothing is deleted at all in the blocked
case. `AppDatabase.transaction` is Drift's own top-level transaction
wrapper (already used inside `TicketDao.insertTicket`); using it here
spans three DAOs in one atomic unit, unlike the existing single-DAO
transaction usage.

## Presentation layer

### `TicketsState` additions

```dart
/// A [TicketsCubit.deleteTicket] call is in flight for the ticket
/// currently shown on [TicketDetailScreen].
class TicketDeleting extends TicketsState {
  const TicketDeleting();
}

/// A ticket was deleted successfully. Carries no data — the UI responds
/// by navigating back to `/tickets`, where [TicketsCubit.loadTickets]
/// re-fetches the now-shorter list.
class TicketDeleted extends TicketsState {
  const TicketDeleted();
}
```

Extend `TicketsErrorReason`:

```dart
enum TicketsErrorReason {
  /// The requested ticket does not exist.
  notFound,

  /// Deletion was blocked because the ticket has structural children.
  /// The widget layer reads [TicketsError.childCount] to build a
  /// count-aware message.
  hasChildren,
}
```

`TicketsError` gains an optional `childCount` field (`int?`, only set
when `reason == hasChildren`) so `ticketsErrorMessage` can interpolate
the count into the localized string without a second lookup.

### `TicketsCubit.deleteTicket`

```dart
/// Deletes the ticket with internal id [id] via
/// [TicketRepository.deleteTicket]. Emits [TicketDeleting] immediately,
/// then [TicketDeleted] on success.
///
/// On failure from [TicketHasChildrenException], emits
/// [TicketsError(reason: TicketsErrorReason.hasChildren)] (carrying the
/// blocking child count) — solely so a listener (e.g. `AppToast`) can
/// react — then immediately re-fetches and emits [TicketDetailLoaded]
/// with the unchanged ticket, so the detail screen's body never falls
/// into the generic error rendering for this case; the delete is
/// blocked, not "confirmed but failed." Any other failure emits a
/// generic [TicketsError] — including "not found," which by this point
/// would only happen from a concurrent delete elsewhere, not a normal
/// user path.
Future<void> deleteTicket(String id) async {
  emit(const TicketDeleting());
  try {
    await _repository.deleteTicket(id);
    emit(const TicketDeleted());
  } on TicketHasChildrenException catch (e) {
    emit(TicketsError('', reason: TicketsErrorReason.hasChildren, childCount: e.childCount));
    final ticket = await _repository.getTicketById(id);
    if (ticket != null) {
      emit(TicketDetailLoaded(ticket));
    }
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

**Correction found during `/verify`:** the original draft of this snippet
(above, now fixed) omitted the re-fetch-and-emit step. Without it, the
detail screen's body `BlocBuilder` — which pattern-matches `TicketsError`
generically for its error-rendering branch — would blank the entire
ticket view on a blocked delete instead of just showing the toast,
directly contradicting §4's "delete never reaches a confirmed-but-failed
limbo state." Fixed during `/apply`; this file updated to match during
`/verify` so the snippet can't mislead a future reader into
reintroducing the bug.

### UI: `TicketDetailScreen`

The header's trailing `PhosphorIcon(PhosphorIcons.dotsThreeLight, ...)`
(currently a static, non-interactive icon at
`ticket_detail_screen.dart:89-93`) becomes the trigger of a new
feature-local `TicketOverflowMenu` widget, built with the same
`Overlay`/`LayerLink`/`CompositedTransformFollower`/`mounted`-guard
mechanics already used by `SelectionMenu<T>` and `MoveToStatusMenu` — a
third instance of that pattern, consistent with the spec's already-
acknowledged "minor duplication" precedent between the first two. It is
not built on `SelectionMenu<T>` because that widget is a *value picker*
(excludes `currentValue`, calls `onSelected(T)`); an overflow menu is an
*action list*, a different shape. Currently lists exactly one item,
"Delete ticket," styled with `AionColors.danger` text/icon.

Selecting "Delete ticket" opens a new core primitive:

```dart
/// Shows a centered, non-Material confirmation dialog: a full-screen
/// scrim (dismiss on tap) behind a card with [title], [message], and
/// Cancel/[confirmLabel] actions. Resolves `true` if the user confirms,
/// `false` if they cancel or tap the scrim.
///
/// Built the same way as [AppToast] — an [OverlayEntry] inserted into
/// the nearest [Overlay] — so it needs no `Scaffold`/`Dialog` ancestor
/// and stays outside the banned-Material-widgets list (no
/// `showDialog`/`AlertDialog`).
Future<bool> showAppConfirmDialog(
  BuildContext context, {
  required String title,
  required String message,
  required String confirmLabel,
  String? cancelLabel,
  bool isDestructive = false,
});
```

New file: `lib/core/widgets/app_confirm_dialog.dart`. Uses `AppButton`
(existing `AppButtonVariant.destructive` when `isDestructive: true`,
`secondary` for cancel) for its two actions — no new button styling
needed. This is a general-purpose primitive (not ticket-specific)
because destructive-confirmation is a pattern the app will need again
(any future delete affordance); it belongs in `core/widgets/` alongside
`AppToast`, not inside the tickets feature.

`TicketOverflowMenu`'s "Delete ticket" handler:

```dart
Future<void> _onDeletePressed(BuildContext context, Ticket ticket) async {
  final confirmed = await showAppConfirmDialog(
    context,
    title: context.l10n.ticketDeleteConfirmTitle,
    message: context.l10n.ticketDeleteConfirmMessage,
    confirmLabel: context.l10n.ticketDeleteConfirmAction,
    isDestructive: true,
  );
  if (confirmed && context.mounted) {
    context.read<TicketsCubit>().deleteTicket(ticket.id);
  }
}
```

`TicketDetailScreen`'s `build` gains a `BlocListener<TicketsCubit,
TicketsState>` (wrapping the existing `BlocBuilder`, or a
`MultiBlocListener`-style combination — implementation detail for
`/apply`) that:
- on `TicketDeleted` → `context.go('/tickets')`.
- on `TicketsError(reason: hasChildren, :childCount)` → `AppToast.show`
  with a count-aware message
  (`context.l10n.ticketDeleteBlockedByChildren(childCount)`).

No change to `TicketsListScreen` or `TicketBoardView` — deletion is
detail-screen-only per scope.

## Localization

New ARB keys in `lib/l10n/app_en.arb` (added to
`context.l10n`/`AppLocalizationsX`, following the existing convention —
no raw string literals in presentation code):

- `ticketDetailOverflowMenuLabel` — semantics label for the `⋮` trigger.
- `ticketDeleteMenuItem` — "Delete ticket" menu item text.
- `ticketDeleteConfirmTitle` — dialog title, e.g. "Delete this ticket?"
- `ticketDeleteConfirmMessage` — body, e.g. "This cannot be undone."
- `ticketDeleteConfirmAction` — confirm button label, "Delete."
- `ticketDeleteBlockedByChildren` — ICU plural, e.g. "This ticket has
  {count, plural, one{1 subticket} other{{count} subtickets}} — delete
  or reparent them first."

## Testing

- `TicketsCubit` unit tests (mocktail + bloc_test): `deleteTicket`
  success (`TicketDeleting` → `TicketDeleted`), `TicketHasChildrenException`
  path (`TicketDeleting` → `TicketsError(reason: hasChildren, childCount:
  n)`), generic repository failure path.
- `DriftTicketRepository` tests (in-memory Drift, matching the existing
  `drift_ticket_repository_test.dart` style): deleting a childless ticket
  removes its row, its comments, and its links (both as source and as
  target); deleting a ticket with children throws
  `TicketHasChildrenException` and leaves all rows — ticket, comments,
  links, children — untouched; deleting a non-existent id throws
  `StateError`.
- No new widget tests planned for `AppConfirmDialog`/`TicketOverflowMenu`
  beyond what `/apply`'s manual interactive pass covers — per
  `project.md`'s testing note, `Overlay`-managing `StatefulWidget`s need a
  live `flutter run` pass (mounted-guard correctness), not just
  `flutter analyze`/`flutter test`.

## Manual verification (required before this change reaches `/verify`)

`AppConfirmDialog` and `TicketOverflowMenu` are both new `Overlay`-based
widgets. Per `project.md`'s note on `AppDropdown`'s prior
setState-after-dispose bug, this needs a live `flutter run` pass:
- Open the overflow menu, dismiss without selecting (tap outside) —
  no error.
- Confirm a delete on a childless ticket — navigates back to `/tickets`,
  ticket is gone from the list.
- Attempt to delete a ticket that has children — blocked, toast shown
  with correct count, ticket still present.
- Cancel the confirm dialog — no deletion occurs, dialog dismisses

# Aion — Ticket Deletion: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AppButton`, `AppToast` by name. **No Material widgets anywhere** — overflow menu and confirm dialog are `OverlayEntry`s inserted into the nearest `Overlay`, built from `DecoratedBox`, `GestureDetector`, `Positioned`, `CompositedTransformFollower`/`CompositedTransformTarget`, and `Container`.

Adds interactivity to `TicketDetailScreen`'s existing header `⋮` icon. No new screens.

One new token required: `AionText.dialogTitle` (justification in §3.4).

---

## 1. Overflow trigger (updated)

The existing header `⋮` glyph, today static, becomes a `GestureDetector`-wrapped icon button.

### 1.1 Default state

- Hit area: `37×37` (matches the header's back-button footprint).
- No chrome at rest — transparent fill, no border — identical to today's static rendering so the header doesn't visually change until interacted with.
- Glyph: `dots-three` (⋯), **20px**, color `textSecondary`.
- Cursor: `SystemMouseCursors.click` (web/desktop).

### 1.2 Hover state (pointer devices only)

- Fill: `surfaceHover`. Radius: `AionRadius.iconBtn` (11).
- Glyph color unchanged (`textSecondary`).
- Transition: 100ms fill fade.

### 1.3 Focused state (keyboard nav)

- Same fill as hover (`surfaceHover`) plus a focus ring: `BoxShadow(color: primary.withValues(alpha: isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)`.

### 1.4 Pressed state

- Fill: `border` (one step darker than `surfaceHover`).
- Scale: `0.96` (`AnimatedScale`, 80ms) — matches `AppButton` press feedback.
- On release: opens the overflow menu (§2), trigger stays in pressed/active look (fill `surfaceHover`) while the menu is open.

---

## 2. Overflow menu

A single-item overlay anchored to the trigger via `CompositedTransformTarget` (wrapping the trigger) / `CompositedTransformFollower` (the menu), offset `(0, 6)`, anchored **top-right** growing down-left (trigger sits at the header's trailing edge, so the menu must not overflow the screen's right side).

### 2.1 Container

- Fill: `surface`.
- Border: `1px solid borderStrong`.
- Radius: `AionRadius.lg` (12).
- Shadow: `BoxShadow(color: const Color(0xFF000000).withValues(alpha: isDark ? 0.55 : 0.16), blurRadius: 28, offset: Offset(0, 12))` — same formula as the base spec's selection-menu overlay.
- Width: content-driven, min `180`, max `240`.
- Padding: `EdgeInsets.symmetric(vertical: 6)` (row fills full width, no horizontal container padding — matches base spec §3.3 pattern).
- Entrance: scale-in `0.96 → 1.0` + fade, 120ms, anchored top-right.

### 2.2 "Delete ticket" row

- Height: `40`. Padding: `EdgeInsets.symmetric(horizontal: 13, vertical: 9)`.
- Layout: `Row`, `gap: 10` — leading `trash` icon, **16px**, color `danger` + label `AionText.bodySm` with `fontWeight` override to `w600`, color `danger`.
- **Default:** fill transparent.
- **Hover:** fill `danger.withValues(alpha: isDark ? fillAlphaObsidian : fillAlphaArctic)`.
- **Focused** (keyboard): same hover fill + inset focus ring: `BoxShadow(color: danger.withValues(alpha: isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: -2)` (inset since the row is edge-to-edge with the container).
- **Pressed:** fill `danger.withValues(alpha: (isDark ? fillAlphaObsidian : fillAlphaArctic) * 1.6)`.
- Tap → closes the overflow menu, then opens the confirm dialog (§3). No intermediate state.

### 2.3 Dismissal

- Tap outside the menu (invisible full-screen `GestureDetector` behind it, inserted into the same `Overlay` beneath the menu) → closes, no change.
- `Esc` (desktop/web) → closes, no change.
- Only one overlay entry open at a time — opening the confirm dialog removes the menu's `OverlayEntry` first.

---

## 3. Confirm dialog

Inserted as its own `OverlayEntry` (scrim + card), replacing the overflow menu. Not a route push — no back-button/URL interaction.

### 3.1 Scrim

- Full-screen `Positioned.fill` behind the card, `GestureDetector` with `onTap` → dismiss (equivalent to Cancel).
- Fill: `const Color(0xFF000000).withValues(alpha: isDark ? 0.62 : 0.40)` // black scrim — not a themed token, same raw-literal exception as white-on-fill glyphs. (Neutral black scrim, consistent overlay-dimming value across both themes, matching common Flutter overlay practice.)
- Entrance: fade 0 → 1, 140ms.

### 3.2 Card

- Centered via `Center`.
- Width: `360` fixed on viewports ≥ `420px`. **Responsive (narrow/mobile):** `viewport width − 32` (16px margin each side) when viewport `< 420px`.
- Padding: `EdgeInsets.all(24)`.
- Fill: `surface`.
- Border: `1px solid border`.
- Radius: `AionRadius.xl` (16).
- Shadow: `BoxShadow(color: const Color(0xFF000000).withValues(alpha: isDark ? 0.60 : 0.18), blurRadius: 40, spreadRadius: -6, offset: Offset(0, 20))`.
- Entrance: scale `0.94 → 1.0` + fade, 160ms, `Curves.easeOutCubic`.

### 3.3 Leading icon

- `44×44` circle, fill `danger.withValues(alpha: isDark ? fillAlphaObsidian : fillAlphaArctic)`, centered horizontally, `margin-bottom: 16`.
- Glyph: `trash`, **20px**, color `danger`, centered in the circle.

### 3.4 Title

- Text: `"Delete this ticket?"`.
- Style: **`AionText.dialogTitle`** (new token) — `TextStyle(fontFamily: 'Manrope', fontSize: 18, fontWeight: FontWeight.w800, letterSpacing: -0.18, height: 1.3)`, color `textPrimary`.
- *Justification:* the existing scale has no 16–18px w700/800 style — `h2` (22px) reads oversized for a dialog headline, `cardTitle` (14px w600) reads undersized. `dialogTitle` fills that gap; scoped to dialogs generally, not deletion-specific.
- Margin-bottom: `8`.
- Alignment: center.

### 3.5 Body message

- Text: `"This cannot be undone."`.
- Style: `AionText.bodySm`, color `textSecondary`.
- Alignment: center.
- Margin-bottom: `24`.

### 3.6 Actions

- Layout: `Row`, `gap: AionSpacing.sp12` (12), `mainAxisAlignment: end`.
- **Cancel** — `AppButton` variant `secondary`. Closes dialog, no change.
- **Delete** — `AppButton` variant `destructive`. Triggers delete; on success the screen pops back to the parent list/board. On failure (subtickets block it), see §4.
- **Responsive (narrow, viewport < 420px):** row becomes a `Column`, `gap: AionSpacing.sp8` (8), both buttons full-width (`double.infinity`), **Delete above Cancel** (destructive action gets thumb-priority position on mobile, matching iOS/Android action-sheet convention).

### 3.7 Dismissal

- Cancel button, scrim tap, or `Esc` → closes, no mutation.
- Delete button → calls delete; dialog shows no separate loading state (delete is expected to be near-instant; if latency is added later, disable both buttons and set `AppButton` `primary`-style opacity 0.6 on Delete while pending — not specified further here as out of scope).

---

## 4. Blocked-by-children toast

Reuses **`AppToast` unchanged** in container, padding, radius, shadow, and layout (base spec / Ticket Editing Spec §5) — same `Row`, `gap: 10`, leading icon + message, same entrance/exit animation and 3.2s auto-dismiss. Only the icon and message differ from the neutral default:

- Icon: `prohibit` (or `warning-circle`), **18px**, color `danger` (default `AppToast` uses `textSecondary` for a neutral icon — this variant swaps to `danger` to signal the blocked action).
- Message: `AionText.bodySm`, color `textPrimary` (unchanged from default).
- Copy: `"Can't delete — this ticket has subtickets. Delete or move them first."`
- Border: unchanged (`1px solid border`) — do not tint the container border; the icon color alone carries the danger signal, keeping the toast visually consistent with every other `AppToast` instance in the app.

Triggered when Delete (§3.6) is tapped on a ticket with ≥ 1 subticket: the confirm dialog closes immediately (as if Delete succeeded from the user's perspective) and this toast appears in its place — the delete never reaches a "confirmed but failed" limbo state.

## 5. State summary

| Component | Default | Hover | Focused | Pressed/Open | Error |
|---|---|---|---|---|---|
| Overflow trigger | transparent, `dots-three` `textSecondary` | `surfaceHover` fill | `surfaceHover` fill + focus ring | `border` fill, scale 0.96 → menu opens | n/a |
| Overflow menu row | transparent | `danger`-tinted fill (`fillAlpha`) | tinted fill + inset ring | tinted fill ×1.6 → confirm dialog opens | n/a |
| Confirm dialog | scrim + card, entrance animation | n/a | Cancel/Delete inherit `AppButton` focus rings | Delete → delete or blocked toast; Cancel/scrim/Esc → close | subtickets present → §4 toast, dialog closes |

No existing color, radius, or spacing tokens required changes. One new type token, `AionText.dialogTitle`, is introduced per §3.4.

## 6. Post-implementation notes (added during `/verify`)

### 6.1 New tokens not originally tracked

`/design-sync`'s Step 2 cross-reference only tracked `AionText.dialogTitle`
(§3.4) as a new token. Two more were added during `/apply` and are noted
here for a complete audit trail:

- **`AionShadows.dialog(AionColors, bool isDark)`** — new shadow method in
  `aion_shadows.dart`, backing §3.2's confirm-dialog card shadow exactly
  (`blurRadius: 40, spreadRadius: -6, offset: Offset(0, 20)`, black at
  `isDark ? 0.60 : 0.18`). Added because no existing `AionShadows` method
  matched this elevation profile.
- **`ticketDeleteBlockedByChildrenGeneric`** ARB key — a non-count-aware
  fallback string, added solely so `ticketsErrorMessage`'s switch over
  `TicketsErrorReason` stays exhaustive once `hasChildren` was added to
  that enum. Not user-facing in the normal flow (see §6.2 below and the
  `TicketsCubit.deleteTicket` correction above) — the count-aware
  `ticketDeleteBlockedByChildren` (§Localization) is what's actually
  shown, via `AppToast`.

### 6.2 Known gaps deferred to a future pass

Two deviations from this design were found during `/verify` and are
being carried forward as known gaps rather than fixed in this change,
per the project's precedent of deferring pre-existing/shared-pattern
polish rather than blocking a change on it:

- **No Hover/Focused/Pressed states on the overflow trigger or its
  "Delete ticket" row.** §1.2/§1.3/§2.2 specify explicit fill tints and
  focus rings for these states; the shipped implementation only has a
  Default state, and the row has no `FocusableActionDetector`, so there
  is no keyboard path to activate "Delete ticket" without a mouse. This
  matches the actual (undocumented) precedent already set by
  `SelectionMenu` and `MoveToStatusMenu`, whose overlay list items have
  the same gap — despite `tickets.md`'s accessibility section claiming
  "each list item is wrapped in `FocusableActionDetector`" for
  `MoveToStatusMenu`, which is inaccurate against the actual code and
  predates this change. Fixing this properly means addressing all three
  overlay-list widgets together, not just `TicketOverflowMenu`.
- **Overflow menu container shadow (§2.1) doesn't match its own spec.**
  Implementation reuses `AionShadows.card(c, isDark)` instead of the
  exact values given (`blurRadius: 28, offset: Offset(0, 12)`, explicit
  non-zero dark-mode alpha). `AionShadows.card` returns an *empty* list
  in Obsidian, so the overflow menu currently renders with **no shadow
  at all in dark theme** — a real visual gap from this spec's dark-theme
  alpha of `0.55`. Matches `SelectionMenu`'s existing reused-shadow
  precedent (same root cause as above).

Both should be revisited together in a follow-up pass that gives
`SelectionMenu`, `MoveToStatusMenu`, and `TicketOverflowMenu` a shared,
correct hover/focus/pressed treatment and shadow token, rather than
three divergent one-off fixes.
