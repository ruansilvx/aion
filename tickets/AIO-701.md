# Spec Delta: Define type-compatibility matrix

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (16/18 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Delta against `aion-arch/specs/tickets.md`. Read alongside
[proposal.md](../proposal.md) and [design.md](../design.md) — this file
only lists what changes, not full current-state context.

## ADDED

- **Type-compatibility rule** (`TicketTypeHierarchy.canParent`,
  `domain/enums/ticket_type.dart`): a strict rank ordering — epic(0) >
  story(1) > task(2), with resource/page/chat as unranked leaves. A
  ticket of type `parent` may structurally parent a ticket of type
  `child` iff `parent` is ranked and either `child` is unranked (any
  ranked type may parent any leaf type) or `parent`'s rank is strictly
  less than `child`'s rank. This is the general type-compatibility
  matrix previously flagged as absent in `tickets.md`'s Known gaps.
- **`TicketsCubit.getValidParentCandidatesForType(TicketType childType)`**
  — new query-only method for the create-ticket flow, where no existing
  ticket id exists to derive self/descendant exclusions from. Returns
  every ticket whose type may parent `childType` per the new rule.
  Feeds `CreateTicketScreen`'s `TicketParentPicker.candidatesLoader`,
  replacing its prior use of the now-narrower-purpose `getAllTickets()`.

## MODIFIED

- **`TicketsCubit.getValidParentCandidates(Ticket ticket)`** — in
  addition to the existing self/descendant exclusion, now also excludes
  any candidate whose type cannot parent `ticket.type` per the new rule.
  Still query-only, still feeds `TicketDetailScreen`'s
  `TicketParentPicker.candidatesLoader`.
- **`TicketsCubit.updateTicketParent(Ticket ticket, String? newParentId)`**
  — in addition to the existing self-parent, epic-child, and cycle
  rejections, now also rejects a `newParentId` whose ticket type cannot
  parent `ticket.type` per the new rule (or whose ticket no longer
  exists, defensively). Rejection path is unchanged: emits
  `TicketsError(reason: invalidParent)` then a re-emitted
  `TicketDetailLoaded`, exactly as the existing rejection cases do — no
  new `TicketsErrorReason` value.
- **`TicketType.task`'s dartdoc** — previously stated that a task whose
  `parentId` points to another task *or story* is "the Aion subtask
  convention (no dedicated type)." The task-under-task half of that
  claim is now false: task-under-task is rejected like every other
  same-type pair. Task-under-story remains valid and unaffected.
- **`TicketParentPicker`** (`presentation/widgets/ticket_parent_picker.dart`)
  — now re-invokes `candidatesLoader` via a new `didUpdateWidget`
  override whenever `ticketType` changes, instead of fetching candidates
  only once at mount. Necessary because `CreateTicketScreen`'s type
  dropdown can now change which candidates are valid for the same
  in-progress ticket.
- **`CreateTicketScreen`**
  (`presentation/screens/create_ticket_screen.dart`) — the type
  dropdown's `onChanged` now clears `_selectedParentId` on every type
  change (previously only when switching to `epic`), since a type
  change can invalidate a previously chosen parent under the new rule.
  Its `TicketParentPicker.candidatesLoader` now calls
  `TicketsCubit.getValidParentCandidatesForType(_selectedType)` instead
  of `TicketsCubit.getAllTickets()`.

## REMOVED

None.

## Known gaps this resolves

Removes this bullet from `tickets.md`'s `## Known gaps` section (to be
folded into current-state prose at `/archive` time, not left as an open
gap):

> Reparenting enforces structural validity (no self-parent, no cycles)
> plus the one documented type invariant (an `epic` can never receive a
> parent) — but there is no general type-compatibility matrix beyond
> that (e.g. nothing prevents a `resource` from becoming the child of a
> `story`, or a `chat` from parenting a `task`).

The companion gap about `getValidParentCandidates`/`TicketParentPicker`
loading every ticket client-side (no DB-level filtering/pagination) is
**not** resolved by this change — the new type filter is applied
client-side alongside the existing self/descendant filter, with the
same scaling characteristics as before. That gap bullet stays as-is.
