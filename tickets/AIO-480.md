# Design: Bulk status and priority edit for ticket selection

## 1. Overview

Three layers change, bottom to top:

1. **`TicketDao`/`TicketRepository`** — two new bulk-write methods,
   mirroring the existing `softDeleteByIds`/`restoreByIds` shape
   (single `UPDATE ... WHERE id IN (...)`, no per-row gating —
   gating is a `TicketsCubit` concern, repositories stay dumb).
2. **`TicketsCubit`** — two new orchestration methods
   (`updateStatusForTickets`, `updatePriorityForTickets`) plus four new
   `TicketsState` subclasses, following the exact shape
   `trashTickets`/`TicketsBatchTrashing`/`TicketsBatchTrashed` already
   established for a bulk action triggered from `TicketSelectionBar`.
3. **`TicketSelectionBar`** — two new inline triggers (Status, Priority),
   each opening a dedicated new overlay (`BulkStatusMenu`/
   `BulkPriorityMenu`, sharing a `BulkOverlayRow` row component) per the
   Claude Design export integrated below — **not** built on
   `SelectionMenu<T>`. See the "Architecture decision" note before §2.

`TicketSelectionCubit` itself is untouched — it only tracks which ids
are checked; it has no opinion on what happens to them.

## 2. `SelectionMenu<T>` — superseded, not built

**Original plan (superseded at `/design-sync`):** this section originally
specced widening `SelectionMenu<T>.currentValue` from `required T` to
`required T?` so a bulk picker could reuse `SelectionMenu<T>` with
nothing excluded from its list.

**Architecture decision (made at `/design-sync`, developer-confirmed):**
the Claude Design export integrated below (starting at "Aion — Bulk
Status & Priority Edit for Ticket Selection") specs two purpose-built
overlay widgets instead — `BulkStatusMenu`/`BulkPriorityMenu`, sharing a
`BulkOverlayRow` row component (§2–§4 of that export) — rather than
reusing `SelectionMenu<T>`. The export is authoritative: `SelectionMenu<T>`
is **not modified** by this change. Every existing caller (the detail
screen's priority/status/type pickers) is completely unaffected — no
risk surface there at all, versus the original plan's (small, but
nonzero) risk of touching a shared design-system primitive.
`tasks.md` reflects this — there is no "widen `SelectionMenu`" task.

## 3. Data layer — `TicketDao`

Two new methods in `data/daos/ticket_dao.dart`, placed alongside
`softDeleteByIds`/`restoreByIds` (same bulk-`UPDATE`-via-`isIn` shape):

```dart
/// Sets `status` (as its `.name`) and bumps `updated_at` for every id in
/// [ids]. Bulk `UPDATE ... WHERE id IN (...)`, same shape as
/// [softDeleteByIds]/[restoreByIds] — used by bulk status change.
Future<void> updateStatusByIds(
  List<String> ids,
  TicketStatus status,
  int updatedAtMs,
) {
  return (update(ticketsTable)..where((t) => t.id.isIn(ids))).write(
    TicketsTableCompanion(
      status: Value(status.name),
      updatedAt: Value(updatedAtMs),
    ),
  );
}

/// Sets `priority` (as its `.name`) and bumps `updated_at` for every id
/// in [ids]. Bulk `UPDATE ... WHERE id IN (...)`, same shape as
/// [updateStatusByIds] — used by bulk priority edit.
Future<void> updatePriorityByIds(
  List<String> ids,
  TicketPriority priority,
  int updatedAtMs,
) {
  return (update(ticketsTable)..where((t) => t.id.isIn(ids))).write(
    TicketsTableCompanion(
      priority: Value(priority.name),
      updatedAt: Value(updatedAtMs),
    ),
  );
}
```

Both take a caller-supplied `updatedAtMs` (matching
`DriftTicketRepository.updateTicketStatus`'s existing pattern of
computing `DateTime.now().millisecondsSinceEpoch` once at the repository
layer, not inside the DAO) rather than calling `DateTime.now()`
internally — keeps the DAO a thin, deterministic SQL layer.

## 4. Domain layer — `TicketRepository` interface

Two new methods in `domain/repositories/ticket_repository.dart`, placed
after `updateTicketStatus`:

```dart
/// Sets `status` on every ticket in [ids] to [status]. Bulk write, same
/// shape as [trashTickets] but with no cascade and no return value — the
/// caller ([TicketsCubit]) already knows exactly which ids it's writing
/// and is responsible for excluding any id that shouldn't receive the
/// write (e.g. one rejected by a gating check). Unconditional: performs
/// no validation itself, matching [updateTicketStatus]'s existing
/// no-validation contract.
Future<void> updateStatusForIds(List<String> ids, TicketStatus status);

/// Sets `priority` on every ticket in [ids] to [priority]. Bulk write,
/// unconditional — priority has no structural gating, unlike status.
Future<void> updatePriorityForIds(List<String> ids, TicketPriority priority);
```

### `DriftTicketRepository` implementation

```dart
@override
Future<void> updateStatusForIds(List<String> ids, TicketStatus status) {
  return _db.ticketDao.updateStatusByIds(
    ids,
    status,
    DateTime.now().millisecondsSinceEpoch,
  );
}

@override
Future<void> updatePriorityForIds(List<String> ids, TicketPriority priority) {
  return _db.ticketDao.updatePriorityByIds(
    ids,
    priority,
    DateTime.now().millisecondsSinceEpoch,
  );
}
```

No-op safe on an empty `ids` list (a bulk `UPDATE ... WHERE id IN ()`
affects zero rows) — `TicketsCubit` doesn't need to special-case an
empty writable set before calling these.

## 5. Presentation layer — `TicketsCubit`

### 5.1 `updateStatusForTickets`

```dart
/// Sets [status] on every ticket in [ids], via
/// [TicketRepository.updateStatusForIds] — but only for the subset that
/// passes the same two per-ticket gates [updateTicketStatus]/
/// [changeTicketStatus] already enforce for a single ticket moving to
/// [TicketStatus.inProgress]: the Blocked-dependency gate
/// ([_isTicketBlocked]) and, for Task/Bug tickets ([TicketTypeHierarchy
/// .isExecutable]), the coding-execution gate
/// ([_codingExecutionGateCheck]). Both gates only apply when [status] is
/// [TicketStatus.inProgress] — every other target status skips gating
/// entirely and writes the full [ids] list, mirroring
/// [updateTicketStatus]'s own short-circuit. Rejected ids are silently
/// excluded from the write (not reported per-id) — the widget layer
/// surfaces the aggregate via [TicketsBatchStatusUpdated.skippedCount].
///
/// Emits [TicketsBatchStatusUpdating] immediately, then
/// [TicketsBatchStatusUpdated] (refreshed page + how many were written +
/// how many were skipped) on success, or [TicketsError] on an unexpected
/// failure. For every successfully-written ticket: triggers git
/// projection (`'status-changed'`, same event [updateTicketStatus]
/// triggers), and — for a Task/Bug moving to [TicketStatus.inProgress] —
/// starts or queues its coding-execution run via
/// [_triggerOrQueueCodingExecution], identical to [updateTicketStatus]'s
/// own post-write side effects. Also calls [_refreshBlockedBoardState]
/// on completion, since a written ticket may be another ticket's
/// blocker.
Future<void> updateStatusForTickets(
  List<String> ids,
  TicketStatus status,
) async {
  _searchGeneration++;
  final currentTickets = switch (state) {
    TicketsLoaded(:final tickets) => tickets,
    TicketCreated(:final tickets) => tickets,
    TicketStatusUpdated(:final tickets) => tickets,
    TicketsBatchTrashed(:final tickets) => tickets,
    TicketsBatchStatusUpdated(:final tickets) => tickets,
    TicketsBatchPriorityUpdated(:final tickets) => tickets,
    TicketsLoadingMore(:final tickets) => tickets,
    TicketsLoadMoreFailed(:final tickets) => tickets,
    _ => <Ticket>[],
  };
  emit(const TicketsBatchStatusUpdating());
  try {
    final writableIds = <String>[];
    if (status == TicketStatus.inProgress) {
      for (final id in ids) {
        final ticket = await _repository.getTicketById(id);
        if (ticket == null) continue;
        if (await _isTicketBlocked(ticket)) continue;
        if (ticket.type.isExecutable) {
          final check = await _codingExecutionGateCheck(ticket);
          if (!check.canStart) continue;
        }
        writableIds.add(id);
      }
    } else {
      writableIds.addAll(ids);
    }

    if (writableIds.isNotEmpty) {
      await _repository.updateStatusForIds(writableIds, status);
      for (final id in writableIds) {
        final updated = await _repository.getTicketById(id);
        if (updated != null) {
          unawaited(_triggerGitProjection(updated, 'status-changed'));
          if (updated.type.isExecutable &&
              status == TicketStatus.inProgress) {
            unawaited(_triggerOrQueueCodingExecution(updated));
          }
        }
      }
    }

    final page = await _repository.searchTickets(
      query: _lastQuery,
      statuses: _lastStatuses,
      types: _lastTypes,
      priorities: _lastPriorities,
      limit: max(_pageSize, currentTickets.length),
    );
    emit(
      TicketsBatchStatusUpdated(
        page.tickets,
        writableIds.length,
        ids.length - writableIds.length,
        hasMore: page.hasMore,
      ),
    );
    unawaited(_refreshBlockedBoardState());
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

**Why per-ticket gate checks stay in the Cubit, not the repository:**
per this project's Cubit-owns-domain-logic convention — validation and
invariant checks belong in Cubits, repositories stay dumb persistence.
`_isTicketBlocked`/`_codingExecutionGateCheck` are already private
`TicketsCubit` methods; this reuses them as-is rather than duplicating
their logic at a lower layer.

**Why gate checks don't emit their own rejection state (unlike
`_interceptBlockedDependencyTrigger`/`_interceptTaskExecutionTrigger`):**
those two helpers emit `TicketsError` + a re-emitted `TicketDetailLoaded`
on rejection — a single-ticket, detail-screen-shaped side effect that
doesn't fit a bulk, list-screen-shaped caller iterating many ids. Bulk
status change calls `_isTicketBlocked`/`_codingExecutionGateCheck`
directly (the underlying checks, not their intercept wrappers) and
aggregates the result into `skippedCount` instead.

### 5.2 `updatePriorityForTickets`

```dart
/// Sets [priority] on every ticket in [ids] via
/// [TicketRepository.updatePriorityForIds] — unconditional, no gating
/// (priority has no structural constraint, unlike status). Emits
/// [TicketsBatchPriorityUpdating] immediately, then
/// [TicketsBatchPriorityUpdated] (refreshed page + updated count) on
/// success, or [TicketsError] on an unexpected failure. Does not trigger
/// git projection (a plain field edit is not one of `project.md`'s
/// event-triggered projection events — see [updateTicket], which doesn't
/// trigger it either) and does not trigger embedding regeneration (only
/// a title/description change does, per [updateTicket]).
Future<void> updatePriorityForTickets(
  List<String> ids,
  TicketPriority priority,
) async {
  _searchGeneration++;
  final currentTickets = switch (state) {
    TicketsLoaded(:final tickets) => tickets,
    TicketCreated(:final tickets) => tickets,
    TicketStatusUpdated(:final tickets) => tickets,
    TicketsBatchTrashed(:final tickets) => tickets,
    TicketsBatchStatusUpdated(:final tickets) => tickets,
    TicketsBatchPriorityUpdated(:final tickets) => tickets,
    TicketsLoadingMore(:final tickets) => tickets,
    TicketsLoadMoreFailed(:final tickets) => tickets,
    _ => <Ticket>[],
  };
  emit(const TicketsBatchPriorityUpdating());
  try {
    await _repository.updatePriorityForIds(ids, priority);
    final page = await _repository.searchTickets(
      query: _lastQuery,
      statuses: _lastStatuses,
      types: _lastTypes,
      priorities: _lastPriorities,
      limit: max(_pageSize, currentTickets.length),
    );
    emit(
      TicketsBatchPriorityUpdated(
        page.tickets,
        ids.length,
        hasMore: page.hasMore,
      ),
    );
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

## 6. New `TicketsState` subclasses

Four additions to `presentation/cubit/tickets_state.dart`, placed after
`TicketsBatchTrashed`, following its exact shape:

```dart
/// A [TicketsCubit.updateStatusForTickets] batch call is in flight
/// (bulk, triggered from `TicketSelectionBar`'s Status action).
class TicketsBatchStatusUpdating extends TicketsState {
  const TicketsBatchStatusUpdating();
}

/// A batch status-change call completed. Carries the refreshed page, how
/// many tickets were actually written ([updatedCount]), and how many
/// were silently skipped ([skippedCount]) because moving to
/// [TicketStatus.inProgress] would have been rejected by the
/// Blocked-dependency gate or the coding-execution gate (see
/// [TicketsCubit._isTicketBlocked]/[TicketsCubit._codingExecutionGateCheck]).
/// [skippedCount] is always 0 for any target status other than
/// [TicketStatus.inProgress], since neither gate applies. The widget
/// layer surfaces both counts via a summary toast.
class TicketsBatchStatusUpdated extends TicketsState {
  const TicketsBatchStatusUpdated(
    this.tickets,
    this.updatedCount,
    this.skippedCount, {
    required this.hasMore,
  });

  final List<Ticket> tickets;
  final int updatedCount;
  final int skippedCount;
  final bool hasMore;

  @override
  List<Object?> get props => [tickets, updatedCount, skippedCount, hasMore];
}

/// A [TicketsCubit.updatePriorityForTickets] batch call is in flight
/// (bulk, triggered from `TicketSelectionBar`'s Priority action).
class TicketsBatchPriorityUpdating extends TicketsState {
  const TicketsBatchPriorityUpdating();
}

/// A batch priority-change call completed. Carries the refreshed page
/// and how many tickets were updated ([updatedCount]) — always equal to
/// the original selection size, since priority has no rejection path
/// (unlike [TicketsBatchStatusUpdated.skippedCount]).
class TicketsBatchPriorityUpdated extends TicketsState {
  const TicketsBatchPriorityUpdated(
    this.tickets,
    this.updatedCount, {
    required this.hasMore,
  });

  final List<Ticket> tickets;
  final int updatedCount;
  final bool hasMore;

  @override
  List<Object?> get props => [tickets, updatedCount, hasMore];
}
```

`TicketsListScreen`'s existing state-switch arms that pattern-match
"any list-shaped state that should render `_TicketsBody`" (currently
`TicketsLoaded() || TicketCreating() || TicketCreated() ||
TicketStatusUpdating() || TicketStatusUpdated() || TicketsBatchTrashed()
|| TicketsLoadingMore() || TicketsLoadMoreFailed()`) and the loading-spinner
arm (`TicketsLoading() || TicketTrashing() || TicketsBatchTrashing()`)
both gain the four new states — the two `*Updating` states join the
spinner arm, the two `*Updated` states join the body-render arm. Same
pattern `_currentTickets`/`_hasMore` helpers (which already `switch` on
state to extract `tickets`/`hasMore`) gain matching `case` arms.

## 8. `TicketsListScreen` wiring

Two new handler methods, alongside the existing
`_confirmAndTrashSelection`:

```dart
void _bulkChangeStatus(BuildContext context, Set<String> ids, TicketStatus status) {
  context.read<TicketsCubit>().updateStatusForTickets(ids.toList(), status);
}

void _bulkChangePriority(BuildContext context, Set<String> ids, TicketPriority priority) {
  context.read<TicketsCubit>().updatePriorityForTickets(ids.toList(), priority);
}
```

No confirmation dialog — unlike Delete (a `reversible`-tone
`showAppConfirmDialog`, since trashing is a structural, cascading
action worth pausing on), a bulk status/priority write is a plain field
edit with no cascade, matching how a single-ticket status/priority edit
today also has no confirmation step.

`TicketSelectionBar`'s call site in `build()` gains the two new
callbacks:

```dart
TicketSelectionBar(
  // ...existing params unchanged...
  onChangeStatus: (status) =>
      _bulkChangeStatus(context, selection.selectedIds, status),
  onChangePriority: (priority) =>
      _bulkChangePriority(context, selection.selectedIds, priority),
),
```

The existing `BlocListener<TicketsCubit, TicketsState>` gains two more
branches, mirroring the `TicketsBatchTrashed` one exactly:

```dart
listener: (context, state) {
  if (state is TicketsBatchTrashed) {
    AppToast.show(context, context.l10n.ticketBulkTrashSummaryToast(state.trashedCount));
    context.read<TicketSelectionCubit>().clear();
  } else if (state is TicketsBatchStatusUpdated) {
    AppToast.show(
      context,
      state.skippedCount > 0
          ? context.l10n.ticketBulkStatusSummaryWithSkippedToast(
              state.updatedCount,
              state.skippedCount,
            )
          : context.l10n.ticketBulkStatusSummaryToast(state.updatedCount),
    );
    context.read<TicketSelectionCubit>().clear();
  } else if (state is TicketsBatchPriorityUpdated) {
    AppToast.show(
      context,
      context.l10n.ticketBulkPrioritySummaryToast(state.updatedCount),
    );
    context.read<TicketSelectionCubit>().clear();
  }
},
```

## 10. Testing

- **`TicketDao` (`ticket_dao_test.dart`)** — `updateStatusByIds`/
  `updatePriorityByIds`: writes the given value to every id in the list,
  leaves other tickets untouched, bumps `updated_at`.
- **`DriftTicketRepository`** — thin passthrough, covered indirectly via
  the DAO test plus a `TicketsCubit` test mocking the repository (this
  project's existing convention: trivial passthroughs skip a dedicated
  repository test).
- **`TicketsCubit` (`tickets_cubit_test.dart`), via `bloc_test` +
  `mocktail`:**
  - `updateStatusForTickets` with target `inProgress`: a mixed selection
    (some blocked via `_isTicketBlocked`, some gated via
    `_codingExecutionGateCheck`, some clean) emits
    `TicketsBatchStatusUpdating` then `TicketsBatchStatusUpdated` with
    the correct `updatedCount`/`skippedCount` split; only the writable
    ids reach `updateStatusForIds`.
  - `updateStatusForTickets` with a non-`inProgress` target: no gate
    calls made at all, every id in the write.
  - `updateStatusForTickets`: git projection and coding-execution
    triggering fire only for successfully-written Task/Bug tickets
    moving to `inProgress`.
  - `updatePriorityForTickets`: unconditional write, `updatedCount`
    always equals `ids.length`, no git-projection call.
  - Repository-throws case for both methods emits `TicketsError`.
- **Widget level:** no new widget tests for `TicketSelectionBar`'s two
  new triggers or the new `BulkStatusMenu`/`BulkPriorityMenu`/
  `BulkOverlayRow` widgets — same rationale `tickets.md`'s existing
  "Known limitations" already documents for this `Overlay`-family of
  widgets (covered by a manual `flutter-web` pass in real Chrome
  instead, not automated widget tests, because of the `Overlay`/focus-
  listener class of bug that only surfaces interactively).

# Aion — Bulk Status & Priority Edit for Ticket Selection

Implementation-ready spec for the two new inline actions on `TicketSelectionBar`
(**Status**, **Priority**) and the two overlay menus they open. Companion
mockups: `Aion Bulk Status and Priority Mockups.dc.html`.

**Scope.** `TicketSelectionBar`'s updated action row + the `BulkStatusMenu`
and `BulkPriorityMenu` overlays, sharing one `BulkOverlayRow`. No new screens.
`TicketsListScreen`, `TicketListTile`/`TicketBoardCard`, and checkbox-selection
behavior are unchanged and out of scope.

**Hard constraint — non-Material.** Every visual is a plain Flutter primitive
(`DecoratedBox`, `Container`, `GestureDetector`, `CustomPaint`, `Row`, `Column`,
`Align`, `Padding`, `Focus`, `Overlay`/`OverlayEntry`, `CompositedTransformFollower`,
`AnimatedContainer`). No `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`,
`ColorScheme`, `ListTile`, `AppBar`, `SnackBar`, `DropdownButton`, `PopupMenuButton`,
`InkWell`, or any other Material widget/type anywhere.

  chosen so the longest label ("In Progress") plus dot plus padding fits without
  wrapping. No existing token defines a menu width, so this is a genuine gap.

## 1. `TicketSelectionBar` — updated action row

A floating, rounded, shadowed contextual bar that replaces the create-ticket FAB
while selection mode is active. Left → right: **Cancel** icon button ·
**count** label · flexible spacer · **Select-all** ghost text button ·
**Status** trigger · **Priority** trigger · **Delete** button.

The Status and Priority triggers are the only additions; Cancel, count,
Select-all, and Delete are unchanged and specified here only for layout context.

### 1.1 Bar container

- Widget: `DecoratedBox` wrapping `Padding` → `Row`.
- Fill: `AionColors.surface`.
- Border: `Border.all(color: AionColors.border, width: 1)`.
- Radius: `BorderRadius.circular(AionRadius.xl)` (16).
- Padding: `EdgeInsets.symmetric(horizontal: 12, vertical: 9)`.
- Shadow: single `BoxShadow(color: shadowColor, blurRadius: 44, spreadRadius: -14, offset: Offset(0, 20))`
  where `shadowColor` = Arctic `Color(0x38182E4A)` (≈ `rgba(24,46,74,0.22)`),
  Obsidian `Color(0x99000000)` (0.6). Express via `.withOpacity`.
- Row: `crossAxisAlignment: center`, children separated by `SizedBox(width: 10)`
  (`AionSpacing`-adjacent; use `10`). The spacer between count and Select-all is
  `Spacer()`.
- Mobile placement: `Positioned(left: 12, right: 12, bottom: 16)` over the list;
  desktop/tablet: same bar centered with `maxWidth: 620`.

### 1.2 Cancel icon button (context — unchanged)

- 32×32, `BorderRadius.circular(AionRadius.md)`, fill `surfaceHover`, glyph = ✕
  (`CustomPaint` two strokes, 16×16, `textSecondary`, width 2, round caps).

### 1.3 Count label (context — unchanged)

- `"$n selected"`, `AionText.button` (14/w700), color `textPrimary`.

### 1.4 Select-all / Deselect-all ghost button (context — unchanged)

- Text only, `AionText.button.copyWith(fontSize: 12.5)`, color `primary`,
  `EdgeInsets.symmetric(horizontal: 6, vertical: 7)`. Label toggles
  "Select all" ↔ "Deselect all".

### 1.5 Status trigger — NEW

`GestureDetector` → `Focus` → `AnimatedContainer` (150 ms) → `Row`.

- Dimensions: intrinsic width, height 32 (content-driven via padding).
- Padding: `EdgeInsets.symmetric(horizontal: 11, vertical: 7)`.
- Radius: `BorderRadius.circular(AionRadius.md)` (10).
- Layout: `Row(mainAxisSize: min)` — icon, `SizedBox(width: 6)`, label.
- Icon: bidirectional up/down arrows ("swap"), 15×15 `CustomPaint`, stroke 1.7,
  round caps/joins. Two vertical shafts, one arrow up on the left shaft, one
  arrow down on the right shaft.
- Label: `"Status"`, `AionText.button.copyWith(fontSize: 12.5)`.
- Only built when `selectedCount >= 1`; below that it is disabled (§1.7).

#### 1.5.1 Default
- Fill `surfaceHover`; border `Border.all(color: border, width: 1)`;
  icon + label `textSecondary`; no glow.

#### 1.5.2 Hover (pointer platforms)
- Fill `surfaceHover`; border `borderStrong`; icon + label `textPrimary`.

#### 1.5.3 Focused (keyboard)
- Fill `surfaceHover`; border `border`; icon `textSecondary`;
  focus ring `BoxShadow(color: primary.withOpacity(ringAlpha), spreadRadius: 3, blurRadius: 0)`
  where `ringAlpha` = 0.16 Arctic / 0.30 Obsidian. Ring is an outer shadow, not
  a border, so it never shifts layout.

#### 1.5.4 Pressed / active (menu open)
- Fill `primarySubtle`; border `Border.all(color: primary, width: 1)`;
  icon + label `primary`. This state persists while `BulkStatusMenu` is open.

#### 1.5.5 Disabled (0 selected)
- Fill `Color(0x00000000)`; border `border`; icon + label `textMuted`;
  `Opacity(0.4)`; `GestureDetector.onTap: null`; excluded from focus traversal.

### 1.6 Priority trigger — NEW

Identical structure, states, dimensions, padding, and radius as §1.5. Only the
icon and label differ:
- Icon: **flag** glyph, 15×15 `CustomPaint`, stroke 1.7 — a vertical pole with a
  pennant. Uses the same `currentColor`-style tint as its state (not a priority
  color; the trigger is value-agnostic).
- Label: `"Priority"`.
- All state tables in §1.5.1–1.5.5 apply verbatim.

### 1.7 Delete button (context — unchanged)

- Fill `danger`; text/icon `#FFFFFF`; `AionText.button.copyWith(fontSize: 12.5)`;
  `EdgeInsets.symmetric(horizontal: 13, vertical: 8)`; radius `AionRadius.md`;
  trash icon 14×14. Disabled (0 selected): fill `surfaceHover`, content
  `textMuted`, `Opacity(0.7)`.

### 1.7b Compact breakpoint — icon-only triggers (mobile)

Below `kBarCompactWidth` (bar available width < ~360, i.e. phone) the Status and
Priority triggers drop their text labels and render as 34×34 square icon buttons
so all seven controls fit the floating bar:

- Dimensions: 34×34, `BorderRadius.circular(AionRadius.md)` (10).
- Glyph only (swap / flag), 16×16, centered; no label, no horizontal text padding.
- State colors are identical to §1.5.1–1.5.5 (default `surfaceHover`/`border`/
  `textSecondary`; active `primarySubtle`/`primary`/`primary`; etc.).
- The count label also compacts to the bare number `"$n"`; Select-all keeps its
  text. Delete keeps its label.
- Overlays open exactly as §2/§3; on mobile they anchor `right: 0` to the trigger
  so the panel stays inside the screen edge (`followerAnchor` mirrored
  accordingly). Everything else is unchanged.

Implement as a single `LayoutBuilder` switch on available width — same widget,
label visibility gated by the breakpoint; no separate component. Mockup: **5a**.

### 1.8 Trigger — theme differences

Structurally identical across Arctic and Obsidian; only the token *values* differ
(see §0.1). No per-theme layout, radius, or padding changes.

## 2. `BulkStatusMenu` — overlay

Opens on Status-trigger tap via `Overlay.of(context).insert(OverlayEntry(...))`
positioned with a `CompositedTransformFollower` targeting the trigger's
`LayerLink`. Opens **upward** (`targetAnchor: topCenter`,
`followerAnchor: bottomCenter`, `offset: Offset(0, -8)`) because the bar floats
near the bottom; if the trigger sits low enough that the panel would clip the top
edge, flip to downward with the mirrored anchors. A full-screen transparent
`GestureDetector` behind the panel dismisses on outside tap.

### 2.1 Panel

- Widget: `DecoratedBox` → `Padding(EdgeInsets.symmetric(vertical: 6))` → `Column(mainAxisSize: min)`.
- Fill `AionColors.surface`.
- Border `Border.all(color: borderStrong, width: 1)`.
- Radius `BorderRadius.circular(AionRadius.lg)` (12).
- Width: `ConstrainedBox(minWidth: 200, maxWidth: 240)`; height content-driven.
- Shadow: `BoxShadow(color: menuShadow, blurRadius: 48, spreadRadius: -16, offset: Offset(0, 22))`
  — `menuShadow` Arctic `Color(0x47182E4A)` (0.28), Obsidian `Color(0xB3000000)` (0.7).
- Clip: `ClipRRect` (`overflow: hidden` equivalent) so row fills/rings stay inside
  the radius.
- Optional eyebrow (recommended, shown in mockup): first child is a
  `Padding(EdgeInsets.fromLTRB(13, 5, 13, 7))` with text `"Set status"`,
  `AionText.caption` size 10, color `textMuted`.

### 2.2 Rows

One `BulkOverlayRow` (§4) per status, in fixed order:
**Backlog · To Do · In Progress · In Review · Done · Cancelled**.

Each row carries a small leading status dot (8×8 circle) using the app's existing
status-dot mapping:

| Status | Dot color |
|---|---|
| Backlog | `textMuted` |
| To Do | `secondary` |
| In Progress | `primary` |
| In Review | `warning` |
| Done | `success` |
| Cancelled | `danger` |

Selecting a row calls `applyStatusToSelection(status)` and closes the overlay.

### 2.3 Auto-focus

On open, the **first row (Backlog)** receives keyboard focus and renders in the
`focused` state (§4.3) — a `primarySubtle` fill plus an inset primary ring, which
is visually distinct from plain hover. Arrow keys move focus; Enter/Space commit;
Esc dismisses without applying.

## 3. `BulkPriorityMenu` — overlay

A matched pair with `BulkStatusMenu`: **same panel chrome, same row component,
same shadow, same open/dismiss/focus behavior**. Only the row set and the leading
glyph differ. Everything in §2.1 and §2.3 applies verbatim (eyebrow text is
`"Set priority"`).

### 3.1 Rows

One `BulkOverlayRow` per priority, in fixed order:
**Critical · High · Medium · Low · None**.

Leading indicator is a 10×10 rounded square (`BorderRadius.circular(3)`) filled
with the existing priority foreground accent:

| Priority | Indicator |
|---|---|
| Critical | fill `priority.critical.fg` |
| High | fill `priority.high.fg` |
| Medium | fill `priority.medium.fg` |
| Low | fill `priority.low.fg` |
| None | `Color(0x00000000)` fill + `Border.all(color: borderStrong, width: 2)` (hollow) |

Selecting a row calls `applyPriorityToSelection(priority)` and closes the overlay.

## 4. `BulkOverlayRow` — shared row component

One component used by both menus. `GestureDetector` → `Focus` →
`AnimatedContainer(100 ms, curve: easeOut)` → `Row`.

- Height: 36 (content-driven).
- Padding: `EdgeInsets.symmetric(horizontal: 13, vertical: 9)`.
- Layout: `Row` — leading indicator (dot 8×8 for status / square 10×10 for
  priority), `SizedBox(width: 10)`, label `Expanded`.
- Label: `AionText.bodySm.copyWith(fontWeight: FontWeight.w600)`, color `textPrimary`.
- Corners: rows are square; the panel's `ClipRRect` rounds the outermost rows.
- No per-row border. Fill changes carry every state.

`fillAlpha` = 0.11 Arctic / 0.16 Obsidian.

### 4.1 Default
- Fill `Color(0x00000000)`; label `textPrimary`; indicator at full color.

### 4.2 Hover (pointer)
- Fill `surfaceHover`; label `textPrimary`.

### 4.3 Focused (keyboard — also the auto-focused first row)
- Fill `primarySubtle`; inset ring
  `Border.all(color: primary, width: 2)` drawn *inside* the row via a
  `DecoratedBox(position: DecorationPosition.foreground)` (so it reads as an inset
  ring, not an outer glow) **or** `BoxShadow` with `spreadRadius: -2` +
  `inset`-style foreground decoration. Distinct from plain hover by both the
  primarySubtle fill and the ring.

### 4.4 Pressed
- Fill `primary.withOpacity(fillAlpha)`; label `textPrimary`. Deepest of the
  neutral progression; reverts to hover/focused on pointer up.

### 4.5 Disabled
- Not applicable — every status/priority value is always selectable. (Row has no
  disabled state; if a future filter needs one, use `Opacity(0.4)` +
  `onTap: null`, matching §1.5.5.)

### 4.6 Error
- Not applicable at row level. If `applyStatusToSelection` /
  `applyPriorityToSelection` fails, surface it on the bar (e.g. a transient
  inline message built from `danger`), not inside the closed overlay.

### 4.7 Theme differences
Structurally identical across themes; only token values differ. `fillAlpha`
differs (0.11 vs 0.16) as noted.

## 5. Interaction summary

1. Selection reaches ≥ 1 ticket → Status and Priority triggers enable (§1.5.5 → §1.5.1).
2. Tap **Status** → trigger enters active state (§1.5.4), `BulkStatusMenu` opens
   upward, Backlog auto-focused (§2.3).
3. Tap a status row (§4) → `applyStatusToSelection`, overlay closes, trigger
   returns to default. Same flow for **Priority** → `BulkPriorityMenu`.
4. Outside tap / Esc → overlay closes with no change, trigger returns to default.
5. Only one overlay open at a time; opening one closes the other.
