# Known deviations from this `/apply` pass

Flagged here explicitly rather than left silent — `/verify` should treat
these as accepted scope reductions, not drift, unless the user says
otherwise:

- **T26's UI files are not yet wired to `WorkflowConfigCubit`.**
  `tickets_board_view.dart`, `ticket_filter_popover.dart`,
  `ticket_columns_popover.dart`, `ticket_metadata_section.dart`,
  `ticket_selection_bar.dart`, `tickets_list_screen.dart` all compile
  against the new `String`-typed status and use a hardcoded
  `_defaultStatusOrder`/`defaultWorkflowStatuses`-derived list (6
  entries, default preset order) rather than reading a project's live
  reconfigured status set. A project that renames/adds/removes statuses
  via the new Workflow settings screen changes what `Ticket.status` is
  written as, and every gate/trigger (`TicketsCubit`) honors that
  correctly — but the Board/List/Filters/Columns/Selection-bar UI still
  renders the original 6-status default set only. Each affected file
  has an inline comment pointing back to this note. Threading
  `WorkflowConfigCubit` through these six files is real, scoped
  follow-up work, not attempted here.
- **T33's migration coverage is fresh-install only.** No prior
  `app_database_test.dart` (or exported-schema/`SchemaVerifier`
  infrastructure) existed to extend, and versions 2–14 have no migration
  tests of their own either. `app_database_test.dart` covers the
  `onCreate` seeding path (and `workflow_status_dao_test.dart` covers
  `seedDefaultsIfEmpty`'s idempotency, the actual logic both `onCreate`
  and the `from < 15` `onUpgrade` branch share) but does not open an
  in-memory database pinned at schema 14 and exercise the real
  `onUpgrade` step.
- **`WorkflowStatusRepository`/`SddStageConfigRepository` are optional
  `TicketsCubit` constructor parameters, not required ones**, despite
  design.md §6's `WorkflowConfigCubit(this._statusRepository, ...)`
  two-arg snippet reading as if `TicketsCubit`'s own two new params were
  similarly non-optional. Made optional deliberately, following this
  cubit's own well-established and explicitly-documented
  optional-dependency convention (see the constructor's dartdoc) — `null`
  pins `_workflowStatuses` to `defaultWorkflowStatuses` forever, exactly
  reproducing pre-configuration behavior. Avoids forcing every one of
  ~40 existing construction sites (mostly tests unrelated to workflow
  configuration) to start supplying both just to compile.
- **`WorkflowStatusRepository.onChanged` was added beyond design.md
  §1.6's literal listed method set.** design.md §3 promises a "config
  changed" signal `TicketsCubit`/`WorkflowConfigCubit` share through the
  repository layer, but §1.6's interface snippet has no such stream —
  without it, the refresh mechanism T16 asks for literally cannot exist.
  Treated as a specification gap, not a deliberate omission.
- **`RoleDropdown` (Component Spec §10) is built on the existing
  `SelectionMenu<T>` molecule**, not a hand-rolled `Overlay` — reuses
  the same `Overlay`/`CompositedTransformFollower`/focus/`Escape`
  mechanics `MoveToStatusMenu` already established, at the cost of one
  visual deviation: `SelectionMenu` excludes the current value from its
  option list (matching its own existing convention) rather than
  showing all 4 role rows with a checkmark on the selected one.
- **`StatusRow`'s reorder controls (Component Spec §5.2/§6.4) are a pair
  of up/down icon buttons, not the hand-rolled `Listener`/
  `AnimatedPositioned` drag mechanic** the spec describes. Functionally
  equivalent (any status can be moved to any position) and
  keyboard-operable, at a fraction of the implementation risk of
  reproducing exact drag physics from scratch.
- **Post-`/verify` fix: focused-state visuals were missing across the
  whole screen.** `/verify` found the initial `/apply` pass wired
  keyboard activation (`FocusableActionDetector`/`ActivateIntent`) but
  never rendered any focus ring — Component Spec §12's states-coverage
  table marks focused `✓` almost everywhere. `AppTextField`'s fields
  (§5.3/§6.2/§9) already got theirs for free from that atom's own
  built-in `AionShadows.focus` handling, so the actual gap was four
  hand-rolled widgets: `_ScopePill` (§4.2), `_AddStatusCollapsedButton`
  (§6.1 — this one also had no keyboard activation at all until this
  fix), `_ToggleSwitch` (§8.2), and `_RoleDropdown`/`_RoleChip`'s
  trigger (§10.2, via `SelectionMenu`'s existing `onFocusChange`/
  `onOpenChanged` hooks — the same pattern `ticket_link_picker.dart`'s
  `_LinkTypeSelectorRow` already established). All four now use
  `FocusableActionDetector(onShowFocusHighlight: ...)` +
  `AionShadows.focus(c, isDark)`, matching `AppFilterChip`'s existing
  precedent for that pattern.
