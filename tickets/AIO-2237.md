# Design: Ticket-graph and embedding context enrichment for spawned chats

## 1. New class: `TicketContextEnricher`

`lib/features/tickets/presentation/cubit/ticket_context_enricher.dart` —
placed alongside `TicketRollupRecomputer`/`TicketEstimationSuggester`,
the two existing "orchestrator classes `TicketsCubit` constructs once and
delegates a self-contained walk to" (per `project.md`'s Cubit-owns-
domain-logic convention: this is judgment logic — what counts as
"related enough" — not a pure data-access concern, so it stays out of
`data/repositories/`).

```dart
class TicketContextEnricher {
  TicketContextEnricher(
    this._repository, {
    TicketLinkRepository? linkRepository,
    EmbeddingProvider? embeddingProvider,
  }) {
    _linkRepository = linkRepository;
    _embeddingProvider = embeddingProvider;
  }

  final TicketRepository _repository;
  late final TicketLinkRepository? _linkRepository;
  late final EmbeddingProvider? _embeddingProvider;

  static const _similarityThreshold = 0.75;
  static const _maxSimilarTickets = 5;
  static const _descriptionSnippetLength = 400;

  Future<String> relatedTicketsSection(Ticket ticket) async { ... }
}
```

Mirrors `TicketEstimationSuggester`'s constructor shape exactly
(required repository, optional collaborators via named parameters,
`late final` backing fields) so the two orchestrator classes read as the
same family.

### 1.1 `relatedTicketsSection(Ticket ticket)`

Returns a `## Related tickets` Markdown block, or `''` (empty string) if
there is nothing to add — every call site checks for an empty return and
skips appending the section header entirely, so a ticket with no parent,
no links, and no embedding provider configured produces exactly today's
output, unchanged.

Algorithm:

1. **One bulk read**: `await _repository.getAllTickets()`, indexed into
   `Map<String, Ticket> byId`. Mirrors `TicketEstimationSuggester._run`'s
   own `getAllTickets()` call and `TicketRollupRecomputer`'s `byId` map —
   both existing precedent for "one full-table read, then walk it
   in-memory" at this app's personal scale. Serves both the parent-chain
   walk and the embedding scan below with a single query.

2. **Structured walk — ancestor chain.** Starting from
   `ticket.parentId`, walk `byId` upward:

   ```dart
   final structuredIds = <String>{};
   final ancestors = <Ticket>[];
   var current = ticket.parentId == null ? null : byId[ticket.parentId];
   while (current != null && structuredIds.add(current.id)) {
     ancestors.add(current);
     final parentId = current.parentId;
     current = parentId == null ? null : byId[parentId];
   }
   ```

   Identical shape to `TicketRollupRecomputer`'s existing ancestor walk
   (`while (current != null && chainIds.add(current.id))`) — the `Set
   .add`'s boolean return doubles as both dedup and cycle guard, so a
   corrupted/cyclic `parentId` chain (shouldn't happen, but not assumed)
   terminates instead of looping forever. `ancestors` ends up ordered
   nearest-parent-first.

3. **Structured walk — direct links.** If `_linkRepository` is non-null:
   `await _linkRepository.getLinksForTicket(ticket.id)`, resolve each
   row's *other* ticket id through `byId`, and record `(other, type)`
   where `type` is the row's `linkType` as read from `ticket`'s side —
   `link.linkType` unchanged when `ticket` is the row's source,
   `link.linkType.inverse` when `ticket` is the target (same
   perspective-flip `TicketLinkTypeRelative.inverse` already provides,
   used today by the linked-tickets UI). Every resolved other ticket's id
   is added to `structuredIds` so step 4 doesn't re-surface it. A link
   row whose other id isn't in `byId` (defensive — shouldn't happen,
   `getAllTickets()` and `getLinksForTicket` read the same table) is
   silently skipped, not an error.

4. **Embedding-similarity walk.** If `_embeddingProvider` is non-null:

   ```dart
   final queryVector = await _embeddingProvider.embed(
     '${ticket.title}\n\n${ticket.description ?? ''}',
   );
   final scored = <(Ticket, double)>[
     for (final other in byId.values)
       if (other.id != ticket.id &&
           !structuredIds.contains(other.id) &&
           other.embedding != null)
         (other, cosineSimilarity(queryVector, other.embedding!)),
   ]..sort((a, b) => b.$2.compareTo(a.$2));
   final similar = scored
       .where((entry) => entry.$2 >= _similarityThreshold)
       .take(_maxSimilarTickets)
       .map((entry) => entry.$1)
       .toList();
   ```

   Same `cosineSimilarity`/scan/sort/take shape as
   `TicketEstimationSuggester._run` and `TicketDocumentSearchService
   .search` — no new similarity primitive, reuses
   `domain/utils/embedding_similarity.dart`'s existing
   `cosineSimilarity`. Threshold-first (only include tickets that are
   genuinely similar; zero results is a valid, expected outcome for a
   ticket with no comparable siblings yet), with the top-K `take` purely
   as a safety cap on an unusually crowded threshold match — not a fixed
   quota that always fires. Excludes every ticket type restriction the
   existing `TicketDocumentSearchService` has (`page`/`resource` only):
   this walk scans every live ticket type, since a Task's most relevant
   sibling is just as likely to be another Task or Story as a
   documentation Page.

5. **Render.** If `ancestors`, the structured links, and `similar` are
   all empty, return `''`. Otherwise build:

   ```
   ## Related tickets

   - Epic — "<ancestor title>" (no description)
   - Story — "<nearer ancestor title>": <snippet>
   - blocks — "<title>": <snippet>
   - blockedBy — "<title>": <snippet>
   - relatesTo — "<title>": <snippet>
   - similar — "<title>": <snippet>
   ```

   Ancestors render nearest-first (`ancestors` is already in that
   order) with their `TicketType` as the relationship label (matches
   how `_assembleStageContext`'s existing `verifying`/`archived` branch
   already labels children by type name, e.g. `## Tasks`/`## Stories`);
   linked tickets render with their resolved `TicketLinkType.name`;
   embedding matches render as `similar`. One bullet per ticket, in that
   fixed section order (ancestors → links → similar) — stable output,
   easy to eyeball in a real transcript during manual testing.

   Each bullet's snippet is
   `other.description` truncated to `_descriptionSnippetLength`
   characters (`'${text.substring(0, cap)}…'` when longer), or the
   literal `(no description)` when `other.description` is `null` or
   empty — bounds how much any single related ticket can inflate the
   prompt, addressing the idea file's open "context-size budget"
   question without introducing a global token-counting mechanism this
   app has no other precedent for.

## 2. Wiring into `TicketsCubit`

Constructed once in the constructor body, next to `_estimationSuggester`:

```dart
_contextEnricher = TicketContextEnricher(
  _repository,
  linkRepository: linkRepository,
  embeddingProvider: embeddingProvider,
);
```

```dart
late final TicketContextEnricher _contextEnricher;
```

### 2.1 `_assembleExecutionContext`

After the title/description block, before the `## Project conventions`
block:

```dart
final related = await _contextEnricher.relatedTicketsSection(task);
if (related.isNotEmpty) {
  buffer
    ..writeln()
    ..writeln(related);
}
```

### 2.2 `_assembleStageContext`

After the title/description block (`buffer.writeln('# ${parent.title}')`
+ description), before the stage-`switch` that adds each stage's own
extra section:

```dart
final related = await _contextEnricher.relatedTicketsSection(parent);
if (related.isNotEmpty) {
  buffer
    ..writeln()
    ..writeln(related);
}
```

Because `retryDesignSync` calls `_assembleStageContext(parent,
SddStage.designSync)` directly — no parallel context-building logic of
its own — this single edit covers all three existing callers
(`_createStageChat`, `_runStageChatTurn`, `retryDesignSync`) with no
further changes needed anywhere else in `tickets_cubit.dart`.

## 3. Dartdoc updates

Both `_assembleExecutionContext`'s and `_assembleStageContext`'s
existing dartdoc comments currently state their context is plain-text
title/description only (`_assembleStageContext`'s literally says "No
embeddings, no repo-map-lite involvement"). Both get updated to describe
the new `## Related tickets` section and reference
`TicketContextEnricher.relatedTicketsSection`, per this project's
documentation rule (public/documented behavior must stay accurate, not
just newly-written code).

## 4. Testing

New unit tests for `TicketContextEnricher.relatedTicketsSection`
(fixture repository + fake `TicketLinkRepository`/`EmbeddingProvider`,
consistent with this codebase's existing Cubit/orchestrator test style):

- No parent, no links, no embedding provider → `''`.
- Ancestor chain of depth > 1 renders nearest-first, each with its type
  label.
- A cyclic `parentId` chain (defensive fixture) terminates instead of
  looping.
- Each stored `TicketLinkType` renders correctly from both the source
  and the target side (i.e. `inverse` is applied correctly).
- A similarity match below `_similarityThreshold` is excluded; one at or
  above it is included.
- A ticket already surfaced by the structured walk is never duplicated
  in the `similar` section even if it also scores above the threshold.
- More than `_maxSimilarTickets` matches above threshold are capped.
- A description longer than `_descriptionSnippetLength` is truncated
  with a trailing `…`; a `null`/empty description renders
  `(no description)`.

Existing `_assembleExecutionContext`/`_assembleStageContext` tests get
one new case each asserting the `## Related tickets` section appears
when `TicketContextEnricher` returns non-empty content, and is absent
when it returns `''` (preserving today's exact output for a ticket with
no graph context).
