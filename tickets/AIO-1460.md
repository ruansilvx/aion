  **Follow-up (post-T50 session): the one issue above — fixed.**
  Root-caused: `BoardColumn`'s per-column `ListView.separated`
  (`tickets_board_view.dart`) built each `TicketBoardCard` with no
  `key:`, relying on Flutter's positional default. `TicketBoardView`
  groups its flat ticket list into one filtered sublist per status —
  moving a Task/Bug between columns (a status change) shortens one
  column's sublist and lengthens another's, entirely inside the
  *same*, never-recreated `BoardColumn`/`ListView` Element (the
  ancestor `TicketsListScreen._TicketsBody`'s `KeyedSubtree`, keyed on
  the flat list's `id`-and-order, doesn't change for a pure status
  flip, since that flip doesn't touch the flat list's order — so it
  never remounts the board subtree and never rescues this). Without a
  key, Flutter's default reconciliation can silently reuse one
  ticket's card Element/State — its `context.select` subscriptions,
  its `MoveToStatusMenu`/`SelectionMenu` Overlay+`LayerLink` state, its
  `_BoardCardStatusBadge` `AnimationController` — for a *different*
  ticket that lands in the same list slot, which is exactly the class
  of bug this error trio (`RenderFlex overflowed`/`Duplicate
  GlobalKey`/`'_dependents.isEmpty'`) is a known Flutter symptom of.
  Concurrent scheduling raising how often several Tasks change status
  back-to-back is what made this far more reachable than it was under
  the old strict-FIFO one-at-a-time queue. **Fix:** key each
  `TicketBoardCard` on `ValueKey(ticket.id)` in `BoardColumn`'s
  `itemBuilder` — the same fix this codebase already applies to
  `TicketsListScreen`'s own list (via its `KeyedSubtree`) for the
  identical class of problem, just scoped per-card instead of
  per-screen. Regression coverage added in
  `tickets_board_view_test.dart`: two `testWidgets` cases drive a mocked
  `TicketsCubit` through several/collapsed `TicketsLoaded` emissions
  that move tickets across columns (one gradually, one as a single
  large jump with a mid-spin `running` badge in flight) under Hybrid's
  `clusterSiblingsAdjacently` reordering, asserting no framework
  exception and that every ticket renders exactly once afterward.
  Caveat: these tests pass both with and without the fix — they
  exercise the real vulnerable code path (confirmed by reasoning through
  `TicketsCubit`'s actual emission shape) but did not themselves trip
  the exact historic assertions, which likely also depend on live
  animation-ticker/gesture timing `flutter test`'s synchronous harness
  doesn't reproduce. If the original crash recurs live, treat it as
  still open and escalate to a DevTools-attached session rather than
  assuming this fix alone was insufficient.
