# T24. Manual interactive pass on a **native desktop build**

(`flutter run -d windows --release`, then the built `aion.exe`
directly) — this feature is desktop-only (`dart:io Process`), so the
usual real-Chrome pass doesn't exercise it at all.
**Verified live** (screenshots captured via Win32 automation —
`SetWindowPos`/`mouse_event`/`CopyFromScreen`, no browser involved):
after `cd agent_bridge && npm install` (real install — see below),
opened Settings from the secondary-actions popover (now showing
"Switch Project"/"Trash"/**"Settings"**, gear-free plain row per
design.md §8's "existing row style already covers this"); the
connection test ran automatically on open, showing `CHECKING`
(spinner) then resolving to `NOT CONNECTED` with the real bridge
error text `"Invalid API key · Please run /login"` (this sandboxed
environment has no Claude plan auth — an accurate result, not a
bug); manually re-tested via "Test Connection" (button correctly
disabled during `checking`); switched the model dropdown to
"Haiku 4.5" (all three items render correctly; selecting one
immediately re-triggers a connection test against the new model,
clearing the previous status message during `checking`); killed the
process and relaunched the built `aion.exe` directly — "Haiku 4.5"
was still selected on the fresh launch, confirming
`SharedPrefsAgentSettingsRepository` persistence; temporarily
renamed `agent_bridge/index.mjs` to simulate a broken bridge path and
re-tested — the app **did not crash**, stayed fully responsive, and
showed `NOT CONNECTED` with Node's raw `MODULE_NOT_FOUND` stack
trace as the status message (restored the file immediately after).
**Real npm install caught two real SDK-integration bugs**, both
fixed and re-verified against the actual installed
`@anthropic-ai/claude-agent-sdk@0.1.77` package (not guessed from
its public docs):
1. `agent_bridge/index.mjs`'s failed-`result`-message branch read a
nonexistent `message.result` field — the real
`SDKResultMessage` failure variant carries `errors: string[]`
instead. Fixed.
2. An authentication failure surfaces as an `assistant` message with
a structured `error: 'authentication_failed'` field *and* text
content, but the SDK can still emit a **later, misleading**
`result` message reporting `subtype: 'success'` with that same
text as its `result` field (confirmed via a throwaway debug
script against the live SDK, not documented anywhere). Fixed two
ways: `index.mjs` now emits `error` immediately whenever
`message.error` is set on an assistant message (any value, not
just `rate_limit`/`billing_error`), and `ClaudeAgentSdkClient`
now only honors the **first** terminal event in a stream and
ignores everything after — hardening `AgentEvent`'s "exactly one
terminal event" contract against this kind of out-of-order
signal regardless of bridge/SDK behavior. Also switched the
overage signal from a keyword-heuristic guess to the SDK's own
structured `error_max_budget_usd` result subtype, confirmed to
exist in the real type definitions.
**Not verified live:** an actual successful `connected` result
against a real authenticated Claude plan (this sandboxed environment
has none) — the `disconnected` and `checking` paths were verified
live instead, and the `connected` path's rendering was already
confirmed structurally via T13/T14's `ProviderConnectionBadge`
states in earlier code review. `agent_bridge/index.mjs`'s
`AgentOverageDetectedEvent` path (`error_max_budget_usd`) was
verified against the SDK's type definitions but not exercised live —
reaching an actual plan budget ceiling wasn't practical to trigger
for this pass. Recommend a follow-up live check once used against a
real, authenticated Claude plan. `flutter run` process and the app
window were stopped at the end of the pass.
