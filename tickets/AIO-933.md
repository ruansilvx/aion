## MODIFIED — Git projection (`#git-projection`)

**Current text** (as left by `trash-restore-git-projection`):

> On a desktop project (`WorkspaceShell`'s `rootPath != null` gate —
> see `projects.md`), four ticket events each attempt to write a
> Markdown file to `<project rootPath>/tickets/<ticketId>.md` and
> commit it via `core/git/git_repository_client.dart`'s
> `GitRepositoryClient` (`init`/`add`/`hasChanges`/`commit`, wrapping
> `Process.run('git', ...)`): ticket created, status changed, moved to
> trash, restored from trash. `TrashCubit` receives the same
> `TicketGitProjector`/`rootPath` pair `TicketsCubit` does (provided by
> `WorkspaceShell`, consumed the same way `InboxCubit` already consumes
> its own git fields), and `restore(id)` projects only the
> explicitly-restored ticket — not any currently-trashed
> ancestors/descendants `restoreTicket` also revives, matching
> `trashTickets`' existing scope for the symmetric trash-side case.
> Content edits via `updateTicket` do not trigger a commit — only the
> four events above do, so editing a ticket doesn't produce a commit
> per keystroke-adjacent save.
>
> **The "moved to trash" and "restored from trash" events currently
> never produce a visible commit in practice**, despite being wired:
> `TicketGitProjector.project` skips its `git commit` whenever
> `GitRepositoryClient.hasChanges` reports no working-tree diff, and
> neither event changes anything `TicketMarkdownSerializer` actually
> serializes (`deletedAt` isn't a frontmatter field; `updatedAt` isn't
> touched by trash or restore) — so the file it (re)writes is
> byte-identical to what's already committed, and the commit is
> silently skipped every time. Only "created" and "status changed"
> reliably produce a commit today. See [Known gaps](#known-gaps).

## MODIFIED — Known gaps

**Current bullet (removed):**

> - Neither the "moved to trash" nor the "restored from trash"
>   git-projection event produces a visible commit in practice, even
>   though both are wired. `TicketGitProjector.project` skips
>   `git commit` whenever the serialized Markdown hasn't changed, and
>   neither event changes any serialized field. Confirmed via a real
>   project's git history containing zero "trashed"-labeled commits
>   ever, despite the trash→restore round trip's UI-visible behavior
>   being independently verified as correct. A follow-up change needs
>   to pick a fix (e.g. serialize `deletedAt`, bump `updatedAt` on
>   trash/restore, or let `TicketGitProjector` force-commit specific
>   event labels regardless of `hasChanges`) — diagnosed in
>   `trash-restore-git-projection`'s `tasks.md` (T4) and
>   `verify-report.md`.

Deleted — the gap it describes is fully closed by this change.

**New bullet (added):**

> - `TicketMarkdownReconciler` never applies a hand-edited `deletedAt`
>   change from a `resource`/`page` file back into the database, for
>   the same reason it never applies a hand-edited `parentId`:
>   `TicketRepository.trashTicket`/`.restoreTicket` carry cascade logic
>   a bare field write would bypass. `deletedAt` only round-trips
>   through parsing for `TicketDbReconstructionService`'s benefit (which
>   builds a fresh `Ticket` with no existing row to protect).
