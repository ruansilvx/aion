# `TicketsCubit` — attachment firing

- [x] T14. `presentation/cubit/tickets_cubit.dart` — constructor gains
      optional `WorkflowSkillAttachmentRepository`/
      `WorkflowPromptTemplateRepository` parameters, following
      `WorkflowStatusRepository`'s own optional-dependency convention;
      new field `_skillAttachments` (`List<SkillAttachment>`, defaults
      to `const []`, loaded once at construction, refreshed on
      `WorkflowSkillAttachmentRepository.onChanged`); private helpers
      `_attachmentForStatus(String workflowStatusId)`/
      `_attachmentForStage(SddStage stage)` (design.md §3.1). Dartdoc
      both helpers and the refresh mechanism, mirroring `_workflowStatuses`'s
      existing doc style.
- [x] T15. Same file — new private methods `_promptFor(SkillAttachment,
      Ticket)` (renders a `WorkflowPromptTemplate` via
      `renderWorkflowPromptTemplate`, or builds `/<skillName>`) and
      `_fireSkillAttachment(Ticket parent, SkillAttachment attachment)`
      (spawns a chat ticket, posts `_promptFor`'s result as a system
      comment, runs it via `ChatCubit.runChatTurn` with
      `toolsEnabled`/`workingDirectory` set per design.md §3.2's table;
      catches a hard error into a "Skill attachment failed: <e>" system
      comment, mirroring `_runStageChatTurn`'s catch-comment shape).
      Full dartdoc citing `_createStageChat`/`_runStageChatTurn` as the
      shape this generalizes.
- [x] T16. Same file — new field `_pendingSkillAttachments`
      (`Map<String, SkillAttachment>`, keyed by ticket id) and private
      method `_resolveAndFireAttachment(Ticket parent, SkillAttachment
      attachment)` implementing the three-way confidence branch (design.md
      §3.3): `auto` fires `_fireSkillAttachment` unawaited immediately;
      `gated` records the pending entry and re-emits `TicketDetailLoaded`
      with `pendingSkillAttachment` set if the ticket's detail screen is
      open (mirrors `_refreshDetailIfOpenAndAffected`'s existing
      pattern); `manual` no-ops. New public methods
      `confirmPendingSkillAttachment(String ticketId)` (fires the
      pending attachment, clears the map entry),
      `rejectPendingSkillAttachment(String ticketId)` (clears the map
      entry, never fires), and `runAttachedSkillManually(Ticket ticket)`
      (resolves the ticket's current status/stage attachment; no-ops
      unless its confidence is `manual`). Full dartdoc on all four,
      citing `confirmPendingToolProposal`/`rejectPendingToolProposal`
      as the existing pattern this mirrors.
- [x] T17. Same file — `updateTicketStatus`/`updateStatusForTickets`:
      after a successful status write, resolve `_resolveStatus(status)?.id`
      and call `_attachmentForStatus`; if non-`null`, call
      `_resolveAndFireAttachment` (design.md §3.4). Symmetric to, and
      independent of, the existing `executionTrigger`-role check.
- [x] T18. Same file — `_createStageChat`/`_runStageChatTurn`: add a
      leading check for `_attachmentForStage(stage)`; when non-`null`,
      `_promptFor`'s output replaces `_assembleStageContext(parent,
      stage)`'s hardcoded prompt, and firing routes through
      `_resolveAndFireAttachment` instead of `advanceSddStage`'s
      existing unconditional `unawaited` call (design.md §3.4). When
      `null`, behavior is byte-for-byte identical to before this change
      — verify no regression against Phase 1's existing stage-advance
      call path.
- [x] T19. `presentation/cubit/tickets_state.dart` —
      `TicketDetailLoaded` gains a `pendingSkillAttachment`
      (`SkillAttachment?`) field, default `null`; update its
      constructor, `props`, `copyWith`, and dartdoc.
