# Design: Fix the ticket → git projection gap

## Architecture overview

```
                         (desktop, rootPath != null)
TicketsCubit / TrashCubit / TicketParentTrashService / TicketMarkdownReconciler / TicketRepairService
                         │  all depend on the TicketRepository INTERFACE only
                         ▼
              RepositoryProvider<TicketRepository>   ← the one place this changes
                         │
        ┌────────────────┴────────────────┐
        │ rootPath == null (mobile/web)    │ rootPath != null (desktop)
        ▼                                  ▼
  DriftTicketRepository            GitProjectingTicketRepository
                                      wraps → DriftTicketRepository
                                      + TicketGitProjector, rootPath
```

Nothing above `RepositoryProvider<TicketRepository>` changes. Every
consumer keeps calling plain `TicketRepository` methods; the decorator
is invisible to them by construction (the whole point of coding
against an interface). This is the same shape the project already
uses for `TicketParentTrashService`/`TicketRollupRecomputer` sharing
one service across two callers — a decorator implementing the domain
interface it wraps, one layer above the persistence implementation.

## New: `GitProjectingTicketRepository`

`lib/features/tickets/data/repositories/git_projecting_ticket_repository.dart`

```dart
class GitProjectingTicketRepository implements TicketRepository {
  GitProjectingTicketRepository(this._inner, this._projector, this._rootPath);

  final TicketRepository _inner;
  final TicketGitProjector _projector;
  final String _rootPath;

  // Every read method and every non-projected write method: pure
  // pass-through, one line each — `Future<X> foo(...) => _inner.foo(...);`.

  @override
  Future<void> createTicket(Ticket ticket) async {
    await _inner.createTicket(ticket);
    unawaited(_project(ticket.id, 'created'));
  }

  @override
  Future<void> updateTicketStatus(String id, String status) async {
    await _inner.updateTicketStatus(id, status);
    unawaited(_project(id, 'status-changed'));
  }

  @override
  Future<void> updateStatusForIds(List<String> ids, String status) async {
    await _inner.updateStatusForIds(ids, status);
    for (final id in ids) {
      unawaited(_project(id, 'status-changed'));
    }
  }

  @override
  Future<void> updateTicketSddStage(String id, SddStage stage) async {
    await _inner.updateTicketSddStage(id, stage);
    unawaited(_project(id, 'stage-changed'));
  }

  @override
  Future<void> updateTicketParent(String id, String? parentId) async {
    await _inner.updateTicketParent(id, parentId);
    unawaited(_project(id, 'reparented'));
  }

  @override
  Future<void> trashTicket(String id) async {
    await _inner.trashTicket(id);
    await _project(id, 'trashed'); // awaited — matches today's behavior
  }

  @override
  Future<void> restoreTicket(String id) async {
    await _inner.restoreTicket(id);
    await _project(id, 'restored'); // awaited — matches today's behavior
  }

  /// Re-fetches [id] from [_inner] (picking up whatever the write just
  /// persisted — generated `ticketId` on create, new `status`/`sddStage`/
  /// `parentId` otherwise) and projects it. A `null` result (id vanished
  /// between the write and this read — not expected in practice) is a
  /// silent no-op, matching every existing single-ticket projection call
  /// site's own null-check today.
  Future<void> _project(String id, String eventLabel) async {
    final ticket = await _inner.getTicketById(id);
    if (ticket == null) return;
    await _projector.project(ticket, _rootPath, eventLabel);
  }

  // ...remaining ~18 TicketRepository methods (getAllTickets,
  // getTicketById, importTicket, updateStatusForIds's sibling
  // updatePriorityForIds, updateTicket, addTimeSpent,
  // applyEstimationSuggestion, updateEmbedding, updateSyncStatus,
  // updateRollup, trashTickets, previewTrashCount,
  // permanentlyDeleteTicket(s), emptyTrash, purgeTrashOlderThan,
  // getTrashedTickets, searchTickets, getTicketsByParent,
  // getAllTicketsByType, getExecutionTokenTotals,
  // applyTokenPrediction) are one-line pass-throughs to `_inner` — see
  // "Method coverage" below for exactly which of these deliberately do
  // NOT project and why.
}
```

`trashTicket`/`restoreTicket` await their projection (matching
`TicketParentTrashService`'s existing `await _triggerGitProjection(...)`
today); every other projected method fires it `unawaited` (matching
`TicketsCubit`'s existing fire-and-forget shape) — a git commit must
never block the UI thread that's waiting on the write to return, except
for the two lifecycle events that already accept that latency today.

### `updateStatusForIds` batching note

Bulk status changes fire one `_project` call per id, exactly matching
`TicketsCubit`'s current (already-correct) behavior at its
`updateStatusForTickets` call site — one commit per ticket, not one
batched commit for the whole selection. This is *not* a regression:
today's bulk-status path already does this. `TicketRollupRecomputer`'s
batching (below) is the one place a single combined commit is a real,
separate requirement.

## Method coverage

Projected (fires `_project`, one of the six events):

| Method | Event label | Status today |
|---|---|---|
| `createTicket` | `created` | Wired at the `TicketsCubit.createTicket()` call site only — this closes every other creation path (`promoteIdea`, `createGapOrQuestion`, decomposition/verify-fix materialization, epic-spec creation, stage/branch-chat, release, coding-execution run/finding tickets, and any future one) |
| `updateTicketStatus` | `status-changed` | Already correct; centralizing removes the manual call |
| `updateStatusForIds` | `status-changed` (per id) | Already correct; centralizing removes the manual per-id loop |
| `updateTicketSddStage` | `stage-changed` | **New — was fully bypassed** (`advanceSddStage`) |
| `updateTicketParent` | `reparented` | **New — was only incidentally covered** when the following rollup recompute happened to also find a changed rollup number |
| `trashTicket` | `trashed` | Already correct (via `TicketParentTrashService`); centralizing removes its manual call |
| `restoreTicket` | `restored` | Already correct (via `TicketParentTrashService`); centralizing removes its manual call |

Deliberately **not** projected (pass-through only) — matches
`specs/tickets.md`'s existing "content edits don't commit" boundary,
not a gap:

| Method | Why excluded |
|---|---|
| `updateTicket` | Title/description/priority/type/estimate/timeSpent/complexity — the documented "no commit per keystroke-adjacent save" exclusion already covers this |
| `updatePriorityForIds` | Bulk priority — same field bucket as `updateTicket`'s own (uncommitted) priority edits; a bulk edit shouldn't commit when the single-ticket equivalent doesn't |
| `addTimeSpent` | Writes `timeSpent`, the same field `updateTicket` already excludes |
| `applyEstimationSuggestion` | Writes `estimate`, the same field `updateTicket` already excludes |
| `updateRollup` | Owned by `TicketRollupRecomputer`'s own batched `projectBatch` call — see below |
| `updateEmbedding`, `updateSyncStatus`, `applyTokenPrediction` | Fields never appear in the serialized Markdown at all (see `core/markdown/ticket_markdown_serializer.dart`'s field list) — nothing to project |
| `importTicket` | File → DB direction (`TicketDbReconstructionService`'s reconstruction path) — projecting back would rewrite the exact file the content just came from |
| `permanentlyDeleteTicket(s)`, `emptyTrash`, `purgeTrashOlderThan` | Out of scope — see proposal.md's Non-goals (deletion projection is a distinct, separate gap) |

## `TicketRollupRecomputer` — explicitly untouched

`TicketRollupRecomputer.recompute` walks a structural ancestor chain,
writes `updateRollup` for every ancestor whose `estimateRollup`/
`timeSpentRollup` actually changed, and projects the whole changed set
in **one** `TicketGitProjector.projectBatch` call — deliberately one
commit for a cascade of N ancestor rewrites, not N commits. If
`updateRollup` were added to `GitProjectingTicketRepository`'s
per-call interception, every ancestor in that cascade would fire its
own immediate commit instead, regressing exactly the batching
`projectBatch` exists for. `TicketRollupRecomputer` keeps its own
`gitProjector`/`projectRootPath` fields and its own `projectBatch`
call exactly as they are today — this fix does not touch
`ticket_rollup_recomputer.dart` at all.

Because `TicketRollupRecomputer` is constructed internally by both
`TicketsCubit` and `TicketParentTrashService` (each already threading
`gitProjector`/`projectRootPath` through to it), **those two classes
keep their own `gitProjector`/`projectRootPath` constructor
parameters** — they're not fully eliminated by this fix, only the
*direct*, per-write-site `_triggerGitProjection` calls are. See
"What gets deleted" below for the precise boundary.

## What gets deleted

Once `GitProjectingTicketRepository` exists and is wired in, the
following become redundant (the repository now does it underneath)
and should be removed, not left as a harmless-but-duplicate second
trigger:

- **`TicketsCubit`**: the `_triggerGitProjection` private method
  itself, its three call sites (`createTicket`, `updateTicketStatus`,
  the per-id loop inside `updateStatusForTickets`), and the `_gitProjector`
  field. The `gitProjector` **constructor parameter stays** (still
  threaded to the internal `TicketRollupRecomputer`/`TicketParentTrashService`
  — see above) — only the field and helper that consumed it directly
  for single-ticket projection go away. `_projectRootPath` is
  untouched in every other respect — it backs several unrelated
  desktop-only features (`_readTokenFilesForContext`, coding-execution
  worktree paths, release version-file detection) that have nothing to
  do with git projection.
- **`TicketParentTrashService`**: the `_triggerGitProjection` private
  method and its two call sites inside `trash()`/`restore()`. Its
  constructor's `gitProjector`/`projectRootPath` parameters **stay**
  (still needed to construct its own internal `TicketRollupRecomputer`).
- **`TrashCubit`**: no direct changes — it never called
  `_triggerGitProjection` itself (it only ever delegated to
  `TicketParentTrashService`), so nothing here references the
  removed code paths. Its own `gitProjector`/`projectRootPath`
  constructor parameters stay, since it still forwards them into its
  internal `TicketParentTrashService`.

Audit both files for any other reference to `_gitProjector`/
`TicketGitProjector` before deleting fields/imports — the list above
reflects what a full-text read of `tickets_cubit.dart` and
`ticket_parent_trash_service.dart` found as of this proposal, but
`/apply` should re-confirm rather than assume it's exhaustive on a
codebase this size.

## DI wiring change (`app_router.dart`)

Today, `RepositoryProvider<TicketRepository>` is created near the top
of `WorkspaceShell`'s provider list (`create: (_) =>
DriftTicketRepository(_database)`), *before* the later
`if (rootPath != null) [...]` block that creates `GitRepositoryClient`/
`TicketMarkdownSerializer`/`TicketGitProjector` for
`TicketParentTrashService`/`TicketMarkdownReconciler`/
`TicketRepairService` to consume. Because `MultiRepositoryProvider`
nests providers in list order (each one wrapping the ones after it),
`TicketRepository`'s own `create` callback can't `context.read` those
three providers today — they don't exist yet at that point in the
tree.

Fix: hoist just those three provider entries (`GitRepositoryClient`,
`TicketMarkdownSerializer`, `TicketGitProjector` — not
`ActiveTicketViewRegistry`/`TicketParentTrashService`/
`TicketMarkdownReconciler`/`TicketRepairService`, which still belong
after `TicketRepository` exists) to *before*
`RepositoryProvider<TicketRepository>` in the list, still gated by the
same `if (rootPath != null)` condition. Then:

```dart
RepositoryProvider<TicketRepository>(
  create: (context) {
    final drift = DriftTicketRepository(_database);
    if (rootPath == null) return drift;
    return GitProjectingTicketRepository(
      drift,
      context.read<TicketGitProjector>(),
      rootPath,
    );
  },
),
```

Every downstream provider that already does `context.read<TicketRepository>()`
(there are several, further down the same list) is unaffected — they
get whichever concrete instance was constructed here, exactly as
today, just now sometimes the decorated one.

## `GitRepositoryClient` hardening

`core/git/git_repository_client.dart`: `add`, `commit`, and
`hasChanges` currently call the unchecked `_run` helper
(`Process.run`, `ProcessResult` discarded without inspecting
`exitCode`/`stderr`) — the same shape `createWorktree`/`push`/`tag`
used to have before `AIO-506` found a real, silent failure and
switched them to `_runChecked` (throws a `ProcessException` carrying
`stderr` on a non-zero exit). Switch all three to `_runChecked`:

- `add`/`commit`: straightforward — return type is already `void`
  wrapping the result, `_runChecked`'s `Future<ProcessResult>` return
  is simply not used, same as `init`.
- `hasChanges`: needs its own boolean return preserved —
  `_runChecked(['status', '--porcelain'], rootPath)` still returns a
  `ProcessResult` on success (only throws on non-zero exit), so
  `result.stdout.toString().trim().isNotEmpty` stays exactly as it is
  today, just now reached only when the command actually succeeded.

This means a failed `git add`/`commit`/`status` during projection now
throws instead of silently doing nothing. Since every projection call
site in `GitProjectingTicketRepository` fires most events `unawaited`,
a thrown exception surfaces as an unhandled async error (visible in
the debug console / crash-reporting zone handler) rather than
propagating to the caller's own call stack — the write itself still
succeeds and returns normally; only the projection side effect is now
loud instead of silent on failure. `trashTicket`/`restoreTicket`
(awaited) will propagate the exception to their caller
(`TicketParentTrashService.trash`/`restore`, then `TicketsCubit`/
`TrashCubit`'s existing `catch (e) { emit(TicketsError(...)) }`
blocks) — an existing, already-handled error path, not new surface
area.

## Testing

- Unit tests for `GitProjectingTicketRepository`: a fake/mock
  `TicketRepository` + a fake/mock `TicketGitProjector`, asserting
  exactly one `project`/`projectBatch` call with the right
  `eventLabel` per intercepted method, and zero calls for every
  pass-through method (`updateTicket`, `updatePriorityForIds`,
  `addTimeSpent`, `applyEstimationSuggestion`, `updateRollup`,
  `updateEmbedding`, `updateSyncStatus`, `importTicket`,
  `applyTokenPrediction`, the permanent-delete family).
- `GitRepositoryClient` tests for `add`/`commit`/`hasChanges` now
  throwing `ProcessException` on a non-zero exit (a temp directory
  with no git repo initialized is the cheapest way to force a
  realistic failure).
- Existing `TicketsCubit`/`TrashCubit`/`TicketParentTrashService` tests
  that assert a `TicketGitProjector` call today (for `createTicket`/
  `updateTicketStatus`/`trashTicket`/`restoreTicket`) need updating:
  the assertion moves from "the cubit/service called the projector
  directly" to "the decorated repository called the projector" — most
  of these tests likely construct a plain fake `TicketRepository`
  today and assert against a directly-injected fake
  `TicketGitProjector`; they'll need to either wrap that fake
  repository in a real `GitProjectingTicketRepository` for the
  assertion, or move the assertion to a new, dedicated
  `GitProjectingTicketRepository` test and simplify the cubit/service
  tests to no longer care about projection at all (preferred — it's
  no longer their concern).

## `/verify` follow-up (2026-09-08)

The first `/apply` pass (tasks 1-5 above) built exactly what this
design specified, but `/verify` found the design itself had a real gap
and two documentation-accuracy problems. All three fixed on the same
branch; see `tasks.md`'s own "`/verify` follow-up fixes" section for
the exact edits.

### CRITICAL — concurrent projections from loop-created tickets

This design's `unawaited` shape for `createTicket`/`updateTicketStatus`/
etc. (chosen specifically so a git commit never blocks the write that
triggered it) has a real interaction this design missed: nothing
serializes *between* separate calls to `GitProjectingTicketRepository`.
`TicketsCubit._materializeParsedChildren` — the exact SDD-decomposition
path this whole fix exists to cover — creates several tickets in a
tight `await`-in-a-loop, and each `createTicket` call fires its own
independent `unawaited` projection chain (write file → `git add` →
`git status` → `git commit`, three real subprocess spawns). Because the
DB insert each loop iteration waits on is fast (sub-millisecond SQLite)
and subprocess spawn/exec is comparatively slow, several of these
chains can genuinely be in flight at once, and two concurrent `git`
invocations against the same working tree collide on `.git/index.lock`.
Before this change's own `GitRepositoryClient` hardening (task 1), that
collision was invisible (the non-zero exit was silently ignored); after
it, the losing call throws — into an `unawaited` Future, so nothing
crashes, but that ticket's projection is lost with no retry. This can
reproduce the original bug's symptom (a decomposition's children never
reaching `tickets/*.md`) via a new mechanism.

**Fix**: serialize at the `TicketGitProjector` level, not the
decorator. Every `TicketRepository` consumer shares one
`TicketGitProjector` instance (provided once in `app_router.dart`), so
adding a FIFO queue there — `Future<void> _tail`, advanced by an
`_enqueue` helper every `project`/`projectBatch` call chains through —
serializes every projection project-wide (single-ticket creates,
status changes, and `TicketRollupRecomputer`'s own batched calls
alike) without requiring every call site to coordinate with every
other one. A queued call's own success/failure still propagates to
its own caller normally; only *when* it starts running is serialized.
A failing call still advances the queue (via `.then((_) {}, onError:
(_) {})`) so one failure never wedges everything queued behind it.
This is a plain "async mutex via Future chaining" — sufficient given
Dart's single-threaded event loop, no real lock object needed.

Scoped to `TicketGitProjector`, not `GitRepositoryClient`: the latter
is also used for unrelated operations (coding-execution worktree
add/remove, release tags/pushes) against different working
directories/worktrees that have no business queuing behind ticket
projection.

### WARNING — trash/restore surfacing git errors as false failures

`trashTicket`/`restoreTicket` `await` their own projection (deliberately,
per this design's own "matches today's behavior" note) — but combined
with the `GitRepositoryClient` hardening in the same change, a git
failure during that awaited call now propagates out of
`TicketParentTrashService.trash`/`restore` into `TicketsCubit`/
`TrashCubit`'s existing `catch (e) { emit(TicketsError(...)) }`. The
user sees a failure for a trash/restore that, in fact, already
succeeded at the database layer — and the rollup recompute
`TicketParentTrashService` fires immediately after is skipped, since it
never reaches that line. This design's original text called the
existing catch block "an existing, already-handled error path, not new
surface area" — that undersold it: the block existed, but a git
failure could never previously reach it (the unchecked
`GitRepositoryClient` swallowed it first).

**Fix**: a `_projectOrSwallow` helper, used only by `trashTicket`/
`restoreTicket` — catches and discards a projection failure rather than
letting it propagate. The failure is not silently invisible in the
sense this whole change cares about: `TicketGitProjector`/
`GitRepositoryClient` still throw internally at the point it happens
(observable to a debugger or future logging infrastructure); this
method only declines to let that failure retroactively mark an
already-successful trash/restore as failed. The fire-and-forget methods
(`createTicket` et al.) need no equivalent, since an unawaited call's
exception never reaches their own caller regardless of whether it's
caught here.

### WARNING — stale constructor dartdoc

`TicketsCubit`'s constructor dartdoc listed `createTicket`/
`updateTicketStatus`/`changeTicketStatus`/`updateStatusForTickets`/
`advanceSddStage` as methods whose git-projection depends on
`_gitProjector`/`_projectRootPath` — no longer true post-`/apply`, since
their projection now depends entirely on whether `_repository` is a

not decorated, see tasks.md's task 3) genuinely still depend on those

## Second `/verify` follow-up (2026-09-08, same day)

A second `/verify` pass confirmed the four fixes above and found one
more, narrower issue in the trash/restore fix itself.

### WARNING — `_projectOrSwallow` caught too broadly

The `_projectOrSwallow` helper added above used a bare `catch (_)`,
which swallows *any* exception `_project` throws — not just the git/
file-write failures it exists to tolerate. If a genuinely unrelated bug
ever threw from `TicketMarkdownSerializer.serialize` or `_inner
.getTicketById` (a bad cast, corrupt data), `trashTicket`/`restoreTicket`
would absorb it identically, with zero visibility anywhere. This
worked against this whole change's own stated principle (stop silently
swallowing failures) for exactly the case it was trying to fix
narrowly.

**Fix**: narrowed to `on ProcessException` (a failed `git add`/
`status`/`commit`) and `on FileSystemException` (the Markdown write
itself failing) — the two failure types `_project`'s own two steps
(file write, then `GitRepositoryClient` calls) can actually throw.
Anything else now propagates and fails loudly, same as it would
anywhere else in this codebase. The two existing swallow tests were
updated to throw a real `ProcessException` (the generic `Exception`
they used before no longer matches the narrower catch), and a new test
confirms an unrelated exception (`StateError`) still propagates.
