# Design: Automation Decision Graphs

## 1. Domain layer (`lib/core/automation/`)

Flat files, following this directory's existing convention
(`automation_context.dart`, `automation_confidence.dart`,
`automation_settings_repository.dart` are all flat, no subfolder).

- **`decision_outcome.dart`** — `enum DecisionOutcome { proceed, gated,
  decline, modelJudgment }`. `modelJudgment` evaluates identically to
  `proceed` at runtime (see §4) — it exists as a distinct value so its
  node's condition description can be collected into prompt-surfaced
  context, not because it changes control flow.
- **`decision_node.dart`** — `DecisionBranch` (sealed class):
  `DecisionBranch.toNode(String nodeId)` (matched/unmatched leads to
  another condition — the strict-tree edge) or
  `DecisionBranch.terminal(DecisionOutcome outcome)` (matched/unmatched
  ends here). `DecisionNode` entity: `id` (UUID v4), `conditionId`
  (references `decision_condition_catalog.dart`), `conditionParams`
  (`Map<String, dynamic>`, validated against the condition spec's
  parameter shape), `matchedBranch`/`unmatchedBranch`
  (`DecisionBranch`). A node's `matchedBranch.toNode`/`unmatchedBranch.toNode`
  target must never be referenced as a child from more than one branch
  anywhere in the same graph — the strict-tree invariant, enforced by
  `DecisionGraphConfigCubit` (§3), never the repository or the entity
  itself, per this project's Cubit-vs-repository split.
- **`decision_graph.dart`** — `DecisionGraph` entity: `context`
  (`AutomationContext`), `rootNodeId` (`String?` — `null` means "no
  graph configured, always `proceed`," the seeded state for
  `sddStage`/`codingExecutionResume`/`ticketCreation`/`ticketLinking`/
  `specAutoLink`).
- **`decision_condition_catalog.dart`** — `DecisionConditionSpec`
  (`id`, `displayName`, `contexts` — which `AutomationContext` values it
  applies to, `parameterSpecs` — name/type pairs for the inline
  condition-editing form). `decisionConditionsFor(AutomationContext)`
  returns the subset of the catalog valid for that context — this is
  the "two separate hand-authored node catalogs" the
  `automation-confidence-decisions` idea's `/explore` pass concluded is
  necessary; here it's eight per-context subsets of one catalog list
  rather than two, since node content doesn't generalize across
  contexts any more than it does across the transition-precondition
  system. This proposal's catalog ships exactly two entries:
  - `attemptExceedsMax` (contexts: `codingExecutionRetry`; param:
    `maxAttempts: int`) — reproduces
    `_effectiveCodingExecutionRetryConfidence`'s existing
    `attempt > _maxVerifyRetries` check.
  - `sessionOverageDetected` (contexts: `codingExecution`; no params) —
    reproduces `_effectiveCodingExecutionConfidence`'s existing
    `_overageDetectedThisSession` check.

  Adding a condition for another context later is additive: a new
  catalog entry plus a matching evaluator case (§4) — no schema change,
  consistent with the idea's "engine built to make this straightforward
  later" conclusion.
- **`decision_graph_repository.dart`** — `abstract interface class
  DecisionGraphRepository`: `getGraph(AutomationContext)` (defaults to
  `DecisionGraph(context: context, rootNodeId: null)` if unseeded),
  `getNode(String id)`, `getAllNodes(AutomationContext)`,
  `upsertNode(DecisionNode)`, `deleteNode(String id)`,
  `setRoot(AutomationContext, String? nodeId)`,
  `seedDefaultsIfEmpty()` (idempotent, mirrors
  `WorkflowStatusRepository`'s own precedent — seeds all 8 `DecisionGraph`
  rows plus the two baseline nodes for `codingExecutionRetry`/
  `codingExecution`), `onChanged` (`Stream<void>`, refreshes
  `TicketsCubit`'s cache the same way `WorkflowStatusRepository.onChanged`
  does today).
- **`decision_graph_evaluator.dart`** — pure, no I/O: `DecisionOutcome
  evaluateDecisionGraph(DecisionGraph graph, Map<String, DecisionNode>
  nodesById, DecisionEvalContext input)`. `DecisionEvalContext` bundles
  whatever a condition might need to read (attempt count, session
  overage flag, ticket/arguments — passed in by the call site, not
  fetched by the evaluator itself, keeping this function pure and
  trivially unit-testable). Walks from `graph.rootNodeId` (returns
  `DecisionOutcome.proceed` immediately if `null`), evaluating each
  node's condition via a small internal `conditionId → bool Function(
  DecisionEvalContext, Map<String, dynamic> params)` registry, following
  `matchedBranch`/`unmatchedBranch` until a `DecisionBranch.terminal` is
  reached.

## 2. Data layer (`lib/core/automation/data/`)

New subfolder — the first drift-backed pieces in `core/automation/`
(the existing `AutomationSettingsRepository` implementation is
`shared_preferences`-backed, per `providers.md`).

- **`automation_decision_graphs_table.dart`** —
  `@DataClassName('AutomationDecisionGraphData') class
  AutomationDecisionGraphsTable extends Table`: `context` (`TextColumn`,
  `AutomationContext.name`, unique), `rootNodeId` (`TextColumn`,
  nullable). No FK constraints, matching every other table in this
  schema (`WorkflowStatusesTable`, `WorkflowSkillAttachmentsTable`).
- **`automation_decision_nodes_table.dart`** —
  `@DataClassName('AutomationDecisionNodeData') class
  AutomationDecisionNodesTable extends Table`: `id` (`TextColumn`,
  primary key), `conditionId` (`TextColumn`), `conditionParamsJson`
  (`TextColumn` — JSON-encoded `Map<String, dynamic>`),
  `matchedBranchKind`/`unmatchedBranchKind` (`TextColumn` —
  `'node'`/`'proceed'`/`'gated'`/`'decline'`/`'modelJudgment'`),
  `matchedBranchNodeId`/`unmatchedBranchNodeId` (`TextColumn`,
  nullable — set only when the corresponding `*Kind` is `'node'`). No
  FK constraint on the node-id columns, same convention.
- **`automation_decision_dao.dart`** — CRUD plus `seedDefaultsIfEmpty`,
  mirroring `WorkflowStatusDao`.
- **`drift_decision_graph_repository.dart`** — implements
  `DecisionGraphRepository` via the DAO, mapping
  `AutomationDecisionGraphData`/`AutomationDecisionNodeData` ↔
  `DecisionGraph`/`DecisionNode` (including `DecisionBranch`
  reconstruction from the `*Kind`/`*NodeId` column pair, and
  `conditionParamsJson` ↔ `Map<String, dynamic>`).
- **`AppDatabase`** (`core/database/app_database.dart`) — schema version
  bumps from 17 to 18, registering both new tables. Migration:
  additive only (two new empty tables), no existing-column changes.
  `AppDatabase.seedDefaultsIfEmpty`-equivalent wiring calls
  `DecisionGraphRepository.seedDefaultsIfEmpty()` on the schema-18
  upgrade path and on fresh-install seeding, mirroring
  `WorkflowStatusRepository`'s own schema-15 precedent.

## 3. `DecisionGraphConfigCubit` (`lib/features/providers/presentation/cubit/`)

Owns node/graph CRUD for the dual-pane editor, enforcing the invariant
`TicketsCubit` never checks: a node can be referenced as a child from at
most one branch across the entire graph (the strict-tree constraint) —
`createNode`/`updateNode` reject an edit that would give a node two
parents or create a cycle. `DecisionGraphConfigState`:
`DecisionGraphConfigInitial` / `DecisionGraphConfigLoaded` (`context`,
`graph`, `nodesById`) / `DecisionGraphConfigError` (`message` plus the
prior `Loaded`, so a rejected edit never loses editor state — mirrors
`WorkflowConfigCubit`'s own error-state shape).

Both the canvas pane and the list pane render from the same
`DecisionGraphConfigLoaded` state and call the same Cubit methods —
this is what makes them "independently editable and kept in
bidirectional sync": there is exactly one source of truth
(`DecisionGraphConfigState`), and each pane is just a different
`Widget` over the same state, the same way two `BlocBuilder`s over one
Cubit never disagree. A canvas-side node edit and a list-side node edit
both go through `updateNode`, so there's no separate "sync" step to get
wrong — the two views literally can't diverge, since neither holds its
own copy of the tree.

## 4. `TicketsCubit` integration

New private helper:

```dart
Future<DecisionOutcome> _evaluateDecisionGraph(
  AutomationContext context,
  DecisionEvalContext input,
) async {
  final repo = _decisionGraphRepository;
  if (repo == null) return DecisionOutcome.proceed;
  final graph = _decisionGraphsByContext[context]; // cached, refreshed on repo.onChanged
  if (graph == null) return DecisionOutcome.proceed;
  return evaluateDecisionGraph(graph, _decisionNodesById, input);
}
```

`DecisionGraphRepository` is an optional `TicketsCubit` constructor
parameter, following `WorkflowStatusRepository`'s own optional-dependency
convention — omitting it pins every context's outcome to `proceed`,
exactly reproducing today's behavior, so existing construction sites
(mostly tests) aren't forced to supply it.

Each of the eight `AutomationContext` call sites' existing
`case AutomationConfidence.auto:` branch is extended to consult the
graph **only when the persisted confidence already resolves to `auto`**
— `gated`/`manual` branches are untouched:

```dart
case AutomationConfidence.auto:
  final outcome = await _evaluateDecisionGraph(
    AutomationContext.ticketCreation,
    DecisionEvalContext(/* ... */),
  );
  return switch (outcome) {
    DecisionOutcome.decline =>
      {'accepted': false, 'reason': 'Blocked by decision graph.'},
    DecisionOutcome.gated => _awaitProposalConfirmation(
      chat,
      PendingToolProposal.createTicket(/* ... */),
      onConfirm: create,
    ),
    DecisionOutcome.proceed || DecisionOutcome.modelJudgment => create(),
  };
```

`DecisionOutcome.gated`/`.decline` route through **each call site's own
existing gated/decline surface** — `_awaitProposalConfirmation` for the
three tool-call handlers (`_handleCreateTicketToolCall`,
`_handleAddLinkToolCall`, `_handleBranchToolCall`/
`_handleCloseBranchToolCall`), the existing `executionAwaitingReview`
banner path for `codingExecution`/`codingExecutionRetry`. The evaluator
only decides *which* outcome; how an outcome that isn't `proceed` gets
surfaced stays exactly what each context already does today for
`AutomationConfidence.gated`/`.manual` — no new UI surface for that
part.

**Migrating the two existing ad hoc checks:** `_effectiveCodingExecutionRetryConfidence`'s
`if (attempt > _maxVerifyRetries) return AutomationConfidence.gated;`
and `_effectiveCodingExecutionConfidence`'s
`_overageDetectedThisSession ? AutomationConfidence.gated : ...` are
**removed** — both functions become plain `getConfidence(context)`
passthroughs. The equivalent behavior moves into each context's seeded
baseline graph: a single node (`attemptExceedsMax`/
`sessionOverageDetected`) whose matched branch terminates `gated` and
whose unmatched branch terminates `proceed`, evaluated from the new
`case auto:` step described above. Net behavior for a project that
never touches its configuration: byte-for-byte identical to today.

**Not migrated:** `_canBranch`'s branch-depth cap
(`_handleBranchToolCall`) stays exactly as-is — it hard-declines
*before* the confidence switch even runs, regardless of confidence
value (including under `gated`/`manual`), which is a different
mechanism from "a graph consulted only inside the `auto` case." Folding
it into the graph would change its behavior (it would stop applying
under `gated`/`manual`), which is out of scope here.

**`sddStage`'s call site** (`ticket_detail_screen.dart:177`, a direct
`getConfidence` read rather than a `TicketsCubit` tool-call handler)
and **`specAutoLink`'s call site** (`TicketsCubit._maybeAutoLinkToSpec`)
get the same `case auto:` graph-consultation treatment; both ship with
`rootNodeId: null` baseline graphs (always `proceed`), so this is a
structural change with no behavior change until a project edits either
graph.

## 5. UI

### `GraphCanvas` (`lib/design_system/molecules/graph_canvas.dart`)

New primitive — Aion's first pan/zoom/node-graph widget (`/explore`
found no existing precedent: every `CustomPainter` in the app is a
small decorative painter, no `InteractiveViewer`/free-positioned-widget
system exists anywhere). Built from `InteractiveViewer` (Flutter SDK,
not a new dependency) wrapping a `Stack` of positioned node widgets,
with a `CustomPainter` beneath drawing edges between node anchor
points. Generic over a node/edge model and a per-node content builder —
`DecisionGraphEditorScreen` (below) is its only consumer in this
proposal, but the API is intentionally not `DecisionNode`-specific, so
`obsidian-style-graph-view-for-ticket-links` could extend it later
without redesign, per the idea file's non-blocking recommendation.

No Material import — hand-built gesture handling
(`GestureDetector`/`Listener`) for node drag/select, matching every
other screen in this app (`tickets.md`'s Material-coupling convention).

### `DecisionGraphEditorScreen` (`lib/features/providers/presentation/screens/decision_graph_editor_screen.dart`)

Reached per-context from `SettingsScreen`'s existing `_AutomationSection`
list (`providers.md`) — each `AutomationContext` row gains a "Configure
decision graph" affordance alongside its existing confidence
`SelectionMenu`. Layout follows `MarkdownEditor`'s `_Wide` precedent
(`design.md §1.5` of that feature): a `Row` of two `Expanded` panes with
a 1px divider — `GraphCanvas` (default/left) and `DecisionOutlineList`
(right). Unlike `MarkdownEditor`'s one-directional raw→preview flow,
both panes here read from and write to the same
`DecisionGraphConfigState` (§3) — genuinely new bidirectional-sync
plumbing, not a reuse of `MarkdownEditor`'s data flow, only its layout
scaffold.

- **`DecisionOutlineList`** — one row per `DecisionNode`: condition
  name + parameters (via `DecisionNodeForm`, inline expand-in-place,
  matching `WorkflowStatusSettingsScreen`'s `_AddStatusControl`
  interaction shape) and an outcome badge when a branch terminates.
  Children are rendered indented beneath the branch that leads to them
  — a direct nested-outline rendering of the strict tree, no depth cap
  (same shape as a Markdown nested bullet list). Reorder controls apply
  only among sibling terminal-vs-node choices on one branch, not
  cross-branch (there is no "order" between a node's matched and
  unmatched branches to reorder).
- **`DecisionNodeForm`** — condition picker (`SelectionMenu` over
  `decisionConditionsFor(context)`), parameter fields (typed per
  `DecisionConditionSpec.parameterSpecs`), and a matched/unmatched
  branch picker (either "end here" + outcome `SelectionMenu`, or
  "continue to another condition"). Shared between the canvas pane's
  node-tap-to-edit interaction and the list pane's inline row form —
  one widget, two call sites, so the two panes can never render
  divergent editing UI for the same node.

Every widget here is built from `flutter/widgets.dart` plus existing
`AppTextField`/`AppButton`/`SelectionMenu` atoms/molecules — no Material
import, matching every other screen in this app.

## 6. What's explicitly unchanged

- `AutomationConfidence`/`AutomationSettingsRepository` — untouched.
  `gated`/`manual` behavior for all eight contexts is byte-for-byte
  identical to today.
- `_canBranch`'s depth cap — untouched (see §4).
- Every context's existing gated/decline surfacing mechanism
  (`_awaitProposalConfirmation`, `executionAwaitingReview`) — untouched;
  the graph only decides which outcome, never how it's shown.

# Aion — Automation Decision Graphs: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and the [Overrides Spec](./Aion%20Overrides%20Spec.md) (Settings screen, `AutomationConfidence` selector rows). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TypeChip`, `AppDropdown`, `IconBtn`, `PrimaryButton`, `GhostButton` by name.

Each of Aion's eight `AutomationContext` decision points gets a project-authored **strict binary tree**: every node is one condition, every condition has exactly two outgoing branches (`matched`, `unmatched`), and each branch either continues to another condition or terminates in an outcome (`proceed` / `gated` / `decline` / `modelJudgment`). The feature adds one screen (`DecisionGraphEditorScreen`, §4), three components (`GraphCanvas` §1, `DecisionOutlineList` §2, `DecisionNodeForm` §3), and one affordance on the existing Settings automation row (§5).

**No Material widgets anywhere.** Every element below is a Flutter primitive: `DecoratedBox`, `Padding`, `Row`/`Column`/`Stack`/`Positioned`, `GestureDetector`, `MouseRegion`, `Focus`, `InteractiveViewer`, `CustomPaint` (grid, edges, glyphs), `CustomMultiChildLayout` (node placement), `OverlayEntry` + `CompositedTransformTarget`/`Follower` (dropdown, popover), `AnimatedContainer`/`TweenAnimationBuilder` (state tweens). `TextField` inside a transparent `Material` ancestor remains the sole permitted Material exception, for text input only — unchanged from existing specs. No `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `MaterialApp`, `InkWell`, `Divider`, `Icons.*`.

Themes: **Arctic** (light) and **Obsidian** (dark). All dimensions, padding, radius, spacing, and typography are **identical** between themes; only colors differ, and every color is a named token resolved per theme. Hex is quoted `Arctic / Obsidian` for reference only — implement against the token. Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB. `fillAlpha` below means `AionColors.fillAlphaArctic` `0.11` / `fillAlphaObsidian` `0.16`, resolved per theme.

**New tokens: none.** No new colors, text styles, radii, or spacing values are introduced. The four outcome semantics map onto existing tokens (§0.1), the canvas plane reuses `background`, and both panes reuse `surface`. Every value in this spec already exists in `AionColors` / `AionText` / `AionRadius` / `AionSpacing`.

## 0. Shared vocabulary

### 0.1 Outcome color map

One table, used identically by the canvas terminal node (§1.2), the outline badge (§2.2), and the form's outcome selector (§3.3). Glyphs are `CustomPaint` primitives — no icon font, no `Icons.*`.

| Outcome | Token | Arctic | Obsidian | Label string | Glyph (12×12 box) |
|---|---|---|---|---|---|
| `proceed` | `success` | `#1E9E76` | `#33D19B` | `Proceed` | Right-pointing solid triangle, 8×9 |
| `gated` | `warning` | `#B8912B` | `#D7B24E` | `Ask first` | Two 3×10 vertical bars, 3px apart (pause) |
| `decline` | `danger` | `#CE3D54` | `#F1546C` | `Decline` | 10×10 cross, 1.6px stroke |
| `modelJudgment` | `secondary` | `#5E7183` | `#57608A` | `Model decides` | 9×9 square rotated 45° (diamond), 1.6px stroke, hollow |

`warning` is used here in its literal role — a `gated` branch is the "stop and ask the human" state. `secondary` (never an outcome color elsewhere) carries `modelJudgment` because it is the only calm, non-verdict token in the palette: model judgment is a deferral, not a decision.

### 0.2 Branch identity

| Branch | Line | Label text | Label color | Anchor dot |
|---|---|---|---|---|
| `matched` | 1.5px **solid** `primary` | `matched` | `primary` | `primary`, 7×7 |
| `unmatched` | 1.5px **dashed** `borderStrong`, dash 4 on / 4 off | `unmatched` | `textMuted` | `borderStrong`, 7×7 |

Solid-vs-dashed carries the distinction without relying on hue, so the two branches remain separable at 40% zoom, in monochrome, and for red-green color vision deficiency. Color reinforces, never carries.

## 1. `GraphCanvas`

The pan/zoom plane. Structure: `DecoratedBox` (plane fill) → `InteractiveViewer` (`constrained: false`, `boundaryMargin: EdgeInsets.all(600)`, `minScale: 0.4`, `maxScale: 2.0`, `panEnabled: true`, `scaleEnabled: true`) → `Stack` → [ `CustomPaint` grid ] + [ `CustomPaint` edges ] + [ `Positioned` node children ]. The zoom cluster (§1.6) sits **outside** the `InteractiveViewer`, in a parent `Stack`, so it never scales.

### 1.1 Plane

| Property | Value |
|---|---|
| Fill | `AionColors.background` — `#EDF2F8` / `#0A0E18`. The plane is deliberately the app canvas color, one step back from the `surface` nodes that float on it. |
| Dot grid | 24px lattice, 1.5px-diameter circles, `borderStrong.withOpacity(0.45)` Arctic / `borderStrong.withOpacity(0.55)` Obsidian. Painted in canvas space, so dots scale with zoom and act as the pan/zoom feedback. |
| Grid fade | Dots hidden below `scale < 0.6` (they alias into noise); `CustomPainter.shouldRepaint` keyed on `scale` + `offset`. |
| Border | None on the plane itself; the pane edge is the screen divider (§4.3). |
| Shadow | None. |
| Cursor | `SystemMouseCursors.grab` over empty plane, `grabbing` while panning, `basic` over a node body, `move` over a node's drag area. |
| Node drag | `GestureDetector` on the node (`onPanUpdate`) writes `node.position` in canvas coords, snapped to the 24px lattice on release (`AnimatedPositioned`, 120ms `Curves.easeOut`). |
| Layout on open | Auto-layout: depth → y (`152px` per level), in-order index → x (`296px` per slot), centered. Manual positions, once set, persist per node. |

Deliberately a different silhouette from a condition node — pill, not rounded rectangle — so tree endpoints are readable at a glance and at low zoom.

## 7. Accessibility

- Every interactive element declares a `Semantics` label; nodes announce as `Condition, attempt count exceeds 3, matched branch asks first, unmatched branch proceeds`.
- Keyboard: `Tab` walks the outline in tree order; `↑`/`↓` move between rows, `→`/`←` expand/collapse, `Enter` opens the form, `Esc` closes it, `Delete` deletes the focused node (with confirm). The canvas is reachable but not tab-walked node-by-node; `Tab` into it focuses the zoom cluster.
- Focus rings are never the sole state signal — every focused state above pairs the ring with a border-weight change.
- Matched / unmatched never rely on hue alone (§0.2); outcomes never rely on color alone (§0.1 glyph + label).
- Minimum text size in the feature is `AionText.caption` at 11 — used only for uppercase mono eyebrows, at `0.14em` tracking, on `textMuted` (contrast ≥ 4.6:1 on both themes' `surface`).
