# Anthropic Messages Api Provider

# Proposal: Anthropic Messages API Provider

## Why

`ProviderRegistry`/`AgentProvider`/`ProviderId`/`ToolAccessTier`/
`AgentModelDescriptor`/`ConsumptionSignal` (`core/contracts/`) are real,
consumed-everywhere abstractions — but exactly one implementation,
`ClaudeAgentSdkProvider`, has ever backed them. `providers.md`'s own
"Known gaps" section names this directly: *"`ProviderRegistry` is
validated against one implementation only."* Every shortcut that
implementation gets away with is untested by the abstraction:

- **Transport.** `ClaudeAgentSdkClient` spawns a bundled Node.js
  subprocess and reads NDJSON off stdout. `AgentModelClient.run()` has
  never been implemented over plain HTTP/SSE — the shape every other
  provider `project.md` §5 names (Anthropic API, OpenAI,
  OpenAI-compatible, Ollama) would actually use.
- **Credentials.** "Authenticated via the user's existing Claude plan —
  no API key entry, nothing Aion stores as a secret." `flutter_secure_storage`
  is already a dependency but nothing in the app touches it. This is
  also its own separate known gap: *"No per-provider credential storage
  or enabled/disabled state."*
- **Consumption.** `ConsumptionSignal`'s `CostConsumption` variant (a
  token-billed provider's cost signal) has no real producer —
  `ClaudeAgentSdkProvider.describeOverage` only ever returns
  `UsageWindowConsumption`.
- **Reach.** Agent SDK is desktop-only (`dart:io Process`), so
  mobile/web have no working provider at all — not addressed by this
  change (see Non-goals), but worth naming as part of why "one
  implementation" is an incomplete proof.

Building a second `AgentProvider` — the Anthropic Messages API,
already named in `project.md` §5 for exactly this role ("conversational
reasoning: spec phase, watcher reviews, ticket estimation,
brainstorm-to-ticket promotion, AI-authored comments... billed per
token at standard API rates") — proves the abstraction against a
structurally different implementation and closes a real functional gap
in the same change, rather than building throwaway scaffolding purely
to validate an interface.

## What

- A second `AgentProvider`: `AnthropicMessagesApiProvider` +
  `AnthropicMessagesApiClient`, calling `https://api.anthropic.com/v1/messages`
  directly via `dio` (new dependency — the package `project.md` §5
  already names for this), parsing the API's SSE stream into the
  existing, unchanged `AgentEvent` shapes. Desktop-only for this round
  (see Non-goals).
- Real credential storage: `AnthropicApiKeyRepository` (abstract) +
  `SecureStorageAnthropicApiKeyRepository` (`flutter_secure_storage`),
  plain reads/writes only, no validation (per `project.md`'s
  Cubit-domain-logic split).
- A new "PROVIDERS" section on the Settings screen — an API-key field
  (obscured, with a reveal toggle), Save, and a provider-scoped Test
  Connection — backed by a new `AnthropicProviderConfigCubit`.
- `_ProviderStatusCard`'s provider title/subline, currently a hardcoded
  "Claude Agent SDK" / "Authenticated via your Claude plan" pair, become
  provider-derived — the natural follow-up
  `changes/archive/pluggable-provider-abstraction/design.md` §7 already
  flagged ("once a second provider makes 'which provider is Frontier
  using' worth surfacing dynamically").
- The provider-prefixed dropdown item row that same archived design.md
  fully specified in §6 but explicitly marked "FUTURE ONLY, do not
  implement" — implemented now, since a second provider is exactly the
  trigger condition it named. Gated per-`ModelPhase` on that phase's
  model list actually spanning more than one provider (Frontier/Capable
  will; Execution won't, since this provider doesn't support
  `ToolAccessTier.full`).
- `AgentProvider.describeOverage`'s first real `CostConsumption`
  producer: an HTTP 429 (rate-limited) response is treated as a
  consumption signal (`AgentOverageDetectedEvent`), not a bare failure —
  the same "usage/rate-limit signal, not necessarily an error" concept
  `AgentOverageDetectedEvent` already exists for, now with a second,
  structurally different real source.

## Non-goals

- **Tool-enabled / coding-execution use of this provider.** It declares
  `supportedToolAccessTiers: {ToolAccessTier.noTools}` only — no file
  edits, git, bash, or MCP. Building an agentic tool loop against the
  raw Messages API is unrelated, much larger scope (`ClaudeAgentSdkProvider`
  gets this for free from the bundled Agent SDK bridge). The
  already-built (if previously inert) `ModelPhaseToolAccess.requiredToolAccessTier`
  filter means the Execution tier's dropdown simply never offers this
  provider's models — no new gating code needed.
- **`ToolAccessTier.readOnly`.** Still unbuilt. This provider doesn't
  reach for it either — it only ever declares `noTools`.
- **Live model-list discovery.** `AnthropicMessagesApiProvider.availableModels`
  is a fixed list, same as `ClaudeAgentSdkProvider`'s. The Messages API
  has no `/api/tags`-equivalent discovery endpoint to query anyway.
- **Per-provider `isEnabled`/`setEnabled` toggle.** The archived
  `pluggable-provider-abstraction/design.md` §5 sketched a
  `ProviderConfigRepository.isEnabled(ProviderId)` shape for "when a
  second provider exists." This change deliberately doesn't build it:
  the provider stays unconditionally registered, and an absent/empty
  API key simply makes its connection test report `disconnected` with
  "No API key configured" — reusing `ProviderConnectionStatus`'s
  existing four states instead of inventing a parallel on/off concept
  with no second consumer yet. Revisit if a real need for disabling an
  *already-configured* provider shows up later.
- **Mobile/web reachability.** `project.md`'s API & Security section
  requires a Firebase Cloud Function proxy for non-Google providers on
  mobile/web (raw API keys aren't trusted there the way they are on a
  desktop-only, locally-run tool). That proxy is unbuilt. This change
  adds no explicit platform gate in the client itself (unlike
  `ClaudeAgentSdkClient`'s `dart:io Process` dependency, `dio` compiles
  fine everywhere) — it simply isn't exercised on mobile/web today,
  since Aion's active development and verification stay desktop-first
  (see `project.md`'s Testing conventions). Naturally, a Flutter Web
  build would fail at the API's CORS policy if it ever reached this
  client; that's an acceptable, explicitly-deferred edge case, not a
  bug this change needs to guard against.
- **Auto-testing the connection on every Settings load.** Unlike
  `ProviderSettingsCubit`, which pings on `load()` "for free" (Claude
  Pro/Max's flat plan), a Messages API ping is a real, billed token
  call. `AnthropicProviderConfigCubit.load()` only checks whether a key
  is *stored* — it never calls the API until the user explicitly presses
  Test Connection.
- **Real live verification against a paid Anthropic account.** Verified
  by code review and (if the developer has a personal API key) a manual
  live test after `/apply`, the same way `ClaudeAgentSdkProvider`'s
  connection path was manually verified on a native Windows build — not
  something this proposal or `/verify` can automate.
