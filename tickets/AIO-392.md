# Board Task Ordering Indication

# Proposal: Board visual indication of task ordering (blocks/blockedBy)

## Why

`TicketLinkType.blocks`/`blockedBy` (`ticket_link_type.dart`) have existed
since the link-type enum shipped, but nothing in the app ever creates or
displays them, confirmed against the live code during `/explore`:

- **`TicketLinkPicker`/`LinkedTicketsSection` are resource-only.**
  `ticket_metadata_section.dart:645-648` only renders the Linked
  Tickets section for `resource`/`bug` tickets, and the one call site
  (line 677) hardcodes `TicketLinkType.relatesTo`. Epic/Story/Task have
  *zero* link-creation UI today — a human cannot express "Task B is
  blocked by Task A" through the app at all, manually or otherwise.
- **Decomposition is text-only.** `proposed`-stage chats
  (`TicketsCubit._assembleStageContext`) have no branch for
  `SddStage.proposed` at all — the spawned chat gets nothing but the
  parent's title/description, replies in plain text, and a human reads
  that reply and creates each child Story/Task by hand via the
  ordinary "+ New ticket" flow. Whatever dependency ordering the model
  reasoned about while decomposing is discarded the moment its reply
  is posted — nothing captures it as a `blocks`/`blockedBy` link.
- **The Board shows no ordering signal.** `TicketBoardCard`/`_CardVisual`
  (`tickets_board_view.dart`) render `TypeChip`/`PriorityBadge` and (since
  `board-execution-indicators-and-notifications`) an execution-state
  badge — nothing reflects whether a card's dependency is still open.
  That change's proposal.md explicitly reserved this ground: *"this
  change's `_CardVisual` edit should leave clear room for that badge to
  land alongside this one later, not conflict with it"* — confirmed
  still true in the shipped code (the meta-chip row ends with a
  `Spacer()` + the execution badge, leaving room before it).

**Correction to the explored idea's premise, found during `/explore`
and re-verified here:** `aion-arch/ideas/board-task-ordering-indication.md`
frames piece 2 as "a new tool-enabled decomposition capability...
distinct from coding-execution's full tier and `designSync`'s read-only
tier" — implying a tiered tool-access system with two tiers already
built. That system does not exist. `ChatCubit.runChatTurn`/`AgentRequest`
expose exactly one flag, `toolsEnabled: bool`. `_runStageChatTurn`
(`tickets_cubit.dart:2370`) never passes `toolsEnabled` for *any* stage
chat, including `designSync` — despite
`design-gate-for-ticket-driven-sdd-workflow`'s idea write-up claiming
designSync got a "read-only tool tier," what actually shipped is
`_assembleStageContext` pre-reading design-token files off disk and
injecting them as plain text (`_readTokenFilesForContext`); the model
never gets tool access there either. There is no working precedent for
a tiered tool system to extend. This proposal does **not** build one —
see "What we're building," item 2, for the alternative that follows the
codebase's actual existing convention instead.

## What we're building

**1. Generalize manual linking to work tickets, with a real link-type
selector.**
- `TicketLinkPicker` gains a `linkType` selection step — a
  `SelectionMenu<TicketLinkType>` (the same pattern already driving
  priority/complexity/type/status pickers in
  `ticket_metadata_section.dart`) offered before the candidate-ticket
  search, restricted to `blocks`/`blockedBy`/`relatesTo`/`duplicates`
  (the four non-hierarchical types — `duplicatedBy` is never
  user-chosen, it's the inverse `createLink` writes automatically, see
  below).
- `LinkedTicketsSection`/`TicketLinkPicker` render on `epic`/`story`/
  `task`/`bug` tickets too, not just `resource`/`bug` — widening
  `ticket_metadata_section.dart`'s existing type gate.
- `TicketLinkRepository.createLink` itself needs **no change** — a
  single row already fully expresses direction. Picking `blocks`
  pointing at another ticket while on ticket X writes `source: X,
  target: Y, linkType: blocks` ("X blocks Y"); picking `blockedBy`
  instead writes `source: X, target: Y, linkType: blockedBy` ("X is
  blocked by Y"). `blockedBy`/`duplicatedBy` are read as the *inverse
  reading* of the same row from the other ticket's side (per
  `ticket_link_type.dart`'s own doc comments — "Inverse of [blocks]"),
  not a second persisted row. `TicketLinkDao.getLinksForTicket` already
  returns the row regardless of which side [ticketId] is; only the
  UI's interpretation of `sourceTicketId`/`targetTicketId` vs. the
  viewed ticket needs to account for direction, which item 3's bulk
  query (below) already has to do.

**2. `proposed`-stage decomposition materializes child tickets and their
ordering — via structured plain text, not a new tool tier.**
Following the exact convention `_designSyncApproved`/
`_executionSucceededWithPr` already establish (the model ends its plain-
text reply with a deterministic sentinel the cubit parses — `"DESIGN
GATE: APPROVED"`, `"EXECUTION: PR_OPENED"` — no tool access involved),
`proposed`'s chat prompt (a new `_assembleStageContext` branch, filling
the gap noted above) asks the model to end its reply with a fenced
`## Decomposition` block, one line per child:

```
## Decomposition
- Story: Set up backend scaffolding
- Story: Build the settings UI (blockedBy: Set up backend scaffolding)
```

A new `TicketsCubit._materializeDecomposition(Ticket parent, String
reply)` runs once the `proposed`-stage chat's turn completes
(`_runStageChatTurn`'s existing post-turn point): parses that block,
creates one child ticket per line (`story` under an `epic`, `task`
under a `story`, matching `_assembleStageContext`'s existing
verifying/archived-stage rank logic) via `TicketRepository.createTicket`,
then resolves each `(blockedBy: <sibling title>)` against the
just-created siblings by exact title match and creates the
`blocks`/`blockedBy` pair via the widened `TicketLinkRepository.createLink`
(item 1). No block, an unparseable block, or an unresolved sibling title
is **not an error** — it silently falls back to today's exact behavior
(plain-text reply, human creates children by hand), the same
fail-open posture `_designSyncApproved` already has for a missing/
malformed gate line.

**3. Board "blocked" badge.**
A new `TicketsLoaded.blockedTicketIds` (`Set<String>`, mirroring
`inFlightExecutionIds`'s shape but persisted-data-derived rather than
in-memory/ephemeral) — a work ticket's id is in the set whenever it has
an unresolved blocking relationship (the blocking ticket exists, is
live, and isn't `TicketStatus.done`). Computed in bulk, not per-card:
`TicketLinkDao` gains `getLinksByTypes([TicketLinkType.blocks,
TicketLinkType.blockedBy])` (mirrors `deleteLinksForTickets`'s bulk,
no-per-ticket-id-filter shape) returning every live `blocks`/`blockedBy`
row app-wide in one query pair. `TicketsCubit` derives, per row, which
side is the *blockee*: a `blockedBy` row's blockee is its `source`
(blocked by its `target`); a `blocks` row's blockee is its `target`
(blocked by its `source`) — then filters to blockees whose blocker
isn't `done`. The `CommentRepository` bulk-query gap
`board-execution-indicators-and-notifications` flagged for
`executionAwaitingReview` does not recur here — link/status data has no
per-ticket async lookup cost once loaded in bulk.
`TicketBoardCard`/`_CardVisual`'s meta-chip row gains a `_BlockedBadge`
(informational icon + "Blocked" label) rendered **before** the existing
`Spacer()` + execution-state badge — same row, same precedent, no
layout conflict with `board-execution-indicators-and-notifications`'s
reserved space. Purely informational: no gate on drag/status-change,
per the idea file's resolved Q4.

## Out of scope

- Any hard gate preventing a blocked Task/Story from moving to
  `inProgress` — visual only, confirmed by the idea file's Q4.
- `duplicates`/`duplicatedBy` UI treatment beyond being selectable in
  the widened `TicketLinkPicker` — no Board/detail-screen visual
  callout for duplicates, only for `blocks`/`blockedBy`.
- A general-purpose agent tool-access tier system. Item 2 above is
  scoped narrowly to `proposed`'s existing text-only chat gaining one
  new sentinel-block convention — it does not touch `AgentRequest`,
  `ChatCubit.runChatTurn`, or introduce any `toolsEnabled`-adjacent
  concept. If a genuine tool-calling tier is ever built for another
  stage, it is a separate proposal.
- Retroactively linking existing Story/Task pairs created before this
  change shipped — no migration/backfill; `blocks`/`blockedBy` only
  exist going forward, either drawn manually (item 1) or from a
  `proposed`-stage decomposition that includes them (item 2).
