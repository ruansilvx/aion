# Design: Private Widget Retrofit

## Conversion pattern

Every `Widget _foo(<params>) { ... }` becomes:

```dart
class _Foo extends StatelessWidget {
  const _Foo({required this.param1, required this.param2});

  final Type1 param1;
  final Type2 param2;

  @override
  Widget build(BuildContext context) {
    // original body, unchanged
  }
}
```

Naming: strip a leading `build` verb if present (`_buildAvatar` → `_Avatar`),
otherwise just PascalCase the existing name (`_titleRow` → `_TitleRow`).
Call sites replace `_foo(a, b)` with `_Foo(param1: a, param2: b)`.

No dartdoc is required on these classes — they're private implementation
detail, same as any other private class in the codebase (per
`flutter-conventions.md`'s documentation standards, which only mandate
dartdoc on public symbols).

## Two source shapes, two field-mapping rules

The 9 files split into two shapes depending on what the helper currently
reads:

**Shape A — helper only reads its own explicit parameters** (e.g. every
helper in `app_confirm_dialog.dart`, which is already a `StatelessWidget`
where `colors`/`isDark`/`tone`/`cancelLabel`/`confirmLabel`/`onResolve` are
read as bare fields, not `widget.foo`). Conversion is a direct 1:1 mapping
of the helper's existing parameter list to constructor fields. Where one
helper calls another Widget-returning helper (`_wideActions()` calling
`_cancelButton()`/`_confirmButton()`), the new widget class simply
constructs the other new widget class in its `build()` — ordinary
composition, no special handling.

**Shape B — helper reads `widget.foo` or a bare `State` field** (e.g.
`app_button.dart`'s `_label()` reading `widget.label`;
`ticket_parent_picker.dart`'s `_buildInlineTrigger`/`_buildFormFieldTrigger`
reading `widget.currentParentId`/`widget.errorText` and the State's
`_isOpen`/`_isFocused`/`_isHovered`). Every such reference becomes an
explicit constructor field, passed by the caller (which is still inside
the original `State.build()` and has full access to `widget.*` and its own
fields). State *ownership* does not move — the new widget class receives
already-resolved values, it does not read or mutate `_isHovered` etc.
itself. This is the out-of-scope boundary called out in `proposal.md`.

**Shape B, second wrinkle — derived-value helper methods.**
`app_button.dart`'s `_buildDecoratedContent` calls sibling instance methods
(`_fillColor`, `_textColor`, `_border`, `_shadow`, all non-`Widget`-
returning, out of scope) to compute its inputs. Since the new
`_DecoratedContent` widget class can't call back into `_AppButtonState`,
those calls move to the call site inside `_AppButtonState.build()` — the
`fill`/`textColor`/`border`/`shadow` values get computed there (exactly as
today) and passed into `_DecoratedContent(...)` as constructor fields
instead of being recomputed inside the extracted widget.

`BuildContext` handling: where a helper's original signature already took
`BuildContext context` explicitly (e.g. `project_card.dart`'s
`_titleRow(BuildContext context, AionColors c)`), drop that constructor
field entirely — the new widget class has its own `build(BuildContext
context)` parameter occupying the same tree position, so any
`ThemeScope.of(context)`/`context.l10n` call inside the body resolves
identically without needing it passed in.

## Per-file notes

- **`project_card.dart`, `empty_hub_state.dart`, `hub_screen.dart`,
  `new_project_screen.dart`, `tickets_list_screen.dart`,
  `ticket_detail_screen.dart`** — all Shape A in practice: every helper
  already takes its inputs (`AionColors c`, feature state/entities) as
  explicit parameters rather than reading `widget.foo`, since these are
  screen-level `StatelessWidget`/`StatefulWidget` build-method splits, not
  State-field-heavy interactive primitives. Straightforward 1:1 field
  mapping.
- **`app_confirm_dialog.dart`** — Shape A (see above). `_wideActions`/
  `_narrowActions` compose `_CancelButton`/`_ConfirmButton` directly.
- **`app_button.dart`** — Shape B with the derived-value wrinkle. Two new
  classes: `_DecoratedContent` (fields: `fill`, `textColor`, `border`,
  `shadow`, `isFullWidth`, `variant`, `icon`, `label` — enough to also
  construct `_Label` internally rather than needing a separate
  `_Label`-construction step at the outer call site) and `_Label` (fields:
  `label`, `color`, `fontSize`).
- **`ticket_parent_picker.dart`** — Shape B. `_InlineTrigger` fields:
  `colors`, `resolvedParent`, `currentParentId`, `isOpen`. `_FormFieldTrigger`
  fields: `colors`, `resolvedParent`, plus whatever subset of
  `errorText`/`isDisabled`/`isFocused`/`isOpen`/`isHovered` its body
  actually reads (confirm exact set against the full method body during
  `/apply`, not just the excerpt reviewed here).

## Enforcement

Add to `flutter-conventions.md`'s "Widget composition — no Material,
primitive-first" section, immediately after the existing rule statement:

```
Enforced by a grep check, run at the end of any `/apply` whose `tasks.md`
touches a `presentation/` or `design_system/` file:
  `grep -rn '^\s*Widget _[a-zA-Z0-9_]*(' lib/ --include=*.dart`
  → zero results (excludes generated `*.g.dart`, which the glob already
  skips).
```

This mirrors `project.md`'s existing "T26 grep checks enforce this
constraint on every apply run" note for the Non-Material constraint —
same lightweight, no-new-tooling enforcement model, just extended to cover
this rule too. Future `tasks.md` files should copy this grep check forward
as their own final task, the same way `T26`-style Non-Material checks
already get copied forward.
