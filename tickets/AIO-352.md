# Board Execution Indicators And Notifications

# Proposal: Board execution/activity indicators and app-wide notifications

## Why

Two related visibility gaps exist today, both traced to `aion-arch/ideas/board-execution-indicators-and-notifications.md`'s explore session and re-verified against the live code during `/explore`:

1. **The Board shows nothing while work is happening.** `TicketsCubit.getTicketById` already computes `isExecuting`/`executionQueuePosition`/`executionAwaitingReview`/`executionFailureReason`/`executionCanRetry` for a Task/Bug's coding-execution run, but only `_CodingExecutionSection` (the Task-detail screen's banner) ever reads them. `TicketBoardCard`/`_CardVisual` (`tickets_board_view.dart`) render only `ticket`-field data (title/type/priority) — zero `TicketsCubit` state subscription. Worse, the underlying problem is deeper than "the widget doesn't read the field": **nothing today re-emits any state when a run starts, finishes, queues, or fails while the Board (not the Task's own detail screen) is the open view.** `_triggerOrQueueCodingExecution`/`_dequeueNext` mutate `_inFlightExecutionTaskId`/`_executionQueue` with no accompanying `emit` at all — the Board would stay blind even if `TicketBoardCard` were rewired to read the right field, because no live signal reaches it.

2. **Epic/Story SDD-stage advancement has no visibility or backgrounding at all.** `TicketsCubit.advanceSddStage` persists the stage transition, then `await`s a full chat turn (`_spawnStageChat` → `ChatCubit.runChatTurn`) before returning. The explicit gated/manual "Advance" button (`ticket_detail_screen.dart:161-166`) `await`s that whole call and only navigates to the spawned chat once it *and* its first AI reply exist — so a slow model call keeps the human parked on that one ticket's screen with no way to check other tickets in the meantime. (The passive `auto` path already wraps its own call in `unawaited(...)` at the *widget* call site, so it doesn't block that screen — but nothing computes a state for it either, so an `auto`-advancing Epic/Story is just as invisible on the Board as an explicit gated/manual one waiting on human's own click.)

Both gaps share one root cause and one fix shape: `TicketsCubit`'s existing background-execution pattern (unawaited task + computed state consumed by `getTicketById`) is real for Task coding-execution, but (a) never reaches the Board's list-shaped state, and (b) doesn't exist at all for Epic/Story stage-advancement.

A third, smaller gap: the `TicketsErrorReason` toast that's supposed to surface `codingExecutionBlocked`/`invalidParent`/`executionBudgetOverageDetected`/`executionVerificationFailed` is wired inconsistently — `ticket_detail_screen.dart:241-259`'s `BlocListener` only catches three of those four reasons (`executionVerificationFailed` is silently dropped, a **pre-existing bug**: it's classified, has a mapped message via `ticketsErrorMessage`, and is emitted by `tickets_cubit.dart:1609`, but no listener anywhere ever shows it), and `create_ticket_screen.dart:153-164`'s separate `BlocListener` duplicates the same generic pattern for a screen where these reasons never realistically fire. Neither the Board (`tickets_list_screen.dart:304-313`'s listener only handles batch-trash) nor Documentation nor Settings ever sees a `TicketsErrorReason` toast today.

## What we're building

**1. Board card indicator (Task, Bug, Epic, Story).** A compact badge on `TicketBoardCard` reflecting live cubit state:
- Task/Bug: reuses `isExecuting`/`executionQueuePosition` exactly (a spinning-gear "Running" badge, or a stack-glyph "Queued #N" badge).
- Epic/Story: a new, parallel `isAdvancingStage` (bool) — a "Advancing to `<stage>`" badge — computed the same way `isExecuting` is, from a new in-memory in-flight set.
- **Explicitly excluded from the Board card**: `executionAwaitingReview`/`executionFailureReason` (and their new stage-chat equivalents). Both require an async, per-ticket persisted-comment lookup (`_executionSucceededWithPr`/`_computeExecutionFailure`, and this change's `_computeStageAdvanceFailure`) — there is no batch/bulk query on `CommentRepository` (confirmed: it exposes only `getCommentsForTicket(String ticketId)`, one ticket at a time). Computing these for every visible Board card (up to 50 per page) would mean up to 50 extra DB round-trips just to render the Board. The Task/Bug/Epic/Story detail screen's own banner still shows these in full, as today; the notification half of this change (below) also still fires a toast the moment a failure/overage/awaiting-review happens, regardless of which screen is open. **This is a deliberate scope-narrowing from the idea file's Q1 answer ("reuse isExecuting/executionQueuePosition/executionAwaitingReview/executionFailureReason exactly") — flagging for reviewer sign-off since it means the Board card alone won't show "failed"/"needs review" as a resting state, only "running"/"advancing"/"queued".**

**2. `advanceSddStage` becomes non-blocking, with board-visible state.** Split into a fast, `await`ed "create the chat ticket + post its context comment" half (returns the chat id quickly, unchanged from the caller's perspective — the explicit Advance button still gets a `Future<String?>` chat id to navigate to) and an `unawaited` "run the AI turn" half. A new in-memory in-flight set (`_inFlightStageAdvanceIds`) — mirroring `_inFlightExecutionTaskId` — drives `isAdvancingStage` for both the Epic/Story ticket (Board badge, detail-screen banner) and, while the human is looking at the freshly-created chat ticket itself, a "Waiting for reply…" indicator (since navigation now happens *before* the AI reply lands, not after). No FIFO queue equivalent to `_executionQueue`: unlike coding-execution, stage chats don't share an exclusive resource (no git worktree), so multiple Epic/Story stage-advances can run fully concurrently — `_inFlightStageAdvanceIds` is a plain `Set`, not a queue.

**3. Stage-advance failure surfacing.** A new `sddStageFailureReason`/`sddStageCanRetry` pair (mirroring `executionFailureReason`/`executionCanRetry`), computed from the same "most recent comment on the most recent stage chat" pattern, with a manual-only retry control (no new `AutomationContext` — the idea file explicitly rules this out, and there's no analogous "verify gate" to auto-retry against for a plain conversational stage chat).

**4. App-wide `TicketsErrorReason` toast.** Relocates toast-listening from `ticket_detail_screen.dart` + `create_ticket_screen.dart` to `WorkspaceNavShell` (`core/routing/workspace_nav_shell.dart`), confirmed to sit above every `/workspace/*` route including Settings (`app_router.dart`'s single `ShellRoute` wraps Tickets, Documentation, and Settings alike). Every `TicketsErrorReason` value gets a toast via one exhaustive `switch` — fixing the `executionVerificationFailed` gap as a byproduct, and giving the Board its first-ever error toast (today a `TicketsError` on the Board renders as an inline full-page message via `ticketsErrorMessage`, never a toast; that inline rendering is unchanged, this is additive coverage for cases that don't already have it). Adds the new `sddStageAdvanceFailed` reason (item 3) to the same switch.

## Out of scope

- A persistent notification center (bell icon, read/unread history) — explicitly deferred by the idea file until Aion has genuine parallel execution; a single-slot coding-execution queue plus now-concurrent-but-rare stage-advances don't yet justify the investment.
- `AutomationContext`/`AutomationConfidence`/`AutomationSettingsRepository` — untouched. This change is execution-mechanics + visibility only; no new persisted setting, no new trigger-confidence gate.
- Board-card treatment of `executionAwaitingReview`/`executionFailureReason` (and the new stage-chat equivalents) — see the scope-narrowing note above.
- Any change to `TicketRepository`/DAO/drift schema — every new field is either in-memory (`_inFlightStageAdvanceIds`) or derived the same way `executionFailureReason` already is (walking existing `CommentRepository` data). No new persisted column.
- `board-task-ordering-indication` (a sibling explored idea, also touching `TicketBoardCard` for a "blocked" badge) — a separate proposal; this change's `_CardVisual` edit should leave clear room for that badge to land alongside this one later, not conflict with it.
