# Spec delta: New-project onboarding — attach-to-existing-project flow

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/projects.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (17/18 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Delta against `aion-arch/specs/projects.md` and `aion-arch/specs/tickets.md`.

## ADDED behaviors

### Gitignore-confirmation gate (projects.md)

- When a user picks a directory for a new project (desktop only) and that
  directory already contains a `.git` entry, `NewProjectScreen` shows an
  inline banner, before submission, offering to append `.aion/` and
  `tickets/` to that repo's `.gitignore` (creating the file if absent). A
  checkbox controls this, checked by default.
- On submit, if the directory was already a git repo:
  - `CreateProjectCubit` no longer calls `git init` (it's already a repo).
  - If the checkbox was checked, `.aion/`/`tickets/` are appended to
    `.gitignore` before any bookkeeping files are written.
  - If unchecked, project creation proceeds unchanged, and a one-shot
    toast (`AppToast.show`) warns that `.aion/`/`tickets/` will be tracked
    in the target repo's own history unless excluded manually later.
- This gate applies to every directory chosen through `NewProjectScreen` —
  there is no separate "Attach to existing project" screen or entry point.
  A brand-new empty directory is unaffected (no `.git` present, gate never
  fires, behavior is exactly what it is today).

### Discoverability for attaching an existing codebase (projects.md)

- `NewProjectScreen`'s directory-picker hint text is updated to state that
  an existing codebase is a valid choice, not only an empty folder.

### Opt-in codebase summarization (tickets.md)

- Immediately after a project is created from a directory that was already
  a git repository, the ticket list screen shows a one-time, dismissible
  banner offering to scan the codebase and draft starting `signal`
  tickets. The offer never reappears once dismissed, a depth is chosen, or
  the app is restarted — it is not a persisted, always-available action in
  this proposal.
- Two depths, user-selected:
  - **Shallow** — a single non-tool-enabled model turn given the detected
    stack (`ProjectStackDetector`) and a depth-limited directory listing
    (filenames only, no file content). Cheap, bounded token cost.
  - **Full** — a tool-enabled agentic turn, isolated in a fresh `git
    worktree` (never the developer's real checkout), free to read the
    project's files. Mirrors the existing coding-execution worktree
    pattern exactly, including guaranteed worktree cleanup.
- Either depth's final reply is parsed into one or more findings, each
  persisted as its own root `signal` ticket (title + description).
  Shallow-depth findings carry a leading
  `"[Shallow scan — structural only, may be incomplete]"` line in their
  description. Each finding ticket is linked (via the existing
  Page/Resource-style linked-ticket mechanism, `TicketLinkType.relatesTo`)
  back to a parent "Codebase Analysis — `<project name>`" `signal` ticket
  that records the run itself and hosts the run's `chat` child (full depth
  only, where the agentic turn's streamed progress is visible as chat
  comments).
- Every resulting `signal` ticket flows through the existing, unmodified
  signal→epic promotion mechanism (`TicketsCubit.promoteSignalToEpic`) —
  no automatic ticket creation beyond what the user explicitly requested
  by picking a depth.

## MODIFIED behaviors

### `CreateProjectCubit.submit` (projects.md)

- Gains an `appendGitignore` parameter (default `true`), consulted only
  when the resolved `rootPath` is already a git repository. Previously,
  `submit` always ran `git init` unconditionally on desktop; it now only
  does so when `rootPath` is not already a repo.

### `CreateProjectSuccess` state (projects.md)

- Gains a `wasExistingGitRepo` field so the widget layer can drive the
  decline-warning toast and the downstream summarization offer without
  re-deriving the git-repo check that already ran once during submission.

### `ActiveProjectCubit.switchTo` (projects.md)

- Gains an `offerCodebaseAnalysis` parameter (default `false`).
  `ActiveProjectOpen` carries this flag; a new
  `consumeCodebaseAnalysisOffer()` method clears it after the ticket-list
  screen has shown the offer once.

## Non-goals / explicitly out of scope

- No `Project`/`RegistryDatabase` schema changes — the summarization
  offer's "shown once" behavior is in-memory only, not persisted.
- No `Ticket.suggestedType` field, no Epic-vs-Bug promotion classification
  — both remain scoped to the future Inbox proposal.
- No new restricted/read-only agentic tool tier — full-depth summarization
  reuses the existing binary `toolsEnabled` mechanism, worktree-isolated.
- No standing, re-triggerable "analyze codebase" entry point (e.g. from
  Settings) — the offer is one-shot, tied to project creation only.
- No Inbox app-level feature of any kind (separate future proposal).
