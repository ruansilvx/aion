# Design: Ticket search pagination

Page size constant: **50**, defined once as `TicketsCubit._pageSize` and
threaded down as an explicit `limit` argument everywhere else (DAO and
repository stay dumb — they take whatever `limit`/`offset` they're given,
no hidden default).

## 1. Domain layer

### New: `domain/entities/ticket_search_page.dart`

```dart
// domain/entities/ticket_search_page.dart — TicketSearchPage entity (domain layer).

import 'package:equatable/equatable.dart';

import 'package:aion/features/tickets/domain/entities/ticket.dart';

/// One page of results from [TicketRepository.searchTickets].
class TicketSearchPage extends Equatable {
  /// Creates a [TicketSearchPage] carrying [tickets] and [hasMore].
  const TicketSearchPage({required this.tickets, required this.hasMore});

  /// The tickets returned for this page, in the same order the query
  /// specified (creation date descending, or FTS relevance when a text
  /// query was set).
  final List<Ticket> tickets;

  /// Whether at least one more ticket exists beyond [tickets] for the same
  /// query/filters — `true` means a subsequent page (a call with a larger
  /// `offset`) would return further results.
  final bool hasMore;

  @override
  List<Object?> get props => [tickets, hasMore];
}
```

### Modified: `domain/repositories/ticket_repository.dart`

```dart
/// Returns one page of tickets matching every non-null filter (ANDed):
/// [status], [type], [priority] restrict to an exact match on that field;
/// [query] full-text-matches against title/description. All filter
/// parameters omitted/null is equivalent to paginating [getAllTickets].
/// Ordered by relevance when [query] is set, otherwise by creation date
/// descending. Excludes trashed tickets, same as [getAllTickets]. Returns
/// at most [limit] tickets starting after the first [offset] matches, plus
/// whether further matches exist beyond this page.
Future<TicketSearchPage> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
  required int limit,
  int offset = 0,
});
```

(Signature change: adds `required int limit` and `int offset = 0`; return
type changes from `Future<List<Ticket>>` to `Future<TicketSearchPage>`.)

## 2. Data layer

### Modified: `data/daos/ticket_dao.dart`

`TicketDao.searchTickets` gains `required int limit, int offset = 0` and
applies them mechanically to both branches — no `+1` trick here, that
decision lives in the repository (see below); the DAO just honors
whatever `limit`/`offset` it's given:

- Typed-select branch: append `..limit(limit, offset: offset)` to the
  existing `select(ticketsTable)` statement chain.
- Raw FTS branch: append `'LIMIT ? OFFSET ?'` to the SQL string and add
  `Variable(limit)`, `Variable(offset)` to `variables` (after the
  existing status/type/priority variables).

### Modified: `data/repositories/drift_ticket_repository.dart`

```dart
@override
Future<TicketSearchPage> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
  required int limit,
  int offset = 0,
}) async {
  final rows = await _db.ticketDao.searchTickets(
    query: query,
    status: status,
    type: type,
    priority: priority,
    limit: limit + 1,
    offset: offset,
  );
  final hasMore = rows.length > limit;
  final page = hasMore ? rows.take(limit).toList() : rows;
  return TicketSearchPage(
    tickets: page.map(_toEntity).toList(),
    hasMore: hasMore,
  );
}
```

## 3. Presentation layer — `TicketsCubit`

New private state (not part of `TicketsState` — mirrors how the current
search filters are already screen-local, not cubit state):

```dart
static const _pageSize = 50;

String? _lastQuery;
TicketStatus? _lastStatus;
TicketType? _lastType;
TicketPriority? _lastPriority;

/// Bumped on every call that replaces the list wholesale (searchTickets,
/// createTicket, updateTicketStatus, trashTicket, trashTickets). A
/// loadMoreTickets() call in flight discards its result if this changes
/// before it resolves — the guard against the "filter/query changes (or
/// a mutation refresh happens) while a page is loading" race.
int _searchGeneration = 0;
```

`_listSnapshot(TicketsState)` — a private helper (not a new domain
entity; an internal `({List<Ticket> tickets, bool hasMore})` record,
never exposed outside the cubit) shared by `loadMoreTickets()` — mirrors
the existing "pull the current list out of state" `switch` pattern
already used by `createTicket`/`updateTicketStatus`:

```dart
({List<Ticket> tickets, bool hasMore})? _listSnapshot(TicketsState s) =>
    switch (s) {
      TicketsLoaded(:final tickets, :final hasMore) =>
        (tickets: tickets, hasMore: hasMore),
      TicketCreated(:final tickets, :final hasMore) =>
        (tickets: tickets, hasMore: hasMore),
      TicketStatusUpdated(:final tickets, :final hasMore) =>
        (tickets: tickets, hasMore: hasMore),
      TicketsBatchTrashed(:final tickets, :final hasMore) =>
        (tickets: tickets, hasMore: hasMore),
      TicketsLoadMoreFailed(:final tickets, :final hasMore) =>
        (tickets: tickets, hasMore: hasMore),
      _ => null, // TicketsLoadingMore and every *ing/non-list state: no snapshot
    };
```

Returning `null` for `TicketsLoadingMore` is deliberate — it's what makes
`loadMoreTickets()`'s guard double as the concurrency debounce (see
below): once a load-more is in flight, there is no snapshot to read, so a
second trigger firing before the first resolves is a clean no-op.

### `searchTickets` (modified)

```dart
Future<void> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
}) async {
  final generation = ++_searchGeneration;
  _lastQuery = query;
  _lastStatus = status;
  _lastType = type;
  _lastPriority = priority;

  final hasVisibleList = switch (state) {
    TicketsLoaded() || TicketCreating() || TicketCreated() ||
    TicketStatusUpdating() || TicketStatusUpdated() ||
    TicketsBatchTrashed() || TicketsLoadingMore() ||
    TicketsLoadMoreFailed() => true,
    _ => false,
  };
  if (!hasVisibleList) emit(const TicketsLoading());

  try {
    final page = await _repository.searchTickets(
      query: query, status: status, type: type, priority: priority,
      limit: _pageSize,
    );
    if (generation != _searchGeneration) return; // superseded by a newer call
    emit(TicketsLoaded(page.tickets, hasMore: page.hasMore));
  } catch (e) {
    if (generation != _searchGeneration) return;
    emit(TicketsError(e.toString()));
  }
}
```

`_searchGeneration` is bumped *before* the `await`, so any
`loadMoreTickets()` already in flight from the previous filter state is
guaranteed to see a mismatched generation when it resolves and discard
its result — this is what "filter/query change mid-scroll resets
pagination" actually means at the code level: not just "the next
`searchTickets` call replaces the list" (true today), but "a stale
in-flight `loadMoreTickets()` from before the change can't silently
append onto the new, unrelated list."

### `loadMoreTickets` (new)

```dart
/// Fetches the next page for whatever query/filters [searchTickets] was
/// last called with, appending to the currently loaded list. No-ops if
/// the cubit isn't in a settled list-shaped state with more results
/// available (covers: nothing loaded yet, a load-more already in flight,
/// or the last page already reached the end) — this doubles as the
/// concurrency guard against a fast/bouncy scroll firing the trigger
/// multiple times before the first request resolves. Emits
/// [TicketsLoadingMore] (carrying the tickets loaded so far) immediately,
/// then [TicketsLoaded] (carrying the combined list) on success, or
/// [TicketsLoadMoreFailed] (carrying the tickets loaded so far, unchanged)
/// if the repository call throws — the existing rows are never discarded
/// by a failed load-more.
Future<void> loadMoreTickets() async {
  final snapshot = _listSnapshot(state);
  if (snapshot == null || !snapshot.hasMore) return;

  final currentTickets = snapshot.tickets;
  final generation = _searchGeneration;
  emit(TicketsLoadingMore(currentTickets));

  try {
    final page = await _repository.searchTickets(
      query: _lastQuery, status: _lastStatus, type: _lastType,
      priority: _lastPriority, limit: _pageSize, offset: currentTickets.length,
    );
    if (generation != _searchGeneration) return;
    emit(TicketsLoaded([...currentTickets, ...page.tickets], hasMore: page.hasMore));
  } catch (e) {
    if (generation != _searchGeneration) return;
    emit(TicketsLoadMoreFailed(currentTickets, hasMore: snapshot.hasMore));
  }
}
```

### `createTicket` / `updateTicketStatus` / `trashTicket` / `trashTickets`
(modified refresh step only)

Each of these already computes `currentTickets` via a `switch` before
doing its work (see `flutter-conventions.md`'s documented pattern) — add
the new list-shaped states (`TicketsLoadingMore`, `TicketsLoadMoreFailed`)
to that existing switch so a mutation triggered mid-scroll or after a
failed load-more doesn't fall through to the `_ => <Ticket>[]` default.
Bump `_searchGeneration` at the very start of each method (same reasoning
as `searchTickets`: invalidate any in-flight `loadMoreTickets()` before
this method's own refresh lands). Replace the refresh call:

```dart
// before
final tickets = await _repository.getAllTickets();
emit(TicketCreated(tickets)); // or TicketStatusUpdated / TicketsBatchTrashed(tickets, trashedCount)

// after
final page = await _repository.searchTickets(
  query: _lastQuery, status: _lastStatus, type: _lastType, priority: _lastPriority,
  limit: max(_pageSize, currentTickets.length),
);
emit(TicketCreated(page.tickets, hasMore: page.hasMore));
```

`max(_pageSize, currentTickets.length)` (from `dart:math`) re-requests at
least however many tickets were already loaded, so a background status
update (e.g. a board drag) never collapses an infinite-scrolled list back
down to one page — this is the "favor the better UX" call flagged during
`/explore`, not the cheaper "always just refetch page one" option.
`trashTicket`'s non-detail-screen branch (`emit(TicketsLoaded(await
_repository.getAllTickets()))`) gets the identical treatment.

`getValidParentCandidates` and `updateTicketParent`'s cycle-detection walk
keep calling `_repository.getAllTickets()` unchanged — see proposal.md's
Non-goals.

## 4. Presentation layer — `TicketsState`

Modified states gain `hasMore` (constructor + field + `props`):
`TicketsLoaded`, `TicketCreated`, `TicketStatusUpdated`,
`TicketsBatchTrashed` (the last keeps its existing `trashedCount` field
too).

Two new states, following the existing `ing`/`ed` and error-state
conventions:

```dart
/// A [TicketsCubit.loadMoreTickets] call is in flight. Carries the tickets
/// loaded so far (unchanged) so the list stays fully visible with a
/// bottom-of-list spinner, rather than blanking out mid-scroll.
class TicketsLoadingMore extends TicketsState {
  /// Creates a [TicketsLoadingMore] state carrying the already-loaded
  /// [tickets].
  const TicketsLoadingMore(this.tickets);

  /// The tickets loaded before this page request started.
  final List<Ticket> tickets;

  @override
  List<Object?> get props => [tickets];
}

/// A [TicketsCubit.loadMoreTickets] call failed. Carries the tickets
/// loaded before the failed attempt (unchanged — a failed load-more never
/// discards what's already on screen) and the [hasMore] value from before
/// the attempt, so the UI can offer a retry rather than silently treating
/// this as the end of the list.
class TicketsLoadMoreFailed extends TicketsState {
  /// Creates a [TicketsLoadMoreFailed] state carrying [tickets] and
  /// [hasMore].
  const TicketsLoadMoreFailed(this.tickets, {required this.hasMore});

  /// The tickets loaded before the failed load-more attempt.
  final List<Ticket> tickets;

  /// Whether another page might still exist — carried over from the state
  /// before the failed attempt, since the failure itself provides no new
  /// information about how many results remain.
  final bool hasMore;

  @override
  List<Object?> get props => [tickets, hasMore];
}
```

## 5. Presentation layer — `TicketsListScreen`

- `_currentTickets(TicketsState)`: add `TicketsLoadingMore` and
  `TicketsLoadMoreFailed` cases (currently missing — without this, a
  scroll-triggered load or a failed retry would blank the list).
- New `_hasMore(TicketsState)` helper, mirroring `_currentTickets`'
  shape, reading `hasMore` off every list-carrying state (`false` for
  `TicketsLoadingMore` and every non-list state — while a page is loading
  there's nothing new to trigger on, and non-list states render no list
  at all).
- New `ScrollController _scrollController` — created in `initState`,
  disposed in `dispose`, with a listener:

  ```dart
  void _handleScroll() {
    if (!_scrollController.hasClients) return;
    final position = _scrollController.position;
    if (position.pixels >= position.maxScrollExtent - 400) {
      context.read<TicketsCubit>().loadMoreTickets();
    }
  }
  ```

  400 logical pixels of lookahead (~2-3 row heights) so the next page is
  in flight before the user hits the physical bottom. The concurrency
  guard against this firing repeatedly while already near the bottom is
  entirely on the cubit side (`loadMoreTickets()`'s `_listSnapshot`
  no-op) — no debounce timer needed here.
- `_buildTicketsBody`'s list-mode `ListView.separated` gets
  `controller: _scrollController` and a footer row appended when
  `state is TicketsLoadingMore || state is TicketsLoadMoreFailed`:
  `itemCount: tickets.length + (showFooter ? 1 : 0)`, with the last index
  rendering a new private `_TicketListFooter` widget (small `AppSpinner`
  centered when loading, or a tappable retry row — icon + text, calling
  `context.read<TicketsCubit>().loadMoreTickets()` again — when the last
  attempt failed). When `hasMore` is `false` and nothing is loading, no
  footer renders at all — no "end of results" caption, keeping this
  consistent with how the rest of the list has no persistent chrome
  today.
- Board mode: a new floating "Load more" button, visible only when
  `_viewMode == _TicketViewMode.board && _hasMore(state) &&
  !selection.isActive`, positioned bottom-left (`left: 18, bottom: 24`)
  so it doesn't collide with `AppFab` (bottom-right) or
  `TicketSelectionBar` (full-width, which already hides the FAB via the
  existing `selection.isActive` branch — the board load-more button
  follows the same visibility rule). Tapping it calls the same
  `context.read<TicketsCubit>().loadMoreTickets()` the list mode's scroll
  trigger calls — one cubit method, two UI triggers.

## Edge cases — explicit mapping to the mechanics above

| Edge case | Mechanism |
|---|---|
| End of results | `hasMore: false` on the last page (via the `limit+1` trick) → `_listSnapshot`/`_hasMore` both read false → no scroll trigger fires, no footer renders, board's "Load more" button hides. |
| Empty search | First page returns 0 tickets, `hasMore: false` → existing empty-state UI in `_buildTicketsBody` renders unchanged (untouched by this change) — no footer, no load-more button (both gated on `tickets.isNotEmpty` implicitly, since `_buildTicketsBody` returns early on `tickets.isEmpty`). |
| Filter/query change mid-scroll | `searchTickets()` always resets `_lastQuery`/etc. and bumps `_searchGeneration` before its own fetch; the emitted `TicketsLoaded` *replaces* (not appends) the list. A `loadMoreTickets()` in flight from before the change is discarded via the generation check when it resolves. |
| Concurrent scroll-trigger firing | `loadMoreTickets()`'s `_listSnapshot(state)` returns `null` while `state is TicketsLoadingMore`, so a second trigger before the first resolves is a clean no-op — no timer, no flag beyond the state machine itself. |
| Error during load-more | `TicketsLoadMoreFailed` carries the pre-attempt `tickets` list unchanged (never discarded) plus the pre-attempt `hasMore`, so the footer shows a retry control instead of the screen collapsing to the full-screen `TicketsError` view (which would lose the loaded rows). |
| Mutation (create/status-update/trash) mid-pagination | Refresh calls switch from `getAllTickets()` to paginated `searchTickets(limit: max(pageSize, currentCount))`, preserving however much was already loaded and re-applying the active filters instead of silently showing every ticket. |

# Aion — Ticket Search Pagination Specification

Implementation-ready spec for **pagination on `TicketsListScreen`**. The screen's flat ticket list currently fetches its entire matching result set in one unbounded query; this change introduces real `LIMIT`/`OFFSET` pagination (**50 tickets per page**) behind three additive UI components:

1. An **infinite-scroll loading footer** appended to the flat `ListView` while the next page is fetching.
2. An **error / retry footer** in the same slot when a page-load attempt fails.
3. A floating **"Load more" button** for the board (Kanban) view, which has six independent per-status scroll columns and therefore no single owning scroll container to hook an automatic trigger onto.

No new screens. All three components attach to the existing `/tickets` route and do not change its header, search field, filter row, list, or board structure — they are strictly additive: one appended list item (states 1–2) and one new floating button (state 3).

- **No Material widgets.** Build from `flutter/widgets.dart` primitives: `GestureDetector` + `DecoratedBox`/`Container` for the tappable rows and the button, `Align`/`Positioned` for floating placement. Reuse the existing **`AppSpinner`** (do **not** redesign it) instead of `CircularProgressIndicator`. No `Card`, `ElevatedButton`, `ListTile`, `InkWell`, `Scaffold`, `SnackBar`, or `CircularProgressIndicator` anywhere.
- `c` = active `AionColors`; `a` = theme `fillAlpha` (Arctic `0.11` / Obsidian `0.16`). `isDark` = Obsidian.
- Both themes share one code path; only token values differ. Where a component is identical across themes it is stated explicitly.
- Companion mockups: `Aion Ticket Search Pagination Mockups.dc.html` — loading footer `1a`, error/retry footer `2a`, board "Load more" `3a`, loading-footer anatomy `4a`, error/retry states `5a`, board-button states `6a` (Arctic + Obsidian throughout).

## 1. List-footer loading state

Rendered as the **last item** in the flat list's `ListView` (index `itemCount` when `hasNextPage && isLoadingNextPage`), triggered automatically by scroll proximity to the bottom (see §4). It sits below dozens of ticket rows, so it must read as a quiet "more is coming" signal — compact, centered, no text, no card chrome.

### 1.1 Container

| Property | Value |
|---|---|
| Width | full list width (`double.infinity`) |
| Padding | `EdgeInsets.symmetric(vertical: 20)` (= `AionSpacing.sp20`), horizontal `0` |
| Alignment | `Alignment.center` — spinner centered both axes |
| Fill | none — inherits the list body's `c.surface` |
| Border | **none** — unlike a ticket row, this slot has no bottom `1px c.border` divider (it is the terminal item, and a divider under a spinner reads as a broken empty row) |
| Radius | n/a |
| Shadow | none |

### 1.2 Spinner

Reuse **`AppSpinner`** verbatim — its stroke, colors, and animation are already specified and must not be re-derived here.

| Property | Value |
|---|---|
| Size | `22×22` (the AppSpinner "inline/small" size) |
| Track color | `c.border` |
| Arc color | `c.primary` |
| Placement | single child of the centered container; no leading/trailing text |

```dart
// last ListView item when a next page is loading
const Padding(
  padding: EdgeInsets.symmetric(vertical: 20),
  child: Center(child: AppSpinner(size: 22)),
)
```

### 1.3 States

This component has **no interactive states** — it is non-tappable, purely presentational, and shown only while `isLoadingNextPage == true`. It is removed from the tree the instant the page resolves (→ new rows) or fails (→ §2).

### 1.4 Theme note

**Identical structure both themes.** Only the AppSpinner's own token colors differ (Arctic arc `c.primary #2E86D4` on track `#D6E0EA`; Obsidian arc `#9366FF` on track `#232C40`).

## 2. List-footer error / retry state

Rendered in the **same last-item slot** when a page-load attempt fails (`hasNextPage && nextPageError != null`). A single **tappable row** — an icon + short text — that retries the failed page fetch on tap. This is a soft, recoverable, inline failure in an otherwise-fine list, **not** a blocking error screen, so `danger` is used restrained: a `danger`-tinted icon and text on the normal `c.surface` background, with **no heavy red fill** in the resting state.

### 2.1 Anatomy

- Widget: `GestureDetector(onTap: retry)` wrapping a `Focus` + `DecoratedBox` + `Padding` + centered `Row`.
- Row: `mainAxisAlignment: center`, `mainAxisSize: max`, `gap: 9` (`SizedBox(width: 9)`), `crossAxisAlignment: center`.
- **Icon:** retry / reload glyph (Phosphor **Light** `arrow-clockwise`), **16px**, color `c.danger`.
- **Label:** `AionText.bodySm` (13.5, w400) `.copyWith(color: c.danger)`, e.g. `"Couldn't load more — tap to retry"` (exact string is l10n's concern).

### 2.2 Sizing shared across states

| Property | Value |
|---|---|
| Width | full list width |
| Outer padding | `EdgeInsets.symmetric(vertical: 12, horizontal: 16)` |
| Inner (hit) radius | `AionRadius.iconBtnSm` (8) — the fill/ring is drawn on the inner tappable area, inset from the list edges |
| Icon size | `16` |
| Icon color | `c.danger` (all states) |
| Text style | `AionText.bodySm.copyWith(color: c.danger)` (all states) |
| Border (row) | none — divider-less, like §1 |

### 2.3 Default state

| Property | Value |
|---|---|
| Fill | `Color(0x00000000)` (bare `c.surface` shows through — no fill, matching this project's existing no-fill convention, e.g. `_SelectModeToggleState`) |
| Ring | none |
| Transform | none |

### 2.4 Hover state (desktop / web build)

| Property | Value |
|---|---|
| Fill | `c.danger.withValues(alpha: a)` — a soft danger wash (Arctic `0.11` / Obsidian `0.16`) |
| Ring | none |
| Transform | none |

### 2.5 Focused state (keyboard)

| Property | Value |
|---|---|
| Fill | `Color(0x00000000)` |
| Ring | `BoxShadow(color: c.danger.withValues(alpha: isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` — a solid 3px ring, matching the design-system focus-ring recipe but **toned to `danger`, not `primary`** (see rationale) |
| Transform | none |

**Rationale for a `danger` focus ring:** the design system's default focus ring is `primary`, but this control is wholly `danger`-colored (icon + text). A `primary` ring wrapped around `danger` content reads as two competing accent colors on one small element. Toning the ring to `danger` keeps the control monochromatic and unambiguous. This is the one intentional deviation from the standard ring token; opacity values (`0.30` / `0.16`) are unchanged.

### 2.6 Pressed state

| Property | Value |
|---|---|
| Fill | `c.danger.withValues(alpha: a + 0.06)` — a slightly deeper wash than hover (Arctic `0.17` / Obsidian `0.22`) |
| Ring | none |
| Transform | `scale(0.98)` |

### 2.7 Disabled / error states

- **Disabled:** n/a — the retry row is only shown when a retry is possible; it is never rendered disabled.
- **Error:** this component *is* the error surface; there is no nested error state.

### 2.8 Theme note

**Identical structure both themes.** Token values differ: Arctic `danger #CE3D54`, washes `0.11`/`0.17`, ring `0.16`; Obsidian `danger #F1546C`, washes `0.16`/`0.22`, ring `0.30`.

## 3. Board-mode "Load more" button

A floating, pill-shaped button anchored **bottom-left** of the board view at `Positioned(left: 18, bottom: 24)` — the existing `AppFab` ("+ New ticket") already floats bottom-right at `right: 18, bottom: 24`. Because both occupy the same floating-chrome role in the same view, the "Load more" button takes a **secondary / outlined** treatment (surface fill, `borderStrong` outline) rather than `AppFab`'s solid `primary` fill, so the create action stays the single visually-dominant control. Shown **only when more tickets are available** (`hasNextPage == true`); otherwise it is not built at all — **no disabled variant**.

### 3.1 Anatomy

- Widget: `Positioned(left: 18, bottom: 24, child: GestureDetector(onTap: loadNextPage, child: Focus(...DecoratedBox...)))`.

## 4. List pagination behavior (flat list)

- **Page size:** 50 tickets (`LIMIT 50 OFFSET page * 50`).
- **Trigger:** attach a `ScrollController` listener to the flat `ListView`; when `position.pixels >= position.maxScrollExtent - 400` and `hasNextPage && !isLoadingNextPage && nextPageError == null`, fetch the next page. The `400px` pre-fetch threshold loads the next page before the user hits the exact bottom, so the loading footer (§1) rarely stalls the scroll.
- **Footer item:** the `ListView` builds `itemCount = rows.length + (showFooter ? 1 : 0)`, where `showFooter = hasNextPage && (isLoadingNextPage || nextPageError != null)`. The final index renders §1 (loading) or §2 (error) based on `nextPageError == null`.
- **End of list:** when `hasNextPage == false`, no footer is rendered — the last ticket row is the last item.
- **No results / first-page states** are unchanged (they remain the existing empty state and first-load spinner; this spec only covers the *next-page* footer).

## 5. Board pagination behavior

- **Page size:** 50 tickets, same query, distributed into the six status columns after fetch.
- **Trigger:** manual only — the `Positioned` "Load more" button (§3). No scroll listener (the six columns each scroll independently; there is no single owning scroll extent to observe).
- **Visibility:** the button is built iff `hasNextPage == true`; it appends the next 50 tickets across the columns on tap, then re-evaluates `hasNextPage`.
