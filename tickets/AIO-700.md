# Design: Define type-compatibility matrix

No new widgets, no new BLoC states, no visual changes — this is a
validation-logic change layered onto existing structures. See
[proposal.md](proposal.md)'s Design gate: `NOT REQUIRED`.

## Domain layer: the matrix itself

Add a pure extension to `lib/features/tickets/domain/enums/ticket_type.dart`
(same file as the enum, since the rule is intrinsic to the type's
semantics and every value already carries a dartdoc there):

```dart
/// Structural parent/child rules between [TicketType] values. A ticket's
/// type determines which other types it may structurally parent —
/// independent of the self-parent/cycle checks [TicketsCubit] already
/// performs, which apply regardless of type.
extension TicketTypeHierarchy on TicketType {
  /// This type's rank in the epic > story > task work-breakdown chain,
  /// or `null` for a leaf type (resource/page/chat) that has no rank and
  /// can never parent anything.
  int? get _rank => switch (this) {
    TicketType.epic => 0,
    TicketType.story => 1,
    TicketType.task => 2,
    TicketType.resource || TicketType.page || TicketType.chat => null,
  };

  /// Whether a ticket of this type may structurally parent a ticket of
  /// type [child]. Leaf types (resource/page/chat) can never parent
  /// anything. A work type (epic/story/task) may parent another work
  /// type only if strictly higher in the chain (epic > story > task,
  /// e.g. task cannot parent story), and may parent any leaf type
  /// unconditionally. Same-type nesting is always rejected — a
  /// consequence of the strict-rank comparison, not a special case.
  bool canParent(TicketType child) {
    final parentRank = _rank;
    if (parentRank == null) return false;
    final childRank = child._rank;
    if (childRank == null) return true;
    return parentRank < childRank;
  }
}
```

This single `parentRank < childRank` comparison (with leaf types as
`null`-ranked, always-unparentable) produces exactly the matrix from
`proposal.md`:

| Parent \ Child | epic | story | task | resource/page/chat |
|---|---|---|---|---|
| **epic** (0) | ✗ (equal rank) | ✓ | ✓ | ✓ |
| **story** (1) | ✗ (rank check fails) | ✗ (equal) | ✓ | ✓ |
| **task** (2) | ✗ | ✗ | ✗ (equal) | ✓ |
| **resource/page/chat** (null) | ✗ | ✗ | ✗ | ✗ |

`TicketType.epic`'s existing "never receives a parent" rule is *not*
re-derived from this matrix — it stays as `TicketsCubit`'s separate
early check on the child ticket's own type (unrelated to what candidate
parent is chosen). `canParent` only answers "is parentType allowed to
parent childType," and is never even consulted when the child is an
epic, since that path already short-circuits first.

Also correct `TicketType.task`'s existing dartdoc, which currently
reads: *"A task whose `parentId` points to another task or story is the
Aion subtask convention (no dedicated type)."* — the "another task" half
of that claim becomes false under this change; task-under-task is now
rejected exactly like every other same-type pair. Reword to drop that
claim (task-under-story remains true and unaffected).

## Cubit layer: wiring the check in

`lib/features/tickets/presentation/cubit/tickets_cubit.dart`:

1. **`getValidParentCandidates(Ticket ticket)`** — add a
   `t.type.canParent(ticket.type)` clause to the existing `.where(...)`
   filter, alongside the current self/descendant exclusion:
   ```dart
   return all
       .where((t) =>
           t.id != ticket.id &&
           !descendantIds.contains(t.id) &&
           t.type.canParent(ticket.type))
       .toList();
   ```

2. **New method `getValidParentCandidatesForType(TicketType childType)`**
   — for `CreateTicketScreen`, where the ticket being created doesn't
   exist yet (no id, no descendants to exclude), mirroring how
   `getAllTickets()` currently serves that screen but adding the type
   filter:
   ```dart
   Future<List<Ticket>> getValidParentCandidatesForType(
     TicketType childType,
   ) async {
     final all = await _repository.getAllTickets();
     return all.where((t) => t.type.canParent(childType)).toList();
   }
   ```
   `getAllTickets()` itself stays unchanged (other callers may still
   want the unfiltered set — none currently do, but the method isn't
   being repurposed).

3. **`updateTicketParent(Ticket ticket, String? newParentId)`** — add a
   type-compatibility check after the existing self-parent/epic/cycle
   checks, before the persist call. Requires fetching the candidate
   parent's own type via `getTicketById`, since only its id is known at
   this point:
   ```dart
   if (newParentId != null) {
     // ...existing self, epic, and cycle checks unchanged...
     final candidateParent = await _repository.getTicketById(newParentId);
     if (candidateParent == null ||
         !candidateParent.type.canParent(ticket.type)) {
       await _emitInvalidParent(ticket.id);
       return;
     }
   }
   ```
   Reuses the existing `TicketsErrorReason.invalidParent` — no new enum
   value. Update this method's dartdoc to mention the new rejection
   cause alongside self-reference, cycles, and the epic-child case.

## Presentation layer

### `CreateTicketScreen`

`lib/features/tickets/presentation/screens/create_ticket_screen.dart`:

- Change the `candidatesLoader` passed to `TicketParentPicker` from
  `() => context.read<TicketsCubit>().getAllTickets()` to
  `() => context.read<TicketsCubit>().getValidParentCandidatesForType(_selectedType)`.
  Because this is a closure reading the `_selectedType` field (not a
  captured snapshot), it always reflects the current selection at the
  moment it's invoked — no extra plumbing needed for that part.
- Broaden the type dropdown's `onChanged` handler: today it clears
  `_selectedParentId` only when the new type is `epic`. Change this to
  clear `_selectedParentId` unconditionally on every type change —
  simplest way to guarantee no stale, now-incompatible parent selection
  survives a type switch (e.g. task → story after a task was already
  chosen as parent, which is no longer valid: task cannot parent task,
  and story doesn't accept a task as a *child* filter issue here, but
  the reverse direction — previously chosen parent becomes invalid for
  the new child type — is exactly what this guards):
  ```dart
  onChanged: (v) => setState(() {
    _selectedType = v;
    _selectedParentId = null;
  }),
  ```

### `TicketParentPicker`

`lib/features/tickets/presentation/widgets/ticket_parent_picker.dart`:

Latent bug this change surfaces: `_loadCandidates()` currently only
runs once, in `initState`. `CreateTicketScreen`'s `candidatesLoader`
closure will now return a *different* result depending on
`_selectedType` at call time, but the picker never calls it a second
time after mount — so switching the type dropdown wouldn't actually
refresh the candidate list shown in the overlay without this fix.

Add a `didUpdateWidget` override that re-fetches when `ticketType`
changes:
```dart
@override
void didUpdateWidget(covariant TicketParentPicker oldWidget) {
  super.didUpdateWidget(oldWidget);
  if (widget.ticketType != oldWidget.ticketType) {
    _loadCandidates();
  }
}
```
This also naturally covers `TicketDetailScreen`'s inline trigger (whose
`ticketType` is effectively fixed per ticket, so this is a no-op there)
without needing variant-specific branching.

## No schema/migration impact

`TicketType` is unchanged as a value set — this is pure validation logic
layered on existing reparenting paths. No drift schema changes, no
`build_runner` step required.
