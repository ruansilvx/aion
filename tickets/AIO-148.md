# Automatic Time Tracking For Tickets

# Proposal: Automatic Time Tracking for Tickets

## What we're building

System-measured, automatic `timeSpent` logging for every AI-driven chat
turn — coding-execution or plain advisory chat alike — by instrumenting
`ChatCubit.runChatTurn`, the one shared chokepoint every such turn already
passes through regardless of provider. `runChatTurn` gains a wall-clock
start/end measurement around its model call and, on completion, calls
`TicketRepository.addTimeSpent(chat.parentId, elapsedMinutes)` itself.
This replaces today's only time-logging path — the model-invoked
`log_time` tool call — which this change removes entirely rather than
keeping alongside the new mechanism.

## Why

Raised in `aion-arch/ideas/automatic-time-tracking-for-tickets.md`:
today's `timeSpent` is either a plain manual field, or whatever a model
chooses to self-report via `log_time` — a guessed `minutes` value the
model has no real means of grounding in actual elapsed time. That's not
good enough for the idea's stated purpose: building a trustworthy actuals
record, good enough to eventually calibrate the already-shipped
AI-suggested `estimate` feature (predicted vs. actual) against comparable
future tickets. A system-measured number is strictly more trustworthy
than a model's guess, at the cost of being an approximation of wall-clock
turn duration rather than a precise effort measurement — a tradeoff the
idea's brainstorm explicitly accepted ("it might not be precise... but we
can also have that info").

`/explore`'s grounding pass additionally found `log_time` becomes
*structurally* redundant once automatic measurement exists, not merely
overlapping with it: a tool call is only ever answered mid-stream, while
the underlying `AgentModelClient.run` call is still in flight
(`ClaudeAgentSdkClient._handleToolCallRequest`). Since `log_time` can
only ever fire from inside a `runChatTurn`-driven turn, every real
invocation of it today already happens strictly inside the exact window
automatic timing will measure. There is no scenario in the current
codebase where `log_time` covers a gap automatic measurement misses — so
rather than keep both and suppress an overlap that's always total, this
change measures directly and removes the now-redundant tool.

## Scope: one instrumentation point, not per-provider bridge timing

The idea's initial brainstorm assumed a two-tier design — time a
coding-execution run's agent-bridge subprocess lifetime, falling back to
a chat's message-span when no bridge session exists. `/explore` found
this doesn't match how the code is actually structured: there are two
`AgentModelClient` implementations, and only one
(`ClaudeAgentSdkClient`) spawns a subprocess at all —
`AnthropicMessagesApiProvider` wraps a plain HTTP client with no bridge
process. "Bridge lifetime" was never really a coding-execution-vs-chat
distinction; it's a provider-implementation detail that doesn't
generalize. `ChatCubit.runChatTurn` is the one call every turn already
passes through regardless of which client backs it, so timing that
single method directly gives real elapsed time uniformly for every turn
— no fallback path, no session-boundary ambiguity to design around.

## Guardrails

- **Always applies, no `AutomationConfidence` gate.** Mirrors
  `log_time`'s own "additive and low-consequence" precedent — logging
  time is never something a user needs to approve or can meaningfully
  decline.
- **Minimum 1 minute per measured turn, ceiling-rounded.** `timeSpent`'s
  existing granularity is whole minutes; most conversational turns take
  well under a minute of wall-clock time, and floor-rounding those to 0
  would silently drop the majority of real turns from the actuals
  record. Every turn that made a real model call contributes at least 1
  minute.
- **Logged for every terminal outcome — success, failure, or
  cancelled.** A failed or cancelled turn still consumed real wall-clock
  time (tokens spent, possibly tool calls already executed before the
  failure/cancellation); excluding those would systematically
  undercount actuals on exactly the tickets that took the most retries.
- **Skipped when there's no ticket to log against.** A chat with no
  resolvable parent (e.g. an Inbox-spawned chat, which stays
  deliberately parentless) logs nothing — mirrors
  `_handleLogTimeToolCall`'s existing "No ticket to log time against"
  guard.

## Non-goals

- **No human-facing start/stop timer UI.** Out of scope — this was
  never what the idea was about (confirmed in its brainstorm session);
  automatic tracking is entirely system-measured, no user interaction.
- **No new `Clock`/time-provider abstraction.** `DateTime.now()` is used
  directly, not injected — the minimum-1-minute floor means tests can
  assert `addTimeSpent` was called with a value `>= 1` without needing
  to control exact elapsed time (see design.md §3).
- **No predicted-vs-actual calibration feedback loop.** This change only
  produces trustworthy `timeSpent` actuals. Using them to improve
  AI-suggested `estimate` values is a separate, later idea — the
  motivation for this change, not part of its scope.
- **No UI change to how `timeSpent` displays** (detail screen, list
  rows, board cards, or the existing rollup). Automatic contributions
  are indistinguishable from any other `addTimeSpent` caller and reuse
  the existing display/rollup machinery unchanged.
- **No change to `ticket_estimation_suggester.dart`'s background model
  calls.** Those call `provider.client.run()` directly, not through
  `runChatTurn`, and aren't attached to any chat ticket — they're
  background inference passes, not conversational work on behalf of a
  ticket, so they're excluded by construction rather than by a special
  case.

reason: no new visual components in this slice — every file this change
touches is a Cubit or a tool-definition const (`chat_cubit.dart`,

widgets or screens. `log_time` itself already had no UI surface (per

introduces none either.
