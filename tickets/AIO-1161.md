# Spec delta: Mid-task/issue chat branching

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/providers.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (43/46 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Delta against `aion-arch/specs/providers.md` and `aion-arch/specs/tickets.md`.
Read alongside `proposal.md`/`design.md` — this file only states what
changes, not full current-state prose.

## `providers.md`

### ADDED

- **`AgentToolDefinition`** (`core/contracts/agent_tool_definition.dart`)
  — `name`/`description`/`inputSchema` value type describing an
  app-defined tool a model may call mid-run. See design.md §2.
- **`AgentToolCallEvent`** — new `AgentEvent` variant reporting an
  app-defined tool call the model made mid-run. Informational only, like
  `AgentToolUseEvent`, never terminal. See design.md §2.
- **`AgentRequest.tools`** (`List<AgentToolDefinition>`, default `const
  []`) and **`AgentRequest.onToolCall`** (nullable callback) — the
  tool-calling axis, independent of `toolsEnabled`/`workingDirectory`
  (file/git/bash access) and of `ModelPhase`'s reasoning-weight axis.
  Every existing call site leaves both at their defaults, preserving
  today's behavior exactly.
- **Bidirectional tool-call support in `ClaudeAgentSdkClient` /
  `agent_bridge/index.mjs`.** The bridge's stdin now stays open for the
  run's duration (previously closed immediately after the single request
  line) to support a new `tool_call_request`/reply NDJSON round trip. See
  design.md §3.
- **Bidirectional tool-call support in `AnthropicMessagesApiClient`.**
  `_streamResponse` now loops internally, issuing a follow-up POST with
  the tool result appended whenever the API reports `stop_reason:
  'tool_use'`, before finally emitting `AgentDoneEvent`. See design.md §4.
- **`AutomationContext.chatBranching`** — new automation-confidence
  context governing both `branch_ticket` and `close_branch` (see
  `tickets.md` below), persisted via
  `SharedPrefsAutomationSettingsRepository` under
  `'automation_settings.chat_branching_automation'`.

### MODIFIED

- **Known gaps.** "No live model-list discovery," "No real `readOnly`
  tool-access tier," etc. are unaffected — this change adds a new,
  independent tool-calling axis rather than touching `ToolAccessTier`.
  Remove or leave as-is per `/archive`'s judgment; no gap listed there
  becomes stale as a direct result of this change.

## `tickets.md`

### ADDED

- **`branch_ticket` tool** — callable by the model on any `chat` turn
  whose own parent is not itself a `chat`. Creates a child `chat` ticket
  (`parentId` set to the branching chat's id), gated by
  `AutomationContext.chatBranching`'s current `AutomationConfidence`:
  `auto` creates it immediately, `gated` surfaces a confirm/reject
  proposal and holds the model's turn open until the user responds,
  `manual` declines the call outright (no proposal ever shown — AI-
  initiated branching is unavailable at `manual`, by design; see
  proposal.md's Non-goals). See design.md §6.
- **`close_branch` tool** — callable by the model on a *branch* chat
  (one whose own parent is itself a `chat`) once it judges the
  sub-issue resolved. Same three-way `AutomationConfidence` gating as
  `branch_ticket`. On acceptance: sets the branch chat's status to
  `TicketStatus.done` and posts one system-authored comment (the
  model-supplied summary) onto the *parent* chat's transcript — the
  "fold into documentation" mechanism `project.md` §2 describes, adapted
  to a chat ticket's comment-thread-as-content shape. See design.md §6.
- **`TicketsCubit.confirmPendingToolProposal(String chatId)` /
  `rejectPendingToolProposal(String chatId)`** — resolve a `gated`
  proposal awaiting user response. See design.md §6.
- **`TicketDetailLoaded.pendingToolProposal`**
  (`PendingToolProposal?`, new sealed type `BranchProposal`/
  `CloseBranchProposal`) — non-null while a `gated` `branch_ticket`/
  `close_branch` call awaits confirmation. See design.md §8.
- **`_ToolProposalBanner`** — new widget in the chat detail screen,
  rendered when `pendingToolProposal` is non-null, mirroring the Design
  Sync retry validation bar's placement. See design.md §8.
- **Settings "Chat branching" automation row** — new
  `_AutomationSection` bound to `AutomationContext.chatBranching`,
  inserted after the existing coding-execution-retry row. See design.md
  §8.

### MODIFIED

- **`TicketTypeHierarchy.canParent`** — `chat` may now parent `chat`
  (previously: "`resource` and `chat` remain full leaves and can never
  parent anything, including each other" — that sentence now applies to
  `resource` only; `chat` gains this one narrow exception). Depth beyond
  one level is *not* a type-level rule — see the new instance-level
  invariant below. `isAlwaysRoot` is unchanged.
- **Depth-capped branching (new instance-level invariant, enforced in
  `TicketsCubit`, not `TicketTypeHierarchy`).** A chat whose own parent
  is already a `chat` (i.e. a branch chat) cannot itself be branched —
  `branch_ticket` is never even offered as a tool on such a chat's turn
  (see `TicketsCubit._toolsFor`), and `_handleBranchToolCall`'s
  `_canBranch` check enforces the same rule defensively. No branch-of-a-
  branch chains exist as a result.
- **Leaf-detection call sites** (estimate/timeSpent rollup, Board
  leaf-card rendering) — confirmed during `/apply` to already key off
  "has zero live children" rather than a `chat`-is-always-a-leaf type
  check; any site found doing the latter is corrected as part of this
  change, since it's no longer universally true.
- **`ChatCubit.runChatTurn`** — gains `tools`/`onToolCall` passthrough
  parameters (default `const []`/`null`), threaded through to
  `AgentModelClient.run`'s `AgentRequest`. Every existing call site
  (`sendMessage`, `TicketsCubit._runStageChatTurn`,
  `_runCodingExecution`, `retryDesignSync`) is updated to resolve and
  pass the tools appropriate to that chat's structural position (see
  design.md §6's `_toolsFor`) instead of leaving the new parameters at
  their defaults everywhere — a chat only actually offers a tool once
  it's structurally eligible (has a non-chat parent for `branch_ticket`,
  or a chat parent for `close_branch`).

### Known gaps this change resolves

- "No mid-task/issue `chat` branching — `chat` tickets remain leaves;
  nothing spawns a chat-under-chat. `project.md` §2's Branch/Merge
  Semantics applied at this granularity stays undesigned; a
  stage-triggered chat runs start-to-finish with no interruption/branch
  path." — resolved by this change in full.
