# Design: Decision graph `agentJudgment` condition

## 1. The resumability question, resolved empirically

`pluggable-decision-graph-conditions`'s original `/explore` pass found
`AgentModelClient`/`agent_bridge` has no session/resume concept at all —
every `ClaudeAgentSdkClient.run()` spawns a fresh bridge process, and
concluded "reuse the live session" was false, forcing a fallback design
(`confirm-decision-tool-for-modeljudgment-leaves`'s optional tool call).

This proposal's own `/explore` pass went one level deeper: the Claude
Agent SDK itself (`@anthropic-ai/claude-agent-sdk`, installed in
`agent_bridge/node_modules`) exposes `query({ options: { resume:
sessionId, forkSession: true } })` — genuine session resumption, not
something `agent_bridge`/`ClaudeAgentSdkClient` would need to build from
scratch. `resume` loads the target session's persisted transcript from
`~/.claude/projects/`; `forkSession: true` branches that into a **new**,
independent session id rather than mutating the original.

**Empirical test** (throwaway script, not part of this diff): spawned
process A with a custom tool whose handler blocks forever (mimicking
`TicketsCubit`'s `onToolCall` being awaited mid-turn), captured A's
`session_id` from the SDK's message stream the moment it appeared, then
— **while A was still blocked, genuinely mid-turn** — spawned process B
with `resume: sessionIdA, forkSession: true` asking an unrelated scoped
yes/no question. Result:

```
[A] tool called — now blocked, mimicking a pending tool_call_request
[B] text: Yes
[B] result subtype=success  usage: input_tokens=10,
    cache_read_input_tokens=15235, cache_creation_input_tokens=227
    (+5980ms)
[A] result subtype=success (+11586ms)   ← A resumed normally once B
                                            released it
```

Three findings this design depends on:

1. **Concurrent resume works.** B successfully resumed and forked A's
   session while A's own SDK generator was still open and blocked
   awaiting its own pending tool call. No lock/conflict error.
2. **It's cheap, not just "possible."** B's usage shows 15,235 cached
   tokens against only 10 fresh input tokens — B inherited A's
   already-loaded context via prompt caching rather than reconstructing
   it. This is what makes the *guaranteed* round trip (this design)
   viable instead of the best-effort fallback the prior session assumed
   was necessary.
3. **A race exists at the message-UUID granularity.** Anchoring `resume`
   to a specific `resumeSessionAt` message UUID immediately after that
   message streams can lose a race against the transcript's disk flush
   (`"No message found with message.uuid of: ..."` on the first
   attempt in testing, success on an immediate retry). §3 below designs
   around this by not anchoring to a UUID at all.

This directly reverses `pluggable-decision-graph-conditions`'s corrected
assumption and confirms `decision-graph-agentjudgment-condition.md`'s
Option 1 (guaranteed, Dart-forced round trip) rather than Option 2
(best-effort tool offer).

## 2. `AgentProvider.supportsSessionResume`

Resumption is a Claude Agent SDK capability, not a universal one.
`ProviderId` has two values today: `claudeAgentSdk` and
`anthropicMessagesApi`. The Messages API is stateless HTTP — no
server-side session to resume; `AnthropicMessagesApiClient` already
re-sends full message history on every `tool_use` continuation inside
its own request loop, which is a fundamentally different (and much more
expensive) mechanism than what §1 measured.

Add to `AgentProvider` (`core/contracts/agent_provider.dart`):

```dart
/// Whether this provider's [client] can resume/fork an existing
/// session cheaply enough for a mid-turn side-question (see
/// `aion-arch/changes/decision-graph-agentjudgment-condition/design.md`
/// §1). `false` means an `agentJudgment` decision-graph condition
/// always resolves to its unmatched branch when evaluated under this
/// provider — never a crash, never a block.
bool get supportsSessionResume;
```

- `ClaudeAgentSdkProvider.supportsSessionResume => true`.
- `AnthropicMessagesApiProvider.supportsSessionResume => false`.

This is a new required member on an `abstract interface class` —
non-breaking to callers (nothing reads it yet outside this change), but
every existing `AgentProvider` implementation must add it.

## 3. Session capture + resume plumbing

### `agent_bridge/index.mjs`

Every SDK message already carries `session_id` (confirmed in §1's test
and in `@anthropic-ai/claude-agent-sdk/sdk.d.ts`), but `index.mjs`
currently ignores it entirely. Two additions:

- Capture `message.session_id` the first time it appears in the
  `for await (const message of query(...))` loop and emit it
  immediately as a new NDJSON line, **before** any `tool_use`/
  `tool_call_request` line that might follow in the same message batch:
  `{"type":"session","sessionId":"..."}`. Emitted at most once per
  process.
- Read two new optional fields off the initial request line —
  `resume` (`string?`) and `forkSession` (`boolean?`) — and pass them
  straight into `query()`'s `options` alongside the existing `model`.
  Per §1 finding 3, this design **never sets `resumeSessionAt`** — a
  resumed round trip always resumes "as of now," which is safe here
  specifically because the outer session has nothing appended to it
  after its pending tool call while that call is still being awaited
  (the model is blocked on exactly that result), so "as of the last
  flushed message" and "as of the pending tool_use" are the same
  content. This sidesteps the UUID race entirely rather than adding
  retry logic for it.
- `forkSession` is always `true` whenever `resume` is set, by
  construction of the request `ClaudeAgentSdkClient` builds below — the
  round trip's answer must never write into the original conversation
  the outer run is still using.

### `ClaudeAgentSdkClient` (`core/agent/claude_agent_sdk_client.dart`)

- `run()`'s stdout listener gains a third intercepted line type
  alongside `tool_call_request`'s existing interception: a `"session"`
  line sets a local `String? sessionId` (scoped to this `run()` call,
  not exposed on `_activeRuns` — nothing outside this method needs it
  across calls). Consumed internally; never surfaces as a public
  `AgentEvent` variant, since only `_handleToolCallRequest` needs it and
  every existing `switch (event)` at every call site would otherwise
  need a new no-op case for a concept most of them don't care about.
- The outgoing request JSON gains `resume`/`forkSession` fields, sent
  only when the new `AgentRequest.resumeSessionId` (below) is non-null:
  `{'resume': request.resumeSessionId, 'forkSession': true}`.
- `_handleToolCallRequest` constructs an `AgentSessionHandle` (new type,
  §4) from the captured `sessionId` and `request.model` — `null` if no
  `"session"` line has arrived yet (defensive; shouldn't happen in
  practice since the session line is always the first thing emitted,
  but a tool call firing before it is parsed is not a crash, just a
  missed opportunity for that one call) — and passes it as the new 4th
  argument to `onToolCall`.

### Why the round trip reuses the exact same model, not a "lightweight" tier

`project.md`'s aspirational Model Assignment section describes a
"Lightweight" tier for cheap/fast on-device tasks; it would be tempting
to route `agentJudgment` there. §1's cache numbers show why that would be
counterproductive here specifically: prompt caching is keyed by exact
model + exact prompt prefix. Switching models for the round trip would
force a full-price reconstruction instead of the near-free cache hit
measured (10 fresh tokens vs. 15,235 cached). `AgentSessionHandle` (§4)
therefore carries the in-flight run's own `modelId`, and the round trip
is required to reuse it — this is a correctness-for-cost constraint, not
a simplification of convenience.

## 4. `AgentSessionHandle` and the `onToolCall` signature change

New file, `core/contracts/agent_session_handle.dart`:

```dart
/// A resumable handle to an in-flight [AgentModelClient.run] call's
/// provider-native session, threaded to [AgentRequest.onToolCall] so a
/// tool-call handler can ask a scoped side-question inside the same
/// conversation via a second, forked [AgentModelClient.run] call. `null`
/// wherever the underlying provider has no session concept
/// ([AgentProvider.supportsSessionResume] `false`) or [AgentRequest.tools]
/// is empty. See `aion-arch/changes/decision-graph-agentjudgment-condition/
/// design.md` §4.
class AgentSessionHandle extends Equatable {
  const AgentSessionHandle({
    required this.providerId,
    required this.sessionId,
    required this.modelId,
  });

  /// Which registered [AgentProvider] this session belongs to — resolved
  /// back via `ProviderRegistry.providerById` at the call site that
  /// wants to make the round-trip call.
  final ProviderId providerId;

  /// The provider-native session identifier to resume.
  final String sessionId;

  /// The exact model id the in-flight run is using — see design.md §3
  /// for why a round trip must reuse it rather than a cheaper tier.
  final String modelId;

  @override
  List<Object?> get props => [providerId, sessionId, modelId];
}
```

`AgentRequest` (`core/contracts/agent_model_client.dart`) gains:

```dart
/// When set, this run resumes and forks [resumeSessionId] rather than
/// starting a fresh conversation — see design.md §3. `null` (the
/// default) for every existing call site, preserving today's behavior.
/// Only honored by a provider whose [AgentProvider.supportsSessionResume]
/// is `true`; ignored otherwise.
final String? resumeSessionId;
```

added to the constructor (default `null`), `props`, and the dartdoc.

`AgentRequest.onToolCall`'s function type gains a 4th parameter:

```dart
final Future<Map<String, dynamic>> Function(
  String toolCallId,
  String toolName,
  Map<String, dynamic> arguments,
  AgentSessionHandle? session,
)?
onToolCall;
```

This is a breaking signature change. Every implementation/closure must
add the parameter (ignoring it is fine where irrelevant). Confirmed by
direct search — exactly these files reference `onToolCall`:

- `core/contracts/agent_model_client.dart` — the type itself (above).
- `core/agent/claude_agent_sdk_client.dart` — `_handleToolCallRequest`
  now passes the constructed `AgentSessionHandle?` (§3) as the 4th
  argument.
- `core/agent/anthropic_messages_api_client.dart` — always passes `null`
  (Messages API has no session concept; see §2). No other change needed
  there.
- `features/tickets/presentation/cubit/tickets_cubit.dart` —
  `_onToolCallFor(Ticket chat)`'s returned closure gains the parameter
  and threads it into `_handleCreateTicketToolCall`/`_handleAddLinkToolCall`/
  `_handleBranchToolCall`/`_handleCloseBranchToolCall` — only the first
  two, plus `_handleBranchToolCall` (the `chatBranching` context), pass
  it onward to `_evaluateDecisionGraph` (§7); `_handleCloseBranchToolCall`
  has no `agentJudgment`-eligible context and simply accepts-and-ignores
  it. `handleChatToolCall` (the public passthrough
  `TicketDetailScreen` uses for a human-initiated follow-up turn) gains
  the parameter and forwards it into `_onToolCallFor(chat)(...)`
  unchanged.
- `features/tickets/presentation/screens/ticket_detail_screen.dart` —
  its `onToolCall:` wiring for `ChatCubit.sendMessage` calls
  `ticketsCubit.handleChatToolCall`, which now needs the extra argument
  threaded through from `ChatCubit`.
- `features/tickets/presentation/cubit/chat_cubit.dart` — `runChatTurn`'s
  `onToolCall` parameter type gains the 4th argument (it only forwards
  the closure into `AgentRequest`, doesn't need to inspect it itself).
- `core/contracts/agent_tool_definition.dart` — only referenced for a
  doc comment cross-link; no functional change, included here since the
  search matched it.

## 5. Evaluator: `evaluateDecisionGraph` becomes conditionally-async

`decision_graph_evaluator.dart`'s pure/synchronous contract was an
explicit, deliberate property (per its own dartdoc and `providers.md`'s
"pure, no I/O"). This is the one property this change breaks — flagged
here rather than silently, per `pluggable-decision-graph-conditions`'s
own note that this was worth calling out to whoever built it.

`DecisionEvalContext` gains two fields, both nullable/optional so every
existing construction (`const DecisionEvalContext()`,
`DecisionEvalContext(attempt: attempt)`) keeps compiling unchanged:

```dart
/// The in-flight run's resumable session, if one exists at this call
/// site — read by the `agentJudgment` condition. `null` for every
/// context with no live tool-call-blocked session (5 of 8
/// `AutomationContext` values always pass `null` here; see
/// proposal.md's "Why this only works for 3 of the 8" section).
final AgentSessionHandle? session;

/// Performs the actual `agentJudgment` round trip: asks [prompt] as a
/// scoped yes/no question inside [session], returning `true`/`false`
/// for a clear answer or `null` for anything else (no session
/// available, the call errored, an ambiguous/empty response). Real I/O
/// — the one reason [evaluateDecisionGraph] is no longer pure. `null`
/// (the default) for a call site with no way to ask at all, in which
/// case an `agentJudgment` node always resolves unmatched without
/// attempting a call.
final Future<bool?> Function(AgentSessionHandle session, String prompt)?
askAgentJudgment;
```

Kept as two separate fields (not merged into one) so the evaluator's
unit tests can inject a fake `askAgentJudgment` without needing a real
`AgentSessionHandle`/provider at all — `session` is just data the fake
can ignore.

`evaluateDecisionGraph`'s signature becomes
`Future<DecisionOutcome> evaluateDecisionGraph(...)`. Its walk loop is
otherwise unchanged — same strict-tree traversal, same defensive
`proceed`-on-`null`-root / `proceed`-on-dangling-node-reference
behavior — except the per-node evaluator lookup becomes `await`-capable:

```dart
final matched = node.conditionId == agentJudgmentConditionId
    ? await _evaluateAgentJudgment(input, node.conditionParams)
    : (_conditionEvaluators[node.conditionId]?.call(input, node.conditionParams) ?? false);
```

`_evaluateAgentJudgment` reads `conditionParams['prompt']` (a `String`;
defensively `false`/unmatched if missing or not a `String` — the same
posture `_evaluateRule` already uses for a malformed rule-builder node),
and:

```dart
Future<bool> _evaluateAgentJudgment(
  DecisionEvalContext input,
  Map<String, dynamic> params,
) async {
  final prompt = params['prompt'];
  final session = input.session;
  final ask = input.askAgentJudgment;
  if (prompt is! String || session == null || ask == null) return false;
  final answer = await ask(session, prompt);
  return answer ?? false;
}
```

Per the cost note in `pluggable-decision-graph-conditions`'s Conclusions
("the cost is per-path, not per-tree"): a walk that never reaches an
`agentJudgment` node stays exactly as fast as today, since the `await`
only actually suspends on that one branch.

`decision_condition_catalog.dart` gains the reserved id (mirroring
`ruleBuilderConditionId`'s placement in `decision_field_catalog.dart`,
but this one lives in `decision_graph_evaluator.dart` itself since it's
the evaluator's own concern, not the field-catalog's):

```dart
/// The reserved `DecisionNode.conditionId` value marking an
/// `agentJudgment` condition — never collides with a real catalog
/// entry or [ruleBuilderConditionId].
const agentJudgmentConditionId = 'agentJudgment';
```

## 6. Catalog + node-display generalization

`decision_field_catalog.dart` already generalizes `decisionNodeTitle`/
`decisionNodeSummary`/`isRecognizedConditionId` to cover the rule-builder
condition kind alongside the fixed catalog. This change adds the third
kind to the same three functions:

- **`decisionNodeTitle`** — for `node.conditionId ==
  agentJudgmentConditionId`, returns a fixed label
  (`context.l10n.decisionGraphAgentJudgmentLabel`, new arb key — see §8)
  rather than deriving anything from `conditionParams`, since there's no
  catalog/field spec to look up (unlike the rule-builder case, which
  looks up the chosen field's `displayName`).
- **`decisionNodeSummary`** — returns `conditionParams['prompt']` itself
  (truncated the same way `summarizeToolInput` in `agent_bridge/index.mjs`
  truncates long strings — reusing that ~120-char convention rather than
  inventing a new one) as the parameter-chip text, or `null` if missing/
  not a `String`.
- **`isRecognizedConditionId`** — `|| conditionId ==
  agentJudgmentConditionId`.

New synthesizer, mirroring `ruleBuilderConditionSpec`'s shape exactly but
gated on the 3-context allowlist from proposal.md rather than
`decisionFieldsFor(context).isEmpty`:

```dart
/// The fixed set of `AutomationContext` values evaluated from inside a
/// live tool-call handler with an in-flight session — see proposal.md's
/// "Why this only works for 3 of the 8". Not derived from any existing
/// enum/field, since "has a live session at evaluation time" isn't a
/// property any other part of this system currently models — this list
/// is this change's own source of truth for it.
const _agentJudgmentEligibleContexts = {
  AutomationContext.ticketCreation,
  AutomationContext.ticketLinking,
  AutomationContext.chatBranching,
};

/// Synthesizes the "Ask the agent" entry `DecisionNodeForm`'s condition
/// picker appends after the rule-builder entry (if any) — `null` if
/// [context] isn't one of the 3 contexts a live session can ever be
/// available for.
DecisionConditionSpec? agentJudgmentConditionSpec(AutomationContext context) {
  if (!_agentJudgmentEligibleContexts.contains(context)) return null;
  return DecisionConditionSpec(
    id: agentJudgmentConditionId,
    displayName: 'Ask the agent',
    contexts: [context],
    parameterSpecs: const [],
  );
}
```

(Not `const` at the top level since `contexts: [context]` depends on the
parameter — matches `ruleBuilderConditionSpec`'s own non-`const`
construction for the same reason.)

`defaultConditionParams`-equivalent for a freshly created `agentJudgment`
node: `{'prompt': ''}` (empty string — `DecisionNodeForm` should treat an
empty prompt as an incomplete/unsaved node, same as any other
required-but-unfilled field elsewhere in that form).

## 7. `TicketsCubit` wiring

`_evaluateDecisionGraph` gains a new optional parameter:

```dart
Future<DecisionOutcome> _evaluateDecisionGraph(
  AutomationContext context,
  DecisionEvalContext input, {
  AgentSessionHandle? session,
}) async { ... }
```

Rather than threading `session` through every one of the ~9 existing
call sites' `input` construction individually, this cubit builds the
real `input` internally: when `session` is non-null, it constructs
`DecisionEvalContext` with `session: session, askAgentJudgment:
_askAgentJudgment` merged in (via `input.copyWith`-style reconstruction,
or by having callers pass `session` as this new named param instead of
inside `input` directly — the latter is simpler and is what the
signature above does, keeping `DecisionEvalContext` construction at each
call site unchanged except the 3 that now also pass `session:`).

Only the 3 live-session call sites pass a non-null `session` — sourced
from the new 4th `onToolCall` parameter (§4), threaded straight through
from `_handleCreateTicketToolCall`/`_handleAddLinkToolCall`/
`_handleBranchToolCall`'s own new parameter:

```dart
// _handleCreateTicketToolCall, updated signature:
Future<Map<String, dynamic>> _handleCreateTicketToolCall(
  Ticket chat,
  Map<String, dynamic> arguments,
  AgentSessionHandle? session,
) async {
  ...
  case AutomationConfidence.auto:
    final outcome = await _evaluateDecisionGraph(
      AutomationContext.ticketCreation,
      const DecisionEvalContext(),
      session: session,
    );
  ...
}
```

(`_handleAddLinkToolCall`/`_handleBranchToolCall` gain the identical
shape for `ticketLinking`/`chatBranching`.)

New private method, the one place that actually performs the round-trip
I/O:

```dart
/// [DecisionEvalContext.askAgentJudgment]'s real implementation — resolves
/// [session]'s provider via [_providerRegistry], issues a forked,
/// resumed [AgentModelClient.run] call asking [prompt] as a scoped
/// yes/no question, and parses the answer. Returns `null` (not `false`)
/// for every failure mode — no provider registered, the run errors, or
/// the response doesn't clearly parse as yes/no — so
/// [evaluateDecisionGraph]'s `answer ?? false` fallback is the single
/// place that turns "couldn't get a clear answer" into "unmatched",
/// rather than this method silently conflating "no" with "couldn't
/// ask". Added for
/// `aion-arch/changes/decision-graph-agentjudgment-condition`.
Future<bool?> _askAgentJudgment(
  AgentSessionHandle session,
  String prompt,
) async {
  final registry = _providerRegistry;
  if (registry == null) return null;
  final AgentProvider provider;
  try {
    provider = registry.providerById(session.providerId);
  } on StateError {
    return null;
  }
  if (!provider.supportsSessionResume) return null;

  final buffer = StringBuffer();
  try {
    final events = await provider.client.run(
      AgentRequest(
        prompt:
            'Answer only "yes" or "no", with no other text: $prompt',
        model: session.modelId,
        resumeSessionId: session.sessionId,
      ),
    );
    await for (final event in events) {
      switch (event) {
        case AgentTextEvent(:final text):
          buffer.write(text);
        case AgentDoneEvent():
          break;
        case AgentErrorEvent():
        case AgentCancelledEvent():
          return null;
        case AgentOverageDetectedEvent():
        case AgentToolUseEvent():
        case AgentToolCallEvent():
          break; // Not expected on a tools-empty request; ignored defensively.
      }
    }
  } catch (_) {
    return null;
  }

  final normalized = buffer.toString().trim().toLowerCase();
  if (normalized.startsWith('yes')) return true;
  if (normalized.startsWith('no')) return false;
  return null; // Ambiguous — evaluateDecisionGraph treats this as unmatched.
}
```

## 8. UI: `DecisionNodeForm` / `DecisionOutlineList` / `GraphCanvas`

Design-gated (see proposal.md) — the concrete visual spec comes from
`/design-brief` + Claude Design, but the structural shape is fixed here
so `/design-sync`/`/apply` know what they're wiring into:

- **`DecisionNodeForm`**'s condition picker (`decision_node_form.dart`)
  appends `agentJudgmentConditionSpec(context)`'s entry (when non-null)
  after the existing rule-builder entry, labeled via a new
  `context.l10n.decisionGraphAgentJudgmentLabel` string (mirroring how
  `decisionGraphRuleBuilderLabel` overrides "Custom rule"'s rendered
  label today). Selecting it swaps the parameter area to a single
  multi-line `AppTextField` bound to `conditionParams['prompt']`, in
  place of both the typed-parameter-field path (fixed catalog) and the
  field/operator/value trio (rule-builder) — a third mutually-exclusive
  branch alongside the two `condition.id == ruleBuilderConditionId`
  checks already in that file (lines 493, 546, 601, 668 per the current
  file).
- **`DecisionOutlineList`** (`decision_outline_list.dart`) gains a third
  `isAgentJudgment = widget.node.conditionId == agentJudgmentConditionId`
  check alongside its existing `isRuleBuilder` one (line 294), rendering
  an `ASK ·` eyebrow (paralleling `RULE ·`/`IF ·`) and the same
  1px-bordered parameter chip pattern the rule-builder already uses,
  populated from `decisionNodeSummary` (§6) — i.e. the truncated prompt
  text.
- **`GraphCanvas` node cards**, built in
  `decision_graph_editor_screen.dart`'s node-content builder (the
  `isRuleBuilder`/`eyebrowText` logic around lines 607–614), gain the
  same third branch: `ASK ·` eyebrow, same chip.
- **Cost/latency affordance** (the open question
  `pluggable-decision-graph-conditions.md` flagged: "a project author
  scanning a graph should be able to tell which paths are free/instant
  and which cost a round-trip without opening each node"): the `ASK ·`
  eyebrow itself is that signal — distinct from `IF ·`/`RULE ·` exactly
  because those are always free/instant and this never is. An additional
  info affordance (tooltip or small icon, exact shape left to Claude
  Design) surfaces text along the lines of "Calls the agent — adds a few
  seconds" on hover/tap, on both the canvas card and the outline row.
- **No new UI for the round trip itself while it's in flight.** The
  round trip happens entirely inside `onToolCall`, which the outer
  chat's existing "assistant is thinking" / pending-tool-call presentation
  already covers — `AutomationConfidence.auto`'s contract is "no user
  interaction," and that holds even while this particular decision takes
  a few extra seconds. Not a gap; a deliberate choice to avoid inventing
  a new pending-state UI for what is, from the user's perspective, still
  just "the agent is thinking."
- **l10n**: new key `decisionGraphAgentJudgmentLabel` in
  `lib/l10n/app_en.arb` (English value: `"Ask the agent"`), regenerating
  `lib/l10n/generated/app_localizations*.dart` per this project's normal
  codegen step.

## 9. Failure-mode / defensive-fallback matrix

Every failure mode resolves to the `unmatched` branch, never a thrown
error and never a block on `auto` automation — consistent with every
other defensive default already in `decision_graph_evaluator.dart`
(dangling node reference, unrecognized `conditionId`, malformed
rule-builder params all already resolve this way):

| Situation | Resolution |
|---|---|
| Context isn't one of the 3 live-session contexts | Picker never offers `agentJudgment` here at all (§6) |
| `agentJudgment` node reached with no live session (`session == null`) | Unmatched, no call attempted |
| Provider resolved from `session.providerId` doesn't support resume | Unmatched, no call attempted |
| `_providerRegistry` unset on this `TicketsCubit` instance | Unmatched, no call attempted |
| The round-trip `run()` call throws, errors, or is cancelled | Unmatched |
| Model's answer doesn't clearly parse as yes/no | Unmatched |
| `conditionParams['prompt']` missing or not a `String` | Unmatched (same posture as `_evaluateRule`'s malformed-params handling) |
| Everything above succeeds, answer is "yes" | Matched |
| Everything above succeeds, answer is "no" | Unmatched |

## 10. Testing implications

- `decision_graph_evaluator_test.dart` (existing) needs new cases:
  `evaluateDecisionGraph` now returns a `Future`; existing sync
  assertions need `await`. New cases for the `agentJudgment` condition
  kind — injected fake `askAgentJudgment` returning `true`/`false`/`null`,
  and the `session == null` / `askAgentJudgment == null` defensive paths.
- `TicketsCubit`'s existing `_handleCreateTicketToolCall`/
  `_handleAddLinkToolCall`/`_handleBranchToolCall` `bloc_test` suites need
  their `onToolCall` invocations updated for the new 4th argument, plus
  new cases exercising `_askAgentJudgment` via a mocked
  `ProviderRegistry`/`AgentProvider`/`AgentModelClient` (mocktail, per
  `project.md`'s testing conventions — no real bridge process spawned).

# Aion — Decision Graph `agentJudgment` Condition: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Automation Decision Graphs Spec](./Aion%20Automation%20Decision%20Graphs%20Spec.md) (cited **DG §n**) and the [Decision Rule Builder Spec](./Aion%20Decision%20Rule%20Builder%20Spec.md) (cited **RB §n**). A decision node's condition can today be a named preset (DG §0.3) or a project-authored field/operator/value rule (RB §1). This slice adds a third authoring path: **`agentJudgment`** — a free-text yes/no question, evaluated at runtime by a real round-trip to the model mid-turn, whose answer routes the matched / unmatched branches. It lives in the existing `DecisionNodeForm` (DG §3), renders through the existing node card (DG §1.2) and outline row (DG §2.1), and adds one shared info affordance (§5).

**No new screens.** One new menu row (§1), one new field group replacing the parameter area (§2), two rendering variants on two existing components (§3, §4), one new affordance (§5).

A bare `TextField` inside a transparent `Material` ancestor remains the sole permitted exception, already wrapped by `AppTextField`. No `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `DropdownButton`, `InkWell`, `ListTile`, `Tooltip`, `Divider`, `Icons.*`.

Themes: **Arctic** (light) and **Obsidian** (dark). Every dimension, `EdgeInsets`, radius, gap, stroke, duration, curve, breakpoint, text style and copy string below is **identical** between themes; only color token values differ (§7). Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB.

## 0. Condition identity: how `ASK ·` differs, and why it may use hue

RB §4.3 deliberately refused hue for rule-vs-preset: both are instant, free, locally-evaluated checks, so the distinction was scannability only. `agentJudgment` is a different claim — **this node spends a live model call and a few seconds of wall clock every time it is reached.** That is a cost the author must be able to count without opening a node, so it earns the accent and one glyph:

| | Preset (DG) | Rule (RB) | **Agent judgment (this slice)** |
|---|---|---|---|
| Eyebrow | `IF · ATTEMPT COUNT`, `textMuted` | `RULE · ATTEMPT COUNT`, `textMuted` | `ASK ·` + `9×9` diamond, **`primary`** |
| Chip fill | `surfaceHover` | `surfaceHover` | `primaryWash` |
| Chip border | none | 1px `border` | 1px `primary.withOpacity(0.28 / 0.40)` |
| Chip content | operator + value symbol | operator + value symbol | the authored question, verbatim, truncated |
| Chip text | `AionText.key` `textSecondary` | `AionText.key` `textSecondary` | `AionText.bodySm` w500 `textPrimary` — prose, not a symbol |
| Cost | free, instant | free, instant | **one model round trip** |

The `9×9` rotated-square diamond is **not a new mark**: it is the same glyph the graph already draws on the `Model decides` outcome badge (DG §1.4). In Aion's decision vocabulary the diamond already means "the model resolves this," so `agentJudgment` inherits it rather than introducing an icon. Never a warning triangle, never `warning`, never `danger` on a healthy node — this is a sanctioned capability, not a fault.

Accent is never the *only* carrier: the leading word `ASK`, the diamond, and the prose-vs-symbol chip content each survive grayscale and 40% canvas zoom independently.

|---|---|

## 6. Accessibility

- Node semantics: `'Ask the agent, is this fix expensive to implement, yes branch asks first, no branch proceeds'` — the branch names are spoken as **yes / no** here, not matched / unmatched, because the author authored a question.
- Incomplete node: `'Ask the agent, no question entered, incomplete'`.
- The prompt field announces as `'Question, editable, multiline, ask something the agent can answer yes or no'`; the character counter is `liveRegion: false` and announced only on blur.
- The `ASK` identity is never hue-only: the leading word, the diamond, and the prose chip each carry it independently (§0).
- Error is never color-only: the 1.5px border-weight change plus the helper line accompany every `danger` border, per RB §3.5.7.
- The info trigger is tab-reachable, `Enter`/`Space` opens its tooltip, `Escape` closes it, and its full copy is in the trigger's own `Semantics.label` so a screen reader never needs the overlay.
- The tooltip is `ExcludeSemantics`d to avoid double announcement.
- Tab order in the form: Condition → Question → Matched → Unmatched → Delete → Cancel → Save.
- `AionText.caption` at 11px on `primaryWash`: contrast ≥ 4.6:1 in both themes.

## 7. Theme parity

Identical across Arctic and Obsidian: every dimension, `EdgeInsets`, radius, gap, stroke width, glyph size, animation duration and curve, breakpoint, text style and copy string. Differing: color token values resolved by name, and the alpha pairs called out inline — `primaryWash` `0.10 / 0.16`, focus ring `0.16 / 0.30`, danger ring `0.14 / 0.26`, error fill `0.08 / 0.14`, accent hairline `0.28 / 0.40`, `neutralTint` `0.09 / 0.14`, `neutralBorderTint` `0.18 / 0.26`, `fillAlpha` `0.11 / 0.16`, text-selection fill `0.24` (both), disabled opacity `0.6` (both).
