# Spec delta: tickets.md — trash/restore cascade git projection

**Reconciled 2026-09-09:** cross-checked against the current `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is present verbatim (expected: this change was archived only moments before this backfill ran, and `/archive` already merges deltas into `specs/*.md` at archive time). No content changes needed.

Applies to `aion-arch/specs/tickets.md`'s "Git projection" and "DB
reconstruction" sections (under "Embeddings, sync status & git
projection (desktop only)").

## MODIFIED — `TicketRepository.trashTicket`/`restoreTicket`/`trashTickets` return values

**Before:** `trashTicket(id)`/`restoreTicket(id)` return `Future<void>`;
`trashTickets(ids)` returns `Future<int>` (count of tickets actually
moved, including cascaded descendants).

**After:** All three return `Future<List<String>>` — the full set of
ids actually affected by the call (the requested id(s) plus every
cascaded ancestor/descendant the underlying trash/restore walk already
resolves), deduplicated, in unspecified order. `trashTickets`' returned
list's length is the same count the old `int` return gave. No other
repository method's signature changes.

## MODIFIED — Git projection now covers the full trash/restore cascade, not just the named id

**Before:** "`restore(id)` projects only the explicitly-restored ticket
— not any currently-trashed ancestors/descendants `restoreTicket` also
revives, matching `trashTickets`' existing scope for the symmetric
trash-side case." A ticket silently revived (or trashed) as a side
effect of a cascade never got its `tickets/<id>.md` file rewritten or
committed — its DB `deletedAt` and its file's `deletedAt` could
diverge indefinitely, with no error surfaced anywhere.

**After:** `GitProjectingTicketRepository.trashTicket`/`restoreTicket`
use the repository's now-complete affected-id list to project *every*
ticket the cascade touched, batched into **one** commit via
`TicketGitProjector.projectBatch` (labelled `'trashed'`/`'restored'`
respectively) — not one commit per affected ticket. For the common case
(no cascade), this is the exact same single-ticket commit as before.
`TicketsCubit.trashTickets` (the bulk-trash path, which calls
`TicketRepository.trashTickets` — plural — directly rather than through
the decorator, per this project's existing "batched rollup must be
strictly sequenced after projection" requirement) is updated the same
way: its own git side effect now batches *every* id the plural call
returns, not just the ids the user explicitly selected. This closes a
"documented scope simplification" the removed dartdoc explicitly named
in both the singular decorator and the bulk cubit path.

`TrashCubit.restoreTickets`' existing loop over
`TicketParentTrashService.restore(id)` needed no logic change — it
already calls the singular `restoreTicket` path per id, so it inherits
the corrected batching automatically.

## MODIFIED — `TicketGitProjector.projectBatch`'s multi-item commit message wording

**Before:** A batch of more than one ticket committed as `"ticket: N
ancestors <eventLabel>"` — accurate only for its original caller
(`TicketRollupRecomputer`'s ancestor-rewrite cascade).

**After:** `"ticket: N tickets <eventLabel>"` — accurate for both the
existing rollup-ancestor caller and the new trash/restore-cascade
callers, whose batched set can include descendants, or (for restore)
both ancestors and descendants at once. `projectBatch`'s parameter/
method names are unchanged.

## MODIFIED — `TicketDbReconstructionService.reconstruct()`'s existing-row detection

**Before:** "a file whose `ticketId` already has a matching DB row
calls `updateTicket`" — "matching DB row" was checked via
`TicketRepository.getAllTickets()` alone, whose underlying query
excludes trashed rows. A trashed ticket's `.md` file (never deleted by
trashing) was therefore always treated as a brand-new ticket on
reconstruction, and `importTicket`'s attempt to insert a second row
with the same (unique) `ticketId` threw a `SqliteException`, aborting
the run.

**After:** The existing-row check is built from `getAllTickets()` **and**
`getTrashedTickets()` together, so a trashed ticket's file is always
recognized as an update. `reconstruct()` no longer throws on a project
that has any trashed ticket.

## ADDED — `TicketDbReconstructionService.reconstruct()` reconciles trash state explicitly

**New behavior**, on the existing-row (`updateTicket`) branch only: if
the parsed file's `deletedAt` disagrees with the existing row's
`deletedAt`, `reconstruct()` now calls `TicketRepository.trashTicket`
or `.restoreTicket` (whichever direction the file's value implies)
immediately after the `updateTicket` call — the same detection logic
`TicketParentTrashService.applyFromParsedFields` already uses for the
identical file→DB reconciliation direction on the live-watcher path.
`updateTicket` itself is unchanged and still never writes `deletedAt`.
A file whose `deletedAt` didn't change, or changed between two non-null
values, is a no-op for this step (matches `applyFromParsedFields`'s
existing no-op cases).

This makes the "`deletedAt` round-trips through reconstruction the same
way `parentId`/`estimate`/`timeSpent` already do" claim in this section
actually true for the update branch, not just asserted.

## ADDED — `createTicket`/`importTicket` persist `deletedAt` on insert

**Before:** The shared insert path (`DriftTicketRepository
._buildInsertCompanion`) never wrote `deletedAt` — every freshly
inserted row started live regardless of the `Ticket` object's own
`deletedAt` value. Inert for `createTicket` (no caller ever constructs
a pre-trashed `Ticket` before creating it) but a real gap for
`importTicket`, whose only real caller (`TicketDbReconstructionService`,
the second-machine/reconstruction path) can legitimately be importing
an already-trashed ticket for the first time.

**After:** The insert companion includes `deletedAt`, sourced from the
`Ticket`'s own field. A ticket imported (or reconstructed) from a `.md`
file whose frontmatter says `deletedAt: <timestamp>` is inserted already
trashed, instead of silently coming back live.
