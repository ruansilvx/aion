# Dont Spawn New Chat Ticket Per Execution Trigger

# Proposal: dont-spawn-new-chat-ticket-per-execution-trigger

## What

`TicketsCubit._runCodingExecution` unconditionally spawns a fresh
`"Coding Execution — <Task title>"` chat child ticket every time it runs —
the first move to `inProgress`, every `retryCodingExecution` click, and
every toggle-status-away-and-back. A Task that fails verification a few
times before passing accumulates several sibling chats, each a dead end
except the last; `_executionSucceededWithPr`/`_computeExecutionFailure`
already have to search for "the most recently created" one just to find
the current state. Resolved in `dont-spawn-new-chat-ticket-per-execution-
trigger.md` (explored 2026-07-24). Concretely, this change:

1. **Reuses one chat per Task across its execution lifecycle.**
   `_runCodingExecution` finds the Task's existing `"Coding Execution — "`-
   prefixed chat (if any) and posts the new run's context/turns to it,
   instead of creating a new ticket. A brand-new chat is only created when
   the Task has no execution chat yet at all — a genuine first trigger.
2. **Hands off to a new chat when the current one nears its model's
   context window**, rather than reusing it forever unconditionally. A
   per-chat running token total (summed from real per-turn usage the
   Node bridge now forwards) is compared against a cap — the currently
   configured execution-phase `AgentModel`'s real context window by
   default, with a Settings field letting the user lower (never raise)
   it. Crossing 90% of that cap triggers one final turn on the current
   chat asking the model to write a handoff summary, then a new chat —
   titled `"... (continued)"` (numbered for a third/fourth, etc.) and
   linked back via `TicketLinkType.relatesTo` — picks up from there,
   seeded with that summary.
3. **Forwards real token usage from the Claude Agent SDK.**
   `agent_bridge/index.mjs` doesn't report usage today; this change reads
   it off the SDK's own `result` message and threads it through
   `AgentDoneEvent` → `ChatCubit.runChatTurn` → a new nullable
   `inputTokens`/`outputTokens` pair persisted on the AI-authored
   `TicketComment` that closes out each turn.

## Why

Every existing "most recently created execution chat" lookup already
tolerates multiple chats per Task — that's the tell that the accumulation
was never actually intended, just an unhandled side effect of always
creating fresh. Reusing one chat turns a Task's execution history into a
single readable thread instead of a pile of same-titled dead ends in its
child list — the [[feedback_ux_over_implementation_cost]] tradeoff this
project consistently makes.

The context-window handoff (rather than reusing one chat forever,
unconditionally) exists because `ChatCubit.runChatTurn` sends the model
only the current turn's `prompt` string, never prior chat history — an
unbounded chat would eventually force `_assembleExecutionContext`'s
opening context comment plus however many corrective-retry turns to
compete for a shrinking budget with no signal that it's happening. The
brainstorm session settled on "real reported usage vs. a real cap" over a
character-count heuristic specifically to avoid a threshold that fires
too early or too late.

## Scope

- **`core/contracts/agent_model_client.dart`** — `AgentDoneEvent` gains
  two new optional fields, `inputTokens`/`outputTokens` (`int?`,
  `null` when the bridge didn't report usage) — a field addition to an
  existing terminal event, not a new event type, since usage is only
  ever known once a turn actually finishes.
- **`agent_bridge/index.mjs`** — the `result`/`success` branch reads
  `message.usage.input_tokens`/`.output_tokens` (present on the SDK's
  own result message) and includes them on the `{"type":"done"}` line.
- **`core/agent/claude_agent_sdk_client.dart`** — `_parseLine`'s `'done'`
  case reads the two new fields into `AgentDoneEvent`.
- **`features/tickets/domain/entities/ticket_comment.dart`** +
  **`data/models/ticket_comment_model.dart`** — `TicketComment` gains
  `inputTokens`/`outputTokens` (`int?`), mirroring the existing `aiModel`
  field's "set only for an AI-authored comment" shape. New nullable
  `IntColumn`s on `TicketCommentsTable`; `AppDatabase.schemaVersion` bumps
  6 → 7 with a matching `addColumn` migration step.
- **`features/tickets/presentation/cubit/chat_cubit.dart`** —
  `runChatTurn` reads `AgentDoneEvent.inputTokens`/`.outputTokens` off the
  terminal event and carries them onto whichever `TicketComment` it
  persists (success or failure path).
- **`features/providers/domain/enums/agent_model.dart`** — `AgentModel`
  gains `contextWindowTokens` (`int`), `200000` for all three current
  values (today's real Claude context window; no beta 1M-context tier
  support).
- **New `features/providers/domain/repositories/
  execution_context_cap_repository.dart`** (`ExecutionContextCapRepository`)
  + **`data/repositories/shared_prefs_execution_context_cap_repository.dart`**
  — persists a nullable token-count override (`null` = no override, use
  the execution-phase model's real `contextWindowTokens`), one
  `shared_preferences` key, mirroring `ModelRoutingRepository`'s shape.
- **`features/tickets/presentation/cubit/tickets_cubit.dart`**:
  - Constructor gains an optional `ExecutionContextCapRepository?`
    (same no-op-if-null pattern as every other optional dependency —
    absent, the cap always resolves to the model's real limit with no
    user override available).
  - `_executionSucceededWithPr`/`_computeExecutionFailure`'s duplicated
    "find the most recently created `Coding Execution — `-prefixed
    child" logic is extracted into one shared `_mostRecentExecutionChat`
    helper — both call sites keep working unchanged, since a
    `"(continued)"` chat still matches the same prefix and simply sorts
    later.
  - New `_resolveExecutionChat`/`_executionChatOverCap`/
    `_effectiveExecutionContextCap`/`_createExecutionChat`/
    `_executionChatTitle`/`_executionChatCount` replace
    `_runCodingExecution`'s unconditional chat-creation block with
    find-existing-or-create, plus the cap check.
  - New `_handoffExecutionChat`/`_assembleChatTranscript`/
    `_assembleHandoffContext` implement the handoff: one summary-only
    `ChatCubit.runChatTurn` call on the old chat (no tools, no
    worktree — the run that owned the old chat's worktree already
    finished), then a new linked chat.
  - `_assembleExecutionContext` gains an optional `handoffSummary`
    parameter, prepended to the opening context comment when a handoff
    just happened.
  - `retryCodingExecution`'s dartdoc is updated — it no longer starts
    "from scratch" in the chat sense, only the worktree/branch sense.
- **New `features/providers/presentation/cubit/
  execution_context_cap_cubit.dart`** (`ExecutionContextCapCubit`) +
  **`execution_context_cap_state.dart`** — Settings-screen business logic
  for the new cap field, one cubit per concern (matches
  `ModelRoutingCubit`/`AutomationSettingsCubit`'s existing split).
- **`features/providers/presentation/screens/settings_screen.dart`** —
  new `_ExecutionContextCapSection` under the existing "MODELS" eyebrow,
  below the Execution model row: a numeric field for the override, plus
  the effective (model-default-or-override) cap shown as helper text.
- **`main.dart`** — registers `RepositoryProvider<ExecutionContextCapRepository>`.
- **`core/routing/app_router.dart`** — wires the new repository into
  `TicketsCubit`'s construction and provides `ExecutionContextCapCubit`
  on the `/workspace/settings` route.
- **`lib/l10n/app_en.arb`** — two new keys for the Settings field's
  label/description.

## Out of scope

- **Retroactive usage backfill for comments posted before this change** —
  existing AI-authored comments have `inputTokens`/`outputTokens: null`;
  a chat that was mid-life when this ships starts its running total from
  whatever comments land after upgrade, undercounting until then. Not
  worth a one-time reconciliation for a soft (fail-open) threshold.
- **A predictive, pre-turn cost/usage estimate** — the cap check runs
  between turns only (before `_resolveExecutionChat` hands work to the
  next implement/corrective turn), not mid-turn; a single turn that
  itself blows through the remaining budget isn't interrupted, mirroring
  this project's existing reactive-only `AgentOverageDetectedEvent`
  precedent (no predictive budget gate there either).
- **Interrupting the retry-on-verify-failure loop mid-cycle for a
  handoff** — the cap is only checked once per `_runCodingExecution`
  invocation (i.e. once per trigger: initial move to `inProgress`, or a
  manual retry), not before each corrective turn inside that run's own
  implement→verify loop. Splitting a single run's tight
  implement/verify/corrective cycle across two chats mid-flight would
  need to hand off *inside* an open worktree, which is materially more
  complex for a case the brainstorm didn't specifically ask for.
- **User-facing surfacing of "a handoff just happened"** beyond the new
  chat's own title/summary/link — no toast, no board indicator. A human
  reading the Task's chat history sees it naturally.
- **Configuring the 90%-of-cap handoff threshold itself** — fixed as a
  constant (`TicketsCubit._handoffThresholdRatio`); only the cap it's a
  fraction of is user-configurable, per the idea's own resolution.
