# Estimate Timespent Rollup For Ticket Hierarchy

# Proposal: Estimate/TimeSpent Rollup for Ticket Hierarchy

## What

Every Epic/Story/Task/Bug/Chat ticket that has at least one live child
gains two new derived, read-only numbers — a rolled-up `estimate` and a
rolled-up `timeSpent` — equal to the ticket's own manually-entered value
plus the recursive sum of every live descendant's own value, Jira-style.
These are computed by `TicketsCubit`/`TrashCubit`, persisted to the
ticket's row (`estimate_rollup`/`time_spent_rollup` columns) and to its
projected git Markdown file, and shown everywhere the ticket already
appears: `TicketDetailScreen`'s metadata section, `TicketListTile`, and
`TicketBoardCard`. A leaf ticket (no live children) shows nothing new —
its existing plain `estimate`/`timeSpent` display is untouched.

Recompute is immediate and upward-walking: any edit that changes a
ticket's own `estimate`/`timeSpent`, any reparent, and any trash/restore
recomputes every affected ancestor's rollup right away, so the number is
always accurate the moment a ticket is viewed — never lazily computed on
open. All cascading ancestor file rewrites triggered by one edit batch
into a single git commit, not one commit per ancestor.

This closes the known gap recorded in `aion-arch/specs/tickets.md`:

> No estimate/timeSpent rollup exists yet, so reparenting has nothing to
> roll up.

and satisfies the existing **Rollup invariant** already written into
that spec ahead of this feature existing:

> any future `estimate`/`timeSpent` rollup must derive parent totals
> from the structural `parentId` tree only. Tickets related via
> `ticket_links` never contribute to a rollup, regardless of link type.

## Why

Epics and Stories currently have no way to answer "how much work is
actually under this?" without a human manually opening every descendant
and adding it up by hand. For a solo developer using Aion as their own
project tracker, that's exactly the kind of bookkeeping the tool should
be doing automatically — the numbers already exist per-ticket
(`estimate`/`timeSpent`, manual entry), they're just never aggregated
upward.

## Scope decisions made during this proposal

The source idea
([`aion-arch/ideas/estimate-timespent-rollup-for-ticket-hierarchy.md`](../../ideas/estimate-timespent-rollup-for-ticket-hierarchy.md))
resolved the core shape of this feature (sum semantics, full recursion,
persistence, immediate recompute, one-commit-per-trigger batching,
universal display). Two points needed resolving against the actual
codebase during this proposal, not fully settled by the brainstorm:

### 1. The hand-edited-file trigger is dropped — it can't structurally occur

The brainstorm session concluded hand-edited `.md` files (picked up by
`TicketMarkdownWatcherService`) should also trigger a rollup recompute.
Grounding against `tickets.md`'s actual git-projection model shows this
scenario cannot occur:

- `TicketMarkdownWatcherService`/`TicketMarkdownReconciler` only ever
  reconcile `resource`/`page` tickets — every other type's projected
  file is a one-way, generated-only projection, "never read back into
  the database" (hand-editing it has zero effect).
- `estimate`/`timeSpent` (and therefore any rollup derived from them)
  are only meaningful on `epic`/`story`/`task`/`bug`/`chat` tickets —
  `resource`/`page` tickets have no estimate/time-spent UI at all.
- The [Structural type-compatibility](../../specs/tickets.md#structural-type-compatibility)
  table means `resource`/`page` can never structurally parent, or be
  parented by, a ranked type — the two subtrees (documentation vs.
  ranked work items) are structurally disjoint.

So the one ticket-type family that's ever hand-editable never carries a
rollup-relevant value, and the ticket-type family that does carry one is
never hand-editable. There is no case where a hand-edit could feed a
rollup recompute. This proposal implements the two triggers that *are*
real (in-app field edits, reparenting) plus trash/restore (see below);
`TicketMarkdownReconciler` is untouched.

### 2. Trash/restore added as a trigger, beyond what was brainstormed

The brainstorm session didn't discuss trashing. Left out, "always
accurate when viewed" would silently break in an obvious case: trash a
Story with a large estimate, and its parent Epic's rollup stays wrong
indefinitely (nothing else re-triggers a recompute until an unrelated
edit happens to touch that subtree again). Since the recompute
primitive already excludes non-live tickets by construction (it's built
on `TicketRepository.getAllTickets()`, which already filters
`deletedAt == null`), extending the same trigger to
`TicketsCubit.trashTicket`/`.trashTickets` and `TrashCubit.restore` is a
small, low-risk addition that keeps the feature's own stated goal true
in an obvious case a reviewer would otherwise hit immediately. Flagged
explicitly here as a deliberate scope addition, not silent creep.
Bulk restore, `permanentlyDelete`, `emptyTrash`, and `purgeOldTrash` are
**not** triggers — a ticket is already excluded from live rollups the
moment it's trashed, so a later permanent deletion of already-trashed
tickets changes nothing about the live tree.

## Non-goals

- **No UI to edit the rolled-up total directly.** It's read-only
  everywhere; only the leaf `estimate`/`timeSpent` fields remain
  editable, exactly as today.
- **No backfill UI or progress indicator.** Existing local databases
  get their rollups computed once, automatically, as part of the schema
  migration (see `design.md`) — no user-facing step.
- **No change to which fields are hand-editable.** `resource`/`page`
  files remain exactly as bidirectional as they are today; this feature
  adds no new writable surface to them.
- **No change to reparenting's own (pre-existing, separate) gap** that
  `updateTicketParent` doesn't itself trigger a git projection of the
  reparented ticket's `parentId` — untouched by this change.
- **No configurable rollup formula.** Sum-only, matching Jira's default
  behavior — no "rollup = max" or "rollup = average" option.
- **No cross-`ticket_links` contribution**, per the existing Rollup
  invariant already recorded in `tickets.md` — only the structural
  `parentId` tree contributes.
