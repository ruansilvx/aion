# Design: task-to-coding-execution-trigger

## 1. Agent-call plumbing: tool access + working directory

### 1.1 `AgentRequest` (`core/contracts/agent_model_client.dart`)

```dart
class AgentRequest extends Equatable {
  const AgentRequest({
    required this.prompt,
    required this.model,
    this.toolsEnabled = false,
    this.workingDirectory,
  });

  final String prompt;
  final String model;

  /// When `true`, the run may edit files, run git/bash, and use MCP —
  /// only ever set by `TicketsCubit`'s coding-execution path. Every
  /// existing caller (SDD-stage chats, Settings' connection test) leaves
  /// this `false`, preserving today's text-only behavior.
  final bool toolsEnabled;

  /// The directory the agent process should run in — required
  /// (non-null) whenever [toolsEnabled] is `true`, so file edits/git land
  /// in the actual project checkout rather than wherever the Flutter
  /// process happens to be running from. `null` for every text-only call.
  final String? workingDirectory;

  @override
  List<Object?> get props => [prompt, model, toolsEnabled, workingDirectory];
}
```

### 1.2 `ClaudeAgentSdkClient.run`

- `Process.start('node', [scriptPath], workingDirectory: request.workingDirectory)`
  — `Process.start`'s `workingDirectory` parameter already accepts `null`
  (defaults to the current process's cwd), so this is a direct pass-through,
  not a new branch.
- The JSON line written to the bridge's stdin gains `toolsEnabled`:
  `jsonEncode({'prompt': request.prompt, 'model': request.model, 'toolsEnabled': request.toolsEnabled})`.

### 1.3 `agent_bridge/index.mjs`

```js
const { prompt, model, toolsEnabled } = await readRequest();

for await (const message of query({
  prompt,
  options: {
    model,
    // Tool-enabled runs (Task coding-execution) get the SDK's default
    // tool set; every other caller keeps today's text-only behavior.
    ...(toolsEnabled ? {} : { allowedTools: [] }),
  },
})) { /* unchanged */ }
```

No new event types — `text`/`done`/`error`/`overage` already cover
whatever a tool-enabled run reports (tool-use turns still surface as
`assistant` messages with text content; intermediate tool-call/tool-result
messages are simply not forwarded as their own `AgentEvent`, same as today
— `ClaudeAgentSdkClient` never modeled those, and this change doesn't
start).

## 2. `ChatCubit.runChatTurn` — three additions

```dart
static Future<bool> runChatTurn({
  required AgentModelClient client,
  required CommentRepository commentRepo,
  required String chatTicketId,
  required String prompt,
  required AgentModel model,
  void Function(String textSoFar)? onChunk,
  bool toolsEnabled = false,
  String? workingDirectory,
  void Function()? onOverageDetected,
}) async {
  final buffer = StringBuffer();
  var succeeded = true;
  String? failureMessage;
  try {
    final events = await client.run(
      AgentRequest(
        prompt: prompt,
        model: model.id,
        toolsEnabled: toolsEnabled,
        workingDirectory: workingDirectory,
      ),
    );
    await for (final event in events) {
      switch (event) {
        case AgentTextEvent(:final text):
          buffer.write(text);
          onChunk?.call(buffer.toString());
        case AgentDoneEvent():
          break;
        case AgentOverageDetectedEvent():
          onOverageDetected?.call();
        case AgentErrorEvent(:final message):
          succeeded = false;
          failureMessage = message;
      }
    }
  } catch (e) {
    succeeded = false;
    failureMessage = e.toString();
  }

  if (succeeded && buffer.isNotEmpty) {
    await commentRepo.addComment(TicketComment(
      id: '',
      ticketId: chatTicketId,
      content: buffer.toString(),
      authorType: CommentAuthorType.ai,
      aiModel: model.id,
      createdAt: DateTime.now(),
    ));
  } else if (!succeeded) {
    // Previously dropped entirely — a failed run left no trace for
    // anyone not watching the chat live. Now persisted so
    // TicketDetailScreen/the chat transcript both show what happened.
    await commentRepo.addComment(TicketComment(
      id: '',
      ticketId: chatTicketId,
      content: 'Execution failed: ${failureMessage ?? 'unknown error'}',
      authorType: CommentAuthorType.ai,
      aiModel: model.id,
      createdAt: DateTime.now(),
    ));
  }
  return succeeded;
}
```

`sendMessage`'s existing call site is unaffected (new params all default
to today's behavior). `TicketsCubit._spawnStageChat`/`retryDesignSync`
are likewise unaffected — they don't pass the new params, so they get
`toolsEnabled: false` exactly as before.

## 3. Fixing `_sddStageAdvanceCheck`'s circular precondition

Before the gate below can mean anything, a real bug in the already-shipped
`_sddStageAdvanceCheck` has to be fixed — see proposal.md's "Grounding
correction." Today, advancing a `story` ticket out of `proposed` (to
`designBrief` or `verifying`) requires every child Task to already be
`TicketStatus.done`, regardless of which branch it's taking. That's
correct for the skip-design branch (straight to `verifying`, the same
"Tasks done gates verify" shape `sdd-ticket-execution` always had) but
wrong for the needs-design branch — `designBrief`/`designSync` are
supposed to run *before* code, so requiring Tasks done to even reach
`designBrief` makes that impossible.

```dart
// _sddStageAdvanceCheck's `case SddStage.proposed:` — story branch only
// (epic branch, checking child Stories archived, is unchanged):
case SddStage.proposed:
  final nextRank = ticket.type == TicketType.story
      ? TicketType.task
      : TicketType.story;
  final children = await _repository.getTicketsByParent(
    ticket.id,
    types: [nextRank],
  );
  final needsDesign = ticket.type == TicketType.story &&
      _storyNeedsDesignReview(children);
  final ready = children.isNotEmpty &&
      (needsDesign ||
          children.every(
            (c) => nextRank == TicketType.task
                ? c.status == TicketStatus.done
                : c.sddStage == SddStage.archived,
          ));
  return (
    canAdvance: ready,
    blockReason: ready ? null : SddStageBlockReason.awaitingChildren,
  );

// _sddStageAdvanceCheck's `case SddStage.designSync:` — now also
// requires Tasks done, restoring the check to the transition it always
// should have gated, one stage later than where it was misplaced:
case SddStage.designSync:
  final approved = await _designSyncApproved(ticket.id);
  final tasks = await _repository.getTicketsByParent(
    ticket.id,
    types: const [TicketType.task],
  );
  final ready = approved && tasks.isNotEmpty &&
      tasks.every((t) => t.status == TicketStatus.done);
  return (
    canAdvance: ready,
    blockReason: ready
        ? null
        : SddStageBlockReason.awaitingDesignApproval,
  );
```

`awaitingDesignApproval`'s hint copy stays generic enough to cover both
"not approved yet" and "approved but Tasks still in flight" — no new
`SddStageBlockReason` value needed. `_nextSddStage` itself (which stage
comes next) is unaffected — only the precondition for *when* the current
stage may be left changes.

## 4. Coding-execution gate

Built directly on the now-correctly-gated `_storyNeedsDesignReview`/
`_designSyncApproved` pair — not on `SddStage` position, sidestepping the
bug above entirely rather than depending on its fix being exactly right:

```dart
Future<({bool canStart, CodingExecutionBlockReason? reason})>
    _codingExecutionGateCheck(Ticket task) async {
  final story = await _governingStory(task);
  if (story == null) return (canStart: true, reason: null);
  final siblingTasks = await _repository.getTicketsByParent(
    story.id,
    types: const [TicketType.task],
  );
  if (!_storyNeedsDesignReview(siblingTasks)) {
    return (canStart: true, reason: null);
  }
  final approved = await _designSyncApproved(story.id);
  return (
    canStart: approved,
    reason: approved ? null : CodingExecutionBlockReason.storyDesignGatePending,
  );
}

/// Walks [task]'s `parentId` up to find the nearest `story` ancestor —
/// `null` if [task] is parentless or its nearest structural ancestor is
/// an `epic` (a Task parented directly by an Epic, ad hoc — no Story to
/// gate on, so it's never blocked). A Task's parent is always a Story or
/// an Epic or nothing at all (task-under-task is disallowed by
/// `TicketTypeHierarchy.canParent`), so this never walks more than one
/// level up in practice, but is written as a walk for defensiveness.
Future<Ticket?> _governingStory(Ticket task) async {
  var current = task;
  while (current.parentId != null) {
    final parent = await _repository.getTicketById(current.parentId!);
    if (parent == null) return null;
    if (parent.type == TicketType.story) return parent;
    if (parent.type == TicketType.epic) return null;
    current = parent;
  }
  return null;
}
```

`CodingExecutionBlockReason` (new enum, `tickets_state.dart`, one value:
`storyDesignGatePending`) mirrors `SddStageBlockReason`'s shape but is
surfaced as a rejection toast (`TicketsErrorReason.codingExecutionBlocked`
+ re-emitted `TicketDetailLoaded`, exactly like `_emitInvalidParent`), not
a persistent hint — the block prevents the status transition itself from
happening at all, so there's no in-between state to show a hint for.

## 5. Trigger + queue

`changeTicketStatus`/`updateTicketStatus` both gain the same intercept
before persisting, factored into a shared private helper:

```dart
Future<bool> _interceptTaskExecutionTrigger(Ticket task, TicketStatus status) async {
  if (task.type != TicketType.task || status != TicketStatus.inProgress) {
    return true; // not a trigger — proceed as normal
  }
  final check = await _codingExecutionGateCheck(task);
  if (!check.canStart) {
    emit(const TicketsError('', reason: TicketsErrorReason.codingExecutionBlocked));
    emit(TicketDetailLoaded(task));
    return false;
  }
  return true;
}
```

`changeTicketStatus`/`updateTicketStatus` call this first; a `false`
return skips the repository write entirely (mirrors `updateTicketParent`'s
early-return-on-rejection shape). On a `true` return, the existing status
write proceeds unchanged, and — only for the Task/`inProgress` case —
`_triggerOrQueueCodingExecution(refreshedTask)` is called after the
refresh.

```dart
String? _inFlightExecutionTaskId;
final List<String> _executionQueue = [];
bool _overageDetectedThisSession = false;

Future<void> _triggerOrQueueCodingExecution(Ticket task) async {
  if (_inFlightExecutionTaskId != null) {
    _executionQueue.add(task.id);
    return;
  }
  _inFlightExecutionTaskId = task.id;
  unawaited(_runCodingExecution(task));
}

Future<void> _runCodingExecution(Ticket task) async {
  final client = _agentClient;
  final commentRepo = _commentRepository;
  final automationRepo = _automationSettingsRepository;
  if (client == null || commentRepo == null) {
    _inFlightExecutionTaskId = null;
    unawaited(_dequeueNext());
    return;
  }

  // Captured before the run starts, not re-read from `state` afterward:
  // onOverageDetected below can emit a one-shot TicketsError toast
  // mid-run, which would otherwise clobber `state` and make a live
  // re-check wrongly conclude the detail screen isn't showing `task`
  // anymore (post-`/verify` correction — the first draft re-read `state`
  // at the bottom of this function and missed this race).
  final wasShowingTaskDetail = state is TicketDetailLoaded &&
      (state as TicketDetailLoaded).ticket.id == task.id;

  final now = DateTime.now();
  final chatTicket = Ticket(
    id: _uuid.v4(), ticketId: '', type: TicketType.chat,
    title: 'Coding Execution — ${task.title}',
    status: TicketStatus.backlog, parentId: task.id,
    createdAt: now, updatedAt: now,
  );
  await _repository.createTicket(chatTicket);
  final persistedChat = await _repository.getTicketById(chatTicket.id);
  if (persistedChat == null) {
    _inFlightExecutionTaskId = null;
    unawaited(_dequeueNext());
    return;
  }

  final context = _assembleExecutionContext(task);
  await commentRepo.addComment(TicketComment(
    id: '', ticketId: persistedChat.id, content: context,
    authorType: CommentAuthorType.system, createdAt: DateTime.now(),
  ));

  await ChatCubit.runChatTurn(
    client: client,
    commentRepo: commentRepo,
    chatTicketId: persistedChat.id,
    prompt: context,
    model: AgentModel.sonnet, // Out of scope: per-phase-tier-based-model-routing
    toolsEnabled: true,
    workingDirectory: _projectRootPath,
    onOverageDetected: () {
      if (!_overageDetectedThisSession) {
        _overageDetectedThisSession = true;
        emit(const TicketsError(
          '', reason: TicketsErrorReason.executionBudgetOverageDetected,
        ));
      }
    },
  );

  final prConfirmed = await _executionSucceededWithPr(task.id);
  if (prConfirmed && automationRepo != null) {
    final confidence = await _effectiveCodingExecutionConfidence(automationRepo);
    if (confidence == AutomationConfidence.auto) {
      await _repository.updateTicketStatus(task.id, TicketStatus.inReview);
    }
    // `gated`/`manual`: leave status as-is; TicketDetailScreen's
    // getTicketById re-check (below) surfaces the "ready for review"
    // banner or leaves it to a manual status change.
  }

  // Cleared before the refresh below (not after) so getTicketById's own
  // `isExecuting` computation correctly sees this run as finished, rather
  // than reporting the just-completed run as still in flight (second
  // post-`/verify` correction on this function — see above).
  _inFlightExecutionTaskId = null;

  if (wasShowingTaskDetail) {
    await getTicketById(task.id); // re-emits with fresh isExecuting/etc.
  }

  unawaited(_dequeueNext());
}

// `automationRepo`'s persisted AutomationContext.codingExecution
// confidence, forced to `gated` once _overageDetectedThisSession is
// true regardless of what's persisted — shared by _runCodingExecution's
// completion-flip decision above and getTicketById's
// executionAwaitingReview computation below so the two can't disagree
// about whether an overage-affected run counts as gated (third
// post-`/verify` correction: getTicketById originally read the
// repository directly, so the "ready for review" banner never appeared
// after an overage forced `gated` — _runCodingExecution correctly
// skipped the auto-flip, but nothing surfaced the resulting
// awaiting-review state instead).
Future<AutomationConfidence> _effectiveCodingExecutionConfidence(
  AutomationSettingsRepository automationRepo,
) async {
  return _overageDetectedThisSession
      ? AutomationConfidence.gated
      : await automationRepo.getConfidence(AutomationContext.codingExecution);
}

Future<void> _dequeueNext() async {
  if (_executionQueue.isEmpty) return;
  final nextId = _executionQueue.removeAt(0);
  final next = await _repository.getTicketById(nextId);
  if (next == null) {
    unawaited(_dequeueNext());
    return;
  }
  _inFlightExecutionTaskId = next.id;
  unawaited(_runCodingExecution(next));
}
```

`_assembleExecutionContext(Ticket task)` mirrors
`_assembleStageContext`'s shape: task title/description, plus an
instruction to open a PR as the last step of the run using the available
git/bash tools, ending the final reply with exactly one line —
`EXECUTION: PR_OPENED <url>` on success or `EXECUTION: NO_PR` if it
couldn't — mirroring `_assembleStageContext`'s existing
`designSync`/`"DESIGN GATE: APPROVED"` convention for a parseable
stage-completion signal.

`_executionSucceededWithPr(String taskId)` mirrors `_designSyncApproved`'s
own signature and lookup shape exactly (it takes the *Story's* id and
internally finds its `"Design Sync — "`-prefixed chat; this takes the
*Task's* id and internally finds its `"Coding Execution — "`-prefixed
chat): fetches `taskId`'s `chat` children, takes the most recently
created one titled `"Coding Execution — "`, and checks its most recent
comment is `CommentAuthorType.ai` with content containing
`'EXECUTION: PR_OPENED'`. Called as `_executionSucceededWithPr(task.id)`
in `_runCodingExecution` (not the spawned chat's own id) so `getTicketById`
(§6) can call it identically without needing to know the chat's id either.

## 6. `getTicketById` additions (Task tickets only)

```dart
bool isExecuting = false;
int? executionQueuePosition;
bool executionAwaitingReview = false;

if (ticket.type == TicketType.task) {
  isExecuting = _inFlightExecutionTaskId == ticket.id;
  final queueIndex = _executionQueue.indexOf(ticket.id);
  executionQueuePosition = queueIndex >= 0 ? queueIndex + 1 : null; // 1-based: queue's first entry is "next in line"
  if (!isExecuting && executionQueuePosition == null &&
      ticket.status == TicketStatus.inProgress) {
    final prConfirmed = await _executionSucceededWithPr(ticket.id);
    final automationRepo = _automationSettingsRepository;
    final confidence = automationRepo == null
        ? null
        : await _effectiveCodingExecutionConfidence(automationRepo);
    executionAwaitingReview =
        prConfirmed && confidence == AutomationConfidence.gated;
  }
}
```

`TicketDetailLoaded` gains `isExecuting`, `executionQueuePosition`,
`executionAwaitingReview` (all default `false`/`null`, Task-only —
mirrors `needsDesignReview`/`linkedDesignPage`'s "populated only for the
relevant type" precedent).

## 7. Widget tree — `TicketDetailScreen` (Task tickets)

Below the existing status/type/parent row (same location
`_SddStageSection` occupies for epic/story tickets), a Task ticket
renders, mutually exclusively:

```
if (isExecuting)
  _ExecutionRunningHint()               // "Coding execution in progress…"
else if (executionQueuePosition != null)
  _ExecutionQueueHint(position: executionQueuePosition!)
else if (executionAwaitingReview)
  _ExecutionReadyForReviewBanner(
    onConfirm: () => context.read<TicketsCubit>()
        .changeTicketStatus(ticket, TicketStatus.inReview),

```

- `_ExecutionRunningHint`/`_ExecutionQueueHint` mirror `_NotReadyHint`'s
  exact shape (`PhosphorIcon` + `Text`, `bodySm`/`textMuted`) — informational
  rows, no action.
- `_ExecutionReadyForReviewBanner` mirrors `_GatedBanner`'s shape (icon +
  text + a confirm `AppButton`) — the `gated` counterpart to SDD-stage
  advancement's own gated banner, calling the ticket's existing
  `changeTicketStatus` rather than a new cubit method.

## 8. `AutomationContext` generalization

```dart
// core/automation/automation_context.dart
enum AutomationContext {
  sddStage,
  codingExecution,
}
```

```dart
// core/automation/automation_settings_repository.dart
abstract interface class AutomationSettingsRepository {
  Future<AutomationConfidence> getConfidence(AutomationContext context);
  Future<void> setConfidence(AutomationContext context, AutomationConfidence confidence);
}
```

`SharedPrefsAutomationSettingsRepository` keys per context:
- `AutomationContext.sddStage` → `automation_settings.sdd_stage_automation`
  (unchanged key string — an existing user's saved preference survives).
- `AutomationContext.codingExecution` → `automation_settings.coding_execution_automation`
  (new key, defaults to `AutomationConfidence.gated` like every other
  first-time automated decision point).

`AutomationSettingsState.AutomationSettingsReady` carries
`Map<AutomationContext, AutomationConfidence> confidenceByContext`
instead of a single `confidence` field — chosen over two named fields so
a third context (the budget gate, the batch-flush gate — both still
unbuilt per `project.md` §5) slots in later with no state-shape change.
`AutomationSettingsCubit.load()` fetches both contexts in parallel;
`selectConfidence(AutomationContext, AutomationConfidence)` persists one
and re-emits the updated map.

`settings_screen.dart`'s `_AutomationSection` takes a
`required AutomationContext context` plus `required String label` /
`required String description` params instead of being SDD-stage-specific;
rendered twice — `AutomationContext.sddStage` (existing copy, unchanged)
and `AutomationContext.codingExecution` (new "Coding Execution
Automation" copy) — directly below each other in the same Settings
section.

## 9. Dependency wiring

`TicketsCubit`'s constructor gains one more optional named parameter,
`AutomationSettingsRepository? automationSettingsRepository`, following
the exact same "`null` no-ops the feature" pattern as `agentClient`/
`commentRepository`. `app_router.dart`'s real construction site
(`core/routing/app_router.dart:406`) adds
`automationSettingsRepository: context.read<AutomationSettingsRepository>()`
alongside its existing `agentClient`/`commentRepository` args — that
provider is already registered app-wide in `main.dart` (used today by
`AutomationSettingsCubit`'s own construction site), so no new
`RepositoryProvider` is needed, just reading the existing one from a
second location.

# Aion — Task-to-Coding-Execution Trigger: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md), and the [SDD Design Gate Spec](./Aion%20SDD%20Design%20Gate%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TicketDetailScreen`, `SettingsScreen`, `AutomationConfidence`, and the existing `_NotReadyHint`, `_GatedBanner`, and `_AutomationTrigger`/`_AutomationMenuRow` by name.

This change closes the last gap in Aion's SDD lifecycle. Moving a **Task** ticket to **"In Progress"** now spawns a real, **tool-enabled coding-execution run** — a chat where the agent edits files, runs git, and opens a PR — instead of the text-only conversational chat every other stage uses. One run executes at a time; additional Tasks queue **FIFO**. A finished run can require human confirmation before the Task flips to **"In Review."**

It **adds no new screens** — it extends two existing surfaces:

- **`TicketDetailScreen`** (`task` tickets) — a new **coding-execution section**, rendered in the same slot the SDD-stage tracker occupies for `epic`/`story` tickets. It shows one of three states: a **running-execution hint** (§1), a **queued-execution hint** (§2), or a **ready-for-review banner** (§3). Task tickets have no stage tracker; this section replaces it.
- **`SettingsScreen`** — the single "SDD Stage Automation" picker is generalized into a reusable **`_AutomationSection`** widget (§4), rendered twice: once for "SDD Stage Automation" (visually unchanged) and once, directly below, for a new **"Coding Execution Automation"** instance.

**No Material widgets anywhere.** Every surface is `DecoratedBox` / `Padding` / `Row` / `Column` / `GestureDetector` / `AnimatedSize` / `AnimatedOpacity` / `AnimatedScale` / `RotationTransition` / `CustomPaint`. No `Card`, `ElevatedButton`, `TextButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `InkWell`, `DropdownButton`, or `Chip`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` with the theme's `fillAlpha` (Arctic `0.11`, Obsidian `0.16`) unless another alpha is stated, exposed at the call site as `ThemeScope.of(context).fillAlpha`.

**No new color, typography, or radius tokens are required.** The one shade the ready-for-review button needs on hover is derived from an existing token (`Color.lerp(success, …)`, §3.4) — not a new palette member. One small structural addition: the `CodingRunState` enum (§5). See §5.

## 0. The coding-execution section (task tickets only)

A new section on `TicketDetailScreen`, rendered **only for `task` tickets whose status is `inProgress` (or later while a run is attached)**, placed directly below the ticket-meta row (type chip + status + priority + complexity) and above the Description block — the **same slot** the SDD-stage section (SDD Ticket Execution spec §2) occupies for `epic`/`story` tickets. Hidden entirely for every other type, and for a Task not yet in progress.

- **Container:** full-width, top `border` 1px (`#D6E0EA / #232C40`) — same section divider as Description/Comments. Padding `EdgeInsets.fromLTRB(22, 16, 22, 16)`. No fill, no radius (flush section, not a card). Inner layout `Column`, `crossAxisAlignment: stretch`, `gap: 14`.
- **Eyebrow:** `"CODING EXECUTION"`, `AionText.caption` (mono 11 / w600 / ls 1.54, uppercase), color `textMuted`.
- **Run-status line** (always present, mirrors the SDD current-stage line): a `Row`, `gap: 8` — an `8×8` filled dot + text, `AionText.body` (15 / w500), color `textPrimary`. The dot color and text encode the run state:

| `CodingRunState` | Dot color | Line text |
|---|---|---|
| `running` | `primary` (`#2E86D4 / #9366FF`) | `"Executing"` |
| `queued` | `secondary` (`#5E7183 / #57608A`) | `"Queued"` |
| `readyForReview` | `success` (`#1E9E76 / #33D19B`) | `"Run complete"` |

- **State body** (below the run-status line, `gap: 14` from it): exactly one of §1 (running), §2 (queued), or §3 (ready-for-review).

## 1. `_ExecutionRunningHint`

Shown while the Task's coding-execution chat is **actively running**. Mirrors `_NotReadyHint`'s informational-row shape (icon + text, no background, no border, no padding box — sits directly in the section flow) but takes an **active** treatment so it reads as "work in progress," not "blocked/waiting."

### 1.1 Layout

- `Row`, `gap: 8`, `crossAxisAlignment: center`. No border, no fill, no button, no tap target.
- **Leading glyph:** a **gear** (`gear` / `gear-six`) glyph, `15px`, color **`primary`** (`#2E86D4 / #9366FF`) — the active-work motif, distinct from `_NotReadyHint`'s passive `info` circle-i. Wrapped in a `RotationTransition` driven by an `AnimationController` (period `2400ms`, linear, `repeat()`) so it turns slowly and continuously — the sole "something is happening" signal. Never a Material `CircularProgressIndicator`. If reduced-motion is set (`MediaQuery.disableAnimations`), the controller is not started and the gear renders static.
- **Text:** `Expanded(Text(…))`, `AionText.bodySm` (13.5 / w400), color **`textSecondary`** (`#46586A / #A2AEC6`) — one notch more present than `_NotReadyHint`'s `textMuted`, because this is live activity, not an absent precondition.
  - Copy: `"Execution running — editing files and opening a pull request."`

### 1.2 States

Purely informational; **no** hover / focused / pressed / disabled / error states. The only motion is the continuous gear rotation (§1.1). Default is the only visual state.

## 2. `_ExecutionQueueHint`

Shown while the Task is **waiting behind another in-flight execution** (FIFO). Same informational-row shape as `_NotReadyHint` — passive/waiting, so it keeps the muted, static treatment — but displays an **interpolated queue position**.

### 2.1 Layout

- `Row`, `gap: 8`, `crossAxisAlignment: center`. No border, no fill, no button, no tap target.
- **Leading glyph:** a **stack / queue** glyph (`stack` or `list-numbers`), `15px`, color `textMuted` (`#8496A6 / #6B7690`) — matches `_NotReadyHint`'s passive weight, since a queued Task genuinely cannot proceed yet.
- **Text:** `Expanded(Text(…))`, `AionText.bodySm` (13.5 / w400), color `textMuted`.
  - Copy: `"Queued for execution — " + ordinal(position) + " in line."` → e.g. `"Queued for execution — 2nd in line."`
  - `position` is 1-based; `ordinal(1) = "1st"`, `ordinal(2) = "2nd"`, `ordinal(3) = "3rd"`, `ordinal(4) = "4th"`, … `ordinal(11..13) = "11th/12th/13th"`. When `position == 1` (next to run, nothing ahead has started yet), copy reads `"Queued for execution — next in line."`

### 2.2 States

Purely informational; **no** hover / focused / pressed / disabled / error states. Default is the only visual state. The position string updates reactively as the queue drains (a plain rebuild — no entrance/exit animation on the text).

## 3. `_ExecutionReadyForReviewBanner`

Shown once the Task's coding-execution run **finished successfully** (a PR was confirmed opened) and `AutomationConfidence.gated` applies — the human must confirm before the Task flips to "In Review." Mirrors `_GatedBanner`'s tinted container, border, leading icon, and title + sub-line, but takes a **`success` identity** rather than `primary` (a PR was actually opened — this is a completion moment, not an "advance the SDD stage" prompt) and **stacks its action button full-width below the text** instead of trailing it inline.

### 3.0 Layout divergence from `_GatedBanner` (button placement)

`_GatedBanner` trails a short `"Advance"` pill inline. This banner's label — `"Mark ready for review"` — is ~2.5× as wide and does not fit inline beside a two-line title at the narrowest supported phone width (`336` content px) without crushing the title to 3 lines. **Decision:** the container is a `Column` (`crossAxisAlignment: stretch`, `gap: 12`) — a top `Row` (icon + text column) then a **full-width** button beneath. This keeps the title on 1–2 lines and reads the confirmation as the banner's primary CTA. All fills/border/radius are otherwise `_GatedBanner`'s, re-keyed to `success`.

### 3.1 Container — geometry mirrors `_GatedBanner`, color re-keyed to `success`

- `DecoratedBox` → `Padding` → `Column`.
- **Fill:** `success.withOpacity(fillAlpha)` (`0.11 / 0.16`) — was `primary` in `_GatedBanner`.
- **Border:** `1px solid success.withOpacity(isDark ? 0.42 : 0.28)`.
- **Radius:** `BorderRadius.circular(12)` (`AionRadius.lg`).
- **Shadow:** none.
- **Padding:** `EdgeInsets.fromLTRB(14, 13, 14, 14)`.
- **Layout:** `Column`, `crossAxisAlignment: stretch`, `gap: 12` — (1) a top `Row` (`gap: 12`, `crossAxisAlignment: center`) holding the leading glyph (§3.2) + text column (§3.3), then (2) the full-width action button (§3.4).

### 3.2 Leading glyph

- A **`git-pull-request`** glyph (the "a PR is open" motif), `18px`, color **`success`** (`#1E9E76 / #33D19B`). This — plus the `success` fill/border and the `success` button — is the whole visual signal that this banner means "coding finished, PR open," distinct from `_GatedBanner`'s `primary` `sparkle` "advance the SDD stage" meaning. (If a `git-pull-request` glyph is unavailable in the icon set, fall back to `seal-check` `18px` `success` — the completion read is preserved.)

### 3.3 Text column (`Expanded`, `gap: 2`)

- **Title:** `"Coding run finished — PR opened"`, `AionText.cardTitle` (14 / w600), color `textPrimary` (`#142230 / #E7EDF7`).
- **Sub-line:** the run summary, `AionText.time` (mono 11 / w400), color `textSecondary` (`#46586A / #A2AEC6`) — e.g. `"PR #128 · 6 files changed · confirm to move to review"`, *if* that metadata is ever parsed from the run's reply. Optional; omitted today since `_executionSucceededWithPr` only checks for the literal `EXECUTION: PR_OPENED` line, with no PR number/file-count parsing — no metadata is available, so the title carries alone (post-`/verify` correction: the shipped implementation initially rendered a placeholder sub-line here instead of omitting it, fixed to match this rule).

### 3.4 Action button — "Mark ready for review" (solid `success`, full-width)

- `GestureDetector` → `DecoratedBox` → `Padding` → centered `Text`. Full container width (`crossAxisAlignment: stretch` on the parent `Column`), label centered.
- **Fill:** `success` (`#1E9E76 / #33D19B`) — the completion color, not `primary`.
- **Label:** `"Mark ready for review"`, `AionText.button` (14 / w700), color `#FFFFFF`, `TextAlign.center`.
- **Padding:** `EdgeInsets.symmetric(horizontal: 15, vertical: 10)`.
- **Radius:** `AionRadius.md` (10).
- **Shadow (glow):** `BoxShadow(color: success.withOpacity(isDark ? 0.60 : 0.45), blurRadius: 18, spreadRadius: -9, offset: Offset(0, 8))` — the same FAB-glow shape as the gated Advance button, re-keyed to `success`.
- **No dismiss affordance.** Unlike `_GatedBanner`, this banner has no `×` — a finished run with an open PR is not dismissible session state; the only forward action is confirmation. (If the automation is later changed to `manual`, the banner is simply not shown; if `auto`, the Task flips silently and an auto-note appears instead — out of scope here, reuse SDD spec §2.5's success-note pattern verbatim.)

### 3.5 Button states (both themes)

| State | Fill | Glow | Extra |
|---|---|---|---|
| **Default** | `success` | `success.withOpacity(isDark ? 0.60 : 0.45)`, blur 18, spread −9, offset (0,8) | — |
| **Hover** | `Color.lerp(success, isDark ? Colors.white : Colors.black, 0.10)` (derived shade — **no new token**) | glow blur → 22 | `MouseRegion` click cursor |
| **Focused** (keyboard) | `success` | default glow | 3px focus ring `BoxShadow(color: success.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` |
| **Pressed** | `success` | glow suppressed (blur → 0) | `AnimatedScale` to `0.98` over 80ms on `onTapDown` |
| **Disabled** (confirm request in flight) | `success` @ `0.45` opacity | none | `IgnorePointer`; label `#FFFFFF` @ `0.45` |
| **Error** | n/a | — | a failed confirmation surfaces via the existing app toast, out of scope — the banner stays in Default |

## 5. New enums / types (no new design tokens)

```dart
// Drives the coding-execution section body (§0). task tickets only.
enum CodingRunState { running, queued, readyForReview }
//   running        → §1 _ExecutionRunningHint
//   queued         → §2 _ExecutionQueueHint  (carries a 1-based `queuePosition`)
//   readyForReview → §3 _ExecutionReadyForReviewBanner (only when confidence == gated)

// Reused verbatim from SDD Ticket Execution spec §7 — governs BOTH automation sections (§4):
enum AutomationConfidence { auto, gated, manual }   // default gated

// Mode-dot color resolver — reused unchanged from SDD Ticket Execution spec §7:
Color confidenceDot(AutomationConfidence c, AionColors k) {
  switch (c) {
    case AutomationConfidence.auto:   return k.success;
    case AutomationConfidence.gated:  return k.primary;
    case AutomationConfidence.manual: return k.secondary;
  }
}

// Queue-position ordinal (§2.1):
String ordinal(int n) {
  if (n >= 11 && n <= 13) return '${n}th';
  switch (n % 10) {
    case 1: return '${n}st';
    case 2: return '${n}nd';
    case 3: return '${n}rd';
    default: return '${n}th';
  }
}
```

**No new `AionColors`, `AionText`, or `AionRadius` members.** Every color is an existing token (the ready-for-review hover shade is `Color.lerp` of `success`, not a stored color); every text style is an existing `AionText.*`; every radius is `AionRadius.md`/`lg` or a `BoxShape.circle`; all spacing is a 4-multiple.
