# Design: blocked-ticket-transition-gate

## 1. `TicketsCubit._isTicketBlocked`

New private helper, scoped to one ticket — the single-ticket counterpart
to `_computeBlockedTicketIds` (which resolves the whole board's blocked
set in one query). Placed near `_computeBlockedTicketIds` in
`tickets_cubit.dart`.

```dart
/// Whether [ticket] currently has an unresolved `blocks`/`blockedBy`
/// dependency — i.e. a live link naming [ticket] as the blockee whose
/// blocker either doesn't exist or isn't [TicketStatus.done]. Mirrors
/// [_computeBlockedTicketIds]'s row-resolution logic (a `blockedBy`
/// row's blockee is its source; a `blocks` row's blockee is its
/// target) but scoped to a single ticket via
/// [TicketLinkRepository.getLinksForTicket] rather than the board-wide
/// bulk query, since this runs once per `inProgress` transition attempt
/// rather than once per board load. Returns `false` if constructed
/// without a [TicketLinkRepository] (mirrors
/// [_computeBlockedTicketIds]'s same fallback). Added for
/// `aion-arch/changes/blocked-ticket-transition-gate`.
Future<bool> _isTicketBlocked(Ticket ticket) async {
  final linkRepo = _linkRepository;
  if (linkRepo == null) return false;

  final rows = await linkRepo.getLinksForTicket(ticket.id);
  for (final row in rows) {
    final (blockeeId, blockerId) = switch (row.linkType) {
      'blockedBy' => (row.sourceTicketId, row.targetTicketId),
      'blocks' => (row.targetTicketId, row.sourceTicketId),
      _ => (null, null),
    };
    if (blockeeId != ticket.id || blockerId == null) continue;
    final blocker = await _repository.getTicketById(blockerId);
    if (blocker == null || blocker.status != TicketStatus.done) {
      return true;
    }
  }
  return false;
}
```

Note: `getLinksForTicket` returns links where the ticket is *either*
source or target, already filtered to just that ticket — no type
filter, so the loop above discards every row whose `linkType` isn't
`blocks`/`blockedBy` (the `_ => (null, null)` branch, then the
`blockeeId != ticket.id` guard for anything not naming this ticket as
blockee) exactly as `_computeBlockedTicketIds` does for its bulk case.

## 2. `TicketsCubit._interceptBlockedDependencyTrigger`

New private interceptor, same shape and same file region as the
existing `_interceptTaskExecutionTrigger` (immediately above or below
it).

```dart
/// Gate on a ticket's move to [TicketStatus.inProgress]: rejects the
/// transition if [ticket] currently has an unresolved `blocks`/
/// `blockedBy` dependency (`_isTicketBlocked`). Unlike
/// [_interceptTaskExecutionTrigger], applies to every ticket type — the
/// Board's `_BlockedBadge` this enforces is itself type-agnostic. `true`
/// means the transition may proceed (not blocked, or [status] isn't
/// `inProgress` — not a gated transition). On rejection, emits
/// [TicketsErrorReason.blockedByOpenDependency] then a re-emitted
/// unchanged [TicketDetailLoaded], mirroring
/// [_interceptTaskExecutionTrigger]'s exact reject shape, and returns
/// `false` so the caller skips the write entirely. Added for
/// `aion-arch/changes/blocked-ticket-transition-gate`.
Future<bool> _interceptBlockedDependencyTrigger(
  Ticket ticket,
  TicketStatus status,
) async {
  if (status != TicketStatus.inProgress) return true;
  if (!(await _isTicketBlocked(ticket))) return true;
  emit(
    const TicketsError(
      '',
      reason: TicketsErrorReason.blockedByOpenDependency,
    ),
  );
  emit(TicketDetailLoaded(ticket));
  return false;
}
```

## 3. Wiring into the two status-changing entry points

Both call sites already special-case `status == TicketStatus.inProgress`
to run `_interceptTaskExecutionTrigger`; this change adds the new
interceptor ahead of it, short-circuiting on the first rejection so only
one toast fires per attempt. Order: blocked-dependency (a structural
"is this ticket even allowed to start" check) before task-execution
readiness (a narrower "is this Task's Story design-approved" check) —
if a ticket is both blocked and design-incomplete, the more fundamental
reason surfaces.

### `updateTicketStatus` (board drag / list-shaped callers)

```dart
Future<void> updateTicketStatus(String id, TicketStatus status) async {
  if (status == TicketStatus.inProgress) {
    final target = await _repository.getTicketById(id);
    if (target != null) {
      if (!(await _interceptBlockedDependencyTrigger(target, status))) {
        return;
      }
      if (!(await _interceptTaskExecutionTrigger(target, status))) {
        return;
      }
    }
  }
  // ...unchanged from here down.
```

### `changeTicketStatus` (detail-screen callers)

```dart
Future<void> changeTicketStatus(Ticket ticket, TicketStatus status) async {
  if (!(await _interceptBlockedDependencyTrigger(ticket, status))) return;
  if (!(await _interceptTaskExecutionTrigger(ticket, status))) return;
  // ...unchanged from here down.
```

Both dartdoc comments (`updateTicketStatus`'s and `changeTicketStatus`'s)
get a clause added describing the new interceptor, alongside their
existing description of `_interceptTaskExecutionTrigger`.

## 4. `TicketsErrorReason.blockedByOpenDependency`

New enum value in `tickets_state.dart`, added next to
`codingExecutionBlocked` (same file region, same doc-comment shape):

```dart
/// A ticket was rejected from moving to `TicketStatus.inProgress`
/// because it has an unresolved `blocks`/`blockedBy` dependency — see
/// `TicketsCubit._isTicketBlocked`. Applies to every ticket type,
/// unlike `codingExecutionBlocked`. The widget layer reads this via
/// `ticketsErrorMessage` / `AppToast`. Added for
/// `aion-arch/changes/blocked-ticket-transition-gate`.
blockedByOpenDependency,
```

## 7. No BLoC-state shape changes

`TicketsError`/`TicketDetailLoaded` are unchanged — this reuses their
existing `reason` field and existing shape entirely. No new
`TicketsState` subclass, no new `TicketsLoaded` field (unlike
`board-task-ordering-indication`'s `blockedTicketIds`, which this change
depends on but does not modify).

## 8. Flow (drag-and-drop path, representative of all three surfaces)

1. User drags a blocked ticket's card onto a different `BoardColumn`.
2. `BoardColumn.onAcceptWithDetails` calls
   `TicketsCubit.updateTicketStatus(ticket.id, TicketStatus.inProgress)`.
3. `status == TicketStatus.inProgress`, so the ticket is fetched fresh
   and `_interceptBlockedDependencyTrigger` runs first.
4. `_isTicketBlocked` finds a live `blocks`/`blockedBy` row naming this
   ticket as blockee, with a blocker whose status isn't `done` → returns
   `true`.
5. `_interceptBlockedDependencyTrigger` emits `TicketsError(reason:
   blockedByOpenDependency)` then `TicketDetailLoaded(ticket)`, returns
   `false`.
6. `updateTicketStatus` returns immediately — no optimistic update, no
   repository write, no git-projection trigger.
7. The `TicketsError` emission is picked up by the existing
   `BlocListener`/`AppToast` wiring (unchanged by this change) and shown
   as a toast reading `ticketsErrorMessage`'s new string.
8. The card visually snaps back (the Board never left its prior
   `TicketsLoaded` state's card positions, since no `TicketStatusUpdating`
   optimistic emission ever happened) — same visual outcome an SDD-
   design-blocked Task drag already produces today.

## 9. Test plan (mirrors existing coverage shape)

- `tickets_cubit_test.dart`: new tests for `updateTicketStatus` and
  `changeTicketStatus`, each covering: (a) a blocked ticket of a
  non-Task type (e.g. an Epic or Story) rejected with
  `blockedByOpenDependency`, proving the gate isn't Task/Bug-scoped
  like `codingExecutionBlocked`; (b) a ticket whose blocker is `done`
  proceeding normally; (c) a ticket with no `blocks`/`blockedBy` links
  at all proceeding normally; (d) a move to a status other than
  `inProgress` never invoking the new interceptor at all (existing
  `verify(...never...)`-style assertions, matching how
  `_interceptTaskExecutionTrigger`'s existing tests already isolate
  `inProgress`-only invocation).
- No widget-test changes needed — `MoveToStatusMenu`/`BoardColumn`
  aren't touched, and the toast-rendering path
  (`ticketsErrorMessage`/`AppToast`) is exercised by existing tests for
  `codingExecutionBlocked`/`invalidParent` already; the new switch case
  just needs its own one-line coverage alongside those (see tasks.md).
