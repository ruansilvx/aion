# Coding Execution Reliability And Safety

# Proposal: coding-execution-reliability-and-safety

## What

`sdd-ticket-execution`/`task-to-coding-execution-trigger` shipped a real,
tool-enabled coding-execution mechanism, and a live dogfood run against the
actual `aion` checkout on 2026-07-23 proved it genuinely works — Aion drove
a real Task through to a real PR. That same run surfaced four
empirically-confirmed gaps (`coding-execution-reliability-and-safety.md`,
explored 2026-07-23), which this change closes together:

1. **No verification gate before a PR opens.** `_assembleExecutionContext`
   instructs the model to open a PR as the run's unconditional last step —
   one dogfood run shipped a real PR containing a non-existent
   `BoxShadow(inset: true)` parameter that `flutter analyze` would have
   caught in about a second.
2. **The agent's own git operations can destroy uncommitted human work.**
   Coding execution runs directly in `Project.rootPath` — the developer's
   real checkout, with no isolation. A `git reset`/branch-checkout sequence
   mid-run silently discarded two unrelated uncommitted files during the
   dogfood run.
3. **No Task-level signal when a run fails, stalls, or finishes
   ambiguously.** A hard API error, a silent no-`EXECUTION:`-line
   completion, and a genuinely stuck run are all invisible at the Task
   level — the only recovery path is the undocumented toggle-status-away-
   and-back workaround.
4. **No progress visibility during the tool-use phase.** A run can sit
   silent for minutes while reading files or fighting permissions, with no
   UI signal until it produces prose or ends.

Concretely, this change:

1. Isolates every coding-execution run in a dedicated `git worktree`,
   created and torn down by Aion's own Dart code (`GitRepositoryClient`) —
   the shared developer checkout is never touched by an execution run
   again.
2. Splits the run into two turns: an implementation turn (tools enabled,
   ends with `IMPLEMENTATION: DONE`, no PR-opening instruction), then an
   Aion-run `flutter analyze` gate inside the worktree, then — only on a
   clean pass — Aion itself (plain `git`/`gh` calls, no model call) pushes
   the branch and opens the PR. Retry-on-failure behavior is a new
   consumer of the existing `AutomationConfidence` pattern
   (`AutomationContext.codingExecutionRetry`): `auto` retries automatically
   (capped at 2 corrective turns, then escalates to `gated`'s visibility —
   mirroring the existing overage-forces-`gated` precedent), `gated`
   surfaces a one-shot toast plus the banner below, `manual` only ever
   surfaces via the banner's always-available retry control.
3. Adds a unified Task-detail status banner covering every non-success
   state — verify-gate failure (with the analyze output), hard error,
   silent no-result completion, and a stalled/orphaned run — each with a
   one-click manual retry, replacing the undocumented toggle-workaround
   entirely. Generalizes the existing `_ExecutionReadyForReviewBanner`
   slot rather than bolting on a second, separate UI element.
4. Adds a real `AgentToolUseEvent` variant to `AgentModelClient`, surfacing
   the Claude Agent SDK's own tool-use events (already received and
   discarded by `agent_bridge/index.mjs` today) live through `ChatCubit`'s
   existing streaming.

## Why

`self-iteration-sequencing.md`'s own `next_action` (2026-07-23) recommended
this exact brainstorm before proposing `new-project-onboarding`'s remaining
pieces — "particularly the working-tree-safety finding, which has real
data-loss consequences independent of any further product surface built on
top of it." The brainstorm session (same date) resolved all four findings
together rather than splitting the data-loss fix off alone, since Findings
1 and 2 turned out to be architecturally coupled (see Scope below) and
splitting them would mean building the worktree lifecycle twice.

Every design decision below was checked against how the equivalent concept
already works elsewhere in this project rather than invented fresh:

- The two-turn verify-then-PR split mirrors `/verify`→`/archive`'s own
  separation (`aion-arch-workflow.md`: "`/verify` reports, doesn't fix"),
  and the retry-cap-then-escalate behavior reuses the exact
  `_overageDetectedThisSession`-forces-`gated` pattern
  `_effectiveCodingExecutionConfidence` already established for budget
  overages — a new instance of an established idiom, not a new one.
- `AutomationContext.codingExecutionRetry` reuses
  `AutomationConfidence`/`_AutomationSection`'s existing per-context
  generalization exactly as `task-to-coding-execution-trigger` did for
  `codingExecution` itself — a third `_AutomationSection` instance in
  Settings, not a new settings mechanism.
- The unified failure banner generalizes `_CodingExecutionSection`'s
  existing mutually-exclusive if/else chain (running / queued / awaiting-
  review) rather than adding a parallel widget tree.
- Worktree isolation was chosen over blocking-on-dirty-tree or auto-stash
  (the two options this idea originally framed) because it removes the
  risk structurally; the vendored Claude Agent SDK's own
  `worktree.bgIsolation` setting was checked and found to be scoped to its
  background-session/agent-view feature, not the plain `query()` call
  `agent_bridge/index.mjs` makes, so Aion has to own this itself via
  `git worktree` directly (see `coding-execution-reliability-and-safety.md`'s
  Summary of answers §2).

## Scope

- **`GitRepositoryClient`** (`core/git/git_repository_client.dart`) gains
  `createWorktree`/`removeWorktree` (wrapping `git worktree add -b
  <branch> <path>` / `git worktree remove <path> --force`) and `push`
  (`git push -u origin <branch>`).
- **New `core/git/github_cli_client.dart`** (`GitHubCliClient`, same
  "thin CLI wrapper, no interface" shape as `GitRepositoryClient`) —
  `openPullRequest(rootPath, branch, title, body)` wraps `gh pr create`.
- **New `core/build/flutter_verifier.dart`** (`FlutterVerifier`) —
  `analyze(String rootPath)` wraps `flutter analyze`, returning a pass/
  fail result plus raw output. Same "one implementation, no interface"
  shape.
- **`AgentModelClient`** (`core/contracts/agent_model_client.dart`) gains
  `AgentToolUseEvent` (tool name + short summary) as a new
  non-terminal `AgentEvent` variant.
- **`ClaudeAgentSdkClient`** parses the bridge's new `tool_use` NDJSON
  line into `AgentToolUseEvent`.
- **`agent_bridge/index.mjs`** additionally filters `tool_use` content
  blocks out of each `assistant` message (already present in the SDK's own
  stream, previously discarded) and emits a summarized `{"type":
  "tool_use", "name", "summary"}` line per tool call.
- **`ChatCubit.runChatTurn`** gains an optional `onToolUse` callback,
  invoked per `AgentToolUseEvent`, mirroring `onOverageDetected`'s
  existing shape. `ChatState`/`ChatLoaded` gains `currentToolUse` (String?,
  cleared on the next text chunk or on completion).
- **`TicketsCubit._runCodingExecution`** is restructured around the
  worktree lifecycle and the two-turn implement→verify→PR split:
  - Creates a worktree + branch, runs `flutter pub get` in it once, points
    `workingDirectory` at the worktree for every turn in the run.
  - `_assembleExecutionContext` drops the PR-opening instruction; ends
    with `IMPLEMENTATION: DONE` instead of `EXECUTION: PR_OPENED`/`NO_PR`.
  - After the implementation turn, runs `FlutterVerifier.analyze` in the
    worktree (no model call). On a clean pass, pushes and opens the PR
    itself via `GitRepositoryClient.push`/`GitHubCliClient.openPullRequest`,
    then posts a system comment ending with `EXECUTION: PR_OPENED <url>`
    (the existing terminal-signal convention, now authored by Aion instead
    of the model — `_executionSucceededWithPr` is updated to match on
    content regardless of author type).
  - On an analyze failure, branches on the effective
    `AutomationContext.codingExecutionRetry` confidence (see What, above)
    to decide whether a corrective turn (same chat, new implementation
    turn fed the analyze errors) runs automatically, up to 2 retries.
  - The worktree is removed (not the branch) in a `finally`, regardless of
    outcome.
- **`AutomationContext`** gains `codingExecutionRetry`.
  `SharedPrefsAutomationSettingsRepository` gains its storage key,
  following the exact pattern `codingExecution` itself already
  established.
- **New `TicketsErrorReason.executionVerificationFailed`** — one-shot
  toast for the `gated` case and for `auto`'s retry-cap-exhausted
  escalation, mirroring `executionBudgetOverageDetected`'s existing shape.
- **`TicketDetailLoaded`** gains `executionFailureReason` (String?) and
  `executionCanRetry` (bool), Task-only, computed in `getTicketById` from
  the most recent execution chat's most recent comment (reusing
  `_mostRecentChatHasTerminalReply`'s existing lookup shape) — survives an
  app restart, unlike today's `isExecuting`/`executionQueuePosition`.
- **`_CodingExecutionSection`**'s if/else chain (running / queued /
  awaiting-review) grows a fourth, mutually-exclusive branch for
  `executionFailureReason != null`, and a shared `_ExecutionActionBanner`
  widget (icon/color/message/action, parameterized) backs both the
  existing ready-for-review banner and the new failure banner, plus a
  small inline "running `<tool>`..." row consuming `ChatState`'s new
  `currentToolUse` while a run is actively executing.
- **Settings screen**: a third `_AutomationSection` instance, "Coding-
  Execution Retry," alongside the existing two.
- **`TicketsCubit`** gains a new public `retryCodingExecution(Ticket
  task)` method — the banner's manual-retry action, and also what
  `gated`'s toast links to.

## Out of scope

- **Scoped `flutter test`** — the original idea floated "`flutter analyze`
  and possibly a scoped `flutter test`" as the verify gate. Test-file
  selection (which tests relate to a given Task's changed files) is a
  nontrivial heuristic on its own; this change ships `flutter analyze`
  only. Captured as a natural follow-up once this ships, not designed
  here.
- **Worktree disk-bloat optimization** (symlinking `.dart_tool`/`build`
  from the main checkout instead of a fresh `flutter pub get` per
  worktree) — correctness over speed for this change; each execution run
  pays one `pub get` in its fresh worktree. Revisit only if this proves
  too slow in practice.
- **Per-tool-call structured detail beyond name + short summary** in
  `AgentToolUseEvent` — no file diffs, no full command output, matching
  this idea's "is this alive + what's it touching" scope, not a full
  transcript viewer.
- **Cancelling an in-flight or queued run** — not raised in this idea's
  brainstorm; still out of scope, as it was for the original coding-
  execution change.
- **True concurrent (multi-slot) execution** — unchanged; still one
  execution slot, FIFO queue.
- **A GitHub-agnostic PR-hosting abstraction** — `GitHubCliClient` wraps
  `gh` directly, matching this project's existing GitHub-specific
  `/archive` skill; no provider abstraction introduced.

mirroring the existing `destructiveTint` shape exactly (see design.md §4

**Notable design decisions worth flagging for `/apply`** (non-blocking):
the failure banner's error region is a fixed-max-height (96px) scrollable
mono well with a persistent bottom fade rather than a "show details"
disclosure, chosen so the banner's height stays constant regardless of
error length (design.md §1.4); the Retry button is colored `secondary`,
not `danger`, so it reads as a calm recovery action rather than a
destructive one (design.md §1.5); the live tool-use indicator uses a slow
opacity pulse rather than sharing the existing gear's rotation, so the two
liveness signals don't visually compete (design.md §2.1).
