# Design: New-project onboarding — Inbox

## 1. Domain additions

### 1.1 `InboxPurpose` (new enum, `domain/enums/inbox_purpose.dart`)

```dart
enum InboxPurpose {
  brainDump,
  whatNextGuidance,
  releasePlanning,
  qa,
}
```

Meaningful only on a `chat` ticket spawned by the Inbox — every other
ticket (including every other `chat`) has `inboxPurpose == null`. Also
the field that lets `TicketTypeHierarchy`'s otherwise type-level
`isAlwaysRoot` rule get a per-instance exception (see §1.3) without
loosening it for every `chat` ticket.

### 1.2 `Ticket.suggestedType` (new field)

`TicketType? suggestedType` — meaningful only for `signal` tickets, set
by the brain-dump purpose's classification (Epic or Bug), read by the
widened promote-chooser (§4) to pre-select which target type to promote
to. `null` for every ticket not created by brain-dump, and `null` for
brain-dump signals until the model actually classifies them (defensive
default — a parse failure on one block shouldn't crash the rest of the
reply).

### 1.3 `Ticket.inboxPurpose` (new field)

`InboxPurpose? inboxPurpose` — set exactly once, at creation, on the
parentless `chat` ticket an Inbox launch spawns. `null` for every other
ticket. Two consumers:

- **`ChatCubit._phaseForChat`** (`tickets.md`'s existing chat-model-phase
  inference): today it walks `chat.parentId` upward to resolve a
  `ModelPhase`, falling back to `ModelPhase.capable` only defensively
  ("never hit in real usage" per its own dartdoc, since every existing
  chat has a resolvable parent). Once Inbox ships, that fallback *would*
  be hit for every Inbox chat's `parentId == null` — but the four
  purposes don't all want `capable` (see §2's phase table). Add a new
  first branch: if `chat.inboxPurpose != null`, resolve phase directly
  from a purpose→phase mapping and return, before ever consulting
  `parentId`. Update the method's dartdoc to describe this as a second,
  parent-independent resolution path, not just a defensive fallback.
- **Reparent guard.** `TicketsCubit.updateTicketParent` currently
  rejects setting a non-null parent on a ticket whose *type*
  `isAlwaysRoot` is true (epic/signal/release). `chat` is deliberately
  **not** added to `isAlwaysRoot` — that's a type-level, unconditional
  rule, and it would wrongly force every manually-created `chat` (which
  `CreateTicketScreen` already permits with no parent validation today —
  a confirmed pre-existing, unrelated gap this change doesn't touch) to
  also be parentless. Instead, `updateTicketParent` gains one more
  per-instance condition alongside the existing `isAlwaysRoot` check:
  also reject a non-null-parent assignment when
  `ticket.type == TicketType.chat && ticket.inboxPurpose != null`. Same
  rejection path (`_emitInvalidParent`), same user-facing behavior as
  the epic/signal/release case — just keyed off an instance field
  instead of the static type property, since `isAlwaysRoot` has no way
  to express "only when this specific ticket came from the Inbox."

### 1.4 Drift schema (version 8)

Two new nullable `TextColumn`s on `TicketsTable`
(`features/tickets/data/models/ticket_model.dart`), storing the enum
name as plain text (matching `complexity`/`sddStage`/`severity`'s
existing convention — no drift enum converter in use anywhere in this
table):

```dart
TextColumn get suggestedType =>
    text().named('suggested_type').nullable()();
TextColumn get inboxPurpose =>
    text().named('inbox_purpose').nullable()();
```

`app_database.dart`: `schemaVersion` → `8`; `migration.onUpgrade` gains
`if (from < 8) { addColumn(ticketsTable, ticketsTable.suggestedType);
addColumn(ticketsTable, ticketsTable.inboxPurpose); }`, following the
exact shape of the existing version-6/7 branches. Update the class
dartdoc's version-history list with the new "Version 8 adds
`TicketsTable.suggestedType`/`inboxPurpose`" line.

`TicketModel`'s row↔entity conversion gains the matching
`TicketType.values.byName(...)`/`InboxPurpose.values.byName(...)`
parse-or-null pairs, mirroring `sddStage`'s existing conversion.

## 2. Model routing

No new `ModelPhase` value — Inbox's four purposes map onto the existing
`frontier | capable | execution` tiers (`execution` never applies; no
Inbox purpose is a Task coding-execution run):

| Purpose | `ModelPhase` | Why |
|---|---|---|
| Brain-dump | `frontier` | Classifying raw ideas into Epics/Bugs is the same reasoning weight as `_materializeDecomposition`'s epic/story decomposition, which already runs at `frontier`. |
| What-next guidance | `frontier` | Advisory judgment call across the whole backlog — same weight class as the CLI `/what-next` skill it ports, which itself runs at spec-phase weight. |
| Release planning | `frontier` | Creates/links planning-level tickets; judgment-heavy, not mechanical. |
| Q&A | `capable` | General lookup/read-and-answer — `ModelPhase.capable`'s own definition ("comparatively mechanical work") fits better than `frontier`'s epic/story-level judgment framing. |

`InboxCubit` resolves each purpose's model directly via
`ModelRoutingRepository.getModelForPhase(phase)` at launch time — it
does not rely on `ChatCubit._phaseForChat`'s inference for the *opening*
turn (only human follow-up replies inside an already-created Inbox chat
go through `ChatCubit.sendMessage`, which is where §1.3's new
`_phaseForChat` branch matters).

## 3. Q&A tool-tier decision

The idea's brainstorm assumed an existing "read-only source-code tool
tier" shared with `designSync`. Confirmed by code inspection this does
not exist: `designSync`'s `ChatCubit.runChatTurn` call
(`TicketsCubit.retryDesignSync`) never sets `toolsEnabled`, so it
defaults to `false` — zero tool access, pure prompt-stuffed text
context. `agent_bridge/index.mjs` itself only ever offers two states:
`allowedTools: []` (`toolsEnabled: false`) or full
`permissionMode: 'bypassPermissions'` (`toolsEnabled: true`) — no
partial/read-only allowlist exists anywhere in the bridge.

**Decision:** Q&A's *opening* turn only reuses codebase-summarization's
exact worktree-isolation shape
(`TicketsCubit._runFullSummarization`): a fresh, throwaway
`GitRepositoryClient.createWorktree` (never `rootPath` itself),
`toolsEnabled: true` (full `bypassPermissions`), a prompt that
explicitly instructs read-only exploration ("do not edit, commit, or
push"), and the worktree removed in a `finally` block regardless of
outcome. Every subsequent human reply inside that same Q&A chat ticket
goes through the ordinary `ChatCubit.sendMessage` path unchanged
(`toolsEnabled` defaults to `false` — plain conversational continuation
off the accumulated transcript, exactly like every other existing chat
ticket type today). This avoids spinning up a new worktree per human
follow-up turn, and avoids inventing worktree-lifecycle management for
an open-ended, potentially-long-lived chat.

**Tradeoff accepted:** Q&A's tool access is enforced by prompt
instruction and worktree disposability, not by a real permission
restriction — identical risk profile to codebase-summarization today,
not a new or worse one. Building an actual read-only `allowedTools`
subset in `agent_bridge/index.mjs` (e.g. `Read`/`Grep`/`Glob` only, no
`Write`/`Edit`/`Bash`) would be a strictly safer future improvement, but
is a meaningfully larger, separate surface (bridge protocol change,
`AgentModelClient` interface change) — out of scope for this change,
left as a follow-up idea if the informal read-only pattern ever proves
insufficient.

## 4. Widened signal promotion

`TicketsCubit.promoteSignalToEpic(Ticket signal, {String?
existingEpicId})` is renamed and generalized:

```dart
Future<void> promoteSignal(
  Ticket signal, {
  required TicketType targetType,
  String? existingTicketId,
})
```

- Validates `targetType == TicketType.epic || targetType ==
  TicketType.bug` (else `TicketsError`, mirroring the existing
  wrong-source-type guard).
- Everything else is identical to today's logic, just parameterized:
  creates a new `targetType` ticket (copying `signal.title`/
  `description`) or links to `existingTicketId`, via the same
  `TicketLinkType.relatesTo` link — still a link, not a type
  conversion, per the existing dartdoc's "promotion is a link, not a
  conversion" framing.

`ticket_overflow_menu.dart`'s `_PromoteChooser`/`_RootMenu`:
`_RootMenu`'s single "Promote to Epic" row becomes two rows ("Promote
to Epic" / "Promote to Bug"); `_PromoteChooser`'s `candidatesLoader`
takes the chosen `targetType` and filters `getAllTickets()` by it
instead of the hardcoded `TicketType.epic`. Whichever row corresponds to
`signal.suggestedType` (when non-null) renders first/pre-highlighted —
exact visual treatment left to `/design-sync`.

## 5. `InboxCubit` / `InboxState`

New files: `presentation/cubit/inbox_cubit.dart`, `inbox_state.dart` —
same feature (`features/tickets/`) as `DocumentationCubit`, following
its exact provisioning precedent: a fresh instance per route entry to
`/workspace/inbox` (not root-scoped), constructed with
`TicketRepository`, `CommentRepository`, `TicketLinkRepository`,
`AgentModelClient`, `ModelRoutingRepository`.

**States:**
- `InboxInitial`
- `InboxLoading`
- `InboxLoaded({required List<Ticket> history})` — every
  Inbox-spawned chat (`getTicketsByParent(null, types: [TicketType.chat])`,
  filtered defensively to `inboxPurpose != null` even though nothing
  else can currently produce a parentless chat, then sorted by
  `createdAt` descending). No new repository method needed — this query
  shape already exists (used today for Documentation's root-doc query).
- `InboxLaunching` — a purpose launch is in flight (spawning the chat
  ticket + running its opening turn); carries which `InboxPurpose` is
  launching, for the launcher UI's own per-card loading state.
- `InboxError(String message)`

**Methods:**
- `load()` — as above.
- `startBrainDump(String rawText)` — creates a parentless `chat` ticket
  (`inboxPurpose: brainDump`), posts a system comment assembling the
  prompt (below), runs the opening turn via `ChatCubit.runChatTurn`
  (`toolsEnabled: false`, model per §2), then parses the reply (§5.1)
  into `signal` tickets. Returns the created chat ticket's id (for the
  screen to navigate into `ticketDetailRoute`).
- `startWhatNextGuidance()` — creates the chat, assembles context per
  §5.2 (no user input needed), runs the opening turn, no reply parsing
  (advisory prose only).
- `startReleasePlanning()` — creates the chat, assembles context per
  §5.3 (existing Epic/Story/Task/Bug tickets, read-only), runs the
  opening turn. Unlike the other three purposes this is genuinely
  multi-turn-conversational before it concludes — the opening turn may
  just be the model asking a clarifying question. Reply parsing (§5.3)
  runs on *every* turn in this chat (opening and human-follow-up alike),
  not just the first — `InboxCubit` re-parses each new AI comment for
  the `RELEASE:`/`RELEASE PLAN: DONE` markers as `ChatCubit.sendMessage`
  persists it, materializing the release ticket + links only once the
  terminal marker actually appears.
- `startQa(String initialQuestion)` — creates the chat
  (`inboxPurpose: qa`), runs the one-shot worktree-isolated opening turn
  per §3, no reply parsing (free-form prose). Every later reply in this
  chat is a normal `ChatCubit.sendMessage` call from the ordinary chat
  UI, not a method on `InboxCubit`.

### 5.1 Brain-dump prompt/parse contract

Prompt instructs: "Read the following raw notes and identify one or
more distinct ideas or issues worth turning into tickets. For each,
reply in exactly this format:

```
SIGNAL: <short title>
<one to three sentence description>
TYPE: epic|bug
```

End your reply with exactly one line: `BRAINDUMP: DONE`."

Parser (mirrors `_parseSummaryFindings`'s existing block-splitting
shape): each `SIGNAL:` line starts a new block; a `TYPE:` line
(case-insensitive, `epic` or `bug`, anything else treated as absent)
sets that block's suggested type; everything else until the next
`SIGNAL:`/terminal line is the description. Each parsed block becomes a
`TicketRepository.createTicket(type: signal, suggestedType: <parsed>,
...)` call.

### 5.2 What-next-guidance context assembly

Literal port of the CLI `/what-next` skill's priority order, reading
from ticket/page data instead of parsing `aion-arch` markdown:

1. Any ticket currently mid-SDD-stage (`sddStage != null`, not
   `archived`) — surfaced first, as "you have in-flight SDD work."
2. "Known gaps" sections from Documentation `page` tickets (plain text
   scan of page body content already loaded via
   `TicketRepository`/`PageTicketProvider` — no new parsing
   infrastructure, same content the human already reads on
   `PageDetailScreen`).
3. Open `signal` tickets not yet promoted (no outgoing `relatesTo` link
   to an `epic`/`bug`).

Assembled as one plain-text prompt (no tool access, matching
`designSync`'s existing shape) — the model's reply is advisory prose,
never parsed or acted on programmatically.

### 5.3 Release-planning prompt/parse contract

Context: every `epic`/`story`/`task`/`bug` ticket's id, title, and
status (read-only `TicketRepository` query, not agent tool access).
Prompt instructs the model to converse with the user about which
tickets belong in the release, and once settled, reply with:

```
RELEASE: <release name>
LINK: <ticket id>
LINK: <ticket id>
...
RELEASE PLAN: DONE
```

On seeing the terminal `RELEASE PLAN: DONE` line in any AI comment in
this chat, `InboxCubit` creates a new `release` ticket titled from the
`RELEASE:` line, then one `TicketLinkRepository.createLink(...,
linkType: relatesTo)` per `LINK:` id (skipping any id that doesn't
resolve to a real ticket — defensive, not surfaced as an error, since
the model may hallucinate an id typo mid-conversation).

## 6. Navigation shell changes

`WorkspaceNavShell` (`core/routing/workspace_nav_shell.dart`) currently
hardcodes exactly two top-level destinations via a closed
`_NavDestination` enum, with per-destination callback plumbing
(`onSelectTickets`/`onSelectDocumentation`) threaded individually
through `_WideShell`, `_Sidebar`, `_CompactShell`, `_BottomTabBar` — not
a data-driven list. Adding Inbox as a third destination:

- `_NavDestination` gains `inbox`.
- `_destinationFor` gains: `location.startsWith('/workspace/inbox') →
  inbox`. Inbox-spawned chats do **not** get their own route prefix —
  they render via the existing `/workspace/tickets/:id` route
  (`TicketDetailScreen`/`ChatCubit`, unchanged), so opening one from the
  Inbox history list resolves to the **Tickets** destination, not
  Inbox — same as any other ticket detail view. This mirrors
  Documentation's own precedent of `page`s living outside their nav
  destination's route prefix, just without the reverse case (Inbox has
  no content living *inside* its own prefix analogous to
  `/workspace/pages/*`).
- `_Sidebar` gains a third `_NavItem` (Inbox, an inbox/tray-style
  Phosphor Light glyph — exact icon choice left to `/design-sync`),
  between Documentation and the `Spacer`.
- `_BottomTabBar`'s `Row` grows from three `Expanded` cells (Tickets,
  Documentation, secondary-trigger) to four. Three equal-width
  destination cells plus the trigger is measurably tighter at narrow
  phone widths than today's two — flagged explicitly as a visual
  question for `/design-sync` to resolve (e.g. whether compact labels
  need to shrink, or the secondary-trigger cell needs a fixed width
  instead of `Expanded`), not assumed free.
- New top-level route in `app_router.dart`: `/workspace/inbox` →
  `InboxScreen`, `ShellRoute`-wrapped by `WorkspaceNavShell` exactly
  like `/workspace/tickets`/`/workspace/documentation` today,
  `BlocProvider<InboxCubit>` scoped to that one route (matching
  `DocumentationCubit`'s provisioning).

## 7. Screens & widgets

- **`InboxScreen`** (`/workspace/inbox`) — header (title), a
  four-card/button launcher section (Brain dump — opens an inline text
  input, submits via `startBrainDump`; What's next — one-tap
  `startWhatNextGuidance`; Plan a release — one-tap
  `startReleasePlanning`; Ask a question — opens an inline text input,
  submits via `startQa`), then the history section: a
  reverse-chronological list of `InboxHistoryItem` rows below a small
  section heading, or `InboxEmptyState` when `history` is empty. Body
  wrapped in `ContentMaxWidth(variant: reading)`, matching
  Documentation's layout precedent. On a successful launch, navigates
  to `ticketDetailRoute(createdTicket)` (the ordinary chat-ticket
  detail view — no new detail screen).
- **`InboxHistoryItem`** (`presentation/widgets/inbox_history_item.dart`)
  — presentational row: a small purpose badge/icon (one of four,
  keyed off `Ticket.inboxPurpose`), title, relative timestamp
  (`relative_time_format.dart`, already exists). Tapping navigates to
  `ticketDetailRoute(ticket)`. No business logic, matching
  `DocumentationTreeItem`'s precedent.
- **`InboxEmptyState`** — shown when `history` is empty: filled faction
  motif, heading, supporting copy, matching
  `DocumentationEmptyState`'s existing convention (no primary action of
  its own — the launcher above it already is one).

# Aion — Inbox Feature Specification

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and references the [Persistent Navigation Shell Spec](./Aion%20Navigation%20Shell%20Spec.md) and [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md) by section. References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `ContentMaxWidth`, `TypeChip`, `SelectionMenu`, `NavShell` by name.

This feature adds a new **standing, non-ticket, app-level "Inbox"** — a third top-level navigation destination (alongside Tickets and Documentation) that launches four purpose-specific AI chats and lists past launches. It also widens one existing chooser (the signal "Promote" menu, §7).

Design covers **both themes** throughout: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). Where a component is theme-identical that is stated; otherwise concrete hex is given as `Arctic / Obsidian` **for reference only** — implement against the named token, which already resolves per theme via `ThemeScope.of(context).colors`.

**Hard constraint — no Material.** Build from Flutter primitives only: `DecoratedBox`, `GestureDetector`, `FocusableActionDetector`, `MouseRegion`, `AnimatedScale`, `AnimatedSize`, `Row`/`Column`/`Stack`, `Container`, `Padding`, `CustomPaint`, `LayoutBuilder`, `MediaQuery`, `Overlay`. **Never** `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `AppBar`, `ListTile`, `SnackBar`, `InkWell`, `DropdownButton`. The **one** sanctioned exception is a bare `TextField` for actual text entry, wrapped in a transparent `Material` ancestor — reuse that existing codebase pattern for the two inline inputs (§4.2, §4.5); do not invent a new text-entry field.

> **API note — translucent fills.** The color section of the brief specifies this codebase's current API as `token.withValues(alpha: x)` (the deprecated form being `withOpacity`). This spec therefore expresses every translucent fill as **`token.withValues(alpha: x)`**. The export-checklist line requesting `withOpacity` is treated as superseded by the codebase's stated current API. If your local `AionColors`/`Color` still predates `withValues`, substitute `withOpacity(x)` one-to-one — no value changes. Never hardcode ARGB.

### 0.2 Routing & shell integration

- Route: `/workspace/inbox`, wrapped by the existing `NavShell` exactly like Tickets and Documentation.
- The `NavSection` enum gains a third value: `enum NavSection { tickets, documentation, inbox }`.
- Every purpose launch (§4) navigates into an **existing** chat-ticket detail view (`TicketDetailScreen` for a `chat`-type ticket) — **out of scope here**. This spec ends at the point of navigation.

### 0.3 New tokens introduced

No new base palette hues. Four **purpose accents** are each an alias of an existing `typeXxx` token, mirroring the `AionColorsHubTokens` extension pattern (`token.withValues(alpha: isDark ? X : Y)`). One new text style is added for the launcher card label; everything else reuses existing `AionText`.

```dart
/// Inbox purpose → base accent (reuses existing type-accent tokens; no new hues).
enum InboxPurpose { brainDump, whatsNext, planRelease, askQuestion }

Color inboxAccentFor(InboxPurpose p, AionColors c) {
  switch (p) {
    case InboxPurpose.brainDump:   return c.typeSignal;  // cyan  — raw captured signals
    case InboxPurpose.whatsNext:   return c.typeStory;   // green — forward momentum / next work
    case InboxPurpose.planRelease: return c.typeRelease; // vermilion — a release/milestone
    case InboxPurpose.askQuestion: return c.typeChat;    // indigo — a Q&A conversation
  }
}
```

Rationale for each base token (per the brief's requirement to state which and why):

| Purpose | Base token | Arctic / Obsidian | Why |
|---|---|---|---|
| **Brain dump** | `typeSignal` | `#0E8C9E / #34C6D6` | Brain dump ingests raw, unstructured notes and converts them into tickets — the same "noticed but not yet resolved into work" idea `signal` already encodes. Cyan. |
| **What's next** | `typeStory` | `#1E9E76 / #33D19B` | Guidance on the next unit of work to advance; green reads as *go / forward progress*, and a story is the canonical "next actionable" unit. |
| **Plan a release** | `typeRelease` | `#D8402C / #F26A4B` | Directly about releases/milestones — reuses the exact accent the `release` ticket type already owns. Vermilion. |
| **Ask a question** | `typeChat` | `#4C6FDE / #7C93FF` | General Q&A is a conversation; reuses the `chat` type accent it launches into. Indigo. |

These four resolve to **four clearly distinct hues** (cyan · green · vermilion · indigo), so the launcher and the history badges are scannable as a set even though the four are functionally similar (2 inputs, 2 one-tap).

**Tint convention** — identical to `TypeChip` (base spec §1.3): a badge/card *fill* uses the accent at `fillAlpha` (Arctic `0.11`, Obsidian `0.16`); the icon and any full-strength swatch/label use the accent at full strength.

```dart
const double fillAlphaArctic   = 0.11;
const double fillAlphaObsidian = 0.16;
double fillAlpha(bool isDark) => isDark ? fillAlphaObsidian : fillAlphaArctic;
// fill  = inboxAccentFor(p, c).withValues(alpha: fillAlpha(isDark));
// icon  = inboxAccentFor(p, c);  // full strength
```

New text style (compact launcher-card label; Manrope, matches the `cardTitle`/`button` family):

```dart
// AionText — one new alias:
static const inboxCardLabel = TextStyle(
  fontFamily: 'Manrope', fontSize: 15, fontWeight: FontWeight.w700,
  letterSpacing: -0.1, height: 1.15,
); // color applied at use site (textPrimary)
```

All other type is existing: `h1`, `caption`, `cardTitle`, `body`, `bodySm`, `button`, `label`, `time`, `streamStatus`.

## 1. `WorkspaceNavShell` — third destination ("Inbox")

### 1.3 Compact bar re-proportioning (4 cells) — the sizing decision

Going from **3 cells** (2 destinations + trigger, each an equal `Expanded` third = **125px** at a 375px window) to a naive **4 equal `Expanded`** quarters would drop every cell to **93.75px** — a visible squeeze on narrow phones.

**Chosen approach: fix the secondary-actions trigger cell to a 56px width and keep the three *destinations* as equal `Expanded` thirds of the remaining space.** A destination is the thing that must stay tappable and legible; the avatar trigger is a fixed 38px circle that never needed a full share.

```dart
// _BottomTabBar Row children:
Row(children: [
  Expanded(child: _NavItem.compact(NavSection.tickets)),        // ~106px @ 375
  Expanded(child: _NavItem.compact(NavSection.documentation)),  // ~106px @ 375
  Expanded(child: _NavItem.compact(NavSection.inbox)),          // ~106px @ 375
  SizedBox(width: 56, child: Center(child: _SecondaryTrigger())),// fixed
]);
```

At 375px: destinations = `(375 − 24 padding − 56 trigger) / 3 ≈ 98px` each (vs. 93.75 for equal quarters) — and, critically, the destinations stay **equal to one another** and the trigger stops stealing a full 94px cell. (Bar padding is Nav Shell §3's `EdgeInsets.fromLTRB(12, 8, 12, 14)` + bottom safe-area; the 56px trigger cell centers its 38px avatar.)

**Secondary tightening at ultra-narrow widths.** Below a 360px bar content-width, step the compact destination icon 22 → **20px** and the label 11 → **10.5px** (`navTabLabel.copyWith(fontSize: 10.5)`), driven off the shell `LayoutBuilder`. This is the only responsive type change; above 360px the §4 values stand.

The mockups show the **current 2-destination** bar and the **new 3-destination** bar side by side at a **375px** window so the difference is visible.

#### 1.3.1 Compact bar container

Unchanged from Nav Shell §3: full width; 72px content + `MediaQuery.viewPadding.bottom`; fill `surface`; **top** 1px `border`; no radius; no shadow; padding `EdgeInsets.fromLTRB(12, 8, 12, 14)` + safe-area.

#### 1.3.2 Inbox compact cell — icon & states

- **Icon:** `tray`, 22px (20px below 360px bar width), `currentColor`.
- **Label:** `"Inbox"`, `AionText.navTabLabel`.
- States identical to Nav Shell §4.2 (Default / Hover / Focused / Pressed scale 0.97 / Active `primarySubtle`+`primary`). Theme values per Nav Shell §2.2.

### 1.4 Trigger cell (unchanged look)

The 38×38 "U" avatar trigger (Nav Shell §5) is visually unchanged — only its cell is now a fixed `SizedBox(width: 56)` instead of an `Expanded` share (§1.3). All trigger states, placement, and the popover (Nav Shell §5–6) are unchanged. The popover still opens upward, right edge inset 16px.

## 3. Launcher section (`_LauncherGrid`)

Four purpose entries (§4). **Layout decision: a 2×2 grid of cards on wide viewports, collapsing to a single vertical stack on narrow ones** — as the brief's default. Justification: the four are peers of equal weight; a 2×2 grid reads them as one balanced set at a glance (no implied ranking), pairs naturally within the 840px reading column, and the card footprint gives the two inline-input purposes room to expand in place (§4.2) without reflowing siblings. A single row of four would crowd at 840px and force tiny targets; a list would over-emphasize order.

| Property | Value |
|---|---|
| Wide (`column width ≥ 560`) | `GridView`-free 2×2 via two `Row`s of two `Expanded` cards, `gap: AionSpacing.sp16` both axes (`Column` of `Row`s, `SizedBox(width/height: sp16)` gutters). Do **not** use a Material `GridView` — plain `Row`/`Column`. |
| Narrow (`< 560`) | single `Column`, cards full width, `gap: AionSpacing.sp12` |
| Card min height | 96px (collapsed); expands with `AnimatedSize` when an inline input opens (§4.2) |

The 560px inner breakpoint is measured on the **content column**, not the window (`LayoutBuilder` inside `ContentMaxWidth`), so the grid collapses correctly whether narrowed by window or by the reading cap.

## 7. Widened "Promote" menu (existing signal chooser, modified)

Extends [SDD Ticket Execution Spec §5](./Aion%20SDD%20Ticket%20Execution%20Spec.md). Today the signal overflow menu offers a single **"Promote to Epic"** row, which (per that spec §5.2) opens an inline candidate-list chooser (existing Epics to link to, or "Create new"). This change makes the **root** a two-choice step — **"Promote to Epic"** and **"Promote to Bug"** — before the same candidate-list overlay opens (now filtered to Epics or Bugs by the choice).

Panel and row styling are **unchanged** from the existing overflow overlay (base + SDD spec §5): `DecoratedBox` panel, fill `surface`, 1px `borderStrong`, `AionRadius.lg` (12), `AionShadows.card` overlay shadow, panel padding `EdgeInsets.all(5)`; rows `GestureDetector` → `DecoratedBox` → `Padding` → `Row`. No Material. Panel width **210px** — a touch wider than the SDD delete-menu (196px) so the longer label plus a trailing "Suggested" pill (§7.3) fit on one line without wrapping.

### 7.1 Root menu — two rows (replacing the single row)

Row order: **Promote to Epic** (1), **Promote to Bug** (2).

| Property | Value |
|---|---|
| Row padding | `EdgeInsets.symmetric(horizontal: 13, vertical: 9)` |
| Row radius | `AionRadius.sm`→8 fill on hover |
| Layout | `Row`, `gap: 10`, `crossAxisAlignment: center` |
| Leading icon | Epic row → `crown` 16px; Bug row → `bug` 16px; both `textSecondary` (default) |
| Label | `AionText.bodySm` at **w600**, color `textPrimary` |
| Trailing (suggested row only) | "Suggested" pill (§7.3) |
| Row gap | 1px (matching the SelectionMenu row stack) |

Both rows open the candidate-list chooser (SDD §5.2) on tap — Epic filters to epics + "Create new epic"; Bug filters to bugs + "Create new bug". The back-chevron header of that chooser (SDD §5.2) now returns to **this two-row root** rather than dismissing.

### 7.2 Root-row states

| State | Fill | Label/icon | Notes |
|---|---|---|---|
| Default | transparent | `textPrimary` / icon `textSecondary` | |
| Hover (pointer) | `surfaceHover` | `textPrimary` / icon `textSecondary` | `MouseRegion` click cursor |
| Focused (keyboard) | `surfaceHover` | same | arrow keys move focus between the two rows |
| Pressed | `border` fill | same | commits → opens candidate chooser (does not dismiss) |
| Selected | n/a | — | root rows are momentary; no persistent selected state |
| Disabled | n/a | — | never disabled |

Both rows are **non-destructive** (promote, not delete) — neither uses the `danger` hover treatment; both use the standard `surfaceHover`. (Consistent with SDD §5.1's non-destructive promote row.)

### 7.3 "Suggested" treatment

When the signal being promoted already carries an AI-suggested classification (Epic **or** Bug), the matching root row gets a **"Suggested" treatment**, distinguishable at a glance from the other row. **Chosen: a compact accent pill on the trailing edge, plus a faint accent-tinted row background** — two redundant cues so it reads instantly and survives greyscale.

- **Trailing pill:** `"Suggested"`, `AionText.chip` (Manrope 10.5 / w700, uppercased → `"SUGGESTED"`), pill `AionRadius.sm` (6), height 18px, padding `EdgeInsets.symmetric(horizontal: 7, vertical: 1)`. Fill = the target type's accent at `fillAlpha(isDark)`; label = full accent. Epic-suggested → `typeEpic` (`#6A5AD0 / #5C7CF5`); Bug-suggested → `typeBug` (`#5E8C1E / #98D13C`).
- **Row background (resting):** the suggested row's default (non-hover) fill becomes `accent.withValues(alpha: isDark ? 0.09 : 0.06)` — a whisper of the accent, lighter than the `surfaceHover` hover fill so hover still reads as a state change on top of it. The non-suggested row stays transparent at rest.
- **Leading dot (optional third cue):** a 6×6 full-accent dot may prefix the suggested row's icon; the pill is the primary signal, so this is optional and off by default to avoid clutter.

Only **one** row is ever suggested (the classifier returns a single best type); if the signal has no suggestion, neither row gets the treatment and both rest transparent.

#### 7.3.1 Suggested-row state interaction

| State | Fill | Pill |
|---|---|---|
| Default (suggested) | `accent.withValues(alpha: isDark ? 0.09 : 0.06)` | shown |
| Hover / Focused | `surfaceHover` (overrides the tint) | shown |

The pill persists across all states; only the row fill changes.
