# Design: Ticket sort control and board as default view

## 1. Domain layer — new sort entity + repository

### 1.1 `TicketSortField` / `TicketSortDirection` (new enums)

`lib/features/tickets/domain/enums/ticket_sort_field.dart`:

```dart
enum TicketSortField { relevance, priority, status, type, createdAt, updatedAt }
```

- `relevance` — BM25 match score against an active search query. Only
  ever the *implicit* default (see §3.2); has no direction toggle (its
  ordering is always "best match first" — SQLite's `bm25()` ascending).
- `priority`/`status`/`type` sort by each enum's **declaration order** —
  already semantically meaningful (`TicketPriority.critical` is index 0,
  `TicketStatus.backlog` is index 0, `TicketType.epic` is index 0), not
  alphabetical by name.
- `createdAt`/`updatedAt` sort by the literal timestamp column.

`lib/features/tickets/domain/enums/ticket_sort_direction.dart`:

```dart
enum TicketSortDirection { ascending, descending }
```

Applies to every field except `relevance`, which ignores it.

### 1.2 `TicketListSort` (new entity)

`lib/features/tickets/domain/entities/ticket_list_sort.dart` — mirrors
`TicketListFilters`' shape:

```dart
class TicketListSort extends Equatable {
  const TicketListSort({required this.field, required this.direction});
  final TicketSortField field;
  final TicketSortDirection direction;
  @override
  List<Object?> get props => [field, direction];
}
```

### 1.3 `TicketListSortRepository` (new interface) + Drift-independent impl

`lib/features/tickets/domain/repositories/ticket_list_sort_repository.dart`:

```dart
abstract interface class TicketListSortRepository {
  /// The persisted explicit sort for [projectId], or `null` if the user
  /// has never explicitly chosen one for this project (the implicit
  /// query-aware default applies — see TicketsCubit._implicitSort).
  Future<TicketListSort?> getSort(String projectId);

  /// Persists [sort] as [projectId]'s explicit selection, overwriting
  /// whatever was previously saved.
  Future<void> setSort(String projectId, TicketListSort sort);
}
```

A sibling of `TicketListFilterRepository`, not an extension of it —
sort and filters are independent selections with different "unset"
semantics (an unset filter field is an empty `Set`, meaning "no
constraint"; an unset sort is `null`, meaning "no explicit choice yet,
use the implicit default"). Keeping them separate leaves every existing
`TicketListFilterRepository`/`SharedPrefsTicketListFilterRepository`
call site and test untouched.

`lib/features/tickets/data/repositories/shared_prefs_ticket_list_sort_repository.dart`
— same `shared_preferences` pattern as
`SharedPrefsTicketListFilterRepository`, two project-id-scoped string
keys instead of three string-list keys (a sort selection is one value,
not a set):

```dart
class SharedPrefsTicketListSortRepository implements TicketListSortRepository {
  String _fieldKey(String projectId) => 'ticket_list_sort.$projectId.field';
  String _directionKey(String projectId) => 'ticket_list_sort.$projectId.direction';

  @override
  Future<TicketListSort?> getSort(String projectId) async {
    final prefs = await SharedPreferences.getInstance();
    final fieldName = prefs.getString(_fieldKey(projectId));
    final directionName = prefs.getString(_directionKey(projectId));
    if (fieldName == null || directionName == null) return null;
    final field = TicketSortField.values
        .where((v) => v.name == fieldName)
        .firstOrNull;
    final direction = TicketSortDirection.values
        .where((v) => v.name == directionName)
        .firstOrNull;
    if (field == null || direction == null) return null;
    return TicketListSort(field: field, direction: direction);
  }

  @override
  Future<void> setSort(String projectId, TicketListSort sort) async {
    final prefs = await SharedPreferences.getInstance();
    await prefs.setString(_fieldKey(projectId), sort.field.name);
    await prefs.setString(_directionKey(projectId), sort.direction.name);
  }
}
```

## 2. Data layer — DB-level ordering

### 2.1 `TicketRepository.searchTickets` gains `sort`

```dart
Future<TicketSearchPage> searchTickets({
  String? query,
  Set<TicketStatus> statuses = const {},
  Set<TicketType> types = const {},
  Set<TicketPriority> priorities = const {},
  required TicketListSort sort,
  required int limit,
  int offset = 0,
});
```

`sort` is `required` (not defaulted) — the caller (`TicketsCubit`, see
§3) always has a concrete resolved value to pass, so there's no
ambiguous "no sort" case at this layer to default around. Dartdoc
updated: "Ordered per `sort.field`/`sort.direction`. `sort.field ==
TicketSortField.relevance` orders by BM25 match score and requires
`query` to be non-empty — passing it with an empty `query` falls back
to `createdAt` descending, since there is no relevance score to order
by; every other field orders independent of whether `query` is set."

`DriftTicketRepository.searchTickets` passes `sort` straight through to
`TicketDao.searchTickets` (thin passthrough, same as every other
parameter today).

### 2.2 `TicketDao.searchTickets` — building the `ORDER BY`

A new private helper resolves `sort` to a Drift `OrderingTerm` for the
query-builder branch (no active query), and to a raw SQL fragment for
the FTS `customSelect` branch (query active):

```dart
/// Maps [field]'s declared enum values to their ordinal position, for
/// priority/status/type — SQLite has no notion of Dart enum order, so
/// this expresses it as an explicit CASE expression. Returns `null` for
/// createdAt/updatedAt/relevance, which don't need this (createdAt/
/// updatedAt sort directly by their own column; relevance sorts by
/// bm25(), handled separately).
String? _enumOrdinalCaseSql(TicketSortField field) {
  List<Enum>? values = switch (field) {
    TicketSortField.priority => TicketPriority.values,
    TicketSortField.status => TicketStatus.values,
    TicketSortField.type => TicketType.values,
    TicketSortField.createdAt ||
    TicketSortField.updatedAt ||
    TicketSortField.relevance => null,
  };
  if (values == null) return null;
  final column = switch (field) {
    TicketSortField.priority => 'tickets.priority',
    TicketSortField.status => 'tickets.status',
    TicketSortField.type => 'tickets.type',
    _ => throw StateError('unreachable'),
  };
  final whens = [
    for (var i = 0; i < values.length; i++)
      'WHEN \'${values[i].name}\' THEN $i',
  ].join(' ');
  return 'CASE $column $whens ELSE ${values.length} END';
}

/// The literal column [field] sorts by directly (createdAt/updatedAt
/// only) — `null` for priority/status/type (see [_enumOrdinalCaseSql])
/// and relevance (see bm25 handling in [searchTickets]).
String? _directColumnSql(TicketSortField field) => switch (field) {
  TicketSortField.createdAt => 'tickets.created_at',
  TicketSortField.updatedAt => 'tickets.updated_at',
  _ => null,
};
```

**No-query branch** (query-builder `select(ticketsTable)`): builds an
`OrderingTerm` list — the resolved field first (via
`OrderingTerm(expression: CustomExpression(caseOrColumnSql), mode:
sort.direction == ascending ? OrderingMode.asc : OrderingMode.desc)`),
then always `OrderingTerm.desc(t.createdAt)` as a **secondary tiebreaker**
so same-value rows (e.g. two `critical` tickets) stay stably ordered
newest-first, matching today's only ordering. When `sort.field` is
itself `createdAt`, the tiebreaker is simply omitted (would be
redundant). `relevance` in the no-query branch (only reachable via the
explicit-override + query-cleared fallback described in §2.1) falls
back to the same `createdAt` descending ordering the pre-existing
default used.

**FTS branch** (raw `customSelect`): the existing
`'ORDER BY bm25(tickets_fts) ASC'` literal becomes conditional —
`sort.field == relevance` keeps exactly that clause (today's behavior,
unchanged); every other field builds `'ORDER BY <case-or-column-sql>
<ASC|DESC>, tickets.created_at DESC'` (same tiebreaker rule as the
no-query branch) and drops the `bm25` ordering entirely — the FTS
`MATCH` still *filters* to matching rows, it just no longer determines
their order. This is what makes "search for `bug` sorted by priority"
work: matching rows, priority-ordered, not relevance-ordered.

Both branches share `_enumOrdinalCaseSql`/`_directColumnSql` — no
duplicated enum-ordinal logic between them.

### 2.3 What's unchanged

`getAllTickets`, `getTicketsByParent`, `getAllTicketsByType`,
`getTrashedTickets` keep their existing hardcoded orderings — none of
them back a UI surface this change touches (pickers, Documentation
tree, and Trash's own DB query respectively). Trash's sort behavior
(§4) is applied client-side, after `getTrashedTickets` returns — see
§4.2 for why.

## 3. `TicketsCubit` — resolving and threading the effective sort

### 3.1 New fields/getters

```dart
/// The user's explicit sort choice for this project, once made — `null`
/// means no explicit choice yet, so every search resolves the sort
/// implicitly from [_implicitSort] instead. Loaded once via
/// [loadPersistedSort], updated by [setSort].
TicketListSort? _explicitSort;

/// The [TicketListSort] actually used by the most recent [searchTickets]
/// call — remembered (like [_lastQuery]/[_lastStatuses]) so
/// [loadMoreTickets] and the mutation-refresh methods reuse the same
/// resolved sort rather than each re-deriving it.
TicketListSort _lastSort = _implicitSort(null);

/// The currently active sort — what the new Sort control should render
/// as selected. Resolves the same way [searchTickets] does: explicit
/// override if one exists, otherwise the implicit query-aware default.
TicketListSort get currentSort => _explicitSort ?? _implicitSort(_lastQuery);

/// `relevance` (only meaningful with a query) while [query] is
/// non-empty, otherwise `createdAt` descending — today's exact
/// pre-existing default behavior, now expressed as a concrete
/// [TicketListSort] value instead of being implicit in the repository.
static TicketListSort _implicitSort(String? query) {
  final hasQuery = query?.trim().isNotEmpty ?? false;
  return hasQuery
      ? const TicketListSort(
          field: TicketSortField.relevance,
          direction: TicketSortDirection.descending, // ignored for relevance
        )
      : const TicketListSort(
          field: TicketSortField.createdAt,
          direction: TicketSortDirection.descending,
        );
}
```

New optional constructor dependency, following the file's established
pattern (see the constructor's existing dartdoc block): `TicketListSortRepository?
sortRepository` — `null` (every existing construction site) makes
[setSort] skip persistence (the in-memory override still works) and
[loadPersistedSort] a no-op, exactly mirroring how `filterRepository`
was added for `multi-select-ticket-list-filters`. Real usage
(`app_router.dart`) always supplies one, alongside the existing
`filterRepository`/`projectId`.

### 3.2 `setSort` / `loadPersistedSort`

```dart
/// Sets [sort] as this project's explicit sort override, persists it
/// (see [_sortRepository]/[_projectId] — no-ops the persistence half if
/// either is `null`, same optional-dependency pattern as
/// [_persistFilters]), then re-runs [searchTickets] with the current
/// query/filters unchanged so the reordered list reflects immediately.
Future<void> setSort(TicketListSort sort) async {
  _explicitSort = sort;
  final repo = _sortRepository;
  final projectId = _projectId;
  if (repo != null && projectId != null) {
    await repo.setSort(projectId, sort);
  }
  await searchTickets(
    query: _lastQuery,
    statuses: _lastStatuses,
    types: _lastTypes,
    priorities: _lastPriorities,
  );
}

/// Reads this project's persisted [TicketListSort] (if any) into
/// [_explicitSort], without emitting a state — same
/// load-before-first-search precedent as [loadPersistedFilters], called
/// alongside it from `TicketsListScreen._initializeAndSearch`. No-ops if
/// [_sortRepository] or [_projectId] is `null`, or nothing was
/// persisted yet (leaves [_explicitSort] `null`, i.e. implicit default).
Future<void> loadPersistedSort() async {
  final repo = _sortRepository;
  final projectId = _projectId;
  if (repo == null || projectId == null) return;
  _explicitSort = await repo.getSort(projectId);
}
```

### 3.3 Resolving inside `searchTickets`, reusing everywhere else

`searchTickets` (the single place that receives a fresh `query`) is the
only method that *resolves* the effective sort:

```dart
Future<void> searchTickets({
  String? query,
  Set<TicketStatus> statuses = const {},
  Set<TicketType> types = const {},
  Set<TicketPriority> priorities = const {},
}) async {
  final generation = ++_searchGeneration;
  _lastQuery = query;
  _lastStatuses = statuses;
  _lastTypes = types;
  _lastPriorities = priorities;
  _lastSort = _explicitSort ?? _implicitSort(query);
  // ...unchanged below, except every `_repository.searchTickets(...)`
  // call (here and in every other method) now also passes
  // `sort: _lastSort`.
```

Every other call site that refreshes the list after a mutation
(`loadMoreTickets`, `createTicket`, `updateTicketStatus`, `trashTicket`,
`trashTickets`, `updateStatusForTickets`, `updatePriorityForTickets` —
8 call sites total, see tasks.md) passes `sort: _lastSort` — the
already-resolved value — exactly like they already reuse `_lastQuery`/
`_lastStatuses`/`_lastTypes`/`_lastPriorities` instead of
re-deriving them. This preserves stable pagination ordering across a
`loadMoreTickets` call (the `ORDER BY` a page's `offset` is relative to
never silently changes mid-scroll) and keeps every mutation's refresh
consistent with what's currently on screen.

## 4. Trash — inheriting the same persisted sort

### 4.1 `TrashCubit` changes

New optional constructor dependencies, same pattern:
`TicketListSortRepository? sortRepository`, `String? projectId`. `load()`
reads the persisted sort (if both are supplied) each time it runs — no
separate `loadPersistedSort` step needed, since `load()` already
re-fetches everything from scratch on every call and Trash has no
per-keystroke re-search to avoid redundant reads for.

```dart
Future<void> load() async {
  emit(const TrashLoading());
  try {
    final all = await _repository.getTrashedTickets();
    // ...existing roots/descendantCounts computation unchanged...
    final sort = await _resolveSort();
    roots.sort(_ticketComparator(sort));
    emit(TrashLoaded(roots, descendantCounts, purgeEligibleCount));
  } catch (e) {
    emit(TrashError(e.toString()));
  }
}

/// This project's persisted sort (via [_sortRepository]/[_projectId]),
/// falling back to `createdAt` descending — Trash has no search query
/// to score `relevance` against, so a persisted `relevance` selection
/// (made from the ticket list, where it's meaningful) resolves the same
/// way TicketsCubit's own implicit default does when no query is
/// active. `null`/no-dependency falls back the same way.
Future<TicketListSort> _resolveSort() async {
  final repo = _sortRepository;
  final projectId = _projectId;
  const fallback = TicketListSort(
    field: TicketSortField.createdAt,
    direction: TicketSortDirection.descending,
  );
  if (repo == null || projectId == null) return fallback;
  final persisted = await repo.getSort(projectId);
  if (persisted == null || persisted.field == TicketSortField.relevance) {
    return fallback;
  }
  return persisted;
}
```

### 4.2 Why client-side, not a DB-level `ORDER BY` change

`TrashCubit.load()` already fetches the *entire* trashed set
unconditionally (no pagination — Trash has none) and reduces it to
roots + per-root descendant counts in Dart, entirely independent of
`TicketDao.getTrashedTickets`' own `ORDER BY deleted_at DESC`. Sorting
the already-computed `roots` list client-side with a shared comparator
(§4.3) reaches the same visible result as a DB-level change would, without
touching `TicketDao.getTrashedTickets`'s SQL or its one other caller's
assumptions (`DriftTicketRepository.emptyTrash`/`purgeTrashOlderThan`,
which only care about the *set* of trashed tickets, never their order).

### 4.3 Shared comparator

A single `Comparator<Ticket> ticketSortComparator(TicketListSort sort)`
utility (`lib/features/tickets/domain/utils/ticket_sort_comparator.dart`)
implements the same field-ordinal/timestamp logic as §2.2's SQL, in
Dart — used only by `TrashCubit` (the query-layer path in §2 handles
List/Board's own ordering at the DB level, where the data already
lives). Keeping the ordinal mapping (`TicketPriority.critical` == 0,
etc.) in one place — read by both the SQL-string builder and this
comparator — via a small shared constant, `ticketFieldEnumValues` in
the same domain-layer file, that both `TicketDao` and this comparator
index into, so the two orderings can't silently drift apart.

## 5. Presentation layer — the Sort control UI

### 5.1 `TicketSortPopover` (new widget)

`lib/features/tickets/presentation/widgets/ticket_sort_popover.dart` —
structurally close to `TicketFilterPopover` (same `LayerLink`/
`CompositedTransformFollower`/`OverlayEntry` mechanics, same
`Escape`-to-dismiss `Shortcuts`/`Actions` wiring), but single-select
with a twist: **every** row (including the currently active field) is
always rendered, unlike `SelectionMenu<T>` (which excludes
`currentValue`) — because tapping the *already-active* row is a valid,
meaningful action here (flips direction) rather than a wasted tap.

```dart
class TicketSortPopover extends StatefulWidget {
  const TicketSortPopover({
    super.key,
    required this.trigger,
    required this.currentSort,
    required this.hasActiveQuery,
    required this.onSortSelected,
    this.onOpenChanged,
    this.onFocusChanged,
  });

  final Widget trigger;
  final TicketListSort currentSort;
  /// Whether a search query is currently active — gates whether the
  /// `Relevance` row is enabled/selectable (see §5.2).
  final bool hasActiveQuery;
  final ValueChanged<TicketListSort> onSortSelected;
  final ValueChanged<bool>? onOpenChanged;
  final ValueChanged<bool>? onFocusChanged;
}
```

Renders one `OverlayMenuItem` per `TicketSortField` value, each showing
its label plus a direction indicator (`↑`/`↓` glyph, or the field's own
`AionText`-styled arrow icon) *only* on the currently active row.
`onTap` for a row:

```dart
void _handleTap(TicketSortField field) {
  if (field == widget.currentSort.field) {
    // Same field tapped again: flip direction (no-op for relevance).
    if (field == TicketSortField.relevance) return;
    widget.onSortSelected(
      TicketListSort(
        field: field,
        direction: widget.currentSort.direction == ascending
            ? descending
            : ascending,
      ),
    );
  } else {
    widget.onSortSelected(TicketListSort(field: field, direction: _defaultDirectionFor(field)));
  }
}
```

`_defaultDirectionFor` — the sensible per-field starting direction
(§5.3), used only when *switching into* a field, never when flipping an
already-active one.

The `Relevance` row is visually disabled (muted, `IgnorePointer`-style,
matching `AppDropdown`/`SelectionMenu`'s existing disabled-row
treatment) whenever `!hasActiveQuery` — selecting it without a query
active would immediately fall back to `createdAt` anyway (per §3.1's
`_implicitSort`/§4.1's `_resolveSort` fallback), so disabling it avoids
offering a choice that silently does something else.

### 5.2 Default direction per field

| Field | Default direction | Rationale |
|---|---|---|
| `priority` | ascending (`critical` → `none`) | "Highest urgency first" reads naturally as the enum's own declared order. |
| `status` | ascending (`backlog` → `cancelled`) | Mirrors the workflow's own left-to-right progression (also Board's own fixed column order). |
| `type` | ascending (`epic` → `bug`) | Mirrors the work-breakdown hierarchy's own declared order (epic above story above task/bug). |
| `createdAt` | descending (newest first) | Matches today's existing default — no behavior change for someone who never touches the new control. |
| `updatedAt` | descending (most-recently-touched first) | The common "what changed recently" use case. |
| `relevance` | n/a (bm25 ascending, fixed) | No toggle — see §1.1. |

### 5.3 Wiring into `TicketsListScreen`

`_TicketFilterSection` is renamed `_TicketFilterAndSortSection` and
gains a second trigger — a new `_SortTriggerButton` (visually a sibling
of the existing `_FilterTriggerButton`, same idle/active/open/focused

# Aion — Ticket Sort Control & Board-Default View: Component Spec

Implementation-ready spec for a **single-active-key sort control** on the ticket list — a new **"Sort" trigger button** (sibling of the existing "Filters" trigger; see [Aion Multi-Select Filters Spec](./Aion%20Multi-Select%20Filters%20Spec.md) §3) that opens a flat 6-field popover — plus one unrelated default-state change: **the ticket list opens to Board view by default** instead of List view. All within the existing `TicketsListScreen` header — no new screens.

**No Material widgets or types anywhere.** Every component below is built from `flutter/widgets.dart` primitives only: `DecoratedBox`, `Container`, `GestureDetector`, `MouseRegion`, `FocusableActionDetector`, `CustomPaint`, `Row`, `Column`, `Align`, `Padding`, `Overlay` / `OverlayEntry` / `CompositedTransformFollower`. Never `Card`, `ElevatedButton`, `Scaffold`, `PopupMenu*`, `ListTile`, `InkWell`, `ThemeData`, `ColorScheme`, `AppBar`, or any `material.dart` import.

- `c` = active `AionColors`; `a` = theme `fillAlpha` (Arctic `0.11` / Obsidian `0.16`); `isDark` = Obsidian. Both themes share **one** code path; only token values differ. Where a component is identical across themes it is stated explicitly.
- Existing primitives reused unchanged: the `TicketFilterButton` trigger geometry (§3 of Filters spec), the `SelectionMenu` elevated-panel treatment, the `OverlayMenuItem` row-fill formula (see [Overlay Menu Item Spec](./Aion%20Overlay%20Menu%20Item%20Spec.md) §1.3), and the priority / type / status accent-swatch styles from `TicketFilterPopover` (`_PriorityAccentDot`, `_TypeAccentSquare`, `_StatusAccentDot`).
- Companion mockups: `Aion Ticket Sort and Board Default Mockups.dc.html` (Arctic + Obsidian; Priority sort ascending over the Board `1a`, Last-updated descending with Relevance disabled `2a`, trigger states `3a`, popover row states `4a`).

## 1. Sort model & behavior

### 1.1 State shape

```dart
enum SortField { relevance, priority, status, type, created, lastUpdated }
enum SortDirection { asc, desc }

class TicketSort {
  final SortField field;
  final SortDirection direction;
  const TicketSort(this.field, this.direction);
}
```

A **single active key** — exactly one `field` is in effect at any time, with one `direction`. There is no multi-column sort.

### 1.2 Field list & order

Six fields, shown in the popover top-to-bottom in this fixed order: **Relevance · Priority · Status · Type · Created · Last updated**.

### 1.3 Default sort

- When a **search query is active**, the default is `TicketSort(SortField.relevance, SortDirection.desc)` (most-relevant first).
- When **no query is active**, `relevance` is not meaningful: the default falls back to `TicketSort(SortField.created, SortDirection.desc)` — matching today's pre-existing default behavior unchanged (see engineering §3.1's `TicketsCubit._implicitSort` and `specs/spec.md`), not `lastUpdated`.
- Because a sort is **always** in effect, the trigger is never in a "no sort" state — every state after the initial implicit default counts as **active** for trigger styling (§3.3).

### 1.4 Tap semantics (single-active-key with direction flip)

Tapping a popover row:
- **Inactive field** → make it the active field. Adopt that field's **natural default direction** (§1.5). Popover stays open.
- **Already-active field** → **flip** direction (`asc ⇄ desc`), like clicking a table column header twice. Popover stays open.

The popover does **not** auto-close on selection; dismiss by tapping outside or `Escape` (§2.2).

### 1.5 Natural default direction per field

When a field first becomes active, it adopts a sensible default so the first tap is useful without a second:

| Field | Default direction | Meaning of that direction |
|---|---|---|
| Relevance | `desc` | Most relevant first |
| Priority | `asc` | Critical first (highest severity first) |
| Status | `asc` | Backlog → In Progress → Done |
| Type | `asc` | Epic → Story → Task → Bug (definition order) |
| Created | `desc` | Newest first |
| Last updated | `desc` | Most recently touched first |

"Ascending / descending" is always expressed to the user only as the ↑ / ↓ glyph (§3.2, §2.5); the words are never shown.

### 1.6 Scope & persistence

- Applied to **List, Board, and Trash** — all three render the same reordered ticket list. No new visuals for Board/Trash beyond the trigger + popover here.
- **Persisted per project**, using the same mechanism as the existing Filters persistence.
- **Live apply:** selecting a field or flipping direction re-sorts the list **immediately** (no "Apply" button). The list body reuses the existing `120ms` opacity cross-fade on reorder.

### 1.7 Board becomes the default view

The `TicketsListScreen` view mode (`ViewMode.list` / `ViewMode.board`, driven by the existing List/Board toggle icons already in the header) now **initializes to `ViewMode.board`**. This is a one-line change to the initial state — **no new visual component**. The toggle, its icons, and Board rendering are all unchanged; only the starting value differs. Persistence of the user's last-chosen view (if any) takes precedence over this default, exactly as today.

## 2. `TicketSortPopover` — the open overlay panel

An overlay panel anchored under the Sort trigger, hosting one flat list of 6 selectable field rows (no group headers — unlike `TicketFilterPopover`'s three grouped sections).

### 2.1 Container

Matches the `SelectionMenu` elevated-panel treatment (identical to `TicketFilterPopover` §4.1).

- **Fill:** `c.surface`.
- **Border:** `1px c.borderStrong`.
- **Border radius:** `AionRadius.lg` (12), `clipBehavior: Clip.antiAlias` (first/last row washes clip to the corners).
- **Shadow:** `BoxShadow(color: Color.fromRGBO(0, 0, 0, isDark ? 0.55 : 0.30), offset: Offset(0, 20), blurRadius: 40, spreadRadius: -14)`.
- **Width:** `min(236, availableWidth - 40)` — wide enough for the longest label ("Last updated") plus its trailing direction glyph, without stretching to the trigger's width.
- **Panel padding:** `EdgeInsets.symmetric(vertical: 6)` (top/bottom breathing room; horizontal padding lives on rows).
- **Position:** `top: triggerHeight + 6`, **left-aligned to the Sort trigger** via `CompositedTransformFollower` (`targetAnchor: bottomLeft` / `followerAnchor: topLeft`). Because Sort is the second button in the trigger row, the panel opens indented from the header's left edge, under Sort — not under Filters. If it would overflow the bottom edge it flips upward (`targetAnchor: topLeft` / `followerAnchor: bottomLeft`); if it would overflow the right edge it shifts left to stay `≥ 16px` inside the screen.
- **Max height / scroll:** `maxHeight: min(availableHeight - anchorBottom - 16, 420)`; contents in a `SingleChildScrollView` when exceeded. Six rows fit without scrolling on a phone.

### 2.2 Dismissal

- **Tap outside:** a full-screen transparent `GestureDetector` barrier behind the panel (part of the `OverlayEntry`) closes on tap.
- **Escape:** a `Shortcuts` / `Actions` pair (`DismissIntent` → close) while the panel owns focus.
- **No close button, no "Apply".** Selection applies live (§1.6).

### 2.3 Structure

```dart
Column(crossAxisAlignment: CrossAxisAlignment.stretch, children: [
  _SortRow(field: SortField.relevance,   ...),
  _SortRow(field: SortField.priority,    ...),
  _SortRow(field: SortField.status,      ...),
  _SortRow(field: SortField.type,        ...),
  _SortRow(field: SortField.created,     ...),
  _SortRow(field: SortField.lastUpdated, ...),
])
```

No `_GroupHeader`, no `_GroupDivider` — a flat list.

### 2.4 `_SortRow` — one field row

Full-row tap target. Reuses the `OverlayMenuItem` neutral row-fill formula: resting transparent → hover/focus `surfaceHover` → pressed `border`, animated `100ms Curves.easeOut`. Tapping the row applies §1.4.

- **Row layout:** `Row(crossAxisAlignment: center)` → [optional leading accent swatch], label, `Spacer`, [trailing direction glyph when active]. The whole width is the tap target.
- **Row padding:** `EdgeInsets.symmetric(horizontal: 13, vertical: 8)` → row height ≈ 36.
- **Leading gap:** `SizedBox(width: 10)` between accent swatch (or its 10px placeholder) and label.
- **Label:** `AionText.bodySm` (Manrope 13.5 / w400).
- **Icon size:** direction glyph `12px` (§2.5); accent swatch `8×8` dot or `10×10` rounded square (§2.6).

#### 2.4.1 `_SortRow` states

| State | Row fill | Label color | Direction glyph |
|---|---|---|---|
| **Default (inactive, enabled)** | transparent | `c.textPrimary` | none |
| **Active** | `c.primarySubtle` | `c.primary` | ↑ (`asc`) or ↓ (`desc`) in `c.primary` |
| **Hover (inactive)** | `c.surfaceHover` | `c.textPrimary` | none |
| **Hover (active row)** | `c.primarySubtle` blended toward `c.primary @ a` (deeper tint) | `c.primary` | unchanged |
| **Focused (keyboard)** | same fill as its hover state **plus** an inset ring `c.primary.withOpacity(isDark ? 0.30 : 0.16)`, spread `2`, blur `0` (the `OverlayMenuItem` focus treatment) | per active/inactive | per active/inactive |
| **Pressed** | `c.border` (inactive) / `c.primary.withOpacity(a * 1.4)` over `primarySubtle` (active) | per active/inactive | per active/inactive |
| **Disabled** (Relevance only, no query — §1.3) | transparent, no hover/press reaction, whole row `opacity: 0.5` | `c.textMuted` | none |

- **Fill choice:** the active row uses the tinted **background** (`primarySubtle`) *and* the `primary` label — both, for a clear single-active indicator, mirroring how the Filters chips/trigger read "on".
- **Focus model:** each enabled row is a focus stop (`FocusableActionDetector`); `Enter` / `Space` applies §1.4. Disabled rows are removed from traversal. On open, the popover autofocuses the **currently active** row.
- **Transition:** `100ms Curves.easeOut` fill fade (matches `OverlayMenuItem` §1.6); the direction glyph swaps instantly on flip (no rotation animation required, though a `120ms` quarter-turn is acceptable).

### 2.5 Direction glyph

A single up/down arrow trailing the label of the **active** row only.

- **Form:** a minimal filled triangle-headed arrow, or `PhosphorIcons.arrowUp` / `arrowDown`. Rendered here as a `10–12px` CustomPaint triangle.
- **Size:** `12px`.
- **Color:** `c.primary`.
- **`asc`** → up arrow; **`desc`** → down arrow.

### 2.6 Leading accent swatch (Priority / Status / Type rows only)

A small decorative field glyph echoing how that field's values look elsewhere. It identifies the field — it is **not** a value selector. Relevance, Created, and Last updated rows carry **no** swatch (a `10px` empty leading box keeps their labels aligned with the swatched rows).

| Row | Swatch | Fill (both themes token-driven) |
|---|---|---|
| **Priority** | `8×8` dot, radius `50%` | `c.priority.criticalFg` — the priority palette's signature tone (Arctic `#B22A41` / Obsidian `#FF6B80`) |
| **Status** | `8×8` dot, radius `50%` | `c.primary` — the "In Progress" status tone |
| **Type** | `10×10` rounded square, radius `2` | `c.typeTask` (Arctic `#2E86D4` / Obsidian `#9366FF`) |

These reuse `_PriorityAccentDot` / `_StatusAccentDot` / `_TypeAccentSquare` verbatim; only the color argument is fixed per row as above.

**Theme note:** identical structure both themes; only token values differ.

## 3. `_SortTriggerButton` — the "Sort" trigger

A new trigger, a visual sibling of `TicketFilterButton` (§3 of Filters spec) — same geometry, same state model — differing only in icon (sort arrows, not a funnel), label text, the trailing direction glyph, and the absence of a count badge.

Built as `FocusableActionDetector → MouseRegion → GestureDetector → AnimatedContainer`. `Enter` / `Space` and tap both call `onTap` (open the popover).

### 3.1 Dimensions & layout

- **Height:** `36` (driven by padding; matches the Filters trigger exactly).
- **Padding:** `EdgeInsets.symmetric(horizontal: 12, vertical: 8)`.
- **Layout:** `Row(mainAxisSize: MainAxisSize.min)` → leading sort icon, `SizedBox(width: 8)`, label, [active only: `SizedBox(width: 8)` + trailing direction glyph].
- **Border radius:** `AionRadius.lg` (12).
- **Leading icon:** a sort/arrows glyph (`PhosphorIcons.arrowsDownUpLight`, or a `CustomPaint` of a stacked up-triangle + down-triangle), **16px** (drawn ~15px here).
- **Label:** `AionText.button` (Manrope 14 / w700). Text = `"Sort"` in the idle default, `"Sort: <Field>"` when a non-default field is active (e.g. `"Sort: Priority"`, `"Sort: Updated"` — "Last updated" abbreviates to "Updated" in the trigger to keep width in check; full name in the popover row).
- **Trailing direction glyph:** the same ↑ / ↓ triangle as §2.5, `12px`, in the current `labelColor`, shown whenever active.
- **No count badge** (unlike Filters — a single active key has no count).
- **Shadow:** none.

### 3.2 Idle sub-state (initial implicit default) — states

Shown only before any explicit change while a query-less default is in effect and reads as "not yet touched". Matches `AppDropdown` inactive.

| State | Fill | Border | Icon color | Label color |
|---|---|---|---|---|
| **Default** | `c.surface` | `1px c.border` | `c.textSecondary` | `c.textPrimary` |
| **Hover** | `c.surface` | `1px c.borderStrong` | `c.textSecondary` | `c.textPrimary` |
| **Focused** | `c.surface` | `1.5px c.primary` + ring `c.primary.withOpacity(isDark ? 0.30 : 0.16)` spread `3` blur `0` | `c.primary` | `c.textPrimary` |
| **Pressed** | `c.surface` | `1px c.borderStrong` | `c.textSecondary` | `c.textPrimary` — plus `scale: 0.98` |
| **Open** (popover showing) | treated as Focused (ring + `1.5px c.primary` + `c.primary` icon) |

Label reads `"Sort"`; no trailing direction glyph in the idle state.

### 3.3 Active sub-state (a non-default sort in effect) — states

Matches `AppDropdown` `isActive`, plus the trailing direction glyph.

| State | Fill | Border | Icon color | Label color | Direction glyph |
|---|---|---|---|---|---|
| **Default** | `c.primarySubtle` | `1.5px c.primary` | `c.primary` | `c.primary` | ↑/↓ `c.primary` |
| **Hover** | `c.primarySubtle` | `1.5px c.primary` | `c.primary` | `c.primary` | ↑/↓ `c.primary` |
| **Focused** | `c.primarySubtle` | `1.5px c.primary` + ring `c.primary.withOpacity(isDark ? 0.30 : 0.16)` spread `3` blur `0` | `c.primary` | `c.primary` | ↑/↓ `c.primary` |
| **Pressed** | `c.primarySubtle` | `1.5px c.primary` | `c.primary` | `c.primary` — plus `scale: 0.98` | ↑/↓ `c.primary` |
| **Open** | as Focused | | | | |

Open and Focused share the same emphasized ring treatment (as required).

### 3.4 Idle ↔ active transition

The whole button cross-fades fill + border + icon/label color over `120ms Curves.easeOut` (via `AnimatedContainer` + `AnimatedDefaultTextStyle`) when it crosses idle ↔ active, tying into the same `120ms` list cross-fade used on reorder (§1.6). The direction glyph fades in over the same `120ms`.

**Theme note:** identical structure both themes; only token values differ (Arctic `primary #2E86D4` / `primarySubtle #DBE9F7`; Obsidian `primary #9366FF` / `primarySubtle #241F3E`).

## 5. Tokens

**No new `AionColors`, `AionRadius`, or `AionSpacing` members.** Every value resolves to existing tokens or to explicit multiples of 4 already used by `TicketFilterButton` / `TicketFilterPopover`:

- Colors — all from `AionColors` (`surface`, `border`, `borderStrong`, `primary`, `primaryHover`, `primarySubtle`, `surfaceHover`, `textPrimary`, `textMuted`), the priority/type accents (`c.priority.criticalFg`, `c.typeTask`), and `c.primary` for the status swatch.
- Radius — `AionRadius.lg` (12) trigger + panel; swatch square radius `2` (a local decorative value, as in `_TypeAccentSquare`).
- Text — `AionText.button` (trigger label), `AionText.bodySm` (row label). No new text styles.
- Translucent fills — always `token.withOpacity(x)`: the focus ring `c.primary @ 0.30/0.16`, active-row hover/pressed tints `c.primary @ a` / `@ a*1.4`. Never hardcoded ARGB.

The only explicit non-scale numbers are the `236` panel width, the `6` panel top offset, the `12` direction-glyph size, and the `8`/`10` accent-swatch sizes — each intentional and local, matching the Filters spec's equivalents.
