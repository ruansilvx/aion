# Bug Ticket Type

# Proposal: Bug ticket type

## What

Add `TicketType.bug` — a ninth ticket type ranked structurally like `task`
(same slot in the `epic > story > task` chain: parentable by `story` or
directly by `epic`, participates in the epic→story→task decomposition,
shows up on the Board in the same status columns), but carrying four
extra diagnostic fields a plain Task has no use for:

- `severity` (`TicketSeverity`: `critical | high | medium | low`) — impact,
  kept distinct from the existing `TicketPriority` (scheduling urgency).
- `stepsToReproduce` (text)
- `expectedBehavior` (text)
- `actualBehavior` (text)

A Bug moved to `TicketStatus.inProgress` triggers Aion's coding-execution
run with full parity to Task — same design-review gate, same single-slot
FIFO queue, same worktree isolation, same implement→verify→PR flow. There
is no separate "bug execution" pathway; every place `TicketsCubit` singles
out `TicketType.task` for execution purposes now recognizes Task and Bug
as the same class of thing.

A Bug's "affected version/environment" is not a new field — it reuses the
existing `TicketLinkType.relatesTo` mechanism a `release` ticket already
has with `epic`/`story`/`task`, now with `bug` as a fourth participant.
Aion has no real versioned distribution yet, but a `release` ticket
already stands alone as an internal milestone/checkpoint concept, and
"which bugs were found in Release X" becomes a real, queryable
relationship instead of a freeform string.

## Why

Grounded in `aion-arch/ideas/bug-ticket-type.md`'s `/brainstorm` session
(status: `explored`, next_action: `/propose bug-ticket-type`). The core
finding: a bug is fundamentally a unit of execution, not a
filtering/labeling distinction — bolting `severity`/repro-steps/expected-
vs-actual onto every plain Task's shape (meaningless for non-bug Tasks)
is worse than a fourth nullable-field group on `Ticket`, exactly the
precedent `complexity`/`sddStage` already set for type-specific-but-
universal fields.

This also resolves the idea file's four open questions, decided here so
`design.md` has a single answer to build from rather than re-opening them:

1. **Rank mechanism** — `bug` gets the exact same `_rank` value as `task`
   (not a new distinct rank that happens to occupy the same matrix
   position). `TicketTypeHierarchy.canParent`'s existing
   `parentRank < childRank` comparison already produces the correct
   matrix for free once `bug` shares `task`'s rank — no new branch, no
   special-casing alongside the existing `page`/`signal`/`release` cases.
   A side effect worth calling out: `task` cannot parent `bug` and `bug`
   cannot parent `task`, exactly like every other same-rank pair (e.g.
   `story` cannot parent `story`) — sharing a rank means Task and Bug are
   siblings in the chain, not nestable inside one another.
2. **`severity` is a new, dedicated enum** (`ticket_severity.dart`), not a
   relabeled `TicketPriority`. Reusing `TicketPriority` would conflate two
   independent axes (impact vs. scheduling urgency) the idea file was
   explicit about keeping separate. Unlike `TicketPriority` (which has an
   explicit `none` hidden from the UI), `TicketSeverity` has no `none`
   member — the field is simply nullable (`TicketSeverity?`) and `null`
   means "not sized yet," the same nullable-until-set treatment
   `TicketComplexity`/`SddStage` already have on `Ticket`.
3. **`expectedBehavior`/`actualBehavior` are two separate fields**, not
   one combined freeform field — matches how the idea file's answer #2
   described them, and keeps each independently editable in place
   (mirrors the existing `description` field's inline-edit pattern rather
   than one large blob a user has to manually re-structure).
4. **`CreateTicketScreen` exposes Bug's extra fields conditionally**,
   shown only when the type dropdown is set to `bug`, using the same
   `AnimatedSize`-driven show/hide pattern the screen already applies to
   the parent field for `isAlwaysRoot` types. This is a new pattern for
   this screen (every type currently shares one identical field set), so
   it needs a design pass — see Design gate below.

## Scope

In scope:
- `TicketType.bug` (domain enum, `ticket_type.dart`), ranked like `task`.
- `TicketTypeHierarchy.executableTypes` (a new static const
  `[TicketType.task, TicketType.bug]`) and `isExecutable` instance getter,
  replacing every `ticket.type == TicketType.task` coding-execution check
  in `TicketsCubit` with `ticket.type.isExecutable`, and every
  `types: const [TicketType.task]` sibling/children query used for
  design-review-gate or SDD-readiness purposes with `executableTypes`.
- New `TicketSeverity` enum + four new nullable `Ticket` fields
  (`severity`, `stepsToReproduce`, `expectedBehavior`, `actualBehavior`),
  meaningless for every type except `bug` — same nullable-until-set
  treatment as `complexity`/`sddStage`.
- Drift schema v5 → v6: four new nullable columns, `addColumn` migration.
- `CreateTicketScreen`: Bug-specific fields shown conditionally; new
  `TicketsCubit.createTicket` optional params for the four new fields.
- Ticket detail screen: a Bug-only "Bug details" section (severity,
  steps to reproduce, expected/actual behavior), editable in place, same
  pattern as the existing description field.
- Widening the ticket-detail screen's Linked-Tickets/Backlinks gate
  (currently `resource`-only) to also cover `bug`, so a Bug can link an
  affected `release` via the existing generic `relatesTo` picker — the
  same mechanism `release` already has with `epic`/`story`/`task`, no new
  UI pattern invented.
- `TypeChip`/`LinkedTicketsSection`/`ticketTypeLabel` switch cases, a new
  `AionColors.typeBug` token (both themes), and the `app_en.arb` string
  entries this new enum value requires everywhere `TicketType` is
  switched on exhaustively — the compiler surfaces every such site once
  `bug` is added; `design.md`/`tasks.md` enumerate all of them, not just
  the semantically load-bearing ones above.
- Unit test coverage: `TicketTypeHierarchy.canParent` for `bug` against
  the full matrix, `TicketsCubit` execution-parity tests (a Bug triggers
  the same gate/queue/worktree flow a Task does), `createTicket`/
  `updateTicket` round-tripping the four new fields.

Out of scope:
- Any change to `promoteSignalToEpic` or Inbox's brain-dump flow. The
  idea file's superseding note (`new-project-onboarding`) says a signal
  should eventually be promotable into `bug` too, not just `epic` — that
  generalization belongs to whichever change implements Inbox's
  brain-dump purpose, not this one.
- Any UI for creating/viewing `relatesTo` links on `epic`/`story`/`task`
  detail screens in general. `release`'s own relatesTo relationship has
  no user-facing picker anywhere today (only created programmatically —
  see `TicketsCubit`'s `promoteSignalToEpic`, `advanceSddStage`, codebase-
  analysis banner call sites). This change adds exactly one new picker
  location — the Bug detail screen — by widening `resource`'s existing
  gate, not by building a general-purpose relatesTo UI for every type.
- Rollup of `estimate`/`timeSpent` across Bug siblings, or any Board/list
  filtering UI specific to Bug (severity-based sort/filter, etc.) —
  Bug participates in the existing generic type/status/priority filters
  exactly like every other type, nothing new needed there.
- Configurability of `TicketTypeHierarchy`'s rank/matrix (already a fixed,
  hardcoded rule set per `define-type-compatibility-matrix`'s precedent).

**Resolved product-decision note:** the Claude Design export makes
`severity` a *required* field on `CreateTicketScreen` (§4.2 — required-
field marker, submit-blocking error state, "Choose a severity" helper
text), which is a stricter behavior than this proposal's original "all
four Bug fields optional" framing. Confirmed with the developer
(2026-07-28): keep the design's required-severity behavior as-is —
`CreateTicketScreen` blocks Bug creation until a severity is chosen.
This doesn't affect the domain/schema design — `Ticket.severity` stays
nullable regardless, matching `complexity`'s existing nullable-until-set
treatment; it's purely a `CreateTicketScreen` client-side validation
rule, and `stepsToReproduce`/`expectedBehavior`/`actualBehavior` remain
optional. `tasks.md` T9 already reflects this — no further changes
needed before `/apply`.
