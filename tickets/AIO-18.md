# Configurable workflow and automation engine

## Key questions asked

1. For `TicketStatus`: is the goal a display-layer subset/reorder of the existing 6 fixed values (gating logic unchanged), or genuinely custom status sets (add/rename/remove), which would force gating logic off literal status names?
2. Given custom-status systems elsewhere (Jira, Linear, GitHub Projects) all solve "gating logic needs to know what a status *means*" via a small fixed category enum every custom status maps to — should this follow that same category-mapping convention?
3. Should `TicketStatus` and `SddStage` merge into one customizable workflow axis per ticket type, or stay two separate configurable axes that can cross-reference each other?
4. Does the confidence-gating mechanism for skill attachment mean reusing the existing static `AutomationConfidence` enum as-is, a genuinely new computed per-run confidence score, or both layered together?
5. Does "attach skill execution to a status" mean the generalization only covers naming *which* status triggers today's two existing hardcoded flows (SDD-stage-chat, coding-execution), or a real generalization to attaching *any* named skill?
6. When a status triggers "skill X," what is X actually a reference to — an Aion-authored prompt/workflow definition, a named skill in the underlying coding agent's own skill system (e.g. Claude Code's `.claude/skills/`), or both as distinct attachment kinds?
7. Should a project-defined status set be one global set shared by every ticket type, fully independent per-type sets, or a shared base set with optional per-type extensions? (User asked how Jira-like platforms handle this before deciding.)
8. Should gate behaviors themselves stay a fixed closed list (config only picks which status maps to an existing gate), become genuinely pluggable (a project can define a wholly new precondition type), or ship the closed list now with pluggability spun off as a separate future idea?
9. Given every fork so far resolved toward the most general/powerful option, should this ship as one large `/propose`, or be sequenced into phases to keep each proposal reviewable?
10. (2026-08-31, Phase 3 transition-precondition half) Today's `SddStageBlockReason`/`CodingExecutionBlockReason` are small, fixed, Aion-authored enums — but a project-invented precondition can't get a custom hint from a fixed enum. Should the blocking reason stay a fixed enum (no free authorship of *why* something's blocked), or does a project-defined precondition need to author its own reason text?
11. (User asked for a recommendation) — see Summary of answers.
12. Should this new mechanism cover both `SddStage` preconditions and `TicketStatus`'s design-review gate in one proposal (structurally identical: bool + reason, one graph per status/stage value), or scope to `SddStage` alone and leave `TicketStatus` as its own follow-on?
13. (User asked for the actual impact of doing both now before deciding) — see Summary of answers.

## Summary of answers

- **Genuinely custom status sets**, not just display-layer reorder/hide of the fixed 6. Rejected the simpler "(a)" option explicitly.
- **Rejected the plain category-mapping convention too.** The user wants more than "map custom status → one of {notStarted, inProgress, blocked, inReview, done}": they want to choose, per status, *which* behaviors trigger/gate off it, optionally tie it to a particular SDD stage, and attach automated skill execution to it — gated by automation confidence. Category-mapping alone doesn't cover the skill-attachment or stage-tie pieces.
- **`TicketStatus` and `SddStage` stay two separate configurable axes**, not merged into one. This matches today's actual code split (`TicketStatus` applies to every ticket type; `SddStage` is Epic/Story-only) rather than forcing a unification neither field currently has. A status can still optionally trigger an SDD-stage transition — that cross-reference is configurable, but the two axes are independently defined.
- **Today's hardcoded config becomes the default baseline preset**, offered at project setup — consistent with the already-shipped pattern in [[project-type-aware-conventions-and-verification]], where `FlutterVerifier`'s existing behavior became "one detected default among many" rather than being torn out.
- **Confidence-gating reuses the existing static `AutomationConfidence` enum only** — no new computed/model-assessed confidence signal. This resolves [[automation-confidence-decisions]]'s original ambiguity in the simpler direction and removes an entire mechanism from scope.
- **Generalizes to attaching *any* named skill**, not just naming which status triggers today's two existing hardcoded flows. This is a real skill-invocation-by-name mechanism, not a thin rename of existing call sites.
- **Both attachment kinds, as distinct types**: a status can attach either an Aion-native prompt/workflow template (project-authored inside Aion) or delegate to a named skill in the underlying coding agent's own system (e.g. Claude Code's discovered skills) — config picks which kind per attachment.
- **Shared base set with optional per-type extensions.** Chosen over a pure global set or fully independent per-type sets, specifically because Aion's Board is a first-class cross-type view (`tickets.md`) that needs a common status vocabulary to stay coherent, while still allowing a genuinely useful case like a `bug`-only "Needs repro" status. Jira supports full per-type independence via workflow schemes (and is notorious for the resulting admin sprawl); Linear/GitHub Projects go fully global. The shared-base-plus-extensions shape was recommended as the middle ground specific to Aion's cross-type Board requirement, not compromise for its own sake.
- **Gate behaviors become genuinely pluggable**, in scope for this idea (not spun off separately) — a project can eventually define a wholly new precondition type (e.g. requiring reviewer approval) with no Aion equivalent today.
- **Sequenced into three phases** rather than one large proposal, specifically to manage the risk that every fork resolved toward maximum generality: Phase 1 (status/stage sets + remapping existing gates only), Phase 2 (any-skill attachment), Phase 3 (pluggable gate behaviors) — each its own reviewable change cycle.
- **(2026-08-31) Blocking reason: auto-derived, not a fixed enum, not free-text authoring.** Recommended and accepted: derive the "why blocked" text from the failing node's own condition summary, reusing `decisionNodeTitle`/`decisionNodeSummary`'s existing display machinery (e.g. `"Blocked: Attempt count > 3 not yet met"`) — scales to any project-invented precondition for free, no new authoring UI, keeps the sentence *template* localizable while accepting the same non-localized-values tradeoff `decisionNodeSummary` already makes today. No per-node override, for now.
- **Terminal outcome: a plain binary result (allowed/blocked), not `DecisionOutcome`.** `DecisionOutcome`'s `proceed`/`gated`/`decline`/`modelJudgment` are confidence-shaped — meaningless for an unconditional structural gate with no "ask the human"/"ask the model" concept. `agentJudgment` is confirmed structurally inapplicable here regardless (no in-flight session at evaluation time, per the 2026-08-31 `/explore` below) — this graph's condition kinds are Aion-authored catalog entries plus the deterministic rule-builder only.
- **Structure: one decision graph per project-defined `SddStage` value** — mirrors Phase 2's `SkillAttachment` scoping exactly (`workflowStatusId`/`sddStage`, "exactly one non-null" per attachment). Not one graph branching on "which stage is this ticket at," since stages are themselves a dynamic, project-editable list, not a fixed enum a rule-builder condition could enumerate against cleanly.
- **Scoped to `SddStage` alone for this round; `TicketStatus`'s design-gate retrofit deferred as a fast-follow.** The engineering cost of doing both now is genuinely small — `_codingExecutionGateCheck` (`TicketStatus`'s design gate) already reuses the exact same two booleans (`_storyNeedsDesignReview`, `_designSyncApproved`) as two of `SddStage`'s own branches, so no new field-instrumentation work — but doing both is a bigger *scope* commitment than it looks: generalizing "any `WorkflowStatus` can hold a precondition graph" opens every project-defined status to genuinely novel gates, not just a ported version of today's one hardcoded check. Consistent with this project's repeated precedent (this file's own Phase 1/2/3 split; `pluggable-decision-graph-conditions` splitting rule-builder from `agentJudgment` despite shared infrastructure) of choosing reviewability over doing the cheap-while-you're-in-there thing.

## Explore findings (2026-08-18, Phase 1 feasibility)

A grounded, read-only `/explore` pass against the actual `aion` codebase (`TicketStatus`, `SddStage`, `TicketsCubit`, `ProjectOverride`/`BaselineAsset`, `AutomationSettingsRepository`) surfaced facts that revise Phase 1's scope:

- **Correction: "blocked" is not a `TicketStatus` value.** The real enum ([ticket_status.dart](../../aion/lib/features/tickets/domain/enums/ticket_status.dart)) is `backlog / todo / inProgress / inReview / done / cancelled`. "Blocked" is a derived, type-agnostic UI state computed from unresolved `blocks`/`blockedBy` dependencies (`_isTicketBlocked`, enforced by `_interceptBlockedDependencyTrigger` for every ticket type regardless of status) — it layers on top of whatever status a ticket is in and should stay outside any project-defined status set entirely, not become a configurable value.
- **`TicketStatus`'s gating logic is thin and generalizes cleanly.** Only the transition *to* `inProgress` is gated at all, via two small boolean interceptors (`_interceptBlockedDependencyTrigger`, type-agnostic; `_interceptTaskExecutionTrigger` → `_codingExecutionGateCheck`, Task/Bug-only). The coding-execution-complete → `inReview` transition is a single hardcoded target status. "Which project-defined status occupies the semantic slot `inProgress` fills today" is low-risk to generalize.
- **`SddStage`'s gating logic is the opposite — bespoke per stage, not a reusable trigger table.** `_sddStageAdvanceCheck` is a 5-branch switch where every branch runs genuinely different precondition code (chat-terminal-reply check for `exploring`/`verifying`; child-completion check with a Story/Epic branch and a design-skip branch for `proposed`; design-page-content check for `designBrief`; design-approval-plus-tasks-done check for `designSync`). This doesn't decompose into "a status maps to one of N existing named gates" — it's identity-coupled to which specific stage a ticket is at. **Consequence: Phase 1 can only let a project reorder/relabel/skip among these five existing precondition types** (which alone fully satisfies [[not-all-projects-will-require-design]]'s original want); inventing a semantically novel stage isn't achievable without first decomposing this switch into reusable primitives — realistically Phase 3 (pluggable gates) territory, not Phase 1.
- **`ProjectOverride`/`BaselineAsset` is the wrong storage precedent.** It shadows individual bundled *files* (skills, model-config stubs, doc pointers) by a flat string key — not a fit for structured, orderable, per-status record data `TicketsCubit` needs to query constantly. `AutomationSettingsRepository` is a closer shape (a small dedicated repository) but is `shared_preferences`-backed and keyed by a fixed five-value enum, still not open-ended. Project-defined status/stage sets are closer in shape to the `tickets` drift table itself — most likely need **a new drift table**, not a reused mechanism.
- **Lower-than-expected migration risk on the `TicketStatus` axis.** `status` is already stored as a plain `TextColumn` ([ticket_model.dart:30](../../aion/lib/features/tickets/data/models/ticket_model.dart)), not a strict drift-enum-mapped column — swapping the *set* of valid values doesn't require an app-database schema migration, only a Dart-side validation/mapping change. The "what happens to existing tickets when a project edits its configured set" open question still stands independent of storage format.
- Confirmed the shared-base-plus-per-type decision is well-founded: `TicketStatus` is referenced across ~20 files (Board, filter/column popovers, list screen, markdown serializer/template, sort comparator, selection bar), so a common vocabulary is worth protecting architecturally, not just for the Board.

## Conclusions reached

The direction is clear at the vision level, and the mechanism is now phased rather than fully flat-designed. Phase 1 itself is asymmetric — see "Explore findings" above:

- **Two separate configurable axes**, not one: a project-defined `TicketStatus` set (shared base + optional per-type extensions) and a project-defined `SddStage` set (still Epic/Story-scoped), each independently defined.
- **`TicketStatus` shape: shared base set + optional per-type extensions.** Chosen over a pure global set (loses useful per-type cases like a `bug`-only "Needs repro" status) and over fully independent per-type sets (Jira's workflow-scheme approach — breaks the Board's cross-type coherence and invites admin sprawl). Confirmed low-risk to implement (thin gating logic, no schema migration needed).
- **`SddStage` shape, Phase 1: reorder/relabel/skip among today's five fixed precondition types only** — not genuinely novel stages. That stronger claim (a project inventing a wholly new stage with new semantics) is out of reach until Phase 3's pluggable gates exist, since `_sddStageAdvanceCheck`'s five branches are bespoke, not reusable.
- **Per-status/per-stage configuration**, not just naming: for each project-defined status or stage, a project can configure (a) whether it acts as a trigger or gate for existing mechanisms (coding-execution start, PR-flow, the design gate — "blocked" stays a separate, type-agnostic, non-configurable dependency gate, not a per-status setting), (b) an optional tie to a specific `SddStage` transition, and (c) — from Phase 2 onward — an optional attached skill to execute automatically on entry.
- **Skill execution is confidence-gated by the existing static `AutomationConfidence` (auto/gated/manual) enum only** — no new computed/model-assessed confidence signal. This resolves [[automation-confidence-decisions]]'s original ambiguity toward the simpler of the two readings and removes a whole mechanism from scope.
- **Skill attachment (Phase 2) generalizes to any named skill**, of two distinct kinds: an Aion-native prompt/workflow template, or a delegated call into the underlying coding agent's own skill system (e.g. Claude Code's `.claude/skills/`) — not limited to naming which status triggers today's two existing hardcoded flows.
- **Gate behavior itself becomes pluggable (Phase 3)** — a project can eventually define a wholly new precondition type with no Aion equivalent today (e.g. requiring reviewer approval before a status), not just remap existing gates onto new statuses.
- **Explicitly phased, not one large proposal**, because every open fork in this session resolved toward maximum generality and the combined scope is now a real workflow-automation-rule engine:
  1. **Phase 1** — project-defined `TicketStatus`/`SddStage` sets (shared base + per-type extensions), each value mapped only to today's existing fixed gate behaviors (design gate, coding-execution block, PR-flow trigger). No new gate types, no skill attachment.
  2. **Phase 2** — any-named-skill attachment to a status/stage (Aion-native template or CLI-delegated skill), gated by the existing static `AutomationConfidence` enum.
  3. **Phase 3** — pluggable gate behaviors (genuinely new precondition types).
- **Today's actual hardcoded values and behavior ship as the default baseline preset** at project setup throughout all three phases, exactly as `FlutterVerifier` became a detected default rather than the only path in [[project-type-aware-conventions-and-verification]]. A project that never touches this configuration behaves exactly as Aion does today.
- This idea absorbs and supersedes the two prior barely-started stub ideas: [[automation-confidence-decisions]] (resolved above — static enum only, no new signal) and [[not-all-projects-will-require-design]] (Phase 1's `SddStage`-configurability axis is exactly what that idea was gesturing at — a backend project could define an `SddStage` set that skips `designBrief`/`designSync` entirely).

## Architectural implications

- `TicketStatus` and `SddStage` move from fixed Dart enums to project-defined data (shared base + per-type extensions for `TicketStatus`; a fixed-precondition-type reorder/relabel/skip model for `SddStage` in Phase 1) — a substantially larger data-model and gating-logic change than anything in `tickets.md` to date; every piece of code that currently pattern-matches on a literal enum value (`TicketStatus.inProgress`, `SddStage.designBrief`, etc.) needs a generalized lookup instead. This is Phase 1's core work.
- Reuses, rather than replaces, the already-shipped `AutomationConfidence` (auto/gated/manual) pattern from [[sdd-workflow-in-ticket-system]]/[[task-to-coding-execution-trigger]] as the confidence-gating mechanism for skill attachment in Phase 2 — additive scope on an existing mechanism, not a new one; the computed-confidence-signal alternative was explicitly rejected.
- Directly resolves [[not-all-projects-will-require-design]]'s core want (skippable SDD stages per project) as a special case of Phase 1's `SddStage` reorder/skip capability — a project can already omit `designBrief`/`designSync` from its configured order, no bespoke "design-optional" logic needed.
- Follows the precedent [[project-type-aware-conventions-and-verification]] already set: today's hardcoded Aion-specific behavior becomes a detected/offered default baseline, not the only supported path. **Correction from explore:** `ProjectOverride`/`BaselineAsset` (that precedent's actual storage mechanism) is a file-shadowing scheme for bundled content, not a fit for structured per-status/per-stage record data — Phase 1's design should plan a new drift table instead, following the `tickets` table's own precedent more than `ProjectOverride`'s.
- Phase 2's CLI-delegated skill attachment kind ties this idea to [[pluggable-provider-abstraction]]/`providers.md` territory — invoking a named skill on the underlying agent CLI is provider-specific behavior, not something every `AgentProvider` implementation is guaranteed to support uniformly. **Confirmed working for the Claude Agent SDK provider specifically** (2026-08-19 spike, see below); still unverified for any other future `AgentProvider`.
- The `SddStage` precondition retrofit reuses [[pluggable-decision-graph-conditions]]'s shipped `GraphCanvas`/`DecisionOutlineList`/`DecisionNodeForm`/`DecisionGraphConfigCubit` and `DecisionNode`/`DecisionBranch` entities wholesale — genuinely shared UI and data-model infrastructure, not a parallel build — but needs its own outcome type (binary allowed/blocked, not `DecisionOutcome`), its own confidence-independent evaluation entry point in `TicketsCubit` (distinct from `_evaluateDecisionGraph`, which only fires once a context resolves to `auto`), and its own field catalog (none of `SddStage`'s ~4 needed fields overlap `AutomationContext`'s existing 2).
- `TicketStatus`'s design-gate retrofit, once picked up, inherits the `SddStage` retrofit's field instrumentation for free (`_storyNeedsDesignReview`/`_designSyncApproved` are shared between them) — a fast-follow, not a from-scratch design pass, when its own `/propose` eventually runs.
- **Explore complete for Phase 1 feasibility** (2026-08-18) — see "Explore findings" above. `TicketStatus` is confirmed low-risk and ready for `/propose` as originally scoped; `SddStage` is ready for `/propose` only at the narrowed reorder/relabel/skip scope. Phase 1 has since shipped as `configurable-ticket-workflow` (archived).
- **Phase 2 CLI-delegation mechanics confirmed** (2026-08-19) — see "Explore findings (2026-08-19, Phase 2 CLI-delegation spike)" below. No bridge or SDK-call changes needed for the CLI-delegated attachment kind; Phase 2's own `/propose` only needs to design the storage/config/UI layer on top of an already-working mechanism.
- **Phase 3's transition-precondition half scoped and direction-resolved** (2026-08-31) — see "Explore findings (2026-08-31, Phase 3 transition-precondition retrofit)" below and "Conclusions reached" above. Ready for a dedicated `/explore` pass (field instrumentation) before its own `/propose`.

## Explore findings (2026-08-19, Phase 2 CLI-delegation spike)

A grounded `/explore` pass into Phase 2 feasibility (scoped to the any-named-skill-attachment mechanism) found `agent_bridge/index.mjs` ([agent_bridge/index.mjs](../../aion/agent_bridge/index.mjs)) forwards a plain `prompt` string into the Claude Agent SDK's `query()` with no first-class "invoke skill by name" call anywhere in the bridge or in `ClaudeAgentSdkClient` ([claude_agent_sdk_client.dart](../../aion/lib/core/agent/claude_agent_sdk_client.dart)) — leaving one real unverified technical unknown: whether `.claude/skills/` discovery actually works through this prompt-string pipe at all, for either attachment-trigger shape (autonomous description-match, or literal `/skill-name` text).

A follow-up empirical spike resolved this. Setup: a throwaway `.claude/skills/aion-spike-test-skill/SKILL.md` (description: "diagnostic marker check"; instructed to output a distinctive marker string) in a scratch project directory, then `node agent_bridge/index.mjs` spawned exactly as `ClaudeAgentSdkClient.run` does — a JSON request line on stdin, `workingDirectory` set to that scratch project. Four cases, all clean:

| Test | Setup | Result |
|---|---|---|
| A | `toolsEnabled: true`, prompt naturally matching the skill's description | `Skill` tool invoked → correct marker returned |
| B | `toolsEnabled: false` (today's SDD-stage-chat mode) | `Skill` tool **still** invoked → correct marker returned |
| C | Literal `/aion-spike-test-skill` slash-command text | Marker returned directly (skill expanded into the prompt before any visible `tool_use` event — pre-processed, not a runtime tool call) |
| D | Unrelated prompt ("What is 2+2?"), negative control | No skill fired — no false positives |

Findings:

- **Discovery is driven purely by `workingDirectory`** (Dart) → spawned process `cwd` (Node) → the Agent SDK's own project-skill scan. `agent_bridge/index.mjs` needs **zero changes** to support skill discovery — the plumbing Phase 1's `TicketsCubit` already threads through (`AgentRequest.workingDirectory`, always the project checkout) is sufficient on its own.
- **Works in both of today's two existing execution modes** — Test B is the load-bearing result: it means the SDD-stage-chat path (which runs `toolsEnabled: false`, "text-only") doesn't need to switch modes just to support skill attachment. Both of today's hardcoded flows (`_runCodingExecution`'s tool-enabled runs and `_createStageChat`/`_runStageChatTurn`'s text-only runs) can host a CLI-delegated skill attachment as-is.
- **Both attachment-trigger shapes work as genuinely distinct mechanisms**, not one degrading to the other: autonomous description-based match (Tests A/B) and literal `/skill-name` (Test C) produce different underlying behavior (a reported `tool_use` event vs. silent prompt pre-processing) but both resolve correctly.
- **This removes the main reason to spike-gate Phase 2's proposal scope.** The CLI-delegated attachment kind is no longer a technical unknown — only unbuilt scope (storage for "which skill name" per status/stage, confidence-gating via new per-status storage rather than the fixed `AutomationContext` enum, and settings UI). Phase 2 can go back to being **one proposal** covering both attachment kinds, as originally concluded in this file's "Conclusions reached" section, rather than being split into a spike-gated 2a (Aion-native templates)/2b (CLI-delegated) sequence.
- **Still unresolved:** the Aion-native prompt/workflow template attachment kind has no equivalent spike — its cost is fully knowable in advance (new template storage + variable substitution against ticket context, generalizing `_assembleStageContext`'s current hardcoded-per-stage shape), so there was no comparable unknown to test empirically. Left to Phase 2's own `/propose`.

## Explore findings (2026-08-31, Phase 3 transition-precondition retrofit)

A grounded `/explore` pass against the now-shipped decision-graph engine (`pluggable-decision-graph-conditions`'s actual code, not the 2026-08-18 pre-engine assumptions above), to determine whether `_sddStageAdvanceCheck`/`_codingExecutionGateCheck` can reuse it:

- **The blocker isn't the node/condition data model — it's the wiring.** `DecisionOutcome` ([decision_outcome.dart:3](../../aion/lib/core/automation/decision_outcome.dart:3)) is explicitly documented as the result of walking a graph "once a context's persisted `AutomationConfidence` has already resolved to `auto`" — confidence-shaped, not precondition-shaped. `_sddStageAdvanceCheck` (unchanged at `tickets_cubit.dart:2807`) returns `(canAdvance: bool, blockReason: SddStageBlockReason?)`, evaluated unconditionally, with no `AutomationConfidence` involvement at all.
- **`agentJudgment` is confirmed structurally inapplicable, not just an unexplored risk.** [decision_field_catalog.dart:186](../../aion/lib/core/automation/decision_field_catalog.dart:186) hardcodes its eligibility to exactly 3 contexts evaluated "from inside a live tool-call handler with an in-flight session" — its round trip works by forking the *already-running, currently-blocked* session. `SddStage` advancement is triggered by UI clicks or automatic status-flip code, never from inside a blocked tool call; there's no session to fork.
- **The rule-builder's data-model *shape* is genuinely reusable.** All 5 `SddStage` branches decompose into deterministic yes/no checks the tree's existing branching (nested nodes) can already express — but every field they'd need is unbuilt (`decisionFieldCatalog` ships exactly 2 entries today, neither usable here).
- **Recommendation (accepted, refined during `/brainstorm`):** reuse the data model and authoring UI (`DecisionNode`/`DecisionBranch`/strict-tree/`DecisionGraphConfigCubit`/`GraphCanvas`/`DecisionOutlineList`/`DecisionNodeForm` — none of them assume `AutomationContext` specifically), but build a new evaluation layer: a binary outcome type, a confidence-independent invocation path, and no `agentJudgment` condition kind for this axis. See "Conclusions reached" above for the outcome/reason shape and scoping decisions the follow-up `/brainstorm` session resolved.
