# Chat Transcript Ux Redesign

# Proposal: Chat Transcript UX Redesign

## What

Redesign how a `chat`-type ticket's conversation is presented in
`TicketDetailScreen`, for `chat` tickets only — the comment thread on
every other ticket type (`epic`/`story`/`task`/`resource`) is untouched.

Four concrete changes, all scoped to the chat rendering path:

1. **Dedicated, independently-scrolling transcript with a collapsing
   header.** Today a chat ticket's messages render as a `shrinkWrap`,
   non-scrollable `ListView` embedded inside the same whole-page
   `SingleChildScrollView` that also carries the ticket header,
   SDD-stage tracker, coding execution section, linked tickets, and
   backlinks. To read new messages, or to reach the compose bar, the
   user scrolls past all of that every time. The transcript becomes a
   single scrolling region whose top is the full ticket-metadata
   content (title/status, parent picker, estimate/time-spent,
   linked-design chip, linked tickets, backlinks — unchanged content)
   and whose messages follow beneath it — scrolling down collapses the
   metadata into a compact pinned header (ticket ID, title, type chip,
   status), scrolling back up re-expands it. Nothing from the existing
   metadata is dropped or made harder to reach; it's just collapsible
   now. Auto-scrolls to the newest message on load and on every
   streaming update, matching how any chat interface behaves. See
   design.md §8 for the collapsing-header mechanics
   (`CustomScrollView` + `SliverPersistentHeader`).
2. **Left/right turn-taking.** Every message today renders identically
   left-aligned (avatar, author label, bubble) regardless of who sent
   it — a user has to read the author label on every bubble to follow
   the conversation. Human messages move to the right, AI/system
   messages stay on the left, the classic messaging-app convention that
   makes turn-taking scannable at a glance in a long transcript.
3. **Markdown-rendered AI replies.** AI replies come from a
   coding-execution-capable agent and can contain fenced code blocks,
   lists, and headings — today they render as one plain-text `Text`
   widget, so a code block reads as an unbroken wall of text with no
   monospace styling. AI/system message content renders through the
   existing `MarkdownView` design-system molecule (already used for
   ticket page content — see
   `aion-arch/changes/page-content-markdown-editor/design.md`) instead
   of plain `Text`. Human messages stay plain text (what a human types
   is not markdown source they intended to format).
4. **Auto-expanding, keyboard-aware compose field.** The compose box is
   a fixed single-line pill today, the same widget used for one-line
   ticket comments. For a chat ticket — where prompts are often
   multi-sentence or include pasted context — it becomes an
   auto-expanding multiline field (starts at one line, grows up to a
   capped height, then scrolls internally) with Enter-to-send /
   Shift+Enter-for-newline on hardware keyboards. The plain ticket
   comment box is untouched.

Alongside these, this change fixes one existing gap directly relevant
to the redesign: `ChatState.currentToolUse` (the live "Running
`<tool>`..." status set by `ChatCubit` on every `AgentToolUseEvent`,
added by `coding-execution-reliability-and-safety`) is populated by the
cubit today but was never rendered anywhere — the new transcript pane
surfaces it as a status line while a reply is in flight.

## Why

Chat tickets are Aion's primary interface for the whole SDD pipeline —
every spec-phase stage, the watcher-equivalent chats, and now coding
execution updates all flow through a chat ticket's transcript (see
`aion-arch/changes/sdd-ticket-execution` and
`coding-execution-reliability-and-safety`). That surface has grown in
capability (streaming text, live tool-use status, longer AI replies
with code) faster than its presentation has kept up — it still looks
and behaves like a lightweight comment thread bolted onto a ticket
detail page, which was an acceptable starting point when chat tickets
were introduced but is now a mismatch for how much time is actually
spent reading and writing in these transcripts.

## Non-goals

- The plain ticket **comment** thread (`CommentsCubit`/`CommentTile`,
  used on `epic`/`story`/`task`/`resource` tickets) is not touched —
  this redesign is scoped to `TicketType.chat` only. `CommentTile`
  keeps its current uniform-left-aligned, plain-text rendering for that
  use.
- No change to `ChatCubit`'s business logic, `AgentModelClient`, model
  routing, or how messages are persisted (`CommentRepository`) —
  presentation-layer only.
- `ChatState.currentToolUse`'s underlying status text
  (`'Running $toolName...'`) is still built as a raw, unlocalized
  string inside `ChatCubit` — this change surfaces it in the UI as-is,
  it does not localize it. A pre-existing gap, not introduced or
  widened here.
- No message editing, deletion, copy-to-clipboard, or reaction
  affordances — out of scope for this pass.
- No changes to how a chat ticket is created, titled, or spawned
  (`TicketsCubit._spawnStageChat`/coding-execution paths).
- The ticket metadata column above the transcript (header fields,
  SDD-stage tracker, coding execution section, linked tickets,
  backlinks) keeps its current content and internal layout
  untouched — only *where and how* it's presented changes: it's
  extracted into its own shared widget (`TicketMetadataSection`, moved
  to `presentation/widgets/` — see design.md §8.4) and, for `chat`
  tickets specifically, made collapsible into a compact pinned header
  as the transcript scrolls (design.md §8) rather than staying a
  separate non-scrolling block. No content is dropped, no new editing
  affordances are added — the parent picker, estimate/time-spent
  fields, linked-design chip, linked tickets, and backlinks work
  exactly as they do today, just inside a collapsing header instead of
  a static block.
