# Documentation Section

# Proposal: Documentation Section

## What

A new top-level "Documentation" section that becomes the primary home for
`resource` and `page` tickets, replacing their presence on the ticket
board/list:

- Pages and resources are removed from the main ticket list and its type
  filters/pickers. They get their own dedicated screen.
- Pages can nest sub-pages (Notion-style tree). Resources remain leaf
  nodes — they can live under a page but never have children.
- Pages/resources keep a link to board tickets (epic/story/task/chat) via
  the existing `TicketLink` relationship, displayed on both sides: a page
  shows its linked tickets, a ticket shows its linked docs.
- Full-text search across pages/resources, backed by the ticket
  embedding data already generated on every create/edit.
- Backlinks: each page/resource shows which other pages/resources link to
  it, via the same `TicketLink` mechanism (see [Open scoping
  decisions](#open-scoping-decisions)).
- One-time migration: existing resource/page tickets currently parented
  under an epic/story/task get that relationship converted into a
  `TicketLink` (type `relatesTo`) automatically on first app launch after
  this ships — nothing is left orphaned.

## Why

Resources and pages currently sit inside the Jira-like ticket
list/board, parented under whatever work item they were attached to.
There's no way to browse "all my documentation" without hunting
ticket-by-ticket, and no support for the kind of nested,
Notion/Obsidian-style knowledge-vault structure that makes documentation
easy to organize and rediscover. This also directly resolves the known
gap in `aion-arch/specs/tickets.md`: "No dedicated UI for browsing,
creating, or editing individual pages."

Source idea: `aion-arch/ideas/notion-obsidian-like-documentation-section.md`
(status: explored).

## Open scoping decisions

Two judgment calls made during design that weren't explicitly settled in
the brainstorm session — flagging both for review before `/apply`:

1. **Embedding-based search is new, not reused.** The app currently only
   *writes* ticket embeddings (on create/edit, via `EmbeddingProvider`);
   there is no existing cosine-similarity query anywhere in the codebase.
   `searchTickets` today is plain SQLite FTS5 text search, unrelated to
   embeddings. This proposal builds a new brute-force cosine-similarity
   search over the already-populated `embedding` BLOB column, scoped to
   `page`/`resource` tickets — consistent with `project.md`'s Foundational
   Decision #1 ("brute-force cosine similarity... sufficient at personal
   scale"), but it is new query-side code, not a reuse of an existing
   search feature.
2. **Backlinks = explicit `TicketLink`s between docs, not inline
   `[[wikilink]]` parsing.** "Backlinks" here means: other pages/resources
   that have an explicit `TicketLink` to this one (same mechanism used
   for doc↔ticket links, just grouped separately in the UI by the other
   side's type). It does **not** mean scanning page Markdown content for
   inline references — that would require a content-parsing feature well
   beyond this change's scope. If inline-reference backlinks were the
   intent, this should be treated as a separate follow-up idea.

## Type-compatibility change

`TicketTypeHierarchy.canParent` (`lib/features/tickets/domain/enums/ticket_type.dart`)
changes:

- `page` can now parent `page` and `resource` (previously: neither —
  both were unconditional leaves).
- `epic`/`story`/`task` can no longer parent `resource` or `page`
  (previously: any work item could parent either, unconditionally).
  `epic`/`story`/`task` parenting `chat` is unchanged.
- `resource` and `chat` remain full leaves — cannot parent anything.

## Out of scope

- Inline `[[wikilink]]`-style content references and their parsing (see
  scoping decision #2 above).
- Rich content editing beyond what already exists generically on
  `TicketDetailScreen` (title/description/comments) — no new WYSIWYG or
  block editor.
- Resource file upload/preview (`aion-arch/ideas/upload-and-visualize-files-for-resource-tickets.md`)
  — separate, still-raw idea; not pulled into this change.
- Mobile/web-specific layout tuning beyond what the existing responsive
  patterns already provide — this ships the same widget tree across
  platforms per Aion's existing convention.
