# Design: trash-restore-git-projection

## Architecture overview

No new files. Two existing files change:

```
lib/
  features/tickets/presentation/cubit/trash_cubit.dart   <-- + gitProjector/projectRootPath, trigger in restore()
core/routing/app_router.dart                              <-- + wiring in the /workspace/tickets/trash route
```

No domain, data, or drift-schema changes — `TicketGitProjector`,
`TicketRepository.restoreTicket`, and `TicketRepository.getTicketById`
already exist and are unchanged by this proposal.

## `TrashCubit` changes

### Constructor

```dart
class TrashCubit extends Cubit<TrashState> {
  TrashCubit(
    this._repository, {
    TicketGitProjector? gitProjector,
    String? projectRootPath,
  }) : super(const TrashLoading()) {
    _gitProjector = gitProjector;
    _projectRootPath = projectRootPath;
  }

  final TicketRepository _repository;
  late final TicketGitProjector? _gitProjector;
  late final String? _projectRootPath;
  // ...
}
```

Both new parameters are optional and named, matching
`TicketsCubit`'s existing `gitProjector`/`projectRootPath` pattern —
every non-desktop caller (mobile/web, and the ~dozen existing
`TrashCubit` unit tests) keeps constructing it with just a repository
and gets a cubit that no-ops on the new trigger, no call-site changes
required anywhere that doesn't care about this feature.

**Corrected during `/apply`**: assigns both fields in the constructor
*body* to `late final` fields, not via initializer-list assignment to
`final` fields as originally sketched above. `flutter analyze` flagged
the initializer-list form with `prefer_initializing_formals` — a false
positive here, for the same reason `TicketsCubit`'s own dartdoc calls
out: the public parameter name (`gitProjector`) differs from the
private backing field (`_gitProjector`), so the lint's suggested fix
(`this._gitProjector` as the parameter itself) isn't actually usable
as an external named-parameter label. Matching `TicketsCubit`'s
existing body-assignment style sidesteps the lint entirely; the two
forms are behaviorally identical.

### `_triggerGitProjection` helper

A private helper identical in shape to `TicketsCubit`'s (see
`proposal.md`'s Non-goals for why this isn't extracted into something
shared):

```dart
/// Projects [ticket] to its Markdown file and commits it, labelled
/// [eventLabel]. No-ops if no [_gitProjector]/[_projectRootPath] was
/// provided (see the constructor's dartdoc) — desktop-only in
/// practice, since `WorkspaceShell` only supplies these on desktop.
Future<void> _triggerGitProjection(Ticket ticket, String eventLabel) async {
  final projector = _gitProjector;
  final rootPath = _projectRootPath;
  if (projector == null || rootPath == null) return;
  await projector.project(ticket, rootPath, eventLabel);
}
```

### `restore(id)`

Current body:

```dart
Future<void> restore(String id) async {
  try {
    await _repository.restoreTicket(id);
    await load();
  } catch (e) {
    emit(TrashError(e.toString()));
  }
}
```

New body — fetches the restored ticket (mirroring how
`TicketsCubit.trashTicket` fetches the just-trashed ticket before
projecting it) and fires the trigger before reloading the list:

```dart
Future<void> restore(String id) async {
  try {
    await _repository.restoreTicket(id);
    final restored = await _repository.getTicketById(id);
    if (restored != null) {
      unawaited(_triggerGitProjection(restored, 'restored'));
    }
    await load();
  } catch (e) {
    emit(TrashError(e.toString()));
  }
}
```

`restoreTicket` also revives any currently-trashed ancestors/
descendants of `id`, but only `id` itself is fetched and projected —
see `proposal.md`'s Non-goals for why this mirrors `trashTickets`'
existing scope simplification rather than trying to enumerate the
cascade.

`unawaited` requires `dart:async`'s `unawaited` — `tickets_cubit.dart`
already imports it the same way; `trash_cubit.dart` needs the same
import added.

## `app_router.dart` changes

The `/workspace/tickets/trash` route currently constructs `TrashCubit`
with only a repository:

```dart
GoRoute(
  path: '/workspace/tickets/trash',
  builder: (context, state) => BlocProvider<TrashCubit>(
    create: (context) =>
        TrashCubit(context.read<TicketRepository>())..load(),
    child: const TrashScreen(),
  ),
),
```

It changes to pass the same two fields the sibling `/workspace/inbox`
route already reads for its own git needs, gated the same way
(`_activeProject(context).rootPath != null` — defined earlier in this
same file):

```dart
GoRoute(
  path: '/workspace/tickets/trash',
  builder: (context, state) => BlocProvider<TrashCubit>(
    create: (context) => TrashCubit(
      context.read<TicketRepository>(),
      gitProjector: _activeProject(context).rootPath != null
          ? context.read<TicketGitProjector>()
          : null,
      projectRootPath: _activeProject(context).rootPath,
    )..load(),
    child: const TrashScreen(),
  ),
),
```

No new `RepositoryProvider` is needed: `TicketGitProjector` is already
registered by `WorkspaceShell` (the ancestor `ShellRoute`'s builder)
whenever `rootPath != null`, and `/workspace/tickets/trash` is nested
inside that same `ShellRoute` alongside `/workspace/inbox`, which
already proves this exact read succeeds at this nesting depth.

## Testing strategy

- `trash_cubit_test.dart` (existing file — add cases, following the
  same `mocktail`-based pattern `tickets_cubit_test.dart` uses for its
  own `TicketGitProjector` coverage):
  - `restore` calls `TicketGitProjector.project` with the restored
    ticket and event label `'restored'` when both `gitProjector` and
    `projectRootPath` are supplied.
  - `restore` does not call `TicketGitProjector.project` when either is
    omitted — the existing no-op behavior every current test already
    implicitly relies on.
  - **Verified during implementation, not assumed**: a thrown
    projection error does *not* stay silently contained — `unawaited`
    means it surfaces as an unhandled Future rejection outside
    `restore`'s own `try`/`catch`, same as every existing
    `TicketsCubit._triggerGitProjection` call site. `tasks.md`'s T3
    documents this finding; no test asserts the opposite.
  - The pre-existing "restore calls the repository then reloads" test
    needed a `getTicketById` stub added, since `restore` now calls it
    unconditionally (same fix class as `storage-embedding-git-sync`'s
    T40).
- No widget-level test changes — `TrashScreen`'s UI and
  `context.read<TrashCubit>().restore(...)` call site are unchanged.
