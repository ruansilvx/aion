# Native Windows Verification Pass

# Proposal: Native Windows Verification Pass

## What

A verification-only change. No source code is written or modified — the
entire deliverable is narrowing two `## Known gaps` bullets in
`aion-arch/specs/` to reflect a live manual QA pass that was just run
against the actual native Windows desktop build (`flutter run -d windows`,
driven end-to-end via raw Win32 mouse/keyboard automation — not the
`flutter-web`/Chrome pass that's this project's usual manual-testing
target).

Three flows were exercised live and confirmed working, none of them
previously verified on any native desktop target:

1. **Board drag-and-drop** — dragged a ticket card from the Backlog
   column to To Do and back, using the desktop `Draggable` mouse path
   (not `LongPressDraggable`, which is mobile-only). Column counts and
   card placement updated correctly in both directions.
2. **Trash delete → restore** — deleted a ticket via
   `TicketOverflowMenu`, confirmed the dialog, verified it landed in
   Trash (`TrashScreen` showed `1 item`), restored it, and confirmed it
   reappeared correctly in the main ticket list at its original status.
3. **Settings → Providers → Test Connection** — triggered a fresh
   connection check against the configured `ClaudeAgentSdkProvider`.
   Observed the full `CHECKING` → `CONNECTED` cycle, confirming the
   `agent_bridge/` Node subprocess (spawned via `dart:io Process`) starts
   and round-trips correctly on native Windows.

No bugs were found in any of the three flows.

## Why

`aion-arch/specs/tickets.md`'s Known gaps section states native Windows
has only ever been verified for ticket creation and git projection —
"broader native-target coverage (other flows, other platforms) still has
not been." That's now measurably narrower for three specific flows.

The Settings connection test is the more consequential finding:
`aion-arch/specs/providers.md`'s Known gaps section notes the Claude
Agent SDK bridge is desktop-only (`dart:io Process`) and that "mobile/web
have no working provider at all today" — meaning this project's
documented default manual-test method (a `flutter-web`/Chrome pass, per
`project.md`'s Testing section) structurally cannot exercise this code
path at all. Until this pass, the one live agent/model call the app
currently makes had never been exercised on any target. It now has.

Per this project's own rule (`aion-arch/specs/` is written only by
`/archive`, never hand-edited), this verification result needs to travel
through a real OpenSpec cycle to land in the specs — even though there's
no code to review. This change exists to satisfy that, as cheaply as a
cycle can be run: no `design.md` architecture, no `tasks.md` file edits,
just the spec deltas below and the paper trail around them.

## Non-goals

- No source code changes of any kind — this change touches only
  `aion-arch/specs/` (via the delta spec below, merged at `/archive`).
- Does not close the remaining native-target gaps still open after this
  pass: accessibility (Tab/Enter keyboard walkthrough), the mobile
  `LongPressDraggable` touch path, and any flow not explicitly listed
  above (chat/coding-execution UI, git-projection reconciliation edge
  cases, etc.) remain unverified and out of scope here.
- Does not change `ProviderRegistry`'s single-implementation status
  (`providers.md`'s other Known gaps bullet) — this only confirms the
  one existing provider's connection-test path works live; it doesn't
  add a second provider or otherwise touch the abstraction.
