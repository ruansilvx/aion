# Spec Delta: pr-metadata-and-notification-center

**Reconciled 2026-09-03:** confirmed against the current `aion-arch/specs/tickets.md` "Persistent notification center" section — the mechanism (`NotificationKind`-keyed rows, `TicketsCubit._recordNotification`, the five call sites, the 20-row-cap dropdown) still matches. Several identifiers the automated check flagged as missing are present but line-wrapped in the source prose (e.g. `TicketsCubit`
`.unreadNotificationCount`) or belong to this delta's own now-superseded UI shape (`_Sidebar`/`_BottomTabBar` were this change's original layout, later replaced by `WorkspaceNavShell` — see the reconciliation note on the Persistent Navigation Shell spec ticket for that history) rather than the notification-center mechanism itself, which is unchanged. No drift in what this delta actually claims.

## ADDED

- **`GitHubCliClient.openPullRequest` return shape.** Now returns
  `({String url, int number})` instead of a bare `String`. `url` is
  unchanged (parsed from `gh pr create`'s stdout, its last non-empty
  line); `number` is newly parsed from that same URL's last path
  segment — `gh pr create` itself never prints a bare PR number (`--help`
  documents it as printing only the URL; `pr create` has no `--json`
  flag, unlike `pr view`/`pr list`).
- **`GitRepositoryClient.changedFileCount(String worktreePath, String
  baseBranch, String branch)`** — returns the count of files changed
  between `baseBranch` and `branch`, via `git diff --name-only
  <baseBranch>...<branch>` run inside `worktreePath`. Computed locally
  (not via a second `gh` call) to avoid both an extra network round trip
  and `gh pr view`'s potential just-after-creation propagation lag.
- **`GitRepositoryClient.defaultBranch(String rootPath)`** — returns the
  repo's default branch name (`git rev-parse --abbrev-ref origin/HEAD`,
  `origin/` prefix stripped), falling back to `'main'` if the command
  fails. Feeds `changedFileCount`'s `baseBranch` argument.
- **`_ExecutionActionBanner.subLine`** (`String?`, default `null`) — a
  short, single-line detail rendered under the banner's `title`,
  `tone: .success` only. Distinct from the existing `errorDetail`
  scrollable well (failure tone only, for verbose agentic output):
  `subLine` is always a short, precomputed, formatted string (e.g. "PR
  #42 · 5 files changed"). `null` renders nothing, preserving the exact
  prior layout.
- **`TicketDetailLoaded.executionPrSubLine`** (`String?`, default
  `null`) — feeds `_ExecutionActionBanner.subLine` above. Computed by
  `TicketsCubit.getTicketById` alongside `executionAwaitingReview`: when
  `true`, looks up this ticket's most recent
  `NotificationKind.executionPrOpened` notification and exposes its
  `message`. `null` when no matching notification exists (pre-upgrade
  tickets, or a `TicketsCubit` constructed without a
  `NotificationRepository`) — the banner's existing `subLine == null`
  fallback already handles this correctly.
- **`Notification`** (`lib/features/tickets/domain/entities/notification.dart`)
  — a new domain entity: `id`, `ticketId`, `ticketTitle` (denormalized
  snapshot at write time), `kind` (`NotificationKind`), `message`
  (precomputed formatted text), `createdAt`, `readAt` (nullable
  timestamp — read/unread, mirroring `Ticket.deletedAt`'s existing
  nullable-timestamp convention rather than a separate bool column). A
  computed `isUnread` getter (`readAt == null`).
- **`NotificationKind`** (enum) — `executionPrOpened`,
  `executionVerificationFailed`, `executionFailed`,
  `stageAdvanceCompleted`, `stageAdvanceFailed`. Mirrors the terminal
  states `TicketsCubit._runCodingExecution`/`_runStageChatTurn` already
  post system comments for.
- **`NotificationRepository`** (domain interface) —
  `addNotification(Notification)`, `getRecent({int limit = 20})`,
  `getUnreadCount()`, `markRead(String id)`, `markAllRead()`, plus
  `getMostRecentForTicket(String ticketId, NotificationKind kind)` (feeds
  `executionPrSubLine` above).
- **`DriftNotificationRepository`** (data layer) — Drift-backed
  implementation, straight delegation to `NotificationDao` with no
  business logic, matching `DriftExecutionQueueRepository`'s exact
  shape.
- **`NotificationsTable`/`NotificationDao`** (data layer) — new Drift
  table (`notifications`) and accessor. `AppDatabase.schemaVersion` →
  `17`, adding `NotificationsTable` with no backfill (a pre-17 database
  has no notification history to migrate).
- **`TicketsCubit._notificationRepository`** (`NotificationRepository?`,
  optional constructor param `notificationRepository`) — `null` for
  every existing construction site except `app_router.dart`, matching
  `_commentRepository`'s existing optional-dependency pattern. Every
  notification-writing/reading method below no-ops or returns an
  empty/zero default when `null`.
- **`TicketsCubit.unreadNotificationCount`** (`ValueNotifier<int>`) —
  live unread count, exposed outside the Bloc `state` machinery (not a
  field on any `TicketsState` subclass) so `WorkspaceNavShell`'s bell
  badge can render regardless of which state variant is currently
  active. `0` if constructed without a `NotificationRepository`. The
  first `ValueNotifier`-shaped field `TicketsCubit` exposes outside
  `state` — a new pattern in this codebase, not reuse of an existing
  one.
- **`TicketsCubit.loadUnreadNotificationCount()`** — loads the current
  unread count into `unreadNotificationCount`. Chained onto construction
  in `app_router.dart`, mirroring `..restoreExecutionQueue()`'s existing
  precedent. No-op without a `NotificationRepository`.
- **`TicketsCubit._recordNotification({required String ticketId,
  required NotificationKind kind, required String message})`** — the
  one shared write path every terminal branch of
  `_runCodingExecution`/`_runStageChatTurn` calls through, rather than
  duplicating insert-plus-refresh logic at each of the five call sites.
  Writes a `Notification` (denormalizing the ticket's current title) and
  refreshes `unreadNotificationCount`. No-op without a
  `NotificationRepository` — a run's own outcome is still fully
  surfaced via its existing system comment either way.
- **`TicketsCubit.getRecentNotifications({int limit = 20})`,
  `.markNotificationRead(String id)`,
  `.markAllNotificationsRead()`** — read/write surface for the
  notification dropdown. All three no-op/return an empty default
  without a `NotificationRepository`.
- **Five new notification write sites** — `_runCodingExecution`'s
  PR-opened branch (`NotificationKind.executionPrOpened`), its
  verification-failed branch (`.executionVerificationFailed`), its
  hard-`catch` infra-failure branch (`.executionFailed`); and
  `_runStageChatTurn`'s success path (`.stageAdvanceCompleted`, newly
  distinguishable from failure — today's code has no explicit success
  branch, only an implicit "no catch fired") and its existing `catch`
  (`.stageAdvanceFailed`).
- **`WorkspaceNavShell._NotificationBellTrigger`** — a new trigger
  widget in both `_Sidebar` and `_BottomTabBar`, beside the existing
  `_SecondaryActionsTrigger`: a bell glyph plus an unread-count badge
  (`ValueListenableBuilder<int>` over `TicketsCubit
  .unreadNotificationCount`), opening a notification dropdown on tap.
- **Notification dropdown widget** — built on the same
  `Overlay`/`LayerLink`/`CompositedTransformFollower`/`mounted`-guard
  mechanics `TicketOverflowMenu` already uses (a fourth instance of that
  pattern, not `SelectionMenu<T>` — an action list, not a value picker).
  Header ("Notifications" + "Mark all read"), up to 20 rows (icon by
  `NotificationKind`, `ticketTitle`, `message`, relative timestamp,
  unread dot), empty state. Tapping a row navigates to
  `/workspace/tickets/<ticketId>` then marks it read.
- New `app_en.arb` keys: `notificationExecutionPrOpened`,
  `notificationExecutionVerificationFailed`, `notificationExecutionFailed`,
  `notificationStageAdvanceCompleted`, `notificationStageAdvanceFailed`,
  `notificationCenterTitle`, `notificationCenterMarkAllRead`,
  `notificationCenterEmptyState`, `notificationBellSemantics`,
  `ticketDetailCodingExecutionPrSubLine`.

## MODIFIED

- **`GitHubCliClient.openPullRequest`'s return type** — was `Future<String>`,
  now `Future<({String url, int number})>`. `TicketsCubit
  ._runCodingExecution`'s call site updates to destructure `pr.url`/
  `pr.number`; the posted `EXECUTION: PR_OPENED <url>` comment's content
  shape is otherwise unchanged, so `_executionSucceededWithPr`'s existing
  detection needs no changes.
- **`_runCodingExecution`'s push step** — now computes `baseBranch`
  (`GitRepositoryClient.defaultBranch`) and `fileCount`
  (`GitRepositoryClient.changedFileCount`) immediately before `push`,
  inside the same `try` block. A failure in either surfaces through the
  existing surrounding `catch` exactly like a `push`/`openPullRequest`
  failure already does — no new error-handling shape.

## Out of scope (explicitly not covered by this delta)

- A dedicated full-history notification screen beyond the dropdown's
  20-row cap.
- `gh pr view`-sourced metadata beyond number/file count (labels,
  reviewers, CI status).
- Any `AutomationContext`/`AutomationConfidence` change — this delta is
  additive observability plus a small parsing fix only.
- Notification retention/pruning — rows persist indefinitely in this
  slice.
