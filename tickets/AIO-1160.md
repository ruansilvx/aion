# Design: Mid-task/issue chat branching

## §1. Overview

Two layers, built bottom-up:

1. **§2–§4: the generic tool-calling layer** — new contracts, and both
   providers' implementations of them. Provider-agnostic; knows nothing
   about tickets, chats, or branching.
2. **§5–§8: branching itself** — `TicketTypeHierarchy`, the two tool
   definitions and their `TicketsCubit` handlers, `AutomationContext`
   wiring, and the BLoC/widget surface for a `gated` proposal.

## §2. New core contracts (`core/contracts/`)

### `AgentToolDefinition` (new file `agent_tool_definition.dart`)

```dart
class AgentToolDefinition extends Equatable {
  const AgentToolDefinition({
    required this.name,
    required this.description,
    required this.inputSchema,
  });

  /// Stable tool name the model calls by (e.g. `'branch_ticket'`).
  final String name;

  /// Model-facing description of when/why to call this tool.
  final String description;

  /// JSON Schema (draft-07-compatible object schema) describing the
  /// tool's expected arguments — the same shape both Anthropic's Messages
  /// API `tools[].input_schema` and the Agent SDK's custom-tool
  /// definitions already expect, so one schema serves both providers
  /// unchanged.
  final Map<String, dynamic> inputSchema;

  @override
  List<Object?> get props => [name, description, inputSchema];
}
```

### `AgentRequest` additions (`agent_model_client.dart`)

```dart
const AgentRequest({
  required this.prompt,
  required this.model,
  this.toolsEnabled = false,
  this.workingDirectory,
  this.tools = const [],                 // NEW
  this.onToolCall,                       // NEW
});

/// App-defined tools the model may call mid-run, independent of
/// [toolsEnabled] (which governs the provider's own file/git/bash tool
/// set, not app-defined tools). Empty for every call site that predates
/// this change.
final List<AgentToolDefinition> tools;

/// Invoked by the [AgentModelClient] implementation when the model calls
/// one of [tools] mid-run. Must resolve with the tool's result — a
/// JSON-serializable [Map] fed back to the model so it can keep
/// reasoning in the same logical turn. Left unresolved for as long as
/// the caller needs (e.g. an `AutomationConfidence.gated` proposal
/// awaiting user confirmation) — the underlying run simply stays open
/// until it resolves. `null` (the default) means [tools] must also be
/// empty; a non-empty [tools] list with no [onToolCall] is a
/// programmer error, asserted in debug builds.
final Future<Map<String, dynamic>> Function(
  String toolCallId,
  String toolName,
  Map<String, dynamic> arguments,
)? onToolCall;
```

`props` gains `tools` (not `onToolCall` — a closure isn't meaningfully
equatable, same reasoning already applied to why `AgentRequest` has no
callback fields today).

### `AgentToolCallEvent` (new `AgentEvent` variant, same file)

```dart
/// An app-defined tool call the model made mid-run — distinct from
/// [AgentToolUseEvent], which reports the *provider's own* file/git/bash
/// tool use. Purely informational, like [AgentToolUseEvent]; the actual
/// execution and result round-trip happens via [AgentRequest.onToolCall],
/// awaited internally by the client implementation before it emits any
/// further events. Never terminal.
class AgentToolCallEvent extends AgentEvent {
  const AgentToolCallEvent(this.toolCallId, this.toolName, this.arguments);

  final String toolCallId;
  final String toolName;
  final Map<String, dynamic> arguments;

  @override
  List<Object?> get props => [toolCallId, toolName, arguments];
}
```

**Why a callback, not a new event the caller must react to and manually
resume:** `Stream<AgentEvent>` stays one-directional (the client emits,
the caller only ever reads) — no change to `AgentModelClient.run`'s
signature or return type. The bidirectional part is entirely internal to
each client implementation: it awaits `onToolCall` itself, wherever its
own transport needs the result to continue (a bridge stdio round-trip, a
follow-up HTTP call). `AgentToolCallEvent` is emitted immediately before
that await starts, purely so the UI can show "calling `branch_ticket`…"
while it's pending — nothing reads it to drive control flow.

## §3. `ClaudeAgentSdkClient` / `agent_bridge/index.mjs`

**Wire protocol change.** Today: Dart writes exactly one JSON line to
stdin, closes it; Node writes N NDJSON lines to stdout, exits. This
change keeps stdin open for the duration of the run instead of closing
it, and adds two new line types:

- Dart → Node (initial request line, extended): adds a `tools` array
  (`[{name, description, inputSchema}, ...]`, empty when
  `request.tools` is empty — no behavior change for any existing caller).
- Node → Dart (new): `{"type":"tool_call_request","toolCallId":"...","name":"...","arguments":{...}}`
- Dart → Node (new, replaces the stdin-close): `{"toolCallId":"...","result":{...}}`
  — one reply line per request line, matched by `toolCallId`.

**Node side (`agent_bridge/index.mjs`).** When `tools` is non-empty,
register each as a custom in-process tool via the Agent SDK's own
custom-tool mechanism (an in-process MCP server definition, each tool's
handler an async function) passed through `query()`'s `options`. A
handler does not resolve the call itself — it:

1. Emits `{"type":"tool_call_request", toolCallId, name, arguments}` to
   stdout (a fresh UUID per call).
2. Awaits a matching `{"toolCallId": ..., "result": {...}}` line on a
   stdin reader kept open for the process's whole lifetime (replacing
   today's read-one-line-then-close `readRequest` for the *reply* path —
   the initial request read stays a single line).
3. Returns the parsed `result` to the SDK, which feeds it back into its
   own tool-use/tool-result loop and continues the model's reasoning —
   this part is entirely the SDK's existing internal behavior, unchanged
   by Aion.

The process only exits once the SDK's `query()` async generator itself
finishes (a `result` message, same as today) — a pending tool call simply
holds the process (and the awaiting `onToolCall` on the Dart side) open,
consistent with §2's "no timeout" note.

**Dart side (`ClaudeAgentSdkClient.run`).** `_parseLine` gains a
`'tool_call_request'` case producing... not an `AgentEvent` directly —
handled specially in the stdout listener: on that line, emit
`AgentToolCallEvent` to the controller, then `await
request.onToolCall!(toolCallId, name, arguments)`, then write the reply
line to `process.stdin` and continue listening. `sawTerminalEvent`'s
existing "ignore everything after the first terminal event" guard is
unaffected — a tool-call round trip never itself terminates the stream.

## §4. `AnthropicMessagesApiClient`

Anthropic's Messages API already defines this exact loop natively —
implemented as an internal `while` loop inside `_streamResponse` rather
than a single POST:

1. First POST includes `tools: request.tools.map(...)` (mapped
   1:1 — `AgentToolDefinition.name`/`description`/`inputSchema` are
   already shaped like the API's own `tools[]` entries) alongside the
   existing `messages` array.
2. The SSE parser (`parseSseBlock`) gains handling for
   `content_block_start` (type `tool_use`: begin accumulating a tool call
   — `id`, `name`) and `content_block_delta` with `delta.type ==
   'input_json_delta'` (accumulate `partial_json` chunks into that call's
   argument buffer) and `content_block_stop` (parse the accumulated JSON
   as the call's `arguments`).
3. On `message_delta` with `stop_reason: 'tool_use'`: emit
   `AgentToolCallEvent` for the accumulated call, `await
   request.onToolCall!(...)`, then issue a **second POST** whose
   `messages` array is the original `messages` plus the assistant's
   `tool_use` content block plus a new `user` message carrying a
   `tool_result` content block (`tool_use_id`, `content: jsonEncode(result)`).
   Re-enter the same SSE-parsing loop against the new response.
4. Repeat until a `message_delta`/`message_stop` with
   `stop_reason` other than `tool_use` — then emit `AgentDoneEvent` as
   today, with `inputTokens`/`outputTokens` summed across every POST in
   the loop (not just the last one), so `ChatCubit.runChatTurn`'s
   persisted usage reflects the whole tool-calling turn, not just its
   final leg.

No change to `run`'s early guards (`toolsEnabled` rejection, API-key
check) — `tools`/`onToolCall` are independent of `toolsEnabled` and work
regardless of its value.

## §6. `TicketsCubit` — tool handlers

### Tool registration (extends `_resolveModelAndProvider` call sites)

A new private helper decides which tools (if any) a given chat turn
offers:

```dart
/// Tools offered on [chatTicketId]'s next turn, based on its own
/// structural position: [branchToolDefinition] whenever [chatTicketId]
/// isn't itself parented by a chat (so a branch can't be branched
/// further — see §7's depth-cap check, which this mirrors at
/// registration time so the model is never even offered a tool it would
/// immediately have declined), [closeBranchToolDefinition] whenever it
/// *is* parented by a chat. A chat can offer at most one of the two —
/// never both, never neither (every chat is either a branch or isn't).
Future<List<AgentToolDefinition>> _toolsFor(String chatTicketId) async { ... }
```

Wired into every call site that builds an `AgentRequest` for a `chat`
turn: `ChatCubit.sendMessage` (via a new optional param threaded through
from `TicketDetailScreen`, or resolved the same way `_phaseForChat`
already is — `ChatCubit` gains its own `_toolsFor`, mirroring
`_phaseForChat`'s existing shape rather than depending on `TicketsCubit`),
`TicketsCubit._runStageChatTurn`, `TicketsCubit._runCodingExecution`'s
execution-chat turn, and `retryDesignSync`. `ChatCubit.runChatTurn` itself
gains `tools`/`onToolCall` passthrough parameters (defaulting to `const
[]`/`null, exactly like `toolsEnabled` defaults to `false` today) so
every caller opts in explicitly.

### `_handleBranchToolCall` (the `onToolCall` implementation for `branch_ticket`)

```dart
Future<Map<String, dynamic>> _handleBranchToolCall(
  Ticket chat,
  Map<String, dynamic> arguments,
) async {
  final title = arguments['title'] as String? ?? 'Untitled branch';
  final description = arguments['description'] as String?;

  if (!_canBranch(chat)) {
    return {'accepted': false, 'reason': 'Already at branch depth cap.'};
  }

  final automationRepo = _automationSettingsRepository;
  final confidence = automationRepo == null
      ? AutomationConfidence.gated
      : await automationRepo.getConfidence(AutomationContext.chatBranching);

  switch (confidence) {
    case AutomationConfidence.manual:
      // Never surfaced proactively — see proposal.md's Non-goals.
      return {'accepted': false, 'reason': 'Automation set to manual.'};
    case AutomationConfidence.auto:
      final childId = await _createBranchChat(chat, title, description);
      return {'accepted': true, 'childChatId': childId};
    case AutomationConfidence.gated:
      return _awaitProposalConfirmation(
        chat,
        PendingToolProposal.branch(title: title, description: description),
        onConfirm: () => _createBranchChat(chat, title, description),
      );
  }
}
```

`_canBranch(Ticket chat)` — instance-level depth-cap check, deliberately
*not* on `TicketTypeHierarchy` (type-level rules only; this needs the
actual parent ticket's type, an instance fact, matching this project's
existing split between `canParent`'s pure type rules and `TicketsCubit`'s
own self-parent/cycle checks):

```dart
Future<bool> _canBranch(Ticket chat) async {
  final parentId = chat.parentId;
  if (parentId == null) return false; // Inbox-spawned chats stay parentless.
  final parent = await _repository.getTicketById(parentId);
  return parent != null && parent.type != TicketType.chat;
}
```

`_createBranchChat` mirrors `_createStageChat`'s direct-repository-create
shape (§ `_createStageChat`, `tickets_cubit.dart:2878`) rather than the
list-oriented public `createTicket`: builds a `Ticket(type: chat, parentId:
chat.id, title: title, description: description, status: backlog, ...)`,
calls `_repository.createTicket`, returns the persisted id. No comment is
posted on the *new* branch chat by this method — the model's next turn
(triggered separately, once the branch chat is navigated to or otherwise
addressed) opens it, same as any other freshly created chat.

### `_handleCloseBranchToolCall` (symmetric, for `close_branch`)

```dart
Future<Map<String, dynamic>> _handleCloseBranchToolCall(
  Ticket branchChat,
  Map<String, dynamic> arguments,
) async {
  final summary = arguments['summary'] as String? ?? 'Branch resolved.';
  final parentId = branchChat.parentId;
  if (parentId == null || (await _repository.getTicketById(parentId))?.type
      != TicketType.chat) {
    return {'accepted': false, 'reason': 'Not a branch chat.'};
  }

  final confidence = ... // same resolution as above, same AutomationContext.chatBranching

  switch (confidence) {
    case AutomationConfidence.manual:
      return {'accepted': false, 'reason': 'Automation set to manual.'};
    case AutomationConfidence.auto:
      await _closeBranch(branchChat, parentId, summary);
      return {'accepted': true};
    case AutomationConfidence.gated:
      return _awaitProposalConfirmation(
        branchChat,
        PendingToolProposal.close(summary: summary),
        onConfirm: () => _closeBranch(branchChat, parentId, summary),
      );
  }
}
```

`_closeBranch` updates `branchChat.status` to `TicketStatus.done` and
posts one `TicketComment(authorType: CommentAuthorType.system, content:
summary)` onto `parentId` (not `branchChat.id`) — the fold, per
`proposal.md`. Mirrors `_runStageChatTurn`'s existing pattern of posting
a system comment via `commentRepo.addComment` on failure; this is the
same mechanism used for a different (success) purpose.

### `_awaitProposalConfirmation` — the gated hold

```dart
Future<Map<String, dynamic>> _awaitProposalConfirmation(
  Ticket chat,
  PendingToolProposal proposal, {
  required Future<Map<String, dynamic>> Function() onConfirm,
}) async {
  final completer = Completer<Map<String, dynamic>>();
  _pendingProposals[chat.id] = (proposal, completer, onConfirm);
  emit(TicketDetailLoaded(chat, pendingToolProposal: proposal));
  return completer.future; // resolved by confirmPendingToolProposal/reject below
}
```

Two new public `TicketsCubit` methods drive it:

```dart
/// Confirms [chatId]'s pending proposal (if any): runs its `onConfirm`
/// action and resolves the held `onToolCall` future with an accepted
/// result, letting the paused model run continue. No-ops if [chatId] has
/// no pending proposal.
Future<void> confirmPendingToolProposal(String chatId) async { ... }

/// Rejects [chatId]'s pending proposal: resolves the held future with
/// `{'accepted': false, 'reason': 'Declined by user.'}` — the model
/// continues its turn knowing the branch/close didn't happen. No-ops if
/// [chatId] has no pending proposal.
void rejectPendingToolProposal(String chatId) { ... }
```

`_pendingProposals` is a private `Map<String, (PendingToolProposal,
Completer<Map<String,dynamic>>, Future<Map<String,dynamic>> Function())>`
field on `TicketsCubit`, cleared on confirm/reject.

# Aion — Mid-Task Chat Branching (Gated): Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Chat Transcript UX Spec](./Aion%20Chat%20Transcript%20Spec.md), the [Task-to-Coding-Execution Trigger Spec](./Aion%20Task%20Execution%20Trigger%20Spec.md), and the [Coding-Execution Reliability & Safety Spec](./Aion%20Coding%20Execution%20Reliability%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TicketDetailScreen`, `SettingsScreen`, `ChatTranscriptPane`, `ChatComposeField`, `AutomationConfidence`, and the existing `_AutomationSection` / `_AutomationTrigger` / `_AutomationMenuRow` and `_GatedBanner` / `_ExecutionActionBanner` patterns by name. Mockups: [Aion Chat Branching Mockups](./Aion%20Chat%20Branching%20Mockups.dc.html).

**What's being built.** Two app-defined AI tools let a `chat` ticket manage its own sub-issues: `branch_ticket` splits a blocking sub-issue off into its own **child `chat` ticket**, and `close_branch` folds that branch's resolution back into the parent conversation. Both are gated by a three-state automation-confidence setting (Auto / Gated / Manual). **This spec covers only the `Gated` state's two visible surfaces:**

1. **`_ToolProposalBanner`** (§1–§5) — a turn-blocking Confirm/Reject surface pinned above the compose field inside a `chat` ticket's detail screen, shown while a `branch_ticket` or `close_branch` call awaits the user. One shell, two content variants (branch, close).
2. **A fourth Settings automation row** (§6) — "Chat Branching," a new instance of the existing `_AutomationSection`, stacked with SDD Stage Automation / Coding Execution Automation / Coding-Execution Retry.

**No new screens.** Both are additions to two existing screens (the `chat`-ticket detail screen, §5; and `SettingsScreen`, §6).

**Hard constraint — no Material widgets or types anywhere.** Every surface is built from plain Flutter primitives: `DecoratedBox` / non-Material `Container` / `Padding` / `Row` / `Column` / `Stack` / `GestureDetector` / `MouseRegion` / `AnimatedContainer` / `AnimatedOpacity` / `AnimatedScale` / `CustomPaint` / `SingleChildScrollView`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `ListTile`, `AppBar`, `SnackBar`, `CircularProgressIndicator`, `DropdownButton`, `InkWell`, `Chip`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` — never a hardcoded ARGB — with the theme's `fillAlpha` (Arctic `0.11`, Obsidian `0.16`) read at the call site as `ThemeScope.of(context).fillAlpha` unless another alpha is stated.

**New tokens:** **none** for color, type, or radius. Two documented **derivations** reuse the existing banner-tint pattern on the already-defined `typeChat` accent (§4). One structural addition: `ToolProposalKind` (§7). The Settings row (§6) introduces **no** new visual states — new copy + a documented mode-dot mapping only.

## 0. Identity decision — the banner is keyed to `typeChat`, not `primary`

`typeChat` (`#4C6FDE / #7C93FF`) is the app's `chat`-type identity color — the CHAT type chip (Chat Transcript spec §0.1), and the accent this whole feature is built around (branching one chat off another). The proposal banner is therefore keyed to **`typeChat`**: its tint fill, border, leading-glyph tile, and Confirm button all resolve from `typeChat`.

**Why `typeChat` rather than `primary` (the `_GatedBanner` hue) or `success`/`danger` (the execution banners):**
- The existing `_GatedBanner` (SDD stage) uses `primary` = "advance the SDD stage." A chat-branch proposal is a **different kind** of gated moment (restructuring the conversation graph), and giving it `typeChat` keeps it from reading as the same prompt.
- `success`/`danger` (the `_ExecutionActionBanner`) carry outcome semantics (a PR opened / verification failed). A branch proposal is **neither** — declining it is not destructive and confirming it is not a "success." A neutral-but-owned accent is correct.
- Tying the banner to the CHAT chip's own color makes the relationship legible: this surface is *about* chat tickets.

Per the app's banner convention (frame hue == confirm-button hue: `_GatedBanner` = `primary`/`primary`; ready-for-review = `success`/`success`), the **Confirm** button is solid `typeChat`. Reject stays a quiet neutral ghost (§3.4).

**No new palette member.** `typeChat` already exists; the banner reuses it at the same two alpha levels the app's other banners and the CHAT chip already use — `fillAlpha` for the fill (identical to the CHAT chip, Chat Transcript spec §0.1) and `0.28 / 0.42` for the border (identical to the `success`/`danger` banner borders). See §4.

## 1. `_ToolProposalBanner` — overview

One shell, two content variants selected by `ToolProposalKind` (§7):

- **`branch`** (`branch_ticket` awaiting confirm) — proposes splitting a blocking sub-issue into its own child `chat`. Shows a proposed **title** (short) and an optional **description** (1–3 sentences of the AI's rationale).
- **`close`** (`close_branch` awaiting confirm) — proposes folding a resolved branch back into its parent. Shows a **summary** (the AI's account of how the branch was resolved) — typically one short paragraph.

Both share one geometry, one fill/border, one action row, and one "waiting" treatment; they differ only in the leading glyph (§2), the header copy (§2.2 / §3.2), and the content well's shape (§3).

```dart
enum ToolProposalKind { branch, close }

class _ToolProposalBanner extends StatelessWidget {
  final ToolProposalKind kind;
  final String? proposedTitle;   // branch only — the child chat's proposed title
  final String? description;     // branch only — optional 1–3 sentence rationale
  final String? summary;         // close only — the resolution summary paragraph
  final VoidCallback? onConfirm; // null → Confirm disabled (§3.5, request posting)
  final VoidCallback? onReject;  // null → Reject disabled
  // ...
}
```

The banner reads as a **deliberate decision point**, not a transcript entry: it is pinned outside the scrolling transcript (§5), uses the `dialogTitle` headline weight (§2.2), a tinted `typeChat` frame no chat bubble uses, and a full-width action row — none of which a `ChatMessageBubble` (Chat Transcript spec §1) has.

## 2. Container, leading glyph & header

### 2.1 Container — shared geometry (both variants, both themes)

- `DecoratedBox` → `Padding` → `Column`, `crossAxisAlignment: stretch`.
- **Width:** full content width of the compose region (pinned, §5) — not capped like a bubble.
- **Padding:** `EdgeInsets.fromLTRB(14, 13, 14, 14)` (matches `_ExecutionActionBanner` §1.1).
- **Radius:** `BorderRadius.circular(12)` — `AionRadius.lg`.
- **Fill:** `typeChat.withOpacity(fillAlpha)` = **`chatTint(isDark)`** (§4) — `0.11 / 0.16`.
- **Border:** `1px solid typeChat.withOpacity(isDark ? 0.42 : 0.28)` = **`chatBorderTint(isDark)`** (§4).
- **Shadow:** none (separated by fill + border, per Design System §1.8). The only elevation the banner carries is the compose-region top divider it sits within (§5).
- **Inner layout:** `Column`, `crossAxisAlignment: stretch`, `gap: 12`:
  1. **Header row** (§2.2) — leading glyph tile + title/status column.
  2. **Content well** (§3) — branch title+description, or close summary.
  3. **Action row** (§3.4) — Reject + Confirm.

### 2.2 Header row (`Row`, `gap: 12`, `crossAxisAlignment: start`)

**(a) Leading glyph tile** — a rounded square echoing the chat avatar disc (Chat Transcript spec §1.0), keyed to `typeChat`, carrying the "waiting" pulse (§2.3):

- **Tile:** `32×32`, `BorderRadius.circular(10)` (`AionRadius.md`), fill `typeChat.withOpacity(isDark ? 0.256 : 0.176)` = **`pressedAccentTint(typeChat, isDark)`** (existing helper — a deeper tile than the banner fill so the glyph reads).
- **Glyph — the direction distinguishes the two variants.** They are genuine **mirror images**, so `branch` (splitting *out* to a child) and `close` (folding *back* to the parent) read as visually opposite, not two unrelated icons:

| Kind | Phosphor glyph | Meaning | Mockup stand-in |
|---|---|---|---|
| `branch` | `PhosphorIcons.arrowBendDownRight` (fallback `git-branch`) | content moves **out / down into a new child thread** | `↳` (U+21B3) |
| `close` | `PhosphorIcons.arrowBendUpLeft` (fallback `git-merge`) | resolution moves **back / up into the parent** | `↰` (U+21B0) |

- **Glyph size/color:** `18px`, color `typeChat` (`#4C6FDE / #7C93FF`), both variants.
- The `arrowBendDownRight` / `arrowBendUpLeft` pair is a 180° point-reflection of each other — the chosen "opposite direction of the same relationship." If the icon set lacks the bend pair, fall back to `git-branch` / `git-merge` (domain-semantic, still opposite).

**(b) Title / status column** (`Expanded`, `Column`, `crossAxisAlignment: start`, `gap: 3`):

- **Title:** `AionText.dialogTitle` (18 / w800), color `textPrimary` (`#142230 / #E7EDF7`), `maxLines: 2`, ellipsis, `letter-spacing: -0.01em`, line-height `1.2`. The `dialogTitle` weight (the app's confirmation-surface headline) is what makes the banner read as a decision point rather than a message.
  - `branch`: `"Branch this sub-issue?"`
  - `close`: `"Fold this branch back in?"`
- **Status line:** `AionText.streamStatus` (mono 12.5 / w400, §Chat Transcript spec §4.1), color `textSecondary` (`#46586A / #A2AEC6`), preceded inline by the waiting dot (§2.3b). The AI's turn is genuinely paused on this decision, so the copy names that state:
  - both: `"Paused — waiting for your decision"`.

Using `streamStatus` (the app's live tool-use face) is deliberate: this banner is the paused-turn analog of the streaming tool-use line (Chat Transcript spec §2.3), and shares its typographic voice.

### 2.3 "Waiting" treatment — decision & spec

**Decision: a soft, slow *breathing halo* on the leading glyph tile only, plus a small pulsing dot before the status line — the banner body itself stays static and fully actionable.** Rationale: the AI's turn is genuinely **paused awaiting the user**, so some liveness is warranted (there is app precedent — the streaming bubble's `ctPulseGlow` border and the live tool-use dot, Chat Transcript spec §2.3 / Coding-Execution Reliability spec §2.1). But a *paused* turn is not *active work*: a frantic, whole-banner pulse would fight the Confirm/Reject affordance and imply the AI is busy. Confining the motion to a gentle halo (slower and softer than the streaming glow) signals "still open, waiting on you" while the two buttons stay the obvious, static focus. Under reduced-motion (`MediaQuery.disableAnimations`) both animations are omitted (static tile, static dot at full opacity).

**(a) Glyph-tile halo:** an `AnimatedOpacity`/`AnimationController` glow behind the tile — `BoxShadow(color: typeChat.withOpacity(isDark ? 0.55 : 0.40), blurRadius: 16, spreadRadius: 0)`, opacity looping `0.35 ↔ 0.85` over **2000ms** ease-in-out (`tpBreathe`) — slower than the 1600ms streaming glow, reading as "breathing," not "working."

**(b) Status dot:** a `6×6` circle, color `typeChat`, immediately before the §2.2b status text (`gap: 7`), opacity+scale looping `0.35→1.0→0.35` (scale `0.8→1.0`) over **1400ms** ease-in-out (`tpPulseDot`) — the same low-key liveness pulse as the live tool-use dot (Coding-Execution Reliability spec §2.1), reused verbatim.

## 3. Content well & actions

### 3.1 `branch` variant — proposed child well

A recessed well that reads as "the child `chat` ticket about to be created" — echoing how a chat ticket renders elsewhere (a `typeChat` square + a title), so the user sees *what* will be spun off.

- **Well container:** `DecoratedBox` → `Padding` → `Column`.
  - **Fill:** `surface` (`#FBFCFE / #131A29`) — recessed against the `typeChat`-tinted banner, exactly as the `_ExecutionActionBanner` error well recesses against its danger tint (Coding-Execution Reliability spec §1.4).
  - **Border:** `1px solid border` (`#D6E0EA / #232C40`).
  - **Radius:** `BorderRadius.circular(10)` — `AionRadius.md`.
  - **Padding:** `EdgeInsets.fromLTRB(11, 10, 11, 11)`.
  - **Layout:** `Column`, `crossAxisAlignment: start`, `gap: 8`.
- **Title row** (`Row`, `gap: 7`, `crossAxisAlignment: center`):
  - a `9×9` square, `BorderRadius.circular(2)`, fill `typeChat` — the chat-type dot from the CHAT chip.
  - a `"NEW CHAT"` micro-eyebrow, `AionText.caption` (mono 11 / w600, tracked, UPPERCASE) re-sized to **9.5**, color `typeChat` — labels the well as a to-be-created chat ticket.
  - `Spacer`.
- **Proposed title:** `AionText.cardTitle` (14 / w600), color `textPrimary`, `maxLines: 2`, ellipsis — e.g. `"Auth token refresh fails silently"`.
- **Description** (optional; omit the node entirely if `description == null`): `AionText.bodySm` (13.5 / w400, line-height 1.55), color `textSecondary`, `maxLines: 3`, ellipsis — the AI's rationale for why this deserves its own thread.

### 3.2 `close` variant — resolution summary well

Same well container geometry as §3.1 (fill `surface`, 1px `border`, radius `10`), padding `EdgeInsets.fromLTRB(12, 11, 12, 12)`, but its body is a **summary paragraph**, not a title+description:

- **Eyebrow row** (`Row`, `gap: 7`, center): a `9×9` square radius `2` fill `typeChat`; `"RESOLUTION"` eyebrow `AionText.caption` re-sized to **9.5**, color `typeChat`.
- **Summary:** `AionText.body` (15 / w500, line-height 1.5), color `textPrimary`, `gap: 7` below the eyebrow — the AI's account of how the branch was resolved, folded back into the parent. `maxLines: 5`, ellipsis; if longer, the well caps at `maxHeight: 132` and scrolls internally (`SingleChildScrollView`, primary:false) with the same static bottom fade as the error well (Coding-Execution Reliability spec §1.4) — a `height:16` `surface`→transparent gradient pinned to the well's bottom radius. Most summaries fit without scrolling.

`AionText.body` (the "primary body text — multiline description" style) is used for the summary because it *is* prose to be read; the branch description (§3.1) is a subordinate rationale, so it steps down to `bodySm`.

### 3.3 Content-well theme note

Both wells use `surface` fill + `border` in both themes — a recessed step off the `typeChat` banner tint that stays legible on Arctic (`#FBFCFE` on a faint blue tint) and Obsidian (`#131A29` on a deep indigo tint). No per-theme geometry change.

### 3.4 Action row — Reject (quiet) + Confirm (affirmative)

`Row`, `gap: 10`, `crossAxisAlignment: center`. **Layout adapts to width (§5.2):**
- **Narrow (mobile, < ~420 content px):** both buttons `Expanded` (equal width), Reject left, Confirm right — two comfortable full-width tap targets.
- **Wide (desktop / tablet):** buttons size to content (`mainAxisSize: min`) and right-align (`MainAxisAlignment.end`), Reject then Confirm; a `Spacer` leads.

Both buttons: `GestureDetector` → `MouseRegion` → `AnimatedScale` → `DecoratedBox` → `Padding` → centered content. Padding `EdgeInsets.symmetric(horizontal: 15, vertical: 10)`, radius `AionRadius.md` (10), label `AionText.button` (14 / w700), `TextAlign.center`.

**Confirm — solid `typeChat` (affirmative / primary weight):**
- **Leading glyph** (in-button, `gap: 7`): `check` (`PhosphorIcons.check`), `15px`, `#FFFFFF`.
- **Label:** `"Confirm"`, color `#FFFFFF`.
- **Fill:** `typeChat` (`#4C6FDE / #7C93FF`).
- **Glow (default):** `BoxShadow(color: typeChat.withOpacity(isDark ? 0.55 : 0.40), blurRadius: 16, spreadRadius: -6, offset: Offset(0, 6))` — the app's FAB/CTA glow shape (send button, Advance), re-keyed to `typeChat`.

**Reject — quiet neutral ghost (secondary, *not* `danger`):**
- **Label:** `"Reject"`, color `textSecondary` (`#46586A / #A2AEC6`). No leading glyph.
- **Fill:** `transparent`.
- **Border:** `1px solid border` (`#D6E0EA / #232C40`).
- **Glow:** none.

**Why Reject is a ghost, not `danger`:** declining a proposal is "not now," not a destructive act — the brief is explicit. A `danger`-red button would imply deleting/destroying something; the branch/fold simply doesn't happen and the AI's turn resumes. The quiet ghost reads as the calm secondary decline while Confirm carries all the affirmative weight.

### 3.5 Button states — both buttons, both themes

`{fill}` = `typeChat` (Confirm); Reject's resting fill is transparent.

| State | Confirm | Reject |
|---|---|---|
| **Default** | `typeChat` fill, glow (§3.4) | transparent, 1px `border`, `textSecondary` label |
| **Hover** | `Color.lerp(typeChat, isDark ? Colors.white : Colors.black, 0.10)` (derived shade — **no new token**), glow blur → 20; click cursor | fill `surfaceHover` (`#E4EDF6 / #1C2436`), border `borderStrong` (`#BAC8D6 / #35415C`), label `textPrimary`; click cursor |
| **Focused** (keyboard) | `typeChat`, default glow, + 3px ring `BoxShadow(color: typeChat.withOpacity(isDark ? 0.30 : 0.16), blur 0, spread 3)` | transparent, + same 3px `typeChat` ring; border stays `border` |
| **Pressed** | `AnimatedScale` → `0.98` (80ms), glow suppressed (blur → 0) | fill `surfaceHover`, `AnimatedScale` → `0.98` (80ms) |
| **Disabled** (`onConfirm`/`onReject == null` — a confirm/reject request is posting and the turn is mid-resolve) | `typeChat` @ `0.45`, no glow, `IgnorePointer`; label+glyph `#FFFFFF` @ `0.55` | whole control `Opacity(0.45)`, `IgnorePointer` |
| **Error** | n/a — a failed confirm/reject surfaces via the app toast (out of scope); the banner stays in Default until the turn resolves | n/a |

The `1px → 3px-ring` focused state insets nothing (ring is an outer `BoxShadow`), so neither button resizes between states. Both buttons are in the tab order and activate on Enter/Space (`FocusableActionDetector`) — **never** an `InkWell`/`ElevatedButton`.

## 4. Derived tints (no new palette members)

Mirror the existing `dangerTint` / `dangerBorderTint` shape (Coding-Execution Reliability spec §4) exactly — `<accent>.withValues(alpha: isDark ? X : Y)`, never a hardcoded ARGB, never a stored color. The accent is the already-defined `AionColors.typeChat`; these two helpers just name the alpha levels the banner uses (both identical to levels the app already applies elsewhere):

```dart
// On AionColorsHubTokens — parallels dangerTint / dangerBorderTint, keyed to typeChat.
Color chatTint(bool isDark)       => typeChat.withValues(alpha: isDark ? 0.16 : 0.11); // == fillAlpha; banner fill (§2.1) — same level as the CHAT type chip
Color chatBorderTint(bool isDark) => typeChat.withValues(alpha: isDark ? 0.42 : 0.28); // banner border (§2.1) — same level as the success/danger banner borders
```

Everything else on the banner reuses an existing helper or documented derivation:

```dart
// c = active AionColors, isDark = obsidian
final glyphTileFill = c.typeChat.withOpacity(isDark ? 0.256 : 0.176); // §2.2a — pressedAccentTint(typeChat) (existing helper)
final tileHalo      = c.typeChat.withOpacity(isDark ? 0.55  : 0.40 ); // §2.3a breathing halo (= retry-glow alpha, re-keyed)
final confirmGlow   = c.typeChat.withOpacity(isDark ? 0.55  : 0.40 ); // §3.4 Confirm CTA glow
final confirmRing   = c.typeChat.withOpacity(isDark ? 0.30  : 0.16 ); // §3.5 focus ring (= app-standard focusRing, re-keyed)
// Confirm hover shade: Color.lerp(typeChat, white/black, 0.10) — derived, not stored.
```

Animations (add to the app's shared curves; no design tokens): `tpBreathe` (2000ms ease-in-out, tile halo), `tpPulseDot` (1400ms ease-in-out, status dot — == the live tool-use dot).

## 5. Screen integration — `chat`-ticket detail

The banner is a **new pinned region** in the `chat`-ticket detail screen (Chat Transcript spec §5), inserted **between the `ChatTranscriptPane` and the `ChatComposeField`**, shown only while a `branch_ticket` / `close_branch` call awaits confirmation and `AutomationConfidence.gated` applies.

```
TicketDetailScreen  (chat-type ticket)
  Column:
    status bar (46)
    ChatMetaHeader           ── pinned
    ChatTranscriptPane       ── Expanded, own scroll (the newest AI message is the one that made the tool call)
    _ToolProposalBanner      ── pinned, NEW (only while gated + awaiting) ← this spec
    ChatComposeField         ── pinned to bottom
```

### 5.1 Placement chrome

- **Outer:** `Padding: EdgeInsets.fromLTRB(18, 12, 18, 12)`, top `1px border` divider (`#D6E0EA / #232C40`), fill `background` (`#EDF2F8 / #0A0E18`) — the same divided, pinned treatment `ChatComposeField` uses (Chat Transcript spec §3.0), so banner + compose read as one pinned footer stack. The banner (§2.1) sits inside this padding.
- The transcript pane keeps auto-scrolling to its newest message beneath the banner; the banner never scrolls with the transcript.

### 5.2 Narrow vs wide

- **Narrow (phone, the primary target):** banner is full content width; action buttons are equal-width `Expanded` (§3.4). This is the mockup's phone canvas (`380×812`, content ≈ 344px).
- **Wide (tablet/desktop):** the chat column is width-capped by the app's content-max-width; the banner fills that column, and its action buttons shrink to content and right-align (§3.4). Nothing else differs — no per-width geometry, radius, or type change.

### 5.3 Turn-blocking behavior (visual)

While the banner is shown the AI turn is paused: the transcript shows no in-flight streaming bubble (the tool call is what paused it), and the compose field stays interactive (a user may type context) but the banner is the clear focus. On Confirm/Reject the banner is removed and the turn resumes (a new system/AI message appears in the transcript — out of scope). There is **no `×` dismiss**: a gated proposal is answered by Confirm or Reject, mirroring the no-dismiss rule of the `_ExecutionActionBanner` (Coding-Execution Reliability spec §1.6).
