# Ticket Sort Control And Board As Default View

# Proposal: Ticket sort control and board as default view

## Why

`aion-arch/specs/tickets.md`'s own "Known gaps" section flags it: the
ticket list has no user-facing sort control. Today ordering is entirely
implicit — `TicketRepository.searchTickets` orders by BM25 relevance
whenever a search query is active, or by `createdAt` descending
otherwise, with no way to ask for priority-first, status-grouped, or
recently-updated-first ordering. That's a gap on the single screen users
touch the most.

A second, unrelated decision rides along in this same change, per an
explicit user call during `/brainstorm` ("ship it with this change, it's
not worth wasting a cycle on it"): `TicketsListScreen` opens to Board
view by default instead of List view.

See `aion-arch/ideas/ticket-sort-control-and-board-as-default-view.md`
for the full exploration that led here.

## What we're building

1. **A single-active-key sort control.** One `{field, direction}`
   selection at a time — not a compound/stacked sort. Selectable
   fields: `priority`, `status`, `type`, `createdAt`, `updatedAt`, plus
   `relevance` (only meaningful, and only offered as the *implicit*
   default, while a search query is active). Picking any field
   explicitly overrides the implicit default and stays sticky — even if
   the query is later cleared or changed — until the user picks a
   different field. Selecting the currently-active field a second time
   flips its direction (ascending ⇄ descending), mirroring a
   click-to-sort table header.
2. **Applied uniformly to List, Board, and Trash.** List and Board both
   render from the same `TicketsCubit` ticket list, so sorting it once
   at the query layer covers both — Board already renders each status
   column by filtering that same ordered list, preserving relative
   order within a column. Trash (a separate `TrashCubit`/screen with no
   sort UI of its own) reads the same persisted per-project sort
   selection and applies it to its own root-ticket list; `relevance`
   falls back to Trash's existing `deletedAt`-descending default, since
   Trash has no search query to score against.
3. **Persisted per-project**, the same way the existing status/type/
   priority filters are (`SharedPrefsTicketListFilterRepository`'s
   pattern) — a sibling repository, not an extension of the existing
   one (keeps the filter contract, and every existing filter test,
   untouched).
4. **Board becomes `TicketsListScreen`'s default view mode** on open,
   replacing List. Not persisted — a fixed default, same as today's `list`
   default was a fixed (not user-configurable) starting point.

## Non-goals

- No compound/multi-level sort (primary + secondary keys). Explicitly
  ruled out during `/brainstorm` as more machinery than this tool needs.
- No new sort UI on the Trash screen itself — Trash inherits the list's
  persisted sort read-only; it gets no independent sort control.
- No change to Board's column order/visibility (a separate known gap in
  `tickets.md`) or to any manual within-column drag-reordering — Board
  has none today; sorting determines a column's row order the same way
  it determines the flat list's row order.
- No persistence of the List/Board view-mode toggle itself — Board is
  simply the new fixed starting mode, exactly as List was before.
- No sort-order indicator/control added anywhere other than the new Sort
  trigger next to the existing Filters trigger.
