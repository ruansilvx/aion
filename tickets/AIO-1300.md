# Proposal: New-project onboarding — Inbox

## Source

`aion-arch/ideas/new-project-onboarding.md` (`status: specced`, five
brainstorm sessions between 2026-07-20 and 2026-07-24) and
`aion-arch/ideas/self-iteration-sequencing.md`. That idea covers three
pieces; this proposal implements the second and last unshipped one: the
"Inbox" app-level feature. The attach-to-existing-project flow (piece 1)
already shipped via `new-project-onboarding`. The Release ticket type
(piece 3) already shipped via `sdd-ticket-foundation`. Once this ships,
every piece of `self-iteration-sequencing`'s four-step build order is
complete.

Grounded via `/explore new-project-onboarding-inbox` immediately before
this proposal: confirmed `chat-transcript-ux-redesign` (this idea's own
stated blocker) is shipped, confirmed `TicketTypeHierarchy.isAlwaysRoot`
and `promoteSignalToEpic` are exactly as the idea describes, and
surfaced two corrections the idea's brainstorm sessions didn't have
code-level visibility into — both addressed in `design.md` below:

1. `WorkspaceNavShell` hardcodes exactly two top-level destinations
   (Tickets, Documentation) via a closed enum and per-destination
   widget wiring, not a data-driven list — adding Inbox as a third slot
   is a real structural change across four widgets plus routing, not
   just an enum case.
2. The idea assumed an existing "read-only source-code tool tier"
   (attributed to `design-gate-for-ticket-driven-sdd-workflow`'s
   `designSync` stage) that the Q&A purpose could reuse. It doesn't
   exist: `designSync`'s chat runs with zero tool access, and
   `agent_bridge/index.mjs`'s tool gating is strictly binary
   (`allowedTools: []` or full `bypassPermissions` — no read-only
   middle tier anywhere in the bridge). The only real "read but don't
   write" precedent is codebase-summarization's `_runFullSummarization`,
   which is full tool access made read-only solely by prompt
   instruction plus a discarded, never-pushed git worktree. Design.md
   makes an explicit decision here rather than assuming a tier that
   isn't built.

## Problem

Starting a new Epic, deciding what to work on next, planning a release,
or asking a question about the project all currently require either
manually creating a ticket by hand or picking an existing Epic/Story to
attach a chat to. There is no entry point for "I have a raw idea and no
ticket yet," "what should I work on next," or "help me plan the next
release" — every one of these needs *some* existing ticket to anchor a
chat to, which doesn't exist until the backlog is already populated.

## What's building

A new standing, non-ticket, app-level "Inbox" feature: a top-level nav
destination (alongside Tickets and Documentation) that acts as a
launcher for four purpose-specific chats, plus a history list of past
Inbox chats.

1. **Brain-dump-to-tickets.** The user pastes/types raw, unstructured
   text; the chat classifies it into one or more `signal` tickets (each
   tagged with a suggested promotion type — Epic or Bug — via a new
   `Ticket.suggestedType` field), feeding the existing signal→epic
   promotion mechanism (`TicketsCubit.promoteSignalToEpic`), which this
   change also widens to support promoting to Bug, not just Epic.
2. **What-next guidance.** A literal port of the CLI `/what-next`
   skill's priority order (active SDD-stage tickets, then known gaps
   surfaced from Documentation Pages, then open `signal` tickets) onto
   ticket/page data instead of parsing `aion-arch` markdown. Advisory
   only — no ticket creation.
3. **Release planning.** A conversational chat that queries existing
   Epic/Story/Task/Bug tickets (read-only) and, as the conversation
   concludes, creates a new `release` ticket plus `relatesTo` links to
   whichever tickets belong in it — not just a read-only report.
4. **General Q&A.** Read-only access to tickets, docs, and source code
   for "how does X work" questions — the one purpose needing real tool
   access, resolved per the Q&A tool-tier decision in `design.md`.

Every launch starts a fresh, purpose-specific chat (no continuous
thread, no auto-recall of past Inbox chats as context — consistent
with the fresh-context-per-purpose pattern SDD-stage chats already
use). The Inbox screen itself shows a single reverse-chronological
history list of past Inbox chats, each tagged with a small purpose
badge — no tabs, no search (deferred until there's evidence a long
enough history needs it).

## Out of scope

- Embedding-based search over Inbox history (explicitly deferred by
  the idea's own brainstorm).
- Making the SDD/coding-execution mechanism project-type-aware (split
  into its own idea, `project-type-aware-conventions-and-verification`).
- A real read-only `allowedTools` subset in `agent_bridge/index.mjs`
  (the Q&A tool-tier decision below reuses the existing
  worktree-isolation pattern instead — see `design.md`).
- Any change to the attach-to-existing-project flow or the Release
  ticket type — both already shipped.

## Design gate

status: APPROVED

Approved: 2026-07-30. No Material-widget violations found in the
Claude Design export (design.md's appended "Aion — Inbox Feature
Specification"). 3 new design-system additions needed before/during
`/apply` — none are new base-palette hues:

  1. `AionText.inboxCardLabel` (new `TextStyle`, Manrope 15/w700,
     letterSpacing -0.1, height 1.15) — add to
     `aion/lib/design_system/tokens/aion_text.dart`.
  2. `AionColorsHubTokens.accentTint(Color accent, bool isDark)` (new
     generic method, `accent.withValues(alpha: isDark ? 0.09 : 0.06)`)
     — add to `aion/lib/design_system/tokens/aion_colors.dart`. Needed
     for the widened promote-chooser's "Suggested" row tint (design.md
     §7.3.1), which is parameterized on whichever accent
     (`typeEpic`/`typeBug`) is suggested rather than one fixed field.
  3. `AionShadows.focus` signature widening to accept an optional
     `Color? color` (defaulting to `c.primary`, every existing caller
     unaffected) — needed for the launcher cards' per-entry
     accent-colored focus ring (design.md §4.1.1).

Claude Design export's own Dart snippets name the destination enum

`_NavDestination`, and `inboxAccentFor` must live in the tickets
feature's presentation layer (not `design_system/`), since it takes
the feature-local `InboxPurpose` enum and `design_system/` must stay
feature-agnostic per project.md's cross-feature rule. tasks.md 5.1 and
6.1 carry both corrections. See Step 2 output in the `/design-sync`
session for full detail.

All annotated `tasks.md` sections (2.2, 5.1, 6.1, 6.2, 6.3) now cite
their exact design.md section — note design.md contains two
