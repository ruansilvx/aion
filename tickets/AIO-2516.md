      **Found a real, pre-existing bug while doing this — not
      introduced by this change, but it directly limits what this
      change achieves**: `TicketGitProjector.project` skips the
      `git commit` whenever `GitRepositoryClient.hasChanges` reports no
      working-tree diff (this is deliberate — it's what stops
      `updateTicket` content edits from producing a commit per
      keystroke). But `TicketMarkdownSerializer.serialize` never
      includes `deletedAt` in the frontmatter, and neither
      `DriftTicketRepository.trashTicket` nor `.restoreTicket` touches
      `updatedAt` — so trashing or restoring a ticket whose
      title/description/status/priority/parentId/estimate/timeSpent
      haven't otherwise changed produces byte-identical Markdown to the
      last commit, `hasChanges` is `false`, and **no commit is written
      at all**, regardless of the `eventLabel` passed in. Confirmed
      empirically twice: (1) the scratch script above — the `'trashed'`
      projection call (already-shipped since `storage-embedding-git-sync`,
      unrelated to this task's own code) produced no commit, and
      neither did the new `'restored'` call this task adds; (2) the
      real `C:\Users\ruans\Desktop\test` project's actual git history
      (`git log --all --oneline`) has zero commits mentioning "trashed"
      anywhere, ever, despite `native-windows-verification-pass`
      having verified the UI-visible trash→restore round trip on this
      exact project — that pass checked ticket-list/count state, not
      git history, so it never would have caught this.

      **Not fixed here** — `TicketGitProjector`'s skip-when-unchanged
      logic and `trashTicket`/`restoreTicket`'s field set both belong
      to `storage-embedding-git-sync`, an already-archived, unrelated
      change; altering either is out of this task's scope (wiring the
      `'restored'` call site) and needs its own proposal to pick an
      approach (e.g. serialize `deletedAt`, bump `updatedAt` on
      trash/restore, or let `TicketGitProjector` force-commit specific
      event labels regardless of `hasChanges`). Flagged for the user
      rather than silently expanded or silently shipped as if it
      works. This task's own scope — that `restore()` calls
      `TicketGitProjector.project` with the correct ticket/rootPath/
      `'restored'` label — is still correctly implemented and covered
      by T3's passing unit tests (which mock `TicketGitProjector` and
      so aren't affected by `hasChanges`'s real behavior); it now
      matches `'trashed'`'s exact existing (silently-inert-in-the-
      common-case) behavior, which is a wash, not a regression.
