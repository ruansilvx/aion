# Design: design-system-restructure

## Directory shape

```
lib/
  design_system/
    tokens/
      aion_colors.dart
      aion_radius.dart        (AionRadius + AionSpacing — unchanged, no split)
      aion_shadows.dart
      aion_text.dart
      aion_theme.dart
      theme_scope.dart
    atoms/
      app_button.dart
      app_checkbox.dart
      app_text_field.dart
      app_spinner.dart
    molecules/
      app_confirm_dialog.dart
      app_dropdown.dart
      app_header.dart
      app_toast.dart
      selection_menu.dart
      inline_editable_field.dart   (moved from features/tickets/presentation/widgets/)
    design_system.dart              (barrel)

  core/
    database/
    localization/
    routing/
    utils/
    core.dart                       (barrel — widgets/theme exports removed)

  features/
    tickets/
      ...                           (inline_editable_field.dart removed)

  main.dart
```

No file content changes beyond import lines and file-header comments
(the one-line `// path — description (layer)` comment at the top of
every file must be updated to its new path, per
`flutter-conventions.md` "File headers"). No widget logic, no token
values, no public API signatures change.

## The barrel rule, extended

`flutter-conventions.md`'s existing rule: **a directory's own files
never import their own barrel** — only outside consumers do. Today this
is why `core/theme/aion_shadows.dart` imports `aion_colors.dart`
directly instead of going through `design_system.dart`, while
`core/widgets/app_button.dart` — a *sibling* of `core/theme/`, not an
owner of it — imports the `design_system.dart` barrel for tokens.

Moving `theme/` and `widgets/` under one `design_system/` directory
with one barrel changes which imports count as "internal." `tokens/`,
`atoms/`, and `molecules/` become three subdirectories of the same
barrel's own directory, so cross-imports between them become
self-imports and must go **direct**, not through `design_system.dart`:

- Every `atoms/*.dart` and `molecules/*.dart` file drops its blanket
  `import 'package:aion/core/design_system.dart';` and instead imports
  only the specific `tokens/*.dart` files it actually uses.
- `molecules/app_confirm_dialog.dart`'s existing
  `import 'package:aion/core/widgets/app_button.dart';` becomes
  `import 'package:aion/design_system/atoms/app_button.dart';` (still a
  direct leaf import, same self-import exception — expressed as an
  absolute `package:` import, not a relative `../atoms/` path, matching
  this codebase's existing convention of never using relative imports;
  confirmed at `/apply` time that zero relative imports exist anywhere
  else in the app).
- `molecules/inline_editable_field.dart` (after its move) imports
  `atoms/app_text_field.dart`, `atoms/app_button.dart`, and
  `molecules/app_toast.dart` directly, the same way — all as absolute
  `package:aion/design_system/...` imports.

Per-file token dependencies, as actually implemented (originally
derived from grepping actual `AionX`/`ThemeScope`/`fillAlpha*` usage in
each file, then corrected at `/apply` time against real usage —
see the `app_text_field.dart` note below):

| File | Needs from `tokens/` |
|---|---|
| `atoms/app_button.dart` | `aion_colors`, `aion_radius`, `aion_text`, `theme_scope` |
| `atoms/app_checkbox.dart` | `aion_radius`, `theme_scope` |
| `atoms/app_text_field.dart` | `aion_radius`, `aion_shadows`, `aion_text`, `theme_scope` — **not** `aion_colors`: `AionColors` appears only inside a `///` doc-comment bracket reference in this file, never as a real symbol, so importing it would be an unused import |
| `atoms/app_spinner.dart` | `theme_scope` |
| `molecules/app_confirm_dialog.dart` | `aion_colors` (also carries `fillAlphaArctic`/`fillAlphaObsidian`), `aion_radius`, `aion_shadows`, `aion_text`, `theme_scope` + `atoms/app_button.dart` |
| `molecules/app_dropdown.dart` | `aion_radius`, `aion_shadows`, `aion_text`, `theme_scope` |
| `molecules/app_header.dart` | `aion_radius`, `aion_text`, `theme_scope` |
| `molecules/app_toast.dart` | `aion_radius`, `aion_shadows`, `aion_text`, `theme_scope` |
| `molecules/selection_menu.dart` | `aion_radius`, `aion_shadows`, `aion_text`, `theme_scope` |
| `molecules/inline_editable_field.dart` | `aion_text`, `aion_radius` (`AionSpacing`), `theme_scope` + `atoms/app_text_field.dart`, `atoms/app_button.dart`, `molecules/app_toast.dart` |

(All cross-`design_system/` imports listed above are absolute
`package:aion/design_system/...` imports — see "The barrel rule,
extended" above for why.)

`theme/` internal cross-imports (e.g. `aion_shadows.dart` importing
`aion_colors.dart`) are unaffected — they were already direct leaf
imports under the self-import exception and stay exactly as they are,
just relocated to `tokens/`.

## Crossing out of `design_system/` into `core/`

`design_system/` is no longer nested inside `core/` — it's a sibling.
Several `atoms`/`molecules` files call `context.l10n`
(`core/localization/context_localizations_x.dart`): `app_confirm_dialog`,
`app_dropdown`, `app_header`, `app_spinner`, `app_text_field`, and
`inline_editable_field`. Today those imports are direct leaf imports
under the self-import exception, because `core/widgets/` is inside
`core/`'s own directory tree. Once `design_system/` moves out from
under `core/`, that exception no longer applies — reaching into
`core/localization/` is now crossing into a sibling directory's barrel
territory, exactly like `core/widgets/app_button.dart` reaching into
`core/theme/` was before this change. Each of those six files must
import `package:aion/core/core.dart` for `context.l10n` instead of the
old direct leaf import.

## External consumers

Checked every import of `core/design_system.dart` and `core/core.dart`
in the app (outside `core/theme/` and `core/widgets/` themselves) — zero
files import a leaf file directly, every consumer already goes through
one or both barrels. That means the fix, for every affected consumer,
is a one-line import-path change, not a restructure of the consumer:

- `import 'package:aion/core/design_system.dart';` →
  `import 'package:aion/design_system/design_system.dart';`
- `import 'package:aion/core/core.dart';` — path unchanged, only its
  export list shrinks. No consumer that also imports `design_system.dart`
  loses access to anything (verified: every file importing widgets
  already imports tokens too, and vice versa — see proposal.md).

Affected consumer files (path-only import change):
`main.dart`,
`features/tickets/presentation/screens/create_ticket_screen.dart`,
`features/tickets/presentation/screens/tickets_board_view.dart`,
`features/tickets/presentation/screens/tickets_list_screen.dart`,
`features/tickets/presentation/screens/ticket_detail_screen.dart`,
`features/tickets/presentation/screens/trash_screen.dart`,
`features/tickets/presentation/widgets/ticket_overflow_menu.dart`,
`features/tickets/presentation/widgets/ticket_selection_bar.dart`,
`features/tickets/presentation/widgets/trashed_ticket_tile.dart`.

One consumer needs more than a path swap:
`ticket_detail_screen.dart` currently has a direct leaf import,
`import 'package:aion/features/tickets/presentation/widgets/inline_editable_field.dart';`,
which must be deleted — `InlineEditableField` now arrives through the
`design_system.dart` import the file already has.

Data-layer files (`features/tickets/data/daos/*.dart`,
`features/tickets/data/repositories/drift_*_repository.dart`) import
`core.dart` only for `AppDatabase` — untouched by this change, no edit
needed.

## Documentation updates

`aion-arch/project.md`, "Architecture" section: add a short paragraph
noting the app has three top-level `lib/` groupings —
`design_system/` (tokens, atoms, molecules — no business logic, no
feature awareness), `core/` (infrastructure: database, routing,
localization, utils), `features/<feature>/` (domain/data/presentation
per feature) — and that `design_system/` is consumed by any feature via
its single barrel, the same way `core/` is.

`aion-arch/flutter-conventions.md`, "Barrel files" section: replace the
`core/design_system.dart` / `core/core.dart` description with the new
`design_system/design_system.dart` / `core/core.dart` split, and add
the promotion rule: a widget moves to `design_system/` only once it
takes no feature domain type as a constructor param and bakes in no
feature-specific copy — generalize first, promote second, never both in
one step. Also update the self-import-exception paragraph to describe
the extended rule from this design.md ("Crossing out of `design_system/`
into `core/`" above).

## Testing

No `bloc_test`/`mocktail` coverage needed — no Cubit or repository
logic touched. Verification is `flutter analyze` (must stay clean) plus
a manual interactive pass in real Chrome (per `project.md`'s testing
note on overlay-managing `StatefulWidget`s — `app_dropdown`,
`app_confirm_dialog`, `app_toast`, `selection_menu`,
`inline_editable_field`, and `ticket_overflow_menu` all manage an
`Overlay` and are exactly the class of widget that note warns automated
tests won't catch regressions in) confirming every screen still
renders, dropdowns/dialogs/toasts still open and dismiss correctly, and
inline-editable fields on `TicketDetailScreen` still enter/exit edit
mode — since this change touches every import path threading through
those widgets, a silent typo is the realistic failure mode, not a
logic bug.
