# Pr Metadata And Notification Center

# Proposal: PR metadata parsing and persistent notification center

## Why

Two gaps, currently documented verbatim in `aion-arch/specs/tickets.md`'s Known gaps section and re-verified against the live code during `/explore`:

1. **No PR metadata is parsed from a completed coding-execution run.** `GitHubCliClient.openPullRequest` (`lib/core/git/github_cli_client.dart`) runs `gh pr create` and returns only the URL — confirmed via `gh pr create --help`, which documents that command as printing *just* the created PR's URL on success, with no `--json` output flag (unlike `gh pr view`/`gh pr list`). `TicketsCubit._runCodingExecution` posts that URL verbatim in an `EXECUTION: PR_OPENED <url>` system comment and stops there. As a direct result, `_ExecutionActionBanner(tone: .success)` (`lib/features/tickets/presentation/widgets/ticket_metadata_section.dart:2859`) has never been able to show a sub-line — its own dartdoc says so explicitly: *"no PR metadata is parsed from the run's reply today, so per the original design's fallback rule the sub-line/detail is omitted."*

2. **No persistent notification center exists for coding-execution or SDD-stage-chat outcomes.** `board-execution-indicators-and-notifications` (archived 2026-07-29) deliberately deferred this, explicitly "until Aion invests in parallel execution" — a single-slot FIFO queue made a history less urgent than an immediate toast. `parallel-work` (archived 2026-08-14) shipped true concurrent coding-execution runs, meeting that stated precondition, and its own Architectural implications section flags the center as "newly relevant" but explicitly not built. Today the only surfaces are each ticket's own detail-screen banner and the app-wide `WorkspaceNavShell` toast (`TicketsErrorReason` only) — both require the human to already be looking at the right place at the right moment; nothing persists a "what happened while I was away" history.

Both gaps are traced to `aion-arch/ideas/pr-metadata-and-notification-center.md`'s brainstorm session, which paired them deliberately: the parsed PR metadata is what makes a "PR opened" notification entry meaningfully different from a bare status ping, so one parse feeds two consumers.

## What we're building

**1. PR metadata parsing.** `GitHubCliClient.openPullRequest` gains a second return value — the PR number, trivially derived from the URL's last path segment (`https://github.com/<owner>/<repo>/pull/<number>`), no extra `gh` call needed. File count is **not** available from `gh pr create`'s output and `gh pr view --json files` risks eventual-consistency lag immediately after creation, so it's computed locally instead: a new `GitRepositoryClient.changedFileCount(worktreePath, baseBranch, branchName)` running `git diff --name-only <base>...<branch>` inside the already-isolated worktree, called just before `push`. Both values feed `_ExecutionActionBanner`'s new `subLine` parameter (a plain `Text` under the title, success-tone only — distinct from the existing failure-tone `errorDetail` scrollable well) and a new "PR opened" notification entry's message — one parse, two consumers, per the idea file's own conclusion.

**2. Persistent notification center.** A new `NotificationsTable`/`NotificationDao`/`NotificationRepository` (schema version 17), following `ExecutionQueueTable`'s exact precedent as the closest existing analog (a persisted-state table unrelated to `Ticket` fields, DAO → domain-entity mapping in a `Drift*Repository` with no business logic). Rows are written from the two already-imperative, one-shot terminal code paths that currently post their own system comments — `TicketsCubit._runCodingExecution`'s PR-opened/verification-failed/hard-failure branches, and `_runStageChatTurn`'s success/failure paths — through one shared `_recordNotification(...)` helper, rather than duplicating notification-insert logic at each of the five call sites. Covers both Task/Bug coding-execution outcomes and Epic/Story SDD-stage-chat outcomes, matching `board-execution-indicators-and-notifications`'s existing computed-state scope (`isExecuting`/`isAdvancingStage` etc.) rather than the narrower "coding-execution status changes" wording in the current gap note.

**3. Bell trigger + dropdown in `WorkspaceNavShell`.** A new `_NotificationBellTrigger`, placed beside the existing `_SecondaryActionsTrigger` in both `_Sidebar` and `_BottomTabBar`, showing an unread-count badge and opening a dropdown of the 20 most recent notifications on tap. Built on the same `Overlay`/`LayerLink`/`CompositedTransformFollower`/`mounted`-guard mechanics `TicketOverflowMenu` already uses as its own third instance of that pattern ("an action list rather than a value picker") — a fourth instance here, not forced into `SelectionMenu<T>`'s single-select shape. Tapping a row navigates to that ticket and marks it read; a header "Mark all read" control clears the badge in one action.

**4. `TicketsCubit.unreadNotificationCount` — a `ValueNotifier<int>`, not a `TicketsState` field.** The badge must render from every `/workspace/*` route regardless of which `TicketsState` variant (`TicketsLoaded`, `TicketDetailLoaded`, `TicketsError`, mutation-in-flight states, …) is currently active. Retrofitting a field onto every existing state subclass would touch far more surface than the badge's own scope justifies, so it's exposed as a `ValueNotifier<int>` field sitting beside `state`, loaded via a new `TicketsCubit.loadUnreadNotificationCount()` chained onto construction in `app_router.dart` (mirroring `..restoreExecutionQueue()`'s existing precedent) and refreshed at every notification write and every mark-read/mark-all-read call. **Flagging for reviewer sign-off**: this is the first `ValueNotifier`-shaped field TicketsCubit exposes outside its Bloc `state`, a genuinely new pattern in this codebase rather than reuse of an existing one.

## Out of scope

- A dedicated full-history notification screen (infinite scroll/pagination beyond the 20 most recent). The dropdown is the only surface this slice builds; a "view all" screen is a natural, separately-proposable follow-up once real usage shows the 20-row cap is actually limiting.
- `gh pr view`-based metadata (PR labels, reviewers, CI status, etc.) — only number and file count, matching the idea file's exact scope.
- Any change to `AutomationContext`/`AutomationConfidence`/`AutomationSettingsRepository` — this change is additive observability + a small parsing fix, not a new automated decision point.
- Retention/pruning of old notification rows — every row persists indefinitely in this slice; a cap or TTL is left for a future change if the table's growth ever becomes a real concern.
- `dependency-caching-and-ancestor-sibling-conflict` — the sibling idea from the same brainstorm split covers the other two coding-execution maturity gaps (per-run dependency caching, sibling-conflict beyond `parentId`) as a fully separate change.
