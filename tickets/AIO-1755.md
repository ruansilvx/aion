# Reconstruction Preserve Ticket Id

# Proposal: Preserve `ticketId` in `TicketDbReconstructionService` imports

## What

Fix `TicketDbReconstructionService` so that reconstructing a project's
database from its git-tracked `tickets/*.md` files preserves each file's
own `ticketId` (e.g. `AIO-42`) when the row doesn't already exist locally,
instead of silently minting a new one.

Concretely:
- `TicketRepository` gains a new method, `importTicket(Ticket ticket)`,
  that persists a ticket with its caller-supplied `ticketId` verbatim.
- `TicketDao` gains a new method, `insertTicketPreservingId`, that inserts
  a row as-is (no sequence-generated id) and advances
  `TicketIdSequenceTable.seq` so a later normal `createTicket` call on
  that device can never mint an id that collides with the one just
  imported.
- `TicketDbReconstructionService` calls `importTicket` instead of
  `createTicket` on its true-import path (file has no matching existing
  row).

`TicketRepository.createTicket` itself is untouched — every other caller
(ticket creation UI, `TicketsCubit`, `ChatCubit`, `InboxCubit`, ...) keeps
its existing "always generate a fresh sequential id" behavior unchanged.

## Why

`aion-arch/specs/tickets.md`'s "DB reconstruction" section documents this
as a known, deliberate limitation: `TicketRepository.createTicket` always
assigns a fresh sequential `ticketId`, ignoring the one on the passed
`Ticket`. That's the correct contract for normal ticket creation (a brand
new ticket has no pre-existing id to preserve), but it's wrong for
reconstruction: when a file's `ticketId` has no matching DB row — the
genuine second-machine case, not just re-running against an
already-imported DB — the service currently mints a *new* id for it. That
breaks the `tickets/<ticketId>.md` filename-to-row correspondence the
entire git-projection/sync mechanism depends on.

`TicketDbReconstructionService` isn't wired into any UI flow yet, so
nothing user-facing breaks today. But it's the load-bearing piece behind
the still-open "clone existing project / multi-machine onboarding"
question in `projects.md`'s Open questions — that flow can't ship
correctly on top of a reconstruction service that silently renames
tickets. Fixing this now, while the service is still small and
standalone, is cheaper than fixing it after a UI flow and real user data
depend on it.

## Non-goals

- No UI flow to trigger reconstruction (`open`/`clone existing project`
  onboarding) — that's the separate, still-open item this change
  unblocks but doesn't itself build.
- No handling for a genuine `ticketId` prefix mismatch between the
  importing device's configured prefix (`ticket_id_prefix` in
  `SharedPreferences`) and the prefix embedded in the imported files —
  out of scope; see `design.md`'s Tradeoffs section for why this is safe
  to defer.
- No change to `createTicket`'s existing contract or any of its current
  call sites.
