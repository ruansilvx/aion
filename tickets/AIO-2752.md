# Spec delta: Tickets — Git projection

**Reconciled 2026-09-09:** cross-checked against the current `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is present verbatim (expected: this change was archived 2026-09-08, only one day before this backfill ran, and `/archive` already merges deltas into `specs/*.md` at archive time). No content changes needed.

Delta against `aion-arch/specs/tickets.md`'s "Git projection"
subsection (under "Embeddings, sync status & git projection (desktop
only)").

## MODIFIED

- **Where projection is triggered from.** The current spec text
  attributes the four (now six, see ADDED below) single-ticket
  projection events to specific `TicketsCubit`/`TrashCubit` call
  sites calling `TicketGitProjector` directly. This is replaced by: a
  `GitProjectingTicketRepository` decorator (`data/repositories/
  git_projecting_ticket_repository.dart`), sitting between every
  `TicketRepository` consumer and `DriftTicketRepository`, fires the
  matching projection event after `createTicket`,
  `updateTicketStatus`, `updateStatusForIds` (per id),
  `updateTicketSddStage`, `updateTicketParent`, `trashTicket`, and
  `restoreTicket` — regardless of which higher-level method (cubit,
  service, or future caller) invoked the repository. Provided in
  place of a plain `DriftTicketRepository` wherever `rootPath != null`
  (the same desktop gate `TicketGitProjector` construction already
  uses), via `RepositoryProvider<TicketRepository>` in
  `app_router.dart`. `TicketsCubit`/`TrashCubit`/
  `TicketParentTrashService` no longer call `TicketGitProjector`
  directly for any of these six events — they call plain
  `TicketRepository` methods and the projection happens underneath.
- **`GitRepositoryClient.add`/`commit`/`hasChanges`.** Previously used
  the unchecked `Process.run` wrapper with no exit-code inspection —
  a failed git operation during projection was silently swallowed.
  Now use the same checked (`_runChecked`, throwing `ProcessException`
  on non-zero exit) helper `createWorktree`/`push`/`tag` already use.
  `hasChanges`'s boolean-from-stdout behavior is unchanged; it's now
  only reached when the underlying `git status` call actually
  succeeded.

## ADDED

- **A sixth structural projection event: `sddStage` transitions.**
  `updateTicketSddStage` — previously not projected at all (fully
  bypassed by `TicketsCubit.advanceSddStage`, which called the
  repository directly) — now fires a `'stage-changed'`-labeled
  projection, refreshing the file's `updatedAt` on every SDD stage
  advance. `sddStage` itself is not part of the serialized frontmatter
  (unchanged by this proposal), but `updatedAt` is, and previously
  went stale indefinitely after a stage advance on an
  already-projected ticket.
- **A seventh structural projection event: reparenting.**
  `updateTicketParent` now unconditionally fires a
  `'reparented'`-labeled projection for the moved ticket itself.
  Previously, a reparent's only path to git was incidental: the
  rollup-recompute walk that follows every `changeParent` call
  (`TicketRollupRecomputer.recompute`) only projects a ticket when its
  own `estimateRollup`/`timeSpentRollup` numbers change — a ticket
  moved to a new parent with no rollup impact (the common case for a
  leaf ticket with no estimate) never got its new `parentId` written
  to `tickets/*.md` at all. This is independent of, and in addition
  to, `TicketRollupRecomputer`'s own existing batched ancestor-rollup
  projection, which still fires separately and is unchanged.
- Both of the above apply to every existing caller automatically
  (`TicketsCubit.advanceSddStage`/`updateTicketParent`, and any
  reparent/stage-advance path added in the future) — the fix is at the
  repository layer, not per call site.

## REMOVED

Nothing — every previously-documented projection event (`created`,
`status-changed` single and bulk, `trashed`, `restored`) still fires,
on the same triggers, with the same event labels, just from a
different layer.

## Non-goals reaffirmed by this delta

`updateTicket` (title/description/priority/type/estimate/timeSpent/
complexity edits), `updatePriorityForIds`, `addTimeSpent`, and
`applyEstimationSuggestion` remain uncommitted, per the current spec's
existing "content edits via `updateTicket` do not trigger a commit"
rule — this delta extends that same boundary to the bulk/dedicated
equivalents of those same fields, rather than narrowing or widening
it. `TicketRollupRecomputer`'s batched-commit shape is unchanged.
Permanent deletion (`permanentlyDeleteTicket(s)`/`emptyTrash`/
`purgeTrashOlderThan`) still never removes the corresponding
`tickets/<id>.md` file — a distinct, separate gap this proposal does
not address (see proposal.md's Non-goals).
