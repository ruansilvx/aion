# T9. Manual verification pass on the native Windows desktop build

(not the web preview — agent/model calls don't run on web at all,
and this change's visible effect depends on a real
`TicketEstimationSuggester` model call landing). Drive the running
app via PowerShell/UIA system calls: (a) open a story with at least
one child Task, keep its detail screen open, change the Task's
status to Done from the Board in a second view/window, and confirm
the Story's "Advance stage" affordance updates live without a
manual reload; (b) open a ticket's detail screen, edit its
description to trigger a fresh AI suggestion, stay on the screen,
and confirm the Complexity/Estimate row picks up the AI-suggested
badge/value once the background call lands, with no visible loading
flicker; (c) confirm ordinary navigation to a ticket not currently
cached still shows the existing loading state as before (the
Loading-skip is scoped to same-id re-entry only). No console/log
errors during the pass.
Built and ran the real Windows release build (`flutter run -d
windows --release`), drove it via synthetic Win32 mouse input
(UI Automation's own tree was unavailable — Flutter's Windows
embedder doesn't populate a semantics tree without an active
assistive-technology client, exposing only one opaque
`FLUTTERVIEW` pane to `System.Windows.Automation` — so this fell
back to `SetCursorPos`/`mouse_event` against screen coordinates,
still a system-level approach per this project's Windows-testing
convention, not a browser/preview substitute).
Verified directly: the Projects hub loads; board→detail
navigation works; opening a Story (AIO-22) renders its SDD-stage
banner correctly (exercises the modified `getTicketById` on every
load); editing its Estimate field writes through
`TicketsCubit.updateTicket`, re-renders with the manual-lock
Regenerate icon, and the Board's rollup chip updates to match
(2h → 2h 45m) on navigating back — the full write → rollup
recompute → board-refresh chain works with no crash, no stuck
loading state, and no console/log errors throughout.
**Not verified interactively, and why:** (a)/(b) both need a
write to originate from *outside* the currently-mounted detail
screen's own user interaction while that screen stays mounted —
(a) a sibling Task's status flipping via some other concurrent
context, (b) a passive AI suggestion actually landing, which
needs a configured model provider. This app is single-window with
no split/multi-instance view in this build, and no AI credentials
were configured in this environment, so neither can be triggered
without navigating away first (which would just be the
old "close and reopen" workaround this change exists to
eliminate, not a test of it). (c) is implicitly covered by the
normal navigation already exercised above — every fresh
`getTicketById(id)` call for a not-already-shown id took the
unmodified Loading path throughout this pass, no exceptions
observed. The exact mechanism (a)/(b) exercise is instead covered
deterministically by T6's seven new Cubit-level tests against
mocked state transitions — arguably the more reliable way to
verify this specific behavior regardless, since it isn't subject
to real-provider timing/flakiness.
