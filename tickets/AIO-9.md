# Automation Confidence Decisions

## Key questions asked

1. Is the goal to reopen `configurable-workflow-and-automation-engine`'s earlier decision and add a real computed confidence signal that picks which mode (auto/gated/manual) applies, or to keep those three modes exactly as user-set and instead give the model an explicit, inspectable graph of criteria to walk *within* `auto` mode?
2. Should the decision graph be one generic graph walked for every `AutomationContext` (same shape of checks applied uniformly), or a distinct graph per context, each tailored to what actually matters there?
3. Is this graph project-authorable/editable data (i.e. actually `configurable-workflow-and-automation-engine`'s unstarted Phase 3), or Aion-authored and fixed in code with no new configurability surface?
4. How does the graph actually get walked — a pure prompt artifact the model reasons through itself (like a skill file, code never evaluates it), or structured, code-evaluated data (nodes/edges/conditions) that Dart walks deterministically wherever possible, dropping into model judgment only at genuinely ambiguous leaves? If the latter, can a deterministic node hard-override the model, or does the model always retain final say?
5. Should this ship as its own independent proposal/mechanism, or be sequenced with/after Phase 3 so both share one underlying pluggable-precondition/decision engine instead of two near-identical parallel systems?
6. (Post-explore, authoring UI) Should the per-context graphs be authored as a flat, reorderable rule list (matching `WorkflowStatusSettingsScreen`'s existing idiom), or does the user want real branching-graph authoring — and if a visual graph, how does a "markdown-view"-style dual-pane (graph + list) actually behave: is the list a read-only reflection of the graph, or independently editable and synced both ways? If synced, is the list the same flat rule-list originally proposed, or a structural (indented/nested) rendering of the graph's branches?
7. (Post-canvas-explore) Should the graph be a strict tree (each branch's outcome leads to its own separate downstream conditions, never merging back), or a true DAG (branches can reconverge onto one shared node)? This determines whether the list pane can honestly be a simple nested/indented outline.

## Summary of answers

- **(b)** — keep `auto`/`gated`/`manual` exactly as-is, still purely user-set. No reopening of the "no computed confidence signal" call. The new want is a structural aid to the model's in-`auto` judgment, not a replacement for the mode-selection mechanism itself.
- **Per-context, tailored graphs** — not one generic graph. "Should I create a ticket" and "should I auto-retry a failed `flutter analyze`" are different enough judgments that a shared generic checklist wouldn't hold up.
- **Project-authored/editable, stored as data**, with an Aion-authored baseline offered by default — explicitly the same pattern already established for skills (`ProjectOverride`/`BaselineAsset` shadowing) and for `TicketStatus`/`SddStage` default presets. This makes the idea, in substance, `configurable-workflow-and-automation-engine`'s Phase 3.
- **Structured, code-evaluated (b)**, not a prompt artifact — real typed nodes/edges/conditions Dart walks deterministically where possible. **Deterministic nodes can hard-override the model** — this is a real enforcement mechanism, not purely advisory context the model can still deviate from.
- **Sequenced with Phase 3, sharing one engine** — not an independent standalone proposal. The user explicitly chose consolidation over building two parallel pluggable-decision systems.
- **Both a graph and a list, dual-pane, graph default.** Explicitly not a choice between the two — the user wants a visual node-graph canvas (real branching authoring) as the default view, alongside a synchronized list view, in a markdown-source/preview-style split pane. Both panes are independently editable and kept in bidirectional sync, not a read-only reflection either direction — the list is offered specifically because it's the faster surface for simple edits, while the graph handles genuine branching structure. The list view is the same flat ordered-rule-list shape originally proposed (condition → outcome rows, reorderable, first-match-wins).
- **Strict tree, not a DAG** — "keep it simple for now." No branch reconvergence; every downstream condition belongs to exactly one parent branch. Chosen specifically because it lets the list pane be an honest nested/indented outline (one row per node, children indented under their branch) rather than needing a "shared node reference" mechanism.

## Conclusions reached

- `AutomationConfidence` (auto/gated/manual) is unchanged and out of scope for further redesign — this idea no longer touches it.
- A new mechanism: **per-`AutomationContext` decision graphs** (one per each of today's 8 contexts — `sddStage`, `codingExecution`, `codingExecutionRetry`, `chatBranching`, `codingExecutionResume`, `ticketCreation`, `ticketLinking`, `specAutoLink`), each a structured, project-editable set of criteria the model walks when acting under `auto` for that context.
- Storage/authoring model: Aion-authored baseline graph per context, project-overridable — same shadowing/override precedent as skills and `TicketStatus`/`SddStage` presets, not a from-scratch mechanism.
- Evaluation model: structured data (nodes/edges/conditions), evaluated by app code wherever a node is deterministic (e.g. retry-count thresholds, "has this exact action failed before," data-scope checks) — genuinely ambiguous leaf nodes hand off to the model's own judgment, with the surrounding graph context informing that judgment rather than leaving it fully free-form. Deterministic nodes are hard gates: they can block the model outright, not just advise it.
- **This is now understood as `configurable-workflow-and-automation-engine`'s Phase 3**, expanded in scope: that file described Phase 3 only as pluggable precondition types for `TicketStatus`/`SddStage` transitions. This session adds that Phase 3's underlying pluggable-precondition/decision engine should also serve `AutomationContext`'s auto/gated/manual decision points, as one shared mechanism rather than two look-alike systems built separately.
- **Authoring UI: dual-pane, graph canvas (default) + synchronized list, both editable.** Grounded against `WorkflowStatusSettingsScreen`/`SkillAttachment`'s existing list+inline-form idiom (`tickets.md`'s "`WorkflowStatus` & configurable workflow" section) as the precedent for *the list side specifically* — the graph-canvas side is genuinely new UI territory for Aion with no existing precedent to reuse (no pan/zoom/node-graph widget exists anywhere in the app; every existing screen is built from bare `flutter/widgets.dart` with no Material). This overlaps [[obsidian-style-graph-view-for-ticket-links]] (still `raw`), which independently wants a node-graph canvas for a different purpose (visualizing `ticket_links` relationships, mostly-visual exploration rather than interactive authoring) — the underlying canvas primitive (pan/zoom, node/edge rendering) may be shareable even though the two features' interaction models differ.
- **Strict tree; list pane is a nested/indented outline.** Resolved by the two loose threads follow-up (2026-08-26, see "Explore findings (canvas feasibility)" below). No reconvergent branches — every node has exactly one parent branch — so the list pane can be an honest indented outline (one row per node: condition + parameter + outcome; children indented under their branch; no depth cap needed, same as a Markdown nested bullet list) rather than needing a "shared node reference" scheme a true DAG would require.
- **Canvas built standalone, not gated on a joint session with `obsidian-style-graph-view-for-ticket-links`.** That idea's own graph wants force-directed/physics auto-layout (nodes attract/repel by connectivity) — a different problem from this tree's deterministic, edge-driven layout. What could genuinely share is the rendering *substrate* (pan/zoom, node/edge hit-testing, edge painting), not the layout algorithm. Recommendation: build a `GraphCanvas` design-system primitive scoped to this feature's actual needs now (following the primitive/molecule-then-feature-consumer split already used for `SelectionMenu`/`MarkdownView`), designed loosely enough to extend later — not blocked on `obsidian-style-graph-view-for-ticket-links`, which is still `raw` and unexplored.

## Open questions

- ~~**Shared engine's actual shape.**~~ **Resolved by explore (2026-08-26)** — see "Explore findings" below. One shared graph engine (structure, evaluator, baseline+override storage), but two separate hand-authored node catalogs — node *content* doesn't generalize across transition preconditions and `AutomationContext` decisions, only the scaffolding around it does.
- **What context a node can actually see.** **Partially resolved by explore.** `codingExecutionRetry` and `codingExecution` already track exactly this (retry-attempt count, session-scoped overage flag — see Explore findings) and `chatBranching` already tracks branch depth. `ticketCreation`, `ticketLinking`, `codingExecutionResume`, `specAutoLink`, `sddStage` have no equivalent ad hoc signal today — whether they need new instrumentation before a deterministic node can say anything useful for them is still unexplored.
- **Model-judgment-leaf integration gap.** **New, surfaced by explore.** No mechanism anywhere in the codebase pauses mid-tool-call to ask the model a follow-up and resume (`gated`'s existing pause — `_awaitProposalConfirmation` — waits on a *human* UI click, never a second model turn). "Defer to model judgment" at a graph leaf can't mean a literal runtime round-trip without new plumbing; realistically it means the graph's criteria get surfaced in the system prompt before the model acts, with deterministic nodes doing the actual enforcement at interception time. `/propose` needs to make this explicit rather than assume a round-trip exists.
- ~~**Authoring UI.**~~ **Resolved this session** — see Conclusions reached. Dual-pane graph canvas (default) + synced, independently-editable list, list shape = flat ordered rule list.
- ~~**List's rendering of deep branching.**~~ **Resolved (2026-08-26)** — see Conclusions reached. Strict tree → nested/indented outline, no depth cap.
- ~~**Canvas feasibility/build approach.**~~ **Resolved (2026-08-26)** — see "Explore findings (canvas feasibility)" below and Conclusions reached. Vanilla Flutter (`InteractiveViewer` + `Stack` + `CustomPainter` edges, no new dependency), built as a standalone `GraphCanvas` design-system primitive scoped to this feature, not gated on `obsidian-style-graph-view-for-ticket-links`.
- **Bidirectional sync mechanics.** Still open, and now the sharpest remaining unknown: `MarkdownEditor`'s closest existing precedent is one-directional (raw text → rendered preview), so keeping two independently-editable views (canvas + outline) of one tree in sync both ways is new state-management design — not just conflict handling (e.g. an in-progress list edit while the graph pane restructures the same node) but the basic single-source-of-truth wiring itself. Left for `/propose`.
- **Migration/versioning** of a project's edited graph when Aion's baseline graph for a context changes in a later release — not discussed this session.

## Explore findings (2026-08-26, Phase 3 engine-sharing feasibility)

A grounded, read-only `/explore` pass against the actual `aion` codebase (`TicketsCubit`'s transition interceptors and `AutomationContext` tool-call handlers) to answer the "shared engine or shared pattern only" open question:

- **Both systems already share the same interception shape** — event fires → Dart intercepts synchronously → runs a check → allows/blocks/asks. Confirmed at [`_interceptTaskExecutionTrigger`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L2823)/[`_sddStageAdvanceCheck`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L2628) (transitions) and [`_handleCreateTicketToolCall`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L5858)/[`_handleAddLinkToolCall`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L5933)/[`_handleBranchToolCall`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L5769) (`AutomationContext`) — the latter today just `case AutomationConfidence.auto: return create();`, a bare pass-through with zero logic, exactly the slot a decision graph fills.
- **The deterministic-hard-override half already exists organically, three times over, unreused:** [`_effectiveCodingExecutionRetryConfidence`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L4006) forces `gated` once retry attempts exceed `_maxVerifyRetries`; [`_effectiveCodingExecutionConfidence`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L4026) forces `gated` once a budget overage is detected this session; [`_canBranch`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L5776)'s depth cap hard-declines branching outright, bypassing `AutomationConfidence` entirely even under `auto`. This validates the design isn't speculative — it's already proven in production three times, just not generalized or made project-editable.
- **The model-judgment-leaf half has zero precedent and a real gap.** [`_awaitProposalConfirmation`](../../aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart#L5744) (the `gated` pause mechanism) resolves its `Completer` only on a human UI confirmation — never a second model turn. By the time any `onToolCall` handler runs, the model has already decided to act; there's no existing round-trip that pauses to ask it something and resumes.
- **Node content doesn't generalize across the two systems.** `_sddStageAdvanceCheck`'s five branches each query fundamentally different data (chat-reply state, sibling-completion, linked-page content, comment-marker text) with no shared vocabulary — confirms the 2026-08-18 finding still holds. A shared engine's *node catalog* has to stay two separate, hand-authored registries; what's genuinely shareable is graph structure, evaluator, and the baseline-preset-with-override storage pattern.

## Explore findings (2026-08-26, canvas feasibility)

A second grounded, read-only `/explore` pass, this time into whether a node-graph canvas is feasible in Aion and shareable with [[obsidian-style-graph-view-for-ticket-links]]:

- **No canvas/pan-zoom/node-graph precedent exists anywhere in Aion.** Every existing `CustomPainter` is a small, single-purpose decorative painter (checkmarks, spinners, dashed borders, icon glyphs — e.g. `app_checkbox.dart:132`, `app_spinner.dart:60`, `ai_suggestion_badge.dart:92`); none does general scene rendering. No `InteractiveViewer`, scale-gesture pan/zoom, or free-positioned-widget system exists. `pubspec.yaml` has zero third-party graph/diagram/canvas packages, consistent with Aion's narrow, comment-justified dependency philosophy — this needs to be hand-built from vanilla Flutter, not bolted on from a library.
- **A directly reusable dual-pane *layout* precedent exists, but its data flow doesn't fit.** [`MarkdownEditor`'s `_Wide`](../../aion/lib/design_system/molecules/markdown_editor.dart#L636) (`design.md §1.5`) is exactly the "markdown views" analogy already shipped: a breakpoint-driven `Row` of two `Expanded` panes with a 1px divider, raw editor left, live `MarkdownView` right. The `Row`+`Expanded`+divider scaffold is directly reusable. What isn't: that sync is one-directional (typing in the raw pane updates the rendered preview; nothing edits the preview back) — true bidirectional sync between two independently-editable panes is new design work, not something to lift from this file.
- **Sharing with `obsidian-style-graph-view-for-ticket-links`: substrate yes, layout algorithm no.** An Obsidian-style link graph conventionally wants force-directed/physics auto-layout (nodes attract/repel by connectivity) — a different problem from this tree's deterministic, edge-driven layout (positions follow the edges the author actually drew, no physics needed). What could genuinely share: pan/zoom (`InteractiveViewer`, SDK-bundled, no new dependency), node/edge hit-testing, drag-to-reposition, and a `CustomPainter` edge-rendering layer.
- **Recommendation:** build one internal `GraphCanvas` design-system molecule (pan/zoom + node positioning + edge painting + drag/select, parameterized by an abstract node/edge model and a per-node content builder) as part of *this* idea's own `/propose` — following the primitive/molecule-then-feature-consumer split Aion already uses for `SelectionMenu`/`MarkdownView` — designed loosely enough to extend later, but not blocked on a joint design session with `obsidian-style-graph-view-for-ticket-links`, which is still `raw` and unexplored. The tradeoff: this risks some rework if that idea's later needs don't fit the abstraction chosen here, weighed against the alternative of blocking a ready idea on one that isn't.

## Architectural implications

- Merges into [[configurable-workflow-and-automation-engine]]'s Phase 3 rather than becoming a separate proposal — that idea's Phase 3 `next_action` should be read as covering both transition-precondition pluggability and this session's `AutomationContext` decision graphs going forward.
- Depends on `core/automation/`'s existing `AutomationConfidence`/`AutomationContext`/`AutomationSettingsRepository` trio (`providers.md`) as the outer gate this mechanism nests inside — a context still has to resolve to `auto` before its decision graph is ever consulted; `gated`/`manual` are unaffected by this idea entirely.
- Reinforces, rather than conflicts with, the baseline-preset-with-override precedent already used for skills and for `TicketStatus`/`SddStage` (`configurable-workflow-and-automation-engine`, `project-type-aware-conventions-and-verification`) — no new storage philosophy introduced, just a new structured-data shape riding the same pattern.
- **Explore complete for the engine-sharing question** (2026-08-26) — see "Explore findings" above. `/propose` should scope this as one shared graph engine/evaluator/storage with two separate node catalogs, and should design "defer to model" as prompt-surfaced criteria rather than assume a runtime model round-trip, since none exists today.
- **New UI subsystem: a node-graph canvas.** Introduces Aion's first pan/zoom/node-graph widget — no precedent to extend, and per this project's Material-coupling convention it needs to be hand-built (no Material import). Overlaps [[obsidian-style-graph-view-for-ticket-links]]'s own unmet need for a graph canvas; the two ideas should at least cross-reference implementation approach even if they ship as separate features, to avoid two independent from-scratch canvas builds.
- **Canvas feasibility and list shape both resolved** (2026-08-26) — see "Explore findings (canvas feasibility)" above. `/propose` should: (1) design a `GraphCanvas` primitive (`InteractiveViewer` + `Stack` + `CustomPainter`, no new dependency) scoped to this feature; (2) constrain the underlying data model to a strict tree (reject reconvergent edges); (3) render the list pane as a nested/indented outline mirroring that tree; (4) design genuinely new bidirectional-sync state management between the canvas and outline panes, since `MarkdownEditor`'s closest precedent is one-directional and doesn't cover this.
