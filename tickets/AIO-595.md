# Consistent Max Width Content Layout

# Proposal: Consistent max-width, centered content layout

## What

On wide viewports, most Aion screens currently stretch their content
edge-to-edge. Text lines, forms, and lists become uncomfortably wide
and hard to scan. `NewProjectScreen` already solves this for itself
with an ad hoc `ConstrainedBox(constraints: BoxConstraints(maxWidth:
520))` wrapped around its form. This change generalizes that pattern
into a shared, reusable `design_system/` widget and applies it
consistently across every screen where it makes sense.

Concretely:

- Add a new shared widget, `ContentMaxWidth`, plus a small
  `ContentWidthVariant` enum (`form` | `reading`) and a new
  `AionContentWidth` token pair (`form = 520`, `reading = 840`) to
  `design_system/`.
- Apply it to: ticket detail, page detail (which also serves as
  Aion's "documentation content" reading surface — see Scope below),
  the documentation tree/search list, the ticket list (list-mode
  body), and every create/edit form (`NewProjectScreen`,
  `CreateTicketScreen`, `PageCreateScreen`).
- Retrofit `NewProjectScreen` itself onto the new widget so the
  520px form-width value has exactly one source of truth instead of
  being duplicated.

## Why

Per the brainstorm captured in
`aion-arch/ideas/consistent-max-width-content-layout.md`: on wide
screens, content stretches edge-to-edge and becomes hard to read.
`NewProjectScreen`'s existing max-width pattern already proves the
fix works — it just isn't shared or applied anywhere else. Both
issues compound as more screens ship: without a shared widget, every
new screen either re-invents the same `ConstrainedBox` ad hoc (and
picks its own width number) or skips the treatment entirely,
producing a visibly inconsistent app.

## Scope

**In scope** (per the brainstorm's capped list):

- Ticket detail screen (`ticket_detail_screen.dart`)
- Page detail screen (`page_detail_screen.dart`) — this is also
  where "documentation content" scope item lands: pages *are* Aion's
  Notion-style documentation content, so there is no separate file
  for it. See [design.md](design.md) for the mapping.
- Documentation tree / search list (`documentation_screen.dart`)
- Ticket list, list-mode body (`tickets_list_screen.dart`)
- Forms: `NewProjectScreen` (retrofit), `CreateTicketScreen`,
  `PageCreateScreen`

**Explicitly exempted:**

- The kanban board (`tickets_board_view.dart`, rendered inline
  inside `tickets_list_screen.dart` when in board mode) — its
  columns need full available width to stay usable on wide screens.
- Floating/viewport-anchored overlays on the ticket list — FAB,
  the multi-select action bar, and the "load more" board button.
  These stay anchored to the full viewport edge regardless of the
  constrained content column beneath them; see design.md's "Overlay
  anchoring" section for the rationale.

**Not addressed by this change** (deferred per the brainstorm): the
chevron shown on documentation pages with no children, markdown
checkbox syntax not rendering, and info-bubble clipping near the
Windows viewport edge — three unrelated bugs the user explicitly
flagged as out of scope for design exploration, to be handled as
direct fixes instead.

## Non-goals

- No change to any screen's colors, typography, spacing *values*
  within the constrained column — this is a width/centering change
  only.
- No responsive breakpoint system beyond the two width variants
  introduced here (`form`, `reading`). If a third variant is needed
  later (e.g. for the board, if that exemption is ever revisited),
  that's a separate change.
- No change to the kanban board's layout.
