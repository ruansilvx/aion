# Design: sdd-ticket-foundation

Read alongside [proposal.md](proposal.md) for the why and the re-scoping
rationale. This file covers the technical shape only.

## Domain layer

### `TicketType` (`lib/features/tickets/domain/enums/ticket_type.dart`)

Two new enum values, appended after `chat` (order-independent — see
"Persistence" below, but appending keeps the diff minimal and matches how
every prior `TicketType` addition has read in git history):

```dart
enum TicketType {
  epic,
  story,
  task,
  resource,
  page,
  chat,

  /// Something noticed but not yet resolved into work: a raw idea, a
  /// known gap, or an open question — not yet shaped into an [epic].
  /// Parentless; may parent a [chat] for exploration/discussion, nothing
  /// else. See [TicketTypeHierarchy.isAlwaysRoot].
  signal,

  /// A named release/milestone. Parentless; may parent a [chat] for
  /// release-planning discussion, nothing else. Relates to [epic]/
  /// [story]/[task] tickets via `TicketLinkType.relatesTo` (a cross-
  /// cutting link, not tree-parentage) — a ticket can belong to a
  /// release without that release being its structural parent. See
  /// [TicketTypeHierarchy.isAlwaysRoot].
  release,
}
```

### `TicketTypeHierarchy` (same file)

`canParent` grows a second special case, mirroring the existing `page`
special case rather than folding `signal`/`release` into the `_rank`
work-breakdown chain (they are not part of the epic→story→task
decomposition — a `signal` doesn't parent a `story` the way an `epic`
does; it gets promoted *into* an `epic` by a separate mechanism that is
explicitly out of scope here, see proposal.md):

```dart
bool canParent(TicketType child) {
  if (this == TicketType.page) {
    return child == TicketType.page || child == TicketType.resource;
  }
  if (this == TicketType.signal || this == TicketType.release) {
    return child == TicketType.chat;
  }
  final parentRank = _rank;
  if (parentRank == null) return false;
  if (child == TicketType.chat) return true;
  final childRank = child._rank;
  if (childRank == null) return false;
  return parentRank < childRank;
}
```

`_rank` itself is unchanged — `signal`/`release` fall through to its
existing `null` default (the switch's `resource || page || chat` arm
does not need `signal`/`release` added to it, since `_rank` is only
consulted for types that don't hit one of the two special cases above;
Dart's exhaustiveness check on the `TicketType` switch does require the
two new values be accounted for somewhere in `_rank`'s switch, so they
join the existing unranked arm: `TicketType.resource || TicketType.page
|| TicketType.chat || TicketType.signal || TicketType.release => null`).

New getter, replacing three scattered `== TicketType.epic` comparisons
(`TicketsCubit.updateTicketParent`, `CreateTicketScreen`'s parent-field
visibility) with one shared source of truth:

```dart
/// Whether a ticket of this type can never receive a parent — always a
/// subtree root. `true` for [TicketType.epic], [TicketType.signal], and
/// [TicketType.release]; `false` for every other type.
bool get isAlwaysRoot =>
    this == TicketType.epic ||
    this == TicketType.signal ||
    this == TicketType.release;
```

### Persistence — no migration needed

`TicketsTable.type` (`lib/features/tickets/data/models/ticket_model.dart`)
is `TextColumn get type => text()()`, storing `TicketType.name`. Drift has
no generated index/ordinal dependency on enum declaration order for a
`TextColumn`, so appending `signal`/`release` is purely additive — no drift
migration, no `app_database.g.dart` regeneration beyond the routine
`build_runner` pass every model change already requires.

## Presentation layer

### `TicketsCubit.updateTicketParent` (`presentation/cubit/tickets_cubit.dart`)

```dart
if (ticket.type.isAlwaysRoot) {
  await _emitInvalidParent(ticket.id);
  return;
}
```

replaces the existing `if (ticket.type == TicketType.epic) { ... }`
block. Behavior for `epic` is unchanged; `signal`/`release` tickets now hit
the same rejection path. Dartdoc updated to name all three types.

No change to `createTicket` — it has never validated `parentId` against
`canParent`/root-ness (enforcement today is entirely UI-side, via
`CreateTicketScreen` hiding the parent field for root types and
`TicketParentPicker` only ever offering `canParent`-valid candidates).
That existing gap is unchanged and out of scope here.

### `CreateTicketScreen` (`presentation/screens/create_ticket_screen.dart`)

The type dropdown already includes every `TicketType` except `page`
(line 153's `.where((type) => type != TicketType.page)`) — `signal`/
`release` need no dropdown-membership change, they're included by
default like every other non-`page` type.

The parent-field visibility condition:

```dart
child: _selectedType == TicketType.epic
    ? const SizedBox.shrink()
    : Column(...)
```

becomes:

```dart
child: _selectedType.isAlwaysRoot
    ? const SizedBox.shrink()
    : Column(...)
```

so creating a `signal` or `release` ticket hides the parent field exactly
as creating an `epic` already does. `TicketParentPicker`'s
`candidatesLoader` (`getValidParentCandidatesForType(_selectedType)`) is
unaffected — it already derives correctness from `canParent`, which now
correctly returns nothing-parents-signal/release automatically.

### `resource`/`page` exclusion filters — unaffected

`TicketsListScreen`'s main-list filter
(`t.type != TicketType.resource && t.type != TicketType.page`) and
`TicketBoardView`'s board-mode filter (`task`/`story` only) both already
pass `signal`/`release` through unfiltered — same treatment `epic` already
gets today (visible in the list, absent from the board). No code change
in either screen.

## Design system

### `TypeChip` / `ticketTypeLabel` (`design_system/molecules/type_chip.dart`)

`ticketTypeLabel`'s switch gains two arms (compile-time exhaustiveness
means this is mandatory, not optional):

```dart
TicketType.signal => l10n.ticketTypeSignal,
TicketType.release => l10n.ticketTypeRelease,
```

`TypeChip.build`'s color switch currently has a catch-all
(`_ => c.typeTask`) that `signal`/`release` would silently fall into if
left unhandled — that's wrong (they're not tasks), so both need explicit
arms:

```dart
TicketType.signal => c.typeSignal,
TicketType.release => c.typeRelease,
```

### `AionColors` (`design_system/tokens/aion_colors.dart`)

Two new required fields, following the existing `typeTask`/`typeStory`/
`typeEpic`/`typeResource`/`typePage` pattern exactly (one accent `Color`
per theme variant, consumed by `TypeChip` at `alpha: t.fillAlpha` for the
tinted background):

```dart
/// Base accent color for [TicketType.signal] chips.
final Color typeSignal;

/// Base accent color for [TicketType.release] chips.
final Color typeRelease;
```

added to the constructor's required params and to both `arctic`/
`obsidian` const instantiations. Exact hex values are a Design gate
deliverable (see proposal.md) — the only hard constraint is visual
distinctness from the five existing type colors in both themes, per the
Claude Design session's normal palette-consistency check (same process
`documentation-section` used to land `typePage`/`typeResource`).

## Localization

`lib/l10n/app_en.arb` gains two keys, alongside the existing
`ticketTypeEpic`/`ticketTypePage`/etc.:

```json
"ticketTypeSignal": "Signal",
"ticketTypeRelease": "Release",
```

Single-locale project (`app_en.arb` only) — no other `.arb` file to
update.

## Cross-cutting linking — no change needed

`release`'s relationship to `epic`/`story`/`task` uses
`TicketLinkType.relatesTo` via `TicketLinkRepository.createLink`
(`domain/repositories/ticket_link_repository.dart`), which takes a bare
`sourceTicketId`/`targetTicketId`/`linkType` with no type-pair
restriction — already works for a `release`↔`epic` pair with zero
repository changes. `linked_tickets_section.dart` (the widget that
renders a ticket's links) is likewise generic over `Ticket.type` and
needs no change. Building an actual "assign this ticket to a release" UI
affordance is not part of this change — see proposal.md's Out of scope;
this section only confirms the underlying mechanism needs nothing new.

# Aion — `signal` & `release` Ticket Types: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TypeChip`, `CreateTicketScreen` by name.

This change adds **no new screens and no new widgets**. It introduces two new `TicketType` values — `signal` and `release` — and extends two existing, fully-specified surfaces to recognize them exactly the way the current six types (`epic`, `story`, `task`, `resource`, `page`, `chat`) are recognized:

1. `TypeChip` — the square-swatch + uppercase-label chip shown wherever a ticket's type appears (list rows, detail screen, board cards).
2. `CreateTicketScreen`'s **Type** dropdown — the create-flow type picker.

The only real design decisions are **two new color tokens**. Everything else (chip geometry, dropdown geometry, typography, spacing, radius) is unchanged from the base spec and is restated here only so implementation can cite an exact section.

**No Material widgets anywhere.** `TypeChip` is a `DecoratedBox` → `Padding` → `Row` (`DecoratedBox` swatch + `Text`). The dropdown trigger is a `GestureDetector` → `DecoratedBox` → `Padding` → `Row`; the open menu is an `OverlayEntry` + `CompositedTransformFollower` whose items are `GestureDetector` → `DecoratedBox` → `Padding` → `Row`. No `Card`, `DropdownButton`, `ListTile`, `InkWell`, `Theme.of`, `ColorScheme`, or `ThemeData` anywhere.

Themes: **Arctic** (light) and **Obsidian** (dark). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal.

---

## 1. New color tokens

Two new base type-accent colors, added to `AionColors` alongside the existing `typeTask` / `typeStory` / `typeEpic` (and the reference `typeResource` / `typePage`). Each is a single base color; the chip fill is that color at the theme's `fillAlpha` (§1.3 of the base spec — Arctic `0.11`, Obsidian `0.16`), never a hardcoded ARGB.

### 1.1 `typeSignal` — deep cyan

Semantic: `signal` is *something noticed but not yet resolved into work* — a raw idea, a known gap, an open question. The hue sits in the open interval between `typeStory` (green/teal) and `typeTask` (blue), reading as informational/attention ("a blip on the radar") without colliding with either neighbor, with `typeEpic` (violet/blue), `typeResource` (orange), or `typePage` (magenta/pink). Cyan holds enough darkness in Arctic to keep the full-strength label legible on the near-white surface.

| | Arctic | Obsidian |
|---|---|---|
| `typeSignal` | `Color(0xFF0E8C9E)` | `Color(0xFF34C6D6)` |

### 1.2 `typeRelease` — warm vermilion

Semantic: `release` is a named release/milestone that other tickets link to cross-cuttingly. Red is the one primary hue entirely absent from the existing type set, and reads intuitively as a version tag / release flag. It is deliberately warmer (more orange) than `danger` (a pink-leaning rose used only for destructive/error states, never as a type accent) and more saturated / redder than `typeResource` (a muted brown-orange), keeping it distinct from both — and from `typeSignal`.

| | Arctic | Obsidian |
|---|---|---|
| `typeRelease` | `Color(0xFFD8402C)` | `Color(0xFFF26A4B)` |

### 1.3 `AionColors` additions

```dart
// AionColors — add two fields alongside the existing type accents:
final Color typeSignal;
final Color typeRelease;

// Arctic:
typeSignal:  Color(0xFF0E8C9E),
typeRelease: Color(0xFFD8402C),

// Obsidian:
typeSignal:  Color(0xFF34C6D6),
typeRelease: Color(0xFFF26A4B),
```

### 1.5 `TicketType` → color resolver

The single point of extension in code. No widget hardcodes a color; both `TypeChip` and the dropdown read through this.

```dart
Color typeColorFor(TicketType type, AionColors c) {
  switch (type) {
    case TicketType.epic:     return c.typeEpic;
    case TicketType.story:    return c.typeStory;
    case TicketType.task:     return c.typeTask;
    case TicketType.resource: return c.typeResource;
    case TicketType.page:     return c.typePage;
    case TicketType.signal:   return c.typeSignal;   // new
    case TicketType.release:  return c.typeRelease;  // new
    case TicketType.chat:     return c.typeChat;     // pre-existing
  }
}

String typeLabelFor(TicketType type) {
  switch (type) {
    case TicketType.signal:  return 'SIGNAL';   // new — pre-uppercased string
    case TicketType.release: return 'RELEASE';  // new — pre-uppercased string
    // …existing labels: 'EPIC', 'STORY', 'TASK', 'RESOURCE', 'PAGE', 'CHAT'
    default: return type.name.toUpperCase();
  }
}
```

## 2. `TypeChip`

Unchanged structurally from base spec §2.2 — this section restates its exact geometry so the two new colors can be cited in context. `signal` and `release` render through the identical widget; only `typeColorFor` returns the new base color.

**No Material.** `DecoratedBox` (fill) → `Padding` → `Row` ( `DecoratedBox` swatch + `SizedBox(width: 5)` + `Text` ).

- Fill: `typeColorFor(type, c).withOpacity(fillAlpha)` — `fillAlpha` = `0.11` Arctic / `0.16` Obsidian.
- Border: none.
- Shadow: none.
- Border radius: `BorderRadius.circular(5)`.
- Leading swatch: solid `DecoratedBox`, fill `typeColorFor(type, c)` (full strength), `borderRadius: BorderRadius.circular(2)`.
- Gap swatch → label: `5` (`SizedBox(width: 5)`).
- Label: `AionText.chip` (Manrope 10.5 / w700 / ls 0.53), `.copyWith(color: typeColorFor(type, c))`, pre-uppercased string.
- Icon size / icon color: n/a (no glyph; the swatch is the only leading element).

### 2.1 Row variant (compact — list rows, board cards)

| Property | Value |
|---|---|
| Padding | `EdgeInsets.fromLTRB(5, 2, 7, 2)` |
| Swatch | `9 × 9`, radius `2` |
| Label | `AionText.chip` |
| Radius | `5` |

### 2.2 Detail variant (larger — ticket detail header)

| Property | Value |
|---|---|
| Padding | `EdgeInsets.fromLTRB(6, 3, 8, 3)` |
| Swatch | `11 × 11`, radius `3` |
| Label | `AionText.chip` |
| Radius | `5` |

### 2.3 New-type renderings

| Type | Label string | Fill | Swatch + text |
|---|---|---|---|
| `signal` | `"SIGNAL"` | `typeSignal.withOpacity(fillAlpha)` | `typeSignal` |
| `release` | `"RELEASE"` | `typeRelease.withOpacity(fillAlpha)` | `typeRelease` |

Arctic signal chip: fill `#0E8C9E` @ 0.11; swatch/text `#0E8C9E`. Obsidian: fill `#34C6D6` @ 0.16; swatch/text `#34C6D6`.
Arctic release chip: fill `#D8402C` @ 0.11; swatch/text `#D8402C`. Obsidian: fill `#F26A4B` @ 0.16; swatch/text `#F26A4B`.

### 2.4 States

`TypeChip` is a **non-interactive display element** — it has no default/hover/focused/pressed/disabled/error states of its own. It reflects the ticket's type only; taps route through the enclosing row/card, not the chip. No state variants to specify. (When it appears inside an interactive ticket row, the row owns hover/press per base spec §2.7 — the chip itself does not change.)

## 3. `CreateTicketScreen` — Type dropdown

Unchanged structurally from base spec §2.5 / §3.2. The Type field is the second field on the create form (Title → **Type** → …). This change extends its option list from 5 to **7** options. `page` is **excluded from this dropdown today and stays excluded** (pages are created from the Documentation section, not the generic create flow).

**Option list, in order:** `Epic`, `Story`, `Task`, `Resource`, `Signal`, `Release`, `Chat`.

**No Material.** Trigger: `GestureDetector` → `DecoratedBox` → `Padding` → `Row`. Menu: `OverlayEntry` anchored via `CompositedTransformFollower` (`LayerLink` on the trigger), a `DecoratedBox` panel wrapping a `Column` of item rows, each `GestureDetector` → `DecoratedBox` → `Padding` → `Row`.

### 3.1 Field label

- Text: `"Type"`, `AionText.label` (Manrope 12 / w700), color `textSecondary` (`#46586A / #A2AEC6`).
- Required marker: trailing `"*"`, `AionText.label`, color `danger` (`#CE3D54 / #F1546C`). Type is required.
- Gap label → control: `7` (`SizedBox(height: 7)`).

### 3.2 Trigger (closed)

Shared geometry with the create form's other controls (base spec §2.5).

| Property | Value |
|---|---|
| Width | `double.infinity` |
| Padding | `EdgeInsets.symmetric(horizontal: 13, vertical: 11)` |
| Fill | `surface` (`#FBFCFE / #131A29`) |
| Border | `1px solid border` (`#D6E0EA / #232C40`) |
| Radius | `BorderRadius.circular(11)` (`AionRadius.lg`, screen value) |
| Shadow | none |
| Layout | `Row`, `gap: 10`, `crossAxisAlignment: center` |
| Content | selected type's `TypeChip` (row variant, §2.1) + `Spacer` + trailing chevron |
| Trailing chevron | `caret-down`, `11–12px`, color `textMuted` (`#8496A6 / #6B7690`) |

Before any selection the trigger shows placeholder text `"Select a type"`, `AionText.bodySm` (render 14), color `textMuted`, in place of the chip.

### 3.3 Open menu (overlay)

- Anchor: `CompositedTransformFollower` to the trigger's `LayerLink`, offset `(0, 6)`, grows top-left, left-aligned to the trigger's left edge.
- Width: matches the trigger width (full form-column width) — the type options are short, so unlike the parent picker the menu is not fixed at 320.
- Panel fill: `surface`. Border: `1px solid borderStrong` (`#BAC8D6 / #35415C`). Radius: `BorderRadius.circular(12)` (`AionRadius.lg`). Padding: `EdgeInsets.symmetric(vertical: 4)`.
- Shadow: `BoxShadow(color: Color(0x00000000)` → use `Colors`-free ARGB via `Colors.black.withOpacity(isDark ? 0.55 : 0.20)`, `blurRadius: 46`, `spreadRadius: -14`, `offset: Offset(0, 22))`. (Same drop as every other Aion overlay; expressed as `withOpacity`, never hardcoded ARGB.)
- No search field (short fixed list); no dividers between rows.

#### 3.3.1 Menu item row

- Padding: `EdgeInsets.symmetric(horizontal: 13, vertical: 9)`.
- Layout: `Row`, `gap: 10`, `crossAxisAlignment: center`.
  - Leading: the type's `TypeChip` (row variant, §2.1).
  - Label: the type's title-case name (`"Epic"`, `"Signal"`, `"Release"`, …), `AionText.bodySm` (Manrope 13.5 / w400), color `textPrimary` (`#142230 / #E7EDF7`), `Expanded`.
  - Trailing (selected only): `check` glyph, `15px`, color `primary` (`#2E86D4 / #9366FF`).
- Icon size / color: trailing check `15px` / `primary`; no other icons.

#### 3.3.2 Item states

| State | Fill | Text | Extra |
|---|---|---|---|
| Default | `transparent` | `textPrimary` | chip at full color |
| Hover (pointer) | `surfaceHover` (`#E4EDF6 / #1C2436`) | `textPrimary` | `MouseRegion` cursor click |
| Focused (keyboard nav) | `surfaceHover` | `textPrimary` | same as hover; arrow keys move focus |
| Pressed | `border` (`#D6E0EA / #232C40`) | `textPrimary` | commits selection on release, closes menu |
| Selected (current value) | `surfaceHover` | `textPrimary` | trailing `check` `primary` |
| Disabled | n/a | — | no option is ever disabled in this menu |

### 3.4 Trigger states

| State | Border | Fill | Extra |
|---|---|---|---|
| Default | `1px border` | `surface` | — |
| Hover | `1px borderStrong` | `surface` | chevron `textMuted` → `textSecondary` |
| Focused | `1.5px primary` | `surface` | focus ring `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` |
| Pressed / Open | `1.5px primary` | `surface` | ring as focused; chevron flips to `caret-up`; trigger holds this state while the overlay is open |
| Disabled | `1px border` | `surface` @ `0.5` opacity | `IgnorePointer`; chip/chevron → `textMuted`. Only while the whole form is submitting. |
| Error | `1.5px danger` | `surface` | ring `danger.withOpacity(isDark ? 0.30 : 0.16)` + helper line below (`AionText.bodySm`, `danger`). Type is required — error state applies if submit is attempted with no type chosen. |

- 1.5px focus/error borders inset 0.5px vs. the 1px default so the box does not resize between states (`BorderSide` drawn inside).
- Press feedback: `AnimatedScale` to `0.99` over 80ms on `onTapDown`, back on release/open.

## 4. Open item — `chat` chip color

The `chat` type must appear in both the `TypeChip` set and the Type dropdown (it is the 7th dropdown option). Its accent color, `typeChat`, is **pre-existing in the running app but was not provided in this brief**. This spec does **not** define or change it — it is referenced by name (`typeChat`) through `typeColorFor` only.

In the mockups, `chat` is rendered with the existing neutral `secondary` token (`#5E7183 / #57608A`) as a stand-in, chosen because it reads as intentionally "meta / non-work-item" and invents no new accent hue. **Confirm the real `typeChat` value before implementation** — if it differs, only the mockup swatch changes; no spec logic depends on it.

## 6. Token summary

- **New colors (2):** `typeSignal` (`#0E8C9E / #34C6D6`), `typeRelease` (`#D8402C / #F26A4B`) — §1. Both are base type accents; chip fills derive via `.withOpacity(fillAlpha)`.
- **No new typography:** `AionText.chip` (chip labels), `AionText.label` (field label), `AionText.bodySm` (dropdown item text) — all existing.
- **No new radius:** chip `5`, control/menu `11`/`12` (`AionRadius.lg`), swatch `2`/`3`.
- **No new spacing:** all internal gaps/paddings are 4-multiples given as explicit `EdgeInsets`; field-label gap `7`, field stack gap `AionSpacing.sp16`.
- **No new widgets, no new screens.** Two enum values, one color resolver extension, one dropdown option list extended 5 → 7 (excluding `page`).
- Translucent fills (chip tints, focus/error rings, overlay shadow) via `token.withOpacity(x)`, never hardcoded ARGB.
