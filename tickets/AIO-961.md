# Design: Idea, Known Gap, and Open Question ticket types

## 0. Summary of the shape

No repository interface changes are needed anywhere in this design —
every new Cubit method composes existing `TicketRepository`/
`TicketLinkRepository` primitives (`updateTicket`, `createTicket`,
`createLink`, `getLinksByTypes`, `getAllTickets`) exactly as
`promoteSignal`/`loadDocumentRelations`/`_refreshBlockedBoardState`
already do today. This is a domain-enum change plus a `TicketsCubit`
change plus new presentation widgets — no new drift columns, no new DAO
queries.

## 1. Domain layer

### 1.1 `TicketType` (`domain/enums/ticket_type.dart`)

```dart
enum TicketType {
  epic, story, task, resource, page, chat,
  idea,          // was `signal` — freestanding, promotable
  knownGap,      // new — never freestanding, never promotable
  openQuestion,  // new — never freestanding, never promotable
  release, bug,
}
```

`idea` gets the exact dartdoc `signal` had (minus the "or a known gap,
or an open question" clause, since those are now their own values).
`knownGap`/`openQuestion` get a new dartdoc pair explaining the hard
target-ticket requirement and pointing at `TicketsCubit.
createGapOrQuestion`/`reclassifyIdea`.

`TicketTypeHierarchy` changes:

- `_rank`: `idea`, `knownGap`, `openQuestion` all resolve to `null`,
  replacing `signal`'s single `null` arm — no rank change, just three
  arms instead of one.
- `canParent`: the existing `this == TicketType.signal ||
  this == TicketType.release` branch becomes `this == TicketType.idea ||
  this == TicketType.knownGap || this == TicketType.openQuestion ||
  this == TicketType.release`, still `return child == TicketType.chat;`
  unchanged. All three new types may parent a `chat` (exploration/
  discussion), nothing else — identical to `signal`'s existing rule.
- `isAlwaysRoot`: `this == TicketType.epic || this == TicketType.idea ||
  this == TicketType.knownGap || this == TicketType.openQuestion ||
  this == TicketType.release`. The "always root" property is about
  *structural* parentage (`parentId`) — `knownGap`/`openQuestion`'s
  mandatory target relationship is a `TicketLink`, a completely
  separate mechanism, so this stays `true` for both exactly as it was
  for `signal`.
- `executableTypes`/`isExecutable`: untouched.

### 1.2 `GapOrQuestionRef` (new — `domain/entities/gap_or_question_ref.dart`)

Mirrors `LinkedTicketRef`'s shape, adding the one extra field the
recursive rollup needs to say *where* in the subtree an entry was
raised:

```dart
typedef GapOrQuestionRef = ({
  Ticket ticket,     // the knownGap/openQuestion ticket itself
  Ticket raisedOn,   // the specific ticket it's relatesTo-linked to —
                      // the viewed ticket itself, or one of its
                      // descendants
  String linkId,
});
```

`raisedOn` is what lets the UI render "Open question — on Login Flow
(Story)" when viewed from the Epic two levels up, vs. just the title
when `raisedOn.id == ticket.id`.

## 2. Data layer

### 2.1 `AppDatabase` migration (`core/database/app_database.dart`)

`type` is a plain `TextColumn` (`ticket_model.dart`) storing
`TicketType.name` — removing `signal` from the enum makes any
pre-existing `type = 'signal'` row throw on deserialization
(`TicketType.values.byName`) the moment the app tries to read it. Bump
`schemaVersion` to `11`:

```dart
if (from < 11) {
  await m.database.customStatement(
    "UPDATE tickets SET type = 'idea' WHERE type = 'signal'",
  );
}
```

This is a blanket default, not a heuristic — every pre-existing
`signal` row becomes `idea` (the type that keeps `signal`'s exact prior
behavior unchanged), never guessed into `knownGap`/`openQuestion`. A
user who wants one of those old tickets reclassified does it by hand
via `TicketsCubit.reclassifyIdea` (§4.3) after upgrade — consistent
with the idea file's explicit rejection of automatic heuristic
migration.

No new/changed columns. `TicketsTable.suggestedType`'s doc comment
("meaningful only for `TicketType.signal` tickets") updates to say
`TicketType.idea` instead — text-only, no schema effect.

### 2.2 `ticket_model.dart` / other `TicketType.signal` references

Every non-domain, non-Cubit reference to `TicketType.signal` found in
this proposal's research becomes `TicketType.idea` (the type that
inherits `signal`'s behavior). No file references `knownGap`/
`openQuestion` yet outside what this change adds — they're wholly new.

## 3. `TicketsCubit` (`presentation/cubit/tickets_cubit.dart`)

### 3.1 `promoteSignal` → `promoteIdea` (rename only)

Same signature, same body, same guard shape — just renamed and
re-pointed at the new enum value:

```dart
Future<void> promoteIdea(
  Ticket idea, {
  required TicketType targetType,
  String? existingTicketId,
}) async {
  if (idea.type != TicketType.idea) {
    emit(TicketsError('Only idea tickets can be promoted.'));
    ...
  }
  if (targetType != TicketType.epic && targetType != TicketType.bug) {
    emit(TicketsError('Ideas can only be promoted to an epic or a bug.'));
    ...
  }
  // unchanged: create-or-link + relatesTo, same as promoteSignal

```

`runCodebaseSummarization` (§4337 in current source) creates
`TicketType.signal` run-record and finding tickets, both flowing
through `promoteSignal` unmodified per its own dartdoc — becomes
`TicketType.idea`, `promoteIdea`, same flow, same dartdoc claim ("no
automatic ticket creation beyond what this explicit, user-triggered
call already represents").

### 3.2 `createGapOrQuestion` (new)

```dart
/// Creates a [type] (`knownGap`/`openQuestion` only) ticket titled
/// [title] with optional [description], linked
/// ([TicketLinkType.relatesTo]) to [targetTicketId] in the same
/// operation. Emits [TicketsError] and refuses to create anything if
/// [type] isn't `knownGap`/`openQuestion`, or if [targetTicketId]
/// doesn't resolve to an existing ticket — the hard rule that a
/// known-gap/open-question can never exist without its target lives
/// here, not as a UI-layer convention. No-ops if constructed without a
/// [TicketLinkRepository].
Future<void> createGapOrQuestion(
  TicketType type, {
  required String title,
  String? description,
  required String targetTicketId,
}) async {
  if (type != TicketType.knownGap && type != TicketType.openQuestion) {
    emit(TicketsError('Only known gaps or open questions can be raised this way.'));
    return;
  }
  final linkRepo = _linkRepository;
  if (linkRepo == null) return;
  final target = await _repository.getTicketById(targetTicketId);
  if (target == null) {
    emit(TicketsError('The target ticket no longer exists.'));
    return;
  }
  final now = DateTime.now();
  final raised = Ticket(
    id: _uuid.v4(),
    ticketId: '',
    type: type,
    title: title,
    description: description,
    status: TicketStatus.backlog,
    createdAt: now,
    updatedAt: now,
  );
  await _repository.createTicket(raised);
  await linkRepo.createLink(
    sourceTicketId: raised.id,
    targetTicketId: targetTicketId,
    linkType: TicketLinkType.relatesTo,
  );
  await loadDocumentRelations(targetTicketId); // refreshes the caller's section
}
```

Called from the new Gaps & Open Questions section's creation popover
(§6.2), where `targetTicketId` is always the currently-viewed ticket's
own id — the hard rule is enforced here regardless, since this is the
same Cubit method `reclassifyIdea`-adjacent future callers would use.

### 3.3 `reclassifyIdea` (new)

```dart
/// Converts an existing `idea` ticket into a `knownGap`/`openQuestion`
/// (per [targetType]), linking it to [targetTicketId] in the same
/// operation — the manual-reclassification path for a misclassified
/// idea, or for a pre-`idea-gap-question-ticket-types` `signal` ticket
/// migrated to `idea` by the schema-11 default (see
/// `AppDatabase`'s migration). Same target-existence/type validation as
/// [createGapOrQuestion]; additionally refuses if [idea.type] isn't
/// [TicketType.idea]. Mutates the ticket's stored `type` via
/// [TicketRepository.updateTicket] — never deletes/recreates it, so its
/// id, ticketId, createdAt, and any comments/chat children survive the
/// reclassification.
Future<void> reclassifyIdea(
  Ticket idea, {
  required TicketType targetType,
  required String targetTicketId,
}) async {
  if (idea.type != TicketType.idea) {
    emit(TicketsError('Only idea tickets can be reclassified.'));
    return;
  }
  if (targetType != TicketType.knownGap && targetType != TicketType.openQuestion) {
    emit(TicketsError('Ideas can only be reclassified to a known gap or an open question.'));
    return;
  }
  final linkRepo = _linkRepository;
  if (linkRepo == null) return;
  final target = await _repository.getTicketById(targetTicketId);
  if (target == null) {
    emit(TicketsError('The target ticket no longer exists.'));
    return;
  }
  await _repository.updateTicket(idea.copyWith(type: targetType));
  await linkRepo.createLink(
    sourceTicketId: idea.id,
    targetTicketId: targetTicketId,
    linkType: TicketLinkType.relatesTo,
  );
  final refreshed = await _repository.getTicketById(idea.id);
  if (refreshed != null) emit(TicketDetailLoaded(refreshed));
}
```

`Ticket.copyWith` already accepts `TicketType? type` (existing
parameter, unused by any current call site) — no entity change needed.

### 3.4 `loadDocumentRelations` extended for recursive rollup

Same gated-type list as today (`page`/`resource`/`bug`/`epic`/`story`/
`task`), same early-return shape, one more query pass added after the
existing `linkedTickets`/`backlinks` loop:

```dart
Future<void> loadDocumentRelations(String ticketId) async {
  final ticket = await _repository.getTicketById(ticketId);
  if (ticket == null) return;
  if (/* unchanged gate */) return;

  final childDocs = /* unchanged */;
  final linkedTickets = <LinkedTicketRef>[];
  final backlinks = <LinkedTicketRef>[];
  /* unchanged linkedTickets/backlinks loop */

  final gapsAndOpenQuestions = <GapOrQuestionRef>[];
  final linkRepo = _linkRepository;
  if (linkRepo != null) {
    final all = await _repository.getAllTickets();
    final byId = {for (final t in all) t.id: t};
    final subtreeIds = {ticket.id, ..._descendantIds(ticket.id, all)};
    final relatesToLinks =
        await linkRepo.getLinksByTypes([TicketLinkType.relatesTo]);
    for (final link in relatesToLinks) {
      final source = byId[link.sourceTicketId];
      final target = byId[link.targetTicketId];
      if (source == null || target == null) continue;
      // The gap/question ticket is always the `relatesTo` link's
      // *source* — createGapOrQuestion/reclassifyIdea always create it
      // that way — so only that direction is checked.
      if ((source.type == TicketType.knownGap ||
              source.type == TicketType.openQuestion) &&
          subtreeIds.contains(target.id)) {
        gapsAndOpenQuestions.add((
          ticket: source,
          raisedOn: target,
          linkId: link.id,
        ));
      }
    }
  }

  final current = state;
  if (current is! TicketDetailLoaded || current.ticket.id != ticket.id) return;
  emit(TicketDetailLoaded(
    ticket,
    childDocs: childDocs,
    linkedTickets: linkedTickets,
    backlinks: backlinks,
    gapsAndOpenQuestions: gapsAndOpenQuestions,
  ));
}
```

`getLinksByTypes([TicketLinkType.relatesTo])` is one bulk, app-wide
query (already used by `_refreshBlockedBoardState` for `blocks`/
`blockedBy`) — no N+1 across the subtree, consistent with the project's
existing "sufficient at personal scale" reasoning for brute-force
queries over the full ticket set.

### 3.5 `TicketDetailLoaded` state (`presentation/cubit/tickets_state.dart`)

Add `gapsAndOpenQuestions` alongside `linkedTickets`/`backlinks`:
same `const [] `default, same "empty until `loadDocumentRelations`
resolves" dartdoc convention, added to `props`.

## 4. Presentation — screen wiring

### 4.1 `ticket_metadata_section.dart`

The existing gate (`ticket.type == TicketType.chat || ticket.type ==
TicketType.signal || ticket.type == TicketType.release` → hide the
whole Documentation-mode block) becomes `chat`/`idea`/`knownGap`/
`openQuestion`/`release` — `idea` keeps `signal`'s exclusion (no
meaningful Linked Tickets/Backlinks/Gaps use case for a freestanding
idea); `knownGap`/`openQuestion` are *also* excluded from this
generic block, per proposal.md's Out-of-scope §3 — their one
relationship is fixed at creation, no generic link management needed
on their own detail screen (see §4.3 below for what they show
instead).

For every ticket that *isn't* excluded (`epic`/`story`/`task`/`bug`/
`resource`/`page`), add `GapsAndOpenQuestionsSection` (§6.1) directly
below the existing `LinkedTicketsSection`/`BacklinksSection` pair,
reading `state.gapsAndOpenQuestions`, its own "+ Add" trailing control
wired to the creation popover (§6.2) which calls
`TicketsCubit.createGapOrQuestion(type, title: ..., description: ...,
targetTicketId: ticket.id)`.

### 4.2 `page_detail_screen.dart`

Same addition, same `state.gapsAndOpenQuestions` source (shared
`loadDocumentRelations` call already covers `page`) — placed after the
existing `LinkedTicketsSection`/`BacklinksSection` pair, matching
`ticket_metadata_section.dart`'s placement.

### 4.3 A `knownGap`/`openQuestion` ticket's own detail screen

These types are excluded from the generic Documentation-mode block
(§4.1), so they need a minimal, read-only substitute showing what
they're raised on — not a full Linked Tickets section, since the
relationship is fixed at creation and never re-pointed. Add a small,
non-interactive header element (below the type chip, above the
description) reading "Raised on: `<target ticket key + title>`",
tappable to navigate to the target — sourced from the same
`relatesTo` link `loadDocumentRelations` would find if these types
weren't gated out of it, so this needs its own tiny lookup: extend the
gate in §4.1 to *compute* (but not render the generic sections for)
`knownGap`/`openQuestion`'s single outgoing `relatesTo` link, or add a
narrow `TicketsCubit.getRaisedOnTicket(String gapOrQuestionId)`
query method. Exact widget placement/visual treatment is Design Gate
work (`proposal.md`'s components list).

reasoning for keeping a parsed-markdown convention. New assembly:

```dart
Future<String> _assembleWhatNextContext() async {
  final all = await _ticketRepository.getAllTickets();

  final inFlight = /* unchanged */;

  final gapsAndQuestions = all.where(
    (t) => t.type == TicketType.knownGap || t.type == TicketType.openQuestion,
  ).toList();

  final openIdeas = <Ticket>[];
  for (final idea in all.where((t) => t.type == TicketType.idea)) {
    final links = await _linkRepository.getLinksForTicket(idea.id);
    final promoted = links.any((l) =>
        l.sourceTicketId == idea.id &&
        l.linkType == TicketLinkType.relatesTo.name);
    if (!promoted) openIdeas.add(idea);
  }

  // priority order in the prompt: (1) in-flight SDD-stage work,
  // (2) open known-gap/open-question tickets, (3) open, not-yet-
  // promoted idea tickets. Same advisory-prose-only contract as today.
}
```

Each `gapsAndQuestions` entry is rendered with its target (via
`getLinksForTicket(gap.id)`, resolving the single `relatesTo` row —
mirrors §4.3's lookup) so the model's recommendation can name which
ticket a gap concerns, not just the gap's own title.

# Aion — `idea`, `known gap` & `open question` Ticket Types: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and the [`signal` & `release` Types Spec](./Aion%20Signal%20and%20Release%20Types%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TypeChip`, `TicketOverflowMenu`, and the existing Linked-Tickets / Backlinks detail sections by name.

This change retires the single `TicketType.signal` and replaces it with three types:

- **`idea`** — inherits `signal`'s behaviour exactly: freestanding, no required target, promotable into an Epic or a Bug. The `typeSignal` accent is carried forward unchanged as **`typeIdea`** (§1.3).
- **`knownGap`** and **`openQuestion`** — never freestanding. Each is created already linked to a **target** ticket, only from that target's detail screen via the new **Gaps & Open Questions** section (§2). That section recursively rolls up every known-gap / open-question raised anywhere in a ticket's subtree, tagging each with the specific ticket it was raised on.

A misclassified (or pre-migration) `idea` can be reclassified into a `knownGap` / `openQuestion` from the ticket overflow menu (§4).

**No Material widgets anywhere.** Every surface below is built from `DecoratedBox`, `Padding`, `Row`/`Column`, `GestureDetector`, `MouseRegion`, `AnimatedContainer`, `AnimatedScale`, `Overlay`/`OverlayEntry`, `CompositedTransformFollower`/`LayerLink`, `Positioned`, `Focus`, `EditableText`/`TextField`-free `EditableText`, `CustomPaint`. No `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`/`ColorScheme`, `InkWell`/`Material` ripple, `AlertDialog`, `ListTile`, `PopupMenuButton`, or `DropdownButton`.

Themes: **Arctic** (light) and **Obsidian** (dark). All layout, dimensions, spacing, radius and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are `token.withOpacity(x)` with the theme `fillAlpha` (Arctic `0.11`, Obsidian `0.16`), never hardcoded ARGB.

## 1. New color tokens

### 1.1 `typeKnownGap` — grass green

Semantic: a *known gap* is an acknowledged hole in a ticket's coverage — a spot in the plan to be filled. Its hue sits in the single widest open interval on the type wheel, between `typeBug` (olive / yellow-green) and `typeStory` (emerald). It is deliberately **yellower and warmer than the emerald** used for `typeStory` / `success` / the "Done" status dot (~32° of hue separation in both themes), so a green *square* type-swatch is never confused with the green *circular* Done indicator.

| | Arctic | Obsidian |
|---|---|---|
| `typeKnownGap` | `Color(0xFF2F9E3F)` | `Color(0xFF54C85C)` |

### 1.2 `typeOpenQuestion` — rose magenta

Semantic: an *open question* is a raised, unresolved point. It is the **cool mirror of `typeRelease`**: where `typeRelease` sits just *warm* of `danger` (more orange), `typeOpenQuestion` sits just *cool* of it (more magenta), and clearly redder / warmer than `typePage`'s cool magenta. It reads as attention-worthy but is distinguished from the destructive `danger` rose by temperature exactly as `typeRelease` is — never used for errors or destructive actions.

| | Arctic | Obsidian |
|---|---|---|
| `typeOpenQuestion` | `Color(0xFFC6397D)` | `Color(0xFFEE72AE)` |

### 1.3 `typeSignal` → `typeIdea` rename (values carried forward)

The rename is **value-preserving**: `typeIdea` takes `typeSignal`'s exact hex. Nothing that currently reads `typeSignal` changes color — including the **`CodebaseAnalysisBanner`** identity accent, which continues to render the same deep cyan. Only the field/getter name changes.

| | Arctic | Obsidian |
|---|---|---|
| `typeIdea` *(was `typeSignal`)* | `Color(0xFF0E8C9E)` | `Color(0xFF34C6D6)` |

### 1.6 `TicketType` resolver + labels

The single point of extension. No widget hardcodes a color or label.

```dart
enum TicketType { epic, story, task, resource, page, idea, knownGap, openQuestion, release, chat, bug }

Color typeColorFor(TicketType type, AionColors c) {
  switch (type) {
    case TicketType.epic:         return c.typeEpic;
    case TicketType.story:        return c.typeStory;
    case TicketType.task:         return c.typeTask;
    case TicketType.resource:     return c.typeResource;
    case TicketType.page:         return c.typePage;
    case TicketType.idea:         return c.typeIdea;          // was signal
    case TicketType.knownGap:     return c.typeKnownGap;      // new
    case TicketType.openQuestion: return c.typeOpenQuestion;  // new
    case TicketType.release:      return c.typeRelease;
    case TicketType.chat:         return c.typeChat;
    case TicketType.bug:          return c.typeBug;
  }
}

String typeLabelFor(TicketType type) {
  switch (type) {
    case TicketType.idea:         return 'IDEA';
    case TicketType.knownGap:     return 'KNOWN GAP';
    case TicketType.openQuestion: return 'OPEN QUESTION';
    default: return type.name.toUpperCase(); // 'EPIC', 'STORY', …
  }
}

// Sentence-case names for menus / indicators:
String typeNameFor(TicketType type) {
  switch (type) {
    case TicketType.knownGap:     return 'Known gap';
    case TicketType.openQuestion: return 'Open question';
    default: return type.name[0].toUpperCase() + type.name.substring(1);
  }
}
```

`knownGap` / `openQuestion` **do not** appear in `CreateTicketScreen`'s Type dropdown — they can only be raised against a target (§2, §4). `idea` **replaces `signal`** in that dropdown's option list; all other dropdown behaviour is unchanged from the `signal`/`release` spec §3.

## 2. `GapsAndOpenQuestionsSection`

A read-only rollup section embedded on every Documentation-capable ticket's detail screen (Epic, Story, Task, Bug, Resource, Page), a **visual sibling** of the existing Linked Tickets / Backlinks blocks: same top-bordered block treatment, same header rhythm. Built as a `Column`; each row a `GestureDetector` → `AnimatedContainer` → `Row`.

### 2.1 Section container

| Property | Value |
|---|---|
| Top border | `1px solid border` (`#D6E0EA / #232C40`) — same divider as sibling sections |
| Padding | `EdgeInsets.fromLTRB(20, 14, 20, 12)` |
| Fill | inherits screen `background` (no own fill) |
| Layout | `Column`, `crossAxisAlignment: stretch` |

### 2.2 Header row

`Row`, `crossAxisAlignment: center`, gap `8`; `EdgeInsets.only(bottom: 10)`.

- **Label:** `"GAPS & OPEN QUESTIONS"`, `AionText.caption` (JetBrains Mono 11 / w600 / ls 1.54), color `textMuted` (`#8496A6 / #6B7690`), pre-uppercased.
- **Count pill:** the total rolled-up count (own + descendants). `AionText.key` (Mono 11 / w600), color `textSecondary`, fill `surfaceHover`, `EdgeInsets.symmetric(horizontal: 6, vertical: 1)`, radius `AionRadius.sm` (`5–6`). Omitted when count is `0` (empty state, §2.5).
- **`+ Add` control:** pushed right (`Spacer`). Text `"+ Add"`, `AionText.cardTitle`-size (13) / w700, color `primary` (`#2E86D4 / #9366FF`). Tap target `≥44px` high via padding `EdgeInsets.symmetric(horizontal: 6, vertical: 6)`, radius `AionRadius.sm`. Opens the popover (§3), anchored to this control's `LayerLink`.
  - **+Add states:** default — `primary` text, transparent fill. Hover — fill `primary.withOpacity(fillAlpha)`. Pressed — fill `primary.withOpacity(fillAlpha * 1.6)`; `AnimatedScale` `0.97`. Focused — fill `primary.withOpacity(fillAlpha)` + focus ring `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), spreadRadius: 3, blurRadius: 0)`. Disabled (never, on this control) — n/a.

### 2.3 Row (one per known-gap / open-question)

Read-only navigable row. Container: fill `surface`, `1px solid border`, radius `AionRadius.md` (10), rows stacked in a `Column` with `gap: 8`. Per-row padding `EdgeInsets.fromLTRB(12, 10, 10, 10)`. `Row`, `crossAxisAlignment: center`, gap `10`.

- **Type dot (leading):** solid `DecoratedBox`, `10 × 10`, `BorderRadius.circular(3)` (rounded square — deliberately not a circle, to separate it from the circular status dot), color `typeColorFor(item.type, c)` — `typeKnownGap` green or `typeOpenQuestion` magenta. `flex: 0 0 auto`.
- **Key badge:** the item's mono key, `AionText.key`, color `textSecondary`, fill `surfaceHover`, `EdgeInsets.symmetric(horizontal: 6, vertical: 2)`, radius `AionRadius.sm`. `flex: 0 0 auto`.
- **Title + subtitle (`Expanded`, `Column`, gap `2`):**
  - **Title:** `AionText.cardTitle` (14 / w600), `textPrimary`, `maxLines: 1`, `TextOverflow.ellipsis`.
  - **Subtitle:** `AionText.bodySm` rendered at `11.5`, color `textMuted`, `maxLines: 1`, ellipsis. Always present, composed as:
    - **Directly raised on this ticket:** the type name only — `"Known gap"` or `"Open question"`.
    - **Rolled up from a descendant** (§2.4): the type name + a leading corner glyph + source — e.g. `"↳ Open question · on Saved filter sets"` (`typeNameFor` + `"· on "` + descendant title). The `↳` (`0x21B3`) and `on ‹title›` are drawn in the same `textMuted`; the descendant title truncates with the line.
- **Trailing chevron:** `caret-right` (`›`), 16px, color `textMuted`, `flex: 0 0 auto`. Signals navigation to the item's own detail.

**No remove / edit affordance** — the row is read-only. The only way to remove an entry is to delete the underlying ticket elsewhere.

### 2.4 Rollup annotation

An entry is *rolled up* when its target ticket is a strict descendant of the currently-viewed ticket (e.g. an Epic showing a gap raised on one of its Stories/Tasks). Directly-raised entries (target == current ticket) omit the `↳ … · on …` clause and show only the type name. Ordering within the list: **directly-raised first, then rolled-up**, each group in descending `createdAt`. No sub-grouping headers.

### 2.5 Empty state

When the rollup count is `0`: keep the header label + `+ Add` (drop the count pill), and render a single quiet placeholder block in place of the rows.

| Property | Value |
|---|---|
| Container | fill `surface`, `1px solid border`, radius `AionRadius.md` (10), `EdgeInsets.symmetric(horizontal: 14, vertical: 18)` |
| Layout | `Column`, `crossAxisAlignment: start`, gap `4` |
| Line 1 | `"No gaps or open questions."` — `AionText.bodySm` (13.5), color `textSecondary` |
| Line 2 | `"Use + Add to note a gap or open question against this ticket."` — `AionText.bodySm` (12.5), color `textMuted` |

No illustration — this is a metadata block, not a screen-level empty state.

### 2.6 States

`GapsAndOpenQuestionsSection` rows are navigable; the section chrome is static.

| Element | Default | Hover | Focused | Pressed | Disabled | Error |
|---|---|---|---|---|---|---|
| Row | fill `surface`, `1px border` | fill `surfaceHover`, border `borderStrong` | fill `surfaceHover` + focus ring (`primary` @ ring α, spread 3) | `AnimatedScale` `0.99`, fill `surfaceHover` | n/a | n/a |
| `+ Add` | see §2.2 | §2.2 | §2.2 | §2.2 | n/a | n/a |
| Section | static (label + count pill) | — | — | — | — | — |

`Overlay`-anchored (never a screen navigation), opened from the section's `+ Add` (§2.2). A `CompositedTransformFollower` bound to the `+ Add` `LayerLink`, offset `(0, 6)`, right-aligned to the trigger's right edge (grows down-left). Two steps share one panel; the panel `AnimatedSize`s between them.

### 3.1 Panel

| Property | Value |

Panel padding `EdgeInsets.symmetric(vertical: 6)`; a `Column` of two item rows.

**Item row** — `GestureDetector` → `MouseRegion` → `AnimatedContainer` → `Row`, gap `11`, `EdgeInsets.symmetric(horizontal: 13, vertical: 10)`.
- **Leading dot:** `10 × 10`, radius `3`, color `typeKnownGap` (row 1) / `typeOpenQuestion` (row 2).
- **Text (`Expanded`, `Column`, gap `1`):**
  - Title: `"Raise a known gap"` / `"Raise an open question"` — `AionText.bodySm` rendered `14` / w600, `textPrimary`.
  - Sub: `"An acknowledged hole in this ticket"` / `"An unresolved point on this ticket"` — `AionText.bodySm` `11.5`, `textMuted`.

| Item state | Fill | Extra |
|---|---|---|
| Default | `transparent` | — |
| Hover | `surfaceHover` (`#E4EDF6 / #1C2436`) | `MouseRegion` click cursor |

### 3.3 Step 2 — compact form

Panel content swaps (Step 1 rows out, form in) under `AnimatedSize`. Padding `EdgeInsets.fromLTRB(14, 12, 14, 14)`; `Column`, `crossAxisAlignment: stretch`, gap `12`.

## 6. Data-model & behaviour notes (design-relevant)

- **`idea`** — freestanding; `target` is `null`; appears in the Create dropdown (replacing `signal`); promotable (Epic / Bug) and reclassifiable (§4).
- **`knownGap` / `openQuestion`** — `target` is **required and non-null** at creation; created only via §3 (from the target's Gaps section) or via §4 reclassify. Absent from the Create dropdown. Their own detail screen shows the §5 indicator, never Linked Tickets / Backlinks.
- **Rollup** (§2.4) is computed over the target's descendant subtree; a single ticket appears once, on the nearest ancestor's section for its whole ancestry chain (an Epic sees gaps raised on its Stories and their Tasks).
- **Migration:** existing `signal` tickets become `idea` with identical behaviour and the same (renamed) accent — no visual change; the `CodebaseAnalysisBanner` accent is unaffected (§1.3).

## 8. Token / type / spacing summary

- **New colors (2):** `typeKnownGap` (`#2F9E3F / #54C85C`), `typeOpenQuestion` (`#C6397D / #EE72AE`) — §1. Chip / dot / wash fills derive via `.withOpacity(fillAlpha)`.
- **Renamed (1):** `typeSignal` → `typeIdea`, values unchanged (`#0E8C9E / #34C6D6`) — §1.3. `CodebaseAnalysisBanner` accent unaffected.
- **No new typography:** `AionText.caption` (section labels / eyebrow), `AionText.key` (keys / count pill), `AionText.cardTitle` (row titles / labels), `AionText.bodySm` (subtitles / fields), `AionText.label` (field / form labels), `AionText.dialogTitle` (picker title), `AionText.button` (actions) — all existing.
- **No new radius:** dot / square `3`; key pill / chip `AionRadius.sm` (`5–6`); row / field / button / menu-item `AionRadius.md` (`10`); panel / picker `AionRadius.lg` (`12`); back button `AionRadius.iconBtnSm` (`8`).
- **No new spacing:** all gaps / paddings are 4-multiples given as explicit `EdgeInsets`; field-label gap `6`, form stack gap `12`, section header gap `8`.
- **No new widgets beyond `GapsAndOpenQuestionsSection`, `RaiseGapOrQuestionPicker`, and the "Raised on" indicator; no new screens** — the menu rows extend `TicketOverflowMenu`, the target picker reuses the existing searchable ticket picker.
- Translucent fills (dot / chip tints, hover / pressed washes, focus / error rings, overlay shadow) via `token.withOpacity(x)`, never hardcoded ARGB. **No Material widgets anywhere** (§0).
