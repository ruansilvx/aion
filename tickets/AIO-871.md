# Design: dont-spawn-new-chat-ticket-per-execution-trigger

## §1. `AgentDoneEvent` gains usage fields

`core/contracts/agent_model_client.dart`:

```dart
class AgentDoneEvent extends AgentEvent {
  const AgentDoneEvent({this.inputTokens, this.outputTokens});

  /// Input tokens the SDK reported for this turn, or `null` if the
  /// bridge process didn't report usage (should not happen in practice,
  /// but `_parseLine` treats a missing field as `null` rather than
  /// throwing).
  final int? inputTokens;

  /// Output tokens the SDK reported for this turn. See [inputTokens].
  final int? outputTokens;

  @override
  List<Object?> get props => [inputTokens, outputTokens];
}
```

A field addition, not a new `AgentEvent` variant — usage is a property of
the *terminal* event, known only once the turn actually finishes, exactly
like the existing `AgentOverageDetectedEvent` precedent of enriching an
existing signal rather than inventing a parallel one.

## §2. `agent_bridge/index.mjs` forwards real usage

Current `result`/`success` branch (index.mjs, in `main()`):

```js
} else if (message.type === 'result') {
  if (message.subtype === 'success') {
    emit({ type: 'done' });
  } else { ... }
}
```

Becomes:

```js
} else if (message.type === 'result') {
  if (message.subtype === 'success') {
    const usage = message.usage ?? {};
    emit({
      type: 'done',
      inputTokens: usage.input_tokens ?? null,
      outputTokens: usage.output_tokens ?? null,
    });
  } else { ... }
}
```

The Claude Agent SDK's `result` message carries a `usage` object
(`input_tokens`/`output_tokens`, alongside cache-related fields this
change doesn't need) on every terminal result, success or not — only the
success path is touched since only a successful turn's usage feeds the
running total (see §8: a hard-failed turn's comment is prefixed
`"Execution failed: ..."`, not counted toward the cap). Update the
file's top-of-file comment listing NDJSON shapes to show
`{"type":"done","inputTokens":123,"outputTokens":456}`.

## §6. `ExecutionContextCapRepository`

/// Persists a user-configurable override for the coding-execution

## §8. Shared execution-chat lookup

Extracted from the duplicated bodies of `_executionSucceededWithPr` and
`_computeExecutionFailure` (identical today except what each does with
the result):

```dart
/// The Task/Bug [taskId]'s current coding-execution chat — its most
/// recently created `"Coding Execution — "`-prefixed child. Covers a
/// `"(continued)"` handoff descendant (§10) automatically: it shares the
/// same prefix and is simply created later, so it naturally sorts first.
/// `null` if [taskId] has no execution chat yet.
Future<Ticket?> _mostRecentExecutionChat(String taskId) async {
  final chats = await _repository.getTicketsByParent(
    taskId,
    types: const [TicketType.chat],
  );
  final executionChats =
      chats.where((c) => c.title.startsWith('Coding Execution — ')).toList()
        ..sort((a, b) => b.createdAt.compareTo(a.createdAt));
  return executionChats.isEmpty ? null : executionChats.first;
}
```

`_executionSucceededWithPr`/`_computeExecutionFailure` are rewritten to
call this instead of repeating the query/filter/sort inline; their own
behavior (what they do with the returned chat) is unchanged.

## §9. Find-or-create + cap check

Replaces `_runCodingExecution`'s current unconditional
`Ticket(...); await _repository.createTicket(...)` block:

```dart
/// Resolves which chat [task]'s next implement/verify turn(s) post to:
/// its existing execution chat (§8), reused as-is; a handoff (§10) to a
/// new one if that chat has crossed [_handoffThresholdRatio] of its
/// effective cap (`_effectiveExecutionContextCap`); or a brand-new one
/// if [task] has no execution chat at all yet. Returns `(chat,
/// handoffSummary)` — `handoffSummary` is non-null only right after a
/// handoff just happened, for the caller to feed into
/// `_assembleExecutionContext`. `(null, null)` only when constructed
/// without an `AgentModelClient`/`CommentRepository` (mirrors every
/// other chat-spawning path's guard) or a create write fails to
/// persist.
Future<(Ticket?, String?)> _resolveExecutionChat(Ticket task) async {
  final existing = await _mostRecentExecutionChat(task.id);
  if (existing == null) {
    final created = await _createExecutionChat(
      task,
      _executionChatTitle(task.title),
    );
    return (created, null);
  }
  if (!await _executionChatOverCap(existing)) {
    return (existing, null);
  }
  return _handoffExecutionChat(task, existing);
}

Future<Ticket?> _createExecutionChat(Ticket task, String title) async {
  final now = DateTime.now();
  final chat = Ticket(
    id: _uuid.v4(),
    ticketId: '',
    type: TicketType.chat,
    title: title,
    status: TicketStatus.backlog,
    parentId: task.id,
    createdAt: now,
    updatedAt: now,
  );
  await _repository.createTicket(chat);
  return _repository.getTicketById(chat.id);
}

/// `"Coding Execution — <taskTitle>"`, or a numbered `"(continued
/// N)"`-suffixed variant per [continuationIndex] (0 = the original,
/// unsuffixed; 1 = the first handoff, suffixed `"(continued)"` with no
/// number; 2+ = `"(continued 2)"`, `"(continued 3)"`, ...) — resolves
/// open question #3 from `dont-spawn-new-chat-ticket-per-execution-
/// trigger.md`: unlike a bare repeated `"(continued)"`, a third+
/// continuation stays distinguishable from the second.
String _executionChatTitle(String taskTitle, [int continuationIndex = 0]) {
  final base = 'Coding Execution — $taskTitle';
  if (continuationIndex <= 0) return base;
  return continuationIndex == 1
      ? '$base (continued)'
      : '$base (continued $continuationIndex)';
}

/// How many `"Coding Execution — "`-prefixed children [taskId] already
/// has — the next one's [_executionChatTitle] continuation index.
Future<int> _executionChatCount(String taskId) async {
  final chats = await _repository.getTicketsByParent(
    taskId,
    types: const [TicketType.chat],
  );
  return chats.where((c) => c.title.startsWith('Coding Execution — ')).length;
}

/// Whether [chat]'s accumulated token usage (every comment's
/// `inputTokens + outputTokens`, `0` for a comment with neither — a
/// human/system comment, or an ai comment predating this change) has
/// crossed [_handoffThresholdRatio] of `_effectiveExecutionContextCap`.
Future<bool> _executionChatOverCap(Ticket chat) async {
  final commentRepo = _commentRepository;
  if (commentRepo == null) return false;
  final comments = await commentRepo.getCommentsForTicket(chat.id);
  final used = comments.fold<int>(
    0,
    (sum, c) => sum + (c.inputTokens ?? 0) + (c.outputTokens ?? 0),
  );
  final cap = await _effectiveExecutionContextCap();
  return used >= cap * _handoffThresholdRatio;
}

/// The execution-phase model's real `contextWindowTokens`, lowered to
/// `_executionContextCapRepository`'s persisted override when one is set
/// and it's a smaller, positive value — an override can never raise the
/// cap past the model's real limit (`ExecutionContextCapCubit`/§12
/// enforce the same ceiling when persisting one, this is defense in
/// depth). Falls back to the model's real limit with no override
/// available when constructed without an `ExecutionContextCapRepository`
/// (§7).
Future<int> _effectiveExecutionContextCap() async {
  final model = await _resolveModel(ModelPhase.execution);
  final override = await _executionContextCapRepository
      ?.getContextCapOverride();
  if (override != null && override > 0 && override < model.contextWindowTokens) {
    return override;
  }
  return model.contextWindowTokens;
}
```

`_handoffThresholdRatio` is a new `TicketsCubit` constant, `0.9` — not
user-configurable (proposal.md's Out of scope); only the cap it's a
fraction of is.

## §10. Handoff

```dart
/// Retires [oldChat] and starts a new linked one for [task]: one
/// summary-only `ChatCubit.runChatTurn` on [oldChat] (no tools, no
/// `workingDirectory` — the worktree that turn's run owned is already
/// gone by the time a later trigger's [_resolveExecutionChat] call gets
/// here) asks the model to write a handoff summary from [oldChat]'s own
/// transcript, then a new chat is created (§9,
/// `_executionChatTitle`/`_executionChatCount` for its numbered title)
/// and linked back to [oldChat] via `TicketLinkType.relatesTo` — a human
/// can navigate between them via the existing generic "linked tickets"
/// UI, no new widget needed. Falls back to `(oldChat, null)` — reuse the
/// old, now-over-cap chat rather than block the run — if the summary
/// turn itself hard-fails, or if constructed without an
/// `AgentModelClient`/`CommentRepository`: a soft context-budget
/// overrun that risks a truncated next turn is preferable to a run that
/// can't proceed at all, matching this project's fail-open precedent
/// for `_computeExecutionFailure`'s "ended without a clear result"
/// stalled case.
///
/// The summary turn's own usage is recorded on [oldChat]'s total (it's
/// just another comment there) but can never trigger a second,
/// recursive handoff — [oldChat] is retired unconditionally once this
/// runs, regardless of that comment's size. Resolves open question #2
/// from `dont-spawn-new-chat-ticket-per-execution-trigger.md`.
Future<(Ticket?, String?)> _handoffExecutionChat(
  Ticket task,
  Ticket oldChat,
) async {
  final client = _agentClient;
  final commentRepo = _commentRepository;
  if (client == null || commentRepo == null) return (oldChat, null);

  final transcript = _assembleChatTranscript(
    await commentRepo.getCommentsForTicket(oldChat.id),
  );
  final summarized = await ChatCubit.runChatTurn(
    client: client,
    commentRepo: commentRepo,
    chatTicketId: oldChat.id,
    prompt: _assembleHandoffContext(transcript),
    model: await _resolveModel(ModelPhase.execution),
  );
  if (!summarized) return (oldChat, null);

  final summary = await _lastCommentContent(oldChat.id);
  final continuationIndex = await _executionChatCount(task.id);
  final newChat = await _createExecutionChat(
    task,
    _executionChatTitle(task.title, continuationIndex),
  );
  if (newChat == null) return (oldChat, null);

  final linkRepo = _linkRepository;
  if (linkRepo != null) {
    await linkRepo.createLink(
      sourceTicketId: newChat.id,
      targetTicketId: oldChat.id,
      linkType: TicketLinkType.relatesTo,
    );
  }
  return (newChat, summary);
}

/// Renders [comments] (a chat's full history, oldest first — matches
/// `CommentRepository.getCommentsForTicket`'s own ordering) as a plain
/// transcript for the handoff-summary prompt: one `[authorType]` line
/// per comment followed by its content, blank-line separated.
String _assembleChatTranscript(List<TicketComment> comments) {
  final buffer = StringBuffer();
  for (final comment in comments) {
    buffer
      ..writeln('[${comment.authorType.name}]')
      ..writeln(comment.content)
      ..writeln();
  }
  return buffer.toString().trim();
}

/// The handoff-summary turn's prompt: [transcript] plus an instruction
/// to summarize what's done/left/decided for whoever picks this Task up
/// next in a new chat, explicitly told not to use any tools — there is
/// no worktree for this turn to act in (see [_handoffExecutionChat]'s
/// dartdoc).
String _assembleHandoffContext(String transcript) {
  return 'This coding-execution chat is nearing its model context '
      'limit, and a new chat will continue this Task\'s work from here. '
      'Write a handoff summary for whoever picks it up next: what has '
      'been done, what is left, and any key decisions or gotchas '
      'discovered so far. Do not use any tools — reply with the summary '
      'only.\n\n'
      '--- Transcript so far ---\n\n$transcript';
}
```

class ExecutionContextCapLoading extends ExecutionContextCapState { ... }

/// [overrideTokens] is the persisted override (`null` = none).
/// [modelDefaultTokens] is the execution-phase model's real

New `execution_context_cap_cubit.dart`:

```dart
class ExecutionContextCapCubit extends Cubit<ExecutionContextCapState> {
  ExecutionContextCapCubit(this._capRepository, this._modelRoutingRepository)
      : super(const ExecutionContextCapLoading());

  final ExecutionContextCapRepository _capRepository;
  final ModelRoutingRepository _modelRoutingRepository;

  Future<void> load() async {
    final override = await _capRepository.getContextCapOverride();
    final model = await _modelRoutingRepository.getModelForPhase(ModelPhase.execution);
    if (isClosed) return;
    emit(ExecutionContextCapReady(
      overrideTokens: override,
      modelDefaultTokens: model.contextWindowTokens,
    ));
  }

  /// Persists [tokens] as the override, clamped to at most one below the
  /// current execution model's real `contextWindowTokens` (an override
  /// can lower the cap, never raise or match it past the real limit) and
  /// at least `1`; `null`/`<= 0` clears the override entirely.
  Future<void> setOverride(int? tokens) async {
    final current = state;
    final ceiling = current is ExecutionContextCapReady
        ? current.modelDefaultTokens
        : (await _modelRoutingRepository.getModelForPhase(ModelPhase.execution))
            .contextWindowTokens;
    final clamped = (tokens == null || tokens <= 0)
        ? null
        : tokens.clamp(1, ceiling - 1);
    await _capRepository.setContextCapOverride(clamped);
    if (isClosed) return;
    emit(ExecutionContextCapReady(
      overrideTokens: clamped,
      modelDefaultTokens: ceiling,
    ));
  }
}
```

One cubit per concern (matches `ModelRoutingCubit`/
`AutomationSettingsCubit`'s existing split, per each one's own dartdoc)
rather than folding this into either.

## Sequence — a Task that needs a handoff mid-lifecycle

1. Task moves to `inProgress` (1st trigger). `_resolveExecutionChat`
   finds no existing execution chat → creates `"Coding Execution — Fix
   the thing"`. Implement/verify turns run; verification fails; a
   `"gated"` failure comment is posted. Task stays `inProgress`.
2. User clicks Retry (`retryCodingExecution`, 2nd trigger).
   `_resolveExecutionChat` finds the same chat, sums its comments'
   usage — say 40% of the cap — well under `_handoffThresholdRatio`, so
   it's reused as-is. Another implement/verify cycle runs, appending
   more comments to the same chat. Say this pushes the running total to
   93%.
3. Verification fails again; user clicks Retry (3rd trigger).
   `_resolveExecutionChat` finds the same chat, computes 93% ≥ 90% →
   `_handoffExecutionChat` runs: one summary turn posts a handoff
   summary as the chat's last comment; a new chat `"Coding Execution —
   Fix the thing (continued)"` is created and linked back via
   `relatesTo`. `_assembleExecutionContext` opens the new chat's first
   comment with that summary. The implement/verify cycle proceeds on
   the new chat.
4. This time verification passes; Aion pushes and opens the PR, posting
   `EXECUTION: PR_OPENED <url>` as the new chat's latest comment.
   `_executionSucceededWithPr`/`_computeExecutionFailure` (§8) both
   resolve correctly against the new chat with no code change of their
   own, since it's still the *most recently created*
   `"Coding Execution — "`-prefixed child of the Task.

# Aion — Execution Context Cap: Settings Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Per-Phase-Tier Model Routing Spec](./Aion%20Per-Phase%20Model%20Routing%20Spec.md) (whose `SettingsScreen`, `"MODELS"` group, and `_ModelPhaseSection` this change sits inside), and the [Coding-Execution Reliability Spec](./Aion%20Coding%20Execution%20Reliability%20Spec.md) (whose token-handoff mechanism this field configures). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AppTextField`, and `_ModelPhaseSection` by name.

This adds the **one user-facing surface** of coding-execution's context-window handoff: a new row on the existing `SettingsScreen` letting the user optionally lower the token cap that decides when a coding-execution chat hands off to a continuation chat. No new screen, no new navigation — a single component, **`ExecutionContextCapField`** (§2), inserted as the **fourth row of the existing "MODELS" group**, directly below the "Execution Model" row (Routing Spec §4).

Mockups: [Aion Execution Context Cap Mockups](./Aion%20Execution%20Context%20Cap%20Mockups.dc.html) — full Settings screen (no override / override) in 1a, full screen (focused / clamped) in 1b, and the field's four-state anatomy in 1c.

**No Material widgets or types anywhere.** The label, description, and helper rows are `Text` / `Row` / `Column` / `Padding` / `DecoratedBox`; the input is the existing **`AppTextField`** atom (`design_system/atoms/app_text_field.dart`) — Aion's single sanctioned `TextField` wrapper, fully re-skinned with token colors — reused unchanged, **not** a new field primitive. No `ThemeData`, `ColorScheme`, `Scaffold`, `Card`, `ElevatedButton`, `TextFormField`, `InputDecoration`, `ListTile`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is quoted `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` — never hardcoded ARGB.

**New tokens:** none for color/typography/radius/spacing. Two **derived tint helpers** on `AionColorsHubTokens` (`warningTint` / `warningBorderTint`, §5) — added only because no warning-family tint helper exists yet, mirroring the existing `dangerTint`/`dangerBorderTint` shape (Reliability Spec §4) exactly. One structural addition: the `ExecutionContextCap` value model + clamp rule (§6).

## 2. `ExecutionContextCapField` (new)

A labeled numeric-override field plus a dynamic helper line. Its **label + description block is byte-identical in geometry to `_ModelPhaseSection`** (Routing §2.2) so it reads as one more MODELS row; its control is the reused `AppTextField` atom; its helper line is a new one-line status row below the field.

### 2.1 Widget contract

```dart
class ExecutionContextCapField extends StatefulWidget {
  final int modelRealLimit;          // the execution model's real context-window limit, e.g. 200000
  final int? overrideValue;          // persisted override; null == no override (use real limit)
  final ValueChanged<int?> onChanged;// commits a parsed override, or null when cleared
  const ExecutionContextCapField({
    required this.modelRealLimit,
    required this.overrideValue,
    required this.onChanged,
  });
}
```

`State` owns a `TextEditingController` (seeded from `overrideValue?.toString() ?? ''`) and a `FocusNode`; the helper-row variant (§2.4) is derived per build from the live controller text + `modelRealLimit` (§6), never stored.

### 2.2 Block structure & internal spacing

`Column`, `crossAxisAlignment: stretch`, four children:

| # | Element | Style | Color | Gap below |
|---|---|---|---|---|
| 1 | **Label** — `"Execution Context Cap"` | `AionText.label` (Manrope 12 / w700) | `textSecondary` (`#46586A / #A2AEC6`) | `6` |
| 2 | **Description** (§2.3) | `AionText.bodySm` (Manrope 13.5 / w400), `height: 1.5`, wraps | `textMuted` (`#8496A6 / #6B7690`) | `10` |
| 3 | **`AppTextField`** (§2.5) | reused atom, full-width | — | `8` (neutral/override helper) · `6` (clamped chip) |
| 4 | **Helper row** (§2.4) | per-state | per-state | — |

**Parity note (label + description color).** The brief proposed `label` / `bodySm` with the description in `textSecondary`. This spec renders the label in `textSecondary` and the **description in `textMuted`** to be **byte-identical to the `_ModelPhaseSection` rows immediately above it** (Routing §2.2 — label `textSecondary` 6-gap, description `textMuted` `height 1.5` 10-gap). A field inserted mid-group must match its siblings exactly; a one-notch-darker description would read as a different component. Label/description gaps (`6`, `10`) are inherited from `_ModelPhaseSection` verbatim.

No fill, border, radius, or padding box on the block itself — it sits flush in the "MODELS" body `Column`, exactly like `_ModelPhaseSection`.

### 2.3 Description copy

> `"Overrides when a coding-execution chat hands off to a new one. Leave blank to use the execution model's real limit."`

One line of intent; it does **not** mention tokens, continuation chats, or the reliability mechanism (the only user-facing surface of that mechanism is this field — Reliability Spec §0 context).

### 2.4 Helper row — the dynamic effective-cap line (three variants)

A single-line status row directly below the field, `8` below it (neutral/override) or `6` below (clamped chip). Exactly one variant renders per build, chosen by §6. It is the field's **sole feedback channel** — `AppTextField` has no error/helper prop (§2.5), so all "what is in force" and "this will be clamped" messaging lives here, never on the field.

Number formatting: grouped with `,` thousands separators via the app's existing `NumberFormat.decimalPattern()` helper (e.g. `200000` → `"200,000"`). The word `"tokens"` always follows.

#### 2.4.1 Neutral — no override (default / focused-empty)

Plain text, no container. `Text.rich`:

- `"Effective cap: "` — `AionText.bodySm` rendered at `13`, `textMuted`.
- `"{realLimit} tokens"` (e.g. `"200,000 tokens"`) — same size, `textSecondary`, `fontWeight: w600` (the concrete number is the readable part).

#### 2.4.2 Override active — a valid override is set

A `Row`, `gap: 8`, `crossAxisAlignment: center`, `Wrap`-safe (wraps to a second line only at extreme text scale):

- **Effective text** — `Text.rich`: `"Effective cap: "` `bodySm` `13` `textMuted` + `"{override} tokens"` (e.g. `"50,000 tokens"`) `textPrimary` (`#142230 / #E7EDF7`) `w700`.
- **`OVERRIDE` tag** — a small tonal pill distinguishing this from the neutral state:
  - Text `"OVERRIDE"`, `AionText.caption`-family mono rendered at `9.5`, `w600`, `letterSpacing: 1.2`, color `primary` (`#2E86D4 / #9366FF`).
  - Fill `primarySubtle` (`#DBE9F7 / #241F3E`); **no border**.
  - Padding `EdgeInsets.symmetric(horizontal: 7, vertical: 2)`; radius `AionRadius.pill` (22).

The tag (not a color change on the whole line) is the chosen "visually distinguished" treatment the brief asked for — it reads as a status chip in the app's existing pill vocabulary (matching the "Connected" provider chip) without recoloring the informational text.

#### 2.4.3 Clamped — entry at or above the model's real limit

A tonal **caution chip** (stronger than the override tag — this is corrective feedback, not a status). `DecoratedBox` → `Padding` → `Row`, `gap: 8`, `crossAxisAlignment: start`:

- **Container:** fill `warningTint(isDark)` (§5, `warning @ 0.12 / 0.18`); border `1px solid warningBorderTint(isDark)` (§5, `warning @ 0.30 / 0.42`); radius `AionRadius.sm` rounded to `8` (matches the nested-well radius convention, Reliability §1.4); padding `EdgeInsets.fromLTRB(10, 8, 10, 8)`; no shadow.
- **Leading badge:** a `14×14` `BoxShape.circle`, fill `warning` (`#B8912B / #D7B24E`), centering a `"!"` glyph `AionText.label`-family `10 / w800`, color `background` (`#EDF2F8 / #0A0E18`, so the mark reads as a knockout). `margin-top: 1` to align with the first text line. `flex: 0`.
- **Text:** `"Above the model's {realLimit} limit — will be clamped to {realLimit − 1} tokens."` (e.g. `"Above the model's 200,000 limit — will be clamped to 199,999 tokens."`), `AionText.bodySm` rendered at `12.5`, `height: 1.45`, color `warningText` (§5.1 — a legibility-boosted `warning` shade: `#7A5E12 / #E8CE7E`). `Expanded`, wraps to 2 lines as needed.

**Why `warning`, not `danger`:** the value is not invalid or destructive — it is silently accepted and clamped to a working value. `danger` would imply a blocking error / data loss; `warning` correctly reads as "accepted, but adjusted." The `danger` family stays reserved for true errors and destructive actions per the base palette.

### 2.5 Control — `AppTextField` (reused atom, not redesigned)

The existing `AppTextField` atom, configured for numeric override entry. Its visual treatment (fill, border, radius, focus ring, padding) is the atom's own re-skinned `TextField` and carries over **unchanged** — the same closed-field treatment every other Settings input and the `AppDropdown` field use.

## 5. New derived tint helpers (no new palette members)

Mirror the existing `dangerTint(isDark)` / `dangerBorderTint(isDark)` shape on `AionColorsHubTokens` exactly — `<baseColor>.withValues(alpha: isDark ? X : Y)`, never a hardcoded ARGB, never a stored palette color. Added only because the palette has no warning-family tint helper yet (the danger family already has one, Reliability §4):

```dart
// On AionColorsHubTokens — parallels dangerTint / dangerBorderTint.
Color warningTint(bool isDark)       => warning.withValues(alpha: isDark ? 0.18 : 0.12); // clamp chip fill (§2.4.3)
Color warningBorderTint(bool isDark) => warning.withValues(alpha: isDark ? 0.42 : 0.30); // clamp chip border (§2.4.3)
```

`warning` = `AionColors.warning` (`#B8912B / #D7B24E`). These are the caution-chip fill and border. Every other translucent value reuses an existing pattern (the field focus ring is the atom's own `primary.withOpacity(0.16 / 0.30)`).

### 5.1 One derived text shade (no new named style)

The clamp-chip text needs a `warning` shade that stays legible as body copy over the tinted chip (raw `warning` on the light chip is low-contrast). Use a **derived shade**, not a new palette token:

```dart
// Legibility-boosted warning for text on a warningTint chip — derived, not stored.
Color warningText(bool isDark) => isDark
    ? Color.lerp(warning, Colors.white, 0.30)!   // ≈ #E8CE7E — brighter for dark chip
    : Color.lerp(warning, Colors.black, 0.45)!;  // ≈ #7A5E12 — deeper for light chip
```

Applied via `AionText.bodySm.copyWith(color: warningText(isDark), fontSize: 12.5, height: 1.45)`. No new `AionText` member; the badge/tag styles are `label`/`caption`-family `copyWith` re-sizes.

## 6. Value model & clamp rule (no new design tokens)

```dart
/// The persisted execution-context-cap override for a project.
/// null  → no override; the effective cap is the execution model's real limit.
/// int   → the user's override (already clamped on commit, §6.1).
typedef ExecutionContextCapOverride = int?;

class ExecutionContextCap {
  final int modelRealLimit;                 // e.g. 200000
  final ExecutionContextCapOverride override;
  const ExecutionContextCap(this.modelRealLimit, this.override);

  bool  get hasOverride  => override != null;
  int   get effectiveCap => override ?? modelRealLimit;
}
```

### 6.1 Which helper variant renders (per build)

Let `text` = the live controller string, `n = int.tryParse(text)`, `limit = modelRealLimit`.

| Condition | Helper variant | Committed value (`onChanged`) |
|---|---|---|
| `text` empty | **Neutral** (§2.4.1), `effectiveCap = limit` | `null` |
| `n != null && n >= 1 && n < limit` | **Override** (§2.4.2), `effectiveCap = n` | `n` |
| `n != null && n >= limit` | **Clamped chip** (§2.4.3); on commit the value is clamped | `limit - 1` |

- **Clamp:** a value `≥ limit` is accepted and stored as `limit - 1` ("just under the real limit," per brief §1.2) on commit (`onSubmitted` / focus-loss). While the user is still typing an over-limit value the chip is shown live; the actual clamp happens on commit, and the field then re-renders showing the clamped value with the **Override** helper.
- `0` and empty are equivalent to "no override" (neutral). Non-digit input is impossible (`digitsOnly` formatter, §2.5.1).
- The mechanism is otherwise internal: nothing else about continuation-chat handoff is user-facing (Reliability §0).
