# Private Widget Retrofit

# Proposal: Private Widget Retrofit

## Summary

Retrofit every remaining `Widget _foo(...)` private helper-function build
split in `lib/` into a private widget class (`class _Foo extends
StatelessWidget`), per `flutter-conventions.md`'s Widget composition rule.
Add a durable grep-based check — mirroring the existing Non-Material `T26`
check — so this pattern can't silently creep back in on future slices.

## Motivation

`aion-arch/specs/README.md`'s "Known gaps" flags that most build methods
written before the Widget composition rule was established still split
into private `Widget _foo(...)` helper functions instead of private widget
classes. Widget-returning functions don't get their own `Element`, so
Flutter can't skip rebuilding them independently of their parent, and they
can't hold their own state (hover/focus/animation) without hoisting it
back up into the enclosing `State` — exactly the class of bug the
`AppDropdown` overlay-dismiss dispose-crash (documented in `project.md`'s
Testing section) came from. Closing this gap now, while the codebase is
still one feature slice (~50 Dart files), is cheaper than doing it
incrementally later once more screens exist.

  (`_buildAvatar`)
- `lib/features/tickets/presentation/widgets/ticket_parent_picker.dart` — 2
  (`_buildInlineTrigger`, `_buildFormFieldTrigger`)
- `lib/features/projects/presentation/widgets/project_card.dart` — 5
  (`_overflowRow`, `_titleRow`, `_locationRow`, `_metaRow`, `_openButton`)
- `lib/features/projects/presentation/widgets/empty_hub_state.dart` — 2
  (`_emblem`, `_newProjectCta`)
- `lib/features/projects/presentation/screens/new_project_screen.dart` — 6
  (`_form`, `_directoryPicker`, `_noDirectoryNotice`,
  `_baselineVersionField`, `_footer`, `_inlineError`)
- `lib/features/projects/presentation/screens/hub_screen.dart` — 4
  (`_header`, `_body`, `_grid`, `_error`)
- `lib/design_system/molecules/app_confirm_dialog.dart` — 5
  (`_leadingIcon`, `_cancelButton`, `_confirmButton`, `_wideActions`,
  `_narrowActions`)
- `lib/design_system/atoms/app_button.dart` — 2
  (`_buildDecoratedContent`, `_label`)

Newer screens/widgets (`tickets_board_view.dart`, `ticket_overflow_menu.dart`,
`app_dropdown.dart`, `trashed_ticket_tile.dart`) already follow the rule —
the drift is concentrated in files written during or before the v1 slice.

Two of the nine files are shared `design_system/` primitives (`AppButton`,
`AppConfirmDialog`) consumed by nearly every screen in the app, so their
conversion has outsized reach even though it's only 7 of the 28 helpers.

There is currently no automated enforcement of the Widget composition rule
— it's checked by convention/review only, the same way the Non-Material
constraint was before `T26`'s grep checks were added to the v1 slice's
`tasks.md`.

## Scope

**In scope:**

- Convert all 28 `Widget _foo(...)` helpers listed above into private
  widget classes (`_PascalCase extends StatelessWidget`), preserving
  identical rendered output, layout, and behavior — pure structural
  refactor, no visual or functional change.
- Add a canonical grep check for this rule to `flutter-conventions.md`'s
  Widget composition section (mirroring the existing Non-Material
  constraint's documented grep checks), and a corresponding final
  verification task in this change's own `tasks.md`, establishing the
  pattern future `tasks.md` files should copy (the same way `T26` already
  gets copied forward for Non-Material checks).
- Update `aion-arch/specs/README.md` to remove the now-closed "Known gap"
  bullet once every file is retrofitted.

**Explicitly out of scope (deferred, not silently dropped):**

- Relocating hover/focus/press interaction *state itself* (e.g.
  `ticket_parent_picker.dart`'s `_isHovered`/`_isFocused`/`_isOpen`,
  `app_button.dart`'s pressed/hover state) down into the new private
  widget classes. This retrofit passes each helper's currently-tracked
  state values in as constructor fields and keeps ownership exactly where
  it already lives (the enclosing `State`) — it does not change *who*
  manages interaction state, only how the resulting widget tree is built.
  Moving state ownership down is a legitimate follow-up (it's the piece
  that would let Flutter skip rebuilding a hovered row's siblings, for
  instance) but it's a behavioral change with its own dispose/lifecycle
  risk (see the `AppDropdown` precedent), not a mechanical widget-class
  extraction — capture it as a new idea if wanted.
- Introducing a real CI/lint gate (custom `analyzer` plugin or a
  pre-commit hook). This project has no CI pipeline and is solo-maintained
  — a documented, copy-forward grep check consistent with the existing
  `T26` pattern is the right-sized enforcement, not new tooling infra.
- Any non-`Widget`-returning private helper methods (e.g. `app_button.dart`'s
  `_fillColor`, `_padding`, `_textColor`, `_border`, `_shadow`). The rule
  in `flutter-conventions.md` is specifically about functions that return
  `Widget`; these return `Color`/`EdgeInsets`/etc. and are unaffected.

## Risks

- **Derived-value helpers that call sibling non-`Widget` methods.**
  `app_button.dart`'s `_buildDecoratedContent` currently calls
  `_fillColor()`/`_textColor()`/`_border()`/`_shadow()` (other instance
  methods on `_AppButtonState`) to compute its inputs. Once
  `_buildDecoratedContent` becomes a private widget class, it can no
  longer reach those sibling methods. Resolution: hoist those calls to the
  construction call site (still inside `_AppButtonState.build()`, which
  keeps access to them) and pass the computed `Color`/`EdgeInsets`/etc.
  values in as constructor fields on the new widget — see `design.md`.
- **Implicit `widget.foo` / state-field references.** Several helpers
  (`app_button.dart`'s `_label` reading `widget.label`;
  `ticket_parent_picker.dart`'s triggers reading `widget.currentParentId`,
  `_isOpen`, `_isFocused`, `_isHovered`) currently read the enclosing
  `State`'s fields directly. Every such reference must become an explicit
  constructor field on the new widget class — missing one is a compile
  error, not a silent runtime bug, so this is a low-risk mechanical
  refactor as long as `flutter analyze` is run per file.
- **Regression risk is UI-only, not logic-only**, given `AppButton` and
  `AppConfirmDialog` are consumed almost everywhere. A single consolidated
  manual interactive pass in real Chrome (per `project.md`'s Testing
  section) across every screen that renders a button, dialog, or the two
  affected project/ticket screens is required before this change is
  considered done — `flutter analyze`/`flutter test` passing is not
  sufficient on its own for this kind of change (same reasoning as the
  `AppDropdown` precedent).

## Design gate

status: NOT REQUIRED
reason: zero new visual components, zero layout changes, zero visual
  changes — every affected screen renders pixel-identical output before
  and after. This is a pure internal widget-tree restructuring (private
  helper function → private widget class), not new UI, following the
  same reasoning as the `intl-string-retrofit` change's Design gate.
