# T2. In the same file, modify `getTicketById(String id)` to skip its

`emit(TicketsLoading())` when the current `state` is already
`TicketDetailLoaded` for this exact `id` — still emitting it in
every other case. Per `design.md`'s "`getTicketById`'s
Loading-skip" section exactly. Update the method's dartdoc with one
added sentence noting the skip condition and why (mirrors
`searchTickets`'s existing no-flash-over-content-already-shown
precedent, scoped per-id).
Implemented with one necessary addition beyond `design.md`'s
literal snippet, found during implementation: `getTicketById`'s
emit only ever carried `childDocs`/`linkedTickets`/`backlinks`/
`gapsAndOpenQuestions`/`pendingToolProposal` from
`loadDocumentRelations` (a *separate* call the screen fires for
`resource`/`bug` tickets after the initial load) — never from
itself. A same-id re-fetch that discarded those back to their
empty defaults would silently blow away an already-open
`resource`/`bug` ticket's visible Linked Tickets/Backlinks/Gaps
sections (and a `chat` ticket's pending tool-confirmation banner)
every time a background write refreshed it — a real regression,
and the opposite of "lands invisibly" this task exists to achieve.
Fixed by carrying those five fields forward from the previous
`TicketDetailLoaded` whenever re-entering for the same `id` (the
same condition already added for the Loading-skip) instead of
leaving them at their constructor defaults. `story` tickets are
unaffected either way (the screen never calls
`loadDocumentRelations` for that type), so this doesn't change
`_refreshDetailIfOpenAndAffected`'s Story/child-status refresh
case at all — it only protects the direct-match case for the
ticket types that actually populate those fields.
