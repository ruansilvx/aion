# Post-`/verify` fixes (CRITICAL findings 1–5)

A `/verify` pass after the first `/apply` run (all tasks above marked
`[x]` at the time) found 5 CRITICAL-severity issues. Fixed below, each
re-verified with its own test(s); full suite re-run afterward
(1297/1297 passing).

- [x] T31. `tickets_cubit.dart` — `_fireSkillAttachment`/
      `_runStageChatTurn` ran a `delegatedSkill` attachment tool-enabled
      directly against `_projectRootPath` instead of an isolated `git
      worktree`, the only tool-enabled path in this cubit that skipped
      the isolation every other one (`_runCodingExecution`,
      `_runFullSummarization`) uses — meaning an unattended
      (`auto`-confidence) attachment could mutate the developer's real
      checkout/branch. Fixed: both methods now create a worktree (via
      `GitRepositoryClient.createWorktree`, branch
      `aion/skill-<attachment.id>-<uuid>`) before firing, remove it in a
      `finally`, and throw (caught, posting the usual failure comment)
      if constructed without a `GitRepositoryClient`/`projectRootPath`
      rather than silently falling back to the root path. Updated
      `tickets_cubit_test.dart`'s two `workingDirectory ==
      '/project/root'` assertions to instead assert against the
      captured worktree path and verify `createWorktree`/
      `removeWorktree` are called correctly.
- [x] T32. `tickets_cubit.dart` — `_resolveAndFireAttachment`'s `gated`
      branch and `confirmPendingSkillAttachment`/
      `rejectPendingSkillAttachment` each constructed a bare
      `TicketDetailLoaded(ticket, ...)`, silently resetting every other
      already-loaded field (`childDocs`, `canAdvanceSddStage`,
      `isExecuting`, `pendingToolProposal`, etc.) to its default instead
      of preserving them — contradicting design.md §3.3/T16's "mirrors
      `_refreshDetailIfOpenAndAffected`'s existing pattern" instruction.
      Same bug in `advanceSddStage`'s gated/manual branch (`emit
      (TicketDetailLoaded(refreshed))`). Fixed: added
      `TicketDetailLoaded.copyWith` (`tickets_state.dart` — `tasks.md`
      T19 had called for one but it was never added) and routed all
      four call sites through it, preserving `current`'s existing
      fields and only touching the field each call site actually
      changes (`pendingSkillAttachment` via a `TicketFieldSetter` for
      explicit-clear, `isAdvancingStage`).
- [x] T33. `workflow_config_cubit.dart` — `createAttachment`/
      `updateAttachment` only checked the one-per-target invariant;
      `SkillAttachment`'s two either/or invariants (exactly one of
      `workflowStatusId`/`sddStage`; exactly one of `templateId`/
      `skillName`, matching `kind`) were documented as
      `WorkflowConfigCubit`-enforced (entity dartdoc, `specs/spec.md`)
      but never actually checked anywhere, letting a malformed
      attachment persist. Fixed: new `_attachmentInvariantViolation`
      helper, checked before `_attachmentTargetTaken` in both methods.
      Five new `workflow_config_cubit_test.dart` cases cover both
      invariants on create and update.
- [x] T34. `test/core/database/app_database_test.dart` — the schema
      15→16 upgrade path (T29's own stated scope) was never actually
      tested, only a fresh `onCreate` install. Fixed: a
      `NativeDatabase.memory(setup: ...)` callback stamps the raw
      sqlite3 `user_version` pragma to `15` before drift's migration
      logic runs, so drift genuinely invokes the real `onUpgrade`'s
      `from < 16` branch (not a re-implementation of it) — no
      `SchemaVerifier`/exported-schema infrastructure needed.
- [x] T35. T30's widget-test coverage was create/delete only, never
      edit — despite T30's own task text listing "create/edit/delete"
      for both. Fixed: added an edit case to
      `workflow_status_settings_screen_test.dart` (reopen an existing
      attachment, change its confidence, Save, assert
      `attachmentRepository.update` is called) and to
      `workflow_prompt_templates_screen_test.dart` (open a template's
      Edit action, change its name, Save template, assert
      `templateRepository.update` is called).
