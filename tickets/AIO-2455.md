# Token Cost Prediction

# Proposal: Token Cost Prediction

## Why

Coding execution (Task/Bug tickets) is the most expensive, highest-variance
thing Aion does — a single run can burn anywhere from a few thousand to
several hundred thousand tokens against the user's Pro/Max usage window,
and today there is zero visibility into that cost until *after* it's
spent. `aion-arch/specs/tickets.md`'s own Known gaps section already
flags this: "There is no predictive, cost-estimate budget gate — only the
reactive `AgentOverageDetectedEvent`-triggered gated-override." A tired
solo dev deciding whether to kick off a run, or whether to keep it running,
has no number to look at either way.

This closes that gap with two purely-informational, additive surfaces:

1. **Pre-flight estimate** — a token-count range shown on a not-yet-run
   Task/Bug's detail screen and Board/list tile, calibrated from
   comparable *past* Task/Bug tickets' own actual recorded token spend.
2. **Running total** — once a run is in flight (or has completed at least
   one turn), the same two surfaces show the ticket's real, accumulated
   token spend so far, recomputed as turns complete.

Neither surface gates anything. `AutomationConfidence`, the reactive
usage-window/overage handling, and coding-execution's actual trigger/queue
mechanics are all untouched — this is display only, wired onto data that
already exists (`ticket_comment.inputTokens`/`outputTokens`) or is cheap to
derive from it.

## What

- Two new nullable `Ticket` fields — `predictedExecutionTokensLow`/`High`
  — populated by a new background predictor (`TicketTokenPredictor`,
  mirroring `TicketEstimationSuggester`'s shape) for `task`/`bug` tickets
  that haven't executed yet. No model call: the predictor ranks other
  `task`/`bug` tickets by embedding cosine similarity (the same mechanism
  `ai-assisted-complexity-and-estimate-suggestions` already built), then
  deterministically sums each comparable candidate's own historical
  execution-chat token totals, and persists the resulting min/max range.
  "No estimate available" (both fields stay `null`) when no comparable
  candidate with recorded execution history exists yet.
- A new `TicketRepository.getExecutionTokenTotals` batched query —
  `Map<String taskId, int total>` summing `inputTokens + outputTokens`
  across every comment in every one of a task's `"Coding Execution — "`
  child chats (spanning implement/verify turns, retries, and continuation
  handoffs alike). Powers both the predictor's candidate lookups and the
  running total.
- `TicketsCubit` maintains an in-memory running-total cache, refreshed
  from that batched query on list/detail load and incremented in place
  whenever a coding-execution turn's `AgentDoneEvent` lands — exposed as
  `TicketsLoaded.executionTokenTotals` (Board/list) and
  `TicketDetailLoaded.executionTokenTotal` (detail screen), mirroring the
  existing `inFlightExecutionIds`/`executionQueuePositions` pattern
  `board-execution-indicators-and-notifications` already established.
- UI: a compact token label on `TicketBoardCard`'s meta-chip row, a
  persistent label near `TicketMetadataSection`'s complexity/estimate
  fields, and a "tokens used so far" line inside
  `_CodingExecutionSection`'s existing execution banner. Display
  precedence is simple: once any real execution data exists for a ticket,
  the running total is shown; otherwise the predicted range is shown (if
  one exists); otherwise nothing is shown.

## Non-goals

- No gate, confirmation, or blocking behavior of any kind — purely
  informational, per this idea's own brainstorm conclusion.
- No dollar-amount conversion — Aion's provider is a flat-rate Claude
  Pro/Max plan; `ConsumptionSignal`'s `CostConsumption.amountUsd` doesn't
  apply here, and a fabricated cost figure would be actively misleading.
  Raw token counts/ranges only.
- No coverage for SDD-stage chats or Inbox chats — scoped to
  coding-execution (Task/Bug) runs only, per this idea's own brainstorm
  scoping decision.
- No true per-tool-call live ticking during an in-flight turn. Confirmed
  during this session: `AgentModelClient`'s only usage-carrying event is
  the terminal `AgentDoneEvent` (`inputTokens`/`outputTokens`), reported
  once per completed turn — `AgentToolUseEvent` (the mid-turn progress
  signal) carries no usage data and the SDK/bridge has no partial-usage
  reporting today. The "running total" therefore updates once per
  completed implement/verify turn (at least two data points per
  execution), not continuously mid-turn. This resolves the open question
  the brainstorm session flagged for `/propose` to investigate.
- No low-confidence flagging of the predicted range (unlike AI-suggested
  complexity/estimate's deterministic low-confidence signal) — left as an
  explicit open question in the idea file, not designed here.
