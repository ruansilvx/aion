# Baseline Staleness Detector

# Proposal: Baseline Skill Staleness Detector

## Problem

`aion-arch/specs/projects.md`'s known-gaps list already documents this:
"No automated or enforced sync between `aion-arch/.claude/skills/` and
the bundled `assets/baseline/<version>/manifest.json` skill assets."
Confirmed by `/explore automated enforced sync between aion arch`
(2026-07-30):

- `0.1.0`/`0.2.0` baseline skill files are literal stub pointers — e.g.
  `aion/assets/baseline/0.2.0/skills/explore.md` is five lines ending in
  "Full skill source: `aion-arch/.claude/skills/explore/`." Both
  versions are frozen (`specs/projects.md`: "`0.1.0`/`0.2.0` are left
  untouched for whichever existing projects are still pinned to them"),
  so they aren't actually part of this problem going forward.
- `0.3.0` (current — what `CreateProjectCubit` pins for every new
  project) already fixed the stale-pointer version of this problem: its
  skill assets are self-contained, generic, stack-agnostic prose, not a
  mirror of `aion-arch`'s own skills.
- What's left, and what `0.3.0` doesn't fix, is a **process** gap:
  `aion-arch`'s real SDD skills keep evolving (they're "developed and
  proven there first," per `specs/projects.md`), but nothing signals
  when a skill's bundled counterpart in the latest baseline version has
  fallen behind. Confirmed with real git history during `/explore`:
  `aion-arch/.claude/skills/verify/SKILL.md` last changed 2026-07-13;
  `aion/assets/baseline/0.3.0/skills/verify.md` last changed 2026-07-25
  — currently fine, but nothing would have caught it if the dates were
  reversed.

## Goal

Whenever an `aion-arch/.claude/skills/<name>/SKILL.md` file has been
committed more recently than its bundled `assets/baseline/<latest
version>/skills/<name>.md` counterpart was last touched, surface that as
a priority-0 gap through the existing `/what-next` → `detect-gaps.sh`
pipeline — the same place `## Known gaps`/`## Open questions` spec
bullets already surface.

This is a **staleness detector, not a content sync**. It only answers
"has this drifted, and when." Deciding *what*, if anything, to port from
`aion-arch`'s operative, project-specific skill instructions into the
bundled baseline's deliberately generic, stack-agnostic wording stays a
human judgment call, made fresh each time — that half of the original
gap isn't being automated away, and this proposal doesn't claim to.

## Approach

A new standalone script, `aion-arch/workflow/scripts/detect-baseline-
staleness.sh`, compares `git log` dates (in each file's own repo) for
every `aion-arch/.claude/skills/<name>/SKILL.md` that has a same-named
counterpart under the latest bundled baseline version's `skills/`
directory, emitting a JSON array in `detect-gaps.sh`'s existing entry
shape (`{"priority": 0, "source": "baseline-staleness", "file": ...,
"title": ..., "next_action": ...}`).

`detect-gaps.sh` folds that script's output into its own priority-0
results, so `/what-next` picks it up with zero changes to its own
priority-selection logic — only its explanatory "Note on the gaps
above" paragraph gains one sentence describing the new source value.
See `design.md` for the exact script content and integration point.

Kept as a separate script (rather than inlined into `detect-gaps.sh`)
because it's the only piece of OpenSpec tooling that reaches into the
sibling `aion/` checkout rather than staying self-contained inside
`aion-arch/` — same single-responsibility split `detect-cycle.sh` and
`detect-gaps.sh` already use for their own distinct concerns. It
degrades to an empty array (not an error) if `aion/` isn't present as a
sibling checkout, since not every `aion-arch` checkout sits inside the
full `aion-workspace/` monorepo layout described in `CLAUDE.md`'s
"Workspace setup."

## Out of scope

- **No content sync or auto-generation.** Explicitly not building —
  porting an `aion-arch` skill's wording into its baseline counterpart
  stays a manual `/propose`-and-edit action, same as today.
- **No `aion/` (app repo) changes.** Every file this change touches
  lives under `aion-arch/`. Nothing under `aion/lib/` or
  `aion/assets/` is created or modified — `/apply` has no Dart tasks and
  no reason to touch the app repo's branch for this change.
- **`0.1.0`/`0.2.0` staleness.** Deliberately out of scope — both are
  frozen per `specs/projects.md`, so flagging drift against them would
  be noise, not signal. Only the latest bundled version is checked.
- **Skills with no bundled counterpart** (e.g. `prepare-release`,
  `aion-arch`-only release tooling with no equivalent in any baseline
  version). Silently skipped, not flagged — there's nothing to compare
  against.
- **A CI/pre-commit hook enforcing this check.** Out of scope for the
  same "sufficient at personal scale" reasoning `project.md` already
  applies elsewhere (e.g. the baseline-upgrade banner's purely local
  detection) — surfacing it through `/what-next`, which already gets
  checked routinely, is enough for a solo developer's workflow.
