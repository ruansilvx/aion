# Repo Release Setup And Distribution

# Proposal: Repo release setup and distribution (Windows + Linux)

## Source

`aion-arch/ideas/repo-release-setup-and-distribution.md` (`status:
explored`, one brainstorm session, 2026-07-24). `/explore` re-verified
the idea's claims against the current codebase before this proposal was
written: no git tags exist yet in the `aion` repo, `windows/`/`linux/`
are still bare Flutter scaffolds with no installer/packaging config
anywhere in the tree, no `.github/` directory exists, `pubspec.yaml` is
at `0.1.0+1`, and `assets/baseline/` already carries independently
numbered `0.1.0`/`0.2.0`/`0.3.0` folders unrelated to the app's own
version — confirming the idea's "independent versioning" premise
against real state rather than assumption. The just-merged
`baseline-version-upgrade-flow` proposal also confirms the deferral
this idea builds on: *"Real app-distribution/update-checking is out of
scope entirely — Aion has no installed users yet to distribute to."*

## Problem

There is no way to get a real, installable build of Aion onto a
Windows or Linux machine today — `flutter run` from source is the only
option, for the developer and for any tester. There is also no CI of
any kind in the `aion` repo, no versioning/changelog discipline beyond
the untouched `pubspec.yaml` stub, and no record connecting a shipped
`aion-arch` change to any release it went out in.

## What's building

1. **Windows packaging via Inno Setup.** `flutter build windows
   --release` output packaged into a real installer (Start Menu
   shortcut, uninstaller entry) — not a bare zip.
2. **Linux packaging via AppImage.** `flutter build linux --release`
   output packaged into a single portable `.AppImage` file — no
   distro-specific packaging.
3. **GitHub Actions release workflow**, triggered on a `v*.*.*` tag
   push: builds and packages both platforms in parallel (Windows on
   `windows-latest`, Linux on `ubuntu-latest`, solving cross-building
   Linux from a Windows dev machine for free) and attaches both
   artifacts to a GitHub Release.
4. **Independent versioning, formalized.** The app's own release
   version (`pubspec.yaml` / git tag) and the baseline version
   (`assets/baseline/<version>/`) stay uncoupled — this proposal
   documents that as an explicit, intentional decision rather than an
   implied side effect of how baseline detection happens to work.
5. **`CHANGELOG.md`** (Keep a Changelog style) as the committed,
   diffable source of truth for release notes; the GitHub Release body
   is generated from it at tag time rather than hand-duplicated or left
   to GitHub's auto-generated notes.
6. **`/prepare-release` skill** (new, local, human-reviewed — not part
   of the OpenSpec SDD cycle): reads every `aion-arch/changes/
   archive/<name>/proposal.md` not yet marked "Shipped in:", drafts a
   changelog entry per change plus a "Fixes & chores" section from
   ad hoc `fix:`/`chore:`/`refactor:` commits not covered by one of
   those changes, suggests a semver bump, and — once the developer
   confirms — bumps `pubspec.yaml`, writes the new `CHANGELOG.md`
   section, and stamps "Shipped in: vX.Y.Z" onto each shipped change's
   `proposal.md`. The developer still tags and pushes manually,
   triggering the CI workflow in (3).

## Non-goals (this proposal)

- **macOS.** No Mac hardware to build or sign on; the coding-execution
  differentiator is desktop-only anyway, and Windows + Linux cover the
  developer's own testing needs.
- **Public distribution or auto-update checking.** This produces
  installable builds for the developer/testers, not a public release
  channel. Aion does not gain any GitHub-Releases-polling or
  update-notification capability — it stays exactly as unaware of its
  own releases as it is today.
- **Code signing.** The Windows installer is unsigned; testers will see
  a SmartScreen warning. Acceptable for the current developer/tester
  scope — flagged as a known rough edge, not silently ignored.
- **Running `/prepare-release`'s drafting step inside CI.** Changelog
  drafting is agentic and needs review before it becomes a release's
  permanent notes; running it in CI would require model-API credentials
  in the workflow and would let unreviewed output ship unchecked. It
  runs locally, before tagging, instead.
- **Any Dart/Flutter application code changes.** Nothing in
  `aion/lib/` changes — this is packaging, CI, and process tooling
  only.
