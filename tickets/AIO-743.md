# Design: Per-run dependency caching and ancestor-based sibling-conflict scheduling

All file paths are relative to the `aion` repo. Line numbers are as of this proposal's `/explore` verification pass and will drift once `/apply` starts editing — treat them as locators, not guarantees.

## 1. Dependency caching

### 1.1 `DependencyCacheService` (`lib/core/build/dependency_cache_service.dart`) — new file

```dart
import 'dart:io';

/// Seeds a coding-execution worktree's `node_modules` from a
/// per-project cache directory, and writes it back after a successful
/// `npm install`, so later runs against the same project start warm.
/// Desktop-only (matches `GitRepositoryClient`'s existing desktop-only
/// scope — coding execution itself is desktop-only). Copy-based, not
/// hardlink-based: `dart:io` has no native hardlink API (`Link` creates
/// symlinks only), and shelling out to `ln`/`mklink` per file across a
/// multi-thousand-file `node_modules` tree would mean thousands of
/// subprocess spawns per run. Added for
/// `aion-arch/changes/dependency-caching-and-ancestor-sibling-conflict`.
class DependencyCacheService {
  /// Copies every file under [cacheDir] into [targetDir], preserving
  /// relative paths, creating parent directories as needed. No-ops
  /// (leaves [targetDir] untouched) if [cacheDir] doesn't exist yet —
  /// a project's first coding-execution run has nothing to seed from.
  Future<void> seed(String cacheDir, String targetDir) async {
    final source = Directory(cacheDir);
    if (!source.existsSync()) return;
    await for (final entity in source.list(recursive: true)) {
      if (entity is! File) continue;
      final relative = entity.path.substring(cacheDir.length + 1);
      final destination = File('$targetDir${Platform.pathSeparator}$relative');
      await destination.parent.create(recursive: true);
      await entity.copy(destination.path);
    }
  }

  /// Replaces [cacheDir]'s contents with [sourceDir]'s current
  /// contents — delete-then-copy, chosen over a diff/sync for
  /// simplicity and correctness over the O(size) cost, which is
  /// already being paid by `npm install`'s own writes this same run.
  /// Called only after a successful install (see
  /// `TicketsCubit._runCodingExecution` §1.3) — never caches a
  /// broken/partial `node_modules`.
  Future<void> writeBack(String sourceDir, String cacheDir) async {
    final cache = Directory(cacheDir);
    if (cache.existsSync()) await cache.delete(recursive: true);
    await cache.create(recursive: true);
    await seed(sourceDir, cacheDir); // same walk-and-copy, source ↔ dest swapped
  }

  /// Resolves [project]'s cache directory for [language]'s dependency
  /// directory name (e.g. `'node_modules'` for Node.js) — co-located
  /// under `Directory.systemTemp` alongside every coding-execution
  /// worktree (`_runCodingExecution`'s `createTempSync('aion_exec_')`),
  /// not under the project's own `rootPath`. Keeps the cache on the
  /// same volume as every worktree (avoiding any cross-volume copy
  /// concern) and out of the user's actual checkout. Keyed by
  /// [Project.storageKey], reusing the existing per-project identifier
  /// convention (`AppDatabase._openConnection`'s `'aion_${project
  /// .storageKey}'` naming).
  String cacheDirFor(String projectStorageKey, String dependencyDirName) {
    return '${Directory.systemTemp.path}${Platform.pathSeparator}'
        'aion_dep_cache${Platform.pathSeparator}$projectStorageKey'
        '${Platform.pathSeparator}$dependencyDirName';
  }
}
```

**Never live-shared across concurrent worktrees.** The cache directory above is only ever read from (`seed`) into a private per-worktree `node_modules`, or written to (`writeBack`) from one, never symlinked/junctioned directly into a worktree. With `parallel-work.md`'s N-concurrent-runs already shipped, a live-shared directory would let two simultaneous Node.js runs corrupt each other's `node_modules` mid-install — worse than the original single-shared-checkout risk `coding-execution-reliability-and-safety`'s worktree isolation closed, since it would be N-way concurrent rather than occasional human-vs-agent.

### 1.2 `TicketsCubit._runCodingExecution` — new steps (`tickets_cubit.dart:3297+`)

```dart
final worktreePath = Directory.systemTemp.createTempSync('aion_exec_').path;
final branchName = 'aion/task-${task.id}';
// ... existing createWorktree call ...
await gitClient.createWorktree(rootPath, worktreePath, branchName);

// NEW — before the implement turn:
final detected = ProjectStackDetector().detect(rootPath);
final isNodeProject = detected?.language == 'Node.js';
if (isNodeProject) {
  final cacheDir = _dependencyCache.cacheDirFor(
    project.storageKey,
    'node_modules',
  );
  await _dependencyCache.seed(cacheDir, '$worktreePath/node_modules');
  final setupResult = await Process.run(
    'npm', ['install'],
    workingDirectory: worktreePath,
  );
  if (setupResult.exitCode == 0) {
    await _dependencyCache.writeBack(
      '$worktreePath/node_modules',
      cacheDir,
    );
  }
  // A non-zero exit here is deliberately not fatal to the run — the
  // model's own implement turn can still attempt its own install/fix
  // (unchanged fallback behavior for a project whose setup genuinely
  // needs judgment `npm install` alone can't provide), it just starts
  // from a cache miss for its own troubleshooting rather than Aion
  // silently absorbing the failure.
}

var prompt = await _assembleExecutionContext(task, handoffSummary: handoffSummary);
```

`project` here is the same `Project` instance `_runCodingExecution`'s surrounding scope already has access to (it's how `rootPath` itself is resolved) — confirm exact variable name during `/apply`.

`_dependencyCache` is a new `late final DependencyCacheService? _dependencyCache` field, constructor-injected the same optional-dependency way as `_gitClient`/`_gitHubClient` (`null` for every existing construction site except `app_router.dart` — though unlike those, `DependencyCacheService` has no I/O-heavy constructor dependencies, so it could alternatively be instantiated inline as `const DependencyCacheService()` with no injection at all; **flagged as an open question below** — optional-injection matches this file's existing convention exactly, but adds DI ceremony for a dependency-free class).

### 1.3 Not wired into `_assembleExecutionContext`'s prompt text

The mechanical `npm install` step above runs *before* the prompt is assembled, independent of what `BaselineTailoringService`'s onboarding-time advisory text (`conventions/architecture-conventions`) says. This is deliberately a second, more reliable mechanism alongside that existing advisory text, not a replacement for it — the advisory text still helps for languages this change doesn't mechanically handle (Python, Rust, Go), and for any Node.js setup nuance beyond a bare `npm install` (e.g. a monorepo needing `npm install` from a different directory) that the model may still need to reason about even after Aion's own mechanical pass.

## 2. Ancestor-based sibling conflict

### 2.1 `TicketsCubit._ancestorIds` — new shared helper (`tickets_cubit.dart`)

```dart
/// Walks [ticketId]'s `parentId` chain via `_repository.getTicketById`
/// until reaching a ticket with no parent, returning every ancestor id
/// encountered (not including [ticketId] itself). Bounded naturally by
/// Aion's Epic→Story→Task/Bug hierarchy — a Task/Bug's parent may be a
/// Story *or* an Epic directly (`TicketTypeHierarchy.canParent` allows
/// any strictly-higher-rank parent, not only the immediately-next
/// rank), so this is not always exactly two hops, but always
/// terminates the first time `parentId` is `null`. Shared by
/// [_nextEligibleForHybrid] (§2.2) and [topmostAncestorIds] (§2.3) so
/// both use one identical chain-walking definition.
Future<List<String>> _ancestorIds(String ticketId) async {
  final ancestors = <String>[];
  var current = await _repository.getTicketById(ticketId);
  while (current?.parentId != null) {
    final parentId = current!.parentId!;
    ancestors.add(parentId);
    current = await _repository.getTicketById(parentId);
  }
  return ancestors;
}
```

### 2.2 `_nextEligibleForHybrid` — direct equality → shared-ancestor test (`tickets_cubit.dart:3803`)

```dart
Future<String?> _nextEligibleForHybrid() async {
  // In-flight tickets' full ancestor sets (was: bare parentId set).
  final inFlightAncestorSets = <String, Set<String>>{};
  for (final id in _inFlightExecutionIds) {
    inFlightAncestorSets[id] = {id, ...await _ancestorIds(id)};
  }
  for (final queuedId in _executionQueue) {
    final ticket = await _repository.getTicketById(queuedId);
    if (ticket == null) return queuedId;
    final queuedAncestors = {queuedId, ...await _ancestorIds(queuedId)};
    final conflicts = inFlightAncestorSets.values.any(
      (inFlightSet) => inFlightSet.intersection(queuedAncestors).isNotEmpty,
    );
    if (!conflicts) return queuedId;
  }
  return null; // every queued ticket is sibling-blocked.
}
```

Each candidate's own id is included in its ancestor-comparison set (`{id, ...await _ancestorIds(id)}`) so two tickets that are direct `blocks`/`blockedBy`-independent siblings (sharing a parent, the pre-existing case) still conflict exactly as before — the shared element is the common parent id, found in both sets' ancestor portions, not their own-id portions. This preserves 100% of today's `parentId`-equality behavior as a subset of the new, broader "shares any ancestor" test.

### 2.3 `TicketsCubit.topmostAncestorIds` — new batch method for the Board (`tickets_cubit.dart`)

```dart
/// Returns a map from each of [ticketIds] to its topmost ancestor id
/// (the root of its `parentId` chain — an Epic, for a well-formed
/// Task/Bug/Story; the ticket's own id if it has no parent at all).
/// Used by `BoardColumn` (§2.4) to precompute `clusterSiblingsAdjacently`
/// 's grouping key — a batch method rather than N individual
/// `getTicketById` calls from the widget layer, and async (unlike
/// `clusterSiblingsAdjacently` itself) because the Board is paginated:
/// a Task/Bug column's own `TicketsLoaded.tickets` very often does not
/// already include the Story/Epic tickets needed to resolve full
/// ancestor chains.
Future<Map<String, String>> topmostAncestorIds(List<String> ticketIds) async {
  final result = <String, String>{};
  for (final id in ticketIds) {
    final ancestors = await _ancestorIds(id);
    result[id] = ancestors.isEmpty ? id : ancestors.last;
  }
  return result;
}
```

### 2.4 `clusterSiblingsAdjacently` — new parameter, still pure (`sibling_cluster.dart:17`)

```dart
/// Returns [tickets] with same-cluster siblings regrouped adjacently
/// ... [existing dartdoc, updated below] ...
///
/// [topmostAncestorId] maps each ticket's id to its cluster key (its
/// topmost ancestor id, or its own id if it has no parent) — see
/// `TicketsCubit.topmostAncestorIds`. Was: grouped by direct
/// `ticket.parentId` equality; now groups by shared topmost ancestor,
/// so two Tasks under different Stories of the same Epic cluster
/// together, matching Hybrid mode's own generalized conflict signal
/// (`TicketsCubit._nextEligibleForHybrid`, §2.2) — the Board's visual
/// grouping and the scheduler's actual serialization now agree on the
/// same definition of "sibling." Still pure/synchronous: this function
/// does no I/O itself, the map is precomputed by an async caller.
List<Ticket> clusterSiblingsAdjacently(
  List<Ticket> tickets,
  Map<String, String> topmostAncestorId,
) {
  final result = <Ticket>[];
  final consumed = <int>{};
  for (var i = 0; i < tickets.length; i++) {
    if (consumed.contains(i)) continue;
    final ticket = tickets[i];
    result.add(ticket);
    consumed.add(i);
    final key = topmostAncestorId[ticket.id];
    if (key == null || key == ticket.id) continue; // no parent — no cluster.
    for (var j = i + 1; j < tickets.length; j++) {
      if (consumed.contains(j)) continue;
      if (topmostAncestorId[tickets[j].id] == key) {
        result.add(tickets[j]);
        consumed.add(j);
      }
    }
  }
  return result;
}
```

### 2.5 `BoardColumn` call site (`lib/features/tickets/presentation/screens/tickets_board_view.dart`)

Currently calls `clusterSiblingsAdjacently(columnTickets)` synchronously during build (a pure function, cheap to call inline). Since grouping now needs `topmostAncestorIds` (async), the fetch has to happen earlier — the cleanest fit is a `FutureBuilder` around just the clustering step is awkward inside an already-built column; instead, resolve it once per `TicketsLoaded` emission rather than per build:

- **Recommended**: `TicketsCubit` computes and caches a `Map<String, String> _topmostAncestorCache` (ticket id → cluster key) alongside `_refreshInFlightBoardState()`'s existing recompute pattern — but **only when `ExecutionSchedulingMode.hybrid` is the active mode**, confirmed as the only mode `BoardColumn` ever calls `clusterSiblingsAdjacently` under (`tickets_board_view.dart:320-327`) and the only mode `_tryStartNextQueuedExecutions` ever calls `_nextEligibleForHybrid` under — so Strict FIFO/Parallel sessions pay zero extra ancestor-walk cost, exactly like today. Refreshed whenever `TicketsLoaded` is re-emitted *and* the mode is Hybrid (new tickets loaded, a page loaded, a reparent happens, or a scheduling-mode switch into Hybrid itself), exposed as a new `TicketsLoaded.topmostAncestorId` field (`Map<String, String>`, default `{}` — including in every non-Hybrid session). `BoardColumn` then calls `clusterSiblingsAdjacently(columnTickets, ticketsLoaded.topmostAncestorId)` synchronously during build exactly as today, just reading a precomputed field instead of `ticket.parentId` directly — no widget-layer async fetch at all.
- **Alternative considered**: a `FutureBuilder`/`initState`-triggered fetch inside `BoardColumn` itself. Rejected — every other Board-state computation (`inFlightExecutionIds`, `executionQueuePositions`) already lives on `TicketsLoaded` via a `TicketsCubit`-side recompute, not a widget-side fetch; matching that existing convention keeps `BoardColumn` a pure `StatelessWidget` reading from `state`, unchanged in kind from today.

## Open questions for `/apply`

- Whether `DependencyCacheService` should be constructor-injected (optional-dependency pattern, matching `_gitClient`/`_gitHubClient`) or instantiated inline as a `const` — it holds no I/O-heavy state itself, only stateless file-copy methods, so injection may be unnecessary ceremony. Lean toward inline instantiation unless a test needs to substitute a fake implementation (confirm during `/apply` by checking whether `_runCodingExecution`'s existing test coverage mocks `_gitClient`/`_gitHubClient` the same way — if so, mirror that for consistency).
- Exact variable name for the already-in-scope `Project`/`project.storageKey` inside `_runCodingExecution` — confirm against the current method body at `/apply` time (this proposal's line numbers may have drifted).
- Exact mechanism for detecting a scheduling-mode switch *into* Hybrid (so `topmostAncestorId` gets computed at that transition even without a concurrent `TicketsLoaded` re-emission) — likely `ExecutionSchedulingCubit`'s existing state stream is already observed somewhere reachable from `TicketsCubit`'s construction/DI wiring; confirm the exact cross-cubit signal shape at `/apply` time (this proposal doesn't assume `TicketsCubit` currently listens to `ExecutionSchedulingCubit` at all, so this may need a new small listener wired in `app_router.dart`, mirroring how other cross-cubit signals in this codebase are wired — confirm precedent, if any, before inventing a new one).
