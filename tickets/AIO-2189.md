# Ticket Detail Status Editing

# Proposal: Ticket Detail Status Editing

## What

Make `status` editable directly from `TicketDetailScreen`, using the same
`SelectionMenu<T>` overlay-picker pattern already used there for `priority`
and `type`. Today `status` is the only one of the three meta-row fields
that's read-only on the detail screen (`StatusIndicator`, no picker) —
changing it requires leaving the ticket and going to the board (drag or
`MoveToStatusMenu`).

## Why

`aion-arch/specs/tickets.md`'s "Known gaps" section flags this explicitly:
> `status` remains board-only by design
> (`TicketRepository.updateTicketStatus`, via `MoveToStatusMenu`/drag).

Investigating the code (not just the spec note) during `/explore` found
this isn't a deliberate UX call — it's a consequence of how the board's
write path was built:

- `TicketsCubit.updateTicketStatus(String id, TicketStatus status)` emits
  list-shaped states (`TicketStatusUpdating`/`TicketStatusUpdated`) built
  for the board's optimistic drag-and-drop. `TicketDetailScreen`'s
  `BlocBuilder` switch only renders `TicketDetailLoaded` (and
  `TicketsLoading`/`TicketsError`); every other state falls through to
  `_ => const SizedBox.shrink()`. Wiring a picker straight to this method
  would blank the whole detail body on every status change.
- `TicketsCubit.updateTicket(Ticket ticket)` — the method that *does*
  re-fetch and emit `TicketDetailLoaded` — calls
  `TicketRepository.updateTicket`, which deliberately excludes `status`
  from the fields it persists (by design, to keep the board's dedicated
  `updateTicketStatus` write path as the sole status mutator). Routing
  through this path would silently drop the change.

So closing this gap needs one small additive Cubit method that reuses the
existing `TicketRepository.updateTicketStatus` (no repository/DAO change)
but re-fetches and emits `TicketDetailLoaded`, the same shape `updateTicket`
already produces — not a change to the repository or to the board.

Per the project's UX-first default, and since `priority`/`type` already
prove this exact pattern works on this screen, closing the gap for
`status` is low-cost and removes a UX inconsistency: a ticket's three
classification fields (type, priority, status) behave identically instead
of two-of-three being editable in place and the third requiring a
navigation round-trip.

## Scope

**In scope:**
- A new `TicketsCubit` method that changes a ticket's status from the
  detail screen and emits `TicketDetailLoaded`.
- Wiring `TicketDetailScreen`'s status field to a `SelectionMenu<TicketStatus>`
  (mirroring the existing `priority`/`type` wiring), replacing the current
  read-only `StatusIndicator`.
- One new localization key (`ticketDetailChangeStatus`) for the picker's
  accessibility label, matching `ticketDetailChangePriority`/
  `ticketDetailChangeType`.
- Cubit unit tests for the new method (success + failure), matching the
  existing `updateTicket`/`updateTicketParent` test style.

**Out of scope:**
- Any change to `TicketRepository`, `TicketDao`, or `DriftTicketRepository`
  — the existing `updateTicketStatus(id, status)` repository method is
  reused as-is.
- Any change to the board (`TicketBoardView`, `BoardColumn`,
  `MoveToStatusMenu`, drag-and-drop) — it keeps calling the existing
  list-shaped `TicketsCubit.updateTicketStatus(String id, TicketStatus)`
  exactly as today.
- Status-transition validation (e.g. disallowing `done → backlog`) — no
  such rule exists today on the board path either; this change doesn't
  introduce one.

`SelectionMenu<T>` overlay-picker component (`core/widgets/selection_menu.dart`)

`/verify`: the implementation introduces no new widget, token, or visual
treatment beyond that reuse.
