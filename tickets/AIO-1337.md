# Overlay Menu Keyboard Focus

# Proposal: Overlay Menu Item Keyboard Focus

## Problem

`aion-arch/specs/tickets.md`'s own Known Gaps section flags this:
`TicketOverflowMenu`'s "Delete ticket" row has no Hover/Focused/Pressed
visual states and no `FocusableActionDetector` — there is no keyboard
path to activate "Delete ticket" without a mouse, and the same per-item
gap exists in `SelectionMenu`/`MoveToStatusMenu`'s own overlay list
items, needing "a shared follow-up pass across all three
overlay-list-item cases rather than divergent one-off fixes."

Confirmed directly in code (`/explore ticketoverflowmenu delete ticket
row`, 2026-08-04): in all three widgets, each menu's *trigger* (the `⋯`
icon, the priority/type badge, the board's move icon) is wrapped in
`MouseRegion` + `FocusableActionDetector` + `GestureDetector`, but once
the overlay is open, its individual rows are wrapped in nothing but a
bare `GestureDetector` + `Semantics` — no hover fill, no focus ring, no
`ActivateIntent`. A keyboard-only user can open any of these three
menus, but cannot then Tab to or Enter-activate an item inside them.
`AppDropdown`'s own item rows have the identical gap, but `AppDropdown`
was not named in the known-gap bullet and stays out of scope here (see
Out of scope) — this proposal fixes exactly the three sites the gap
names, plus the structurally-identical rows living inside those same
three widgets' own files (see Approach).

Also confirmed during that `/explore`: the known-gap bullet immediately
below this one — claiming `AionShadows.card` "returns an empty list in
Obsidian" so the overflow menu "renders with no shadow at all in dark
theme" — is stale. Commit `7def852` ("Fix overflow menu missing depth
cue in Obsidian dark theme", 2026-07-23) already gave `card()`'s
dark-theme branch a real inset glow; the bullet was never removed. This
proposal's spec delta corrects that alongside the real fix, since both
bullets sit in the same paragraph and both are now resolved.

## Goal

Give every overlay-menu list item across the app real keyboard
affordance — Tab-focusable, Enter/Space-activatable, with a hover/focus
fill matching the interaction language these menus' own triggers
already use — through one shared, reusable primitive rather than three
divergent patches.

## Approach

New `OverlayMenuItem` widget (`design_system/molecules/`) — a thin
interaction/accessibility wrapper, not a layout primitive: it takes
whatever already-built, already-padded row content a caller passes as
`child` and layers `Semantics(button: true)` → `MouseRegion` →
`FocusableActionDetector` (`ActivateIntent` → the row's own `onTap`) →
`GestureDetector` (tap/tapDown/tapUp/tapCancel) → a `DecoratedBox` fill
around `child`, mirroring `TicketOverflowMenu`'s own trigger button's
three-state fill logic (`pressed → c.border`, `hovered || focused →
c.surfaceHover`, otherwise transparent — or a caller-supplied resting
tint, see `design.md` for `_PromoteRootRow`'s "suggested" case). No
separate focus ring — hover and keyboard focus intentionally render
identically (`c.surfaceHover`), since a highlighted row is a highlighted
row regardless of input method, and adding a second, competing visual
(a glow ring) inside an already-small menu row line would be more
visual noise than signal, per `design.md`.

`OverlayMenuItem` replaces the bare `GestureDetector`/`Semantics`
wrapper at every row inside the three named menus:

- `TicketOverflowMenu`'s `_MenuActionRow` (Delete ticket) and
  `_PromoteRootRow` (Promote to Epic/Bug) — the two row shapes the known
  gap's own overlay directly presents.
- `TicketOverflowMenu`'s `_PromoteChooser`'s "Create new epic/bug" row —
  structurally identical to the two rows above (same file, same open
  overlay); leaving it as the one non-focusable row in an otherwise
  fully keyboard-navigable menu would be a worse, inconsistent Tab
  experience than not touching the file at all.
- `SelectionMenu<T>`'s per-item row (`selection_menu.dart`) — fixes
  every existing `SelectionMenu` consumer app-wide (ticket priority/
  type/status/complexity pickers, automation-confidence pickers, model-
  routing dropdowns, the link-type picker) automatically, with no
  consumer-side change, since the fix lives inside the shared widget
  itself.
- `MoveToStatusMenu`'s per-status row (`tickets_board_view.dart`).

Default Flutter focus traversal (`ReadingOrderTraversalPolicy`) already
Tabs through sibling `FocusableActionDetector`s inside a plain `Column`
in tree order — none of these three menus need an explicit
`FocusTraversalGroup` added for this to work.

## Out of scope

- **`AppDropdown`'s own item rows.** Same gap (bare `GestureDetector`,
  no hover/focus), confirmed during `/explore`, but not named in the
  known-gap bullet this proposal addresses. Left as a narrowed known gap
  (see `specs/spec.md`) rather than folded in here.
- **`TicketOverflowMenu`'s `_PromoteChooser`'s "Link to existing"
  row.** Its interactive element is an embedded `TicketLinkPicker` (a
  separate widget with its own trigger/overlay), not a plain tappable
  row — that widget's own keyboard accessibility is a separate, larger
  concern, not a one-line `OverlayMenuItem` swap.
- **`_ChooserHeader`'s back-caret button.** A single nav icon, not a
  list item a user chooses among — outside this proposal's "list items
  inside an open overlay" framing.
- **A keyboard `Escape`-to-close affordance** for any of these three
  overlays. Not part of the named gap; each already closes on an
  outside tap. Left as a possible future, separately-scoped addition.
- **A focus ring / box-shadow glow on individual rows.** Deliberately
  not built — see Approach.
- **Any `Cubit`/state-layer change.** This is a pure presentation-layer
  accessibility fix; no `TicketsState`, `AutomationSettingsState`, etc.
  fields change.

`typeBug`, `accentTint`, `fillAlphaArctic`/`fillAlphaObsidian`). No
Material widget references found. See `/design-sync`'s Step 2 output
for the full cross-reference.

Non-blocking notes carried forward for `/apply`:
  - The approved export's `OverlayMenuItem` API shape supersedes this
    change's own architecture-draft sketch (design.md §1, the
    hand-written section preceding the pasted export): params are
    `child`/`onTap`/`semanticsLabel`/`accent`/`restingTinted`, not
    `restingColor`; the fill wrapper is a 100ms `Curves.easeOut`
    `AnimatedContainer`, not a plain `DecoratedBox`; the menu autofocuses
    its first enabled row on open; and a held `Enter`/`Space` key drives
    the same pressed feedback as mouse-down. `tasks.md`'s T1–T4 have been
    annotated to point at the export's actual sections — build to those,
    not the superseded draft snippet earlier in `design.md`.
  - The export's rationale in §1.4 cites "the shipped Ticket Deletion
    Spec §2.2" as prior art for an inset focus ring and the 1.6× pressed
    multiplier. No such prior ring exists in the current codebase —
    `_MenuActionRow` has zero interaction states today, which is this
    change's whole premise. Doesn't change any value or block `/apply`;
    flagged in case "Ticket Deletion Spec" references something real
    elsewhere worth reconciling later.
