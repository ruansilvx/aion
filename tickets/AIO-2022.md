# Storage Embedding Git Sync

# Proposal: storage-embedding-git-sync

## What

Completes the second half of the Storage Model foundational decision —
the half that `multi-project-hub` didn't touch. Three things ship
together because they share one underlying pipeline (a deterministic
Markdown serializer + a per-project git repo):

1. **Bundled on-device embeddings.** Populate the already-existing
   `Ticket.embedding` column via a fully bundled, on-device embedding
   model (no Ollama, no external server, no cloud call) — generated
   asynchronously whenever `title`/`description` change.
2. **Ticket ↔ Markdown git projection.** One Markdown file per ticket,
   committed to the project's per-project git repo on structural events
   (create, status change, trash, restore). Sync direction is
   type-dependent:
   - `epic`/`story`/`task`/`chat` — one-way, DB → file. The file is a
     generated, read-only audit trail.
   - `resource`/`page` — bidirectional. A focus-only filesystem watcher
     detects external edits, debounces, and reconciles them back into
     the DB, file-wins on conflict.
3. **Lint/repair tooling.** A shared validate/reformat/restore core,
   exposed through three thin entry points — an in-app UI action, a
   standalone CLI, and a baseline skill — so malformed hand-edited
   `resource`/`page` files can be fixed without burning agent tokens on
   purely mechanical parsing.

## Why

`project.md`'s Storage Model foundational decision names three storage
layers — drift, embeddings, git version history — but only drift ships
today. `aion-arch/specs/projects.md`'s "Known gaps" section calls this
out explicitly: *"The bundled on-device embedding model and
ticket↔Markdown git sync mechanics... are not yet implemented."*
`aion-arch/specs/tickets.md` separately flags `embedding` as
"unpopulated/unexposed."

This was fully resolved at the design level across three
`/brainstorm` sessions on
[storage-model-per-project-scoping](../../ideas/storage-model-per-project-scoping.md)
(2026-07-17 through 2026-07-18) — every architectural question that
would block implementation has an answer or an explicit, documented
default. This proposal turns that resolved design into a buildable
change.

Doing embeddings and git-sync in the same change (rather than two
separate ones) is deliberate: both write through the same "ticket
content changed" trigger, both need the same per-project `rootPath`
plumbing, and the Markdown serializer that git-projection needs is the
same one the DB-reconstruction recovery path needs. Splitting them
would mean building the serializer twice or awkwardly stubbing one
around the other.

## Scope

### In scope

- `EmbeddingProvider` core contract + bundled on-device implementation
  (native via ONNX, web via WASM), wired to fire async on ticket
  save when `title`/`description` changed.
- Deterministic Markdown template/serializer/parser for tickets
  (frontmatter + body), shared by every consumer below.
- One-way git projection for `epic`/`story`/`task`/`chat` tickets,
  triggered by: ticket created, status changed, moved to trash,
  restored from trash.
- Bidirectional sync for `resource`/`page` tickets: focus-only
  filesystem watcher, debounced reconcile, file-wins conflict
  resolution, per-field degrade on partially-invalid frontmatter,
  "needs repair" flagging (no silent overwrite in either direction) on
  fully unparseable frontmatter.
- `TicketSyncStatus` (synced / pendingReconcile / needsRepair) surfaced
  in the UI via a small badge on `resource`/`page` tickets, and a
  repair banner with reformat / restore-from-last-known-good actions
  when `needsRepair`.
- Lint/repair core logic + three entry points: UI action (on the
  existing ticket detail screen), a standalone Dart CLI
  (`aion/bin/ticket_lint.dart`), and a new baseline skill
  (`ticket-lint`), bundled as baseline version `0.2.0`.
- A DB-reconstruction-from-git service: rebuilds ticket rows from a
  project's committed `.md` files, followed by bulk embedding backfill
  for any ticket lacking a local embedding. Built and unit-tested as a
  standalone service — **not** wired into any UI flow (see Non-goals).
- `GitRepositoryClient` core wrapper around `git` CLI calls
  (init/add/commit/status), replacing the inline `Process.run` call in
  `CreateProjectCubit` and used by every git-writing service above.

### Non-goals (explicitly out of scope)

- **Batch review commit coalescing.** `project.md`'s change-review/
  batching system (scheduled edits, thresholds, auto-apply/defer gates)
  isn't built yet. Every trigger event in this change produces its own
  commit; coalescing multiple events into one commit is a natural
  follow-up once batching exists, not something to fake here.
- **A "clone existing project" / multi-machine onboarding UI flow.**
  The DB-reconstruction service is built and tested in isolation; there
  is currently no UI path that clones a project's git repo onto a new
  machine to call it from. Wiring it in is a future change once that
  onboarding flow exists.
- **Baseline upgrade flow for existing projects.** Already a tracked
  gap in `aion-arch/specs/projects.md`. The new `ticket-lint` skill
  ships in baseline `0.2.0`, which only new projects created after this
  ships will pin. Existing projects stay on `0.1.0` until the (separate,
  unbuilt) upgrade flow exists.
- **Mobile/web project-scoped git version history.** Already a tracked
  gap. This change's git projection is desktop-only, matching the
  existing desktop-only scope of `CreateProjectCubit._initializeDesktopProject`.
- **Cross-device git push/pull.** This change only commits locally.
  Push/pull sync between machines is `project.md`'s broader "Git ...
  cross-device sync" scope and stays a separate, unbuilt concern.
- **The future Notion/Obsidian-like pages screen.** The repair UI
  action attaches to the existing ticket detail screen for
  `resource`/`page` tickets. A richer, dedicated surface is tracked
  separately as
  [notion-obsidian-like-documentation-section](../../ideas/notion-obsidian-like-documentation-section.md)
  (still `raw`) and this change does not depend on or block it.

## Design decisions carried in from `/brainstorm`

(Full reasoning in
[storage-model-per-project-scoping.md](../../ideas/storage-model-per-project-scoping.md).)

- Embeddings regenerate only when `title`/`description` change, not on
  every mutation; generation is async, never blocks ticket save.
- Embedding BLOB is never committed to git, not even as a hash — a
  rebuilt DB has no cached value to compare a hash against anyway, so a
  hash only helps a same-machine staleness check, which is better
  served by a local-only concern.
- Filesystem watcher for `resource`/`page` runs **only while Aion is
  focused** — no background daemon, avoids idle resource usage.
- On focus-regain, reconciliation fires **immediately in the
  background, non-blocking**, surfaced via a subtle sync indicator —
  except when the user is actively viewing the specific page being
  reconciled, where it blocks (the only real conflict-risk window).
- Debounce window: suggested default ~1.5s of inactivity after the
  last detected write (implementation detail, tunable during `/apply`).
- Embedding model: suggested default all-MiniLM-L6-v2, int8-quantized,
  ONNX (desktop/mobile) + WASM (web) — one set of weights across every
  platform (implementation detail, tunable during `/apply` if the
  chosen package can't source it).
- Lint/repair is UI + skill + CLI, sharing one core validate/reformat
  implementation — the CLI exists specifically to keep agentic/scripted
  repair calls cheap (mechanical parsing shouldn't cost a skill
  invocation's worth of tokens).
