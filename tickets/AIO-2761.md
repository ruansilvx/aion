# Fix Ticket Trash Cascade Projection Gap

# Proposal: Fix the trash/restore cascade → git projection gap

## Origin

Originates from this session's `/explore` investigation into a live
data-integrity incident on Aion's own self-hosted project: two duplicate
Epic tickets (`AIO-2703`, `AIO-2704`, created by a `promoteIdea`
duplicate-promotion bug) were trashed via the app on 2026-09-08 — git
history shows the correct `ticket: AIO-2703 trashed` / `AIO-2704
trashed` commits, and `tickets/AIO-2703.md` / `AIO-2704.md` both
correctly show `deletedAt: 2026-09-08T...` in their frontmatter — yet
both tickets' DB rows showed `deleted_at: NULL` the next day, as if the
trash had never happened, with no error anywhere. No standalone idea
file precedes this; the investigation and this proposal were scoped in
one pass, same as `fix-ticket-git-projection-gap` before it.

## Problem

`/explore` root-caused and **reproduced** (via throwaway tests against
the real `DriftTicketRepository`/`TicketDbReconstructionService`, not
mocks) two independent defects, both instances of the same underlying
mistake: a write that cascades to *other* tickets beyond the one
explicitly named is never told to those other tickets' git projection.

### 1. `trashTicket`/`restoreTicket` cascade past what gets projected

`DriftTicketRepository.restoreTicket(id)` doesn't just restore `id` —
it also revives every currently-trashed **ancestor** and **descendant**
of `id` (`drift_ticket_repository.dart`'s own `toRestore` set). The
symmetric `trashTicket(id)` cascades to every **descendant** of `id`.
Both are correct, intentional structural behavior — a ticket can't be
visibly live while an ancestor is trashed, and a subtree trashed
together should return to life together.

But `GitProjectingTicketRepository.trashTicket`/`restoreTicket` only
re-project the one `id` explicitly passed in:

```dart
Future<void> restoreTicket(String id) async {
  await _inner.restoreTicket(id);
  await _projectOrSwallow(id, 'restored');   // only this id
}
```

**Reproduced**: trashed an epic + its child (both correctly got
`deletedAt` in the DB), restored *only the child*, and the epic's DB
row flipped back to `deletedAt: null` — with zero write to its `.md`
file and zero git commit. This is an exact mechanical match for the
observed incident: for `AIO-2703`/`AIO-2704` (root-level Epics with no
parent of their own), the only way they get swept up is as a revived
**ancestor** of some child ticket that was later restored — plausible
if a child under one of the duplicate epics was salvaged before the
duplication itself was noticed.

This gap already exists on the same-named symptom in two more places,
found and self-documented by the developer at the time each was built
(quoted here because they explain the intended scope, not because
anything was missed carelessly):

- `TicketsCubit.trashTickets`'s own dartdoc: *"projects only the
  explicitly-requested ids, not their cascaded descendants, also
  trashed by `TicketRepository.trashTickets` but not individually
  enumerable from its return value — a documented scope simplification,
  not an oversight."* This proposal removes the exact limitation that
  dartdoc cites (the return value not enumerating the cascade), so the
  simplification no longer needs to hold.
- `trash-restore-git-projection`'s own archived proposal.md listed
  "Cascade projection of restored ancestors/descendants" as an explicit
  Non-goal, deferring it "mirroring `trashTickets`' existing, documented
  scope simplification for the symmetric trash-side case." Both sides of
  that mirror are fixed together here.

### 2. `TicketDbReconstructionService.reconstruct()` can't tolerate a trashed ticket

Separately, `/explore` found and reproduced (a real `SqliteException`,
not a mock assertion) that `reconstruct()` — the DB-from-git rebuild
tool, also invoked by `bin/migrate_aion_arch.dart --import`'s step 3 —
crashes with `UNIQUE constraint failed: tickets.ticket_id` on **any**
trashed ticket:

- Its "does this ticketId already have a row" check is built from
  `TicketRepository.getAllTickets()`, whose DAO query is `WHERE
  deleted_at IS NULL` — trashed tickets are invisible to it.
- But trashing never deletes the ticket's `.md` file (only `deletedAt`
  changes in its frontmatter), so `reconstruct()`'s directory walk finds
  it anyway, treats it as brand new, and calls `importTicket` with a
  freshly-minted internal id against a `ticketId` that already has a
  `.unique()` row — constraint violation.
- Independently, even once that crash is fixed:
  `DriftTicketRepository.updateTicket()`'s SQL companion never includes
  `deletedAt`/`deleted_at` at all, so the *existing-row* branch's own
  dartoc claim — `"deletedAt round-trips through reconstruction the same
  way parentId/estimate/timeSpent already do"` — is false. The existing
  unit test for this only checks the `Ticket` object handed to a
  *mocked* `updateTicket`; it never asserts a real one persists the
  field.
- The same insert path (`_buildInsertCompanion`, shared by
  `createTicket`/`importTicket`) also omits `deletedAt` entirely, so
  even a *fresh* import of an already-trashed ticket would silently
  come back live.

`bin/migrate_aion_arch.dart --import` will crash on this project right
now, since `AIO-2703`/`AIO-2704` are currently trashed.

## Goal

Every ticket whose `deletedAt` actually changes as part of a
trash/restore operation — whether it's the one explicitly named or one
swept up by the cascade — gets its `tickets/<id>.md` file rewritten and
committed, every time, with no silent gap. `TicketDbReconstructionService
.reconstruct()` never crashes on a trashed ticket and correctly
re-derives its trash state from the file, matching what its own dartdoc
already claims.

## Approach

- Change `TicketRepository.trashTicket`/`restoreTicket` (singular) and
  `trashTickets` (plural) to return the **full set of ids actually
  affected** (the requested id(s) plus every cascaded ancestor/
  descendant) instead of `void`/a bare count — `DriftTicketRepository`
  already computes this set internally for the cascade walk; today it's
  simply discarded. This is the same shape the interface already uses
  elsewhere (`trashTickets` already returns something beyond `void`,
  today just a count).
- `GitProjectingTicketRepository.trashTicket`/`restoreTicket` fetch
  every id in that returned set and project them together in **one**
  commit via `TicketGitProjector.projectBatch` (the same primitive
  `TicketRollupRecomputer` already uses for its own cascading ancestor
  rewrites) — for the common case with no cascade, this is exactly
  today's one-ticket commit; unchanged.
- `TicketsCubit.trashTickets`'s own git side effect
  (`_trashBatchGitSideEffects`) switches from its per-explicit-id loop
  of individual `TicketGitProjector.project` calls to one
  `projectBatch` call over the plural repository call's now-complete
  affected-id list — see "Behavior changes" below for the one visible
  side effect of this.
- `TicketDbReconstructionService.reconstruct()`: build the "does this
  ticket already exist" map from `getAllTickets()` **and**
  `getTrashedTickets()` together (both already exist on the interface —
  no new repository method needed), so a trashed ticket's file is
  recognized as an update, never a doomed re-import. For the
  existing-row branch, explicitly reconcile a changed `deletedAt` via
  `_repository.trashTicket`/`restoreTicket` — mirroring the detection
  logic `TicketParentTrashService.applyFromParsedFields` already uses
  for the same file→DB direction — since `updateTicket` deliberately
  never touches trash state (see design.md for why that boundary stays,
  rather than widening `updateTicket` itself).
- `_buildInsertCompanion` (shared by `createTicket`/`importTicket`)
  gains `deletedAt`, so a freshly-inserted row (always the case for
  `importTicket`; never populated in practice for `createTicket`) seeds
  its trash state faithfully instead of silently defaulting to live.

## Behavior changes worth flagging

- **Bulk trash's commit shape**: today, `TicketsCubit.trashTickets`
  produces one commit *per explicitly-selected id* (via a loop of
  individual `project` calls), still never touching cascaded
  descendants at all. After this change, a bulk trash produces **one**
  combined commit covering every explicitly-selected id plus every
  cascaded descendant of each — matching the batching convention this
  codebase already uses for rollup-cascade commits. Net fewer, more
  complete commits per user action, not more.
- **`bin/migrate_aion_arch.dart --import`** stops crashing on this
  project's current state (two trashed tickets) and correctly leaves
  their DB rows trashed on reconstruction, instead of crashing partway
  through step 3.

## Non-goals

- **Whether trash/restore should cascade to ancestors/descendants at
  all.** That structural behavior is unquestioned and correct — only
  its git projection was incomplete. Not touched.
- **`permanentlyDeleteTicket(s)`/`emptyTrash`/`purgeTrashOlderThan`
  never removing the projected `.md` file from git.** A separate,
  already-documented gap (`fix-ticket-git-projection-gap`'s own
  Non-goals list it too) — missing *deletion* projection, a distinct
  problem from this proposal's missing *cascade* projection.
- **`bin/migrate_aion_arch.dart`'s own step-1 registration loop**, which
  also builds its existence map from `getAllTickets()` alone — left
  as-is, since it only ever iterates `result.tickets` (freshly generated
  by that same run's migrators), which can never already be a trashed
  ticket from a prior run. Not exposed to this bug in practice.
- **`TicketRollupRecomputer`**, whose own `getAllTickets()`-based
  ancestor walk is correctly scoped to live tickets only (rollups are a
  live-subtree computation by design) — untouched.
- **No UI changes.** Entirely a data/service-layer fix.
