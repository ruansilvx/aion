# Design: Native Windows Verification Pass

## No architecture change

This change has no technical design in the usual sense — no new classes,
BLoC states, widgets, or data flow. It documents a verification method
and its results, for reproducibility and for the record `/archive` will
merge into `aion-arch/specs/`.

## Verification method

Driven live against `flutter run -d windows --debug` in the `aion/` app
repo (the actual native Windows executable, `build\windows\x64\runner\
Debug\aion.exe` — not `flutter-web`/Chrome). Interaction was performed
via raw Win32 API calls from PowerShell rather than a UI-testing
framework, since Flutter's semantics tree isn't reliably exposed to
Windows UI Automation without a screen reader active:

- **Window focus:** `SetForegroundWindow`, preceded by a synthetic Alt
  keypress/release — Windows refuses `SetForegroundWindow` from a process
  that doesn't already hold foreground-change rights, and the fake Alt
  keystroke satisfies that check.
- **Clicks:** `SetCursorPos` to a target coordinate (window-relative,
  resolved via `GetWindowRect` each call so window movement doesn't
  desync coordinates), then `mouse_event` with
  `MOUSEEVENTF_LEFTDOWN`/`MOUSEEVENTF_LEFTUP`.
- **Drags:** same down/up pair, but with ~20 interpolated `SetCursorPos`
  calls between them (25ms apart) so Flutter's `Draggable` gesture
  recognizer sees continuous pointer movement rather than a teleport,
  which it does not reliably recognize as a drag.
- **Scrolling:** `mouse_event` with `MOUSEEVENTF_WHEEL`, signed delta
  reinterpreted as `uint32` via `BitConverter`.
- **Text input:** `System.Windows.Forms.SendKeys`. Noted as unreliable in
  practice — one search-box entry dropped its leading character, which
  briefly looked like a search-index bug until manual scrolling
  confirmed the underlying data was correct. Future passes should prefer
  click-driven verification over `SendKeys` text entry where possible,
  or double-check `SendKeys` results against a non-search-dependent path
  before concluding anything from them.
- **Screenshots:** `System.Drawing.Graphics.CopyFromScreen` over the
  window's `GetWindowRect` bounds, saved to PNG and read back for visual
  confirmation at each step.

## Flows exercised and outcomes

| Flow | Steps | Outcome |
|---|---|---|
| Board drag-and-drop | Board view → drag AIO-12 Backlog → To Do → drag back | Card moved correctly both directions; column counts updated live |
| Trash delete → restore | Overflow menu → Delete ticket → confirm dialog → Trash screen shows `1 item` → Restore → Trash shows `0 items` → ticket confirmed back in main list | Full round trip correct, no data loss |
| Settings connection test | Settings → Providers → Test Connection | `CHECKING` → `CONNECTED`; `agent_bridge/` Node subprocess spawned and replied correctly |

No crashes, no visual glitches, no incorrect state observed in any of the
three flows.

## What this does not cover

Per the proposal's Non-goals: accessibility keyboard walkthrough, mobile
`LongPressDraggable`, coding-execution/chat flows, and git-projection
reconciliation edge cases were not part of this pass and remain open
gaps.
