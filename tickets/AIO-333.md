# Spec delta: Baseline version upgrade flow for an existing project

**Reconciled 2026-09-03:** checked against the current `aion-arch/specs/projects.md's Baseline version upgrades section` — the mechanism/behavior this delta describes is still present and architecturally coherent with current text. Identifiers the automated screen flagged as missing are private-method requalification, line-wrapped tokens, or names covered in a neighboring section rather than repeated here — not behavioral drift. BaselineManifest, Project.baselineVersion, and the upgrade-offer mechanism this delta introduces are confirmed current.

Delta against `aion-arch/specs/projects.md`.

## ADDED behaviors

### Baseline version mutation (projects.md)

- `ProjectRepository` gains `updateBaselineVersion(String id, String
  version)` — a narrow, single-field registry write, same shape as the
  existing `updateLastOpened`. This is the first path anywhere in the
  codebase that changes a project's pinned `baselineVersion` after
  creation.
- A new `ProjectManifestWriter` (`core/build/`) writes
  `<rootPath>/.aion/manifest.json`, shared between project creation
  (`CreateProjectCubit`) and the new upgrade path (`ActiveProjectCubit`).

### Lazy, per-project upgrade offer (projects.md)

- Every `ActiveProjectCubit.switchTo` call now also compares the
  switched-to project's pinned `baselineVersion` against
  `BaselineRepository.getAvailableBaselineVersions().last` (the latest
  version bundled in the running build) and emits the result as
  `ActiveProjectOpen.offerBaselineUpgrade`.
- `TicketsListScreen` shows a new, dismissible `BaselineUpgradeBanner`
  (same insertion point and shared visual shell as the existing
  `CodebaseAnalysisBanner`) the first time it builds after
  `offerBaselineUpgrade` is `true`, then calls the new
  `ActiveProjectCubit.consumeBaselineUpgradeOffer()` so it never
  reappears for that same switch. Declining is purely local (hides the
  banner) — the flag is recomputed fresh, and the banner can reappear,
  the next time this project is switched into, for as long as a newer
  version remains bundled.
- Detection is purely local: no network calls, no GitHub polling —
  entirely a comparison against `BundledBaselineRepository`'s hardcoded
  bundled-version list.

### Accepting an upgrade (projects.md)

- New `ActiveProjectCubit.acceptBaselineUpgrade()` (exposed on the
  `ActiveProjectProvider` contract so other features can trigger it):
  updates the registry DB row via `updateBaselineVersion`; on desktop
  (`rootPath != null`) also rewrites `.aion/manifest.json` via
  `ProjectManifestWriter` and calls the new
  `BaselineTailoringService.tailorNewlyIntroducedAssets`. No diff/review
  step — a straight version-pin bump. Existing `ProjectOverride` files
  are untouched and keep resolving by asset key exactly as before.
- `BaselineTailoringService.tailorNewlyIntroducedAssets(projectId,
  rootPath, oldManifest, newManifest)`: if the new manifest introduces an
  `architectureConvention`-kind asset key that did not exist in the old
  manifest at all, and no override already shadows it, runs the existing
  detected-stack tailoring (`tailorForDetectedStack`) against it. Any
  other newly-introduced asset key (e.g. a new `skills/*` file) is left
  unoverridden, resolving to its bundled default — no generic tailoring
  exists for those kinds.
- Mobile/web projects (`rootPath == null`) still get the registry-DB
  version bump; the manifest rewrite and tailoring step are skipped,
  matching the existing desktop-only scope of the override system.
- An override shadowing an asset key the new version removed entirely is
  left in place, unused — no cleanup, no warning.

### Manual "Upgrade" action in Settings (projects.md)

- New `BaselineUpgradeCubit`, route-scoped on `/workspace/settings`,
  loads the active project's current pinned version and the latest
  bundled version, and exposes `upgrade()` (delegating to
  `ActiveProjectProvider.acceptBaselineUpgrade()`).
- `SettingsScreen` gains a "BASELINE" section showing the current pinned
  version and an "Upgrade to v{latest}" action, always available
  regardless of whether the lazy banner has already been shown or
  declined this session. Disabled (or hidden) when already on the latest
  version.

## MODIFIED behaviors

### `ActiveProjectState.ActiveProjectOpen` (projects.md)

- Gains `bool offerBaselineUpgrade` (default `false`), independent of the
  existing `offerCodebaseAnalysis` flag — consuming one never clears the
  other.

### `ActiveProjectCubit` (projects.md)

- Constructor gains two new dependencies: `BaselineRepository` and
  `BaselineTailoringService`.
- `switchTo` now also computes and emits `offerBaselineUpgrade`.

### `ActiveProjectProvider` contract (projects.md)

- Gains `offerBaselineUpgrade`, `consumeBaselineUpgradeOffer()`, and
  `acceptBaselineUpgrade()` — mirroring how `offerCodebaseAnalysis`/
  `consumeCodebaseAnalysisOffer()` already expose the codebase-analysis
  offer to other features without a direct `features/projects/` import.

### `BaselineTailoringService.tailorForDetectedStack` (projects.md)

- Signature changes from an implicit hardcoded `0.3.0` asset constant to
  accepting a `BaselineManifest` parameter and resolving the
  `architectureConvention`-kind asset from it dynamically. Behavior at
  the existing project-creation call site (`CreateProjectCubit`) is
  unchanged — it now explicitly fetches the manifest it already has a
  resolved version string for, rather than relying on a hardcoded
  constant that happened to match.

### `Project.baselineVersion` (projects.md)

- No longer immutable through the app's UI — its doc comment is updated
  to reflect this proposal's `acceptBaselineUpgrade` as the (only)
  legitimate post-creation write path.

## Non-goals / explicitly out of scope

- No diff/review UI showing what changed between baseline versions — a
  straight version-pin bump, trusting the existing per-key override
  resolution.
- No full agentic tailoring of newly-introduced assets, and no per-project
  persisted record of a "summarization depth" choice to tailor by — neither
  exists in the codebase today (see design.md's Corrections §1).
- No tailoring of any newly-introduced asset kind other than
  `architectureConvention` — no generic per-kind template mechanism
  exists for `skill`/`modelConfig` kinds.
- No cleanup of overrides orphaned by a removed asset key.
- No network/GitHub-based update checking — detection is purely a local
  comparison against the bundled version list already compiled into the
  running build.
- No changes to mobile/web's existing lack of an override surface.
