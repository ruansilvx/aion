# Spec Ticket Type

# Proposal: spec-ticket-type

## What

A new first-class `TicketType.spec` — Aion's own record of current-state
behavior, written by the ticket-native SDD cycle instead of a hand-edited
file. Six pieces, all additive:

1. **`TicketType.spec`** — parentless like `release`/`idea` (`canParent`:
   `chat` only, `isAlwaysRoot: true`), available in `CreateTicketScreen`'s
   generic dropdown (unlike `page`/`knownGap`/`openQuestion` — a spec has
   no mandatory link the way a gap/question does, so nothing blocks
   manual creation). Gets a `typeSpec` color token and `TypeChip`
   coverage, and a slot in the 9×9 `TicketTypeHierarchy.canParent`
   expectation-matrix test.
2. **Auto-creation at Epic archival** — `TicketsCubit.advanceSddStage`'s
   existing `nextStage == SddStage.archived` branch (today a bare
   `emit`+`return null`) gains one new step, guarded by
   `ticket.type == TicketType.epic` specifically: synthesize a
   `TicketType.spec` ticket titled `"Spec — <epic.title>"` from the
   Epic's own outcome (title/description + every direct child Story's
   title/status — the same assembly `_assembleStageContext` already
   builds for the `verifying`/`archived` transitions), run one
   `ModelPhase.capable` model call to write the spec body, create the
   ticket, and link it to the Epic via `TicketLinkType.relatesTo`. A
   Story reaching `archived` (which happens routinely, as every child
   Story's own precondition for the *Epic's* `verifying` transition)
   does **not** trigger this — only the Epic gets a spec, written once.
3. **Spec ticket editing** — `PagesCubit`/`PageDetailScreen` extended to
   also accept `TicketType.spec` alongside `TicketType.page`, reusing
   the existing `MarkdownEditor` design-system molecule and relation
   loading verbatim. A spec ticket is an ordinary editable document once
   created — corrections, linking a resolved bug, etc. are plain content
   edits, with no cycle of their own.
4. **Auto-linking to the nearest relevant spec** — a new
   `AutomationContext.specAutoLink` value, gating (per the existing
   `auto`/`gated`/`manual` `AutomationConfidence` pattern) a new
   `TicketsCubit` check that runs Aion's existing embedding-similarity
   scan (`domain/utils/embedding_similarity.dart`'s `cosineSimilarity`,
   the same 0.75 threshold `TicketContextEnricher` already uses) against
   every live `TicketType.spec` ticket, taking the single best match
   above threshold (not a top-K list — this creates a real link, not
   context prose). Fires from two call sites: `createGapOrQuestion`
   (`knownGap`/`openQuestion` creation — additive to that method's
   existing mandatory target link) and `updateTicketStatus` (when a
   `TicketType.bug` moves to a `done`-role status). This is the first
   consumer where a similarity match autonomously creates a write rather
   than enriching a prompt or suggesting a value.
5. **`project.md`'s ticket-native equivalent** — no new mechanism beyond
   #1/#3: a single `spec` ticket (e.g. titled `"Architecture — Aion"`),
   created manually once via the ordinary New Ticket flow, its content
   written/pasted by hand from `project.md`. See
   [Out of scope](#out-of-scope) for why this is deliberately not
   automated.
6. **`DocumentationScreen` stays scoped to human-curated content** — its
   existing `ticket.type == TicketType.page` check is left as-is (not
   widened to include `spec`); spec tickets are reachable via their
   owning Epic's `relatesTo` link and, later, the graph-view idea, not
   via the generic Documentation listing — consistent with
   `knownGap`/`openQuestion` also being excluded from that same
   generic-browsing surface.

## Why

Originates from `aion-arch/ideas/spec-ticket-type.md` (`status:
explored`). `aion-arch/specs/*.md` is the CLI-driven SDD cycle's own
record of current-state behavior, merged by hand at `/archive` time —
but that mechanism doesn't exist inside Aion's ticket-native SDD cycle
(`sdd-ticket-foundation`/`sdd-ticket-execution`, archived) at all. An
Epic can run all the way through `exploring → proposed → verifying →
archived` today and nothing records what it actually shipped anywhere
durable — the only trace is the Epic and its now-archived Stories
themselves, with no synthesized "here's what this capability does now"
artifact the way `aion-arch/archive`'s merge step produces one.

The idea's own `/explore` pass (this session) grounded the mechanism
against current code and confirmed the two riskiest assumptions hold:
the `advanceSddStage` hook point is real and currently a no-op exactly
where this needs it, and `AutomationConfidence`/`AutomationContext`
is already a bare, per-context-keyed primitive designed for exactly
this kind of new consumer — see `design.md` for the full grounding.

## Re-scoped from the original idea — what changed and why

The idea bundled a per-domain-vs-per-Epic scoping question, a domain-tag
question, and `project.md`'s fate, all resolved during `/brainstorm`
before this proposal — see the idea file's "Summary of answers" for the
full reasoning trail (per-Epic over per-domain-merged-file avoids an
unbounded-token merge problem entirely; domain tags were rejected as
weaker than the `relatesTo` links this project already leans on).
Re-checking against current code during `/explore` surfaced one
correction to the idea's own framing: `PagesCubit` is not already
generically parameterized over `TicketType` the way "reuses page's
content-editing widget" implied — only the shared `MarkdownEditor`
widget is a true drop-in. Extending `PagesCubit`/`PageDetailScreen`
themselves to also handle `TicketType.spec` (piece #3 above) is real,
scoped work, not a zero-cost reuse — sized accordingly in `tasks.md`.

## Out of scope

- **Migrating `project.md`'s actual content into the architecture spec
  ticket.** A content decision, not a code gap, consistent with
  `sdd-ticket-foundation`'s identical precedent for `aion-arch/specs/`
  content. This proposal makes manual creation possible (`spec` is a
  generically-creatable type); a human does the one-off writing
  afterward.
- **A dedicated retry UI for a failed spec-write model call.** The
  Epic's own `archived` transition is already durably persisted several
  lines before the spec-write step runs (see `design.md`), so a failed
  spec write never blocks or rolls back the stage transition — it
  surfaces as a `TicketsError` (`specWriteFailed` reason), and the
  existing generic New Ticket flow (spec is creatable there, per piece
  #1) is the fallback: a human can hand-create the missing spec ticket.
  A first-class "Generate spec" retry affordance is a reasonable
  follow-up, not required for this change to be useful.
- **The domain-grouping rollup/index UI** the idea's brainstorm
  explicitly deferred to the not-yet-built
  `obsidian-style-graph-view-for-ticket-links` idea. Nothing here builds
  it.
- **Everything else in `aion-arch`** (the existing `~50` file-based
  ideas' migration, `changes/archive/*` history's fate, `CLAUDE.md`/
  `workflow/`'s CLI-process docs, retiring `.claude/skills/` itself) —
  entirely separate scope, captured as
  `aion-arch/ideas/decommission-aion-arch-cli-workflow.md`.
- **Bulk/backfill spec generation for Epics archived before this ships.**
  This change only wires the trigger going forward; no migration script
  retroactively generates specs for already-archived Epics.
