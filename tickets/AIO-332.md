# Design: Baseline version upgrade flow for an existing project

## Corrections (resolved during `/propose`, before implementation)

These resolve gaps between the source idea's aspirational description and
what's actually in the codebase today (confirmed by reading the code during
`/explore`, not assumed from the idea file) — the same "Corrections" pattern
`project-type-aware-conventions-and-verification`'s own design.md used:

1. **"Tailor new assets per the project's original summarization-depth
   choice" is not implementable as literally stated.** The idea's Q5/Q6
   assumed a project remembers whether it was set up with `shallow` or
   `full` codebase-summarization tailoring. It doesn't —
   `SummarizationDepth` (`aion/lib/features/tickets/domain/enums/
   summarization_depth.dart`) is passed directly into
   `TicketsCubit.runCodebaseSummarization(depth:)` as a one-shot UI choice
   and is never written to `Project`, `RegistryDatabase`, or anywhere else
   persisted. There is no "original choice" to look up. Separately, the
   *full* agentic tailoring path doesn't exist at all yet — `aion-arch/
   specs/projects.md`'s "Full agentic baseline tailoring" is listed as an
   unbuilt open question, and `BaselineTailoringService` has exactly one
   real method, `tailorForDetectedStack`, which only fills in
   `conventions/architecture-conventions` from `ProjectStackDetector`'s
   marker-file detection. This proposal therefore reuses *only* that one
   shallow path for "tailor new assets," unconditionally — there's nothing
   else built to call.

2. **"Tailor new assets" only ever has real content for one asset kind.**
   `tailorForDetectedStack`'s template (`detected.language` +
   `detected.checkCommand`/`setupCommand`) is meaningful only for a
   `BaselineAssetKind.architectureConvention` asset — it has no generic
   templating mechanism for an arbitrary newly-introduced `skill`- or
   `modelConfig`-kind asset (there is no "detected stack" content that would
   make sense inside a skill file). So "tailor newly-introduced assets"
   narrows, honestly, to: *if the new baseline version introduces a new
   `architectureConvention`-kind asset key that didn't exist in the
   project's old pinned version, and no override already shadows it, run
   the existing detected-stack tailoring for it.* Every other
   newly-introduced key — including any future new `skills/*` file — simply
   has no override written, resolving to its bundled default exactly like
   any other unoverridden asset does today. This is not a gap in this
   proposal; it's the honest current ceiling of what `BaselineTailoringService`
   can produce, and the idea's own architectural-implications section
   already anticipated the tailoring mechanism might need generalizing
   later "with richer input" — this proposal is that first, narrow
   generalization (accepting a manifest instead of a hardcoded asset), not
   the final one.

3. **`BaselineTailoringService.tailorForDetectedStack` currently hardcodes
   a `0.3.0`-specific `BaselineAsset`** (`bundledPath:
   'assets/baseline/0.3.0/architecture_convention.md'`) rather than
   resolving the architecture-convention asset from whatever manifest is
   actually in play. That's fine for project creation (which always
   tailors against the version it just pinned), but an upgrade needs to
   tailor against the *new* version's manifest, which won't always be
   `0.3.0` once a future baseline version ships. This proposal generalizes
   the method's signature to take a `BaselineManifest` and resolve the
   `architectureConvention`-kind asset from it dynamically — a pure
   refactor of the existing method, not new behavior for the
   already-shipped creation-time call site (see §3 below).

## Data model changes

No new fields. `baselineVersion`'s doc comment is updated — it's no longer

```dart
@override
```

### `.aion/manifest.json` rewrite

Today only `CreateProjectCubit._initializeDesktopProject` writes this file
(`{"baselineVersion": "$baselineVersion"}`), once, at creation. The upgrade
flow needs to rewrite the same file later, from a different Cubit
(`ActiveProjectCubit`) — duplicating the exact path-construction +
JSON-write logic across two Cubits is unnecessary repetition of a
non-trivial detail (path separator handling, the `.aion` subdirectory).
Extracted into a tiny shared helper:

```dart
// core/build/project_manifest_writer.dart
/// Writes `<rootPath>/.aion/manifest.json`, creating the `.aion/`
/// directory if absent. The sole writer of this project marker file —
/// used both at project creation (`CreateProjectCubit`) and on a baseline
/// version upgrade (`ActiveProjectCubit.acceptBaselineUpgrade`).
class ProjectManifestWriter {
  static Future<void> write(String rootPath, String baselineVersion) async {
    final aionDir = Directory('$rootPath${Platform.pathSeparator}.aion')
      ..createSync(recursive: true);
    final manifest = File(
      '${aionDir.path}${Platform.pathSeparator}manifest.json',
    );
    await manifest.writeAsString('{"baselineVersion": "$baselineVersion"}');
  }
}
```

`CreateProjectCubit._initializeDesktopProject` is refactored to call this
instead of its own inline `File(...).writeAsStringSync(...)` — same
behavior, one fewer duplicated implementation.

### `BaselineTailoringService` (generalized + one new method)

```dart
/// Writes a project's `conventions/architecture-conventions` override
/// from [ProjectStackDetector]'s marker-file detection, resolving the
/// concrete asset (key, bundled path) from [manifest] rather than a
/// hardcoded version — used both at project creation (against the
/// version just pinned) and, via [tailorNewlyIntroducedAssets], during a
/// baseline upgrade (against the new version). No-ops if no stack is
/// detected, or if [manifest] has no `architectureConvention`-kind asset.
Future<void> tailorForDetectedStack({
  required String projectId,
  required String rootPath,
  required BaselineManifest manifest,
}) async {
  final detected = _detector.detect(rootPath);
  if (detected == null) return;

  // No `package:collection` dependency exists in pubspec.yaml today —
  // a plain loop instead of `.firstOrNull` avoids adding one for this.
  BaselineAsset? asset;
  for (final a in manifest.assets) {
    if (a.kind == BaselineAssetKind.architectureConvention) {
      asset = a;
      break;
    }
  }
  if (asset == null) return;

  final content = '...'; // unchanged template text
  await _baselineRepository.writeOverride(
    projectId: projectId,
    asset: asset,
    content: content,
  );
}

/// Called on a baseline version upgrade. Finds the
/// `architectureConvention`-kind asset in [newManifest], if any, whose
/// key did not exist at all in [oldManifest] — i.e. genuinely
/// newly-introduced by this version bump, not merely re-tailored. If
/// found and not already locally overridden, runs
/// [tailorForDetectedStack] against [newManifest]. No-ops otherwise: this
/// is the only asset kind [tailorForDetectedStack]'s template mechanism
/// can produce content for (see design.md's Corrections §2) — any other
/// newly-introduced key (a new `skills/*` file, say) is deliberately left
/// unoverridden, resolving to its bundled default like any other
/// unoverridden asset.
Future<void> tailorNewlyIntroducedAssets({
  required String projectId,
  required String rootPath,
  required BaselineManifest oldManifest,
  required BaselineManifest newManifest,
}) async {
  final oldKeys = oldManifest.assets.map((a) => a.key).toSet();
  BaselineAsset? newConventionAsset;
  for (final a in newManifest.assets) {
    if (a.kind == BaselineAssetKind.architectureConvention &&
        !oldKeys.contains(a.key)) {
      newConventionAsset = a;
      break;
    }
  }
  if (newConventionAsset == null) return;

  final overrides = await _baselineRepository.readOverrides(projectId);
  final alreadyOverridden = overrides.any(
    (o) => o.assetKey == newConventionAsset.key,
  );
  if (alreadyOverridden) return;

  await tailorForDetectedStack(
    projectId: projectId,
    rootPath: rootPath,
    manifest: newManifest,
  );
}
```

`CreateProjectCubit.submit` is updated to fetch the manifest it's already
resolved a version string for (`getManifest(resolvedVersion)`) before
calling `tailorForDetectedStack`, matching the new signature. No behavior
change at creation time — the resolved asset is the same one the old
hardcoded constant pointed at.

## Presentation layer

### `ActiveProjectState` (`ActiveProjectOpen` gains a second one-shot flag)

Exactly mirrors how `offerCodebaseAnalysis` was added
(`new-project-onboarding`) — both flags are independent, in-memory-only,
one-shot, and must not clobber each other when either is individually
consumed:

```dart
class ActiveProjectOpen extends ActiveProjectState {
  const ActiveProjectOpen(
    this.project, {
    this.offerCodebaseAnalysis = false,
    this.offerBaselineUpgrade = false,
  });

  final Project project;
  final bool offerCodebaseAnalysis;

  /// Whether `TicketsListScreen` should show the baseline-upgrade offer
  /// banner the next time it builds. `true` whenever [project]'s pinned
  /// `baselineVersion` isn't the latest version bundled in the running
  /// build — recomputed fresh on every `ActiveProjectCubit.switchTo` call,
  /// never persisted, so declining only dismisses the current instance:
  /// the same check re-runs (and the banner reappears) the next time this
  /// project is switched into, for as long as a newer version remains
  /// available.
  final bool offerBaselineUpgrade;

  @override
  List<Object?> get props => [project, offerCodebaseAnalysis, offerBaselineUpgrade];
}
```

### `ActiveProjectCubit`

Gains two new constructor dependencies — `BaselineRepository` and
`BaselineTailoringService` (both already constructed elsewhere in the app:
`BaselineRepository` is already a root `RepositoryProvider` in `main.dart`;
`BaselineTailoringService` is constructed inline wherever needed, same
pattern as its existing `/hub/new` route call site):

```dart
ActiveProjectCubit(
  this._repository,
  this._baselineRepository,
  this._baselineTailoringService,
) : super(const ActiveProjectNone());
```

`switchTo` computes the offer flag fresh on every call:

```dart
Future<void> switchTo(
  Project project, {
  bool offerCodebaseAnalysis = false,
}) async {
  final previous = activeProject;
  emit(ActiveProjectSwitching(from: previous, to: project));

  final now = DateTime.now();
  await _repository.updateLastOpened(project.id, now);

  final versions = await _baselineRepository.getAvailableBaselineVersions();
  final offerBaselineUpgrade = project.baselineVersion != versions.last;

  emit(
    ActiveProjectOpen(
      _withLastOpened(project, now),
      offerCodebaseAnalysis: offerCodebaseAnalysis,
      offerBaselineUpgrade: offerBaselineUpgrade,
    ),
  );
}
```

New `consumeBaselineUpgradeOffer()`, mirroring `consumeCodebaseAnalysisOffer()`
exactly (preserving the *other* flag untouched):

```dart
void consumeBaselineUpgradeOffer() {
  final current = state;
  if (current is! ActiveProjectOpen || !current.offerBaselineUpgrade) return;
  emit(
    ActiveProjectOpen(
      current.project,
      offerCodebaseAnalysis: current.offerCodebaseAnalysis,
    ),
  );
}
```

New `acceptBaselineUpgrade()` — the whole accept action, callable both from
the banner and from the Settings manual action:

```dart
/// Bumps [activeProject]'s pinned baseline to the latest bundled version:
/// updates the registry DB row, rewrites `.aion/manifest.json` (desktop
/// only), and tailors any newly-introduced `architectureConvention`-kind
/// asset (desktop only — see `BaselineTailoringService
/// .tailorNewlyIntroducedAssets`). A no-op if the current state isn't
/// [ActiveProjectOpen] or the project is already pinned to the latest
/// version. Re-emits [ActiveProjectOpen] with the bumped project and
/// [ActiveProjectOpen.offerBaselineUpgrade] cleared.
Future<void> acceptBaselineUpgrade() async {
  final current = state;
  if (current is! ActiveProjectOpen) return;
  final project = current.project;

  final versions = await _baselineRepository.getAvailableBaselineVersions();
  final newVersion = versions.last;
  if (newVersion == project.baselineVersion) return;

  final oldManifest = await _baselineRepository.getManifest(
    project.baselineVersion,
  );
  final newManifest = await _baselineRepository.getManifest(newVersion);

  await _repository.updateBaselineVersion(project.id, newVersion);

  final rootPath = project.rootPath;
  if (rootPath != null) {
    await ProjectManifestWriter.write(rootPath, newVersion);
    await _baselineTailoringService.tailorNewlyIntroducedAssets(
      projectId: project.id,
      rootPath: rootPath,
      oldManifest: oldManifest,
      newManifest: newManifest,
    );
  }

  emit(
    ActiveProjectOpen(
      _withBaselineVersion(project, newVersion),
      offerCodebaseAnalysis: current.offerCodebaseAnalysis,
    ),
  );
}
```

Mobile/web projects (`rootPath == null`) still get the registry-DB bump —
harmless and keeps `Project.baselineVersion` truthful — but skip the
manifest rewrite and tailoring step, matching the existing
override-system's desktop-only gating (`readOverrides`/`writeOverride`
already no-op without a `rootPath`). In practice this is close to
invisible either way: `conventions/architecture-conventions` and
`skills/verify` are only ever read into a model prompt by the
coding-execution flow, which is desktop-only already.

### `ActiveProjectProvider` contract (`core/contracts/`)

Gains the same three members, so any feature can trigger/observe the
upgrade without importing `features/projects/` directly (Pattern 1, same
as `offerCodebaseAnalysis`/`consumeCodebaseAnalysisOffer` already do):

```dart
bool get offerBaselineUpgrade;
void consumeBaselineUpgradeOffer();
Future<void> acceptBaselineUpgrade();
```

### `BaselineUpgradeBanner` (new widget, `features/tickets/presentation/widgets/`)

Shown on `TicketsListScreen` the same way `CodebaseAnalysisBanner` already
is — same insertion point (between the header and the search/filter row),
same `_BannerShell` visual language (reused directly, not duplicated: it's
already a shared private widget in `codebase_analysis_banner.dart` — if
`/design-sync` calls for it, this is a natural moment to hoist `_BannerShell`/
`_IconChip`/`_DismissButton` into a small shared file both banners import,
rather than copy-pasting them a second time). Two states only — no
running/done/failed progression, since the idea's Q3 explicitly resolved
"no diff/review UI, straight bump":

- **Offer state:** icon chip (`PhosphorIcons.arrowUpLight` in
  `c.signalIconTint`/`c.typeSignal`, mirroring `_OfferBanner`'s notice
  treatment), title + one-line body naming the target version (e.g. "A
  newer baseline (v0.3.0) is available."), a primary "Upgrade" button and
  a dismiss × (dismiss calls the same `onDismiss` callback
  `TicketsListScreen` already threads through for `CodebaseAnalysisBanner`,
  just hiding this banner locally — no cubit state change beyond the
  `consumeBaselineUpgradeOffer()` that already fired in `initState`).
- **Upgrading state:** entered the instant "Upgrade" is tapped — a
  spinner + "Upgrading…" status line (mirrors `_RunningBanner`'s shell,
  no "Hide" control since this step is near-instant local I/O, not a
  long-running model turn). On completion, the banner is dismissed by its
  parent exactly like the offer state's dismiss path — no separate
  "done" confirmation state; the version now shown wherever
  `project.baselineVersion` is rendered (`ProjectCard`, the new Settings
  section) is confirmation enough.

```dart
class BaselineUpgradeBanner extends StatefulWidget {
  const BaselineUpgradeBanner({super.key, required this.onDismiss, required this.targetVersion});
  final VoidCallback onDismiss;
  final String targetVersion;
  @override
  State<BaselineUpgradeBanner> createState() => _BaselineUpgradeBannerState();
}

class _BaselineUpgradeBannerState extends State<BaselineUpgradeBanner> {
  bool _isUpgrading = false;

  Future<void> _accept() async {
    setState(() => _isUpgrading = true);
    await context.read<ActiveProjectProvider>().acceptBaselineUpgrade();
    if (!mounted) return;
    widget.onDismiss();
  }

  @override
  Widget build(BuildContext context) {
    return _isUpgrading ? _UpgradingBanner() : _OfferBanner(
      targetVersion: widget.targetVersion,
      onAccept: _accept,
      onDismiss: widget.onDismiss,
    );
  }
}
```

### Settings screen — manual "Upgrade baseline" action

New `BaselineUpgradeCubit` (route-scoped, provided alongside the other
Settings cubits), thin by design — the actual upgrade logic already lives
on `ActiveProjectCubit.acceptBaselineUpgrade()`; this cubit only merges
"current version" + "latest available version" into a UI-ready state and
forwards the accept call:

```dart
sealed class BaselineUpgradeState extends Equatable { ... }
class BaselineUpgradeLoading extends BaselineUpgradeState { ... }
class BaselineUpgradeReady extends BaselineUpgradeState {
  const BaselineUpgradeReady({
    required this.currentVersion,
    required this.latestVersion,
    this.isUpgrading = false,
  });
  final String currentVersion;
  final String latestVersion;
  final bool isUpgrading;
  bool get isUpToDate => currentVersion == latestVersion;
}

class BaselineUpgradeCubit extends Cubit<BaselineUpgradeState> {
  BaselineUpgradeCubit(this._baselineRepository, this._activeProjectProvider)
      : super(const BaselineUpgradeLoading());

  final BaselineRepository _baselineRepository;
  final ActiveProjectProvider _activeProjectProvider;

  Future<void> load() async {
    emit(const BaselineUpgradeLoading());
    final versions = await _baselineRepository.getAvailableBaselineVersions();
    final project = _activeProjectProvider.activeProject!;
    emit(BaselineUpgradeReady(
      currentVersion: project.baselineVersion,
      latestVersion: versions.last,
    ));
  }

  Future<void> upgrade() async {
    final current = state;
    if (current is! BaselineUpgradeReady || current.isUpToDate) return;
    emit(BaselineUpgradeReady(
      currentVersion: current.currentVersion,
      latestVersion: current.latestVersion,
      isUpgrading: true,
    ));
    await _activeProjectProvider.acceptBaselineUpgrade();
    final project = _activeProjectProvider.activeProject!;
    emit(BaselineUpgradeReady(
      currentVersion: project.baselineVersion,
      latestVersion: current.latestVersion,
    ));
  }
}
```

`SettingsScreen` gains a new "BASELINE" eyebrow section (`_BaselineUpgradeSection`),
placed after the existing "OVERRIDES" section, following
`_OverridesSummarySection`'s exact shape (short description + one
`AppButton`): shows "Current version: v{currentVersion}" and either "Your
baseline is up to date" (`isUpToDate`) or an enabled "Upgrade to v{latestVersion}"
button (disabled + spinner-labeled while `isUpgrading`).

`/workspace/settings`'s `MultiBlocProvider` in `app_router.dart` gains:

```dart
BlocProvider<BaselineUpgradeCubit>(
  create: (context) => BaselineUpgradeCubit(
    context.read<BaselineRepository>(),
    context.read<ActiveProjectProvider>(),
  )..load(),
),
```

## Data flow (accept path)

```
TicketsListScreen (BaselineUpgradeBanner, offer state)
  │ user taps "Upgrade"
  ▼
ActiveProjectProvider.acceptBaselineUpgrade()   [== ActiveProjectCubit]
  │
  ├─ BaselineRepository.getAvailableBaselineVersions() → newVersion
  ├─ BaselineRepository.getManifest(oldVersion), getManifest(newVersion)
  ├─ ProjectRepository.updateBaselineVersion(id, newVersion)   [registry DB]
  ├─ if rootPath != null:
  │    ├─ ProjectManifestWriter.write(rootPath, newVersion)     [.aion/manifest.json]
  │    └─ BaselineTailoringService.tailorNewlyIntroducedAssets(
  │         oldManifest, newManifest)
  │         → writeOverride(...) only if a new architectureConvention
  │           asset was introduced and isn't already overridden
  └─ emit ActiveProjectOpen(project.copyWith(baselineVersion: newVersion),
       offerBaselineUpgrade: false)
       │
       ▼
BaselineUpgradeBanner.onDismiss() → removed from TicketsListScreen
ProjectCard / Settings "Current version" now read the bumped value
```

The manual Settings path is identical from `ProjectRepository.
updateBaselineVersion` onward — `BaselineUpgradeCubit.upgrade()` calls the
exact same `ActiveProjectProvider.acceptBaselineUpgrade()`, just triggered
from a different entry point with no one-shot flag involved.

## Edge cases

- **Project already on the latest version when Settings is opened.**
  `BaselineUpgradeReady.isUpToDate` is `true`; the button doesn't render
  (or renders disabled with "up to date" copy) — `acceptBaselineUpgrade()`
  itself also guards this (`newVersion == project.baselineVersion` early
  return) as a second line of defense, since the banner's own trigger
  condition normally prevents this path from being reachable via the
  banner at all.
- **Mobile/web project.** Registry DB bumps normally; manifest
  rewrite/tailoring is skipped (`rootPath == null`). The Settings section
  and banner both still work, since neither depends on `rootPath` to
  display/trigger — only the accept path's second half branches on it.
- **Switching away from the project before the offer is consumed.**
  Unchanged from `offerCodebaseAnalysis`'s existing behavior — the flag is
  purely in-memory on the current `ActiveProjectOpen` state; switching
  projects emits a fresh `ActiveProjectSwitching`/`ActiveProjectOpen` pair
  and the old flag value is simply gone, recomputed fresh next time this
  project is switched back into.
- **Orphaned override after a key is removed.** Already the existing
  `readOverrides` behavior — `bundled_baseline_repository.dart`'s
  `_assetKeyFromFileName`/`keyBySegment` fallback already handles a file
  whose key no longer matches any manifest asset (falls back to the bare
  file-name segment) without throwing. Nothing new needed here; this
  proposal just confirms it and doesn't add cleanup.

# Aion — Baseline Version Upgrade — Design Spec

Implementation-ready spec for a Flutter developer. Mockups: [Aion Baseline Upgrade Mockups](./Aion%20Baseline%20Upgrade%20Mockups.dc.html).

**Hard constraint — no Material widgets.** Build everything from plain Flutter primitives (`DecoratedBox`, `Container`, `GestureDetector`, `MouseRegion`, `Row`/`Column`, `Stack`, `CustomPaint`). Do not use `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `AppBar`, `SnackBar`, `CircularProgressIndicator`, `InkWell`, or any other Material-library type. Reuse the existing app primitives (`AppButton`, `AppSpinner`) noted below.

Colors are accessed via `ThemeScope.of(context).colors` (`AionColors`). `isDark` is `true` for **Obsidian**, `false` for **Arctic**. Translucent fills are written `token.withOpacity(x)` in this spec for readability; transcribe to `token.withValues(alpha: x)` per the codebase convention.

---

## 0. Summary & scope

Two additions, no new screens:

1. **`BaselineUpgradeBanner`** — a lazy, one-time offer banner on `TicketsListScreen`, in the same slot as `CodebaseAnalysisBanner` (both may be visible, stacked). Two states: `offer`, `upgrading`. Accepting bumps the pinned baseline version immediately (no diff/review). Dismissing hides it for this open only.
2. **Settings "BASELINE" section** — a permanent, always-available manual upgrade action on `SettingsScreen`, placed after the "OVERRIDES" section.

### 0.1 State model

```dart
// Newer default baseline availability for the current project.
enum BaselineUpgradeState { offer, upgrading }

// Banner visibility is per-open (lazy, one-time-per-open), not persisted-dismissed forever:
//   project.baselineOfferSeenThisOpen  -> bool (in-memory, reset each project open)
//   project.pinnedBaselineVersion      -> String  e.g. "v0.2.0"
//   Aion.latestBaselineVersion         -> String  e.g. "v0.3.0"
// Banner shows on the first open where pinnedBaselineVersion < latestBaselineVersion
// AND baselineOfferSeenThisOpen == false. Dismiss sets baselineOfferSeenThisOpen = true.
// It can reappear on a later open (unlike CodebaseAnalysisBanner's persisted once-only flag).
```

### 0.2 Tint family choice

The banner uses the existing **`notice*`** tint family (primary-toned), **not** the `signal*` (typeSignal/teal) family. Rationale: a baseline upgrade is a general product-version notice tied to the app's primary identity, not a `signal`-ticket scan. Using `notice*` also keeps it visually distinct from the teal `CodebaseAnalysisBanner` when both are stacked. The `upgrading` state uses the existing **`pending*`** family ("active but calm"), consistent with other in-progress affordances. **No new tokens are introduced.**

### 0.3 Tokens referenced (all pre-existing)

| Helper | Formula | Used for |
|---|---|---|

## 3. Behavior notes

- **Immediate bump:** tapping "Upgrade" (banner or Settings) performs the version bump with no diff/review step. UI enters the `upgrading` state, then resolves.
- **Lazy, per-open offer:** the banner is evaluated on project open. It shows only when `pinnedBaselineVersion < latestBaselineVersion` and `baselineOfferSeenThisOpen == false`. Dismiss sets `baselineOfferSeenThisOpen = true` (in-memory) — it can reappear on a later open. This differs from `CodebaseAnalysisBanner`, which is persisted-once-only.
- **Settings is always available:** the BASELINE section is present regardless of banner state; when already latest it shows §2.4.
- **Transitions:** banner mount/unmount = `AnimatedSize` + `FadeTransition` `180ms easeOut`; `offer → upgrading` = `AnimatedSwitcher` crossfade `200ms easeInOut` over the fixed-size shell.
- **Stacking:** when both `BaselineUpgradeBanner` and `CodebaseAnalysisBanner` are present, `BaselineUpgradeBanner` renders **first** (top), separated by `AionSpacing.sp12`.
- **No Material:** spinner = `AppSpinner` (`CustomPaint`); buttons = `AppButton`; banners = `DecoratedBox` + `Column`/`Row`/`Stack`; dismiss = `GestureDetector` + `MouseRegion`. No `SnackBar`, `Card`, `ElevatedButton`, `CircularProgressIndicator`.
