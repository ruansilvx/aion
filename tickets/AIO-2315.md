# Ticket Search Filters

# Proposal: Ticket Search & Filters

## Problem

`aion-arch/specs/tickets.md`'s own known-gaps list flags this: "No search,
filtering, or sorting on the ticket list (the board's type-filter to
task/story is fixed, not a user-facing filter control)." In practice it's
worse than "missing" — `TicketsListScreen`'s search box
(`tickets_list_screen.dart:164-193`) already renders a magnifying-glass
icon and "Search tickets" hint text, but it's pure UI chrome: no
`TextField`, no `onChanged`, no state. `TicketsCubit.loadTickets()` always
calls `TicketRepository.getAllTickets()`, which always returns every
ticket ordered by `created_at desc` — no query parameters exist anywhere
in `TicketDao`/`TicketRepository`. A user typing into that box today gets
no feedback and no filtering, ever.

Flagged by `/explore ticket list search filtering` (2026-07-15). Because
every Aion entity — epic, story, task, resource, page, chat — is modelled
as a ticket, ticket volume is expected to grow well beyond what a
personal to-do list would see. That ruled out the cheaper option (loading
everything and filtering client-side, the pattern this codebase already
uses elsewhere — see [Out of scope](#out-of-scope)) in favor of a
database-level approach that stays fast as the table grows.

## Goal

Make the existing search box and a new set of filter controls actually
work, with a design that holds up at high ticket volume:

1. Structured filtering by status, type, and priority.
2. Free-text search over title and description.
3. Both combine (ANDed) and both query the database directly rather than
   filtering an in-memory list.

## Approach

**Structured filters** (status/type/priority) are plain indexed `WHERE`
clauses against `TicketsTable` — exact-match, low-cardinality columns,
the standard tool for the job. New SQL indexes on `status`, `type`, and
`priority` keep these fast regardless of table size.

**Free-text search** (title/description) uses SQLite's **FTS5** extension
— a full-text index that stays fast at scale, unlike `LIKE '%query%'`
(which can't use an index and degrades to a full table scan as the table
grows). Built as an **external-content** FTS5 virtual table (indexes the
text without duplicating it — `tickets` stays the only place `title`/
`description` are actually stored), kept in sync via `INSERT`/`UPDATE`/
`DELETE` triggers on `tickets`, and ranked by SQLite's built-in `bm25()`
relevance function so the best match shows first instead of results
appearing in arbitrary order.

**WASM FTS5 support is already confirmed**, not assumed. The actual
binary this project ships — `aion/web/sqlite3.wasm` (sqlite3 v3.3.3,
drift v2.34.0) — was inspected directly and contains `fts5_api_ptr`,
`fts5_get_locale`, `fts5_source_id`, `fts5vocab`, and all three built-in
tokenizers (`unicode61`, `porter`, `trigram`). These are internal FTS5
symbols that only exist in a binary compiled with
`-DSQLITE_ENABLE_FTS5` — static, but strong, evidence. `tasks.md`'s first
task is still a live `CREATE VIRTUAL TABLE ... USING fts5(...)` smoke
test before anything is built on top of it, per this project's own
"test drift on web early" convention (`project.md`).

This requires a schema version bump (`AppDatabase.schemaVersion`: 1 → 2)
and drift's first-ever migration (`onUpgrade`), since no schema change
has happened since the v1 slice. See `design.md` for the exact migration,
trigger, and query shape.

## Out of scope

- **`TicketsCubit.getValidParentCandidates` / `TicketParentPicker`
  (ticket-detail's reparent picker).** This picker already has its own
  search field, but it works the way the main ticket list search *used*
  to look like it should work: `getValidParentCandidates` calls
  `getAllTickets()` and walks the whole list in memory to exclude
  self/descendants, and `TicketParentPicker` fetches that list once and
  re-filters it locally on every keystroke (`.contains()` on
  ticketId/title, no debounce, no async state). Converting this to a
  DB-level query isn't a small extension of the work here — it needs a
  `WITH RECURSIVE` CTE to compute the descendant-exclusion set in SQL
  (new SQL machinery this change doesn't otherwise need), plus a rework
  of the picker's fetch-once-filter-locally interaction model into a
  debounced async one. Logged as a known gap in `specs/spec.md` instead
  of folded into this change's scope.
- **Sorting.** The known-gaps bullet this change addresses mentions
  "sorting" alongside search/filtering, but no sort control is being
  added here. Results stay ordered by `bm25()` relevance when a text
  query is active, or by `created_at desc` (today's existing order)
  otherwise. A user-facing sort control (by priority, due date, etc.) is
  left as a narrowed known gap.
- **Semantic/similarity search.** `Ticket.embedding` and the
  brute-force-cosine-similarity system in `project.md`'s Storage Model
  foundational decision are a separate, still-unbuilt feature ("find
  conceptually similar tickets"). This change is lexical keyword search
  ("find tickets containing this word") — the two are complementary, not
  overlapping.
- **Board view's fixed type filter.** `TicketBoardView` still only ever
  receives task/story tickets from `_buildTicketsBody`, unchanged. The
  new type filter is still honored while in board view — selecting a
  type outside `{task, story}` while board view is active is expected to
  produce an empty board (the type filter and the board's own fixed
  restriction both apply, ANDed), matching how a narrow search already
  can outnumber-empty the board today. No special-case guard is added
  for this; it's the same intersection behavior the screen already has.
