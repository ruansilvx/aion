# Offer the choice at project-creation time

Extend `NewProjectScreen`/`CreateProjectCubit`'s existing
`GitignoreConfirmationBanner`/`appendGitignore` first-run moment to also
offer a dedicated tickets repo, rather than adding a second, separate
toggle. Local-only `git init` for a fresh project (no remote
auto-provisioning -- out of scope, see epic).

## Technical shape

Two layers, in dependency order:

1. **CreateProjectCubit/domain** -- `CreateProjectCubit.submit` gains a
   new parameter (name TBD at implementation, e.g.
   `separateTicketsRepo: bool = false`) alongside the existing
   `appendGitignore`. When `true` (desktop only), `_initializeDesktopProject`
   sets up a local-only tickets repo at a fixed convention path --
   `<rootPath>/.aion/tickets-repo` (already inside the `.aion/` tree
   that's gitignored from the source repo by the existing
   `appendGitignore` flow, so no extra exclusion logic needed), runs
   `git init` there, and the created `Project` gets `ticketsRootPath`
   set to that path. `false` (the default) preserves today's behavior
   exactly -- `ticketsRootPath` stays unset. No remote provisioning --
   local-only `git init`, per the epic's stated out-of-scope.
2. **UI** -- `NewProjectScreen`/`GitignoreConfirmationBanner` surfaces
   this as a choice in the same first-run moment as the existing
   gitignore checkbox, per the epic's "extend the existing banner
   rather than a second, separate toggle" framing.

## Design gate: PENDING

Layer 2 is real user-facing UI work (a new option inside
`GitignoreConfirmationBanner`, new copy, a visual decision about how it
reads alongside the existing checkbox) -- per this project's design-gate
convention, it needs a `/design-brief` -> Claude Design -> `/design-sync`

## Revision — remote URL support (corrects the original scope above)

The "no remote auto-provisioning -- out of scope" framing above and in
the Technical shape's item 1 was a mistake made during `/propose`,
never actually confirmed with the user. Corrected: a fresh project's
separate tickets repo can now be pointed at a user-supplied existing
remote URL. If none is given, it still falls back to a local-only repo
(same as the original framing) -- so `false`/unset stays fully
backward compatible, only the "no remote, ever" framing was wrong.

Implemented in AIO-2856 (already revised): `CreateProjectCubit.submit`
gained `ticketsRepoRemoteUrl` (optional) alongside `separateTicketsRepo`
-- when given, `GitRepositoryClient.addRemote` configures it as the new
tickets repo's `origin` (no push at creation time -- nothing to push
yet). AIO-2857's design brief has been corrected and resent to reflect
this (the new repo needs a way to enter/paste that URL, not just a
checkbox).

## Design gate: PENDING (design-sync findings, revision needed)

`/design-sync` validated the export pasted into AIO-2858 against the
actual codebase (not just read at face value). Concrete mismatches
found -- send back to Claude Design for a revision before AIO-2857's
`/apply` proceeds:

1. `AppTextField` (lib/design_system/atoms/app_text_field.dart) is a
   real, fixed-styling component -- `AionRadius.lg`, `EdgeInsets
   .symmetric(horizontal: 14, vertical: 12)`, `AionShadows.focus`-based
   focus state. The export's "compact variant" (`sm+2`→`10` radius,
   `12/9` padding, custom border+ring focus) doesn't exist and isn't
   reviewed scope to add.
2. The custom "Optional" qualifier row reinvents `AppTextField`'s
   built-in `isOptional: true` flag, which already renders this via the
   existing `commonOptionalMarker` l10n key.
3. The l10n plan cites keys that don't match
   lib/l10n/app_en.arb: real keys are `newProjectGitignoreBannerTitle`/
   `...BodyBefore/Middle/After`/`...CheckboxLabelBefore/Middle/After`
   (a 3-key-plus-inline-WidgetSpan split), not the single consolidated
   keys the export names. That split exists because generated l10n
   methods return plain `String` and can't take a `WidgetSpan` (the
   monospace path chip) as an ICU placeholder -- the export's new keys
   (e.g. `"Add {aionPath} to {gitignorePath}"`) need the same
   Before/Middle/After treatment, not a single parameterized string.
4. `noticeDivider`'s proposed code uses `withOpacity`, not
   `withValues(alpha:)` -- every sibling token in `AionColorsHubTokens`
   (aion_colors.dart) uses the latter.
5. §6's wiring claim doesn't match AIO-2856's actual cubit code:
   `_initializeDesktopProject` always passes `['.aion/', 'tickets/']`
   to `_gitignoreEditor.ensureIgnored` regardless of
   `separateTicketsRepo` -- it does NOT narrow to `.aion/`-only. Harmless
   (ignoring a path that won't exist) but contradicts the label
   AIO-2857 would show the user unless fixed alongside (a small
   follow-up to AIO-2856, conditioning that list on
   `ticketsRootPath != null`).
6. Minor/non-blocking: `AppTextField` does wrap a Material `TextField`
   internally (the one sanctioned exception, per design.md) -- the
   export's "never a Material TextField" phrasing is imprecise, though
   its intent (use `AppTextField`, don't hand-build one) is correct.
