# Design: Workflow Skill Attachments (Phase 2)

## §1. Domain layer

### §1.1. `SkillAttachmentKind`

New file `domain/enums/skill_attachment_kind.dart`:

```dart
/// Which of the two Phase 2 attachment mechanisms a [SkillAttachment]
/// uses — see `aion-arch/changes/workflow-skill-attachments/design.md`
/// §1.2.
enum SkillAttachmentKind {
  /// Renders a project-authored [WorkflowPromptTemplate] against the
  /// triggering ticket and runs it text-only, exactly like today's
  /// hardcoded `_assembleStageContext` prompts.
  aionNativeTemplate,

  /// Sends `/<skillName>` as the run's prompt, tool-enabled, so the
  /// underlying coding agent's own discovered `.claude/skills/<skillName>`
  /// skill executes. Confirmed viable by the 2026-08-19 spike documented
  /// in `aion-arch/ideas/configurable-workflow-and-automation-engine.md`.
  delegatedSkill,
}
```

### §1.2. `SkillAttachment` entity

New file `domain/entities/skill_attachment.dart`:

```dart
class SkillAttachment extends Equatable {
  final String id;                    // UUID v4
  final String? workflowStatusId;     // WorkflowStatus.id this attaches to
  final SddStage? sddStage;           // SddStage this attaches to
  final SkillAttachmentKind kind;
  final String? templateId;           // WorkflowPromptTemplate.id — kind == aionNativeTemplate only
  final String? skillName;            // literal skill name, no leading '/' — kind == delegatedSkill only
  final AutomationConfidence confidence;
  // ... const constructor, props, copyWith, per project.md's dartdoc rule
}
```

Exactly one of `workflowStatusId`/`sddStage` is non-`null` (what this
attachment is *for*); exactly one of `templateId`/`skillName` is
non-`null`, matching `kind` (what it *runs*). Both invariants are
enforced by `WorkflowConfigCubit`, never the repository or the entity
itself — this entity performs no validation, mirroring `WorkflowStatus`'s
own precedent.

### §1.3. `WorkflowPromptTemplate` entity

New file `domain/entities/workflow_prompt_template.dart`:

```dart
class WorkflowPromptTemplate extends Equatable {
  final String id;          // UUID v4
  final String name;        // human label, e.g. "Repro Steps Request"
  final String body;        // plain text with {{variable}} placeholders
  // ... const constructor, props, copyWith
}
```

`name` is unique project-wide (a flat namespace — templates aren't
scoped per status/stage the way `WorkflowStatus` names are, since one
template may be reused by more than one attachment).

### §1.4. Template variable substitution

New pure function, `domain/utils/render_workflow_prompt_template.dart`:

```dart
/// Substitutes every `{{variable}}` placeholder in [template.body]
/// against [ticket], leaving an unrecognized placeholder's literal text
/// untouched (defensive — a template referencing a since-removed
/// variable degrades to visible text instead of throwing). Supported
/// variables: `ticket.title`, `ticket.description`, `ticket.type`,
/// `ticket.status`, `ticket.priority`. No loops, conditionals, or nested
/// lookups — deliberately the simplest substitution that satisfies the
/// idea file's "Aion-native prompt/workflow template" want (see
/// proposal.md's Non-goals).
String renderWorkflowPromptTemplate(WorkflowPromptTemplate template, Ticket ticket);
```

### §1.5. `WorkflowSkillAttachmentRepository` interface

New file `domain/repositories/workflow_skill_attachment_repository.dart`

### §2.3. `app_database.dart` — schema 15 → 16

Add both tables to `@DriftDatabase(tables: [...])`. New
`MigrationStrategy` branch:

```dart
onCreate: (m) async {
  await m.createAll();
  // ...existing seeds, including workflowStatusDao.seedDefaultsIfEmpty()...
  // no seed needed here — an empty attachment/template table is the
  // correct starting state (Phase 1's seeded-defaults precedent doesn't
  // apply: there is no pre-configuration attachment behavior to
  // reproduce, since nothing fires automatically today outside the
  // already-unconditional SddStage flow).

```

## §3. `TicketsCubit` integration

### §3.1. Cached attachment list

A new in-memory cache, `_skillAttachments` (`List<SkillAttachment>`,
defaulting to `const []` — the correct empty baseline, since Phase 1's
`defaultWorkflowStatuses`-style seeded-default pattern doesn't apply
here), loaded once at construction and refreshed on
`WorkflowSkillAttachmentRepository.onChanged`, exactly mirroring
`_workflowStatuses`'s existing refresh pattern. Two new private helpers:

```dart
SkillAttachment? _attachmentForStatus(String workflowStatusId) =>
    _skillAttachments.where((a) => a.workflowStatusId == workflowStatusId).firstOrNull;

SkillAttachment? _attachmentForStage(SddStage stage) =>
    _skillAttachments.where((a) => a.sddStage == stage).firstOrNull;
```

`WorkflowSkillAttachmentRepository`/`WorkflowPromptTemplateRepository`
are optional `TicketsCubit` constructor parameters, following
`WorkflowStatusRepository`'s own established optional-dependency
convention (omitting them pins `_skillAttachments` to `const []`
forever — every existing construction site that doesn't care about
attachments is unaffected).

### §3.2. Shared firing primitive

New private method, generalizing `_createStageChat`/`_runStageChatTurn`'s
existing two-phase (create-chat-then-unawaited-run) shape to any
`SkillAttachment`:

```dart
/// Builds the run prompt for [attachment] against [parent] — either
/// rendering its [WorkflowPromptTemplate] (aionNativeTemplate) via
/// [renderWorkflowPromptTemplate], or `/<skillName>` (delegatedSkill).
Future<String> _promptFor(SkillAttachment attachment, Ticket parent) async { ... }

/// Spawns a chat ticket titled '<attachment kind label> — <parent.title>'
/// as a child of [parent], posts [_promptFor]'s result as a system
/// comment, and runs it via ChatCubit.runChatTurn — toolsEnabled/
/// workingDirectory set per attachment.kind (see design §3.2 table
/// below). Mirrors _createStageChat + _runStageChatTurn's exact shape,
/// generalized to any SkillAttachment rather than an SddStage. A hard
/// error is caught and posted as a "Skill attachment failed: <e>" system
/// comment (mirrors _runStageChatTurn's own catch-comment shape).
Future<void> _fireSkillAttachment(Ticket parent, SkillAttachment attachment) async { ... }
```

| `attachment.kind` | `toolsEnabled` | `workingDirectory` |
|---|---|---|
| `aionNativeTemplate` | `false` | `null` |
| `delegatedSkill` | `true` | the active project's checkout path (same resolution `_runCodingExecution` already uses) |

### §3.3. Confidence-gated firing

New private helper resolving how an attachment fires, called from both
hook points below:

```dart
Future<void> _resolveAndFireAttachment(Ticket parent, SkillAttachment attachment) async {
  switch (attachment.confidence) {
    case AutomationConfidence.auto:
      unawaited(_fireSkillAttachment(parent, attachment));
    case AutomationConfidence.gated:
      _pendingSkillAttachments[parent.id] = attachment; // new Map<String, SkillAttachment>
      // re-emits TicketDetailLoaded with a new pendingSkillAttachment field
      // if parent's detail screen is currently open, mirroring
      // _refreshDetailIfOpenAndAffected's existing pattern
    case AutomationConfidence.manual:
      break; // no-op; runAttachedSkillManually is the only trigger
  }
}
```

New public methods, mirroring `confirmPendingToolProposal`/
`rejectPendingToolProposal`'s existing shape (§ mid-task-chat-branching):

```dart
Future<void> confirmPendingSkillAttachment(String ticketId);  // fires it, clears the pending entry
void rejectPendingSkillAttachment(String ticketId);           // clears the pending entry, never fires

/// Always-available manual trigger — no-ops if [ticket]'s resolved
/// status/stage attachment (if any) has confidence other than `manual`,
/// or has none at all.
Future<void> runAttachedSkillManually(Ticket ticket);
```

### §3.4. Hook points

**`WorkflowStatus` entry** — `updateTicketStatus`/`updateStatusForTickets`
gain a new check, symmetric to the existing `executionTrigger`-role
check already there: after a successful status write, resolve
`_resolveStatus(status)?.id` and look it up via `_attachmentForStatus`;
if found, call `_resolveAndFireAttachment`.

**`SddStage` entry** — `_createStageChat`/`_runStageChatTurn` gain a
branch at the top: if `_attachmentForStage(stage)` returns non-`null`,
use `_promptFor(attachment, parent)` in place of
`_assembleStageContext(parent, stage)`, and the attachment's own
`confidence` in place of today's unconditional-fire behavior (routing
through `_resolveAndFireAttachment` instead of the direct `unawaited`
call `advanceSddStage` makes today). No attachment configured for
`stage` ⇒ identical code path to today, unconditional, no confidence
check — the default baseline stays exactly as it is.

Existing `WorkflowConfigCubit` (Phase 1) gains attachment/template CRUD
alongside its existing status/stage-settings methods:

```dart
Future<void> createAttachment(SkillAttachment attachment);

```

`WorkflowConfigCubit`'s constructor gains
`WorkflowSkillAttachmentRepository`/`WorkflowPromptTemplateRepository`
parameters. `WorkflowConfigState.WorkflowConfigLoaded` gains
`attachments`/`templates` fields; `load()` fetches both alongside its
existing statuses/stage-settings reads.

# Aion — Workflow Skill Attachments (Phase 2): Component Spec

Implementation-ready spec for **Workflow Skill Attachments** — a project can attach an automated *skill* to any ticket workflow **status** or **SDD stage**, so entering that status/stage fires an AI-driven action. Each attachment is one of two **kinds** (a project-authored **Template** prompt, or a **Delegated skill** — a literal call into the coding agent's own named skill) and carries one of three **confidence** levels that decide *how* it fires: **Auto** (fires silently), **Gated** (fires only after in-ticket confirmation), **Manual** (fires only on an explicit button tap).

This feature **extends** the existing [`WorkflowStatusSettingsScreen`](./Aion%20Configurable%20Ticket%20Workflow%20Spec.md) — it is not a redesign of it. It adds:
1. an **attachment indicator + inline edit form** to each status/stage row on that screen (§2–§4),
2. one **new screen**, `WorkflowPromptTemplatesScreen` (§5),
3. two small **ticket-detail-screen additions** — a gated-confirmation banner (§6) and a manual-run button (§7).

**No Material widgets or types anywhere.** Every component below is built from `flutter/widgets.dart` primitives only: `DecoratedBox`, `Container`, `GestureDetector`, `MouseRegion`, `FocusableActionDetector`, `CustomPaint`, `Row`, `Column`, `Align`, `Padding`, `AnimatedContainer`/`AnimatedAlign` (transitions), `AnimatedSize` (form expand/collapse), and `Overlay`/`OverlayEntry`/`CompositedTransformFollower` for the template picker dropdown. **Never** `Card`, `ElevatedButton`, `Scaffold`, `AppBar`, `ListTile`, `InkWell`, `Switch`, `Checkbox`, `DropdownButton`, `PopupMenu*`, `TextField` (use the existing `AppTextField`), `ThemeData`, or `ColorScheme`.

- `c` = active `AionColors` (`arctic` / `obsidian`); `isDark` = Obsidian. Both themes share **one** code path; only token values differ. Where a component is identical across themes it is stated explicitly.
- Existing atoms reused unchanged: `AppButton` (primary / ghost / secondary, [DS §2.1](./Aion%20Design%20System%20Spec.md#21-button)), `AppTextField` (DS §2.5), the `StatusRow` shell and `AddStatusControl` inline-form pattern ([Workflow §5–§6](./Aion%20Configurable%20Ticket%20Workflow%20Spec.md)). New atoms introduced here: `AttachmentBadge` (§2), `SegmentedControl` (§3.1), `AttachmentForm` (§3), template-list row (§5), `PendingSkillAttachmentBanner` (§6), `RunAttachedSkillButton` (§7).
- Translucent fills are always `token.withOpacity(x)` — never hardcoded ARGB. (`withOpacity` per this spec's export convention; the codebase's `withValues(alpha:)` is the equivalent call.)
- `a` = **role/confidence chip-fill alpha: Arctic `0.13` / Obsidian `0.20`** (matches the existing `RoleDropdown` tint so 10.5px uppercase chip text stays legible — [Workflow §10.1](./Aion%20Configurable%20Ticket%20Workflow%20Spec.md)).
- Companion mockups: `Aion Workflow Skill Attachments Mockups.dc.html` — screens `1a`–`1g` · component states `2a`–`2e`.

## 1. Models & behavior

### 1.1 Types

```dart
/// How aggressively an attachment fires when its status/stage is entered.
enum AttachmentConfidence { auto, gated, manual }

/// What the attachment runs.
enum AttachmentKind { template, delegatedSkill }

class WorkflowPromptTemplate {
  final String id;          // stable
  final String name;        // e.g. "Repro Steps Request"
  final String body;        // plain text; may contain {{variable}} placeholders
  const WorkflowPromptTemplate({required this.id, required this.name, required this.body});
}

class SkillAttachment {
  final AttachmentKind kind;
  final AttachmentConfidence confidence;
  final String? templateId;   // set iff kind == template
  final String? skillName;    // set iff kind == delegatedSkill (literal skill name)
  const SkillAttachment({required this.kind, required this.confidence, this.templateId, this.skillName});
}
```

- An attachment hangs off a **workflow status** (any scope) or an **SDD stage**. At most **one** attachment per status/stage.
- Project-level `List<WorkflowPromptTemplate>` templates are shared by all statuses/stages and managed on `WorkflowPromptTemplatesScreen` (§5).

### 1.2 Confidence semantics — the visual axis

Confidence is the primary thing a project scans for, so it drives the **badge color** (and the whole gradient of the feature). The mapping runs strongest → quietest as the action gets more hands-off, so a glance down the list reads how autonomous each status is:

| Confidence | Fires… | Color token | Rationale |
|---|---|---|---|
| **`auto`** | silently, on entering the status/stage | `c.primary` | live / active — the app's "this is on" color |
| **`gated`** | only after an in-ticket **Confirm** (§6) | `c.warning` | amber "will prompt you" — a pending decision, not an error |
| **`manual`** | only on an explicit **Run** tap (§7) | `c.textSecondary` (neutral) | quiet, opt-in — no automatic behavior at all |

Kind (`template` / `delegatedSkill`) is **secondary** — carried by a leading glyph and the first word of the badge label, never by color.

### 1.3 Behavior

- **Attach:** the resting row shows a `+ Attach skill` affordance (§2.3). Tapping it expands the inline `AttachmentForm` (§3) *in place* on that row — same interaction shape as `AddStatusControl` (Workflow §6): expand-in-place, never a modal.
- **Edit:** tapping an existing `AttachmentBadge` re-opens the same form pre-filled, now also offering **Remove** (§3.5).
- **Save / Cancel / Remove** collapse the form back to the badge (or, on remove, back to `+ Attach skill`).
- **Gated fire:** entering a `gated` status on a ticket surfaces `PendingSkillAttachmentBanner` (§6) at the top of that ticket's detail screen until the user confirms or rejects.
- **Manual fire:** while a ticket's current status/stage has a `manual` attachment, `RunAttachedSkillButton` (§7) is always visible near the top of its detail screen.
- SDD-stage attachments behave identically to status attachments; the row that carries them is the `SddStageRenameRow` (Workflow §9), which gains the same badge + form.

### 1.4 Validation

All inline, no dialogs (matches Workflow §7):

| Trigger | Treatment |
|---|---|
| Save with kind = Template but no template chosen | name field error ring + message "Pick a template to attach." (§3.3, §3.6); Save disabled |
| Save with kind = Delegated skill but empty name | name field error ring + message "Enter a skill name." (§3.3, §3.6); Save disabled |
| Template kind chosen but **zero templates exist** | picker shows the no-templates state (§3.4); Save disabled until one is created |
| Template-name save with empty name (§5 editor) | name field error ring + message "Name this template." |

## 2. `AttachmentBadge`

A compact indicator on a status/stage row. It has two jobs: show at a glance **that** a skill is attached and — through color — **how** it fires. It sits on the row's **meta line**, to the right (on Base-scope status rows it sits left of the `RoleDropdown`; where both are present, order is: internal name → `Spacer` → `AttachmentBadge` → `RoleDropdown`).

### 2.1 Attached state (chip)

- **Layout:** `Row(gap: 6, crossAxisAlignment: center, mainAxisSize: min)` → kind glyph (§2.2) + label.
- **Shape:** `EdgeInsets.fromLTRB(8, 4, 9, 4)`, radius `AionRadius.sm` (6), `line-height: 1`.
- **Label:** `AionText.chip` (Manrope 10.5 / w700, 0.53 tracking), **pre-uppercased**, single string of the form `"{KIND} · {CONFIDENCE}"` — e.g. `TEMPLATE · GATED`, `SKILL · AUTO`, `SKILL · MANUAL`. (`delegatedSkill` shortens to `SKILL` in the label.)
- **Fill / text — by confidence** (`col` = the confidence color from §1.2; `a` = 0.13 / 0.20):

| Confidence | Label text + glyph | Fill | Border |
|---|---|---|---|
| `auto` | `c.primary` | `c.primary.withOpacity(a)` | none |
| `gated` | `c.warning` | `c.warning.withOpacity(a)` | none |
| `manual` | `c.textSecondary` | `AionColorsHubTokens.neutralTint(isDark)` = `c.textSecondary.withOpacity(isDark ? 0.15 : 0.09)` | `1px c.textSecondary.withOpacity(isDark ? 0.28 : 0.18)` |

### 2.2 Kind glyph (leading)

A `9×9` mark in the confidence color (`col`), drawn from primitives — encodes kind independent of color:

- **`template`** — a `9×11` rounded rectangle **outline** (`1.2px col`, radius `2`) with two `1.2px col` horizontal strokes inset (a "document"). Rendered via `CustomPaint` or a nested `DecoratedBox`.
- **`delegatedSkill`** — a `9×9` **diamond** (a `Transform.rotate(0.785)` `7×7` square, fill `col`) — the AI/skill mark, echoing the DS AI avatar's diamond.

### 2.3 Resting state — `+ Attach skill`

Shown on a row with **no** attachment. A quiet ghost affordance, so an un-configured row stays calm:
