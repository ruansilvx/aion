# Design: Concurrent, cancellable, restart-safe coding execution

Companion to `proposal.md`. Read `aion-arch/ideas/parallel-work.md` first
for the full brainstorm reasoning trail this design implements —
sections below reference its conclusions by number rather than
re-arguing them.

---

## 1. Domain additions

### `ExecutionSchedulingMode` (`lib/features/providers/domain/enums/execution_scheduling_mode.dart`)

```dart
enum ExecutionSchedulingMode {
  /// One coding-execution run in flight at a time — today's shipped
  /// behavior, unchanged. The concurrency ceiling is not consulted.
  strictFifo,

  /// Up to the configured concurrency ceiling of runs execute at once,
  /// with no awareness of ticket relationships.
  parallel,

  /// Same as [parallel], but same-parent sibling Tasks/Bugs never run
  /// concurrently against each other — the scheduler skips a queued
  /// sibling of an already-running ticket and starts the next eligible
  /// one instead, preserving the skipped ticket's queue position.
  hybrid,
}
```

Serialized as `.name`, same convention as every other persisted enum in
this codebase (`TicketStatus`, `AutomationConfidence`, etc.).

### `AutomationContext` gains a fifth value

`lib/core/automation/automation_context.dart`'s enum gains
`codingExecutionResume`, alongside the existing `sddStage |
codingExecution | codingExecutionRetry | chatBranching`. Governs whether
an interrupted run (an in-flight or queued Task/Bug found in the
persisted execution-queue snapshot at launch — see §5) is silently
re-triggered (`auto`), proactively offered with a confirm/dismiss prompt
(`gated`), or left for the existing orphaned/stalled failure-banner retry
path with no proactive surfacing at all (`manual`) — see §5.3. Defaults
to `gated` if unset, same as every other `AutomationContext`
(`AutomationSettingsRepository.getConfidence`'s existing default).
`SharedPrefsAutomationSettingsRepository` gets one more
`shared_preferences` key,
`automation_settings.coding_execution_resume_automation`, following the
exact naming pattern its four siblings already use.

No other `AutomationContext` semantics change. `codingExecution` (the
completion status-flip) and `codingExecutionRetry` (the verify-failure
retry) are untouched by this proposal.

## 2. `AgentModelClient` contract — cancellation

### `AgentRequest` gains an optional `runId`

```dart
class AgentRequest extends Equatable {
  const AgentRequest({
    required this.prompt,
    required this.model,
    this.toolsEnabled = false,
    this.workingDirectory,
    this.tools = const [],
    this.onToolCall,
    this.runId, // NEW
  });

  /// Caller-supplied correlation id for this specific run, used to target
  /// a later [AgentModelClient.cancel] call. `null` (the default) means
  /// the caller never intends to cancel this run — every call site that
  /// predates cancellation passes nothing and is unaffected. Generated
  /// fresh per turn by the caller (`const Uuid().v4()`, the same
  /// generator already used for `Ticket.id`), never reused across turns.
  final String? runId;

  @override
  List<Object?> get props => [prompt, model, toolsEnabled, workingDirectory, tools, onToolCall, runId];
}
```

Additive and backward compatible — identical precedent to how `tools`/
`onToolCall` were added.

### `AgentModelClient` gains `cancel`

```dart
abstract interface class AgentModelClient {
  Future<Stream<AgentEvent>> run(AgentRequest request);

  /// Cancels the in-flight run identified by [runId] (see
  /// [AgentRequest.runId]), if it's still active on this client
  /// instance. No-op if [runId] is unknown (never started, already
  /// finished, or was never assigned a runId).
  void cancel(String runId);
}
```

A client instance may have more than one run active at once now that
coding execution can trigger several concurrently through the *same*
`ClaudeAgentSdkProvider`/`ClaudeAgentSdkClient` singleton (constructed
once in `main.dart`, shared by every caller) — `cancel` must therefore
target a specific run by id, not "the current run." This is why `runId`
is caller-supplied rather than a value `run()` returns: the caller needs
it available *before* `run()`'s `Future` resolves, to store alongside
whatever UI state (a Task id, a chat ticket id) will later trigger
cancellation.

### `AgentEvent` gains a third terminal variant

```dart
/// The run was cancelled via [AgentModelClient.cancel] before it
/// produced a normal terminal event. Always the last event on a
/// cancelled stream — no [AgentDoneEvent]/[AgentErrorEvent] follows.
/// Unlike [AgentErrorEvent], a cancellation is not a failure: callers
/// must not treat it as one (no "Execution failed" comment, no retry
/// escalation).
class AgentCancelledEvent extends AgentEvent {
  const AgentCancelledEvent();
}
```

The contract's "finished by exactly one terminal event" rule now reads
`AgentDoneEvent | AgentErrorEvent | AgentCancelledEvent`.

### `ClaudeAgentSdkClient` implementation

Keeps a `Map<String, Process> _activeProcesses`, keyed by `runId`, entries
added only when `request.runId != null` (immediately after
`Process.start` succeeds) and removed when the process exits (any
reason). `cancel(runId)` looks up the map; if found, calls
`process.kill(ProcessSignal.sigterm)` (falling back to `sigkill` if the
process hasn't exited after a short grace period — mirrors how a
terminal handles Ctrl-C escalation) and, on the stdout listener's side,
emits `AgentCancelledEvent` then closes the stream — this is the one
case where the client itself emits a terminal event rather than parsing
one off an NDJSON line, since a killed process never gets to write its
own `{"type":"done"|"error",...}` line. The existing "only the first
terminal event counts" guard (already in place for the
late-misleading-`result`-message hardening) covers the case where a kill
races a genuine in-flight NDJSON terminal line — whichever the stdout
listener observes first wins, and cancellation racing a just-finished
run resolving as a completion instead is an acceptable, harmless
outcome (the run's actual work already happened either way).

### `AnthropicMessagesApiClient` implementation

Keeps a `Map<String, CancelToken> _activeTokens` (Dio's own
`CancelToken` type), keyed by `runId`, one per `_streamResponse` call
(including every re-POST inside its own tool-calling loop — the same
token cancels all of them, since they're all one logical run).
`cancel(runId)` looks up and calls `token.cancel()`; the resulting
`DioException` (type `cancel`) is caught inside `_streamResponse` and
translated to `AgentCancelledEvent` instead of propagating as
`AgentErrorEvent`, mirroring the `429` → `AgentOverageDetectedEvent`
translation already in place for this client.

### `agent_bridge/index.mjs` — no change needed

Cancellation is enforced entirely at the Dart process-management layer
(`Process.kill`); the bridge itself has no cancellation-awareness to add
— killing the Node process terminates whatever `query()` call it's
mid-stream on. This keeps the bridge's NDJSON protocol completely
unchanged.

## 3. `ChatCubit` — stop button and turn-result shape

### `runChatTurn` return type changes

Today: `Future<bool> runChatTurn(...)` — `true`/`false` for
success/failure, with `AgentErrorEvent`/exceptions auto-persisting an
`"Execution failed: ..."` comment internally.

New: a sealed result type, so cancellation never gets treated as a
failure by any caller.

```dart
sealed class ChatTurnResult extends Equatable {
  const ChatTurnResult();
}

/// The turn completed normally; comment already persisted by runChatTurn.
class ChatTurnSuccess extends ChatTurnResult {
  const ChatTurnSuccess();
  @override
  List<Object?> get props => [];
}

/// The turn hard-failed; the "Execution failed: ..." comment was already
/// persisted by runChatTurn, exactly as today's `false` return implied.
class ChatTurnFailure extends ChatTurnResult {
  const ChatTurnFailure();
  @override
  List<Object?> get props => [];
}

/// The turn was cancelled via [AgentModelClient.cancel] before reaching
/// a normal terminal event. runChatTurn persists NO comment in this
/// case — every caller decides for itself what (if anything) to record,
/// since "cancelled mid-chat-reply" and "cancelled mid-coding-execution"
/// need different comments (see §4, §5).
class ChatTurnCancelled extends ChatTurnResult {
  const ChatTurnCancelled(this.accumulatedText);
  /// Whatever text had streamed in before cancellation. Empty string if
  /// cancelled before any AgentTextEvent arrived.
  final String accumulatedText;
  @override
  List<Object?> get props => [accumulatedText];
}
```

`runChatTurn`'s three existing call sites (`ChatCubit.sendMessage`,
`TicketsCubit._spawnStageChat`, `TicketsCubit._runCodingExecution`) all
switch on the result instead of checking a bool. None of them pass
`runId`/expect cancellation today except the two this proposal adds it
to (`sendMessage`, `_runCodingExecution` — see §5); `_spawnStageChat`
simply never produces a `ChatTurnCancelled` in practice (nothing calls
`cancel()` against its runId, since SDD-stage chats get no stop-button UI
in this slice — out of scope, see Non-goals) and its `switch` treats that
arm as unreachable-but-handled (`ChatTurnCancelled() => false`, matching
its pre-existing bool contract unchanged).

### `ChatLoaded` gains `activeRunId`

```dart
class ChatLoaded extends ChatState {
  const ChatLoaded({
    required this.comments,
    this.streamingText,
    this.currentToolUse,
    this.activeRunId, // NEW — String?, null when nothing is streaming
  });
  // ...
  @override
  List<Object?> get props => [comments, streamingText, currentToolUse, activeRunId];
}
```

Set the moment `sendMessage` generates a `runId` and calls `client.run`;
cleared (`null`) on any terminal `ChatTurnResult`. Drives the stop
button's visibility — the transcript shows a stop control whenever
`activeRunId != null`, mirroring how `currentToolUse != null` already
drives the live tool-use indicator.

### `ChatCubit.sendMessage` changes

Generates `final runId = const Uuid().v4();` before calling
`runChatTurn`, passes it through to the underlying `AgentRequest`, stores
it on the emitted `ChatLoaded.activeRunId`. On `ChatTurnCancelled
(accumulatedText)`: if `accumulatedText` is non-empty, persists it as one
`CommentAuthorType.ai` comment via `commentRepo.addComment` (partial
output is kept, not discarded — consistent with `parallel-work.md`'s
§1.5 "keep artifacts" conclusion applied to a plain chat reply); either
way, reloads the thread and emits `ChatLoaded` with `streamingText`/
`currentToolUse`/`activeRunId` all cleared.

### `ChatCubit.cancelReply(String chatTicketId)` — new method

```dart
/// Cancels the chat's current in-flight AI reply, if one is streaming.
/// No-op if nothing is active. Emits no new state directly — the
/// in-flight sendMessage call's own ChatTurnCancelled handling (above)
/// does that once the cancellation actually lands.
Future<void> cancelReply(String chatTicketId) async { ... }
```

Reads `state.activeRunId` (state must be `ChatLoaded`); if non-null,
resolves the same provider `sendMessage` used (via the same
`_phaseForChat`/`_resolveModelAndProvider` pair, re-run — cheap, pure
lookups) and calls `provider.client.cancel(runId)`. Fire-and-forget from
the UI's perspective: the stop button calls this, then waits for the
already-in-flight `sendMessage` call's `ChatTurnCancelled` handling to
update state, exactly like every other async UI action in this app.

## 5. `TicketsCubit` — scheduling, cancellation, persistence

### 5.1 In-flight bookkeeping generalizes to a set

`_inFlightExecutionTaskId` (`String?`) is replaced by:

```dart
final Set<String> _inFlightExecutionIds = {};
final Map<String, _InFlightExecutionRun> _inFlightRuns = {};
final Map<String, TicketStatus> _preExecutionStatus = {};
```

```dart
/// Private bookkeeping for one in-flight coding-execution run, keyed by
/// Task/Bug id in [TicketsCubit._inFlightRuns] — enough to target a
/// cancellation without re-resolving the provider.
class _InFlightExecutionRun {
  const _InFlightExecutionRun({required this.runId, required this.provider});
  final String runId;
  final AgentProvider provider;
}
```

`_executionQueue` stays `List<String>` (Task/Bug ids), FIFO by
enqueue order — unchanged shape, since Strict FIFO mode still needs a
plain ordered list and Hybrid mode's skip-ahead scan (§5.2) still
respects that order for everything it *doesn't* skip.

`_preExecutionStatus[taskId]` is written the moment
`_interceptTaskExecutionTrigger`'s allowed path is about to persist the
`inProgress` write (capturing whatever `TicketStatus` the ticket had
immediately before), and read/cleared by cancellation (§5.4) or normal
completion (whichever comes first — completion already doesn't need it,
so it's simply left to be overwritten by the *next* trigger of the same
Task, never accumulating stale entries in practice since a Task can only
have one active status-transition-in-flight at a time).

### 5.2 Scheduling algorithm

New private helper, `int _effectiveConcurrencyCeiling()`: returns `1` if
`ExecutionSchedulingMode.strictFifo` is configured, else `1` if
this-session overage was detected (`_overageDetectedThisSession` — same
flag §"Reactive budget override" already sets), else the configured
ceiling from `ExecutionSchedulingRepository` (§6, default e.g. `2`).

New private helper, replacing today's "start next queued run"
single-slot logic:

```dart
Future<void> _tryStartNextQueuedExecutions() async {
  final ceiling = _effectiveConcurrencyCeiling();
  final mode = await _schedulingRepository.getMode();
  while (_inFlightExecutionIds.length < ceiling && _executionQueue.isNotEmpty) {
    final nextId = switch (mode) {
      ExecutionSchedulingMode.hybrid => _nextEligibleForHybrid(),
      ExecutionSchedulingMode.strictFifo ||
      ExecutionSchedulingMode.parallel => _executionQueue.first,
    };
    if (nextId == null) break; // Hybrid: everything queued is sibling-blocked right now
    _executionQueue.remove(nextId);
    unawaited(_runCodingExecution(/* resolved Task/Bug */));
  }
  _refreshInFlightBoardState();
}

/// Hybrid mode only. Scans the queue front-to-back for the first ticket
/// whose parentId doesn't match any currently in-flight ticket's
/// parentId (null parentId is always eligible — no siblings to conflict
/// with). Returns null if every queued ticket is currently sibling-
/// blocked. Leaves the queue itself untouched — only the caller removes
/// the returned id, once found.
String? _nextEligibleForHybrid() {
  final inFlightParents = _inFlightExecutionIds
      .map((id) => _ticketById(id)?.parentId)
      .whereType<String>()
      .toSet();
  for (final id in _executionQueue) {
    final parentId = _ticketById(id)?.parentId;
    if (parentId == null || !inFlightParents.contains(parentId)) return id;
  }
  return null;
}
```

Called from every site that previously called the old single-slot
"start next" logic: the trigger path (a slot might already be free), and
`getTicketById`'s completion handling (a slot just freed) — same call
sites, same shape, just delegating to this instead of a bare
`_executionQueue.removeAt(0)`.

`_nextEligibleForHybrid` reads `_ticketById`, a small private
`Map<String, Ticket>` lookup already maintained wherever the currently-
loaded ticket list lives in state (a pre-existing pattern, not new to
this design) — no extra DB round-trip.

### 5.3 Restart persistence and resume

New repository interface (domain layer):

```dart
/// A snapshotted entry in the execution queue, persisted so it survives
/// an app restart. See ExecutionQueueRepository.
class ExecutionQueueEntry extends Equatable {
  const ExecutionQueueEntry({required this.taskId, required this.inFlight, this.queuePosition});
  final String taskId;
  final bool inFlight; // false = queued, not yet started
  final int? queuePosition; // 1-based, null iff inFlight
  @override
  List<Object?> get props => [taskId, inFlight, queuePosition];
}

abstract interface class ExecutionQueueRepository {
  Future<List<ExecutionQueueEntry>> getSnapshot();
  /// Replaces the entire persisted snapshot with [entries] — a full
  /// wipe-and-rewrite, not an incremental diff (the row count is always
  /// small — at most the concurrency ceiling plus queue length — so this
  /// stays cheap; see flutter-conventions.md's DAO transaction pattern).
  Future<void> replaceSnapshot(List<ExecutionQueueEntry> entries);
}
```

`DriftExecutionQueueRepository` implementation backed by a new table
(§7). `TicketsCubit` calls `_persistExecutionQueueSnapshot()`
(`unawaited`, fire-and-forget — mirrors `_refreshInFlightBoardState`'s
existing no-await-needed pattern) from every mutation site of
`_inFlightExecutionIds`/`_executionQueue`: trigger, cancel, completion,
and `_tryStartNextQueuedExecutions`.

**Resume, at `TicketsCubit` construction / first load.** A new method,
`Future<void> restoreExecutionQueue()`, called once by `WorkspaceShell`
right after constructing `TicketsCubit` for a project (same lifecycle
point `TicketMarkdownWatcherService`'s existing one-time init hooks in,
per `projects.md`), gated on `automationSettingsRepository`/
`executionQueueRepository` both being non-null (desktop only, same
optional-dependency pattern every other coding-execution-adjacent
constructor param already follows):

1. Read the snapshot. Empty → no-op, done.
2. Re-validate: drop any entry whose `taskId` no longer resolves to a
   live, still-`inProgress` Task/Bug (the user may have manually changed
   its status, or trashed it, while the app was closed) — resume never
   resurrects a ticket the user has since moved on from.
3. Resolve `AutomationContext.codingExecutionResume`'s confidence:
   - **`manual`** — clear the snapshot (`replaceSnapshot([])`) and do
     nothing further. `_inFlightExecutionIds`/`_executionQueue` stay
     empty, exactly like today's shipped restart behavior — every
     surviving entry's Task/Bug falls through to the existing orphaned/
     stalled `executionFailureReason` detection (unchanged) the first
     time its detail screen loads, with the existing failure banner's
     retry button as the only path forward. This is the *default*
     resume experience, since `manual`... no — default is `gated` (per
     §1's stated default); `manual` is simply the mode that reproduces
     today's exact behavior with zero proactive surfacing.
   - **`gated`** — surface one proactive prompt (a toast or a small
     confirm affordance — left for `/design-brief`; see Design gate) at
     Board load: "N coding-execution run(s) were interrupted — resume?"
     Accepting re-enqueues every surviving entry (queued entries restore
     their relative order via `queuePosition`; in-flight entries are
     re-enqueued at the *front* of the queue, ahead of anything that was
     merely queued, since they were closer to done) and calls
     `_tryStartNextQueuedExecutions()`. Declining behaves like `manual`
     (clear the snapshot, fall back to the existing orphaned/stalled
     path).
   - **`auto`** — same re-enqueue as `gated`'s "accept" path, with no
     prompt.
4. Whichever branch ran, always end by writing a fresh snapshot
   reflecting the resulting in-memory state (empty for `manual`/declined
   `gated`, repopulated for `auto`/accepted `gated`).

"Resume" never means re-attaching to a live process — the app just
started, so nothing is actually running. A resumed in-flight entry is
re-triggered via the exact same code path `retryCodingExecution` already
uses (fresh worktree/branch, chat reused) — restart-resume and manual
retry are the same underlying operation, just triggered proactively
instead of by a click.

### 5.4 Cancellation

New public method:

```dart
/// Cancels [task]'s coding-execution run, whether it's currently queued
/// (removed before ever starting) or in flight (its process is killed).
/// Either way, reverts the ticket to its pre-trigger status, preserves
/// any git artifacts already created, and posts a comment on its
/// execution chat noting what happened. No-op if [task] is neither
/// queued nor in flight.
Future<void> cancelCodingExecution(Ticket task) async { ... }
```

- **Queued path** (`task.id` in `_executionQueue`, not in
  `_inFlightExecutionIds`): remove from `_executionQueue`; look up and
  clear `_preExecutionStatus[task.id]`, write it back via
  `_repository.updateTicketStatus`; post a `system` comment ("Execution
  cancelled before it started.") on the Task's execution chat via
  `_resolveExecutionChat` (reused, not a new chat); refresh board state;
  persist snapshot.
- **In-flight path** (`task.id` in `_inFlightExecutionIds`): look up
  `_inFlightRuns[task.id]`, call
  `run.provider.client.cancel(run.runId)`. The already-in-flight
  `_runCodingExecution` call (§5.5) observes `ChatTurnCancelled` from its
  current `runChatTurn` call, stops immediately (no verify turn — same
  "nothing to verify" precedent the existing hard-failure path already
  establishes), posts its own `system` comment ("Execution cancelled —
  work up to this point is preserved on branch `aion/task-<id>`; the
  worktree itself has been removed.", reusing the existing, already-
  documented branch-naming convention), reverts status via
  `_preExecutionStatus`, removes the Task from
  `_inFlightExecutionIds`/`_inFlightRuns`, persists the snapshot, and
  calls `_tryStartNextQueuedExecutions()` to backfill the freed slot —
  the same sequence `_runCodingExecution`'s existing completion path
  already runs, just reached via cancellation instead of success/
  failure.

The worktree itself is *always* removed in `_runCodingExecution`'s
existing `finally` (§ existing "Worktree isolation" behavior, unchanged)
— cancellation doesn't special-case that. Only the pushed-nowhere branch
and whatever commits the model made before cancellation survive, exactly
like a normal failed run's branch already does today (abandoned, never
cleaned up automatically — no change to that either).

### 5.5 `_runCodingExecution` changes

Generates a `runId` (`const Uuid().v4()`) before each `runChatTurn` call
(implement turn, verify turn, and any corrective retry turn — a fresh id
per turn, so cancelling mid-verify doesn't accidentally also carry a
stale handle from the implement turn), stores
`_inFlightRuns[task.id] = _InFlightExecutionRun(runId: runId, provider: provider)`
before each call and updates it before the next turn starts. Switches on
`ChatTurnResult` instead of the old bool: `ChatTurnSuccess` continues to
the verify turn (or to push/PR, if this was the verify turn) exactly as
today; `ChatTurnFailure` behaves exactly as today's `false` case
(existing "Execution failed: ..." comment already persisted by
`runChatTurn` itself); `ChatTurnCancelled` runs the in-flight cancellation
sequence from §5.4 instead of either.

## 6. `ExecutionSchedulingRepository` and `ExecutionSchedulingCubit`

Domain interface, `shared_preferences`-backed, same shape family as
`ExecutionContextCapRepository`:

```dart
abstract interface class ExecutionSchedulingRepository {
  Future<ExecutionSchedulingMode> getMode(); // defaults to strictFifo if unset
  Future<void> setMode(ExecutionSchedulingMode mode);
  Future<int> getConcurrencyCeiling(); // defaults to 2 if unset
  Future<void> setConcurrencyCeiling(int ceiling); // clamped to >= 1
}
```

Defaulting to `strictFifo` (not `parallel`/`hybrid`) means this change
ships with **zero behavior change** for a user who never opens the new
Settings section — Strict FIFO is byte-for-byte today's shipped
single-slot behavior. `SharedPrefsExecutionSchedulingRepository` stores
`ExecutionSchedulingMode.name` under
`execution_scheduling.mode` and the ceiling `int` under
`execution_scheduling.concurrency_ceiling`.

`ExecutionSchedulingCubit` (`presentation/cubit/`), structurally
identical to `ExecutionContextCapCubit`:

States: `ExecutionSchedulingLoading` (initial), `ExecutionSchedulingReady`
(`mode` — `ExecutionSchedulingMode`, `concurrencyCeiling` — `int`).

Methods: `load()`; `selectMode(ExecutionSchedulingMode mode)`; `setConcurrencyCeiling(int ceiling)`.

## 7. Persistence — new Drift table

```dart
@DataClassName('ExecutionQueueEntryData')
class ExecutionQueueTable extends Table {
  @override
  String get tableName => 'execution_queue';

  /// Internal UUID v4 row id.
  TextColumn get id => text()();

  /// The Task/Bug ticket id this snapshot row concerns.
  TextColumn get taskId => text().named('task_id')();

  /// Whether this ticket's run was actually in flight (true) or merely
  /// queued behind another (false) at the moment this snapshot was
  /// written.
  BoolColumn get inFlight => boolean().named('in_flight')();

  /// 1-based position in the FIFO queue; null iff inFlight is true.
  IntColumn get queuePosition => integer().named('queue_position').nullable()();

  @override
  Set<Column> get primaryKey => {id};
}
```

`ExecutionQueueDao` (`@DriftAccessor(tables: [ExecutionQueueTable])`):
`getSnapshot()` (`orderBy queue_position`, nulls first — in-flight
entries have no meaningful order relative to each other), `replaceSnapshot
(List<ExecutionQueueTableCompanion>)` (wrapped in
`transaction<void>(() async { delete + bulk insert })`, following
flutter-conventions.md's "multi-step invariants live inside the DAO
wrapped in a transaction" rule).

`AppDatabase` schema version bumps from 12 to **13**: `if (from < 13)`
creates `ExecutionQueueTable` — no backfill needed (a fresh install and
every pre-existing local database alike start with an empty queue; there
is no meaningful historical in-flight/queued state to reconstruct from
before this version existed). Registers `ExecutionQueueDao` alongside
the existing five DAOs.

No FK constraints, consistent with every existing table in this schema.

### Wiring

`ExecutionSchedulingRepository` (constructed as

# Aion — Concurrent, Cancellable, Restart-Safe Coding Execution: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Task-to-Coding-Execution Trigger Spec](./Aion%20Task%20Execution%20Trigger%20Spec.md) (its coding-execution section, `_ExecutionRunningHint`/`_ExecutionQueueHint`, and the reusable `_AutomationSection`/`_AutomationTrigger`/`_AutomationMenuRow`), the [Coding-Execution Reliability Spec](./Aion%20Coding%20Execution%20Reliability%20Spec.md) (`CodingRunState`, `_ExecutionLiveToolLine`, `dangerTint`/`dangerBorderTint`), the [Execution Context Cap Spec](./Aion%20Execution%20Context%20Cap%20Spec.md) (the MODELS-group row geometry + `AppTextField` numeric field + helper-chip pattern this sits beside), the [Board Execution/Advance Indicators Spec](./Aion%20Board%20Advance%20Indicators%20Spec.md) (`BoardCardStatusBadge` + its `pendingTint`/`secondary` families), and the [Chat Transcript Spec](./Aion%20Chat%20Transcript%20Spec.md) (`AionText.streamStatus`, the streaming in-flight bubble this stops). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AppTextField`, `SettingsScreen`, `TicketBoardCard`, `TicketDetailScreen`, and `AutomationConfidence` by name.

This change makes coding execution **concurrent, cancellable, and restart-safe**. Today execution runs exactly one Task/Bug at a time off an in-memory FIFO queue, with no way to cancel and no queue memory across an app restart. This pass adds five surfaces — **all additions to existing screens, no new screens**:

1. **`ExecutionSchedulingSection`** (§1) — a new "MODELS"-group row (scheduling mode + concurrency ceiling), inserted directly below the Execution Context Cap row.
2. **`ExecutionCancelControl`** (§2) — one cancel action in three placements (Board card, Task/Bug detail, streaming chat reply), one visual language.
3. **`ResumeRunsPrompt`** (§3) — a one-time inline banner offering to resume interrupted runs after a restart.
4. **A fifth `_AutomationSection` instance** (§4) — "Resume After Restart," a content-only reuse of the existing automation-row component (no new visual design).
5. **Board sibling clustering** (§5) — in Hybrid mode, Task/Bug cards sharing a parent Story sit physically adjacent within a column (an ordering change, no new component).

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (decoration only, non-Material) / `Padding` / `Row` / `Column` / `Stack` / `GestureDetector` / `FocusableActionDetector` / `MouseRegion` / `AnimatedContainer` / `AnimatedSize` / `AnimatedOpacity` / `AnimatedScale` / `RotationTransition` / `CustomPaint`; the scheduling ceiling is the existing **`AppTextField`** atom (base spec §2.5), reused unchanged. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `AppBar`, `SnackBar`, `SnackBarAction`, `DropdownButton`, `InkWell`, `ListTile`, `Chip`, `CircularProgressIndicator`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is quoted `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` (or the equivalent `token.withValues(alpha: x)` derived helper) — never hardcoded ARGB.

**New tokens:** none for color / typography / radius / spacing. Every translucent value reuses an existing derived helper (`dangerTint`/`dangerBorderTint`, `pendingTint`, `neutralTint`/`neutralBorderTint`, `primaryWash`, `focusRing`). Two small structural additions: the `ExecutionSchedulingMode` enum + concurrency-ceiling value model (§6), and a `cancelFocusRing(isDark)` derivation documented in §7.1 (a `danger`-keyed parallel of the existing `focusRing`, not a new palette member).

## 3. `ResumeRunsPrompt` (resume-after-restart)

Shown **once per app launch** when Aion detects interrupted coding-execution runs AND the user's "Resume After Restart" automation (§4) is in its **"asks before resuming"** (`gated`) mode. Follows the app's existing banner language — specifically the `primary`/neutral-toned family (not `danger`/`warning`): an interrupted run is **recoverable and needs a yes/no**, not an error. It borrows `_ExecutionActionBanner`'s container geometry (Reliability §1.1) re-keyed to `primary`, with a two-button action row.

### 3.1 Placement

**Decision: an inline banner pinned to the top of the Board view**, above the columns (not a transient toast). Rationale: the prompt must (a) list N runs, (b) persist until the user answers yes/no, and (c) offer two actions — none of which a top-of-screen auto-dismissing toast holds well. It matches the app's inline-banner precedent (`_ExecutionActionBanner`, `TicketNeedsRepairBanner`) rather than the toast precedent (which the app reserves for transient confirmations). Full board content width, `20` gutter each side, `16` below it to the column header row.

### 3.2 Container

- `DecoratedBox` → `Padding` → `Column`, `crossAxisAlignment: stretch`, `gap: 12`.
- **Fill:** `primaryWash(isDark)` (`primary @ 0.10 / 0.16`) — the app's "faint fill under an actively-recoverable control."
- **Border:** `1px solid primary.withOpacity(isDark ? 0.42 : 0.28)` (the banner-border alpha step, keyed to `primary`).
- **Radius:** `AionRadius.lg` (12).
- **Shadow:** none.
- **Padding:** `EdgeInsets.fromLTRB(14, 13, 14, 14)`.
- **Layout:** (1) header `Row` (`gap: 12`, `crossAxisAlignment: start`) — leading glyph + text column; (2) action `Row` (§3.3).

**Leading glyph:** `arrow-clockwise` / `arrows-counter-clockwise` (the "resume / re-run" motif), `18px`, `primary` (`#2E86D4 / #9366FF`), pinned to `start` (the title may wrap above the run list).

### 3.1.1 Content (text column, `Expanded`, `gap: 4`)

- **Title:** `"{N} coding-execution run(s) were interrupted"` (e.g. `"2 coding-execution runs were interrupted"` — `run` singular at `N == 1`), `AionText.cardTitle` (14 / w600), `textPrimary`.
- **Run list:** up to 3 lines, one per interrupted run; overflow collapses to `"…and {k} more"`. Each line `Row`, `gap: 7`, center: an `AionText.key`-styled mono ticket id chip (`"AIO-12"`, `textSecondary` on `surfaceHover`, padding `2×6`, radius `5`) + the ticket title `AionText.bodySm` (13.5) `textSecondary`, `maxLines: 1`, ellipsis. Between the title and the list: `gap: 4`; between list lines: `gap: 4`.

### 3.3 Actions (`Row`, `gap: 10`, `mainAxisAlignment: end`)

Two buttons, right-aligned, matching the app's confirm/dismiss pairing weight:

- **Dismiss** (secondary / text-only): `GestureDetector` → `Padding` (`EdgeInsets.symmetric(horizontal: 14, vertical: 9)`) → `Text` `"Dismiss"`, `AionText.button` (14 / w700), `textSecondary`; no fill, no border.
- **Resume** (primary solid): `GestureDetector` → `DecoratedBox` → `Padding` → centered `Row` (`gap: 7`) glyph `arrow-clockwise` `15px` `#FFFFFF` + `Text` `"Resume"`, `AionText.button` `#FFFFFF`. Fill `primary`; radius `AionRadius.md` (10); padding `EdgeInsets.symmetric(horizontal: 15, vertical: 10)`; glow `BoxShadow(color: primary.withOpacity(isDark ? 0.60 : 0.45), blurRadius: 18, spreadRadius: -9, offset: Offset(0, 8))` — the app's FAB-glow shape, keyed to `primary`.

### 3.4 Button states

| Button | Default | Hover | Focused | Pressed | Disabled |
|---|---|---|---|---|---|
| **Resume** | `primary` fill + glow | `primaryHover` (`#1E6DB6 / #A886FF`), glow blur → 22 | 3px ring `focusRing(isDark)` | `primaryHover`, glow off, `AnimatedScale` 0.98 | `primary @ 0.45`, label `#FFFFFF @ 0.55`, `IgnorePointer` (resume spawning) |
| **Dismiss** | text `textSecondary`, no fill | fill `surfaceHover`, text `textPrimary` | 3px ring `focusRing(isDark)`, fill `surfaceHover` | fill `border`, `AnimatedScale` 0.98 | text `textSecondary @ 0.45`, `IgnorePointer` |

Both buttons are keyboard-navigable (`FocusableActionDetector`, `Enter`/`Space` activate). The banner has no `×` dismiss glyph — **Dismiss** is the explicit no. Once either action is taken the banner is removed for the session (shown once per launch, §3.0).

## 4. "Resume After Restart" automation row (Settings) — confirm, don't redesign

This is the **fifth** instance of the already-designed `_AutomationSection` (Task Trigger spec §4 / Reliability spec §3) — the same label + description + `_AutomationTrigger` + `_AutomationMenuRow` (`AutomationConfidence`) used by "SDD Stage Automation," "Coding Execution Automation," "Coding-Execution Retry," and "Chat Branching." **No new visual design.** It stacks under the shared `AUTOMATION` eyebrow after the four existing instances, with `20` vertical spacing and no divider (Task Trigger §4.1). ## 5. Board sibling clustering (Hybrid mode — ordering only)

An **ordering change** to `TicketBoardCard` layout within a column — **no new component, no new badge**. In `ExecutionSchedulingMode.hybrid`, Task/Bug cards that share a parent Story are kept **physically adjacent** within their board column (so "related work in order" is visible), while unrelated cards keep their normal position.

### 5.1 Ordering rule

Within each column, the existing sort order (Ticket Sort spec) is preserved as the primary key; in Hybrid mode a **stable secondary grouping** brings same-parent-Story Task/Bug siblings together: a sibling cluster is anchored at the position of its **earliest-sorted** member, and the remaining siblings are pulled up to immediately follow it. Cards with no coding-execution relevance (no running/queued sibling group) are untouched. This is a pure reorder of the column's card list — the cards, their `BoardCardStatusBadge` (§2.1 host), and their `ExecutionCancelControl` are unchanged.

- **Strict FIFO / Parallel:** no clustering — the column uses its normal sort order.
- **Hybrid:** clustering applied as above.
- **No visual cluster chrome** by default (no bracket, no shared background). If a future pass wants a cue, `neutralTint`/`neutralBorderTint` (the app's quiet-chrome family) is the sanctioned tint — but this spec ships clustering as ordering only, per the brief.

### 5.2 Mockup illustration (Board §2 of the mockups)

The "In Progress" column shows, top to bottom: `AIO-12` (Task, high, **Running** + cancel) immediately followed by its sibling `AIO-14` (Task, medium, **Queued #1** + cancel) — both children of the same Story, clustered — then an unrelated third card `AIO-23` (Task, medium, normal / non-executing) in its normal position lower in the column.

## 6. New enums / value model (no new design tokens)

```dart
/// How coding-execution runs are scheduled (§1). Persisted per workspace.
enum ExecutionSchedulingMode { strictFifo, parallel, hybrid }   // default: strictFifo

extension ExecutionSchedulingModeX on ExecutionSchedulingMode {
  String get displayName => switch (this) {
    ExecutionSchedulingMode.strictFifo => 'Strict FIFO',
    ExecutionSchedulingMode.parallel   => 'Parallel',
    ExecutionSchedulingMode.hybrid     => 'Hybrid',
  };
  bool get usesCeiling => this != ExecutionSchedulingMode.strictFifo; // §1.5 show/hide
}

/// Concurrency ceiling — the max simultaneous runs in Parallel / Hybrid (§1.5).
class ExecutionSchedulingConfig {
  final ExecutionSchedulingMode mode;
  final int concurrencyCeiling;          // clamped ≥ 1 on commit (§6.1); ignored in strictFifo
  const ExecutionSchedulingConfig(this.mode, this.concurrencyCeiling);
}

// Cancel-control placement (§2).
enum CancelPlacement { boardBadge, detailButton, chatStream }

// Reused verbatim (Task Trigger §5) — now also drives the 5th automation section (§4):
enum AutomationConfidence { auto, gated, manual }   // Resume After Restart default: gated
```

### 6.1 Ceiling validity (which helper variant renders)

Let `text` = the live controller string, `n = int.tryParse(text)`.

| Condition | Helper variant | Committed value (`onChanged`) |
|---|---|---|
| `n != null && n >= 1` | **Neutral** (§1.5.3), `"Up to {n} run(s) at once"` | `n` |
| `text` empty, or `n == null`, or `n <= 0` | **Error chip** (§1.5.3) | last valid value retained; not committed until valid |

- The `digitsOnly` formatter (§1.5.2) makes non-digit and negative input impossible to type; the reachable invalid states are **empty** and **`0`**, both surfaced by the error chip.
- On commit (`onSubmitted` / focus-loss) an empty/`0` entry re-renders the field with the last valid ceiling and drops the error chip.
- The ceiling is only meaningful in `Parallel` / `Hybrid`; in `strictFifo` the field is hidden (§1.5.1) and the stored ceiling is ignored.
