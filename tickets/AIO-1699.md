# Provider Configuration

# Proposal: Provider Configuration

## What

The first working `AgentModelClient` implementation, scoped down to a
single provider for the desktop MVP: **Claude Agent SDK**, authenticated
via the user's existing Claude plan (Pro/Max), invoked through a small
bundled Node.js bridge process. Concretely, this change ships:

- `AgentModelClient` (`core/contracts/`) — the provider-agnostic
  interface `project.md` §3 already declares, plus the `AgentRequest`/
  `AgentEvent` shapes it exchanges. No feature code will ever depend on
  a concrete provider directly.
- `ClaudeAgentSdkClient` (`core/agent/`) — the sole implementation,
  spawning a bundled Node.js bridge script via `dart:io Process` (same
  `Process`-wrapping pattern as the existing `GitRepositoryClient`),
  streaming NDJSON events back as `AgentEvent`s.
- A new `features/providers/` feature: a single Settings screen showing
  connection status for Claude Agent SDK (auto-checked on open, with a
  manual "Test Connection" action) and a model picker (Opus / Sonnet /
  Haiku) persisted via `shared_preferences`.
- A new "Settings" entry in `WorkspaceNavShell`'s existing
  secondary-actions popover, alongside "Switch Project" and "Trash".
- A one-time local setup step (`npm install` inside a new `agent_bridge/`
  directory) documented in `project.md`'s Bootstrap & Dependency Notes.

No chat UI, ticket estimation, or SDD-in-ticket-system feature consumes
this yet — same "build it inert, ahead of any consuming UI" pattern
`sdd-workflow-in-ticket-system`'s Foundation phase already uses for its
ticket-stage field. This change's job is only to make a configured,
testable `AgentModelClient` exist.

## Why

Every chat-based feature on the roadmap — `sdd-workflow-in-ticket-system`
(SDD-stage chats), `new-project-onboarding` (Inbox chats), ticket
estimation — is blocked on a working provider. Nothing in `project.md`
§5's originally-envisioned six-provider `ModelRouter` has shipped yet.

Source idea: `aion-arch/ideas/provider-configuration.md` (status:
`explored`), refined further during this change's own `/explore` pass.
The idea's own exploration already cut scope from six providers down to
one (Claude Agent SDK), reasoning that the standalone "watcher" concept
being dropped (see `sdd-workflow-in-ticket-system`) removes the two
strongest arguments for a separate lightweight Messages-API provider —
subprocess overhead and rate-limit contention with a persistent daemon
that no longer exists. The remaining argument (mobile/web can't run a
Node subprocess) doesn't apply yet either, since this MVP is desktop-only.

`self-iteration-sequencing` places this change first in the build order:
smallest of the three explored ideas, and a hard prerequisite for
everything else on the path to Aion iterating on itself.

## Scope

**In scope:**

- `AgentModelClient`/`AgentRequest`/`AgentEvent` contracts in
  `core/contracts/`.
- `ClaudeAgentSdkClient`, the Node.js bridge script it spawns, and a
  `AgentBridgeLocator` resolving the bridge's path (desktop-only, same
  `isDesktop` gate the git-projection services already use).
- A single global (not per-project) provider/model setting, wired at
  `AionApp` level in `main.dart` — provider identity isn't a per-project
  concept.
- One Settings screen: connection status + "Test Connection" + a model
  dropdown (Opus 4.8 / Sonnet 5 / Haiku 4.5 — the only models `/apply`
  will confirm the Agent SDK's `model` parameter actually accepts).
- Detecting and surfacing (read-only, informational) an overage/rate-limit
  signal from the bridge subprocess, if the SDK/CLI reports one.

**Out of scope (non-goals) — and why, since several of these narrow the
original idea's stated scope:**

- **Anthropic Messages API, Ollama, OpenAI, OpenAI-compatible, Firebase
  AI Logic** — deferred per the idea's own conclusion. Revisited once
  mobile/web parity is actually being built.
- **Per-phase/tier model routing UI** (`project.md` §5's "Settings →
  Models" with Spec/Watcher/Tier 1-3/Lightweight rows). Nothing in the
  app has a "phase" yet — every consumer that would need to route
  differently per phase (SDD-stage chats, ticket estimation, Inbox
  chats) is itself unbuilt. Building per-phase routing UI now, with zero
  real phases to differentiate between, would be speculative UI with no
  way to validate it's even the right shape. `ModelRouter`'s resolution
  method is written as a single no-argument `resolve()` for this MVP; a
  phase parameter is a mechanical, additive change once a second real
  phase exists to route differently — see design.md's Deviations
  section.
- **`AutomationConfidence` and the budget/usage-window consent gate.**
  The idea's conclusion kept the budget gate in this change's first
  pass, reframed as guarding the Claude Pro/Max usage window. Nothing in
  the Claude Agent SDK exposes a way to query remaining usage-window
  budget proactively (confirmed by inspecting the SDK's documented
  surface during `/explore`) — there is no reliable signal to gate on
  *before* hitting a limit, only an error the CLI/SDK may surface
  *after*. Building `AutomationConfidence` now, for a gate that can only
  ever be reactive (detect-and-inform, not predict-and-consent) and has
  no other consumer yet (no batch-flush gate, no watcher-override case —
  both also unbuilt), is the same premature-abstraction risk as the
  per-phase UI above. This change surfaces an overage/rate-limit signal
  informationally instead (see Scope, above); a real consent-gated
  `AutomationConfidence` type is deferred to whichever change first has
  more than one real gate to unify.
- **Auto-installing the Node.js bridge's dependencies from inside the
  Flutter app.** `agent_bridge/` ships with its own `package.json`; the
  user runs `npm install` there once, same category of manual setup step
  as `flutter pub get`. Aion is a personal, non-distributed tool today —
  automating this is unwarranted complexity for an audience of one.
- **Windows/macOS/Linux-specific Node.js discovery beyond checking
  `PATH`.** If `node` isn't resolvable, the connection test simply
  reports "Node.js not found" — no bundled Node runtime, no installer.

status: APPROVED

Approved: 2026-07-20. No CRITICAL issues found in the Claude Design
export (appended to `design.md` below the architecture section) — every
Material-widget reference in it is an explicit disclaimer ("no
`Scaffold`/`AppBar`", "never `Card`, `ElevatedButton`, ...", "no
Material `CircularProgressIndicator`/`DropdownButton`"), not a proposed
implementation. Every actual component is built from Flutter primitives
(`DecoratedBox`, `Row`/`Column`, `GestureDetector`,
`CustomPaint`+`AnimationController`, `SelectionMenu`). 6 new derived-
tint helper methods to add to `AionColorsHubTokens` in `aion_colors.dart`
before `/apply` — no new hex color tokens, all six reuse existing
`success`/`warning`/`primary` (see the `/design-sync` run's Step 2
output for the exact ready-to-paste Dart). 3 tasks (T13, T14, T18)
annotated with their design.md section references; T8 additionally
flagged with a naming-consistency note (see below).

Non-blocking notes for `/apply` (see the `/design-sync` run's full
output for detail):
  - Use `.withValues(alpha: x)`, not the deprecated `.withOpacity(x)`
    the export's tint-helper snippets use — `project.md`'s Bootstrap
    notes already establish this convention app-wide.
  - The new `checkingTint`/`checkingSpinnerTrack` helpers are
    numerically identical to the existing `pendingTint`/
    `pendingSpinnerTrack` on `AionColorsHubTokens` — consider reusing
    those directly instead of adding duplicates, unless the distinct
    names read better at `ProviderConnectionBadge`'s call sites.
  - **Enum naming mismatch:** the Claude Design export's §1.1
    independently defines `ProviderConnectionState` with the same four
    values (`unknown`/`checking`/`connected`/`disconnected`) as this
    change's own `ProviderConnectionStatus` (design.md's architecture
    §4.1, tasks.md T8). Same enum, two names in the same document — keep
    `ProviderConnectionStatus`, per tasks.md T8's updated note.
  - `design.md` now contains two independently-numbered `§` schemes:
    the original architecture section's §1–§6, and the appended
    Component Spec's own §1–§9. Harmless for a human reader (section
    titles disambiguate) but worth knowing before searching design.md
    for "§4" and finding two unrelated hits.
