# Design: board-task-ordering-indication

## 1. Data layer

### 1.1 `TicketLinkDao` (`data/daos/ticket_link_dao.dart`)

New bulk query, mirroring `deleteLinksForTickets`'s "no per-ticket
filter, whole-table-scoped" shape rather than `getLinksForTicket`'s
per-ticket shape:

```dart
/// Returns every live (neither side trashed) link row whose `linkType`
/// is one of [types], app-wide — not scoped to a single ticket. Used by
/// `TicketsCubit` to compute the Board's `blockedTicketIds` in one
/// query pair instead of one `getLinksForTicket` round-trip per visible
/// card.
Future<List<TicketLinkData>> getLinksByTypes(List<TicketLinkType> types)
```

Implementation: a single `select(ticketLinksTable)` with
`linkType.isIn(types.map((t) => t.name))`, inner-joined against
`ticketsTable` twice (source and target) with both `deletedAt.isNull()`
— same trashed-filter posture `getLinksForTicket` already has, just
without a `sourceTicketId`/`targetTicketId` equality filter.

### 1.2 `TicketLinkRepository` (`domain/repositories/ticket_link_repository.dart`)

```dart
/// Returns every live link whose `linkType` is one of [types],
/// app-wide. See `TicketLinkDao.getLinksByTypes`.
Future<List<TicketLinkData>> getLinksByTypes(List<TicketLinkType> types);
```

`DriftTicketLinkRepository` delegates straight through, same one-line
shape as its existing `getLinksForTicket`/`createLink`.

No change to `createLink` or `TicketLinkType` — see proposal.md's
correction on why no inverse-row write is needed.

## 2. `TicketsCubit` — Board blocked-set

### 2.1 New private helper

```dart
/// Computes the current set of blocked work-ticket ids: a ticket whose
/// blocking counterpart (the other side of a `blocks`/`blockedBy` row)
/// exists, is live, and is not `TicketStatus.done`. Queries
/// `TicketLinkRepository.getLinksByTypes` once, resolves each row's
/// blockee/blocker pair (a `blockedBy` row's blockee is its `source`;
/// a `blocks` row's blockee is its `target`), then looks up each
/// blocker's current status from [allTickets] (already loaded for the
/// Board — no extra per-ticket fetch). Returns the empty set if
/// constructed without a [TicketLinkRepository].
Future<Set<String>> _computeBlockedTicketIds(List<Ticket> allTickets) async
```

Body sketch:
1. `final linkRepo = _linkRepository; if (linkRepo == null) return {};`
2. `final rows = await linkRepo.getLinksByTypes([TicketLinkType.blocks, TicketLinkType.blockedBy]);`
3. `final byId = {for (final t in allTickets) t.id: t};`
4. For each row, compute `(blockeeId, blockerId)`:
   - `blockedBy` → `(row.sourceTicketId, row.targetTicketId)`
   - `blocks` → `(row.targetTicketId, row.sourceTicketId)`
5. Add `blockeeId` to the result set iff `byId[blockerId]?.status != TicketStatus.done` (a blocker missing from `allTickets` — trashed or otherwise not loaded — is treated as *not* blocking, consistent with `getLinksByTypes`'s live-only join).

### 2.2 Call site: board ticket loads

`searchTickets` (`tickets_cubit.dart:288`, the Board's actual load path
per `tickets_list_screen.dart`) computes `blockedTicketIds` via 2.1
right before `emit(TicketsLoaded(...))` and passes it through. Same
treatment for the other `emit(TicketsLoaded(...))` site at line 2767
(`loadMoreTickets`'s continuation). This is a **derived-from-persisted-
data** field, unlike `inFlightExecutionIds`/`inFlightAdvanceIds`
(in-memory-only) — it does not need `_refreshInFlightBoardState`'s
every-mutation-site treatment. It only needs recomputing when the
ticket list itself reloads (new page load) or when a status change or
link creation could plausibly affect it:

- `updateTicketStatus` (a blocker's status changing to/from `done`)
  and `createLink`'s call site in the widened `TicketLinkPicker`
  (a new `blocks`/`blockedBy` row appearing) both call a new
  `_refreshBlockedBoardState()` — mirrors `_refreshInFlightBoardState`'s
  shape (re-emits the current `TicketsLoaded` with a freshly computed
  field, no-ops unless `state is TicketsLoaded`), but recomputes
  `blockedTicketIds` via 2.1 instead of reading in-memory sets.

### 2.3 `TicketsState` (`tickets_state.dart`)

`TicketsLoaded` gains:

```dart
/// Work-ticket ids currently blocked by an unresolved `blocks`/
/// `blockedBy` link (the blocker isn't `done`). Recomputed by
/// `TicketsCubit._computeBlockedTicketIds` on ticket-list load, a
/// blocker's status change, or a new blocking link — see
/// `TicketsCubit._refreshBlockedBoardState`. Added for
/// `aion-arch/changes/board-task-ordering-indication`.
final Set<String> blockedTicketIds;
```
Default `const {}`, added to the constructor and `props`, same pattern
as `inFlightExecutionIds`.

## 3. `TicketsCubit` — decomposition materialization

### 3.1 `_assembleStageContext` gains a `SddStage.proposed` branch

Currently `proposed` matches none of the existing `if`/`else if` arms
(falls through to just title+description). New arm:

```dart
} else if (stage == SddStage.proposed) {
  final childRank = parent.type == TicketType.epic
      ? TicketType.story
      : TicketType.task;
  buffer
    ..writeln()
    ..writeln(
      'Decompose this ${parent.type.name} into child '
      '${childRank == TicketType.task ? "Tasks" : "Stories"}. End your '
      'reply with a fenced block titled "## Decomposition", one line per '
      'child in the exact form '
      '"- ${childRank == TicketType.task ? "Task" : "Story"}: <title>" '
      'optionally suffixed with " (blockedBy: <exact title of an earlier '
      'line in this block>)" when that child cannot start until another '
      'one finishes.',
    );
}
```
(A `story`'s children are always `task`/`bug`-ranked; this proposal only
ever asks for `Task:` lines from a `story` parent, matching
`_assembleStageContext`'s existing rank derivation for
verifying/archived — no request to decompose into `bug`, which is a
human/QA-originated ticket type, not a decomposition target.)

### 3.2 New parser: `_parseDecomposition`

```dart
/// Parses [reply]'s trailing "## Decomposition" fenced block (see
/// `_assembleStageContext`'s `SddStage.proposed` prompt) into an
/// ordered list of `(title, blockedByTitle)` pairs — `blockedByTitle`
/// `null` when the line has no `(blockedBy: ...)` suffix. Returns an
/// empty list if no such block is found or no line matches the
/// expected `"- Story: "`/`"- Task: "` prefix — parse failure is
/// silent, not an error (see proposal.md's fail-open note).
List<(String title, String? blockedByTitle)> _parseDecomposition(
  String reply,
  TicketType childType,
)
```
Regex per line: `^- (?:Story|Task): (.+?)(?: \(blockedBy: (.+)\))?$`,
matched against the block's content only (text between `## Decomposition`
and the next blank line or end of reply). `childType` picks which
literal prefix (`Story`/`Task`) is accepted — a line with the wrong
prefix for `parent.type` is skipped, not an error.

### 3.3 New materializer: `_materializeDecomposition`

```dart
/// Runs once per `proposed`-stage chat turn (called from
/// `_runStageChatTurn` immediately after a successful turn, only when
/// `stage == SddStage.proposed`): parses [reply] via
/// [_parseDecomposition], creates one child ticket per parsed line
/// under [parent] (via `TicketRepository.createTicket`), then — for
/// every line with a `blockedByTitle` that exact-matches (case-
/// insensitive) another parsed line's title — creates a `blockedBy`
/// link from the new child to its blocker sibling (via
/// `TicketLinkRepository.createLink`). An unresolved `blockedByTitle`
/// (no matching sibling title) is skipped for the link only — the
/// child ticket itself is still created. No block, or a block with no
/// parseable lines, is a silent no-op: today's exact behavior (human
/// creates children by hand) is preserved, not treated as failure.
Future<void> _materializeDecomposition(Ticket parent, String reply) async
```
Body: parse → create tickets in parse order, keeping a
`title.toLowerCase() → newTicket.id` map as each is created → second
pass over the parsed list creating `blockedBy` links (new child is
`source`, resolved blocker sibling is `target` — see proposal.md's
direction note) wherever `blockedByTitle` resolves against that map.
Requires both `_linkRepository` and the child having been created
successfully; guarded the same optional-dependency way
`loadDocumentRelations` already guards `_linkRepository`.

### 3.4 Call site

`_runStageChatTurn` (`tickets_cubit.dart:2370`), immediately after
`ChatCubit.runChatTurn` returns `true` (success) and only when
`stage == SddStage.proposed`: `await _materializeDecomposition(parent,
<the AI reply text>)`. `ChatCubit.runChatTurn` doesn't currently return
the reply text (only `bool succeeded`) — it needs a companion accessor,
or `_materializeDecomposition` re-reads the just-posted comment via
`commentRepo.getCommentsForTicket(chatId)`'s most-recent entry (mirrors
`_designSyncApproved`'s own "read back the most recent comment" style
exactly) rather than threading a new return value through
`runChatTurn`'s shared contract. This design picks the latter — no
change to `ChatCubit.runChatTurn`'s signature, which is shared by
coding-execution and every other stage.

## 4. Manual linking — widget layer

### 4.1 `TicketLinkPicker` (`presentation/widgets/ticket_link_picker.dart`)

Gains a `linkTypeOptions` param (`List<TicketLinkType>`, caller-supplied
so a future non-work-ticket caller isn't forced into
`blocks`/`blockedBy`/`duplicates` it doesn't want) and an
`onSelected` signature change: `ValueChanged<Ticket>` →
`void Function(Ticket ticket, TicketLinkType linkType)`. The overlay's
header row gains a leading `SelectionMenu<TicketLinkType>` (same
trigger-pattern component `ticket_metadata_section.dart` already uses
for priority/complexity/type/status), defaulting to `relatesTo`, next
to the existing search field — selecting a candidate row commits
`(candidate, currentlySelectedLinkType)`.

### 4.2 `ticket_metadata_section.dart`'s Linked Tickets call site

- Type gate widened: `ticket.type != TicketType.resource && ticket.type
  != TicketType.bug` → excludes only `page`/`chat`/`signal`/`release`
  (types with no `TicketLink` use case) instead of everything but
  `resource`/`bug`.
- `TicketLinkPicker`'s `candidatesLoader` unchanged in shape; its
  exclusion list (`candidate.type != TicketType.page && candidate.type
  != TicketType.resource`) is reused for work-ticket callers unchanged
  — a work ticket still can't link to a `page`/`resource` this way
  (Documentation stays the entry point for those), consistent with
  `bug`'s existing `relatesTo`-to-`release` use case.
- `linkTypeOptions`: `[TicketLinkType.blocks, TicketLinkType.blockedBy,
  TicketLinkType.relatesTo, TicketLinkType.duplicates]` for `epic`/
  `story`/`task`/`bug`; unchanged single-`relatesTo` behavior preserved
  for `resource` by passing `[TicketLinkType.relatesTo]` there (so the
  existing resource-linking flow keeps its current one-tap UX with no
  new picker step).
- `onSelected` passes the selected `linkType` straight to
  `TicketLinkRepository.createLink` instead of the hardcoded
  `TicketLinkType.relatesTo` literal, then calls
  `TicketsCubit._refreshBlockedBoardState()` (§2.2) if the created type
  was `blocks`/`blockedBy` — otherwise unchanged
  (`loadDocumentRelations` reload).

### 4.3 `loadDocumentRelations` gate widened to match

The doc-comment's `page`/`resource`/`bug`-only gate
(`tickets_cubit.dart:2843-2847`) widens to also include `epic`/`story`/
`task`, mirroring §4.2's widened render gate — otherwise a work
ticket's newly-visible Linked Tickets section would call
`loadDocumentRelations` and get an early return, silently never
populating.

## 5. Board — blocked badge widget layer

### 5.1 `tickets_board_view.dart` — `_CardVisual`

New badge, same file, same class, alongside the existing
`_BoardCardStatusBadge`:

```dart
/// A small "Blocked" pill shown in `_CardVisual`'s meta-chip row
/// whenever the card's ticket id is in `TicketsLoaded.blockedTicketIds`
/// — purely informational, no gate on drag/status-change (idea file
/// Q4). Rendered before the existing `Spacer()` + execution-state
/// badge, in the same row `board-execution-indicators-and-notifications`
/// left room for. Added for
/// `aion-arch/changes/board-task-ordering-indication`.
class _BlockedBadge extends StatelessWidget
```
Static (no animation, unlike `_BoardCardStatusBadge`'s spinning-gear
`running` state) — a link glyph (`PhosphorIcons.linkBreakLight` or
similar "broken link" icon — final glyph choice deferred to
`/design-brief`) + `"Blocked"` label, `AionText.chip` styling matching
`_BoardCardStatusBadge`'s type scale, `dangerTint`-family fill (an
open dependency reads as a caution state, distinct from
`_BoardCardStatusBadge`'s neutral `pendingTint`/`secondary` fills).
Exact color/glyph/geometry is a `/design-brief`/`/design-sync` question
per the idea file's resolved open question, not fixed here.

`_CardVisual.build`'s meta-chip `Row` gains:
```dart
if (isBlocked) ...[
  const SizedBox(width: AionSpacing.sp8),
  const _BlockedBadge(),
],
```
inserted right after the existing `PriorityBadge` conditional and
before the execution-state `Spacer()` block — `isBlocked` resolved via
`context.select((TicketsCubit cubit) => cubit.state is TicketsLoaded &&
(cubit.state as TicketsLoaded).blockedTicketIds.contains(ticket.id))`,
same `context.select`-scoped-to-this-ticket's-id discipline
`_cardExecutionState` already follows so a card only rebuilds on its
own blocked-state change.

Applies to `epic`/`story`/`task`/`bug` cards only (the only types with
a meaningful `blocks`/`blockedBy` relationship) — `isBlocked` resolves
`false` unconditionally for every other `TicketType` reaching the
Board (there are none today; the Board only ever renders work-type
tickets per `TicketBoardView`'s existing caller-side filtering, so this
is a defensive floor, not a new filter).

# Aion — Dependency Link Types & Board "Blocked" Badge: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and references the [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md) (its `SelectionMenu<T>` and `TicketLinkPicker` usage) and the [Board Execution/Advance Indicators Spec](./Aion%20Board%20Advance%20Indicators%20Spec.md) (the `BoardCardStatusBadge` meta-row pill this badge sits beside). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AionPriorityColors`, `TicketBoardCard`, `TicketLinkPicker`, `TypeChip`, `PriorityBadge`, `SelectionMenu<T>`, and `BoardCardStatusBadge` — by name.

Mockups: [Aion Link Type and Blocked Badge Mockups](./Aion%20Link%20Type%20and%20Blocked%20Badge%20Mockups.dc.html).

This change makes ticket **dependencies** — a first-class relationship the app already models — both *creatable* (pick a link type when adding a link) and *legible* (see an unresolved blocker on the board). It **adds no new screens**. It extends two existing surfaces:

- **`TicketLinkPicker`** (the "+ Add" overlay on any ticket-detail *Linked Tickets* section) — a new **`LinkTypeSelector`** (§1) is added to the overlay header, above the existing search field. The search field and candidate list below it are **unchanged and out of scope**. The user picks a link type, then picks a candidate row exactly as today; the two together commit the link.
- **`TicketBoardCard`** (Kanban board, every ticket type) — a new non-interactive **`BlockedBadge`** (§2) is inserted into the card's existing meta-chip row, after the `PriorityBadge` and before the trailing spacer / execution badge (§3).

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (non-Material) / `Padding` / `Row` / `Column` / `GestureDetector` / `MouseRegion` / `Focus` / `Overlay` + `CompositedTransformFollower` / `AnimatedScale` / `SingleChildScrollView` / `CustomPaint`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `DropdownButton`, `PopupMenuButton`, `Chip`, `InkWell`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token or a documented derivation that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)`, never a hardcoded ARGB. The default tinted-chip fill alpha is `fillAlpha` = `0.11` (Arctic) / `0.16` (Obsidian), read at the call site as `ThemeScope.of(context).fillAlpha`.

**New tokens: none.** No new `AionColors`, `AionText`, or `AionRadius` member is required. The `LinkTypeSelector` reuses the app's existing `SelectionMenu` trigger/menu geometry (SDD Ticket Execution §1.2 / §5.2). The `BlockedBadge` reuses `AionText.chip` with tracking relaxed and **no** uppercase transform (matching `BoardCardStatusBadge` §1.2), and the `dangerTint` / `dangerBorderTint` derivations already used by the stage-advance failure banner.

## 0. Where each surface sits

| Component | Screen / widget | Placement | Which ticket types |
|---|---|---|---|
| `LinkTypeSelector` (§1) | `TicketLinkPicker` overlay | Overlay header, full-width, directly **above** the search field | all (the picker is opened from any ticket's Linked Tickets section) |
| `BlockedBadge` (§2) | `TicketBoardCard` on the Kanban board | Meta-chip row (holds `TypeChip` + optional `PriorityBadge`), **after** the priority badge, **before** the trailing spacer / execution badge (§3) | all — shown iff the ticket has an unresolved `blocks`/`blockedBy` dependency |

The `LinkType` a selector commits and the `BlockedBadge` a card shows are the two ends of the same relationship: a `blocks` / `blockedBy` link created in the picker is exactly what later resolves a card to "Blocked" once the linked ticket is not yet done.

```dart
// The four link relationships offered by LinkTypeSelector. Already modeled on the ticket;
// this feature only adds the ability to choose one at creation time.
enum TicketLinkType { blocks, blockedBy, relatesTo, duplicates }
```

`BlockedBadge` derives from live dependency state, not a stored flag: a card is blocked when it has ≥1 `blockedBy` link (or an inbound `blocks` link from another ticket) whose source ticket is not in a done column. No ticket-data-model change, no new persisted field.

## 1. `LinkTypeSelector`

A compact single-select control added to the `TicketLinkPicker` overlay header. It is a straightforward instance of the app's existing `SelectionMenu<T>` pattern (trigger + dropdown overlay), typed to `TicketLinkType`, so its **trigger geometry, overlay panel, and state model are inherited unchanged** from SDD Ticket Execution §1.2 / §1.5 and §5.2 — only the option set, glyphs, and copy are new. It defaults to `relatesTo` (today's implicit behavior, now explicit).

```dart
class LinkTypeSelector extends StatefulWidget {
```

Each option carries a directional glyph so the *relationship direction* reads at a glance, plus a one-line sub-label used only in the open menu (§1.5).

## 2. `BlockedBadge`

A small, **non-interactive** filled pill added to `TicketBoardCard`, shown when the ticket has an unresolved `blocks` / `blockedBy` dependency on a ticket that is not yet done. It is a sibling of `BoardCardStatusBadge` (Board Advance Indicators §1) — same pill geometry, same meta-row placement family — but in the **`danger` tint family**, because a blocker is an impediment to progress (distinct from the calm `pendingTint` "actively working" and neutral `secondary` "queued" badges it may sit beside).

```dart
class BlockedBadge extends StatelessWidget {
  const BlockedBadge();
  // no props, no onTap, no MouseRegion cursor change — a single static state.
}
```

### 2.1 Container

- `DecoratedBox` → `Padding` → `Row` (`mainAxisSize: min`, `crossAxisAlignment: center`, `gap: 4`).
- **Padding:** `EdgeInsets.symmetric(horizontal: 7, vertical: 3)` → visual height ≈ `19px`, sitting flush with the `TypeChip` and any `BoardCardStatusBadge` on the same row.
- **Radius:** `AionRadius.pill` (22) → a stadium pill (height-clamped), matching the `TypeChip` / `BoardCardStatusBadge` pill family.
- **Fill:** `dangerTint(isDark)` = `danger.withOpacity(isDark ? 0.16 : 0.11)` (`#CE3D54 / #F1546C` base). Reuses the existing helper (stage-advance failure banner).
- **Border:** `1px solid dangerBorderTint(isDark)` = `danger.withOpacity(isDark ? 0.42 : 0.28)`. A hairline keeps the light tint legible on `surface` (the neutral `queued` badge takes the same treatment; the `pendingTint` active badges are borderless — so the border also visually groups "attention" states apart from "active").
- **Shadow:** none.

### 2.2 Leading glyph

- **Glyph:** `link-break` (`link-simple-break` / `prohibit` fallback) — a broken-dependency mark. In the mockup this is approximated by `⊘` (`U+2298`).
- **Size:** `11px`.
- **Color:** `danger` (`#CE3D54 / #F1546C`) — same as the label.
- **Motion:** none. Static.

### 2.3 Label

Reuse `AionText.chip` (Manrope 10.5 / w700) **but do not uppercase the string** and relax tracking — identical treatment to `BoardCardStatusBadge` §1.2, so the two pills read as one chip family:

```dart
AionText.chip.copyWith(letterSpacing: 0.2, height: 1.0) // rendered mixed-case: "Blocked"
```

- **Text:** `"Blocked"`.
- **Color:** `danger` (`#CE3D54 / #F1546C`).

### 2.4 Dimensions recap

- Height ≈ `19px` (from `vertical: 3` padding + 11px glyph / 10.5px cap). Width sizes to content.
- Inner gap glyph→label: `4`. Padding `EdgeInsets.symmetric(horizontal: 7, vertical: 3)`. Radius `AionRadius.pill` (22). Glyph `11px`. Icon color = label color = `danger`.

### 2.5 States — confirmed single-state

**Non-interactive.** No hover / focused / pressed / disabled / error states, and **no motion** (unlike the `running` badge's spinning gear). It is purely informational and never blocks interaction with the card — the whole card remains tappable *through* it. The badge appears / disappears on a plain rebuild as the ticket's live dependency state changes; no entrance/exit animation.

## 3. Composed card meta row

The `TicketBoardCard` meta-chip row is unchanged in structure — this section only fixes where `BlockedBadge` slots in.

- **Row:** `Row`, `gap: AionSpacing.sp8` (8), `crossAxisAlignment: center`.
- **Order, left to right:** `TypeChip` → optional `PriorityBadge` → **`BlockedBadge`** → `Spacer()` → optional execution `BoardCardStatusBadge`.
- `BlockedBadge` sits in the **leading cluster** (after priority, before the `Spacer`); the execution badge is pushed to the **trailing edge** by the `Spacer`. When both are present they never touch — the `Spacer` guarantees a gap — and their color families read as distinct: `BlockedBadge` in `danger` tint on the left, the `running`/`queued` `BoardCardStatusBadge` in `pendingTint`/`secondary` on the right.

| Variant | Row contents |
|---|---|
| **(a) blocked only** | `TypeChip` · `PriorityBadge` · `BlockedBadge` · `Spacer` |
| **(b) blocked + execution** | `TypeChip` · `PriorityBadge` · `BlockedBadge` · `Spacer` · `BoardCardStatusBadge(running)` |
| **(c) neither (baseline)** | `TypeChip` · `PriorityBadge` · `Spacer` *(unchanged from today)* |

`BlockedBadge`'s `danger` tint coexists legibly with every `PriorityBadge` hue — Critical (rose), High (amber), Medium (teal), Low (slate), and None — because priority badges are the low-contrast solid-fill `AionPriorityColors` chips and `BlockedBadge` is a bordered tint pill; the two never share an edge treatment. See the mockup's §1d for all five priority pairings.
