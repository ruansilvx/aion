# Project Type Aware Conventions And Verification

# Proposal: project-type-aware-conventions-and-verification

## Revision note

This supersedes this proposal's first draft, which generalized
`FlutterVerifier` into a `ProcessVerifier` running a project-configured
shell command (`Project.verifyCommand`/`verifySetupCommand`, set via new
`NewProjectScreen` fields). That approach was wrong: Aion's own
architecture already gives "verify" a specific meaning — the `/verify`
OpenSpec skill, an agentic review against a change's own material, not a
shell invocation — and that skill is already one of the 13 baseline
`skills/*` assets this same proposal is making stack-agnostic (see
Gap 2 below). A user-typed shell command duplicated, and conflicted
with, a mechanism Aion already ships. This draft replaces the
shell-command gate with an agentic one: coding-execution's verify step
now runs the project's effective `skills/verify` baseline content as a
real model turn, using the model's own tool access to check whatever
the codebase's own tooling actually is — rather than Aion's Dart code
shelling out to a hardcoded or user-configured command.

## What

Aion's baseline/coding-execution system was built entirely around Aion
developing itself, and breaks down the moment a project of any other
stack is attached. Two concrete gaps confirmed in code:

1. **`FlutterVerifier`** (`core/build/flutter_verifier.dart`) is a
   hardcoded concrete class that shells out to `flutter analyze`/`flutter
   pub get` — the coding-execution verify gate `coding-execution-
   reliability-and-safety` shipped. It only works for a Flutter project,
   and it's a raw mechanical exit-code check with no awareness of what
   "correct" actually means for the code it's checking.
2. **The bundled `skills/*` baseline assets** (`assets/baseline/0.2.0/
   manifest.json`) are literal pointers into `aion-arch/.claude/skills/`
   and `aion-arch/flutter-conventions.md` — meaningful only when the
   managed project *is* Aion itself. For any other attached project
   these pointers resolve to nothing — including the `skills/verify`
   asset, which is exactly the mechanism Gap 1 should have used instead
   of inventing a parallel, mechanical one.

These turn out to be the same gap, and this change closes both at once:

1. **A new, self-contained, stack-agnostic skill baseline** (baseline
   version `0.3.0`) replaces every `aion-arch`-pointer asset with real,
   generic SDD-workflow content. `aion-arch`'s own skills are untouched —
   they stay purpose-built for developing Aion itself; this is the
   *default* bundle every other project starts from. The `skills/verify`
   asset in this new bundle is written as genuinely operative
   instructions (not just descriptive orientation text, unlike the other
   12), because it's about to become a real model prompt, not just
   reference material — see point 2.
2. **Coding-execution's verify gate becomes agentic, not mechanical.**
   After the implement turn, `TicketsCubit._runCodingExecution` runs a
   second model turn using the project's *effective* `skills/verify`
   content (its bundled default, or a project override if one exists) as
   its operative instructions, plus the effective `conventions/
   architecture-conventions` content for background. The model uses its
   own file/git/bash tool access to check its own work — running
   whatever build, lint, or test tooling is actually appropriate for the
   codebase — and ends its reply with either `"VERIFICATION: PASSED"` or
   `"VERIFICATION: FAILED — <reason>"`. Aion trusts that terminal line
   the same way it already trusts `"IMPLEMENTATION: DONE"` and
   `"EXECUTION: PR_OPENED"` — an established convention, not a new trust
   model. `FlutterVerifier` is deleted outright, with **no
   shell-command-running replacement** — there is nothing generic left
   for Aion's own Dart code to shell out to, because verification is now
   the model's job, guided by a real skill.
3. **`BaselineTailoringService`** writes a real `ProjectOverride` for the
   architecture-convention asset at project-creation time, populated from
   lightweight marker-file detection (`ProjectStackDetector` —
   `pubspec.yaml`, `package.json`, `Cargo.toml`, etc.): the detected
   language and a *suggested* setup/check command, written as guidance
   text the model reads during both the implement and verify turns — not
   a value Aion's own code runs or enforces mechanically.
4. **Override-authoring UI** — a new "Overrides" section in Settings
   lets a user view and edit any baseline asset's project-local override,
   resolving `projects.md`'s already-known "Override-authoring UI" gap as
   a byproduct of building the tailoring-editing surface this change
   needs anyway. This is also what makes editing a project's own
   `skills/verify` content (e.g. "always run `cargo clippy --
   -D warnings` too") a real, user-facing capability, not just an
   internal default no one can see or change.

## Why

`self-iteration-sequencing.md` and `new-project-onboarding.md` both
depend on Aion being usable against a project that isn't Aion itself.
`new-project-onboarding`'s attach-flow only makes sense once a non-
Flutter project gets its own working verify gate and non-broken default
skill content — this change is the prerequisite both those ideas already
flagged (`aion-arch/ideas/project-type-aware-conventions-and-
verification.md`).

Every design decision below reuses an existing pattern rather than
inventing one:

- The verify gate reuses the `skills/verify` baseline asset — a
  mechanism this proposal is *already* building stack-agnostic content
  for (point 1 above) — instead of inventing a second, parallel
  verification concept (a shell command) that duplicates and conflicts
  with it.
- The verify turn's "fail closed" parsing (design.md §5) preserves the
  actual safety property `coding-execution-reliability-and-safety`
  shipped — a run never opens a PR on an ambiguous or missing result —
  even though *how* pass/fail is determined changes from an exit code to
  a model's own terminal-line report.
- Tailoring writes real `ProjectOverride` files into the exact same
  `<rootPath>/.aion/overrides/` mechanism `storage-model-per-project-
  scoping`/`hub-and-infrastructure-to-support-multiple-projects` already
  shipped — no new persistence layer.
- The new baseline version (`0.3.0`) follows the exact versioning
  precedent `0.1.0` → `0.2.0` already set (a new manifest + asset
  directory, old versions untouched, `BundledBaselineRepository.
  getAvailableBaselineVersions().last` picks it up automatically as the
  new default).
- Reading `BaselineRepository` content into a real model prompt — a gap
  this proposal's first draft explicitly left unsolved — is not
  reinvented as a general-purpose mechanism here either. It's scoped
  narrowly to exactly the two assets coding-execution actually needs
  (`conventions/architecture-conventions`, `skills/verify`), via a small
  `TicketsCubit`-local resolver, not a new cross-cutting "wire baseline
  content into every prompt" system. See design.md §5 and Out of scope
  below.

## Scope decisions (read before `/apply`)

This idea's own brainstorm assumed `new-project-onboarding`'s attach flow
and codebase-summarization-depth choice already existed, since the two
ideas were explored together. Sequencing has this change proposed
*first* (see `self-iteration-sequencing.md`'s updated ordering), so two
things are deliberately scoped down here rather than built against
features that don't exist yet:

- **Only today's "New Project" flow** (`NewProjectScreen`/
  `CreateProjectCubit`) gets the marker-file-detected tailoring —
  `new-project-onboarding`'s not-yet-built "Attach to existing project"
  flow will reuse the same `BaselineTailoringService` machinery once it
  exists, not duplicate it. (The original draft's plan to also add
  verify-command fields to `NewProjectScreen` is dropped along with the
  shell-command approach — see Revision note.)
- **Only the shallow (template-substitution) tailoring path is built.**
  The idea's "full agentic tailoring, tied to codebase-summarization
  depth" path depends on `new-project-onboarding`'s not-yet-built deep
  summarization feature. `BaselineTailoringService`'s public API
  (`tailorForDetectedStack`) is designed so that feature can call it
  again later with richer input, but this change only wires the
  marker-file-detected path automatically at project creation.

One more scope decision, corrected from the first draft: **reading
baseline content into a model prompt is now in scope, but only for
coding-execution's two directly-relevant assets** (`conventions/
architecture-conventions`, `skills/verify`), consumed by a small
resolver local to `TicketsCubit`. Every *other* baseline asset
(`skills/explore`, `skills/propose`, `skills/apply`, etc.) is still never
read into any prompt anywhere — that broader gap (see `specs/spec.md`'s
Non-goals) remains genuinely out of scope, since nothing in Aion's
ticket-driven coding-execution flow currently has a use for them.

## Out of scope

- Attach-to-existing-project flow, Inbox, codebase summarization —
  `new-project-onboarding`.
- Wiring any baseline asset *other than* `conventions/
  architecture-conventions` and `skills/verify` into a model prompt — a
  pre-existing gap, not solved here.
- Per-language built-in verifier classes, and any project-level,
  user-configured verify/setup shell command — both deliberately
  rejected; see Revision note. `Project` gains no new fields in this
  change.
- Baseline version *upgrade* for an already-created project —
  `baseline-version-upgrade-flow-for-an-existing-project` (separate,
  not-yet-proposed idea). A project pinned to `0.1.0`/`0.2.0` still gets
  the old pointer-based `skills/verify` content — no worse than today's
  hardcoded-Flutter behavior, not a regression, just still unfixed for
  those projects until that idea ships.
- Rich Markdown split-view editor for override content — the override
  editor added here is a plain multi-line text field, not the fancier
  editor `create-edit-and-delete-pages` built for Page ticket content
  (that editor is coupled to the `Ticket`/Page entity model; decoupling
  it to work over raw override files is unnecessary scope here).
