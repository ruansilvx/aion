# Design: Ticket Search & Filters

## Architecture overview

```
TicketsListScreen (widget)
  - owns local filter state: _searchQuery, _statusFilter, _typeFilter, _priorityFilter
  - debounces text input (Timer, ~300ms), calls filters immediately
        |
        v
TicketsCubit.searchTickets({query, status, type, priority})
        |
        v
TicketRepository.searchTickets({query, status, type, priority})   [new interface method]
        |
        v
DriftTicketRepository.searchTickets(...)   [new impl, reuses existing _toEntity]
        |
        v
TicketDao.searchTickets(...)   [new DAO method, two query paths]
        |
        v
  no query text  ->  typed drift `select(ticketsTable)` + `.where()` on
                      non-null filters, `.orderBy(createdAt desc)`
  query text set ->  raw `customSelect` joining `tickets_fts MATCH ?`,
                      same filters in WHERE, `ORDER BY bm25(tickets_fts) ASC`
```

`loadTickets()` is removed from `TicketsCubit` — its only two call sites
(`TicketsListScreen.initState`, the error-state Retry button) both move to
`searchTickets()` called with no arguments, which is equivalent (no
filters = every ticket, `created_at desc` — identical to today's
`getAllTickets()` behavior). `TicketRepository.getAllTickets()` itself is
**not** removed — `TicketsCubit.getValidParentCandidates` still calls it
(see proposal.md's Out of scope), so it stays a live, needed method.

## Schema change

`aion/lib/core/database/app_database.dart`: `schemaVersion` goes from `1`
to `2`. This is the first migration this project has ever needed —
`MigrationStrategy.onUpgrade` is currently absent.

New SQL, applied both on fresh install (`onCreate`) and on existing
databases (`onUpgrade` from 1): three indexes plus one FTS5 virtual table
plus three sync triggers, extracted into a shared private helper so
`onCreate`/`onUpgrade` don't duplicate the statements:

```dart
@override
int get schemaVersion => 2;

@override
MigrationStrategy get migration => MigrationStrategy(
  onCreate: (Migrator m) async {
    await m.createAll();
    await into(ticketIdSequenceTable).insert(
      const TicketIdSequenceTableCompanion(id: Value(1), seq: Value(0)),
    );
    await _createSearchInfrastructure(m);
  },
  onUpgrade: (Migrator m, int from, int to) async {
    if (from < 2) {
      await _createSearchInfrastructure(m);
    }
  },
);

/// Adds the status/type/priority indexes and the FTS5 search index (plus
/// its sync triggers) for ticket search/filtering. Shared by `onCreate`
/// (fresh install) and `onUpgrade` from schema 1 (existing local
/// databases) so both end up with identical search infrastructure.
///
/// `tickets` is a normal (non-`WITHOUT ROWID`) table, so it has SQLite's
/// implicit integer `rowid` even though its declared primary key (`id`)
/// is a UUID `TEXT` column — that `rowid` is what ties `tickets_fts` back
/// to `tickets` via `content_rowid='rowid'`.
Future<void> _createSearchInfrastructure(Migrator m) async {
  await m.database.customStatement(
    'CREATE INDEX IF NOT EXISTS idx_tickets_status ON tickets(status);',
  );
  await m.database.customStatement(
    'CREATE INDEX IF NOT EXISTS idx_tickets_type ON tickets(type);',
  );
  await m.database.customStatement(
    'CREATE INDEX IF NOT EXISTS idx_tickets_priority ON tickets(priority);',
  );

  await m.database.customStatement('''
    CREATE VIRTUAL TABLE IF NOT EXISTS tickets_fts USING fts5(
      title, description, content='tickets', content_rowid='rowid'
    );
  ''');

  // Backfill: index whatever rows already exist. A no-op on a fresh
  // onCreate (tickets is empty at this point), essential on onUpgrade
  // (existing local ticket data must become searchable retroactively —
  // the triggers below only cover writes from this point forward).
  await m.database.customStatement('''
    INSERT INTO tickets_fts(rowid, title, description)
    SELECT rowid, title, description FROM tickets;
  ''');

  await m.database.customStatement('''
    CREATE TRIGGER IF NOT EXISTS tickets_fts_ai AFTER INSERT ON tickets BEGIN
      INSERT INTO tickets_fts(rowid, title, description)
      VALUES (new.rowid, new.title, new.description);
    END;
  ''');
  await m.database.customStatement('''
    CREATE TRIGGER IF NOT EXISTS tickets_fts_ad AFTER DELETE ON tickets BEGIN
      INSERT INTO tickets_fts(tickets_fts, rowid, title, description)
      VALUES ('delete', old.rowid, old.title, old.description);
    END;
  ''');
  await m.database.customStatement('''
    CREATE TRIGGER IF NOT EXISTS tickets_fts_au AFTER UPDATE ON tickets BEGIN
      INSERT INTO tickets_fts(tickets_fts, rowid, title, description)
      VALUES ('delete', old.rowid, old.title, old.description);
      INSERT INTO tickets_fts(rowid, title, description)
      VALUES (new.rowid, new.title, new.description);
    END;
  ''');
}
```

The `INSERT INTO tickets_fts(tickets_fts, rowid, ...) VALUES ('delete', ...)`
form is FTS5's documented "special command" syntax for external-content
tables — it removes that row from the index. `AFTER UPDATE` issues a
delete-then-reinsert pair rather than trying to patch the index in place,
which is the standard, documented pattern for external-content FTS5
tables (SQLite's own FTS5 docs use this exact trigger trio).

## DAO: two query paths

`aion/lib/features/tickets/data/daos/ticket_dao.dart` gains one public
method and one private helper:

```dart
/// Returns tickets matching every non-null filter (ANDed). With [query]
/// null/empty, returns a plain filtered list ordered by `created_at desc`
/// (identical shape to [getAllTickets] when every filter is also null).
/// With [query] set, matches against the `tickets_fts` index (title +
/// description) and orders by relevance (`bm25`, ascending — SQLite's
/// bm25 scores are negative, more-negative meaning a better match).
Future<List<TicketData>> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
}) {
  final trimmed = query?.trim() ?? '';
  if (trimmed.isEmpty) {
    final q = select(ticketsTable)
      ..orderBy([(t) => OrderingTerm.desc(t.createdAt)]);
    if (status != null) q.where((t) => t.status.equals(status.name));
    if (type != null) q.where((t) => t.type.equals(type.name));
    if (priority != null) q.where((t) => t.priority.equals(priority.name));
    return q.get();
  }

  final conditions = <String>['tickets_fts MATCH ?'];
  final variables = <Variable<Object>>[Variable(_buildFtsQuery(trimmed))];
  if (status != null) {
    conditions.add('tickets.status = ?');
    variables.add(Variable(status.name));
  }
  if (type != null) {
    conditions.add('tickets.type = ?');
    variables.add(Variable(type.name));
  }
  if (priority != null) {
    conditions.add('tickets.priority = ?');
    variables.add(Variable(priority.name));
  }

  return customSelect(
    'SELECT tickets.* FROM tickets_fts '
    'JOIN tickets ON tickets.rowid = tickets_fts.rowid '
    'WHERE ${conditions.join(' AND ')} '
    'ORDER BY bm25(tickets_fts) ASC',
    variables: variables,
    readsFrom: {ticketsTable},
  ).map((row) => ticketsTable.map(row.data)).get();
}

/// Converts free-typed search text into a safe FTS5 MATCH query: each
/// whitespace-separated token becomes a quoted, prefix-matched literal
/// (`"token"*`), ANDed together (FTS5's default when terms are just
/// space-separated). Quoting every token avoids FTS5 query-syntax errors
/// from characters that are otherwise special to FTS5 (`-`, `(`, `"`,
/// `:`, ...) appearing in ordinary user input; an embedded `"` is escaped
/// by doubling it, per FTS5's string-literal rules.
String _buildFtsQuery(String raw) {
  final tokens = raw.split(RegExp(r'\s+')).where((t) => t.isNotEmpty);
  return tokens.map((t) => '"${t.replaceAll('"', '""')}"*').join(' ');
}
```

Every value that comes from user input or an enum (`status.name`,
`_buildFtsQuery(trimmed)`, etc.) is passed as a bound `Variable`, never
string-interpolated into the SQL text itself — only the fixed set of
`AND`-clause fragments (whose *shape*, not content, depends on which
filters are non-null) is built as a string. This is the same
parameterization discipline `TicketDao.insertTicket` already follows;
no new SQL-injection surface.

`getAllTickets()` is unchanged and stays for `getValidParentCandidates`.

## Repository layer

`TicketRepository` (domain) gains one interface method:

```dart
/// Returns tickets matching every non-null filter (ANDed): [status],
/// [type], [priority] restrict to an exact match on that field; [query]
/// full-text-matches against title/description. All parameters
/// omitted/null is equivalent to [getAllTickets]. Ordered by relevance
/// when [query] is set, otherwise by creation date descending.
Future<List<Ticket>> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
});
```

`DriftTicketRepository` implements it as a thin pass-through, reusing the
existing `_toEntity` mapper exactly like `getAllTickets` does:

```dart
@override
Future<List<Ticket>> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
}) async {
  final rows = await _db.ticketDao.searchTickets(
    query: query,
    status: status,
    type: type,
    priority: priority,
  );
  return rows.map(_toEntity).toList();
}
```

## Cubit

`TicketsCubit.loadTickets()` is replaced by:

```dart
/// Fetches tickets matching every non-null filter (ANDed) — see
/// [TicketRepository.searchTickets]. Called with no arguments, this is
/// equivalent to the old `loadTickets()` (every ticket, most recent
/// first). Emits [TicketsLoading] first only when nothing is on screen
/// yet ([TicketsInitial]/[TicketsError]/[TicketDeleted]) — once a ticket
/// list is already showing, the previous list stays visible until the
/// new results arrive, so re-searching/re-filtering doesn't flash a
/// spinner over the existing list on every keystroke. Emits
/// [TicketsLoaded] on success, [TicketsError] if the repository call
/// throws.
Future<void> searchTickets({
  String? query,
  TicketStatus? status,
  TicketType? type,
  TicketPriority? priority,
}) async {
  final hasVisibleList = switch (state) {
    TicketsLoaded() ||
    TicketCreating() ||
    TicketCreated() ||
    TicketStatusUpdating() ||
    TicketStatusUpdated() => true,
    _ => false,
  };
  if (!hasVisibleList) emit(const TicketsLoading());

  try {
    final tickets = await _repository.searchTickets(
      query: query,
      status: status,
      type: type,
      priority: priority,
    );
    emit(TicketsLoaded(tickets));
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

No new state class — `TicketsLoaded`/`TicketsState` are unchanged. The
active filter values themselves are **not** cubit state; they're owned by
`TicketsListScreen` as local widget state (see below), the same way
`_viewMode` already is. This keeps `TicketsLoaded`'s shape untouched (no
new fields, no risk to the existing `TicketCreating`/`TicketStatusUpdating`
list-carrying states that don't need to know about filters) and matches
the existing precedent that UI-only concerns live in the widget, not the
Cubit.

**Accepted, undefended edge case:** no request-generation guard exists
against out-of-order responses (e.g. a slow query for an earlier keystroke
resolving after a faster one for a later keystroke). Given debouncing
already limits call frequency and local SQLite queries are fast, this is
judged not worth the added complexity at personal scale — noted here so
it's a deliberate omission, not an oversight.

## Widget: `TicketsListScreen`

`_TicketsListScreenState` gains local filter state alongside the existing
`_viewMode` field:

```dart
final TextEditingController _searchController = TextEditingController();
TicketStatus? _statusFilter;
TicketType? _typeFilter;
TicketPriority? _priorityFilter;
Timer? _searchDebounce;
```

- The existing decorative search `Row` (`tickets_list_screen.dart:164-193`)
  is replaced by an `AppTextField` bound to `_searchController`, hint text
  reusing the existing `ticketsListSearchHint` l10n key. `onChanged`
  cancels any pending `_searchDebounce` timer and starts a new ~300ms one;
  when it fires, calls `_runSearch()`.
- A new filter row (exact layout resolved via `/design-brief` — see
  proposal.md's Design gate) holds three `AppDropdown<TicketStatus?>` /
  `AppDropdown<TicketType?>` / `AppDropdown<TicketPriority?>` instances.
  Each list of `items` is `[null, ...EnumType.values]`, with `itemLabel`
  mapping `null` to a new "All ___" l10n string and every other value to
  the existing `ticketStatusLabel`/`ticketTypeLabel`/`ticketPriorityLabel`
  helpers (`tickets_board_view.dart`) already used elsewhere. Selecting an
  item calls `_runSearch()` immediately (no debounce needed — discrete
  selection, not per-keystroke text).
- `_runSearch()` reads all four current local values and calls
  `context.read<TicketsCubit>().searchTickets(query: ..., status: ...,
  type: ..., priority: ...)` — always passing the full current filter
  set, not just whichever one changed.
- `initState` calls `_runSearch()` instead of `loadTickets()` (equivalent
  at that point — every field is still at its default `null`/empty).
- The error state's Retry `AppButton.onPressed` also calls `_runSearch()`
  instead of `loadTickets()`, so retrying re-applies whatever
  search/filters were active rather than silently dropping them.
- `dispose()` cancels `_searchDebounce` and disposes `_searchController`.

### Two empty states

`_buildTicketsBody`'s existing `tickets.isEmpty` branch currently always
shows `ticketsListEmptyState` ("No tickets yet"). It now branches on
whether any filter is active:

```dart
final hasActiveFilter = _searchController.text.trim().isNotEmpty ||
    _statusFilter != null || _typeFilter != null || _priorityFilter != null;

if (tickets.isEmpty) {
  return Center(
    child: Text(
      hasActiveFilter
          ? context.l10n.ticketsListNoResultsState
          : context.l10n.ticketsListEmptyState,
      style: AionText.body.copyWith(color: c.textMuted),
    ),
  );
}
```

This is the reason `hasActiveFilter` needs to be computable from widget
state alone (see the Cubit section above) rather than needing a round
trip through `TicketsState`.

### Considered and rejected

A clear ("×") button inside the search field to reset text in one tap was
considered and dropped — `AppTextField` has no suffix-icon slot today,
and adding one is a new capability on a shared primitive outside this
change's scope. Deleting the text manually clears the search; "All ___"
is already a selectable item in each filter dropdown, so no separate
"clear filters" control is needed either.

## Test plan

**`ticket_dao`/`drift_ticket_repository` — real in-memory Drift, not
mocktail.** This project's existing convention (`flutter-conventions.md`)
is "mock the DAO via mocktail; don't spin up a real in-memory Drift
instance unless the test is specifically about persistence behavior" —
but `drift_ticket_repository_test.dart` already opens a real
`AppDatabase(NativeDatabase.memory())` and exercises the real DAO
underneath (it's a persistence-behavior test by nature). FTS5/migration
correctness is the textbook case for that exception — there is nothing
meaningful to verify by mocking the SQL itself. New cases are **added to
the existing `drift_ticket_repository_test.dart`** (no new test file):
create several tickets with distinct titles/descriptions/status/type/
priority, then assert `repository.searchTickets(...)`:
  - with only `query` set, returns title/description matches, best match
    (title hit) ranked ahead of a weaker one (description-only hit);
  - with only `status`/`type`/`priority` set, returns only exact matches;
  - with `query` + a structured filter combined, both apply (ANDed);
  - with everything null, returns everything (parity with
    `getAllTickets`);
  - a query with FTS5-special characters in it (e.g. a title containing
    `-`) does not throw.

**Migration test (new case, same file).** Because this is the project's
first-ever migration, add one test that exercises `onUpgrade` specifically
rather than only `onCreate` (every other test's `NativeDatabase.memory()`
only ever creates fresh at the *current* `schemaVersion`, which never
touches the upgrade path): manually create the pre-migration (schema 1)
table shape via raw `customStatement` SQL against a fresh
`NativeDatabase.memory()`, insert a couple of ticket rows directly, set
the connection's `user_version` pragma to `1`, then open a new
`AppDatabase` against that same connection. Drift detects
`user_version(1) != schemaVersion(2)` and runs `onUpgrade` automatically;
assert the pre-existing rows are now findable via `searchTickets(query:
...)` — proving the backfill `INSERT INTO tickets_fts ... SELECT ... FROM
tickets` actually ran. (A heavier drift_dev schema-snapshot/`SchemaVerifier`
setup was considered and is disproportionate to this project's scale —
this hand-rolled version is sufficient given there is exactly one
migration to verify today.)

**`tickets_cubit_test.dart`.** Replace the two existing `loadTickets`
`blocTest` cases (success/exception) with equivalent `searchTickets()`
(no-args) cases against a mocked `TicketRepository.searchTickets` instead
of `getAllTickets`. Add cases: `searchTickets` with a mock repository
already returning a list from a prior successful load emits only
`[TicketsLoaded(...)]` (no intervening `TicketsLoading`) — covering the
"don't flash a spinner over a visible list" behavior. Add a case starting
from `TicketsInitial` that does expect `[TicketsLoading, TicketsLoaded]`.

No widget test is added for `TicketsListScreen` — this project doesn't
widget-test its screens (per `project.md`'s testing section); the
debounce/filter-row/empty-state behavior is confirmed in the manual
interactive pass instead.

# Aion — Ticket Search & Filters Specification

Implementation-ready spec for the **ticket list screen's search and filter toolbar** (`TicketsListScreen`). Turns the decorative search box into a functioning text field and adds a Status / Type / Priority filter row above the list body. No new screens; no new primitive components — this specifies how the existing `AppTextField` and `AppDropdown` are **composed** into this screen's header, plus a new "no results" empty state.

- **No Material widgets.** All chrome is base Flutter primitives (`DecoratedBox`, `Container`, `GestureDetector`, `CustomPaint`, `Row`, `Column`, `Padding`, `Align`). The only Material dependency is the one already inside `AppTextField` (a transparent `Material` ancestor wrapping `TextField`) — reuse it as-is.
- `c` = active `AionColors`; `a` = theme `fillAlpha` (Arctic `0.11` / Obsidian `0.16`). `isDark` = Obsidian.
- Both themes share one code path; only token values differ. Where a component is identical across themes, it is stated explicitly.
- Companion mockups: `Aion Ticket Search and Filters Mockups.dc.html` (Arctic + Obsidian; resting `1a`, active `2a`, no-results `3a`, control states `4a`).

## 1. Toolbar composition

### 1.1 Layout & placement

The toolbar is a **vertical stack**: the search field on top, the filter row directly below it. Placed inside the existing header block, between the title row (eyebrow + "Tickets" + avatar) and the list body.

```
Header block  (Column, crossAxisAlignment: stretch)
├─ Title row            (existing: AION · MAIN / Tickets / avatar)
├─ SizedBox(height: 16)
├─ Search field         (§2 — full width)
├─ SizedBox(height: 10)
└─ Filter row           (§3 — three equal dropdowns)
List body               (top border, ticket rows / empty state)
```

- **Header block padding:** `EdgeInsets.fromLTRB(20, 8, 20, 14)` (unchanged from the current header).
- **Search-to-title gap:** `AionSpacing.sp16` (16).
- **Filters-to-search gap:** `10` (between `sp8` and `sp12` — matches the tighter grouping of the two search controls; keep as an explicit `10`).
- **Toolbar-to-list gap:** none — the list body's own top `border` (1px `c.border`) is the divider, flush under the `14px` header bottom padding.
- The whole header block is `flex: 0 0 auto`; the list body is `Expanded`.

**Rationale for stacking (not one combined row):** at a 380px phone width the search field needs full width to be usable, and three dropdowns need the full width to stay legible. Stacking gives each its own line; a combined row would crush both.

### 1.2 Narrow-width behavior

Three equal-width dropdowns in a single `Row`, each `Expanded(flex: 1)` with `SizedBox(width: 8)` gaps. They **never wrap and never scroll** — because the labels are short ("All statuses", "All types", "All priorities" and their selected values) and each cell ellipsizes its own text, three equal thirds remain legible down to the app's minimum supported width (320px logical). Do **not** add horizontal scrolling or a wrap-to-two-lines fallback; equal thirds + per-cell ellipsis is the whole responsive story.

```dart
Row(
  children: [
    Expanded(child: _FilterDropdown(kind: FilterKind.status)),
    const SizedBox(width: 8),
    Expanded(child: _FilterDropdown(kind: FilterKind.type)),
    const SizedBox(width: 8),
    Expanded(child: _FilterDropdown(kind: FilterKind.priority)),
  ],
)
```

Reuse **`AppTextField`** exactly — its fill, border, focus ring, radius, and padding are already specified and must not be re-derived here. This section only fixes the *composition* choices specific to the list header. It is a single-line field with a **leading search glyph** and **no floating label** (the placeholder carries the affordance).

- **Width:** full header width (stretch).
- **Fill:** `c.surface`.
- **Radius:** `AionRadius.lg` (12).

- **No label above; no trailing clear (×) button** — clearing is by deleting the text (out of scope for a new affordance).

## 3. Filter dropdown trigger (this-context composition)

Each of the three filters is an **`AppDropdown<T>`** — reuse its tap-target + overlay + selected-item styling exactly. This section specifies the three composition decisions the base primitive leaves open.

### 3.0 Decisions

1. **No caption label** above each dropdown. The selected-value text ("All statuses" / "In Progress" / "Task" / "Critical") already names what the control filters; three stacked `AionText.label` captions would add a full text row of vertical clutter on a phone. The value text alone carries the meaning.
2. **Equal width**, not size-to-content — `Expanded(flex: 1)` each. Equal thirds read as one coherent control group and keep tap targets uniform; content-sized triggers would jump around as selections change.
3. **Active (non-default) selections get a distinct treatment** (§3.2) — a tinted fill, a primary border, and a leading dot — so a user can see at a glance that the list is being narrowed. This is the key affordance since there is no explicit "clear filters" button.

### 3.1 Trigger — default / cleared ("All ___")

The resting state, showing `"All statuses"` / `"All types"` / `"All priorities"`.

| Height | driven by padding (≈ 34) |
| Padding | `EdgeInsets.symmetric(horizontal: 11, vertical: 9)` |
| Fill | `c.surface` |
| Border | `1px c.border` |
| Radius | `AionRadius.lg` (12) |
| Value text | `AionText` `12px w600`, color `c.textMuted` (reads as "unset / neutral") |
| Trailing chevron | down-chevron, `9px`, `c.textMuted`, `flex: 0 0 auto` |
| Leading dot | none |

## 4. "No results" empty state

Shown centered in the list body **only when a search query and/or a non-default filter is active and zero tickets match**. Distinct from the existing "No tickets yet" empty state (which stays for the genuinely-empty list). No `AppButton` "clear filters" affordance — clearing is by editing the search text or re-selecting an "All ___" option (out of scope for a new control), so the empty state is informational only.

- **Container:** fills the list body (`c.surface`), centered both axes.
- **Layout:** `Column`, `mainAxisAlignment: center`, `crossAxisAlignment: center`, `gap: 16`, horizontal padding `EdgeInsets.symmetric(horizontal: 48)`.
- **Motif** (top): `58×58` rounded square, `radius AionRadius.xl` (16), fill `c.primary.withOpacity(a)`, containing a search glyph **27px**, color `c.primary`. Per the design-system iconography rule, a filled faction motif is permitted in empty states.
- **Primary line:** `"No tickets match your search"`, `AionText.body` (15px) `w600`, `c.textPrimary`, `textAlign: center`.
- **Secondary line:** `"Try a different term, or reset a filter to its "All" option."`, `AionText.bodySm` (13.5px), `c.textMuted`, `textAlign: center`, `gap: 6` under the primary line.

**Theme note:** identical both themes; token values differ.

## 5. Active-search feedback on the list body

- **Debounce:** the list re-filters `250ms` after the last search keystroke; filter-dropdown selections apply **immediately** (no debounce).
- **Result transition:** a single **120ms opacity cross-fade** (`0.55 → 1.0`) on the list body when the result set changes. No skeleton rows, no shimmer, no reflow animation — the swap is otherwise instant. This is enough to signal "results updated" without the list feeling laggy.
- **No count chip / results banner** is added — out of scope.

```dart
AnimatedSwitcher(
  duration: const Duration(milliseconds: 120),
  transitionBuilder: (child, anim) => FadeTransition(opacity: anim, child: child),
  child: KeyedSubtree(key: ValueKey(resultSignature), child: listOrEmpty),
)
```
