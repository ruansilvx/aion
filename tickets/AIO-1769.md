# Reject Epic Reparenting

# Proposal: Reject Epic Reparenting

## Problem

`project.md`'s watcher foundational decision states: "Epics have no parent
and are not watcher-reviewed themselves." Every epic is the root of exactly
one watcher-reviewed subtree — the whole per-epic-subtree review model
depends on that being true.

But `TicketsCubit.updateTicketParent` (built by `parentid-editable`) only
rejects two things: self-parenting and cycles. It never checks `type`.
Nothing today stops an epic from being reparented under any other ticket
via `TicketParentPicker` on its own detail screen — a single mis-click
would silently break the "epic is a subtree root" invariant, making "which
epic owns this ticket" ambiguous for the watcher system and for any future
rollup logic (`aion-arch/specs/tickets.md`'s own known-gaps list already
flags that a future estimate/timeSpent rollup must key off the parent
chain).

Flagged by `/explore reparenting enforces structural validity` (2026-07-14):
`aion-arch/specs/tickets.md`'s known-gaps bullet on this reads "no
type-compatibility rule (e.g. nothing prevents an `epic` from becoming the
child of a `task`)" — this proposal closes the one case of that gap that's
an actual documented invariant violation, not just an aesthetic mismatch.

## Goal

Make it structurally impossible to give an epic a parent — both by
removing the UI affordance to attempt it, and by rejecting the attempt at
the Cubit layer if it's ever reached some other way.

## Approach

Two layers, cheapest-and-most-visible first:

1. **UI** — `TicketDetailScreen` stops rendering `TicketParentPicker` at
   all when `ticket.type == TicketType.epic`. No "+ PARENT" affordance
   ever appears on an epic's detail screen. Mirrors the type-conditional
   visibility already used in `tickets_list_screen.dart`.
2. **Cubit (defense in depth)** — `TicketsCubit.updateTicketParent` adds
   one more short-circuit: reject any non-null `newParentId` when
   `ticket.type == TicketType.epic`, via the exact same
   `_emitInvalidParent`/`TicketsErrorReason.invalidParent` path already
   used for self-parent and cycle rejection. Per `project.md`'s state
   management convention, `TicketsCubit` is the only production caller of
   the repository, so this is the real enforcement boundary — it protects
   against any future caller (a bulk-reparent feature, a test harness, a
   watcher-driven auto-reorganize) that reaches `updateTicketParent`
   without going through this picker.

No new error reason, no new l10n string. The existing generic "can't
reparent" toast (`ticketInvalidParentError`) already covers self-parent
and cycle rejection with one message — a third invalid-parent case doesn't
need its own wording.

## Out of scope

- **The full type-compatibility matrix** (e.g. can a `resource` parent a
  `story`? can a `chat` parent a `task`?). Only the one invariant that's
  actually documented in `project.md` — epics never have a parent — is
  enforced here. The broader question is captured separately:
  `aion-arch/ideas/define-type-compatibility-matrix.md`.
- **Existing bad data.** If any epic somehow already has a non-null
  `parentId` today (unlikely — `CreateTicketScreen` doesn't expose parent
  selection, and this is the only reparent path in the app), this change
  adds no migration to clean it up. It only prevents new violations going
  forward.
- **Rollup recalculation.** No estimate/timeSpent rollup exists yet
  (already called out as out of scope in `parentid-editable`'s
  proposal.md) — nothing to recompute.
