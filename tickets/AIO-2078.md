# Task To Coding Execution Trigger

# Proposal: task-to-coding-execution-trigger

## What

Closes the last gap on the path to Aion's self-iteration milestone: today,
`TicketsCubit.advanceSddStage` drives every SDD-stage chat (exploring,
proposed, designBrief, designSync, verifying, archived) conversationally,
but no Task ticket can trigger a real, tool-enabled coding-execution run.
Every model call the app makes runs with `allowedTools: []`
(`agent_bridge/index.mjs`) — confirmed still true in code as of this
proposal. This change makes moving a Task ticket to `TicketStatus.inProgress`
the trigger for a real coding-execution run: a spawned, visible `chat`
child ticket whose model call has tools enabled (file edits, git, bash),
reusing the exact `advanceSddStage`/`_spawnStageChat` chat-spawning pattern
already shipped for the conversational stages.

Concretely, this change:

1. Adds `toolsEnabled`/`workingDirectory` to `AgentRequest` and threads them
   through `ClaudeAgentSdkClient`/`agent_bridge/index.mjs`, so a caller can
   opt in to a real, cwd-scoped agent run instead of the text-only calls
   every existing caller makes.
2. Adds a hard, non-`AutomationConfidence`-gated precondition: a Task
   cannot start coding execution while its governing Story's Tasks
   indicate UI work and that work hasn't been design-approved yet (via
   the already-shipped `_storyNeedsDesignReview`/`_designSyncApproved`
   checks from `sdd-design-gate`). A Task with no Story ancestor
   (parentless, or a direct Epic child), or whose Story's Tasks don't
   indicate UI work, has no such gate. See "Grounding correction" below
   for why this checks those two functions directly rather than the
   Story's `SddStage` position.
3. Runs one coding-execution slot at a time. A second Task moved to
   `inProgress` while a run is already in flight queues FIFO, with a
   visible "Queued for execution — Nth in line" hint on its detail screen.
4. Gates the post-completion status flip (`inProgress` → `inReview`) behind
   the existing `AutomationConfidence` pattern (`auto | gated | manual`) —
   its second real consumer, after SDD-stage-triggering. This requires
   generalizing `AutomationSettingsRepository`/`AutomationSettingsCubit`
   from their current single-purpose (SDD-stage-only) shape to a
   per-context one, which their own doc comments already flagged as
   deferred "until a second consumer actually exists." It now does.
5. Reactive-only budget handling: once `AgentOverageDetectedEvent` fires
   during any coding-execution run, force every subsequent trigger to
   `gated` for the rest of the session, regardless of the configured
   confidence — informing the user once via a toast when it happens.
6. On failure, posts the result in the spawned chat with no
   auto-escalation or auto-retry — which also means fixing a latent gap in
   `ChatCubit.runChatTurn`: today a failed run persists nothing at all, so
   a failure is invisible to anyone not actively watching the chat live.

## Why

`self-iteration-sequencing.md` (2026-07-21) treats `sdd-ticket-execution`
shipping as reaching "the literal self-hosting transition point," but that
change only gets Aion driving its own *conversational* SDD stages through
its own UI. The step that actually lets Aion write its own Dart code —
instead of a human running Claude Code CLI against `aion-arch/` by hand,
which is literally how every prior change in this repo (including this
one's own `/propose` stage) has been produced — is this one. Confirmed by
re-reading `agent_bridge/index.mjs` while grounding this proposal:
`allowedTools: []` is still hardcoded, unconditionally, on every call.

`task-to-coding-execution-trigger.md`'s own `/explore` session identified
one hard prerequisite for this: a way to express "this Story's design work
is outstanding" on the ticket side, so a Task can't jump ahead of design
review. `sdd-design-gate` shipped that exact mechanism today
(2026-07-22) — `SddStage.designBrief`/`designSync`, gating `verifying`.
With that prerequisite cleared, this idea can now `/propose` on its own,
per that idea's own `next_action`.

`per-phase-tier-based-model-routing` (the other sibling idea) is
confirmed self-contained and non-blocking — this change's coding-execution
calls use the same hardcoded `AgentModel.sonnet` default every other stage
chat already uses, exactly like `sdd-design-gate` did for its own two new
stages. Model-tier routing can retrofit an "Execution" tier onto this
change's call site later with no rework, per that idea's own framing.
(While grounding that idea's model-selection angle, confirmed the
installed Claude Agent SDK does expose live model discovery
(`Query.supportedModels()`) — but only in streaming-input mode, which
`agent_bridge/index.mjs` doesn't use today. Captured as a follow-up on
`per-phase-tier-based-model-routing.md` rather than pulled into this
change, since it's a restructuring of the bridge's whole invocation shape,
not a model-selection concern this proposal touches.)

## Grounding correction: the design-gate precondition was circular as first drafted

The first draft of this proposal blocked a Task from starting execution
until its Story's `SddStage` reached `verifying`. Re-reading
`TicketsCubit._sddStageAdvanceCheck`'s already-shipped `proposed` case
while writing `design.md` surfaced a real bug that makes that condition
impossible to satisfy: advancing a `story` ticket *out of* `proposed` (to
`designBrief` or `verifying`) already requires every child Task to be
`TicketStatus.done`. So the original gate was circular — a Story can't
reach `verifying` until its Tasks are done, and Tasks couldn't start until
the Story reached `verifying`.

This also exposes a pre-existing bug in the already-shipped
`sdd-design-gate`: it inserted `designBrief`/`designSync` between
`proposed` and `verifying` on the explicit reasoning that "design-sync
runs before any code is written," but never updated `proposed`'s own
advance-precondition (written earlier, in `sdd-ticket-execution`, before
the design-gate stages existed) to match — it still requires Tasks
*done* to leave `proposed`, for every Story, UI-touching or not. In
practice this means a UI-touching Story can never actually reach
`designBrief` before its Tasks are finished, exactly backwards from the
stage's own stated purpose. Nothing could have hit this before now:
Tasks have never had any automated way to reach `done` until this change
adds one.

**Fix, folded into this change's scope** (the real CLI order — design
review before `/apply`, `/verify` after — is the ground truth this
correction restores):

- `_sddStageAdvanceCheck`'s `proposed` case (Story only) now requires
  only "Tasks *exist*" to advance to `designBrief`, but still "Tasks
  *done*" to advance straight to `verifying` when no design review is
  needed (the skip-design branch is unaffected — it never had a
  designBrief/designSync stage to run *before* code in the first place).
- Its `designSync` case now requires **both** `_designSyncApproved` and
  all child Tasks done to advance to `verifying` — restoring "Tasks
  done" to gate the transition it always should have gated, one stage
  later than where it was misplaced.
- This proposal's own coding-execution gate no longer compares `SddStage`
  ordinals at all — it calls `_storyNeedsDesignReview`/
  `_designSyncApproved` directly (see design.md §4), sidestepping the
  now-fixed stage-position bug entirely rather than depending on it.

## Scope

- `AgentRequest` (`core/contracts/agent_model_client.dart`) grows
  `toolsEnabled`/`workingDirectory`, both optional, defaulting to today's
  behavior (`false`/`null`) — every existing caller is unaffected.
- `ClaudeAgentSdkClient` passes `workingDirectory` to the spawned process
  and forwards `toolsEnabled` to the bridge.
- `agent_bridge/index.mjs` drops the hardcoded `allowedTools: []` in favor
  of the SDK's default tool set when `toolsEnabled` is true.
- `ChatCubit.runChatTurn` gains optional `toolsEnabled`/`workingDirectory`/
  `onOverageDetected` parameters, and persists an AI-authored failure
  comment instead of silently dropping a failed run's result — a shared
  fix benefiting every existing caller (SDD-stage chats), not just this
  change's new one.
- **`_sddStageAdvanceCheck`'s `proposed`/`designSync` cases (Story only)
  are corrected** per the Grounding correction above — `proposed` no
  longer requires Tasks done to reach `designBrief` (only "Tasks exist"),
  and `designSync` now requires Tasks done *in addition to*
  `_designSyncApproved` to reach `verifying`.
- `TicketsCubit` gains: the coding-execution gate check (built directly
  on `_storyNeedsDesignReview`/`_designSyncApproved`, not `SddStage`
  position), an in-memory single-slot execution queue (FIFO), the spawn/
  completion mechanism, PR-detection parsing on the final AI reply
  (mirroring `_designSyncApproved`'s `DESIGN GATE: APPROVED` string-match
  convention), and the reactive overage-forces-gated behavior. Takes a
  new optional `AutomationSettingsRepository` dependency (same
  optional-dependency pattern as `agentClient`/`commentRepository`).
- `AutomationSettingsRepository`/`AutomationSettingsCubit`/
  `SharedPrefsAutomationSettingsRepository` generalize from a single SDD-
  stage-only value to a per-`AutomationContext`-keyed one (new
  `AutomationContext` enum: `sddStage | codingExecution`). The existing
  `shared_preferences` key for SDD-stage automation is preserved unchanged
  so no user setting is silently reset.
- Settings screen: the existing "SDD Stage Automation" section becomes one
  of two instances of a generalized automation-picker widget, the second
  labeled "Coding Execution Automation."
- `TicketDetailScreen`: a new queue-position hint row (Task tickets only,
  mirrors `_NotReadyHint`'s style) and a gated "Mark ready for review"
  banner (mirrors the existing `_GatedBanner`/`_ManualAdvanceButton`
  pattern) for a completed run awaiting confirmation.
- `app_router.dart`: wires the new `AutomationSettingsRepository` dependency
  into `TicketsCubit`'s real construction site.
- New `TicketsErrorReason` values (`codingExecutionBlocked`,
  `executionBudgetOverageDetected`) and new `TicketDetailLoaded` fields
  (`isExecuting`, `executionQueuePosition`, `executionAwaitingReview`),
  Task-only, mirroring the existing `sddStageBlockReason`/
  `needsDesignReview` precedent.

## Out of scope

- **Per-phase/tier model routing** for the coding-execution call itself —
  uses the same hardcoded `AgentModel.sonnet` default every stage chat
  uses today. `per-phase-tier-based-model-routing` will route this to its
  "Execution" tier once it ships; no dependency in either direction.
- **True multi-line (concurrent) coding execution** — one execution slot,
  FIFO queue, exactly as `task-to-coding-execution-trigger.md` scoped it.
  Flagged there as a later improvement, not designed here.
- **The predictive, cost-estimate "Budget gate"** from `project.md` §5 —
  only the reactive `AgentOverageDetectedEvent` override is implemented,
  per that same idea's explicit deferral.
- **Cancelling a queued or in-flight execution** — not raised in the
  `/explore` session; a Task already shows `inProgress` immediately on
  trigger regardless of queue position, so the status itself is never
  blocked on the queue, only the actual model run is queued behind it.
- **Surviving an app restart mid-queue** — the execution queue is
  in-memory `TicketsCubit` state, not persisted. If Aion restarts with a
  Task still `inProgress` and no execution actually ran, the user must
  manually re-trigger (e.g. toggle status away and back) — an accepted
  gap consistent with this project's existing "sufficient at personal
  scale" reasoning elsewhere (embeddings, trash-purge scheduling).
- **Verifying that a PR genuinely exists** beyond string-matching the
  agent's own final reply for an `EXECUTION: PR_OPENED` line — Aion trusts
  the coding-execution agent's self-report, the same trust level
  `_designSyncApproved` already places in a stage chat's own verdict line.
