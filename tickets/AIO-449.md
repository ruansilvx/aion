# Bulk Status And Priority Edit For Ticket Selection

# Proposal: Bulk status and priority edit for ticket selection

## Why

`TicketsListScreen`'s selection mode (`TicketSelectionCubit` +
`TicketSelectionBar`) already lets a user check off multiple tickets and
act on all of them at once — but the only bulk action available today is
Delete (trash). Changing the status or priority of several tickets at
once — clearing out a finished batch, bumping priority on a cluster of
related work — currently requires opening each ticket individually and
editing it one at a time. `tickets.md`'s own "Known gaps" section already
flags this: *"No bulk operations other than delete (status change,
reparent, type/priority edit) — `TicketSelectionCubit` is a plausible
foundation for these later, but none are built yet."*

This change narrows that gap to exactly two of the three named
operations — **bulk status change** and **bulk priority edit** — and
builds them on the existing selection foundation. See
`aion-arch/ideas/bulk-status-and-priority-edit-for-ticket-selection.md`
for the full exploration.

## What

Add two new actions to `TicketSelectionBar`, alongside the existing
Delete: **Status** and **Priority**, each an inline trigger that opens a
dedicated overlay (`BulkStatusMenu`/`BulkPriorityMenu`, per the
integrated Claude Design export — see design.md) listing every value, no
current-value exclusion, since a selection can span tickets with
different current statuses/priorities. Picking a value applies it to
every selected ticket in one write.

- **Bulk status change** respects the same two per-ticket gates a
  single-ticket status write already enforces when moving to
  `TicketStatus.inProgress` — the Blocked-dependency gate
  (`TicketsCubit._isTicketBlocked`) and, for Task/Bug tickets, the
  coding-execution gate (`TicketsCubit._codingExecutionGateCheck`).
  Tickets that would be rejected are silently skipped (not written), and
  the summary toast reports both how many succeeded and how many were
  skipped. Every other target status has no gate — all selected tickets
  are written unconditionally, same as the single-ticket path.
- **Bulk priority edit** has no structural gating at all — priority is a
  plain enum field — so every selected ticket is always written.

## Non-goals (explicitly out of scope)

- **Bulk reparent.** A single ticket's valid-parent-candidate set already
  requires self/descendant exclusion, type-compatibility filtering, and
  cycle detection (`TicketsCubit.getValidParentCandidates`, itself a
  flagged performance gap). Bulk reparent would require intersecting
  that candidate set across every selected ticket at once, with no clear
  answer for a selection spanning mixed types. Rejected as not making
  sense for Aion in bulk form — not deferred.
- **Bulk type edit.** Changing a ticket's type can invalidate its
  existing parent and existing children against Aion's type-compatibility
  rules (see the still-open `define-type-compatibility-matrix` idea).
  Bulk would multiply that cascade-checking across a whole selection.
  Rejected as not making sense for Aion in bulk form — not deferred.
- No change to `TicketSelectionCubit` itself — it stays a plain id-set
  toggler; the new gating/write logic lives entirely in `TicketsCubit`,
  per this project's Cubit-owns-domain-logic convention.
- No change to the single-ticket status/priority editors on
  `TicketDetailScreen` or the board's `MoveToStatusMenu` — those keep
  excluding the ticket's current value, unchanged.
