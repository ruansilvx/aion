# Ticket Link Management Ui

# Proposal: Ticket link management UI

## What

Today a ticket's "Linked Tickets" section (`LinkedTicketsSection`, shown
on `TicketDetailScreen`/`PageDetailScreen` for every gated ticket type)
renders each linked ticket as a bare tappable row — a type-color dot, key,
and title. It carries no information about *how* the two tickets are
linked (`blocks`/`blockedBy`/`relatesTo`/`duplicates`), and there is no
way to remove a link once created, or to change its type after the fact.
`TicketLinkRepository` itself has no `delete`/`update` method at all
today — only `getLinksForTicket`, `createLink`, and the bulk
`getLinksByTypes`.

This change adds, to that same inline section (no new screen):

1. **A relationship-type indicator per row** — the same directional
   glyph + label `TicketLinkPicker`'s type selector already uses
   (`_linkTypeGlyph`/`_linkTypeLabel` in `ticket_link_picker.dart`),
   computed *relative to the ticket whose detail screen is showing it*
   (a `blocks` row viewed from its target reads "Blocked by", not
   "Blocks" — see design.md for the direction math).
2. **A remove action per row** — a real `TicketLinkRepository.deleteLink`
   backing a delete affordance, replacing today's "no way to remove a
   link once created" gap, including for a `blocks`/`blockedBy` link the
   Board's `BlockedBadge` is actively reflecting.
3. **In-place link-type editing** — a real, atomic
   `TicketLinkRepository.updateLinkType`, exposed via the same relative
   type-selector UI as row 1, so a link created as `relatesTo` can become
   `blocks` (etc.) without deleting and recreating it.

Scoped to `LinkedTicketsSection` (the "authored" links list) only.
`BacklinksSection` stays exactly as it is today — read-only, no "+ Add"
affordance, since (per its own existing doc comment) those links are
"derived, not authored" from the viewing ticket's side; removing one is
still possible from the *other* ticket's own Linked Tickets section,
where it was authored.

Grounded in `aion-arch/ideas/ticket-link-management-ui.md`'s brainstorm
conclusion — see that file for the fuller rationale trail, including why
no global link-browser screen is being built (Jira precedent: link
management is inline-only there too).

## Why

Flagged as a known gap in `aion-arch/specs/tickets.md`'s "Still no
general-purpose UI for browsing, editing, or deleting arbitrary
`ticket_links` rows" bullet. Two concrete, user-confirmed pains: a
mistakenly-created or now-stale link has no removal path at all, and a
ticket's links are shown as a bare list of other tickets with no
indication of *what kind* of relationship each one represents — you have
to open the other ticket (or remember) to know if it's a blocker, a
duplicate, or just related.

## Non-goals

- No global "browse all `ticket_links` rows across the project" screen —
  inline-only, per the brainstorm's Jira-precedent conclusion.
- No changes to `BacklinksSection` or backlink creation flows — backlinks
  remain derived-only, exactly as today.
- No Obsidian-style graph visualization — a separate, larger idea
  (`aion-arch/ideas/obsidian-style-graph-view-for-ticket-links.md`),
  deliberately not folded into this scope.
- No "AI-reviewed manual changes" gate on link edits — a broader,
  unscoped concern raised during the brainstorm session but not resolved
  or touched here.
- No change to link *creation*'s existing candidate-filtering or
  `linkTypeOptions` restriction (e.g. `duplicatedBy` staying
  non-creatable, `resource` staying `relatesTo`-only) — this change
  reuses those restrictions as-is for editing (see design.md).
- No retroactive backfill of `blocks`/`blockedBy` on pre-existing
  Story/Task pairs — separate, already-known gap
  (`aion-arch/specs/tickets.md`), untouched here.
