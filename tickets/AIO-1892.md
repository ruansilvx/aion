# Sdd Ticket Foundation

# Proposal: sdd-ticket-foundation

## What

Two new first-class `TicketType` values, purely additive at the data-model
level:

- **`signal`** — something noticed but not yet resolved into work: a raw
  idea, a known gap, or an open question. One type covers all three
  because they share the same lifecycle (captured → discussed → either
  resolved inline or promoted into an `epic`) and the same eventual
  consumer (`/what-next`'s ticket-native equivalent, step 3) — see
  [Naming](#naming-idea--signal) below for why this isn't called `idea`.
  Parentless (like `epic`), can parent a `chat` (for exploring/discussing
  it), cannot parent anything else. Reuses every existing ticket
  mechanism (status, priority, search, embeddings, git projection, Trash)
  for free.
- **`release`** — a named release/milestone. Parentless (like `epic`), can
  parent a `chat` (release-planning discussion), cannot parent anything
  else. Relates to `epic`/`story`/`task` tickets via the existing
  `TicketLinkType.relatesTo` cross-cutting link — not tree-parentage, so a
  Story can ship early while sibling Stories in the same Epic slip to the
  next release, and a release can bundle loose ad hoc Tasks with no Epic.

Both types get: an entry in `TicketTypeHierarchy` (structural
parent/child rules), a `TypeChip`/`ticketTypeLabel` rendering (new
`typeSignal`/`typeRelease` color tokens, one per theme), a slot in
`CreateTicketScreen`'s type dropdown, and coverage in the existing
`TicketTypeHierarchy.canParent` expectation-matrix test (6×6 → 8×8).

One small generalization ships alongside them: `TicketsCubit
.updateTicketParent`'s hardcoded "an epic can never receive a parent"
check becomes a `TicketTypeHierarchy.isAlwaysRoot` getter covering
`epic`/`signal`/`release` — the same invariant, extended to the two new
types via one shared source of truth instead of three scattered
`== TicketType.x` comparisons. `CreateTicketScreen`'s parent-field-hidden
condition reads the same getter, so UI and Cubit enforcement can't drift
apart.

### Naming: `idea` → `signal`

Both source ideas (see below) called this type `idea`. Renamed here
because its actual job — established while exploring how `/what-next`'s
`detect-gaps.sh` would need to work once specs become pages (see the
updated `sdd-workflow-in-ticket-system.md`) — is to represent a *known
gap* or *open question* surfaced against an already-shipped spec just as
often as a fresh idea. Calling a documented gap in a shipped feature an
"idea" reads wrong; `signal` — something noticed that hasn't been
resolved into actionable work yet — covers a raw idea, a gap, and an
open question equally well without implying any one of the three
specifically.

## Why

This is step 2 of the build order locked in by
`aion-arch/ideas/self-iteration-sequencing.md`: provider-configuration
(step 1) is archived; this is the next piece toward the milestone where
Aion can drive its own further development through its own ticket UI
instead of the CLI-driven `aion-arch/.claude/skills/` process currently
used to build Aion itself.

Source ideas: `aion-arch/ideas/sdd-workflow-in-ticket-system.md` (the
new ideas/gaps ticket type — called `idea` there, renamed `signal` here,
see above — originally bundled with a "specs-as-pages" migration and a
Cubit-gated "current SDD stage" field) and
`aion-arch/ideas/new-project-onboarding.md` (the `release` ticket type).
`aion-arch/ideas/self-iteration-sequencing.md` already concluded these
two belong in one combined change, since both are pure data-model/
compatibility-matrix work with zero cross-dependency and no chat
requirement.

## Re-scoped from the original idea — what changed and why

The idea files were written before `documentation-section`,
`page-content-markdown-editor`, and `storage-embedding-git-sync` shipped.
Re-checking against current `aion-arch/specs/tickets.md` before writing
this proposal turned up two scope changes:

1. **"Specs-as-pages" is dropped from this change entirely — but not
   because it's fully solved.** The original idea wanted
   `aion-arch/specs/*.md` modeled as Page tickets as part of this
   foundation. The *storage* half of that already exists —
   `page-content-markdown-editor` shipped a dedicated `features/pages/`
   module with nested Markdown pages, and `storage-embedding-git-sync`
   shipped the generic ticket↔Markdown git projection every ticket type
   already gets. Representing a spec as a `page` ticket today requires
   zero new code. What's *not* solved, and doesn't belong in this
   ticket-model change either, is the *mechanism* half:
   `/what-next`'s ticket-native equivalent needs a way to enumerate
   "known gaps" and "open questions" against a spec page, which today's
   CLI does by regex-parsing `## Known gaps`/`## Open questions`
   sections out of spec markdown prose (`detect-gaps.sh`). The resolved
   design — a gap/open question becomes its own `signal` ticket, linked
   to the spec page via `TicketLinkType.relatesTo`, discoverable by an
   ordinary type/status query instead of parsing prose — is recorded in
   the updated `sdd-workflow-in-ticket-system.md`, since it's a step-3
   consumer decision (needs the chat/agent orchestration this change
   doesn't touch), not a step-2 schema gap. Same for `project.md`
   becoming a linked page in its own right, and a new universal
   `Ticket.complexity` field (small/medium/large) — both decided this
   session, both deferred to step 3 for the same "no consumer yet"
   reason as the SDD-stage field below. Migrating `aion-arch/specs/`'s
   actual content into pages remains a separate content decision for
   whenever Aion is far enough along to manage its own project.
2. **The Cubit-gated "current SDD stage" field is deferred to step 3**
   (SDD-stage-triggering Execution), not built here. `sdd-workflow-in-
   ticket-system.md` itself flagged this as an open judgment call ("built
   inert, ahead of any UI that uses it" vs. "move into step 3 alongside
   the stage-triggering UI that actually consumes it"). Building it now
   would mean a stored field with a Cubit method enforcing a precondition
   ("all child Tasks Done before advancing to verification") that no UI
   reads or writes yet — untestable in the way that matters (no consumer
   to exercise the transition logic against) and indistinguishable from
   dead code until step 3 exists. Deferring keeps this change to what's
   provably needed now: two new ticket types.

What's confirmed unchanged from the original ideas: `release`'s
cross-cutting (not tree-parented) relationship to work tickets needs no
new link type — `TicketLinkType.relatesTo` and
`TicketLinkRepository.createLink` are already fully generic over ticket
type pairs. No drift schema migration is needed for either new type —
`TicketsTable.type` is a plain `TextColumn` storing `TicketType.name`
(`lib/features/tickets/data/models/ticket_model.dart`), so appending
enum values is purely additive.

## Out of scope

- The "current SDD stage" ticket field and any stage-triggering UI —
  step 3.
- Any mechanism that promotes/converts a `signal` ticket into an `epic`
  (either attaching it to an existing epic or spinning up a new one) —
  step 3, and depends on a working chat/provider flow this change
  doesn't touch.
- The universal `Ticket.complexity` field (small/medium/large) — a real
  schema migration (new column, not a free enum-value addition — see
  `design.md`), deferred to step 3 alongside the SDD-stage field since
  neither has a consumer yet.
- Migrating `aion-arch/specs/*.md` content into in-app `page` tickets —
  a content decision, not a code gap (see above).
- Board view changes — the board already scopes to `task`/`story` only
  (`tickets.md`'s "Board view" section); `signal`/`release` tickets
  appear in the list view the same way `epic` already does, nothing to
  change.
- Multi-locale localization — the project ships a single `app_en.arb`
  today; new strings follow that existing single-locale convention.
