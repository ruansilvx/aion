# Design: Estimate/TimeSpent Rollup for Ticket Hierarchy

## 1. Domain model

### 1.1 `Ticket` entity — two new fields

`lib/features/tickets/domain/entities/ticket.dart` gains:

```dart
/// Derived, recursive rollup of this ticket's own [estimate] plus every
/// live descendant's effective value (a child's own rollup if it has
/// children, its own [estimate] otherwise). `null` when this ticket has
/// no live children — the UI falls back to [estimate] directly in that
/// case, so a leaf never shows a redundant "rollup of itself." Computed
/// and persisted only by `TicketsCubit`/`TrashCubit`'s rollup-recompute
/// walk (see [TicketRollupCalculator]); never part of [copyWith] — same
/// treatment as [sddStage], written only through a dedicated repository
/// method ([TicketRepository.updateRollup]) so a plain content edit
/// can't accidentally clobber it.
final int? estimateRollup;

/// Same as [estimateRollup], for [timeSpent].
final int? timeSpentRollup;
```

Both are added to the constructor (optional, default `null`), `props`,
and `Equatable` — but **not** to `copyWith`'s parameter list, matching
`sddStage`'s existing precedent of "written only via a dedicated path."

### 1.2 `TicketRollupCalculator` — new shared pure function

`lib/features/tickets/domain/utils/ticket_rollup_calculator.dart` (pure
Dart, no Flutter/drift dependency — sibling of
`domain/utils/ticket_sort_comparator.dart`), so the exact same logic
backs both the runtime recompute walk (`TicketsCubit`/`TrashCubit`) and
the one-time migration backfill (`AppDatabase`'s `onUpgrade`, which
needs to run this over raw drift rows, not full `Ticket` entities).

```dart
/// One node's minimal shape for rollup computation — deliberately
/// narrower than [Ticket] so this can run directly against raw drift
/// rows during the schema-9 migration backfill, without constructing a
/// full [Ticket] for every row.
typedef RollupNode = ({
  String id,
  String? parentId,
  int? estimate,
  int? timeSpent,
});

/// This node's computed rollup — `null` for both fields means "no live
/// children," i.e. nothing to persist (falls back to the node's own
/// value in the UI).
typedef RollupResult = ({int? estimateRollup, int? timeSpentRollup});

/// Computes [RollupResult] for every node in [nodes] that has at least
/// one other node in [nodes] pointing at it via `parentId` (i.e. every
/// internal node — leaves are omitted from the returned map entirely).
/// Pure, deterministic, `O(n)`: builds a `parentId -> children`
/// adjacency map once, then computes bottom-up via post-order recursion
/// from every root (`parentId == null` or pointing outside [nodes]).
/// Guards against a malformed cycle (should never occur — cycles are
/// rejected at write time by `TicketsCubit`/`TicketRepository.trashTicket`'s
/// cascade logic — but a defensive `visiting` set prevents a corrupt
/// migration from hanging) by treating a re-visited in-progress node as
/// contributing `0`/`null` rather than recursing infinitely.
Map<String, RollupResult> computeRollups(List<RollupNode> nodes);
```

**Algorithm:** build `childrenByParent` (identical shape to
`TicketsCubit._descendantIds`'s existing helper). For each node with at
least one child, `effective(node) = node.own ?? 0` plus, for each direct
child, `effective(child)` — where `effective(child)` recurses using the
same rule (a child with its own children contributes its *rollup*, a
childless child contributes its own raw value). A node whose own value
and every descendant's effective value are all `null`/absent produces
`null` (not `0`) for that field, so an all-unestimated subtree shows
"no estimate" rather than a misleading `0`.

### 1.3 Repository — one new method, both layers

**`TicketRepository`** (`domain/repositories/ticket_repository.dart`)
gains:

```dart
/// Updates only [estimateRollup]/[timeSpentRollup] for the ticket with
/// id [id]. Independent of [updateTicket] — same rationale as
/// [updateEmbedding]/[updateSyncStatus]: a recomputed derived value is
/// not a user edit and must not perturb `updatedAt`. Both parameters
/// are required (even to pass `null`) since a rollup recompute always
/// resolves both fields together from the same children set — there is
/// no meaningful "update just one." Throws if [id] does not exist.
Future<void> updateRollup(
  String id, {
  required int? estimateRollup,
  required int? timeSpentRollup,
});
```

**`DriftTicketRepository`** implements it via the existing
`TicketDao.updateFields` generic path, mirroring `updateEmbedding`:

```dart
@override
Future<void> updateRollup(
  String id, {
  required int? estimateRollup,
  required int? timeSpentRollup,
}) {
  return _db.ticketDao.updateFields(
    id,
    TicketsTableCompanion(
      estimateRollup: Value(estimateRollup),
      timeSpentRollup: Value(timeSpentRollup),
    ),
  );
}
```

### 1.4 Drift schema — version 9

`lib/features/tickets/data/models/ticket_model.dart`'s `TicketsTable`
gains two nullable `IntColumn`s, appended after `inboxPurpose` (matches
the file's existing append-only column ordering convention):

```dart
/// Derived rollup of [estimate] across this ticket's live structural
/// subtree. `null` if this ticket has no live children.
IntColumn get estimateRollup =>
    integer().named('estimate_rollup').nullable()();

/// Derived rollup of [timeSpent] across this ticket's live structural
/// subtree. `null` if this ticket has no live children.
IntColumn get timeSpentRollup =>
    integer().named('time_spent_rollup').nullable()();
```

`AppDatabase.schemaVersion` bumps `8 -> 9`. `onUpgrade` gains:

```dart
if (from < 9) {
  await m.addColumn(ticketsTable, ticketsTable.estimateRollup);
  await m.addColumn(ticketsTable, ticketsTable.timeSpentRollup);
  await _backfillRollups(m);
}
```

`_backfillRollups` (new private method, sibling of
`_createSearchInfrastructure`): selects every row's
`(id, parent_id, estimate, time_spent)` — **not** filtered to live rows
only, since a pre-existing trashed subtree should not silently poison
an ancestor's backfilled total; the same `deleted_at IS NULL` filter
`getAllTickets()` already applies at runtime is applied here too, via a
`WHERE deleted_at IS NULL` clause on the initial select — maps each row
to a `RollupNode`, calls `computeRollups`, then writes each non-empty
result back with `UPDATE tickets SET estimate_rollup = ?,
time_spent_rollup = ? WHERE id = ?`. Runs once, inside the same
migration transaction Drift already wraps `onUpgrade` in — a fresh
`onCreate` install never runs this (no pre-existing rows to backfill).

### 1.5 Markdown projection

`lib/core/markdown/ticket_markdown_template.dart`'s
`TicketMarkdownTemplate` gains two keys, **appended to the end** of
`fieldOrder` (per the file's own explicit rule — a new key never gets
inserted next to a semantically related existing one, to avoid
reordering every existing ticket file's frontmatter on next write):

```dart
static const estimateRollup = 'estimateRollup';
static const timeSpentRollup = 'timeSpentRollup';

static const List<String> fieldOrder = [
  ticketId, type, status, priority, parentId,
  estimate, timeSpent,
  createdAt, updatedAt, deletedAt,
  estimateRollup, timeSpentRollup, // new, appended
];
```

`TicketMarkdownSerializer.serialize` adds both to its `values` map
(`ticket.estimateRollup`, `ticket.timeSpentRollup`) — they round-trip
through `parse()`'s existing generic `fieldOrder` loop for free (same
`int?`-shaped `_convertField` case `estimate`/`timeSpent` already use,
extended to cover the two new keys). **No change needed in
`TicketMarkdownReconciler._apply`** — it only ever reads specific named
keys out of the parsed `fields` map, and `Ticket.copyWith` has no
`estimateRollup`/`timeSpentRollup` parameters for it to pass even if it
tried, so the two new keys parse (for round-trip completeness) but are
structurally inert to `_apply`. Combined with §1.6 below (rollup only
ever appears on `epic`/`story`/`task`/`bug`/`chat` tickets, and
`TicketMarkdownReconciler` only ever runs on `resource`/`page`
tickets), there is no code path where a hand-edited rollup value could
reach the database — add one doc sentence to
`TicketMarkdownReconciler`'s class-level "Known limitation" list
noting this explicitly, for the same reason the two existing
`parentId`/`deletedAt` notes exist.

### 1.6 `TicketGitProjector` — new batched-commit method

Existing `project(Ticket, rootPath, eventLabel)` writes one file, stages
it, and commits immediately — one commit per call. Batching several
ancestor rewrites into a single commit needs staging (`git add`)
separated from committing:

```dart
/// Writes every ticket in [ancestors] to its own Markdown file (same
/// serialization [project] uses) and stages each one, then makes **one**
/// commit covering the whole batch — skipped if nothing actually
/// changed (same `hasChanges` guard [project] uses). Used for a rollup
/// recompute's cascading ancestor rewrites, where committing per-file
/// would turn one estimate edit into a wall of near-identical commits.
/// No-ops (writes nothing, commits nothing) if [ancestors] is empty.
Future<void> projectBatch(
  List<Ticket> ancestors,
  String rootPath,
  String eventLabel,
) async {
  if (ancestors.isEmpty) return;
  for (final ticket in ancestors) {
    final relativePath = 'tickets/${ticket.ticketId}.md';
    final file = File('$rootPath/$relativePath');
    await file.parent.create(recursive: true);
    await file.writeAsString(_serializer.serialize(ticket));
    await _git.add(rootPath, relativePath);
  }
  if (!await _git.hasChanges(rootPath)) return;
  final label = ancestors.length == 1
      ? '${ancestors.single.ticketId} $eventLabel'
      : '${ancestors.length} ancestors $eventLabel';
  await _git.commit(rootPath, 'ticket: $label');
}
```

`project`'s own body is left untouched (still used by the four existing
single-ticket events); `projectBatch` is new, sharing the same
`_serializer`/`_git` fields.

## 2. `TicketsCubit` — the recompute walk

### 2.1 `_recomputeRollupChain` — shared private helper

New private method, positioned alongside `_triggerGitProjection`/
`_descendantIds`:

```dart
/// Recomputes and persists the rollup for every ticket on the path from
/// each id in [startIds] up to its structural root (inclusive of each
/// starting ancestor, i.e. [startIds] itself should already be the
/// *parent* of whatever changed, not the changed ticket — see call
/// sites below), then projects every ticket whose rollup actually
/// changed to git in one batched commit labelled [eventLabel]. No-ops
/// (and does no I/O at all) if [startIds] is empty. Fire-and-forget from
/// every call site — never awaited by the caller's own return path,
/// same pattern as [_triggerEmbeddingRegen]/[_triggerGitProjection].
Future<void> _recomputeRollupChain(
  Set<String> startIds,
  String eventLabel,
) async {
  if (startIds.isEmpty) return;
  final all = await _repository.getAllTickets();
  final byId = {for (final t in all) t.id: t};
  final nodes = [
    for (final t in all)
      (id: t.id, parentId: t.parentId, estimate: t.estimate, timeSpent: t.timeSpent),
  ];
  final results = computeRollups(nodes);

  // Walk every starting id upward to its root, collecting the full
  // ancestor chain (deduplicated — two starting ids can share upper
  // ancestors, e.g. two siblings both reparented under the same new
  // parent in one bulk trash call).
  final chainIds = <String>{};
  for (final start in startIds) {
    var current = byId[start];
    while (current != null && chainIds.add(current.id)) {
      final parentId = current.parentId;
      current = parentId == null ? null : byId[parentId];
    }
  }

  final changed = <Ticket>[];
  for (final id in chainIds) {
    final ticket = byId[id];
    if (ticket == null) continue;
    final result = results[id];
    final newEstimateRollup = result?.estimateRollup;
    final newTimeSpentRollup = result?.timeSpentRollup;
    if (newEstimateRollup == ticket.estimateRollup &&
        newTimeSpentRollup == ticket.timeSpentRollup) {
      continue; // no real change — skip the write and the file rewrite
    }
    await _repository.updateRollup(
      id,
      estimateRollup: newEstimateRollup,
      timeSpentRollup: newTimeSpentRollup,
    );
    changed.add(
      ticket.copyWith().let((t) => /* pseudo: */ t), // see note below
    );
  }

  if (changed.isEmpty) return;
  final projector = _gitProjector;
  final rootPath = _projectRootPath;
  if (projector == null || rootPath == null) return;
  await projector.projectBatch(changed, rootPath, eventLabel);
}
```

(The `.let(...)` line above is illustrative shorthand for "re-fetch or
locally reconstruct the ticket with its new rollup values before
projecting" — `/apply` should build `changed` from a small local record
carrying the post-write ticket, not a second `getTicketById` round trip
per ancestor; exact shape left to implementation, no dartdoc-worthy
public API involved.)

**Why walk from `startIds` rather than the changed ticket itself:**
callers below always pass the *parent* of whatever mutated (or, for a
leaf's own estimate edit, the leaf's own id — see call sites), and the
walk includes the starting id itself in `chainIds`. This keeps the
helper's contract uniform: "recompute every ancestor starting at
`startIds`, inclusive," regardless of whether the actual field mutation
happened on a leaf or an internal node.

### 2.2 Call sites

**`updateTicket(Ticket ticket)`** (existing method, `presentation/cubit/tickets_cubit.dart`) —
after persisting, if `previous.estimate != refreshed.estimate ||
previous.timeSpent != refreshed.timeSpent`:

```dart
unawaited(_recomputeRollupChain({refreshed.id}, 'rollup updated'));
```

Starting at `refreshed.id` itself (not just its parent) — if the edited
ticket has its own children, its own rollup needs recomputing too
before the walk continues upward.

**`updateTicketParent(Ticket ticket, String? newParentId)`** — capture
`ticket.parentId` (the *old* parent) before the write; after a
successful reparent:

```dart
unawaited(_recomputeRollupChain(
  {ticket.id, if (oldParentId != null) oldParentId, if (newParentId != null) newParentId}
    ..removeWhere((id) => id == ticket.id) // ticket.id has no rollup of its own to walk from here — its parent chain does
  ,
  'rollup updated',
));
```

More precisely: start from `ticket.id` (the moved ticket's own subtree
may itself have a rollup, unaffected by the move, but its *ancestors*
on both sides need recomputing) — simplest correct formulation is
`_recomputeRollupChain({ticket.id}, ...)` run **twice conceptually**
but **once in practice**, because the helper already walks from a
starting id up through `parentId` using the *current* (post-write)
tree. The old parent chain needs a separate walk seeded explicitly
since post-write, walking up from `ticket.id` only reaches the *new*
parent chain. Final call:

```dart
final startIds = <String>{ticket.id};
if (oldParentId != null) startIds.add(oldParentId);
unawaited(_recomputeRollupChain(startIds, 'rollup updated'));
```

`{ticket.id, oldParentId}` walked against the post-write tree correctly
covers both sides: `ticket.id`'s walk reaches the new parent chain (its
`parentId` now points there); `oldParentId`'s walk reaches the old
parent chain directly (its own `parentId` is unaffected by the move).

**`trashTicket(String id)`** / **`trashTickets(List<String> ids)`** —
after the trash write succeeds, seed from each explicitly-trashed
ticket's (pre-trash) `parentId` — mirrors the existing "projects only
the explicitly-requested ids" scope simplification already documented
for git projection at this call site:

```dart
unawaited(_recomputeRollupChain(
  {for (final id in ids) if (parentIdOf[id] != null) parentIdOf[id]!},
  'rollup updated',
));
```

**`TrashCubit.restore(String id)`** — same pattern, seeded from the
restored ticket's `parentId` after the restore write.

# Aion — Estimate / Time-Spent Rollup Specification

A read-only **rollup** of `estimate` / `timeSpent` for any Epic / Story / Task / Bug / Chat ticket that has **at least one live child**. The rollup is Jira-style: the ticket's own manually-entered value **plus** the recursive sum of every live descendant's value (own value is added, not replaced). Only the leaf value stays editable; the rollup itself is never editable and never interactive.

It surfaces on three existing surfaces, additively:

1. **`TicketMetadataSection`** (shared by `TicketDetailScreen`) — the `RollupIndicator`, a quiet subline beneath each existing editable field. §1.
2. **`TicketListTile`** (list rows) — the compact `RollupBadge`. §2.
3. **`TicketBoardCard`** (Kanban cards) — the same `RollupBadge`. §2.

A ticket with **no live children** renders **nothing new** on any of the three surfaces; its existing display is byte-for-byte unchanged.

This spec is implementation-ready. All values reference Aion's `AionColors` / `AionText` / `AionRadius` / `AionSpacing` tokens read via `ThemeScope.of(context)`. **No Material widgets** — Flutter primitives only (`DecoratedBox`, decoration-only `Container`, `Row`/`Column`/`Padding`, `Text`, `CustomPaint`). Translucent fills are `token.withOpacity(x)`, never hardcoded ARGB. Both themes (**Arctic** light, **Obsidian** dark) are covered; where identical it is stated.

## 0. Foundations for this feature

### 0.1 New tokens

Rollup information is **neutral, informational, secondary-priority** — not error / warning / success / active. It must not read as an accent. Two new translucent tokens carry it, following the existing `xxxTint` / `xxxBorderTint` naming and computed from `textSecondary` so they track the theme automatically. Add them as helper methods on `AionColorsHubTokens` (same place as `pendingTint`, `dangerTint`).

```dart
// neutral, informational tint — quiet numeric/data chrome
Color get neutralTint =>
    textSecondary.withOpacity(isDark ? 0.14 : 0.09);

// hairline for the same family, used when the fill must sit on a tinted bg
Color get neutralBorderTint =>
    textSecondary.withOpacity(isDark ? 0.26 : 0.18);
```

No new hue is introduced. If a `neutralTint` already exists in the hub, reuse it and skip this addition.

### 0.2 Minutes formatter

`Ticket.estimate` and `Ticket.timeSpent` are raw **minute integers** (nullable). Rollups sum to a single non-negative `int` of minutes. One shared formatter renders every rollup value (detail and compact), so both surfaces always agree.

```dart
/// Compact human-readable duration. Input: whole minutes (>= 0).
String formatRollupMinutes(int minutes) {
  if (minutes <= 0) return '0m';
  final h = minutes ~/ 60;
  final m = minutes % 60;
  if (h == 0) return '${m}m';       // 45  -> "45m"
  if (m == 0) return '${h}h';       // 300 -> "5h"
  return '${h}h ${m}m';             // 90  -> "1h 30m"
}
```

| Minutes | Output | Rule |
|---|---|---|
| `0` | `0m` | zero, still rendered (a rollup with children but no values) |
| `45` | `45m` | under an hour → minutes only |
| `90` | `1h 30m` | hours + remainder minutes |
| `300` | `5h` | exact hours → no `0m` suffix |
| `1090` | `18h 10m` | **no day rollover** — hours accumulate past 24 |

- Space between the `h` and `m` groups; no leading zeros; no `d` (days) unit.
- Worked example (brief): own estimate `30`, three children summing `270` → `300` → **`5h`**.

### 0.3 Rollup data (read model)

**Amended 2026-08-11 (post-design-sync):** the count caption is
**detail-screen only**. `RollupBadge` (§2, `TicketListTile`/
`TicketBoardCard`) never shows a count and never needs one — dropped
from those two surfaces per the developer's explicit call. `§1`
(`RollupIndicator`) keeps it.

Two different data sources back this now, not one shared read model:

- **`RollupBadge` (§2)** reads `ticket.estimateRollup`/
  `.timeSpentRollup` **directly** off the already-loaded `Ticket` —
  these are the persisted, architecture.md-§1.1 fields every ticket row
  already carries. Gating (`hasAnyRollup`-equivalent) is just
  `ticket.estimateRollup != null` (or `timeSpentRollup`) — no separate
  read-model object, no count, no extra query. This is what makes the
  badge cheap enough to render on every row of a list/board with no
  per-row query.
- **`RollupIndicator` (§1)** is the *only* consumer of a count, and the
  *only* place `TicketRollup` (below) gets constructed — on demand, for
  the single ticket `TicketDetailScreen` is currently showing, via a
  new `TicketsCubit.getRollupCounts(Ticket ticket)` query method (see
  tasks.md T11/T13). Not persisted — a full-subtree walk for one ticket
  on-demand is cheap; the reason a persisted rollup exists at all
  (§1.2/1.3) is to avoid that walk *per list row*, which doesn't apply
  to a single detail-screen view.

```dart
/// Detail-screen-only read model — constructed on demand by
/// `TicketsCubit.getRollupCounts` for the one ticket
/// `TicketDetailScreen` is showing. Never constructed for a
/// `TicketListTile`/`TicketBoardCard` row — those read
/// `Ticket.estimateRollup`/`.timeSpentRollup` directly instead (see
/// above).
@immutable
class TicketRollupCounts {
  final int estimateCount;     // live tickets (self + descendants) contributing an estimate
  final int timeSpentCount;    // live tickets (self + descendants) contributing time spent
  const TicketRollupCounts({
    required this.estimateCount,
    required this.timeSpentCount,
  });
}
```

**Gate for §1:** render the Estimate subline when
`ticket.estimateRollup != null` (same persisted-field check `RollupBadge`
uses), using `counts.estimateCount` for the caption once the on-demand
query resolves — not before. See tasks.md T13 for the loading-order
note (the subline appears once `getRollupCounts` resolves, alongside
the rest of `TicketMetadataSection`'s existing `initState` fetch, not
as a second late-arriving pop-in).

| Time spent | `PhosphorIcons.hourglass` | detail own-value field + compact fallback badge |
| Rollup / aggregation | `PhosphorIcons.stack` (stacked layers) | the marker on every rollup (detail subline + compact badge) |

`Timer` and `Hourglass` reuse the existing detail-screen estimate/time-spent affordance. `Stack` conveys "own value stacked with its descendants"; it is distinct from the board `Queued #N` glyph (which is `primary`/`secondary` accented and pairs with a count, whereas the rollup `Stack` is neutral and pairs with a duration). Default icon color is `textSecondary`; the rollup marker is never rendered in an accent color.

## 1. `RollupIndicator` — detail-screen variant

Lives in `TicketMetadataSection`, beneath (not replacing) each existing editable `InlineEditableField<int?>` — one instance for **Estimate**, one for **Time Spent**. Layout is: the existing label, the existing editable own-value row, then a rollup subline. The two numbers never read as redundant because the own value keeps the metric icon + `textPrimary` weight while the rollup is a separate `Stack`-marked, `textSecondary`, monospace chip carrying the subtree total and the contributing-ticket count.

### 1.1 Default (and only) state

Read-only, non-interactive — one visual state. It does not hover, focus, press, or disable. The adjacent editable own-value field keeps all of its existing states unchanged.

**Field column** (per metric — Estimate and Time Spent are identical apart from icon + label):

- Container: `Column`, `crossAxisAlignment: start`, `mainAxisSize: min`, vertical `gap: AionSpacing.sp8` (8) between label / own / rollup — implement as `SizedBox(height: 7)` spacers or a `Column` with `spacing`-equivalent padding; 7px used in mockups, 8 (`sp8`) is the token-clean value.
- The two field columns sit in a `Row` with horizontal `gap: 34` (between Estimate and Time Spent). If both do not fit the width, wrap to a second line — never truncate a value.

**1 · Label** (unchanged): `AionText.caption`-family — `Text('ESTIMATE')` / `Text('TIME SPENT')`, uppercased in Dart, `fontSize: 10`, mono, `letterSpacing: 1.4`, color `textSecondary` → use `textMuted` to match the existing meta label. Color: `AionColors.textMuted`.

**2 · Own value row** (unchanged — the editable field):
- `Row`, `gap: 6`, `center`.
- Leading icon: `PhosphorIcons.timer` (Estimate) / `PhosphorIcons.hourglass` (Time Spent), size **15**, color `textSecondary`.
- Value `Text`: `AionText.bodySm` at `fontWeight: w600`, `fontSize: 14`, color `textPrimary`. Content is the own value via `formatRollupMinutes(ownMinutes)` (e.g. `30m`). Empty own value keeps the existing placeholder ("Add an estimate…", `textMuted`).

**3 · Rollup subline** (new):
- Container: `DecoratedBox`(`Container` decoration-only), `alignment: start` (`mainAxisSize: min` so it hugs content), `padding: EdgeInsets.fromLTRB(7, 3, 9, 3)`, `borderRadius: BorderRadius.circular(6)` (`AionRadius.sm`), fill `neutralTint`, **no border, no shadow**.
- Inner `Row`, `gap: 6`, `center`:
  - **Rollup marker** — `PhosphorIcons.stack`, size **11–12**, color `textSecondary`. (Mockup draws it as three stacked 2px bars, top→bottom opacity `0.5 / 0.75 / 1.0`; the production icon is `PhosphorIcons.stack` at that scale.)
  - **Total** — `Text(formatRollupMinutes(ticket.estimateRollup!))` (or `.timeSpentRollup!`), `AionText.key` (mono, 11, w600), color `textSecondary`, `letterSpacing: 0.02em`. e.g. `5h`.
  - **Count caption** — `Text('· ${counts.estimateCount} tickets')` (or `.timeSpentCount`), mono `fontSize: 10.5`, `fontWeight: w400`, color `textMuted`. Singular/plural: `'· 1 ticket'` / `'· N tickets'`. `counts` is this ticket's on-demand `TicketRollupCounts` (§0.3) — render the subline once it resolves, alongside `TicketMetadataSection`'s existing data fetch, not as a second late pop-in.

Render the subline only when that metric's persisted rollup exists: Estimate subline gated by `ticket.estimateRollup != null`, Time Spent subline by `ticket.timeSpentRollup != null` — same persisted-field check `RollupBadge` (§2) uses, so detail screen and tile/card agree on "does this ticket have a rollup" without needing `TicketRollupCounts` for the gate itself, only for the caption text. A metric with no rollup shows just label + own value (its pre-existing appearance).

## 2. `RollupBadge` — compact list-row / board-card variant

One component, used verbatim in both `TicketListTile`'s meta row and `TicketBoardCard`'s meta row. It sits **after** the type chip / priority badge / status indicator and is pushed to the **trailing edge** (`Spacer()` before it), before any execution/blocked badge. Rendered only when `rollup.hasAnyRollup`.

### 2.1 Which metric shows — single-badge rule

The compact meta row is already occupied by `TypeChip`, `PriorityBadge`, and `StatusIndicator`. Showing **two** numeric pills (estimate + time-spent) would crowd that row and dilute the priority signal. So **exactly one** rollup shows:

1. If the subtree has an **estimate** rollup → show the **estimate** total (marker: `PhosphorIcons.stack`). Rationale: on a list/board you scan for *scope / size*, and the planned estimate is the size signal.
2. Else if it has a **time-spent** rollup → show the **time-spent** total, disambiguated by leading `PhosphorIcons.hourglass` before the `Stack` marker (or replacing it — see 2.2), so a viewer can tell it is elapsed time, not estimate.
3. Else → render nothing.

Time-spent rollups without an estimate are rare; the fallback keeps them visible without ever showing two pills. Full estimate + time-spent detail remains available on the detail screen (§1).

### 2.2 Default state (on `surface`)

- Container: `DecoratedBox`, `padding: EdgeInsets.fromLTRB(6, 2, 7, 2)`, `borderRadius: BorderRadius.circular(6)` (`AionRadius.sm`), fill `neutralTint`, **no border, no shadow**.
- Inner `Row`, `gap: 5`, `center`:
  - **Marker** — estimate variant: `PhosphorIcons.stack`, ~10px, `textSecondary`. Time-spent fallback variant: `PhosphorIcons.hourglass`, ~11px, `textSecondary` (the `Stack` marker may be dropped in the fallback to keep the pill narrow).
  - **Value** — `Text(formatRollupMinutes(total))`, `AionText.key` family at `fontSize: 10.5`, `fontWeight: w600`, mono, color `textSecondary`.
- Height matches the neighboring meta-row chips (~19–20px); it sizes to content and never wraps.

Radius `6` (a calm data chip) deliberately differs from the type chip's pill (22) and reads quieter than the priority badge — it recedes rather than competes.

### 2.3 States

`RollupBadge` is **non-interactive** — no hover / focus / press / disabled of its own. Its only variation is the **background it lands on**, because the row/card owns hover and selection:

| Context | Fill | Border | Text / marker |
|---|---|---|---|
| **Default** — on `surface` | `neutralTint` | none | `textSecondary` |
| **On hovered row** — on `surfaceHover` | `neutralTint` | none | `textSecondary` (tint stays legible on the raised surface) |
| **On selected row** — on `primarySubtle` | **`surface`** (solid) | **1px `neutralBorderTint`** | `textSecondary` |

On a selected `TicketListTile` (see 2.4) the background is `primarySubtle`; the translucent `neutralTint` would muddy against it, so the badge switches to a **solid `surface`** pill with a **1px `neutralBorderTint`** hairline. Text and marker colors are unchanged. This is a pure fill/border swap driven by the row's `isSelected`, passed into the badge (e.g. `RollupBadge(onSelectedRow: isSelected)`).

There is no error state — a rollup is always a valid computed number; if it cannot be computed the badge is simply not rendered.

### 2.4 `TicketListTile` integration

Existing row per Design System §2.7: `Column` gap 8; top row = ID badge → title (expands, ellipsis) → priority badge; meta row = type chip → status indicator.

- **Insert** `RollupBadge` on the **meta row**, after the status indicator, preceded by `Spacer()` so it right-aligns.
- Row padding unchanged: `EdgeInsets.symmetric(horizontal: 20, vertical: 12)`.
- **Leaf ticket** (`!rollup.hasLiveChildren` or no metric rollup): meta row is exactly as today — no badge, no reserved slot.
- **Selected row** (`isSelected`): existing treatment is `primarySubtle` background + a 3px `primary` left accent border (left padding reduced from 20 → 17 to compensate). Pass `onSelectedRow: true` to the badge → solid `surface` fill + `neutralBorderTint` hairline (2.3). ID badge fill also flips `surfaceHover → surface` per existing selected behavior; the rollup badge follows the same logic.

### 2.5 `TicketBoardCard` integration

Existing card: `surface` fill, 1px `border`, radius 12, `padding: EdgeInsets.symmetric(horizontal: 14, vertical: 13)`, `Column` gap 9 — ID row, title, meta row (type chip + priority badge).

- **Insert** `RollupBadge` on the **meta row**, after the priority badge, preceded by `Spacer()`, before any trailing execution/blocked badge.
- If both a `RollupBadge` and an execution/`BlockedBadge` are present, order is: type chip · priority · `Spacer()` · `RollupBadge` · execution badge (rollup left of the live-activity badge, matching the list's trailing-cluster convention).
- Cards have no selection background variant → the badge uses only its default (`neutralTint`) fill here.
- **Leaf card:** meta row unchanged; no badge.

| Padding | `EdgeInsets.fromLTRB(6, 2, 7, 2)` |
| Radius | `AionRadius.sm` (6) |
| Fill (default / hover) | `AionColors.neutralTint` |
| Fill (on selected row) | `AionColors.surface` |
| Border (default / hover) | none |
| Border (on selected row) | `1px AionColors.neutralBorderTint` |

## 3. Implementation notes

- **Gate first.** Compute `TicketRollup` once; wrap every new widget in `if (rollup.hasLiveChildren)`. A leaf ticket must produce the exact pre-existing subtree.
- **Never hardcode the tint.** Use `colors.neutralTint` / `colors.neutralBorderTint` so both themes are served by one widget.
- **One formatter.** All surfaces call `formatRollupMinutes`; do not format inline anywhere.
- **Read-only.** Neither `RollupIndicator` nor `RollupBadge` takes a tap/gesture. Only the leaf `estimate` / `timeSpent` editable field (unchanged) accepts input.
- **No Material.** Chips are `Container`(decoration-only)/`DecoratedBox` + `Row`/`Text`; icons are `phosphoricons_flutter` glyphs via `Icon`-equivalent (`PhosphorIcon`) — no `Chip`, `Card`, `ListTile`, `Badge`, or `Tooltip` Material widgets.
- **Marker parity.** The three stacked bars in the mockup are the visual stand-in for `PhosphorIcons.stack`; ship the real Phosphor Light glyph at 10–12px, color `textSecondary`.
