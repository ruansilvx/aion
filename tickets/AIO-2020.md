# Design: spec-ticket-type

Read alongside [proposal.md](proposal.md) for the why and the re-scoping
rationale. This file covers the technical shape only.

## Domain layer

### `TicketType` (`lib/features/tickets/domain/enums/ticket_type.dart`)

One new enum value, appended after `bug` (matching how every prior
addition — `signal`→`idea`/`knownGap`/`openQuestion`, `release` — has
read in git history):

```dart
enum TicketType {
  epic,
  story,
  task,
  resource,
  page,
  chat,
  idea,
  knownGap,
  openQuestion,
  release,
  bug,

  /// Aion's own record of a capability's current-state behavior — the
  /// ticket-native replacement for `aion-arch/specs/*.md`. Created
  /// automatically, once, when an [epic]'s `SddStage` reaches
  /// [SddStage.archived] (`TicketsCubit._createEpicSpec`, called from
  /// `advanceSddStage`), or manually via the ordinary New Ticket flow
  /// (used for the one-off "architecture spec" ticket that plays
  /// `project.md`'s role — see `aion-arch/ideas/spec-ticket-type.md`).
  /// Parentless; may parent a [chat] for discussion, nothing else. Once
  /// created, its content is an ordinary editable document — see
  /// [PagesCubit] below — with no cycle of its own; corrections and
  /// resolved-bug links are plain edits. See
  /// [TicketTypeHierarchy.isAlwaysRoot].
  spec,
}
```

### `TicketTypeHierarchy` (same file)

`canParent` gains `spec` alongside the existing `idea`/`knownGap`/
`openQuestion`/`release` special case (all five share the same rule —
parentless, may parent only a `chat`):

```dart
if (this == TicketType.idea ||
    this == TicketType.knownGap ||
    this == TicketType.openQuestion ||
    this == TicketType.release ||
    this == TicketType.spec) {
  return child == TicketType.chat;
}
```

`isAlwaysRoot` gains the same fifth member:

```dart
bool get isAlwaysRoot =>
    this == TicketType.epic ||
    this == TicketType.idea ||
    this == TicketType.knownGap ||
    this == TicketType.openQuestion ||
    this == TicketType.release ||
    this == TicketType.spec;
```

`test/features/tickets/domain/ticket_type_hierarchy_test.dart`'s
expectation matrix grows from 9×9 to 10×10 (`idea`/`knownGap`/
`openQuestion`/`release`/`bug` already brought it to 9 since
`sdd-ticket-foundation`/`idea-gap-question-ticket-types`; `spec` is the
tenth column/row).

### `AutomationContext` (`lib/core/automation/automation_context.dart`)

One new value, following the existing doc-comment convention of citing
its consumer method:

```dart
/// Auto-linking a fresh `knownGap`/`openQuestion` or a `bug` reaching a
/// `done`-role status to the most similar existing `TicketType.spec`
/// ticket — whether the link is created immediately, asks for
/// confirmation first, or is declined outright (a manual "Link to
/// spec" action remains available regardless). Added for
/// `aion-arch/changes/spec-ticket-type`; see
/// `TicketsCubit._maybeAutoLinkToSpec`.
specAutoLink,
```

Distinct from the existing `ticketLinking` context deliberately — that
one gates a *model's own* `add_link` tool-call request during a chat
turn; `specAutoLink` gates a deterministic, code-computed similarity
match with no model/tool-call involved at all. Conflating the two would
let a user's chosen confidence for "how much do I trust the model's own
linking decisions" silently also govern an unrelated mechanical process.

No drift migration needed for either enum addition — `TicketsTable.type`
is a plain `TextColumn` storing `TicketType.name`
(`lib/features/tickets/data/models/ticket_model.dart`), and
`AutomationContext` is persisted via `SharedPrefsAutomationSettingsRepository`
(`lib/core/automation/shared_prefs_automation_settings_repository.dart`),
keyed by enum name — both purely additive.

## Presentation layer — `TicketsCubit`

### Auto-creation at Epic archival

`advanceSddStage`'s existing `archived` branch
(`lib/features/tickets/presentation/cubit/tickets_cubit.dart`, currently
a bare `emit(TicketDetailLoaded(refreshed)); return null;`) becomes:

```dart
if (nextStage == SddStage.archived) {
  if (ticket.type == TicketType.epic) {
    unawaited(_createEpicSpec(refreshed));
  }
  emit(TicketDetailLoaded(refreshed));
  return null;
}
```

The `ticket.type == TicketType.epic` guard is load-bearing: this branch
also fires for `story` tickets (a Story reaching `SddStage.archived` is
the existing, routine precondition for its parent Epic's own `proposed →
verifying` transition — see `_sddStageAdvanceCheck`), and only the Epic
should ever get a spec, per the idea's "only the Epic gets a spec"
conclusion. `unawaited` matches this method's existing fire-and-forget
treatment of post-persistence side effects (e.g.
`_refreshDetailIfOpenAndAffected`) — the Epic's own `archived` write is
already durably persisted by `_repository.updateTicketSddStage` several
lines above this branch, so a slow or failed spec write never blocks or
reverts the stage transition the user is actually waiting on.

```dart
/// Synthesizes and creates [epic]'s spec ticket — see [TicketType.spec]'s
/// dartdoc. Fetches [epic]'s direct Story children
/// (`getTicketsByParent`), assembles the same kind of context
/// `_assembleStageContext` already builds for the `verifying`/`archived`
/// transitions (epic title/description + each child's title/status),
/// and resolves the model via `_resolveModelAndProvider
/// (ModelPhase.capable)` — matching `SddStageModelPhase.archived`'s
/// existing tier, since writing up a finished Epic is comparatively
/// mechanical work, not a fresh judgment call. Creates a
/// `TicketType.spec` ticket titled `"Spec — <epic.title>"` with the
/// model's reply as its content, then links it to [epic] via
/// `TicketLinkRepository.createLink(linkType: TicketLinkType.relatesTo)`.
/// A failure anywhere in this call is caught and emits
/// `TicketsError(reason: TicketsErrorReason.specWriteFailed)` — the
/// Epic itself stays `archived` regardless (see above); the fallback is
/// manually creating the missing spec ticket via the ordinary New
/// Ticket flow, since `TicketType.spec` is generically creatable there.
/// No-ops if the cubit was constructed without a `ProviderRegistry`/
/// `TicketLinkRepository`.
Future<void> _createEpicSpec(Ticket epic) async { ... }
```

No `chat`-type ticket is spawned for this — consistent with the
pre-existing "nothing to spawn after Archival" behavior this branch
already documented before this change (there is no further SDD stage
after `archived` for a chat to represent). The model call's reply
becomes the spec ticket's content directly.

### Auto-linking to the nearest relevant spec

```dart
/// Best-effort auto-link from [ticket] to the single most similar live
/// `TicketType.spec` ticket, gated by
/// `AutomationSettingsRepository.getConfidence(AutomationContext
/// .specAutoLink)`. Reuses `domain/utils/embedding_similarity.dart`'s
/// `cosineSimilarity` the same way `TicketContextEnricher`'s embedding-
/// similarity pass does (`ticket.title`+`ticket.description` as the
/// query, 0.75 threshold, unchanged) but takes only the single best
/// match above threshold rather than a top-K list — this creates a
/// real `relatesTo` link, not enrichment prose, so a lower bar for
/// "worth mentioning" doesn't apply. `auto`: creates the link
/// immediately via `TicketLinkRepository.createLink`. `gated`: creates
/// no link yet; a `_pendingSpecLinkSuggestion` surfaces on `ticket`'s
/// own `TicketDetailLoaded` state as a confirm banner (mirrors the
/// stage-advance gated banner's shape — see `_SddStageSection`'s
/// `gated` branch in `tickets.md`), calling this same match through on
/// confirm. `manual`: no proactive surfacing; the same similarity
/// lookup backs a manual "Link to spec" action available on every
/// ticket's Documentation-mode section, prefilling its suggestion when
/// invoked. No-ops silently (no error, no banner) if nothing clears the
/// 0.75 threshold, or if the cubit was constructed without an
/// `EmbeddingProvider`/`TicketLinkRepository`.
Future<void> _maybeAutoLinkToSpec(Ticket ticket) async { ... }
```

Two call sites, both `unawaited` for the same reason as
`_createEpicSpec` — linking is a downstream enrichment, never a
precondition for the triggering write to succeed:

- **`createGapOrQuestion`** — after its existing mandatory
  `relatesTo` link to `targetTicketId` is created, call
  `unawaited(_maybeAutoLinkToSpec(created))` on the freshly created
  `knownGap`/`openQuestion` ticket. This is additive to, not a
  replacement for, the existing mandatory target link — a `knownGap`
  can end up with two `relatesTo` links: one to whatever it was
  literally raised against (human-chosen, mandatory), one to the spec
  it's most semantically relevant to (auto-discovered, best-effort).
- **`updateTicketStatus`** — when the resolved status has the
  `done` role (`WorkflowStatus.isDoneRole`, the same check
  `_interceptTaskExecutionTrigger`-adjacent logic already reads
  elsewhere) and `ticket.type == TicketType.bug`, call
  `unawaited(_maybeAutoLinkToSpec(refreshedTicket))` after the status
  write is confirmed. Scoped to `bug` only, not `task` — a Task's
  completion is already structurally traceable to its Epic's spec via
  its `parentId` chain (see the idea's "structurally-traceable tickets
  need no new link" conclusion); only a Bug (which may be filed and
  resolved with no structural relationship to the Epic whose spec it
  actually invalidates) needs the similarity-based path.

## Presentation layer — spec ticket editing

### `PagesCubit`/`PageDetailScreen`

Both currently operate specifically on `TicketType.page` (confirmed via
`/explore` — `PagesCubit` is not already generically `TicketType`-
parameterized the way the source idea assumed; only the underlying
`MarkdownEditor` design-system molecule is a true drop-in reuse). This
change widens both to also accept `TicketType.spec`:

- Wherever `PagesCubit`/`PageDetailScreen` branch on
  `ticket.type == TicketType.page` to decide "is this mine to render,"
  the condition becomes `ticket.type == TicketType.page || ticket.type
  == TicketType.spec`.
- Content editing itself is unchanged — the same `MarkdownEditor`
  instance, the same save path, since both types store their body in
  the same `description` field a `page` already uses.
- `PageCreateScreen` is **not** touched — a `spec` ticket is never
  created through it; creation is either automatic
  (`_createEpicSpec`) or through the generic `CreateTicketScreen` (see
  below), never the page-specific create flow, since specs don't nest
  the way pages do.

### `CreateTicketScreen`

`spec` is added to the generic dropdown's included types (currently
excludes `page`/`knownGap`/`openQuestion`; `spec` joins `epic`/`idea`/
`release`/etc. as directly selectable) — this is what makes the
one-off "Architecture — Aion" spec possible without any new UI, and
gives a human an escape hatch to hand-create a spec if `_createEpicSpec`
ever fails (see proposal.md's Out of scope).

### `DocumentationScreen`

Left unchanged deliberately — its existing `final isPage = ticket.type
== TicketType.page;` check (line 325) stays exactly as-is, not widened
to `spec`. A spec ticket is reachable via its owning Epic's `relatesTo`
link (and, later, the graph-view idea), not via generic
Documentation-section browsing — the same treatment `knownGap`/
`openQuestion` already get.

## `TicketsErrorReason`

One new value, `specWriteFailed`, following the existing
`sddStageAdvanceFailed`/`executionFailureReason` naming convention —
localized via `ticketsErrorMessage` like every other reason.

## Design tokens

One new color pair in `lib/design_system/tokens/aion_colors.dart`:
`typeSpec` (Arctic/Obsidian values TBD at `/apply` time, following the
exact `typeSignal`/`typeRelease` addition precedent from
`sdd-ticket-foundation`'s design gate) — used by `TypeChip`/
`ticketTypeLabel`'s existing `TicketType`-keyed switch, and by
`LinkedTicketsSection._typeColor`'s existing switch (which
`sdd-ticket-execution` already had to patch for `signal`/`release`/
`chat` gaps — this change adds the `spec` arm proactively rather than
leaving another silent catch-all fallthrough).

# Aion — `spec` Ticket Type: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Page Content Editor Spec](./Aion%20Page%20Content%20Editor%20Spec.md) (`PageDetailScreen`, `MarkdownEditor`, `MarkdownView`), the [Signal & Release Types Spec](./Aion%20Signal%20and%20Release%20Types%20Spec.md) and [Bug Ticket Type Spec](./Aion%20Bug%20Ticket%20Type%20Spec.md) (type-accent pattern, `TypeChip`, type dropdown). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TypeChip`, `AppDropdown` by name.

`TicketType.spec` is Aion's own record of a capability's **current-state behavior**. It is written automatically when an Epic finishes (title `"Spec — <Epic title>"`) or created by hand, and from then on it is viewed and edited on the **existing** `PageDetailScreen` with the **existing** `MarkdownEditor`, unchanged. **No new screens, no new routes.** The change is three things: one accent token (§1), one small new molecule — `SpecOriginBadge` (§2) — mounted at the top of `PageDetailScreen` (§3), and one new entry in the create-form type dropdown (§4).

**No Material widgets anywhere.** Every element below is a Flutter primitive: `DecoratedBox`, `Padding`, `Row`/`Column`, `GestureDetector`, `MouseRegion`, `Focus`, `RichText`/`Text.rich` + `TapGestureRecognizer`, `CustomPaint` (link underline), `OverlayEntry` + `CompositedTransformTarget`/`Follower` (dropdown). `TextField` inside a transparent `Material` ancestor remains the sole permitted Material exception, for text input only — unchanged from existing specs.

Themes: **Arctic** (light) and **Obsidian** (dark). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only colors differ, and every color is a named token resolved per theme. Hex is quoted `Arctic / Obsidian` for reference only — implement against the token. Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB.

New tokens introduced: **one** — `typeSpec`. No new text, radius, or spacing tokens.

## 1. `typeSpec` accent color

A new base type-accent added to `AionColors` alongside the nine existing `type*` fields. It renders through the **unchanged** `TypeChip` and every accent that derives from the ticket's type (type dropdown row, ticket rows, linked-ticket rows, `SpecOriginBadge` §2). The only code change is one enum case in `typeColorFor` / `typeLabelFor` (§1.4).

### 1.1 Value

| | Arctic | Obsidian |
|---|---|---|
| `typeSpec` | `Color(0xFF8A3FB0)` — amethyst | `Color(0xFF3FA9F5)` — azure |

This is the one token pair in the type family whose **hue differs between themes**. That is deliberate; §1.2 explains why, and it follows the precedent already set by `primary` (`#2E86D4` blue in Arctic, `#9366FF` violet in Obsidian).

### 1.2 Rationale

The brief's hard constraint is distinctness from all nine existing type accents, with specific attention to the already-tight `typeIdea` / `typeStory` neighborhood. Plotting every accent on the hue wheel per theme:

**Arctic** — `typeRelease` 9°, `typeResource` 22°, `warning` 44°, `typeBug` 93°, `typeKnownGap` 128°, `typeStory` 163°, `typeIdea` 187°, `typeTask` 207°, `typeChat` 226°, `typeEpic` 248°, `typePage` 317°, `typeOpenQuestion` 328°, `danger` 349°.
Largest open interval: **248° → 317° (69° wide)** — the red-violet / amethyst band.

**Obsidian** — `typeRelease` 12°, `typeResource` 26°, `warning` 45°, `typeBug` 85°, `typeKnownGap` 124°, `typeStory` 158°, `typeIdea` 186°, `typeEpic` 228°, `typeChat` 230°, `typeTask` 258°, `typePage` 291°, `typeOpenQuestion` 330°, `danger` 352°.
Largest open interval: **186° → 228° (42° wide)** — the azure band, and it is open *because* `typeTask` follows `primary` from blue into violet in the dark theme. Obsidian's amethyst band, by the same migration, is the one region that is **not** free (`typeTask` 258° / `typePage` 291°).

So the two themes have opposite vacancies, and the honest answer is to take each theme's real gap rather than force one hue through both:

- **Arctic takes amethyst (280°)** — 32° off `typeEpic`'s blue-violet and 37° off `typePage`'s orchid-magenta, sitting cleanly between two colors that lean in opposite directions.
- **Obsidian takes azure (205°)** — the slot `typeTask` vacated. 19° off `typeIdea` but on the correct side of the cyan/blue boundary (idea reads *cyan*, spec reads *blue*), and 23° off `typeEpic`'s indigo. Critically, it moves **away** from the `typeIdea` / `typeStory` green-cyan crowd rather than adding a tenth color to it; had the ninth accent been placed at 170° the two would have become three.

Semantically both readings land: amethyst and azure are the palette's "cool, authoritative, reference-material" end, the opposite of the warm action colors (`typeRelease`, `typeResource`, `danger`) — appropriate for a record of what a system *already does*. Contrast on each theme's `surface` is 6.0:1 (Arctic) and 6.7:1 (Obsidian) at full strength, above every existing type accent's floor.

The cross-theme hue shift is stated in the token doc comment so it is never "fixed" as a bug.

### 1.3 `AionColors` addition

```dart
// AionColors — add one field alongside the existing type accents:
/// Spec chip accent. NOTE: intentionally hue-shifts between themes —
/// amethyst in Arctic, azure in Obsidian — because `typeTask` follows
/// `primary` from blue to violet in the dark theme, swapping which hue
/// band is free. Do not "correct" one to match the other.
final Color typeSpec;

// Arctic:
typeSpec: Color(0xFF8A3FB0),

// Obsidian:
typeSpec: Color(0xFF3FA9F5),
```

### 1.4 Resolver extension

The single point of extension — no widget hardcodes a color.

```dart
Color typeColorFor(TicketType type, AionColors c) {
  switch (type) {
    // …existing: epic, story, task, resource, page, idea, knownGap,
    //            openQuestion, release, chat, bug…
    case TicketType.spec: return c.typeSpec;   // new
  }
}

String typeLabelFor(TicketType type) {
  case TicketType.spec: return 'SPEC';          // new — pre-uppercased
  // …existing labels…
}
```

### 1.5 `TypeChip` renderings (widget unchanged)

`fillAlpha` is `AionColors.fillAlphaArctic` `0.11` / `fillAlphaObsidian` `0.16`, resolved per theme.

| Variant | Padding | Swatch | Label | Radius | Fill | Swatch + text |
|---|---|---|---|---|---|---|
| Row (list / board / dropdown) | `EdgeInsets.fromLTRB(5,2,7,2)` | `9×9`, radius `2` | `AionText.chip` | `5` | `typeSpec.withOpacity(fillAlpha)` | `typeSpec` |
| Detail (header) | `EdgeInsets.fromLTRB(6,3,8,3)` | `11×11`, radius `3` | `AionText.chip` | `5` | `typeSpec.withOpacity(fillAlpha)` | `typeSpec` |

- Arctic: fill `#8A3FB0` @ `0.11`; swatch/text `#8A3FB0`. Obsidian: fill `#3FA9F5` @ `0.16`; swatch/text `#3FA9F5`.
- Label string: `"SPEC"`. Border: none. Shadow: none.
- `TypeChip` is **non-interactive** — no hover / focus / pressed / disabled / error states of its own. Taps route through the enclosing row.

## 2. `SpecOriginBadge`

A new, small, single-line identity strip shown at the top of `PageDetailScreen` **only when `ticket.type == TicketType.spec`**. It answers one question: *did Aion write this, and from what?*

Structure, no Material: `DecoratedBox` (fill + border + radius) → `Padding` → `Row` (`crossAxisAlignment: center`, `gap: AionSpacing.sp8`) → [ icon chip `DecoratedBox` → `CustomPaint`/glyph ] + [ `Text.rich` with an inline link span ].

### 2.1 Variant decision — manual specs

Three cases, and **the strip always renders** for a spec ticket. Hiding it for manual specs was rejected: absence would be indistinguishable from an ordinary `page` ticket, so the badge would stop being a reliable "this is a spec" signal exactly when the user most needs it. Instead the manual variant keeps the chrome and drops the link.

| Variant | Condition | Text | Link |
|---|---|---|---|
| **A — auto** | `ticket.sourceEpicId != null` and the Epic resolves | `"Auto-generated from "` + **Epic title** | yes, §2.4 |
| **B — manual** | `ticket.sourceEpicId == null` | `"Manually created spec"` | no |
| **C — orphaned** | `sourceEpicId != null` but the Epic is deleted / unresolvable | `"Auto-generated from a deleted Epic"` | no |

Variants B and C are visually identical to A minus the link: same fill, border, radius, padding, icon, and text style; the whole line renders in `textMuted` and the row is non-interactive (no `MouseRegion`, no `Focus` node, cursor stays default).

### 2.2 Container — both themes (dimensions identical)

| Property | Value |
|---|---|
| Width | intrinsic (`MainAxisSize.min`), never full-bleed; wraps to a second line by ellipsizing the Epic title, not by growing |
| Height | `30` (intrinsic from content; do not hardcode a `SizedBox`) |
| Padding | `EdgeInsets.fromLTRB(7, 5, 12, 5)` |
| Radius | `BorderRadius.circular(AionRadius.md)` — `10` |
| Fill | `typeSpec.withOpacity(isDark ? 0.10 : 0.07)` |
| Border | `1px solid typeSpec.withOpacity(isDark ? 0.28 : 0.20)` |
| Shadow | none |
| Row gap | `AionSpacing.sp8` (8) between icon chip and text |

Arctic reference: fill `#8A3FB0` @ `0.07`, border `#8A3FB0` @ `0.20`. Obsidian: fill `#3FA9F5` @ `0.10`, border `#3FA9F5` @ `0.28`.

### 2.3 Icon chip

| Property | Value |
|---|---|
| Size | `20 × 20` |
| Radius | `BorderRadius.circular(AionRadius.sm)` — `6` |
| Fill | `typeSpec.withOpacity(isDark ? 0.22 : 0.15)` |
| Border | none |
| Glyph | `file-check` (document with check) — the "recorded behavior" mark, distinct from the plain `file-text` used for `page` |
| Glyph size | `12` |
| Glyph color | `typeSpec` |

The glyph is drawn from the existing icon set (`CustomPaint`-backed), never a Material `Icon`.

### 2.4 Text line and Epic link

A single `Text.rich`, `maxLines: 1`, `overflow: TextOverflow.ellipsis` — the Epic title truncates before the strip ever wraps.

| Span | Copy | Style |
|---|---|---|
| Prefix | `"Auto-generated from "` (variant A) | `AionText.breadcrumb` (11 / w500), color `textMuted` (`#8496A6 / #6B7690`) |
| Link | the Epic title, e.g. `"Board Filtering & Saved Views"` | `AionText.breadcrumb.copyWith(fontWeight: FontWeight.w600)`, color `primary` (`#2E86D4 / #9366FF`) |
| Variant B | `"Manually created spec"` | `AionText.breadcrumb`, color `textMuted` |
| Variant C | `"Auto-generated from a deleted Epic"` | `AionText.breadcrumb`, color `textMuted` |

`AionText.breadcrumb` is chosen over `bodySm` deliberately: this strip is an ancestor-path statement ("this spec belongs to that Epic"), the same relationship every other breadcrumb subtitle in the app expresses, and at 11px it stays subordinate to the `h2` page title directly below it.

The link is a `TextSpan` with a `TapGestureRecognizer`, wrapped in a `MouseRegion` (`cursor: SystemMouseCursors.click`, hit-tested to the span's own box only — the surrounding strip is **not** tappable) and a `Focus` node so keyboard nav reaches it. Tap / `Enter` / `Space` → push that Epic's detail screen.

#### 2.4.1 Link states

| State | Color | Underline | Other |
|---|---|---|---|
| Default | `primary` | none | — |
| Hover (pointer) | `primaryHover` (`#1E6DB6 / #A886FF`) | `1px` solid `primaryHover`, `TextDecoration.underline` with `decorationThickness: 1`, offset ~`2` | cursor `click`; 100ms color tween |
| Focused (keyboard) | `primary` | none | `1.5px solid primary` ring on the span's bounds, `BorderRadius.circular(4)`, inflated `EdgeInsets.symmetric(horizontal: 3, vertical: 1)`; drawn with `CustomPaint` behind the span so the text never shifts |
| Pressed | `primaryHover` at `0.80` opacity | underline retained | no scale change — the target is too small for `AnimatedScale` to read as anything but jitter |
| Focused + hover | `primaryHover` | underline | ring retained |
| Disabled | n/a — the link is either present and live, or replaced by variant B/C plain text | | |
| Error | n/a — an unresolvable Epic is variant C, not an error state | | |

The badge as a whole has **no** hover or pressed state: only the link responds, so the strip never reads as a button.

### 2.5 Copy rules

- Epic title is rendered verbatim, never re-cased and never quoted.
- The prefix keeps its trailing space inside the prefix span so the underline never extends under it.
- No ticket key in the strip (`AIO-98` is redundant — the link goes there, and the key already appears on the Epic's own screen).

## 3. `PageDetailScreen` integration

The screen is otherwise **unchanged**: same header (Page Content Editor §3.1), same `MarkdownEditor` / `MarkdownView` (§1–§2), same sub-pages / linked-tickets / backlinks sections (§4–§5), same delete action, same sync badge. A spec ticket is edited exactly like a page.

### 3.1 Header differences

| Element | Page ticket | Spec ticket |
|---|---|---|
| Type chip (header, leading) | `TypeChip` `page` — `"PAGE"`, `typePage` | `TypeChip` `spec` — `"SPEC"`, `typeSpec` (§1.5, detail variant) |
| Key eyebrow | `AionText.key`, `textSecondary` | unchanged (`AIO-142`) |
| Title | `AionText.h2`, `textPrimary`, inline-editable | unchanged — including for auto-generated specs; the `"Spec — …"` title is a default, not a lock |
| Sub-pages / linked / backlinks | as spec'd | unchanged |

Module-accent usages inside the screen that resolve from the ticket's type (sub-page icon color, `+ ADD` label color — Page Content Editor §4.1/§4.2) resolve to `typeSpec` on a spec ticket, `typePage` on a page. Nothing else changes.

### 3.2 Badge placement

`SpecOriginBadge` is the **first child of the scroll body**, above the `MarkdownEditor`:

1. **`SpecOriginBadge`** — new, spec-only.
2. `MarkdownEditor` (page content).
3. Sub-pages section.
