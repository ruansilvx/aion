# Delta spec: project-type-aware-conventions-and-verification

## ADDED

- **A new baseline version, `0.3.0`**
  (`assets/baseline/0.3.0/manifest.json`), added to
  `BundledBaselineRepository._bundledVersions` as the new default
  (`getAvailableBaselineVersions().last`). Every `skills/*` asset and the
  architecture-convention asset (renamed key: `conventions/
  architecture-conventions`, was `conventions/flutter-conventions`) is
  real, self-contained, stack-agnostic content — no pointers into
  `aion-arch`. `0.1.0`/`0.2.0` are untouched. `skills/verify` is written
  as genuinely operative instructions (not just descriptive orientation
  text like the other 12 skill files), since it is fed directly into a
  real coding-execution verify turn (see below) rather than only being
  reference material.
- `ProjectStackDetector` (`core/build/project_stack_detector.dart`) —
  marker-file-based stack detection (`pubspec.yaml`, `package.json`,
  `Cargo.toml`, `go.mod`, `pyproject.toml`, `requirements.txt`) returning
  a `DetectedStack` (language + a suggested setup/check command). Used
  only by `BaselineTailoringService` — purely informational guidance
  text, never a value Aion's own code runs.
- `BaselineTailoringService` (`features/projects/data/services/
  baseline_tailoring_service.dart`) — at project creation
  (`CreateProjectCubit.submit`, desktop only), if `ProjectStackDetector`
  detects a stack, writes a `ProjectOverride` for the
  architecture-convention asset mentioning the detected language and a
  suggested build/verification command.
- `BaselineRepository` gains three new methods: `readBundledContent`,
  `readOverrideContent`, `writeOverride` — write-side capability the
  interface previously lacked entirely. Consumed by two callers: the new
  override-authoring UI (below), and `TicketsCubit`'s new
  `_effectiveAssetContent` resolver (below) — the first code path that
  reads baseline/override content into an actual model prompt.
- **`TicketsCubit`'s coding-execution verify gate becomes agentic.**
  After a successful implement turn, `_runCodingExecution` runs a second
  model turn (`_assembleVerificationContext`) using the project's
  effective `skills/verify` content (bundled default, or a project
  override) as operative instructions, plus the effective `conventions/
  architecture-conventions` content already included in the implement
  turn's prompt (`_assembleExecutionContext`, also newly async). The
  model uses its own file/git/bash tool access to check its own work and
  ends its reply with `"VERIFICATION: PASSED"` or `"VERIFICATION:
  FAILED — <reason>"`. `_verificationFailureReason` parses that terminal
  line and **fails closed**: only an explicit `PASSED` line counts as a
  pass; a missing or unparseable terminal line is treated as a failure
  with a generic reason, preserving the actual safety property
  `coding-execution-reliability-and-safety` shipped (never open a PR on
  an ambiguous result) even though pass/fail is no longer determined by
  a shell exit code.
- **Override-authoring UI** — a new "Overrides" Settings section linking
  to `OverridesListScreen` (`/workspace/settings/overrides`, lists every
  baseline asset in the active project's pinned manifest with an
  "Overridden" indicator) and `OverrideEditorScreen`
  (`/workspace/settings/overrides/:assetKey`, a plain multi-line text
  editor over that asset's bundled default or existing override,
  saving via `writeOverride`). Backed by new `OverridesCubit`/
  `OverrideEditorCubit`. This is what makes editing a project's own
  `skills/verify` content (e.g. adding a stricter lint invocation) a
  real, user-facing capability.

## MODIFIED

- `TicketsCubit`'s coding-execution constructor param removed
  (`FlutterVerifier? flutterVerifier`) and replaced with three new
  optional params: `BaselineRepository? baselineRepository`, `String?
  projectId`, `String? baselineVersion` — same optional-dependency
  pattern as `projectRootPath` (`null` no-ops `_runCodingExecution`
  entirely).
- `_runCodingExecution` drops the mechanical `flutterVerifier.pubGet`
  setup call before the loop (no replacement — the model installs its
  own dependencies as its first action, guided by `Project conventions`
  in the implement-turn prompt) and replaces the `flutterVerifier.
  analyze(worktreePath)` mechanical check with the agentic verify turn
  described above.
- `_assembleExecutionContext` becomes `Future<String>` (was
  synchronous): unchanged title/description/`"IMPLEMENTATION: DONE"`
  instruction, plus a new `## Project conventions` section (the
  project's effective `conventions/architecture-conventions` content, if
  any) and one added sentence instructing the model to set up its
  environment first if needed.
- `_assembleCorrectiveContext` now takes a `String` failure reason
  (parsed from the verify turn's reply) instead of a `FlutterVerifyResult`.
- `app_router.dart`'s `TicketsCubit` construction passes
  `baselineRepository: context.read<BaselineRepository>()`,
  `projectId: widget.project.id`, and `baselineVersion:
  widget.project.baselineVersion` instead of `flutterVerifier:
  FlutterVerifier()`.
- `CreateProjectCubit` gains a new constructor dependency,
  `BaselineTailoringService`, and calls
  `tailorForDetectedStack` (desktop only) after
  `_initializeDesktopProject` succeeds. `submit`'s signature is
  otherwise unchanged.
- `settingsAutomationCodingExecutionRetryDescription`
  (`lib/l10n/app_en.arb`) is reworded to describe verification generically
  instead of naming `flutter analyze` literally.

## REMOVED

- `FlutterVerifier` (`core/build/flutter_verifier.dart`) and its test —
  no replacement class. Nothing in Aion's own Dart code shells out for
  verification anymore.
- The `conventions/flutter-conventions` baseline asset key (baseline
  `0.3.0` only — `0.1.0`/`0.2.0` keep it, since those manifests are
  historical and untouched).

## Non-goals (explicitly not covered)

- No change to any prompt assembly other than coding-execution's own
  (`_assembleExecutionContext`/`_assembleVerificationContext`). No other
  stage-chat prompt (`_spawnStageChat` and friends) reads
  `BaselineRepository`, and no baseline asset other than `conventions/
  architecture-conventions`/`skills/verify` is read into any prompt —
  still true after this change.
- No project-level, user-configured verify/setup shell command of any
  kind, and no per-language `Verifier` subclass. `Project` gains no new
  fields in this change.
- `new-project-onboarding`'s attach flow, Inbox, and codebase
  summarization remain unbuilt; `BaselineTailoringService`'s "full
  agentic" tailoring path (tied to that idea's summarization-depth
  choice) is not implemented here.
- `baseline-version-upgrade-flow-for-an-existing-project` remains
  unbuilt — a project pinned to `0.1.0`/`0.2.0` still resolves
  `skills/verify` to the old `aion-arch`-pointer content (meaningless
  outside Aion's own self-hosting checkout) — an unchanged limitation,
  not a regression introduced by this change.
