# Ticket Link Count Excludes Trashed

# Proposal: Ticket Link Count Excludes Trashed

## Problem

`aion-arch/specs/tickets.md`'s known-gaps list (line 1098-1101) already
documents this: "A live ticket's link count (`ticket_links`) still counts
links to a currently-trashed linked ticket." Confirmed by
`/explore live ticket link count` (2026-07-16):
`TicketLinkDao.getLinksForTicket` (`aion/lib/features/tickets/data/daos/ticket_link_dao.dart`)
is a plain `WHERE source_ticket_id = ? OR target_ticket_id = ?` query — no
join back to `TicketsTable`, no filter on the *other* ticket's
`deleted_at`. `LinkCountLabel`
(`aion/lib/features/tickets/presentation/screens/tickets_list_screen.dart`)
renders that raw row count on every ticket row in the list, via
`context.read<TicketLinkRepository>().getLinksForTicket(ticketId)`.

Net effect: if ticket A links to ticket B, and B is moved to Trash, A's
list-row link count still includes that link — a number the user can no
longer act on (B isn't reachable from the list), until B is restored or
permanently deleted. The spec already calls this "minor, low-stakes" since
it self-corrects on restore and resolves cleanly on permanent delete
(`emptyTrash`/`permanentlyDeleteTicket` cascade-delete the `ticket_links`
rows via `TicketLinkDao.deleteLinksForTickets`). It's still a wrong number
shown to the user in the interim, and the fix is small and self-contained.

`/explore` also flagged a second, unrelated staleness while investigating:
`aion-arch/specs/tickets.md` line 1149-1150 ("No UI for `ticket_links`...
no screen consumes them yet") is itself inaccurate — `LinkCountLabel`
already consumes `TicketLinkRepository.getLinksForTicket`, and
`TicketLinkRepository`'s own dartoc ("No link UI exists yet in this
slice") repeats the same stale claim. Both get corrected as part of this
change since they're immediately adjacent to the file being touched.

## Goal

`TicketLinkDao.getLinksForTicket(ticketId)` returns only links whose
*other* endpoint (not `ticketId` itself) is a live, non-trashed ticket.
Trashed-and-restored or permanently-deleted tickets already correct
themselves per the existing restore/cascade-delete behavior — this change
only fixes the interim window while the other ticket sits in Trash.

## Approach

`TicketLinkDao` gains `TicketsTable` to its `@DriftAccessor` so it can join
against `deleted_at`. `getLinksForTicket` becomes two joined queries (one
for `ticketId` as source, one as target, each joined to `TicketsTable` on
the *other* column with a `deletedAt.isNull()` filter) whose results are
concatenated — see `design.md` for the exact query shape. No schema
change, no new columns, no new repository method signature —
`DriftTicketLinkRepository` and the domain `TicketLinkRepository`
interface are unchanged; only the DAO's internal query changes.

## Out of scope

- **`ticketId` itself being trashed.** This change only filters the
  *other* endpoint. `LinkCountLabel` is only ever rendered for tickets
  visible in the live ticket list, so `ticketId` itself is never trashed
  in practice — no behavior change needed on that side.
- **A `TicketLinksRepository`/`LinksCubit` or any `ticket_links` UI beyond
  the existing count label.** Still not built; still a separate,
  already-tracked known gap (line 1149-1150 is only being corrected for
  accuracy, not implemented against here).
- **Restore/permanent-delete cascade behavior.** Already correct today
  (confirmed by `/explore`) — untouched.
- **Caching or a dedicated Cubit for link counts.** `LinkCountLabel`'s
  existing `FutureBuilder`-per-row pattern is unchanged; this proposal
  only fixes what the query returns, not how it's fetched/rendered.
