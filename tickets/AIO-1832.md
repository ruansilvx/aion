# Design: repo-release-setup-and-distribution


No file under `aion/lib/` changes. This is the first CI/CD surface and
the first release-tooling skill in either repo.

## GitHub Actions workflow (`aion/.github/workflows/release.yml`)

Triggered on tag push matching `v*.*.*`. Three jobs:

```yaml
on:
  push:
    tags:
      - 'v*.*.*'

jobs:
  build-windows:
    runs-on: windows-latest
    steps:
      - checkout
      - subosito/flutter-action (channel: stable)
      - flutter pub get
      - flutter build windows --release
      - choco install innosetup -y
      - ISCC.exe windows/installer/aion.iss
        # produces windows/installer/Output/Aion-Setup-<version>.exe
      - upload-artifact: windows-installer

  build-linux:
    runs-on: ubuntu-latest
    steps:
      - checkout
      - subosito/flutter-action (channel: stable)
      - apt-get install: ninja-build, libgtk-3-dev (flutter linux build deps)
      - flutter pub get
      - flutter build linux --release
      - linux/packaging/build_appimage.sh
        # produces Aion-<version>-x86_64.AppImage
      - upload-artifact: linux-appimage

  publish-release:
    needs: [build-windows, build-linux]
    runs-on: ubuntu-latest
    steps:
      - download-artifact (both)
      - extract this version's section from CHANGELOG.md
        (split on `## [` headers, take the block under the tag's version)
      - gh release create <tag> --title <tag> --notes-file <extracted-section>
        --attach <installer.exe> --attach <appimage>
```

The version string used for artifact filenames and the extracted
changelog section comes from the pushed tag itself (`github.ref_name`,
stripped of its leading `v`), not from re-reading `pubspec.yaml` in
CI — `/prepare-release` (below) is what keeps `pubspec.yaml` and the
tag in agreement before the developer ever tags, so CI only needs to
trust the tag.

No model-API credentials of any kind exist in this workflow — it is
pure build/package/publish, matching the proposal's decision to keep
changelog drafting local and human-reviewed.

## Windows packaging (`aion/windows/installer/aion.iss`)

Standard Inno Setup script:

- `[Setup]`: `AppName=Aion`, `AppVersion` sourced from a `/DAppVersion=`
  command-line define passed by the workflow (`ISCC.exe
  /DAppVersion=1.2.3 aion.iss`) so the script itself doesn't hardcode a
  version; `DefaultDirName={autopf}\Aion`; `OutputBaseFilename=Aion-Setup-{#AppVersion}`.
- `[Files]`: recursively includes `build\windows\x64\runner\Release\*`.
- `[Icons]`: Start Menu shortcut + optional desktop shortcut checkbox.
- `[UninstallRun]` / default Inno uninstaller entry — no custom
  uninstall logic needed, Aion has no registry keys or services to
  clean up beyond its own install directory.

No code signing — the resulting `.exe` is unsigned. `/prepare-release`'s
skill doc and this design both flag the resulting SmartScreen warning
as a known, accepted rough edge (see proposal.md Non-goals).

## Linux packaging (`aion/linux/packaging/build_appimage.sh`)

Shell script, committed so it's runnable identically in CI or locally:

1. Downloads `linuxdeploy` and `appimagetool` AppImages (pinned
   versions, cached between runs where the workflow supports it) if not
   already present.
2. Stages an `AppDir/` from `build/linux/x64/release/bundle/` (Flutter's
   own Linux build output — binary + `data/` + `lib/`), using
   `linuxdeploy --appdir AppDir --executable
   build/linux/x64/release/bundle/aion --desktop-file
   linux/packaging/aion.desktop --icon-file
   assets/icons/aion_icon.png` (bundles GTK3 shared libs the Flutter
   linux runner depends on).
3. Runs `appimagetool AppDir Aion-<version>-x86_64.AppImage`, `<version>`
   passed in as an environment variable / script argument the same way
   the Inno Setup script receives its version define.

No distro-specific `.deb`/`.rpm` packaging — a single portable AppImage
only, per the idea's explicit scope decision.

## Versioning (documented, not newly built)

- **App release version**: `pubspec.yaml`'s `version:` field and the
  matching `v<version>` git tag. Bumped only by `/prepare-release`.
- **Baseline version**: `assets/baseline/<version>/` +
  `BundledBaselineRepository._bundledVersions` — entirely separate,
  bumped whenever new/changed baseline assets ship, independent of app
  release cadence. This proposal makes no code change here; it only
  states the independence explicitly in `aion-arch/specs/release.md`
  (see spec.md) so it's no longer an implied consequence of how
  baseline detection happens to work, but a documented, intentional
  design decision.

## `CHANGELOG.md` format

Keep a Changelog style, newest first:

```markdown
# Changelog

## [Unreleased]

## [0.2.0] - 2026-08-03

### Added
- <one bullet per archived change shipped, drawn from that change's
  proposal.md "What's building">

### Fixes & chores
- <one bullet per ad hoc fix:/chore:/refactor: commit not covered by
  an archived change above>

## [0.1.0] - 2026-07-20
...
```

An `## [Unreleased]` section always exists at the top, kept empty
between releases — `/prepare-release` renames it to the new version
heading (inserting a fresh empty `## [Unreleased]` above it) rather
than deleting and recreating the structure each time.

The CI workflow's changelog-extraction step (see release.yml above)
splits on `## [` headers and takes the block immediately following the
version being released — mechanical text extraction, no parsing
beyond that.

## `/prepare-release` skill (`aion-arch/.claude/skills/prepare-release/SKILL.md`)

A new kind of skill: it operates on the `aion` repo's own
release/versioning process, not the OpenSpec SDD cycle. Lives under
`aion-arch/.claude/skills/` per this project's existing rule that all
Claude Code skills are versioned there regardless of which repo they
act on (see `aion-arch/CLAUDE.md`'s Workspace setup section) — this is
explicitly not an SDD-stage skill (`/explore` through `/archive`) or an
orientation skill (`/what-next`, `/brainstorm`, `/capture`); it's a
third category, "release tooling."

**Inputs it reads:**

1. Every `aion-arch/changes/archive/<name>/proposal.md` that does
   **not** already contain a `Shipped in:` line — this is the
   "unshipped since last release" set. Using presence/absence of that
   line (rather than comparing archive-move dates to the last tag's
   date) is deliberate: it's exact and never needs re-deriving from
   timestamps, matching the idea's own reasoning.
2. `aion`'s git log for `fix:`/`chore:`/`refactor:` commits reachable
   from the current branch but not reachable from the last release tag
   (`git log <last-tag>..HEAD --grep='^fix:\|^chore:\|^refactor:'`),
   excluding any commit whose subject matches a "Merge pull request ...
   from <change-name>" for a change already covered by input (1) — so
   an archived change's own squashed/merged commits aren't
   double-counted as "ad hoc."
3. The current `pubspec.yaml` version and `CHANGELOG.md`'s existing
   `## [Unreleased]` section (normally empty, but respected if the
   developer already hand-added notes there).

**What it drafts:**

- One changelog bullet per change in (1), phrased from that change's
  own `proposal.md` "What's building" section (richer source than a
  commit message).
- A "Fixes & chores" bullet per commit in (2).
- A suggested semver bump: **major** if any shipped change's
  `specs/spec.md` contains a `## REMOVED` section (a removed behavior);
  **minor** if any shipped change adds a new capability (a non-empty
  `## ADDED` section) or the idea itself was tagged
  `complexity: large`/`medium`; **patch** otherwise (fix-scoped changes
  and ad hoc commits only). This is a suggestion the developer can
  freely override — never applied silently.

**On developer confirmation:**

1. Bumps `pubspec.yaml`'s `version:` field.
2. Renames `CHANGELOG.md`'s `## [Unreleased]` to the confirmed version
   heading with today's date, inserts a fresh empty `## [Unreleased]`
   above it, and fills in the drafted bullets.
3. Adds `Shipped in: vX.Y.Z` as a new line under each shipped change's
   `proposal.md` in `aion-arch/`.
4. Commits (1)+(2) in the `aion` repo (`chore: release vX.Y.Z`) and (3)
   in `aion-arch` (`chore: mark vX.Y.Z shipped`) — two separate commits
   in two separate repos, matching this project's existing two-repo
   discipline.
5. Stops. **Does not tag or push.** The developer tags
   (`git tag vX.Y.Z`) and pushes the tag themselves, which is what
   triggers `release.yml`. Keeping this manual means a bad draft never
   auto-triggers a public-facing build.

Both commits in step 4 are ad hoc (not an OpenSpec cycle commit) — they
follow `branch-and-commit.md`'s "Outside an OpenSpec cycle" convention:
a `chore/release-vX.Y.Z` branch in each repo, pushed and PR'd the same
as any other ad hoc change, rather than committed straight to `main`.

## Documentation updates

`aion-arch/workflow/shared/aion-arch-workflow.md` gains a short new
section (after "Idea files and cycles") explaining that `/archive`
itself never writes `Shipped in:` — it doesn't know the eventual
release version at archive time — and that `/prepare-release` writes
it retroactively once a release is actually cut, so a future reader
doesn't mistake the absence of that line on a freshly archived change
for a missed step.

`aion-arch/specs/release.md` (new file) becomes the current-state spec
for this whole domain — see specs/spec.md for its initial content.
