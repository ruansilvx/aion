# Design: Automatic Time Tracking for Tickets

## 1. Overview

Two moves, both confined to the presentation-layer Cubit files that
already own this territory — no new files, no new domain/data-layer
surface (`TicketRepository.addTimeSpent` already exists and is reused
unchanged, per `ticket-crud-tool-calls/design.md` §4):

1. `ChatCubit.runChatTurn` gains a `TicketRepository` parameter, times
   its own model call, and calls `addTimeSpent` on the chat's parent
   ticket before returning — for every terminal outcome.
2. `log_time` (`logTimeToolDefinition`, `_handleLogTimeToolCall`, and
   every place `TicketsCubit` wires them in) is deleted.

## 2. `ChatCubit.runChatTurn` — timing + single exit point

Current shape (`chat_cubit.dart:344`) has three return points: an early
`return ChatTurnCancelled(...)` right after the event loop, and a
trailing `return succeeded ? ChatTurnSuccess() : ChatTurnFailure()`.
Adding a step that must run for *every* outcome is cleaner as a single
trailing return than as logging duplicated across three exit points, so
the control flow is restructured accordingly.

New required parameter: `required TicketRepository ticketRepository`.
Every existing call site already holds a `TicketRepository` instance
(`ChatCubit._ticketRepository`, `TicketsCubit._repository`,
`InboxCubit._ticketRepository`) — no new dependency injection anywhere,
purely a new argument at each of the 12 call sites (§4).

```dart

    String toolCallId,
    String toolName,

  onToolCall,
}) async {
  final startedAt = DateTime.now(); // NEW

  final buffer = StringBuffer();
  var succeeded = true;
  var cancelled = false;
  String? failureMessage;
  AgentDoneEvent? doneEvent;
  try {
    final events = await client.run(/* unchanged */);
    await for (final event in events) {
      /* unchanged switch */
    }
  } catch (e) {
    succeeded = false;
    failureMessage = e.toString();
  }

  final ChatTurnResult result; // was: three separate `return`s
  if (cancelled) {
    result = ChatTurnCancelled(buffer.toString());
  } else if (succeeded && buffer.isNotEmpty) {
    await commentRepo.addComment(/* unchanged success comment */);
    result = const ChatTurnSuccess();
  } else if (!succeeded) {
    await commentRepo.addComment(/* unchanged failure comment */);
    result = const ChatTurnFailure();

    // (a turn with only tool calls, no text): no comment persisted,
```

Every branch's existing behavior (which comment gets persisted, if any;
which `ChatTurnResult` subtype) is preserved byte-for-byte — the only
change is routing through one `result` variable instead of three early
returns, so `_logElapsedTime` runs exactly once, unconditionally, right
before the method returns.

### 2.1 `_logElapsedTime` — new private static helper

```dart
/// Logs [chatTicketId]'s parent ticket's elapsed time for a turn that
/// started at [startedAt], via [ticketRepository.addTimeSpent]. No-ops
/// silently if [chatTicketId] has no resolvable parent (e.g. an
/// Inbox-spawned chat) — mirrors `_handleLogTimeToolCall`'s existing
/// "No ticket to log time against" guard. Always logs at least 1
/// minute (ceiling-rounded) for any turn that reaches this point,
/// regardless of terminal outcome — a failed or cancelled turn still
/// consumed real wall-clock time. Added for
/// `aion-arch/changes/automatic-time-tracking-for-tickets`; replaces
/// the model-self-reported `log_time` tool call as `timeSpent`'s
/// source of truth — see that change's proposal.md for why.
static Future<void> _logElapsedTime(
  TicketRepository ticketRepository,
  String chatTicketId,
  DateTime startedAt,
) async {
  final chat = await ticketRepository.getTicketById(chatTicketId);
  final parentId = chat?.parentId;
  if (parentId == null) return;
  final elapsedSeconds = DateTime.now().difference(startedAt).inSeconds;
  final minutes = max(1, (elapsedSeconds / 60).ceil());
  await ticketRepository.addTimeSpent(parentId, minutes);
}
```

`max`/`ceil` on a `double` division (`elapsedSeconds / 60`) rather than
`Duration.inMinutes` (which truncates) — `Duration.inMinutes` would
return `0` for any turn under 60 real seconds, which is most of them;
ceiling-rounding with an explicit `max(1, ...)` floor guarantees every
measured turn contributes at least 1 minute, matching
`logTimeToolDefinition`'s own prior `minimum: 1` constraint on the tool
it replaces.

## 3. Testing approach — no `Clock` abstraction needed

`_logElapsedTime` calls `DateTime.now()` directly rather than through an
injected `Clock`/time-provider seam. This is a deliberate simplification
made possible by the minimum-1-minute floor: since every real test turn
completes in well under a second, `(elapsedSeconds / 60).ceil()` always
evaluates to `1` regardless of the (uncontrolled, real) wall-clock time
a test actually took. Tests assert `verify(() =>
ticketRepository.addTimeSpent(parentId, 1)).called(1)` (or, more
loosely, any positive `int`) rather than needing to fake elapsed time —
no new test infrastructure required. Introducing a `Clock` seam only
becomes necessary if a future change needs to assert an *exact* elapsed
duration, which nothing here does.

## 4. Call-site updates — thread `ticketRepository` through

Every existing `ChatCubit.runChatTurn(...)` call gains one new named
argument, `ticketRepository: <the caller's existing TicketRepository
field>`. No caller needs a new lookup or a new constructor
parameter — each already holds the repository instance for unrelated
reasons:

| File | Call site | Existing field passed |
|---|---|---|
| `chat_cubit.dart` | `sendMessage` | `_ticketRepository` |
| `tickets_cubit.dart` | `retryDesignSync` | `_repository` |
| `tickets_cubit.dart` | `_handoffExecutionChat` (old-chat summarization turn) | `_repository` |
| `tickets_cubit.dart` | `_runCodingExecution` — implement turn | `_repository` |
| `tickets_cubit.dart` | `_runCodingExecution` — verify turn | `_repository` |
| `tickets_cubit.dart` | `_runStageChatTurn` (SDD-stage chat spawn) | `_repository` |
| `tickets_cubit.dart` | `_fireSkillAttachment` | `_repository` |
| `tickets_cubit.dart` | `_runFullSummarization` | `_repository` |
| `inbox_cubit.dart` | `startBrainDump` | `_ticketRepository` |
| `inbox_cubit.dart` | `startWhatNextGuidance` | `_ticketRepository` |
| `inbox_cubit.dart` | `startReleasePlanning` | `_ticketRepository` |
| `inbox_cubit.dart` | `startQa` | `_ticketRepository` |

Each `tickets_cubit.dart` chat has a real parent ticket
(`designSyncChat.parentId`, the execution `task`, the stage `parent`,
`runTicket`, etc.), so its `_logElapsedTime` call actually logs
something. Every `inbox_cubit.dart` chat is the opposite: `InboxCubit`
only ever creates parentless chats (`_createInboxChat` never sets
`parentId` — see `InboxCubit`'s own class dartdoc, "every Inbox-spawned
chat is a parentless `chat` ticket"), so `_logElapsedTime`'s
no-resolvable-parent guard makes all 4 of these call sites permanent
no-ops. They still need the new `ticketRepository` argument threaded
through — `runChatTurn`'s parameter is `required`, so every caller must
supply it regardless of whether the resulting `_logElapsedTime` call
ever does anything — but automatic time tracking does not, and by
construction cannot, cover Inbox conversations. No per-call-site special
casing needed either way: the guard in `_logElapsedTime` itself is what
makes the Inbox case safe.

One `provider.client.run()` call site (`tickets_cubit.dart`'s
`runCodebaseSummarization`'s non-full path, ~line 6813) calls the client
directly rather than through `runChatTurn` — its own dartdoc already
notes "there's no chat ticket to [attach a comment to]." It stays
untouched: no `runChatTurn`, no time logging, exactly as today.
`ticket_estimation_suggester.dart`'s direct `provider.client.run()`
calls are likewise untouched — background inference, not chat-attached
(proposal.md's Non-goals).

## 5. Removing `log_time`

- **`ticket_crud_tool_definitions.dart`** — delete the
  `logTimeToolDefinition` const and its dartdoc. `createTicketToolDefinition`/
  `addLinkToolDefinition` are untouched.
- **`TicketsCubit._toolsFor`** — drop `logTimeToolDefinition` from the
  returned list (back to branch-or-close-branch tool + `create_ticket` +
  `add_link`). Update its dartdoc, which currently enumerates all three
  appended tools by name.
- **`TicketsCubit._onToolCallFor`** — remove the `'log_time' /*
  logTimeToolDefinition.name */ => _handleLogTimeToolCall(...)` case
  from the switch. Update its dartdoc's tool-name list (currently reads
  "not `close_branch`/`create_ticket`/`add_link`/`log_time`").
- **`TicketsCubit._handleLogTimeToolCall`** — delete the method
  entirely.

No `AutomationContext` entry existed for `log_time` (it never had one —
"always applies immediately, no gate" per its own prior dartdoc), so
there's no automation-settings cleanup, no Settings-screen row to
remove, and no `PendingToolProposal` variant to remove — `log_time`
never had any of those, matching `ticket-crud-tool-calls/design.md`
§0.2's "no visual surface" decision for it.

## 6. Non-goals / explicitly deferred

- No `Clock`/time-provider abstraction (§3).
- No change to `TicketRepository.addTimeSpent`'s signature or
  implementation — reused exactly as `log_time` already used it.
- No change to the estimate/timeSpent rollup mechanism
  (`estimate-timespent-rollup-for-ticket-hierarchy`) — it already reads
  whatever value sits in `timeSpent` regardless of source, so automatic
  contributions participate in the existing recompute walk with no
  special-casing.
- No predicted-vs-actual calibration feedback loop (proposal.md).
- No UI change anywhere (proposal.md's Design gate).
