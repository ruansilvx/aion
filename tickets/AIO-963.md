# Inline Wikilink Backlinks

# Proposal: Inline `[[wikilink]]` backlinks for the Documentation section

## Why

The shipped [Documentation section](../../specs/tickets.md#documentation-section)
explicitly carried forward a known gap: "backlinks" today means only
explicit `TicketLink`s between docs — there's no scan of a `page`
ticket's Markdown content for inline `[[Title]]`-style references, the
thing Notion/Obsidian users actually mean by "backlinks." Explored in
[aion-arch/ideas/inline-wikilink-backlinks.md](../../ideas/inline-wikilink-backlinks.md).

This closes that gap: typing `[[Page Title]]` while writing a page
becomes a real, navigable, backlink-producing reference, the way it
would in the tools the Documentation section was explicitly modeled on.

## What

- **Two-tier resolution.** `[[Title]]` (bare, hand-typed) resolves by
  case-insensitive title match against live `page`/`resource` tickets,
  same as originally designed. `[[TicketId]]` (e.g. `[[AIO-42]]`) —
  what the autocomplete actually inserts — resolves by Aion's existing
  unique `Ticket.ticketId`, always unambiguous regardless of duplicate
  titles, with its displayed text always the target's *current* title,
  resolved live at render time rather than baked into stored text. Both
  forms support `[[Target|Alias]]` for a literal, user-chosen display
  label. See design.md's "Resolution model" for the full rationale —
  this closes the duplicate-title-ambiguity gap without a new
  uniqueness constraint on the Pages module.
- **Parsing & persistence.** A page's `[[...]]` references are parsed
  out of its Markdown content on every save (both the in-app save path
  and the desktop file-watcher's reconcile path) and resolved as above.
  Resolved references are stored in a new, lightweight
  `PageWikilinksTable` index — not as `TicketLink` rows — kept in sync
  by a full delete-and-replace of a page's outgoing rows on every save.
- **Narrowed rename rewrite.** Renaming a page rewrites every
  title-anchored `[[Old Title]]` occurrence in every referencing page to
  `[[New Title]]`, matching Obsidian's real default — but id-anchored
  references never need this (their display re-resolves live), so the
  rewrite's blast radius is now limited to hand-typed, bare-title
  references. Where a rewrite would touch a page the user currently has
  open, it's deferred via the same `ActiveTicketViewRegistry` the
  file-watcher already uses for the equivalent external-edit case,
  rather than clobbering an open editor's content.
- **Backlinks display.** `BacklinksSection` (used by both
  `PageDetailScreen` and `TicketDetailScreen`) now renders two kinds of
  row side by side — explicit `TicketLink`-derived backlinks (unchanged)
  and inline-wikilink-derived ones (new, visually distinguished) — since
  both represent "something references this doc," just authored
  differently. A `resource` ticket can now be a wikilink target, so its
  own `BacklinksSection` on `TicketDetailScreen` gains this too.
- **Authoring UX.** Typing `[[` inside a page's `MarkdownEditor` opens a
  searchable, **caret-anchored** autocomplete of existing page/resource
  titles, reusing the app's existing `Overlay`/`LayerLink`/
  `CompositedTransformFollower` pattern. When nothing matches, pressing
  Enter creates a new page with that title and inserts a reference to it
  — the same create-on-the-fly affordance is also available by tapping
  an already-rendered, unresolved `[[Title]]` in a page's preview.
- **Forward navigation (scope addition — see below).** A resolved
  `[[...]]` renders as a distinct, tappable inline link in
  `MarkdownView`'s rendered preview, navigating straight to the
  referenced page/resource.

## Scope decisions beyond the brainstorm

The idea file settled resolution model, rename handling, backlinks
placement, and autocomplete — but left a few implementation-shaping
questions unasked. Flagging the calls made here explicitly so they're
open to pushback at review, before `/apply` locks them in:

1. **Forward navigation was added to scope.** The brainstorm only
   resolved *where backlinks display* (the target page's
   `BacklinksSection`), not whether the *source* page's own rendered
   content makes `[[Title]]` clickable. Without this, the feature has no
   forward navigation at all — you'd type a reference and only ever
   discover it by opening the target page and checking its Backlinks
   section. That undercuts the entire "Obsidian-style" premise, so
   `MarkdownView` gains an optional, generic `resolveWikilink` callback
   to render `[[Title]]` as a tappable, resolved inline span.
2. **Wikilink targets widened to `resource`, source stays `page`-only.**
   (Revised this session.) `resource` tickets can now be resolved as a
   wikilink target — they get a `ticketId` like any other ticket, and
   showing wikilink-origin backlinks on a resource's own
   `TicketDetailScreen` needed no new mechanism. `resource` tickets
   still can't be a wikilink *source*: they edit `description` through
   the plain `InlineEditableField`, not `MarkdownEditor`, and giving
   them an authoring surface is an editor-architecture change unrelated
   to this feature — that half stays deferred.
3. **Unresolved-title UX, closed.** (Revised this session.) The Claude
   Design pass already replaced "plain unstyled text" with a real,
   muted, chip-backed treatment (design.md §6). This session adds the
   "create page" affordance the original proposal deferred — from both
   the autocomplete's no-matches state and a tap on an already-rendered
   unresolved reference — via a new `onCreatePage`/`onCreateWikilinkTarget`
   pair calling `PagesCubit.createPage`.
4. **Duplicate-title ambiguity, closed for app-authored references.**
   (Revised this session.) Rather than enforcing a new page-title
   uniqueness constraint, wikilink resolution now has two tiers: bare
   `[[Title]]` keeps the original first-match-wins limitation
   (documented, narrow, hand-typed-only), while `[[TicketId]]` — what
   the autocomplete actually inserts — resolves via Aion's existing
   unique `Ticket.ticketId` and is never ambiguous. See design.md's
   "Resolution model" for the full reasoning.
5. **Rename-rewrite blast radius narrowed, not eliminated.** (Revised
   this session.) Id-anchored references never need rewriting at all —
   their display re-resolves live, not from stored text — so the
   rewrite cascade only fires for the (now much smaller) set of bare,
   hand-typed title references. What's left still isn't transactional
   across pages (file writes and embedding regen aren't transactional
   resources to begin with) and a rewrite failure is still swallowed
   rather than surfaced as a user notification — judged acceptable
   given the shrunk exposure, not because it's fully solved.
6. **Concurrent-edit race, mitigated.** (Revised this session.) Before
   rewriting a referencing page, `TicketsCubit` now checks the existing
   `ActiveTicketViewRegistry` (the same signal `TicketMarkdownReconciler`
   already uses to defer a write to a page the user has open) and
   defers the rewrite until the user navigates away, rather than
   clobbering an open editor's content. Desktop-only (matches that
   registry's own gating) — mobile/web have no separate file-watcher
   write path, so this specific race was already lower-exposure there.

## Non-goals

- No path-qualified disambiguation syntax (e.g. `[[Parent/Title]]`) —
  `[[TicketId]]` is the disambiguation escape hatch instead.
- No global page-title uniqueness enforcement — duplicate titles stay
  allowed everywhere else in the app; only bare, hand-typed `[[Title]]`
  references are affected by an existing collision, and even then only
  by staying on the documented first-match behavior, not by blocking
  anything.
- No new sequential ticket-key/numbering system — reuses Aion's
  existing `Ticket.ticketId` (e.g. `AIO-42`, already unique, already
  rendered via `AionText.key`), not a wikilink-specific invention.
- No `resource`-ticket wikilink *authoring* — resources can be a
  wikilink target (see Scope decision #2) but not a source, since they
  don't use `MarkdownEditor`.
- No cross-page transactional guarantee on rename-triggered rewrites —
  narrowed in scope (see Scope decision #5), not made atomic.

~~No alias syntax~~, ~~no caret-following autocomplete~~ — both were
listed as non-goals in the original proposal and are now built (see
"Scope decisions" above); struck through here rather than silently
removed, so the revision is visible in history.
