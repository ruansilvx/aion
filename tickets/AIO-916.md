# Design: Generalized live-refresh for all ticket writes

## 1. Overview

Pure `TicketsCubit`-layer change. No new BLoC states, no new widgets, no
DB migration. Everything here either modifies
`lib/features/tickets/presentation/cubit/tickets_cubit.dart` or adds one
small new file it depends on.

## 2. The dependency table

A new top-level constant, `_liveRefreshDependents`, replacing the
hardcoded `if (current.ticket.type == TicketType.story) { ... }` branch
inside `_refreshDetailIfOpenAndAffected`:

```dart
/// Declares which direct-child ticket types a parent's displayed detail
/// state (`TicketDetailLoaded.canAdvanceSddStage`/`sddStageBlockReason`,
/// computed from `getTicketsByParent` — see `getTicketById`'s dartdoc)
/// depends on. Checked by [_refreshDetailIfOpenAndAffected]: whenever a
/// write touches a ticket whose `(parent.type, ticket.type)` pair
/// appears here, the parent's open detail screen (if that's what's
/// currently shown) is silently re-fetched. Generalizes the
/// single hardcoded `story → task/bug` case from
/// `aion-arch/changes/live-refresh-open-ticket-detail-screen` — extend
/// this map, not the surrounding method, if a third dependency is ever
/// discovered. Added for
/// `aion-arch/changes/generalized-live-refresh-for-all-ticket-writes`.
const Map<TicketType, Set<TicketType>> _liveRefreshDependents = {
  TicketType.story: {TicketType.task, TicketType.bug},
  TicketType.epic: {TicketType.story},
};
```

Both entries are read-only lookups against a ticket's own `type` field
— no new enum, no persisted data, no migration.

## 3. `_refreshDetailIfOpenAndAffected`: single id → set of ids

Current signature (`tickets_cubit.dart:5444`):

```dart
Future<void> _refreshDetailIfOpenAndAffected(
  String writtenTicketId, {
  TicketsState? fromState,
})
```

New signature — widened to a set, mirroring
`TicketRollupRecomputer.recompute`'s `Set<String> startIds` shape so a
single call after a bulk write can check every affected id in one pass:

```dart
/// Re-fetches and silently re-emits [TicketDetailLoaded] for the
/// currently open ticket detail screen when a background write may have
/// changed data it depends on. Originally added for
/// `aion-arch/changes/live-refresh-open-ticket-detail-screen`;
/// generalized to a set of ids and a declarative dependency table
/// ([_liveRefreshDependents]) by
/// `aion-arch/changes/generalized-live-refresh-for-all-ticket-writes`.
///
/// Two cases trigger a refresh, checked against every id in
/// [writtenTicketIds] until one matches (no-ops the rest — a refresh is
/// idempotent and only one screen can ever be open):
/// - one of [writtenTicketIds] is the ticket currently shown
///   ([TicketDetailLoaded.ticket]'s `id` matches);
/// - the currently shown ticket's `type` is a key in
///   [_liveRefreshDependents], one of [writtenTicketIds]' tickets has a
///   `type` in that key's value set, and that ticket's `parentId`
///   matches the currently shown ticket's `id`.
///
/// No-ops when no detail screen is open, or every id in
/// [writtenTicketIds] is unrelated. Delegates to [getTicketById], which
/// never flashes [TicketsLoading] and preserves the open ticket's
/// already-loaded Documentation-section relations when re-entering for
/// the same id — see that method's dartdoc.
///
/// [fromState] defaults to a live read of [state] — correct for call
/// sites that chain this onto some other async operation's completion
/// well after their own synchronous emission (e.g. `createTicket`'s
/// `_estimationSuggester` chain). Call sites whose *own* write emits an
/// intermediate state first (`updateTicketStatus`,
/// `updateStatusForTickets`, `trashTicket`, `trashTickets`,
/// `updateTicketParent`, `advanceSddStage`) must instead pass the state
/// captured *before* that emission — see each method's own dartdoc for
/// why a live [state] read there would never see the detail screen that
/// was open when the call started.
Future<void> _refreshDetailIfOpenAndAffected(
  Set<String> writtenTicketIds, {
  TicketsState? fromState,
}) async {
  if (writtenTicketIds.isEmpty) return;
  final current = fromState ?? state;
  if (current is! TicketDetailLoaded) return;

  if (writtenTicketIds.contains(current.ticket.id)) {
    await getTicketById(current.ticket.id);
    return;
  }

  final childTypes = _liveRefreshDependents[current.ticket.type];
  if (childTypes == null) return;

  for (final id in writtenTicketIds) {
    final written = await _repository.getTicketById(id);
    if (written != null &&
        childTypes.contains(written.type) &&
        written.parentId == current.ticket.id) {
      await getTicketById(current.ticket.id);
      return;
    }
  }
}
```

This drops the old `getTicketsByParent`-based membership check (fetch
every child, see if the written id is among them) in favor of reading
the *written* ticket's own `parentId` directly — one lookup per written
id instead of one lookup returning the parent's whole child list. Both
are correct; this shape is what lets `writtenTicketIds` scale to a bulk
call without an O(children) fetch, and is symmetric with how the "same
id" case already reads the written ticket's own identity, not the
parent's.

A convenience call sites can use for the (still common) single-id case:
callers simply pass `{id}` — no separate overload, Dart doesn't support
default-parameter-driven overloading cleanly here and every call site
already has the id in hand.

## 4. Call-site wiring

No central interception point exists in `TicketsCubit` — see
`proposal.md`'s "What's deliberately not changing." Each method below
gets one new (or upgraded) `unawaited(_refreshDetailIfOpenAndAffected(...))`
call, following the two existing idioms already established:

- **"Chain onto a later async completion"** idiom (`createTicket`,
  `updateTicket` already use this for `_estimationSuggester`): read
  `state` live at the point the check actually runs.
- **"Capture state before this method's own emissions"** idiom
  (`updateTicketStatus` already uses this): capture `state` in a local
  (`stateBeforeThisWrite`) at the top of the method, before any `emit`
  call, and pass it as `fromState`.

| Method | Idiom | What changes |
|---|---|---|
| `updateTicketStatus` | capture-before (already does) | Pass `{id}` instead of `id` to the now-set-based helper. No other change — this call site's `fromState` capture is already correct. |
| `updateStatusForTickets` | capture-before (new) | Capture `stateBeforeThisWrite = state` at the method's top, before `emit(const TicketsBatchStatusUpdating())`. After the final `emit(TicketsBatchStatusUpdated(...))`, add `unawaited(_refreshDetailIfOpenAndAffected(writableIds.toSet(), fromState: stateBeforeThisWrite))` — placed after the existing `pendingAttachmentFires` loop, same ordering rationale `updateTicketStatus` already documents (an attachment's own pending-state emission must not be clobbered by this one landing after it — but here neither writes a *different* ticket's pending-attachment state, so simple sequencing after is sufficient; no `.then()` chaining needed). |
| `advanceSddStage` | capture-before (new) | Capture `stateBeforeThisWrite = state` at the method's top. After the successful `TicketRepository.updateTicketSddStage` write and its `TicketDetailLoaded` re-emission (the ticket's own screen, per §5's "same id" case already covers this), add `unawaited(_refreshDetailIfOpenAndAffected({ticket.id}, fromState: stateBeforeThisWrite))` — this is the call that closes the named Epic gap: if an Epic's detail screen was open when a child Story's `advanceSddStage` call landed, `{ticket.id}` is that Story's id, `ticket.parentId` is the Epic's id, `(epic, story)` is in the table, so the Epic re-fetches. |
| `trashTicket` | capture-before (new) | **Revised during `/apply`** — the plan below turned out to produce dead code; see the correction after this row. ~~Capture `stateBeforeThisWrite = state` before `emit(const TicketTrashing())`. The method already branches on whether `previousState is TicketDetailLoaded` (in which case the ticket being trashed *is* the open one, and it navigates away — no refresh needed, matches today's behavior). Add the call only in the `else` branch, after `emit(TicketsLoaded(...))`.~~ |
| `trashTickets` | capture-before (new) | Capture `stateBeforeThisWrite = state` before `emit(const TicketsBatchTrashing())`. After the final `emit(TicketsBatchTrashed(...))`, add `unawaited(_refreshDetailIfOpenAndAffected(ids.toSet(), fromState: stateBeforeThisWrite))`. Matches `trashTickets`' own documented scope simplification (checks only the explicitly-passed `ids`, not enumerated cascaded descendants) — consistent with, not a regression from, the git-projection side effect's existing same simplification. |
| `updateTicketParent` | capture-before (new) | **Revised during `/apply`** — "one call covers both directions" turned out to be wrong; see the correction below. ~~Capture `stateBeforeThisWrite = state` at the method's top. On `ParentChangeSuccess`, after `emit(TicketDetailLoaded(ticket))`, add `unawaited(_refreshDetailIfOpenAndAffected({ticket.id}, fromState: stateBeforeThisWrite))` — covers both directions (old parent loses a child, new parent gains one) via the same single check.~~ |
| `createTicket` | chain-onto-later-completion (already does, for self only) | **Revised during `/apply`** — the new call needs `capture-before`, not live `state`; see the correction below. ~~Alongside the existing `_estimationSuggester.suggest(persisted).then((_) => _refreshDetailIfOpenAndAffected({persisted.id}))` chain (unchanged — still closes the "self" case), add one more independent `unawaited(_refreshDetailIfOpenAndAffected({persisted.id}))` call right after the existing `unawaited(_triggerGitProjection(persisted, 'created'))` line, reading `state` live.~~ |

**`trashTicket` correction, found during `/apply`**: the plan above
assumed the existing `if (previousState is TicketDetailLoaded)` branch
already meant "the trashed ticket is the one currently open." It
doesn't — that condition never compares `previousState.ticket.id` to
`id`, so it treats *any* open detail screen as "self," including a
*different* ticket's. Consequently the originally-planned `else`-branch
call could never run: being in that branch already proves no detail
screen was open, and `_refreshDetailIfOpenAndAffected` no-ops whenever
`fromState` isn't `TicketDetailLoaded` — the call was unreachable by
construction. Confirmed with the user before deviating (three options
were offered: fix the id check, ship the dead code as specified, or
drop the wiring and flag the bug separately — fixing it was chosen).

Implemented instead: the guard became `previousState is
TicketDetailLoaded && previousState.ticket.id == id` (only that exact
case still emits `TicketTrashed` and navigates away). Its `else` now
covers both the list/board case *and* a different ticket's detail
screen being open; within it, `TicketsLoaded` is only emitted when
`previousState is! TicketDetailLoaded` (so a different open detail
screen's own state isn't clobbered by a list-shaped emission), and
`unawaited(_refreshDetailIfOpenAndAffected({id}, fromState:
previousState))` fires unconditionally within that `else` — now
genuinely reachable for the different-ticket-open case, and still
correctly skipped for self-trash (where re-fetching the just-trashed
ticket could undo the `TicketTrashed` navigate-away).

**`updateTicketParent` correction, found while writing its own test**:
the plan above assumed a single call using the written ticket's
post-write `parentId` could detect *both* the new parent (gains a
child) and the old parent (loses one). It can't — after the write,
`ticket.parentId` is always the *new* parent; nothing about the
post-write ticket still points at the old one, so the old-parent
direction is structurally undiscoverable through
`_refreshDetailIfOpenAndAffected`'s normal "re-fetch the written ticket,
read its current `parentId`" mechanism, no matter how that mechanism is
shaped. The old parent is only ever known to the *caller* —
`updateTicketParent`'s own `ticket` parameter still holds it, before the
service call overwrites it.

Fixed by capturing `oldParentId = ticket.parentId` (the method
parameter, pre-write) alongside `stateBeforeThisWrite`, then — still in
the `ParentChangeSuccess` case, after the existing new-parent-covering
call — adding a second, narrower check: if `oldParentId` is non-null,
differs from the ticket's new `parentId` (a real move happened, not a
same-parent edit), and `stateBeforeThisWrite` is `TicketDetailLoaded`
for that exact old parent, look up
`_liveRefreshDependents[stateBeforeThisWrite.ticket.type]` directly and
call `getTicketById(oldParentId)` if the reparented ticket's type is in
that set. This reuses the same dependency table rather than
special-casing the old-parent relationship outside it, but doesn't go
through `_refreshDetailIfOpenAndAffected` itself, since that helper's
whole design is built around "re-fetch the written ticket to learn its
parent" — a premise that's specifically false for this one case.

**`createTicket` correction, found while writing its own test**: the
plan above said the new immediate call should read live `state` (no
`fromState`), reasoning that it fires "right after the write." That's
true in wall-clock terms, but irrelevant to what `state` holds — by
that point `createTicket`'s own earlier `emit(TicketCreating(...))` has
already overwritten it, so a live read can never see a parent's detail
screen that was open when the call *started*. Fixed by capturing
`stateBeforeThisWrite = state` at the very top of `createTicket`
(before that emit) and passing `fromState: stateBeforeThisWrite` to the
new call. The *existing* `_estimationSuggester`-chained call is
correctly unaffected and still reads live `state` — it resolves well
after `createTicket`'s own emissions are done (including the final
`emit(TicketCreated(...))`), so "is a detail screen open right now" is
still the right question for that one.

**`trashTickets`/`updateStatusForTickets`/`advanceSddStage` were
unaffected by either correction above** — each already captured
`stateBeforeThisWrite` before its own emissions, and each affected
parent is discoverable via the written ticket's *current* state (no
old/new-parent split, since none of those methods reparent anything).

`updateTicket` (generic field edit) and `updatePriorityForTickets`
(bulk priority) are unchanged — neither writes a field any
`_liveRefreshDependents` entry watches (see `proposal.md`'s Non-goals).

## 5. Cross-cubit boundary: what's not reachable

`TrashCubit.restore` (and the `TicketParentTrashService.trash`/
`.restore`/`.changeParent` calls made by `TicketMarkdownReconciler`/
`TicketRepairService`, per that service's own dartdoc) cannot call
`_refreshDetailIfOpenAndAffected` — it's a private method on
`TicketsCubit`, and none of those callers hold a reference to the live
`TicketsCubit` instance. `TrashCubit` and `TicketsCubit` are
independently constructed (`TicketsCubit` app-wide via `WorkspaceShell`,
`TrashCubit` route-scoped per Trash-screen visit) and share only
`TicketRepository`/`TicketParentTrashService`, neither of which knows
about `TicketsCubit`'s BLoC state at all.

This is a real architectural wall, not a convenience omission — see
`proposal.md`'s Non-goals for why it's out of scope rather than worked
around.

## 6. Testing

All new coverage lives in
`test/features/tickets/cubit/tickets_cubit_test.dart`'s existing
`'live-refresh an open ticket detail screen (live-refresh-open-ticket-detail-screen)'`
group (`tickets_cubit_test.dart:9559`) — rename the group to drop the
now-stale single-change reference (e.g.
`'live-refresh an open ticket detail screen'`) and add cases per new
call site:

- `updateStatusForTickets` live-refreshes an open Story's detail screen
  when one of its direct Task/Bug children is in the written `ids` list
  (the named bulk gap), and does not refresh when the open ticket is
  unrelated to any written id.
- `advanceSddStage` live-refreshes an open Epic's detail screen when a
  direct child Story's stage is advanced (the named Epic gap), and does
  not refresh a Story's own already-open screen from a *different*
  Story's advance.
- `trashTicket`/`trashTickets` live-refresh an open Story's detail
  screen when one of its direct Task/Bug children is trashed; `trashTicket`
  does *not* fire the new call when the trashed ticket is itself the
  open one (the existing navigate-away branch).
- `updateTicketParent` live-refreshes an open Epic's detail screen both
  when a Story is newly reparented *into* it and when a Story already
  shown as a child is reparented *out* of it.
- `createTicket` live-refreshes an open Story's detail screen the moment
  a new Task is created under it, independent of the existing AI
  suggestion chain (assert the refresh happens even when
  `_estimationSuggester` is stubbed to a still-pending `Future`).
- A same-shape negative case for each: the currently open ticket's
  `type` has no `_liveRefreshDependents` entry (e.g. a `task`'s own open
  detail screen), or the written ticket's `parentId` doesn't match — no
  refresh fires.
