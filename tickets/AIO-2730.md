# 2. Add `GitProjectingTicketRepository`

- [x] Create `lib/features/tickets/data/repositories/git_projecting_ticket_repository.dart`:
      a `TicketRepository`-implementing decorator wrapping an inner
      `TicketRepository`, a `TicketGitProjector`, and a root path
      string. Per design.md's "Method coverage" table:
      - `createTicket`, `updateTicketStatus`, `updateTicketSddStage`,
        `updateTicketParent`: delegate, then `unawaited(_project(id, label))`
        (`created`/`status-changed`/`stage-changed`/`reparented`
        respectively). `createTicket` projects `ticket.id` (the
        caller-supplied uuid, unaffected by the repository generating
        a fresh `ticketId`).
      - `updateStatusForIds`: delegate, then loop `ids` firing
        `unawaited(_project(id, 'status-changed'))` per id — no
        batching, matching today's already-correct bulk-status
        behavior.
      - `trashTicket`, `restoreTicket`: delegate, then `await
        _project(id, 'trashed'/'restored')` — awaited, matching
        today's behavior.
      - A private `_project(String id, String eventLabel)` helper:
        re-fetches via `_inner.getTicketById(id)`, no-ops if `null`,
        otherwise calls `_projector.project(ticket, _rootPath, eventLabel)`.
      - Every other `TicketRepository` method (`getAllTickets`,
        `getTicketById`, `getTicketByTicketId`, `importTicket`,
        `updateStatusForIds`'s sibling `updatePriorityForIds`,
        `updateTicket`, `addTimeSpent`, `applyEstimationSuggestion`,
        `updateEmbedding`, `updateSyncStatus`, `updateRollup`,
        `trashTickets`, `previewTrashCount`,
        `permanentlyDeleteTicket`, `permanentlyDeleteTickets`,
        `emptyTrash`, `purgeTrashOlderThan`, `getTrashedTickets`,
        `searchTickets`, `getTicketsByParent`, `getAllTicketsByType`,
        `getExecutionTokenTotals`, `applyTokenPrediction`): one-line
        pass-through to `_inner`, no projection.
      - Class-level dartdoc explains the decorator's purpose and links
        to design.md's method-coverage rationale (which methods
        project and why the rest deliberately don't — cite
        `specs/tickets.md`'s Git projection section for the boundary).
        File header comment per project convention.
