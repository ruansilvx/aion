# Design: Overlay Menu Item Keyboard Focus

No `Cubit`/BLoC changes — this is a pure presentation-layer widget
change. No new state, no new repository/DAO calls, no schema change.

## 1. New widget: `OverlayMenuItem`

`aion/lib/design_system/molecules/overlay_menu_item.dart`

```dart
class OverlayMenuItem extends StatefulWidget {
  const OverlayMenuItem({
    super.key,
    required this.child,
    required this.onTap,
    required this.semanticsLabel,
    this.restingColor,
  });

  /// The row's own already-built, already-padded content (icon+label
  /// `Row`, etc.) — this widget adds no padding/layout of its own.
  final Widget child;

  /// Called on tap, Enter, or Space.
  final VoidCallback onTap;

  /// Announced by `Semantics(button: true)`.
  final String semanticsLabel;

  /// The idle-state background when neither hovered, focused, nor
  /// pressed — `null` (transparent) for a plain row; a caller-supplied
  /// tint (e.g. `_PromoteRootRow`'s "suggested" accent tint) for a row
  /// that already carries its own resting-state emphasis. Hover/focus/
  /// pressed states always override this, same as they override
  /// transparent.
  final Color? restingColor;

  @override
  State<OverlayMenuItem> createState() => _OverlayMenuItemState();
}

class _OverlayMenuItemState extends State<OverlayMenuItem> {
  bool _isHovered = false;
  bool _isFocused = false;
  bool _isPressed = false;

  @override
  Widget build(BuildContext context) {
    final c = ThemeScope.of(context).colors;
    final fill = _isPressed
        ? c.border
        : (_isHovered || _isFocused)
            ? c.surfaceHover
            : widget.restingColor;

    return Semantics(
      button: true,
      label: widget.semanticsLabel,
      child: MouseRegion(
        cursor: SystemMouseCursors.click,
        onEnter: (_) => setState(() => _isHovered = true),
        onExit: (_) => setState(() => _isHovered = false),
        child: FocusableActionDetector(
          actions: {
            ActivateIntent: CallbackAction<ActivateIntent>(
              onInvoke: (_) {
                widget.onTap();
                return null;
              },
            ),
          },
          onShowFocusHighlight: (v) => setState(() => _isFocused = v),
          child: GestureDetector(
            onTap: widget.onTap,
            onTapDown: (_) => setState(() => _isPressed = true),
            onTapUp: (_) => setState(() => _isPressed = false),
            onTapCancel: () => setState(() => _isPressed = false),
            child: DecoratedBox(
              decoration: BoxDecoration(color: fill),
              child: widget.child,
            ),
          ),
        ),
      ),
    );
  }
}
```

This is exactly `TicketOverflowMenu`'s own trigger button's
`MouseRegion` → `FocusableActionDetector` → `GestureDetector` nesting
(`ticket_overflow_menu.dart:236-280`) and three-state fill formula
(`ticket_overflow_menu.dart:217-221`), generalized to take arbitrary
`child` content and an `onTap` instead of the trigger's own hardcoded
`_toggleOverlay`. No border radius, no box shadow, no `AnimatedContainer`/
`AnimatedScale` (those are the trigger *button*'s own polish, not
required here — a plain `DecoratedBox` swap is enough for a flat list
row, matching `AppDropdown`'s existing item-row fill pattern, which is
also an unanimated plain `Container(color: ...)`).

Deliberately no focus ring / box-shadow glow: hover and keyboard focus
render identically (`c.surfaceHover`) rather than each getting a
distinct visual, since inside a small, single-column list of rows,
"this row is highlighted" is the only information that matters — which
input method produced the highlight isn't. Skipping the ring also
avoids a second surface (the ring's `spreadRadius`) fighting the row's
existing padding/adjacent-row spacing.

## 2. `TicketOverflowMenu` integration (`ticket_overflow_menu.dart`)

**`_MenuActionRow`** (Delete ticket) — today:

```dart
Semantics(
  button: true,
  label: label,
  child: GestureDetector(
    onTap: onTap,
    child: Padding(/* icon + label Row */),
  ),
)
```

Becomes:

```dart
OverlayMenuItem(
  onTap: onTap,
  semanticsLabel: label,
  child: Padding(/* icon + label Row, unchanged */),
)
```

`OverlayMenuItem` now owns the `Semantics` wrapper — `_MenuActionRow`
stops building its own.

**`_PromoteRootRow`** — today wraps its `Padding` content in its own
`DecoratedBox(decoration: BoxDecoration(color: suggested ?
c.accentTint(accent, t.isDark) : null))` for the "Suggested" resting
tint, itself inside `Semantics` + `GestureDetector`. Becomes:

```dart
OverlayMenuItem(
  onTap: onTap,
  semanticsLabel: label,
  restingColor: suggested ? c.accentTint(accent, t.isDark) : null,
  child: Padding(/* icon + label + optional _SuggestedPill Row, unchanged */),
)
```

The row's own `DecoratedBox`/`suggested` ternary is deleted —
`OverlayMenuItem`'s `restingColor` param now owns that decision;
`_PromoteRootRow` just computes and passes the color through.

**`_PromoteChooser`**'s "Create new epic/bug" row — today the same
`Semantics` + `GestureDetector` + `Padding` shape as `_MenuActionRow`.
Same `OverlayMenuItem` swap, `restingColor: null`. The "Link to
existing" row and `_ChooserHeader`'s back-caret button are unchanged
(see `proposal.md`'s Out of scope).

## 3. `SelectionMenu<T>` integration (`selection_menu.dart`)

Today (`selection_menu.dart:152-175`), each selectable item is:

```dart
GestureDetector(
  onTap: () {
    widget.onSelected(item);
    _removeOverlay();
  },
  child: Padding(
    padding: const EdgeInsets.symmetric(vertical: 9, horizontal: 13),
    child: builder != null
        ? builder(context, c, item)
        : Text(widget.itemLabel(item), /* ... */),
  ),
)
```

Becomes:

```dart
OverlayMenuItem(
  onTap: () {
    widget.onSelected(item);
    _removeOverlay();
  },
  semanticsLabel: widget.itemLabel(item),
  child: Padding(
    padding: const EdgeInsets.symmetric(vertical: 9, horizontal: 13),
    child: builder != null
        ? builder(context, c, item)
        : Text(widget.itemLabel(item), /* ... */),
  ),
)
```

`widget.itemLabel` is a required, non-optional constructor param on
`SelectionMenu<T>` independent of the optional `itemBuilder` (see
`selection_menu.dart:29`/`47`), so it's always available as
`semanticsLabel` regardless of which visual a given caller renders —
every existing `SelectionMenu<T>` consumer (priority/type/status/
complexity pickers, automation-confidence pickers, model-routing
dropdowns, the ticket-link-type picker) picks this fix up automatically
with zero consumer-side edits.

## 5. Focus traversal

None of the four call sites need a `FocusTraversalGroup` added. Each
overlay's list is a plain `Column` of siblings; Flutter's default
`ReadingOrderTraversalPolicy` already Tabs through sibling
`FocusableActionDetector`s in the order they appear in the widget tree,
which matches each list's visual top-to-bottom order exactly.

## 6. Pre-existing cosmetic edge case (not fixed here)

None of the three menus' overlay panels wrap their item `Column` in a
`ClipRRect`, even though the panel's own `DecoratedBox` has a rounded
`borderRadius: AionRadius.lg`. A full-bleed row fill (this change's
`c.surfaceHover`/`c.border`, or the pre-existing `suggested` tint) can
therefore theoretically render past the panel's rounded corner on the
very first/last row. This already exists today for `_PromoteRootRow`'s
`suggested` tint and is not introduced by this change; adding
`ClipRRect` to three separate overlay shells to fully close it is out
of scope (see `proposal.md`'s Out of scope).

# Aion — Overlay Menu Item: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing` by name. **No Material widgets or types anywhere** — `OverlayMenuItem` is built from `flutter/widgets.dart` primitives only: `FocusableActionDetector` (focus + hover + shortcut/activation in one), `MouseRegion`, `GestureDetector`, `AnimatedContainer`, `DecoratedBox`, `Semantics`. No `InkWell`, `ListTile`, `PopupMenuItem`, or any `material.dart` import.

Adds keyboard focus, `Enter`/`Space` activation, and hover/focus/pressed visual feedback to the individual rows inside three already-shipped overlay menus — `TicketOverflowMenu`, `SelectionMenu<T>`, and `MoveToStatusMenu`. Today those menus open with mouse or keyboard, but their rows are mouse-only: no hover fill, no focus ring, no Tab/Enter reachability. This is **one new shared primitive** applied to existing row layouts. No new screens, no new navigation.

**New tokens required: none.** Every fill is an existing token or a documented derivation reusing an existing pattern (`fillAlpha`, `accentTint`, the `fillAlpha × 1.6` pressed wash from Ticket Deletion §2.2, and the `surface → surfaceHover → border` raised-surface progression the overflow trigger already uses). `c` = active `AionColors`; `a` = theme `fillAlpha` (Arctic `0.11` / Obsidian `0.16`); `isDark` = Obsidian. Both themes share one code path; only token values differ.

Companion mockups: `Aion Overlay Menu Item Mockups.dc.html` — plain-row context (Delete ticket, AIO-12) `1a`, suggested-tinted-row context (Promote to Epic, AIO-31) `2a`, each in Arctic and Obsidian across all four states.

## 1. `OverlayMenuItem` — the primitive

A single row wrapper. It owns **only** interaction state and the fill it paints behind its child; it adds **no padding, size, layout, or content of its own**. The caller passes the existing row body (icon + label, icon + label + pill, or a plain label) as `child`, and the existing per-menu padding is preserved exactly (see §4).

### 1.1 Structure

```
FocusableActionDetector( // focus node, autofocus, onShowHoverHighlight, onShowFocusHighlight, shortcuts+actions
  → MouseRegion(cursor: SystemMouseCursors.click)
    → GestureDetector(onTapDown/onTapUp/onTapCancel → _pressed, onTap → onActivate)
      → AnimatedContainer(duration: 100ms, curve: Curves.easeOut, decoration: BoxDecoration(color: _fill))
        → child   // the existing row body, unchanged
)
```

- **Focus / activation:** `FocusableActionDetector` supplies the `FocusNode`, participates in the ambient `FocusTraversalGroup` (so `Tab`/`Shift+Tab` walk the rows in visual order), and binds `ActivateIntent` (`Enter` and `Space`) to a callback that runs `onActivate` — identical behavior to a mouse tap. On open, the menu autofocuses its **first** enabled row (`autofocus: true` on row 0) so keyboard users land inside immediately.
- **Hover:** `onShowHoverHighlight` toggles `_hovered`.
- **Pressed:** `GestureDetector` `onTapDown` → `_pressed = true`; `onTapUp` / `onTapCancel` → `_pressed = false`. While `Enter`/`Space` is held, the `ActivateAction` sets `_pressed` for the key-down duration so held-key feedback matches mouse-down.
- **Semantics:** wrap in `Semantics(button: true, label: <row label>, enabled: <enabled>)` so screen readers announce each row as an actionable button.

**Implementation note (added post-`/verify`):** the shipped nesting is
`Semantics → Focus(key-down/up tracking, canRequestFocus: false,
skipTraversal: true) → MouseRegion(cursor, onEnter/onExit → _hovered)
→ FocusableActionDetector(actions: {ActivateIntent: ...},
onShowFocusHighlight → _focused) → GestureDetector(onTapDown/onTapUp/
onTapCancel → _pressed, onTap) → AnimatedContainer`, not the
`FocusableActionDetector → MouseRegion → GestureDetector →
AnimatedContainer` order sketched above. Two differences, both
deliberate:

1. **`MouseRegion` wraps `FocusableActionDetector`, not the reverse.**
   This matches `TicketOverflowMenu`'s own trigger button's *actual*
   nesting (`ticket_overflow_menu.dart:236-250`) — the precedent this
   section's own prose says to mirror — using a plain `onEnter`/`onExit`
   `MouseRegion` for `_hovered` rather than
   `FocusableActionDetector.onShowHoverHighlight`, since the latter's
   input-modality suppression logic is meant for focus rings, not
   plain mouse-hover feedback.
2. **An extra bubbling `Focus` wrapper handles the held-key pressed
   state**, since a single `CallbackAction<ActivateIntent>.onInvoke`
   fires once per activation and can't express a held-duration press
   the way `GestureDetector`'s `onTapDown`/`onTapUp` do for the mouse.
   It sits above `MouseRegion`/`FocusableActionDetector` in the tree
   but doesn't request focus itself (`canRequestFocus: false`) — it
   only listens for `KeyDownEvent`/`KeyUpEvent` on `Enter`/`Space`/
   `NumpadEnter` as they bubble up from whichever row actually holds
   focus, always returning `KeyEventResult.ignored` so the real
   `ActivateIntent` binding below still fires normally.

Verified equivalent to the sketch above via a `WidgetTester` check
during `/apply`: autofocus paints the correct fill, `Enter` fires
`onTap`, and `Tab` moves the fill from row to row.

### 1.2 Fill inputs

`OverlayMenuItem` takes an optional **`accent`** color and a **`restingTinted`** flag:

| Row | `accent` | `restingTinted` |
|---|---|---|
| Neutral (SelectionMenu item, MoveToStatus item, "Create new epic", Promote-to-X when **not** the suggested target) | `null` | `false` |
| Destructive ("Delete ticket") | `c.danger` | `false` |
| Suggested Promote-to-Epic / Promote-to-Bug (`_PromoteRootRow` when it is the AI's suggested target) | `c.typeEpic` / `c.typeBug` | `true` |

### 1.3 Fill by state

Resolved every build from `_hovered`, `_focused`, `_pressed`. Focus and hover paint the **same** fill (see §1.4). Priority: pressed → (hover **or** focus) → resting.

**Neutral rows (`accent == null`)** — the standard raised-surface progression (same three shades the overflow trigger button steps through):

| State | Fill |
|---|---|
| Default | `Colors.transparent` |
| Hover | `c.surfaceHover` |
| Focused | `c.surfaceHover` (same as hover) |
| Pressed | `c.border` |

**Accented rows (`accent != null`)** — a wash of the row's own accent, one step per state; `restingTinted` only changes the *default* fill:

| State | Fill |
|---|---|
| Default, `restingTinted: false` | `Colors.transparent` |
| Default, `restingTinted: true` | `accent.withOpacity(c.accentTint(...))` = `accent @ 0.06 / 0.09` (existing `_PromoteRootRow` resting tint) |
| Hover | `accent.withOpacity(a)` (`0.11 / 0.16`) |
| Focused | `accent.withOpacity(a)` (same as hover) |
| Pressed | `accent.withOpacity(a * 1.6)` (`0.176 / 0.256`) — same pressed-wash multiplier as Ticket Deletion §2.2 |

Because hover/pressed reuse the *accent's own hue*, an accented row's states read as the same color deepening step by step — never a hue change. For a **suggested** row this means the resting `accentTint` (`0.06/0.09`) → hover `fillAlpha` (`0.11/0.16`) → pressed (`0.176/0.256`) is a clean three-stop deepen of the exact tint already sitting there: hover/focus **replace** the resting tint with a stronger value of the same color, they do not blend a second hue over it. (§2 answers the "replace or blend" question explicitly.)

### 1.4 Focus treatment — fill only, no ring (confirmed)

Per the brief, keyboard focus paints the **same fill as hover** with **no separate focus ring**. This is a deliberate departure from the ad-hoc inset ring the shipped Ticket Deletion Spec §2.2 gave its delete row — `OverlayMenuItem` supersedes that and standardizes all three menus on fill-only focus.

**Confirmation that fill-only reads as clearly highlighted at both row scales:**
- The highlight is a **full-bleed, full-row-width wash** (the row is edge-to-edge inside the container — see §1.5), not a subtle 1–2px change. It covers ~34px (the compact Delete-ticket row, 16px icon + 9px vertical padding) and the taller ~40px SelectionMenu / `_PromoteRootRow` rows equally, so the cue does not shrink with content.
- Only **one** row can be focused at a time, and hover + keyboard focus effectively never co-occur (keyboard-only users produce no hover), so a "focused vs merely hovered" ambiguity never arises in practice — the wash is the single, unambiguous "this row is armed" signal for both input modes.
- Contrast holds in both themes: `surfaceHover` (`#E4EDF6` / `#1C2436`) and the `fillAlpha` accent washes are the same values the app already relies on to signal raised/hovered surfaces elsewhere, and are legible against `surface` (`#FBFCFE` / `#131A29`).

The one caveat worth a reviewer's eye: a fill-only focus offers no cue for a low-vision user who needs a hard edge. If accessibility testing later flags it, the additive fix is a `1px` inset ring `c.primary.withOpacity(isDark ? 0.30 : 0.16)` (the app's standard ring opacity) drawn *inside* the wash — no layout change. It is **not** part of this spec's baseline.

### 1.5 Geometry the primitive assumes (not its own decisions)

- **Fill shape:** full row width, **no corner radius** — rows sit flush to the container's inner edges. The menu container carries `clipBehavior: Clip.antiAlias` with its own `AionRadius.lg` (12) corners, so the first and last rows' outer corners are clipped to the container radius automatically; interior rows are plain rectangles.
- **Padding:** none added by `OverlayMenuItem`. Preserved from each caller (§4).
- **Border / shadow:** none — the row never draws a border or shadow; those belong to the menu container.

### 1.6 Transition — 100ms fill fade (decided)

All fill changes (default ↔ hover/focus ↔ pressed) animate via the `AnimatedContainer` in §1.1: **`duration: 100ms`, `curve: Curves.easeOut`**, animating `decoration.color` only.

Rationale for matching the `TicketOverflowMenu` trigger's 100ms fade rather than staying instant like `AppDropdown`'s current rows: the trigger button and the rows it opens live in the **same** popover surface, so an animated trigger feeding into instant rows would read as two different interaction languages inside one menu. 100ms is short enough that the held-press wash still feels immediate (the fade completes well within a tap-and-hold). The unanimated `AppDropdown` rows are the outlier to be brought in line, not the precedent to match.

## 2. Context: plain row (e.g. "Delete ticket")

The primitive wraps the existing row body **unchanged**. Reference: `TicketOverflowMenu` "Delete ticket".

### 2.1 Row body (unchanged from today)

- Layout: `Row`, `gap: 10`, `crossAxisAlignment: center`.
- Leading icon: `PhosphorIcons.trashLight`, **16px**, color `c.danger`.
- Label: `"Delete ticket"`, `AionText.bodySm` with `fontWeight: FontWeight.w600`, color `c.danger`.
- Padding (from caller, preserved): `EdgeInsets.symmetric(horizontal: 13, vertical: 9)` → row height ≈ 34.

### 2.2 States (`accent: c.danger`, `restingTinted: false`)

| State | Fill | Icon | Label |
|---|---|---|---|
| **Default** | transparent | `trashLight` 16px `danger` | `bodySm` w600 `danger` |
| **Hover** | `danger.withOpacity(a)` (`0.11 / 0.16`) | unchanged | unchanged |
| **Focused** | `danger.withOpacity(a)` (same as hover) | unchanged | unchanged |
| **Pressed** | `danger.withOpacity(a * 1.6)` (`0.176 / 0.256`) | unchanged | unchanged |
| **Disabled** | transparent, whole row `opacity: 0.45`, cursor `basic`, no focus stop | dimmed | dimmed |

**Fill vs. the danger-red content:** the danger washes (`0.11–0.256` opacity of `danger`) sit far below the full-strength `danger` icon/label, so the tint never muddies or lowers contrast against the red text at any state — it reads as a rose backing plate behind red content, in both themes. (Verified in the companion mockups, `1a`.)

## 3. Context: tinted "suggested" row (e.g. "Promote to Epic")

Reference: `_PromoteRootRow`. Two resting appearances — not-suggested (transparent) and suggested (accent-tinted + trailing "Suggested" pill) — sharing one set of interactive states.

### 3.1 Row body

- Layout: `Row`, `gap: 10`, center; leading icon then label, trailing pill only when suggested (pushed right via `Spacer` / `mainAxisAlignment` per existing `_PromoteRootRow`).
- Leading icon: **16px** — `c.textSecondary` when not suggested; the accent (`c.typeEpic` / `c.typeBug`) when suggested (existing behavior, unchanged).
- Label: `"Promote to Epic"` / `"Promote to Bug"`, `AionText.bodySm` `fontWeight: w600`, color `c.textPrimary`.
- **"Suggested" pill** (suggested only, unchanged from today): `AionText.chip` (Manrope 10.5 / w700), UPPERCASE `"SUGGESTED"`, text color = accent, fill = `accent.withOpacity(c.accentTint(...))`, padding `EdgeInsets.symmetric(horizontal: 6, vertical: 2)`, radius `AionRadius.sm` (6).
- Padding (from caller, preserved): the `_PromoteRootRow` menu's existing row padding — for the `TicketOverflowMenu` host, `EdgeInsets.symmetric(horizontal: 13, vertical: 9)`.

### 3.2 States — not suggested (`accent: c.typeEpic`/`typeBug`, `restingTinted: false`)

Identical progression to §2.2 but with the type accent instead of danger, and content colors per §3.1 (`textSecondary` icon / `textPrimary` label):

| State | Fill |
|---|---|
| Default | transparent |
| Hover / Focused | `accent.withOpacity(a)` |
| Pressed | `accent.withOpacity(a * 1.6)` |
| Disabled | transparent, `opacity: 0.45` |

### 3.3 States — suggested (`accent: c.typeEpic`/`typeBug`, `restingTinted: true`)

| State | Fill | Interaction with the resting tint |
|---|---|---|
| **Default (suggested)** | `accent.withOpacity(c.accentTint)` = `accent @ 0.06 / 0.09` | the resting suggested tint, as today |
| **Hover** | `accent.withOpacity(a)` (`0.11 / 0.16`) | **replaces** the resting tint with a stronger value of the **same** accent hue — not a blend, not a second color layered on |
| **Focused** | `accent.withOpacity(a)` (same as hover) | same replace |
| **Pressed** | `accent.withOpacity(a * 1.6)` (`0.176 / 0.256`) | deepest stop of the same hue — again a replace, not a blend |
| **Disabled (suggested)** | resting tint, whole row `opacity: 0.45` | pill dims with the row |

The pill (icon-accent text on `accentTint`) stays put through every state; the wash deepening behind it never collides with it because both derive from the same accent, so the pill remains the lighter chip against a slightly stronger row wash.

## 4. Existing padding preserved per host (not `OverlayMenuItem`'s decision)

`OverlayMenuItem` adds no padding; each menu keeps its current row padding, applied **inside** the wrapper's `child`:

| Host menu | Row padding (unchanged) |
|---|---|
| `TicketOverflowMenu` | `EdgeInsets.symmetric(horizontal: 13, vertical: 9)` |
| `MoveToStatusMenu` | `EdgeInsets.symmetric(horizontal: 14, vertical: 10)` |
| `SelectionMenu<T>` | its existing per-instance padding (unchanged) |

Dividers between groups (e.g. above "Delete ticket") are the host menus' existing separators and are **not** wrapped by `OverlayMenuItem` — they are non-interactive and take no focus stop.

## 5. State summary

| Row kind | Default | Hover | Focused | Pressed | Disabled |
|---|---|---|---|---|---|
| **Neutral** (SelectionMenu / MoveToStatus item, non-suggested Promote) | transparent | `surfaceHover` | `surfaceHover` (= hover) | `border` | transparent, `opacity 0.45` |
| **Destructive** (Delete ticket) | transparent | `danger @ a` | `danger @ a` (= hover) | `danger @ a×1.6` | transparent, `opacity 0.45` |
| **Suggested Promote** (tinted + pill) | `accent @ accentTint` | `accent @ a` | `accent @ a` (= hover) | `accent @ a×1.6` | resting tint, `opacity 0.45` |
| **Non-suggested Promote** | transparent | `accent @ a` | `accent @ a` (= hover) | `accent @ a×1.6` | transparent, `opacity 0.45` |

- **Focus = hover fill, no ring** (§1.4, confirmed).
- **Transition:** 100ms `Curves.easeOut` fill fade on every state change (§1.6, decided).
- **Tokens:** no new `AionColors`, `AionText`, `AionRadius`, or `AionSpacing` members. Fills use existing `surfaceHover`, `border`, `danger`, `typeEpic`, `typeBug`; the `accentTint(accent, isDark)` helper (`0.06/0.09`); `fillAlpha` (`0.11/0.16`); and the `fillAlpha × 1.6` pressed wash (Ticket Deletion §2.2). Translucent fills always `token.withOpacity(x)` — never hardcoded ARGB.
