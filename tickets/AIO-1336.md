# Spec delta: New-project onboarding — Inbox

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/providers.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (18/20 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Delta against `aion-arch/specs/tickets.md` and
`aion-arch/specs/providers.md`.

## ADDED behaviors

### Inbox nav destination (tickets.md — Persistent navigation shell)

- `WorkspaceNavShell` gains a third top-level destination, Inbox,
  alongside Tickets and Documentation, in both the wide sidebar and
  compact bottom-tab-bar layouts. `/workspace/inbox` resolves to it.
  Inbox-spawned `chat` tickets still render via the existing
  `/workspace/tickets/:id` route and resolve to the Tickets
  destination, not Inbox.

### `InboxScreen` and Inbox history (tickets.md)

- A new `/workspace/inbox` screen: a four-purpose launcher (brain-dump,
  what-next guidance, release planning, general Q&A) above a
  reverse-chronological history list of past Inbox-spawned chats, each
  tagged with a purpose badge. Empty state shown when no Inbox chat has
  ever been launched. No search, no grouping/tabs by purpose (single
  flat list) — deferred until there's evidence a longer history needs
  it.
- Every launch creates a fresh, purpose-specific `chat` ticket with
  `parentId: null` and a new `inboxPurpose` field set to the launched
  purpose — no auto-recall of any other Inbox chat's content as
  context, matching the existing fresh-context-per-purpose pattern
  SDD-stage chats already use.

### Brain-dump-to-tickets purpose (tickets.md)

- User supplies raw, unstructured text; the chat classifies it into one
  or more `signal` tickets, each carrying a new `suggestedType` field
  (`epic` or `bug`) reflecting the model's classification.

### What-next guidance purpose (tickets.md)

- Advisory-only chat porting the CLI `/what-next` skill's priority
  order (in-flight SDD-stage tickets, then Documentation Pages' "Known
  gaps" sections, then open `signal` tickets) onto ticket/page data. No
  ticket creation.

### Release planning purpose (tickets.md)

- Conversational chat with read-only access to existing
  Epic/Story/Task/Bug tickets; on conclusion, creates a new `release`
  ticket and `relatesTo` links to whichever tickets the conversation
  settled on — not a read-only report.

### General Q&A purpose (tickets.md)

- Free-form chat with real read access to tickets, docs, and the
  project's source code. The opening turn only runs tool-enabled inside
  a throwaway, isolated git worktree (never the user's real working
  tree), prompt-instructed to be read-only; the worktree is discarded
  immediately after. Every subsequent human reply in the same chat is
  an ordinary, non-tool-enabled conversational turn.

### Widened signal promotion (tickets.md)

- `TicketsCubit.promoteSignalToEpic` is renamed to `promoteSignal` and
  gains a required `targetType` parameter (`epic` or `bug`), replacing
  the previous Epic-only behavior. The promote-chooser UI
  (`TicketOverflowMenu`) offers both targets, pre-selecting whichever
  matches the signal's `suggestedType` when set.

### `Ticket.suggestedType` / `Ticket.inboxPurpose` fields (tickets.md)

- Two new nullable `Ticket` fields, drift schema version 8.
  `suggestedType` is meaningful only on `signal` tickets (brain-dump
  output). `inboxPurpose` is meaningful only on Inbox-spawned `chat`
  tickets.

## MODIFIED behaviors

### `ChatCubit._phaseForChat` (tickets.md)

- Gains a first-checked branch: a chat ticket with a non-null
  `inboxPurpose` resolves its `ModelPhase` directly from a
  purpose→phase mapping (brain-dump/what-next/release-planning →
  `frontier`, Q&A → `capable`), never consulting `parentId`. Every
  existing (non-Inbox) chat's resolution path — parent walk, then the
  defensive `capable` fallback — is unchanged.

### `TicketsCubit.updateTicketParent` (tickets.md)

- Gains an additional rejection condition alongside the existing
  `ticket.type.isAlwaysRoot` check: also rejects setting a non-null
  parent when `ticket.type == TicketType.chat && ticket.inboxPurpose !=
  null`. Every other ticket's reparent behavior is unchanged.

## Non-goals / explicitly not built

- No real read-only `allowedTools` subset in `agent_bridge/index.mjs`
  — Q&A's tool access remains prompt-instructed and worktree-isolated,
  the same informal pattern codebase-summarization already uses.
- No embedding-based search over Inbox history.
- No `AutomationConfidence` gating anywhere in the Inbox — every launch
  is human-initiated.
- No change to `TicketTypeHierarchy.isAlwaysRoot` — `chat` is not added
  to it; the per-instance `inboxPurpose` field carries the exception
  instead (see MODIFIED above).
