# Design: Ticket Link Count Excludes Trashed

## Architecture

No new widgets, no new BLoC states, no new repository methods, no schema
migration. This is a data-layer-only fix confined to `TicketLinkDao`.
`DriftTicketLinkRepository.getLinksForTicket` and the domain
`TicketLinkRepository.getLinksForTicket` interface keep their exact
signatures — `LinkCountLabel` needs no change at all; it just starts
receiving a correct list.

Per `project.md`'s state-management convention, this is deliberately
**not** a Cubit-level fix. Excluding rows whose other endpoint is
soft-deleted is a plain read filter — the same category of thing
`TicketDao.getAllTickets()` already does with
`..where((t) => t.deletedAt.isNull())` — not a validation rule or
invariant check. Repositories/DAOs stay the right layer for it; no
`LinksCubit` exists or is being introduced here.

## DAO change

`TicketLinkDao` (`aion/lib/features/tickets/data/daos/ticket_link_dao.dart`)
currently declares only `TicketLinksTable`:

```dart
@DriftAccessor(tables: [TicketLinksTable])
class TicketLinkDao extends DatabaseAccessor<AppDatabase>
    with _$TicketLinkDaoMixin {
```

It gains `TicketsTable` so it can join against `deleted_at`:

```dart
@DriftAccessor(tables: [TicketLinksTable, TicketsTable])
class TicketLinkDao extends DatabaseAccessor<AppDatabase>
    with _$TicketLinkDaoMixin {
```

`getLinksForTicket` changes from a single unfiltered `OR` query to two
joined queries (source-side and target-side), each filtered on the
*other* ticket's `deletedAt`, concatenated and deduplicated by id:

```dart
/// Returns every link where [ticketId] is the source or the target, and
/// the *other* ticket in the link is not currently trashed. A link to a
/// trashed ticket reappears automatically once that ticket is restored,
/// and disappears for good once it's permanently deleted (which
/// cascade-deletes the link row itself via [deleteLinksForTickets]) — so
/// this filter only affects the interim window while the other ticket
/// sits in Trash. Deduplicated by [TicketLinkData.id]: a self-link (a
/// ticket linked to itself) would otherwise match both the source-side
/// and target-side query below and be returned twice.
Future<List<TicketLinkData>> getLinksForTicket(String ticketId) async {
  final asSource = await (select(ticketLinksTable).join([
        innerJoin(
          ticketsTable,
          ticketsTable.id.equalsExp(ticketLinksTable.targetTicketId),
        ),
      ])
        ..where(
          ticketLinksTable.sourceTicketId.equals(ticketId) &
              ticketsTable.deletedAt.isNull(),
        ))
      .map((row) => row.readTable(ticketLinksTable))
      .get();

  final asTarget = await (select(ticketLinksTable).join([
        innerJoin(
          ticketsTable,
          ticketsTable.id.equalsExp(ticketLinksTable.sourceTicketId),
        ),
      ])
        ..where(
          ticketLinksTable.targetTicketId.equals(ticketId) &
              ticketsTable.deletedAt.isNull(),
        ))
      .map((row) => row.readTable(ticketLinksTable))
      .get();

  final byId = <String, TicketLinkData>{};
  for (final link in [...asSource, ...asTarget]) {
    byId[link.id] = link;
  }
  return byId.values.toList();
}
```

`insertLink` and `deleteLinksForTickets` are unchanged.

### Why two joined queries instead of one `CASE`-based join

Drift's typed query builder doesn't offer a fluent way to join on "target
if I matched as source, else source" in one `equalsExp` — that needs a
`CASE` expression inside the join condition, which would mean dropping to
`customSelect`/raw SQL. Two separate equi-joins (source→other-is-target,
target→other-is-source) concatenated in Dart stays inside the typed API,
matches this DAO's existing style (`getAllTickets`, `getTrashedTickets`
etc. are all typed `select()..where()` chains, no raw SQL), and is
trivially testable.

### Why the concatenated result needs deduplication

The two `WHERE` branches overlap for exactly one case: a self-link, where
a single `ticket_links` row has `source_ticket_id == target_ticket_id ==
ticketId`. That row matches the source-side query's `WHERE` (source
equals `ticketId`) *and* the target-side query's `WHERE` (target equals
`ticketId`) independently, so it would appear twice in the naive
concatenation — a regression from the original single-query
implementation, which returned it once. Nothing in the stack actually
prevents a self-link from being created: `TicketLinkRepository.createLink`
and `TicketLinkDao.insertLink` are deliberately unvalidated (repositories
stay dumb per `project.md`'s convention), and no `LinksCubit` exists yet
to reject one at a higher layer. So rather than assume self-links can't
happen, the result is deduplicated by `TicketLinkData.id` (a `Map<String,
TicketLinkData>` keyed by id, then `.values.toList()`) — cheap, and
correct regardless of whether a self-link, or any other overlap, is ever
possible. Every other combination of source/target rows is naturally
non-overlapping between the two queries, so this only ever collapses a
genuine duplicate.

## Test plan

No standalone DAO test file exists today, and none is introduced here.
The established pattern in this codebase (confirmed in
`aion/test/features/tickets/data/repositories/drift_ticket_repository_test.dart`,
e.g. its `permanentlyDeleteTicket / emptyTrash` group at line 498) is to
exercise `TicketLinkDao` indirectly through `DriftTicketLinkRepository`
inside that same shared-database test file — it already sets up
`database = AppDatabase(NativeDatabase.memory())` in `setUp`, already
imports `DriftTicketLinkRepository`, and already instantiates
`linkRepository = DriftTicketLinkRepository(database)` inline within a
test. This is exactly the kind of persistence-behavior test
`project.md`'s testing section calls out as warranting a real drift
instance rather than a mocktail mock, and reusing the existing file keeps
the new coverage next to the closely-related trash/cascade tests it
depends on for context.

A new group, `getLinksForTicket excludes trashed`, is added to that same
file (after the `permanentlyDeleteTicket / emptyTrash` group). Cases:
1. Link between two live tickets — counted (returned) from both the
   source's and the target's `getLinksForTicket` call.
2. Link where the *other* ticket is trashed (`deletedAt` non-null) —
   excluded from the live ticket's `getLinksForTicket` result.
3. Restoring the trashed ticket (`deletedAt` back to `null`) — the link
   reappears in a subsequent `getLinksForTicket` call, with no other
   write needed (confirms the "self-corrects on restore" claim in the
   known-gaps bullet being resolved).
4. A ticket with no links — returns an empty list (existing zero-count
   behavior, unchanged).
5. A ticket linked as both source in one row and target in another —
   both are returned (confirms the source-side and target-side queries
   both contribute correctly and nothing is double-counted or dropped).
6. A self-link (`sourceTicketId == targetTicketId == ticketId`) —
   returned exactly once, not twice (confirms the id-based dedup in
   "Why the concatenated result needs deduplication" above).
