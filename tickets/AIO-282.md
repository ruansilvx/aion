# Design: barrel-files

## The rule that governs everything below

**A directory's own files never import their own barrel.** Every other
consumer — a sibling subdirectory, another feature, `main.dart`,
`test/` — imports through the barrel instead of reaching past it into
individual files.

This is what keeps the barrels from becoming pointless indirection or
import cycles: `core/theme/aion_shadows.dart` importing
`aion_colors.dart` directly is unaffected by this change (it's internal
to the directory `design_system.dart` represents), but
`core/widgets/app_button.dart` — a *sibling* of `core/theme/`, not an
owner of it — switches to `import 'package:aion/core/design_system.dart';`
for the same tokens. Same logic one level up: nothing inside
`features/tickets/` imports `features/tickets/tickets.dart`; every file
in `main.dart`, `app_router.dart`, `app_database.dart`, and `test/` that
currently reaches into `features/tickets/domain/` or
`features/tickets/presentation/` does, once those symbols are in the
barrel's scope.

## The three barrels

### 1. `lib/core/design_system.dart`

```dart
// design_system.dart — Design-system barrel: theme tokens and ThemeScope (core layer).

export 'theme/aion_colors.dart';
export 'theme/aion_radius.dart';
export 'theme/aion_shadows.dart';
export 'theme/aion_text.dart';
export 'theme/aion_theme.dart';
export 'theme/theme_scope.dart';
```

No files move — `core/theme/*.dart` stays exactly where it is. This is
the one carve-out called out explicitly: it gets its own barrel
*separate from* `core.dart`, not folded into it, because design tokens
are imported by nearly every presentation-layer file in the app and
deserve a shorter, dedicated import path.

### 2. `lib/core/core.dart`

```dart
// core.dart — Barrel for core infrastructure: database, routing, localization, utils, widgets (core layer).

export 'database/app_database.dart';
export 'localization/context_localizations_x.dart';
export 'routing/app_router.dart';
export 'utils/duration_format.dart';
export 'utils/platform_utils.dart';
export 'widgets/app_button.dart';
export 'widgets/app_confirm_dialog.dart';
export 'widgets/app_dropdown.dart';
export 'widgets/app_header.dart';
export 'widgets/app_spinner.dart';
export 'widgets/app_text_field.dart';
export 'widgets/app_toast.dart';
export 'widgets/selection_menu.dart';
```

Deliberately excludes `theme/` — that's `design_system.dart`'s job, not
`core.dart`'s. The two barrels are siblings, not nested; importing
`core.dart` does **not** pull in design tokens, and vice versa. A
screen that needs both imports both.

### 3. `lib/features/tickets/tickets.dart`

```dart
// tickets.dart — Public-surface barrel for the tickets feature: domain
// entities/enums/exceptions/repository interfaces plus presentation
// cubits/states/screens/widgets. The data layer (DAOs, Drift table
// models, Drift*Repository implementations) is intentionally not
// exported — see flutter-conventions.md "Barrel files".

export 'domain/entities/ticket.dart';
export 'domain/entities/ticket_comment.dart';
export 'domain/enums/comment_author_type.dart';
export 'domain/enums/ticket_link_type.dart';
export 'domain/enums/ticket_priority.dart';
export 'domain/enums/ticket_status.dart';
export 'domain/enums/ticket_type.dart';
export 'domain/exceptions/ticket_has_children_exception.dart';
export 'domain/repositories/comment_repository.dart';
export 'domain/repositories/ticket_link_repository.dart';
export 'domain/repositories/ticket_repository.dart';
export 'presentation/cubit/comments_cubit.dart';
export 'presentation/cubit/comments_state.dart';
export 'presentation/cubit/tickets_cubit.dart';
export 'presentation/cubit/tickets_state.dart';
export 'presentation/screens/create_ticket_screen.dart';
export 'presentation/screens/ticket_detail_screen.dart';
export 'presentation/screens/tickets_board_view.dart';
export 'presentation/screens/tickets_list_screen.dart';
export 'presentation/widgets/inline_editable_field.dart';
export 'presentation/widgets/ticket_overflow_menu.dart';
```

#### Why `data/` stays unexported

`project.md`'s Key Constraint is explicit: "UI and domain code must
never depend on a concrete data source." If `tickets.dart` re-exported
`data/repositories/drift_ticket_repository.dart` alongside the
`TicketRepository` interface, nothing would stop a future screen from
writing `context.read<DriftTicketRepository>()` instead of
`context.read<TicketRepository>()` — the barrel would actively
encourage the violation it should prevent. Excluding `data/` means the
only place a concrete `Drift*Repository`/DAO/table model is reachable
at all is a direct leaf import — and the only file that legitimately
needs that is `main.dart` (the composition root that binds interface
to implementation via `RepositoryProvider`) and `core/database/app_database.dart`
(which owns wiring the DAOs/tables into the `@DriftDatabase`). Both keep
their existing direct imports into `features/tickets/data/`, unchanged
by this proposal.

This also means every *future* feature barrel follows the same
domain-plus-presentation-only shape — this isn't a `tickets`-specific
exception, it's the pattern, documented in
`flutter-conventions.md` (see tasks.md).

## What changes in existing files, and what doesn't

**Unchanged (self-import exception applies):**
- `core/theme/*.dart` internal cross-imports (`aion_shadows.dart` →
  `aion_colors.dart`, etc.)
- Every intra-`tickets` import — a screen importing a sibling screen,
  a cubit importing its state file, a repository interface importing a
  domain enum, etc. These stay direct leaf imports; barrels are for
  crossing the `core`/`design_system`/`<feature>` boundary, not for
  files talking to their own neighbors.
- `main.dart`'s and `core/database/app_database.dart`'s direct imports
  into `features/tickets/data/` (excluded from the feature barrel by
  design, see above).

**Changed — collapse to barrel imports:**
- `core/widgets/*.dart` (8 files): their `core/theme/*.dart` imports
  become one `import 'package:aion/core/design_system.dart';`. Their
  `core/localization/context_localizations_x.dart` imports stay direct
  (self-import exception — `core.dart` is `core`'s own barrel).
- `features/tickets/presentation/**/*.dart` (6 files: both screens
  under `screens/`, both widgets under `widgets/`, plus
  `create_ticket_screen.dart` and `tickets_board_view.dart`): their
  `core/theme/*` imports become `design_system.dart`; their
  `core/localization`/`core/utils`/`core/widgets` imports become
  `core.dart`.
- `main.dart`: `core/database` + `core/routing` → `core.dart`;
  `core/theme` × 2 → `design_system.dart`; the three domain repository
  interfaces + `TicketsCubit` → `tickets.dart`. The three
  `Drift*Repository` imports (data layer) stay direct.
- `core/routing/app_router.dart`: its five `features/tickets/domain`
  and `features/tickets/presentation` imports collapse to one
  `import 'package:aion/features/tickets/tickets.dart';`.
- Five files under `test/`: `duration_format_test.dart` →
  `core.dart`; `tickets_cubit_test.dart` and `ticket_test.dart` →
  `tickets.dart` entirely; the two `drift_*_repository_test.dart` files
  → `core.dart` (for `AppDatabase`) + `tickets.dart` (for domain
  symbols) + unchanged direct imports for the concrete
  `Drift*Repository` classes under test (data layer, not in the
  barrel — a test importing the thing it tests directly is correct,
  not a layering violation).
- Six data-layer files that reach for `AppDatabase` — the three DAOs
  (`data/daos/{comment_dao,ticket_dao,ticket_link_dao}.dart`) and the
  three `Drift*Repository` implementations
  (`data/repositories/drift_{comment,ticket,ticket_link}_repository.dart`)
  — switch their `core/database/app_database.dart` import to
  `core.dart`. These files are outside `core/`, so the governing rule
  ("every other consumer imports through the barrel") applies to them
  the same as it does to `core/widgets/` or a presentation screen; this
  was missed in the first apply pass and closed as a `/verify` finding.
  `features/tickets/domain/repositories/ticket_link_repository.dart`'s
  pre-existing `AppDatabase` import is deliberately **not** touched here
  — see the note below, it's a separate, out-of-scope layering issue,
  not a barrel-consistency one.

Full per-file list is in [tasks.md](tasks.md).

## Enforcement

Convention + code review, not a lint rule — matching the precedent
already set for the localization convention (`flutter-conventions.md`
"Localization" section, decided in
`changes/archive/intl-string-retrofit/`: "enforced by code review, not
a lint rule or CI check — the app is solo-dev scale, so tooling
enforcement was judged overkill"). No `custom_lint` package is added by
this change.

## Note for a future change (not in scope here)

While mapping every import for this proposal,
`features/tickets/domain/repositories/ticket_link_repository.dart` was
found to import `core/database/app_database.dart` directly and return
`TicketLinkData` (a generated Drift row type) from a domain-layer
interface — itself a version of the exact layering leak this barrel
scoping is designed to prevent, just pre-existing and un-barrel-related.
Fixing it is out of scope for barrel-files (no behavior/API changes
here), but it's worth its own change later.
