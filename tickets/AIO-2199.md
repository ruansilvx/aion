# Ticket Editing

# Proposal: Ticket Editing

## What We Are Building

In-place inline editing on `TicketDetailScreen` for a ticket's `title`,
`description`, `priority`, `type`, `estimate`, and `timeSpent`. Each field
becomes independently tappable: title/description turn into a text field in
place; priority/type open a compact overlay menu (the same interaction
`MoveToStatusMenu` already uses for status on the board); estimate/time
spent turn into a duration-formatted text field ("2h 30m"). No navigation
away from the detail screen, no separate edit form/screen. `status` and
`parentId` editing are unaffected — status stays board-only, exactly as
today.

## Why

`aion-arch/specs/tickets.md`'s "Known gaps" section: *"Ticket editing is
limited to status only, via the board... Title, description, priority,
type, and parent remain non-editable"* and *"`embedding`, `estimate`, and
`timeSpent` fields exist in the schema/entity but are not populated or
displayed anywhere."* This change closes both gaps for the fields that
matter most day-to-day (title, description, priority, type, estimate,
timeSpent), deliberately leaving `parentId` (structural, its own change)
and `embedding` (system-populated, no user-facing edit makes sense) out.

In-place editing was chosen over a separate edit screen after explicit
user direction: tickets are reopened and tweaked far more often than
created, so avoiding a navigation round-trip away from the comment thread
already visible on the detail screen matters more than the lower
implementation cost of reusing `CreateTicketScreen`'s form wholesale. See
`/opsx-explore ticket editing` session for the full comparison.

Automatic time tracking (a start/stop timer that accumulates `timeSpent`)
was explicitly deferred out of this change — see
`aion-arch/ideas/automatic-time-tracking-for-tickets.md`. `timeSpent` here
is manually editable only, same as `estimate`.

## Scope

### In

- `Ticket.copyWith(...)` widened from its current `{status, updatedAt}`-only
  form to also cover `title`, `description`, `priority`, `type`,
  `estimate`, `timeSpent`. The three nullable fields (`description`,
  `estimate`, `timeSpent`) use a nullary-function ("setter") parameter
  instead of a plain `?? this.x` fallback, so a field can be explicitly
  cleared back to `null` — a plain optional-positional `??` copyWith cannot
  distinguish "leave unchanged" from "set to null," which matters here
  because clearing an estimate/description is an expected user action.
- `TicketRepository.updateTicket(Ticket ticket)` — new general write path,
  alongside (not replacing) the existing `updateTicketStatus`.
- `TicketDao.updateStatus` renamed to `TicketDao.update` — it already
  accepted an arbitrary `TicketsTableCompanion` under a status-specific
  name; this change is the second caller that needs the same generic
  write, so the name is corrected to match what it actually does. One
  mechanical call-site update in `DriftTicketRepository`.
- `DriftTicketRepository.updateTicket` — builds a companion covering
  title/description/priority/type/estimate/timeSpent/updatedAt (not
  status — the passed-in `Ticket` always carries its current, unmodified
  status since this change never edits status).
- `TicketsCubit.updateTicket(Ticket ticket)` — persists, re-fetches, emits
  the existing `TicketDetailLoaded` state (no new state classes needed;
  unlike the board's optimistic drag pattern, the inline field widgets
  supply their own instant visual feedback locally).
- `core/utils/duration_format.dart` — `formatDurationMinutes`/
  `parseDurationMinutes` helpers ("2h 30m" ⇄ 150).
- `core/widgets/selection_menu.dart` — `SelectionMenu<T>`, a generic
  version of the board's `MoveToStatusMenu` overlay-picker pattern, reused
  here for priority and type. `MoveToStatusMenu` itself is left untouched
  (already shipped/verified; not in scope to refactor here).
- `features/tickets/presentation/widgets/inline_editable_field.dart` —
  `InlineEditableField<T>`, the tap-to-edit text primitive reused for
  title, description, estimate, and time spent.
- `TicketDetailScreen` wiring: title/description/priority/type/estimate/
  timeSpent become editable in place; `StatusIndicator` is untouched.
- Unit tests: `Ticket.copyWith` (new field cases, including explicit
  null-clearing), `duration_format.dart`, `TicketsCubit.updateTicket`,
  `DriftTicketRepository.updateTicket`.

### Out

- Editing `status` from the detail screen — remains board-only
  (`MoveToStatusMenu` / drag), unchanged by this proposal.
- Editing `parentId` — structural hierarchy change, its own future change.
- Any UI for `embedding` — system-populated, not user-facing.
- Automatic time tracking (timer UI) — captured separately as
  `aion-arch/ideas/automatic-time-tracking-for-tickets.md`.
- Ticket deletion — separate gap, not addressed here.
- Refactoring `MoveToStatusMenu` to use the new `SelectionMenu<T>` — left
  as pre-existing bespoke code; flagged as optional future cleanup, not
  part of this change's scope.
- Per-field rollback/toast on a *backend*-level failure (e.g. the
  repository call itself throwing). That case still falls through to the
  existing `TicketsError` full-screen state, consistent with how
  `updateTicketStatus` already behaves. Only *client-side format
  validation* (an unparseable duration string) gets its own inline
  `AppToast` + revert, without ever reaching the cubit.

## Non-Goals

- A generic multi-field "SelectMenu" retrofit across the whole codebase —
  `SelectionMenu<T>` is introduced because this change is the second
  legitimate use of the pattern (priority and type), not as a speculative
  abstraction.
- Visual/pixel-level polish of the new inline-edit affordances — routed
  through the existing Design gate (`/design-brief` → Claude Design →
  `/opsx-design-sync`) before `/opsx-apply`, same as every prior UI change.
