# Manual verification

- [x] T35 — Live pass against the `flutter-web` dev server, driven from
  a real Chrome (Claude in Chrome — per project.md, the sandboxed
  preview browser stalls before first frame on this app). Verified:
  single-ticket delete (`TicketOverflowMenu`) shows the cascade-aware
  confirm message ("These 2 tickets will move to Trash" for a
  parent+child pair, singular phrasing for a childless ticket) and
  moves the ticket to Trash; bulk delete of a selection containing a
  parent but not its child correctly pulled the unselected child in via
  cascade (confirm dialog showed "Delete 2 tickets?" / "These 3 tickets
  will move to Trash", matching selection-count vs. cascade-total
  exactly); Trash screen lists only root tickets (a cascaded child never
  gets its own tile, folded into its root's "+N subtasks" count
  instead); Restore brought back a trashed root and its child together,
  and the restored ticket was fully functional afterward (detail
  screen, parent link intact); per-tile Permanently Delete and Empty
  Trash both showed the correct destructive-tone confirm copy
  (ticket-title-interpolated for per-tile, count-aware for empty-trash)
  and worked correctly, including the empty state and the "Empty trash"
  button auto-disabling; selection mode verified on both the list (left
  rail + tint) and board (full border + tint) renderings, with
  `TicketOverflowMenu`/`MoveToStatusMenu` correctly suppressed on the
  board card while active; search/filter never surfaced a trashed
  ticket (implicit — trashed tickets never reappeared in any list/board
  view for the rest of the session); zero console errors throughout.
  **Not verified live:** "existing local data survives the schema
  migration" — this environment's Chrome automation context logs
  `Using WasmStorageImplementation.inMemory due to missing browser
  features: {MissingBrowserFeature.workerError}` on load, i.e. drift-
  wasm falls back to non-persistent storage here regardless of this
  change (confirmed via console diagnostic), so a real reload-and-
  persist round trip can't be exercised in this harness. Covered
  instead by the automated `AppDatabase` v1→current migration test
  (T31), which does exercise a real close/reopen against a file-backed
  SQLite db and explicitly asserts pre-existing tickets stay live (not
  trashed) after the v3 `addColumn` step runs.
