# Ticket Crud Tool Calls

# Proposal: Ticket CRUD Tool Calls

## What we're building

Three new app-defined tools — `create_ticket`, `add_link`, `log_time` — that
a model can call mid-turn on any chat that already offers app-defined tools
(coding-execution's implement/verify turns, SDD-stage chats, design-sync),
generalizing the `branch_ticket`/`close_branch` mechanism shipped by
`aion-arch/changes/archive/mid-task-chat-branching` to real ticket-graph
writes instead of just chat-branch structure.

Today, a coding-execution run (or any tool-enabled chat) has no way to spin
off a follow-up ticket, relate itself to another ticket, flag a likely
duplicate, or log time against the ticket it's working — the model can only
narrate these things in chat text, where nothing acts on them. The one
precedent for "model proposes, Aion executes" is decomposition's structured
`## Decomposition` reply-block, parsed only after the whole turn completes,
and it exists for exactly one hardcoded case (initial story/task breakdown).
`branch_ticket`/`close_branch` proved a better precedent: a real mid-turn
tool call, dispatched through `TicketsCubit`, gated by
`AutomationConfidence` — the model gets a result back immediately instead of
finding out next turn.

## Why

Raised in `aion-arch/ideas/delegate-ticket-crud-to-aion-during-coding-execution.md`:
coding execution's tool-enabled model already has file/git/bash access to
the worktree, and was suspected of "wanting" to touch tickets directly —
which is structurally impossible today, since `epic`/`story`/`task`/`bug`/
`chat` ticket files are one-way, generated-only `TicketGitProjector`
projections. Giving the model real tool calls, dispatched through Aion's
own repository layer, closes that gap the same safe way branching already
does: the model never touches the DB directly, and every write can be
gated behind human confirmation independently of whatever confidence level
governs the coding-execution run itself.

## Scope: 3 tools, not 4

The idea's brainstorm session identified four candidate operations (create
a follow-up ticket, add a link, flag a duplicate, log time).
`/explore`'s grounding against `TicketLinkRepository` found `flag_duplicate`
collapses into `add_link`: `TicketLinkType.duplicates` already exists as an
ordinary link type, and `createLink` is already generic over `linkType`. A
dedicated `flag_duplicate` tool would just be `add_link` with one specific
enum value, so it isn't built as a separate tool — the model calls
`add_link` with `linkType: "duplicates"`.

## Guardrails

- **`log_time` always auto-applies.** Logging time is additive and
  low-consequence — no `AutomationConfidence` gate, no confirmation banner.
- **`create_ticket` and `add_link` each get their own new
  `AutomationContext` entry** (`ticketCreation`, `ticketLinking`),
  independently configurable in Settings, mirroring `chatBranching`'s
  existing one-entry-per-decision-point pattern — not a single "inherit
  whatever governs this run" rule, since no such single run-level dial
  exists in the codebase today (`codingExecution` and `chatBranching` are
  already separately-configured decisions, not a hierarchy). `manual`
  declines outright, `auto` applies immediately, `gated` surfaces a
  confirmation banner and pauses the model's turn — exactly
  `_handleBranchToolCall`'s existing three-way branch.

## Non-goals

- No new tool for `epic`/`chat`/`resource`/`page` ticket types —
  `create_ticket`'s `type` argument is constrained to `story`/`task`/`bug`.
- `create_ticket` never accepts a model-supplied `parentId`. Every
  model-created ticket is top-level (`parentId: null`); relating it to the
  ticket under discussion is a separate, explicit `add_link` call. This
  avoids trusting the model with `TicketTypeHierarchy.canParent` structural
  decisions it has no visibility into.
- `delegatedSkill` workflow-attachment runs stay out of scope — they
  already explicitly skip `_toolCallParamsFor` per
  `aion-arch/changes/archive/workflow-skill-attachments`'s own Non-goals,
  and this change doesn't reopen that decision.
- No new duplicate-detection UI or embedding-driven duplicate surfacing —
  that's `aion-arch/ideas/ticket-graph-and-embedding-context-enrichment.md`'s
  concern (context flowing *into* a run); this change only builds the
  write path a model would use *after* it already suspects a duplicate,
  however it forms that suspicion.
- No SDD-stage-chat-specific tuning — the three tools are offered wherever
  `_toolCallParamsFor` already runs, with no per-stage carve-out.
