# Ticket Parent Selection Ux

# Proposal: Ticket Parent Selection UX

## What

Two related UX improvements to ticket parent assignment, both scoped to
the existing parent-picker mechanism:

1. **Set a parent at creation time.** `CreateTicketScreen` gets a parent
   field (reusing the picker UI), wired to `TicketsCubit.createTicket`'s
   existing `parentId` parameter — which the Cubit already accepts and
   persists, but which the create form has never surfaced. The field is
   hidden whenever the selected ticket type is `TicketType.epic`, since
   epics are always subtree roots.
2. **Show ancestor breadcrumbs in the picker.** Each candidate row in the
   parent picker currently shows only a ticket key + flat title. It
   gains a single-line ancestor-path breadcrumb underneath (e.g. "Auth
   Epic / OAuth redesign"), computed from the ticket list the picker has
   already fetched — no new query. This follows the pattern used by
   Linear and Jira's parent/epic pickers: a flat searchable list with a
   breadcrumb subtitle, not a full indented tree (appropriate for
   Aion's shallow epic → story → task depth, where a ClickUp-style deep
   tree picker would be overkill).

## Why

Investigated during `/explore` of `TicketsCubit.getValidParentCandidates`
and `TicketParentPicker` (see `aion-arch/specs/tickets.md`'s "Known
gaps" — reparenting only happens post-creation via `TicketDetailScreen`,
and the picker has no hierarchy context).

- Today, assigning a parent always requires a two-step flow: create the
  ticket, then open its detail screen and use the parent picker. The
  Cubit already has everything needed to skip that second step —
  `createTicket(parentId: ...)` exists and is fully implemented; only
  the create form's UI is missing.
- The picker's flat `ticketId + title` rows give no sense of where in
  the hierarchy a ticket sits, which matters once a workspace has more
  than a handful of epics — a user reparenting a story can't tell which
  epic a same-named sibling story belongs to without opening it first.

## Scope

In scope:
- Parent field on `CreateTicketScreen`, gated on ticket type.
- Ancestor-breadcrumb subtitle on parent-picker candidate rows, reused
  by both the existing reparent flow (`TicketDetailScreen`) and the new
  create-time flow.
- Extracting `TicketParentPicker` and its row widgets out of
  `ticket_detail_screen.dart` into their own file so both screens can
  use it without file-private (`_`-prefixed) access issues.
- A `TicketsCubit.getAllTickets()` passthrough for the create-time
  picker, which has no ticket yet to exclude self/descendants for.

Out of scope (explicitly not part of this change):
- Bulk reparent.
- Full indented tree view (rejected — see "Why" above).
- Caching/reducing the duplicate `getAllTickets()` fetch between
  picker-open and commit-time re-validation in `updateTicketParent` —
  pre-existing behavior, unrelated to this change's UX scope.
