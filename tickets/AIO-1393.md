# Page Nesting Depth Limit

# Proposal: Page-nesting depth limit

## What we're building

`DocumentationTreeItem`'s tree-mode row indent grows unbounded with
nesting depth (`leftPad = 12 + depth * 20`, no ceiling). This change
clamps that indent calculation at a fixed maximum depth so a deeply
nested `page` tree can no longer push its row content (icon, title,
child-count pill) into negative available width and trigger a
`RenderFlex` overflow on narrow/mobile viewports — while leaving
actual page-nesting *depth itself* completely unbounded, unchanged
from today.

Rows past the clamp depth render at the same fixed indent as the
clamp depth itself (visually flush with their nearest still-indented
ancestor), rather than continuing to step outward. Each such row still
shows its own expand/collapse chevron when it has children, so drilling
further into the tree stays fully functional — only the *visual*
indent signal flattens out, not the navigation.

## Why

This closes the "no page-nesting depth limit is enforced" item
carried in `aion-arch/specs/tickets.md`'s Known Gaps, per
[[page-nesting-depth-limit]] (`aion-arch/ideas/page-nesting-depth-limit.md`).
That exploration's conclusion, reconfirmed when this change was
proposed:

- **No cap on the data model.** `TicketTypeHierarchy.canParent`, the
  `page`-under-`page` structural rule, and every `TicketsCubit`
  invariant stay exactly as they are. A personal docs vault is
  unlikely to realistically nest deep enough for an arbitrary policy
  cap to matter, and blocking creation would only exist to protect UI
  rendering — not data integrity. (The precedent this project already
  has for an actual policy-level nesting cap — `chat`'s branch-depth
  invariant in `TicketsCubit._canBranch`, per the idea file's own open
  question — was checked and doesn't apply here: that cap exists for
  conversation-branching reasons specific to `chat`, not as a general
  nesting-depth pattern to reuse.)
- **The real risk is UI overflow, not data integrity**, and it's
  addressed at the UI layer only: `DocumentationTreeItem`'s indent
  calculation, used exclusively by `DocumentationScreen`'s tree-mode
  body. The flat search-result variant and `PageSubPagesSection`'s
  `_SubPageRow` are both already depth-independent (fixed indent) and
  need no change.

## Non-goals

- No change to `TicketTypeHierarchy.canParent`, `page` structural
  parenting rules, or any `TicketsCubit` create/reparent invariant.
- No new settings/configuration surface — the indent clamp depth is a
  fixed constant, not a user-facing preference.
- No change to `PageSubPagesSection`/`_SubPageRow` (flat, single-level
  list — never affected by nesting depth) or to the flat search-result
  variant of `DocumentationTreeItem` (`showChevron: false`, fixed
  `leftPad`).
