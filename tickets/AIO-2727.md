# Fix Ticket Git Projection Gap

# Proposal: Fix the ticket → git projection gap

## Origin

Originates from a finding recorded in
`aion-arch/ideas/decommission-aion-arch-cli-workflow.md`'s 2026-09-08
Amendment ("DB/git-projection drift root-caused via `/explore`"), one
of two explicit gates on that idea's step 3 (cutover). This proposal
is the follow-up fix that Amendment recommended, not a new idea of its
own.

## Problem

`TicketGitProjector` (`data/services/ticket_git_projector.dart`) is
the one-way DB → `tickets/*.md` writer, invoked today from a handful
of call sites scattered across `TicketsCubit`/`TrashCubit`/
`TicketParentTrashService`. Per `specs/tickets.md`'s "Git projection"
section, exactly five events are meant to produce a commit: a ticket
created, its status changed (single or bulk), it's trashed, and it's
restored — everything else (title/description/priority/type/estimate/
timeSpent/complexity edits via `updateTicket`) is a deliberate
non-event, to avoid a commit per keystroke-adjacent save.

In practice, only tickets created or status-changed *through
`TicketsCubit`'s own two public methods* (`createTicket`,
`updateTicketStatus`) reliably reach git. A large and growing set of
other internal call sites construct and persist a `Ticket` (or change
its `sddStage`/`parentId`) by calling `TicketRepository` directly,
bypassing the projection trigger entirely:

- `promoteIdea` — the Epic/Bug created when an idea is promoted.
- `createGapOrQuestion` — knownGap/openQuestion tickets.
- `_materializeParsedChildren` (backs both `_materializeDecomposition`
  and `_materializeVerifyFixes`) — every Story/Task/Bug child an SDD
  decomposition or verify-fix turn creates.
- `_createEpicSpec` — an Epic's own spec ticket.
- Stage-chat, branch-chat, release-ticket, and coding-execution run/
  finding-ticket creation (several more `_repository.createTicket`
  call sites, same shape, not individually enumerated here).
- `advanceSddStage` — every SDD stage transition (`updateTicketSddStage`).
- `updateTicketParent` — reparenting only gets swept up in git
  incidentally, and only when the rollup-recompute walk that follows
  it also finds a *rollup number* changed; the ticket's own new
  `parentId` is otherwise silently dropped, since
  `TicketRollupRecomputer.recompute` compares `estimateRollup`/
  `timeSpentRollup`, not `parentId`.

This was root-caused and live-reproduced against the real "Aion
Self-Iteration Dogfood" project: a plain ticket created through the
ordinary New Ticket screen committed to `tickets/*.md` correctly, but
an Epic created by promoting an idea (`promoteIdea`) never reached git
until it was later, incidentally, trashed — the only one of its
writes that happened to go through an instrumented path. This is the
same shape as the originally observed drift (`AIO-2701`-`AIO-2714`,
`AIO-2717`-`AIO-2723`): most of a real SDD proof run's own ticket
history never made it into git at all.

The gap keeps recurring because projection is opt-in per call site in
an ~8,700-line, actively-growing cubit — each of the five write paths
above has to remember to call `_triggerGitProjection` itself, and
several new ones (this proposal's own investigation found two more
beyond what the original `/explore` listed) have already slipped
through since the mechanism was first built.

## Goal

Make projection structural instead of opt-in: every ticket write that
is *already* meant to commit (per `specs/tickets.md`'s five-event
list, plus `updateTicketParent` — a sixth, equally structural event
this proposal's investigation found is missing from that list) commits
correctly regardless of which `TicketsCubit`/`TrashCubit`/internal
method triggered it, including call sites that don't exist yet.

## Approach

Move the projection trigger from `TicketsCubit` (and
`TicketParentTrashService`'s own trash/restore methods) down to a new
`GitProjectingTicketRepository` — a `TicketRepository` decorator that
wraps `DriftTicketRepository`, delegates every method unchanged, and
fires the matching git-projection event after the six writes above.
Every existing caller already depends on the `TicketRepository`
*interface*, not the concrete Drift class, so wiring the decorator in
at the composition root (`app_router.dart`, the same `rootPath != null`
desktop gate `TicketGitProjector` itself is already built behind)
requires no change to any of the ~20+ call sites this fix closes —
they keep calling plain repository methods and get projected for
free, today's bypasses included. A future new call site inherits the
same guarantee automatically, closing the class of bug, not just
today's instances of it.

The estimate/timeSpent rollup cascade (`TicketRollupRecomputer`) is
deliberately left untouched: it already has its own working git
projection (`TicketGitProjector.projectBatch`, one commit for every
changed ancestor), and that batching is a real, documented requirement
the generic per-call decorator can't replicate without adding
batch-aware machinery this fix doesn't need. See design.md's
"Non-goals" for the full boundary between what the decorator covers
and what deliberately stays as-is.

Alongside the decorator, harden `GitRepositoryClient.add`/`commit`/
`hasChanges` (currently the unchecked `Process.run` wrapper, exit code
never inspected) to surface a failed git operation instead of
swallowing it — the same class of bug `AIO-506` already fixed for
`createWorktree`/`push`/`tag` via `_runChecked`. Not implicated in the
live repro (every projection that should have committed, once
reached, did), but directly adjacent code left in the same
fail-silently shape the rest of this change is fixing.

## Non-goals

- **No new projection triggers beyond the six structural events.**
  `updateTicket` (title/description/priority/type/estimate/timeSpent/
  complexity), `updatePriorityForIds` (bulk priority — the same field
  bucket as `updateTicket`'s own priority edits), `addTimeSpent`, and
  `applyEstimationSuggestion` stay uncommitted, exactly as today —
  `specs/tickets.md` already excludes plain content edits from
  projection on purpose (no commit per keystroke-adjacent save), and
  extending that boundary is a separate, deliberate feature decision,
  not part of closing this gap.
- **No change to `TicketRollupRecomputer`'s batched-commit shape.**
  Kept exactly as documented in `specs/tickets.md`'s "Git projection"
  section.
- **No projection on permanent deletion.** `permanentlyDeleteTicket(s)`/
  `emptyTrash`/`purgeTrashOlderThan` remove rows from the database but
  never delete the corresponding `tickets/<id>.md` file from git — a
  real, separate gap this investigation surfaced in passing (an
  orphaned file left behind forever), out of scope here since it's a
  distinct problem (missing deletion, not missing creation/update) with
  its own design questions (e.g., should a purge produce a commit
  removing the file, and is that safe to do unattended for a bulk
  "Empty trash"). Worth its own follow-up idea/proposal.
- **No change to `TicketMarkdownWatcherService`/`TicketMarkdownReconciler`**
  (the reverse, file → DB direction for `resource`/`page` tickets) —
  unaffected by this fix, which is scoped to DB → file only.
- **No UI changes.** This is entirely a data/service-layer fix; no
  widget, screen, or user-facing surface is touched.
