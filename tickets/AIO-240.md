# Barrel Files

# Proposal: barrel-files

## What

Introduce barrel files (re-export-only Dart files) at three points in
`lib/`:

1. **`lib/core/design_system.dart`** — re-exports the six existing
   `core/theme/*.dart` files (`aion_colors.dart`, `aion_radius.dart`,
   `aion_shadows.dart`, `aion_text.dart`, `aion_theme.dart`,
   `theme_scope.dart`). No files move; only the barrel is new.
2. **`lib/core/core.dart`** — re-exports the rest of `core/`:
   `database/app_database.dart`, `localization/context_localizations_x.dart`,
   `routing/app_router.dart`, both `utils/*.dart` files, and all eight
   `widgets/*.dart` files. Deliberately excludes `core/theme/` — the design
   system is the one carve-out with its own barrel, per direct instruction.
3. **`lib/features/tickets/tickets.dart`** — re-exports the tickets
   feature's *public surface only*: everything under `domain/` (entities,
   enums, exceptions, repository interfaces) and everything under
   `presentation/` (cubits, states, screens, widgets). `data/` (DAOs,
   Drift table models, `Drift*Repository` implementations) is
   **intentionally not exported** — see [Design](design.md#why-data-stays-unexported).

Every future feature directory gets the same `<feature>.dart` barrel
pattern; `flutter-conventions.md` is updated to document it as a
standing convention, not a one-off for `tickets`.

## Why

Aion currently has zero barrel files. Every file imports individual
leaf files directly — `ticket_detail_screen.dart` alone carries 18
`package:aion/...` imports, 12 of which are core (theme × 5, utils × 1,
widgets × 5, localization × 1) that collapse to 2 imports once
`design_system.dart`/`core.dart` exist. As more features are added,
this import noise scales linearly with every screen that touches the
design system or shared widgets. Barrels fix the noise without
changing any runtime behavior.

The harder question this proposal resolves is *scope*: a naive "one
barrel re-exports everything in the folder" would let a screen import
`DriftTicketRepository` straight through `tickets.dart`, which
undermines the repository-interface boundary that's already a hard
rule in [project.md](../../project.md#key-constraint) ("UI and domain
code must never depend on a concrete data source"). Scoping the
feature barrel to domain + presentation only closes that hole by
construction — the data layer simply isn't reachable through the
barrel, so nothing outside `main.dart` (the composition root) can grab
a concrete `Drift*Repository` by accident.

## Non-goals

- No file moves. `core/theme/*.dart` stays exactly where it is; only
  `design_system.dart` (the barrel) is new.
- No change to any app behavior, widget tree, or Cubit logic — this is
  a pure import-organization change.
- No custom `analyzer`/`custom_lint` rule to enforce barrel usage.
  Aion already has a documented precedent for convention-over-tooling
  at this project's scale (see `flutter-conventions.md`'s localization
  section, decided in `changes/archive/intl-string-retrofit/`) — this
  proposal follows the same precedent rather than introducing new
  tooling.
