## What Is Aion
A spec-based AI agentic code assistant with a Jira-like project management
structure, built as a single Flutter app across all platforms. Core concept:
everything is a "ticket" (epics, stories, tasks, resources, Notion-style
pages, agent chats), tickets link to each other freely, chats are tied to
tickets and can branch into subtickets, code and ticket data is versioned,
and the app embeds full agentic coding capability (file edits, git, MCP,
skills) plus multi-model routing (local + cloud, switchable, with
cost-aware Auto mode).

Aion is agent/model-agnostic by design — no user-facing text, docs, or
naming should hardcode a specific vendor or model provider (Claude,
Anthropic, GPT, Gemini, etc.). Provider identity is a user-configured
setting (see "Provider configuration" under Foundational Decisions §5),
not part of Aion's own branding or architecture naming.

## Stack
Flutter, solo developer. Complex, multi-feature app with offline support.
No backend — local-first permanently.

### Data & Sync
- drift (SQLite) — local source of truth, all platforms.
- Git (private repo) — event-triggered versioning + cross-device sync
  (push/pull). Eventually consistent; acceptable for a personal tool.

### API & Security
- Cloud model calls go directly client-to-provider on desktop, where API
  keys live safely in local .env / flutter_secure_storage.
- On mobile/web, API keys must never be shipped in the app bundle.
  Firebase AI Logic (official Dart SDK) acts as a secure proxy for
  Google/Gemini models. For non-Google providers (Anthropic, etc.) on
  mobile/web, route through a lightweight Firebase Cloud Function — no
  full backend needed, just a single authenticated proxy function per
  provider.
- On-device models (flutter_local_ai) require no key handling at all.

## Architecture
Three top-level groupings under `lib/`:
- `design_system/` — design tokens plus every reusable, feature-agnostic
  widget (atomic-design vocabulary: `tokens/`, `atoms/`, `molecules/`).
  No business logic, no awareness of any feature. Exposed via one
  barrel, `design_system/design_system.dart`.
- `core/` — infrastructure with no UI of its own: database, routing,
  localization, utils. Exposed via `core/core.dart`.
- `features/<feature>/` — feature-first, layered:
  - presentation/ — widgets (no business logic) + Cubits (may hold
    business/domain logic — see [State Management](#state-management))
  - domain/ — entities, repository interfaces. No Flutter imports.
  - data/ — models, repository implementations (local drift DB now,
    remote source later)

Any feature consumes `design_system/` the same way it consumes
`core/` — through that grouping's single barrel, never a leaf file
inside it (see `flutter-conventions.md` "Barrel files"). A widget only
belongs in `design_system/` once it's fully generic: no feature
entity/enum constructor parameter, no feature-specific copy baked into
its body. Generalize first, promote second — never both in the same
change (see flutter-conventions.md's design-system promotion rule).

## Key Constraint
All data access goes through repository interfaces defined in domain/.
UI and domain code must never depend on a concrete data source.

## Cross-Feature Dependencies
Aion is one Flutter package with feature-first folders under
`lib/features/<feature>/` (not separate pub packages), so nothing stops
`lib/features/boards/` from importing `package:aion/features/tickets/...`
at the language level. The rule is enforced by convention and code
review, the same way as the [Non-Material constraint](flutter-conventions.md)
and [Localization](flutter-conventions.md#localization) are.

**Hard rule:** no feature imports another feature's internals, and no two
features import each other, directly or indirectly. No exceptions. If you
see `import 'package:aion/features/<other_feature>/...'` inside a
different feature's folder, that's a violation — stop and apply one of
the two patterns below instead.

The screen or widget itself stays in the feature it conceptually belongs
to (the one the user is "in"). It does not move or split just because
part of its content is sourced from another feature.

**Pattern 1 — dependency inversion via `core` (default, for data/behavior):**

1. Define an abstract contract in `core/contracts/` (e.g.
   `core/contracts/ticket_summary_provider.dart`).
2. The owning feature implements it under its own `data/` folder (e.g.
   `features/tickets/data/ticket_summary_provider_impl.dart`).
3. The consuming feature depends only on the `core` abstraction, never on
   the other feature directly.
4. Wire the concrete implementation where all repositories are already
   wired: the `MultiRepositoryProvider`/`RepositoryProvider` tree in
   `main.dart` (see [BLoC/Cubit structure](flutter-conventions.md#bloccubit-structure)
   — Aion has no `get_it`/`riverpod`; constructor injection via
   `flutter_bloc`'s provider tree is the one DI mechanism).

```
lib/
  core/
    contracts/
      ticket_summary_provider.dart        <-- interface only

  features/
    boards/
      presentation/screens/
        board_screen.dart                 <-- depends on core's interface

    tickets/
      data/
        ticket_summary_provider_impl.dart <-- implements the interface

  main.dart                               <-- binds interface -> impl via RepositoryProvider
```

Use this whenever, say, `boards` needs data or behavior that `tickets`
owns. Neither feature ends up depending on the other — both depend
downward on `core`.

**Pattern 2 — shared widget in `design_system/` (for UI):**

If what one feature needs from another is a UI widget, and that widget
is genuinely generic and reusable (not deeply tied to the owning
feature's business logic — no feature entity/enum constructor param,
no feature-specific copy baked into its body), promote it to
`design_system/atoms/` or `design_system/molecules/` alongside
`AppButton`/`AppTextField`/`AppSpinner`. Generalize the widget first if
it isn't already fully generic — never move it as-is and generalize
later. The owning feature can still own the logic behind it via
Pattern 1; the presentational widget itself becomes shared and
importable by any feature without creating a feature-to-feature
dependency.

**Decision guide:**

| Situation | Use |
|---|---|
| Feature A needs data/behavior owned by Feature B | Pattern 1 — interface in `core/contracts/`, impl in B's `data/`, wired via `RepositoryProvider` in `main.dart` |
| Feature A needs a UI widget that's generic/reusable | Pattern 2 — generalize, then promote to `design_system/atoms/` or `design_system/molecules/` |
| Dependency doesn't fit either pattern cleanly | Reconsider the feature boundary — the shared concept likely belongs in `core/` or `design_system/` rather than in either feature |

## State Management
flutter_bloc only. Cubit preferred.

Cubits are not required to be thin view-models that just forward calls
to a repository — a Cubit may be UI-agnostic and hold real
business/domain logic (validation rules, invariant checks like cycle
prevention). Repositories stay dumb persistence layers: plain reads/
writes, no validation. Widgets themselves still hold no business
logic — this split applies to Cubits vs. repositories, not to widgets
vs. everything else.

## Testing
mocktail and bloc_test.
Unit tests required for every Cubit and repository with real logic.
Trivial pass-throughs may be skipped. Repository tests mock dependencies
via mocktail; do not spin up a real drift in-memory instance unless
the test is specifically about persistence behavior.

Automated tests won't catch everything — the v1 slice's setState-after-
-dispose crash in AppDropdown (its overlay-dismiss/focus-listener callback
firing after the widget was disposed) only surfaced via interactive
manual testing (`flutter run`), not `flutter analyze` or `flutter test`.
Any custom `StatefulWidget` that manages an `Overlay`, async callback, or
listener outside the normal build/dispose cycle needs a manual interactive
pass, not just unit tests — guard with `mounted` checks before `setState`.

For that manual interactive pass, run the app in a real Chrome instance
(e.g. via the Claude in Chrome tools), not a sandboxed headless preview
browser. A sandboxed preview failed to paint even a first frame for this
app — Flutter Web's CanvasKit/semantics pipeline plus drift's
sqlite3-WASM init depend on real IndexedDB/Worker/GPU support that a
sandboxed headless browser may not provide, and the failure mode looks
identical to a real app bug (blank canvas, no console errors) unless you
know to suspect the environment first. Don't spend time debugging a
"blank screen" in a sandboxed preview for this project — switch to real
Chrome immediately instead.

When the pass is done, close the Chrome tab and stop the `web-server`
process — don't leave either running past the check that needed them
(see CLAUDE.md's shared rules).

## Bootstrap & Dependency Notes
Learned while turning the blank scaffold into the v1 slice — relevant to
any future project reset or fresh-checkout setup:
- `analysis_options.yaml` already referenced `flutter_lints` before it was
  added as a dependency (fresh `flutter create` scaffolds sometimes lag
  behind this) — caused an `include_file_not_found` warning until
  `flutter_lints` was added to `dev_dependencies`. If `flutter analyze`
  complains about a missing include, check the dependency is actually
  declared before debugging the YAML.
- `meta` must be a direct (not transitive) dependency once any code uses
  `@immutable`, `@visibleForTesting`, etc. explicitly — the SDK provides
  it transitively but `flutter analyze`/pub treat direct use as requiring
  a direct dependency.
- `Color.withOpacity(x)` is deprecated on the Flutter SDK this project
  targets — use `.withValues(alpha: x)` everywhere instead. All color/
  shadow token code (`AionShadows`, chip fills, etc.) already does this;
  keep new code consistent.
- A dev server launch config lives at `.claude/launch.json`
  (`flutter-web`, port 8765) for the Claude Code preview tooling — reuse
  it instead of hand-rolling a new server entry for web preview/testing.
- `agent_bridge/` (sibling to `aion/lib/`, see `provider-configuration`)
  is a separate Node.js project, not part of the Flutter build — run
  `cd aion/agent_bridge && npm install` once before using any
  provider-configuration feature (Settings, and later any
  provider-backed feature). Not automated from inside the Flutter app;
  same category of manual one-time setup as `flutter pub get`. Requires
  `node` reachable on `PATH` — `ClaudeAgentSdkClient` surfaces a
  readable error via the Settings connection test if it isn't.

## Documentation Standards

### Dart/Flutter code
Every public symbol (class, method, field, enum value) must have a
dartdoc comment (///). No exceptions, including generated-looking
boilerplate like repository implementations and Cubit states.

Minimum per symbol type:
- Class: one-line summary + purpose in the architecture
  (e.g. /// Drift-backed implementation of [TicketRepository].
  ///  Source of truth for all ticket read/write operations.)
- Method: one-line summary + @param for non-obvious params +
  @returns if the return value has nuance + @throws if it can throw.
- Cubit/BLoC state class: describe what UI condition this state
  represents and what data it carries.
- Entity/model field: inline /// comment if the field name alone
  is ambiguous (e.g. estimateMinutes vs just estimate).
- Enum value: one-line /// on every value, especially status and
  type enums that drive business logic.

Do NOT document:
- Private implementation details that are obvious from the code.
- Overrides of well-known Flutter lifecycle methods (initState,
  dispose, build) unless the implementation is non-obvious.

### File headers
Every file under lib/ starts with a one-line comment stating what
the file contains and which layer it belongs to:
// domain/entities/ticket.dart — Ticket entity (domain layer).
// data/repositories/drift_ticket_repository.dart — Drift implementation
//   of TicketRepository. Data layer only — no business logic.

### tasks.md enforcement
Every task that creates or modifies a Dart file must include
documentation as part of the task definition, not as a separate
cleanup task. Qwen/Claude must write docs in the same pass as the
implementation. tasks.md tasks that produce undocumented public
symbols are considered incomplete.

## Design System
Two cold themes — Arctic (light, celestial) and Obsidian (dark, abyssal).
Inspired by the Elyos and Asmodian factions from the AION MMORPG.
Full token and component spec in aion-arch/changes/<v1-change>/design.md.

### Fonts
Manrope (UI/display) + JetBrains Mono (keys, captions, code).
Both as variable fonts, bundled as assets under assets/fonts/ — no
google_fonts package. Declared in pubspec.yaml flutter.fonts.
JetBrains Mono ships both upright and italic variable files:
JetBrainsMono[wght].ttf       → style: normal
JetBrainsMono-Italic[wght].ttf → style: italic

### Icons
Phosphor Light weight via the **phosphoricons_flutter** package (not
phosphor_flutter — phosphor_flutter's `PhosphorIconData` extends Flutter's
`IconData`, which is now a `final` class on current Flutter SDKs, so
phosphor_flutter no longer compiles. phosphoricons_flutter is a drop-in
replacement: same icon set, near-identical `PhosphorIcon`/`PhosphorIcons`
API). If a future slice hits an "IconData is final" compile error from
phosphor_flutter, this is why — don't try to patch around it, just use
phosphoricons_flutter.
Thin-line, fantasy-forward. Rendered 20–24px, color textSecondary
unless active/selected (switch to primary or filled weight).
Faction motifs (filled, primary color) reserved for empty states,
onboarding, section headers — never inline controls.

### Non-Material constraint (hard)
No ThemeData, MaterialApp, ColorScheme, Card, ElevatedButton,
ListTile, AppBar, Scaffold, SnackBar, ScaffoldMessenger,
CircularProgressIndicator, DropdownButton, InkWell anywhere in lib/.
Theme accessed via ThemeScope (InheritedWidget) returning AionThemeData.
All visual values via AionColors, AionText, AionRadius tokens only —
never raw hex, font sizes, or spacing values in widget code.
T26 grep checks enforce this constraint on every apply run.

`TextField` is the sole permitted Material widget (needed as the only
practical cross-platform text-input primitive). It requires
`flutter_localizations` as a dependency and a transparent `Material`
ancestor wrapping it — both are needed even with no `MaterialApp`/
`Scaffold` anywhere in the tree, because `TextField` reads
`MaterialLocalizations`/`Material` internally regardless. `AppTextField`
(`design_system/atoms/app_text_field.dart`) already does this wrapping;
build on top of it rather than dropping a bare `TextField` into a new
widget.

## Platform Support
Targeting all Flutter platforms: iOS, Android, web, macOS, Windows, Linux.

### Feature scope per platform
- Desktop: full agentic coding (file edits, git, MCP, skills) +
  tickets/boards/chat/posts.
- Mobile: tickets/boards/chat/posts only, no coding. On-device LLM
  (flutter_local_ai) for lightweight text-in/text-out tasks. Tool-calling
  on Apple only (Android Gemini Nano does not support it — use
  text-context-stuffing fallback on Android).
- Web: same scope as mobile. No on-device LLM tier — AI tasks go
  straight to cloud models via Firebase proxy.

### Platform caveats
- drift on web uses sqlite3 WASM (different init path than
  mobile/desktop). Test drift on web early, before building features
  on top of it. Concretely requires `web/worker.dart` and
  `web/sqlite3.wasm` in the project's `web/` directory — both fetched
  from the `drift`/`sqlite3` packages, both gitignored (not hand-written,
  don't commit them, re-fetch if missing). `AppDatabase`
  (`core/database/app_database.dart`) opens `WasmDatabase.open(...)` on
  web vs. `drift_flutter`'s `driftDatabase(...)` on native — see that
  file for the platform-conditional `_openConnection()` split.
- flutter_secure_storage on web falls back to browser storage — treat
  web as a reduced-security target for sensitive data.
- go_router on web: clean paths (no #) are the default. A static
  production host must rewrite all paths to index.html to avoid 404
  on refresh or direct URL entry. Firebase Hosting requires:
  { "hosting": { "rewrites": [{ "source": "**",
  "destination": "/index.html" }] } }
  in firebase.json. Must be in place before deploying any web build
  with deep links.

## Foundational Decisions (Pre-v1 Architecture)

### 1. Storage Model
Three distinct layers, not one mechanism:
- Live state — drift (SQLite). Source of truth for ticket fields,
  relationships, time tracking, status.
- Semantic memory — embeddings stored as BLOB columns in drift.
  Generated via local Ollama embedding model on ticket create/update.
  Retrieval via brute-force cosine similarity (sufficient at personal
  scale; revisit with sqlite-vec only if performance demands it).
  Powers both "similar ticket" estimation and long-term memory recall.
- Version history — git, event-triggered only (ticket created, status
  change, branch merge, explicit spec save, batch review commit). Not
  used for continuous/live field mutations.

### 2. Branch / Merge Semantics
Branching a chat creates a subticket. Closing a subticket "merges" it
by folding its resolution/context into the parent ticket's documentation
— a content fold, not a literal diff merge. The subticket itself remains
archived-but-linked (never deleted), so the branch graph stays fully
inspectable after merge.

### 3. Agentic Engine
Three distinct backend types, all behind a shared AgentModelClient
interface. No custom agent loop reimplementation needed for desktop.

```dart
abstract interface class AgentModelClient {
  Future<Stream<AgentEvent>> run(AgentRequest request);
}
```

**Status (as of `provider-configuration`, 2026-07-20):** only Claude
Agent SDK is implemented — `ClaudeAgentSdkClient`
(`aion/lib/core/agent/claude_agent_sdk_client.dart`), spawning a bundled
`agent_bridge/` Node.js process per call. Contrary to "Desktop — coding
execution" below, this MVP's sole implementation is the only provider
call the app currently makes at all (Settings' connection test; the
future ticket-estimation/spec-phase callers below are still unbuilt),
not just coding execution — and every call runs with tool access fixed
off (`agent_bridge/index.mjs`'s `allowedTools: []`), since there is no
coding-execution caller yet to need it. The rest of this section, and
all of §5 below, describe the long-term multi-provider/multi-phase
vision this MVP is a first step toward, not what's built today — see
`aion-arch/changes/provider-configuration/design.md` §6 for the
reasoning behind scoping this down.

#### Desktop — coding execution
Delegated to the user's configured coding-execution provider (currently
only Claude Agent SDK: a Node.js subprocess, controlled via dart:io
Process, exposing the full Claude Code agent loop — file edits, git,
bash, MCP, subagents, permission system — authenticated via the user's
Claude plan). Only invoked when a Task ticket is ready for coding
execution (/apply equivalent). Not used for ticket management, watcher
reviews, or spec work.

#### All platforms — conversational reasoning
Anthropic Messages API (or any configured provider) via direct HTTP
using dio. Used for: spec phase (explore/propose/verify/archive),
watcher reviews, ticket estimation, brainstorm-to-ticket promotion,
AI-authored comments. Fully cross-platform — works on desktop, mobile,
and web equally. Billed per token at standard API rates; user supplies
their own API key. NOT covered by Claude Pro subscription.

#### Mobile/web — lightweight text tasks (on-device)
flutter_local_ai (Apple Foundation Models / Android Gemini Nano).
Summarize, draft description, triage suggestions. Free, offline,
no API key required. Tool-calling on Apple only; text-context-stuffing
fallback on Android (Gemini Nano does not support function calling).

#### Repo-map-lite (shared infrastructure)
Tree-sitter parsing for Dart only, simple file→symbol index,
file-modification-time cache, no ranking step at v1 (codebase too
small to need it). Serves double duty:
- LLM context — which symbols exist and where, fed into coding prompts
- Ticket-to-code linking — which files/symbols a ticket touched,
  feeds similarity-based estimation and auto-linking to parent epics

#### Watcher implementation note
The watcher is an Aion orchestration feature, not an agent capability.
Aion detects relevant events, assembles context from drift (ticket +
parent epic + related tickets + similar past tickets via embeddings),
calls the user's configured watcher model via the Messages API, parses
the response, and writes results back to drift (AI comment, scheduled
change, new task subticket). The coding-execution provider (e.g. Claude
Agent SDK) only enters the picture if the watcher's delegation decision
results in a Task ready for coding execution — at that point Aion hands
off to it.

### 5. Model Routing, Provider Configuration & Watcher System

**Status (as of `provider-configuration`, 2026-07-20):** only **Claude
Agent SDK** is configurable today, via a single Settings screen
(`aion/lib/features/providers/presentation/screens/settings_screen.dart`,
reached from `WorkspaceNavShell`'s secondary-actions popover) showing a
live connection-test result — not a static "auto-detected" credential
check; Agent SDK exposes no such introspection, so this is a real `ping`
call — and one global model dropdown (Opus 4.8 / Sonnet 5 / Haiku 4.5).
Anthropic API, Ollama, OpenAI, OpenAI-compatible, and Firebase AI Logic
all remain unbuilt. There is no `ModelRouter` and no per-phase/tier
"Settings → Models" screen yet — nothing in the app has a "phase" to
route between yet. The Budget gate described below is not a proactive
predictive gate — Agent SDK exposes no way to query remaining plan
usage-window budget, only a best-effort reactive signal
(`AgentOverageDetectedEvent`) surfaced informationally when the bridge
process detects one. Everything below this note describes the
long-term vision this MVP is a first step toward, not current
behavior — see `aion-arch/changes/provider-configuration/proposal.md`'s
Non-goals and `design.md` §6 for the full reasoning.

**Status (as of `sdd-ticket-execution`, 2026-07-21):** the standalone
"watcher" persona this section used to describe — an on-demand Tier 1
role reviewing every ticket creation/edit within an epic's subtree,
deciding tier delegation, asking the human to clarify/reorganize — is
dropped entirely. Every responsibility it was meant to cover already
has a concrete owner among the SDD-stage-specific chats this change
introduces (`TicketsCubit._spawnStageChat`), the Branch/Merge Semantics
decision (§2), and mid-task issue branching (deliberately out of scope
this round — see
`aion-arch/changes/sdd-ticket-execution/proposal.md`'s Out of scope):
the Propose-stage chat decomposes and creates child tickets, the
Archive-stage chat updates documentation, the Verify-stage chat handles
quality/hallucination review, and mid-task branching (once designed)
handles failure escalation. A standalone watcher persona would
duplicate this machinery under a different name — see
`aion-arch/ideas/sdd-workflow-in-ticket-system.md`'s Follow-up decisions
for the full reasoning trail. Ad hoc manual ticket edits outside an
active SDD-cycle chat get no automatic quality check as a result — an
accepted gap, consistent with this project's existing "sufficient at
personal scale" reasoning. `AutomationConfidence` is now implemented,
three-state (`auto | gated | manual`), with exactly one real consumer:
SDD-stage-triggering (`TicketsCubit.advanceSddStage`, gated by a single
global `AutomationSettingsRepository`-backed setting, editable in
Settings' "SDD Stage Automation" section). The budget gate and
batch-flush gate described below remain unbuilt concepts, not wired to
`AutomationConfidence` yet — the shared type is designed to support
them later without changing its shape, per "Shared automation-
confidence pattern" below.

#### Provider configuration (user-facing)
Users configure providers independently in Settings → Providers:
- Anthropic API — API key + model selection. Used for Messages API
  calls (spec phase, watcher, AI comments). Billed per token.
- Claude Agent SDK — authenticated via user's Claude plan
  (auto-detected). Used for coding execution only (desktop).
- Ollama / local — base URL (default localhost:11434), models fetched
  from /api/tags on save. Free, offline, desktop only.
- OpenAI — API key + model selection.
- OpenAI-compatible / custom — base URL + API key + model name.
  Covers any provider exposing an OpenAI-compatible endpoint.
- Firebase AI Logic — for mobile/web Google model proxy.

All providers implement AgentModelClient. ModelRouter resolves
phase → provider+model → client at runtime. No phase/tier logic
leaks into UI or ticket code.

#### Model assignment (user-facing)
Users assign a model per phase/tier in Settings → Models:
- Spec phase (explore / propose / verify / archive)
- Watcher (epic oversight, ticket review)
- Tier 1 — Frontier (epic/story reasoning)
- Tier 2 — Capable (medium tasks, manual override)
- Tier 3 — Execution (task implementation, coding)
- Lightweight (summarize/draft/triage — on-device, mobile/web only)

Dropdowns show only models from configured, reachable providers.
UX: simple mode collapses to "planning model" + "execution model"
for new users; per-phase assignment available under advanced toggle.
Defaults to the only configured provider if just one exists.

#### Capability tiers
- Tier 1 — Frontier: reasoning, architecture, planning,
  epic/story-level work, watcher reviews, spec phase.
- Tier 2 — Capable: moderate scoped work, manual override.
- Tier 3 — Execution: file edits, mechanical task implementation.
  On desktop: backed by the configured coding-execution provider (e.g.
  Claude Agent SDK).
  On mobile/web: not available (no filesystem/subprocess access).

#### Orchestration pattern
Tier 1 watchers decompose Epics/Stories into Tasks dispatched
downward. Tier 1 is always the architect for its own decomposition;
Tier 3 (the configured coding-execution provider, e.g. Claude Agent SDK,
on desktop) is the executor for leaf-level coding work. If Tier 3 fails
repeatedly, the escalation mechanism hands the Task back to Tier 1,
which fixes it directly or determines the Task was mis-scoped and needs
splitting.

#### Change review & batching
Small edits to tickets enter a "scheduled" (pending review) state
instead of triggering immediate watcher review. They flush and get
reviewed together when:
- a significant event occurs in the same epic/story subtree
  (subtree-scoped, not global), or
- a configurable threshold is reached — either a count of pending
  changes, or an estimated cost (inferred from historical similarity;
  UI must prominently disclose this is an estimate, not a guaranteed
  cost ceiling).

Once a threshold hits, no further scheduled changes may be added
until the batch is applied. Behavior at that gate is configurable:
- auto-apply: flush and commit silently.
- defer: block and prompt the user to manually trigger the flush.

If an agent's task depends on fields with pending scheduled changes
(relevance-scoped — not "any pending change anywhere"), the user is
prompted to apply or proceed knowingly stale. Configurable:
always ask / always proceed / always apply.

Conflicting scheduled edits to the same field are surfaced as a diff
chain at review time, never silently resolved.

#### Budget gate
A user-set cost threshold (or "unlimited — never ask") triggers a
consent prompt before using a paid model when approaching the limit.
Cost-based thresholds are estimates only (inferred from historical
similarity) — the UI must disclose this wherever a cost-based
threshold is configured. Configurable: prompt always / prompt near
limit / never prompt.

#### Shared automation-confidence pattern
The budget consent gate, the batch-flush gate, SDD-stage-triggering,
and the stale-context prompt are all instances of the same underlying
setting shape: `auto | gated | manual` (three states, not the
`auto-override | ask-first` two-state version this section originally
described — extended when `sdd-ticket-execution` shipped
`AutomationConfidence`'s first real implementation). Modeled as one
shared `AutomationConfidence` type with per-context overrides — not
independent flags per subsystem. `auto` applies the decision silently;
`gated` surfaces it and waits for explicit confirmation; `manual`
never surfaces proactively, requiring the user to initiate the action
themselves via an always-available control. Ensures consistent UI and
easy extension as new automated decision points are introduced — SDD-
stage-triggering is the only real consumer today (see the Status note
above); the budget gate and batch-flush gate remain unbuilt.
