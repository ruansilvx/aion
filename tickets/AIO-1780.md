# Design: Reject Epic Reparenting

## Architecture

No new widgets, no new BLoC states, no new repository methods. This change
layers a validation-and-visibility rule onto the exact mechanism
`parentid-editable` already built (`TicketsCubit.updateTicketParent`,
`TicketParentPicker`).

## Cubit change

`TicketsCubit.updateTicketParent` (`tickets_cubit.dart`) gains one
short-circuit, placed after the existing self-parent check and before the
`getAllTickets()`/cycle-check block — this ordering skips an unnecessary
repository round trip when the ticket is an epic:

```dart
Future<void> updateTicketParent(Ticket ticket, String? newParentId) async {
  if (newParentId != null) {
    if (newParentId == ticket.id) {
      await _emitInvalidParent(ticket.id);
      return;
    }
    if (ticket.type == TicketType.epic) {
      await _emitInvalidParent(ticket.id);
      return;
    }
    final all = await _repository.getAllTickets();
    final descendantIds = _descendantIds(ticket.id, all);
    if (descendantIds.contains(newParentId)) {
      await _emitInvalidParent(ticket.id);
      return;
    }
  }

  try {
    await _repository.updateTicketParent(ticket.id, newParentId);
    final refreshed = await _repository.getTicketById(ticket.id);
    if (refreshed != null) {
      emit(TicketDetailLoaded(refreshed));
    }
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

`updateTicketParent`'s dartdoc gains one added sentence: "Also rejects any
attempt to set a non-null parent on an `epic` ticket — epics are always
subtree roots (see `project.md`'s watcher system) — via the same rejection
path as self-parent/cycle."

`getValidParentCandidates` is **unchanged**. It answers "what can `ticket`
be reparented under," which stays type-agnostic — a `story` or `task`
choosing an epic as its parent is still the normal, expected case. The
epic-can't-have-a-parent invariant is about the ticket *being reparented*,
not about what appears in someone else's candidate list, so it's enforced
one level up in `updateTicketParent`, not in the candidate query.

## Widget change

`TicketDetailScreen.build` (`ticket_detail_screen.dart`), inside the
ticket-header `Column`'s children — the existing:

```dart
const SizedBox(height: AionSpacing.sp8),
TicketParentPicker(ticket: ticket),
const SizedBox(height: AionSpacing.sp12),
```

becomes:

```dart
if (ticket.type != TicketType.epic) ...[
  const SizedBox(height: AionSpacing.sp8),
  TicketParentPicker(ticket: ticket),
],
const SizedBox(height: AionSpacing.sp12),
```

Only the `sp8` spacer collapses together with the picker for epics — the
`sp12` spacer before the next `Row` stays unconditionally, so the vertical
rhythm above that row is identical whether or not the picker rendered. No
new tokens, no new colors, no new component — `TicketParentPicker` itself
is untouched.

## Validation & error toast

Unchanged. `TicketDetailScreen`'s existing `BlocListener` branch for
`TicketsErrorReason.invalidParent` —

```dart
} else if (state is TicketsError &&
    state.reason == TicketsErrorReason.invalidParent) {
  AppToast.show(context, context.l10n.ticketInvalidParentError);
}
```

— already fires for this new rejection path with no new branch needed,
since it's keyed on the error *reason*, not the specific cause.

## Why hide, not disable-with-tooltip

Considered showing a disabled `TicketParentPicker` with a tooltip ("Epics
can't have a parent") instead of omitting it outright. Rejected: this
codebase has no existing "disabled control + tooltip" pattern to build on
— introducing one would be a new interaction pattern for a single one-off
case. Type-conditional *visibility* (show/hide by `ticket.type`), on the
other hand, already has precedent in `tickets_list_screen.dart`. Hiding is
also simpler, and the epic/no-parent relationship is a fixed structural
fact rather than a transient state a tooltip would help someone recover
from.

## Test plan

`tickets_cubit_test.dart` gets one new case in the `updateTicketParent`
group: an epic-typed ticket fixture, `act`ed with a non-null
`newParentId`, asserting via `verifyNever` that
`repository.updateTicketParent` is never called, and expecting
`[TicketsError(reason: invalidParent), TicketDetailLoaded(epicTicket)]` —
mirroring the existing self-parent/descendant-parent test shape exactly.

No new widget test is added — this project doesn't widget-test
`TicketDetailScreen` (only Cubit/repository logic gets automated
coverage, per `project.md`'s testing section); the UI-visibility half of
this change is confirmed in the manual interactive pass instead, same as
`parentid-editable`'s T15.
