# Git Projection Commit Visibility

# Proposal: git-projection-commit-visibility

## What

Makes the "moved to trash" and "restored from trash" git-projection
events actually produce a visible commit, by serializing
`Ticket.deletedAt` into the ticket Markdown frontmatter. Also applies
`deletedAt` during `TicketDbReconstructionService`'s DB rebuild, a
related correctness gap the same root cause was already causing.

## Why

`trash-restore-git-projection`'s `verify-report.md` (CRITICAL finding
1) diagnosed why neither event has ever produced a commit, despite
both being wired: `TicketGitProjector.project` skips `git commit`
whenever `GitRepositoryClient.hasChanges` reports no working-tree
diff, and nothing trash or restore does changes any field
`TicketMarkdownSerializer` actually serializes — `deletedAt` isn't in
the frontmatter at all, and neither `DriftTicketRepository.trashTicket`
nor `.restoreTicket` touches `updatedAt`. So the file (re)written on
trash/restore is byte-identical to what's already committed, and the
commit is silently, deterministically skipped every time. Confirmed
against a real project's actual git history: zero commits mentioning
"trashed", ever.

This is the same underlying git-projection mechanism
`storage-embedding-git-sync` and `trash-restore-git-projection` both
built on top of — it's an existing-feature bug, not a new capability,
so it gets its own change rather than being bundled into either of
those.

## Scope

### In scope

- `Ticket.deletedAt` becomes a serialized frontmatter field
  (`core/markdown/ticket_markdown_template.dart` +
  `ticket_markdown_serializer.dart`), nullable ISO-8601, following the
  exact existing pattern `createdAt`/`updatedAt` already use. Appended
  at the end of `fieldOrder` (not inserted alongside `createdAt`/
  `updatedAt`) so every already-committed ticket file's frontmatter key
  order is undisturbed — an insertion partway through would reorder
  every existing key on that ticket's next write, producing a
  file-wide diff/commit unrelated to any real change.
- Once `deletedAt` is serialized, trashing or restoring a ticket
  genuinely changes the file's content (`null` <-> a real timestamp),
  so `TicketGitProjector`'s existing `hasChanges`-gated commit fires
  normally through the exact same code path already used by
  `'created'`/`'status-changed'` — no change needed to
  `TicketGitProjector`, `GitRepositoryClient`, or either caller
  (`TicketsCubit`'s `trashTicket`/`trashTickets`,
  `TrashCubit.restore`).
- `TicketDbReconstructionService._buildTicket` also reads `deletedAt`
  from parsed fields (same `fields.containsKey(...)` pattern already
  used for `parentId`/`estimate`/`timeSpent`), so a DB rebuilt from git
  correctly restores which tickets were trashed — previously every
  reconstructed ticket silently came back non-trashed regardless of its
  real state, since `_buildTicket` never set `deletedAt` at all. Same
  root cause (the field didn't exist in the wire format yet), so fixed
  alongside rather than left as a second follow-up for the identical
  underlying gap.
- Backward compatibility: a `tickets/*.md` file written before this
  change (no `deletedAt` key at all) still parses cleanly — missing key
  and "present but null" are already indistinguishable in
  `TicketMarkdownSerializer.parse`'s existing convention for other
  optional fields (`parentId`/`estimate`/`timeSpent`), and `deletedAt`
  follows the identical rule.

### Non-goals (explicitly out of scope)

- **Applying a hand-edited `deletedAt` back into the DB via
  `TicketMarkdownReconciler`** (the bidirectional `resource`/`page`
  sync path). `TicketMarkdownReconciler._apply` already deliberately
  excludes `parentId` for the same reason: `TicketRepository
  .trashTicket`/`.restoreTicket` carry cascade logic (trashing revives
  cascades to descendants; restoring revives trashed ancestors/
  descendants too) that a bare field write from a background
  reconciler would bypass entirely, risking a corrupted trash state the
  same way a bare `parentId` write risks a corrupted parent graph. This
  proposal only makes `deletedAt` round-trip through *parsing*
  (needed for `TicketDbReconstructionService`, which builds a fresh
  `Ticket` from scratch rather than mutating an existing row); it does
  not add a new case to `_apply` for it. Documented as a second "known
  limitation" on `TicketMarkdownReconciler`, matching its existing one
  for `parentId`.
- **The other two candidate fixes** `trash-restore-git-projection`'s
  `tasks.md`/`verify-report.md` named (bumping `updatedAt` on trash/
  restore, or a `TicketGitProjector` force-commit flag per event
  label). Serializing `deletedAt` was chosen over both: bumping
  `updatedAt` would conflate two different meanings on one field
  (content-edit timestamp vs. trash-state timestamp) and contradicts
  `trashTicket`/`restoreTicket`'s own existing dartdoc ("sets
  `deletedAt`... does not touch `updatedAt`"); a force-commit flag
  would produce a git commit whose diff shows no actual file change,
  which reads as confusing/noisy history rather than a real audit
  trail. Serializing `deletedAt` is also strictly more informative —
  the ticket's own file now visibly states its trash state — and fixes
  the DB-reconstruction gap as a side effect, which neither alternative
  would have.
- **A drift schema change.** `Ticket.deletedAt` and its drift column
  already exist (since `ticket-trash`) — this change only adds it to
  the *Markdown* wire format. No `AppDatabase.schemaVersion` bump, no
  migration.
