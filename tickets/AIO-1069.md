# List Board View And Column Visibility

# Proposal: List/board view persistence & board column visibility

## What we're building

Two small, related quality-of-life improvements to `TicketsListScreen`
(`/workspace/tickets`), both about the ticket list remembering what the
user last set up rather than resetting on every visit:

1. **Persist the List/Board view-mode choice.** Today `_TicketViewMode`
   is screen-local, non-persisted state that always resets to `board`
   on every screen open (per
   `aion-arch/changes/archive/ticket-sort-control-and-board-as-default-view`,
   which made `board` the fixed starting point). This proposal makes
   the user's last-chosen view mode persist per project and restore on
   the next visit — the same way filter selections and sort choice
   already do — so `board` remains only the *first-ever-open* default,
   not a value the screen snaps back to every time.

2. **Board column visibility.** Today's Board view spec is explicit
   that "all 6 columns always render... there's no configurable/
   persisted column order or visibility." A user who never uses, say,
   `Cancelled` or `Backlog` as a working column has to scroll past it
   every time. This proposal adds a "Columns" control (next to the
   existing Filters/Sort triggers, shown only in Board mode) that lets
   the user hide/show individual status columns, persisted per project
   and restored the same way. Column *order* stays fixed and
   unconfigurable — this is visibility only, not reordering.

## Why

Both gaps are the same shape as a problem this project has already
solved twice (filters, sort): a per-project display preference that
silently resets is a small but real daily friction for a tool used
every day. Making the view mode and the board's column set "sticky"
removes two repeated manual steps (switching back to List if that's
the user's actual preference; scrolling past columns that are never
used) with no new screens, no new data model, and a persistence
mechanism this codebase already has a proven, well-tested pattern for
(`SharedPreferences`-backed, project-id-prefixed repositories — see
`TicketListFilterRepository`/`TicketListSortRepository`).

## Scope

- Persist and restore the List/Board toggle per project.
- Add a per-project-persisted set of hidden board-status columns, with
  a checkbox-group "Columns" control mirroring the existing Filters
  popover's mechanics.
- Board column *order* is unchanged — still fixed at
  `TicketStatus.values` declaration order, just with hidden entries
  skipped.
- Hiding a column is a display preference only, not a workflow
  restriction: a ticket can still be moved into a hidden column's
  status via `MoveToStatusMenu` (it simply won't be visible on the
  board until that column is shown again). This mirrors the existing
  "board status changes are never drag-only" reasoning — a hidden
  column has no `DragTarget` to drop onto, but the keyboard/menu path
  stays fully functional.

## Out of scope

- Column *reordering* (drag-to-reorder columns, or any
  persisted/configurable column order) — a separate, larger feature;
  this proposal only touches visibility.
- Hiding columns in List mode — List mode has no columns; this is a
  Board-only control.
- A "restore all columns" one-tap action beyond just re-checking each
  one in the Columns popover — not worth a dedicated control for a
  6-row checkbox list.
- Per-device (as opposed to per-project) view-mode/column-visibility
  preferences — follows the existing filter/sort precedent of
  project-scoped `SharedPreferences`, not device- or user-scoped.
