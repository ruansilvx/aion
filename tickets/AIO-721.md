# Spec Delta: Delegated-Skill Provider-Discovery Capability

**Reconciled 2026-09-03:** checked against the current `aion-arch/specs/tickets.md` `aion-arch/specs/providers.md`'s "Wiring" section and the provider-portability work merged after it — the mechanism/behavior this delta describes is still present and architecturally coherent with current text. Identifiers the automated screen flagged as missing are private-method requalification (e.g. bare `_foo` vs `TicketsCubit._foo`), line-wrapped tokens, or names covered in a neighboring section rather than repeated here — not behavioral drift. the two-provider `ProviderRegistry` this delta's context depends on is confirmed current; the `supportsSkillDiscovery` capability this delta anticipated was later added by delegated-skill-provider-portability (see that change's own spec ticket).

Delta against `aion-arch/specs/providers.md` and `aion-arch/specs/
tickets.md`. Read alongside `proposal.md` and `design.md` in this
change folder.

## ADDED

- **`AgentProvider.supportsSkillDiscovery`**
  (`core/contracts/agent_provider.dart`, `bool`) — whether this
  provider's underlying agent discovers and can execute project-local
  `.claude/skills/<name>` skills on disk when sent a `/<name>`
  slash-command prompt. Same per-call-site-capability shape as the
  existing `supportsSessionResume`: declared once per `AgentProvider`
  implementation, consulted directly at its one call site
  (`TicketsCubit._fireSkillAttachment`), not folded into
  `ModelPhaseToolAccess`/`ModelRoutingCubit`'s phase-wide Settings-
  dropdown filtering.
  - `ClaudeAgentSdkProvider.supportsSkillDiscovery` → `true`.
  - `AnthropicMessagesApiProvider.supportsSkillDiscovery` → `false`
    (already unreachable for `delegatedSkill` today via
    `supportedToolAccessTiers: {noTools}`; this makes that exclusion
    explicit on the capability that actually applies, rather than
    leaving it an accidental side effect of a different, coarser
    filter).

## MODIFIED

- **`TicketsCubit._fireSkillAttachment`** — after resolving
  `(model, provider)` via `_resolveModelAndProvider`, when the
  attachment's `kind` is `SkillAttachmentKind.delegatedSkill`
  (`toolsEnabled == true`) and the resolved `provider
  .supportsSkillDiscovery` is `false`, throws a `StateError` naming
  `provider.displayName` before `ChatCubit.runChatTurn` is ever called.
  Caught by the method's existing surrounding `catch (e)`, which posts
  the existing `'Skill attachment failed: $e'`
  `CommentAuthorType.system` comment — no new failure-reporting path.
  `aionNativeTemplate` attachments (`toolsEnabled == false`) are
  unaffected; they never reach this check. The existing `finally`
  block's worktree cleanup is unaffected — the throw lands after
  worktree creation (if any) has already happened, so it's torn down
  through the same existing cleanup path as any other failure past that
  point. This covers `SkillAttachment`'s `WorkflowStatus`-targeted
  surface.
- **`TicketsCubit._runStageChatTurn`** — the same check, applied to
  this method's independent resolution of `(model, provider)` for a
  `delegatedSkill` attachment targeting an `SddStage` (gated on this
  method's own `attachmentToolsEnabled` local). Caught by this method's
  own existing surrounding `catch (e)`, which posts its own existing
  `'Stage advance failed: $e'` comment — a separate, pre-existing
  failure-comment text from `_fireSkillAttachment`'s, left as-is rather
  than unified. Found by `/verify` after the first `/apply` pass missed
  this second call site; `SkillAttachment` fires on entry to *either* a
  `WorkflowStatus` *or* an `SddStage` (exactly one), so both surfaces
  needed the identical fix.

## REMOVED

None.

## Behavioral note (not a code change, stated for completeness)

Given today's two registered providers, this change alters no
observable runtime behavior: `ClaudeAgentSdkProvider` (the only
provider `ModelPhase.execution` — and therefore `delegatedSkill` — can
resolve to today, since `AnthropicMessagesApiProvider` only supports
`ToolAccessTier.noTools`) declares `supportsSkillDiscovery: true`, so
the new check never trips in practice. The change exists to make the
next full-tool-access provider added under `ProviderRegistry` declare
this capability honestly, and to fail loudly and safely instead of
silently misbehaving if it doesn't.
