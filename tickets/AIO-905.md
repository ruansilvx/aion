# Generalized Live Refresh For All Ticket Writes

# Proposal: Generalized live-refresh for all ticket writes

## Why

`TicketsCubit._refreshDetailIfOpenAndAffected` already live-refreshes an
open `TicketDetailScreen` when a background write affects it, but only
for two hardcoded cases: the exact ticket shown, or — only when the open
ticket is a `story` — one of its direct Task/Bug children via
`updateTicketStatus`. `aion-arch/specs/tickets.md:6957-6964` documents
the resulting gap precisely:

> Two related cases remain unrefreshed without a manual reload: a
> **bulk** status/priority edit changing a Story's child Task/Bug, and
> an Epic's detail screen when a child Story's own `sddStage` advances.

Both gaps have the same root cause: the mechanism is hardcoded to one
`(parentType, childType)` pair (Story ← Task/Bug) and wired from exactly
one write method (`updateTicketStatus`). This proposal generalizes both
axes at once — see [generalized-live-refresh-for-all-ticket-writes](../../ideas/generalized-live-refresh-for-all-ticket-writes.md)
for the brainstorm that reached this direction.

## What's changing

- Replace the two hardcoded checks inside `_refreshDetailIfOpenAndAffected`
  with a small declarative table — `story → {task, bug}`,
  `epic → {story}` — checked generically: given a written ticket's type
  and its parent, look up whether `(parent.type, writtenTicket.type)` is
  a table entry, and refresh if that parent is the currently-open
  `TicketDetailLoaded` ticket.
- Widen `_refreshDetailIfOpenAndAffected` to accept a *set* of written
  ticket ids (mirroring `TicketRollupRecomputer.recompute`'s
  `Set<String> startIds` shape) instead of exactly one, so a single call
  after a bulk write can check every affected ticket in one pass.
- Wire this generalized check into every `TicketsCubit` write method
  whose written ticket type/relationship could match a table entry:
  `updateTicketStatus` (already wired — upgraded to the table-driven
  form), `updateStatusForTickets` (bulk status — newly wired, closes the
  named bulk gap), `advanceSddStage` (newly wired — closes the named
  Epic/Story `sddStage` gap), `trashTicket`/`trashTickets`/
  `updateTicketParent` (newly wired — a trashed, restored, or reparented
  child changes its parent's *live children* set, which the same
  Story/Epic preconditions read via `getTicketsByParent`), and
  `createTicket` (extended — a newly created child can also flip a
  parent's precondition, e.g. "at least one child exists").

## What's deliberately not changing

- **No central write-interception point.** `TicketsCubit` has no single
  low-level method every write funnels through — every existing side
  effect (`_recomputeRollupChain`, `_triggerGitProjection`,
  `_triggerEmbeddingRegen`) is fired explicitly by each write method
  that needs it, mirroring `TicketRollupRecomputer`'s own extraction
  from this same cubit. This change follows that same convention: the
  table-driven check is called explicitly from each relevant write
  method, not intercepted centrally. See `design.md` for the full
  reasoning.
- **`updatePriorityForTickets` (bulk priority) is not wired.** No table
  entry watches `priority` — neither Story's nor Epic's precondition
  computation reads a child's priority at all. The named gap's "bulk
  status/**priority**" phrasing refers to the shipped bulk-edit
  feature's name, not an implied priority dependency; wiring it would be
  a no-op call on every bulk priority edit.
- **`TrashCubit.restore` (restoring a ticket from the Trash screen) is
  not wired.** It lives in a different Cubit with no reference to the
  live `TicketsCubit` instance, and the Trash screen and
  `TicketDetailScreen` are mutually exclusive routes in Aion's
  single-pane navigation — there is no code path today where a human
  restores a ticket while some other ticket's detail screen is
  simultaneously open, and no background/automation process restores
  tickets either. Revisit only if either of those stops being true.
- **`TicketMarkdownReconciler`/`TicketRepairService`'s background
  trash/restore/reparent writes are not wired.** Same reason as above —
  neither service holds a reference to `TicketsCubit`. Out of scope; a
  much larger change than this one.
- **No field-level diffing.** The table matches on `(parentType,
  childType)` only, same as today's Story check — any write to a
  matching child type triggers a re-fetch of the open parent, regardless
  of which field changed. Consistent with the existing mechanism: a
  same-id re-fetch is already cheap and flicker-free
  (`getTicketById`'s Loading-skip), so filtering by field would add
  complexity without a real performance reason.
- **`estimateRollup`/`timeSpentRollup` stay on their own separate
  `TicketRollupRecomputer` mechanism**, not folded into this table. That
  mechanism recomputes and *persists* a rollup value across the whole
  ancestor chain on every write regardless of whether a screen is open;
  this one only *re-fetches for display* when a screen happens to be
  open right now. Different shapes, different concerns — left as a
  possible future idea, not resolved here.

## Non-goals

- Sweeping every `TicketsCubit` write method (there are roughly 80).
  Only methods that write `status`, `sddStage`, or a ticket's live
  parent/child membership are in scope — see `tasks.md`.
- Any new widget, screen, or visual component. This is a pure
  `TicketsCubit`-layer change (see `design.md` — no UI tasks, so the
  design gate below is not required).
