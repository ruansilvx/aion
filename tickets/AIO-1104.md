# Presentation — Cubit

- [x] T1. In `aion/lib/features/tickets/presentation/cubit/tickets_cubit.dart`,
      add the private helper `_refreshDetailIfOpenAndAffected(String
      writtenTicketId)`: if `state` isn't `TicketDetailLoaded`, return.
      If the loaded ticket's `id` equals `writtenTicketId`, `await
      getTicketById(...)` for it and return. Otherwise, if the loaded
      ticket's `type` is `TicketType.story`, fetch its direct
      `task`/`bug` children via `_repository.getTicketsByParent(id,
      types: const [TicketType.task, TicketType.bug])` and, if
      `writtenTicketId` is among them, `await getTicketById(...)` for the
      loaded story. Full dartdoc per `design.md`'s exact code block.

      Implemented with one refinement over `design.md`'s literal
      snippet: the Story-children query uses
      `TicketTypeHierarchy.executableTypes` instead of a hand-written
      `const [TicketType.task, TicketType.bug]` literal — that constant's
      own dartdoc explicitly says "anywhere a Story's rank-2 children are
      gathered for design-review-gate or SDD-readiness purposes should
      use this list instead of a `task`-only literal," and `getTicketById`
      itself already uses it for the identical query. Same value, more
      consistent with existing convention.

- [x] T2. In the same file, modify `getTicketById(String id)` to skip its
      `emit(TicketsLoading())` when the current `state` is already
      `TicketDetailLoaded` for this exact `id` — still emitting it in
      every other case. Per `design.md`'s "`getTicketById`'s
      Loading-skip" section exactly. Update the method's dartdoc with one
      added sentence noting the skip condition and why (mirrors
      `searchTickets`'s existing no-flash-over-content-already-shown
      precedent, scoped per-id).

      Implemented with one necessary addition beyond `design.md`'s
      literal snippet, found during implementation: `getTicketById`'s
      emit only ever carried `childDocs`/`linkedTickets`/`backlinks`/
      `gapsAndOpenQuestions`/`pendingToolProposal` from
      `loadDocumentRelations` (a *separate* call the screen fires for
      `resource`/`bug` tickets after the initial load) — never from
      itself. A same-id re-fetch that discarded those back to their
      empty defaults would silently blow away an already-open
      `resource`/`bug` ticket's visible Linked Tickets/Backlinks/Gaps
      sections (and a `chat` ticket's pending tool-confirmation banner)
      every time a background write refreshed it — a real regression,
      and the opposite of "lands invisibly" this task exists to achieve.
      Fixed by carrying those five fields forward from the previous
      `TicketDetailLoaded` whenever re-entering for the same `id` (the
      same condition already added for the Loading-skip) instead of
      leaving them at their constructor defaults. `story` tickets are
      unaffected either way (the screen never calls
      `loadDocumentRelations` for that type), so this doesn't change
      `_refreshDetailIfOpenAndAffected`'s Story/child-status refresh
      case at all — it only protects the direct-match case for the
      ticket types that actually populate those fields.

- [x] T5. In the same file, in `updateTicketStatus(String id, TicketStatus
      status)`, add `unawaited(_refreshDetailIfOpenAndAffected(id))`
      immediately after the existing `emit(TicketStatusUpdated(tickets,
      hasMore))` on the success path — after the git-projection step, per
      `design.md`. No change to the optimistic `TicketStatusUpdating`
      emission or the failure path.

      **Found and fixed while writing T6's tests, before any code ran:**
      `updateTicketStatus`'s own `TicketStatusUpdating`/`TicketStatusUpdated`
      emissions overwrite `state` *synchronously*, before this new call
      even runs — so a live `state` read at that point would never see
      the detail screen that was open when the call started, making
      `_refreshDetailIfOpenAndAffected`'s Story/child-status case
      permanently dead code as originally written in `design.md`. Fixed
      by capturing `state` into `stateBeforeThisWrite` at the top of
      `updateTicketStatus` (before its own emissions) and giving
      `_refreshDetailIfOpenAndAffected` an optional `TicketsState?
      fromState` parameter (defaulting to a live `state` read, which
      stays correct for the `createTicket`/`updateTicket` call sites —
      those chain onto `_estimationSuggester`'s completion well after
      their own synchronous emission, so "is a detail screen open right
      now" is the right question there). `updateTicketStatus` passes
      `fromState: stateBeforeThisWrite` explicitly. One consequence
      documented rather than engineered away: because
      `updateTicketStatus`'s own emissions already interpose a
      non-`TicketDetailLoaded` state, `getTicketById`'s Loading-skip
      condition can't apply for this path — the Story's detail screen
      still sees a brief `TicketsLoading` frame before the refreshed
      `TicketDetailLoaded` lands, unlike the fully invisible
      `createTicket`/`updateTicket` case. Still a strict improvement
      over today (no refresh at all, permanently stale until a manual
      reload) — not the fully flicker-free result originally described,
      but the flicker was already unavoidable given this single-cubit
      architecture's pre-existing behavior (any unrelated cubit
      emission already blanks `TicketDetailScreen`'s body to
      `SizedBox.shrink()` while it's outstanding).
