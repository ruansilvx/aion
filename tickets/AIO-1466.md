# Parentid Editable

# Proposal: Editable Ticket Parent (`parentId`)

## Problem

`Ticket.parentId` (the structural epic/story/task hierarchy field) can only
be set once, at creation time via `TicketsCubit.createTicket` — and even
that path is unreachable from the UI today, since `CreateTicketScreen`
never passes it. Once a ticket exists, nothing can change its parent:
`Ticket.copyWith` hard-codes `parentId: parentId` (never mutated), and
`DriftTicketRepository.updateTicket` never writes the `parent_id` column.
This is `aion-arch/specs/tickets.md`'s own flagged known gap:
`parentId` remains non-editable (structural hierarchy change, deferred).

Symptoms today:
- A task filed directly under the wrong story/epic can never be moved —
  the only workaround is delete-and-recreate, which loses comments and
  history.
- The "subtask" convention (spec: a task ticket parenting another
  task/story via `parentId`) can only be established at creation, so a
  ticket can't be demoted into a subtask of another after the fact.
- `TicketDao`/`DriftTicketRepository` have **no cycle-prevention or
  self-reference check anywhere** — this proposal must close that gap
  as part of making the field writable at all, or reparenting becomes a
  way to corrupt the hierarchy (self-parent, or a parent/child loop that
  breaks any future tree walk, e.g. estimate/timeSpent rollups per
  `tickets.md`'s rollup invariant).

## Goal

Let a ticket's parent be changed after creation, from the ticket detail
screen, while guaranteeing the hierarchy can never become cyclic or
self-referencing.

## Approach

Treat `parentId` as an isolated structural field, the same way `status`
already is: a dedicated `TicketRepository.updateTicketParent(id, parentId)`
method (mirroring `updateTicketStatus`), not folded into the generic
`updateTicket`/`copyWith` path. `Ticket.copyWith`'s existing "never
mutates `parentId`" contract is preserved untouched — no domain entity
change needed.

Per [[project.md's State Management convention]] (Cubits may hold
business/domain logic; repositories stay dumb persistence layers), all
cycle/self-reference validation lives in `TicketsCubit`, not in
`DriftTicketRepository` or `TicketDao`. The repository's
`updateTicketParent` performs a plain, unvalidated column write — the
same trust boundary `updateTicketStatus` already establishes. `TicketsCubit`
is the only production caller of the repository, so this is a real
enforcement boundary in practice, not just a style preference — see
`design.md` for the explicit tradeoff this implies.

A new `TicketParentPicker` overlay widget (detail screen only) lets the
user search/select a new parent from a cycle-filtered candidate list, or
clear it back to "No parent." Setting parent at ticket-creation time
remains out of scope for this change (see below).

## Out of scope

- **Parent selection at creation time.** `CreateTicketScreen`/
  `TicketsCubit.createTicket` already thread `parentId` end-to-end at
  the domain/data layer — only the UI form field is missing. That's a
  smaller, separate gap; bundling it here would blur this change's
  single focus (editing an *existing* ticket's parent). Worth a
  follow-up idea once this change ships.
- **Type-compatibility rules** (e.g. preventing an `epic` from becoming
  a child of a `task`). Not part of the flagged known gap; the only
  invariant this change enforces is structural (no self-parent, no
  cycles).
- **Rollup recalculation.** No estimate/timeSpent rollup exists yet
  (spec: "system-only, no UI planned" for embeddings; rollups aren't
  built either) — nothing to recompute on reparent today. Flagged in
  `design.md` as a landmine for whoever builds rollups later.
- **List/board re-render on reparent.** Confirmed via grep: no board or
  list view renders `parentId`/hierarchy today (only used for delete-
  blocking and data mapping), so refreshing just the single ticket via
  `getTicketById` — the same pattern `TicketsCubit.updateTicket` already
  uses — is sufficient. Not a gap this change needs to fix.
