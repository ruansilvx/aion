# Sdd Design Gate

# Proposal: sdd-design-gate

## What

Ports the CLI's `/design-brief` → `/design-sync` round-trip into the
ticket-driven `SddStage` workflow, per
`aion-arch/ideas/design-gate-for-ticket-driven-sdd-workflow.md`. Today, a
Story's `SddStage` sequence is `exploring → proposed → verifying →
archived` (`TicketsCubit.advanceSddStage`), and nothing in that sequence
ever checks whether a UI-touching Story actually got real design work —
the CLI-only design gate (`proposal.md`'s `PENDING`/`NOT REQUIRED`/
`APPROVED` field) has no equivalent on the ticket side at all.

This change makes the gate two new `SddStage` values, not a bolt-on
field:

```
exploring → proposed → designBrief → designSync → verifying → archived
```

1. **`proposed → designBrief` (or straight to `verifying` if skipped)** —
   once a Story's child Tasks all exist, scan their titles/descriptions
   for the same widget/screen/component/UI keywords `/propose`'s own
   design-gate logic already uses. If none touch UI, skip straight to
   `verifying`, identical to today. No new persisted field — this is
   computed fresh from the child Tasks each time, the same way the
   existing `proposed` precondition already fetches them.
2. **`designBrief`** — spawns a chat generating the same ready-to-paste
   Claude Design prompt `/design-brief` produces (Context / Existing
   design system / Feature to design / Components to specify / Export
   requirements / Mockup request), reusing the token-file contents the
   same way `/design-brief`'s own `cat`-injected context does — read off
   disk into the spawned chat's context, not fetched via any new tool
   access. Also auto-creates an empty `page`-type ticket ("Design —
   `<Story title>`"), linked to the Story via the existing
   `TicketLinkRepository` (`relatesTo`, the same mechanism Documentation
   pages already use) — this is where the human pastes their Claude
   Design export, mirroring `design.md` as its own artifact.
3. **`designBrief → designSync`** — unlocked once that linked design Page
   has real content (non-empty `description`).
4. **`designSync`** — spawns a chat whose context includes the linked
   Page's pasted content plus the actual `AionColors`/`AionText`/
   `AionRadius` token file contents (again read off disk into context,
   zero tool access — see [Grounding correction](#grounding-correction-no-new-tool-tier)
   below), asked to perform the same two checks `/design-sync` does
   (Material-widget-name leakage, color cross-reference) and end its
   reply with the literal line `DESIGN GATE: APPROVED` or `DESIGN GATE:
   PENDING`, mirroring `/design-sync`'s own final-summary line format.
5. **`designSync → verifying`** — unlocked only once the designSync
   chat's most recent reply says `DESIGN GATE: APPROVED`. A **"Retry
   validation"** action (new) lets the human re-run the check in place
   after fixing the Page content, re-assembling fresh context and
   posting another turn to the same chat — no new chat, no new stage.
6. **Tracker UI** — `TicketDetailScreen`'s existing 4-step SDD tracker
   becomes a variable 4-or-6-step tracker: full 6 steps while it's still
   unknown or confirmed-needed, collapsed to 4 (skipping `designBrief`/
   `designSync` entirely) once a Story is confirmed not to need design
   work.

Everything reuses `AutomationConfidence` (`auto|gated|manual`) exactly as
it already gates every other `SddStage` transition — no special-casing
per stage. `epic` tickets are unaffected: `designBrief`/`designSync` only
ever apply to `story` tickets, matching the existing "meaningless for
every other `TicketType`" treatment `sddStage` already has.

## Why

Flagged as a hard prerequisite by
`aion-arch/ideas/task-to-coding-execution-trigger.md`: that idea wants a
Task blocked from entering `inProgress` while its Story's design work is
outstanding, but nothing in the shipped ticket system can express "design
work is outstanding" today. Once this change ships, that precondition
collapses to "the Story's `SddStage` hasn't reached `verifying` yet" — no
separate field to check on the consuming side, since a Story that needed
design work can't reach `verifying` until `designSync` passes, and a
Story that didn't need it skipped straight there anyway.

## Grounding correction: no new tool tier

The brainstorm session that led to this idea concluded `designSync` would
need a new read-only tool-access tier — the first stage chat with any
file access at all — reasoning that `/design-sync` "genuinely greps the
codebase" the way `/apply` eventually will. Re-reading
`aion-arch/.claude/skills/design-sync/SKILL.md` while grounding this
proposal shows that's not actually what it does: its Material-widget
check greps the text of `design.md` itself (the pasted export), and its
token cross-reference only checks against `aion_colors.dart`'s
already-known constants — both injected as static context via shell
`cat`, not a live tool call, and there's no implementation to check
against yet at this point in the cycle either way (design-sync runs
*before* any code is written for the Story).

So `designSync`'s ticket-driven equivalent needs no new capability at
all: the linked Page's content plus the token files' contents, assembled
as plain text the same way `_assembleStageContext` already assembles
every other stage's context (which already reads ticket data; this adds
reading a small, fixed set of token files off disk when `_projectRootPath`
is set — the same desktop-only-when-a-root-path-exists gate
`gitProjector` already uses). Confirmed with the user before writing
`design.md` — see this proposal's actual scope above, which has zero
`AgentRequest`/`ClaudeAgentSdkClient`/`agent_bridge` changes as a result.

## Scope

- New `SddStage.designBrief`/`SddStage.designSync` enum values.
- `TicketsCubit._nextSddStage` becomes ticket-aware and async (needs to
  inspect a Story's child Tasks to decide `designBrief` vs. `verifying`).
- `TicketsCubit._sddStageAdvanceCheck` grows two new stage cases.
- `TicketsCubit._spawnStageChat` grows two new stage branches (one of
  which also creates+links the design Page ticket).
- A new `TicketsCubit.retryDesignSync` method + a small "Retry
  validation" UI action on a `designSync`-stage chat's detail screen.
- `TicketDetailScreen`'s `_SddStageSection` tracker becomes
  variable-length; `SddStageBlockReason` grows two new hint values.
- New l10n strings for the two new stage labels/hints.
- **No drift schema change** — `SddStage` is stored as plain
  `.name` text with no DB-level constraint, so adding enum values needs
  no migration. No new `Ticket` field either (the design-review
  determination is computed on the fly from child Tasks, not persisted).

## Out of scope

- **The read-only tool tier** — dropped per the grounding correction
  above. `task-to-coding-execution-trigger`'s full read/write tier for
  Task coding-execution is unaffected and unrelated to this change.
- **Per-phase/tier model routing** — `designBrief`/`designSync` use the
  same hardcoded `AgentModel.sonnet` default every other stage chat uses
  today. `per-phase-tier-based-model-routing` (a separate idea, already
  `explored`) will route these to its "Capable" tier once it ships; no
  dependency in either direction.
- **`task-to-coding-execution-trigger`'s own scope** (Task-level
  `inProgress` trigger, execution queueing, PR-opening) — this change
  only makes the design-gate signal available for that idea to consume
  later; it does not itself touch Task tickets or coding execution.
- **Rich content editing for the design Page** — it uses the exact same
  page-content editing surface every other `page` ticket already has
  (per `create-edit-and-delete-pages`, already shipped); no new editor.
