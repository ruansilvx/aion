# Design: Live-Refresh an Open Ticket Detail Screen

## Architecture

No new widgets, no new BLoC states, no new repository methods, no
migration. This layers a "should I re-emit for the currently-open
ticket?" check onto write paths `TicketsCubit` already owns, exploiting
the fact that it's a single app-wide instance (provided once by
`WorkspaceShell`, not per-screen) — the same instance that owns
`TicketEstimationSuggester` is the same instance whose `state` may
currently be `TicketDetailLoaded` for the ticket a background write just
touched.

## The core helper

```dart
/// Re-fetches and silently re-emits [TicketDetailLoaded] for the
/// currently open ticket detail screen when a background write may have
/// changed data it depends on.
///
/// Two cases trigger a refresh:
/// - [writtenTicketId] is the ticket currently shown ([TicketDetailLoaded
///   .ticket.id] matches) — e.g. a passive AI-suggestion landed for it.
/// - The currently shown ticket is a `story` and [writtenTicketId] is one
///   of its direct `task`/`bug` children — e.g. a sibling Task's status
///   changed, which may flip [TicketDetailLoaded.canAdvanceSddStage].
///
/// No-ops when no detail screen is open, or the open ticket is unrelated
/// to [writtenTicketId]. Never flashes [TicketsLoading] — see
/// [getTicketById]'s Loading-skip note.
Future<void> _refreshDetailIfOpenAndAffected(String writtenTicketId) async {
  final current = state;
  if (current is! TicketDetailLoaded) return;

  if (current.ticket.id == writtenTicketId) {
    await getTicketById(current.ticket.id);
    return;
  }

  if (current.ticket.type == TicketType.story) {
    final children = await _repository.getTicketsByParent(
      current.ticket.id,
      types: const [TicketType.task, TicketType.bug],
    );
    if (children.any((c) => c.id == writtenTicketId)) {
      await getTicketById(current.ticket.id);
    }
  }
}
```

Placed as a private method on `TicketsCubit`, near `_recomputeRollupChain`
and the other background-orchestration helpers — same
"judgment logic kept in the Cubit, not the repository" convention
`TicketRollupRecomputer`/`TicketEstimationSuggester`/
`TicketContextEnricher` already follow.

The Story-children query is scoped to `[TicketType.task, TicketType.bug]`
deliberately, not "every child regardless of type" — `canAdvanceSddStage`'s
`proposed → verifying` precondition for a story specifically checks
Task/Bug `TicketStatus`, not a chat child's comment state or any other
child type, so a status write anywhere else (a chat, a page) never
triggers this query's `any()` to begin with — it wouldn't be in the
returned list.

## `getTicketById`'s Loading-skip

```dart
Future<void> getTicketById(String id) async {
  final alreadyShowingThis =
      state is TicketDetailLoaded && (state as TicketDetailLoaded).ticket.id == id;
  if (!alreadyShowingThis) {
    emit(TicketsLoading());
  }
  // ...unchanged fetch + canAdvanceSddStage/needsDesignReview computation...
}
```

This mirrors `searchTickets`'s existing "`TicketsLoading` only when
nothing is on screen yet" precedent, scoped to per-ticket-id instead of
per-list. Without this, every silent background refresh would flash a
loading spinner over content the user is actively looking at — the exact
flicker this feature exists to avoid. This also quietly smooths the three
*existing* re-fetch-via-`getTicketById` call sites (`updateTicket`,
`changeTicketStatus`, `regenerateComplexitySuggestion`) — a welcome side
effect, not a behavior change any of them depend on the absence of.

## Call site changes

**`createTicket`** and **`updateTicket`** — both already fire
`TicketEstimationSuggester.suggest(ticket)` `unawaited`. Chain the
refresh check onto that same future instead of discarding it bare:

```dart
// Before:
unawaited(_estimationSuggester.suggest(ticket));

// After:
unawaited(
  _estimationSuggester
      .suggest(ticket)
      .then((_) => _refreshDetailIfOpenAndAffected(ticket.id)),
);
```

`suggest()`'s own signature and internal behavior are unchanged — it
already returns `Future<void>` (it's `await`-able today, just not
awaited by these call sites). No change to `TicketEstimationSuggester`
itself.

**`updateTicketStatus(String id, TicketStatus status)`** — after its
existing `emit(TicketStatusUpdated(tickets, hasMore))` on success, add:

```dart
unawaited(_refreshDetailIfOpenAndAffected(id));
```

Fired after the list-facing state is already emitted, so the board's own
optimistic-drag feedback is never delayed by this check.

**`regenerate`/`regenerateComplexitySuggestion`/`regenerateEstimateSuggestion`
and `changeTicketStatus` are untouched** — they already re-fetch and
re-emit `TicketDetailLoaded` synchronously today (the explicit,
user-invoked paths), so they have no staleness gap to begin with.

## Why not a Drift `.watch()` stream or event bus

Considered and rejected: `TicketsCubit` being a single app-wide instance
already gives every write path direct access to `state`, so a reactive
stream layer would duplicate information the cubit already has for free.
A stream/watch approach would also need to re-derive `canAdvanceSddStage`/
`needsDesignReview`/`sddStageBlockReason` reactively for *every* Drift
row change app-wide (most of them irrelevant to whatever's open), where
this approach only ever re-checks on the exact write paths already known
to matter. Consistent with `project.md`'s existing brute-force-at-personal-
scale precedent — the cheapest correct thing, not the most general one.

## Test plan

New cases in `tickets_cubit_test.dart`:

- **Direct-match refresh**: seed a ticket, `emit`/reach
  `TicketDetailLoaded` for it via `getTicketById`, then call
  `updateTicket` with a changed `description` (fires `suggest`) against a
  fake `EmbeddingProvider`/model stub that resolves with a `complexity`
  suggestion. Expect a second `TicketDetailLoaded` carrying the
  AI-suggested value, with **no** intervening `TicketsLoading` in the
  emitted sequence.
- **Story/child refresh**: seed a `story` with one `task` child, reach
  `TicketDetailLoaded` for the story, then call `updateTicketStatus` on
  the task's id with `TicketStatus.done`. Expect a trailing
  `TicketDetailLoaded` for the story with `canAdvanceSddStage` flipped
  (using existing precondition fixtures), and no `TicketsLoading` between
  the two `TicketDetailLoaded` emissions for the story.
- **No-op: nothing open** — `updateTicketStatus` from `TicketsInitial`/
  `TicketsLoaded` triggers no extra `getTicketById` call
  (`verifyNever`-style check against a spy repository, or asserting no
  additional emitted states beyond the existing
  `TicketStatusUpdating`/`Updated` pair).
- **No-op: unrelated open ticket** — `TicketDetailLoaded` open for ticket
  A; `updateTicketStatus` fires for unrelated ticket B (not A's child).
  Expect no additional state emitted for A.
- **No-op: open ticket is a `task`, not a `story`** — confirms the
  Story-children query is skipped entirely (not just empty-result) for a
  non-story open ticket, via `verifyNever` on
  `repository.getTicketsByParent`.
- **`getTicketById` Loading-skip, standalone**: call `getTicketById` for
  an id already reflected in the current `TicketDetailLoaded` state;
  assert the emitted sequence contains no `TicketsLoading`. Call it again
  for a *different* id (simulating fresh navigation); assert
  `TicketsLoading` **is** still emitted first — the skip is scoped to the
  same id, not a blanket removal.

No new widget test — this project doesn't widget-test `TicketDetailScreen`
(Cubit/repository logic only gets automated coverage, per `project.md`'s
testing section). Manual verification confirms the visible effect (see
`tasks.md`'s Verification section).
