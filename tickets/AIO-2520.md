# Trash Screen Multi Select

# Proposal: Trash screen multi-select

## Why

`TrashScreen` already supports per-row Restore (no confirmation) and
Permanently Delete (destructive, confirmed), plus screen-level "Purge
old" and "Empty trash" actions that operate on everything at once. There
is nothing in between: restoring or permanently deleting a specific
*subset* of trashed tickets requires repeating the per-row action one
ticket at a time. `tickets.md`'s own Known Gaps section already flags
this: *"No multi-select inside the Trash screen itself (bulk restore,
bulk permanent-delete beyond the screen-level 'Empty trash,' which
already covers the all-at-once case)."*

`TicketsListScreen` already solved the identical problem for the live
ticket list via `TicketSelectionCubit` + `TicketSelectionBar`. This
change extends that same selection foundation to `TrashScreen`. See
`aion-arch/ideas/trash-screen-multi-select.md` for the full exploration
and `/explore trash-screen-multi-select`'s codebase-grounded follow-up
(both linked below) for the reasoning behind this proposal's specific
architectural choices.

## What

Add selection mode to `TrashScreen`, reusing `TicketSelectionCubit`
as-is (screen-scoped, provided around `/workspace/tickets/trash` the
same way `/workspace/tickets` already provides it) — no changes to that
cubit's own code. A new header toggle enters selection mode (disabled
when Trash is empty); while active, each `TrashedTicketTile` grows a
leading checkbox (row tap toggles selection instead of doing nothing,
which is all a Trash row's tap does today), and its per-row Restore/
Permanently-Delete buttons hide to avoid an ambiguous "act on this row
vs. act on my selection" affordance clash. A new floating
`TrashSelectionBar` — Cancel, selected count, Select-all/Deselect-all,
and exactly two actions — replaces nothing (`TrashScreen` has no FAB to
swap out, unlike the ticket list) and simply appears at the bottom while
selection is active. The header's "Purge old"/"Empty trash" actions hide
during selection, for the same "avoid an ambiguous scope" reason.

- **Bulk Restore** — no confirmation dialog, matching the existing
  single-row Restore's frictionless, reversible precedent regardless of
  selection size. A summary toast reports the count on success.
- **Bulk Delete forever** — a `destructive`-tone confirm dialog stating
  the *aggregate* count: selected roots plus their already-loaded
  `TrashLoaded.descendantCounts` (no new query — Trash already has this
  data in memory), mirroring how "Empty trash"/"Purge old" already state
  exact counts. A summary toast reports the count on success.

Selection is inherently root-only, since `TrashLoaded` only ever lists
trashed root tickets (see its own dartdoc) — descendants are folded into
each root's "+N subtasks" count, never given their own row. Both bulk
actions cascade per selected root exactly the way their existing
single-ticket counterparts already do.

### Implementation split: why bulk Restore and bulk Delete-forever are architected differently

Despite shipping together, the two actions take deliberately different
paths through the stack — decided during `/propose`, since the explored
idea only committed to "these two actions must exist," not their exact
plumbing:

- **Bulk Restore stays a loop over the existing single-ticket path**
  (`TicketParentTrashService.restore`, called once per selected id) — no
  new repository method. This is correctness-equivalent to a real batch
  call: the cascade invariant ("a live ticket never has a trashed
  ancestor") guarantees every id `TrashLoaded` calls a "root" already has
  a fully-live ancestor chain, so `restore`'s ancestor-revival step is
  always a no-op here, and two selected roots' subtrees can never
  overlap. Restore is also non-destructive and safely retryable, so
  there's no atomicity requirement forcing a single transaction. Looping
  reuses 100% of the existing, already-tested cascade + git-projection +
  rollup-recompute logic with zero new domain/data-layer surface.
- **Bulk Delete-forever gets a genuine new batch repository method**,
  `TicketRepository.permanentlyDeleteTickets`, mirroring `emptyTrash`'s
  existing single-transaction shape. Permanent deletion is irreversible,
  so an all-or-nothing transaction matters here in a way it doesn't for
  restore — a partial failure partway through a sequential loop would
  leave some selected tickets gone and others not, with no way back.

## Non-goals (explicitly out of scope)

- No change to `TicketSelectionCubit`/`TicketSelectionState` — reused
  verbatim, exactly as the explored idea concluded.
- No change to `TicketSelectionBar`, `BulkStatusMenu`, or
  `BulkPriorityMenu` (the ticket-list-specific selection bar) — Trash
  gets its own, much simpler `TrashSelectionBar` with two plain actions
  and no overlay/menu mechanics, since neither Trash action opens a
  sub-picker.
- No change to `TicketDao` — every bulk DB primitive
  (`restoreByIds`, `deleteTicketRows`, `getDescendantIds`) this change
  needs already exists.
- No new preview-count repository method for the bulk Delete-forever
  confirm dialog — it computes the aggregate client-side from
  `TrashLoaded.descendantCounts`, which is already loaded.
- No compact/breakpoint behavior for `TrashSelectionBar` (unlike
  `TicketSelectionBar`'s icon-only compacting at narrow widths) — two
  plain `AppButton`s are expected to fit or wrap reasonably without it.

  3× `Colors.transparent` (§1.1/§1.3/§1.6 of the export, the Select

  others); 1× `Colors.black.withOpacity(0.08)` (§3.4.2, the Delete-
  forever button's hover blend) → a literal `Color(0xFF000000)` (`
  Color.alphaBlend` itself isn't Material-specific). No other Material
  references found — "TicketListTile" (a plain text mention, not code)
  is Aion's own existing widget, not a false-positive match on
  Material's `ListTile`.
- **Token cross-reference:** every color in the export matches an
  existing `AionColors` field/constant exactly — all CONFIRMED, zero new
  tokens needed, matching the export's own claim. Two non-blocking
  implementation notes for `/apply`: (1) §3.1's bar shadow uses one-off
  hardcoded ARGB instead of an existing formula — prefer reusing

  the export uses `.withOpacity(x)` throughout — translate every
  occurrence to `.withValues(alpha: x)`, matching every existing
  `AionColors` extension method's convention.
- **Architecture decision:** the export specifies fully bespoke
  Restore/Delete-forever buttons on `TrashSelectionBar` (custom
  default/hover/focused/pressed/disabled states, a neutral-gray disabled

  this proposal's original placeholder plan of plain `AppButton
  (variant: secondary/destructive)` reuse — `AppButton`'s existing
  disabled/hover behavior doesn't reproduce what was designed. Adopted
  as designed: task 7 in `tasks.md` was rewritten to build bespoke
  widgets per the export instead of wrapping `AppButton`. Everything
  else in the export (the Select-mode toggle, the row checkbox/selected-
  row treatment, and the confirm-dialog content) matches or extends the
  original plan without contradiction — notably, the export's checkbox
  spec (§2.2) is pixel-identical to the already-existing `AppCheckbox`
  atom, so no change was needed there.
- **tasks.md:** 6 tasks annotated with the export's section references
  (tasks 7–12), qualified with the export's own title
