# Design: Preserve `ticketId` in `TicketDbReconstructionService` imports

## Scope

Data/domain layer only. No BLoC states, no widget tree, no presentation-
layer changes — nothing in `lib/features/tickets/presentation/` is
touched.

## Current call chain (the bug)

```
TicketDbReconstructionService._buildTicket()
  → builds Ticket(ticketId: <from file>, id: Uuid().v4(), ...)
  → TicketRepository.createTicket(ticket)     // ticket.ticketId ignored, by contract
      → DriftTicketRepository.createTicket()
          → companion = TicketsTableCompanion.insert(..., ticketId: '', ...)
          → TicketDao.insertTicket(companion, prefix)
              → transaction:
                  seq = TicketIdSequenceTable.seq + 1
                  ticketId = '$prefix-$seq'          // <-- caller's ticketId discarded
                  insert(companion.copyWith(ticketId: Value(ticketId)))
```

There is no insertion path anywhere in the stack that keeps a
caller-supplied `ticketId`. `TicketsTable.ticketId` is `unique()`, so any
fix must still respect that constraint.

## New call chain (this change)

```
TicketDbReconstructionService._buildTicket()
  → builds Ticket(ticketId: <from file>, id: Uuid().v4(), ...)
  → TicketRepository.importTicket(ticket)     // NEW — preserves ticket.ticketId
      → DriftTicketRepository.importTicket()
          → companion = TicketsTableCompanion.insert(..., ticketId: ticket.ticketId, ...)
          → TicketDao.insertTicketPreservingId(companion)
              → transaction:
                  insert(companion)                    // ticketId inserted as-is
                  suffix = parse trailing digits of companion.ticketId.value
                  if suffix != null and suffix > current seq:
                    TicketIdSequenceTable.seq = suffix  // prevents future collisions
```

`createTicket`/`insertTicket` are untouched — every other call site keeps
generating fresh sequential ids exactly as today.

## Why a separate method instead of a parameter on `createTicket`

Considered adding an optional `String? presetTicketId` parameter to the
existing `createTicket`/`insertTicket` methods instead of new methods.
Rejected: `createTicket`'s current contract — "the argument's `ticketId`
is always ignored" — is relied on by every other caller (`TicketsCubit`,
`ChatCubit`, `InboxCubit`, the create-ticket screens), and is asserted by
existing tests. Overloading it with a second, opposite-effect parameter
means every future reader of `createTicket` has to hold both semantics in
mind to know which one applies for a given call site. A separate,
narrowly-named `importTicket`/`insertTicketPreservingId` pair makes the
"this call preserves the id, that one doesn't" distinction visible at the
call site and grep-able to its one caller (`TicketDbReconstructionService`),
at the cost of two extra methods on the repository/DAO surface.

## Sequence-bump logic

`TicketsTable.ticketId` values are always `'$prefix-$n'` for a locally
configured `prefix` (default `AIO`) and integer `n`. `insertTicketPreservingId`
parses `n` from whatever `ticketId` it's given — the substring after the
*last* `-`, `int.tryParse`'d — regardless of whether its prefix matches
this device's currently configured prefix, and raises
`TicketIdSequenceTable.seq` to `n` if `n` is larger than the current value.

This deliberately doesn't check the prefix against `SharedPreferences`'s
`ticket_id_prefix`:
- If the imported ticket's prefix matches the local one (the expected
  case — reconstructing the *same* project that produced these files),
  bumping `seq` is exactly what's needed to prevent a later `createTicket`
  from re-issuing `n`.
- If the prefix differs (a device that hasn't configured a matching
  prefix yet), a locally-generated id can never collide with the imported
  one anyway, since local generation always uses the local prefix — so
  bumping `seq` on a differently-prefixed import is a no-op in terms of
  correctness (it may skip some future sequence numbers, but never causes
  a collision). Checking the prefix first would only add complexity
  without changing correctness, so it's left out.
- If `n` fails to parse (a hand-edited or otherwise irregular file-derived
  `ticketId`), the bump is skipped silently — the insert itself still
  succeeds, since `TicketsTable.ticketId` has no format constraint beyond
  uniqueness.

## Files touched

- `lib/features/tickets/data/daos/ticket_dao.dart` — new
  `insertTicketPreservingId` method.
- `lib/features/tickets/domain/repositories/ticket_repository.dart` — new
  abstract `importTicket` method.
- `lib/features/tickets/data/repositories/drift_ticket_repository.dart` —
  new `importTicket` implementation; shared companion-building logic
  factored out of `createTicket` to avoid duplicating the thirteen-field
  `TicketsTableCompanion.insert(...)` call.
- `lib/features/tickets/data/services/ticket_db_reconstruction_service.dart`
  — swap `createTicket` → `importTicket` on the true-import branch; update
  the class dartdoc's "Known limitation" paragraph, since this change
  removes it.
- `test/features/tickets/data/services/ticket_db_reconstruction_service_test.dart`
  — update the mock stub/verification from `createTicket` to
  `importTicket` for the "imports valid files as new tickets" case.
- `test/features/tickets/data/daos/ticket_dao_test.dart` — new tests for
  `insertTicketPreservingId` against a real in-memory drift database (per
  this file's own stated exception to the "mock the repository" testing
  convention — `flutter-conventions.md` treats sequence/uniqueness
  persistence behavior as something a mock can't catch a mistake in).
- `test/features/tickets/data/repositories/drift_ticket_repository_test.dart`
  — new test for `DriftTicketRepository.importTicket` end to end.
