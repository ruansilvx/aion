# Design: Inline `[[wikilink]]` backlinks

## Overview

New capability inside `lib/features/tickets/` and `lib/features/pages/`
(no new top-level feature — same rationale the Documentation section
itself used: this operates on `Ticket`/`TicketLink`-adjacent data that
already lives in `features/tickets/`). Three moving parts:

1. **Index** — a new `PageWikilinksTable`/`PageWikilinkRepository`,
   parallel to (not merged into) `TicketLinksTable`/`TicketLinkRepository`.
2. **Orchestration** — `TicketsCubit.updateTicket` gains the reindex/
   rename-rewrite side effect, the same place/pattern that already fires
   embedding regeneration.
3. **Presentation** — `BacklinksSection` renders a merged, origin-tagged
   list; `MarkdownEditor` gets a `[[`-triggered autocomplete; `MarkdownView`
   renders resolved wikilinks as tappable spans.

### `PageWikilinkRepository` (`domain/repositories/page_wikilink_repository.dart`)

```dart
/// Persists resolved inline `[[wikilink]]` references between `page`
/// tickets. Parallel to [TicketLinkRepository], not built on it — a
/// wikilink is derived from content, never user-authored, so it has no
/// remove/retype affordance and no [TicketLinkType].
abstract interface class PageWikilinkRepository {
  /// Every page that links to [targetPageId] — the raw rows behind a
  /// doc's wikilink-origin backlinks. [targetPageId] is always a `page`
  /// ticket's id — only pages produce *outgoing* references — but note
  /// that [getOutgoingLinks]' own `targetPageId` values (the other end
  /// of the same rows) may point at a `resource` ticket too, now that
  /// wikilink targets are widened beyond `page`-only (see design.md's
  /// "Resource participation, widened").
  Future<List<PageWikilink>> getIncomingLinks(String targetPageId);

  /// Every page [sourcePageId] currently links to — each id may be a
  /// `page` or a `resource` ticket.
  Future<List<PageWikilink>> getOutgoingLinks(String sourcePageId);

  /// Atomically replaces every outgoing row for [sourcePageId] with one
  /// row per id in [targetPageIds] (each a `page` or `resource` ticket
  /// id). The sole write path — called after every `page` save with the
  /// freshly re-parsed, freshly resolved set. An empty [targetPageIds]
  /// clears all of [sourcePageId]'s outgoing rows, correctly reflecting
  /// a page that removed its last reference.
  Future<void> replaceOutgoingLinks(String sourcePageId, Set<String> targetPageIds);

  /// Batch cleanup for permanent delete — removes every row where any id
  /// in [ticketIds] is source or target. Mirrors
  /// `TicketLinkRepository`'s `deleteLinksForTickets` shape.
  Future<void> deleteLinksForTickets(List<String> ticketIds);
}
```

## Core layer (`lib/core/markdown/` — pure Dart, no Flutter dependency)

### Resolution model (amended this session — see rationale below)

Originally, every `[[Title]]` reference resolved and stayed resolved
purely by matching literal title text, which forced two compromises:
duplicate page titles were ambiguous (first-match-wins, undocumented to
the user), and renaming a page required rewriting every referencing
page's raw content to keep old references matching the new title.

Aion already has a stable, unique per-ticket identifier —
`Ticket.ticketId` (e.g. `AIO-42`, generated by `TicketIdSequenceTable`,
already rendered via `AionText.key` wherever a "mono key" appears in
existing rows, including `LinkedTicketsSection`/`BacklinksSection`).
Anchoring wikilink resolution on that id instead of on title text
removes both compromises for anything the app itself authors, while
bare, hand-typed `[[Title]]` references keep working exactly as
originally designed (first-match, subject to staying in sync with the
current title) — a deliberate two-tier design, not a breaking change to
the original syntax:

- **`[[Title]]`** — resolves by case-insensitive exact title match
  against every live `page`/`resource` ticket (widened from `page`-only
  — see [Resource participation](#resource-participation-widened) below).
  First-match-wins (by `createdAt` ascending) on a duplicate title,
  same limitation as originally designed, now scoped explicitly to this
  form only. If the referenced page is later renamed, this reference
  stops resolving (no rewrite is attempted for it — see
  [Rename handling, narrowed](#rename-handling-narrowed-to-title-anchored-references)
  below) until a user fixes it by hand — the same "goes unresolved"
  fallback Obsidian itself uses outside its own awareness.
- **`[[TicketId]]`** (e.g. `[[AIO-42]]`) — resolves by exact `ticketId`
  match. Always unambiguous, regardless of how many pages share a
  title. Since there is no alias, the *displayed* text is the target's
  **current, live title** — resolved at render time, never baked into
  stored text, so it can never go stale. This is the form
  `MarkdownEditor`'s autocomplete inserts by default (see
  [`MarkdownEditor`](#markdowneditor-design_systemmoleculesmarkdown_editordart)
  below) — the raw Markdown source is a little less immediately
  readable (`[[AIO-42]]` instead of `[[Auth Notes]]`), but the
  *rendered* preview a reader actually sees always shows the correct,
  current title regardless, which matters more for the reading
  experience than the raw source's prettiness.
- **`[[Target|Alias]]`** — true alias syntax (either `Target` form
  above). `Alias` is literal, user-authored display text, rendered
  verbatim and never auto-rewritten — the link still resolves via
  `Target`, but the displayed label is whatever the user chose,
  independent of the target's actual title (Obsidian's own alias
  semantics). Not inserted by the autocomplete; available for anyone
  who types it by hand.

#### Resource participation, widened

Wikilink **targets** now include `resource` tickets, not just `page` —
both forms above resolve against every live `page`/`resource` ticket.
`resource` tickets still cannot be a wikilink **source**: they edit
`description` via the plain `InlineEditableField`, not `MarkdownEditor`,
so there's no editor surface to parse outgoing references from — that
half of the original gap stays deferred, unrelated to this widening.

#### Rename handling, narrowed to title-anchored references

Renaming a page still rewrites referencing pages' raw content — but
only occurrences that resolved via **title** text matching the old
title. An id-anchored reference (`[[TicketId]]` or `[[TicketId|Alias]]`)
never needs rewriting: its target never changes, and its displayed
title (when no alias is given) re-resolves live on every render. Since
`MarkdownEditor`'s autocomplete inserts id-anchored references by
default, the rewrite cascade's practical blast radius — and therefore
its failure/race exposure — shrinks to whatever fraction of references
were hand-typed as bare titles. See
[`TicketsCubit`](#presentation-layer--orchestration-ticketscubit) below
for what's still done to reduce that residual risk further.

### `WikilinkExtractor` (`core/markdown/wikilink_extractor.dart`)

```dart
/// One parsed `[[...]]` occurrence in a page's raw Markdown content.
class WikilinkMatch {
  const WikilinkMatch({required this.raw, required this.target, this.alias});

  /// The full matched text, brackets included — used to locate/replace
  /// this exact occurrence during a rewrite.
  final String raw;

  /// The text before an optional `|` — either a page/resource title or
  /// a `Ticket.ticketId` (see [WikilinkExtractor.looksLikeTicketId]).
  final String target;

  /// The text after an optional `|`, verbatim, or `null` if this
  /// occurrence has no alias.
  final String? alias;
}

/// Pure parsing/rewriting helpers for `[[Target]]`/`[[Target|Alias]]`
/// inline references. No Flutter dependency — same precedent as
/// `TicketMarkdownSerializer`, so `bin/ticket_lint.dart`-style tooling
/// could reuse it if ever needed. Resolution itself (matching a
/// [WikilinkMatch.target] against live tickets) is deliberately not
/// this class's job — it has no database access — see
/// `TicketsCubit`/`PageTicketProviderImpl` for that.
abstract final class WikilinkExtractor {
  /// Every distinct `[[Target]]`/`[[Target|Alias]]` occurrence in
  /// [content], each parsed into a [WikilinkMatch]. Matches
  /// `\[\[([^\[\]|]+)(?:\|([^\[\]]+))?\]\]`. Deduplicated by
  /// `(target, alias)` pair, case-insensitively on `target`, first-seen
  /// casing preserved.
  static List<WikilinkMatch> extractReferences(String content);

  /// Whether [target] looks like a `Ticket.ticketId` (e.g. `AIO-42`) —
  /// an uppercase-letter prefix, a hyphen, and a numeric suffix — rather
  /// than a title. A pure syntactic check; the caller still needs a real
  /// lookup to confirm a match actually exists.
  static bool looksLikeTicketId(String target);

  /// Replaces every case-insensitive occurrence of `[[oldTitle...`
  /// (bare or aliased, i.e. `[[oldTitle]]` or `[[oldTitle|...]]`) in
  /// [content] with the equivalent using [newTitle] in place of
  /// [oldTitle]. Only touches occurrences whose **target** matches
  /// [oldTitle] as literal text — an id-anchored occurrence's target is
  /// never a title, so this can never touch one, even if its alias text
  /// happens to contain the old title. Pure string transform; returns
  /// [content] unchanged if no occurrence matches.
  static String rewriteTitle(String content, String oldTitle, String newTitle);
}
```

## Data layer (`lib/features/tickets/data/`)

### `PageWikilinksTable` (`data/models/page_wikilink_model.dart`)

```dart
@DataClassName('PageWikilinkData')
class PageWikilinksTable extends Table {
  @override
  String get tableName => 'page_wikilinks';

  /// Internal UUID v4 primary key.
  TextColumn get id => text()();

  /// The `page` ticket whose content contains the `[[...]]` reference.
  TextColumn get sourcePageId => text().named('source_page_id')();

  /// The `page` ticket the reference resolved to.
  TextColumn get targetPageId => text().named('target_page_id')();

  /// When this row was (re)created — refreshed on every reindex, not
  /// preserved across a `replaceOutgoingLinks` call.
  DateTimeColumn get createdAt => dateTime().named('created_at')();

  @override
  Set<Column> get primaryKey => {id};
}
```

No FK constraints, matching every other table in this schema — integrity
enforced at the repository layer.

### `AppDatabase` changes

- Registers `PageWikilinksTable` + `PageWikilinkDao` in `@DriftDatabase`.
- Schema version 11 → **12**. `onCreate`: create `page_wikilinks` fresh.
  `onUpgrade` (`if (from < 12)`): create the table, **then run a one-time
  computed backfill** (precedent: version 9's rollup backfill) — select
  every live `page` ticket's `(id, title, description)`, build an
  in-memory `title.toLowerCase() → id` map from that same set, run
  `WikilinkExtractor.extractTitles` over each page's `description`,
  resolve against the map, and bulk-insert the resolved rows. This
  indexes `[[...]]` text a user may have hand-typed into an existing
  page *before* this feature shipped — without it, those references
  would silently miss the Backlinks section until each page happens to
  be re-saved. A fresh `onCreate` install has no pre-existing rows, so
  this step never runs there (same caveat version 9's backfill notes).

## Presentation layer — orchestration (`TicketsCubit`)

`TicketsCubit` gains one new optional constructor dependency,
`PageWikilinkRepository? pageWikilinkRepository` — same optionality
pattern as `_embeddingProvider`/`_gitProjector`/`_ticketLinkRepository`.
`null` (mobile/web-agnostic — this has nothing to do with desktop-only
gating, it's just "not wired up") makes every method below a no-op.

`updateTicket` gains a new tail step, gated exactly like the existing
embedding-regen trigger (`title`/`description` actually changed) and
additionally on `ticket.type == TicketType.page`. It also gains a second
new optional constructor dependency, `ActiveTicketViewRegistry?
activeTicketViewRegistry` — the same desktop-only registry
`TicketMarkdownWatcherService`/`TicketMarkdownReconciler` already use to
defer a write to a ticket the user currently has open — reused here to
defer (not skip) a rewrite that would otherwise clobber content the user
is actively looking at:

```dart
Future<void> updateTicket(Ticket ticket, {...}) async {
  // ...existing repository write, refetch, TicketDetailLoaded emit,
  // embedding-regen trigger, TicketEstimationSuggester trigger...

  if (pageWikilinkRepository != null && ticket.type == TicketType.page) {
    _reindexAndCascadeWikilinks(oldTicket: previousTicket, newTicket: refreshed);
    // fire-and-forget — same non-blocking precedent as embedding regen
  }
}

/// Resolves a wikilink [WikilinkMatch.target] against [candidates]
/// (every live page/resource ticket): an exact [Ticket.ticketId] match
/// when [WikilinkExtractor.looksLikeTicketId] says it looks like one,
/// otherwise a case-insensitive title match (first `createdAt` wins on
/// a duplicate title). Returns `null` when nothing matches.
String? _resolveWikilinkTarget(String target, List<Ticket> candidates) { ... }

Future<void> _reindexAndCascadeWikilinks({
  required Ticket oldTicket,
  required Ticket newTicket,
}) async {
  try {
    final candidates = await _repository.getAllTicketsByType(
      [TicketType.page, TicketType.resource], // widened — see design.md
    );
    final matches = WikilinkExtractor.extractReferences(newTicket.description ?? '');
    final resolvedIds = {
      for (final m in matches)
        if (_resolveWikilinkTarget(m.target, candidates) case final id?) id,
    };
    await pageWikilinkRepository!.replaceOutgoingLinks(newTicket.id, resolvedIds);

    if (oldTicket.title != newTicket.title) {
      // Only title-anchored occurrences can possibly need a rewrite —
      // an id-anchored one never contains the old title as its target.
      final referrers = await pageWikilinkRepository!.getIncomingLinks(newTicket.id);
      for (final link in referrers) {
        await _rewriteReferrerOrDefer(
          referrerId: link.sourcePageId,
          oldTitle: oldTicket.title,
          newTitle: newTicket.title,
        );
      }
    }
  } catch (_) {
    // Swallowed — matches embedding regen's existing non-blocking,
    // best-effort failure tolerance. Does not roll back the primary
    // ticket update that triggered it. Logged (not silently opaque) via
    // whatever debug-log facility this codebase already uses for
    // non-fatal background failures — not surfaced as a user-facing
    // notification; see design.md's "Known gaps, updated" for why that
    // remains out of scope this pass.
  }
}

Future<void> _rewriteReferrerOrDefer({
  required String referrerId,
  required String oldTitle,
  required String newTitle,
}) async {
  final referrer = await _repository.getTicketById(referrerId);
  if (referrer == null) return;
  final rewritten = WikilinkExtractor.rewriteTitle(referrer.description ?? '', oldTitle, newTitle);
  if (rewritten == referrer.description) return; // no title-anchored occurrence found

  if (activeTicketViewRegistry?.activeTicketId == referrerId) {
    // The user has this exact referrer open right now — rewriting its
    // content underneath them risks the same stale-Save race
    // TicketMarkdownReconciler already avoids for external file edits.
    // Defer: listen once for activeTicketId to change away from
    // referrerId, then retry — same "re-attempt once the active id
    // changes" pattern that service already uses.
    late final VoidCallback listener;
    listener = () {
      if (activeTicketViewRegistry!.activeTicketId != referrerId) {
        activeTicketViewRegistry!.removeListener(listener);
        unawaited(_rewriteReferrerOrDefer(
          referrerId: referrerId, oldTitle: oldTitle, newTitle: newTitle,
        ));
      }
    };
    activeTicketViewRegistry!.addListener(listener);
    return;
  }

  // Recurses through updateTicket — inherits file write-through,
  // embedding regen, and its own outgoing-link reindex for free. Cannot
  // recurse further: this call can never itself change a title.
  unawaited(updateTicket(referrer.copyWith(description: rewritten)));
}
```

`oldTicket` (the pre-write value) comes from wherever `updateTicket`
already resolves "did title/description change" for the embedding-regen
gate — `/apply` reuses that existing comparison rather than performing a
second lookup. `activeTicketViewRegistry` is `null` on mobile/web (it's
desktop-only, same gating as the watcher) — the deferral step is simply
skipped there, matching that platform's existing lower exposure to this
specific race (no separate file-watcher creating a second write path).

**`TicketMarkdownReconciler`'s watcher-driven apply path** (desktop-only,
external file edits) needs the same hook: after a successful,
non-`Unparseable` reconcile of a `page` ticket, it calls into the same
reindex/cascade logic `TicketsCubit.updateTicket` uses (including the
same id-or-title resolution and `ActiveTicketViewRegistry`-based
deferral for any rename-triggered rewrite) — `/apply` locates the exact
shared seam already used for "the same embedding-regen trigger as any
other content edit" (per `tickets.md`'s existing description of that
path) and wires wikilink reindexing through the identical seam, rather
than duplicating the extraction/resolution logic in the reconciler
directly.

## Presentation layer — relations query (`loadDocumentRelations` / `loadPageRelations`)

`TicketsCubit.loadDocumentRelations` and `PageTicketProviderImpl
.loadPageRelations` both change their `backlinks` computation from
"TicketLink rows where the other side is page/resource" alone to a
merge of two sources, each mapped to `BacklinkRef`:

1. Existing: `TicketLinkRepository`-derived rows where the other side's
   type is `page`/`resource` → `BacklinkRef(origin: explicitLink)`.
2. New (only when `ticketId`'s type is `page` **or `resource`** — widened
   along with the resolution-target change above — and only when the
   cubit/provider was constructed with a `PageWikilinkRepository`):
   `pageWikilinkRepository.getIncomingLinks(ticketId)`, each row's
   `sourcePageId` resolved to a `Ticket` → `BacklinkRef(origin: wikilink)`.
   A `resource` ticket can now show wikilink-origin backlinks on its own
   `TicketDetailScreen`, exactly like a `page` does on `PageDetailScreen`
   — only the *source* side stays `page`-only, per "Resource
   participation, widened" above.

Both lists concatenate into one `List<BacklinkRef>`. A page linked via
*both* an explicit `TicketLink` and an inline wikilink produces two
separate rows — a deliberate simplification (each represents a distinct,
independently-true relationship), not deduplicated.

`PageRelations`/`TicketDetailLoaded`'s `backlinks` field type changes
from `List<Ticket>` to `List<BacklinkRef>` accordingly.

## Presentation layer — widgets

### `BacklinksSection` (`design_system/molecules/backlinks_section.dart`)

Signature changes from `List<Ticket> backlinks` to `List<BacklinkRef>
backlinks`. Still fully read-only (no per-row mutation — unchanged).
Each row renders exactly as today when `origin == explicitLink`; when
`origin == wikilink`, renders an additional small trailing/leading
glyph or label distinguishing it as content-derived rather than
authored (exact visual — spacing, glyph, color token — resolved by the
Claude Design pass this change's design gate requires; functionally it
must be visually distinct, not identical to an explicit link row).

### `MarkdownEditor` (`design_system/molecules/markdown_editor.dart`)

Gains one new optional constructor parameter:

```dart
List<WikilinkSuggestionItem> Function(String query)? wikilinkSuggestions,
```

`WikilinkSuggestionItem` (new, `design_system/molecules/
wikilink_suggestion_list.dart` — see below) is a small, feature-agnostic
value type — `{required String ticketId, required String title, String?
breadcrumb}` — not a `Ticket`, so `MarkdownEditor` stays fully generic
(no `tickets`/`pages` domain type in its signature, preserving its
current design-system-eligible genericness) while still carrying the id
it needs to insert.

Internally: a `TextEditingController` listener detects a just-typed
`[[` with no closing `]]` yet in the current line, extracts the
in-progress query (text between `[[` and the cursor), and — only when
`wikilinkSuggestions != null` — opens a searchable overlay listing the
callback's result (capped, e.g. 20 rows) via `WikilinkSuggestionList`,
using **caret-anchored** `Overlay`/`LayerLink`/
`CompositedTransformFollower` positioning per design.md §4.1 (a `LayerLink`
pinned to the caret's insertion point, flipping above the caret if the
panel would overflow the viewport bottom) — built for real this pass,
not the field-anchored MVP simplification originally proposed (see
proposal.md's amended Non-goals). `Escape` or an outside tap dismisses,
matching every other overlay in the app.

Selecting a suggestion replaces the in-progress `[[<partial>` span with
**`[[<ticketId>]]`** — bare, no alias — not `[[<Title>]]`. This is
deliberate: an id-anchored reference never needs a rename-rewrite and
its rendered display always re-resolves to the *current* title live
(see design.md's "Resolution model" above), so the raw Markdown source
is a little less immediately readable but the rendered preview a reader
actually sees is always accurate. The cursor moves past the closing
brackets. When `wikilinkSuggestions` is `null` (no consumer today, but
keeps the widget genuinely optional), typing `[[` is inert — plain
literal characters, no overlay.

New file: `WikilinkSuggestionList` (`design_system/molecules/
wikilink_suggestion_list.dart`) — the overlay's row-list content,
generic (`List<WikilinkSuggestionItem> items`, `ValueChanged<
WikilinkSuggestionItem> onSelected`), same promotion-eligible
genericness bar as every other `design_system/` widget — `title`/
`breadcrumb` back its row rendering (design.md §4.2), `ticketId` is what
actually gets inserted on selection.

**No-match / create-on-the-fly** (design.md §4.5): when the query
matches nothing, `MarkdownEditor` shows the existing no-matches block.
Pressing Enter there calls a new optional `Future<WikilinkSuggestionItem?>
Function(String title)? onCreatePage` — when supplied, invoked with the
typed query; its returned item (the newly created page) is inserted the
same way a picked suggestion is. `null`/no callback means Enter is a
no-op in that state (matches design.md §4.5's stated fallback when
create-on-the-fly isn't wired up). `PageDetailScreen`/`PageCreateScreen`
wire this to `PagesCubit.createPage(title: query)`.

### `MarkdownView` (the shared AST-to-widgets renderer)

Gains three optional, generic callbacks:

```dart
Ticket? Function(String target)? resolveWikilink,
void Function(Ticket)? onWikilinkTap,
void Function(String title)? onCreateWikilinkTarget,
```

A new inline-node pre-processing step recognizes `[[Target]]`/
`[[Target|Alias]]` sequences inside paragraph/inline content (the same
non-standard-syntax handling precedent `MarkdownView` already applies
for GFM extensions it supports), parsed via `WikilinkExtractor
.extractReferences` — reused directly rather than a second ad hoc regex,
since `core/markdown/` has no Flutter dependency and `design_system/`
already imports `core/core.dart` for infrastructure like this. For each
match, `resolveWikilink(match.target)` decides the rendering:

- **Resolved** (non-`null` `Ticket`) — design.md §5: brackets dropped,
  `typePage`-colored, underlined, tappable (calls `onWikilinkTap`).
  Displayed text is `match.alias` when present (literal, user-chosen,
  never re-resolved), otherwise the resolved `Ticket.title` **live** —
  fetched fresh from the `Ticket` `resolveWikilink` just returned, so it
  can never go stale even without a rewrite.
- **Unresolved** (`null`) — design.md §6: brackets kept, muted
  `neutralTint` chip, non-interactive by default. When
  `onCreateWikilinkTarget` is supplied, the span becomes tappable too —
  invoking it with `match.target` (only when `match.target` doesn't
  itself look like a `ticketId` per `WikilinkExtractor
  .looksLikeTicketId` — an unresolved id-anchored reference means the
  target ticket was trashed/deleted, not that a new page should be
  created under that literal id string) — offering the same
  create-on-the-fly affordance design.md §4.5 specs for the
  autocomplete's own no-matches state, now available from already-saved
  content too, not just while typing. `null`/no callback keeps the span
  fully inert, as originally designed.

All three callbacks default to `null`, so every other `MarkdownView`
consumer (comments, descriptions, anywhere Markdown renders outside a
page) is completely unaffected — wikilink syntax there just isn't
specially recognized, identical to today's behavior.

### `PageDetailScreen` / `PageCreateScreen`

Both supply:

- `MarkdownEditor.wikilinkSuggestions` — a case-insensitive substring
  filter (capped, e.g. 20) over a cached candidate list, mapping each
  matching `Ticket` to a `WikilinkSuggestionItem(ticketId: t.ticketId,
  title: t.title, breadcrumb: ...)`.
- `MarkdownEditor.onCreatePage` — calls `PagesCubit.createPage(title:
  query)`, maps the returned `Ticket` to a `WikilinkSuggestionItem`.
- `MarkdownView.resolveWikilink` — `WikilinkExtractor.looksLikeTicketId
  (target) ? candidates.firstWhereOrNull((t) => t.ticketId == target) :
  candidates.firstWhereOrNull((t) => t.title.toLowerCase() ==
  target.toLowerCase())` against the same cached candidate list (client-
  side, same "brute-force ... sufficient at personal scale" precedent
  the rest of this design leans on).
- `MarkdownView.onWikilinkTap` — navigates via the existing
  `ticketDetailRoute(ticket)` helper, same as every other generic-by-id
  ticket navigation in this codebase.
- `MarkdownView.onCreateWikilinkTarget` — same `PagesCubit.createPage`
  call `onCreatePage` uses, then navigates into the newly created
  page's own detail screen (mirrors `PageCreateScreen`'s existing
  post-create navigation behavior).

The candidate list itself comes from a new `PagesCubit
.loadWikilinkCandidates()` query-only method (no state emitted — same
precedent as `getValidParentCandidates`/`getAllTickets`) delegating to
a new `PageTicketProvider.getWikilinkCandidates()` (below). Each screen
calls this once in `initState` and caches the result in local `State` —
no re-fetch per keystroke.

### `PageTicketProvider` (`core/contracts/page_ticket_provider.dart`)

New method:

```dart
/// Every live `page`/`resource` ticket, for wikilink-autocomplete/
/// resolution — widened beyond `page`-only since a wikilink can now
/// target a resource too (see design.md's "Resource participation,
/// widened"). No self/descendant exclusion — unlike parent-candidate
/// queries, a wikilink reference has no cycle constraint.
Future<List<Ticket>> getWikilinkCandidates();
```

Implemented by `PageTicketProviderImpl` as a direct
`TicketRepository.getAllTicketsByType([TicketType.page,
TicketType.resource])` passthrough — no business logic, matching this
provider's existing read-path convention.

## `WorkspaceShell` wiring

Constructs one `DriftPageWikilinkRepository` (wrapping the shared
`AppDatabase`) alongside the existing `TicketRepository`/
`TicketLinkRepository` construction, and passes it to both
`TicketsCubit`'s constructor and `PageTicketProviderImpl`'s constructor
— same wiring shape those two already share for `TicketLinkRepository`.
Also passes `TicketsCubit`'s existing `ActiveTicketViewRegistry?`
instance (already constructed there today for
`TicketMarkdownWatcherService`/`TicketRepairCubit`'s use — `WorkspaceShell`
doesn't need to construct a second one) into `TicketsCubit`'s new
`activeTicketViewRegistry` parameter, so the rename-rewrite deferral
described above shares the exact same "is this ticket currently open"
signal the file-watcher path already relies on.

## Known gaps / risks, updated

The id-anchored resolution model above (added this session) closes or
substantially narrows several gaps the original design left open:

- **Duplicate-title ambiguity** — closed for anything the app itself
  authors (autocomplete always inserts an id-anchored reference, always
  unambiguous). Bare, hand-typed `[[Title]]` references keep the
  original first-match limitation — a narrower, explicitly-scoped
  residual, not a global constraint on the Pages module (no page-title
  uniqueness is enforced).
- **Rename-rewrite risk & the concurrent-edit race** — the rewrite
  cascade's blast radius shrinks to title-anchored references only
  (id-anchored ones never need rewriting), and the
  `ActiveTicketViewRegistry` deferral directly closes the specific race
  of rewriting a page the user has open, for whatever title-anchored
  rewrites remain. Genuine cross-page atomicity is still not attempted —
  file writes and embedding regen aren't transactional resources to
  begin with — so a rewrite failure is still swallowed rather than
  surfaced as a user-facing notification; that residual is judged low
  enough stakes, given the shrunk blast radius, not to justify a new
  toast/notification pipeline this pass. Worth revisiting if it proves
  wrong in practice.
- **Unresolved-title UX** — the Claude Design pass already replaced
  "plain unstyled text" with a real, muted, chip-backed treatment (§6);
  this session adds the "create page" affordance on both ends (the
  autocomplete's own no-matches state, §4.5, and now also a tap on an
  already-rendered unresolved span, via `onCreateWikilinkTarget`).
- **`resource` participation** — targets now include `resource`
  tickets; `resource`-as-*source* stays deferred (an editor-architecture
  limitation, not a wikilink-specific one — resources use the plain
  `InlineEditableField`, not `MarkdownEditor`).

Still genuinely out of scope, unchanged: no path-qualified disambiguation
syntax (e.g. `[[Parent/Title]]`) beyond the id-anchored escape hatch;
`resource`-as-source; a caret-following popup was *not* actually a gap
this session resolved differently from originally speced — it was
already assumed caret-anchored by the Claude Design export (§4.1) and is
simply being built to match that, correcting `proposal.md`'s stale
Non-goal.

# Aion — Inline `[[wikilink]]` Backlinks: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Documentation Section Spec](./Aion%20Documentation%20Section%20Spec.md) (Backlinks §8.4, `typePage`/`typeResource` tokens), the [Page Content Editor Spec](./Aion%20Page%20Content%20Editor%20Spec.md) (`MarkdownEditor`/`MarkdownView` §1–2, inline-link precedent §2.2), and the [Create-form Parent Field Spec](./Aion%20Create%20Form%20Parent%20Field%20Spec.md) (overlay picker conventions §2–3). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing` by name.

**No Material widgets anywhere.** Every surface below is `DecoratedBox` / `Container` / `GestureDetector` / `MouseRegion` / `CustomPaint` / `Row` / `Column` / `Stack` / `Positioned` / `AnimatedContainer`, and the overlay is `Overlay` / `OverlayEntry` + `CompositedTransformTarget`/`Follower` — never `Card`, `Scaffold`, `AppBar`, `ListTile`, `ElevatedButton`, `TextButton`, `InkWell`, `Chip`, `PopupMenuItem`, `DropdownButton`, `ColorScheme`, or `ThemeData`. The one sanctioned exception app-wide is a bare `TextField` in a transparent `Material` (already encapsulated by `AppTextField`); the editor here builds on `MarkdownEditor` (Page Content Editor §1) and touches no other Material widget.

This feature turns a page's `[[Title]]` references into real, persisted, navigable connections: parsed on save, rewritten on rename, surfaced in the existing Backlinks section with a second row *origin*, autocompleted while typing, and rendered as tappable links in the page's own `MarkdownView` preview. **No new screens** — it modifies `PageDetailScreen`, `PageCreateScreen`, and `TicketDetailScreen`'s documentation-mode sections, and adds/extends molecules within them.

Four components need real design work (§3–§6); everything else in the change is backend/data-layer or reuses existing components unmodified. Both themes are specified for every component: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). Where the two differ only by token resolution, that is stated explicitly.

Companion mockups: [Aion Inline Wikilink Backlinks Mockups](./Aion%20Inline%20Wikilink%20Backlinks%20Mockups.dc.html).

Throughout: `c` = active `AionColors`; `a` = theme `fillAlpha` (Arctic `0.11` / Obsidian `0.16`); `isDark` = `theme.brightness == Brightness.dark`.

## 1. Foundations

### 1.1 No new named `AionColors`

Every value below derives from existing tokens. **`typePage` is the wikilink accent** for this whole feature — the origin tag (§3), the resolved inline span (§5), and the autocomplete accent hint (§4) all resolve from it, giving `[[wikilink]]` one coherent "page-reference" identity everywhere it appears.

| Token | Arctic | Obsidian | Role |
|---|---|---|---|
| `typePage` | `Color(0xFFB0499E)` | `Color(0xFFD98CE6)` | Wikilink accent — resolved span text, origin-tag glyph, suggestion accent hint |
| `textSecondary` | `Color(0xFF46586A)` | `Color(0xFFA2AEC6)` | Unresolved span text; origin-tag label |
| `textMuted` | `Color(0xFF8496A6)` | `Color(0xFF6B7690)` | Unresolved literal bracket glyphs; captions |

### 1.2 Why `typePage`, not `primary` (deviation from the MarkdownView link precedent, reasoned)

`MarkdownView` renders ordinary Markdown links `[text](url)` in `primary` with a `primary.withOpacity(0.4)` underline (Page Content Editor §2.2). A `[[wikilink]]` is **not** an arbitrary URL link — it is a reference to another Aion page, the exact concept `typePage` already brands (page chips, page icons, sub-page glyphs, the pages-module accent). Coloring wikilinks `primary` would make them indistinguishable from external/inline links in the same paragraph and would waste the one accent that already means "page." **Decision:** resolved wikilinks use `typePage`; ordinary Markdown links keep `primary` (unchanged). A reader scanning a paragraph can then tell an internal page reference from any other link at a glance. (If a later review prefers a single link color, the additive fallback is to swap §5's `typePage` for `primary` with no structural change — the states, underline, and geometry are token-parameterized.)

### 1.3 Derived tints & underlines (no new named constants)

All translucent fills via `token.withOpacity(x)`, never hardcoded ARGB. These reuse the established wash ladder (`fillAlpha` → `fillAlpha × 1.6`, the pressed-wash multiplier from Ticket Deletion §2.2 / Overlay Menu Item §1.3) and the `neutralTint` family (a quiet, non-accent informational tint derived from `textSecondary`):

```dart
// c = active AionColors, a = fillAlpha (0.11 Arctic / 0.16 Obsidian), isDark = Obsidian

// resolved wikilink (§5) — typePage accent
final wikilinkUnderline    = c.typePage.withOpacity(0.4);        // rest underline
final wikilinkHoverWash     = c.typePage.withOpacity(a);          // 0.11 / 0.16 — hover background chip
final wikilinkPressedWash   = c.typePage.withOpacity(a * 1.6);    // 0.176 / 0.256 — pressed background chip

// origin tag (§3) — typePage accent, subtle
final originTagFill         = c.typePage.withOpacity(a);          // 0.11 / 0.16

// unresolved wikilink (§6) — neutralTint family, inert (NOT accent, NOT danger)
final unresolvedFill        = c.textSecondary.withOpacity(isDark ? 0.14 : 0.09);  // neutralTint chip
final unresolvedBorder      = c.textSecondary.withOpacity(isDark ? 0.24 : 0.16);  // neutralBorderTint hairline

// overlay chrome (§4)
final focusRing             = c.primary.withOpacity(isDark ? 0.30 : 0.16);        // base §1.8 focus ring
final overlayShadow         = Colors.black.withOpacity(isDark ? 0.66 : 0.22);     // popover elevation, §4.1
```

### 1.4 Bracket-pair glyph (`wikilink` mark)

A small **double-bracket mark** `⟦ ⟧` is the feature's signature glyph, used on the origin tag (§3) and as the optional leading affordance on the resolved span (§5). Draw it as two thin bracket strokes (1.5px, same line family as the base icon set), **not** a text `[[`, so it renders crisply at small sizes and never inherits the surrounding font's bracket kerning. It is deliberately distinct from the `TicketLinkType` relationship glyphs (`blocks`/`relatesTo`/etc.) used elsewhere — those are directional link icons; this is a bracket pair, and it is **always paired with a word** on the origin tag (§3.2) so it can never be mistaken for a relationship badge.

- Sizes: `13px` (origin tag), `11px` (inline leading affordance, optional).
- Color: `typePage` (resolved/origin contexts), `textMuted` (unresolved literal brackets, §6).

### 1.5 Typography (all existing `AionText`)

| Token | Family / size / weight | Used for |
|---|---|---|
| `AionText.badgeLabel` | Manrope 11 / 600, sentence case | Origin-tag label `"In text"` (§3.2) — calm, not the uppercased `chip` |
| `AionText.chip` | Manrope 10.5 / 700, uppercase | Existing `"PAGE"` / `"RESOURCE"` type label (unchanged, §3.1) |
| `AionText.cardTitle` | Manrope 14 / 600 | Backlink & suggestion row titles |
| `AionText.body` | Manrope 15 / 500 | Rendered paragraph body (§5–6 host) |
| `AionText.breadcrumb` | Manrope 11 / 500 | Ancestor-path subtitle (backlink & suggestion rows) |
| `AionText.key` | JetBrains Mono 11 / 600 | Mono keys where a row shows one (reused, not a new scheme) |
| `AionText.caption` | JetBrains Mono 11 / 600, uppercase | Section eyebrow, overlay hint labels |

No new `AionText`, `AionRadius`, or `AionSpacing` members are introduced by this spec.

## 2. Row-origin model (shared context for §3)

`DocumentationBacklinksSection` (Documentation §8.4) currently renders one row shape for a single origin: **explicit** — another doc that authored a link to this page. This feature adds a second origin, **content-derived** — a doc whose `[[Title]]` reference resolved to this page. Both origins share one row skeleton (Documentation §8.4: leading 26×26 type-icon tint chip → title (+ optional breadcrumb) → trailing cluster); they differ **only** in the trailing cluster (§3.1 vs §3.2), so the two never differ in height and always align in a mixed list.

| Origin | Meaning | Trailing cluster |
|---|---|---|
| Explicit (existing, unchanged) | someone authored a link to this doc | `chip` type label only (`"PAGE"` / `"RESOURCE"`) |
| Wikilink (new) | discovered from a `[[…]]` reference in another doc's content | **origin tag** (§3.2) + `chip` type label |

## 3. Backlinks row — wikilink origin variant

Row container, leading type-icon chip, title, and breadcrumb are **identical** to the existing backlink row (Documentation §8.4) — reproduced here for a self-contained reference. The wikilink variant adds one element to the trailing cluster; nothing else changes.

### 3.0 Shared row geometry (both origins)

- Container: `GestureDetector` → `MouseRegion(cursor: click)` → `AnimatedContainer` (120ms fill/border), fill `surface`, `1px border`, radius `AionRadius.md` (10), padding `EdgeInsets.symmetric(horizontal: 12, vertical: 9)`. Whole row is tap-to-navigate (same as today).
- Structure: `Row`, `crossAxisAlignment: center`, `gap: 10`:
  1. **Type-icon chip** — `26×26`, radius `AionRadius.iconBtnSm` (8), fill `typePage.withOpacity(a)` / `typeResource.withOpacity(a)`, centered glyph `15px` (`file-text` page `typePage` / `bookmark` resource `typeResource`).
  2. **Title column** — `Expanded`, `Column`, `gap: 2`:
     - Title: `AionText.cardTitle`, color `textPrimary`, `maxLines: 1`, ellipsis.
     - Breadcrumb (optional): `AionText.breadcrumb`, color `textMuted`, `maxLines: 1`, ellipsis (ancestor path).
  3. **Trailing cluster** — `Row`, `crossAxisAlignment: center`, `gap: 8`, `MainAxisSize.min`: origin-dependent (§3.1 / §3.2).

### 3.1 Explicit-link origin (existing — unchanged)

Trailing cluster is the single type label:

- `AionText.chip`, uppercase (`"PAGE"` / `"RESOURCE"`), color `typePage` / `typeResource`, right-aligned. No fill, no border. This is exactly today's row.

### 3.2 Wikilink origin (new) — the origin tag

Same row, with the **origin tag** inserted as the first element of the trailing cluster, immediately left of the type label:

- **Origin tag** — a compact pill:
  - Container: `DecoratedBox`, fill `originTagFill` (`typePage.withOpacity(a)`), radius `AionRadius.sm` (6), padding `EdgeInsets.fromLTRB(6, 3, 8, 3)`, `MainAxisSize.min`.
  - Layout: `Row`, `crossAxisAlignment: center`, `gap: 5`:
    - **Bracket-pair glyph** (§1.4): `13px`, color `typePage`.
    - **Label:** `"In text"`, `AionText.badgeLabel` (Manrope 11 / 600, sentence case), color `textSecondary`.
- **Type label:** `AionText.chip` uppercase, color `typePage` / `typeResource` — same as §3.1, unchanged, sits to the tag's right.

Rationale: the tag reads as "this connection was **discovered from content**" — the bracket glyph signals wikilink syntax, the sentence-case `"In text"` names the origin plainly. Because it is a labeled pill (glyph **+ word**) and not a bare glyph, it cannot be confused with the glyph-only `TicketLinkType` relationship badges. The `typePage` tint ties it to the wikilink accent (§1.2) while the subtle `a`-opacity fill keeps it quiet — origin metadata, not a call to action. On narrow widths the breadcrumb ellipsizes first; the trailing cluster never wraps or truncates.

### 3.3 States (both origins — tap-to-navigate, identical to Documentation §8.3/§8.4)

| State | Fill | Border | Extra |
|---|---|---|---|
| **Default** | `surface` | `1px border` | — |
| **Hover** | `surfaceHover` | `1px borderStrong` | cursor `click`; origin tag & labels unchanged |
| **Focused** (keyboard) | `surface` | `1.5px primary` | focus ring `BoxShadow(color: focusRing, spreadRadius: 3, blurRadius: 0)` (base §1.8); the whole row is the focus target |
| **Pressed** | `surfaceHover` | `1px borderStrong` | `AnimatedScale` `0.99` (80ms) |
| **Disabled** | n/a | — | backlink rows are never disabled |

The origin tag and type label are **decoration inside** the row — they carry no independent hover/press state; only the row does. Theme parity: structure identical; all colors resolve from the active `AionColors` + §1.3 tints.

### 3.4 Empty

The Backlinks section is omitted entirely when there are no backlinks of **either** origin (derived — an empty section carries no affordance), exactly as Documentation §8.4. There is no wikilink-specific empty state.

## 4. `WikilinkSuggestionList` — autocomplete overlay

Triggered by typing `[[` inside a page's Markdown editor (`MarkdownEditor` raw textarea, Page Content Editor §1.2 / §1.5). A searchable, scrollable overlay listing up to ~20 page-title matches as the user keeps typing after `[[`. Same family as the app's existing `TicketParentPicker` popover (Create-form Parent Field §2.4): `OverlayEntry` + `CompositedTransformTarget`/`CompositedTransformFollower`, anchored to the caret, growing top-left, dismissed by `Escape` or an outside tap — no close button.

### 4.1 Panel chrome

- Anchor: a `LayerLink` pinned to the caret position (the `[[` insertion point). `CompositedTransformFollower` offset `(0, 6)` below the caret line; if the panel would overflow the viewport bottom, flip to render above the caret (offset `(0, -6)`, growing bottom-left).
- Container: `DecoratedBox` → `ClipRRect`, fill `surface`, `1px border`, radius `AionRadius.lg` (12), `clipBehavior: Clip.antiAlias`.
- Shadow (popover elevation, deeper than the flat card §1.8): `BoxShadow(color: overlayShadow, blurRadius: 40, spreadRadius: -12, offset: Offset(0, 18))` — soft, high, wide. Arctic `overlayShadow` = `black @ 0.22`; Obsidian = `black @ 0.66`.
- Width: `300` (matches the app's overlay width family; `TicketParentPicker` uses `320` — `300` here because rows carry no leading key column). Left-aligned to the caret.
- Max height: `284` (≈ 6 rows + header strip). Content beyond that scrolls in a `SingleChildScrollView`; scroll physics `ClampingScrollPhysics`. Rows are flush to the container inner edges (no per-row radius); the container radius clips the first/last row corners (Overlay Menu Item §1.5).
- Header strip (query echo, optional but recommended): `AionText.caption` `textMuted`, padding `EdgeInsets.fromLTRB(14, 12, 14, 8)`, showing the live query, e.g. `"[[ AUTH"`. Omit on very short heights.

### 4.2 Suggestion row

- Wrapper: reuse `OverlayMenuItem` (Overlay Menu Item §1) — `FocusableActionDetector` (Tab/Enter/Space, autofocus row 0) → `MouseRegion` → `GestureDetector` → `AnimatedContainer` (100ms fill). The row paints **fill only, no ring** for focus (Overlay Menu Item §1.4), consistent with the app's other overlay menus. `accent: null` (neutral rows).
- Row body (the `child`), padding `EdgeInsets.symmetric(horizontal: 14, vertical: 10)`, `Row`, `crossAxisAlignment: center`, `gap: 10`:
  1. **Accent hint** — a `typePage` dot: `7×7`, radius circular, color `typePage`. (Resources in the candidate set use a `typeResource` dot; pages use `typePage`.) A dot, not the full 26×26 icon chip, keeps the overlay dense.
  2. **Title column** — `Expanded`, `Column`, `gap: 2`:
     - Title: `AionText.cardTitle`, color `textPrimary`, `maxLines: 1`, ellipsis. The matched substring of the query is emphasized `w800` (same `textPrimary`) via `TextSpan`, as in Documentation §3.4 search.
     - Breadcrumb (only when the candidate has ≥1 ancestor): `AionText.breadcrumb`, color `textMuted`, `maxLines: 1`, ellipsis. Omitted (not empty) for root candidates, collapsing the row to one line (Create-form Parent Field §3.2).
  3. **Enter hint** (focused/hovered row only): a mono `↵` glyph `12px` color `textMuted`, right-aligned — signals "Enter inserts this." Hidden on unfocused rows.

### 4.3 Row states (neutral, Overlay Menu Item §5)

| State | Fill | Notes |
|---|---|---|
| **Default** | `transparent` | title + accent dot + breadcrumb |
| **Hover** | `surfaceHover` | `↵` hint appears |
| **Focused** (keyboard) | `surfaceHover` (= hover, no ring) | first row autofocuses on open; `↑`/`↓` move focus; `↵` hint shown |
| **Pressed** | `border` | `AnimatedContainer` 100ms |
| **Disabled** | n/a | rows are never disabled |

Selecting a row (`Enter`/`Space`/tap) replaces the in-progress `[[query` in the buffer with the canonical `[[Resolved Title]]` and closes the overlay, returning focus to the textarea after the inserted reference.

### 4.4 Empty-query state (just typed `[[`, nothing else)

The overlay opens immediately on `[[` with **no query yet**. Show the most recently edited / most relevant pages (product decides the ranking) as ordinary suggestion rows (§4.2), first row autofocused — so the user can arrow-and-Enter without typing. The header strip reads `"[["` (empty query). This is a populated, actionable state, **not** an empty state.

### 4.5 No-matches state (typed something, nothing matched)

- The scroll body is replaced by a single centered block, padding `EdgeInsets.symmetric(horizontal: 16, vertical: 22)`, `Column`, `crossAxisAlignment: center`, `gap: 10`:
  - Bracket-pair glyph (§1.4) `18px`, color `textMuted`.
  - Line 1: `"No pages match \u201c{query}\u201d"`, `AionText.body`, color `textSecondary`, centered.
  - Line 2 (create affordance, if the product supports create-on-the-fly): `"Press \u21b5 to create it"`, `AionText.bodySm`, color `typePage` — Enter creates a new page titled `{query}` and links it. If create-on-the-fly is out of scope for the MVP, drop line 2; the block is then informational only and Enter is a no-op.
- The header strip still echoes the query. `Escape`/outside-tap dismisses as always.

### 4.6 Theme parity

Structure identical across themes; only `overlayShadow` alpha (§1.3) and every `AionColors` token resolve per theme. No per-theme layout differences.

## 5. Inline wikilink span — resolved & tappable (in `MarkdownView`)

Where `[[Title]]` resolves to a live page, `MarkdownView` (Page Content Editor §2.2) renders it as a distinct inline run inside the surrounding paragraph — an internal page reference, visibly a link and tappable (navigates to that page). Built as a `TextSpan` with a `TapGestureRecognizer` inside the paragraph's `Text.rich`, plus a `WidgetSpan`-backed hover/press background when a background wash is shown (or an inline `MouseRegion`/`GestureDetector` if the renderer already wraps interactive spans).

### 5.1 Rendered text

- The `[[ ]]` brackets are **dropped**; only the resolved page **title** renders (Obsidian/Notion convention) — e.g. `[[Auth Epic Overview]]` → `Auth Epic Overview`. This is the signal that the reference resolved: clean title, no syntax noise.
- Optional leading affordance: the bracket-pair glyph (§1.4) `11px` `typePage` immediately before the title, `gap: 3`, when the host wants an explicit "this is a page link" marker. Default is **title-only** (no leading glyph) inside dense body copy; enable the glyph in wide-preview reading contexts. State the choice per call site; the mockup shows title-only.

### 5.2 States

Consistent with the app's inline-link treatment (Page Content Editor §2.2) but in the wikilink accent (§1.2):

| State | Text color | Underline | Background |
|---|---|---|---|
| **Default** | `typePage` | `1px` `wikilinkUnderline` (`typePage @ 0.4`), `decorationStyle: solid` | none |
| **Hover** (pointer) | `typePage` | `1px` full-strength `typePage` | `wikilinkHoverWash` (`typePage @ a`) chip behind the run, radius `AionRadius.sm` (4 here for a tight inline chip), padding H`3` V`1` |
| **Pressed** | `typePage` | `1px` full `typePage` | `wikilinkPressedWash` (`typePage @ a × 1.6`) |
| **Focused** (keyboard, if spans are focusable) | `typePage` | `1px` full `typePage` | `wikilinkHoverWash` (= hover) — fill, no separate ring, matching Overlay Menu Item §1.4 |
| **Disabled** | n/a | — | resolved spans are always live; an unresolvable one is §6, not a disabled §5 |

- Font weight matches the surrounding `AionText.body` run (no bolding — color + underline carry the link affordance). Line-height and baseline follow the paragraph (`height: 1.5`); the hover/press background chip must not shift the line box (draw it behind, via `background` paint / `WidgetSpan` sized to the text, not extra vertical padding that reflows).
- Cursor: `SystemMouseCursors.click` over the run; default elsewhere in the paragraph.

### 5.3 Theme parity

Identical structure; `typePage` and the §1.3 washes resolve per theme.

## 6. Inline wikilink span — unresolved (in `MarkdownView`)

Where `[[Title]]` matches **no** live page, it renders as plain, non-interactive text — legible as "this is wikilink syntax, not a typo," but visibly quieter than §5 and clearly not tappable. This is a deliberate, expected MVP state (a reference to a page that does not exist yet), **not** an error — so it uses the `neutralTint` family, never `danger`, and never `warning` (`warning` is reserved for `needsRepair`-style states elsewhere; a plain unresolved reference is calmer than that).

### 6.1 Rendered text

- The literal `[[ ]]` brackets are **kept visible** — e.g. `[[Deprecated Spec]]` renders with its brackets — which is precisely how it reads as *syntax that did not resolve* rather than a mistyped word. This is the deliberate inverse of §5.1 (resolved hides brackets; unresolved shows them).
- Layout: an inline chip drawn behind the text:
  - Background: `unresolvedFill` (`textSecondary @ 0.09 / 0.14`), radius `AionRadius.sm` (4), padding H`3` V`1`, drawn behind the run without reflowing the line box (as §5.2).
  - Optional `1px` hairline `unresolvedBorder` (`textSecondary @ 0.16 / 0.24`) — use the fill-only form in dense body copy, the fill+hairline form in wide-preview reading contexts where a firmer token edge helps.
- Text color: the title text `textSecondary`; the literal `[[` and `]]` bracket glyphs a step fainter, `textMuted`, so the eye reads the title first and the brackets as quiet syntax framing.
- Font: same family/size/weight as the surrounding `AionText.body` run — no italic, no strikethrough (those read as emphasis/deletion, not "unresolved").

### 6.2 States

Non-interactive:

| State | Treatment |
|---|---|
| **Default** | `unresolvedFill` chip, `textSecondary` title, `textMuted` brackets |
| **Hover** | **no change** — cursor stays `SystemMouseCursors.basic` (the default text cursor), no fill deepening, no underline. The absence of any hover response is itself the "not tappable" signal. |
| **Pressed / focused / disabled** | n/a — the span takes no pointer or focus |

### 6.3 Contrast with the resolved span (why they can't be confused)

In one sentence a reader sees: a **`typePage`-colored, underlined, bracket-free** run that lights up on hover (§5) versus a **muted, bracketed, chip-backed, inert** run that never responds (§6). Color (accent vs neutral), brackets (hidden vs shown), and interactivity (underline + hover vs none) all differ — three independent cues, so the two states are unambiguous even for a color-blind reader (brackets + interactivity carry the distinction without relying on hue).

### 6.4 Theme parity

Identical structure; `textSecondary` / `textMuted` and the §1.3 neutral tints resolve per theme.
