# Tasks: Generalized live-refresh for all ticket writes

All edits are in
`lib/features/tickets/presentation/cubit/tickets_cubit.dart` unless
noted. Complete in order — later tasks assume the widened
`_refreshDetailIfOpenAndAffected` signature from task 1 already exists.

- [x] 1. Add the `_liveRefreshDependents` const map (`Map<TicketType,
      Set<TicketType>>`, entries `story → {task, bug}`,
      `epic → {story}`) above `_refreshDetailIfOpenAndAffected`, with
      the dartdoc from `design.md` §2. Widen
      `_refreshDetailIfOpenAndAffected`'s signature from
      `String writtenTicketId` to `Set<String> writtenTicketIds` and

      "capture state before this method's own emissions" idiom.

- [x] 2. In `updateTicketStatus`, update its existing

- [x] 3. In `updateStatusForTickets`: capture `stateBeforeThisWrite =
      state` at the method's top, before `emit(const
      TicketsBatchStatusUpdating())`. After the existing
      `pendingAttachmentFires` firing loop (still inside the `try`
      block, following `design.md` §4's ordering), add
      `unawaited(_refreshDetailIfOpenAndAffected(writableIds.toSet(),
      fromState: stateBeforeThisWrite))`. Update the method's dartdoc to
      document this new side effect, following the phrasing pattern its
      existing dartdoc already uses for `_refreshBlockedBoardState`/
      attachment-firing.
      **CRITICAL bug found during `/verify`, fixed**: the call was
      originally implemented un-chained, in the statement order above
      (refresh call, then the `pendingAttachmentFires` loop below it) —
      textually matching "after the loop" only in the sense of coming
      later in the *loop's own position relative to other code*, not in
      actual execution order. `getTicketById` (which the refresh call
      delegates to) captures its own `previousDetail = state` **synchronously**,
      before this method's synchronous execution ever reaches the loop
      below it (calling an async function runs synchronously up to its
      own first internal `await`). A `gated`-confidence
      `_resolveAndFireAttachment` call has no internal `await` in its
      gated branch, so it emits `pendingSkillAttachment` fully
      synchronously, immediately after the refresh call yields — landing
      *before* the refresh's own later, async re-emission. That later
      re-emission then carries forward the *stale*,
      pre-attachment `previousDetail?.pendingSkillAttachment`,
      overwriting the banner the loop just set — for any bulk write
      whose `ids` include the ticket whose own detail screen is open, on
      a status with a `gated` attachment configured. Fixed by chaining
      the `pendingAttachmentFires` loop onto the refresh call's
      completion via `.then()`, mirroring `updateTicketStatus`'s own
      chaining (which this bug's root cause — the same hazard
      `updateTicketStatus`'s dartdoc already names — was supposed to
      replicate but didn't). Added a regression test:
      `'updateStatusForTickets does not clobber pendingSkillAttachment
      when the bulk-written ids include the currently-open ticket'` in
      `tickets_cubit_test.dart`'s `'Skill attachments (Phase 2)' → 'gated
      confidence — WorkflowStatus entry'` group — confirmed it fails
      against the pre-fix code (`Expected: 'attach-3c', Actual: <null>`)
      and passes against the fix.

- [x] 5. In `trashTicket`: **deviates from the original plan below** —

      previousState))` unconditionally within that `else`. Updated the

- [x] 7. In `updateTicketParent`: capture `stateBeforeThisWrite = state`
      at the method's top. In the `ParentChangeSuccess` case, after
      `emit(TicketDetailLoaded(ticket))`, add
      `unawaited(_refreshDetailIfOpenAndAffected({ticket.id},
      fromState: stateBeforeThisWrite))`. **Corrected during test-writing**:
      a single call using the written ticket's post-write `parentId`
      can only ever discover the *new* parent — the old parent is
      structurally undiscoverable that way, since nothing about the
      post-write ticket still points at it, so "one call covers both
      directions" (as originally planned above) was wrong. Also capture
      `oldParentId = ticket.parentId` (the method parameter, before the
      service call) and, in the same `ParentChangeSuccess` case, added a
      second targeted check: if `oldParentId` is non-null, differs from
      the ticket's new `parentId`, and `stateBeforeThisWrite` is
      `TicketDetailLoaded` for that old parent, look up
      `_liveRefreshDependents[stateBeforeThisWrite.ticket.type]` directly
      and call `getTicketById(oldParentId)` if the reparented ticket's
      type is in that set. Updated the method's dartdoc accordingly.

- [x] 8. In `createTicket`: add
      `unawaited(_refreshDetailIfOpenAndAffected({persisted.id}))`
      immediately after the existing
      `unawaited(_triggerGitProjection(persisted, 'created'))` line —
      independent of, and in addition to, the existing
      `_estimationSuggester.suggest(persisted).then((_) =>
      _refreshDetailIfOpenAndAffected({persisted.id}))` chain (updated

      stateBeforeThisWrite` to the new call — the *existing*
      suggester-chained call correctly keeps reading live `state`
      unchanged, since it resolves well after this method's own
      emissions complete. Updated the method's dartdoc to explain the
      two calls are independent.
