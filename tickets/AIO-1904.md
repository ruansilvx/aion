# Spec Delta: sdd-ticket-foundation

**Reconciled 2026-09-03, with real drift folded in:** this delta's TicketType.signal (a single combined type for raw ideas, known gaps, and open questions) was later split into three distinct types — TicketType.idea, .knownGap, .openQuestion — by the Idea/Known-Gap/Open-Question ticket types change (see that spec ticket's own reconciliation note). signal/ticketTypeSignal/AionColors.typeSignal no longer exist in current code; every other mechanism this delta introduces (TicketType.release, isAlwaysRoot, the canParent special-casing pattern) is otherwise unchanged and still accurate — only the signal half was superseded, not the ticket-foundation mechanism as a whole.

Delta against `aion-arch/specs/tickets.md`. Read alongside
[proposal.md](../proposal.md) and [design.md](../design.md) — this file
only lists what changes, not full current-state context.

## ADDED

- **`TicketType.signal`** (`domain/enums/ticket_type.dart`) — a raw idea,
  known gap, or open question. Parentless; may parent a `chat`, nothing
  else. Reuses every existing ticket mechanism (status, priority,
  search, embeddings, git projection, Trash) with no schema changes.
- **`TicketType.release`** (`domain/enums/ticket_type.dart`) — a named
  release/milestone. Parentless; may parent a `chat`, nothing else.
  Relates to `epic`/`story`/`task` tickets via the existing
  `TicketLinkType.relatesTo` cross-cutting link, not tree-parentage.
- **`TicketTypeHierarchy.isAlwaysRoot`** (same file) — `true` for
  `epic`/`signal`/`release`, `false` otherwise. New shared source of truth
  for "this type can never receive a parent," replacing three scattered
  `== TicketType.epic` comparisons (see MODIFIED below).
- **`ticketTypeSignal`/`ticketTypeRelease`** l10n keys (`lib/l10n/app_en.arb`)
  and matching `ticketTypeLabel` switch arms.
- **`AionColors.typeSignal`/`AionColors.typeRelease`** — new required
  color-token fields, one accent per theme (`arctic`/`obsidian`), feeding
  `TypeChip`'s tinted-fill rendering for the two new types.

## MODIFIED

- **`TicketTypeHierarchy.canParent`** — gains a second special case
  (alongside the existing `page` case): `signal`/`release` may parent
  `chat` and nothing else. Existing behavior for every other type pair
  is unchanged.
- **`TicketsCubit.updateTicketParent(Ticket ticket, String? newParentId)`**
  — the existing "epic can never receive a parent" rejection
  (`ticket.type == TicketType.epic`) is generalized to
  `ticket.type.isAlwaysRoot`, so `signal`/`release` tickets are now
  rejected the same way. Rejection path is unchanged: emits
  `TicketsError(reason: invalidParent)` then a re-emitted
  `TicketDetailLoaded` — no new `TicketsErrorReason` value.
- **`CreateTicketScreen`** (`presentation/screens/create_ticket_screen.dart`)
  — the parent-field visibility condition changes from
  `_selectedType == TicketType.epic` to `_selectedType.isAlwaysRoot`, so
  the parent field also hides when `signal` or `release` is selected. The
  type dropdown itself is unchanged (already includes every type except
  `page` by default, which already covered `signal`/`release`).
- **`TypeChip`** (`design_system/molecules/type_chip.dart`) — its color
  switch gains explicit `TicketType.signal => c.typeSignal` and
  `TicketType.release => c.typeRelease` arms, so neither type falls
  into the existing task-colored catch-all.

## REMOVED

None.

## Known gaps this change does not resolve

New gaps introduced by adding these two types, deliberately left open
per proposal.md's Out of scope:

- No UI affordance to promote/convert a `signal` ticket into an `epic` —
  creating that link (structural or otherwise) is entirely manual today,
  same as every other cross-ticket relationship without a dedicated
  creation flow.
- No dedicated "assign to release" UI — a `release`↔`epic`/`story`/`task`
  `relatesTo` link can only be created through whatever generic
  link-creation path already exists (see `tickets.md`'s existing gap:
  "still no general-purpose UI for browsing, editing, or deleting
  arbitrary `ticket_links` rows"). This change adds a valid use of that
  mechanism, not a new UI for it.
- No stored "current SDD stage" field yet — `signal` tickets have no way
  to track progress through the explore/propose/verify/archive cycle
  beyond the generic `TicketStatus` every ticket type already has.
  Deferred to the next change in this sequence (see proposal.md).
- No universal `Ticket.complexity` field yet (small/medium/large) — a
  real schema migration (new column), deferred alongside the SDD-stage
  field above for the same "no consumer yet" reason.
- `/what-next`'s ticket-native equivalent has no way to enumerate gaps/
  open questions against a spec page yet — the resolved design (a gap or
  open question becomes its own `signal` ticket linked to the spec page
  via `relatesTo`, not a parsed markdown section) is recorded in
  `aion-arch/ideas/sdd-workflow-in-ticket-system.md`, not built here.
