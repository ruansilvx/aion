# 6. `/verify` follow-up fixes (2026-09-08)

`/verify` found one CRITICAL and two WARNING findings against the tasks
above. All three fixed on the same branch, plus the accompanying
SUGGESTION — see `design.md`'s new "`/verify` follow-up" section for
the full rationale behind each.

- [x] **CRITICAL — concurrent git commits from loop-created tickets.**
      `lib/features/tickets/data/services/ticket_git_projector.dart`:
      added an internal FIFO queue (`_tail`/`_enqueue`) serializing every
      `project`/`projectBatch` call through one `TicketGitProjector`
      instance, so tickets created back-to-back in a loop (`TicketsCubit
      ._materializeParsedChildren`, backing SDD decomposition/
      verify-fixes materialization) can no longer fire concurrent `git`
      subprocesses against the same working tree and lose a projection to
      an `index.lock` collision. A failing queued call still throws to
      its own caller and does not block calls queued behind it. Added a
      `serialization (git-projection-concurrency-race)` test group to
      `test/features/tickets/data/services/ticket_git_projector_test.dart`
      covering both the queuing behavior (a blocked first call delays a
      second call's `git.add`) and the no-wedge-on-failure behavior.
- [x] **WARNING — trash/restore surfacing git errors as false
      failures.** `lib/features/tickets/data/repositories/
      git_projecting_ticket_repository.dart`: added a `_projectOrSwallow`
      helper (catches and discards a projection failure, since the
      trash/restore write it follows already succeeded) and switched
      `trashTicket`/`restoreTicket` to use it instead of the plain
      `_project` every fire-and-forget method still uses. Added two
      tests to `git_projecting_ticket_repository_test.dart` confirming
      `trashTicket`/`restoreTicket` complete normally even when the
      projector throws.
- [x] **WARNING — stale constructor dartdoc.**
      `lib/features/tickets/presentation/cubit/tickets_cubit.dart`:
      rewrote the constructor's dartdoc paragraph about `_gitProjector`/
      `_projectRootPath` to stop claiming `createTicket`/
      `updateTicketStatus`/`changeTicketStatus`/`updateStatusForTickets`/
      `advanceSddStage`/`updateTicketParent`'s projection depends on
      those fields (it doesn't anymore — it depends on `_repository`'s
      own type) and to correctly scope what still does:
      `_rollupRecomputer`'s batched projection and `trashTickets`'
      per-ticket loop.
- [x] **SUGGESTION — per-method dartdoc on the seven projecting
      methods.** Added a one-line `///` doc to each of `createTicket`/
      `updateTicketStatus`/`updateStatusForIds`/`updateTicketSddStage`/
      `updateTicketParent`/`trashTicket`/`restoreTicket` in
      `git_projecting_ticket_repository.dart` noting its event label
      and, where relevant, which pre-existing gap it closes.
- [x] Re-ran `flutter analyze` (still clean, same 2 pre-existing
      unrelated lints) and the full `test/features/tickets/` suite
      (1274/1274 — 1270 plus the 4 new tests above) and `test/core/`
      (263/263).
