# Trash Restore Git Projection

# Proposal: trash-restore-git-projection

## What

Wires the fourth, already-designed git-projection trigger event —
"restored from trash" — into `TrashCubit.restore`. `TicketGitProjector`
has supported a `'restored'` `eventLabel` since it was built; nothing
has ever called it with that label. This closes a gap `tickets.md`
documents in two places: its "Git projection" prose (only three of the
four originally-scoped trigger events are wired) and its "Known gaps"
list (`TrashCubit.restore` has no projector/`rootPath` access).

## Why

`storage-embedding-git-sync`'s own `tasks.md` (T25) flagged this
explicitly at the time rather than silently expanding scope:

> **Known gap**: the "restored" trigger lives in `TrashCubit`, which
> has no projector/root-path access and wasn't in this task's stated
> scope — flagged, not silently wired in.

The result is a real audit-trail inconsistency: today, trashing a
ticket produces a `tickets: <id> trashed` commit, but restoring it
back out of trash produces no commit at all. Anyone reading the
project's git history sees a ticket disappear from view with no
corresponding "came back" entry — the Markdown file on disk is also
never rewritten, so it keeps stating the ticket status the file had
right before it was trashed, with no visible record that the ticket
un-trashed at all.

The fix is small and precedented: `InboxCubit` already consumes the
same `WorkspaceShell`-provided `TicketGitProjector`/`rootPath` pair,
gated the same way, at the same `ShellRoute` nesting level that
`/workspace/tickets/trash` sits at. No new DI wiring needs to be
introduced — `TrashCubit` just needs to receive what's already in the
provider tree above it.

## Scope

### In scope

- `TrashCubit` gains optional `TicketGitProjector? gitProjector` and
  `String? projectRootPath` constructor parameters, following the
  existing no-op-when-null pattern `TicketsCubit` already established
  for the same desktop-only feature.
- `TrashCubit.restore(id)` fetches the restored ticket after
  `TicketRepository.restoreTicket` succeeds and fires a fire-and-forget
  git-projection call labelled `'restored'`.
- `app_router.dart`'s `/workspace/tickets/trash` route passes the
  already-provided `TicketGitProjector`/`rootPath` into the `TrashCubit`
  it constructs, gated on `rootPath != null` exactly like the
  `/workspace/inbox` route already gates its own git fields.

### Non-goals (explicitly out of scope)

- **Cascade projection of restored ancestors/descendants.**
  `TicketRepository.restoreTicket` also revives any currently-trashed
  ancestors and descendants of `id`, but only the explicitly-restored
  ticket gets projected here — mirroring `trashTickets`' existing,
  documented scope simplification for the symmetric trash-side case
  (`tickets_cubit.dart`'s `trashTickets` projects only the
  explicitly-requested ids, not their cascaded descendants).
- **A shared git-projection-trigger helper.** The
  no-op-if-null/else-call-`.project()` boilerplate is now duplicated a
  second time (`TicketsCubit` has its own copy). Given only two call
  sites exist and `InboxCubit` already tolerates an analogous
  duplication for its own git fields, extracting a shared mixin/service
  isn't justified yet — revisit if a third cubit needs the same trigger.
- **Bulk restore.** The Trash screen has no multi-select today (a
  separate tracked gap); this change only wires the single-ticket
  `restore(id)` path that already exists.

## Design decisions carried in from `/explore`

(Full reasoning in the `/explore` session that preceded this
proposal — no separate idea file; the investigation and the fix were
scoped in one pass.)

- Event label: `'restored'`, already named in `TicketGitProjector
  .project`'s own dartoc alongside `'created'`/`'status-changed'`/
  `'trashed'` — no changes needed to `TicketGitProjector` itself.
- Fire-and-forget (`unawaited`), matching every existing
  `_triggerGitProjection` call site — a trash restore must not block
  on git I/O.
- DI wiring copies `InboxCubit`'s established
  `_activeProject(context).rootPath != null` gate rather than
  inventing a new pattern.
