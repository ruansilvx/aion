# Per Phase Tier Based Model Routing

# Proposal: per-phase-tier-based-model-routing

## What

Today every model call Aion makes — every SDD-stage chat spawn
(`TicketsCubit._spawnStageChat`), every design-sync retry
(`TicketsCubit.retryDesignSync`), every coding-execution run
(`TicketsCubit._runCodingExecution`), and every human follow-up reply in
an existing chat (`ChatCubit.sendMessage`) — hardcodes `AgentModel.sonnet`.
Confirmed in code while grounding this proposal: all three `TicketsCubit`
call sites carry an explicit `// Out of scope:
per-phase-tier-based-model-routing.` marker (or an equivalent dartdoc
note) left by `sdd-design-gate` and `task-to-coding-execution-trigger`,
and `providers.md`'s "Known gaps" section states it plainly: "`AgentRequest`/
`AgentModelClient` resolve to exactly one globally-configured model —
there is no `ModelPhase` concept."

This change adds that concept: a `ModelPhase` enum (`frontier | capable |
execution`) bucketing every call site by how much reasoning weight the
job needs, independent of the tool-access tiers (`no-tools | read-only |
full`) `sdd-design-gate`/`task-to-coding-execution-trigger` already
established. Settings' single global "Model" dropdown is replaced by
three per-phase dropdowns. Every existing call site is rewired to resolve
its model through the phase it belongs to, instead of the `AgentModel.sonnet`
literal.

Concrete mapping (confirmed in `per-phase-tier-based-model-routing.md`'s
brainstorm session, re-verified against the shipped `SddStage` enum):

- **Frontier** — `SddStage.exploring`, `.proposed`, `.verifying` (epic/
  story-level judgment calls).
- **Capable** — `SddStage.designBrief`, `.designSync`, `.archived`
  (comparatively mechanical: prompt generation, checklist-style
  validation, doc updates).
- **Execution** — Task coding-execution.

## Why

Scoped narrowly, on purpose: `self-iteration-sequencing.md`
optimized for the fastest path to the point where Aion can drive its own
further development, and that point has now been reached and exercised —
`task-to-coding-execution-trigger` merged and is live. This is the one
piece of that critical path left unbuilt: `per-phase-tier-based-model-routing.md`'s
own `next_action` already flagged it as ready to `/propose`, non-blocking
on anything else, and self-contained. Its architectural-implications note
is explicit: "Fully independent axis from the tool-access tiers... doesn't
hard-block on either [sibling idea] shipping first... can `/propose` and
ship now."

Concretely, shipping this closes the last piece `project.md` §5 envisioned
for the desktop MVP: every reasoning-heavy stage (explore/propose/verify)
can run a stronger model than the mechanical stages (design-brief/design-
sync/archive) or the tool-enabled execution stage, instead of every call
in the app — regardless of how much judgment it requires — running the
same one hardcoded model.

## Grounding correction: the human-reply path was in scope all along

The idea file's own summary scopes this to "the SDD-stage/Task call
sites," and its "Open questions" never resolved what `ChatCubit.sendMessage`
(a human typing a follow-up message into an *already-spawned* chat)
should do. Re-reading `chat_cubit.dart`/`ticket_detail_screen.dart` while
grounding this proposal: `_sendComment` also hardcodes
`model: AgentModel.sonnet` for every reply, with its own out-of-scope note
("no per-phase model routing/composer picker exists yet").

Leaving that path out would mean a spawned chat's *opening* AI turn uses
the phase-correct model, but every human reply after it flips back to a
single hardcoded model regardless of which phase the chat belongs to —
visibly inconsistent (the "via `<model>`" line under each AI comment
would show the model changing mid-conversation for no reason) and
defeats the point of tiering a conversation's model choice at all. This
proposal folds that path in: `ChatCubit.sendMessage` now infers the
phase from the chat ticket's parent (its `SddStage` for an epic/story
parent, `ModelPhase.execution` for a Task parent) instead of taking a
`model` parameter from the caller.

Confirmed every chat ticket in the app is spawned exclusively by
`TicketsCubit` (`_spawnStageChat`/`_runCodingExecution` are the only two
`_repository.createTicket(...TicketType.chat...)` call sites in the
codebase) — a chat always has a parent, so this inference is reliable,
not a best-effort guess.

## Scope

- New `ModelPhase` enum (`features/providers/domain/enums/model_phase.dart`):
  `frontier | capable | execution`.
- New `SddStage.modelPhase` extension getter
  (`features/tickets/domain/enums/sdd_stage.dart`) mapping each stage per
  the confirmed split above.
- New `ModelRoutingRepository` interface + `SharedPrefsModelRoutingRepository`
  impl (`features/providers/domain/repositories/`,
  `features/providers/data/repositories/`) — `getModelForPhase`/
  `setModelForPhase`, one `shared_preferences` key per phase. A phase
  with no persisted value yet falls back to the legacy single-model key
  (`agent_settings.selected_model_id`) if present, else `AgentModel.sonnet`
  — an already-chosen model survives into all three tiers on first run,
  mirroring `AutomationContext.sddStage`'s key-preservation precedent
  from `task-to-coding-execution-trigger`.
- **Removes** `AgentSettingsRepository`/`SharedPrefsAgentSettingsRepository`
  and `ProviderSettingsCubit.selectModel` outright — fully superseded by
  the per-phase repository/dropdowns, not kept alongside it.
  `ProviderSettingsCubit`'s connection test now pings whichever model is
  currently configured for `ModelPhase.frontier`, re-read fresh on every
  `load()`/`testConnection()` call rather than cached, so it always
  reflects the latest Frontier-tier setting without the cubit needing to
  listen to `ModelRoutingCubit`.
- New `ModelRoutingCubit`/`ModelRoutingState` (`features/providers/presentation/cubit/`),
  structurally identical to `AutomationSettingsCubit`/`AutomationSettingsState`
  — loads/persists an `AgentModel` per `ModelPhase`.
- Settings screen: the single `AppDropdown<AgentModel>` under a "Model"
  label is replaced by a "MODELS" eyebrow and three `AppDropdown<AgentModel>`
  rows (Frontier/Capable/Execution), each with a one-line description of
  what that tier drives — same visual slot the old dropdown occupied,
  directly above the existing "AUTOMATION" section.
- `TicketsCubit`: new optional `ModelRoutingRepository` constructor
  dependency (mirrors the existing optional-dependency pattern for
  `agentClient`/`commentRepository`/`automationSettingsRepository` — falls
  back to `AgentModel.sonnet` when not supplied, so every existing test
  construction site keeps working unchanged). `_spawnStageChat`,
  `retryDesignSync`, and `_runCodingExecution` each resolve their model
  through the phase-appropriate lookup instead of the `AgentModel.sonnet`
  literal.
- `ChatCubit`: new required `TicketRepository` and `ModelRoutingRepository`
  constructor dependencies. `sendMessage` drops its `model` parameter and
  resolves the model internally via phase inference (see Grounding
  correction above). `runChatTurn` (the shared static helper both
  `ChatCubit` and `TicketsCubit` call) is unchanged — it still just runs
  with whatever `AgentModel` its caller resolved.
- `ticket_detail_screen.dart`'s `_sendComment`: drops the
  `model: AgentModel.sonnet` argument (and the now-unused `AgentModel`
  import) to match `sendMessage`'s new signature.
- `main.dart`/`app_router.dart` wiring: `RepositoryProvider<AgentSettingsRepository>`
  replaced by `RepositoryProvider<ModelRoutingRepository>`;
  `ProviderSettingsCubit`/`TicketsCubit`/`ChatCubit` construction sites
  updated for their new dependencies.
- New l10n strings for the three tier labels/descriptions; the old
  `settingsModelDropdownLabel` key is removed (no longer referenced).

## Out of scope

- **Multi-provider tier assignment.** Only Claude Agent SDK's 3 models
  are selectable per tier today, exactly as `providers.md`'s "Known gaps"
  describes. Once a second provider ships, a tier can mix any provider/
  model combination — no rework needed to this mechanism, per the idea
  file's own framing.
- **Live model discovery** (`Query.supportedModels()` in streaming-input
  mode) — flagged as a real but separate restructuring of
  `agent_bridge/index.mjs`'s whole invocation shape in
  `per-phase-tier-based-model-routing.md`'s 2026-07-22 follow-up note.
  Not touched here; the three dropdowns still list the fixed `AgentModel`
  enum.
- **A fourth tier for on-device/mobile models** — desktop-only concern
  today, per the idea file's own deferral.
- **A per-ticket/per-chat manual override** of a tier's default model for
  one run — raised as an open question in the idea file, not resolved or
  built here.
- **Changing what the "via `<model>`" line shows or when.** Re-verified
  in code: `ticket_detail_screen.dart` already shows it for every AI
  comment unconditionally (`comment.aiModel` is always set by
  `ChatCubit.runChatTurn` on both success and failure), so the idea
  file's "shown always" ask is already satisfied by existing code — no
  widget change needed there.
