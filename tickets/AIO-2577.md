# Design: v1 Release Readiness

Five independent workstreams. No shared architecture between them beyond
"things a first release needs to be true" — each is designed separately
below.

## 1. Real app icon

**Source of truth:** `aion/assets/icons/aion_icon.png` (currently
Flutter's 1024×1024 default template icon). Two consumers derive from it:

- `windows/runner/resources/app_icon.ico` — a hand-generated multi-size
  ICO (16/32/48/256px), referenced by `windows/installer/aion.iss`'s
  `SetupIconFile` and Windows' own executable-icon embedding. This file
  is **not** regenerated automatically from the PNG by anything in the
  build — it's a separate binary that needs to be regenerated by hand
  whenever the source PNG changes.
- The Linux AppImage — `linux/packaging/build_appimage.sh` copies
  `assets/icons/aion_icon.png` directly (`ICON_SRC`/`ICON_STAGED`) and
  hands it to `linuxdeploy --icon-file`. No separate binary to keep in
  sync; this side updates for free once the PNG does.

**Design direction for the artwork itself:** Aion's design system
(`project.md`) already has a visual language to draw from — Arctic
(light, celestial)/Obsidian (dark, abyssal) themes inspired by AION's
Elyos/Asmodian factions, Phosphor Light-weight iconography, Manrope
type. An OS app icon can't switch between the two themes at runtime, so
it needs its own one-time, single-static-mark decision: a mark that
reads clearly at 16px (Windows taskbar/Alt-Tab scale) and holds up at
1024px (macOS/store-listing scale, even though this release ships no
macOS build — the source PNG should stay future-proof), drawing on the
faction-motif visual language `project.md` reserves for "empty states,
onboarding, section headers" rather than either theme's literal
background/surface colors (which would look wrong as a fixed icon
against an arbitrary OS taskbar background).

**Task shape:** produce a new 1024×1024 PNG replacing
`assets/icons/aion_icon.png`, then regenerate `app_icon.ico` from it
(any ICO tool that emits the 16/32/48/256 size set `aion.iss` expects).
No Dart code changes — this is an asset-only task. Final artwork is a
human sign-off, not something `/apply` should consider done just because
a file exists at the right path and dimensions.

## 2. Release pipeline: real dry run + Linux decoupled

**Current state** (`.github/workflows/release.yml`): `build-windows` and
`build-linux` run in parallel on a `v*.*.*` tag push; `publish-release`
declares `needs: [build-windows, build-linux]` and unconditionally
attaches both artifacts to the GitHub Release via `gh release create`.
A Linux build failure today blocks the Windows release entirely, which
contradicts this release's explicit "ship both targets, don't block on
Linux actually working" stance.

**Change:**
- `build-linux` gains `continue-on-error: true` — a failure there no
  longer fails the job for `needs:` purposes downstream, but is still
  visibly red in the Actions UI (not silently swallowed).
- `publish-release` keeps `needs: [build-windows, build-linux]` (so it
  still waits for both to finish, not race ahead of a slow Linux build)
  but no longer assumes the Linux artifact exists: the
  `actions/download-artifact@v4` step for `linux-appimage` gets
  `continue-on-error: true`, and the `gh release create` step is
  rewritten to build its file-argument list conditionally — glob for
  `artifacts/linux-appimage/*.AppImage` and only add it to the command
  if the glob actually matches, so a missing Linux artifact degrades to
  "Windows-only release" instead of failing the whole job.
- No change to `build-windows` — it stays a hard requirement; a failure
  there should still block the release.

**Dry run:** push a real `v*.*.*` tag (the actual candidate for this
release, e.g. `v0.1.0` once `/prepare-release` has run — see this
proposal's Non-goals) and confirm the workflow produces a working
Windows installer end to end, attached to a real GitHub Release. This is
a verification task in `tasks.md`, not a code task — the assumptions
called out in `specs/release.md` (the chocolatey Inno Setup install
path, the pinned `linuxdeploy`/`appimagetool` download URLs) either hold
or get fixed as part of confirming this.

## 3. Workflow-status UI wiring

**Root cause:** `WorkflowConfigCubit` (backing
`WorkflowStatusSettingsScreen`) is today only ever constructed per-route,
scoped to `/workspace/settings/workflow` and
`/workspace/settings/workflow/templates`
(`app_router.dart`'s `GoRoute` builders). Board/List/Filters/Columns/
Selection-bar/ticket-detail all live under the separate `WorkspaceShell`
subtree (`app_router.dart`'s `_WorkspaceShellState.build`, the
`MultiRepositoryProvider` that already instantiates `TicketsCubit`
shell-wide) and have no access to it — so they fall back to the
module-level `defaultWorkflowStatuses` constant, unconditionally.

**Fix, in two parts:**

### 3a. Provide `WorkflowConfigCubit` shell-wide

Add a `BlocProvider<WorkflowConfigCubit>` inside
`_WorkspaceShellState.build`, alongside the existing
`BlocProvider<TicketsCubit>`, constructed from the same
`WorkflowStatusRepository`/`SddStageConfigRepository`/`TicketRepository`/
`WorkflowSkillAttachmentRepository`/`WorkflowPromptTemplateRepository`
already provided one level up in that same `MultiRepositoryProvider`,
and `..load()`ed immediately (mirroring `WorkflowStatusSettingsScreen`'s
own route-level construction). The two settings-screen routes keep their
own separate per-route instances exactly as-is — they're reached via a
`go_router` page push that doesn't inherit `WorkspaceShell`'s subtree,
same reasoning already documented on the templates route — this is
additive, not a consolidation.

### 3b. Two derived views on `WorkflowConfigLoaded`

Two getters added to `WorkflowConfigLoaded`
(`presentation/cubit/workflow_config_state.dart`) — pure derivations of
already-loaded state, not new business logic beyond what
`WorkflowConfigCubit`'s own dartdoc already describes as "the merged
view a type scope actually renders":

```dart
/// The shared-base statuses only (no per-type extensions), sorted by
/// [WorkflowStatus.sortOrder] — the scope a cross-type surface (Board,
/// Filters, Columns, bulk status menu) renders, since a status
/// extension only makes sense for tickets of its own [TicketType].
List<WorkflowStatus> get sharedBaseStatuses => [
  for (final s in statuses.where((s) => s.ticketType == null))
    s,
]..sort((a, b) => a.sortOrder.compareTo(b.sortOrder));

/// The effective status set for a single ticket of [type]: the
/// shared-base set plus [type]'s own extensions, sorted by
/// [WorkflowStatus.sortOrder] — the scope a single ticket's own status
/// picker renders. Mirrors [WorkflowConfigCubit]'s own
/// `_isNameUniqueInScope` scope definition.
List<WorkflowStatus> effectiveStatusesForType(TicketType type) => [
  for (final s in statuses)
    if (s.ticketType == null || s.ticketType == type) s,
]..sort((a, b) => a.sortOrder.compareTo(b.sortOrder));
```

### 3c. Two top-level resolver functions, not constructor threading

Every one of the six affected widgets already reads `BuildContext`
inline for something else in the exact same spot the status list is
built — `ticketStatusLabel(context, s)` for l10n (`ticket_columns_
popover.dart`, `ticket_filter_popover.dart`, `ticket_selection_bar.
dart`'s `BulkStatusMenu`, `tickets_board_view.dart`'s `MoveToStatusMenu`)
or an outright `context.read<TicketsCubit>()` call
(`ticket_metadata_section.dart`). None of them are the kind of fully
context-free, prop-only leaf `design_system/` widgets are held to —
they're feature-owned presentation widgets already coupled to
`BuildContext`. So rather than adding a `statusOrder`/`order`
constructor parameter to each and threading it through every call site,
each widget calls `context.watch<WorkflowConfigCubit>()` directly where
it already reads `context` for labels, via two top-level resolver
functions added to `workflow_config_state.dart` (module-level, not
methods — callable without a `WorkflowConfigCubit` import cycle, and
co-located with the getters they wrap):

```dart
/// The shared-base status names, in sortOrder — from [state] if loaded,
/// falling back to [defaultWorkflowStatuses]' own order otherwise (the
/// brief window before `WorkflowConfigCubit.load` resolves; every real
/// project seeds these exact rows, so this is never a stale value for a
/// customized project, only a momentary loading placeholder). Used by
/// every cross-type status surface — Board, Filters, Columns, the bulk
/// status menu.
List<String> resolveSharedStatusOrder(WorkflowConfigState state) =>
    switch (state) {
      WorkflowConfigLoaded(:final sharedBaseStatuses) => [
        for (final s in sharedBaseStatuses) s.name,
      ],
      _ => [for (final s in defaultWorkflowStatuses) s.name],
    };

/// The effective per-[type] status names, in sortOrder — same
/// loaded/fallback split as [resolveSharedStatusOrder]. Used by a single
/// ticket's own status picker (`ticket_metadata_section.dart`), where a
/// type-specific extension status is meaningful.
List<String> resolveStatusOrderForType(
  WorkflowConfigState state,
  TicketType type,
) => switch (state) {
  WorkflowConfigLoaded() => [
    for (final s in state.effectiveStatusesForType(type)) s.name,
  ],
  _ => [for (final s in defaultWorkflowStatuses) s.name],
};
```

Per-file wiring, all using `resolveSharedStatusOrder` except the last:

- **`tickets_board_view.dart`** — the module-level `_defaultStatusOrder`
  constant is removed. Its one read for the board's own column
  rendering becomes `resolveSharedStatusOrder(context.watch<
  WorkflowConfigCubit>().state)` in the widget that builds the column
  list; `MoveToStatusMenu`'s `_MoveToStatusMenuState._showOverlay`
  (same file) gets its own `context.watch<WorkflowConfigCubit>()` call
  the same way, since it's a separate `State` with its own `context`.
- **`tickets_list_screen.dart`** — same call, local to wherever it
  builds the `TicketFilterPopover`/`TicketColumnsPopover` instances
  (lines 1122/1158) that need a status list passed as data (see below).
- **`ticket_columns_popover.dart`** / **`ticket_filter_popover.dart`** —
  drop the module-level `_defaultStatusOrder` constant; call
  `resolveSharedStatusOrder(context.watch<WorkflowConfigCubit>().state)`
  directly inside `build`, right alongside each widget's existing
  `ticketStatusLabel(context, ...)` calls. No constructor change needed.
- **`ticket_selection_bar.dart`**'s `BulkStatusMenu` — `static final
  List<String> order` (a `static` field can't read `BuildContext`)
  becomes a `build`-time local, same `resolveSharedStatusOrder(context.
  watch<WorkflowConfigCubit>().state)` call.
- **`ticket_metadata_section.dart`** — same pattern, using
  `resolveStatusOrderForType(context.watch<WorkflowConfigCubit>().state,
  ticket.type)` for the status `SelectionMenu`'s `items`, matching the
  type-scoped semantics `WorkflowConfigCubit` itself already documents.

The fallback logic lives once, inside the two resolver functions above
— every consumer file drops its own `default_workflow_statuses.dart`
import entirely (`workflow_config_state.dart` is the only file that
still imports it, for that shared fallback branch).

No change to `ticketStatusLabel`'s localization/humanization fallback
(`tickets_board_view.dart`) — it already handles an arbitrary
project-renamed/added status name correctly; only the *set and order* of
statuses fed into it was ever hardcoded.

## 4. Automation-confidence validated live

**Scope:** the two real consumers of `AutomationConfidence` today
(`core/automation/automation_confidence.dart`):

- `TicketsCubit.advanceSddStage`, gated by the single global
  `AutomationSettingsRepository`-backed setting (Settings' "SDD Stage
  Automation" section).
- Coding execution's reactive override: `_overageDetectedThisSession`
  (`TicketsCubit`) flips to `true` on the first
  `AgentOverageDetectedEvent` observed this session, and every
  subsequent completion is treated as `AutomationConfidence.gated`
  regardless of the configured value from that point on.

**Verification, not code:** with the setting actually set to `auto`,
run an Epic → Story → Task lifecycle through real SDD-stage advances and
confirm each stage transition fires correctly with no unwanted side
effect (no unintended chat spawn, no incorrect ticket-status write) and
that a `gated`-configured transition still correctly waits instead of
silently applying. Then confirm the overage-reactive path: with no way
to force a real plan-usage-window overage on demand, this is a
code-level trace-through of `_overageDetectedThisSession`'s write/read
sites (confirm every completion path actually checks it, not just the
"happy path" one) rather than a live-triggered repro, documented as such
in the verification evidence — noted explicitly so a future reader
doesn't mistake "traced" for "live-fired."

**Explicit decision recorded here, not left implicit:** the known
no-timeout gap on `gated` proposals (`specs/tickets.md`'s Known
gaps — ticket CRUD tool calls and mid-task branching both leave a model
run open indefinitely if a `gated` confirmation is never answered) is
**accepted as a documented v1 limitation**, not fixed by this change. A
single-user release means the one person who could leave a prompt
unanswered is also the only person who'd notice and answer it — the
same "sufficient at personal scale" reasoning `project.md` §5 already
applies to the reactive-only budget gate. This gets a line in
`specs/tickets.md`'s Known gaps section (see `specs/spec.md`) so it
reads as a decision, not an oversight.

## 5. End-to-end native Windows verification

Same method `native-windows-verification-pass` (archived) already
established and documented in its own `design.md` — `flutter run -d
windows --debug`, driven live via raw Win32 mouse/keyboard automation
(or, this session, the `Windows-MCP` tool surface, which wraps the same
kind of native automation) rather than a UI-testing framework, since
Flutter's semantics tree isn't reliably exposed to Windows UI Automation
without a screen reader active. This change extends that pass with one
new flow: create a Task ticket, trigger coding execution, observe the
full run through to `EXECUTION: PR_OPENED <url>` (confirmed via a real
`gh pr create` call per `specs/tickets.md`'s Coding execution section,
not a self-reported model claim), and confirm the resulting entry
appears in the persistent notification center. No source change — this
produces evidence for `specs/spec.md`'s delta the same way the archived
change's single verification task did.

# Aion — Live Workflow Statuses in Status-Rendering Widgets: Component Spec

Implementation-ready spec for the **v1 Release Readiness** change that threads `WorkflowConfigCubit`'s live, per-project status list into six already-shipped widgets in place of the hardcoded 6-status default. **No new screens and no new widgets.** What this spec defines is (a) one genuinely new design decision — the role-keyed status-dot rule that replaces name matching (§2) — and (b) the layout contracts each of the six widgets must hold when the status list is not exactly six default-length labels (§3–§8).

**No Material widgets or types anywhere.** Everything below is built from `flutter/widgets.dart` primitives only: `DecoratedBox`, `Container`, `GestureDetector`, `MouseRegion`, `FocusableActionDetector`, `CustomPaint`, `Row`, `Column`, `Stack`, `Positioned`, `Align`, `Padding`, `SingleChildScrollView`, `ListView`, `Overlay` / `OverlayEntry` / `CompositedTransformFollower`, `Text` with `TextOverflow.ellipsis`. Never `Card`, `ElevatedButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `SnackBar`, `DropdownButton`, `InkWell`, `PopupMenu*`, `ListTile`, `Checkbox`, or any `material.dart` import.

- `c` = active `AionColors` (`ThemeScope.of(context).colors`; `arctic` / `obsidian`); `isDark` = Obsidian. One code path for both themes — only token values differ. Where a component is identical across themes it is stated explicitly.
- Translucent fills are always `token.withOpacity(x)` — never hardcoded ARGB. (`withOpacity` per this spec's export convention; the codebase's `withValues(alpha:)` is the equivalent call.)
- **No new color, type, spacing, or radius tokens are introduced.** Every value below resolves to an existing `AionColors` / `AionText` / `AionSpacing` / `AionRadius` member.
- Companion mockups: `Aion Live Workflow Statuses Mockups.dc.html` — 3-status board `1a`, 9-status board with a long custom label `1b`, Columns + Filters popovers on the reduced set `2a`, `BulkStatusMenu` + `MoveToStatusMenu` on the expanded set `2b`, bug-type picker with an extension status `2c`, dot-rule swatch table `3a`. Arctic and Obsidian for each.

---

## 1. Data contract

### 1.1 Source of truth

```dart
/// Ordered, per-project, live. Never assume length == 6.
List<WorkflowStatus> statuses = context.watch<WorkflowConfigCubit>().state.statuses;
```

```dart
class WorkflowStatus {
  final String name;          // internal, e.g. 'in_progress'
  final String displayName;   // user-facing, e.g. 'Waiting on Design Review'
  final WorkflowStatusRole? role;
  final int order;
}

enum WorkflowStatusRole { executionTrigger, reviewReady, done }
```

Rules every one of the six widgets must obey:

1. **Order** is the cubit's order. Never re-sort, never re-group, never hoist a role-holding status.
2. **Count** is `statuses.length` — `1` and `20` are both legal. No layout may assume `6`.
3. **Label** is `displayName`, rendered verbatim (single line, ellipsised — §1.3). No truncation of the string itself, no title-casing, no abbreviation.
4. A ticket's own `status` string may name a status that no longer exists (renamed/removed while the ticket was open). Render such a value as an **unknown status** — see §2.3.
5. Per-type extension statuses merge into the base list **in workflow order** with no visual seam (§8).

### 1.2 Ticket-type scoping

Only the ticket detail status picker (§8) is type-scoped:

```dart
List<WorkflowStatus> forType(TicketType t) =>
    config.baseStatuses.followedBy(config.extensionStatusesFor(t)).sortedByOrder();
```

The Board, both popovers, `BulkStatusMenu`, and `MoveToStatusMenu` use the **base** list only (they span tickets of mixed type).

### 1.3 Label rendering contract (all six widgets)

- `maxLines: 1`, `overflow: TextOverflow.ellipsis`, `softWrap: false`.
- Never wraps. Wrapping is specifically forbidden in board column headers (it desynchronises header heights across the column row) and in overlay rows (it breaks the fixed 38px row rhythm).
- Text style per widget below; color `c.textPrimary` unless stated.

---

## 2. Status-dot color rule (the one new design decision)

Replaces the existing `_statusDotColor(c, statusName)` helpers in `tickets_board_view.dart` and `ticket_selection_bar.dart`, which pattern-match the six literal default names and therefore return nothing meaningful for a renamed or added status.

The new rule is keyed on `WorkflowStatusRole`, with a **position-derived fallback** for role-less statuses so that a project's custom statuses read as neutral rather than accidental. No new tokens.

### 2.1 Decision table

`terminal` = the status's `order` is **greater than** the `order` of the status holding `WorkflowStatusRole.done`. (If no status holds the `done` role, no status is terminal.)

| Role | `terminal` | Dot color token | Arctic | Obsidian |
|---|---|---|---|---|
| `executionTrigger` | — | `c.primary` | `Color(0xFF2E86D4)` | `Color(0xFF9366FF)` |
| `reviewReady` | — | `c.warning` | `Color(0xFFB8912B)` | `Color(0xFFD7B24E)` |
| `done` | — | `c.success` | `Color(0xFF1E9E76)` | `Color(0xFF33D19B)` |
| `null` | `false` | `c.textSecondary` | `Color(0xFF46586A)` | `Color(0xFFA2AEC6)` |
| `null` | `true` | `c.textMuted` | `Color(0xFF8496A6)` | `Color(0xFF6B7690)` |

```dart
Color statusDotColor(AionColors c, WorkflowStatus s, {required bool terminal}) {
  switch (s.role) {
    case WorkflowStatusRole.executionTrigger: return c.primary;
    case WorkflowStatusRole.reviewReady:      return c.warning;
    case WorkflowStatusRole.done:             return c.success;
    case null:                                return terminal ? c.textMuted : c.textSecondary;
  }
}
```

Applied to the default 6-status project this yields: Backlog `textSecondary` · To Do `textSecondary` · In Progress `primary` · In Review `warning` · Done `success` · Cancelled `textMuted`. This is an intentional, small change from today's output (In Review gains the `warning` dot; Backlog / To Do move from `textMuted` to `textSecondary`) and is the same in every one of the six widgets.

### 2.2 Dot geometry (identical in both themes)

- **Board column header dot:** `7 × 7`, `BoxShape.circle`, no border, no shadow. Followed by `SizedBox(width: AionSpacing.sp8)`.
- **Overlay-row dot** (`BulkStatusMenu`, `MoveToStatusMenu`, both popovers, detail picker): `8 × 8`, `BoxShape.circle`, no border, no shadow. Followed by `SizedBox(width: 10)`.
- **Detail-picker trigger dot:** `8 × 8`, same treatment, `SizedBox(width: AionSpacing.sp8)` before the label.
- Dots are decorative: `ExcludeSemantics`; the status name carries the accessible label.

### 2.3 Unknown status (ticket references a removed/renamed status)

Not a new component — an existing-value fallback the widgets must not crash on.

- **Dot:** `c.textMuted`.
- **Label:** the raw stored string, `AionText.bodySm.copyWith(color: c.textMuted)`, `fontStyle: FontStyle.italic`.
- **Board:** the ticket is not placed in any column; it is unaffected by column rendering (existing behavior for out-of-set values).
- **Detail picker:** the unknown value appears as the trigger's current value but **not** as a row in the menu; choosing any row replaces it. No error state, no `danger`.

## 3. `BoardColumn` — variable column count

`tickets_board_view.dart`. Structure unchanged: a horizontally scrolling `Row` of fixed-width columns.

### 3.1 Column geometry (unchanged, both themes)

- **Width:** `280` fixed. **Never** flexes, stretches, or divides the viewport — 3 columns and 9 columns use the same 280.
- **Gap between columns:** `14`. **Row padding:** `EdgeInsets.fromLTRB(20, 20, 20, 20)`.
- **Header row:** height driven by content, `EdgeInsets.symmetric(horizontal: 4)`; dot (§2.2) → `SizedBox(8)` → label → `SizedBox(8)` → count.
  - **Label:** `AionText.cardTitle` (Manrope 14/w600 — rendered at 13 in the column header per existing code) `color: c.textPrimary`, `Expanded` + `maxLines: 1` + ellipsis (§1.3).
  - **Count:** `AionText.key` (JetBrains Mono 11/w600) `color: c.textMuted`, `flex: 0`, never ellipsised — the count wins the space contest against a long label.
- **Card list:** existing `TicketCard` unchanged — `c.surface` fill, `1px c.border`, `AionRadius.lg` (12), `EdgeInsets.symmetric(horizontal: 13, vertical: 12)`.
- **Shadow:** none on the column; existing card shadows unchanged.

### 3.2 Fewer statuses than fill the viewport (see mockup `1a`)

- Columns are **left-aligned** (`MainAxisAlignment.start`); trailing space is left empty. Do not center, do not stretch, do not add a placeholder column.
- Horizontal scrolling is disabled implicitly (content narrower than viewport) — `SingleChildScrollView` keeps `physics: ClampingScrollPhysics()` and simply does not scroll.
- **1 status** is legal: one 280px column, otherwise identical.
- **0 statuses** (all removed, or all hidden by `BoardColumnVisibility`) uses the existing all-columns-hidden empty state — no change.

### 3.3 More statuses than fit (see mockup `1b`)

- The `Row` scrolls horizontally inside the existing `SingleChildScrollView(scrollDirection: Axis.horizontal)`. No paging, no snapping.
- **Trailing fade:** the existing edge treatment — `Positioned(top: 0, right: 0, bottom: 0, width: 96)`, `IgnorePointer`, `LinearGradient(begin: centerLeft, end: centerRight, colors: [c.background.withOpacity(0), c.background])`. Shown only while the row can scroll further right.
- **Scrollbar:** track `c.borderStrong.withOpacity(isDark ? 0.35 : 0.50)`, thumb `c.borderStrong`, height `6`, radius `3`, insets `left: 20, right: 20, bottom: 6`. Visible during scroll and for `800ms` after; not an overlay panel.
- **Long labels truncate, never wrap** (§1.3). "Waiting on Design Review" ellipsises inside the 280px header; the full string is available via the existing tooltip-on-hover treatment on the header row.
- Column count has no effect on card width, card padding, or drag-and-drop hit targets.

## 4. `MoveToStatusMenu` — one row per status

`tickets_board_view.dart`. An `OverlayEntry` + `CompositedTransformFollower` anchored to the card's overflow control. Row structure unchanged (`OverlayMenuItem`).

### 4.1 Panel

- **Width:** `244` fixed (unchanged). **Padding:** `EdgeInsets.all(5)`. **Row gap:** `2`.
- **Fill:** `c.surface`. **Border:** `1px c.borderStrong`. **Radius:** `AionRadius.lg` (12).
- **Shadow:** `BoxShadow(color: Color(0xFF000000).withOpacity(isDark ? 0.60 : 0.22), blurRadius: 44, offset: Offset(0, 20), spreadRadius: -14)`.
- **Max height:** `344` (≈ 8 rows + padding). Beyond that the row list scrolls (`ListView`, `shrinkWrap: true`, `ClampingScrollPhysics`) — the panel never grows past `344` and never past `viewportHeight - 24`, whichever is smaller. Scrollbar: `4` wide, radius `2`, thumb `c.borderStrong`, track `c.borderStrong.withOpacity(isDark ? 0.35 : 0.50)`, inset `right: 3`.
- **Flip:** existing behavior — if the panel would overflow the bottom edge it anchors above the trigger. A 9-status list makes this the common case; no new logic.

### 4.2 Row

- **Height:** `38` (`EdgeInsets.symmetric(horizontal: 10, vertical: 9)`). **Radius:** `AionRadius.iconBtnSm` (8).
- **Layout:** dot `8 × 8` (§2.2) → `SizedBox(10)` → `Expanded` label → optional trailing marker.
- **Label:** `AionText.bodySm` (Manrope 13.5/w400) `color: c.textPrimary`, ellipsised.
- **Current status row:** label `c.textSecondary`, whole row `opacity: 0.50`, trailing `Text('current', AionText.key.copyWith(color: c.textMuted))`, and it is **not tappable** (`GestureDetector` omitted) — not a disabled-looking-but-tappable row.

### 4.3 States

| State | Row fill | Label | Notes |
|---|---|---|---|
| **Default** | `transparent` | `c.textPrimary` | — |
| **Hover** | `c.surfaceHover` | `c.textPrimary` | `MouseRegion`, `120ms` fade |
| **Focused** (keyboard) | `c.surfaceHover` + `1.5px c.primary` inset border, radius 8 | `c.textPrimary` | arrow keys move focus; `Enter` commits |

## 8. Ticket detail status picker (`SelectionMenu`) — base + type extension

`ticket_metadata_section.dart`. Single-select dropdown-style overlay for one ticket. See mockup `2c` (bug ticket AIO-58 with the bug-only "Needs Repro").

### 8.1 Trigger (unchanged)

- **Layout:** `Row(mainAxisSize: min)` → dot `8 × 8` (§2.2) → `SizedBox(AionSpacing.sp8)` → label → `SizedBox(8)` → caret glyph (`CustomPaint`, `9`, `c.textMuted`).

- **States:** Default border `1px c.border` · Hover `1px c.borderStrong` · Focused/Open `1.5px c.primary` + ring `c.primary.withOpacity(isDark ? 0.30 : 0.16)` spread `3` blur `0` · Pressed `1px c.borderStrong` + `scale: 0.98` · Disabled (ticket in trash) fill `c.surfaceHover`, label `c.textMuted`, not tappable · Error (write failed) border `1.5px c.danger` + ring `c.danger.withOpacity(isDark ? 0.30 : 0.16)`, with the existing inline retry message below the field (`AionText.bodySm`, `c.textSecondary`).

### 8.2 Menu

- **Panel:** width `236`, padding `EdgeInsets.all(5)`, row gap `2`, fill `c.surface`, border `1px c.borderStrong`, radius `AionRadius.lg` (12), shadow as §4.1, max height `344` + scroll.
- **Rows:** §4.2 geometry. **Selected row:** fill `c.primarySubtle`, trailing check glyph (`CustomPaint`, `13`, `c.primary`). Hover / focus / pressed per §4.3.

### 8.3 No seam between base and extension rows

The merged list (§1.2) renders as **one flat list in workflow order**. Specifically forbidden:

- No divider, no gap change, no section header ("Bug statuses"), no badge or tag on extension rows.
- No re-grouping — an extension status sits at its `order` position (e.g. "Needs Repro" between "In Progress" and "In Review"), not appended at the end.
- Extension rows take exactly the same fill, height, dot geometry, and text style as base rows; their dot follows §2.1 like any other status (role-less, pre-done → `c.textSecondary`).
- The only per-type difference visible anywhere is *which* rows exist. If the reader can tell base from extension in the mockup, the implementation is wrong.
