## ADDED

### Packaging and CI

- Pushing a git tag matching `v*.*.*` to the `aion` repo triggers a
  GitHub Actions workflow that builds a Windows installer (Inno
  Setup — Start Menu shortcut, uninstaller entry) and a Linux AppImage
  (single portable file) and attaches both to a GitHub Release named
  after the tag.
- The Windows installer and the AppImage are unsigned. Installing the
  Windows build shows a SmartScreen warning; this is a known, accepted
  limitation at the current developer/tester distribution scope, not a
  defect.
- No macOS build is produced. No auto-update or update-checking
  mechanism exists in the app itself — Aion has no awareness of its own
  releases.

### Versioning

- The app's release version (`pubspec.yaml` `version:` field, matching
  git tag) and the baseline version (`assets/baseline/<version>/`) are
  independent numbering schemes. They change at different cadences and
  are never coupled or bumped together automatically.

### Changelog

- `aion/CHANGELOG.md` (Keep a Changelog format) is the committed source
  of truth for release notes. It always has an `## [Unreleased]`
  section at the top, normally empty between releases. The GitHub
  Release body for a given tag is generated by extracting that
  version's section from this file at CI time — never hand-duplicated,
  never left to GitHub's own auto-generated notes.

### `/prepare-release` skill

- A local, human-reviewed skill (`aion-arch/.claude/skills/
  prepare-release/`) drafts a release: it finds every archived change
  under `aion-arch/changes/archive/<name>/` whose `proposal.md` has no
  `Shipped in:` line yet, drafts one changelog bullet per change from
  that change's own "What's building" content, drafts a "Fixes &
  chores" section from `fix:`/`chore:`/`refactor:` commits not already
  covered by one of those changes, and suggests a semver bump the
  developer can confirm or override.
- On confirmation, it bumps `pubspec.yaml`, writes the new
  `CHANGELOG.md` section, and adds a `Shipped in: vX.Y.Z` line to each
  shipped change's `proposal.md`. It commits these via the standard ad
  hoc (non-cycle) branch+PR convention, in both repos separately. It
  never tags or pushes the release tag itself — that remains a manual
  developer action, and is the only thing that triggers the CI workflow
  above.
- This skill is not part of the OpenSpec SDD cycle (`/explore` through
  `/archive`) and not an orientation skill (`/what-next`,
  `/brainstorm`, `/capture`) — it is a third skill category, scoped to
  release/versioning process for the `aion` repo itself.

### Archived-change "Shipped in" convention

- `/archive` itself never writes a `Shipped in:` line — it has no way
  to know which future release a change will ship in. `/prepare-release`
  is the only thing that adds this line, retroactively, once a release
  is actually cut. A freshly archived change with no `Shipped in:` line
  yet is expected, not a missed step.
