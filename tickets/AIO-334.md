# Blocked Ticket Transition Gate

# Proposal: blocked-ticket-transition-gate

## What

`board-task-ordering-indication` gave the Board a `_BlockedBadge` that
shows whenever a ticket has an unresolved `blocks`/`blockedBy` link to
another ticket that isn't `done` — but the badge is purely visual.
Nothing today stops that same ticket from actually being dragged (or
menu-moved) to `TicketStatus.inProgress` anyway. `tickets.md`'s own
Known gaps section flags this directly: "No hard gate preventing a
blocked Task/Story from moving to `inProgress` — the Board's
`BlockedBadge` is visual-only, with no effect on drag-and-drop or
`MoveToStatusMenu`."

This change closes that gap: moving *any* ticket (not just Task/Story —
see Scope) to `inProgress` while it has an unresolved `blocks`/
`blockedBy` dependency is rejected, with a toast explaining why,
exactly the way an SDD-design-incomplete Task's `inProgress` move is
already rejected today.

## Why

The badge already tells the user a ticket is blocked; letting them move
it to `inProgress` anyway makes the badge decorative rather than
meaningful, and lets in-progress work quietly start on top of an
unresolved dependency the UI itself flagged. Enforcing it removes that
gap between what the Board *shows* and what it *allows*.

Every design decision below reuses an already-shipped mechanism rather
than inventing a new one:

- `TicketsCubit` already gates one `inProgress` transition today —
  `_interceptTaskExecutionTrigger`, which rejects a Task/Bug's move to
  `inProgress` when its governing Story's design work is outstanding,
  emitting `TicketsErrorReason.codingExecutionBlocked` then re-emitting
  `TicketDetailLoaded`. This change adds a second, independent
  interceptor of the exact same shape — same reject pattern, same
  toast-surfacing path (`ticketsErrorMessage`/`AppToast`) — rather than
  folding new logic into the existing one, since the two checks test
  unrelated things (SDD-design readiness vs. an unresolved dependency
  link) and apply to different type sets (Task/Bug-only vs. every
  type).
- The blocked/not-blocked determination reuses
  `_computeBlockedTicketIds`'s exact row-resolution logic (a
  `blockedBy` row's blockee is its source, a `blocks` row's blockee is
  its target; a blocker missing or not `done` counts as blocking) —
  scoped to one ticket via the already-existing
  `TicketLinkRepository.getLinksForTicket`, rather than recomputing the
  board-wide set for a single check.
- Both status-changing entry points (`updateTicketStatus`,
  `changeTicketStatus`) already funnel drag-and-drop
  (`BoardColumn.onAcceptWithDetails`), `MoveToStatusMenu`, and the
  detail screen's status control through the same two cubit methods —
  so gating at the cubit level covers all three surfaces automatically,
  with no per-widget changes needed.

## Scope

- **Uniform across ticket types.** The known gap's wording names
  "Task/Story," but the `_BlockedBadge` it complains about is already
  type-agnostic — every ticket type gets the badge if it has an
  unresolved dependency. Gating only Task/Story would leave a visible
  asymmetry (a blocked Epic or Bug shows the badge but can still be
  moved to `inProgress` unopposed). This change gates every type
  uniformly, matching the badge 1:1.
- **`inProgress` only.** Neither the known gap nor the existing badge
  says anything about `inReview`/`done`; the concern is blocked work
  *starting*, not finishing what's already in flight. No other status
  transition is touched.
- **`TicketsCubit`** (`features/tickets/presentation/cubit/tickets_cubit.dart`)
  gains a new private `_isTicketBlocked(Ticket)` check and a new
  private `_interceptBlockedDependencyTrigger(Ticket, TicketStatus)`
  interceptor, wired into `updateTicketStatus` and `changeTicketStatus`
  ahead of the existing `_interceptTaskExecutionTrigger` call.
- **`TicketsErrorReason`** (`tickets_state.dart`) gains
  `blockedByOpenDependency`. **`ticketsErrorMessage`**
  (`tickets_board_view.dart`) gains its switch case. **`app_en.arb`**
  gains the matching toast string.
- No new widgets, no new BLoC states, no schema changes — this is a
  gate on an existing transition path, not a new feature surface.

## Out of scope

- **Disabling `MoveToStatusMenu`'s "In Progress" item proactively**
  (greying it out before the user picks it) — this change stays
  reactive, mirroring `_interceptTaskExecutionTrigger`'s existing
  reject-after-attempt shape exactly. A proactive disabled-state would
  need the menu to know the blocked set at render time, which is a
  separate (and larger) change to `MoveToStatusMenu`'s data
  dependencies; not raised in the source gap, not built here.
- **A "why is this blocked" detail view** (listing the specific
  blocking ticket(s) by name) — the toast names the situation generically,
  matching every existing `TicketsErrorReason` toast's plain-string
  shape (none of them enumerate specific tickets/entities today).
- **Extending the gate to `inReview`/`done`** — see Scope above.
- **A hard *cross-hierarchy* gate** (e.g. blocking an Epic's `inProgress`
  move because an incomplete child Story exists) — that's a different
  relationship (`parentId` hierarchy) from the `blocks`/`blockedBy` link
  this change enforces; unrelated to the source gap.
