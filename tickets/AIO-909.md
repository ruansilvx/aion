# 3. In `updateStatusForTickets`: capture `stateBeforeThisWrite =

state` at the method's top, before `emit(const
TicketsBatchStatusUpdating())`. After the existing
`pendingAttachmentFires` firing loop (still inside the `try`
block, following `design.md` §4's ordering), add
`unawaited(_refreshDetailIfOpenAndAffected(writableIds.toSet(),
fromState: stateBeforeThisWrite))`. Update the method's dartdoc to
document this new side effect, following the phrasing pattern its
existing dartdoc already uses for `_refreshBlockedBoardState`/
attachment-firing.
**CRITICAL bug found during `/verify`, fixed**: the call was
originally implemented un-chained, in the statement order above
(refresh call, then the `pendingAttachmentFires` loop below it) —
textually matching "after the loop" only in the sense of coming
later in the *loop's own position relative to other code*, not in
actual execution order. `getTicketById` (which the refresh call
delegates to) captures its own `previousDetail = state` **synchronously**,
before this method's synchronous execution ever reaches the loop
below it (calling an async function runs synchronously up to its
own first internal `await`). A `gated`-confidence
`_resolveAndFireAttachment` call has no internal `await` in its
gated branch, so it emits `pendingSkillAttachment` fully
synchronously, immediately after the refresh call yields — landing
*before* the refresh's own later, async re-emission. That later
re-emission then carries forward the *stale*,
pre-attachment `previousDetail?.pendingSkillAttachment`,
overwriting the banner the loop just set — for any bulk write
whose `ids` include the ticket whose own detail screen is open, on
a status with a `gated` attachment configured. Fixed by chaining
the `pendingAttachmentFires` loop onto the refresh call's
completion via `.then()`, mirroring `updateTicketStatus`'s own
chaining (which this bug's root cause — the same hazard
`updateTicketStatus`'s dartdoc already names — was supposed to
replicate but didn't). Added a regression test:
`'updateStatusForTickets does not clobber pendingSkillAttachment
when the bulk-written ids include the currently-open ticket'` in
`tickets_cubit_test.dart`'s `'Skill attachments (Phase 2)' → 'gated
confidence — WorkflowStatus entry'` group — confirmed it fails
against the pre-fix code (`Expected: 'attach-3c', Actual: <null>`)
and passes against the fix.
