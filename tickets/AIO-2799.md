# Does further investment in .claude/skills/ materialization make sense given Aion's agent-agnostic architecture?

delegatedSkill (the mechanism SkillMaterializationService now serves) is inherently tied to one vendor's CLI skill-discovery convention, gated behind AgentProvider.supportsSkillDiscovery (today: only ClaudeAgentSdkProvider). aionNativeTemplate is the actual agent-agnostic mechanism — plain text, works with any provider, no filesystem dependency.

Assessment reached in conversation: the materialization work is architecturally sound and correctly gated (a provider that doesn't support it simply never gets delegatedSkill offered, same precedent as supportsSessionResume) — not a design mistake. But it only benefits Claude-Code-CLI-backed setups, and the materialized file format is hardcoded to .claude/skills/<name>/SKILL.md — it wouldn't generalize if a second skill-discovery-capable provider with a different convention ever ships.

Recommendation: keep it as a gated bonus feature, don't invest further in generalizing the format until a second such provider actually exists. Not yet confirmed by the user as of this ticket's creation.
