# Live Refresh Open Ticket Detail Screen

# Proposal: Live-Refresh an Open Ticket Detail Screen

## Why

`aion-arch/specs/tickets.md`'s Known gaps section documents two separate
staleness problems that turn out to share one root cause:

1. **AI-suggestion live-push** (tickets.md:6325) — when
   `TicketEstimationSuggester.suggest()`'s *passive* background path lands
   a `complexity`/`estimate` value while the same ticket's detail screen
   is already open, the screen doesn't show it until the user navigates
   away and back. The explicit Regenerate action already re-emits
   immediately; only the passive path is stale.
2. **`canAdvanceSddStage` staleness** (tickets.md:6332) — "a sibling Task
   completing while the Story's detail screen is already open does not
   retroactively flip the banner/button without a reload."

Both are the same shape: a background write happens somewhere else in the
app while `TicketDetailScreen` is already showing a ticket whose computed
state depends on that write. The `/brainstorm` session for this idea
(`aion-arch/ideas/live-refresh-open-ticket-detail-screen.md`) confirmed
this is worth fixing generally rather than patching the AI-suggestion case
alone, and — separately — confirmed the sibling AI-suggestion gaps (list/
board badge, model-reported confidence score, Settings-level config) are
**not** worth pursuing; this proposal touches none of those.

## What

A single mechanism inside `TicketsCubit`, not a new subsystem:

- `TicketsCubit` is a single app-wide instance, provided once by
  `WorkspaceShell` — not re-created per screen. Every write path that
  could affect the currently-open `TicketDetailScreen` already runs
  through that same instance.
- A new private helper, `_refreshDetailIfOpenAndAffected(String
  writtenTicketId)`, checks whether the cubit's current state is
  `TicketDetailLoaded` for the affected ticket itself, or for a `story`
  whose direct Task/Bug child is the affected ticket, and — only in
  those two cases — silently re-fetches and re-emits `TicketDetailLoaded`
  for the open ticket. No-ops otherwise (nothing open, or the open ticket
  is unrelated).
- Two call sites get wired to it: the passive `suggest()` completion
  (`createTicket`/`updateTicket`) and the board/list-oriented
  `updateTicketStatus`.
- `getTicketById` gains an explicit Loading-skip: re-fetching for a ticket
  whose `TicketDetailLoaded` is already showing no longer flashes
  `TicketsLoading` — required so the live update lands invisibly instead
  of flickering the screen.

No new BLoC state class, no new repository method, no new widget, no DB
migration.

## Non-goals

- **List/board badge, model self-reported confidence, Settings-level
  config** — the three other documented AI-suggestion gaps. The
  brainstorm session explicitly decided none of these are worth building;
  this proposal doesn't touch them.
- **Epic-level `canAdvanceSddStage` staleness from a Story's `sddStage`
  advancing.** The documented gap (tickets.md:6332) is specifically about
  a Task/Bug's `TicketStatus` write affecting an open **Story's** detail
  screen — that's what this change fixes. A Story's own `sddStage`
  reaching `archived` while its parent **Epic's** detail screen happens to
  be open is a related-but-undocumented scenario, not raised in the
  brainstorm session, and is left for a future idea if it turns out to
  matter.
- **Bulk status edit** (`TicketsCubit`'s batch status-update path, see
  [Bulk status/priority edit](../../specs/tickets.md)). Only the
  single-ticket `updateTicketStatus` path (board drag,
  `MoveToStatusMenu`) is wired — bulk edits changing a Story's child
  Task/Bug in bulk won't live-refresh an open Story detail screen. Noted
  as an explicit scope cut, not an oversight; can be swept in later if it
  proves to matter.
- **`estimateRollup`/`timeSpentRollup` live-refresh.** `TicketRollupRecomputer`
  has the identical staleness shape (a background rollup recompute
  doesn't refresh an open ancestor's detail screen either), but it wasn't
  raised in the brainstorm session and isn't touched here.
- **No new stream/watch/pub-sub infrastructure.** This is possible
  entirely because `TicketsCubit` is already a single instance — deferred
  as unnecessary, not because it was ruled out on merits.
