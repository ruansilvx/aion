# Spec delta: Automatic Time Tracking for Tickets

**Reconciled 2026-09-03:** confirmed against the current `aion-arch/specs/tickets.md` "Automatic time tracking" section — this delta *is* the change that introduced system-measured `timeSpent` and removed the `log_time` tool; the current text still describes exactly this mechanism. The identifiers this delta's own REMOVED section names (`_toolsFor`, `_onToolCallFor`, `_handleLogTimeToolCall`) are correctly absent from current specs — they were deleted by this same change, not superseded later. No drift.

Delta against `aion-arch/specs/tickets.md`. Read alongside
`proposal.md`/`design.md` — this file only states what changes, not
full current-state prose.

## `tickets.md`

### ADDED

- **Automatic `timeSpent` logging on every AI chat turn with a real
  parent ticket.** `ChatCubit.runChatTurn` — the shared entry point
  every AI-driven chat turn passes through (plain chat sends,
  coding-execution's implement/verify turns, SDD-stage chats,
  design-sync, skill attachments, codebase-analysis summarization, and
  every Inbox chat — brain dump, what-next guidance, release planning,
  Q&A) — now measures its own wall-clock duration and calls
  `TicketRepository.addTimeSpent` on the chat's parent ticket once the
  turn reaches any terminal outcome (success, failure, or cancellation),
  logging at least 1 minute (ceiling-rounded) per turn. No
  `AutomationConfidence` gate — always applies immediately, the same
  "additive and low-consequence" treatment `log_time` (removed by this
  change, below) previously had. A chat with no resolvable parent
  ticket logs nothing — in practice this means every Inbox-spawned chat
  (`InboxCubit` only ever creates parentless chats), so automatic time
  tracking, while wired through all 4 Inbox launch methods, never
  actually produces a logged minute for Inbox conversations. See
  design.md §2, §4.

### MODIFIED

- **`ChatCubit.runChatTurn`** — gains a new required
  `TicketRepository ticketRepository` parameter, and its control flow
  is restructured from three return points (an early
  `ChatTurnCancelled` return plus a trailing
  success/failure return) to one, so the new time-logging step runs
  exactly once regardless of which terminal outcome the turn reaches.
  Every existing branch's persisted-comment/returned-`ChatTurnResult`
  behavior is otherwise unchanged. See design.md §2.
- **`TicketsCubit._toolsFor`** — no longer appends
  `logTimeToolDefinition`. Returns the branch-or-close-branch tool plus
  `create_ticket` and `add_link` only. See design.md §5.
- **`TicketsCubit._onToolCallFor`** — the `'log_time'` case is removed
  from its name-keyed switch; `branch_ticket` remains the `_` default
  case. See design.md §5.

### REMOVED

- **`log_time` tool** (`logTimeToolDefinition`,
  `TicketsCubit._handleLogTimeToolCall`) — the model-self-reported
  time-logging tool call. Every real invocation of it happened strictly
  inside the same `client.run()` window automatic measurement now
  covers (tool calls are only ever answered mid-turn, while the
  underlying model call is still in flight), so it became fully
  redundant once automatic measurement exists rather than covering any
  distinct gap. Its effect (`TicketRepository.addTimeSpent` on the
  chat's parent ticket) is superseded, not replicated by a different
  mechanism with the same shape — automatic logging measures real
  elapsed time rather than accepting a model-supplied `minutes` value.
  See proposal.md's "Why" for the redundancy finding, design.md §5 for
  the removal's exact scope.
- `log_time` never had an `AutomationContext` entry, `PendingToolProposal`
  variant, or Settings row to begin with (it "always applies
  immediately, no gate, no UI" per its own prior spec), so none of
  those needed removing alongside it.

### Known gaps this change resolves

- From `tickets.md`'s own known-gaps list: `timeSpent` previously
  relied entirely on manual entry or a model's self-reported `log_time`
  guess — no system-measured actuals existed anywhere in the codebase.
  This change gives `timeSpent` a trustworthy, automatic source for
  every AI-driven ticket interaction, laying the groundwork (not built
  here) for a future predicted-vs-actual calibration loop against the
  already-shipped AI-suggested `estimate` feature.
