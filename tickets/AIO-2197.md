# Design: Ticket Detail Status Editing

## Overview

Add one Cubit method and rewire one widget slot. No new state classes, no
new primitive widgets, no repository/DAO/schema changes.

```
TicketDetailScreen
  └─ BlocBuilder<TicketsCubit, TicketsState>
       └─ TicketDetailLoaded(:ticket)
            └─ Row (type/status meta row)
                 ├─ SelectionMenu<TicketType>       (existing, unchanged)
                 └─ SelectionMenu<TicketStatus>      (NEW — replaces StatusIndicator)
                      trigger: StatusIndicator(status: ticket.status)   (existing widget, reused as trigger)
                      onSelected → TicketsCubit.changeTicketStatus(ticket, status)
```

## Cubit changes (`presentation/cubit/tickets_cubit.dart`)

### New method: `changeTicketStatus(Ticket ticket, TicketStatus status)`

```dart
/// Changes [ticket]'s status from the ticket-detail screen. Persists via
/// the same [TicketRepository.updateTicketStatus] the board's drag/
/// [MoveToStatusMenu] path calls, then re-fetches and emits
/// [TicketDetailLoaded] with the refreshed ticket — unlike
/// [updateTicketStatus], which emits list-shaped optimistic states built
/// for the board and would fall through `TicketDetailScreen`'s state
/// switch. Emits [TicketsError] on failure.
Future<void> changeTicketStatus(Ticket ticket, TicketStatus status) async {
  try {
    await _repository.updateTicketStatus(ticket.id, status);
    final refreshed = await _repository.getTicketById(ticket.id);
    if (refreshed != null) {
      emit(TicketDetailLoaded(refreshed));
    }
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

This is structurally identical to the existing `updateTicket` method
(same try/re-fetch/emit shape) — it just calls
`TicketRepository.updateTicketStatus` instead of
`TicketRepository.updateTicket`, since `updateTicket` deliberately excludes
`status` (see `aion-arch/specs/tickets.md`'s `TicketRepository` section).

**Why not extend `updateTicket` to also persist `status`?** That would
require changing `TicketRepository.updateTicket` /
`DriftTicketRepository.updateTicket` / `TicketDao`, which today
deliberately omit `status` so the board's dedicated
`updateTicketStatus(id, status)` stays the single write path for status
mutations (per the existing spec and its test coverage in
`drift_ticket_repository_test.dart`). Reusing that existing repository
method from a new Cubit method is smaller and touches no
already-verified repository/DAO code.

**Why not reuse the existing `updateTicketStatus` Cubit method as-is?**
It intentionally emits `TicketStatusUpdating`/`TicketStatusUpdated` — list-
shaped states for the board's optimistic drag feedback. `TicketDetailScreen`'s
`BlocBuilder<TicketsCubit, TicketsState>` switch (see
`ticket_detail_screen.dart`) only matches `TicketsLoading` / `TicketsError`
/ `TicketDetailLoaded`; anything else falls through to
`_ => const SizedBox.shrink()`. Calling the board's method from the detail
screen would blank the entire ticket body the instant a status is picked.

No new `TicketsState` subclass is needed — `changeTicketStatus` reuses
`TicketDetailLoaded`, exactly like `updateTicket` and
`updateTicketParent` already do for their own fields.

## Widget changes (`presentation/screens/ticket_detail_screen.dart`)

Replace the current read-only status cell:

```dart
StatusIndicator(
  status: ticket.status,
),
```

with:

```dart
SelectionMenu<TicketStatus>(
  trigger: StatusIndicator(status: ticket.status),
  items: TicketStatus.values,
  itemLabel: (s) => ticketStatusLabel(context, s),
  currentValue: ticket.status,
  onSelected: (s) => context
      .read<TicketsCubit>()
      .changeTicketStatus(ticket, s),
  semanticsLabel: context.l10n.ticketDetailChangeStatus,
),
```

This is a direct copy of the existing `SelectionMenu<TicketType>` /
`SelectionMenu<TicketPriority>` wiring immediately above it in the same
`Row` — same overlay mechanics (`Overlay`/`LayerLink`/
`CompositedTransformFollower`/`mounted`-guard, all internal to
`SelectionMenu<T>`, no changes needed there), same accessibility treatment
(`Semantics(button: true, ...)` + `FocusableActionDetector` +
`ActivateIntent`, all inherited from `SelectionMenu<T>`), same visual
placement (still the middle cell of the type/status `Row`).

`ticketStatusLabel` is already defined (in `tickets_board_view.dart`) and
already imported/used by `StatusIndicator` — no new import needed beyond
what the file already has via `StatusIndicator`'s own file.

`StatusIndicator` itself is unchanged — reused as-is as the trigger,
exactly the way `PriorityBadge`/`TypeChip` are reused as triggers for
their own `SelectionMenu<T>` instances. Its dot-plus-label rendering
already looks identical whether or not it's wrapped in a tappable
overlay trigger.

## Localization (`lib/l10n/app_en.arb`)

Add one key, next to the existing `ticketDetailChangePriority`/
`ticketDetailChangeType`:

```json
"ticketDetailChangeStatus": "Change status",
```

No placeholders, no `@`-metadata block needed (matches the existing
`ticketDetailChangeType`/`ticketDetailChangePriority` entries, which have
none either).

## Board — explicitly unchanged

`TicketBoardView`, `BoardColumn`, `TicketBoardCard`, and `MoveToStatusMenu`
(`presentation/screens/tickets_board_view.dart`) are untouched. They keep
calling the existing `TicketsCubit.updateTicketStatus(String id,
TicketStatus status)` exactly as today — that method, its
`TicketStatusUpdating`/`TicketStatusUpdated` states, and the optimistic
list-replacement logic are not modified by this change.

## Testing (`test/features/tickets/cubit/tickets_cubit_test.dart`)

Add a new `group` (or extend the existing one) with two `blocTest` cases
for `changeTicketStatus`, mirroring the existing `updateTicket` tests:

1. **Success** — mock `repository.updateTicketStatus(ticket.id, newStatus)`
   to complete, mock `repository.getTicketById(ticket.id)` to return the
   updated ticket, assert `expect: () => [TicketDetailLoaded(updatedTicket)]`.
2. **Failure** — mock `repository.updateTicketStatus(...)` to throw,
   assert `expect: () => [isA<TicketsError>()]`, and `verifyNever` on
   `repository.getTicketById` (mirroring how `updateTicket`'s failure test
   is structured today).

No repository-layer test changes — `DriftTicketRepository.updateTicketStatus`
is unchanged and already covered.

## Non-goals / explicitly not changed

- No status-transition validation (e.g. blocking `done → backlog`). None
  exists on the board path today; this change doesn't add asymmetry
  between the two entry points.
- No optimistic local state in the new picker. `priority`/`type` editing
  on this screen already accepts the brief round-trip before the
  `BlocBuilder` rebuilds with the new `TicketDetailLoaded`; `status`
  follows the identical, already-accepted pattern.
- No changes to `TicketRepository`, `TicketDao`, `DriftTicketRepository`,
  or the drift schema.
