## MODIFIED: "Live-refreshing an open ticket detail screen"

Replace the existing section (current `tickets.md:2381-2429`) with:

`TicketsCubit` is a single app-wide instance, provided once by
`WorkspaceShell` rather than re-created per screen — so every write path
that could affect the currently-open `TicketDetailScreen` already runs
through the same instance whose `state` may be `TicketDetailLoaded` for
a ticket a background write just touched (or affects an ancestor of).

A declarative table, `_liveRefreshDependents` (`Map<TicketType,
Set<TicketType>>`), names which direct-child ticket types a parent
type's displayed detail state depends on: `story → {task, bug}`
(Story's `canAdvanceSddStage`/`sddStageBlockReason` reads its direct
Task/Bug children's status) and `epic → {story}` (Epic's
`canAdvanceSddStage`/`sddStageBlockReason` reads its direct Story
children's `sddStage`).

A private helper, `_refreshDetailIfOpenAndAffected(Set<String>
writtenTicketIds, {TicketsState? fromState})`, exploits both: if
`fromState` (or, when omitted, a live read of `state`) isn't
`TicketDetailLoaded`, it no-ops. Otherwise it re-fetches and silently
re-emits `TicketDetailLoaded` for the open ticket in two cases, checked
against every id in `writtenTicketIds` until one matches: any id in
`writtenTicketIds` is the ticket currently shown; or the currently shown
ticket's `type` is a key in `_liveRefreshDependents`, some id in
`writtenTicketIds` resolves to a ticket whose `type` is in that key's
value set, and that ticket's `parentId` matches the currently shown
ticket's `id`. No-ops otherwise (nothing open, or every written ticket
is unrelated). The re-fetch itself goes through `getTicketById`, whose
same-id Loading-skip is what keeps this invisible rather than flashing
a spinner over content already on screen.

Call sites wired to it:

- `createTicket`/`updateTicket` chain it onto the completion of their
  existing `TicketEstimationSuggester.suggest` call — reading a live
  `state` is correct here, since this runs well after the call's own
  synchronous emission. `createTicket` additionally fires it
  immediately (not chained onto the suggester) right after its own
  write, passing the state captured *before* its own `TicketCreating`
  emission — independent of whether a suggestion ever lands, since a
  newly created child can flip its parent's precondition (e.g. "at
  least one child exists") the moment it exists.
- `updateTicketStatus`, `updateStatusForTickets`, `trashTicket`,
  `trashTickets`, `updateTicketParent`, and `advanceSddStage` each fire
  it after their own write, passing the state captured *before* their
  own emissions (`fromState`) — their own intermediate/optimistic
  emissions would otherwise have already overwritten a live `state`
  read by the time this runs, permanently hiding the case where a
  detail screen was open when the call started. `trashTicket` only
  fires it from the branch where the trashed ticket is *not* the one
  currently shown (the "trashed ticket is itself open" case already
  navigates away via its existing `TicketTrashed` emission and needs no
  refresh) — this branch now correctly checks the open ticket's `id`
  against the trashed id, not just "was *some* detail screen open";
  previously it navigated away from whichever detail screen happened to
  be open regardless of which ticket was actually trashed.
  `updateTicketParent` fires two checks, not one: the generalized call
  above only ever discovers the reparented ticket's *new* parent (its
  post-write `parentId`), so a second, narrower check — reading the
  ticket's *pre*-write `parentId` directly, which only the caller still
  has — separately catches the *old* parent losing a child.

This closes the "passive AI suggestion lands while the same ticket's
detail screen is already open" staleness gap; the "a sibling Task
completing while the Story's detail screen is already open"
`canAdvanceSddStage` staleness gap, now for **every** relevant write
path (single status write, bulk status write, trash/restore-via-create,
reparent — not just the single-ticket status-write path); and the "an
Epic's detail screen when a child Story's own `sddStage` advances"
staleness gap. The explicit Regenerate path and `changeTicketStatus`
(the detail screen's own status-write path) are unaffected — both
already re-emit synchronously and have no gap to begin with.

**Not wired**, deliberately: `updatePriorityForTickets` (no
`_liveRefreshDependents` entry watches `priority`); `TrashCubit.restore`
and any `TicketParentTrashService`-driven write originating outside
`TicketsCubit` (`TicketMarkdownReconciler`, `TicketRepairService`) —
none of those callers hold a reference to the live `TicketsCubit`
instance, and `TrashCubit`'s Trash screen is a mutually exclusive route
from `TicketDetailScreen` in Aion's single-pane navigation, so no
human-driven restore can race an open detail screen today.
