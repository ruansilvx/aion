# Ticket Search Pagination

# Proposal: Ticket search pagination

## Problem

`TicketRepository.searchTickets` / `TicketDao.searchTickets` return every
matching row with no `LIMIT`/pagination of any kind — confirmed in
`aion/lib/features/tickets/data/daos/ticket_dao.dart` (both the typed-select
branch and the raw `tickets_fts` `customSelect` branch) and in
`aion/lib/features/tickets/data/repositories/drift_ticket_repository.dart`
(a bare pass-through, no slicing). This is the exact known-gap flagged in
`aion-arch/specs/tickets.md`'s "Known gaps" section:

> `TicketRepository.searchTickets`/`TicketDao.searchTickets` return every
> matching row with no `LIMIT`/pagination — an unfiltered or
> loosely-filtered search on a large ticket table fetches and holds the
> entire result set in memory (and, on web, marshals it across the drift
> WASM worker boundary) even though `TicketsListScreen`'s
> `ListView.separated` only ever builds the visible rows.

`TicketsListScreen` is the sole production call site for `searchTickets`
(both the unfiltered initial load and every filtered/text search), so this
is the primary ticket-browsing surface in the app.

## What we're building

Real cursor-style pagination (offset-based `LIMIT`/`OFFSET` under the
hood) from the DAO up through an infinite-scroll list UI:

- `TicketDao.searchTickets` accepts `limit`/`offset` and applies them to
  both its typed-select and raw-SQL FTS branches.
- `DriftTicketRepository.searchTickets` fetches `limit + 1` rows to derive
  `hasMore` without a separate `COUNT` query, trims to `limit`, and
  returns a new `TicketSearchPage` entity (`tickets` + `hasMore`) instead
  of a bare `List<Ticket>`.
- `TicketsCubit` gains a `loadMoreTickets()` method and remembers the
  active query/filters internally so the screen doesn't need to pass them
  on every scroll trigger. A page size of 50 is used throughout.
- `TicketsListScreen`'s flat list gains scroll-triggered infinite loading.
  Board mode (which has no single owning scroll container — six
  independent per-status columns) gets an explicit "Load more" affordance
  instead of a scroll trigger.

## Why this shape

- **Offset-based, not keyset/cursor pagination.** A true keyset cursor
  (paginating on `(created_at, id)` or `bm25` rank) would be more robust
  against concurrent inserts during a scroll session, but adds real
  complexity (composite comparison predicates, especially awkward against
  `bm25`-ranked FTS results, which have no stable numeric tiebreaker
  exposed today). This is a solo-scale, single-user, local-first app —
  the same reasoning `project.md`'s Storage Model already applies to
  embeddings similarity ("brute-force ... sufficient at personal scale;
  revisit ... only if performance demands it"). Plain `LIMIT`/`OFFSET`
  is simpler, and the `TicketRepository`/`TicketDao` interface changes
  needed to move to keyset pagination later are additive, not a rewrite.
- **`limit + 1` trick for `hasMore`**, not a separate `COUNT(*)` query —
  avoids doubling every page fetch's round trip for a boolean the app
  only uses to decide whether to show a scroll trigger.
- **A new `TicketSearchPage` entity**, not a raw `(List<Ticket>, bool)`
  record, to stay consistent with this codebase's existing
  `Equatable`-entity convention (`project.md`'s Models section) and to
  give the pagination result a documented, discoverable type.
- **Board mode gets a manual "Load more" button, not per-column infinite
  scroll.** `TicketBoardView` groups whatever's already loaded into six
  independent status columns, each with its own `ListView.separated`.
  Wiring scroll-triggered loading to six independent scroll positions
  (and deciding which column's proximity-to-bottom should fire a global
  page fetch) is meaningfully more complex than the flat list's single
  scroll container, for a mode that's secondary to the primary list view.
  A single "Load more" affordance reuses the exact same
  `loadMoreTickets()` cubit method with a UI trigger suited to the
  layout, rather than a time-boxed hack.

## Non-goals

- **`TicketRepository.getAllTickets()` stays unbounded.** It backs
  `TicketsCubit.getValidParentCandidates`/`updateTicketParent`'s cycle
  detection, which needs the *complete* ticket graph to be correct — a
  paginated view would silently miss cycles involving tickets outside the
  loaded window. It's also not the known-gap this change targets. Out of
  scope here; revisit separately if it ever becomes a real bottleneck.
- **No new "jump to page N" or page-count UI.** Infinite scroll only,
  matching how every other list in this app already renders (lazy
  `ListView.builder`/`.separated`, no pager control anywhere).
- **No debounce timer for the scroll trigger.** The concurrency guard is
  state-based (`loadMoreTickets()` no-ops unless the cubit is in a
  settled, `hasMore: true` list state), not time-based — see design.md.

## Known ripple effect (in scope)

`TicketsCubit.createTicket`, `updateTicketStatus`, `trashTicket`, and
`trashTickets` currently refresh their list via the *unbounded*
`_repository.getAllTickets()` after every mutation — today this silently
discards whatever search/filter was active (a pre-existing, separate
quirk, not touched here beyond what's necessary) and would also
re-introduce this change's exact problem (an unbounded fetch) on every
ticket create/status-change/trash. This change switches those four
refreshes to the same paginated `searchTickets` call, re-requesting
however many tickets were already loaded (so a background status update
from a board drag doesn't collapse an infinite-scrolled list back down to
page one) using the cubit's remembered filters. See design.md for exact
mechanics.
