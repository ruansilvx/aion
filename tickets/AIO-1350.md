# Page Content Markdown Editor

# Proposal: Page Content Markdown Editor (restructured — dedicated `features/pages/` module)

**Restructure note:** this supersedes the original proposal, which planned
to embed the new Markdown editor directly into the shared
`TicketDetailScreen`. Per a follow-up brainstorm session
(`aion-arch/ideas/dedicated-page-feature-module.md`), pages now get their
own dedicated feature module instead. This is still the same change name
(`page-content-markdown-editor`) and branch, restructured before
`/apply` per `cycle-stages.md`'s guidance — cheaper to redirect now than
migrate later, since nothing has been implemented yet.

## What

Two things, delivered together because the second depends on the first:

1. **A Markdown-rendering content editor** (`MarkdownEditor`/`MarkdownView`,
   `design_system/molecules/`) — unchanged from the original proposal: full
   CommonMark + GFM (tables, strikethrough, task lists, autolinks) via the
   `markdown` pub.dev package for parsing, a hand-written non-Material
   renderer for display, responsive (toggle edit/view on narrow screens,
   live split view on wide screens).
2. **A new `features/pages/` module** — `PageDetailScreen` and
   `PageCreateScreen`, replacing `page`-type tickets' current use of the
   shared `TicketDetailScreen`/`CreateTicketScreen`. This module renders
   only page-relevant fields (title, the new Markdown content editor,
   sub-pages tree, linked tickets, backlinks) — no priority/estimate/
   time-spent/status chrome that only makes sense for work-item tickets.
   It depends on `features/tickets`-owned data only through a new
   `core/contracts/PageTicketProvider` interface (per `project.md`'s
   Pattern 1), never a direct cross-feature import.

`page` stays a `Ticket` row (`TicketType.page`) in the same drift table —
no new entity, no change to the type-compatibility matrix, the Markdown
git-sync/embeddings pipeline, trash, or linked-tickets/backlinks
infrastructure. Only the presentation layer (which screens render a page,
and which module owns them) changes.

## Why

Two independent-but-compounding problems, both surfaced this session:

- Page *content* editing was still a plain single-line-styled text box
  (see the original conclusion in
  `aion-arch/ideas/create-edit-and-delete-pages.md`) — addressed by the
  Markdown editor, unchanged from the original proposal.
- Pages sharing `TicketDetailScreen`/`CreateTicketScreen` with work-item
  tickets means every page renders (and every page-create form asks for)
  fields that don't apply to it — priority, estimate, time-spent, status —
  and every future addition to `TicketDetailScreen` for work-item needs
  risks bloating a screen pages don't need. Splitting pages into their own
  feature module fixes both: a cleaner page UI, and a `tickets` feature
  that isn't forced to keep growing to serve two very different UI shapes
  (a Jira-like work item vs. a Notion-like document) through one screen.

## Scope boundaries (explicit)

- **In scope:**
  - Full CommonMark + GFM Markdown parsing/rendering (`markdown` package +
    hand-written `MarkdownView`/`MarkdownEditor`).
  - A new `features/pages/` module: `PageDetailScreen`, `PageCreateScreen`,
    `PagesCubit`, routes (`/workspace/pages/:id`, `/workspace/pages/new`).
  - A new `core/contracts/PageTicketProvider` interface + its
    `features/tickets/data/` implementation.
  - Promoting the handful of existing `tickets`-owned widgets
    `PageDetailScreen` needs (sub-pages/linked-tickets/backlinks sections,
    sync-status badge/repair banner, a minimal delete action) to
    `design_system/molecules/`, per Pattern 2 — generalizing first if
    they're not already type-agnostic.
  - Updating `Documentation` section navigation (the "+ New page" action
    and page-node taps) to target the new routes instead of the shared
    ticket routes.
  - Removing `page` as a creatable type from `CreateTicketScreen`'s type
    picker, and redirecting `/workspace/tickets/:id` to
    `/workspace/pages/:id` when the id resolves to a `page` ticket, so
    there's exactly one creation/detail path per type, not two.
- **Out of scope:**
  - A draggable/reorderable block-based editor, a formatting toolbar, and
    full inline image display — all still deferred, unchanged from the
    original proposal.
  - `resource` tickets — stay on `TicketDetailScreen`/`CreateTicketScreen`
    exactly as today (resources aren't part of this restructure; only
    `page` moves to the new module). `resource`'s own eventual UI
    treatment is the separate `upload-and-visualize-files-for-resource-tickets`
    idea's concern.
  - Comment threads on pages — `TicketDetailScreen`'s comment section is
    explicitly **not** promoted or ported to `PageDetailScreen` in this
    slice, to keep the widget-promotion list bounded. Pages have no
    comment thread for now; this can be revisited later if wanted.
  - Any change to the `Ticket` entity, drift schema, type-compatibility
    matrix, or Markdown file-sync pipeline.
