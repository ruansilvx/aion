# Design: coding-execution-reliability-and-safety

## 1. `GitRepositoryClient` — worktree + push

`core/git/git_repository_client.dart` (existing "thin CLI wrapper, no
interface" class — see its own class doc) gains three methods, same
`Process.run`-via-`_run` shape as `init`/`add`/`commit`:

```dart
/// Runs `git worktree add -b <branchName> <worktreePath>` in [rootPath],
/// creating a new branch checked out into an isolated working directory
/// at [worktreePath] — the branch starts from [rootPath]'s current HEAD.
/// Throws if `worktreePath` already exists or `branchName` is already
/// checked out elsewhere.
Future<void> createWorktree(
  String rootPath,
  String worktreePath,
  String branchName,
) async {
  await _run(['worktree', 'add', '-b', branchName, worktreePath], rootPath);
}

/// Runs `git worktree remove <worktreePath> --force` in [rootPath].
/// `--force` because the worktree may contain untracked build artifacts
/// (`.dart_tool/`, `build/`) from the `flutter pub get`/coding-execution
/// turn that ran inside it — git's default refuses removal with any
/// untracked content present. Does not delete [branchName] itself; the
/// branch survives (and stays pushed, if `push` below already ran)
/// after the worktree is gone.
Future<void> removeWorktree(String rootPath, String worktreePath) async {
  await _run(['worktree', 'remove', worktreePath, '--force'], rootPath);
}

/// Runs `git push -u origin <branchName>` in [worktreePath] — pushes the
/// branch created by [createWorktree] from inside the worktree itself
/// (not [rootPath]), since that's where the branch's commits actually
/// live.
Future<void> push(String worktreePath, String branchName) async {
  await _run(['push', '-u', 'origin', branchName], worktreePath);
}
```

## 2. New `GitHubCliClient` (`core/git/github_cli_client.dart`)

Same shape as `GitRepositoryClient` — plain `core/` infrastructure, one
implementation, no `core/contracts/` interface (matches its own "no
feature-specific logic to invert" reasoning).

```dart
// core/git/github_cli_client.dart — GitHubCliClient (core layer).

import 'dart:io';

/// Thin wrapper around the `gh` CLI, invoked via [Process.run]. Mirrors
/// [GitRepositoryClient]'s shape — one implementation, no interface.
/// Desktop-only, same scope as [GitRepositoryClient].
class GitHubCliClient {
  /// Runs `gh pr create --title <title> --body <body> --head <branch>`
  /// in [rootPath] (the worktree the branch's commits live in — `gh`
  /// resolves the remote/base branch from the local repo config the same
  /// way it does for a human running the command by hand). Returns the
  /// created PR's URL, parsed from `gh pr create`'s stdout (its last
  /// non-empty line). Throws [ProcessException]-shaped output on
  /// failure (`gh` not installed/authenticated) — the caller
  /// (`TicketsCubit._runCodingExecution`) surfaces this as a normal
  /// execution failure, not a special case.
  Future<String> openPullRequest({
    required String rootPath,
    required String branch,
    required String title,
    required String body,
  }) async {
    final result = await Process.run('gh', [
      'pr',
      'create',
      '--title',
      title,
      '--body',
      body,
      '--head',
      branch,
    ], workingDirectory: rootPath);
    if (result.exitCode != 0) {
      throw ProcessException('gh', ['pr', 'create'], result.stderr.toString());
    }
    return result.stdout.toString().trim().split('\n').last;
  }
}
```

## 3. New `FlutterVerifier` (`core/build/flutter_verifier.dart`)

```dart
// core/build/flutter_verifier.dart — FlutterVerifier (core layer).

import 'dart:io';

/// Result of a [FlutterVerifier.analyze] run.
class FlutterVerifyResult {
  const FlutterVerifyResult({required this.passed, required this.output});

  /// Whether `flutter analyze` exited 0 (no issues at or above the
  /// project's configured `analysis_options.yaml` severity).
  final bool passed;

  /// Raw combined stdout/stderr, fed back to the model verbatim as the
  /// corrective turn's prompt content on failure.
  final String output;
}

/// Thin wrapper around `flutter analyze`/`flutter pub get`, invoked via
/// [Process.run]. One implementation, no interface — same shape as
/// [GitRepositoryClient]/[GitHubCliClient].
class FlutterVerifier {
  /// Runs `flutter analyze` in [rootPath] (a coding-execution worktree).
  Future<FlutterVerifyResult> analyze(String rootPath) async {
    final result = await Process.run('flutter', [
      'analyze',
    ], workingDirectory: rootPath);
    return FlutterVerifyResult(
      passed: result.exitCode == 0,
      output: '${result.stdout}\n${result.stderr}'.trim(),
    );
  }

  /// Runs `flutter pub get` in [rootPath] — the one-time setup a fresh
  /// coding-execution worktree needs so [analyze] (and the model's own
  /// tool calls) see a working `.dart_tool/package_config.json`. Kept on
  /// this same injectable class (rather than a raw `Process.run` inline
  /// in `TicketsCubit`) specifically so tests can mock it instead of
  /// spawning a real `flutter` subprocess.
  Future<void> pubGet(String rootPath) async {
    await Process.run('flutter', ['pub', 'get'], workingDirectory: rootPath);
  }
}
```

## 4. `AgentModelClient` — `AgentToolUseEvent`

`core/contracts/agent_model_client.dart`'s sealed `AgentEvent` gains a
fourth non-terminal variant, alongside `AgentTextEvent`:

```dart
/// A tool call the model made mid-run (file edit, git, bash, MCP). Purely
/// informational — never a terminal event. [toolName] is the SDK's own
/// tool name (`Read`, `Write`, `Bash`, ...); [summary] is a short,
/// human-readable one-liner derived from the tool's input (e.g. the file
/// path for `Read`/`Write`, the command for `Bash`) — `null` if the
/// bridge couldn't derive one for an unrecognized tool.
class AgentToolUseEvent extends AgentEvent {
  const AgentToolUseEvent(this.toolName, this.summary);

  final String toolName;
  final String? summary;

  @override
  List<Object?> get props => [toolName, summary];
}
```

## 5. `agent_bridge/index.mjs` — emitting `tool_use`

The existing `assistant` message handler already filters
`message.message.content` for `block.type === 'text'`; add a sibling
filter for `block.type === 'tool_use'`:

```js
} else if (message.type === 'assistant') {
  const content = message.message?.content ?? [];
  const text = content
    .filter((block) => block.type === 'text')
    .map((block) => block.text)
    .join('');
  for (const block of content.filter((b) => b.type === 'tool_use')) {
    emit({
      type: 'tool_use',
      name: block.name,
      summary: summarizeToolInput(block.name, block.input),
    });
  }
  // ...existing message.error / text.length > 0 handling unchanged...
}
```

`summarizeToolInput(name, input)` — a small new helper in the same file:
returns `input.file_path` for `Read`/`Write`/`Edit`, `input.command` for
`Bash`, `input.pattern` for `Grep`/`Glob`, else `undefined` (bridge omits
`summary` from the emitted JSON, `ClaudeAgentSdkClient._parseLine` passes
`null` through). Truncated to ~120 chars — this is a live status hint, not
a transcript.

## 8. `TicketsCubit._runCodingExecution` — worktree + two-turn restructure

Full replacement of today's single-turn body. New private constants:

```dart
static const _maxAnalyzeRetries = 2;
```

New collaborators (constructor-injected, same optional-dependency pattern
as `_agentClient`/`_commentRepository`/`_automationSettingsRepository` —
`null` no-ops the same way): `GitRepositoryClient`, `GitHubCliClient`,
`FlutterVerifier`.

```
_runCodingExecution(task):
  1. worktreePath = a fresh temp dir (Directory.systemTemp.createTempSync)
  2. branchName = 'aion/task-${task.id}'
  3. await _gitClient.createWorktree(_projectRootPath, worktreePath, branchName)
  4. await _flutterVerifier.pubGet(worktreePath)
     — one-time setup so `flutter analyze` (step 7) and the model's own
     tool calls both see a working `.dart_tool/package_config.json`.
     Landed as `FlutterVerifier.pubGet` rather than an inline
     `Process.run` in `TicketsCubit` (this section's original sketch) so
     tests can mock it instead of spawning a real `flutter` subprocess —
     see `core/build/flutter_verifier.dart` §3's updated shape.
  5. spawn "Coding Execution — <task.title>" chat, post system context
     comment (_assembleExecutionContext — see §9), same as today.
  6. try:
       attempt = 0
       loop:
         run implementation turn via ChatCubit.runChatTurn
           (workingDirectory: worktreePath, toolsEnabled: true,
            onToolUse: ... as §7)
         verifyResult = await _flutterVerifier.analyze(worktreePath)
         if verifyResult.passed: break out to step 7 (PR path)
         attempt += 1
         confidence = effective AutomationContext.codingExecutionRetry
                      confidence (same _overageDetectedThisSession-style
                      escalation: forced to `gated` once attempt >
                      _maxAnalyzeRetries, regardless of configured value)
         if confidence == auto and attempt <= _maxAnalyzeRetries:
           post system comment with verifyResult.output, continue loop
           (next iteration re-prompts: "flutter analyze reported: <output>.
            Fix these issues, then end your reply with
            'IMPLEMENTATION: DONE' again.")
         else:
           post final "Execution failed verification: <output>" comment
           (authorType: system)
           if confidence != auto (i.e. gated, or auto-exhausted):
             emit TicketsErrorReason.executionVerificationFailed toast
           break out to step 8 (cleanup), no PR
  7. (verify passed) await _gitClient.push(worktreePath, branchName)
     final prUrl = await _githubClient.openPullRequest(...)
     post system comment: 'EXECUTION: PR_OPENED $prUrl'
     — proceeds to the existing prConfirmed / AutomationConfidence.
       codingExecution completion-flip logic, unchanged from today.
  8. finally: await _gitClient.removeWorktree(_projectRootPath, worktreePath)
     — always runs, success or failure, mirroring today's
       _inFlightExecutionTaskId-cleared-in-finally discipline.
```

`retryCodingExecution(Ticket task)` (new public method — the failure
banner's manual-retry action, and what the `gated`/exhausted-`auto` toast
links to): re-enters the same `_runCodingExecution` flow for `task`,
creating a fresh worktree/branch exactly as a first attempt would
(the failed attempt's worktree is already removed per step 8 above,
and its branch — never pushed, since it never reached step 7 — is simply
abandoned; no cleanup needed beyond what step 8 already does).

## 11. `getTicketById` additions — `executionFailureReason`/`executionCanRetry`

Computed alongside today's `isExecuting`/`executionQueuePosition`/
`executionAwaitingReview`, in the same `if (ticket.type ==
TicketType.task)` block, only when none of those three apply and
`ticket.status == TicketStatus.inProgress`:

```
find the Task's most recent "Coding Execution — "-prefixed chat
find its most recent comment
if comment.authorType == system and content starts with
   "Execution failed verification:":
     executionFailureReason = content (the analyze output)
     executionCanRetry = true
else if comment.authorType == ai/system and content starts with
   "Execution failed:" (the pre-existing ChatCubit.runChatTurn hard-error
   comment, unchanged):
     executionFailureReason = content
     executionCanRetry = true
else if no terminal reply exists at all on the most recent chat (reuses
     _mostRecentChatHasTerminalReply's lookup, inverted) — an
     orphaned/stalled run, e.g. from an app restart mid-run:
     executionFailureReason = a fixed "Execution ended without a clear
       result — retry to try again." string
     executionCanRetry = true
else:
     executionFailureReason = null
     executionCanRetry = false
```

Both fields persist across an app restart (unlike `isExecuting`/
`executionQueuePosition`, which are in-memory-queue-derived) since
they're computed from the persisted comment thread — this also finally
gives the "restart mid-queue" known gap a real recovery path (the retry
button) instead of only the toggle-status workaround.

# Aion — Coding-Execution Reliability & Safety: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Task-to-Coding-Execution Trigger Spec](./Aion%20Task%20Execution%20Trigger%20Spec.md), the [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md), and the [SDD Design Gate Spec](./Aion%20SDD%20Design%20Gate%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TicketDetailScreen`, `SettingsScreen`, `CodingRunState`, `AutomationConfidence`, and the existing `_ExecutionRunningHint`, `_ExecutionQueueHint`, `_ExecutionReadyForReviewBanner`, `_AutomationSection`, `_AutomationTrigger`, and `_AutomationMenuRow` by name.

This change closes the last **reliability/safety** gap in coding execution. A live dogfood run proved coding execution works, but a run could open a **broken PR with no verification**, and there was **no way to see or recover from a failed/stalled run** except an undocumented workaround. This pass adds two things:

1. A **verification gate** (`flutter analyze`) that runs before any PR opens. A run only reaches the success/ready-for-review path if verification passes.
2. New UI to show a run's **outcome** — a **fourth coding-run state**, `verificationFailed`, surfaced by generalizing the existing ready-for-review-only banner into a **two-tone `_ExecutionActionBanner`** (§1); plus a **live tool-use indicator** during the running state (§2); plus a **third Settings automation-picker instance** governing retry behavior (§3).

It **adds no new screens**. It extends two existing surfaces:

- **`TicketDetailScreen`** (`task` tickets) — the coding-execution section (Task Trigger spec §0), rendered directly below the ticket-meta row and above the Description block. Its state body now resolves one of **four** states (was three): running (§2 adds a sub-line to it), queued (unchanged), **`_ExecutionActionBanner` success tone** (the former ready-for-review banner), or **`_ExecutionActionBanner` failure tone** (new).
- **`SettingsScreen`** — a **third** `_AutomationSection` instance, "Coding-Execution Retry" (§3), stacked under the shared `AUTOMATION` eyebrow after the two existing instances. No new visual states — new copy in the existing shape.

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (non-Material) / `Padding` / `Row` / `Column` / `GestureDetector` / `MouseRegion` / `AnimatedScale` / `AnimatedOpacity` / `RotationTransition` / `SingleChildScrollView` / `ShaderMask` / `CustomPaint`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `LinearProgressIndicator`, `InkWell`, `DropdownButton`, `Chip`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` with the theme's `fillAlpha` (Arctic `0.11`, Obsidian `0.16`) unless another alpha is stated, exposed at the call site as `ThemeScope.of(context).fillAlpha`.

**New tokens:** none for color/type/radius. Two **derived tint helpers** are added on `AionColorsHubTokens`, mirroring the existing `destructiveTint(isDark)` shape exactly (§4) — `dangerTint` / `dangerBorderTint`. One structural addition: `CodingRunState.verificationFailed` (§5).

## 0. The coding-execution section — updated state resolution

The section container, eyebrow, and run-status line are **unchanged** from Task Trigger spec §0 (top `border` 1px divider, padding `EdgeInsets.fromLTRB(22, 16, 22, 16)`, no fill/radius, inner `Column` `crossAxisAlignment: stretch`, `gap: 14`; eyebrow `"CODING EXECUTION"` in `AionText.caption` / `textMuted`; run-status `Row` `gap: 8` = `8×8` dot + `AionText.body` text).

The **run-status line** gains a fourth row and the **state body** gains a fourth branch:

| `CodingRunState` | Dot color | Line text | State body |
|---|---|---|---|
| `running` | `primary` (`#2E86D4 / #9366FF`) | `"Executing"` | §2 running hint **+ live tool-use line (new)** |
| `queued` | `secondary` (`#5E7183 / #57608A`) | `"Queued"` | `_ExecutionQueueHint` (Task Trigger spec §2, unchanged) |
| `readyForReview` | `success` (`#1E9E76 / #33D19B`) | `"Run complete"` | **`_ExecutionActionBanner`, tone `success`** (§1) |
| `verificationFailed` | `danger` (`#CE3D54 / #F1546C`) | `"Verification failed"` | **`_ExecutionActionBanner`, tone `failure`** (§1) |

The `verificationFailed` state is entered when the run's `flutter analyze` gate fails, when the run hard-errors, when it ends ambiguously with no clear result, or when it is detected stalled/orphaned (e.g. after an app restart). All four map to the same failure tone; the message (§1.4) carries the specific reason.

## 1. `_ExecutionActionBanner` (new — replaces `_ExecutionReadyForReviewBanner`)

A single banner with a `tone` parameter — `BannerTone.success` or `BannerTone.failure` — sharing one layout/geometry. The `success` tone **is** the former `_ExecutionReadyForReviewBanner` (Task Trigger spec §3) re-housed unchanged; the `failure` tone re-keys the tint/border/glyph to `danger` and adds a scrollable error region + a `secondary` Retry button.

```dart
enum BannerTone { success, failure }

class _ExecutionActionBanner extends StatelessWidget {
  final BannerTone tone;
  final String title;          // §1.3
  final String? subline;       // §1.3 — optional PR/run metadata
  final String? errorDetail;   // §1.4 — failure tone only; raw analyze/error text
  final String actionLabel;    // "Mark ready for review" | "Retry"
  final VoidCallback? onAction; // null → disabled (§1.6)
  // ...
}
```

### 1.1 Container — shared geometry, color re-keyed by tone

- `DecoratedBox` → `Padding` → `Column`.
- **Radius:** `BorderRadius.circular(12)` (`AionRadius.lg`), both tones, both themes.
- **Shadow:** none.
- **Padding:** `EdgeInsets.fromLTRB(14, 13, 14, 14)`, both tones.
- **Layout:** `Column`, `crossAxisAlignment: stretch`.
  - **success tone:** `gap: 12` — (1) header `Row` (§1.2 + §1.3), (2) action button (§1.5).
  - **failure tone:** `gap: 11` — (1) header `Row` (§1.2 + §1.3), (2) error region (§1.4), (3) action button (§1.5).
- **Fill / border, per tone:**

| Tone | Fill | Border |
|---|---|---|
| `success` | `success.withOpacity(fillAlpha)` (`0.11 / 0.16`) | `1px solid success.withOpacity(isDark ? 0.42 : 0.28)` |
| `failure` | `danger.withOpacity(fillAlpha)` = **`dangerTint(isDark)`** (§4) | `1px solid danger.withOpacity(isDark ? 0.42 : 0.28)` = **`dangerBorderTint(isDark)`** (§4) |

### 1.2 Leading glyph (header `Row`, `gap: 12`)

| Tone | Glyph | Size | Color | `crossAxisAlignment` of header Row |
|---|---|---|---|---|
| `success` | `check` (`git-pull-request` / `seal-check` fallback per Task Trigger spec §3.2) | `18px` | `success` (`#1E9E76 / #33D19B`) | `center` |
| `failure` | `warning` (`warning-triangle` / `warning-circle` fallback) | `17px` | `danger` (`#CE3D54 / #F1546C`) | `start` — the title can wrap to 2 lines above a sub-line, so the glyph pins to the top |

### 1.3 Text column (`Expanded`, `gap: 2`)

- **Title:** `AionText.cardTitle` (14 / w600), color `textPrimary` (`#142230 / #E7EDF7`).
  - success: `"Coding run finished — PR opened"`
  - failure: `"Verification failed — PR not opened"`
- **Sub-line** (optional): `AionText.time` (mono 11 / w400), color `textSecondary` (`#46586A / #A2AEC6`).
  - success: e.g. `"PR #131 · 4 files changed · analyze clean"`
  - failure: e.g. `"flutter analyze · 3 issues · run #44"` — a short one-line summary; the full text goes in the error region (§1.4).

### 1.4 Error region — failure tone only (long-content behavior)

**Decision: a fixed-max-height, vertically scrollable mono well with a persistent bottom fade.** Chosen over a "show details" disclosure because (a) the banner keeps a constant height regardless of error length — a stalled/orphaned run and a 30-line analyze dump look the same size in the ticket flow; (b) no extra tap is required to read the reason (recovery-critical info stays visible); (c) it matches the app's existing terminal/mono affordances. The bottom fade signals "more below" without a scrollbar-dependent cue on touch.

- **Container:** `DecoratedBox` → `ConstrainedBox(maxHeight: 96)` → `SingleChildScrollView` → `Padding` → `Text`.
- **Fill:** `background` (`#EDF2F8 / #0A0E18`) — one step off `surface`, reads as a recessed code well against the `danger`-tinted banner (near-black terminal in Obsidian). **Not** a `danger` tint — the well must stay legible.
- **Border:** `1px solid border` (`#D6E0EA / #232C40`).
- **Radius:** `BorderRadius.circular(8)` (`AionRadius.sm` = 6 rounded up to 8 for the nested well; use `8` explicitly).
- **Padding:** `EdgeInsets.fromLTRB(11, 10, 11, 10)`.
- **Max height:** `96` (≈ 5 mono lines). Content taller than this scrolls inside the well; the banner does not grow. Shorter content sizes to fit (no min height beyond its own lines).
- **Text:** the raw error/analyze block, `AionText.time` re-sized to **11.5 / w400** mono (`JetBrains Mono`), color `textSecondary`, `height: 1.55` (line-height), `softWrap: true`, `overflow: TextOverflow.clip`, `WidgetSpan`-free plain string. Wrapping long tokens (paths, commands): `TextWidthBasis.parent` + allow break — implement with a `Text` whose string is emitted as-is; Flutter wraps on whitespace, and for unbroken tokens use `softWrap` with a zero-width-space injector on `/` and `:` if a single token would overflow (optional; the well scrolls horizontally-free — no `Axis.horizontal`).
- **Scroll:** `SingleChildScrollView(primary: false, physics: ClampingScrollPhysics)`. `Scrollbar` is **not** a Material dependency violation (it's `material.dart`) — **do not use it**; instead the bottom fade (below) is the sole overflow cue. A thin custom scroll thumb via `RawScrollbar` is permitted (Flutter widgets layer, not Material) if a persistent indicator is desired: `thickness: 4`, `radius: Radius.circular(2)`, `thumbColor: textMuted.withOpacity(0.4)`.
- **Bottom fade:** a `ShaderMask` / `Stack` overlay pinned to the well's bottom edge — an `IgnorePointer` `Container` `height: 20`, `decoration: BoxDecoration(gradient: LinearGradient(begin: topCenter, end: bottomCenter, colors: [background.withOpacity(0), background]))`, clipped to the well's bottom radius. It sits above the scroll content, below the well's border. When content is scrolled to the end the fade may remain (a static bottom fade is acceptable); a scroll-position-aware fade that hides at `maxScrollExtent` is a nice-to-have (listen to the scroll controller, `AnimatedOpacity` 120ms) — not required.

### 1.5 Action button — full-width, solid, re-colored by tone

Both tones use the **same button geometry** (Task Trigger spec §3.4): `GestureDetector` → `MouseRegion` → `AnimatedScale` → `DecoratedBox` → `Padding` → centered `Row` (glyph + label). Full container width (`crossAxisAlignment: stretch` parent), content centered (`MainAxisAlignment.center`).

- **Padding:** `EdgeInsets.symmetric(horizontal: 15, vertical: 10)`.
- **Radius:** `AionRadius.md` (10).
- **Label:** `AionText.button` (14 / w700), color `#FFFFFF`, `TextAlign.center`.
- **Leading glyph** (in-button, `gap: 7` before label): success — none (label only, unchanged); failure — `arrow-clockwise` / `arrows-counter-clockwise`, `15px`, `#FFFFFF`.
- **Fill / glow, per tone:**

| Tone | Label | Fill | Glow (default) |
|---|---|---|---|
| `success` | `"Mark ready for review"` | `success` (`#1E9E76 / #33D19B`) | `success.withOpacity(isDark ? 0.60 : 0.45)`, blur 18, spread −9, offset (0,8) |
| `failure` | `"Retry"` | **`secondary`** (`#5E7183 / #57608A`) | `secondary.withOpacity(isDark ? 0.55 : 0.40)`, blur 18, spread −9, offset (0,8) |

**Why `secondary`, not `danger` or `primary`, for Retry:** the brief requires the Retry button read as a **secondary/retry action, not destructive**, at the **same visual weight** as the success confirm button (a solid full-width pill). `danger` would read as "delete/destroy"; `primary` would read as the app's main "advance the SDD stage" CTA (wrong meaning) and over-weight a recovery action. `secondary` — the app's neutral solid — carries the same solid weight while reading as "run this again," not "destroy." The `danger` identity of the failure situation is fully carried by the banner frame + warning glyph + error text (§1.1–§1.4); the button is the calm recovery affordance.

### 1.6 Button states — both tones, both themes

`{fill}` = the tone's fill token (`success` / `secondary`); `{glow}` = the tone's glow (§1.5).

| State | Fill | Glow | Extra |
|---|---|---|---|
| **Default** | `{fill}` | tone glow, blur 18, spread −9, offset (0,8) | — |
| **Hover** | `Color.lerp({fill}, isDark ? Colors.white : Colors.black, 0.10)` (derived shade — **no new token**) | glow blur → 22 | `MouseRegion` click cursor |
| **Focused** (keyboard) | `{fill}` | default glow | 3px focus ring `BoxShadow(color: {fill}.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` |
| **Pressed** | `{fill}` | glow suppressed (blur → 0) | `AnimatedScale` → `0.98` over 80ms on `onTapDown` |
| **Disabled** (`onAction == null` — action in flight: confirm request posting, or a retry already spawning) | `{fill}` @ `0.45` opacity | none | `IgnorePointer`; label + glyph `#FFFFFF` @ `0.55` |
| **Error** | n/a | — | a failed confirm/retry surfaces via the existing app toast, out of scope — the banner stays in its current tone/Default |

There is **no `×` dismiss** on either tone (Task Trigger spec §3.4 rationale holds): a finished-with-PR run and a verification-failed run are both non-dismissible run outcomes; the only forward moves are the action button (confirm / retry) or an automation-driven transition. If retry automation is `auto` the banner is not shown for `verificationFailed` (a retry is spawned silently, back to `running`); if `manual` it is shown with the Retry button; the `success` tone is shown for `readyForReview` only when the *stage* automation is `gated`.

## 2. Live tool-use indicator (new — extends the running state)

A small, secondary status line shown **only** while `CodingRunState.running`, added **below** the existing `_ExecutionRunningHint` (Task Trigger spec §1 — the rotating-gear hint), reflecting the run's current tool call.

### 2.0 Placement & structure

The running-state body becomes a `Column`, `crossAxisAlignment: start`, `gap: 9`:
1. `_ExecutionRunningHint` — unchanged (gear `15px` `primary`, `RotationTransition` 2400ms; text `AionText.bodySm` `textSecondary`: `"Execution running — editing files and opening a pull request."`).
2. **`_ExecutionLiveToolLine`** (new) — indented to align under the hint's *text* (not its gear).

### 2.1 `_ExecutionLiveToolLine` layout

- `Padding(EdgeInsets.only(left: 23))` — `23 = 15 (gear box) + 8 (hint row gap)`, so the line's content left edge aligns with the hint text above it, reading as subordinate to it.
- Inner `Row`, `gap: 7`, `crossAxisAlignment: center`.
- **Leading glyph:** a `6×6` filled dot, `BoxShape.circle`, color `textMuted` (`#8496A6 / #6B7690`), wrapped in an `AnimatedOpacity`/`AnimationController` **pulse** (opacity `0.35 ↔ 1.0`, 1400ms ease-in-out, `repeat(reverse: true)`).
  - **Motif decision:** it does **not** share the gear's *rotation* — a second spinning glyph would compete with the primary "Executing" signal. Instead a slow low-contrast **pulse** signals liveness quietly. It is `textMuted` (subordinate), never `primary`. Under reduced-motion (`MediaQuery.disableAnimations`) the dot renders static at full opacity and the controller is not started.
- **Text:** `Expanded(Text(…, maxLines: 1, overflow: TextOverflow.ellipsis, softWrap: false))`.
  - Verb (`"Running"` / `"Reading"` / `"Editing"` / `"Opening"` …): `AionText.bodySm` re-sized to **12.5 / w400**, color `textMuted`.
  - Tool argument (file path / command), appended in the **same `Text` via a `TextSpan`**: `JetBrains Mono` **11.5 / w400**, color `textSecondary` (one notch more present than the verb, so the concrete thing being touched is the readable part), followed by a literal `"…"`.
  - Composed example: `Running ` + `flutter analyze` (mono) + `…`.

### 2.2 Truncation — confirmed

**Single line with ellipsis is sufficient** (`maxLines: 1`, `overflow: TextOverflow.ellipsis`, `softWrap: false`). A long file path or bash command (e.g. `git commit -m "fix: restore overflow-menu elevation shadow in Obsidian theme"`) truncates at the right edge with `…`; the line never wraps and never grows the section. The mono argument and the trailing `…` are in the ellipsized span, so an over-long argument simply clips.

### 2.3 States

Purely informational; **no** hover / focused / pressed / disabled / error states. The only motion is the dot pulse (§2.1). The text updates reactively as the run's active tool changes (plain rebuild — no entrance/exit animation on the string). Default is the only visual state.
