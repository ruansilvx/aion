# Verify follow-ups (2026-09-01)

Gaps found by `/verify` against design.md, not covered by the
sections above. Ordered data → UI, same convention as the rest of
this file.

- [x] `TransitionPreconditionRepository`/`TransitionPreconditionDao`/
      `DriftTransitionPreconditionRepository` — `getNodeCounts()`:
      fetches every graph row and every node row once each (two
      queries total, not an N-stage fan-out), then walks each graph's
      reachable set in memory to produce the per-stage count map.
      Landed on the repository directly rather than
      `TransitionPreconditionConfigCubit` — that cubit is scoped to
      editing one stage at a time, not a natural home for an
      all-5-stages batch read; `WorkflowConfigCubit` (which already
      aggregates everything `WorkflowStatusSettingsScreen` needs) calls
      it instead, via a new optional `TransitionPreconditionRepository`
      constructor param.
- [x] `WorkflowStatusSettingsScreen` — wired the count into
      `_PreconditionAffordance` (via `WorkflowConfigLoaded
      .transitionPreconditionNodeCounts`) and implemented the §5.1/§5.2
      variant split, each showing the live count (or `None`/hidden dot
      when unconfigured). One deviation from the literal spec: the
      compact/labeled decision is made by `_PreconditionAffordance`
      itself from its own `LayoutBuilder`-measured space, not by
      `_SddStageRenameRow`'s gross row width (design.md's literal
      `420`px *row*-width figure) — the row's width alone isn't a
      reliable proxy, since a wide `AttachmentBadge` (a long "KIND ·
      CONFIDENCE" label) can leave this affordance far less room than
      the row's total width would suggest; measuring locally is
      robust to that and was required to fix real `RenderFlex`
      overflow in `workflow_status_settings_screen_test.dart`. The
      count also refreshes on return from the precondition editor
      route (`WorkflowConfigCubit.load()` re-called after the
      `context.push` future resolves).
- [x] `SddStagePreconditionEditorScreen` — added design.md §4.1's two
      missing header elements: the read-only "Stage N of 5"
      stage-position chip (`_StagePositionChip`), and the "N UNSAVED
      CHANGE" dirty indicator (`_DirtyIndicator`, fed by a
      `ValueNotifier<bool>` the screen owns). Dirty-tracking required
      threading a new `TransitionNodeForm.onDirtyChanged` callback
      through both mount sites (`TransitionOutlineList`'s inline form
      and the canvas's popover) up to the screen.
- [x] `SddStagePreconditionEditorScreen` — implemented design.md §4.4's
      narrow-width behavior: outline pane collapses to `340` at
      `760`–`1039`px, both panes full-width at `>= 1040`px; below
      `760`px, a single pane with a header `Graph`/`Outline` toggle
      (`_PaneModeToggle`, mirroring `_BranchModeToggle`'s two-segment
      shape), defaulting to `Outline` whenever the ambient width is
      already below `560`px (re-derived every build until the user
      picks explicitly, rather than fixed once at construction); below
      `560`px the header stacks to two lines. One deliberate
      simplification: the stacked header keeps the Reset button inline
      on the second line (in a horizontally-scrollable row alongside
      the chips/toggle) rather than building a new overflow-menu
      component for design.md's literal "⋯ overflow IconBtn" — Reset
      stays a plain, always-reachable button at the cost of occasional
      horizontal scroll at the very narrowest widths. The canvas
      pane's `400`px "min-width" at the `760`–`1039`px band is not
      separately enforced (no `ConstrainedBox`/custom flex clamp) —
      `Expanded` naturally leaves it `>= 419px` there since the outline
      is capped to `340`px, so no code-level minimum was needed to
      honor the spec's intent.
