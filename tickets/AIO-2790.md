# Design: Fix the trash/restore cascade → git projection gap

## Architecture overview

No new classes and no DI/wiring changes — this is a set of signature and
internal-logic edits to four existing files (interface, Drift impl,
decorator, cubit) plus the reconstruction service, following the exact
`TicketRepository`-interface boundary `fix-ticket-git-projection-gap`
already established:

```
TicketsCubit / TrashCubit / TicketParentTrashService   (unaffected callers —
      │  await trashTicket/restoreTicket/trashTickets,   ignore the now-
      │  richer return value exactly like ignoring void)  richer return
      ▼
GitProjectingTicketRepository        ← batches the FULL affected-id set
      │  wraps
      ▼
DriftTicketRepository                ← now RETURNS the affected-id set
                                        it already computes internally
```

## 1. `TicketRepository` interface changes

`lib/features/tickets/domain/repositories/ticket_repository.dart`

```dart
/// Moves [id] and every ticket in its structural subtree into trash
/// (sets `deletedAt`, deletes nothing). Never blocked by children —
/// they're cascaded into trash alongside [id] instead. Returns every id
/// actually moved to trash — [id] itself plus every cascaded descendant,
/// deduplicated, in unspecified order — so a caller that must react to
/// every affected ticket (not just [id]) can, without re-deriving the
/// cascade itself. Throws [StateError] if [id] does not exist.
Future<List<String>> trashTicket(String id);

/// Moves every ticket in [ids] — and each one's full structural
/// subtree — into trash in one call. Returns every id actually moved
/// (== [ids] plus every cascaded descendant, deduplicated) — the full
/// set, not just a count, for the same reason [trashTicket] returns one.
/// Ids that don't exist are silently skipped.
Future<List<String>> trashTickets(List<String> ids);

/// Restores [id] out of trash, along with any currently-trashed
/// ancestors (so it's never left with a hidden parent) and any
/// currently-trashed descendants (its own subtree, trashed alongside it
/// originally). Returns every id actually restored — [id] itself plus
/// every revived ancestor/descendant, deduplicated, in unspecified
/// order. Throws [StateError] if [id] does not exist.
Future<List<String>> restoreTicket(String id);
```

`previewTrashCount`/`getTrashedTickets` are untouched.

This is a breaking signature change to a domain interface with two
implementations (`DriftTicketRepository`, `GitProjectingTicketRepository`)
and every test double that stubs these three methods — see "Testing"
below for the full blast radius. No production call site needs its own
logic to change beyond the two decorator methods and one cubit method
below: every other caller (`TicketParentTrashService.trash`/`restore`,
`TrashCubit.restoreTickets`'s loop, `bin/migrate_aion_arch.dart` if it
ever called these — it doesn't) simply `await`s the call and can go on
ignoring the return value exactly as it ignored `void`/`int` before.

## 2. `DriftTicketRepository` — return the cascade instead of discarding it

`lib/features/tickets/data/repositories/drift_ticket_repository.dart`

```dart
@override
Future<List<String>> trashTicket(String id) async {
  final existing = await _db.ticketDao.getTicketById(id);
  if (existing == null) {
    throw StateError('Ticket $id does not exist');
  }
  return trashTickets([id]);
}

@override
Future<List<String>> trashTickets(List<String> ids) async {
  final affected = await _resolveDescendantCascade(ids);
  if (affected.isEmpty) return const [];
  await _db.ticketDao.softDeleteByIds(
    affected.toList(),
    DateTime.now().millisecondsSinceEpoch,
  );
  return affected.toList();
}

@override
Future<List<String>> restoreTicket(String id) async {
  final existing = await _db.ticketDao.getTicketById(id);
  if (existing == null) {
    throw StateError('Ticket $id does not exist');
  }
  final toRestore = <String>{id};
  toRestore.addAll(await _db.ticketDao.getAncestorIds(id));
  toRestore.addAll(await _db.ticketDao.getDescendantIds(id));
  await _db.ticketDao.restoreByIds(toRestore.toList());
  return toRestore.toList();
}
```

No DAO changes — `_resolveDescendantCascade` and `restoreTicket`'s
`toRestore` set were already computing exactly this; only the return
statement changes. `trashTicket`'s existence check moves inline (was
previously delegated entirely to `trashTickets([id])`, whose own
`_resolveDescendantCascade` silently no-ops on a missing id rather than
throwing) so the `StateError` contract for a missing single id is
preserved unchanged.

### `_buildInsertCompanion` — seed `deletedAt` on insert

Shared by `createTicket`/`importTicket`. Add one field:

```dart
TicketsTableCompanion _buildInsertCompanion(
  Ticket ticket, {
  required String ticketId,
}) {
  return TicketsTableCompanion.insert(
    id: ticket.id,
    ticketId: ticketId,
    // ...every existing field, unchanged...
    deletedAt: Value(ticket.deletedAt?.millisecondsSinceEpoch),
  );
}
```

Inert for `createTicket` (no call site constructs a `Ticket` with
`deletedAt` set before creating it — this only ever writes `null`,
identical to today's implicit default). Necessary for `importTicket`,
which is exactly how `TicketDbReconstructionService.reconstruct()`
brings in a `.md` file with no existing DB row — including a trashed
one, per #3 below.

`updateTicket`'s companion is **deliberately left untouched** — it still
never includes `deletedAt`. Widening it would blur the one invariant
this whole fix protects: a live row's trash state changes only through
`trashTicket`/`restoreTicket` (which now correctly cascade *and*
project), never as a side effect of an unrelated content edit that
happens to carry a stale `deletedAt` value on its `Ticket` object.
Reconstruction's own need to flip an *existing* row's trash state is
handled explicitly in #3, through the same blessed methods — not by
loosening `updateTicket`.

## 3. `GitProjectingTicketRepository` — batch-project the returned cascade

`lib/features/tickets/data/repositories/git_projecting_ticket_repository.dart`

```dart
@override
Future<List<String>> trashTicket(String id) async {
  final affected = await _inner.trashTicket(id);
  await _projectAllOrSwallow(affected, 'trashed');
  return affected;
}

@override
Future<List<String>> restoreTicket(String id) async {
  final affected = await _inner.restoreTicket(id);
  await _projectAllOrSwallow(affected, 'restored');
  return affected;
}

/// Re-fetches every id in [ids] from [_inner] and projects the ones
/// still found (a null — the ticket vanished — is dropped, same
/// tolerance [_project] already has) as one batched commit via
/// [_projector.projectBatch] — a single commit for the whole cascade
/// [trashTicket]/[restoreTicket] just persisted, not one commit per id.
/// For the common case (no cascade — [ids] has exactly one member),
/// this produces the identical single-ticket commit [_project] always
/// did. Swallows the same two failure types [_projectOrSwallow] does,
/// for the same reason.
Future<void> _projectAllOrSwallow(List<String> ids, String eventLabel) async {
  try {
    final tickets = <Ticket>[];
    for (final id in ids) {
      final ticket = await _inner.getTicketById(id);
      if (ticket != null) tickets.add(ticket);
    }
    await _projector.projectBatch(tickets, _rootPath, eventLabel);
  } on ProcessException {
    // See _projectOrSwallow's own dartdoc.
  } on FileSystemException {
    // See _projectOrSwallow's own dartdoc.
  }
}
```

`_project`/`_projectOrSwallow` stay exactly as they are today (still
used by `createTicket`/`updateTicketStatus`/`updateStatusForIds`/
`updateTicketSddStage`/`updateTicketParent`, none of which cascade).
`_projectAllOrSwallow` is the new sibling used only by `trashTicket`/
`restoreTicket`, replacing their old `_projectOrSwallow(id, ...)` calls.

## 4. `TicketGitProjector` — generalize the batch commit-message wording

`lib/features/tickets/data/services/ticket_git_projector.dart`

`_projectBatch`'s multi-item label is hardcoded to the word "ancestors"
— correct for its original, only caller (`TicketRollupRecomputer`), no
longer accurate once `GitProjectingTicketRepository` and `TicketsCubit`
(below) also call it for a trash/restore cascade that can include
descendants, or (for restore) both ancestors and descendants at once:

```dart
final label = ancestors.length == 1
    ? '${ancestors.single.ticketId} $eventLabel'
    : '${ancestors.length} tickets $eventLabel';   // was "ancestors"
```

The parameter itself keeps its name (`List<Ticket> ancestors`) and the
method keeps its name (`projectBatch`) — renaming either is pure churn
for this fix's actual purpose. Only the two literal words in the
generated commit message change. Existing rollup-cascade commits change
from `"N ancestors rollup updated"` to `"N tickets rollup updated"` —
called out here since it's a small, deliberate wording change riding
along with this fix, not a silent one.

## 5. `TicketsCubit.trashTickets`/`_trashBatchGitSideEffects` — use the plural return value

`lib/features/tickets/presentation/cubit/tickets_cubit.dart`

```dart
Future<void> trashTickets(List<String> ids) async {
  // ...unchanged state capture...
  try {
    final parentIdOf = <String, String?>{
      for (final id in ids)
        id: (await _repository.getTicketById(id))?.parentId,
    };
    final affectedIds = await _repository.trashTickets(ids);
    unawaited(_trashBatchGitSideEffects(affectedIds, parentIdOf));
    // ...unchanged searchTickets/emit...
    emit(
      TicketsBatchTrashed(page.tickets, affectedIds.length, hasMore: page.hasMore),
    );
    // ...unchanged _refreshDetailIfOpenAndAffected(ids.toSet(), ...) —
    // still the explicitly-selected ids, not affectedIds: a live-open
    // detail screen for a *cascaded descendant* not itself selected was
    // never this call's concern (see its own dartdoc's existing
    // "documented scope simplification" note, which this fix does not
    // touch) and refreshing it isn't needed for correctness — only the
    // git-projection side of the cascade was ever the bug.
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}

/// Projects every id in [affectedIds] (the explicitly-trashed ids plus
/// every cascaded descendant `TicketRepository.trashTickets` already
/// returns) as one batched `'trashed'` commit, then runs the rollup
/// recompute seeded from [parentIdOf]'s values.
Future<void> _trashBatchGitSideEffects(
  List<String> affectedIds,
  Map<String, String?> parentIdOf,
) async {
  final projector = _gitProjector;
  final rootPath = _projectRootPath;
  if (projector != null && rootPath != null) {
    final tickets = <Ticket>[];
    for (final id in affectedIds) {
      final ticket = await _repository.getTicketById(id);
      if (ticket != null) tickets.add(ticket);
    }
    await projector.projectBatch(tickets, rootPath, 'trashed');
  }
  await _recomputeRollupChain({
    for (final id in parentIdOf.keys)
      if (parentIdOf[id] != null) parentIdOf[id]!,
  }, 'rollup updated');
}
```

`trashedCount` (renamed `affectedIds.length` inline above — same value
as today's `int` return, just derived from the richer return type) is
unaffected in what it displays: `DriftTicketRepository.trashTickets`
already counted the full cascade today, only its *enumeration* was
missing. `parentIdOf` is still built from the caller's original `ids`
(rollup recompute only ever needs to walk upward from what was
explicitly acted on — cascaded descendants' ancestors are already
covered by that same walk).

`_triggerGitProjection` stays — nothing else in this file calls it
after this change removes its one remaining call site
(`_trashBatchGitSideEffects`'s old loop). **Do not delete it in this
pass**: confirm via a full-text search at `/apply` time that nothing
else references it before removing the method and its now-stale
dartdoc cross-references (the several `[_triggerGitProjection]` doc
links at lines ~141, ~1190, ~7553 per `/explore`'s read of this file)
— same "audit before deleting" caution `fix-ticket-git-projection-gap`
`design.md` used for its own cleanup pass.

## 6. `TicketDbReconstructionService.reconstruct()` — trash-aware existence check + explicit reconciliation

`lib/features/tickets/data/services/ticket_db_reconstruction_service.dart`

```dart
Future<TicketReconstructionReport> reconstruct(String rootPath) async {
  final ticketsDir = Directory('$rootPath/tickets');
  if (!await ticketsDir.exists()) {
    return const TicketReconstructionReport(importedCount: 0, skippedPaths: []);
  }

  final existing = [
    ...await _repository.getAllTickets(),
    ...await _repository.getTrashedTickets(),
  ];
  final existingByTicketId = {for (final t in existing) t.ticketId: t};

  // ...unchanged loop shape...
  await for (final entity in ticketsDir.list()) {
    if (entity is! File || !entity.path.endsWith('.md')) continue;
    final result = _serializer.parse(await entity.readAsString());
    final ticket = _buildTicket(result, existingByTicketId);
    if (ticket == null) { skippedPaths.add(entity.path); continue; }

    final existingRow = existingByTicketId[ticket.ticketId];
    if (existingRow != null) {
      await _repository.updateTicket(ticket);
      await _reconcileTrashState(existingRow, ticket);
    } else {
      await _repository.importTicket(ticket);
    }
    existingByTicketId[ticket.ticketId] = ticket;
    imported.add(ticket);
    importedCount++;
  }
  // ...unchanged embedding backfill + report...
}

/// Brings [existing]'s trash state in line with [parsed]'s (the file's)
/// `deletedAt`, via the same blessed [TicketRepository.trashTicket]/
/// [TicketRepository.restoreTicket] methods every other write path
/// uses — never by writing `deletedAt` directly, and never through
/// [TicketRepository.updateTicket] (which deliberately excludes the
/// field, see [DriftTicketRepository]'s own design note). Mirrors
/// `TicketParentTrashService.applyFromParsedFields`'s identical
/// detection logic for the same file→DB direction, duplicated rather
/// than shared — the same "not worth a helper for two call sites"
/// judgment call that class's own dartdoc already makes for its
/// `parentId` handling. A no-op if `deletedAt` didn't change, or if it
/// changed to a different non-null value (re-trashing an
/// already-trashed ticket with a new timestamp has no domain operation
/// to reconcile through — same as `applyFromParsedFields`).
Future<void> _reconcileTrashState(Ticket existing, Ticket parsed) async {
  if (parsed.deletedAt != null && existing.deletedAt == null) {
    await _repository.trashTicket(existing.id);
  } else if (parsed.deletedAt == null && existing.deletedAt != null) {
    await _repository.restoreTicket(existing.id);
  }
}
```

`_buildTicket` itself needs no change — it already parses `deletedAt`
from frontmatter correctly (this was never the bug; only what happened
to that value afterward was).

This keeps `TicketDbReconstructionService`'s dependency surface exactly
as it is today (`TicketRepository`, `TicketMarkdownSerializer`,
`EmbeddingProvider`) — no new dependency on `TicketParentTrashService`
or `TicketRollupRecomputer`. A reconciliation triggered this way still
gets correct git projection for free whenever `_repository` happens to
be a `GitProjectingTicketRepository` (the in-app case); the bare-CLI
case (`bin/migrate_aion_arch.dart`, which constructs a plain
`DriftTicketRepository` with no decorator) gets the corrected DB state
with no projection attempted, matching that CLI's existing scope.

### Why not fix this at the `updateTicket` call site instead

An alternative would be widening `DriftTicketRepository.updateTicket`
to include `deletedAt` in its companion. Rejected: `updateTicket` is
also the generic path for `TicketMarkdownReconciler` (the live
file-watcher) and any future direct caller — none of which are trash-
aware today, and every one of which would then need to remember to
preserve `deletedAt` correctly on every call or risk *accidentally*
untrashing/retrashing a ticket as a side effect of an unrelated content
edit. Keeping `deletedAt` a fully separate, single-purpose lane
(`trashTicket`/`restoreTicket` only) is the same reasoning
`specs/tickets.md`'s existing "content edits don't commit" boundary
already rests on — trash state is not a content field.

## `/verify` follow-up

`/verify` found one CRITICAL against `_reconcileTrashState` (§6) and one
SUGGESTION for stronger end-to-end coverage. Both fixed on the same
branch.

### CRITICAL — `_reconcileTrashState` compared against a stale `existingByTicketId` snapshot

`reconstruct()` builds `existingByTicketId` **once**, before the
directory walk, and only patches the *currently-processed* ticket's own
entry after each iteration. But `_reconcileTrashState` calls
`trashTicket`/`restoreTicket`, which — by this same proposal's own
design — cascade to *other* tickets (ancestors/descendants) in the real
database. If ticket A's reconciliation cascades and changes ticket B's
trash state too, and B hasn't had its own turn in the loop yet, B's
entry in `existingByTicketId` is now stale: when B's turn comes,
`_reconcileTrashState` compares B's *parsed* file against that stale
snapshot instead of B's true, just-changed DB state — for the common
case (both files agree on the cascade's outcome), this fires a
redundant, wasted `trashTicket`/`restoreTicket` call (and, in-app, a
redundant git commit); for a genuinely conflicting hierarchy (two files
in the same ancestor chain disagreeing about trash state — possible
only via manual git tampering, since a normal in-app cascade always
commits every affected file together in one batch), it could silently
miss B's own reconciliation need entirely, since the stale comparison
sometimes shows no change at all.

**Fix**: `_reconcileTrashState` now takes `existingByTicketId` and, after
any `trashTicket`/`restoreTicket` call, re-fetches every id the call
reports as affected (`trashTicket`/`restoreTicket`'s own return value —
already built for exactly this kind of "what else did this touch"
question) via `getTicketById`, writing each one's fresh state back into
the shared map. This doesn't — can't — make two *genuinely* conflicting
files both win (cascading methods enforce one trash state across the
whole chain by design, so a real conflict still resolves to whichever
file is processed last), but it closes the *silent* failure mode: every
reconciliation now compares against accurate state, and a
cascade-consistent case never fires a redundant call. Documented
precisely in `_reconcileTrashState`'s own dartdoc, including the
residual "genuine conflict" limitation.

Added a regression test (`ticket_db_reconstruction_service_test.dart`)
using a `MockTicketRepository` that delegates every call to a real, in
-memory `DriftTicketRepository` — mocktail's call-count verification is
the only way to *observe* the redundant call, since a real repository
has no introspection of its own. Verified the test fails against the
pre-fix code (`trashTicket` called twice) before confirming it passes
against the fix (called once).

### SUGGESTION — add an end-to-end (real repository + real git) test for the cascade → one-commit chain

Every layer of the cascade-projection fix was covered in isolation
(`DriftTicketRepository` returns the right ids; `GitProjectingTicketRepository`
calls `projectBatch` with the right tickets; `TicketGitProjector`
produces the right commit for a batch) but nothing exercised the whole
chain together against a real git repository. Added a test wiring a
real `DriftTicketRepository` (in-memory), a real `TicketGitProjector`
(real `GitRepositoryClient`, real `git init`'d temp directory), and the
real `GitProjectingTicketRepository` decorator: trashes an epic + child,
restores only the child, and asserts (a) exactly one `"2 tickets
trashed"` commit and one `"2 tickets restored"` commit land, and (b)
the epic's own `.md` file content is actually rewritten to
`deletedAt: null` — the precise, literal proof that this proposal fixes
the AIO-2703/2704 incident end to end, not just at the unit level.
