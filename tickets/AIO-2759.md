# Design: Scope the exploring-stage system prompt to read-only investigation

## Overview

Purely a prompt-text addition inside one existing private method,
`TicketsCubit._assembleStageContext`
(`lib/features/tickets/presentation/cubit/tickets_cubit.dart`). No new
classes, no state changes, no BLoC states, no widgets. The method already
branches on `SddStage` to append stage-specific instructional text after
the shared title/description/related-tickets preamble; this change adds
one more branch for `SddStage.exploring`, following the exact shape of the
existing `designBrief`/`designSync`/`proposed` branches.

## Current shape (for reference)

```dart
if (stage == SddStage.verifying || stage == SddStage.archived) {
  // ...children summary + verify-gate instructions...
} else if (stage == SddStage.designBrief) {
  // ...design-brief instructions...
} else if (stage == SddStage.designSync) {
  // ...design-sync instructions...
} else if (stage == SddStage.proposed) {
  // ...decomposition instructions...
}
// SddStage.exploring falls through here with NO branch — the gap.
```

## Change

Add a new branch, placed first (mirroring `SddStage`'s own declared enum
order — `exploring → proposed → designBrief → designSync → verifying`) so
the method's branch order reads top-to-bottom in the same order a ticket
actually moves through the cycle:

```dart
if (stage == SddStage.exploring) {
  buffer
    ..writeln()
    ..writeln(
      'Investigate this ${parent.type.name}\'s problem space using the '
      'title, description, and related tickets above. This stage is '
      'read-only investigation and analysis only — do not edit, create, '
      'or delete any project files, do not draft a file-by-file '
      'implementation plan, do not write code, and do not ask for write '
      'access to any repository. Ground every claim in what the context '
      'above actually shows rather than speculating. End your reply with '
      'a written exploration summary: the problem as you understand it, '
      'what you found, and the tradeoffs of any options — a decision aid '
      'for a human to read before a later stage decomposes this into '
      'real work, not a proposal or an implementation.',
    );
} else if (stage == SddStage.verifying || stage == SddStage.archived) {
  // ...unchanged...
} else if (stage == SddStage.designBrief) {
  // ...unchanged...
} else if (stage == SddStage.designSync) {
  // ...unchanged...
} else if (stage == SddStage.proposed) {
  // ...unchanged...
}
```

Exact wording is intentionally close to `aion-arch/.claude/skills/explore
/SKILL.md`'s own rule ("Do not edit, create, or delete any project files.
This stage is purely for brainstorming and analysis.") plus one addition
specific to the observed incident: an explicit "do not ask for write
access" line, since that's exactly what happened in the 2026-09-08 proof
run and a generic read-only rule alone didn't anticipate a model
*asking* rather than *doing*.

## Method dartdoc update

`_assembleStageContext`'s own dartdoc (lines ~7038-7053) currently
enumerates what each branch adds ("for `SddStage.verifying` specifically,
instructions to end the reply with `VERIFY GATE: ...`" etc.) but never
mentions `exploring` at all. Add a clause describing the new branch,
in the same enumerated style, so the dartdoc stays a complete map of what
the method does.

## Why no tool-access change

See proposal.md's "Non-goals / investigated and deferred" section for the
full investigation. Summary: `ToolAccessTier.readOnly` isn't implemented
at the provider/bridge level today (`ClaudeAgentSdkProvider
.supportedToolAccessTiers` only supports `{noTools, full}`), and the
default `exploring`-stage chat (no `SkillAttachment` configured) already
runs with `toolsEnabled: false` — equivalent to `noTools` — via
`_runStageChatTurn`. There is no live filesystem/bash capability to strip
from the path that actually produced the observed drift; only app-defined
ticket tools (`create_ticket`/`branch_ticket`/`add_link`) are available
regardless of `toolsEnabled`, and none of those let a model write source
files. No `ToolAccessTier`/`AutomationContext` wiring changes are part of
this change.

## Testing

Unit-test the new branch the same way `sdd_stage_model_phase_test.dart`
and the existing `designBrief`/`proposed` coverage in
`tickets_cubit_test.dart` test their own branches: drive
`TicketsCubit.advanceSddStage` on an epic/story transitioning into
`exploring` (the `null → exploring` precondition-met path already has
existing test setup to extend, ~line 5887 of
`test/features/tickets/cubit/tickets_cubit_test.dart`), capture the
posted `TicketComment` via `commentRepository.addComment(captureAny())`,
and assert its `content` contains the new instructional text (e.g. a
substring check for "read-only investigation" and "do not ask for write
access"). No widget tests — no UI surface changed.

## Risks

None beyond ordinary prompt-tuning risk (a model might still occasionally
drift despite the instruction — same residual risk every other stage's
prompt-only instruction already carries, e.g. `verifying`'s "VERIFY GATE"
suffix isn't enforced structurally either, just requested). Consistent
with this codebase's existing posture: `_parseDecomposition`/
`_parseVerifyFixes` are both documented as "fail-open," not hard gates.
