# `features/tickets/presentation/cubit/` — the second call site (found by `/verify`)

`SkillAttachment` fires on entry to *either* a `WorkflowStatus`
(`_fireSkillAttachment`, patched by T4) *or* an `SddStage`
(`_runStageChatTurn`) — exactly one, never both, per
`SkillAttachment`'s own dartdoc. `/verify` found `_runStageChatTurn`
independently resolves `ModelPhase.execution` and calls
`ChatCubit.runChatTurn` for a `delegatedSkill` attachment fired on an
`SddStage`, with no `supportsSkillDiscovery` check — the exact same gap
T4 closed for the `WorkflowStatus` surface, left open on this one.
Confirmed by a pre-existing test (`'SddStage entry' > 'a configured
attachment uses its own prompt...'`) that passes regardless of the
shared fixture's `supportsSkillDiscovery` stub value, since nothing in
`_runStageChatTurn` ever reads it. Per design.md §3a.

- [x] T9. `lib/features/tickets/presentation/cubit/tickets_cubit.dart`
  — MODIFY: in `_runStageChatTurn`, immediately after resolving
  `final (model, provider) = await _resolveModelAndProvider(...)`
  (the branch keyed on `attachmentToolsEnabled`) and before the
  `await ChatCubit.runChatTurn(...)` call, add:
  ```dart
  if (attachmentToolsEnabled && !provider.supportsSkillDiscovery) {
    throw StateError(
      '${provider.displayName} cannot run delegated skills — it has no '
      '.claude/skills/ discovery capability.',
    );
  }
  ```

  resolution. The throw is caught by the method's existing surrounding
  `catch (e)`, which already posts `'Stage advance failed: $e'`; no new
  catch/comment logic. Update `_runStageChatTurn`'s dartdoc to document
  this new failure mode alongside its existing
  "missing git client/project root" one. Per design.md §3a. Depends on
  T1.
