# Intl String Retrofit

# Proposal: intl String Retrofit

## Summary

Introduce `intl`/ARB-based localization infrastructure and retrofit every
existing hardcoded, user-facing string in the `aion` app to source its text
from generated `AppLocalizations`. English is the only shipped locale;
the point of this change is eliminating loose string literals, not adding
a second language today.

## Motivation

From [aion-arch/ideas/use-internationalization-for-the-strings.md](../../ideas/use-internationalization-for-the-strings.md):
the driver is code hygiene, not an active multi-language requirement. The
app is still small (one feature area, ~55–60 distinct strings), so a full
one-pass retrofit is cheaper now than an incremental migration would be
later. Enforcement going forward is a documented convention in
`flutter-conventions.md`, not a lint rule or CI gate — the idea session
explicitly ruled out tooling-based enforcement as overkill at this size.

## Current state (as investigated)

- No `intl`/l10n setup exists: no `l10n.yaml`, no `.arb` files, no
  `AppLocalizations` usage anywhere in `lib/`.
- `intl` (0.20.2) is present only *transitively*, pulled in by
  `flutter_localizations`. Not a direct dependency, not imported by app
  code.
- The app has **no `MaterialApp`** (hard non-Material design constraint).
  The root widget (`lib/main.dart`, `AionApp`) uses `WidgetsApp.router`,
  with `GlobalMaterialLocalizations.delegate` /
  `GlobalWidgetsLocalizations.delegate` wired in solely to satisfy
  `TextField`'s internal `MaterialLocalizations` dependency — not for app
  string translation. Standard `flutter gen-l10n` quickstart docs assume
  `MaterialApp`; this change wires the generated delegate into
  `WidgetsApp.router` instead.
- ~55–60 distinct user-facing string literals across ~90+ call sites,
  concentrated in `lib/features/tickets/presentation/` (4 screens + 1
  widget + the cubit layer) and `lib/core/widgets/` (shared primitives:
  `AppHeader`, `AppSpinner`, `AppDropdown`, `AppTextField`).
- Two duplicated strings exist today ("New ticket" / "Create ticket"
  appearing as separate literal instances in `tickets_list_screen.dart`
  and `create_ticket_screen.dart`) — this retrofit consolidates them
  behind shared ARB keys.
- Ticket priority and type are currently rendered via raw
  `enum.name.toUpperCase()` (bypassing any label mapping entirely), unlike
  ticket status, which already has a `ticketStatusLabel()` mapping
  function. This is a pre-existing labeling gap that blocks a clean ARB
  retrofit for those two fields, so this change extends the existing
  label-mapping pattern to cover them too.
- Two `Cubit`-layer hardcoded strings exist (e.g.
  `TicketsError('Ticket not found')`) and two exception-message string
  literals in `core/utils/duration_format.dart` and
  `ticket_detail_screen.dart`. None of these have `BuildContext` available
  at the point the string is currently constructed — see
  [design.md](design.md) for the resolution pattern.

## Scope

**In scope:**

- Add `intl` as a direct dependency; set up `l10n.yaml` + a single base
  `lib/l10n/app_en.arb`; enable `generate: true`.
- Wire generated `AppLocalizations` into `WidgetsApp.router` in
  `main.dart`.
- Add a `BuildContext` extension (`context.l10n`) for terse call sites.
- Retrofit every user-facing string literal identified in the
  `features/tickets/presentation/` tree and `core/widgets/` shared
  primitives to source text from `AppLocalizations`.
- Extend the existing enum→label mapping pattern
  (`ticketStatusLabel()`) to cover `TicketPriority` and `TicketType`,
  replacing raw `.name.toUpperCase()` rendering.
- Introduce an error-code pattern for the two `Cubit`-layer and two
  exception-layer strings that have no `BuildContext` at their current
  construction site, localizing them at the widget layer instead.
- Document the "no new hardcoded UI strings" convention in
  `flutter-conventions.md`.

**Explicitly out of scope (deferred, not silently dropped):**

- Raw exception `.toString()` forwarding into `TicketsError`/
  `CommentsError` states (e.g. `catch (e) { emit(TicketsError(e.toString()))
  }` in `tickets_cubit.dart`/`comments_cubit.dart`). These aren't string
  *literals* — they're dynamic driver/DB exception text — so ARB
  extraction doesn't directly apply. Replacing them with a generic
  localized fallback message is a legitimate follow-up but is an
  error-handling UX change, not a pure string-literal retrofit; capture
  it as a new idea if wanted rather than folding it into this change's
  scope.
- Avatar-initial glyphs (`'U'`, `'+'`) and the single-character required-
  field asterisk are borderline. The asterisk is included (see
  `design.md`) for consistency; the avatar initials are excluded — they
  render a data-derived initial, not app copy, and localizing "U" has no
  well-defined meaning without a concept of per-locale name-initial
  rules the app doesn't have.
- A runtime language switcher / locale-selection UI. Only English ships;
  `supportedLocales` is exactly `[Locale('en')]`. Adding a second locale
  is a future, additive change (new ARB file + one `supportedLocales`
  entry), not part of this slice.
- `theme_scope.dart`'s debug-only `assert()` message — never rendered to
  end users.

## Risks

- **Non-standard localization wiring.** Because there's no `MaterialApp`,
  the generated `AppLocalizations.localizationsDelegates` /
  `.supportedLocales` static helpers must be manually spread into
  `WidgetsApp.router` rather than following the standard tutorial. Needs
  a manual interactive check (not just `flutter analyze`), consistent
  with this project's existing testing note that overlay/localization-
  adjacent wiring issues don't always surface in automated tests.
- **Cubit-layer strings have no `BuildContext`.** Addressed via an
  explicit error-code pattern (see `design.md`) rather than passing
  `BuildContext` into Cubits, which would violate the project's
  presentation/domain separation. This is a real design decision, not a
  mechanical find-and-replace, so `tasks.md` calls it out as its own
  task rather than bundling it into a screen-level retrofit task.
- **Scope creep risk is low** given the codebase's current size (one
  feature area, 50 Dart files), but the retrofit still touches every
  presentation-layer file that renders text — `tasks.md` is deliberately
  file-scoped, one file (or tightly related pair) per task, to keep each
  task reviewable.

## Design gate

status: NOT REQUIRED
reason: this change swaps existing string literals for
  `AppLocalizations` lookups with zero new widgets, zero layout changes,
  and zero visual changes — every screen renders identically to before,
  just sourcing text from a different place. No Claude Design session is
  needed.
