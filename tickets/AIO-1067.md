## Domain Layer

### `Ticket.copyWith` (new method on existing entity)

```dart
/// Returns a copy of this ticket with [status] and/or [updatedAt]
/// replaced. Scoped to the fields this change mutates — extend with more
/// parameters only when a future change needs them.
Ticket copyWith({TicketStatus? status, DateTime? updatedAt}) {
  return Ticket(
    id: id,
    ticketId: ticketId,
    type: type,
    title: title,
    description: description,
    status: status ?? this.status,
    priority: priority,
    parentId: parentId,
    embedding: embedding,
    estimate: estimate,
    timeSpent: timeSpent,
    createdAt: createdAt,
    updatedAt: updatedAt ?? this.updatedAt,
  );
}
```

Deliberately not a full-field `copyWith` — only `status`/`updatedAt` are
needed by `TicketsCubit.updateTicketStatus`'s optimistic-update step below.

### `TicketRepository` (interface, modified)

```dart
abstract interface class TicketRepository {
  Future<List<Ticket>> getAllTickets();
  Future<Ticket?> getTicketById(String id);
  Future<void> createTicket(Ticket ticket);

  /// Updates only the status (and updatedAt) of the ticket with id [id].
  /// Does not touch any other field. Throws if [id] does not exist.
  Future<void> updateTicketStatus(String id, TicketStatus status);
}
```

## Data Layer

### `TicketDao` (modified)

```dart
/// Updates the status column (and updatedAt) for the ticket with id [id].
Future<void> updateStatus(String id, TicketsTableCompanion companion) {
  return (update(ticketsTable)..where((t) => t.id.equals(id))).write(companion);
}
```

Takes a `TicketsTableCompanion` (consistent with `insertTicket`'s existing
signature) rather than raw `String`/`int` params — the repository builds
the companion, the DAO just writes it.

### `DriftTicketRepository` (modified)

```dart
@override
Future<void> updateTicketStatus(String id, TicketStatus status) {
  return _db.ticketDao.updateStatus(
    id,
    TicketsTableCompanion(
      status: Value(status.name),
      updatedAt: Value(DateTime.now().millisecondsSinceEpoch),
    ),
  );
}
```

No enum-fallback parsing needed here (unlike reads) — `status.name` is
always a valid `TicketStatus` value at the call site.

No table/schema changes: `status` and `updated_at` columns already exist
on `TicketsTable` (schema version stays 1).

## Presentation Layer

### `TicketsState` (modified) — 2 new states

```dart
/// A status-change drag/move is in flight. Carries the list with the
/// affected ticket's status already updated locally (optimistic), so the
/// board reflects the move instantly instead of waiting on the DB round
/// trip.
class TicketStatusUpdating extends TicketsState {
  const TicketStatusUpdating(this.tickets);
  final List<Ticket> tickets;
  @override
  List<Object?> get props => [tickets];
}

/// The status change persisted successfully. Carries the list re-fetched
/// from the repository (source of truth, supersedes the optimistic copy).
class TicketStatusUpdated extends TicketsState {
  const TicketStatusUpdated(this.tickets);
  final List<Ticket> tickets;
  @override
  List<Object?> get props => [tickets];
}
```

On failure, `TicketsCubit.updateTicketStatus` emits the existing
`TicketsError` — same as every other mutation. `TicketsError` carries no
list, so a failed move surfaces as the existing full-screen error state
(with the existing Retry button, which calls `loadTickets()`). This is a
deliberate scope call: no per-card rollback/toast is built in this change,
consistent with the existing error-handling shape everywhere else in this
cubit.

### `TicketsCubit` (modified) — 1 new method

```dart
/// Moves ticket [id] to [status]. Emits [TicketStatusUpdating] (carrying
/// the list with [id]'s status optimistically replaced) immediately, then
/// [TicketStatusUpdated] (carrying the re-fetched list) once the
/// repository call succeeds, or [TicketsError] if it throws.
Future<void> updateTicketStatus(String id, TicketStatus status) async {
  final currentTickets = switch (state) {
    TicketsLoaded(:final tickets) => tickets,
    TicketCreated(:final tickets) => tickets,
    TicketStatusUpdating(:final tickets) => tickets,
    TicketStatusUpdated(:final tickets) => tickets,
    _ => <Ticket>[],
  };

  final optimistic = [
    for (final t in currentTickets)
      if (t.id == id) t.copyWith(status: status) else t,
  ];
  emit(TicketStatusUpdating(optimistic));

  try {
    await _repository.updateTicketStatus(id, status);
    final tickets = await _repository.getAllTickets();
    emit(TicketStatusUpdated(tickets));
  } catch (e) {
    emit(TicketsError(e.toString()));
  }
}
```

`TicketsListScreen`'s `BlocBuilder` switch must add `TicketStatusUpdating`
and `TicketStatusUpdated` alongside the existing `TicketCreating`/
`TicketCreated` branch (same `ListView.separated` rendering for List mode;
`TicketBoardView` handles them directly for Board mode).

### `TicketsListScreen` (modified)

Adds a private, non-persisted view-mode toggle:

```dart
enum _TicketViewMode { list, board }
```

Local `State` field `_TicketViewMode _viewMode = _TicketViewMode.list`.
The header's existing `Row` (currently: eyebrow/title on the left, avatar
circle on the right) gains a small two-icon segmented toggle immediately
left of the avatar:

- List icon (`PhosphorIcons.listLight` or nearest equivalent in
  `phosphoricons_flutter` — confirm exact identifier during implementation)
  and board icon (`PhosphorIcons.hexagonLight`, matching the "board →
  hexagon" glyph already assigned in the design-system icon table).
- Active mode: icon color `c.primary`, background `c.primarySubtle`. Inactive:
  icon color `c.textMuted`, transparent background. `AionRadius.sm`
  container per icon, `Semantics(button: true, label: 'Switch to list
  view'/'Switch to board view')`.

Body: the existing `BlocBuilder<TicketsCubit, TicketsState>` switch stays
the single source of truth. When `_viewMode == board`, the same resolved
`tickets` list (from whichever state carries one) is filtered to
`{TicketType.task, TicketType.story}` and passed to
`TicketBoardView(tickets: filtered)` instead of `ListView.separated`. Both
branches read from the same cubit state — no separate load call, no second
`BlocProvider`.

### `tickets_board_view.dart` (new file)

#### `TicketBoardView`

```dart
class TicketBoardView extends StatelessWidget {
  const TicketBoardView({super.key, required this.tickets});
  final List<Ticket> tickets; // already type-filtered by the caller
```

- Groups `tickets` by `status` into a `Map<TicketStatus, List<Ticket>>`.
- `SingleChildScrollView(scrollDirection: Axis.horizontal)` → `Row` of
  `BoardColumn`, one per `TicketStatus.values` entry in declared order —
  every column renders even if its group is empty.
- Each `BoardColumn` gets a fixed width (e.g. `280`) via `SizedBox`, with
  `AionSpacing.sp12` gaps between columns and `AionSpacing.sp20` outer
  padding, matching the list screen's existing horizontal padding.

#### `BoardColumn`

```dart
class BoardColumn extends StatelessWidget {
  const BoardColumn({super.key, required this.status, required this.tickets});
  final TicketStatus status;
  final List<Ticket> tickets;
```

- Header: status label (reusing the label logic extracted from
  `StatusIndicator`, see below) + a count badge
  (`DecoratedBox` fill `c.surfaceHover`, `Text('${tickets.length}')`).
- Body: `DragTarget<Ticket>` wrapping a vertical `ListView.separated` (or
  `Column` inside a `SingleChildScrollView` — `ListView` is fine, the outer
  scroll is horizontal so no gesture conflict) of `TicketBoardCard`.
  - `onWillAcceptWithDetails`: always `true` (accepting a drop onto the
    same column it came from is a harmless no-op, simpler than special-casing it).
  - `onAcceptWithDetails`: `if (details.data.status != status)
    context.read<TicketsCubit>().updateTicketStatus(details.data.id, status);`

    column background `c.primarySubtle`.

**Refactor note:** `StatusIndicator`'s private `_statusLabel` method in
`tickets_list_screen.dart` is extracted to a top-level function (e.g.
`ticketStatusLabel(TicketStatus)`) in the same file, so both
`StatusIndicator` and `BoardColumn`'s header can call it — avoids
duplicating the 6-case switch.

#### `TicketBoardCard`

```dart
class TicketBoardCard extends StatelessWidget {
  const TicketBoardCard({super.key, required this.ticket});
  final Ticket ticket;
```

- Card visual: `DecoratedBox` (fill `c.surface`, `BorderRadius.all(AionRadius.lg)`,
  border 1px `c.border`, shadow `AionShadows.card(c, t.isDark)` — floating
  card, unlike the full-width bordered list row) containing:
  - Top row: ticket-id badge (same styling as `TicketListTile`'s) +
    `Expanded(Text(title, maxLines: 2))` + `PriorityBadge` (omitted when
    `none`, same as list).
  - Meta row: `TypeChip`.
  - Trailing-corner `MoveToStatusMenu` icon button (`PhosphorIcons.dotsThreeLight`
    or similar "more" glyph — opens the status-picker overlay).
- The whole card is wrapped in `GestureDetector(onTap: () =>
  context.go('/tickets/${ticket.id}'))` (same navigation as `TicketListTile`)
  and `Semantics(label: '${ticket.ticketId} ${ticket.title}, status:
  ${ticketStatusLabel(ticket.status)}', button: true)`.
- Drag wrapping, platform-branched via `platform_utils.dart`:
  ```dart
  isMobile
    ? LongPressDraggable<Ticket>(data: ticket, feedback: _feedback(context), childWhenDragging: _placeholder(context), child: cardContent)
    : Draggable<Ticket>(data: ticket, feedback: _feedback(context), childWhenDragging: _placeholder(context), child: cardContent)
  ```
  `_feedback`: the same card content at fixed width, wrapped in
  `Opacity(opacity: 0.9)` + a stronger shadow (`AionShadows.fab`) to read as
  "lifted". `_placeholder`: the original card slot at `Opacity(opacity: 0.35)`.
- **Manual-testing note:** nesting `GestureDetector.onTap` inside
  `Draggable`/`LongPressDraggable` relies on Flutter's gesture arena to
  disambiguate tap vs. drag — this needs the same kind of interactive
  `flutter run` verification the project's `AppDropdown` overlay bug
  needed (`flutter analyze`/`flutter test` won't catch a gesture-arena
  regression). Call out explicitly in `tasks.md`.

#### `MoveToStatusMenu`

```dart
class MoveToStatusMenu extends StatefulWidget {
  const MoveToStatusMenu({super.key, required this.ticket});
  final Ticket ticket;
```

- Small icon-button trigger (`PhosphorIcons.dotsThreeLight`, 16px,
  `c.textMuted`), `Semantics(button: true, label: 'Move ${ticket.ticketId}
  to another status')`.
- On tap, opens an `OverlayEntry` via `Overlay.of(context)` — same
  `CompositedTransformFollower`/`LayerLink`/outside-tap-dismiss mechanics
  as `AppDropdown`, but the trigger is an icon button, not a full field,
  and the list is `TicketStatus.values.where((s) => s != widget.ticket.status)`
  instead of a generic `items` list. This is intentionally a bespoke
  small widget (not a reuse of generic `AppDropdown<T>` itself), since
  `AppDropdown` always renders its current value in the trigger and
  expects `value`/`itemLabel` symmetry that doesn't fit an icon-button
  trigger — but it copies `AppDropdown`'s overlay implementation pattern
  exactly (see `core/widgets/app_dropdown.dart`), including the `mounted`
  guard on `setState` after overlay dismissal (the class of bug the
  project's `AppDropdown` crash notes already flag).
- Selecting an item calls
  `context.read<TicketsCubit>().updateTicketStatus(widget.ticket.id, selected)`
  and closes the overlay — the exact same cubit call the drag path makes,
  so drag and the accessible fallback are provably equivalent, not two
  parallel code paths that can drift.

## Accessibility

- Drag-and-drop is the fast path; `MoveToStatusMenu` is the required
  keyboard/screen-reader path — both call the identical
  `TicketsCubit.updateTicketStatus`, so there is no behavioral drift
  between them.
- `TicketBoardCard` keeps the same focus/activate pattern as
  `TicketListTile` (`FocusableActionDetector` + `ActivateIntent` →
  navigate to detail); `MoveToStatusMenu`'s icon button is a separate
  focusable stop in Tab order, immediately after its card, so Enter/Space
  on the card still means "open ticket" and never accidentally triggers a
  status change.
- View-mode toggle icons carry `Semantics(button: true, label: ...)` per
  the existing interactive-primitive convention.
- Column headers are plain text, not interactive — no additional
  semantics needed beyond the default text semantics.
