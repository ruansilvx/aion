# Presentation layer — cubits

- [x] **T11.** Modify `lib/features/tickets/presentation/cubit/tickets_cubit.dart`:
  - Import `ticket_rollup_calculator.dart`.
  - Add private `_recomputeRollupChain(Set<String> startIds, String
    eventLabel)` per design.md §2.1: fetches `getAllTickets()`, builds
    `RollupNode`s, calls `computeRollups`, walks each `startIds` member
    upward via `parentId` (deduplicated into one `chainIds` set),
    diffs each ancestor's newly-computed rollup against its current
    persisted value (skip the write/projection if unchanged), calls
    `_repository.updateRollup` for every changed ancestor, then a
    single `_gitProjector?.projectBatch(...)` call for the whole
    changed set (no-op if `_gitProjector`/`_projectRootPath` is
    `null`, matching `_triggerGitProjection`'s existing optional-
    dependency pattern). Full dartdoc per design.md §2.1, including the
    "why walk from `startIds` inclusive" note.
  - In `updateTicket`: after the existing embedding-regen check, add a
    second check — if `previous.estimate != refreshed.estimate ||
    previous.timeSpent != refreshed.timeSpent`, fire `unawaited(
    _recomputeRollupChain({refreshed.id}, 'rollup updated'))`.
  - In `updateTicketParent`: capture `ticket.parentId` before the
    write as `oldParentId`; after a successful reparent, fire
    `unawaited(_recomputeRollupChain({ticket.id, if (oldParentId !=
    null) oldParentId}, 'rollup updated'))` per design.md §2.2's exact
    reasoning for why this pair of starting ids is correct against the
    post-write tree.
  - In `trashTicket`: after the existing `_triggerGitProjection` call
    for the trashed ticket, capture its pre-trash `parentId` (fetch the
    ticket *before* calling `_repository.trashTicket`, since the
    trashed row's `parentId` is unchanged by trashing but its
    `deletedAt` will exclude it from `getAllTickets()` — either
    ordering works for reading `parentId` itself, but fetch before the
    write for clarity) and fire `unawaited(_recomputeRollupChain({if
    (parentId != null) parentId}, 'rollup updated'))`.
  - In `trashTickets`: same pattern, unioning every explicitly-passed
    id's pre-trash `parentId` into one `_recomputeRollupChain` call
    (one call, not one per id) — mirrors the existing per-id git-
    projection loop's "explicitly-requested ids only" scope note.
  - Update each modified method's existing dartdoc to mention the new
    rollup-recompute side effect, matching how the embedding-regen
    trigger is already documented on `updateTicket`.
  - **Added post-design-sync (design.md §0.3, amended 2026-08-11):** add
    a public `Future<TicketRollupCounts> getRollupCounts(Ticket ticket)`
    method — query-only (no writes, no state emission), fetches
    `getAllTickets()`, calls `computeRollups` (T1), and returns the
    `estimateCount`/`timeSpentCount` for `ticket.id` (`0`/`0` if absent
    from the result map, i.e. `ticket` has no live children). Backs
    `TicketDetailScreen`'s on-demand count caption (T13) — deliberately
    not part of `_recomputeRollupChain`'s persisted write path, since
    counts are never written to drift (see T1). Full dartdoc explaining
    why this is on-demand rather than persisted (cheap for a single
    detail-screen ticket; would be wasteful per list/board row, which is
    why `RollupBadge` doesn't use it at all — see design.md §0.3).
