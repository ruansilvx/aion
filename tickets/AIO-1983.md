# Design: SddStage Transition Preconditions

## 1. Domain layer (`lib/features/tickets/domain/`)

Lives alongside `WorkflowStatus`/`SddStageConfigRepository`, not under
`core/automation/` — this mechanism has nothing to do with
`AutomationConfidence`/`AutomationContext`; it's an unconditional
structural gate, evaluated regardless of any confidence setting.

- **`enums/transition_outcome.dart`** — `enum TransitionOutcome {
  allowed, blocked }`.
- **`entities/transition_branch.dart`** — `TransitionBranch` (sealed):
  `TransitionBranch.toNode(String nodeId)` or
  `TransitionBranch.terminal(TransitionOutcome outcome)`. Structurally
  identical in shape to `DecisionBranch` but a separate type — see
  proposal.md's "Why parallel types, not shared ones."
- **`entities/transition_node.dart`** — `TransitionNode`: `id` (UUID
  v4), `fieldId` (references `TransitionFieldSpec.id`),
  `matchedBranch`/`unmatchedBranch` (`TransitionBranch`). No
  `conditionParams`, no operator, no value — every field this proposal
  ships is a plain boolean, so a node is just "which field; where its
  `true` branch goes; where its `false` branch goes." (Simpler than
  `DecisionNode` deliberately — that type carries `conditionId`+
  `conditionParams`+an operator/value shape because it has to
  distinguish fixed-catalog/rule-builder/`agentJudgment` conditions.
  Nothing here needs that distinction.)
- **`entities/transition_field_spec.dart`** — `TransitionFieldSpec`
  (`id`, `displayName`, `stages` — which `SddStage` values this field
  is valid for) and `transitionFieldsFor(SddStage)`. The catalog ships
  exactly 7 entries:
  - `mostRecentChatHasTerminalReply` (stages: `exploring`, `verifying`)
    — wraps the existing `_mostRecentChatHasTerminalReply` helper.
  - `hasChildren`, `storyNeedsDesignReview`, `allChildrenComplete`
    (stages: `proposed`) — the three terms of today's
    `children.isNotEmpty && (needsDesign || children.every(...))`.
    `storyNeedsDesignReview` wraps the existing `_storyNeedsDesignReview`
    helper; the other two are extracted from `_sddStageAdvanceCheck`'s
    inline logic into their own small helpers.
  - `linkedDesignPageHasContent` (stages: `designBrief`) — folds "page
    exists" and "description non-empty" into one field, since both
    failure modes produce the same outcome today.
  - `allTasksComplete`, `designSyncApproved` (stages: `designSync`) —
    `designSyncApproved` wraps the existing `_designSyncApproved`
    helper.
- **`repositories/transition_precondition_repository.dart`** —
  `abstract interface class TransitionPreconditionRepository`:
  `getGraph(SddStage)` (a graph entity: `stage`, `rootNodeId`;
  defaults to `rootNodeId: null` if unseeded), `getNode(String id)`,
  `getAllNodes(SddStage)`, `upsertNode(TransitionNode)`,
  `deleteNode(String id)`, `setRoot(SddStage, String? nodeId)`,
  `seedDefaultsIfEmpty()` (idempotent — seeds all 5 precondition-bearing
  stages' graphs, each reproducing today's exact check as a small tree
  — see §5), `onChanged` (`Stream<void>`).
- **`utils/evaluate_transition_graph.dart`** — pure, no I/O:
  `TransitionEvalContext` (7 nullable `bool?` fields, one per catalog
  entry, populated by the call site — mirrors `DecisionEvalContext`'s
  own "bundled by the caller, not fetched here" convention) and
  `({TransitionOutcome outcome, String? blockingFieldDisplayName})
  evaluateTransitionGraph(TransitionGraph graph, Map<String,
  TransitionNode> nodesById, TransitionEvalContext input)`. Walks from
  `graph.rootNodeId` (returns `(allowed, null)` immediately if `null` —
  same "never silently block automation" defensive posture
  `evaluateDecisionGraph` already uses, appropriate here too: an
  unconfigured stage should never gate). A missing field value (e.g. a
  stale node referencing a removed field) resolves that node's branch
  as unmatched — defensive, never throws. On `blocked`, returns the
  failing node's field's `displayName` alongside the outcome, so the
  call site can build `"Waiting on: $blockingFieldDisplayName"` without
  a second lookup.

## 2. Data layer (`lib/features/tickets/data/`)

Mirrors `WorkflowSkillAttachmentsTable`'s no-FK, flat-column
conventions exactly.

- **`models/transition_precondition_graphs_table.dart`** —
  `@DataClassName('TransitionPreconditionGraphData') class
  TransitionPreconditionGraphsTable extends Table`: `sddStage`
  (`TextColumn`, `SddStage.name`, unique), `rootNodeId` (`TextColumn`,
  nullable).
- **`models/transition_precondition_nodes_table.dart`** —
  `@DataClassName('TransitionPreconditionNodeData') class
  TransitionPreconditionNodesTable extends Table`: `id` (`TextColumn`,
  primary key), `fieldId` (`TextColumn`),
  `matchedBranchKind`/`unmatchedBranchKind` (`TextColumn` —
  `'node'`/`'allowed'`/`'blocked'`),
  `matchedBranchNodeId`/`unmatchedBranchNodeId` (`TextColumn`,
  nullable).
- **`daos/transition_precondition_dao.dart`** — CRUD plus
  `seedDefaultsIfEmpty`, mirroring `AutomationDecisionDao`.
- **`repositories/drift_transition_precondition_repository.dart`** —
  implements the domain interface via the DAO.
- **`AppDatabase`** — schema version 18 → 19 (additive: two new empty
  tables), registers both, wires
  `TransitionPreconditionRepository.seedDefaultsIfEmpty()` into the
  schema-19 upgrade path and fresh-install seeding.

## 3. Seeded baseline graphs (reproducing today's exact behavior)

Each tree below is the seed data for its stage — a project that never
edits it gets byte-for-byte identical behavior to today's hardcoded
`_sddStageAdvanceCheck` branch:

- **`exploring`/`verifying`** — one node: `mostRecentChatHasTerminalReply`
  → matched: `allowed`; unmatched: `blocked`.
- **`proposed`** — three nodes: `hasChildren` → unmatched: `blocked`;
  matched → `storyNeedsDesignReview` → matched: `allowed`; unmatched →
  `allChildrenComplete` → matched: `allowed`; unmatched: `blocked`.
  Reproduces `children.isNotEmpty && (needsDesign ||
  children.every(...))` exactly.
- **`designBrief`** — one node: `linkedDesignPageHasContent` → matched:
  `allowed`; unmatched: `blocked`.
- **`designSync`** — two nodes: `allTasksComplete` → unmatched:
  `blocked`; matched → `designSyncApproved` → matched: `allowed`;
  unmatched: `blocked`. Reproduces the existing `approved && tasks...`
  AND exactly.

## 4. `TicketsCubit` integration

`_sddStageAdvanceCheck`'s 5 real-precondition branches (`exploring`,
`verifying`, `proposed`, `designBrief`, `designSync`) are **replaced**,
not layered — consistent with this project's baseline-preset precedent
(`WorkflowStatus`, `SkillAttachment`, `automation-decision-graphs` all
made this same choice). Each branch now:

1. Computes a `TransitionEvalContext` from the same existing helpers
   (`_mostRecentChatHasTerminalReply`, `_storyNeedsDesignReview`,
   `_designSyncApproved`, plus three new small helpers extracted for
   `hasChildren`/`allChildrenComplete`/`linkedDesignPageHasContent`).
2. Looks up that stage's cached graph (loaded once at construction,
   refreshed on `TransitionPreconditionRepository.onChanged` — mirrors
   `_workflowStatuses`'s cache-and-refresh pattern) and calls
   `evaluateTransitionGraph`.
3. Returns `(canAdvance: outcome == TransitionOutcome.allowed,
   blockReason: outcome == .blocked ? 'Waiting on:
   $blockingFieldDisplayName' : null)`.

`TransitionPreconditionRepository` is an optional `TicketsCubit`
constructor parameter, following `WorkflowStatusRepository`'s own
optional-dependency convention — omitting it pins every stage to
`allowed` (**not** today's hardcoded checks), so any construction site
that omits it needs to also not depend on precondition enforcement;
existing tests that exercise `_sddStageAdvanceCheck`'s real logic must
supply a `TransitionPreconditionRepository` seeded with the baseline
graphs above, or migrate to asserting against the new
`(bool, String?)` shape directly.

**`SddStageBlockReason` is removed.** `_sddStageAdvanceCheck`'s return
type becomes `Future<({bool canAdvance, String? blockReason})>` (the
`String?` is now the auto-derived text, not an enum lookup key).
`TicketDetailLoaded.canAdvanceSddStage`/`.sddStageBlockReason` change
type to match. `_SddStageSection`'s "Not ready" hint row — today a
`switch` over `SddStageBlockReason` picking one of 4 hardcoded
strings — is simplified to display `blockReason` directly; the switch
statement is deleted.

## 5. `TransitionPreconditionConfigCubit` (`lib/features/providers/presentation/cubit/`)

Mirrors `DecisionGraphConfigCubit`'s shape, keyed by `SddStage` instead
of `AutomationContext`: `load(SddStage)`,
`createNode`/`updateNode`/`deleteNode`, `setRoot`. Enforces the same
strict-tree invariant (a node referenced as a child from at most one
branch) — never in the repository or entity.
`TransitionPreconditionConfigState`: `Initial`/`Loaded` (`stage`,
`graph`, `nodesById`)/`Error` (message + prior `Loaded`).

## 6. UI

### `SddStagePreconditionEditorScreen`

Same dual-pane layout scaffold as `DecisionGraphEditorScreen`/
`MarkdownEditor._Wide` (`Row` of two `Expanded` panes, 1px divider) —
`GraphCanvas<TransitionNode>` (default/left, genuinely reused —
confirmed generic at [graph_canvas.dart:95](../../aion/lib/design_system/molecules/graph_canvas.dart:95))
and a new `TransitionOutlineList` (right), both bound to the same
`TransitionPreconditionConfigState`.

### `TransitionOutlineList` (new — simpler than `DecisionOutlineList`)

One row per `TransitionNode`: field name only (no parameter chip — no
field here has a parameter), children indented beneath their branch,
a 2-value outcome badge (`allowed`/`blocked`) on terminal branches.
Same nested-outline shape, no depth cap, inline `TransitionNodeForm`
expand-in-place per row.

### `TransitionNodeForm` (new — simpler than `DecisionNodeForm`)

Field picker only (`SelectionMenu` over `transitionFieldsFor(stage)`)
— no condition-kind picker (there's only one kind), no parameter
field (every field is a plain boolean), matched/unmatched branch
picker identical in shape to `DecisionNodeForm`'s (`§3.3`/`§3.4` in
that form's own design spec): "end here" + a 2-option outcome chip
pair, or "continue to another field."

### `WorkflowStatusSettingsScreen`'s SDD Stages section

Each `_SddStageRenameRow` for one of the 5 precondition-bearing stages
gains a "Configure precondition" affordance, mirroring the existing
`_AttachmentBadge`/"+ Attach skill" pattern already built for
`SkillAttachment` — tapping it opens `SddStagePreconditionEditorScreen`.
`null`-start and `archived` rows (no precondition) don't get this
affordance.

### Outcome badge/color treatment

A new 2-entry color map (`allowed` → `success`, `blocked` → `danger`),
distinct from the shipped `DecisionOutcome` 4-value map — used
identically by the canvas terminal node, the outline badge, and the
form's outcome selector, same pattern as the sibling engine's own
"one table, three consumers" shape.

## 7. What's explicitly unchanged

- `AutomationConfidence`/`AutomationContext`/every `AutomationContext`
  decision graph — untouched. This mechanism is orthogonal.
- `TicketStatus`'s design gate (`_codingExecutionGateCheck`) —
  untouched; deferred as a fast-follow (see proposal.md's Non-goals).
- `SddStage`'s own configurability (Phase 1's reorder/relabel/skip,
  `SddStageConfigRepository`) — untouched; this proposal only changes
  *what gates leaving* a stage, not which stages exist or their order.
- The `null`/`archived` branches of `_sddStageAdvanceCheck` — no
  precondition today, none added.

# Aion — SDD Stage Transition Preconditions: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Configurable Ticket Workflow Spec](./Aion%20Configurable%20Ticket%20Workflow%20Spec.md) (`WorkflowStatusSettingsScreen`, §1.6 SDD stages, §9 `SddStageRenameRow`), and the [Automation Decision Graphs Spec](./Aion%20Automation%20Decision%20Graphs%20Spec.md) — referenced below as **DG**. References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `IconBtn`, `PrimaryButton`, `GhostButton`, `AppTextField` by name.

Each of the five `SddStage` values that carries a real precondition today (`exploring`, `proposed`, `designBrief`, `designSync`, `verifying`) gets a project-authored **strict binary tree** of plain yes/no field checks. Every node is one field check; every check has exactly two outgoing branches (`matched`, `unmatched`); each branch either continues to another field check or terminates in one of exactly **two** outcomes — `allowed` or `blocked`. A `blocked` terminal carries a plain-language reason string surfaced in the ticket detail UI (§6).

The feature adds one screen (`SddStagePreconditionEditorScreen`, §4), three components (`PreconditionGraphCanvas` §1, `PreconditionOutlineList` §2, `TransitionNodeForm` §3), and one affordance on the existing `SddStageRenameRow` (§5).

**Relationship to DG.** This is the same dual-pane editor pattern with a **smaller vocabulary**: two outcomes instead of four, and field checks that take **no parameter** (every field is a plain fact, not a threshold). Consequences that run through the whole spec: DG's parameter chip (DG §1.2), integer parameter field (DG §3.2), and 2×2 outcome grid (DG §3.3) do not exist here; the node card is shorter, the outcome selector is a single row of two chips, and there is no `Model decides` deferral state. Where a value is unchanged from DG it is stated as unchanged and not re-derived.

**No Material widgets anywhere.** Every element below is a Flutter primitive: `DecoratedBox`, `Padding`, `Row`/`Column`/`Stack`/`Positioned`, `GestureDetector`, `MouseRegion`, `Focus`/`FocusableActionDetector`, `InteractiveViewer`, `CustomPaint` (grid, edges, glyphs), `CustomMultiChildLayout` (node placement), `OverlayEntry` + `CompositedTransformTarget`/`Follower` (menus, popover), `AnimatedContainer`/`AnimatedAlign`/`TweenAnimationBuilder` (state tweens), `CustomScrollView` + `SliverList` (outline scrolling). `TextField` inside a transparent `Material` ancestor remains the sole permitted Material exception, for text input only. No `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `MaterialApp`, `InkWell`, `Divider`, `VerticalDivider`, `Icons.*`, `Tooltip`.

**Themes.** **Arctic** (light) and **Obsidian** (dark). Every dimension, `EdgeInsets`, radius, gap, stroke width, dash pattern, glyph size, duration, curve and text style is **identical** between themes — only color token values differ, and every color is a named token resolved per theme (§7). Hex quoted `Arctic / Obsidian` is reference only; implement against the token. Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB. `fillAlpha` means `AionColors.fillAlphaArctic` `0.11` / `fillAlphaObsidian` `0.16`.

**New tokens: none.** No new colors, text styles, radii or spacing values. `allowed` maps onto `success`, `blocked` onto `danger`; `warning` and `secondary` are deliberately **unused** in this feature (there is no "ask" and no "defer" state).

Companion mockups: `Aion Stage Precondition Mockups.dc.html` — `1a` the full editor screen for **Proposed** · `1b` canvas vocabulary · `1c` outline rows · `1d` `TransitionNodeForm` + field menu · `1e` Workflow Settings affordance and the ticket-detail "Not ready" hint.

## 0. Shared vocabulary

### 0.1 Outcome treatment (2 values)

One table, used **identically** by the canvas terminal node (§1.3), the outline badge (§2.2) and the form's outcome picker (§3.3). Glyphs are `CustomPaint` primitives — no icon font, no `Icons.*`.

| Outcome | Token | Arctic | Obsidian | Label string | Glyph (12×12 box) |
|---|---|---|---|---|---|
| `allowed` | `AionColors.success` | `#1E9E76` | `#33D19B` | `Allowed` | Check: two strokes, `11` long ×`7` tall, `2.0px`, `StrokeCap.round`, `StrokeJoin.round` |
| `blocked` | `AionColors.danger` | `#CE3D54` | `#F1546C` | `Blocked` | Cross: two `10`-long strokes at ±45°, `1.6px`, `StrokeCap.round` |

Two outcomes means the pair must be separable without hue: the **glyph silhouette** (closed check vs. open cross) and the **label word** each carry the distinction alone, and both survive grayscale and 40% canvas zoom. Color reinforces, never carries.

`warning` is **not** used for either outcome — there is no third state to reserve it for, and using it would imply one. Any implementation that renders an outcome in `warning`, `secondary` or `primary` is wrong.

### 0.2 Branch identity

Unchanged from DG §0.2.

| Branch | Line | Label text | Label color | Anchor dot |
|---|---|---|---|---|
| `matched` | 1.5px **solid** `primary` — `#2E86D4` / `#9366FF` | `matched` | `primary` | `primary`, 7×7 circle |
| `unmatched` | 1.5px **dashed** `borderStrong` — `#BAC8D6` / `#35415C`, dash `4` on / `4` off | `unmatched` | `textMuted` | `borderStrong`, 7×7 circle |

### 0.3 Field catalog

Rendered by the picker (§3.1). Every field is a **plain fact** — no parameter, no operator, no units. Phrasing is always a positive statement, so `matched` unambiguously means "the statement is true".

| Field | Label | Valid stages |
|---|---|---|
| `chatHasReply` | Most recent chat has a reply | `exploring`, `designSync` |
| `hasDescription` | Ticket has a description | `exploring` |
| `openQuestionsResolved` | All open questions are resolved | `exploring`, `proposed` |
| `hasChildren` | Ticket has children | `proposed` |
| `needsDesignReview` | Story needs design review | `proposed`, `designBrief` |
| `childrenComplete` | All children are complete | `proposed`, `verifying` |
| `designPageHasContent` | Design page has content | `designBrief`, `designSync` |
| `designPageReviewed` | Design page has been reviewed | `designBrief`, `designSync` |
| `childTasksComplete` | All child tasks are complete | `verifying` |
| `prMerged` | Pull request is merged | `verifying` |
| `noOpenBlockers` | No open blocking links | `proposed`, `verifying` |

Menu grouping (§3.1): `THIS TICKET` (`hasDescription`, `hasChildren`, `openQuestionsResolved`, `noOpenBlockers`, `needsDesignReview`) then `LINKED WORK` (`chatHasReply`, `designPageHasContent`, `designPageReviewed`, `childrenComplete`, `childTasksComplete`, `prMerged`). Fields outside the stage's valid set are not listed — not listed-and-disabled.

### 0.4 Blocked reason — superseded, see 2026-09-01 `/verify` reconciliation below

Every `blocked` terminal owns a short reason string, authored in §3.3 and displayed verbatim in §6, prefixed by the app: `Waiting on: ` + reason. Reason input: max `48` characters, sentence-fragment lowercase (`chat reply`, `child stories`, `design review`). Empty reason is an **error** state on the terminal (§1.3, §3.3) — a `blocked` outcome with nothing to tell the user is unshippable.

**Reconciliation (post-`/verify`, 2026-09-01):** this subsection contradicts proposal.md's own "What this builds" ("Blocking reason: auto-derived, not a fixed enum … no `SddStageBlockReason` enum to maintain, no free-text authoring UI, no override"), which is the design intent that actually shipped. `/apply` built the auto-derived version and `/verify` flagged the conflict; the developer's call is to keep the auto-derived behavior. §0.4's authored-reason-field UI described here, and every place below that depends on it (§1.3's reason chip, §2.2's reason/empty-reason error treatment, §3.3's `Blocked reason` text field and its error states), is **intentionally not implemented**. The shipped behavior instead: a `blocked` terminal carries no reason of its own; `TicketsCubit._sddStageAdvanceCheck`/`evaluateTransitionGraph` auto-derive `'Waiting on: ' + <failing TransitionFieldSpec.displayName>` at evaluation time (`transition_field_spec.dart`'s `displayName`, e.g. `Most recent chat has a reply`), and that's what §6's hint displays verbatim. No authoring UI, no per-terminal reason storage, no "empty reason" error state — a `blocked` terminal is never incomplete for lacking one, since there's nothing to author.

## 8. Accessibility

- Every interactive element declares a `Semantics` label. Nodes announce as `Field check, ticket has children, matched continues to story needs design review, unmatched blocked waiting on child stories`.
- Keyboard: `Tab` walks the outline in tree order; `↑`/`↓` move between rows, `→`/`←` expand/collapse, `Enter` opens the form, `Esc` closes it, `Delete` deletes the focused node (with confirm). The canvas is reachable but not tab-walked node-by-node; `Tab` into it focuses the zoom cluster.
- Focus rings are never the sole state signal — every focused state above pairs the ring with a border-weight change.
- `matched` / `unmatched` never rely on hue alone (§0.2: solid vs. dashed). `allowed` / `blocked` never rely on color alone (§0.1: check vs. cross, plus the label word).
- With only two outcomes the risk is a red/green-only reading. The check-vs-cross silhouettes differ in closure and stroke count, and both terminals always render their label — an outcome pill is never glyph-only, at any zoom or pane width.
- Minimum text size in the feature is `AionText.caption` at `11`, used only for uppercase mono eyebrows at `0.14em` tracking on `textMuted` (contrast ≥ 4.6:1 on both themes' `surface`).
