# Multi Project Hub

# Proposal: multi-project-hub

## What we're building

Aion currently assumes a single implicit project: one global drift DB, one
global git repo, one global skill/config set. This change turns that into
explicit, isolated **projects**, and gives the app a **hub** — a project
list/switcher screen — as its entry point.

Concretely:

- A `Project` concept: each project gets its own drift DB and (desktop-only,
  see Scope below) its own git repo, addressed by a per-project storage key
  rather than one global path.
- A **baseline**: a versioned bundle of default skills, model/provider
  config, and architecture-convention references, shipped inside the app.
  Every project pins a baseline version and may locally override individual
  baseline items by name. Upgrading a project's pin is explicit, never
  silent.
- A **Hub screen**: lists existing projects, creates new ones, and opens one
  into the main workspace. Becomes the app's initial route.
- A runtime **active-project switch**: swapping projects closes the old
  project's DB connection and workspace state and opens the new one, live,
  without an app restart.

## Why

This is not speculative — it directly resolves two already-explored ideas:
[[hub-and-infrastructure-to-support-multiple-projects]] and
[[storage-model-per-project-scoping]] (both in `aion-arch/ideas/`, both
already marked `next_action: /propose multi-project-hub`). Aion is meant to
be a personal tool the user runs across every codebase they touch, not one
pinned to a single project — without this, the v1 ticket slice's data model
only ever supports one workspace, which blocks the entire premise of a
general-purpose spec-based coding assistant.

## Scope of this change

**In scope:**
- `Project` entity, repository, and drift schema (multi-project registry —
  a lightweight top-level DB that lists known projects and their metadata,
  distinct from each project's own per-project DB).
- Baseline package concept: versioned, bundled-in-app manifest of default
  skills/config/conventions; pinned-version + named-override resolution.
- Hub screen: project list, create-project flow, open/switch, remove.
- Runtime active-project switching: closing/reopening the per-project drift
  connection, rebuilding the workspace subtree scoped to the newly active
  project, persisting `lastOpenedAt`.
- go_router restructuring: `/hub` (and `/hub/new`) as new top-level routes;
  existing workspace routes (`/tickets`, `/boards`, …) become a child branch
  gated on having an active project.

**Explicitly out of scope (deferred to a follow-up change):**
- The bundled on-device embedding model itself, and per-ticket
  Markdown↔drift git sync mechanics (frontmatter schema, the
  `resource`/`page` bidirectional filesystem watcher, lint/repair tooling).
  These are deep storage-layer internals captured in
  [[storage-model-per-project-scoping]]'s "deep dive" section and are
  orthogonal to project isolation itself — project isolation only requires
  that each project's storage live at its own key/path, not that the
  git-sync engine be built yet. Building them together would make this
  change's `tasks.md` unreviewable.
- Full git version-history wiring (event-triggered commits) on
  mobile/web. See the platform note below — this change only initializes
  an empty per-project git repo on desktop.
- Any UI for editing baseline overrides (this change resolves overrides at
  read-time from whatever override files exist; authoring/editing them
  through the app UI is future work).

## Platform note (new scoping decision, not previously resolved)

`storage-model-per-project-scoping.md` described "own git repo" as part of
every project's isolated environment without stating a platform boundary.
This proposal narrows that: **git-backed version history is desktop-only**
for now, consistent with `project.md`'s existing platform scope (coding/git
capability is already desktop-only; extending plain version-history git
usage to mobile/web would require a bundled git implementation with no
current story). On mobile/web, a project's isolation is drift-DB-only
(scoped via `Project.storageKey`, not a filesystem path). This is flagged
as an open question in `design.md` for a future change, not silently
decided away.
