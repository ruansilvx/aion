# Dependency Caching And Ancestor Sibling Conflict

# Proposal: Per-run dependency caching and ancestor-based sibling-conflict scheduling

## Why

Two gaps, documented verbatim in `aion-arch/specs/tickets.md`'s Known gaps section and re-verified against the live code during `/explore`:

1. **No dependency caching across coding-execution runs.** Every `_runCodingExecution` worktree starts with zero installed dependencies, and — confirmed via `DetectedStack`'s own dartdoc in `lib/core/build/project_stack_detector.dart` — its `setupCommand` (`npm install`, `flutter pub get`, etc.) is "purely informational: nothing in Aion's own Dart code runs [it] — it's read by the model during a coding-execution implement/verify turn," surfaced only as advisory text `BaselineTailoringService` writes once into a project's `conventions/architecture-conventions` at onboarding time. Nothing mechanically invokes it, and nothing caches its output across runs.

2. **Hybrid mode's sibling-conflict signal is `parentId`-only.** Both `TicketsCubit._nextEligibleForHybrid` (the skip-ahead scheduler) and `clusterSiblingsAdjacently` (the Board's visual grouping, `lib/features/tickets/domain/utils/sibling_cluster.dart`) compare `ticket.parentId` directly. Two Tasks under different Stories of the same Epic are never treated as related, even though `parallel-work.md`'s own Hybrid-mode rationale ("siblings likely touch overlapping code") applies just as much one level up.

Both are traced to `aion-arch/ideas/dependency-caching-and-ancestor-sibling-conflict.md`'s brainstorm session, paired as one execution-mechanics change per that idea's explicit split from `pr-metadata-and-notification-center` (its UI/observability sibling, proposed separately).

## What we're building

**1. Aion-driven dependency setup + caching (Node.js only, this slice).** `_runCodingExecution` calls `ProjectStackDetector.detect(rootPath)` fresh at execution time (not the onboarding-time advisory text) and, when it detects Node.js:
- Seeds the worktree's `node_modules` from a per-project cache directory (`DependencyCacheService.seed`) before the implement turn.
- Mechanically runs `npm install` inside the worktree via `Process.run` — a new, deliberate step, not left to the model's own first action, mirroring the verify gate's existing `flutter analyze` precedent (`coding-execution-reliability-and-safety`: Aion invokes tooling directly, doesn't ask the model to).
- Writes the worktree's now-current `node_modules` back to the cache after a successful install (`DependencyCacheService.writeBack`), so the next run starts warmer.

**Scoped to Node.js only, not the full marker set `ProjectStackDetector` recognizes.** `/explore` found the caching win is genuinely uneven across languages: Node's `node_modules` has no global equivalent and is fully re-fetched per worktree today — the clear, unambiguous case. Flutter/Dart's `.dart_tool` win is smaller (the expensive part, package downloads, is already deduplicated globally via `~/.pub-cache`, shared across every worktree through `$HOME` regardless of this change). Rust/Go need no Aion-side caching at all — `ProjectStackDetector` defines no `setupCommand` for either, and their dependency caches (`~/.cargo`, Go's module cache) are already global. Python's `pip install` has no fixed local-directory convention without an assumed venv Aion doesn't currently enforce. Generalizing beyond Node.js is real, separately-scoped future work, not a natural extension of this slice.

**Cache mechanism: plain recursive copy, not hardlinks.** `dart:io` has no native hardlink API (`Link` creates symlinks only); per-file `Process.run('ln'/'mklink', ...)` calls across a multi-thousand-file `node_modules` tree would mean thousands of subprocess spawns per run — almost certainly slower and more fragile than one recursive `File.copy()` walk. The idea file's own open question ("hardlink vs. copy, per-platform") is resolved here as: copy, uniformly, on every platform. A true OS-level bulk-hardlink optimization (`cp -al`, Windows directory junctions) is flagged as possible future work, not attempted now.

**Cache location: co-located with worktrees in system temp, never a live-shared directory.** `_runCodingExecution`'s worktrees already live under `Directory.systemTemp` (`createTempSync('aion_exec_')`), not under the project's own `rootPath` — so the cache directory lives there too (`<systemTemp>/aion_dep_cache/<project.storageKey>/node_modules`), avoiding both a cross-volume copy concern and cluttering the user's actual checkout. Critically, the cache is only ever **copied into** a private per-worktree `node_modules`, never symlinked or junctioned directly into a worktree — with `parallel-work.md`'s N-concurrent-worktree support already shipped, a live-shared directory would let two simultaneous Node.js runs corrupt each other's `node_modules` mid-install, a strictly worse version of the exact shared-tree mutation risk `coding-execution-reliability-and-safety`'s worktree isolation was built to close.

**2. Ancestor-based sibling-conflict signal.** Both conflict-membership checks generalize from direct `parentId` equality to "shares any ancestor":
- `_nextEligibleForHybrid` (already `async`/repository-aware) gains a shared `_ancestorIds(String ticketId)` helper that walks the `parentId` chain via `_repository.getTicketById` until reaching a ticket with no parent — bounded naturally by Aion's Epic→Story→Task/Bug hierarchy (a Task/Bug's parent may be a Story *or* an Epic directly, per `TicketTypeHierarchy.canParent`'s any-strictly-higher-rank rule — not always exactly two hops, but always terminating).
- `clusterSiblingsAdjacently` stays a **pure, synchronous function** (unchanged contract otherwise) — it gains a second parameter, a precomputed `Map<String, String> topmostAncestorId`, built by a new `TicketsCubit.topmostAncestorIds(List<String> ticketIds)` batch method (reusing `_ancestorIds`) that `TicketsBoardView`/`BoardColumn` calls before grouping. A precomputed map, not an async function signature change, because Board columns are typically single-type (Task/Bug only) and their ancestor Stories/Epics are very often *not* already loaded in `TicketsLoaded.tickets` — the Board is paginated, so this can't be resolved purely from already-in-memory data.

## Out of scope

- Any caching for Flutter/Dart, Rust, Go, or Python — Node.js only, per the uneven-value analysis above.
- Hardlink/junction-based cache seeding — plain copy only, this slice.
- Cache invalidation tied to `package.json`/lockfile changes — `npm install` itself already reconciles a stale `node_modules` against the worktree's actual `package.json` on every run (the whole point of seeding-then-installing rather than seeding-and-trusting); no separate invalidation logic is added.
- Cache size limits/eviction — the cache directory grows unbounded in this slice; a future change can add pruning if real usage shows it matters.
- Deeper-than-Epic ancestor generalization, or any change to the hard `blocks`/`blockedBy` gate — untouched, per the idea file's own scoping.
- Any Board visual change beyond `clusterSiblingsAdjacently`'s existing grouping behavior — cousins now cluster the same way direct siblings already did; no new badge or visual treatment.
- `pr-metadata-and-notification-center` — the sibling idea from the same brainstorm split, proposed separately.
