# Design: Delegated-Skill Provider-Discovery Capability

## §1. `AgentProvider.supportsSkillDiscovery`

```dart
// core/contracts/agent_provider.dart
abstract interface class AgentProvider {
  // ...existing members unchanged...

  /// Whether this provider's underlying agent discovers and can execute
  /// project-local `.claude/skills/<name>` skills on disk when sent a
  /// `/<name>` slash-command prompt — the mechanism
  /// `SkillAttachmentKind.delegatedSkill` depends on entirely (see
  /// `TicketsCubit._promptFor`). `false` means a `delegatedSkill`
  /// attachment resolved to this provider cannot run at all; checked at
  /// `TicketsCubit._fireSkillAttachment`'s provider-resolution point,
  /// not folded into `ModelPhaseToolAccess`/`ModelRoutingCubit`'s
  /// dropdown filtering, since `ModelPhase.execution` is shared with
  /// plain coding-execution runs that have no such dependency. Same
  /// per-call-site-capability shape as `supportsSessionResume`, above.
  bool get supportsSkillDiscovery;
}
```

Placed directly below `supportsSessionResume` in the interface —
same category of declaration (a narrow, call-site-specific capability
bool, not a tool-access-tier-level concept).

## §2. Implementations

```dart
// core/agent/claude_agent_sdk_provider.dart
@override
bool get supportsSkillDiscovery => true;
```

`true` — `ClaudeAgentSdkClient`/`agent_bridge/index.mjs` runs the real
Claude Agent SDK, which discovers `.claude/skills/<name>` on disk
exactly the way a `/<name>` slash-command prompt expects.

```dart
// core/agent/anthropic_messages_api_provider.dart
@override
bool get supportsSkillDiscovery => false;
```

`false` — plain HTTP/SSE against the Messages API, no filesystem-based
skill discovery of any kind. Already unreachable for `delegatedSkill`
today via `supportedToolAccessTiers: {noTools}` (`ModelPhase.execution`
requires `full`); this declaration makes that exclusion explicit on the
capability that actually matters, rather than leaving it as an
accidental side effect of a different, coarser filter.

## §3. `TicketsCubit._fireSkillAttachment` — the first call site

Current shape (`presentation/cubit/tickets_cubit.dart`, inside the
existing `try` block, after worktree setup):

```dart
final (model, provider) = await _resolveModelAndProvider(
  toolsEnabled ? ModelPhase.execution : ModelPhase.capable,
);
await ChatCubit.runChatTurn(
  client: provider.client,
  ...
);
```

New shape — one check inserted between resolution and the run, gated
on `toolsEnabled` (`true` only for `delegatedSkill`, per the method's
existing `final toolsEnabled = attachment.kind ==
SkillAttachmentKind.delegatedSkill;` above it — `aionNativeTemplate`
never reaches this branch):

```dart
final (model, provider) = await _resolveModelAndProvider(
  toolsEnabled ? ModelPhase.execution : ModelPhase.capable,
);
if (toolsEnabled && !provider.supportsSkillDiscovery) {
  throw StateError(
    '${provider.displayName} cannot run delegated skills — it has no '
    '.claude/skills/ discovery capability.',
  );
}
await ChatCubit.runChatTurn(
  client: provider.client,
  ...
);
```

The `throw` is caught by the method's existing surrounding `catch (e)`,
which already posts `'Skill attachment failed: $e'` as a
`CommentAuthorType.system` comment on the spawned chat ticket — the
same failure-reporting path every other hard error in this method
already uses (e.g. the git-client/project-root `StateError` a few lines
above for a missing worktree dependency). The `finally` block's
worktree cleanup still runs correctly: if `toolsEnabled` is `true`, the
worktree was already created earlier in the `try` block (before model
resolution), so it's torn down like any other failure past that point —
no new cleanup logic needed. Message text intentionally names the
provider's `displayName` (already the app's vendor-neutral, per-provider
identity string — see `AgentProvider.displayName`), not a raw enum
value, matching this method's existing "Skill attachment failed: <e>"
comment's plain-English register.

## §3a. `TicketsCubit._runStageChatTurn` — the second call site (found by `/verify`)

`SkillAttachment` fires on entry to *either* a `WorkflowStatus`
(`_fireSkillAttachment`, §3 above) *or* an `SddStage` — exactly one,
never both. The `SddStage` surface is handled by a structurally
independent method, `_runStageChatTurn`, which §3's original "the one
call site" framing missed:

```dart
final attachmentToolsEnabled =
    attachment?.kind == SkillAttachmentKind.delegatedSkill;
final (model, provider) = await _resolveModelAndProvider(
  attachment == null
      ? stage.modelPhase
      : (attachmentToolsEnabled
            ? ModelPhase.execution
            : ModelPhase.capable),
);
// ...worktree setup when attachmentToolsEnabled...
final result = await ChatCubit.runChatTurn(
  client: provider.client,
  ...
);
```

Same shape as §3, same fix — one check inserted between resolution and
the run, gated on `attachmentToolsEnabled` (the local this method
already computes, equivalent to §3's `toolsEnabled`):

```dart
final (model, provider) = await _resolveModelAndProvider(
  attachment == null
      ? stage.modelPhase
      : (attachmentToolsEnabled
            ? ModelPhase.execution
            : ModelPhase.capable),
);
if (attachmentToolsEnabled && !provider.supportsSkillDiscovery) {
  throw StateError(
    '${provider.displayName} cannot run delegated skills — it has no '
    '.claude/skills/ discovery capability.',
  );
}
final result = await ChatCubit.runChatTurn(
  client: provider.client,
  ...
);
```

The throw is caught by `_runStageChatTurn`'s own existing surrounding
`catch (e)`, which already posts `'Stage advance failed: $e'` (not §3's
`'Skill attachment failed: $e'` — each method keeps its own existing
failure-comment text; this fix doesn't unify them). The `finally`
block's worktree cleanup and `_recordNotification(...,
kind: NotificationKind.stageAdvanceFailed, ...)` call both still run
correctly on this path, exactly as they already do for the method's
existing git-client/project-root `StateError`.

## §4. What does not change

- `ModelPhase`, `ModelPhaseToolAccess.requiredToolAccessTier`,
  `ModelRoutingCubit`/`ModelRoutingState`, and the Settings "MODELS"
  section — untouched. `ModelPhase.execution`'s dropdown keeps offering
  every provider declaring `ToolAccessTier.full`, regardless of
  `supportsSkillDiscovery` — narrowing it would also wrongly restrict
  plain coding-execution runs (`_runCodingExecution`), which share the
  same phase and have no skill-discovery dependency.
- `SkillAttachmentKind`, `SkillAttachment`, `_promptFor`,
  `WorkflowConfigCubit`, and every UI screen under
  `features/tickets/presentation/` — untouched. The `/<skillName>`
  prompt construction and attachment configuration UI are unaffected;
  this change only makes an already-impossible-in-practice run path
  fail loudly instead of silently.
- `AgentModelClient`, `AgentRequest`, `AgentEvent` — untouched.
- `ProviderRegistry`/`StaticProviderRegistry` — untouched; no new
  provider is added by this change.

## §5. Barrel/export impact

None — `AgentProvider` is already exported via
`core/contracts/agent_provider.dart` at its existing import path; no
barrel file lists individual interface members.
