# Ticket Trash

# Proposal: Ticket Trash & Bulk Delete

## What

Replace ticket deletion's current model — hard delete, blocked outright
if the ticket has structural children — with a soft-delete/trash model,
and add multi-select bulk delete on top of it. Deleting a ticket (single,
via the existing `TicketOverflowMenu`, or bulk, via a new multi-select
mode on `TicketsListScreen`/`TicketBoardView`) now moves it *and its
full structural subtree* into a trash instead of destroying anything —
nothing is unrecoverable until the user explicitly restores it or
permanently deletes it from a new Trash screen. `TicketHasChildrenException`
and its block-on-children behavior are removed entirely: cascading to
children is now always safe, because it's always reversible.

This single mechanism change eliminates a category of complexity that
came up while designing plain bulk delete on top of the *existing*
hard-delete model: there is no more "what if one selected ticket has
subtasks that aren't also selected" problem to solve, because trash
cascades unconditionally instead of blocking or requiring the user to
pre-select an entire subtree.

## Why

`aion-arch/specs/tickets.md`'s Known Gaps section lists two separate,
related gaps: "no bulk/multi-select delete" and "no undo/trash/soft-delete."
Working through bulk delete's design surfaced that these aren't actually
independent — mainstream project-management tools (Jira, Asana, ClickUp,
Azure DevOps) all solve "what about tickets with subtasks" the same way:
cascade to children, show the user what's about to happen, and lean on a
recoverable trash so an aggressive cascade is never actually risky. Azure
DevOps in particular pairs cascade delete with a temporary Recycle Bin.
Building bulk delete on top of Aion's current block-on-children,
no-undo model would have meant inventing bespoke selection-time or
delete-time partial-failure handling that the rest of the industry
doesn't need, specifically because it doesn't have a trash to fall back
on. Building the trash first removes the need for any of that.

## Scope

**In scope:**

- New `deletedAt` column on `TicketsTable` (schema version 3). A ticket
  is "in trash" iff `deletedAt != null`. No new table — soft-delete is a
  flag on the same row, so comments/`ticket_links` stay fully intact and
  ready to reappear exactly as they were on restore.
- `TicketRepository.trashTicket`/`trashTickets` — move a ticket (or a
  set of tickets) and their full structural subtrees into trash,
  unconditionally (no blocking). `restoreTicket` — restore a ticket,
  along with any trashed ancestors (so it's never left with a hidden
  parent) and any trashed descendants (its own subtree, trashed
  alongside it). `permanentlyDeleteTicket`/`emptyTrash` — hard-delete
  from trash, cascading to comments/`ticket_links` exactly as the old
  `deleteTicket` did.
- `getAllTickets`/`searchTickets` exclude trashed tickets (they're the
  main list/board/search surfaces); `getValidParentCandidates` excludes
  them too (can't reparent under a trashed ticket). `getTicketById`
  stays unfiltered — direct lookups still resolve a trashed ticket
  (needed internally by restore/permanent-delete).
- `TicketOverflowMenu`'s existing "Delete ticket" action switches to
  `trashTicket` — same entry points (`TicketDetailScreen`,
  `TicketListTile`, `TicketBoardCard`), updated (non-catastrophic)
  confirm-dialog copy reflecting that it's now reversible via Trash.
- A cascade preview (`TicketsCubit.previewTrashCount`) shown in the
  confirm dialog before any trash action — "this will move N ticket(s)
  to Trash, including any subtasks" — so cascading is transparent, not
  silent, matching the Jira/Azure DevOps pattern of disclosing the
  blast radius before an irreversible-feeling action.
- Multi-select bulk delete: a "Select" toggle in `TicketsListScreen`'s
  header, a screen-scoped `TicketSelectionCubit` shared between its list
  and board renderings, checkboxes on `TicketListTile`/`TicketBoardCard`,
  and a contextual `TicketSelectionBar` (replacing the FAB while active)
  with a selected count, select-all/deselect-all, Cancel, and a Delete
  action that trashes the whole selection (cascading, same as single
  delete) in one call.
- New `/tickets/trash` screen: lists trashed tickets, with per-ticket
  Restore and Permanently Delete actions, plus an "Empty trash" action
  for the whole list. Reachable via a new icon button in
  `TicketsListScreen`'s header.

**Out of scope (explicitly deferred):**

- Automatic/timed purge of trash (e.g. auto-delete after 30 days, like
  Azure DevOps). Trash is manual-only for v1 — items stay until the user
  restores or permanently deletes them. An auto-purge policy can be
  layered on later without restructuring anything here.
- Multi-select inside the Trash screen itself (bulk restore, bulk
  permanent-delete beyond "empty trash" which already covers the
  all-at-once case). Single-item actions plus "empty trash" cover the
  real need for v1.
- Bulk operations other than delete (status change, reparent, type/
  priority edit) — `TicketSelectionCubit` is a plausible foundation for
  these later, but none are built now.
- Any change to how `ticket_links` display for a trashed ticket (e.g. a
  live ticket's link count still counts links to a currently-trashed
  ticket) — a minor, low-stakes staleness that self-corrects on restore
  and resolves cleanly on permanent delete (which cascades to links).

## Known gaps this closes

From `aion-arch/specs/tickets.md`:
> Deletion is single-ticket and permanent — no bulk/multi-select delete,
> no undo/trash/soft-delete.

Both halves of this bullet are closed together — bulk delete only
became simple to build *because* trash removes the permanence that made
partial-failure handling necessary in the first place.
