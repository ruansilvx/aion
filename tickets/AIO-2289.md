# Design: Ticket link management UI

## 1. How `blocks`/`blockedBy` (and `duplicates`/`duplicatedBy`) are actually stored

Confirmed against the live code (`ticket_link_dao.dart`,
`tickets_cubit.dart`'s `_computeBlockedTicketIds`/`_isTicketBlocked`):
each relationship is **one row**, not an inverse pair. A row has
`sourceTicketId`, `targetTicketId`, and a single `linkType` naming the
relationship *from source to target* — e.g. `{source: A, target: B,
linkType: blocks}` means "A blocks B". There is no second row storing
"B is blockedBy A" — that reading is computed at *display* time by
whichever ticket is looking at the row.

This matters for the two mutations this change adds:

- **Delete** is a plain `DELETE ... WHERE id = ?` — no companion row to
  clean up.
- **Update** is a plain `UPDATE ticket_links SET link_type = ? WHERE id
  = ?` — no inverse-side recalculation needed. (The original brainstorm
  session assumed a stored inverse pair needing atomic dual-row
  recalculation; that assumption doesn't hold once the actual DAO code
  was checked. The *atomicity* motivation still applies for a different
  reason — see §4 — but the operation itself is a single-row update.)

## 2. Relative type: the actual new domain logic

Nothing today computes "how does this row read from a specific ticket's
point of view" as a reusable function — `_computeBlockedTicketIds` and
`_isTicketBlocked` both inline the same switch-on-`linkType`-string logic
ad hoc. This change introduces one canonical version and reuses it in
both new and existing call sites.

```dart
// domain/enums/ticket_link_type.dart — new extension, same file.

/// Perspective-flipping helpers for [TicketLinkType].
extension TicketLinkTypeRelative on TicketLinkType {
  /// The type that reads the same relationship from the other ticket's
  /// side. `relatesTo` is its own inverse (symmetric).
  TicketLinkType get inverse => switch (this) {
    TicketLinkType.blocks => TicketLinkType.blockedBy,
    TicketLinkType.blockedBy => TicketLinkType.blocks,
    TicketLinkType.relatesTo => TicketLinkType.relatesTo,
    TicketLinkType.duplicates => TicketLinkType.duplicatedBy,
    TicketLinkType.duplicatedBy => TicketLinkType.duplicates,
  };
}
```

A new pure function (`domain/utils/ticket_link_direction.dart` or a
static method — see tasks.md) computes the relative type for a viewing
ticket:

```dart
/// The relationship type [row] expresses **from [viewingTicketId]'s
/// point of view** — [row.linkType] as stored if [viewingTicketId] is
/// the row's source, or its [TicketLinkTypeRelative.inverse] if
/// [viewingTicketId] is the target.
TicketLinkType relativeLinkType(TicketLinkData row, String viewingTicketId) {
  final stored = TicketLinkType.values.byName(row.linkType);
  return row.sourceTicketId == viewingTicketId ? stored : stored.inverse;
}
```

`_computeBlockedTicketIds`/`_isTicketBlocked` are refactored to call
`relativeLinkType` + a check against `TicketLinkType.blockedBy` instead
of their current duplicated inline switches — same behavior, one less
copy of the logic to keep in sync (in scope for this change since it's
the same file, same concept, and a trivial substitution — see tasks.md;
not a separate cleanup pass).

## 3. Data flow: `TicketLinkData` reaching the widget layer

Today, `TicketsCubit.loadDocumentRelations` fetches `TicketLinkData` rows
but immediately discards them, resolving each to a bare `Ticket` in
`TicketDetailLoaded.linkedTickets`/`.backlinks` (`List<Ticket>`). That's
why `LinkedTicketsSection` can't show a type today — the type never
survives past `loadDocumentRelations`.

New shape:

```dart
// A small record pairing the resolved other-side Ticket with this
// row's relative type and its own row id (needed for delete/update).
// Domain layer — lives alongside TicketLinkData, no Flutter import.
typedef LinkedTicketRef = ({Ticket ticket, TicketLinkType relativeType, String linkId});
```

- `TicketDetailLoaded.linkedTickets` and `.backlinks` change type from
  `List<Ticket>` to `List<LinkedTicketRef>`. `loadDocumentRelations`
  computes `relativeType` via `relativeLinkType(link, ticket.id)` for
  each row instead of discarding `link`.
- `PageRelations.linkedTickets`/`.backlinks` (the `PagesCubit`-side
  equivalent feeding `PageDetailScreen`) gets the same shape change —
  same underlying `loadDocumentRelations`-style resolution.
- Every existing caller that reads `.linkedTickets`/`.backlinks` as
  `List<Ticket>` (both `LinkedTicketsSection`/`BacklinksSection` call
  sites: `ticket_metadata_section.dart`, `page_detail_screen.dart`)
  updates to unwrap `.ticket` where it only needs the ticket (e.g.
  `BacklinksSection`, which stays `List<Ticket>`-shaped since it has no
  new per-row behavior — callers map `relations.backlinks.map((r) =>
  r.ticket).toList()` there) or pass the full `LinkedTicketRef` through
  to `LinkedTicketsSection` (which does need it).

`LinkedTicketsSection`'s public contract changes from `List<Ticket>
tickets` to `List<LinkedTicketRef> links`, adding two new callbacks:

```dart
class LinkedTicketsSection extends StatelessWidget {
  const LinkedTicketsSection({
    required this.links,
    required this.onTap,
    required this.onRemove,        // new
    required this.onChangeType,    // new
    this.trailing,
  });

  final List<LinkedTicketRef> links;
  final ValueChanged<String> onTap;          // unchanged: ticket id
  final ValueChanged<String> onRemove;       // new: linkId
  final void Function(String linkId, TicketLinkType newRelativeType) onChangeType; // new
  final Widget? trailing;
}
```

`_LinkRow` gains the type glyph (reusing `_linkTypeGlyph`/
`_linkTypeLabel`, promoted from `ticket_link_picker.dart`'s private
top-level functions to shared internal functions both files import —
see tasks.md; they're pure functions with no state, safe to hoist
without a design-system promotion decision since both call sites stay
inside the `tickets` feature... except `LinkedTicketsSection` itself
lives in `design_system/molecules/`, which cannot import
feature-specific enums' *label strings* tied to `context.l10n` the same
way — resolved below), a remove control, and the type editor.

**Cross-layer wrinkle:** `LinkedTicketsSection` lives in
`design_system/molecules/` (feature-agnostic) but now needs
`TicketLinkType`'s glyph/label — a `tickets`-feature-owned enum. It
already imports `TicketType`/`Ticket` from the `tickets` feature (see
existing `_typeColor` switch), so this isn't a new precedent — the
design system already treats `tickets`' core vocabulary (`Ticket`,
`TicketType`) as fair game the same way `core/` is, per project.md's
"any feature consumes design_system/ the same way it consumes core/"
framing read in reverse (design_system already depends on this one
foundational feature's domain enums). `TicketLinkType`'s glyph/label
functions move from `ticket_link_picker.dart` (presentation, `tickets`
feature) to `domain/enums/ticket_link_type.dart` itself, as extension
methods (`glyph`, `label(BuildContext)`) — domain layer already has no
Flutter dependency issue since `IconData`/`PhosphorIcons` come from
`phosphoricons_flutter`, a package, not a Flutter framework type; this
matches how `TicketType`'s own display helpers are already colocated
(see `_typeColor`'s reliance on `AionColors` tokens, itself imported
into a `tickets`-domain-adjacent spot). `ticket_link_picker.dart` and
the new `_LinkRow` code both call the same extension.

## 4. Cubit methods: `deleteTicketLink` / `updateTicketLinkType`

Per this project's Cubit-owns-domain-logic convention, and to fix an
existing inconsistency while touching this exact code path: today
`ticket_metadata_section.dart`'s `TicketLinkPicker.onSelected` callback
calls `context.read<TicketLinkRepository>().createLink(...)` directly
from the widget layer, then separately calls
`TicketsCubit.loadDocumentRelations` and (conditionally)
`refreshBlockedBoardState()`. This change adds two new `TicketsCubit`
methods following the *same* pattern already used elsewhere in this
cubit (see `updateTicketStatus`'s `_refreshBlockedBoardState` call), and
migrates the existing create call site to match — so all three
mutations (create/update/delete) go through the Cubit consistently
rather than two going through it and one bypassing it:

```dart
/// Deletes the [linkId] row, then refreshes this ticket's document
/// relations and (if the deleted link was a blocks/blockedBy pair) the
/// Board's blocked-badge state. No-ops if constructed without a
/// [TicketLinkRepository].
Future<void> deleteTicketLink(String ticketId, String linkId) async {
  final linkRepo = _linkRepository;
  if (linkRepo == null) return;
  final wasBlocking = await _linkInvolvesBlocking(linkId);
  await linkRepo.deleteLink(linkId);
  await loadDocumentRelations(ticketId);
  if (wasBlocking) await _refreshBlockedBoardState();
}

/// Updates the [linkId] row's stored type to [newRelativeType] — the
/// type as picked in `LinkedTicketsSection`'s `_LinkTypeEditor`, i.e.
/// *as it reads from [ticketId]'s own side*, not the row's raw
/// source-to-target reading — then refreshes the same state
/// [deleteTicketLink] does.
///
/// **Post-`/verify` correction:** earlier drafts of this method (and
/// tasks.md's T14/T15) had the caller translate the relative selection
/// to canonical via `toCanonical` before calling this method. As built,
/// the translation happens *here* instead — this method fetches the row
/// anyway (for the `wasBlocking` check below), and `LinkedTicketRef`
/// deliberately doesn't carry the row's `sourceTicketId`/
/// `targetTicketId`, so a widget-layer `toCanonical` call would need a
/// second, redundant row fetch. One fetch, one write; the relative→
/// canonical mapping stays domain logic owned by the Cubit rather than
/// leaking into the widget layer.
Future<void> updateTicketLinkType(
  String ticketId,
  String linkId,
  TicketLinkType newRelativeType,
) async {
  final linkRepo = _linkRepository;
  if (linkRepo == null) return;
  final row = await linkRepo.getLinkById(linkId);
  if (row == null) return;
  final wasBlocking = row.linkType == TicketLinkType.blocks.name ||
      row.linkType == TicketLinkType.blockedBy.name;
  final newCanonicalType = toCanonical(newRelativeType, row, ticketId);
  await linkRepo.updateLinkType(linkId, newCanonicalType);
  await loadDocumentRelations(ticketId);
  if (wasBlocking || newCanonicalType == TicketLinkType.blocks ||
      newCanonicalType == TicketLinkType.blockedBy) {
    await _refreshBlockedBoardState();
  }
}

/// Also migrated: link *creation* moves from
/// `ticket_metadata_section.dart`'s direct repository call into a third
/// new method, `createTicketLink`, mirroring the two above — same
/// refresh-after-write shape, now consistent across all three
/// mutations.
Future<void> createTicketLink(
  String ticketId,
  String targetTicketId,
  TicketLinkType linkType,
) async {
  final linkRepo = _linkRepository;
  if (linkRepo == null) return;
  await linkRepo.createLink(
    sourceTicketId: ticketId,
    targetTicketId: targetTicketId,
    linkType: linkType,
  );
  await loadDocumentRelations(ticketId);
  if (linkType == TicketLinkType.blocks ||
      linkType == TicketLinkType.blockedBy) {
    await _refreshBlockedBoardState();
  }
}
```

`_linkInvolvesBlocking(String linkId)` is a small private helper (fetch
the row via a new `TicketLinkRepository.getLinkById` — see §5 — and
check its stored `linkType`) so delete/update only pay for
`_refreshBlockedBoardState()`'s extra query when the affected link could
actually change the Board's blocked-badge state, mirroring the existing
create call site's `if (linkType == blocks || blockedBy)` guard.

Atomicity note (why `updateLinkType` is one repository call instead of
delete+recreate, even though §1 shows the DB operation is a single-row
`UPDATE`): a delete-then-create pair would still emit two separate
`loadDocumentRelations` refreshes and, if the recreate half ever failed
validation, leave the user with the link silently gone. Wrapping it as
one repository method keeps it one write, one refresh, no partial-
failure window — cheap to guarantee now that it's understood to be a
single-row update rather than dual-row bookkeeping.

## 5. Repository/DAO additions

```dart
// domain/repositories/ticket_link_repository.dart
abstract interface class TicketLinkRepository {
  Future<List<TicketLinkData>> getLinksForTicket(String ticketId);
  Future<void> createLink({required String sourceTicketId, required String targetTicketId, required TicketLinkType linkType});
  Future<List<TicketLinkData>> getLinksByTypes(List<TicketLinkType> types);

  /// New. Returns the single row with id [linkId], or `null` if it no
  /// longer exists (e.g. already deleted by a concurrent action).
  Future<TicketLinkData?> getLinkById(String linkId);

  /// New. Deletes the single row with id [linkId]. No-ops if it doesn't
  /// exist.
  Future<void> deleteLink(String linkId);

  /// New. Updates the single row with id [linkId]'s stored type to
  /// [newType]. No-ops if the row doesn't exist.
  Future<void> updateLinkType(String linkId, TicketLinkType newType);
}
```

`DriftTicketLinkRepository` implements all three by delegating to three
new `TicketLinkDao` methods (`getLinkById`, `deleteLink`,
`updateLinkType`) — trivial single-row `select`/`delete`/`update`
statements, following `deleteLinksForTickets`'s existing style but
scoped to one `id` instead of a source/target-id list.

## 7. The `duplicatedBy` carve-out

`TicketLinkPicker.linkTypeOptions` already never offers
`TicketLinkType.duplicatedBy` as a raw creation choice — it's
documented as "always the inverse reading of a `duplicates` row, never
a user-chosen value." This change preserves that policy for editing
too, rather than inventing new direction-flip semantics: the
`_LinkTypeEditor` on a row currently read (relatively) as "Duplicated
by" renders **no edit control** — that one row is delete-only (its glyph
+ label still render normally; only the pencil affordance is omitted).
Every other relative type (`Blocks`, `Blocked by`, `Relates to`,
`Duplicates`) remains editable via the same `linkTypeOptions` set
already computed per ticket type in `ticket_metadata_section.dart`
(`resource`: `[relatesTo]` only, so its rows never show an edit control
with more than one option; everything else: the full four).

Translating an edited *relative* selection back to the *canonical*
stored value passed to `updateTicketLinkType`:

```dart
// If the viewing ticket is the row's source, relative == canonical.
// If the viewing ticket is the row's target, canonical == relative.inverse.
TicketLinkType toCanonical(TicketLinkType relativeSelection, TicketLinkData row, String viewingTicketId) =>
    row.sourceTicketId == viewingTicketId ? relativeSelection : relativeSelection.inverse;
```

# Aion — Linked Ticket Relationships (row type-indicator, remove & inline edit): Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References the [Link Type & Blocked Badge Spec](./Aion%20Link%20Type%20and%20Blocked%20Badge%20Spec.md) (its `LinkTypeSelector` trigger/menu geometry and the four-type glyph/copy set, which this feature extends to a fifth derived type) and the [Overlay Menu Item Spec](./Aion%20Overlay%20Menu%20Item%20Spec.md) (the `OverlayMenuItem` row primitive the editor's menu rows are built on). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `LinkedTicketsSection`, `LinkTypeSelector`, `OverlayMenuItem`, `TypeChip` — by name.

Mockups: [Aion Linked Ticket Relationships Mockups](./Aion%20Linked%20Ticket%20Relationships%20Mockups.dc.html).

This change makes an already-created `TicketLink` both **legible** (each row now shows *what kind* of relationship it is, relative to the ticket you're viewing) and **mutable** (each row can be removed with a confirmation step, or have its type changed inline without deleting and recreating). It **adds no new screen and no new route** — every state below appears inline inside the existing `LinkedTicketsSection` molecule, which already sits on a ticket's detail view. The section's own header (a `"LINKED TICKETS"` caption + count badge + trailing `"+ Add"` button) is **unchanged and out of scope** — it sits above the rows specified here.

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (non-Material) / `Padding` / `Row` / `Column` / `Stack` + `Positioned` / `GestureDetector` / `MouseRegion` / `Focus` / `FocusableActionDetector` / `Overlay` + `CompositedTransformFollower` / `AnimatedOpacity` / `AnimatedSlide` / `AnimatedContainer` / `AnimatedScale` / `CustomPaint`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `DropdownButton`, `PopupMenuButton`, `IconButton`, `Tooltip`, `Dialog`, `AlertDialog`, `SnackBar`, `InkWell`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token or a documented derivation that already resolves per theme. Concrete hex is `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)`, never a hardcoded ARGB. Read the theme at the call site: `final c = ThemeScope.of(context).colors;`, `final isDark = ThemeScope.of(context).isDark;`, `final a = ThemeScope.of(context).fillAlpha;` (Arctic `0.11` / Obsidian `0.16`).

**New tokens required: none.** The static indicator, editor trigger, and editor menu reuse the `LinkTypeSelector` type/glyph/copy set and its state model; the remove icon-button reuses `destructiveTint`; the editor menu rows reuse `OverlayMenuItem`; the confirmation popover reuses the app's overlay panel + shadow geometry. The one derived value not already named — a darkened destructive button hover — is documented in §5.4 as an inline `Color.alphaBlend`, not a new token.

## 0. Model, direction, and where each piece sits

The relationship is stored once on the `TicketLink`; the row computes a **relative type** from the perspective of the ticket currently being viewed. A `blocks` link viewed from the *other* end reads `blockedBy`; a `duplicates` link viewed from the other end reads `duplicatedBy`. `relatesTo` is symmetric.

```dart
// The five relative relationships a row can read as.
// blockedBy and duplicatedBy are the derived inverse views of blocks / duplicates.
enum LinkRelation { blocks, blockedBy, relatesTo, duplicates, duplicatedBy }
```

Each row is handed:

```dart
class LinkRow extends StatefulWidget {
  final LinkRelation relation;              // computed relative to the viewed ticket
  final TicketRef target;                   // key + title + type of the linked ticket
  final List<LinkRelation> allowedTypes;    // caller-supplied editable set (may be length 1)
  final ValueChanged<LinkRelation> onRetype;
  final VoidCallback onRemove;
}
```

**Edit-affordance rule** (single source of truth, applied in §2 / §6):

```dart
bool get _editable =>
    relation != LinkRelation.duplicatedBy && // always derived, never directly editable
    allowedTypes.where((t) => t != relation).isNotEmpty; // ≥1 *other* type to switch to
```

- `duplicatedBy` rows **always** show their glyph + label but **never** an edit affordance (§6.3).
- A row whose `allowedTypes` is effectively a single value (nothing else to switch to) **omits** the edit button entirely (not a disabled icon) — see §6.1. The remove action is always present.

| Piece | Where | When |
|---|---|---|
| Relationship indicator (§1) | trailing end of every link row | always (all five relations) |
| Row action buttons (§3) | trailing end, right of the indicator | revealed on row hover / focus-within |
| `_LinkTypeEditor` (§4) | replaces the static indicator in place | while editing (edit button pressed) |
| Remove confirmation (§5) | popover anchored to the remove button | after remove button pressed, before deletion |

## 1. `RelationshipIndicator` — static/default state

The glyph + short label shown at the trailing end of a link row. It carries **directional emphasis**: the two dependency relations (`blocks`, `blockedBy`) read as *active / attention-worthy* in `textSecondary`; the three associative relations (`relatesTo`, `duplicates`, `duplicatedBy`) read *quieter* in `textMuted`. Glyphs are **monochrome** — never a type-accent hue (this is a relationship, not a ticket-type dimension; matches `LinkTypeSelector` §1.4).

```dart
class RelationshipIndicator extends StatelessWidget {
  final LinkRelation relation;
  const RelationshipIndicator({required this.relation});
}
```

### 1.1 Container & layout

| Property | Value |
|---|---|
| Container | `Row` (`mainAxisSize: min`, `crossAxisAlignment: center`) |
| Padding | none (the row owns trailing spacing; §6) |
| Gap glyph→label | `6` |
| Fill / border / shadow | none — bare inline mark |
| Leading glyph | per-relation (§1.3), `14px`, pinned in a `16px` box so labels left-align across relations |
| Label | per-relation (§1.3), `AionText.key` (JetBrains Mono 11 / w600 — today's link-type label style, unchanged) |

### 1.2 Tone per relation

| Tone | Relations | Glyph color | Label color |
|---|---|---|---|
| **Directional** (attention) | `blocks`, `blockedBy` | `textSecondary` (`#46586A / #A2AEC6`) | `textSecondary` |
| **Associative** (quiet) | `relatesTo`, `duplicates`, `duplicatedBy` | `textMuted` (`#8496A6 / #6B7690`) | `textMuted` |

The tone split is the *only* color difference between relations — no relation gets its own hue. Rationale: `Blocks` / `Blocked by` describe a dependency that gates work and deserves to read one weight stronger; `Relates to` / `Duplicates` / `Duplicated by` are informational cross-references.

### 1.3 Per-relation glyph + copy

| Relation | Glyph (Phosphor name / mockup unicode) | Label |
|---|---|---|
| `blocks` | `arrow-right` (`arrow-line-right`) / `→` | `"Blocks"` |
| `blockedBy` | `arrow-left` (`arrow-line-left`) / `←` | `"Blocked by"` |
| `relatesTo` | `arrows-left-right` (`link`) / `↔` | `"Relates to"` |
| `duplicates` | `copy` / `⧉` | `"Duplicates"` |
| `duplicatedBy` | `copy-simple` (`copy` fallback) / `⧉` | `"Duplicated by"` |

`duplicates` and `duplicatedBy` deliberately share the `copy` glyph family (they are two views of one relationship); the label carries the direction. Implementers may substitute `copy-simple` for `duplicatedBy` where the icon set provides it, for a subtle visual distinction — not required.

### 1.4 States

Non-interactive on its own — **default only**. It has no hover/focus/pressed of its own; those belong to the row (§2) and to the controls that replace or sit beside it (§3, §4). No disabled or error state.

## 2. Link row — hover / action-revealed state

The row is the interactive surface. On hover (mouse) or focus-within (keyboard) it (a) raises its own fill + border, and (b) reveals the action buttons (§3), which **fade + slide in** alongside the still-visible relationship indicator (the indicator stays — it remains informative while you act).

### 2.1 Row container (existing look, unchanged geometry)

| Property | Value |
|---|---|
| Container | `GestureDetector` (whole row tappable → open ticket) → `MouseRegion` → `Focus` → `AnimatedContainer` (`DecoratedBox` equivalent) |

### 2.2 Row content, left → right

1. **Type square** — `8×8`, radius `2`, color = target ticket's type accent (`typeTask`/`typeStory`/`typeEpic`/…). `flex: 0 0 auto`.
2. **Key chip** — mono key, `AionText.key` (11 / w600), color `textSecondary`, fill `surfaceHover`, padding `EdgeInsets.symmetric(horizontal: 6, vertical: 2)`, radius `AionRadius.sm` (6). `flex: 0 0 auto`.
3. **Title** — `AionText.cardTitle` (14 / w600), color `textPrimary`, `maxLines: 1`, ellipsis. `Expanded`.
4. **Trailing cluster** — `Row(mainAxisSize: min, gap: 4, crossAxisAlignment: center)`:
   - `RelationshipIndicator` (§1) — always present.
   - Action buttons (§3) — occupy zero width when hidden; revealed on hover/focus-within.

### 2.3 Reveal animation

The action buttons are wrapped in an `AnimatedSlide` + `AnimatedOpacity` (or a single `AnimatedContainer` clip):

- Hidden (default): `opacity: 0`, `offset: Offset(0.10, 0)` (≈ `+4px` right), `IgnorePointer(ignoring: true)`, and their box collapses (`maxWidth: 0` via an `AnimatedContainer` clip) so they take no layout width and never push the title.
- Revealed (hover/focus-within): `opacity: 1`, `offset: Offset.zero`, pointer-enabled, box expands to content width.
- Transition: `140ms`, `Curves.easeOut`. The relationship indicator does **not** move; only the buttons slide in to its right.

Keyboard: `Focus`/`FocusableActionDetector` on the row exposes `onFocusChange` → the same revealed state as hover, so keyboard users can Tab to the row and reach the buttons; the buttons are their own focus stops after the row.

## 4. `_LinkTypeEditor` — inline type editor

A compact, row-embedded sibling of `LinkTypeSelector` (Link Type & Blocked Badge §1). When the edit button is pressed, the static `RelationshipIndicator` (§1) is **replaced in place** by this trigger; opening it drops a menu of `allowedTypes`. Committing a choice calls `onRetype` and reverts the trailing area to the (new) static indicator. Dismissing without a choice reverts to the original indicator.

```dart
class _LinkTypeEditor extends StatefulWidget {
  final LinkRelation value;                 // current relation
  final List<LinkRelation> allowedTypes;    // the menu's options (already excludes duplicatedBy)
  final ValueChanged<LinkRelation> onChanged;
  final VoidCallback onDismiss;
}
```

### 4.1 Trigger — appearance

Same control family as `LinkTypeSelector`'s trigger, shrunk to sit inside a row and sharing the action buttons' corner radius so the whole trailing cluster reads as one unit.

This is the only place the editor shows an error affordance; the menu itself never does.
