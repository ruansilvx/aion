# Delta spec: Inline `[[wikilink]]` backlinks

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (51/53 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Relative to `aion-arch/specs/tickets.md`'s current
[Documentation section](../../../specs/tickets.md#documentation-section)
and [Pages module](../../../specs/tickets.md#pages-module-libfeaturespages).

Amended 2026-08-13, after design-sync approval: reworked to anchor
wikilink resolution on `Ticket.ticketId` (Aion's existing unique
per-ticket identifier) rather than title text alone, closing or
narrowing several gaps the original version of this spec left open. See
`proposal.md`'s "Scope decisions beyond the brainstorm" for the
per-gap reasoning.

## ADDED

- **`PageWikilinksTable` / `PageWikilinkData`** (`data/models/
  page_wikilink_model.dart`) — new Drift table: `id`, `source_page_id`,
  `target_page_id`, `created_at`. `target_page_id` may reference a
  `page` or a `resource` ticket; `source_page_id` is always a `page`.
  No FK constraints. Schema version 12.
- **`PageWikilinkDao`** (`data/daos/page_wikilink_dao.dart`) —
  `getIncomingLinks`, `getOutgoingLinks`, `replaceOutgoingLinks`
  (transactional delete-then-insert), `deleteLinksForTickets` (batch,
  source-or-target match).
- **`PageWikilinkRepository`** (domain interface) /
  **`DriftPageWikilinkRepository`** (implementation) — persists resolved
  inline-wikilink references, parallel to and independent from
  `TicketLinkRepository`.
- **`WikilinkExtractor`** (`core/markdown/wikilink_extractor.dart`) —
  pure, Flutter-free parsing: `extractReferences(String) ->
  List<WikilinkMatch>` (each carrying `raw`, `target`, and an optional
  `alias`), `looksLikeTicketId(String target) -> bool`, and
  `rewriteTitle` (title-anchored occurrences only).
- **Two-tier wikilink resolution.** `[[Title]]` resolves by
  case-insensitive exact title match against every live `page`/
  `resource` ticket (first-match-wins by `createdAt` on a duplicate
  title). `[[TicketId]]` (e.g. `[[AIO-42]]`) resolves by exact
  `Ticket.ticketId` match — always unambiguous — with its displayed
  text the target's live current title (re-resolved at render time, not
  baked into stored text). Both forms support `[[Target|Alias]]`, a
  literal, user-authored display label rendered verbatim and never
  auto-rewritten.
- **`BacklinkOrigin` enum** (`explicitLink | wikilink`) and
  **`BacklinkRef`** entity (`{Ticket ticket, BacklinkOrigin origin}`).
- **A `page` ticket's outgoing wikilink references are parsed and
  resolved on every save** — both the in-app save path
  (`TicketsCubit.updateTicket`) and the desktop file-watcher's reconcile
  path (`TicketMarkdownReconciler`) — via the two-tier resolution above
  against every live `page`/`resource` ticket, and persisted via
  `PageWikilinkRepository.replaceOutgoingLinks`.
- **Renaming a page rewrites referencing pages' title-anchored
  references only.** When a `page` ticket's `title` changes, every page
  with a stored outgoing wikilink to it has its `[[Old Title]]`
  occurrences (title-anchored only — `id`-anchored occurrences are
  never touched, since their target never changes) rewritten to
  `[[New Title]]` and re-saved through `TicketsCubit.updateTicket`
  (recursively), fired fire-and-forget/non-blocking. Before rewriting a
  given referrer, `TicketsCubit` checks the existing
  `ActiveTicketViewRegistry` (the same signal
  `TicketMarkdownReconciler` already uses for the equivalent
  external-file-edit case) and defers the rewrite — retrying once the
  user navigates away — rather than clobbering a page the user
  currently has open. Desktop-only, matching that registry's own
  gating.
- **A one-time schema-12 upgrade migration backfills the wikilink index**
  from every pre-existing live `page` ticket's current content, so
  `[[...]]` text hand-typed before this feature shipped is indexed
  without requiring a re-save.
- **`MarkdownEditor` gains a `[[`-triggered, caret-anchored autocomplete
  overlay** (`wikilinkSuggestions` optional constructor callback,
  returning `WikilinkSuggestionItem`s — `{ticketId, title, breadcrumb}`),
  reusing the existing `Overlay`/`LayerLink`/`CompositedTransformFollower`
  pattern, anchored to the live text caret (not just the field). On
  selection, inserts a bare `[[TicketId]]` reference (not
  `[[Title]]`) — the robust, always-unambiguous, never-stale form.
- **New `WikilinkSuggestionList` widget** (`design_system/molecules/
  wikilink_suggestion_list.dart`) — the autocomplete's row-list content.
- **Create-on-the-fly for unresolved references.** When the autocomplete
  query matches nothing, pressing Enter (via a new optional
  `MarkdownEditor.onCreatePage` callback) creates a new page with that
  title and inserts a reference to it. The same affordance is available
  by tapping an already-rendered, unresolved wikilink span in
  `MarkdownView` (a new optional `onCreateWikilinkTarget` callback) —
  only offered when the unresolved target doesn't itself look like a
  `ticketId` (an unresolved id means the target was trashed/deleted,
  not a new-page candidate).
- **`MarkdownView` gains optional `resolveWikilink`/`onWikilinkTap`/
  `onCreateWikilinkTarget` callbacks**, parsing `[[Target]]`/
  `[[Target|Alias]]` via `WikilinkExtractor.extractReferences` and
  rendering a resolved reference as a tappable, visually distinct
  inline span (displayed text: the literal alias if given, otherwise
  the target's live title) or an unresolved one as plain, chip-backed,
  optionally tappable-to-create text. All three default to `null` —
  every non-page `MarkdownView` consumer is unaffected.
- **`PageTicketProvider.getWikilinkCandidates()`** — every live
  `page`/`resource` ticket (widened from `page`-only), no self/
  descendant exclusion, backing wikilink autocomplete/resolution.
- **`PagesCubit.loadWikilinkCandidates()`** — query-only, no state
  emitted (same shape as `getValidParentCandidates`), delegates to
  `PageTicketProvider.getWikilinkCandidates()`.

## MODIFIED

- **`BacklinksSection`** (`design_system/molecules/backlinks_section.dart`)
  — signature changes from `List<Ticket> backlinks` to `List<BacklinkRef>
  backlinks`. Still fully read-only; rows with `origin == wikilink` are
  now visually distinguished from `origin == explicitLink` rows (which
  render exactly as before).
- **`TicketsCubit.loadDocumentRelations`** and **`PageTicketProviderImpl
  .loadPageRelations`** — `backlinks` computation now merges explicit
  `TicketLink`-derived rows with wikilink-derived rows into one
  `List<BacklinkRef>`. The wikilink half now applies when the gated
  ticket is a `page` **or a `resource`** (widened — a resource can be a
  wikilink target now), and only when the cubit/provider was
  constructed with a `PageWikilinkRepository`. A doc linked via both
  mechanisms produces two separate rows — not deduplicated.
- **`PageRelations.backlinks`** field type: `List<LinkedTicketRef>` →
  `List<BacklinkRef>`.
- **`TicketsCubit`** constructor gains two new optional dependencies:
  `PageWikilinkRepository? pageWikilinkRepository` and
  `ActiveTicketViewRegistry? activeTicketViewRegistry` (the latter
  reused from the existing instance `WorkspaceShell` already constructs
  for `TicketMarkdownWatcherService`/`TicketRepairCubit` — not a new
  registry). `null` on either makes the corresponding wikilink side
  effect a no-op — existing callers/tests that don't pass them are
  unaffected.
- **`TicketsCubit.updateTicket`** — when `pageWikilinkRepository` is
  provided and the updated ticket is a `page`, additionally (a)
  reindexes the page's own outgoing wikilinks (resolved against
  `page`/`resource` candidates via the two-tier model above) and (b) —
  only when the title changed — cascades a rewrite to every referencing
  page's title-anchored occurrences, deferring via
  `activeTicketViewRegistry` where the referrer is currently open. Both
  fire-and-forget, after the primary update has already resolved; a
  failure in either doesn't affect the primary update's outcome and is
  logged rather than surfaced as a user-facing notification.
- **`TicketMarkdownReconciler`**'s successful, non-`Unparseable` apply
  path for a `page` ticket now also triggers the same reindex/cascade
  step `TicketsCubit.updateTicket` triggers, via the same shared seam
  already used for embedding-regen parity between the two paths.
- **`AppDatabase`** — schema version 11 → 12; registers
  `PageWikilinksTable`/`PageWikilinkDao`.
- **`WorkspaceShell.build`** — constructs one `DriftPageWikilinkRepository`
  and passes it, plus the existing `ActiveTicketViewRegistry` instance,
  to `TicketsCubit`; also passes the wikilink repository to
  `PageTicketProviderImpl`.

## Known gaps carried forward (supersedes `tickets.md`'s prior entry)

`tickets.md`'s existing "Inline `[[wikilink]]`-style content-reference
backlinks are out of scope" line under Documentation section's Known
gaps is removed — no longer a gap, it's what this change builds. The
following gaps replace it — substantially fewer, and narrower, than
this change's original version of this spec listed, after the
id-anchored resolution model closed most of them:

- No path-qualified disambiguation syntax (e.g. `[[Parent/Title]]`) —
  `[[TicketId]]` serves as the unambiguous form instead.
- `resource` tickets can be a wikilink **target** but not a **source** —
  they edit `description` via the plain `InlineEditableField`, not
  `MarkdownEditor`, so there's no editor surface to parse outgoing
  references from.
- Bare, hand-typed `[[Title]]` references (as opposed to the
  autocomplete-inserted `[[TicketId]]` form) still resolve
  first-match-wins when two live pages share a title, and still stop
  resolving (rather than being rewritten) if the referenced page is
  later renamed — both are accepted limitations of the low-effort,
  hand-typed path specifically, not of wikilinks generally.
- Rename-triggered rewrites of referencing pages are still best-effort
  and non-blocking, not transactional across pages (file writes and
  embedding regen aren't transactional resources to begin with) — but
  now apply only to the shrunk set of title-anchored references. A
  rewrite failure is logged, not surfaced as a user-facing notification.
- The `ActiveTicketViewRegistry`-based deferral that protects an
  open-elsewhere referencing page from a rename-triggered rewrite is
  desktop-only, matching that registry's own gating — mobile/web have
  no equivalent guard, though they also lack the separate file-watcher
  write path that made this race notable on desktop in the first place.
