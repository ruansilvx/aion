# Sdd Ticket Execution

# Proposal: sdd-ticket-execution

## What

Step 3 of `aion-arch/ideas/self-iteration-sequencing.md`'s build order —
the mechanism that lets Aion drive its own further development through
its own ticket UI. Six pieces, all additive:

1. **A universal `Ticket.complexity` field** (`small | medium | large`,
   nullable) — a real drift migration, a manual `SelectionMenu` picker in
   `CreateTicketScreen`/`TicketDetailScreen` (mirroring `TicketPriority`'s
   existing pattern), no automated estimation logic yet.
2. **A Cubit-gated `Ticket.sddStage` field** (`exploring | proposed |
   verifying | archived`, nullable, `epic`/`story` only) tracking an
   Epic's or Story's progress through the SDD cycle, with
   `TicketsCubit.advanceSddStage` enforcing the precondition for each
   transition before writing.
3. **`AutomationConfidence`** (`auto | gated | manual`) — the shared
   three-state type `project.md` §5 describes, built here for its first
   real consumer (stage-triggering), backed by one new persisted global
   setting.
4. **Stage-triggering + chat-spawning** — an "Advance to `<next stage>`"
   affordance on Epic/Story detail screens that, once its precondition is
   satisfied, creates a new `chat`-type child ticket, posts an
   auto-assembled context message into it, and calls the configured
   `AgentModelClient` to kick off that stage's conversation.
5. **Turning the existing comment thread into a live chat** — no new
   chat storage or screen. `TicketDetailScreen`'s comment thread
   (`CommentTile`, human/AI-distinguished, already rendered for every
   ticket type including `chat`) already *is* the transcript UI. The gap
   is a streaming reply loop, not a missing feature — see
   [Re-scoped from the original idea](#re-scoped-from-the-original-idea)
   below.
6. **`signal` → `epic` promotion** — a "Promote to Epic" action on
   `signal` ticket detail, linking to an existing epic or creating a new
   one, closing the gap `tickets.md`'s Known gaps section already flags.

Plus one bug fix surfaced while grounding this proposal in the current
code: `LinkedTicketsSection._typeColor` (`design_system/molecules/
linked_tickets_section.dart`) has no explicit arm for `signal`/`release`/
`chat`, so a `page` ticket's linked-signals section (gaps/open questions
linked via `relatesTo`, the mechanism this change is supposed to make
visible) would render with the wrong tint (falls into the `typeTask`
catch-all).

## Why

`provider-configuration` (step 1) and `sdd-ticket-foundation` (step 2,
the `signal`/`release` types) are both archived. This is the next and
last piece before Aion can run its own subsequent development —
including further work on itself — through its own ticket-native
workflow instead of the CLI-driven `aion-arch/.claude/skills/` process
currently used to build it.

Source idea: `aion-arch/ideas/sdd-workflow-in-ticket-system.md`,
specifically its 2026-07-21 "Follow-up decisions" section, which
resolved this phase's scope after `sdd-ticket-foundation` shipped:
signal-tracking via linked `signal` tickets, the universal `complexity`
field, the Cubit-gated SDD-stage field, and `AutomationConfidence`
(three-state) all belong here.

## Re-scoped from the original idea — what changed and why

Re-checking the idea against current code before writing this proposal
turned up one significant simplification and one deliberate narrowing:

1. **No new chat feature module, no new message storage.** The idea
   assumed "chat" needed building from scratch. It doesn't:
   `TicketDetailScreen` already renders a full comment thread for every
   ticket type — `CommentTile` already visually distinguishes
   `CommentAuthorType.human`/`.ai` (avatar, "via `<model>`" line), backed
   by `CommentsCubit`/`CommentRepository`/`TicketCommentsTable`, all
   pre-existing. A chat ticket's comment thread already *is* its
   transcript. What's actually missing is: (a) nothing today calls
   `AgentModelClient.run()` and posts the reply — sending a comment on a
   `chat` ticket is currently a dead end — and (b) no streaming
   (`CommentsCubit.addComment` posts once, then reloads; there's no
   token-by-token live update). This change adds a new `ChatCubit`
   (alongside `CommentsCubit`, not replacing it) used only when
   `ticket.type == TicketType.chat`, plus a new `CommentAuthorType.system`
   value for the auto-assembled context message a spawned chat starts
   with. This is a materially smaller build than a from-scratch chat
   module.
2. **Mid-task chat branching is deliberately out of scope this round.**
   The source idea itself flags the branch/merge UX as "unresolved and
   'fundamental,' not something settled in this session," with the
   fold-vs-spawn decision at merge time left as an undesigned user
   choice. Building an interruption/branch flow on top of an
   undesigned UX would mean guessing at product decisions the idea
   explicitly didn't make. This change ships the straight-line path only
   (trigger stage → spawn chat → chat completes → advance stage) — see
   [Out of scope](#out-of-scope).

## `AutomationConfidence` for stage-triggering — what `auto`/`gated`/`manual` actually do

`project.md` §5's watcher-era version of this pattern needed a
standalone background process to notice "precondition now met" and
react. That whole concept is dropped (see
[project.md rewrite](#projectmd-rewrite-watcher-removal) below), and
this change deliberately does not reintroduce an equivalent
always-on watcher just to serve three states. Instead, the precondition
check happens synchronously whenever an Epic/Story's detail screen loads
(`TicketsCubit.getTicketById`, which already fetches the ticket; this
change has it also fetch direct children when the type is `epic`/
`story`) — no new background subsystem:

- **`auto`** — if the precondition is already satisfied when the screen
  loads, the stage advances and the next chat spawns immediately, no tap
  required.
- **`gated`** — if satisfied, a banner appears ("Ready to advance to
  Verification") with an explicit confirm button; nothing happens until
  tapped.
- **`manual`** — if satisfied, a plain "Advance" button is shown; same
  as `gated` minus the banner framing. The distinction from `gated` is
  UI emphasis (proactive suggestion vs. quietly-available control), not
  a functional gap — both require a tap.

Not satisfied ⇒ no control shown at all, regardless of confidence level.

## Out of scope

- **Mid-task/issue chat branching** (project.md §2's Branch/Merge
  Semantics applied to chats) — undesigned UX, see above. `chat` tickets
  remain leaves; nothing in this change creates a chat-under-chat.
- **Budget gate, batch-flush gate** — no consumer exists yet for those
  `AutomationConfidence` contexts (per `providers.md`, the budget gate
  isn't even a real predictive check today). This change ships exactly
  one `AutomationConfidence` instance (SDD-stage-triggering); the type
  supports per-context values later without changing its shape.
- **`project.md`-as-Page-ticket migration** — still an open,
  undecided question in the source idea itself ("whether... agent-
  constitution content should become a page at all... not decided").
  Consistent with `sdd-ticket-foundation`'s precedent of treating
  spec-content migration as a content decision, not a code gap.
- **Repo-map-lite / embedding-based context enrichment for spawned
  chats.** A spawned chat's initial context message is parent-ticket
  fields + direct hierarchy/`relatesTo` links, assembled as plain text —
  no similarity search, no tree-sitter symbol index. Both are
  unbuilt foundational pieces (`project.md` §3) outside this change.
- **Automated ticket estimation from `complexity`/embeddings** —
  `complexity` ships as a plain user-set field (like `priority`), not
  wired into any estimation pipeline.
- **Mobile/web parity** — `ClaudeAgentSdkClient` is desktop-only; the
  spawned-chat mechanism is desktop-only by the same existing
  constraint, nothing new here.
- **Watcher-driven epic oversight** — already dropped by the source
  idea's own conclusion; this change codifies the removal in
  `project.md` but doesn't replace it with anything beyond what's
  already in scope above (the stage-specific chats are the replacement).

## project.md rewrite (watcher removal)

`project.md` §5 still describes the pre-idea two-state
`AutomationConfidence` (`auto-override`/`ask-first`) driving a standalone
watcher persona reviewing every ticket edit. The source idea concluded
this is superseded (every one of the watcher's responsibilities has a
concrete owner among stage-specific chats, Branch/Merge Semantics, and
mid-task branching) and flagged the rewrite for whenever this idea
reaches `/propose` — this proposal is that point. `tasks.md` includes an
`/apply`-time task rewriting §5's "Watcher system" subsection and the
"Shared automation-confidence pattern" subsection in `project.md` itself
(precedent: `provider-configuration`'s own status-note edits to the same
file), done inline with the rest of this change rather than as a
separate chore — reviewers should see the design decision and the doc
update together.
