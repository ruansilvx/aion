# Design: Bug ticket type

See [proposal.md](proposal.md)'s Design gate: `PENDING` — four
presentation-layer components need a Claude Design pass before `/apply`.
This file specifies the full domain/data/cubit architecture now (none of
it depends on the pending design work) plus the shape the pending
components must fill in.

## Domain layer

### `TicketType` (`domain/enums/ticket_type.dart`)

Add one new value to the enum, after `release`:

```dart
/// A defect: something existing that doesn't work as intended. Ranked
/// like [task] in the epic→story→task chain (see
/// [TicketTypeHierarchy]) — a bug is fundamentally a unit of execution,
/// with extra diagnostic fields ([Ticket.severity],
/// [Ticket.stepsToReproduce], [Ticket.expectedBehavior],
/// [Ticket.actualBehavior]) a plain [task] has no use for. Its affected
/// version/environment is expressed via a `TicketLinkType.relatesTo`
/// link to a [release] ticket, not a dedicated field — the same
/// mechanism [release] already has with [epic]/[story]/[task].
bug,
```

### `TicketTypeHierarchy` (same file)

`_rank` gets a combined case for `task`/`bug` — they share the literal
rank value, which is what makes them siblings (neither can parent the
other) without any new branch in `canParent`:

```dart
int? get _rank => switch (this) {
  TicketType.epic => 0,
  TicketType.story => 1,
  TicketType.task || TicketType.bug => 2,
  TicketType.resource ||
  TicketType.page ||
  TicketType.chat ||
  TicketType.signal ||
  TicketType.release => null,
};
```

`canParent` itself is unchanged — its generic `parentRank < childRank`
branch already produces the correct row/column for `bug` once `_rank`
reports 2 for it:

| Parent \ Child | epic | story | task | bug | chat | resource/page/signal/release |
|---|---|---|---|---|---|---|
| **epic** (0) | ✗ | ✓ | ✓ | ✓ | ✓ | ✗ |
| **story** (1) | ✗ | ✗ | ✓ | ✓ | ✓ | ✗ |
| **task** (2) | ✗ | ✗ | ✗ | ✗ | ✓ | ✗ |
| **bug** (2) | ✗ | ✗ | ✗ | ✗ | ✓ | ✗ |

(Every other row/column — `resource`/`page`/`chat`/`signal`/`release` as
parents, and their existing columns — is unaffected; `bug` is simply
never a valid child for any of them, same as `task` isn't.)

`isAlwaysRoot` needs no change — it's an explicit allow-list
(`epic`/`signal`/`release`) that `bug` was never going to match by
accident.

Add the new members used for execution parity, in the same extension:

```dart
/// The [TicketType] values whose move to [TicketStatus.inProgress]
/// triggers a real coding-execution run — see
/// `TicketsCubit._interceptTaskExecutionTrigger`. `bug` was added here
/// for full execution parity with `task`; anywhere a Story's rank-2
/// children are gathered for design-review-gate or SDD-readiness
/// purposes should use this list instead of a `task`-only literal.
static const List<TicketType> executableTypes = [
  TicketType.task,
  TicketType.bug,
];

/// Whether this type's move to [TicketStatus.inProgress] triggers
/// coding-execution. See [executableTypes].
bool get isExecutable => executableTypes.contains(this);
```

Also correct `TicketType.task`'s dartdoc, which currently reads *"task-
under-task is not permitted — see `TicketTypeHierarchy.canParent`"* to
also note bug shares its rank: append *"; a `bug` ticket occupies the
same rank and is likewise unparentable by a `task`."*

### `TicketSeverity` (new file `domain/enums/ticket_severity.dart`)

```dart
// domain/enums/ticket_severity.dart — TicketSeverity enum (domain layer).

/// The impact of a [Ticket](../entities/ticket.dart) of type
/// [TicketType.bug] — independent of [TicketPriority], which is
/// scheduling urgency, not impact. Meaningless for every other
/// [TicketType]; `null` on [Ticket.severity] means "not sized yet,"
/// mirroring [TicketComplexity]'s nullable-until-set treatment (no
/// `none` member, unlike [TicketPriority]).
enum TicketSeverity {
  /// The bug makes the product unusable or causes data loss/corruption.
  critical,

  /// The bug significantly degrades a core flow but has a workaround.
  high,

  /// The bug is a real problem but affects a non-critical flow.
  medium,

  /// The bug is cosmetic or a minor inconvenience.
  low,
}
```

### `Ticket` entity (`domain/entities/ticket.dart`)

Add four nullable fields, same treatment as `complexity`: new
constructor params, new `props` entries, new `copyWith`
`TicketFieldSetter` params (so a caller can explicitly clear one back to
`null`, same as `description`/`estimate`/`timeSpent`/`complexity`):

```dart
/// Impact of a [TicketType.bug] ticket. `null` until sized. Meaningless
/// for every other type.

/// Reproduction steps for a [TicketType.bug] ticket. `null` until set.
/// Meaningless for every other type.
final String? stepsToReproduce;

/// What should have happened, for a [TicketType.bug] ticket. `null`
/// until set. Meaningless for every other type.

/// What actually happened, for a [TicketType.bug] ticket. `null` until
/// set. Meaningless for every other type.
final String? actualBehavior;
```

`copyWith` gains `TicketFieldSetter<TicketSeverity?>? severity`,
`TicketFieldSetter<String?>? stepsToReproduce`,
`TicketFieldSetter<String?>? expectedBehavior`,
`TicketFieldSetter<String?>? actualBehavior` — same zero-arg-setter
shape `description`/`complexity` already use, same reasoning (a bare
`?? this.x` can't distinguish "not passed" from "explicitly cleared").

# Aion — `bug` Ticket Type: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Signal & Release Types Spec](./Aion%20Signal%20and%20Release%20Types%20Spec.md) (type-accent pattern), the [Create-form Parent Field Spec](./Aion%20Create%20Form%20Parent%20Field%20Spec.md) (`AnimatedSize` slide-in), and the [Ticket Detail Inline Editing Spec](./Aion%20Ticket%20Editing%20Spec.md) (inline text-field states, overlay picker). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TypeChip`, `PriorityBadge`, `AppTextField`, `AppDropdown` by name.

`TicketType.bug` ranks structurally like `task` (same epic→story→task slot) and carries **full coding-execution parity** with Task — moving a Bug to "in progress" triggers the same Aion agentic run. It adds four bug-only fields: `severity` (critical / high / medium / low), `stepsToReproduce`, `expectedBehavior`, `actualBehavior`. **No new screens or routes.** The UI lands inside two existing screens: `CreateTicketScreen` (§4) and the ticket detail screen (§5).

**No Material widgets anywhere.** Every element below is a Flutter primitive: `DecoratedBox`, `GestureDetector`, `MouseRegion`, `Focus`, `Stack`, `Column`/`Row`, `Padding`, `AnimatedSize`, `CustomPaint` (severity ▲ marker), `OverlayEntry` + `CompositedTransformTarget`/`Follower`. `TextField` (wrapped in a transparent `Material` ancestor) is the sole permitted Material exception, for text input, matching the existing `AppTextField`.

Themes: **Arctic** (light) and **Obsidian** (dark). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color is a named token that resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB.

This spec introduces **two new token groups**: one type-accent color (`typeBug`, §1) and one four-level badge scale (`AionSeverityColors`, §2). No new text, radius, or spacing tokens are required.

## 1. `typeBug` accent color

A new base type-accent added to `AionColors` alongside `typeTask` / `typeStory` / `typeEpic` / `typeResource` / `typePage` / `typeSignal` / `typeRelease` / `typeChat`. It renders through the **unchanged** `TypeChip` (base spec §2.2) and every linked-ticket-row accent, exactly like the existing eight — the only code change is one enum case in `typeColorFor` / `typeLabelFor` (§1.4). The chip fill is `typeBug.withOpacity(fillAlpha)` (Arctic `0.11` / Obsidian `0.16`), never a hardcoded ARGB.

### 1.1 Value — acid lime

| | Arctic | Obsidian |
|---|---|---|
| `typeBug` | `Color(0xFF5E8C1E)` | `Color(0xFF98D13C)` |

### 1.2 Rationale

The brief's hard constraints: **clearly distinct from `typeTask`** (Bug and Task are the two highest-volume chips and will sit adjacent on the same Board), evokes **defect / alert**, and must not collide with `danger` (reserved rose, destructive/error only) or `warning` (reserved gold).

Plotting every existing accent on the hue wheel (Arctic): `typeRelease` ~9°, `typeResource` ~22°, `warning` ~44°, `typeStory` ~163°, `typeSignal` ~187°, `typeTask` ~207°, `typeChat` ~226°, `typeEpic` ~250°, `typePage` ~317°, `danger` ~349°. The single largest open interval is **44°→163° (≈119° wide)** — the yellow-green / lime band. `typeBug` is placed at ~93° (Arctic) / ~85° (Obsidian): the palette's one genuinely unoccupied hue, mirroring how `typeSignal` claimed the open cyan gap and `typeRelease` the open red gap.

This lands well: **acid lime reads as "caution / biohazard / bug"** (the literal insect-and-toxicity association), it is ~114° from `typeTask` — the maximum available separation for the two most-adjacent chips — and it never approaches the reserved warm `danger`/`warning`/`typeRelease`/`typeResource` cluster. It is legible at full strength on the near-white Arctic `surface` (contrast comparable to `typeSignal`'s deep cyan) and vivid on the Obsidian `surface`, matching the "bright accent on dark" family (`typeStory` `#33D19B`, `typeSignal` `#34C6D6`). It sits ~60–70° off `typeStory`, and reads distinctly *yellower*, so the two greens never merge on a Board.

## 2. `SeverityBadge`

A new badge component, parallel to `PriorityBadge` (base spec §2.3), showing one of **critical / high / medium / low** severity on a Bug. It needs its own four-color scale and must be **instantly distinguishable from `PriorityBadge`** so a user scanning a Bug header never confuses "severity: critical" with "priority: critical."

**No Material.** `DecoratedBox` (fill) → `Padding` → `Row` ( `CustomPaint` ▲ marker + `SizedBox(width)` + `Text` ). The ▲ marker is a filled triangle drawn with `CustomPaint` (or a `Transform.rotate` square) — never a Material `Icon`.

### 2.1 Two-axis differentiation from `PriorityBadge`

`PriorityBadge` and `SeverityBadge` are told apart by **two independent cues**, so the distinction survives even for a color-blind or fast-scanning user:

1. **Palette gestalt.** `PriorityBadge` is a **four-hue** set (rose / amber / teal / slate — base spec §1.2). `SeverityBadge` is a **single-temperature ember ramp**: fire-red → orange → clay → ash-gray, cooling monotonically from critical to low. A polychrome pill vs. a warm gradient reads as two different scales at a glance.
2. **Leading ▲ hazard marker.** Every `SeverityBadge` carries a small filled **triangle** before its label. `PriorityBadge` has **no** leading glyph. This is the primary non-color differentiator and reinforces the "hazard / defect severity" meaning.

The two also never appear in the same slot: priority lives in the top metadata block; severity lives in the "Bug details" section (§5) and the create form's Bug block (§4).

### 2.2 `AionSeverityColors` scale

Same shape as `AionPriorityColors` — a `Bg` / `Fg` pair per level.

```dart
@immutable
class AionSeverityColors {
  final Color criticalBg, criticalFg;
  final Color highBg, highFg;
  final Color mediumBg, mediumFg;
  final Color lowBg, lowFg;
  const AionSeverityColors({
```

## 4. `CreateTicketScreen` — Bug-conditional fields block

A new field block that appears **only when the Type dropdown = "Bug."** It sits **after the existing Priority / Complexity row and before the Description field**, and slides in/out with the same `AnimatedSize` the screen already uses for its Parent field (Parent-Field spec §1.2).

### 4.1 Placement, visibility & spacing

Create-form field order, top to bottom (existing fields referenced by name):

1. Title — `AppTextField`, required.
2. Type — `AppDropdown`.
3. Parent — form-field picker (Parent-Field spec §2), when Type ∈ {task, story, bug}.
4. Priority / Complexity — row of two `AppDropdown`s.
5. **Bug block — new (§4.2 / §4.3)** — only when Type = `bug`.
6. Description — multiline `AppTextField`.

- **Gap above the block** (from the Priority/Complexity row): `AionSpacing.sp16` (16) — the same field rhythm as every other gap on the form; the block reads as "four more fields," not a separately-chromed panel (no container fill, border, or card).
- **Gap below the block** (to Description): `AionSpacing.sp16` (16).
- **Visibility animation:** wrap the block in `AnimatedSize(duration: 150ms, curve: Curves.easeOut, alignment: Alignment.topCenter)`; on Type change to/from `bug` the block's child swaps between the built subtree and a `SizedBox.shrink()`, so the form grows/collapses smoothly and Description slides down/up. Pair with an `AnimatedOpacity` (120ms) on the block content so it fades as it expands. Identical mechanism to the Parent field's Epic collapse.
- **Internal spacing between the four sub-fields:** `AionSpacing.sp16` (16), implemented as a `Column(crossAxisAlignment: start)` with `spacing: 16` — Severity → Steps to reproduce → Expected behavior → Actual behavior.
- Every sub-field is a `Column`, `crossAxisAlignment: start`, with a **label row** then the **control**, `gap: 7` between them (base create-form field grammar, Parent-Field spec §1).

### 4.2 Severity selector

An `AppDropdown`-equivalent whose selected-value visual is a `SeverityBadge` (§2). Unselected by default.

- **Label row:** `"Severity"`, `AionText.label` (Manrope 12 / w700), color `textSecondary`; trailing required marker `"*"`, `AionText.label`, color `danger` (`#CE3D54 / #F1546C`) — a Bug must have a severity to be created.

## 5. Ticket detail screen — "Bug details" section

- **Section padding:** `EdgeInsets.fromLTRB(22, 16, 22, 18)`.
- **Section eyebrow:** `"BUG DETAILS"`, `AionText.caption` (JetBrains Mono 11 / w600 / ls 1.54, uppercase), color `textMuted` — matches the `"COMMENTS · 3"` / `"DESCRIPTION"` pattern. `margin-bottom: 14` to the first row.
- **Internal field spacing:** `Column(crossAxisAlignment: start)`, `spacing: 16` — Severity row → Steps to reproduce → Expected behavior → Actual behavior.
- Each of the three text blocks carries a **field caption** above it: `AionText.caption` at field scale, color `textMuted` — `"STEPS TO REPRODUCE"`, `"EXPECTED BEHAVIOR"`, `"ACTUAL BEHAVIOR"` — with `margin-bottom: 6` to its editable body (matching the Estimate/Time-Spent field-caption treatment, Ticket-Editing §4.3). ### 5.3 Three inline-editable text blocks

`stepsToReproduce`, `expectedBehavior`, `actualBehavior` — each is an **inline-editable multiline text field** following the Description field's three states exactly (Ticket-Editing §1.1 / §1.2 / §1.4). Each sits under its field caption (§5.1).

#### 5.3.1 View — filled

- No container chrome (no fill, no border) — plain text in the layout.

Matches `AppTextField` exactly (Ticket-Editing §1.4):

| Property | Value |
|---|---|
