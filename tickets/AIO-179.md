# Design: Automatic Trash Purge on Launch

No new BLoC states, no new widgets, no new schema. This is a one-function
bootstrap wiring change on top of infrastructure that already exists in
full: `TicketRepository.purgeTrashOlderThan(Duration age)` (domain),
`DriftTicketRepository.purgeTrashOlderThan` (data, already implemented
and unit-tested), and `TrashCubit.purgeAgeThreshold` (the existing fixed
30-day `Duration` constant, already public).

## §1. Where the hook lives

`lib/main.dart` today:

```dart
void main() {
  final database = AppDatabase();
  runApp(AionApp(database: database));
}
```

`AionApp.build` separately constructs its own `DriftTicketRepository`
instance for the widget tree, inside `RepositoryProvider<TicketRepository>
(create: (_) => DriftTicketRepository(widget.database))`. That instance
isn't reachable from `main()` — there's no `BuildContext` yet at that
point, since the provider tree doesn't exist until `runApp` builds it.
So the purge call needs its own, separate, short-lived
`DriftTicketRepository`, constructed the same way
(`DriftTicketRepository(database)`, same `AppDatabase` instance), purely
to make this one call. `DriftTicketRepository` holds no mutable state of
its own beyond the `AppDatabase` reference and a `SharedPreferences`
lookup for the ticket-ID prefix (unrelated to this call), so constructing
a second instance has no behavioral difference from reusing the one
`AionApp` builds later — it's not a singleton, and both instances talk
to the same underlying `AppDatabase`/SQLite connection.

## §2. New code in `lib/main.dart`

```dart
import 'dart:async';

// ...existing imports unchanged...

/// App entry point. Opens the [AppDatabase], fires off a best-effort
/// trash purge, and runs [AionApp].
void main() {
  final database = AppDatabase();
  unawaited(_purgeOldTrashOnLaunch(database));
  runApp(AionApp(database: database));
}

/// Permanently purges trashed tickets older than
/// [TrashCubit.purgeAgeThreshold] on every cold start, so trash is
/// cleaned up even for users who never visit the Trash screen's manual
/// "Purge old" action. Fire-and-forget: [main] does not await this, so
/// it never delays first paint. Failures are swallowed — a missed purge
/// has no user-visible consequence and simply gets another chance on
/// the next launch.
Future<void> _purgeOldTrashOnLaunch(AppDatabase database) async {
  try {
    await DriftTicketRepository(
      database,
    ).purgeTrashOlderThan(TrashCubit.purgeAgeThreshold);
  } catch (_) {
    // Best-effort housekeeping — no user-facing surface for failures,
    // and this codebase has no logging infrastructure to report into.
  }
}
```

`TrashCubit` is already exported by the `tickets.dart` barrel that
`main.dart` already imports (`import
'package:aion/features/tickets/tickets.dart';`), so no new import is
needed for that reference — only `dart:async` for `unawaited`, used
here (though not enforced by any active lint in this project's
`analysis_options.yaml`) so the call reads unambiguously as deliberate
fire-and-forget rather than an accidentally-dropped `await`.

## §3. Why not thread this through `AionApp`/a widget lifecycle instead

Considered and rejected: running the purge from `_AionAppState.initState`
via `context.read<TicketRepository>()`. This doesn't actually work
cleanly — `_AionAppState` is the widget that *constructs* the
`MultiRepositoryProvider`/`RepositoryProvider<TicketRepository>` in its
own `build`, so nothing above or within its own `initState` can
`context.read` a provider it hasn't built yet. Reaching the already-
provided repository would require a *new* descendant widget purely to
host a post-frame callback, adding a widget-tree surface for zero
behavioral benefit over calling `purgeTrashOlderThan` directly from
`main()` with a fresh repository instance. `main()` is simpler, runs
strictly earlier (no frame dependency), and needs no new widget.

## §4. Why no throttling / "last run" persistence

`purgeTrashOlderThan` is already a cheap, idempotent, no-op-safe query
(returns `0` and performs one indexed-free scan over the (small,
personal-scale) trashed subset when nothing qualifies). Persisting a
"last purge timestamp" via `shared_preferences` (the project's existing
mechanism for simple primitives, already used elsewhere in
`DriftTicketRepository` for the ticket-ID prefix) to skip re-running
within, say, 24 hours would be pure premature optimization for a
personal-use app with no measured cost problem — consistent with this
project's existing stance on other by-design brute-force operations at
this scale (embedding similarity search is intentionally
brute-force-cosine "sufficient at personal scale; revisit ... only if
performance demands it"). Not adding it now.

## §5. Testing

No new automated test is added. The only new "logic" introduced is a
single wiring call from a bootstrap function to a repository method
that is already fully covered by
`test/features/tickets/data/repositories/drift_ticket_repository_test.dart`'s
existing `purgeTrashOlderThan` cases (age-cutoff filtering, cascade,
no-op-when-none-eligible). `_purgeOldTrashOnLaunch` itself is a private
top-level function in `main.dart`; this codebase has no existing
precedent for testing `main()`/bootstrap functions (no `widget_test.dart`
exists), and doing so here would mean either exposing the helper
publicly solely for testability or standing up Flutter widget-test
platform-channel scaffolding (`path_provider`, `shared_preferences`
mocks) that nothing else in the test suite currently needs — both out of
proportion to a one-call wiring change. Verified instead by a manual
launch pass (see tasks.md's Manual verification section).
