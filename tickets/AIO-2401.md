# Spec Delta: Ticket sort control and board as default view

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (31/36 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Delta against `aion-arch/specs/tickets.md`. All section references below
are to that file's existing headings, so `/archive` can merge precisely
rather than overwrite.

## ADDED

### `TicketSortField` / `TicketSortDirection` enums (new, under `## Domain (lib/features/tickets/domain/) > ### Enums`)

- **`TicketSortField`** — `relevance`, `priority`, `status`, `type`,
  `createdAt`, `updatedAt`. `priority`/`status`/`type` order by each
  enum's own declaration order (already semantically meaningful:
  `TicketPriority.critical` == 0, `TicketStatus.backlog` == 0,
  `TicketType.epic` == 0), not alphabetically. `relevance` orders by
  BM25 match score against an active search query and has no direction
  (always "best match first").
- **`TicketSortDirection`** — `ascending`, `descending`. Applies to
  every field except `relevance`.

### `TicketListSort` entity (new, under `### TicketListFilters entity`, renamed section `### TicketListFilters & TicketListSort entities`)

Immutable `Equatable` value object (`domain/entities/ticket_list_sort.dart`)
pairing a `TicketSortField` with a `TicketSortDirection`. The ticket
list's single active sort selection — one field/direction pair at a
time, not a compound/multi-key sort.

### `TicketListSortRepository` interface + `SharedPrefsTicketListSortRepository` impl (new, under `### Repository interfaces` and `### Repository implementations`)

`getSort(String projectId) → Future<TicketListSort?>` (`null` means no
explicit choice has ever been persisted for that project — distinct
from `TicketListFilters`' "empty set means no constraint" convention,
since a sort always has exactly one active field once chosen) and
`setSort(String projectId, TicketListSort sort) → Future<void>`. A
sibling of `TicketListFilterRepository`, not an extension of it — kept
independent so the existing filter contract/tests are untouched.
Implemented by `SharedPrefsTicketListSortRepository`
(`data/repositories/shared_prefs_ticket_list_sort_repository.dart`),
storing `ticket_list_sort.<projectId>.field`/`.direction` as two
project-id-scoped string keys, mirroring
`SharedPrefsTicketListFilterRepository`'s key-naming convention.

### `TicketsCubit.setSort`/`.loadPersistedSort`/`.currentSort` (new, under `### TicketsCubit / TicketsState`)

- **`currentSort`** (getter) — the sort currently in effect: the
  project's explicit override if one has been set this session (or
  restored via `loadPersistedSort`), otherwise the implicit
  query-aware default (`relevance` while a search query is active,
  `createdAt` descending otherwise — the exact ordering behavior that
  existed before this change, now expressed as a concrete value instead
  of being baked into the repository).
- **`setSort(TicketListSort sort)`** — sets the project's explicit
  override, persists it via the optional `TicketListSortRepository`/
  `projectId` constructor dependencies (no-ops the persistence half if
  either is `null`, same optional-dependency convention as
  `_persistFilters`), then re-runs `searchTickets` with the current
  query/filters unchanged so the reordered list reflects immediately.
  Once set, the override applies regardless of query state — including
  after the query is cleared — until `setSort` is called again.
- **`loadPersistedSort()`** — reads the project's persisted sort (if
  any) into the in-memory override, without emitting a state. Called
  once, before the first `searchTickets`, alongside the existing
  `loadPersistedFilters()`.

### `TicketSortPopover` widget (new, under `### Screens`)

`presentation/widgets/ticket_sort_popover.dart` — a `TicketsListScreen`
overlay control next to the existing Filters trigger, listing all six
`TicketSortField` values (including the currently active one, unlike
`SelectionMenu<T>`'s exclude-current-value convention — re-tapping the
active field is a meaningful action here). Tapping a non-active field
switches to it at that field's own sensible default direction; tapping
the already-active field flips its direction (ascending ⇄ descending;
a no-op tap for `relevance`, which has none). The `Relevance` row is
disabled whenever no search query is active. Default direction per
field: `priority`/`status`/`type` ascending (their enum declaration
order already reads naturally low-to-high in each case — most-urgent
first, workflow-start first, top-of-hierarchy first), `createdAt`/
`updatedAt` descending (newest/most-recently-touched first).

## MODIFIED

### `TicketRepository.searchTickets` (`### Repository interfaces`)

Gains a required `TicketListSort sort` parameter. Previous behavior
("Ordered by relevance when `query` is set, otherwise by creation date
descending") is now the *caller's* responsibility to express as an
explicit `TicketListSort` value (see `TicketsCubit.currentSort`'s
implicit-default computation, above) rather than being an unconditional
repository-level rule. `sort.field == TicketSortField.relevance`
against an empty/absent `query` falls back to `createdAt` descending —
there is no relevance score to order by without a query.

### `TicketDao.searchTickets` (`### DAOs`)

Both the no-query and FTS-`MATCH` branches now build their `ORDER BY`
from the passed-through `sort` instead of a hardcoded
`createdAt`-descending / `bm25`-ascending rule. `priority`/`status`/
`type` sort via a generated `CASE` expression mapping each enum value's
`.name` to its declared ordinal (SQLite has no native notion of Dart
enum order); `createdAt`/`updatedAt` sort by their own column directly;
`relevance` keeps the previous `bm25(tickets_fts) ASC` clause verbatim
in the FTS branch (and falls back to `createdAt` descending in the
no-query branch, where no FTS match score exists). Every non-relevance
ordering also appends `created_at DESC` as a secondary tiebreaker, so
same-value rows (e.g. two `critical`-priority tickets) stay stably
ordered, matching the tiebreaker `createdAt`-descending already
provided implicitly before this change.

### `TicketsListScreen` (`### Screens`)

- Default `_TicketViewMode` on open changes from `list` to `board`.
  The list/board toggle itself, and its non-persisted nature, are
  otherwise unchanged — this only changes which mode is selected
  before the user's first interaction.
- Gains a second overlay trigger next to the existing Filters trigger:
  a Sort trigger wrapping the new `TicketSortPopover` (see ADDED,
  above), showing the active field in its label (e.g. `"Sort:
  Priority"`). `_initializeAndSearch` now awaits
  `TicketsCubit.loadPersistedSort()` alongside the existing
  `loadPersistedFilters()`, before the first `searchTickets` call.

### Board view (`### Board view`)

`TicketBoardView`'s per-column ticket order was previously whatever
order the caller's `tickets` list happened to carry (implicitly
`createdAt` descending, since that was `searchTickets`' only
unfiltered-query ordering). It now reflects whichever `TicketListSort`
is currently active — Board performs no sorting of its own; it groups
an already-ordered list by `status`, so a column's row order is exactly
the list's own resolved sort, filtered to that column's status.
`TicketBoardView`/`BoardColumn`/`TicketBoardCard` themselves are
unchanged.

### Trash & bulk delete (`### Trash & bulk delete`)

`TrashCubit.load()` now sorts its computed `roots` list by the current
project's persisted `TicketListSort` (client-side, after
`getTrashedTickets()`'s existing DB-level `deletedAt`-descending fetch
and the existing roots/descendant-count reduction — see design.md §4.2
for why this stays client-side rather than becoming a DB-level `ORDER
BY` change). A persisted `relevance` selection falls back to `createdAt`
descending here, since Trash has no search query to score against.
Trash has no sort control of its own — it inherits the ticket list's
persisted selection read-only. `TicketDao.getTrashedTickets`'s own
`ORDER BY deleted_at DESC` SQL is unchanged; the client-side sort
happens after that fetch.
