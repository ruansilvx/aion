# Spec Delta: dont-spawn-new-chat-ticket-per-execution-trigger

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/README.md`, `aion-arch/specs/projects.md`, `aion-arch/specs/providers.md`, `aion-arch/specs/release.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (36/42 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

## ADDED

- **Real per-turn token usage, forwarded end to end.** `AgentDoneEvent`
  (`core/contracts/agent_model_client.dart`) gains `inputTokens`/
  `outputTokens` (`int?`). `agent_bridge/index.mjs` reads them off the
  Claude Agent SDK's own `result` message's `usage` field on its
  `{"type":"done"}` line; `ClaudeAgentSdkClient._parseLine` parses them.
  `TicketComment` gains matching `inputTokens`/`outputTokens` (`int?`,
  set only on `CommentAuthorType.ai` comments), persisted on
  `TicketCommentsTable` (new nullable columns, `AppDatabase.schemaVersion`
  6 → 7). `ChatCubit.runChatTurn` carries the terminal `AgentDoneEvent`'s
  usage onto whichever comment it persists.
- **`AgentModel.contextWindowTokens`** (`int`) — each of the three
  current values (`opus`/`sonnet`/`haiku`) gets `200000`, today's real
  Claude context window (no beta 1M-context tier support).
- **New `ExecutionContextCapRepository`** (`features/providers/domain/
  repositories/execution_context_cap_repository.dart`) +
  `SharedPrefsExecutionContextCapRepository` — persists a nullable
  token-count override for the coding-execution handoff cap; `null`
  means "use the execution-phase model's real `contextWindowTokens`."
- **Coding-execution chat reuse.** `TicketsCubit._resolveExecutionChat`
  finds a Task/Bug's existing `"Coding Execution — "`-prefixed chat (via
  new shared helper `_mostRecentExecutionChat`, extracted from
  `_executionSucceededWithPr`/`_computeExecutionFailure`'s previously
  duplicated lookup) and reuses it for every subsequent trigger — the
  first move to `inProgress`, every `retryCodingExecution` call, and
  every toggle-status-away-and-back — instead of creating a new chat
  ticket each time. A new chat is created only when the Task/Bug has no
  execution chat yet at all.
- **Context-window handoff.** Before reusing an existing execution chat,
  `_executionChatOverCap` sums that chat's comments' `inputTokens +
  outputTokens` and compares against `_effectiveExecutionContextCap`
  (the execution-phase model's real `contextWindowTokens`, or
  `ExecutionContextCapRepository`'s override when smaller and positive).
  At or above 90% (`TicketsCubit._handoffThresholdRatio`) of that cap,
  `_handoffExecutionChat` runs: one summary-only `ChatCubit.runChatTurn`
  call on the old chat (no tools, no `workingDirectory`) asks the model
  to write a handoff summary of that chat's own transcript
  (`_assembleChatTranscript`/`_assembleHandoffContext`); a new chat is
  then created, titled `"Coding Execution — <title> (continued)"` for
  the first handoff, `"... (continued N)"` (N = 2, 3, ...) for
  subsequent ones (`_executionChatTitle`/`_executionChatCount`), and
  linked back to the old chat via `TicketLinkType.relatesTo`.
  `_assembleExecutionContext` gains an optional `handoffSummary`
  parameter, prepended to the new chat's opening context comment when a
  handoff just happened. A summary-turn hard failure, or construction
  without an `AgentModelClient`/`CommentRepository`, falls back to
  reusing the old (still over-cap) chat rather than blocking the run.
- **Settings — Execution Context Cap.** New `_ExecutionContextCapSection`
  in the "MODELS" eyebrow group (below the Execution model row): a
  numeric field for the override, with helper text showing the
  effective (override-or-model-default) cap. Backed by new
  `ExecutionContextCapCubit`/`ExecutionContextCapState`
  (`load`/`setOverride`, the latter clamping to at most one below the
  execution model's real limit and at least `1`; `null`/`<= 0` clears
  the override).

## MODIFIED

- **`TicketsCubit._runCodingExecution`'s chat-acquisition step.**
  Previously: unconditionally built a fresh `Ticket`, persisted it, and
  bailed if the re-fetch returned `null`. Now: calls
  `_resolveExecutionChat(task)` (returns `(chat, handoffSummary)`),
  bails under the same condition (`chat == null`). Every other part of
  the method's implement→verify→retry→PR loop is unchanged — it already
  operates purely in terms of "the chat" and "the worktree."
- **`_assembleExecutionContext(Ticket task)`** → `_assembleExecutionContext(Ticket
  task, {String? handoffSummary})` — when `handoffSummary` is non-null,
  the opening context comment is prefixed with a "picking up from a
  prior chat" block containing that summary before the existing
  title/description/conventions/instructions content, which is
  otherwise unchanged.
- **`_executionSucceededWithPr`/`_computeExecutionFailure`** now call the
  new shared `_mostRecentExecutionChat` helper instead of each
  duplicating the same query/filter/sort inline. Behavior is unchanged —
  a `"(continued)"` handoff chat shares the `"Coding Execution — "`
  prefix and is simply created later, so it already sorts as "most
  recent" with no logic change needed at either call site.
- **`retryCodingExecution`'s dartdoc** — "re-enters the coding-execution
  flow from scratch" now describes only the worktree/branch (still fresh
  every time); the chat itself is found-or-reused-or-handed-off exactly
  like any other trigger, not recreated.
- **`TicketsCubit`'s constructor** gains an optional
  `ExecutionContextCapRepository? executionContextCapRepository`
  (default `null`, same no-op-if-absent pattern as every other optional
  dependency) — absent, `_effectiveExecutionContextCap` always resolves
  to the execution-phase model's real limit with no user override
  available; the handoff mechanism itself still functions.

## Out of scope (see proposal.md)

- Retroactive usage backfill for `TicketComment`s that predate this
  change (`inputTokens`/`outputTokens` stay `null`; a chat's running
  total only counts comments posted after upgrade).
- A predictive, pre-turn usage estimate — the cap check runs only
  between triggers, not mid-turn; a single turn can still overrun the
  cap before the next check catches it.
- Interrupting the retry-on-verify-failure loop mid-cycle for a
  handoff — the cap is checked once per `_runCodingExecution`
  invocation (once per trigger), not before each corrective turn inside
  one run's own implement/verify loop.
- User-facing surfacing of "a handoff just happened" beyond the new
  chat's own title, summary, and `relatesTo` link — no toast, no board
  indicator.
- Making the 90%-of-cap handoff threshold itself user-configurable —
  fixed as `TicketsCubit._handoffThresholdRatio`; only the cap is.
