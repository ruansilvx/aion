# Design: Decision Graph Rule Builder

## 1. Domain layer (`lib/core/automation/`)

One new flat file, following this directory's existing convention.

- **`decision_field_catalog.dart`** (new) — the field/operator
  vocabulary a rule-builder condition picks from, mirroring
  `decision_condition_catalog.dart`'s own shape:
  - `enum DecisionFieldType { integer, boolean }`.
  - `DecisionFieldSpec` (`id`, `displayName`, `type`, `contexts` — which
    `AutomationContext` values expose this field). Ships two entries:
    - `attemptField` (`id: 'attempt'`, `type: integer`,
      `contexts: [codingExecutionRetry]`) — the same
      `DecisionEvalContext.attempt` signal `attemptExceedsMax` already
      reads.
    - `sessionOverageDetectedField` (`id: 'sessionOverageDetected'`,
      `type: boolean`, `contexts: [codingExecution]`) — the same
      `DecisionEvalContext.sessionOverageDetected` signal
      `sessionOverageDetected` already reads.
  - `decisionFieldCatalog` (`List<DecisionFieldSpec>`),
    `decisionFieldsFor(AutomationContext)` — same filter shape as
    `decisionConditionsFor`.
  - `enum DecisionRuleOperator { equals, notEquals, greaterThan,
    greaterThanOrEqual, lessThan, lessThanOrEqual }`. `operatorsFor
    (DecisionFieldType type)` returns the valid subset per type:
    integer gets all six; boolean gets `[equals, notEquals]` only (a
    boolean field's "value" is `true`/`false`, picked via the same
    trigger the field/operator pickers use — no separate `isTrue`/
    `isFalse` operators, keeping the operator vocabulary one shared enum
    across both field types instead of a type-specific split).
  - `ruleBuilderConditionId` (`'ruleBuilder'`) — the reserved
    `DecisionNode.conditionId` value marking a rule-builder condition,
    never collides with a real `decisionConditionCatalog` entry (none of
    which use this id).
  - `ruleBuilderConditionSpec(AutomationContext context)` — synthesizes
    a `DecisionConditionSpec(id: ruleBuilderConditionId, displayName:
    '<localized "Custom rule">', contexts: [context], parameterSpecs:
    [])` *only if* `decisionFieldsFor(context)` is non-empty, `null`
    otherwise. This is the "Custom rule" entry `DecisionNodeForm`'s
    picker appends to `decisionConditionsFor(context)`'s list — reusing
    `_ConditionPicker`'s existing `SelectionMenu<DecisionConditionSpec>`
    mechanism unchanged; `parameterSpecs: []` means the picker's
    existing generic per-catalog-parameter loop renders nothing for it,
    matching how a flag-only condition like `sessionOverageDetected`
    already renders nothing there today.
  - `defaultRuleConditionParams(AutomationContext context)` — the
    `conditionParams` a freshly created rule-builder node seeds with:
    `{'field': <first field id for context>, 'operator':
    <first operator valid for that field's type>, 'value': <0 for
    integer, false for boolean>}`. Mirrors `defaultConditionParams`'s
    role for the fixed catalog. Returns `{}` if `decisionFieldsFor
    (context)` is empty (defensive — the picker never offers "Custom
    rule" in that case, so this is unreachable in practice).
  - `isRecognizedConditionId(String conditionId, AutomationContext
    context)` — `true` for a real `decisionConditionCatalog` entry *or*
    `conditionId == ruleBuilderConditionId`. Replaces the bare
    `decisionConditionSpecById(id) != null` check `GraphCanvas`'s layout
    currently uses to flag a node `isError` — without this, every
    rule-builder node would show as "INCOMPLETE" (§3).
  - `decisionNodeTitle(DecisionNode node)` — the node's display title:
    a catalog spec's `displayName`, or (for a rule-builder node) the
    chosen field's `displayName` (looked up in `decisionFieldCatalog`
    by `node.conditionParams['field']`), or `node.conditionId` as a
    last-resort fallback (mirrors today's `spec?.displayName ??
    node.conditionId` pattern at every call site, generalized to also
    cover the rule-builder case).
  - `decisionNodeSummary(DecisionNode node)` — the parameter-chip text:
    a catalog spec's existing `conditionParameterSummary` output, or
    (for a rule-builder node) `'<operator symbol> <value>'` (e.g. `> 3`,
    `is false`) built from `node.conditionParams`, or `null`. Both new
    functions read `node.conditionParams` defensively (missing/malformed
    keys fall back to `null`/the raw id, never throw) — same posture as
    every other lookup in this file.

No changes to `decision_condition_catalog.dart` itself — this is
additive, a new file alongside it, not a modification of the fixed
catalog's own shape.

## 2. Evaluator (`lib/core/automation/decision_graph_evaluator.dart`)

One new entry in the existing `_conditionEvaluators` registry:

```dart
'ruleBuilder': (input, params) => _evaluateRule(input, params),
```

`_evaluateRule(DecisionEvalContext input, Map<String, dynamic> params)`:
looks up `params['field']` in a new private `_fieldAccessors` map
(`Map<String, Object? Function(DecisionEvalContext)>`, one entry per
`decisionFieldCatalog` spec — `'attempt': (i) => i.attempt,
'sessionOverageDetected': (i) => i.sessionOverageDetected`), reads the
field's current value, parses `params['operator']` via
`DecisionRuleOperator.values.byName` (guarded — an unrecognized name
falls through to the same `false` default below), and compares against
`params['value']` per operator (`==`, `!=`, `>`, `>=`, `<`, `<=` — the
last four only meaningful for `num`, so a boolean field's stored
operator is always `equals`/`notEquals` by construction from the UI, but
the comparison itself doesn't assume that — it just no-ops to `false`
for a numeric operator against a non-`num` value). Any failure mode —
unknown `field`, unknown `operator`, the accessed field currently `null`
(e.g. `attempt` unset for a context that never populated it) — returns
`false`, never throws: the same "never silently block automation that
otherwise resolved to `auto`" defensive posture `evaluateDecisionGraph`
already applies to a dangling node reference.

No change to `DecisionEvalContext` itself (still exactly `attempt`/
`sessionOverageDetected`) and no change to `evaluateDecisionGraph`'s own
signature or walk logic — purely a new registry entry plus its handler
function, exactly the "catalog entry plus a matching evaluator case, no
schema change" extension path this file's own dartdoc already documents.

## 3. `DecisionNodeForm` (`lib/features/providers/presentation/widgets/decision_node_form.dart`)

- **Condition picker.** `_ConditionPicker`'s `items` becomes
  `[...decisionConditionsFor(automationContext), if
  (ruleBuilderConditionSpec(automationContext) case final spec?)
  spec]` — the synthetic "Custom rule" entry appended after the real
  catalog, offered only when the context has a non-empty field
  vocabulary. Selecting it behaves exactly like selecting any other
  `DecisionConditionSpec` in the existing picker — no change to
  `_ConditionPicker` itself.
- **Rule trio.** When `_condition?.id == ruleBuilderConditionId`,
  render three controls in place of the (empty, for this spec) generic
  parameter loop:
  1. **Field** — `SelectionMenu<DecisionFieldSpec>` over
     `decisionFieldsFor(automationContext)`, `itemLabel: (f) =>
     f.displayName`. Changing the field resets operator to the first
     one valid for the new field's type and value to that type's zero
     value (mirrors `defaultRuleConditionParams`'s seeding), since an
     operator/value chosen for one field type may not be valid for
     another.
  2. **Operator** — `SelectionMenu<DecisionRuleOperator>` over
     `operatorsFor(field.type)`, `itemLabel:` a short symbol/word map
     (`equals → "is"`, `notEquals → "is not"`, `greaterThan → ">"`,
     `greaterThanOrEqual → "≥"`, `lessThan → "<"`, `lessThanOrEqual →
     "≤"`).
  3. **Value** — for `DecisionFieldType.integer`: the existing
     `AppTextField` + `FilteringTextInputFormatter.digitsOnly` pattern
     already used for catalog integer params (reused verbatim, same
     `isError` invalid-int guard). For `DecisionFieldType.boolean`: a
     `SelectionMenu<bool>` over `[true, false]` with a "True"/"False"
     `itemLabel` — no new design-system atom, reusing the same
     `SelectionMenu` molecule the field/operator pickers use.

  All three are locally `setState`-held (mirrors `_condition`'s own
  existing pattern), assembled into `conditionParams: {'field': ...,
  'operator': ..., 'value': ...}` by `_save()` when `_condition!.id ==
  ruleBuilderConditionId`, instead of the existing
  `_paramControllers`-based assembly.
- **Chained-child creation** (`_BranchSection`'s `onChainConditionSelected`
  → the form's own `onCreateChainedChild` plumbing) already threads
  through by `conditionId` string alone — its seeding call
  (`decision_graph_editor_screen.dart`'s closure and
  `decision_outline_list.dart`'s `_createChainedChild`, see §5) needs a
  `conditionId == ruleBuilderConditionId` branch calling
  `defaultRuleConditionParams(automationContext)` instead of
  `defaultConditionParams(spec)` (which requires a real catalog `spec`
  the rule-builder doesn't have).
- **`existingChildConditionLabel`** (`chainedChildConditionLabel` in
  `decision_outline_list.dart`, §5) swaps its
  `decisionConditionSpecById(id)?.displayName ?? id` body for
  `decisionNodeTitle(child)`.

## 4. `GraphCanvas` node chrome (`decision_graph_editor_screen.dart`)

Three edits, all inside `_CanvasLayout`/`_ConditionCanvasNode` (the
private classes backing `GraphCanvas`'s node rendering for this screen —
`GraphCanvas` itself, the `design_system/molecules/` primitive, stays
untouched; it's generic over `data`, no awareness of conditions at all):

- **Layout's `isError` check** (`layout()`, ~L421): `final spec =
  decisionConditionSpecById(node.conditionId);` /
  `isError = spec == null || ...` becomes `isError =
  !isRecognizedConditionId(node.conditionId, automationContext) ||
  ...` — a rule-builder node with no `spec` (by construction — it isn't
  in the fixed catalog) must not be flagged "INCOMPLETE" just for being
  a rule.
- **Node chrome title** (~L604, L635): `spec?.displayName ??
  node.conditionId` → `decisionNodeTitle(node)`.
- **Node chrome parameter chip** (~L606-608): `spec == null ? null :
  conditionParameterSummary(spec, node.conditionParams)` →
  `decisionNodeSummary(node)`.
- **Chained-child creation closure** (~L370, `onCreateChainedChild`):
  same seeding branch as `decision_outline_list.dart`'s
  `_createChainedChild` (§3) — `conditionId == ruleBuilderConditionId`
  seeds via `defaultRuleConditionParams(automationContext)`.

## 5. `DecisionOutlineList` row chrome (`decision_outline_list.dart`)

Same three call sites, same fixes, in the list pane instead of the
canvas pane:

- `chainedChildConditionLabel` (~L53) → `decisionNodeTitle(child)`.
- `_createChainedChild` (~L210-214) → rule-builder seeding branch via
  `defaultRuleConditionParams`.
- `_NodeRowState.build`'s `spec`/`parameterSummary` (~L283-286) →
  `decisionNodeTitle(widget.node)` / `decisionNodeSummary(widget.node)`.

Both panes stay independently editable and kept in sync exactly as
today — this change only replaces *how* each resolves a node's display
title/summary, not the sync mechanism itself.

## 6. No changes

- **`decision_graph_repository.dart` / `drift_decision_graph_repository.dart`
  / `automation_decision_nodes_table.dart`** — `conditionId` (`TextColumn`)
  and `conditionParamsJson` (`TextColumn`, JSON-encoded
  `Map<String, dynamic>`) already accept `'ruleBuilder'` and a
  `{field, operator, value}` map with no schema change. `jsonEncode`/
  `jsonDecode` (already used for every other condition's params) handle
  `int`/`bool`/`String` values natively.
- **`DecisionGraphConfigCubit`** — `createNode`/`updateNode`/`deleteNode`/
  `setRoot`/the strict-tree invariant checks never inspect `conditionId`/
  `conditionParams` semantically (§ of `automation-decision-graphs/design.md`
  already noted this). Zero changes.
- **`TicketsCubit`** — every `_evaluateDecisionGraph` call site is
  already condition-agnostic; it only ever reads the returned
  `DecisionOutcome`, never a node's `conditionId`. Zero changes.
- **Localization / documentation** — new user-facing strings (the
  "Custom rule" picker label, field/operator/value control labels, the
  operator symbol/word set) go in `lib/l10n/app_en.arb`, per this
  project's localization convention; every new/modified public symbol
  gets a dartdoc, every new file gets its one-line header, in the same
  pass as the implementation (see `tasks.md`).

# Aion — Decision Graph Rule Builder: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and the [Automation Decision Graphs Spec](./Aion%20Automation%20Decision%20Graphs%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `AppDropdown`, `AppTextField`, `GhostButton`, `PrimaryButton`, and every section of the Decision Graphs spec (cited as **DG §n**) by name.

A decision node's condition can today be one of Aion's named presets (DG §0.3). This slice adds a third authoring path: a **custom rule** — a `field` + `operator` + `value` triple assembled entirely from pickers, e.g. `Attempt count > 3` or `Session budget overage detected is False`. It lives inside the existing `DecisionNodeForm` (DG §3), reuses that form's existing dropdown, text-field and chip components unchanged, and renders through the existing node card (DG §1.2) and outline row (DG §2.1).

**No new screens.** One new option in an existing menu (§2), one new field group in an existing form (§3), and two one-line rendering rules on two existing components (§4).

**No Material widgets anywhere.** Same primitive set as DG: `DecoratedBox`, `Padding`, `Row`/`Column`/`Stack`, `GestureDetector`, `MouseRegion`, `Focus`, `CustomPaint`, `OverlayEntry` + `CompositedTransformTarget`/`Follower`, `AnimatedContainer`/`AnimatedSize`. `TextField` inside a transparent `Material` ancestor remains the sole permitted exception, already wrapped by `AppTextField`. No `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `DropdownButton`, `InkWell`, `Divider`, `Icons.*`.

Themes: **Arctic** (light) and **Obsidian** (dark). Every dimension, `EdgeInsets`, radius, gap, stroke, duration and text style below is **identical** between themes; only color token values differ (§6). Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB. `fillAlpha` = `AionColors.fillAlphaArctic` `0.11` / `fillAlphaObsidian` `0.16`.

**New tokens: none.** No new colors, text styles, radii or spacing values. The one new visual affordance in this slice (the custom-rule chip variant, §4.1) is a 1px `border` hairline on an existing chip — a token already in the palette, applied where the preset chip has none.

## 1. Rule vocabulary

### 1.1 Field catalog

Each field declares a value type. The type selects the operator set (§1.2) and the value control (§3.4). Fields are grouped in the picker menu by type.

| Field id | Label | Type | Range / values | Unit suffix | Applies to |
|---|---|---|---|---|---|
| `attemptCount` | Attempt count | `int` | 1–20 | — | retry, resume |
| `estimatedCost` | Estimated cost | `int` | 1–10000 | `¢` | all |
| `filesTouched` | Files touched | `int` | 1–200 | — | completion, retry |
| `diffLines` | Diff lines | `int` | 1–10000 | `lines` | completion |
| `modelConfidence` | Model confidence | `int` | 1–99 | `%` | all |
| `ticketDepth` | Ticket depth | `int` | 1–10 | — | creation, linking |
| `elapsedMinutes` | Elapsed minutes | `int` | 1–480 | `min` | all |
| `protectedPath` | Touches protected path | `bool` | True / False | — | completion, retry |
| `outsideWorkHours` | Outside working hours | `bool` | True / False | — | all |
| `budgetOverage` | Session budget overage detected | `bool` | True / False | — | all |
| `openQuestions` | Ticket has open questions | `bool` | True / False | — | advance, linking |
| `ticketBlocked` | Ticket is blocked | `bool` | True / False | — | advance, linking |

Menu group headers: `NUMBERS`, `FLAGS` — same header treatment as DG §3.1's `THRESHOLDS` / `FLAGS`.

### 1.2 Operator catalog

Labels are deliberately short so the operator trigger never ellipsizes at its `200` width (§3.3). The symbol is what renders in the chip (§4.1) — never the label.

| Operator id | Label (trigger + menu) | Chip symbol | Valid for |
|---|---|---|---|
| `gt` | is greater than | `>` | `int` |
| `gte` | is at least | `≥` | `int` |
| `lt` | is less than | `<` | `int` |
| `lte` | is at most | `≤` | `int` |
| `eq` | equals | `=` | `int` |
| `neq` | is not | `≠` | `int` |
| `is` | is | `is` | `bool` |

Boolean fields resolve to exactly one operator (`is`). Its trigger is still rendered — never hidden — but in the **disabled** state (§3.5.6), so the three-slot rhythm of the row is stable across field types and the sentence still reads left to right.

### 1.3 Chip summary string

One function, used by the node card (§4.1) and the outline row (§4.2):

```
int  →  '${operator.symbol} ${value}${field.unitSuffix ?? ''}'   // '> 3', '≥ 25', '> 50¢'
bool →  'is ${value ? 'True' : 'False'}'                          // 'is False'
incomplete → '—'                                                  // em dash, error treatment
```

### 1.4 Changing the field

Changing the field re-validates the rest of the rule in one frame:

- Type unchanged (`int` → `int`): operator and value are **kept**; value is re-clamped to the new field's range and flagged `error` (§3.5.7) if out of range rather than silently rewritten.
- Type changed (`int` ↔ `bool`): operator resets to the new type's default (`gt` for `int`, `is` for `bool`), value resets to empty (`int`) / `True` (`bool`). The value slot cross-fades between variants over 140ms `Curves.easeOut` at a **fixed** `132×40` (§3.4) — the form never reflows.

## 3. `RuleFieldGroup` — the Field / Operator / Value trio

Mounts inside `DecisionNodeForm` (DG §3) directly below the condition picker (DG §3.1), replacing the parameter field (DG §3.2) — a custom rule never shows the preset parameter input. Both of the form's hosts render it identically: the canvas **popover mount** (376 wide, `16` padding → `344` content) and the outline **inline mount** (full width at the row indent). The only host difference is the field fill, inherited from DG §3.1: `surface` in the popover, `surfaceHover` inline.

### 3.1 Layout

Two rows, not three. At the popover's `344` content width three stacked full-width pickers push the branch selectors below the fold; the sentence also reads better broken after its subject.

```
┌ Field ─────────────────────────────────────┐   full width (344 / inline: fill)
└────────────────────────────────────────────┘
┌ Operator ──────────┐  ┌ Value ─────┐            200 + 12 gap + 132 = 344
└────────────────────┘  └────────────┘
```

| Property | Value |
|---|---|
| Root | `Column`, `crossAxisAlignment: CrossAxisAlignment.start` |
| Row 1 | Field picker, `double.infinity` width |
| Row 1 → Row 2 gap | `AionSpacing.sp12` |
| Row 2 | `Row`, `crossAxisAlignment: CrossAxisAlignment.start`; operator `Expanded` (min `176`, `200` at popover width), gap `AionSpacing.sp12`, value `SizedBox(width: 132)` |
| Label → control gap | `7` — DG §3's form constant |
| Label style | `AionText.label` (Manrope 12 w700) `textSecondary`; required marker `*` in `danger` on Field and Value, none on Operator (it always has a value) |
| Labels | `Field *` · `Operator` · `Value *` |
| Helper line | Error helper text sits under its own control only, `AionText.bodySm` `danger`, top gap `5`; it grows the row rather than overlaying, `AnimatedSize` 140ms |
| Group → next section gap | `AionSpacing.sp16` — DG §3's section gap, unchanged |
| Narrow inline mount (< `320` available) | Row 2 wraps: operator full width, value `132` on its own line below, gap `AionSpacing.sp12`. No other change. |

| Text | `AionText.bodySm` w600 `textPrimary`: `True` / `False` |
| Caret | `7×7` chevron, `1.5px` `textSecondary` |
| Menu | Width `132`, two rows of height `36`, padding `EdgeInsets.symmetric(vertical: 4)`, radius `AionRadius.lg` = `12`, 1px `borderStrong`, DG popover shadow. Rows: `True`, `False`. |
| Default value | `True` |
| No empty state | A `bool` value is never unset, so this variant has no placeholder and no error state |

#### 3.4.3 Variant transition

`AnimatedSwitcher`-equivalent built from `AnimatedOpacity` + `Stack` (no Material): outgoing control fades `1 → 0` over 100ms, incoming `0 → 1` over 140ms `Curves.easeOut`, both pinned to the `132×40` box. Focus is not moved by the swap.

### 3.5 States — every picker trigger and the integer input

Applies to §3.2, §3.3, §3.4.1 and §3.4.2 unless a row says otherwise.

#### 3.5.1 Default
Fill `surface` / `surfaceHover` per host · 1px `border` · text `textPrimary` (or `textMuted` placeholder) · caret `textSecondary` · no shadow.

#### 3.5.2 Hover
Border → 1px `borderStrong`. Fill unchanged in the inline mount; → `surfaceHover` in the popover mount. Caret → `textPrimary`. 100ms `Curves.easeOut`. Cursor `SystemMouseCursors.click` on pickers, `text` on the integer input.

#### 3.5.3 Focused (and, for pickers, open)
Border → **1.5px** `primary` · ring `BoxShadow(color: AionColors.primary.withOpacity(0.16 Arctic / 0.30 Obsidian), blurRadius: 0, spreadRadius: 3)` · caret glyph `primary` · fill unchanged. An open picker keeps this treatment for as long as its menu is mounted, and its caret rotates `0° → 180°` over 140ms `Curves.easeOut`.

#### 3.5.4 Pressed
Fill → `surfaceHover` (popover) / `border` (inline, one step darker than the field's own `surfaceHover`) · border unchanged from the current state · 80ms · no scale, no lift.

#### 3.5.5 Disabled
Fill `surfaceHover` · 1px `border` · text `textMuted` · caret `textMuted` @ `0.5` · no hover, no focus ring, not tab-reachable · cursor `basic`. Applies to the operator picker before a field is chosen and on `bool` fields (§3.3), and to every control while a graph save is in flight (DG §1.2.1 disabled).

#### 3.5.6 Disabled-resolved (operator on a `bool` field)
Identical fill/border to §3.5.5, but the label reads `is` in `textMuted` w600 rather than the placeholder, and no caret is drawn — nothing is choosable, so no affordance is offered. `Semantics(label: 'Operator, is, fixed for true or false fields')`.

#### 3.5.7 Error (integer value only)
Border → **1.5px** `danger` · ring `danger.withOpacity(0.14 Arctic / 0.26 Obsidian)` spread `3` · text `textPrimary` (the typed value stays legible; the border carries the state) · helper line below in `AionText.bodySm` `danger`, top gap `5`.

| Cause | Helper copy |
|---|---|
| Empty on save | `Enter a value` |
| Out of the field's range (§1.1) | `Enter 1–20` — the field's own bounds, formatted with an en dash |
| Field is empty (Field picker error) | 1.5px `danger` + ring on the **Field** picker, helper `Pick a field to continue` |

Error state clears on the first keystroke that produces a valid value, not on blur.

### 3.6 Save gating

`Save` (DG §3.5) is disabled — fill `primary.withOpacity(0.35)`, label `#FFFFFF` @ `0.65` — whenever the rule is incomplete: no field, or an `int` field with an empty or out-of-range value. The two branch selectors (DG §3.3 / §3.4) gate `Save` exactly as they already do; this adds one more condition to the same predicate, no new UI.

## 4. Rule-builder node identity

A rule node reads as its **field name** as title, and the operator + value as chip: `Attempt count` + `> 3`. A preset node keeps reading as its full condition name: `Attempt count exceeds` + `> 3`.

**A marker is warranted, and it is two existing elements re-toned — no new element, no new token.** Title text alone is not sufficient: `Attempt count` and `Attempt count exceeds` differ by one word at 14px, and at 40% canvas zoom or in a truncated 420px outline row that word is the first thing lost. The two markers below are each free, survive truncation, and never rely on hue.

### 4.1 Canvas node card (extends DG §1.2)

| Property | Preset node (unchanged) | Rule node |
|---|---|---|
| Eyebrow content | `IF · ATTEMPT COUNT` | `RULE · ATTEMPT COUNT` |
| Eyebrow style | `AionText.caption`, uppercase, `0.14em`, `textMuted` | **Identical** — same style, same slot, same color. Only the leading word differs. |
| Title | `AionText.cardTitle` `textPrimary`: `Attempt count exceeds` | `AionText.cardTitle` `textPrimary`: `Attempt count` |
| Chip fill | `surfaceHover` | `surfaceHover` — identical |
| Chip border | None | **1px `AionColors.border`** — the one difference |
| Chip text | `AionText.key` `textSecondary`: `> 3` | `AionText.key` `textSecondary`: `> 3` |
| Chip padding | `EdgeInsets.fromLTRB(6, 2, 6, 2)` | `EdgeInsets.fromLTRB(6, 1, 6, 1)` — 1px less vertical, so the bordered chip's outer height matches the borderless preset chip exactly and rows stay on the same baseline |
| Chip radius | `AionRadius.sm` = `6` | `AionRadius.sm` = `6` |
| Everything else | DG §1.2 | **Identical** — width `264`, padding, radius `12`, fill, border, shadow, anchor dots, and all of DG §1.2.1's states |

Error / incomplete rule node: DG §1.2.1's error state verbatim — 1.5px `danger`, ring `danger.withOpacity(0.14 / 0.26)` spread `3` — with eyebrow `RULE · INCOMPLETE` in `danger` and chip content `—`.

### 4.2 Outline row (extends DG §2.1)

The row has no eyebrow, so the chip hairline is the whole marker here — which is why it exists.

| Property | Value |
|---|---|
| Title | `AionText.cardTitle` `textPrimary`, `maxLines: 1`, ellipsis: the field name |
| Chip | §4.1's rule chip verbatim: `AionText.key` `textSecondary`, fill `surfaceHover`, **1px `border`**, radius `6`, padding `EdgeInsets.fromLTRB(6, 1, 6, 1)` |
| Everything else | DG §2.1 unchanged — height `44`, `24` indent per depth, guide rails, branch label, trailing outcome badges, and all of DG §2.1.1's states |
| Error row | DG §2.1.1 error verbatim: fill `danger.withOpacity(0.08 / 0.14)`, 2px `danger` left rail, chip content `—` |

### 4.3 What deliberately does not change

No icon prefix on the title, no accent-colored chip, no badge. A colored chip would read as a status (the outcome badges next to it are colored and semantic), and an icon prefix costs `18px` of a `264px` card and a `420px` row to say something the eyebrow already says on the canvas and the hairline already says in the list. The marker is for scannability only and is intentionally the quietest thing on the card.

## 5. Accessibility

- `Semantics` on the trio: field `'Field, Attempt count, button'`; operator `'Operator, is greater than, button'`; value `'Value, 3, editable'`. The assembled node announces as `'Rule, attempt count greater than 3, matched branch asks first, unmatched branch proceeds'` — spoken words, never symbols.
- The chip's `>` `≥` `≤` `≠` symbols are `ExcludeSemantics`d and replaced by the spoken operator label; screen readers never hear a bare glyph.
- Tab order: Field → Operator → Value → Matched → Unmatched → Delete → Cancel → Save. A disabled operator (§3.5.6) is skipped.
- Error state is never color-only: the `1.5px` border-weight change and the helper line accompany every `danger` border.
- The custom-vs-preset marker (§4) never relies on hue — one is a word, one is a border.
- The chip's `AionText.key` at 11px on `surfaceHover` is the smallest text in this slice; contrast ≥ 4.6:1 on both themes.

## 6. Theme parity

Identical across Arctic and Obsidian: every dimension, `EdgeInsets`, radius, gap, stroke width, glyph size, animation duration and curve, breakpoint, text style, and copy string. Differing: color token values, resolved by name, and the alpha pairs called out inline — focus ring `0.16 / 0.30`, danger ring `0.14 / 0.26`, `fillAlpha` `0.11 / 0.16`, disabled caret `0.5` (both), text-selection fill `0.24` (both).
