# Tasks: Define type-compatibility matrix

Ordered checklist. Every task touching a `.dart` file includes its
documentation (dartdoc + file header, where new) in the same task — not
a follow-up.

- [x] T1. In `lib/features/tickets/domain/enums/ticket_type.dart`:
  add the `TicketTypeHierarchy` extension (`_rank` getter and
  `canParent(TicketType child)` method) exactly as specified in
  `design.md`'s Domain layer section, with full dartdoc on the
  extension and both members. Correct `TicketType.task`'s existing
  dartdoc to remove the now-false "another task" half of its
  subtask-convention claim, per `specs/spec.md`'s MODIFIED entry —
  task-under-story remains true and stays in the comment.

- [x] T2. In `lib/features/tickets/presentation/cubit/tickets_cubit.dart`:
  - Add `t.type.canParent(ticket.type)` to `getValidParentCandidates`'s
    existing `.where(...)` filter. Update its dartdoc to mention the
    new type-compatibility exclusion alongside self/descendant.
  - Add the new `getValidParentCandidatesForType(TicketType childType)`
    method exactly as specified in `design.md`, with full dartdoc
    (purpose, no self/descendant exclusion since no ticket id exists
    yet, feeds `CreateTicketScreen`).
  - In `updateTicketParent`, add the type-compatibility rejection
    (fetch `candidateParent` via `_repository.getTicketById`, reject if
    null or `!candidateParent.type.canParent(ticket.type)`) after the
    existing self-parent/epic/cycle checks, before the persist call.
    Update the method's dartdoc to list this new rejection cause
    alongside the existing ones.

- [x] T3. In
  `lib/features/tickets/presentation/widgets/ticket_parent_picker.dart`:
  add the `didUpdateWidget` override to `_TicketParentPickerState` that
  re-invokes `_loadCandidates()` when `widget.ticketType` changes, per
  `design.md`. Add a one-line dartdoc comment above the override
  explaining why (candidates depend on `ticketType`, which
  `CreateTicketScreen` can change after mount).

- [x] T4. In
  `lib/features/tickets/presentation/screens/create_ticket_screen.dart`:
  - Change the type dropdown's `onChanged` to unconditionally clear
    `_selectedParentId` on every type change (replacing the current
    epic-only clear).
  - Change `TicketParentPicker`'s `candidatesLoader` from
    `() => context.read<TicketsCubit>().getAllTickets()` to
    `() => context.read<TicketsCubit>().getValidParentCandidatesForType(_selectedType)`.
  - No new public symbols introduced here, so no new dartdoc required;
    leave existing comments intact unless they now describe stale
    behavior.

- [x] T5. In `test/features/tickets/cubit/tickets_cubit_test.dart`:
  - Extend the `getValidParentCandidates` group: a candidate whose type
    cannot parent the ticket's type is excluded (e.g. a `task` ticket
    excluded from a `story`'s candidates), while a valid-type candidate
    is still included.
  - Extend the `updateTicketParent` group: reparenting under a
    type-incompatible candidate (e.g. task under task, story under
    task, resource-as-parent-of-anything) short-circuits before calling
    the repository (`verifyNever`), emits
    `TicketsError(reason: invalidParent)` then `TicketDetailLoaded`,
    mirroring the existing self-parent/cycle test pattern. A
    valid-type reparent (e.g. task under story, chat under task) still
    persists and emits the refreshed `TicketDetailLoaded`.
  - Add a new `getValidParentCandidatesForType` test group: returns
    only tickets whose type can parent the given `childType`, with no
    self/descendant exclusion applied (there is no ticket id to exclude
    by, since the ticket doesn't exist yet).

- [x] T6. Add a new test file
  `test/features/tickets/domain/ticket_type_hierarchy_test.dart`

  against the matrix in `design.md`/`specs/spec.md` — all 36
  parent/child type pairs (6×6, including same-type pairs), asserting
  each against the expected `true`/`false`. This is the rule's own
  source of truth test, independent of how the Cubit consumes it.
