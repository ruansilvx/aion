# Pluggable Provider Abstraction

# Proposal: Pluggable Provider Abstraction

## What

Generalizes Aion's model-provider layer from "one hardcoded provider,
three hardcoded models" into a real `AgentProvider` abstraction — so
adding a second provider later (or routing different tiers to different
providers simultaneously) is a matter of implementing one new class and
registering it, not touching every consumer. Concretely, this change
ships:

- **`ProviderId`** (`core/contracts/`) — the extensible provider
  identifier. One value today (`claudeAgentSdk`).
- **`ToolAccessTier`** (`core/contracts/`) — `noTools | readOnly | full`,
  a capability-declaration axis a provider states support for.
- **`AgentModelDescriptor`** (`core/contracts/`) — replaces the
  `AgentModel` enum as the provider-scoped model value object
  (`providerId`, `modelId`, `label`, `contextWindowTokens`), so a model
  is no longer implicitly "the one provider's model."
- **`ConsumptionSignal`** (`core/contracts/`) — a sealed type (
  `UsageWindowConsumption` / `CostConsumption`) that's the one generic
  "consumption" dimension every provider maps its own budget/usage
  semantics onto, replacing today's bare `VoidCallback` overage signal.
- **`AgentProvider`** (`core/contracts/`) — the abstraction itself:
  identity, display name, declared `ToolAccessTier` support, its model
  list, its `AgentModelClient`, and pure mapping functions for
  overage→`ConsumptionSignal` and raw→normalized error text.
- **`ProviderRegistry`** (`core/contracts/` interface,
  `StaticProviderRegistry` impl in `core/agent/`) — the
  provider-ID-to-`AgentProvider` lookup every consumer now goes through,
  constructed once in `main.dart` with a one-entry list
  (`ClaudeAgentSdkProvider`).
- **`ClaudeAgentSdkProvider`** (`core/agent/`) — the first (and only)
  `AgentProvider` implementation, wrapping the existing
  `ClaudeAgentSdkClient` unchanged and declaring `{noTools, full}`
  support (no `readOnly` — the bridge has no allowlist tier).
- Updated `ModelRoutingRepository`/`ModelRoutingCubit`/Settings UI to
  store and display `AgentModelDescriptor` (provider-scoped) instead of
  the flat `AgentModel` enum — the mechanism that makes per-tier
  provider assignment real, even though only one provider is registered
  today.
- Updated `ChatCubit.runChatTurn` (the single shared choke point every
  text/tool-enabled turn already goes through) and its ~14 call sites
  across `TicketsCubit`/`ChatCubit`/`InboxCubit` to resolve a model's
  provider from the registry instead of a single constructor-injected
  `AgentModelClient`, and to normalize error text and emit typed
  `ConsumptionSignal`s.
- `ModelPhase.requiredToolAccessTier` — a new getter making each
  phase's actual tool-access requirement (already true today via
  scattered `toolsEnabled: true/false` literals) into declared data,
  used to filter which providers' models a phase's dropdown may offer.

No source in `AgentRequest`/`AgentEvent` (`core/contracts/agent_model_client.dart`)
changes shape — that contract was already provider-agnostic (`model` is
a plain `String`). This change generalizes everything *above* it: which
provider a model belongs to, and how Aion picks one.

## Why

Source idea: `aion-arch/ideas/pluggable-provider-abstraction.md`
(status: `explored`). Both `per-phase-tier-based-model-routing` and
`provider-configuration` — the two already-shipped ideas this
generalizes — explicitly scoped themselves to Claude Agent SDK only and
deferred multi-provider work "to a later idea once provider coverage
improves." The user's stated intent (currently on Claude Agent SDK, may
switch or *combine* providers later, wants future integrations "almost
plug and play") is that later moment.

Two concrete forces make this worth doing now, before a second provider
exists, rather than waiting:

1. **Combining providers per tier** (Frontier on one provider, Execution
   on another) requires the *data model* — not just the UI — to know a
   model's provider. Retrofitting that onto a live `AgentModel` enum
   used by ~14 call sites across three feature cubits later is a larger,
   riskier change than building it in from the start.
2. **`provider-error-messages-leak-vendor-text.md`** (a `raw` idea) is
   resolved as a direct side effect of this change's error-normalization
   piece, rather than needing its own separate cycle.

## Scope

**In scope:**

- The eight new/changed `core/contracts/` and `core/agent/` types listed
  in What, all real and consumed today (not speculative — see Design
  rationale in `design.md` §1 for why each one has an actual call site).
- Migrating `ModelRoutingRepository` (interface + `SharedPrefsModelRoutingRepository`
  impl), `ModelRoutingCubit`, `ProviderSettingsCubit`,
  `ExecutionContextCapCubit`, and the Settings screen's model dropdowns
  from `AgentModel` to `AgentModelDescriptor`, sourced from
  `ProviderRegistry` instead of a fixed enum.
- Migrating `TicketsCubit`, `ChatCubit`, `InboxCubit` (and
  `ChatCubit.runChatTurn` itself) from a single injected
  `AgentModelClient` field to a `ProviderRegistry`, resolving the
  correct provider+client per call from the tier's (or a chat's
  inferred) `ModelPhase`.
- `main.dart`/`app_router.dart` wiring: register `ProviderRegistry`,
  remove the now-redundant standalone `AgentModelClient` registration.
- A one-time `shared_preferences` migration path for
  `ModelRoutingRepository`'s persisted keys (a phase with no
  `..._provider_id` key yet defaults to `ProviderId.claudeAgentSdk`, so
  an already-chosen model survives) — mirrors the existing
  `_legacySelectedModelKey` fallback precedent.

**Out of scope (non-goals) — and why:**

- **A second real `AgentProvider` implementation.** Per the idea's own
  conclusion — this change defines and validates the interface against
  its one existing implementation only. The idea file itself flags the
  real risk this carries: an interface shaped by a single implementation
  sometimes needs revision once a second one arrives. Accepted risk,
  revisited when Anthropic Messages API (or another provider) actually
  gets built.
- **Per-provider credential storage / enabled-disabled state.** The
  idea's brainstorm asked to "settle that shape," which this proposal
  does — in `design.md` §5 — but doesn't implement as working
  repository code. Claude Agent SDK has no credentials to store (auth
  via the user's existing Claude plan) and there is no UI reason to
  disable Aion's only provider. Building an unused
  `ProviderConfigRepository` now would be the same premature-abstraction
  risk `provider-configuration`'s own proposal.md called out for
  per-phase UI when nothing had a phase yet — no real consumer exists
  until a second provider does. `ProviderRegistry.availableProviders`'s
  construction-time list is today's de facto "which providers are
  enabled."
- **Cross-provider per-ticket/per-chat manual override.** Folded into
  the interface's *shape* (an `AgentModelDescriptor` is already
  provider-self-describing, so an override slot would just be "a
  nullable `AgentModelDescriptor` field checked before phase routing" —
  no interface redesign needed later) but not built: it needs a new
  persisted field plus a UI affordance on every ticket/chat surface, and
  with only one provider configured there's no user-visible value yet.
  Deferred to its own change once a second provider makes overriding
  meaningful.
- **A predictive budget/usage-window consent gate.** `ConsumptionSignal`
  is built and wired to the one real signal that exists today
  (`AgentOverageDetectedEvent`, reactive/after-the-fact) — see
  `design.md` §4. Nothing in the Claude Agent SDK exposes a way to query
  remaining plan-usage-window budget *proactively*, so there is no data
  source for a predictive gate to predict from yet, same reasoning
  `provider-configuration`'s proposal.md already gave for deferring
  this.
- **A real `readOnly` tool-access tier.** `ToolAccessTier` is a
  three-value enum (`design.md` §2), but `agent_bridge/index.mjs` still
  only supports zero-tools or the full set — `ClaudeAgentSdkProvider`
  honestly declares `{noTools, full}`, not all three. Building bridge
  support for an allowlisted tool tier is unrelated, larger scope
  (tracked as its own known gap in `tickets.md`).
- **Coupling `ModelPhase.requiredToolAccessTier` to `AgentRequest.toolsEnabled`.**
  Both describe the same real constraint today, by coincidence, not by
  shared derivation — see `design.md` §3's rationale for why unifying
  them now is premature.
