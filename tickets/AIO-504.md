# Design: Chat Transcript UX Redesign

## 1. Scope recap

Presentation-layer only, scoped to `TicketType.chat` rendering inside
`TicketDetailScreen`. No changes to `ChatCubit`, `ChatState`,
`CommentRepository`, `AgentModelClient`, or any domain/data-layer code.
`CommentsCubit`/`CommentTile` (the non-chat comment thread) are
untouched — a new sibling code path is added for chat, the existing
path for every other ticket type is not modified in behavior, only
relocated where noted in §4.

## 2. Current state (baseline, for contrast)

`_TicketDetailScreenState.build` renders one `Column`:

```
Column
  AppHeader
  Expanded
    Column
      Expanded(
        child: SingleChildScrollView(          <- single page-wide scroll
          ContentMaxWidth(
            Column(                             <- "metadata column"
              [header fields, SDD-stage tracker, coding execution
               section, linked-tickets picker, BacklinksSection]
              Container(border)
              Padding(                           <- chat-or-comments block
                BlocBuilder<TicketsCubit>(ticket.type == chat
                  ? BlocBuilder<ChatCubit>(ListView.builder(
                      shrinkWrap: true,
                      physics: NeverScrollableScrollPhysics(),
                      itemBuilder: (_, i) => CommentTile(comments[i]),
                    ) + _StreamingBubble if streaming)
                  : BlocBuilder<CommentsCubit>(same shrinkWrap pattern
                      with CommentTile))
              )
            )
          )
        )
      )
      Container(border)
      AnimatedSize(retry-validation banner, chat-only, gated on
        ChatCubit.state)
      ColoredBox(compose row: avatar + pill TextField + send button,
        calls _sendComment which branches ChatCubit vs CommentsCubit)
```

The transcript's `ListView` is `shrinkWrap`/non-scrollable by
construction — it has no scroll extent of its own, it just contributes
its full height to the single outer `SingleChildScrollView`. There is
no auto-scroll-to-bottom: a freshly-loaded or actively-streaming chat
leaves the viewport wherever it happened to be. `CommentTile` renders
every author type identically: avatar + name/badge row + full-width
bubble, left-aligned, `Text(comment.content)` (plain, no markdown).
`ChatState.currentToolUse` is emitted by `ChatCubit` but has no
consumer in the widget tree.

## 3. Target state

For `ticket.type == TicketType.chat` only, the layout under the header
splits into two flex regions instead of one shared scroll:

```
Column
  AppHeader
  Expanded
    Column
      Expanded(
        child: ticket.type == TicketType.chat
          ? Column(                                          <- NEW split
              children: [
                SingleChildScrollView(                        <- metadata,
                  child: ContentMaxWidth(                        intrinsic
                    child: _TicketMetadataSection(ticket)),       height,
                ),                                                not flex
                Expanded(
                  child: ChatTranscriptPane(                  <- NEW,
                    ticketId: widget.ticketId,                    flexible,
                  ),                                              owns its
                ),                                                 own scroll
              ],
            )
          : SingleChildScrollView(                            <- UNCHANGED
              child: ContentMaxWidth(                             for every
                child: Column([                                   other type
                  _TicketMetadataSection(ticket),
                  Container(border),
                  Padding(BlocBuilder<CommentsCubit>(...
                    CommentTile...)),
                ]),
              ),
            ),
      )
      Container(border)
      AnimatedSize(retry-validation banner — UNCHANGED, still only
        renders for a "Design Sync — " chat, still a sibling below the
        transcript/comment region and above the compose row)
      ticket.type == TicketType.chat
        ? ChatComposeField(...)                                <- NEW
        : <existing single-line pill compose row, UNCHANGED>
```

`_TicketMetadataSection` is the existing metadata-column content
(header fields through `BacklinksSection`) extracted verbatim into its
own private `StatelessWidget` in `ticket_detail_screen.dart` — same
convention as `_RepairBanner`/`_SddStageSection` already in that file
(see flutter-conventions.md's "small presentational pieces... in the
same file as the screen that uses them"). This is the one piece of
*existing* rendering that moves; it is not rewritten, only lifted out
so both the chat and non-chat branches can render it in their own
container without duplicating ~700 lines of layout code. It keeps
reading whatever `BuildContext`-scoped Cubits/state it already reads
today (`TicketsCubit`, `TicketLinkRepository`, etc.) — no new
constructor parameters beyond what it needs to identify the current
ticket.

The metadata column is intentionally *not* given its own `Expanded`/
independent scroll in the chat branch — it sits above the transcript
at its natural (intrinsic) height inside a non-flex
`SingleChildScrollView`, and `ChatTranscriptPane` takes whatever
vertical space remains via `Expanded`. See proposal.md's Non-goals for
why this is an accepted scope boundary, not an oversight.

## 4. New widgets

All three new widgets live in
`lib/features/tickets/presentation/widgets/` (existing folder,
alongside `ticket_link_picker.dart` etc. — the established location for
tickets-feature widgets that aren't the screen itself), each with its
own file per that folder's existing one-widget-per-file convention.

### 4.1 `ChatTranscriptPane` (`chat_transcript_pane.dart`)

```dart
class ChatTranscriptPane extends StatefulWidget {
  const ChatTranscriptPane({super.key, required this.ticketId});
  final String ticketId;
}
```

- `StatefulWidget` because it owns a `ScrollController` (disposed in
  `dispose()`) — pure view-layer state, not business logic, so it
  belongs on the widget per this project's Cubit/widget split (Cubits
  hold *domain* logic; scroll-position bookkeeping is a rendering
  concern with no meaning outside this widget's own `Element`).
- `BlocBuilder<ChatCubit, ChatState>`, exhaustively switching
  `ChatInitial` (center `AppSpinner`) / `ChatError` (message text,
  styled `c.danger`, same as today) / `ChatLoaded` (the transcript).
- `ChatLoaded` renders a real `ListView.builder` (not `shrinkWrap`),
  `controller: _scrollController`, item count =
  `comments.length + (streamingText != null || currentToolUse != null
  ? 1 : 0)`. Each `comments[i]` renders a `ChatMessageBubble`. The
  trailing synthetic item (only present while a reply is in flight)
  renders the moved-and-adapted `_StreamingBubble` (private class in
  this same file), now also showing `currentToolUse` as a status line
  above the streamed text when non-null and `streamingText` is still
  null (a tool call fired before any text chunk arrived) — once
  `streamingText` becomes non-null the accumulated text takes over the
  bubble body as before, per `ChatCubit.sendMessage`'s existing
  "carry forward" comment.
- Keeps the existing `context.l10n.ticketDetailCommentsCount(...)`
  header line, now rendered once above the `ListView.builder` inside
  the same `ChatLoaded` branch (unchanged copy/logic, just relocated
  from the old inline block into this widget).
- Auto-scroll: a `didUpdateWidget`-equivalent effect keyed off
  `ChatState` — since this is a `BlocBuilder`, the scroll trigger is a
  `BlocListener<ChatCubit, ChatState>` wrapping the `BlocBuilder` (or a
  combined `BlocConsumer`), whose `listener` calls
  `WidgetsBinding.instance.addPostFrameCallback((_) { if (!mounted)
  return; _scrollController.animateTo(_scrollController
  .position.maxScrollExtent, duration: ..., curve: ...); })` whenever
  the emitted state is `ChatLoaded` (covers: initial load, a new human
  message appended, every streaming chunk, and the settled AI reply).
  Mirrors the existing precedent of driving scroll-position side
  effects from post-frame callbacks already used elsewhere in this
  file for auto-advance (`_maybeAutoAdvanceSddStage`) and the
  stage-tracker's own scroll-into-view behavor
  (`_StageTrackerRowState`).

### 4.2 `ChatMessageBubble` (`chat_message_bubble.dart`)

```dart
class ChatMessageBubble extends StatelessWidget {
  const ChatMessageBubble({super.key, required this.comment});
  final TicketComment comment;
}
```

Adapted from `CommentTile`'s existing structure (author label row +
timestamp + bubble + "via `<model>`" caption for AI), with three
changes:

- **Alignment.** `CommentAuthorType.human` renders right-aligned: outer
  `Row(mainAxisAlignment: MainAxisAlignment.end)`, avatar after
  (visually right of) the bubble column instead of before it, author
  label row also right-aligned (`Row` reversed / `MainAxisAlignment
  .end` with the timestamp first). `ai`/`system` stay left-aligned,
  unchanged from `CommentTile` today.
- **Capped bubble width.** `CommentTile`'s bubble stretches full width
  via `Expanded`. Here the bubble column is wrapped in
  `ConstrainedBox(constraints: BoxConstraints(maxWidth: <parent
  width> * 0.78))` via `LayoutBuilder` at the top of `build`, so a
  short message doesn't stretch edge-to-edge and the left/right split
  actually reads as two-sided conversation rather than two full-width
  columns that happen to differ by an icon's position.
- **Content rendering.** `CommentAuthorType.ai` renders
  `MarkdownView(source: comment.content)` in place of `Text(comment
  .content, style: AionText.bodySm...)`. `human` and `system` keep
  plain `Text` — human input isn't markdown source, and system
  messages are short auto-generated status text with no formatting
  needs today.
- **Bubble corner/tail.** Today's asymmetric corner treatment
  (`topLeft: circular(3)`, others `AionRadius.lg` — a left-pointing
  "tail") stays for left-aligned `ai`/`system` bubbles; `human`'s
  right-aligned bubble mirrors it (`topRight: circular(3)`, others
  `AionRadius.lg`).
- Fill/border colors, the `AI`/`You`/`System` label text and badge, the
  timestamp formatting (`_formatTime`), and the "via `<model>`"
  caption are unchanged from `CommentTile` — only relocated into this
  new chat-only widget. `_Avatar` (already a standalone private class
  in `ticket_detail_screen.dart`) is reused as-is by both
  `CommentTile` (unchanged) and `ChatMessageBubble` (new) — it takes no
  chat-specific parameters, so no duplication needed there.

`CommentTile` itself is untouched — it keeps rendering every author
type uniformly left-aligned with plain text, exactly as today, for the
non-chat comment thread.

### 4.3 `ChatComposeField` (`chat_compose_field.dart`)

```dart
class ChatComposeField extends StatefulWidget {
  const ChatComposeField({
    super.key,
    required this.controller,
    required this.onSend,
  });
  final TextEditingController controller;
  final VoidCallback onSend;
}
```

- Not built on `AppTextField` — that widget's multiline mode forces a
  5-line minimum height (`minLines: isMultiline ? 5 : 1`) and an
  outlined-box shape, neither of which fits an auto-expanding compose
  bar that should start at one line. `ChatComposeField` wraps
  `TextField` directly (same pattern the existing single-line compose
  row already uses — `Material(type: MaterialType.transparency,
  child: TextField(...))`), the same sanctioned exception to the
  no-Material-widgets rule `AppTextField` relies on.
- `maxLines: null`, `minLines: 1` — grows with content. Wrapped in
  `ConstrainedBox(constraints: BoxConstraints(maxHeight: 160))` so
  growth caps out (roughly 6-7 lines at `AionText.bodySm`) and the
  `TextField` scrolls internally past that, rather than growing
  unbounded and pushing the transcript off-screen.
  Shape: `AionRadius.lg` rounded rect (not the current single-line
  compose row's `AionRadius.pill` — a pill shape reads oddly once a
  field is multiple lines tall; `AionRadius.lg` is the same radius
  token `AppTextField`'s own multiline mode already uses, so this stays
  visually consistent with the one other multiline field in the app).
  Same `c.surface` fill / `c.border` outline as the existing compose
  row.
- Enter/Shift+Enter handling: wraps the `TextField` in a `Focus`
  widget with an `onKeyEvent` handler. On a `KeyDownEvent` for
  `LogicalKeyboardKey.enter`: if `HardwareKeyboard.instance
  .isShiftPressed`, return `KeyEventResult.ignored` (lets `TextField`
  insert the newline itself); otherwise call `widget.onSend()` and
  return `KeyEventResult.handled` (suppresses the newline). This only
  affects hardware-keyboard input (desktop/web) — Flutter has no
  equivalent physical-key event stream for on-screen mobile keyboards,
  so on mobile the field's own return key inserts a newline (standard
  multiline-`TextField` behavior) and the paper-plane send button
  (unchanged, still calls `_sendComment`/`onSend`) remains the only —
  and already-expected — way to send.
- No change to the surrounding avatar-circle + send-button row layout
  (`_TicketDetailScreenState.build`'s compose `Row`) beyond swapping
  the middle `Expanded(DecoratedBox(...TextField...))` for
  `Expanded(child: ChatComposeField(controller: _commentController,
  onSend: _sendComment))` when `ticket.type == TicketType.chat`. The
  non-chat compose row (used for plain ticket comments) keeps its
  existing single-line pill `TextField` untouched.

## 5. `_sendComment` / `ChatCubit` — unchanged

`_sendComment` already branches on `_currentTicket?.type ==
TicketType.chat` to call `ChatCubit.sendMessage` vs
`CommentsCubit.addComment`, and already clears `_commentController`
after sending (needed for `ChatComposeField` to shrink back to one line
post-send — no new controller-reset logic required, `TextEditingController
.clear()` already collapses the field's content and Flutter's
`TextField` recomputes its intrinsic height from the now-empty text on
the next frame). `ChatState`'s three variants (`ChatInitial`/
`ChatLoaded`/`ChatError`) are unchanged — `ChatLoaded.currentToolUse`
already exists (added by `coding-execution-reliability-and-safety`),
this change is its first consumer.

## 6. Non-Material / token compliance

- No new Material widgets beyond the already-sanctioned `TextField` (+
  its required transparent `Material` ancestor) inside
  `ChatComposeField` — same exception `AppTextField` and the current
  compose row already use.
- All colors/radii/spacing/text styles via `AionColors`/`AionRadius`/
  `AionSpacing`/`AionText` tokens, no raw values — `ChatMessageBubble`
  and `ChatTranscriptPane` reuse the exact token references
  `CommentTile`/`_StreamingBubble` already use today.
- `MarkdownView` (reused, not modified) is already non-Material per
  its own header comment (`page-content-markdown-editor/design.md`
  §2) — pure `flutter/widgets.dart` primitives, no
  `flutter_markdown` dependency.

## 7. Testing

- `ChatTranscriptPane`'s auto-scroll behavior and `ChatMessageBubble`'s
  alignment/markdown branching are pure widget-layer rendering with no
  Cubit/domain logic changes — no new unit tests required beyond what
  `ChatCubit`/`ChatState` already have (untouched).
- `ChatComposeField`'s Enter/Shift+Enter key handling is exactly the
  kind of custom `Focus`/keyboard-event logic flagged in project.md's
  Testing section as needing a manual interactive pass (`flutter run`)
  rather than relying on `flutter analyze`/`flutter test` alone — see
  tasks.md's final verification task.

# Aion — Chat Transcript UX: Component & Screen Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, and the existing header/back-button, section-eyebrow, avatar-disc, comment-bubble, and comment-composer patterns by name. Mockups: [Aion Chat Transcript Mockups](./Aion%20Chat%20Transcript%20Mockups.dc.html).

**What's being built.** A redesign of how a **`chat`-type ticket's** conversation renders inside the existing ticket detail screen — scoped entirely to `chat` tickets; the plain comment thread on every other ticket type is unaffected and out of scope. A `chat` ticket is a live, streaming conversation between a human and an AI coding-execution agent, so it must read as a real two-sided messaging interface, not a static comment list. Four changes:

1. The message transcript becomes its **own independently-scrolling region** (`ChatTranscriptPane`, §2) beneath a compact metadata header — auto-scrolling to the newest message on load and on every streaming update — replacing today's non-scrolling list embedded in the whole page's shared scroll.
2. **Human** messages render **right-aligned**; **AI** and **system** messages render **left-aligned** (`ChatMessageBubble`, §1) — replacing today's uniformly left-aligned treatment.
3. **AI**-authored content renders as **Markdown** (headings, fenced code, inline code, lists, links, tables) inside the bubble, matching the app's existing `MarkdownView` conventions.
4. The compose field becomes an **auto-expanding multiline input** (`ChatComposeField`, §3) with Enter-to-send / Shift+Enter-for-newline, replacing today's fixed single-line pill.

No new screens — everything below replaces how the chat-only portion of the existing ticket detail screen renders.

**Hard constraint — no Material widgets or types anywhere.** Every surface is built from plain Flutter primitives: `DecoratedBox` / `Container` (non-Material) / `Padding` / `Row` / `Column` / `Stack` / `GestureDetector` / `MouseRegion` / `AnimatedContainer` / `AnimatedOpacity` / `AnimatedScale` / `CustomPaint` / `SingleChildScrollView`. The **sole** sanctioned exception is a raw `TextField` (wrapped in a transparent `Material` ancestor) for the compose input (§3). **No** `Card`, `ElevatedButton`, `Scaffold`, `ThemeData`, `ColorScheme`, `ListTile`, `AppBar`, `SnackBar`, `CircularProgressIndicator`, `DropdownButton`, `InkWell`, `Chip`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). **All** layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` with the theme's `fillAlpha` (Arctic `0.11`, Obsidian `0.16`) unless another alpha is stated.

**New tokens:** none in `AionColors` / `AionRadius`; **one** new `AionText` style (`AionText.streamStatus`, §4.1) and a small set of documented derivations that reuse existing patterns (§4). Two view-model enums carry no design tokens (§6).

## 1. `ChatMessageBubble` (new)

A single transcript message. `Column`/`Row` of primitives; no Material. Author type (`ChatAuthor`, §6) selects one of three layouts that share the same bubble geometry and avatar-disc pattern (base spec §2.6).

### 1.0 Shared geometry (all author types)

- **Bubble max-width:** `human` bubbles cap at **82%** of the transcript's available content width; `ai` / `system` cap at **88%** (their leading avatar consumes the difference, so the bubbles' right edges land at a consistent inset). Implement with `ConstrainedBox(maxWidth: paneContentWidth * fraction)` inside a `Row` whose `mainAxisAlignment` is `end` (human) or `start` (ai/system). Never full-width — the cap is what makes two-sided alignment read.
- **Bubble radius:** `16` on three corners; the **tail corner** is `5`. The tail is the corner nearest the avatar's vertical edge:
  - `human` (avatar on the right): tail = **bottom-right** → `BorderRadius.only(topLeft: 16, topRight: 16, bottomLeft: 16, bottomRight: 5)`.
  - `ai` / `system` (avatar on the left): tail = **top-left** → `BorderRadius.only(topLeft: 5, topRight: 16, bottomLeft: 16, bottomRight: 16)`.
- **Avatar disc:** `30×30` (base spec §2.6). AI = radius-`9` square, fill `primary`, glyph `sparkle` `15px` white, glow `BoxShadow(color: primary.withOpacity(isDark ? 0.60 : 0.45), blurRadius: 14)`. System = radius-`9` square, fill `surfaceHover`, 1px `border`, glyph `diamond` (`◆`) `12px` color `textSecondary`. Human = full circle, fill `secondary`, initial `"U"` `12px` w700 white.
- **Avatar↔bubble gap:** `AionSpacing.sp8 + 1 = 9`. Author-label row sits above the bubble (ai/system) or above-right of it (human); `gap: 6` between label row, bubble, and caption.
- **Inline code** (inside any bubble body): `Container`, fill `surfaceHover`, 1px `border`, radius `4`, padding `EdgeInsets.symmetric(horizontal: 5, vertical: 1)`, text mono `12 / w400` color `textPrimary`.
- Bubbles carry **no shadow** (separated by fill + border, per base spec §1.8).

### 1.1 Human message — default

Right-aligned. `Column`, `crossAxisAlignment: end`, `gap: 6`.

- **Label row** (`Row`, `gap: 8`, right-aligned, inset `padding-right: 41` to clear the avatar column): timestamp `AionText.time` `textMuted`, then author label `"You"` `AionText.cardTitle` re-sized to **12.5 / w700** color `textPrimary`. (Timestamp before name so the name sits nearest the bubble.)
- **Body row** (`Row`, `crossAxisAlignment: end`, `gap: 9`): the bubble, then the human avatar disc.
- **Bubble:** padding `EdgeInsets.symmetric(horizontal: 13, vertical: 10)`, fill `surface` (`#FBFCFE / #131A29`), 1px `borderStrong` (`#BAC8D6 / #35415C`), radius per §1.0 (tail bottom-right). Content: **plain text**, `AionText.bodySm` re-sized to **13.5 / w400 / height 1.55**, color `textPrimary`. No Markdown for human messages.

> **Fill rationale.** AI already owns the `primarySubtle` tinted bubble in this app (base spec §2.8); giving the human the neutral `surface` fill with the stronger `borderStrong` outline keeps the AI bubble the visually "active" side while still giving the right-aligned human bubble enough weight to read as its own side. Do **not** tint the human bubble `primary`.

### 1.2 AI message — default

Left-aligned. `Row`, `crossAxisAlignment: start`, `gap: 9`: AI avatar disc, then a `Column` (`crossAxisAlignment: start`, `gap: 6`).

- **Label row** (`Row`, `gap: 7`, center): author name `"Aion"` `AionText.cardTitle` re-sized to **12.5 / w700** color `primary`; **AI badge** — label `"AI"`, `AionText.prioritySm` (8.5 / w800, tracked), UPPERCASE, color `primary`, fill `primarySubtle`, padding `EdgeInsets.symmetric(horizontal: 6, vertical: 2)`, radius `4` (the existing AI-tag pattern, base spec §2.8, refreshed); timestamp `AionText.time` `textMuted`.
- **Bubble:** padding `EdgeInsets.fromLTRB(13, 11, 13, 11)`, fill `primarySubtle` (`#DBE9F7 / #241F3E`), 1px `primary.withOpacity(isDark ? 0.42 : 0.28)` = **`aiBubbleBorder(isDark)`** (existing helper, base spec §1.4), radius per §1.0 (tail top-left). Content: **Markdown** (§1.5), rendered as a `Column`, `gap: 9` between block-level nodes.
- **`via <model>` caption** (below the bubble, `gap: 6`): `"via claude-sonnet-4.6"`, `AionText.time` (mono 11 / w400), color `textMuted`, `padding-left: 2`. Omitted for system messages; omitted on the in-flight bubble until streaming completes.

### 1.3 System message — default

Left-aligned like AI, but neutral and un-badged. `Row`, `crossAxisAlignment: start`, `gap: 9`: system avatar disc, then a `Column` (`gap: 6`).

- **Label row** (`Row`, `gap: 7`, center): author label `"System"` `AionText.cardTitle` re-sized to **12.5 / w700** color `textSecondary` (not `primary` — system is neutral); timestamp `AionText.time` `textMuted`. **No AI badge, no via caption.**
- **Bubble:** padding `EdgeInsets.symmetric(horizontal: 13, vertical: 9)`, fill `surfaceHover` (`#E4EDF6 / #1C2436`), 1px `border`, radius per §1.0 (tail top-left). Content: **plain text**, `13 / height 1.5` color `textSecondary`. Inline monospace fragments (branch names, keys) use the inline-code face at color `textPrimary` (no fill needed inside the already-tinted surface — a bare mono run is enough).

### 1.4 States

Bubbles are display-only (not buttons); they expose no hover/pressed/disabled visual. The only interactive affordances are optional per-message actions (copy, retry) surfaced on long-press/hover via the app's existing context affordance — out of scope here. The in-flight bubble is a distinct **variant**, not a state, and is specified as part of `ChatTranscriptPane` in §2.3.

| Author | Alignment | Avatar | Fill | Border | Badge | Content |

## 2. `ChatTranscriptPane` (new)

The scrollable message-list container. Fills the height between `ChatMetaHeader` and `ChatComposeField`. `Column`: a pinned count header (§2.1) then the scrolling list (§2.2).

### 2.1 Count header

- **Outer:** `Padding: EdgeInsets.fromLTRB(20, 14, 20, 8)`, `flex: 0`.
- **Eyebrow:** `"MESSAGES · {n}"` (pre-uppercased; `n` = message count), `AionText.caption` (JetBrains Mono 11 / w600, tracking `1.54`), color `textMuted` (`#8496A6 / #6B7690`). Reuses the base spec's uppercase eyebrow pattern (the "COMMENTS · n" style), relabeled `MESSAGES` for the chat context.

### 2.2 Scrolling list

- **Container:** `Expanded` → `SingleChildScrollView` (own `ScrollController`), padding `EdgeInsets.fromLTRB(18, 0, 18, 8)`, `Column` of `ChatMessageBubble` (§1) separated by `gap: AionSpacing.sp16 + 2 = 18`.
- **Auto-scroll:** on first layout and on **every** streaming update (§2.3) and new message, jump/animate the controller to `maxScrollExtent` so the newest message is pinned to the bottom edge; older messages scroll off the top. (In the mockup this is simulated with `mainAxisAlignment: end` on the list so the newest bubble + compose stay visible and older content clips at the top — the real implementation scrolls a normal top-anchored list to its end.)
- No fill or border on the pane itself — the transcript sits directly on `background`.

### 2.3 In-flight / streaming variant

While an AI reply is generating, its bubble renders as a distinct **in-progress** variant of the AI bubble (§1.2) — visibly "working," not a plain AI bubble. Two sub-phases:

**(a) Tool-use, pre-text** — before any reply text has streamed, the bubble body is a single **tool-use status line** in place of body text:
- `Row`, `gap: 8`, center: a `7×7` **pulsing dot**, then the status text.
- **Pulsing dot:** circle `primary`, `AnimatedOpacity`/`AnimatedScale` loop `0.35→1.0→0.35` over `1100ms` ease-in-out (opacity + scale `0.8→1.0`).
- **Status text:** `"Running {tool}…"` in `AionText.streamStatus` (§4.1, mono 12.5) color `textSecondary`, with `{tool}` (e.g. `read_file`) colored `primary`.

**(b) Streaming text** — once text begins arriving, the tool-use line stays (or is replaced by the newest tool call) and the **accumulating Markdown** (§1.5) renders below it, ending in a **blinking caret**:
- **Caret:** an inline `2×15` bar, color `primary`, blink `1s` step-end (`ctBlink`: opaque `0–45%`, transparent `55–100%`), rendered as the last inline of the last streamed text node.

**In-progress affordance (both sub-phases):** the bubble gets an animated border glow — an overlay `1px` `primary` border at `inset: -1` on the same radius, opacity looping `0.35→0.85→0.35` over `1600ms` ease-in-out (`ctPulseGlow`), layered over the static `aiBubbleBorder`. `pointerEvents: none`. The `via <model>` caption (§1.2) is **hidden** until the reply completes, at which point the bubble drops the glow/caret and becomes a normal AI bubble.

### 2.4 Empty state

A freshly-spawned chat ticket with no messages. Centered in the list body: `Column`, `mainAxisAlignment: center`, `gap: AionSpacing.sp12`, `crossAxisAlignment: center`.
- **Glyph:** `sparkle` faction motif (filled), `40px`, color `primary.withOpacity(0.5)` (matches the app's other empty states, base spec §1.9 / Overrides §2.6).
- **Title:** `"No messages yet"`, `AionText.cardTitle`, color `textSecondary`.
- **Caption:** `"Send the first message to start the run."`, `AionText.bodySm`, color `textMuted`, `TextAlign.center`, max-width `260`.

### 2.5 Loading state

Existing `AppSpinner` (no new spec). Placement: centered in the list body via `Center` — `22×22`, a `2.5px` ring of `textMuted.withOpacity(0.25)` with a `primary` top arc, `800ms` linear spin. No surrounding chrome.

### 2.6 Error state

Existing `danger`-colored message row (no new spec). Placement: a full-width row inside the list body (or pinned above the compose field when a send fails): `Row`, `gap: 9`, center; fill `danger.withOpacity(isDark ? 0.16 : 0.10)`, 1px `danger.withOpacity(isDark ? 0.34 : 0.24)`, radius `AionRadius.md` (10), padding `EdgeInsets.symmetric(horizontal: 12, vertical: 10)`; leading `7×7` dot `danger`; text `"Couldn't reach the agent. Tap to retry."` `13.5 / height 1.4` color `danger`. `GestureDetector` → retry.

The mockup shows the disabled variant for completeness; ship the always-enabled behavior unless product says otherwise.

## 8. Collapsing header (chat-only) — post-design-sync amendment

Resolves the `ChatMetaHeader` (§0.1) scope question raised during
`/design-sync`: rather than replacing the full ticket-metadata content
(title/status, parent picker, estimate/time-spent, linked-design chip,
linked tickets, backlinks) with the compact `ChatMetaHeader`, **both
are kept** — the full content is what's shown when the transcript is
scrolled to the top, and it collapses into `ChatMetaHeader` as the user
scrolls down into the message list, re-expanding on scrolling back up.
Nothing from `TicketMetadataSection`'s existing content is dropped;
it's reachable the same way it always was, just collapsible now for a
`chat` ticket specifically. This section is written by the implementing
agent (not part of the original Claude Design export) to specify the
mechanics precisely enough for `/apply` — the visual content of both
the expanded and collapsed states is unchanged from §0.1/§1
respectively.

### 8.1 Why a `CustomScrollView`, not two independently-scrolling regions

§3's original two-region split (a non-flex `SingleChildScrollView` for
metadata above an `Expanded` `ChatTranscriptPane` with its own
`ScrollController`) is **superseded** by this section for `chat`
tickets — those were two separate scroll gestures; a scroll-driven
collapse needs **one** continuous scroll region so the same gesture
that scrolls the message list also drives the header's collapse
progress. The idiomatic non-Material way to pin a header that shrinks
as its sliver's `shrinkOffset` grows, while the content below it keeps
scrolling underneath, is `CustomScrollView` + `SliverPersistentHeader`
(`pinned: true`) + `SliverList` — both are plain
`flutter/widgets.dart`/`flutter/rendering.dart` primitives, not
Material (same "primitive, not Material" analysis as `ListView`
itself). No new package dependency.

### 8.2 Structure

```
ChatTranscriptPane                          <- now owns everything below
  CustomScrollView(controller: _scrollController)
    SliverPersistentHeader(               <- §8.3, replaces the old
      pinned: true,                          non-flex SingleChildScrollView
      delegate: _CollapsingChatHeaderDelegate(
        ticket: ticket,
      ),
    )
    SliverPadding(
      padding: EdgeInsets.fromLTRB(18, 14, 18, 8),
      sliver: SliverList.builder(          <- was a plain ListView.builder
        itemCount: comments.length + (in-flight ? 1 : 0),
        itemBuilder: ... ChatMessageBubble / streaming bubble ...,
      ),
    )
```

`ChatTranscriptPane`'s constructor grows from `{ticketId}` to
`{ticketId, ticket}` — it needs the full `Ticket`, not just its id, to
render both header states without an extra `BlocBuilder<TicketsCubit>`
round-trip of its own (the caller already has `ticket` from its own
`TicketDetailLoaded` state — see §8.5).

### 8.3 `_CollapsingChatHeaderDelegate`

A private class in `chat_transcript_pane.dart` implementing
`SliverPersistentHeaderDelegate`:

- `maxExtent`: the natural height of `TicketMetadataSection`'s content
  for the given `ticket` (a `LayoutBuilder`/`GlobalKey`-measured
  intrinsic height, computed once per `ticket` — same measurement
  approach `AnimatedSize` already uses elsewhere in this screen for
  variable-height content, e.g. the retry-validation banner).
- `minExtent`: `ChatMetaHeader`'s fixed height — the nav row + title
  block per §0.1, measured the same way (or hardcoded once §0.1's
  exact padding/line-heights are implemented, whichever the
  implementer finds more robust against text-scale/localization
  length changes — either is acceptable, just document the choice at
  the call site).
- `build(context, shrinkOffset, overlapsContent)`: computes `progress =
  (shrinkOffset / (maxExtent - minExtent)).clamp(0.0, 1.0)`, then
  renders `Stack` with two children cross-faded by `progress` —
  `Opacity(opacity: 1 - progress, child: TicketMetadataSection(ticket:
  ticket))` and `Opacity(opacity: progress, child: ChatMetaHeader(
  ticket: ticket, onBack: ...))` — both `IgnorePointer`-guarded by
  their own opacity being `0` so a fully-transparent state isn't still
  tappable underneath the other. No `AnimationController` needed —
  purely driven by `shrinkOffset`, matching this project's existing
  preference for scroll-position-driven effects over animation-timer
  ones (design.md §4.1's rationale for why `ChatTranscriptPane`'s
  original auto-scroll was post-frame-callback-driven, not a
  controller).
- `shouldRebuild`: `true` whenever `ticket` changes (identity or
  `updatedAt`).

### 8.4 `TicketMetadataSection` becomes a shared, file-level widget

T1 originally planned `_TicketMetadataSection` as a **private** class
inside `ticket_detail_screen.dart`. Since `_CollapsingChatHeaderDelegate`
(in `chat_transcript_pane.dart`) now also needs to render it, it moves
to its own public widget file —
`features/tickets/presentation/widgets/ticket_metadata_section.dart`,
`TicketMetadataSection extends StatelessWidget` — following the exact
"existing folder, one-widget-per-file" convention already used for
`ChatMessageBubble`/`ChatTranscriptPane`/`ChatComposeField` in this
same change, rather than staying inline in the screen file. Its
content, internal layout, and the fact that it reads
`TicketsCubit`/`TicketLinkRepository`/etc. via `BuildContext` (no new
constructor parameters beyond `ticket`) are **unchanged** from T1's
original plan — only its file location and visibility change.

### 8.5 `ChatTranscriptPane`'s new `ticket` parameter

Since `ChatTranscriptPane` now renders `TicketMetadataSection`/
`ChatMetaHeader` inside its collapsing header, its caller
(`_TicketDetailScreenState.build`'s chat branch, §5/T5) passes the
already-resolved `Ticket` from its own `TicketDetailLoaded` state:
`ChatTranscriptPane(ticketId: widget.ticketId, ticket: ticketsState.ticket)`.

### 8.6 Screen layout — supersedes §3/§5's two-region split for chat

For a `chat`-type ticket, the middle `Expanded` region is now a single
child, not a `Column` of two:

```
Expanded(
  child: ticket.type == TicketType.chat
    ? ChatTranscriptPane(ticketId: widget.ticketId, ticket: ticket)
    : SingleChildScrollView(...unchanged non-chat layout...),
)
```

The non-flex `SingleChildScrollView` wrapping `TicketMetadataSection`
that §3/T5 originally planned as a sibling above `ChatTranscriptPane`
is removed for the chat branch — `TicketMetadataSection` now renders
*inside* `ChatTranscriptPane`'s collapsing header sliver instead. The
retry-validation banner and `ChatComposeField` stay exactly where §3/§5
put them: siblings below this `Expanded`, unaffected by this section.

### 8.7 States

| Scroll position | Header | Message list |
|---|---|---|
| At top (`shrinkOffset == 0`) | `TicketMetadataSection`, full content, opacity 1 | scrolls normally beneath |
| Mid-collapse | both cross-fading by `progress` | scrolls normally |
| Fully collapsed (`shrinkOffset >= maxExtent - minExtent`) | `ChatMetaHeader` only, pinned, opacity 1 | scrolls normally underneath the pinned header |
| Freshly-loaded chat, content shorter than viewport | header stays fully expanded (nothing to collapse — `shrinkOffset` never leaves `0`) | no scrollbar needed |
| Auto-scroll-to-bottom (new message / streaming chunk) | collapses immediately to match the new `shrinkOffset` (no separate animation — same `animateTo(maxScrollExtent)` call as before, §2.2, now also passing through the header's `shrinkOffset` range) | scrolls to newest message, same as before |

### 8.8 Testing note

`_CollapsingChatHeaderDelegate`'s `shrinkOffset`-driven cross-fade is
pure widget-layer rendering with no Cubit/domain logic — no new unit
tests required. It's exactly the kind of custom `Sliver`/scroll-offset
behavior that needs the manual interactive pass already planned in
`tasks.md`'s final verification task — extend that pass to also cover:
scrolling down collapses the header smoothly into `ChatMetaHeader`;
scrolling back up re-expands it; `TicketMetadataSection`'s parent
picker/estimate/time-spent/linked-tickets/backlinks remain fully
interactive while expanded; the compact header's back button stays
functional while collapsed.

label row (author name `"Aion"` `primary`, `"AI"` badge, timestamp) are
**unchanged from §1.2**. What changes is the content container:

- **No fill, no border, no bubble radius, no tail.** Drop the
  `DecoratedBox` entirely — `MarkdownView` content renders directly
  against `background`, the same surface the rest of the transcript
  sits on.
- **Width stays capped** at **88%** of the pane's available content
  width via the same `ConstrainedBox` mechanism as §1.0 — flat does not
  mean unconstrained; a capped measure keeps long paragraphs readable
  and keeps the AI side visually distinct from a full-width block.
- **Padding:** no bubble insets — content starts flush with the label
  row's left edge, `padding-top: 2` between the label row and the first
  block node (was implicit inside the old bubble's top padding),
  `padding-bottom: 0` (the `via <model>` caption below supplies its own
  gap, §1.2, unchanged).
- **`via <model>` caption:** unchanged from §1.2 — position, style,
  omission rules.
- Markdown node treatments (§1.5 — headings, fenced code, inline code,
  lists, blockquote, table) are unchanged in their own styling values;
  code blocks and tables already carry their own `surfaceHover`
  containers independent of the outer bubble, so they read identically
  well on a flat background.

### 9.2 System message — subtle centered divider (supersedes §1.3's bubble)

No longer a message row at all — no avatar, no bubble, not
left-aligned as if it were a peer of the human/AI turns. Renders as a
compact, centered divider that visually recedes from the actual
conversation:

- **Row:** `Row`, `mainAxisAlignment: center`, `gap: 6`.
  - Leading glyph: `diamond` (`◆`), `10px`, color `textMuted`.
  - Label: the system text (e.g. `"Switched to branch main"`),
    `AionText.caption` re-sized to **12 / w500** (sentence case, not
    the tracked-uppercase eyebrow weight `caption` normally carries —
    this is a one-off note, not a section label), color `textMuted`,
    `TextAlign.center`, single line, ellipsis if it exceeds 80% of the
    pane's content width.
  - Optional trailing timestamp on the same row: a small `·` separator
    (`textMuted`) then `AionText.time`, color `textMuted`.
- **Vertical padding:** none of its own — `_SystemMessage` carries no
  internal padding, same as `_HumanMessage`/`_AiMessage`; the gap comes
  entirely from `ChatMessageBubble`'s single outer wrapper, which uses
  `AionSpacing.sp8` (not the `sp16` every other message type gets) for
  the system case specifically. (`/verify` caught a first pass that
  stacked an internal `sp8` padding *on top of* the unchanged outer
  `sp16`, netting `24px` around a system divider — heavier than the
  `16px` inter-message gap, the opposite of "tighter." Fixed by
  removing the internal padding and reducing the outer wrapper's own
  value instead, so the system divider now gets a `8px` trailing gap —
  half the normal `16px` — reading as a light separator, not a peer
  message.)
- Inline monospace fragments (branch names, keys) inside the label use
  the §1.0 inline-code chip, sized down to `11px`, still centered
  within the row.
- **No badge, no avatar, no `via` caption, no Markdown** — system
  content stays plain text per §1.3's original decision; only the
  container changes from bubble to divider.

### 9.3 In-flight variant — drop the border glow (supersedes §2.3's glow)

§2.3(a)'s pulsing dot (pre-text tool-use status) and §2.3(b)'s blinking
caret (streaming text) are **unchanged** — both are independent of the
bubble shape. What's removed: the animated `1px` `primary` border-glow
overlay (`ctPulseGlow`) — there is no bubble edge left to glow around.
While streaming, the in-flight AI content renders with §9.1's flat
treatment (no fill/border); the pulsing dot and blinking caret remain
the sole "in progress" signals. The `via <model>` caption stays hidden
until the reply completes, unchanged from §1.2/§2.3.

### 9.4 Tokens

No new tokens. Reuses `c.textMuted`, `c.primary`, `AionText.caption`/

existing use — the Markdown blockquote's left accent bar, §1.5 — that

away, since that bubble no longer exists.
