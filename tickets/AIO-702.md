# Delegated Skill Provider Portability

# Proposal: Delegated-Skill Provider-Discovery Capability

Originates from
`aion-arch/ideas/delegated-skill-provider-portability.md`.

## Why

`SkillAttachmentKind.delegatedSkill` sends the literal prompt
`/<skillName>` (`TicketsCubit._promptFor`), tool-enabled, entirely
dependent on the resolved provider's underlying agent discovering
`.claude/skills/<skillName>` on disk itself — Aion's own code never
reads or interprets that file. Today this works only because
`ClaudeAgentSdkProvider` genuinely wraps a Claude Code CLI-style bridge
that does that discovery.

Nothing in the `AgentProvider` contract captures this requirement.
`_fireSkillAttachment` resolves its provider via
`_resolveModelAndProvider(ModelPhase.execution)` — the exact same call
every plain coding-execution run already uses
(`TicketsCubit._runCodingExecution`'s implement/verify turns). The
existing `ModelPhaseToolAccess`/`ModelRoutingCubit` filter only checks
"does this provider support `ToolAccessTier.full`" — true of both
today's coding-execution runs and `delegatedSkill` runs alike — not
"can this provider discover `.claude/skills/*` files," a strictly
narrower requirement that only `delegatedSkill` has. A hypothetical
future full-tool-access provider that isn't a Claude-Code-CLI wrapper
(e.g. a direct HTTP-based coding-agent provider) would pass that filter
today and be silently offered for `delegatedSkill`, then fail or
no-op at runtime with no signal pointing at why.

Confirmed via code as a real, pre-existing gap
(`aion-arch/ideas/delegated-skill-provider-portability.md`), independent
of `aion-arch`'s own fate, and explicitly flagged to close before
`decommission-aion-arch-cli-workflow`'s migration proceeds (that
migration's execution likely leans on `delegatedSkill`-style
mechanisms).

`AgentProvider` already has a direct precedent for this exact shape of
fix: `supportsSessionResume` is a per-provider capability `bool`,
declared once per implementation and consulted at its one call site
(`TicketsCubit`'s `agentJudgment` resolution) — never folded into
`ModelPhaseToolAccess`/`ModelRoutingCubit`'s Settings-dropdown
filtering, precisely because that filtering is phase-wide (shared with
call sites that don't need the capability) while the capability itself
is call-site-specific.

## What

- A new `AgentProvider.supportsSkillDiscovery` (`bool`) capability
  declaration — `true` on `ClaudeAgentSdkProvider` (it genuinely wraps
  a `.claude/skills/`-discovering CLI bridge), `false` on
  `AnthropicMessagesApiProvider` (stateless HTTP, no filesystem-based
  skill discovery of any kind, and already excluded from
  `ModelPhase.execution` entirely via `supportedToolAccessTiers`).
- `TicketsCubit._fireSkillAttachment` checks
  `provider.supportsSkillDiscovery` immediately after resolving the
  provider for a `delegatedSkill` attachment (never for
  `aionNativeTemplate`, which has no such dependency) and throws a
  descriptive `StateError` if it's `false` — caught by the method's
  existing `catch` block, which already posts a `"Skill attachment
  failed: <e>"` `CommentAuthorType.system` comment. No new failure
  path is invented; an already-correctly-excluded provider
  (`AnthropicMessagesApiProvider`) can't reach this branch today, so
  this is a defensive, forward-looking guard against a provider that
  doesn't exist yet, not a fix for a currently-reachable bug.
- No change to `ModelPhaseToolAccess`, `ModelRoutingCubit`, or the
  Settings "MODELS" dropdown — `ModelPhase.execution`'s model list stays
  shared between plain coding-execution and `delegatedSkill` runs,
  since ordinary coding execution has no skill-discovery dependency and
  must not be narrowed by one.

## Non-goals

- **Making `delegatedSkill` genuinely provider-portable.** This change
  makes the gap fail loud and safe instead of silently misbehaving; it
  does not make `delegatedSkill` attachments actually *work* under a
  non-CLI-bridge provider. That would require Aion's own code to read
  `.claude/skills/<name>/SKILL.md` off disk and inject its content into
  the prompt directly (closer to how `aionNativeTemplate` already
  works) — a materially larger change (path resolution, and skills can
  carry more than a markdown body: supporting files, frontmatter-gated
  tool permissions) that isn't justified today, since zero shipped
  providers are affected by the gap this closes. Left as a follow-up
  idea, gated on an actual second full-tool-access provider existing.
- **Gating the Settings "MODELS" dropdown by skill-discovery support.**
  Deliberately not done — see Why above; `ModelPhase.execution`'s
  dropdown must keep offering every full-tool provider, since plain
  coding execution has no skill-discovery dependency.
- **Restricting `AnthropicMessagesApiProvider` further.** It's already
  fully excluded from `ModelPhase.execution` (and therefore
  `delegatedSkill`) via `supportedToolAccessTiers: {noTools}` — this
  change adds an explicit, honest `supportsSkillDiscovery: false`
  declaration to it for completeness and future-proofing, not because
  it changes that provider's reachable behavior today.
- **Retroactively touching `decommission-aion-arch-cli-workflow`.**
  That idea remains a separate, unstarted cycle; this change only
  removes the gap it flagged as a blocker.
