# Design: project-type-aware-conventions-and-verification

## 0. Shape of the change (revised)

The first draft's `ProcessVerifier`/`Project.verifyCommand` line of work
is dropped entirely — no replacement shell-command-running class, no new
`Project`/`RegistryDatabase` fields, no new `NewProjectScreen` fields.
`FlutterVerifier` is deleted outright (§6) and nothing takes its place as
a thing Aion's own Dart code invokes. Verification becomes a model turn
instead (§5), reusing the `skills/verify` baseline asset this change is
already writing generic content for (§1).

What survives unchanged from the first draft: the generic skill baseline
itself (§1, except `skills/verify.md`'s content requirement — see
below), `ProjectStackDetector` (§2, now serving only `BaselineTailoringService`),
`BaselineTailoringService` (§3), `BaselineRepository`'s three new
read/write methods (§4 — now doing double duty as the mechanism
`TicketsCubit` uses to resolve effective prompt content, not just the
override editor's read path), and the override-authoring UI (§7).

## 1. Generic skill baseline (`assets/baseline/0.3.0/`)

New `assets/baseline/0.3.0/manifest.json`, structurally identical to
`0.2.0`'s (same 13 skill keys + `config/model-config`) except:
- Every `bundledPath` re-pointed to `0.3.0/...`.
- `conventions/flutter-conventions` renamed to `conventions/
  architecture-conventions` (no Dart code references this key string
  directly — it's resolved generically via `BaselineAsset.key` — so the
  rename is isolated to this manifest).

`assets/baseline/0.3.0/model_config.json` — byte-identical copy of
`0.2.0`'s (already stack-agnostic: "no provider is pre-configured").

`assets/baseline/0.3.0/skills/*.md` (13 files) — each replaces its
`0.2.0` pointer-to-`aion-arch` content with short, self-contained,
stack-agnostic content for the generic `explore → propose → apply →
verify → archive` cycle. **Two different shapes, by design:**

- **12 files** (`explore.md`, `propose.md`, `apply.md`, `archive.md`,
  `brainstorm.md`, `capture.md`, `clean-up.md`, `design-brief.md`,
  `design-sync.md`, `handoff.md`, `what-next.md`, `ticket-lint.md`) stay
  **descriptive orientation content** — 15–30 lines describing what that
  stage represents, what it reads/produces, and how it fits the cycle —
  exactly as the first draft planned. Nothing in this change reads them
  into a model prompt (see proposal.md's Out of scope); they exist for a
  human (or a future feature) to read directly.
- **`verify.md` is different: it must be genuinely operative
  instructions**, not descriptive text, because §5 below feeds it
  directly into a real coding-execution verify turn as the model's
  operating instructions. Its content:

  ```markdown
  # Verify

  You are verifying a change that was just implemented and committed in
  this worktree. Do not trust that the implementation is correct just
  because it compiled or the model said it was done — check it for real.

  1. Review the diff against the task it was implementing (visible
     earlier in this conversation) — does it actually do what was asked,
     completely, without leaving anything half-finished?
  2. Run whatever build, lint, type-check, and test commands are
     appropriate for this codebase. Check `Project conventions` above
     (if present) for a suggested command; if none is given, infer one
     from the project's own config files (`package.json` scripts,
     `Makefile`, `pubspec.yaml`, `Cargo.toml`, etc.) or run what you'd
     normally run for this kind of project.
  3. If everything is clean, end your reply with exactly one line:
     "VERIFICATION: PASSED".
  4. If anything is broken, incomplete, or wrong, end your reply with
     exactly one line: "VERIFICATION: FAILED — <a short reason>". Do not
     fix it yourself in this turn — just report it; you'll get a
     follow-up turn to fix it if needed.

  Always end with exactly one of those two lines, verbatim, as the very
  last line of your reply — Aion parses it mechanically to decide
  whether to open a pull request.
  ```

  This is a template a project's own `skills/verify` override can
  replace or extend (e.g. "always also run `cargo clippy -- -D
  warnings`") via the override-authoring UI (§7) — the whole point of
  making this asset editable.

`assets/baseline/0.3.0/architecture_convention.md` — replaces the old
"pointer" doc with an honest generic placeholder:
```markdown
# Architecture conventions

No project-specific conventions are configured yet. This project's
[BaselineTailoringService](TODO) will populate a starting point once
its stack is detected; edit this file's project override (Settings →
Overrides) to add your own conventions, formatting rules, and
architectural constraints.
```

`BundledBaselineRepository._bundledVersions` gains `'0.3.0'` (appended
last — `getAvailableBaselineVersions().last` already resolves the
newest, no other change needed for it to become every new project's
default).

## 2. `ProjectStackDetector`

Unchanged from the first draft, except it now feeds only
`BaselineTailoringService` (§3) — `NewProjectScreen` no longer consumes
it. `DetectedStack`'s fields are renamed to avoid the exact naming
collision this revision exists to fix: `verifyCommand` → `checkCommand`,
since this is a *suggestion written into guidance text*, not a value
Aion runs or that means "the verify step" — "check" is honest about it
being a build/lint/test hint, nothing more.

```dart
// core/build/project_stack_detector.dart — ProjectStackDetector (core layer).

/// A stack detected by [ProjectStackDetector.detect] — a display name
/// plus a suggested setup/check command, written as guidance text into
/// a project's `conventions/architecture-conventions` override by
/// [BaselineTailoringService]. Purely informational: nothing in Aion's
/// own Dart code runs [checkCommand] — it's read by the model during a
/// coding-execution implement/verify turn (see `tickets_cubit.dart`
/// §5), the same way any other line of `Project conventions` is.
class DetectedStack {
  const DetectedStack({
    required this.language,
    this.setupCommand,
    required this.checkCommand,
  });
  final String language;
  final String? setupCommand;
  final String checkCommand;
}

/// Lightweight marker-file detection — no dependency parsing, just
/// "does this file exist at the project root." Order matters only in
/// that the first match wins; today's marker set doesn't overlap.
class ProjectStackDetector {
  static const _markers = <String, DetectedStack>{
    'pubspec.yaml': DetectedStack(
      language: 'Flutter/Dart',
      setupCommand: 'flutter pub get',
      checkCommand: 'flutter analyze',
    ),
    'package.json': DetectedStack(
      language: 'Node.js',
      setupCommand: 'npm install',
      checkCommand: 'npm test',
    ),
    'Cargo.toml': DetectedStack(
      language: 'Rust',
      checkCommand: 'cargo check',
    ),
    'go.mod': DetectedStack(
      language: 'Go',
      checkCommand: 'go build ./...',
    ),
    'pyproject.toml': DetectedStack(
      language: 'Python',
      setupCommand: 'pip install -e .',
      checkCommand: 'pytest',
    ),
    'requirements.txt': DetectedStack(
      language: 'Python',
      setupCommand: 'pip install -r requirements.txt',
      checkCommand: 'pytest',
    ),
  };

  /// Returns the first detected stack for [rootPath], or `null` if no
  /// known marker file exists — [BaselineTailoringService] simply
  /// writes no override in that case (§3), leaving the generic
  /// placeholder content in place for the model to reason from directly.
  DetectedStack? detect(String rootPath) {
    for (final entry in _markers.entries) {
      if (File('$rootPath${Platform.pathSeparator}${entry.key}')
          .existsSync()) {
        return entry.value;
      }
    }
    return null;
  }
}
```

## 3. `BaselineTailoringService`

Unchanged in shape from the first draft; only the written content's
wording changes (guidance, not a command Aion enforces):

```dart
// features/projects/data/services/baseline_tailoring_service.dart

/// Writes a project's initial baseline overrides at creation time,
/// scoped for now to the architecture-convention asset populated from
/// [ProjectStackDetector]'s marker-file detection (the "shallow" path —
/// see `aion-arch/ideas/project-type-aware-conventions-and-
/// verification.md`). The "full agentic" path (tied to
/// `new-project-onboarding`'s not-yet-built codebase-summarization
/// depth choice) is out of scope for this change; this method's shape
/// (project id + root path in, overrides written as a side effect) is
/// designed to be called again later by that feature with richer input,
/// not to be the only caller forever.
class BaselineTailoringService {
  BaselineTailoringService(this._baselineRepository, this._detector);
  final BaselineRepository _baselineRepository;
  final ProjectStackDetector _detector;

  /// No-ops if [ProjectStackDetector.detect] finds nothing (an
  /// undetected stack has no sensible content to template).
  Future<void> tailorForDetectedStack({
    required String projectId,
    required String rootPath,
  }) async {
    final detected = _detector.detect(rootPath);
    if (detected == null) return;

    const asset = BaselineAsset(
      key: 'conventions/architecture-conventions',
      kind: BaselineAssetKind.architectureConvention,
      bundledPath:
          'assets/baseline/0.3.0/architecture_convention.md',
    );
    final content =
        '# Architecture conventions\n\n'
        'Detected stack: ${detected.language}.\n\n'
        'Suggested build/verification command: `${detected.checkCommand}`'
        '${detected.setupCommand != null ? ' (after `${detected.setupCommand}`)' : ''}.\n\n'
        'Add your own conventions, formatting rules, and architectural '
        'constraints below.';

    await _baselineRepository.writeOverride(
      projectId: projectId,
      asset: asset,
      content: content,
    );
  }
}
```

`CreateProjectCubit` gains this as a new constructor dependency and
calls `tailorForDetectedStack` after `_initializeDesktopProject`
succeeds (desktop only, `rootPath != null`) — no other change to
`CreateProjectCubit.submit`'s signature; the first draft's
`verifyCommand`/`verifySetupCommand` params and the `emptyVerifyCommand`
failure reason are dropped entirely:

```dart
if (isDesktop && rootPath != null) {
  await _initializeDesktopProject(rootPath, resolvedVersion);
  await _baselineTailoringService.tailorForDetectedStack(
    projectId: id,
    rootPath: rootPath,
  );
}
```

`NewProjectScreen` is **unchanged** by this proposal — no new fields, no
new controllers, no new l10n keys. `ProjectStackDetector` is invoked
only from `CreateProjectCubit`'s side effect, not from the screen.

## 4. `BaselineRepository` additions (read/write)

Unchanged from the first draft — these three methods now serve two
callers instead of one: the override editor (§7) and `TicketsCubit`'s
effective-content resolver (§5).

```dart
abstract interface class BaselineRepository {
  // ...existing three methods (getAvailableBaselineVersions, getManifest,
  // readOverrides) unchanged...

  /// Returns [asset]'s bundled default content (from the app's asset
  /// bundle).
  Future<String> readBundledContent(BaselineAsset asset);

  /// Returns the content of an override file at [overridePath]
  /// ([ProjectOverride.overridePath]).
  Future<String> readOverrideContent(String overridePath);

  /// Creates or overwrites [projectId]'s override for [asset], writing
  /// [content] to `<rootPath>/.aion/overrides/<lastKeySegment>.<ext>` —
  /// same flat-filename convention `readOverrides`'s
  /// `_assetKeyFromFileName` already reads back. No-ops silently if the
  /// project has no `rootPath` (mobile/web).
  Future<void> writeOverride({
    required String projectId,
    required BaselineAsset asset,
    required String content,
  });
}
```

`BundledBaselineRepository` implementation:
```dart
@override
Future<String> readBundledContent(BaselineAsset asset) =>
    _bundle.loadString(asset.bundledPath);

@override
Future<String> readOverrideContent(String overridePath) =>
    File(overridePath).readAsString();

@override
Future<void> writeOverride({
  required String projectId,
  required BaselineAsset asset,
  required String content,
}) async {
  final project = await _projectRepository.getProject(projectId);
  final rootPath = project?.rootPath;
  if (rootPath == null) return;

  final overridesDir = Directory(
    '$rootPath${Platform.pathSeparator}.aion${Platform.pathSeparator}overrides',
  )..createSync(recursive: true);
  final keySegment = asset.key.split('/').last;
  final ext = asset.bundledPath.split('.').last;
  final file = File(
    '${overridesDir.path}${Platform.pathSeparator}$keySegment.$ext',
  );
  await file.writeAsString(content);
}
```

Remove the interface's class-level dartdoc's stale "out of scope for
this change, see multi-project-hub/proposal.md" note about
override-authoring UI — no longer true after this change (§7).

## 5. `TicketsCubit` — agentic verify turn (replaces the `FlutterVerifier` gate)

This is the actual fix for Gap 1 (proposal.md), replacing what the first
draft called `ProcessVerifier`.

### 5.1 Constructor changes

Drop `FlutterVerifier? flutterVerifier`. Add three new optional
constructor params, following the exact same optional-dependency
pattern as `projectRootPath` (`null` no-ops `_runCodingExecution`
entirely, same guard shape):

```dart
BaselineRepository? baselineRepository,
String? projectId,
String? baselineVersion,
```

with matching `late final` private fields (`_baselineRepository`,
`_projectId`, `_baselineVersion`), replacing `_flutterVerifier`.
`GitRepositoryClient`/`GitHubCliClient` are unchanged — the worktree/
push/PR mechanics don't change, only what decides pass/fail.

`_maxAnalyzeRetries` is renamed `_maxVerifyRetries` (same value, `2`,
same purpose — no longer analyze-specific).

### 5.2 `_effectiveAssetContent` — the new resolver

A small private helper, local to `TicketsCubit`, that resolves one
baseline asset's effective content (override if present, else bundled
default) — the mechanism proposal.md's "Why" section refers to as
narrowly scoped, not a general prompt-assembly system:

```dart
/// Resolves the effective content for baseline asset [assetKey] in the
/// active project — its local [ProjectOverride] content if one exists,
/// otherwise the bundled default for the project's pinned
/// [_baselineVersion]. Returns `null` if any of [_baselineRepository]/
/// [_projectId]/[_baselineVersion] is unset, or if [assetKey] isn't
/// present in the pinned manifest at all (e.g. a project pinned to
/// `0.1.0`/`0.2.0`, which predate the `conventions/
/// architecture-conventions` key — see `specs/spec.md`'s Non-goals).
/// Callers treat a `null` return as "no guidance available," not an
/// error.
Future<String?> _effectiveAssetContent(String assetKey) async {
  final baselineRepo = _baselineRepository;
  final projectId = _projectId;
  final baselineVersion = _baselineVersion;
  if (baselineRepo == null || projectId == null || baselineVersion == null) {
    return null;
  }

  final manifest = await baselineRepo.getManifest(baselineVersion);
  BaselineAsset? asset;
  for (final candidate in manifest.assets) {
    if (candidate.key == assetKey) {
      asset = candidate;
      break;
    }
  }
  if (asset == null) return null;

  final overrides = await baselineRepo.readOverrides(projectId);
  for (final override in overrides) {
    if (override.assetKey == assetKey) {
      return baselineRepo.readOverrideContent(override.overridePath);
    }
  }
  return baselineRepo.readBundledContent(asset);
}
```

### 5.3 `_assembleExecutionContext` — now reads `conventions/architecture-conventions`

Becomes `Future<String>` (was synchronous). Same title/description
opening and same closing `"IMPLEMENTATION: DONE"` instruction as today,
with a new middle section and one added sentence about environment
setup (replacing the mechanical `flutterVerifier.pubGet` call this
change removes — see §5.5):

```dart
Future<String> _assembleExecutionContext(Ticket task) async {
  final buffer = StringBuffer()..writeln('# ${task.title}');
  final description = task.description;
  if (description != null && description.isNotEmpty) {
    buffer
      ..writeln()
      ..writeln(description);
  }

  final conventions = await _effectiveAssetContent(
    'conventions/architecture-conventions',
  );
  if (conventions != null && conventions.isNotEmpty) {
    buffer
      ..writeln()
      ..writeln('## Project conventions')
      ..writeln()
      ..writeln(conventions);
  }

  buffer
    ..writeln()
    ..writeln(
      'If this worktree needs dependencies installed or a build step '
      'run before you can work effectively, do that first (see any '
      'suggested command in Project conventions above). Then implement '
      'this Task using the available file, git, and bash tools, and '
      'commit your changes (git add + git commit). Do not push or open '
      'a pull request — Aion verifies and does that itself once you\'re '
      'done. End your reply with exactly one line: '
      '"IMPLEMENTATION: DONE".',
    );
  return buffer.toString().trim();
}
```

### 5.4 `_assembleVerificationContext` — new, reads `skills/verify`

```dart
/// Assembles the verify-turn prompt run immediately after a successful
/// implement turn (see [_runCodingExecution] §5.5) — the project's
/// effective `skills/verify` content (§5.2), which is written as
/// operative instructions (see `assets/baseline/0.3.0/skills/
/// verify.md`), plus a one-line reminder of what's being verified. Runs
/// in the same chat/worktree as the implement turn, so the model still
/// has the diff it just produced in context; this reminder is cheap
/// insurance against that continuity, not a full re-statement of the
/// task.
Future<String> _assembleVerificationContext(Ticket task) async {
  final verifySkill = await _effectiveAssetContent('skills/verify');
  final buffer = StringBuffer();
  if (verifySkill != null && verifySkill.isNotEmpty) {
    buffer
      ..writeln(verifySkill)
      ..writeln();
  }
  buffer.writeln(
    'Verify the change you just implemented and committed for '
    '"${task.title}", following the instructions above.',
  );
  return buffer.toString().trim();
}
```

### 5.5 `_runCodingExecution` — restructured loop

The `try` block drops the mechanical setup call entirely (no
`flutterVerifier.pubGet` and no replacement — the model installs its
own dependencies as its first action if the implement-turn prompt's new
sentence, §5.3, applies):

```dart
await gitClient.createWorktree(rootPath, worktreePath, branchName);

var prompt = await _assembleExecutionContext(task);
await commentRepo.addComment(/* unchanged system comment */);

var attempt = 0;
var verified = false;
while (true) {
  final implementSucceeded = await ChatCubit.runChatTurn(
    /* unchanged params: client, commentRepo, chatTicketId, model,
       toolsEnabled: true, workingDirectory: worktreePath, onChunk,
       onToolUse, onOverageDetected */
    prompt: prompt,
  );
  if (!implementSucceeded) break; // hard error — runChatTurn already
                                   // posted "Execution failed: ..."

  final verifyPrompt = await _assembleVerificationContext(task);
  final verifySucceeded = await ChatCubit.runChatTurn(
    /* same params, new prompt */
    prompt: verifyPrompt,
  );
  if (!verifySucceeded) break; // hard error during the verify turn
                                // itself — same as above

  final verifyReply = await _lastCommentContent(persistedChat.id);
  final failureReason = _verificationFailureReason(verifyReply);
  if (failureReason == null) {
    verified = true;
    break;
  }

  attempt += 1;
  final retryConfidence = await _effectiveCodingExecutionRetryConfidence(
    automationRepo,
    attempt,
  );
  if (retryConfidence == AutomationConfidence.auto) {
    prompt = _assembleCorrectiveContext(failureReason);
    continue;
  }

  await commentRepo.addComment(
    TicketComment(
      id: '',
      ticketId: persistedChat.id,
      content: 'Execution failed verification:\n\n$failureReason',
      authorType: CommentAuthorType.system,
      createdAt: DateTime.now(),
    ),
  );
  if (retryConfidence == AutomationConfidence.gated) {
    emit(const TicketsError('',
        reason: TicketsErrorReason.executionVerificationFailed));
  }
  break;
}

if (verified) {
  // unchanged: push, open PR, post "EXECUTION: PR_OPENED <url>"
}
```

Everything below `if (verified)` (push/PR/comment), the outer
`catch`/`finally` (worktree cleanup), and the post-run completion-flip
logic (`_executionSucceededWithPr`, `AutomationContext.codingExecution`)
are **unchanged**.

### 5.6 New helpers: `_lastCommentContent` and `_verificationFailureReason`

```dart
/// Returns [chatTicketId]'s most recently created comment's raw
/// content, or `null` if it has none. Used by [_runCodingExecution]
/// (§5.5) to read back the verify turn's own reply — mirrors
/// [_executionSucceededWithPr]'s existing "find the most recent
/// comment" lookup, simplified since the caller already has the chat's
/// id directly rather than needing to look it up from a Task id.
Future<String?> _lastCommentContent(String chatTicketId) async {
  final commentRepo = _commentRepository;
  if (commentRepo == null) return null;
  final comments = await commentRepo.getCommentsForTicket(chatTicketId);
  if (comments.isEmpty) return null;
  final mostRecent = comments.reduce(
    (a, b) => a.createdAt.isAfter(b.createdAt) ? a : b,
  );
  return mostRecent.content;
}

/// Parses a verify turn's reply ([reply], from [_lastCommentContent])
/// for its terminal `VERIFICATION:` line. Returns `null` **only** when
/// [reply] contains the literal `VERIFICATION: PASSED` line — an
/// explicit `VERIFICATION: FAILED — <reason>` line returns that reason;
/// anything else (a missing terminal line, or a `null` reply) fails
/// closed, returning a generic reason. This "fail closed" behavior is
/// what preserves `coding-execution-reliability-and-safety`'s actual
/// safety property (proposal.md's "Why") — a run must never open a PR
/// on an ambiguous or missing verification result, even though pass/
/// fail is no longer determined by an exit code.
String? _verificationFailureReason(String? reply) {
  if (reply == null) {
    return 'The verification turn produced no reply.';
  }
  if (reply.contains('VERIFICATION: PASSED')) return null;
  final match = RegExp(
    r'VERIFICATION:\s*FAILED\s*(?:—|-)?\s*(.*)',
  ).firstMatch(reply);
  final reason = match?.group(1)?.trim();
  if (reason != null && reason.isNotEmpty) return reason;
  return reply.length > 500 ? '${reply.substring(0, 500)}...' : reply;
}
```

### 5.7 `_assembleCorrectiveContext` — now takes a reason string

```dart
/// Assembles the corrective-turn prompt fed back to the model when
/// [_verificationFailureReason] reports a failure and the effective
/// `AutomationContext.codingExecutionRetry` confidence is
/// [AutomationConfidence.auto] — the verify turn's own failure [reason],
/// plus a repeat of [_assembleExecutionContext]'s commit +
/// `IMPLEMENTATION: DONE` completion-signal instruction.
String _assembleCorrectiveContext(String reason) {
  return 'Verification reported:\n\n'
      '$reason\n\n'
      'Fix these issues and commit your changes (git add + git '
      'commit), then end your reply with exactly one line: '
      '"IMPLEMENTATION: DONE".';
}
```

# Aion — Skill/Convention Overrides: Component & Screen Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md) and reuses the Settings surface established by the [Coding-Execution Reliability Spec](./Aion%20Coding%20Execution%20Reliability%20Spec.md) (its third `_AutomationSection` instance and the shared `AUTOMATION` eyebrow). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `SettingsScreen`, and the existing header/back-button, section-eyebrow, `AppButton`, and text-field patterns by name.

**What's being built.** Aion's baseline skill/convention bundle has been generalized to a stack-agnostic set (backend/data-layer work, not covered here). The one user-facing surface this change adds is an **Overrides** area, reached from Settings, where a user browses every baseline skill/convention asset for the active project and edits a plain-text **local override** for any one of them — including their own project's `skills/verify` content. This spec covers the three surfaces:

- **`OverridesSection`** — a new eyebrow-labeled section on the existing `SettingsScreen` (§1).
- **`OverridesListScreen`** — a new full screen listing every baseline asset with an "Overridden" indicator (§2).
- **`OverrideEditorScreen`** — a new full screen: a full-bleed plain-text editor for one asset's override, with a save action (§3).

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (non-Material) / `Padding` / `Row` / `Column` / `GestureDetector` / `MouseRegion` / `AnimatedScale` / `AnimatedOpacity` / `RotationTransition` / `SingleChildScrollView` / `TextField` (the raw widget, wrapped in Aion's own decoration) / `EditableText` / `CustomPaint`. **No** `Card`, `ElevatedButton`, `TextButton`, `OutlinedButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `LinearProgressIndicator`, `InkWell`, `DropdownButton`, `Chip`, or `Divider`.

Themes: **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold). All layout, dimensions, spacing, radius, and typography are **identical** between themes; only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Concrete hex is given as `Arctic / Obsidian` for reference only — implement against the token, never the literal. Translucent fills are always `token.withOpacity(x)` with the theme's `fillAlpha` (Arctic `0.11`, Obsidian `0.16`) unless another alpha is stated, exposed at the call site as `ThemeScope.of(context).fillAlpha`.

**New tokens: none.** No new `AionColors`, `AionText`, or `AionRadius` members, and no new derived helpers. Every color is an existing token or a documented derivation reusing an existing pattern; the two info-notice fills reuse the existing `noticeFill(isDark)` / `noticeBorder(isDark)` and the AI-tone `primarySubtle` + `aiBubbleBorder(isDark)` helpers already on `AionColorsHubTokens`. One structural addition: two view-model enums (`OverrideKind`, `OverrideEditorMode`) carry no design tokens (§5).

## 0. Navigation & information model

```
SettingsScreen
  └─ OverridesSection (§1)  ── "Manage Overrides" ──▶  OverridesListScreen (§2)
                                                          └─ tap a row ──▶ OverrideEditorScreen (§3)
                                                                             └─ back ◀── / Save ──▶ back to list
```

- An **asset** is one baseline skill or convention file, identified by a **key** — a path-like string, `skills/verify`, `conventions/architecture-conventions`. Two **kinds**: `OverrideKind.skill` and `OverrideKind.convention` (§5).
- An asset is **overridden** when the project has a saved local override string for it; otherwise the baseline default is in effect. The list marks overridden assets; the editor distinguishes "editing your override" from "editing the default — save to create one."
- The baseline always seeds a non-empty asset set, so `OverridesListScreen` is never truly empty; a defensive empty state is specified in §2.6 for completeness only.

Phone canvas `380×812`, status bar `46px` — identical to the base spec's screen layouts (§3 of the base spec).

### 3.3 `_OverrideTextEditor`

A full-bleed **plain** multi-line text editor — a raw `TextField` / `EditableText` wrapped in Aion's existing text-field decoration (base spec §2.5). **Not** a rich Markdown split-view or preview editor: the override content is edited as raw text, exactly as it is stored and sent to the model.

**Monospace decision.** The editor text is **monospace** — `JetBrains Mono`, **13 / w400**, line-height `1.6`, color `textPrimary` (`#142230 / #E7EDF7`). Override content is Markdown that routinely carries fenced code, inline `commands`, and indented lists; a proportional face misaligns those and makes the fenced blocks read as prose. Mono keeps columns honest, matches the app's existing code/terminal wells (Reliability spec §1.4), and signals "this is source you are editing," not a formatted document. Placeholder (empty override): `"Start typing to override the default…"`, same face, color `textMuted`.

- **Outer:** `Padding: EdgeInsets.fromLTRB(20, 0, 20, 12)`, then the field fills the remaining column height (`Expanded`).

- **Scroll:** the `TextField` is `maxLines: null`, `expands: true`, `textAlignVertical: top`, `keyboardType: multiline`, wrapped so its own `scrollController` scrolls content within the fixed container; the container never grows.
- **Selection / cursor:** `cursorColor: primary`; selection highlight `primary.withOpacity(isDark ? 0.30 : 0.16)`.

### 6.1 Token usage recap

- **Colors (all existing):** `background`, `surface`, `surfaceHover`, `primary`, `primaryHover`, `primarySubtle`, `secondary`, `danger`, `border`, `borderStrong`, `textPrimary`, `textSecondary`, `textMuted`.
- **Derived / translucent (all existing patterns):** `aiBubbleBorder(isDark)` = `primary @ 0.28/0.42` (chip + status-A border, editor focus/selection at `0.16/0.30`); `noticeFill(isDark)` / `noticeBorder(isDark)` (status-B); focus rings `token.withOpacity(0.16/0.30)`; Save glow `primary.withOpacity(0.45/0.60)` (blur 18, spread −9); overlay/hover shades via `Color.lerp` or the named hover tokens. Never hardcoded ARGB.
- **Typography (all existing):** `caption`, `h2`, `bodySm` (+`copyWith` 12.5 for descriptor/status), `button` (+`copyWith` 12.5 for the Reset ghost), `chip`, `breadcrumb`, `time`, `key` (+`copyWith` 13 list / 16 editor title / 13 editor body — mono).
- **Radius (all existing):** `lg` (12, list container + editor), `md` (10, buttons + status bar), `iconBtn` (11, back button), `iconBtnSm` (8, kind well), `5` (chip), `BoxShape.circle` (dots).
- **Spacing:** 4-multiples throughout, given as explicit `EdgeInsets` / gaps; documented non-multiples: `50` title inset (§2.1), `3`/`5`/`7` chip & dot dimensions.
