**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/providers.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (33/36 identifiers confirmed verbatim; the rest are prose/filename references, not drift). Delta against `aion-arch/specs/tickets.md` and `aion-arch/specs/providers.md`.
Read alongside `proposal.md`/`design.md` — this file only states what
changes, not full current-state prose.

## `tickets.md`

### ADDED

- **`create_ticket` tool** — callable by the model on any chat turn that
  already offers app-defined tools (coding-execution's implement/verify
  turns, SDD-stage chats, design-sync). Creates a new top-level ticket
  (`parentId: null`, no model-supplied parent accepted) of type `story`,
  `task`, or `bug`, gated by `AutomationContext.ticketCreation`'s current
  `AutomationConfidence`: `auto` creates it immediately, `gated` surfaces a
  confirm/reject proposal and holds the model's turn open until the user
  responds, `manual` declines the call outright. See design.md §3.3.
- **`add_link` tool** — callable the same places. Creates a
  `TicketLink` from the ticket the current chat is attached to
  (`chat.parentId`) to another ticket resolved by its human-readable
  `ticketId` (never the internal uuid), with `linkType` one of `blocks`/
  `blockedBy`/`relatesTo`/`duplicates`. Same three-way
  `AutomationConfidence` gating, keyed on the new
  `AutomationContext.ticketLinking`. Declines with a reason string if
  `targetTicketId` doesn't resolve. Doubles as duplicate-flagging —
  `linkType: 'duplicates'` is an ordinary call, not a separate tool. See
  design.md §3.3.
- **`log_time` tool** — callable the same places. Adds `minutes` to the
  time spent on the ticket the current chat is attached to. No
  `AutomationConfidence` gate — always applies immediately, unlike the
  other two tools in this change. See design.md §3.3.
- **`TicketRepository.getTicketByTicketId(String ticketId)`** — resolves a
  ticket by its human-readable `ticketId` (e.g. `"TASK-42"`), not its
  internal uuid `id`. No prior method resolved tickets this way; every
  existing caller went through `getTicketById` (internal uuid). See
  design.md §4.
- **`TicketRepository.addTimeSpent(String id, int minutesDelta)`** — an
  atomic increment on the `timeSpent` column, distinct from
  `updateTicket`'s whole-object read-modify-write, so a `log_time` tool
  call can never race and clobber a concurrent human edit to the same
  ticket's other fields. See design.md §4.
- **`AutomationContext.ticketCreation`** / **`AutomationContext.ticketLinking`**
  — two new independently-configured automation-confidence contexts,
  governing `create_ticket` and `add_link` respectively. Persisted the
  same way every other `AutomationContext` entry is, via
  `AutomationSettingsRepository`. See design.md §7.
- **`PendingToolProposal.createTicket`/`.addLink`** — two new
  `PendingToolProposal` variants (`CreateTicketProposal`/`AddLinkProposal`),
  held on `TicketDetailLoaded.pendingToolProposal` while a `gated`
  `create_ticket`/`add_link` call awaits confirmation — same field,
  same lifecycle `BranchProposal`/`CloseBranchProposal` already use. See
  design.md §5.
- **`_ToolProposalBanner` new render branches** — two more `case` arms
  for `CreateTicketProposal`/`AddLinkProposal`, same component, same
  Confirm/Reject wiring already in place for branch/close-branch. See
  design.md §6.
- **Settings "Ticket creation"/"Ticket linking" automation rows** — two
  new `_AutomationSection`s bound to the new `AutomationContext` values,
  inserted after the existing "Chat branching" row. See design.md §7.

### MODIFIED

- **`TicketsCubit._toolsFor`** — previously returned *exactly one* of
  `branch_ticket`/`close_branch`. Now returns that same single
  branch-or-close-branch tool *plus* `create_ticket`, `add_link`, and
  `log_time` unconditionally appended — every chat this method serves
  offers all three new tools regardless of branch depth or structural
  position. See design.md §3.1.
- **`TicketsCubit._onToolCallFor`** — previously a binary ternary
  (`toolName == close_branch ? closeHandler : branchHandler`, with
  `branch_ticket` as the implicit "everything else" default). Now a
  name-keyed `switch` over all five tool names, with `branch_ticket`
  remaining the `_` default case — behavior for the two existing tools is
  unchanged, but the dispatch shape is no longer implicitly
  two-tools-only. See design.md §3.2.

### Known gaps this change resolves

- From `tickets.md`'s own known-gaps list: coding execution's tool-enabled
  model previously had no working path to create/edit/link tickets — only
  `page`/`resource` tickets were ever live-writable, and only by a human
  hand-editing a file. This change gives any tool-enabled chat turn
  (including coding execution) a real, gated, mid-turn write path for
  ticket creation, linking, and time logging — without touching
  `TicketGitProjector`'s one-way projection, which remains a read-only
  side effect of these writes exactly as before.
