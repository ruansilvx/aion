# Design: Token Cost Prediction

## 1. Data layer

### 1.1 New `Ticket` fields

Two new nullable `int` fields on `Ticket` (`domain/entities/ticket.dart`):

- `predictedExecutionTokensLow`
- `predictedExecutionTokensHigh`

Both `null` together always ("no estimate available"); when set, both are
non-`null` together (a range always has two ends). **Deliberately excluded
from `Ticket.copyWith`** — same treatment `complexitySource`/
`estimateSource` already get, and for the same reason `Ticket.copyWith`'s
existing `deletedAt` omission is a known latent bug
(`aion-arch/ideas/ticket-copywith-drops-deletedat.md`): a field written
only through a dedicated repository method must never also be a
`copyWith` parameter, or a generic `updateTicket(ticket.copyWith(...))`
call site can silently reset it. These two fields follow
`complexitySource`'s exact precedent instead: written only by
`TicketRepository.applyTokenPrediction`, read everywhere else.

### 1.2 Drift schema — version 13 → 14

`TicketModel` (`data/models/ticket_model.dart`) gains two nullable
`IntColumn`s:

```dart
/// Predicted token-count range's low end for a not-yet-executed task/bug,
/// or `null` if no estimate has been computed (see
/// `TicketTokenPredictor`). Always non-null exactly when
/// [predictedExecutionTokensHigh] is. Never part of `Ticket.copyWith` —
/// written only via `TicketRepository.applyTokenPrediction`.
IntColumn get predictedExecutionTokensLow =>
    integer().named('predicted_execution_tokens_low').nullable()();

/// See [predictedExecutionTokensLow].
IntColumn get predictedExecutionTokensHigh =>
    integer().named('predicted_execution_tokens_high').nullable()();
```

`schemaVersion` bumps to `14`; a `MigrationStrategy.onUpgrade` step adds
both columns (`ADD COLUMN`, following the exact pattern used for
`estimateRollup`/`timeSpentRollup`'s own migration). No backfill —
existing tickets simply start `null`/`null`, computed lazily the next
time `TicketTokenPredictor.suggest` fires for them (ticket update, or
`/apply`'s standard "next natural trigger" precedent — no batch migration
job).

### 1.3 `TicketRepository` — two new methods

```dart
/// Sums `inputTokens + outputTokens` across every comment in every
/// `"Coding Execution — "`-titled chat parented directly under each of
/// [taskIds] (spanning implement/verify turns, retries, and continuation
/// handoffs alike — every chat `_executionChatCount` would count).
/// Returns a map containing only ids with at least one non-zero total —
/// a missing key means "no recorded execution spend," equivalent to `0`.
/// One grouped SQL query regardless of `taskIds.length` — see
/// `DriftTicketRepository`'s implementation note below; callers must
/// never loop this per-id (`getValidParentCandidates`'s known
/// in-memory-fan-out gap is exactly the shape this method exists to
/// avoid repeating).
Future<Map<String, int>> getExecutionTokenTotals(List<String> taskIds);

/// Persists [low]/[high] as [Ticket.predictedExecutionTokensLow]/
/// [predictedExecutionTokensHigh] for ticket [id] — a dedicated write
/// path, exactly like [applyEstimationSuggestion], never routed through
/// `updateTicket`/`copyWith`. `low`/`high` are always written together.
Future<void> applyTokenPrediction(String id, {required int low, required int high});
```

`DriftTicketRepository.getExecutionTokenTotals` implementation shape: a
single query joining `TicketModel` (chat rows: `type = chat`, `parentId
IN taskIds`, `title LIKE 'Coding Execution — %'`) to `TicketCommentModel`
on `ticketId`, grouped by `parentId`, summing
`COALESCE(inputTokens, 0) + COALESCE(outputTokens, 0)`. Drift's
`customSelect`/query-builder `sum()` aggregate covers this without raw
SQL string interpolation of `taskIds` (bind as a `.and(parentId.isIn(...))`
predicate).

## 2. Domain service — `TicketTokenPredictor`

New class, `presentation/cubit/ticket_token_predictor.dart`, placed
alongside `TicketEstimationSuggester` for the same reason that class
gives in its own doc comment — this owns judgment logic
(`project.md`'s Cubit-owns-domain-logic convention), not a
`data/services/` concern. `TicketsCubit` constructs one instance in its
constructor body, next to `_estimationSuggester`.

```dart
class TicketTokenPredictor {
  TicketTokenPredictor(this._repository, {EmbeddingProvider? embeddingProvider});

  final TicketRepository _repository;
  late final EmbeddingProvider? _embeddingProvider;

  static const _maxComparableTickets = 5;
  // Candidate scan cap: similarity-ranked tickets are walked in order
  // until _maxComparableTickets *with actual execution history* are
  // found, or this many have been scanned — mirrors
  // TicketEstimationSuggester's fixed top-N shape while tolerating that
  // most similarity-ranked candidates won't have executed yet.
  static const _maxScannedCandidates = 20;

  Future<void> suggest(Ticket ticket) async { ... }
}
```

`suggest(ticket)` no-ops immediately (mirrors
`TicketEstimationSuggester.suggest`'s own guard shape) when:
- `_embeddingProvider` is `null`, or
- `ticket.type` isn't `TicketType.task`/`TicketType.bug`, or
- `ticket.embedding` is `null` (nothing to rank candidates against yet —
  embedding generation itself is a separate, already-existing background
  trigger), or
- the ticket already has at least one `"Coding Execution — "` child chat
  (`_repository.getTicketsByParent(ticket.id, types: [TicketType.chat])`,
  same filter `TicketsCubit._executionChatCount` uses) — once real
  execution data exists, predicting is moot; the running total supersedes
  display regardless, so this guard is a pure efficiency skip, not a
  correctness requirement.

Otherwise:
1. Rank every other live `task`/`bug` ticket with a non-null `embedding`
   by cosine similarity to `ticket.embedding` (same
   `embedding_similarity.dart` helper `TicketEstimationSuggester` uses).
2. Walk the ranked list top-down, calling
   `getExecutionTokenTotals([candidate.id])` — **batched**: collect
   candidate ids in chunks (e.g. `_maxScannedCandidates` at a time, one
   query) rather than one query per candidate, since the method already
   accepts a list. Keep candidates whose total is present (non-zero);
   stop once `_maxComparableTickets` are collected or
   `_maxScannedCandidates` have been scanned.
3. If zero comparable-with-history candidates were found: no-op (fields
   stay `null` — "no estimate available", per the idea's cold-start
   decision). No fallback number is ever fabricated.
4. Otherwise: `low = comparables.map(totals).min`,
   `high = comparables.map(totals).max` (a single-comparable match
   yields `low == high`, a valid degenerate range, not a special case).
   Persist via `_repository.applyTokenPrediction(ticket.id, low: low, high: high)`.

No model call anywhere in this path — deliberately. Predicting token
spend by spending tokens to ask a model to guess would be self-defeating;
real historical totals are strictly better ground truth than a model's
guess, and free.

**Trigger:** fires exactly where `TicketEstimationSuggester.suggest`
already fires — `TicketsCubit.createTicket`/`updateTicket`, `unawaited`,
alongside the existing call (not replacing it). Every failure mode
(missing dependency, DB error) is swallowed, same as
`TicketEstimationSuggester._run`'s own `catch (_)` — this is a background
nicety, never allowed to surface as `TicketsError`.

## 3. `TicketsCubit` — running-total cache

New private field:

```dart
/// In-memory cache of each task/bug's accumulated coding-execution token
/// spend so far (implement + verify turns, retries, continuation
/// handoffs). Seeded from `getExecutionTokenTotals` whenever a ticket
/// enters view (`loadTickets`/`getTicketById`), incremented in place the
/// moment a turn's `AgentDoneEvent` is known (inside `_runCodingExecution`,
/// right after that turn's `ai` comment is persisted) — never recomputed
/// from a fresh DB sweep on every `_refreshInFlightBoardState` call, since
/// that method must stay synchronous and cheap (see its own doc comment).
/// Not persisted separately — always reconstructable from
/// `ticket_comments`, this is purely a read cache.
final Map<String, int> _executionTokenTotals = {};
```

- `loadTickets`/`loadMoreTickets`: after fetching a page, batch-call
  `getExecutionTokenTotals(pageTicketIds)` once and merge into
  `_executionTokenTotals` (only overwriting keys not already tracked as
  in-flight-updated this session, to avoid clobbering a same-session
  increment with a stale read — compare-and-keep-max is sufficient and
  avoids ordering assumptions).
- `getTicketById`: same batched call with a single-element list when the
  id isn't already cached.
- `_runCodingExecution`: immediately after persisting the implement (and,
  if reached, verify) turn's `ai` comment with its real
  `inputTokens`/`outputTokens`, does
  `_executionTokenTotals.update(task.id, (v) => v + delta, ifAbsent: () => delta)`
  where `delta = (event.inputTokens ?? 0) + (event.outputTokens ?? 0)`,
  then calls `_refreshInFlightBoardState()`/`_refreshTaskDetailIfShowing()`
  (both already called at this point in the existing flow) so the new
  total reaches whichever state is current.

Exposed via:
- `TicketsLoaded.executionTokenTotals` (`Map<String, int>`, default `{}`)
  — new field alongside `inFlightExecutionIds`/`executionQueuePositions`,
  populated by `_refreshInFlightBoardState` from
  `Map.unmodifiable(_executionTokenTotals)` (a plain copy — no new async
  work added to that synchronous method, per its own existing
  in-memory-only contract).
- `TicketDetailLoaded.executionTokenTotal` (`int?`) — new field alongside
  `isExecuting`/`executionFailureReason`, resolved in `getTicketById`
  from `_executionTokenTotals[ticket.id]` (already seeded per above by
  the time this runs). `null` means no coding-execution chat has ever
  existed for this ticket — distinct from `0`, which would mean a chat
  exists but no turn has reported usage yet (defensive; shouldn't happen
  in practice since `AgentDoneEvent.inputTokens`/`outputTokens` are
  populated "in practice", per that class's own doc comment).

## 4. Widget tree

### 4.1 `TokenCountLabel` (new, shared)

`features/tickets/presentation/widgets/token_count_label.dart` — a small
stateless widget + one pure formatting function, shared by all three call
sites below (Board card, detail metadata, detail execution banner) so the
"~45K" abbreviation logic exists exactly once:

```dart
/// Formats [tokens] as a compact "~12.3K"/"~1.2M" label, or the exact
/// integer below 1000. Shared by every token-count display this change
/// adds — see `TokenCountLabel`.
String formatTokenCount(int tokens) { ... }

/// Renders either a single [formatTokenCount] value (running total) or a
/// "low–high" range (predicted estimate), both prefixed with a small
/// token-glyph icon and styled as a caption-weight label — visually
/// consistent with `AiSuggestionBadge`'s own caption treatment
/// (`ai-assisted-complexity-and-estimate-suggestions/design.md`) without
/// reusing that widget directly, since this isn't an AI-generated value
/// needing its "AI-suggested" framing.
class TokenCountLabel extends StatelessWidget {
  const TokenCountLabel.range({required this.low, required this.high, super.key})
      : total = null;
  const TokenCountLabel.total({required this.total, super.key})
      : low = null, high = null;

  final int? low;
  final int? high;
  final int? total;
  ...
}
```

### 4.2 `TicketBoardCard` — meta-chip row

New helper alongside `_cardExecutionState`/`_cardIsBlocked`:

```dart
/// Resolves [t]'s token label, or `null` when nothing should render —
/// mirrors [_cardExecutionState]'s same no-signal floor. Running total
/// (from [TicketsLoaded.executionTokenTotals]) takes precedence over the
/// persisted prediction whenever a real total is present, per this
/// change's display-precedence rule (see design.md §5).
TokenCountLabel? _cardTokenLabel(TicketsState s, Ticket t) {
  if (t.type != TicketType.task && t.type != TicketType.bug) return null;
  if (s is TicketsLoaded) {
    final total = s.executionTokenTotals[t.id];
    if (total != null) return TokenCountLabel.total(total: total);
  }
  final low = t.predictedExecutionTokensLow;
  final high = t.predictedExecutionTokensHigh;
  if (low != null && high != null) return TokenCountLabel.range(low: low, high: high);
  return null;
}
```

Rendered in `_CardVisual`'s meta-chip row, same `context.select` pattern
already scoping `_cardExecutionState`/`_cardIsBlocked` to `ticket.id` so a
card only rebuilds on its own change — placed after `PriorityBadge`,
before `RollupBadge`/`_BoardCardStatusBadge` (a small caption label, not
another status badge, so it visually recedes behind the louder
execution-state badges).

### 4.3 `TicketMetadataSection` — predicted-range label

Immediately beside the existing complexity/estimate row (same visual
tier as `AiSuggestionBadge`'s placement at line ~271/~459), a
`TokenCountLabel.range(...)` renders when
`ticket.predictedExecutionTokensLow != null && executionTokenTotal ==
null` — i.e. a prediction exists and no real execution data has
superseded it yet. `executionTokenTotal` is threaded in as a new
constructor parameter (`TicketMetadataSection` already takes
`isExecuting`/`executionFailureReason` similarly, per its existing
destructuring at lines ~149–152).

### 4.4 `_CodingExecutionSection` — running-total line

New required parameter `executionTokenTotal` (`int?`), rendered as a
`TokenCountLabel.total(...)` line inside the banner whenever non-null —
alongside the existing `isExecuting`/`executionQueuePosition`/
`executionAwaitingReview`/`executionFailureReason`-driven content, not
gating the banner's own visibility condition (the banner already shows
whenever any of those four is truthy; a ticket with `executionTokenTotal
!= null` necessarily has at least one of those truthy too, since a token
total only exists once execution has started).

## 5. Display precedence (both surfaces)

1. `executionTokenTotal`/`executionTokenTotals[id]` non-null → show
   running total.
2. Else `predictedExecutionTokensLow`/`High` non-null → show predicted
   range.
3. Else → render nothing (no label, no reserved space).

This rule is implemented identically in `_cardTokenLabel` (§4.2) and in
`TicketMetadataSection`'s conditional (§4.3) — no shared helper needed
since one is Board-state-driven and the other is
`TicketDetailLoaded`-field-driven, but the *rule* itself must stay in
sync between them; both reference this section in their doc comments.

**Queued-state carve-out (added at `/design-sync`, per the approved
Component Spec §2.1/§4.2):** while a task/bug is queued but no
implement/verify turn has completed yet, neither surface shows anything
— not even a leftover predicted range from before the run was triggered.
This narrows rule 2 above: "predicted range" only applies when the
ticket has *never* had a coding-execution chat at all, not merely when
`executionTokenTotal` happens to be `null` (which is also briefly true
the instant a run is queued, before its first turn completes). The Board
card's `_cardTokenLabel` (§4.2) and `TicketMetadataSection`'s conditional
(§4.3) must both check "no coding-execution chat exists yet" — not just
"`executionTokenTotal` is null" — before falling back to the predicted
range. `TicketTokenPredictor` never clears `predictedExecutionTokensLow`/
`High` once a run starts (§2), so the stale value is still sitting on the
`Ticket` row during the queued window; display logic, not data mutation,
is what must suppress it.

## 6. What this deliberately does not touch

- `AutomationConfidence`, `ConsumptionSignal`, `AgentOverageDetectedEvent`
  — the reactive usage-window/overage gate (`providers.md`) is completely
  unrelated code and stays untouched.
- `AgentModelClient`/`AgentToolUseEvent` — no new event type, no bridge
  changes. Per proposal.md's Non-goals, true mid-turn live ticking isn't
  possible with today's SDK usage-reporting granularity; this change
  doesn't attempt to add it.
- `TicketEstimationSuggester` itself — read-only reuse of its comparable-
  ticket ranking *pattern*, not its code (different comparison field,
  different persistence method, no model call), so it's duplicated
  narrowly rather than refactored into a shared base class. Revisit only
  if a third similar predictor shows up.

# Aion — Token Cost Prediction: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Estimate / Time-Spent Rollup Spec](./Aion%20Estimate%20Rollup%20Spec.md) (`neutralTint` / `neutralBorderTint`, the `RollupBadge` compact data-chip pattern this sits beside), the [AI Suggestion Badge Spec](./Aion%20AI%20Suggestion%20Badge%20Spec.md) (`AionText.badgeLabel`, `primaryWash`, and the `TicketMetadataSection` complexity/estimate value rows this attaches to), the [Task-to-Coding-Execution Trigger Spec](./Aion%20Task%20Execution%20Trigger%20Spec.md) (the `_CodingExecutionSection` eyebrow + run-status line + `CodingRunState` this adds a line to), the [Board Execution/Advance Indicators Spec](./Aion%20Board%20Advance%20Indicators%20Spec.md) (`BoardCardStatusBadge` + the meta-chip trailing cluster this joins), and the [Concurrent, Cancellable Execution Spec](./Aion%20Concurrent%20Cancellable%20Execution%20Spec.md) (`ExecutionCancelControl`, the last member of that trailing cluster). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, `TicketBoardCard`, `TicketMetadataSection`, `_CodingExecutionSection`, `TypeChip`, `PriorityBadge`, `RollupBadge`, `BoardCardStatusBadge`, and `ExecutionCancelControl` by name.

This change adds **cost visibility** to coding execution — the most expensive, highest-variance work Aion does — before, during, and after a run. Today there is zero token visibility until after tokens are spent. This pass adds two small, **purely-informational, non-blocking** numeric displays, both carried by one new shared widget:

1. A **pre-flight token-count range** on a not-yet-run Task/Bug — a predicted estimate (e.g. `~28K–61K tokens`) calibrated from comparable past tickets' real historical token spend, shown before a coding-execution run ever starts.
2. A **running total** once a run is in flight or has completed at least one turn — the ticket's real accumulated token spend so far (e.g. `~18.4K tokens`).

Neither triggers a confirmation, blocks anything, or represents a **dollar** cost (Aion's model provider is a flat-rate plan, not per-token billing). They are quiet, caption-weight numeric labels — closer in visual weight to a timestamp or a `RollupBadge` than to a status badge or an alert.

It **adds no new screens and no navigation.** It is additive chrome on three already-existing surfaces:

- **`TicketBoardCard`** (Kanban card) — the compact `TokenCountLabel` in the existing meta-chip trailing cluster (§2).
- **`TicketMetadataSection`** (Task/Bug detail) — the detail `TokenCountLabel.range` as a persistent line beside the complexity/estimate fields (§3).
- **`_CodingExecutionSection`** (Task/Bug detail execution banner) — the detail `TokenCountLabel.total` as a line inside the run-status banner (§4).

This spec is implementation-ready. All values reference Aion's `AionColors` / `AionText` / `AionRadius` / `AionSpacing` tokens read via `ThemeScope.of(context)`. **No Material widgets or types anywhere** — Flutter primitives only (`DecoratedBox`, decoration-only `Container`, `Row` / `Column` / `Padding` / `Wrap`, `Text`, `CustomPaint`, `AnimatedOpacity`, and an `Icon`-equivalent `PhosphorIcon`). **No** `Card`, `ElevatedButton`, `Chip`, `Scaffold`, `AppBar`, `Tooltip`, `Badge`, `ThemeData`, `ColorScheme`, `InkWell`, `ListTile`, or any other `package:flutter/material.dart` widget. Translucent fills are always `token.withOpacity(x)` (equivalently `token.withValues(alpha: x)`), never a hardcoded ARGB. Both themes — **Arctic** (light, celestial-cold) and **Obsidian** (dark, abyssal-cold) — are covered; where identical it is stated. Concrete hex is quoted `Arctic / Obsidian` for reference only — implement against the token, never the literal.

**New tokens: none for color, typography, radius, or spacing.** Every value reuses an existing token or documented helper. The one genuine gap is an **icon** — Aion has no token/cost/usage glyph precedent — resolved in §0.3 by adopting an existing Phosphor glyph, not by drawing a new one. Two small structural additions carry no design surface: the `formatTokenCount` formatter (§5.1) and the `TokenCountMode` / `TokenCountVariant` enums + `TokenCountData` read model (§5.2).

## 0. Foundations for this feature

### 0.1 Tokens — reuse, no new hue

A token count is **informational, neutral, secondary-priority** — not an accent, not a status/severity/priority signal, and explicitly **not a dollar cost**. It must not read as an accent and must not compete with `PriorityBadge`'s colored scale, the `TypeChip` accent, or `BoardCardStatusBadge`'s `primary`/`secondary` live-work families.

It therefore reuses the existing **quiet data-chrome** tints — the same family that carries the estimate/time-spent rollup and the AI-suggestion badge — **not** `primary` / `primarySubtle` (which Aion reserves for AI and active-state chrome):

```dart
// neutral, informational tint — quiet numeric/data chrome (already defined, Rollup §0.1)
Color get neutralTint =>
    textSecondary.withOpacity(isDark ? 0.14 : 0.09);

// hairline for the same family (already defined, Rollup §0.1)
Color get neutralBorderTint =>
    textSecondary.withOpacity(isDark ? 0.26 : 0.18);

// faint primary fill under an actively-working control (already defined, AI Badge §0.1)
Color get primaryWash =>
    primary.withOpacity(isDark ? 0.16 : 0.10);
```

**Design decision — `neutralTint`, not `primarySubtle`/`pendingTint`.** The `RollupBadge` (Rollup §0.1) established `neutralTint` precisely for "quiet numeric/data chrome that must not read as an accent," reasoning from the same estimate/timeSpent rollup need. That reasoning applies directly here: a token count is one more quiet number in the same family, and the two even co-occupy the board meta row (§2). `pendingTint` (`primary @ 0.12/0.18`) belongs to `BoardCardStatusBadge`'s *live-work* signal and would make a passive number look active; `primarySubtle` is the AI accent. Both are rejected. **No new color token is introduced.** `primaryWash` is touched only by the execution banner's in-flight liveness dot (§4.3), never by the label fill.

### 0.2 Number formatter — `formatTokenCount`

One shared formatter renders every token value (range endpoints and totals, compact and detail), so all three surfaces always agree. Raw token counts are non-negative `int`s.

```dart
/// Compact token count. Input: whole token count (>= 0).
///   under 1000  -> exact             (842      -> "842")
///   1000 .. <1M -> one decimal + K   (12300    -> "12.3K", 34000 -> "34K")
///   >= 1M       -> one decimal + M   (1200000  -> "1.2M")
/// One decimal, with a trailing ".0" dropped (12000 -> "12K", not "12.0K").
String formatTokenCount(int n) {
  if (n < 0) n = 0;
  if (n < 1000) return '$n';
  String abbrev(double v) {
    final s = v.toStringAsFixed(1);
    return s.endsWith('.0') ? s.substring(0, s.length - 2) : s;
  }
  if (n < 1000000) return '${abbrev(n / 1000.0)}K';
  return '${abbrev(n / 1000000.0)}M';
}
```

| Tokens | Output | Rule |
|---|---|---|
| `842` | `842` | under 1000 → exact, no suffix |
| `12000` | `12K` | one decimal, `.0` dropped |
| `12300` | `12.3K` | one decimal kept |
| `18400` | `18.4K` | one decimal kept |
| `34000` | `34K` | `.0` dropped |
| `1200000` | `1.2M` | ≥ 1M → `M` suffix |

**Approximation `~` prefix and unit word are applied by the widget, not the formatter** (§1.1) — `formatTokenCount` returns only the bare number so the same output composes into `~12.3K`, `~12K–34K tokens`, `842 tokens`.

### 0.3 Icon — the one genuine gap

Aion has **no** token / cost / usage glyph. `sparkle` is the AI mark (reserved), `stack` is the rollup marker (reserved, "own value stacked with descendants"), `timer` / `hourglass` are the estimate / time-spent metrics — none read as "metered consumption." The gap is real, so this feature adopts an existing Phosphor glyph rather than inventing a bespoke mark:

| Meaning | Phosphor icon | Weight | Where |
|---|---|---|---|
| Token usage / consumption | `PhosphorIcons.gauge` | Regular (Light for detail) | Leading glyph in every `TokenCountLabel` |

**Why `gauge`.** A gauge reads unambiguously as *metered consumption / usage rate* — the correct mental model for token spend — and is visually distinct from `sparkle` (AI), `stack` (rollup aggregation), and `timer`/`hourglass` (time). It is never rendered in an accent color: default glyph color is `textSecondary`, matching the sibling `RollupBadge` marker. If `gauge` is unavailable in the shipped icon set, fall back to `PhosphorIcons.speedometer`, then `PhosphorIcons.coins` (the "usage" read is preserved; `coins` last because it leans toward money, which this is not).

> **Mockup note.** `Aion Token Cost Prediction Mockups.dc.html` draws `gauge` as an inline SVG stand-in (a bottom-arc dial with a short needle). Ship the real Phosphor `gauge` glyph at the sizes in §1.2 / §1.3.

### 0.4 Typography

No new style. The value is a quiet mono number in the timestamp/rollup family, so it reuses **`AionText.key`** (JetBrains Mono, 11, w600) — the same style the `RollupBadge` value uses — with a single documented `copyWith` down to 10.5 for the compact variant. The optional trailing unit word `"tokens"` reuses the same mono family at `w400`, one tone quieter (`textMuted`), exactly like the rollup count caption.

```dart
// value (range endpoints / total) — reuses AionText.key
AionText.key                                   // detail variant: mono 11 / w600
AionText.key.copyWith(fontSize: 10.5)          // compact variant: mono 10.5 / w600
// unit word "tokens" (detail variant only, §1.3)
AionText.key.copyWith(fontWeight: FontWeight.w400) // mono 11 / w400
```

All styles are colorless; color is applied per use site (§1). No `AionText` member is added.

## 1. `TokenCountLabel` — the core deliverable

A small, quiet, caption-weight, **non-interactive** label rendering either a predicted **range** or a running/actual **total** of tokens, with a leading `gauge` glyph and `neutralTint` fill. It is deliberately **not** an `AiSuggestionBadge` reuse: a token count is a measured/derived number, not an AI-authored field value, so it must not carry `sparkle` iconography or the `primary`/`primarySubtle` AI framing. It reads as neutral metrics chrome, in the same family as `RollupBadge`.

```dart
enum TokenCountMode { range, total }        // §5.2
enum TokenCountVariant { compact, detail }  // §5.2

class TokenCountLabel extends StatelessWidget {
  final TokenCountMode mode;
  final TokenCountVariant variant;
  final int? lowTokens;   // range mode: lower bound
  final int? highTokens;  // range mode: upper bound
  final int? totalTokens; // total mode: accumulated count
  final bool live;        // total mode only: pairs the banner liveness dot (§4.3); ignored elsewhere
  // non-interactive: no onTap, no MouseRegion cursor change, no focus node.
}
```

### 1.1 Content model — what the two modes render

Both modes are `gauge` glyph + a mono value string, built from `formatTokenCount` (§0.2). The widget (not the formatter) adds the `~` approximation prefix and the `tokens` unit word:

| Mode | Composed string (detail variant) | Rule |
|---|---|---|
| **range** | `~{lo}–{hi} tokens` — e.g. `~28K–61K tokens` | En dash `–` (U+2013), no spaces around it. Always prefixed `~` (a forecast is inherently approximate). `lo`/`hi` each via `formatTokenCount`. |
| **total** (≥ 1000, abbreviated) | `~{v} tokens` — e.g. `~18.4K tokens` | `~` prefix because the value is abbreviated/rounded. |
| **total** (< 1000, exact) | `{v} tokens` — e.g. `842 tokens` | **No** `~` — the value is exact. |

- **Compact variant drops the `tokens` unit word** — it renders `gauge` glyph + value only (`~28K–61K`, `~18.4K`, `842`), matching the `RollupBadge` precedent of relying on its glyph for the unit read (§1.2). The `~` and en-dash rules are unchanged.
- Degenerate range where `lo == hi` collapses to total-mode rendering (`~{v} tokens`); the caller should prefer `mode: total` in that case.

### 1.2 Compact variant (`variant: compact`) — board meta-chip row

Sized to sit flush beside `RollupBadge`, `TypeChip`, `PriorityBadge`, and `BoardCardStatusBadge` on the board card's meta row. Geometry is **byte-identical to `RollupBadge`** (Rollup §2.2) so the two neutral data chips read as one family.

- **Container:** `DecoratedBox` → `Padding` → `Row` (`mainAxisSize: min`, `crossAxisAlignment: center`, `gap: 5`).
  - `padding: EdgeInsets.fromLTRB(6, 2, 7, 2)`
  - `borderRadius: BorderRadius.circular(6)` — `AionRadius.sm`
  - fill: `colors.neutralTint`
  - border: **none**
  - shadow: **none**
- **Leading glyph:** `PhosphorIcon(PhosphorIcons.gauge, size: 11, color: colors.textSecondary)`.
- **Value:** `Text`, `AionText.key.copyWith(fontSize: 10.5)` (mono 10.5 / w600), color `colors.textSecondary`. No unit word (§1.1).
- **Height:** ≈ 19–20px, sizes to content, **never wraps internally**.

Radius `6` (a calm data chip) deliberately differs from `TypeChip`'s pill (22) and from `BoardCardStatusBadge`'s pill (22) — it recedes rather than competes, exactly as `RollupBadge` does.

### 1.3 Detail variant (`variant: detail`) — detail-screen placements

A touch roomier, similar in weight to the `AiSuggestionBadge` caption treatment it sits near, used by both detail-screen placements (§3 metadata, §4 execution banner).

- **Container:** `DecoratedBox` → `Padding` → `Row` (`mainAxisSize: min`, `crossAxisAlignment: center`, `gap: 6`).
  - `padding: EdgeInsets.fromLTRB(7, 3, 9, 3)`
  - `borderRadius: BorderRadius.circular(6)` — `AionRadius.sm`
  - fill: `colors.neutralTint`
  - border: **none**
  - shadow: **none**
- **Leading glyph:** `PhosphorIcon(PhosphorIcons.gauge, size: 12, color: colors.textSecondary)`.
- **Value:** `Text`, `AionText.key` (mono 11 / w600), color `colors.textSecondary`.
- **Unit word:** `Text(' tokens')` — rendered as a trailing `Text` in the same `Row` (or a `TextSpan` sharing the value's baseline), `AionText.key.copyWith(fontWeight: FontWeight.w400)` (mono 11 / w400), color `colors.textMuted`. The muted weight gives the value slight prominence over the unit, matching the rollup value/count hierarchy.
- **Height:** ≈ 22px, sizes to content.

### 1.4 States

**N/A — non-interactive.** `TokenCountLabel` has a single resting visual state in both variants and both modes. It has **no** hover, focus, pressed, disabled, or error state of its own — it takes no gesture, no focus node, and no cursor change. (Implementers: do not add any.) The only permitted external variation is the execution banner's separate liveness dot in §4.3, which is a sibling element in the banner row, **not** a state of this widget. Its background may change with the surface it lands on; see §1.6.

There is no error state — a token value is always a valid computed number; if a value cannot be computed the label is simply not rendered (the gate in §2/§3/§4).

### 1.6 Theme differences

Identical structure, radius, padding, glyph, and token references in both themes. Only the resolved colors differ via the active `AionColors`: `neutralTint` = `textSecondary @ 0.09` (Arctic) / `@ 0.14` (Obsidian); `neutralBorderTint` = `@ 0.18` / `@ 0.26` (used only on a selected board row, §2.3); glyph/value resolve to the theme's `textSecondary`, the unit word to `textMuted`. ## 2. Board card integration (`TicketBoardCard`)

The compact `TokenCountLabel` (§1.2) joins `TicketBoardCard`'s existing meta-chip row — the row per Design System §2.7 / Board Advance §1: `surface` card, 1px `border`, radius `12`, `padding: EdgeInsets.symmetric(horizontal: 14, vertical: 13)`, `Column` gap `9` (ID row, title, meta row). It appears **only on Task/Bug cards** that have a token value to show; it is **never** rendered on Epic/Story/Chat/Resource/Page cards (they have no coding-execution run, §2.4).

### 2.1 Which value shows

Exactly one `TokenCountLabel` per card, chosen by the card's coding-execution state (`CodingRunState`, Task Trigger §5, plus the not-yet-run case):

| Card execution state | Label | Mode |
|---|---|---|
| **Not yet run** (Task/Bug, no run started, has a prediction) | predicted range | `range` — `~{lo}–{hi}` |
| **Running** (`CodingRunState.running`) | running total so far | `total` — `~{v}` |
| **Queued** (`CodingRunState.queued`, no turn completed yet) | **none** — no turn has produced tokens; the `BoardCardStatusBadge "Queued #N"` carries the state | — |
| **Completed** (run finished — `readyForReview` / done) | settled total | `total` — `~{v}` |

On the board the label is always **static neutral** in every state — even `running`. Liveness on the board is already carried by the `BoardCardStatusBadge "Running"` (spinning gear); the token pill stays a quiet number so the card does not double-signal. The in-flight liveness dot (§4.3) is reserved for the detail execution banner. (`live` is passed `false` for all board usage.)

### 2.2 Ordering & gap within the meta row

The meta row's trailing cluster (after `TypeChip` + optional `PriorityBadge`, pushed right by a `Spacer()`) already may hold, in order, `RollupBadge` → `BoardCardStatusBadge` → `ExecutionCancelControl` (Rollup §2.5, Board Advance §0, Concurrent §2.1). `TokenCountLabel` inserts **immediately before `BoardCardStatusBadge`**, after `RollupBadge`:

```
TypeChip · [PriorityBadge] · Spacer() · [RollupBadge] · [TokenCountLabel] · [BoardCardStatusBadge] · [ExecutionCancelControl]
```

- **Rationale for the slot.** The two neutral data pills (`RollupBadge`, `TokenCountLabel`) sit together, left of the louder live-work cluster (`BoardCardStatusBadge` + cancel), keeping the quiet-chrome family visually grouped and the live signal rightmost. `TokenCountLabel` sits directly left of `BoardCardStatusBadge` because the two are semantically paired (both describe *this* card's run — its cost and its live status). In practice `RollupBadge` and `TokenCountLabel` rarely co-occur: `RollupBadge` needs live children, and a Task/Bug getting a coding run is typically a leaf.
- **Gaps:** the meta row's existing inter-chip gap is used between every member — `AionSpacing.sp8` (8) between chips in the trailing cluster, matching the row's established rhythm (the `TypeChip`→cluster relationship keeps its `Spacer()`). No new gap value.

### 2.3 Crowding — wrap, with a documented drop order

A Task/Bug card at its busiest could carry `TypeChip` + `PriorityBadge` + `TokenCountLabel` + `BoardCardStatusBadge` + `ExecutionCancelControl` on one row — tight on a narrow column.

- **Primary behavior — wrap, never truncate a value.** Implement the meta row as a `Wrap` (`spacing: 8`, `runSpacing: 8`, `crossAxisAlignment: WrapCrossAlignment.center`) rather than a single `Row`. When the row cannot fit, the trailing cluster wraps to a second meta line; a token value is never clipped or ellipsized (a half-shown number is worse than a wrapped one). The `Spacer()` right-alignment is replaced by `Wrap`'s natural flow when wrapping is in effect; on a single line, an `Expanded` spacer between the type/priority group and the trailing cluster preserves the right-alignment.
- **Fallback — priority-order drop (only if a design later forbids a 2-line meta row).** If a card must keep the meta row to one line, drop members last-shown-first in this order until it fits: **`TokenCountLabel` drops first** (it is the most optional — the full number is always available on the detail screen, §3/§4), then `RollupBadge`, then `PriorityBadge`. **`TypeChip` and `BoardCardStatusBadge` never drop** (type identity and live-run status are load-bearing). This spec ships the wrap behavior; the drop order is documented so a future single-line constraint has a sanctioned resolution.

### 2.4 Type gate — the label must not appear on non-Task/Bug cards

`TokenCountLabel` is rendered on `TicketBoardCard` **iff** `ticket.type == task || ticket.type == bug` **and** a token value exists for the card's state (§2.1). For every other type — Epic, Story, Chat, Resource, Page — the card renders exactly as today, with no label and no reserved slot. Coding execution (and therefore token spend) is a Task/Bug-only mechanism; an Epic/Story card carrying a token number would be meaningless. Gate first, at the card level:

```dart
if ((ticket.type == TicketType.task || ticket.type == TicketType.bug) && tokenCount != null)
  TokenCountLabel(/* … */)   // else: nothing, no SizedBox slot
```

## 3. Detail-screen metadata placement (`TicketMetadataSection`)

The detail `TokenCountLabel.range` (§1.3, `mode: range`) is added to `TicketMetadataSection` on the Task/Bug detail screen, beside the existing Complexity / Estimate fields (and their `AiSuggestionBadge`s, AI Badge §3). It shows the **pre-flight prediction** and persists on the ticket regardless of run state (it remains visible even after a run starts — the running total lives separately in the execution banner, §4).

### 3.1 Placement — its own line beneath the complexity/estimate row

**Decision: a separate, full-width line directly beneath the Complexity/Estimate row, not inline within it.**

- The existing row is two field columns (Complexity, Estimate) in a `Row` with horizontal `gap: 34`, each a `Column` (caption label → value row + any `AiSuggestionBadge`/`RegenerateButton`), per AI Badge §3. That layout is **unchanged**.
- Beneath it, `gap: AionSpacing.sp16` (16) below the field row, add a new field-shaped block: a mono caption label then the range label.

**Rationale.** Complexity and Estimate are *manual/AI-suggested planning inputs* the user can set or lock; a token range is a *derived pre-flight forecast* with a different provenance and a different shape (a range, not a single value with a suggest/lock lifecycle). Inlining it as a third value in the two-field row would (a) crowd the row past the 336px narrow-phone width when an `AiSuggestionBadge` is also present, and (b) imply it belongs to the same suggest/lock model, which it does not. A dedicated line reads it as the related-but-distinct forecast it is, and leaves room for the full `tokens` unit word.

### 3.2 Block structure

`Column`, `crossAxisAlignment: start`, gap `AionSpacing.sp8` (8):

- **Caption label:** `Text('PREDICTED TOKENS')`, uppercased in Dart, `AionText.caption`-family rendered at the metadata caption scale (`fontSize: 10`, mono, `letterSpacing: 1.4`, `AionColors.textMuted`) — byte-identical to the Complexity/Estimate captions above it so the block reads as one more member of the section.
- **Value row:** `TokenCountLabel(mode: range, variant: detail, lowTokens: …, highTokens: …)` — the §1.3 pill, left-aligned (`Align(alignment: centerLeft)` / `mainAxisSize: min`). No other element on this line.

### 3.3 Gate & absence

Rendered only when a prediction exists for the ticket (`tokenPrediction != null`, i.e. the calibrator produced a range from comparable history). When absent — a brand-new ticket type with no comparable history, or a non-Task/Bug detail screen — the block is omitted entirely (no caption, no empty slot); the metadata section is byte-for-byte its pre-existing self. A cold-start prediction with wide uncertainty is still a valid range and shows normally; this feature does **not** add a low-confidence variant (the range width itself communicates uncertainty).

## 4. Execution banner placement (`_CodingExecutionSection`)

The detail `TokenCountLabel.total` (§1.3, `mode: total`) is added inside the existing coding-execution banner (`_CodingExecutionSection`, Task Trigger §0) on the Task/Bug detail screen — the section with the `"CODING EXECUTION"` eyebrow, the run-status line (dot + `"Executing"` / `"Queued"` / `"Run complete"`), and the state body (`_ExecutionRunningHint` / `_ExecutionQueueHint` / `_ExecutionReadyForReviewBanner`).

### 4.1 Placement — its own line, below the state body

The section's inner layout is a `Column`, `crossAxisAlignment: stretch`, `gap: 14` (Task Trigger §0). Insert the token line as a new child **below the state body** (below `_ExecutionRunningHint` + its live tool-use line for `running`; below `_ExecutionQueueHint` for `queued`; below the ready-for-review banner for `readyForReview`), at the section's existing `gap: 14`. Left-aligned in the stretch column (`Align(alignment: centerLeft)` / `mainAxisSize: min`) — the label hugs content, it does not stretch full-width.

### 4.2 Which value shows per run state

| `CodingRunState` | Run-status line (unchanged) | Token line |
|---|---|---|
| `running` | `primary` dot · `"Executing"` | `TokenCountLabel.total` **in-flight** treatment (§4.3), `live: true` |
| `queued` | `secondary` dot · `"Queued"` | **none** — no turn has completed, so there is no real total yet (matches §2.1) |
| `readyForReview` | `success` dot · `"Run complete"` | `TokenCountLabel.total` **settled** treatment (§4.4), `live: false` |

The token line is gated on `runState != queued && totalTokens != null`. A queued run shows the queue hint only.

### 4.3 In-flight treatment (`running`) — a live liveness dot beside a still-neutral label

The brief calls for a distinct in-flight treatment "paired with a live/pulsing accent." The label **itself stays neutral** (§0.1 forbids it reading as an accent); liveness is carried by a small **sibling** element in the token line, so the number remains quiet while the line reads as "still climbing."

Token line = a `Row`, `crossAxisAlignment: center`, `gap: 8`:

1. `TokenCountLabel(mode: total, variant: detail, live: true)` — the standard §1.3 neutral pill, **unchanged** (no accent recoloring).
2. A **liveness dot** — a `7×7` filled circle, `BoxShape.circle`, color `primary` (`#2E86D4 / #9366FF`), with the app-standard pulse: `AnimatedOpacity` / `AnimatedScale` loop `0.35 → 1.0 → 0.35` opacity and `0.8 → 1.0` scale over `1100ms` ease-in-out, `repeat(reverse: true)` — the exact `ctPulseDot` / `WaitingForReplyIndicator` treatment (Board Advance §4.1). Static at full opacity under `MediaQuery.disableAnimations`.
3. A **caption** — `Text('counting…')`, `AionText.time` (mono 11 / w400), color `textMuted`.

The pulsing dot + `"counting…"` is the whole in-flight differentiator; it reuses the app's existing live-activity motif (same dot as the chat waiting indicator), so "this is live" reads identically to the rest of the app, without tinting the number. The dot and caption are **siblings of** the label, never part of it (§1.4).

### 4.4 Settled treatment (`readyForReview` / completed) — calm and static

The token line is just the `TokenCountLabel(mode: total, variant: detail, live: false)` neutral pill — **no** liveness dot, **no** `"counting…"` caption, no motion. A finished run's total is a fixed fact; it reads calm and static, distinct at a glance from the in-flight line by the absence of the pulse. This is the same widget as §4.3 minus the two sibling elements.

### 4.5 Dimensions recap (banner token line)

| Property | Value |
|---|---|
| Line offset below state body | `14` (section inner `Column` gap) |
| Label | `TokenCountLabel.detail` (§1.3) — `neutralTint`, radius 6, `gauge` 12, mono 11 |
| Liveness dot (in-flight only) | `7×7` circle, `primary`, 1100ms pulse `0.35↔1.0` opacity / `0.8↔1.0` scale |
| Dot → label / dot → caption gap | `8` |
| Caption (in-flight only) | `"counting…"`, `AionText.time` (mono 11 / w400), `textMuted` |
| Settled line | label only, no dot, no caption, no motion |

## 5. Enums, formatter & read model (no new design tokens)

### 5.1 Formatter

`formatTokenCount(int)` — §0.2. One formatter for every surface and both variants; never format a token count inline anywhere else.

### 5.2 Enums & read model

```dart
enum TokenCountMode { range, total }
//   range -> pre-flight prediction "~{lo}–{hi} tokens"   (§1.1)
//   total -> running/actual accumulated "~{v} tokens"    (§1.1)

enum TokenCountVariant { compact, detail }
//   compact -> board meta-chip row, no unit word          (§1.2)
//   detail  -> detail-screen metadata + execution banner  (§1.3)

/// Per-ticket token figures, computed off the widget tree; the widgets are pure display.
/// A null field means "not available" -> the corresponding surface renders nothing (gate).
@immutable
class TokenCountData {
  final int? predictedLow;    // pre-flight range lower bound (comparable-history calibrated)
  final int? predictedHigh;   // pre-flight range upper bound
  final int? runningTotal;    // real accumulated spend so far (>= one completed turn)
  final CodingRunState? runState; // running / queued / readyForReview; null => not-yet-run
  const TokenCountData({
    this.predictedLow, this.predictedHigh, this.runningTotal, this.runState,
  });

  bool get hasPrediction => predictedLow != null && predictedHigh != null;
  bool get hasRunningTotal =>
      runningTotal != null && runState != null && runState != CodingRunState.queued;
}
```

- `CodingRunState` is reused unchanged (Task Trigger §5). `TokenCountData` carries no persisted ticket-model change — the prediction is a calibrator output and the running total is live run telemetry, both derived, both nullable.
- **Board (§2):** not-yet-run (`runState == null`) + `hasPrediction` → range; `running` → total; `readyForReview`/done → total; `queued` → nothing.
- **Metadata (§3):** `hasPrediction` → range line; else nothing.
- **Banner (§4):** `hasRunningTotal` → total line (in-flight if `running`, settled if `readyForReview`); `queued` → nothing.
