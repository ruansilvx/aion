# Design: Verify-stage quality gate

## 1. Overview

Everything here mirrors an existing, shipped precedent — `designSync`'s
`DESIGN GATE: APPROVED` gate for the field/graph/prompt pieces, and
`advanceSddStage`'s three-way `AutomationConfidence` footer for the retry
UI. No new architectural pattern is introduced; this is an extension of
the configurable-`TransitionGraph` engine (`sddstage-transition-
preconditions`) plus the existing `AutomationContext` family
(`core/automation/automation_context.dart`).

## 3. Data layer

### 3.1 `transition_precondition_dao.dart` — `seedDefaultsIfEmpty`

Pull `SddStage.verifying` out of the shared
`for (final stage in [SddStage.exploring, SddStage.verifying])` loop (that
loop now seeds `exploring` only) and give it its own two-node tree,
structured exactly like `designSync`'s block immediately below it:

```
mostRecentChatHasTerminalReply
  ├─ unmatched → blocked
  └─ matched → verifyGateApproved
        ├─ matched   → allowed
        └─ unmatched → blocked
```

### 3.2 Migration — schema version 20

`app_database.dart`: bump `schemaVersion` to `20`, add an `onUpgrade`
branch:

```dart
if (from < 20) {
  await transitionPreconditionDao.upgradeVerifyingGraphIfDefault();
}
```

New `TransitionPreconditionDao.upgradeVerifyingGraphIfDefault()`: reads
the current `verifying` graph; if its root node's `fieldId ==
'mostRecentChatHasTerminalReply'` with `matchedBranchKind == 'allowed'`
(the exact original single-node fingerprint — i.e. untouched by any
project-level customization), replace it in place with the new two-node
shape from §3.1. Any other shape (a project has already edited this
graph via the Workflow config UI, or it's somehow already been upgraded)
is left untouched. This only ever runs once per existing local database,
same as any other numbered migration branch; a fresh install skips it
entirely (`onCreate` already seeds the new shape directly via
`seedDefaultsIfEmpty`).

## 4. `TicketsCubit` changes

### 4.1 `_verifyGateApproved(String storyOrEpicId)`, and fixing `_designSyncApproved` alongside it

Mirrors `_designSyncApproved` (`tickets_cubit.dart:3064`) with one
correction: the chat-title lookup must use the project's *effective*
stage display name, not a hardcoded literal — `_designSyncApproved`
hardcodes `"Design Sync — "`, which is already latently wrong for any
project that has overridden `designSync`'s display name via
`SddStageConfigRepository` (`_stagePresentName` is override-aware;
`_createStageChat` titles every stage chat through it). This proposal
fixes `_designSyncApproved` itself the same way, in the same pass,
rather than leaving the new method's sibling carrying the bug forward:

```dart
Future<bool> _designSyncApproved(String storyId) async {
  final commentRepo = _commentRepository;
  if (commentRepo == null) return false;
  final prefix = '${await _stagePresentName(SddStage.designSync)} — ';
  final chats = await _repository.getTicketsByParent(
    storyId,
    types: const [TicketType.chat],
  );
  final designSyncChats =
      chats.where((c) => c.title.startsWith(prefix)).toList()
        ..sort((a, b) => b.createdAt.compareTo(a.createdAt));
  // ...unchanged from here: same most-recent-comment / APPROVED check.
```

Only the prefix line changes — the literal `'Design Sync — '` becomes
`'${await _stagePresentName(SddStage.designSync)} — '`. The method is
already `async` (it already awaits `getTicketsByParent`/
`getCommentsForTicket`), so this is a same-signature, same-caller-set
change — no ripple beyond the method body itself.

`_verifyGateApproved` is written the same corrected way from the start:

```dart
Future<bool> _verifyGateApproved(String storyOrEpicId) async {
  final commentRepo = _commentRepository;
  if (commentRepo == null) return false;
  final prefix = '${await _stagePresentName(SddStage.verifying)} — ';
  final chats = await _repository.getTicketsByParent(
    storyOrEpicId,
    types: const [TicketType.chat],
  );
  final verifyChats = chats.where((c) => c.title.startsWith(prefix)).toList()
    ..sort((a, b) => b.createdAt.compareTo(a.createdAt));
  if (verifyChats.isEmpty) return false;
  final comments = await commentRepo.getCommentsForTicket(verifyChats.first.id);
  if (comments.isEmpty) return false;
  final mostRecent = comments.reduce(
    (a, b) => a.createdAt.isAfter(b.createdAt) ? a : b,
  );
  return mostRecent.authorType == CommentAuthorType.ai &&
      mostRecent.content.contains('VERIFY GATE: APPROVED');
}
```

A small private helper, `_mostRecentVerifyChat(String id)`, factors out
the lookup shared by this and §4.5's pending-check, mirroring
`_mostRecentExecutionChat`'s own extraction (`tickets_cubit.dart:4965`).

### 4.2 `_sddStageAdvanceCheck`'s `verifying` branch

Currently `exploring`/`verifying` share one switch case
(`tickets_cubit.dart:2964-2971`) computing only
`mostRecentChatHasTerminalReply`. Split them: `exploring` keeps the
existing single-field context; `verifying` additionally computes
`verifyGateApproved` via §4.1 and passes both into
`TransitionEvalContext`:

```dart
case SddStage.verifying:
  final ready = await _mostRecentChatHasTerminalReply(ticket.id);
  final approved = ready ? await _verifyGateApproved(ticket.id) : false;
  return _resolveTransition(
    SddStage.verifying,
    TransitionEvalContext(
      mostRecentChatHasTerminalReply: ready,
      verifyGateApproved: approved,
    ),
  );
```

(`approved` short-circuits to `false` when there's no reply yet at all,
avoiding a redundant chat-content lookup — `verifyGateApproved`'s node is
unreached in the seeded graph until `mostRecentChatHasTerminalReply`
already matched, but a project could reorder its custom graph, so the
accessor itself should stay defensively cheap either way.)

### 4.3 `_assembleStageContext` — `verifying` prompt

Extend the `verifying`/`archived` context-assembly branch
(`tickets_cubit.dart` near `_assembleStageContext`'s stage-specific
request text) so `verifying` specifically also requests: end the reply
with `VERIFY GATE: APPROVED` or `VERIFY GATE: PENDING`; on `PENDING`,
optionally include a fenced `## Fixes Needed` block — one
`"- Task: <title>"`/`"- Bug: <title>"` line per fix — mirroring
`proposed`'s `## Decomposition` block format exactly (including the
optional `" (blockedBy: <title>)"` suffix already supported there).
`archived`'s own request text (Epic spec synthesis context) is
unaffected.

### 4.4 `_materializeVerifyFixes(Ticket parent, String reply)`

Parses a `## Fixes Needed` block the same way
`_materializeDecomposition` parses `## Decomposition`
(`tickets_cubit.dart:6698`) — reusing its line-parsing helper rather than
duplicating it, parameterized by the block header and the child
type keyword (`Task`/`Bug`) instead of `Story`/`Task`. Creates each
listed child under `parent` (`task`/`bug` per its line prefix, default
creation status, `blockedBy` links resolved against earlier lines in the
same block exactly as `_materializeDecomposition` already does).
Called from `_runStageChatTurn`'s `verifying`-stage completion path only
when the reply contains `VERIFY GATE: PENDING` — mirrors the existing
`if stage == proposed` conditional call to `_materializeDecomposition`
there (`tickets_cubit.dart:5376`). A `PENDING` reply with no `## Fixes
Needed` block is valid and materializes nothing — the manual retry bar
(§5.1) still covers that case; only the automatic retry tier (§5.2)
depends on fix Tasks existing at all, since it triggers off "all children
done."

### 4.5 `retryVerify(Ticket verifyingChat)`

Mirrors `retryDesignSync` (`tickets_cubit.dart:2763`) exactly — same
guard shape (`verifyingChat.type != TicketType.chat` → return; parent
must still be at `SddStage.verifying`), same
`_assembleStageContext(parent, SddStage.verifying)` re-context, same
`ChatCubit.runChatTurn` call via `_resolveModelAndProvider
(SddStage.verifying.modelPhase)`. Reentrancy for the *automatic* trigger
(§4.6) is guarded there, not here — this method itself stays a plain,
repeatable action, the same way `retryDesignSync` is.

### 4.6 `_maybeRetryPendingVerify(Ticket task)`

Called from `updateTicketStatus`'s post-write side effects
(`tickets_cubit.dart:1893-1906`), alongside the existing
`_maybeAutoLinkToSpec` call, under a new condition parallel to it:

```dart
if (updated.type.isExecutable &&
    _roleOf(status) == WorkflowStatusRole.done) {
  unawaited(_maybeRetryPendingVerify(updated));
}
```

(also mirrored in `changeTicketStatus`'s equivalent status-write path,
the same way `_maybeAutoLinkToSpec` is reachable from both today).

Logic:

1. Fetch `task.parentId`'s ticket. If it's `null` or not `epic`/`story`,
   return — a Task's parent is always a Story/Epic or nothing
   (`_governingStory`'s own documented invariant), so no walking loop is
   needed, just a direct fetch.
2. If that parent's `sddStage != SddStage.verifying`, return.
3. If `_verifyGateApproved(parent.id)` is already `true`, return —
   nothing to retry.
4. Look up the Verifying-stage chat via `_mostRecentVerifyChat` (§4.1);
   if none, or its most recent comment isn't an `ai` reply containing
   `VERIFY GATE: PENDING`, return — not an explicit pending verdict yet
   (still running, or never started).
5. Fetch `parent`'s current Task/Bug children
   (`TicketTypeHierarchy.executableTypes`) and check
   `_allChildrenComplete(children, TicketType.task)` (existing helper,
   `tickets_cubit.dart:2892`). If `false`, return — more fixes still
   outstanding.
6. Resolve `AutomationContext.verifyGateRetry`'s confidence via
   `_automationSettingsRepository?.getConfidence(...)` (defaults to
   behaving as if unset the same way every other optional-repository
   context does — `null` repository or unset value effectively no-ops,
   consistent with this cubit's existing "no repository, no
   automation" posture). `auto`: guard against concurrent re-entrancy
   using a new `_inFlightVerifyRetryIds` set (mirrors
   `_inFlightStageAdvanceIds`'s exact purpose, scoped separately since
   this isn't itself a stage advance), then call `retryVerify` on the
   found chat, `unawaited`. `gated`/`manual`: no direct action here —
   §5.2 renders the "ready to retry" tier for both, differing only in
   whether that tier's action is a confirm banner or a plain button
   (the same distinction `_SddStageSection`'s existing advance tier
   already draws between the two).

# Aion — Verify-stage quality gate: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [SDD Ticket Execution Spec](./Aion%20SDD%20Ticket%20Execution%20Spec.md) (§2 `_SddStageSection`), and the [SDD Design Gate Spec](./Aion%20SDD%20Design%20Gate%20Spec.md) (§4 `_RetryValidationButton`). References `AionColors`, `AionText`, `AionRadius`, `AionSpacing`, and `TicketDetailScreen` by name.

This change puts a content quality gate on the SDD `verifying → archived` transition. A Verifying-stage chat reply now ends in `VERIFY GATE: APPROVED` or `VERIFY GATE: PENDING`, mirroring the Design Sync gate. On `PENDING` two surfaces appear, **both on existing screens — no new screens**:

- **`TicketDetailScreen`** (`epic` / `story`) — a new **"Ready to retry verification"** footer tier in the `_SddStageSection` slot (§1), in the same three confidence-driven treatments the existing "Advance to next stage" tier uses.
- **`TicketDetailScreen`** (`chat`) — the **already-shipped** `_RetryValidationButton` gains a new placement/trigger: a horizontally-inset bar above the composer in a Verifying-stage chat (§2). The button is not redesigned; only its slot, trigger, and loading state are specified here.

**No Material widgets anywhere.** Every surface is `DecoratedBox` / `Padding` / `Row` / `Column` / `GestureDetector` / `MouseRegion` / `AnimatedSize` / `AnimatedOpacity` / `AnimatedScale` / `RotationTransition` / `CustomPaint`. No `Card`, `ElevatedButton`, `TextButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `InkWell`, or `Chip`.

Themes: **Arctic** (light) and **Obsidian** (dark). **All layout, dimensions, padding, radius, typography, and motion are identical between themes** — only color tokens differ, and every color below is a named `AionColors` token that already resolves per theme. Hex is given as `Arctic / Obsidian` for reference only; implement against the token. Translucent fills are always `token.withOpacity(x)`, never hardcoded ARGB. `fillAlpha` = `0.11` Arctic / `0.16` Obsidian.

**No new color, typography, radius, or spacing tokens are required.** One enum and one derived flag are added (§4).

## 1. "Ready to retry verification" footer tier (`epic` / `story` detail)

### 1.0 Slot, trigger, and shared geometry

- **Slot:** the footer of the existing `_SddStageSection`, directly below the current-stage line (`"Verifying"`), `gap: 12` from it — the same slot the "Advance to next stage" tier occupies. The two tiers are mutually exclusive: while a `PENDING` verdict is unresolved the advance tier is suppressed (advance to `archived` is blocked by the gate), and the retry tier takes its place.
- **Visibility rule:** render only when *all* hold —
  1. current stage is `verify`;
  2. the ticket's Verifying-stage chat's latest AI reply carries `VerifyGateStatus.pending`;
  3. every fix Task/Bug spawned by that `PENDING` verdict has `status == done` (`pendingFixesRemaining == 0`).
  While fixes are still open, the section shows the existing not-ready hint row instead (§1.4).
- **Which treatment renders** is driven by the project's existing automation-confidence setting for the stage, exactly as the advance tier: `gated` → §1.1, `manual` → §1.2, `auto` → §1.3.
- **Width:** the tier fills the section's content width (`double.infinity` inside the section's `EdgeInsets.symmetric(horizontal: 22)` padding), except the manual button, which hugs its content (`MainAxisSize.min`, left-aligned).
- **Enter/exit:** the tier grows in via `AnimatedSize` (`160ms`, `Curves.easeOut`) when the last fix Task flips to Done, and collapses the same way once the retry is dispatched (replaced by the in-flight state, §1.1.4).

### 1.1 Gated state (confidence = `gated`)

Identical geometry to the existing advance banner (SDD Ticket Execution §2.3); only the leading glyph motif, the copy, and the absence of a sub-line differ.

**1.1.1 Container**

| Property | Value |
|---|---|
| Widget | `DecoratedBox` → `Padding` → `Row` |
| Fill | `primary.withOpacity(fillAlpha)` — `#2E86D4 @ 0.11 / #9366FF @ 0.16` |
| Border | `1px solid primary.withOpacity(isDark ? 0.42 : 0.28)` |
| Radius | `BorderRadius.circular(12)` (`AionRadius.lg`) |
| Shadow | none |
| Padding | `EdgeInsets.fromLTRB(14, 12, 12, 12)` |
| Layout | `Row`, `gap: AionSpacing.sp12`, `crossAxisAlignment: center` |
| Height | intrinsic — `~56` at default text scale |

**1.1.2 Contents**

- **Leading glyph:** `arrows-clockwise` (`↻`), `18px`, color `primary`. *(The advance banner uses `sparkle`; the retry motif is the one distinguishing mark, and it reuses the same glyph already on `_RetryValidationButton` so the two retry surfaces read as one action. No color change — still `primary`.)*
- **Title:** `"Ready to retry verification"`, `AionText.cardTitle` (14 / w600), color `textPrimary`, `Expanded`, `maxLines: 1`, `TextOverflow.ellipsis`.
- **No sub-line.** The advance banner's second line names a stage-specific precondition; this tier only ever means one thing, so the text column is a single `Text`, not a `Column`. Vertical centering keeps the banner's `~56` height unchanged.
- **Confirm button:** compact filled primary — label `"Retry"`, see §1.1.3. *(The banner title already names the action; a `"Retry verification"` label plus the glyph, gaps, and dismiss leaves under `122` for the title at the `336` phone content width, forcing it to ellipsize. The shipped advance banner solves this the same way — its title carries the target, its button reads just `"Advance"`. The manual button (§1.2) keeps the full `"Retry verification"` label because it stands alone with no title above it.)*
- **Dismiss affordance:** `26×26` `GestureDetector`, `close` (`×`) glyph `13px` color `textMuted`, radius `AionRadius.iconBtnSm` (8), transparent fill, `gap: 4` after the button. Dismissing collapses the banner (`AnimatedSize` 160ms) and falls back to the manual presentation (§1.2) for the rest of the session — same behavior as the advance banner.

**1.1.3 Confirm button states** (`"Retry"`, `AionText.button` 14 / w700, `#FFFFFF`, padding `EdgeInsets.symmetric(horizontal: 15, vertical: 9)`, radius `AionRadius.md` (10))

| State | Fill | Shadow | Text / extra |
|---|---|---|---|
| **Default** | `primary` | `BoxShadow(color: primary.withOpacity(isDark ? 0.60 : 0.45), blurRadius: 18, spreadRadius: -9, offset: Offset(0, 8))` | `#FFFFFF` |
| **Hover** | `primaryHover` (`#1E6DB6 / #A886FF`) | same | `MouseRegion(cursor: SystemMouseCursors.click)` |
| **Focused** (keyboard) | `primary` | glow + `BoxShadow(color: primary.withOpacity(isDark ? 0.30 : 0.16), blurRadius: 0, spreadRadius: 3)` | — |
| **Pressed** | `primaryHover` | glow | `AnimatedScale` → `0.98`, 80ms, on `onTapDown` |
| **Disabled / in flight** | `primary.withOpacity(0.45)` | none | text `#FFFFFF.withOpacity(0.7)`; wrapped in `IgnorePointer` |
| **Error** | n/a — a failed retry produces a new AI reply ending in `VERIFY GATE: PENDING`, which simply re-shows the tier enabled |

**1.1.4 In-flight**

On confirm, the banner keeps its container and title and swaps the button to its disabled state; the leading `↻` glyph spins (`RotationTransition`, 900ms linear loop) — never a `CircularProgressIndicator`. The dismiss affordance is hidden while in flight. When the new verdict arrives: `APPROVED` → the whole tier collapses (`AnimatedSize` 160ms) and the stage advances; `PENDING` → the tier returns to §1.1.1 and the new fix Tasks reset `pendingFixesRemaining`.
