# Ticket Graph And Embedding Context Enrichment

# Proposal: Ticket-graph and embedding context enrichment for spawned chats

## Problem

Two call sites in `TicketsCubit` spawn a `chat`-type ticket with an
auto-assembled, plain-text opening context comment, and both hand the
model far less than what Aion already knows about the ticket:

- **`_assembleExecutionContext`** (coding execution, the *only* stage run
  with `toolsEnabled: true`) passes the Task's title/description plus the
  project's effective `conventions/architecture-conventions` content —
  nothing about the Task's parent Story, its sibling Tasks, or any
  `blockedBy`/`relatesTo` ticket. A tool-enabled model that actually needs
  that context has to spend live `grep`/read tool calls rediscovering it
  from `tickets/<id>.md` files inside the worktree, one call at a time.
- **`_assembleStageContext`** (every SDD-stage chat spawned by
  `advanceSddStage` — `designBrief`/`designSync`/`proposed`/`verifying`/
  `archived` — and re-run verbatim by `retryDesignSync`) passes parent
  title/description plus whatever narrow, stage-specific extra its own
  branch adds (children for `verifying`/`archived`, design-token file
  contents for `designBrief`/`designSync`, the one design Page linked via
  `_linkedDesignPage`). These chats run with `toolsEnabled: false` — no
  file/git/bash access at all — so a Story with a `blockedBy` ticket
  carrying important constraints, or an Epic whose sibling Story already
  covered related ground, is invisible to the model with no way for it to
  go look.

This is the known gap already recorded in `aion-arch/specs/tickets.md`:
"No repo-map-lite or embedding-based context enrichment for a spawned
SDD-stage chat's initial message — plain-text parent fields and direct
hierarchy/`relatesTo` links only, no similarity search, no tree-sitter
symbol index." Explored in `aion-arch/ideas/ticket-graph-and-embedding-
context-enrichment.md`.

## What we're building

One shared helper, `TicketContextEnricher.relatedTicketsSection`,
consumed by both `_assembleExecutionContext` and `_assembleStageContext`
(which automatically covers `retryDesignSync`'s re-assembly too, since it
calls `_assembleStageContext` directly — no separate wiring needed). It
assembles a `## Related tickets` Markdown section from two passes over
the ticket graph, entirely local (Drift reads + the existing on-device
[`EmbeddingProvider`](../../project.md), no network call beyond what the
call site was already going to make for its own model turn):

1. **Structured walk** — the ticket's full ancestor chain (walking
   `parentId` upward) plus every direct `TicketLink` row
   (`TicketLinkRepository.getLinksForTicket`, any type, any ticket type).
   Generalizes `_linkedDesignPage`'s existing single-link, `page`-only
   walk into something reusable for every relationship and every ticket.
2. **Embedding-similarity walk** — cosine-similarity scan (mirrors
   `TicketEstimationSuggester`'s existing comparable-ticket scan) over
   every other live ticket's already-populated `embedding` column,
   querying with the source ticket's own title+description. Included
   only above a fixed similarity threshold, capped at a top-K fallback,
   excluding the source ticket and anything the structured walk already
   surfaced (no duplication).

Each surfaced ticket is rendered as one bullet with its title, type,
relationship (`ancestor` / `blocks` / `blockedBy` / `relatesTo` /
`duplicates` / `duplicatedBy` / `similar`), and a length-capped snippet
of its description — the actual content a tool-enabled model would
otherwise have spent a `grep`+read round trip to obtain, and the only
way a tool-disabled SDD-stage chat can see it at all.

## Why this shape

- **Reuses proven infrastructure.** `Ticket.embedding` is already
  populated on every create/edit; brute-force cosine similarity is
  already the accepted pattern for this codebase (`project.md`'s
  Foundational Decision #1, already exercised by
  `TicketDocumentSearchService` and `TicketEstimationSuggester`). No new
  dependency, no new storage.
- **One helper, two call sites.** Coding execution gets fewer wasted tool
  calls; SDD-stage chats — which have no tool access at all — get
  materially richer context than today's bare title/description, with no
  new call-site-specific logic.
- **`retryDesignSync` falls out for free.** It already re-runs
  `_assembleStageContext` verbatim to pick up the Page's *current*
  content on retry; wiring the enrichment into that shared method means
  the retry path automatically re-runs the structured+embedding walk too,
  with no separate change needed there.

## Out of scope

- Source-code-level context (repo-map-lite, tree-sitter symbol indexing).
  Confirmed during brainstorming: Aion has no plans to build this: tickets
  are the only structure it reasons over, not the project's source tree.
- Tuning the exact similarity threshold/top-K values beyond the sane
  defaults chosen here (see `design.md`) — flagged as adjustable
  constants, not a configurable setting.
- A global context-size token budget across the whole assembled prompt.
  Bounded instead via a per-ticket description-snippet cap and the
  embedding walk's top-K cap (see `design.md`'s Decisions section) —
  consistent with this app's "brute-force... sufficient at personal
  scale" philosophy rather than introducing new budgeting machinery.
- Live invalidation/refresh if a surfaced ticket is edited or deleted
  mid-run. The assembled context stays a one-shot snapshot, exactly like
  every other piece of context these two methods already assemble.
