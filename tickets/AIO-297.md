# Baseline Version Upgrade Flow

# Proposal: Baseline version upgrade flow for an existing project

## Source

`aion-arch/ideas/baseline-version-upgrade-flow-for-an-existing-project.md`
(`status: explored`, two brainstorm sessions, 2026-07-24). All six of that
idea's questions are answered and its blocking dependency
(`project-type-aware-conventions-and-verification`, providing the setup-time
tailoring mechanism this proposal reuses) has since shipped (`status:
archived`, 2026-07-25). `/explore` re-verified the idea's claims against the
current codebase before this proposal was written — see the Corrections
section in design.md for where the idea's assumptions didn't quite match
what's actually built.

## Problem

`Project.baselineVersion` (`aion/lib/features/projects/domain/entities/
project.dart`) is pinned once at creation and never mutated again anywhere in
the codebase — its own doc comment says so explicitly. `aion-arch/specs/
projects.md` lists this as a known open question: a project pinned to an old
baseline (`0.1.0`/`0.2.0`) permanently resolves `skills/verify` and other
assets to stale content, even after Aion ships a newer, better baseline
(`0.3.0`'s self-contained, stack-agnostic skill set). There is no way,
today, for an existing project to move forward.

## What's building

1. **Lazy, per-project upgrade offer.** The first time a project is
   switched into (`ActiveProjectCubit.switchTo`) while a newer baseline
   version than its pin is bundled in the running build, `TicketsListScreen`
   shows a one-time, dismissible banner (mirroring `CodebaseAnalysisBanner`'s
   existing shape) offering to upgrade. Declining just hides that instance —
   the same check re-runs, and the same banner re-appears, the next time the
   project is opened, for as long as a newer version remains available.
2. **Straight version-pin bump on accept.** No diff/review UI. Accepting
   updates the registry DB row and (desktop only) rewrites `<rootPath>/.aion/
   manifest.json` to the new version. Existing `ProjectOverride` files keep
   applying exactly as before — they shadow by asset key, independent of
   version, so no override migration is needed.
3. **Tailoring for the one asset kind that can actually be tailored.**
   Reuses `BaselineTailoringService`'s existing detected-stack template
   mechanism — but only for `conventions/architecture-conventions` (the one
   asset kind that mechanism knows how to fill in). See design.md's
   Corrections §1 for why this proposal narrows the source idea's more
   general "tailor new assets" language to this one concrete case.
4. **Orphaned overrides are left alone.** If the new version removes an
   asset key an existing override was shadowing, that override file just
   stays on disk, unused. No cleanup, no warning.
5. **Manual "Upgrade" action in Settings**, always available regardless of
   whether the lazy banner has already been shown/declined this session.

## Non-goals (this proposal)

- **Any diff/review UI for what changed between baseline versions.** The
  idea explicitly resolved this as a straight bump, trusting the existing
  per-key override-matching mechanism.
- **Full agentic tailoring of newly-introduced assets.** `aion-arch/specs/
  projects.md`'s "Full agentic baseline tailoring" open question remains
  unresolved — this proposal only reuses the already-shipped *shallow*,
  marker-file-detection tailoring path. There is no per-project persisted
  record of which summarization depth (shallow/full) a project originally
  chose at creation (confirmed empirically — `SummarizationDepth` is never
  written to `Project`/`RegistryDatabase` anywhere in the codebase), so
  "tailor per the project's original depth choice" is not something this
  proposal can actually implement; see design.md's Corrections §1.
- **Network/update-checking of any kind.** "Is a newer version available"
  is a pure local comparison against `BundledBaselineRepository`'s
  hardcoded `_bundledVersions` list — whatever's compiled into the
  currently-running build. No GitHub polling, no release feed. (Real
  app-distribution/update-checking is out of scope entirely — Aion has no
  installed users yet to distribute to.)
- **Tailoring any asset kind other than `architectureConvention`.** A
  newly-introduced `skill`- or `modelConfig`-kind asset simply resolves to
  its bundled default, same as any other unoverridden asset today — no
  special handling, because no generic per-kind template content exists to
  write for those kinds.
- **Mobile/web override tailoring.** Overrides remain desktop-only
  (`rootPath == null` short-circuits both the manifest rewrite and the
  tailoring step) — unchanged from today's existing override system.
