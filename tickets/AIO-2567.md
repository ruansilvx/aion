      **Evidence (code-level trace-through, not live-fired):**
      - **Write site (one):** `onConsumptionSignal` (`tickets_cubit.dart`
        ~L3425), the sole place `_overageDetectedThisSession` is set to
        `true`. Wired into *both* `ChatCubit.runChatTurn` calls inside
        `_runCodingExecution`'s `while (true)` retry loop — the implement
        turn (~L3466) and the verify turn (~L3505) — via the same closure
        reused across every retry iteration, so a signal fired on any
        attempt, either turn, is captured.
      - **Read site 1 — `_effectiveCodingExecutionConfidence`** (~L3841):
        forces `AutomationConfidence.gated` once the flag is `true`,
        regardless of the persisted `AutomationContext.codingExecution`
        value. Called from two places, confirmed to share this one
        function so they can't disagree: (a) `_runCodingExecution`'s
        single unconditional completion point (~L3631–3642, after the
        `try/catch/finally`, gated on `_executionSucceededWithPr` — runs
        whether the loop exited via verified success, cancellation, or a
        hard error, since it's outside the loop and outside the
        try/catch); (b) `getTicketById`'s live `executionAwaitingReview`
        computation (~L6317–6323), independently re-deriving the same
        confidence for the UI's "ready for review" banner.
      - **Read site 2 — `_effectiveConcurrencyCeiling`** (~L3871): caps
        concurrency to `1` for the rest of the session once the flag is
        `true` — the same reactive-budget precedent applied to scheduling
        rather than confidence. Confirmed as a *separate* mechanism from
        the two `AutomationConfidence` read sites above, not a third
        confidence check.
      - **Finding — not itself a bug to fix here (T15 is trace-only, no
        source edits), but worth recording as a real gap for a future
        change:** `_effectiveCodingExecutionRetryConfidence` (~L3821,
        governing whether a failed verify turn retries with a fresh
        `auto` tool-enabled attempt, ~L3528–3535) does **not** read
        `_overageDetectedThisSession` at all — it only forces `gated`
        once `attempt > _maxVerifyRetries`, independent of session
        overage state. Its own doc comment's "mirrors
        `_effectiveCodingExecutionConfidence`'s own overage-forces-
        `gated` precedent" describes the same *shape* (force `gated`
        under an override condition), not the same *trigger* — so today,
        an overage detected mid-run does not prevent a subsequent
        verify-failure retry from launching another tool-enabled `auto`
        turn on `AutomationContext.codingExecutionRetry`, if that context
        is independently configured to `auto`. Only the run's *terminal*
        review-flip (read site 1) and its concurrency ceiling (read site
        2) are overage-protected; the mid-run retry decision is not.
