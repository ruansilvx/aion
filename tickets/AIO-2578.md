# Spec Delta: v1 Release Readiness

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/release.md`, `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (20/22 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

## ADDED

- **`aion/assets/icons/aion_icon.png` is real Aion artwork**, no longer
  Flutter's default template icon. `windows/runner/resources/app_icon.ico`
  is regenerated from it (16/32/48/256px). The Linux AppImage picks up
  the same PNG automatically via `linux/packaging/build_appimage.sh`.
- **`Board`/`Filters`/`Columns`/bulk status menu/ticket-detail status
  picker render a project's live, reconfigured `WorkflowStatus` set**,
  not the fixed 6-status default — `WorkflowConfigCubit` is now provided
  shell-wide (`WorkspaceShell`), and `tickets_board_view.dart` (both its
  own board columns and `MoveToStatusMenu`), `tickets_list_screen.dart`,
  `ticket_filter_popover.dart`, `ticket_columns_popover.dart`,
  `ticket_selection_bar.dart`'s `BulkStatusMenu`, and
  `ticket_metadata_section.dart`'s status picker all derive their status
  list from it (shared-base-only for cross-type surfaces, base + type
  extensions for a single ticket's own picker) via two new top-level
  resolver functions, `resolveSharedStatusOrder`/
  `resolveStatusOrderForType`, built on two new `WorkflowConfigLoaded`
  getters, `sharedBaseStatuses` and `effectiveStatusesForType`.
- **The release pipeline's Linux build no longer blocks a release.**
  `build-linux` in `.github/workflows/release.yml` runs with
  `continue-on-error: true`; `publish-release` degrades to a
  Windows-only GitHub Release if the Linux AppImage artifact is absent,
  rather than failing outright.

## Explicitly unchanged (called out to prevent scope creep during `/apply`)

- **No new `ProviderRegistry` implementation, no predictive budget
  gate, no mobile/web provider work.** Automation-confidence validation
  (item 4) exercises what's already built; it adds no new automated
  decision point.
- **No accessibility audit, no mobile `LongPressDraggable` verification,
  no macOS/Linux desktop provider verification.** Only the specific
  Windows flow named above is added to the verified-flows list.
- **No bulk reparent/bulk type edit, no page-side link creation, no
  cross-device sync.** Untouched by this change.
- **`WorkflowStatusSettingsScreen`'s and
  `WorkflowPromptTemplatesScreen`'s existing per-route
  `WorkflowConfigCubit` construction is untouched** — the new
  shell-wide provider is additive, not a replacement for those two
  routes' own instances.
- **No change to `ticketStatusLabel`'s localization/humanization
  logic** — only the set/order of statuses fed into it changes.
