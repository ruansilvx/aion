# Design: Configurable Ticket Workflow (Phase 1)

## §1. Domain layer

### §1.1. `WorkflowStatusRole`

New file `domain/enums/workflow_status_role.dart`:

```dart
/// The semantic slot a [WorkflowStatus] fills in TicketsCubit's existing
/// gate/trigger logic — the generalized replacement for literal
/// `TicketStatus.inProgress`/`.inReview`/`.done` comparisons. Exactly one
/// shared-base [WorkflowStatus] must hold each value at all times;
/// [WorkflowConfigCubit] enforces this invariant, never the repository.
enum WorkflowStatusRole {
  /// Fills today's `TicketStatus.inProgress` slot: the transition that
  /// starts coding execution (`TicketsCubit._interceptTaskExecutionTrigger`)
  /// and that the blocked-dependency gate
  /// (`_interceptBlockedDependencyTrigger`) checks against.
  executionTrigger,

  /// Fills today's `TicketStatus.inReview` slot: the status a successful
  /// coding-execution run auto-writes to when
  /// `AutomationConfidence.auto` (`_runCodingExecution`'s PR-confirmed
  /// path).
  reviewReady,

  /// Fills today's `TicketStatus.done` slot: what the blocked-dependency
  /// gate's blocker-resolution and `SddStage.proposed`/`designSync`'s
  /// children-completion checks require.
  done,
}
```

### §1.2. `WorkflowStatus` entity

New file `domain/entities/workflow_status.dart`:

```dart
class WorkflowStatus extends Equatable {
  final String id;              // UUID v4
  final String name;             // written to Ticket.status
  final String displayName;
  final TicketType? ticketType;  // null = shared base; else a per-type extension
  final int sortOrder;
  final WorkflowStatusRole? role; // null for most statuses; base-set only
  // ... const constructor, props, per project.md's dartdoc-every-field rule
}
```

`name` is unique within its scope: unique among all base-set entries, and
unique among a given `ticketType`'s extensions (a base name and an
extension name may collide across different types without conflict,
since `getForType` never merges two different types together).

### §1.3. Default baseline preset

New file `domain/entities/default_workflow_statuses.dart` — a single
`const List<WorkflowStatus>` constant, `defaultWorkflowStatuses`, seeded
into a brand-new project's `WorkflowStatusesTable` (and backfilled for
every pre-existing project on schema upgrade — see §2.2) reproducing
today's exact hardcoded behavior:

| name | displayName | ticketType | sortOrder | role |
|---|---|---|---|---|
| `backlog` | Backlog | `null` | 0 | — |
| `todo` | Todo | `null` | 1 | — |
| `inProgress` | In Progress | `null` | 2 | `executionTrigger` |
| `inReview` | In Review | `null` | 3 | `reviewReady` |
| `done` | Done | `null` | 4 | `done` |
| `cancelled` | Cancelled | `null` | 5 | — |

### §1.4. `TicketStatus` enum removal

`domain/enums/ticket_status.dart` is deleted. Every reference across the
codebase (grep found ~20 files) migrates to either a raw `String` (where
code just needs *a* status name — e.g. `Ticket.status` itself) or a
`WorkflowStatus`/role lookup (where code needs to know what a status
*means* — the former gate-check call sites). `Ticket.status`'s type
changes from `TicketStatus` to `String`; its dartdoc is rewritten to
describe it as a project-defined status name, resolved against
`WorkflowStatusRepository`/`WorkflowConfigCubit` rather than a fixed enum.

### §1.5. `SddStageConfigRepository`

New file `domain/repositories/sdd_stage_config_repository.dart` — mirrors
`AutomationSettingsRepository`'s exact shape (the correct-fit precedent
per `/explore`, not `ProjectOverride`):

```dart
abstract interface class SddStageConfigRepository {
  /// Defaults to `true` — matches today's automatic per-Story heuristic
  /// being effectively "on."
  Future<bool> getDesignStagesEnabled();
  Future<void> setDesignStagesEnabled(bool enabled);

  /// `null` means "use SddStage's own hardcoded display name."
  Future<String?> getDisplayNameOverride(SddStage stage);
  Future<void> setDisplayNameOverride(SddStage stage, String? displayName);
```

### §1.6. `WorkflowStatusRepository` interface

New file `domain/repositories/workflow_status_repository.dart` — a dumb
persistence layer (no validation; invariants live in `WorkflowConfigCubit`
per `project.md`'s Cubit-vs-repository split):

```dart
abstract interface class WorkflowStatusRepository {
  Future<List<WorkflowStatus>> getAll();
  Future<void> create(WorkflowStatus status);
  Future<void> update(WorkflowStatus status);
  Future<void> delete(String id);
  Future<void> reorder(List<String> idsInSortOrder);
  /// Seeds `defaultWorkflowStatuses` iff the table is currently empty —
  /// called once at app startup for the active project, and by the
  /// schema-15 migration's backfill for every pre-existing project.
  Future<void> seedDefaultsIfEmpty();
}
```

`getForType(TicketType? type)`-shaped merging (base ∪ that type's
extensions, sorted by `sortOrder`) is a pure function over `getAll()`'s
result, not a repository method — it belongs in `WorkflowConfigCubit` or
a domain util, consistent with keeping the repository dumb.

## §2. Data layer

### §2.1. `WorkflowStatusesTable`

New file `data/models/workflow_status_table.dart`, following
`ExecutionQueueTable`'s exact precedent (no FK constraints, matching
every other table in this schema):

```dart
@DataClassName('WorkflowStatusData')
class WorkflowStatusesTable extends Table {
  @override
  String get tableName => 'workflow_statuses';

  TextColumn get id => text()();
  TextColumn get name => text()();
  TextColumn get displayName => text().named('display_name')();
  TextColumn get ticketType => text().named('ticket_type').nullable()();
  IntColumn get sortOrder => integer().named('sort_order')();
  TextColumn get role => text().nullable()();

  @override
  Set<Column> get primaryKey => {id};
}
```

`ticketType`/`role` store `TicketType.name`/`WorkflowStatusRole.name`
respectively (or `null`), the same string-encoding convention
`TicketModel.sddStage` already uses for `SddStage.name`.

### §2.2. `app_database.dart` — schema 14 → 15

Add `WorkflowStatusesTable` to `@DriftDatabase(tables: [...])`. New
`MigrationStrategy` branches:

```dart
onCreate: (m) async {
  await m.createAll();
  // ...existing seed...
  await workflowStatusDao.seedDefaultsIfEmpty(); // fresh install
},
onUpgrade: (m, from, to) async {
  // ...existing from < 14 branches, unchanged...
  if (from < 15) {
    await m.createTable(workflowStatusesTable);
    await workflowStatusDao.seedDefaultsIfEmpty(); // backfill for every
                                                     // pre-existing project
  }
},
```

No `tickets.status` column change — it was already a raw `TextColumn`
(`ticket_model.dart:30`), confirmed during `/explore`.

### §2.3. `WorkflowStatusDao` / `DriftWorkflowStatusRepository`

`data/daos/workflow_status_dao.dart` follows `ExecutionQueueDao`'s exact

### §2.4. `drift_ticket_repository.dart` — status mapping simplification

## §3. `TicketsCubit` gate-check migration

Every literal `TicketStatus.x` comparison found during `/explore` becomes
a role lookup against a small in-memory cache, `List<WorkflowStatus>
_workflowStatuses`, populated by a new constructor-injected
`WorkflowStatusRepository` and refreshed the same way
`AutomationSettingsRepository`'s consumers already refresh cached config
— loaded once in the constructor, re-read whenever `WorkflowConfigCubit`
persists a change (via a `Stream<void>`-shaped "config changed" signal
the two Cubits share through the repository layer, not a direct Cubit-to-
Cubit reference — Aion's Cubits communicate through shared repositories,
never each other directly).

New private helper on `TicketsCubit`:

```dart
/// Resolves [status] (a raw Ticket.status string) to its configured
/// WorkflowStatus, or `null` if it's a per-type extension not in
/// [_workflowStatuses]'s currently-cached scope. Existence beyond the
/// cache is defensive only — a status a project has since deleted still
/// round-trips safely as "no role."
WorkflowStatus? _resolveStatus(String status) =>
    _workflowStatuses.where((s) => s.name == status).firstOrNull;

WorkflowStatusRole? _roleOf(String status) => _resolveStatus(status)?.role;
```

Call-site migration (file: line references from `/explore`):

| Today | `tickets_cubit.dart` | Becomes |
|---|---|---|
| `status == TicketStatus.inProgress` | `_interceptBlockedDependencyTrigger`, `_interceptTaskExecutionTrigger`, `updateTicketStatus`, `updateStatusForTickets` | `_roleOf(status) == WorkflowStatusRole.executionTrigger` |
| `byId[blockerId]?.status != TicketStatus.done` | `_isTicketBlocked` (both call sites) | `_roleOf(byId[blockerId]?.status) != WorkflowStatusRole.done` |
| `updateTicketStatus(task.id, TicketStatus.inReview)` | `_runCodingExecution`'s PR-confirmed path | resolve the current `reviewReady`-role status's `name`, write that string |
| `c.status == TicketStatus.done` | `_sddStageAdvanceCheck`'s `proposed` branch | `_roleOf(c.status) == WorkflowStatusRole.done` |
| `t.status == TicketStatus.done` | `_sddStageAdvanceCheck`'s `designSync` branch | `_roleOf(t.status) == WorkflowStatusRole.done` |
| `status: TicketStatus.backlog` (every ticket-creation default) | `createTicket` and every other creation call site | the shared base set's lowest-`sortOrder` status's `name` |

`_storyNeedsDesignReview` gains one new short-circuit at its top:
`if (!(await _sddStageConfigRepository.getDesignStagesEnabled())) return
false;` — before its existing per-Story child-signal heuristic, which is
otherwise untouched.

The stage-display-name switch (`sddStageDisplayName` or equivalent,
around line 4536) resolves through `_sddStageConfigRepository
.getDisplayNameOverride(stage) ?? <today's hardcoded literal>`.

## §4. `WorkflowConfigCubit`

New file `presentation/cubit/workflow_config_cubit.dart` — owns
`WorkflowStatus` CRUD/reorder and the two `SddStageConfigRepository`
settings, enforcing the invariants `TicketsCubit` itself never checks
(domain logic lives in the Cubit, not the repository, per `project.md`):

```dart
class WorkflowConfigCubit extends Cubit<WorkflowConfigState> {
  WorkflowConfigCubit(this._statusRepository, this._sddStageConfigRepository)
      : super(WorkflowConfigInitial());

  Future<void> load();  // -> WorkflowConfigLoaded(statuses, designStagesEnabled, stageNameOverrides)

  /// Rejects (emits WorkflowConfigError, re-emits the unchanged Loaded
  /// state) if `status.name` isn't unique in its scope.
  Future<void> createStatus(WorkflowStatus status);

  /// Rejects if this update would remove the last shared-base status
  /// holding [WorkflowStatus.role] — every role must always resolve.
  Future<void> updateStatus(WorkflowStatus status);

  /// Same role-emptying rejection as updateStatus; also rejects deleting
  /// a status any live ticket currently sits at (Phase 1 has no
  /// migration story — see proposal.md's Non-goals).
  Future<void> deleteStatus(String id);

  Future<void> reorderStatuses(List<String> idsInOrder);

  Future<void> setDesignStagesEnabled(bool enabled);
  Future<void> setStageDisplayNameOverride(SddStage stage, String? name);
}
```

# Aion — Configurable Ticket Workflow: Component Spec

Implementation-ready spec for `WorkflowStatusSettingsScreen` — a new Settings screen where a project customizes its ticket workflow instead of inheriting Aion's fixed defaults. Two sections: **Ticket Statuses** (per-type-scoped, reorderable status list with Base-only workflow roles and an inline add form) and **SDD Stages** (one gating toggle plus five stage-label rename fields). Reached from the same secondary-actions popover as the existing provider Settings screen (see [Aion Provider Configuration Spec](./Aion%20Provider%20Configuration%20Spec.md) §7).

**No Material widgets or types anywhere.** Every component below is built from `flutter/widgets.dart` primitives only: `DecoratedBox`, `Container`, `GestureDetector`, `MouseRegion`, `FocusableActionDetector`, `CustomPaint`, `Row`, `Column`, `Align`, `Padding`, `ReorderableListView`-equivalent hand-rolled drag (see §6.4 — a `Listener`/`GestureDetector` + `AnimatedPositioned` reorder, **not** Material's `ReorderableListView`), `Overlay`/`OverlayEntry`/`CompositedTransformFollower` for the role dropdown. Never `Card`, `ElevatedButton`, `Scaffold`, `AppBar`, `ListTile`, `InkWell`, `Switch`, `Checkbox`, `DropdownButton`, `PopupMenu*`, `TextField` (use the existing `AppTextField`), `ThemeData`, or `ColorScheme`.

- `c` = active `AionColors` (`arctic` / `obsidian`); `isDark` = Obsidian. Both themes share **one** code path; only token values differ. Where a component is identical across themes it is stated explicitly.
- Existing atoms reused unchanged: `AppButton` (primary / ghost, [DS §2.1](./Aion%20Design%20System%20Spec.md)), `AppTextField` (§2.5), `AppDropdown` field geometry. Where this screen's needs diverge (grip-handle row, role chip/dropdown, toggle switch, add-row form) they are specced here as new atoms.
- Translucent fills are always `token.withOpacity(x)` — never hardcoded ARGB. (`withOpacity` per this spec's export convention; the codebase's `withValues(alpha:)` is the equivalent call.)
- `a` = theme chip-fill alpha for role tints: **Arctic `0.13` / Obsidian `0.20`** (a touch stronger than the DS type-chip `fillAlpha` so 10.5px uppercase role text stays legible on the tint).
- Companion mockups: `Aion Configurable Ticket Workflow Mockups.dc.html` — screens `1a` (Base, mid-drag) · `1b` (Bug scope, inherited + extension) · `1c` (add form) · `1d` (SDD stages) · `1e` (role-validation error); component states `2a`–`2e`.

## 1. Models & behavior

### 1.1 Types

```dart
enum TicketType { epic, story, task, bug, resource, page } // + any future types

/// The three Base workflow roles. Exactly one Base status holds each, always.
enum WorkflowRole { none, executionTrigger, reviewReady, done }

class WorkflowStatus {
  final String id;            // stable, immutable — the internal name (e.g. "in_progress")
  final String displayName;   // editable label shown on tickets (e.g. "In Progress")
  final WorkflowRole role;    // meaningful on Base scope only; always none on type scopes
  const WorkflowStatus({required this.id, required this.displayName, this.role = WorkflowRole.none});
}

/// The Base status set plus, per type, an ordered list of type-only extension statuses.
class ProjectWorkflow {
  final List<WorkflowStatus> base;                          // ordered
  final Map<TicketType, List<WorkflowStatus>> extensions;   // ordered, type-only additions
  final bool requireDesignReview;                           // SDD toggle
  final Map<SddStage, String> sddLabels;                    // 5 fixed stages -> display label
}

enum SddStage { exploring, proposed, designBrief, designSync, verifying } // fixed, ordered
```

### 1.2 Scope model

- The **Ticket Statuses** section is scoped by a selector: a shared **Base** scope plus one tab per `TicketType`.
- **Base scope** shows `workflow.base`, fully editable: reorder, rename, add, delete, assign roles.
- **Type scope** (e.g. Bug) shows the Base list as **read-only inherited rows** (dimmed, no role control, no delete) interleaved in Base order with that type's **extension** statuses, which are editable / reorderable / deletable and carry **no role**. Order within a type scope is: extensions may be positioned anywhere relative to inherited rows; inherited rows keep their Base-relative order and cannot be dragged from a type scope.
- The selected scope is view state only (not persisted); it resets to **Base** on entry.

### 1.3 Role invariant (Base only)

- Exactly **one** Base status holds each of `executionTrigger`, `reviewReady`, `done` **at all times**. `none` may be held by any number of statuses.
- Assigning a role to status B **moves** it off whatever status A currently held it (a role is single-holder). The role dropdown reflects the move live.
- **Blocked actions** (surface an inline error, never silently fail — §7):
  - Deleting the sole holder of a role.
  - Setting the sole holder's role to `none` (would leave the role unfilled) — the dropdown keeps the value and shows the error.
- Role controls and the invariant apply on **Base scope only**. Type-scope rows never show a role control.

### 1.4 Delete eligibility

A status row's delete is **disabled** when either:
1. it is the sole holder of a role (§1.3), or
2. it is currently **in use** by ≥1 live ticket in this project.

Disabled delete is dimmed (§4.5) and, on tap/hover, explains why (§7.3). Inherited rows in a type scope have **no** delete affordance at all.

### 1.5 Add semantics

- Adding creates a status in the **currently-selected scope** (Base → a base status with `role: none`; a type scope → a type-only extension).
- The internal `id` is **derived live** from the display name (lower-snake-case, dedup-suffixed) and shown read-only; the display name is the only required input.
- **Duplicate display name within the scope** blocks confirm and shows the error ring + message (§7.1).

### 1.6 SDD stages

- `SddStage` is a **fixed** five-value enum — no reorder, no add, no delete. Only two things are editable: the `requireDesignReview` toggle and each stage's display label.
- The toggle gates whether Epics/Stories must clear the stage cycle before execution; it does not hide the rename fields (the labels are always editable so a project can prepare them).

### 6.1 Collapsed (button)

- **Container:** `EdgeInsets.symmetric(horizontal: 14, vertical: 12)`, radius `AionRadius.lg` (12), fill transparent, **`1.5px dashed c.borderStrong`**, top margin `2`.
- **States:** hover → border `c.primary`, fill `c.primary.withOpacity(isDark ? 0.08 : 0.05)`; pressed → `scale 0.98`; focused → focus ring.

### 6.2 Expanded (inline form)

- **Container:** fill `c.surface`, **`1.5px c.primary`**, radius `AionRadius.lg` (12), padding `15`, `Column(gap: 13)`, top margin `2`, focus ring `c.primary.withOpacity(isDark ? 0.30 : 0.16)` spread `3` blur `0`.
- **Eyebrow:** `AionText.caption` mono, `c.textMuted` — `"NEW STATUS · {SCOPE}"`.
- **Fields row:** `Row(gap: 10)` of two `Expanded` fields:
  - **Display name** (required): label `AionText.label` `c.textSecondary` + `*` in `c.danger`; field = focused `AppTextField` (`1.5px c.primary` + focus ring), fill `c.background`, caret, Manrope 14 `c.textPrimary`.
  - **Internal name** (read-only, derived): label `c.textSecondary`; field fill `c.background`, `1px c.border`, mono 13.5 `c.textMuted`.
- **Duplicate error** (conditional, §7.1): `▲` `c.danger` + message `c.textSecondary` 12px.
- **Actions row:** right-aligned `Row(gap: 9)` → **Cancel** (`AppButton` ghost, `c.primary`, padding `9×14`) + **Add status** (`AppButton` primary, fill `c.primary`, white, padding `10×17`, radius `AionRadius.md`, FAB-glow shadow `0 10 18 -9 fabGlow`). Add is **disabled** (opacity `0.45`, no shadow) while the name is empty or duplicate.

### 6.3 Behavior

- Confirm (Add / `Enter`) appends the new status to the end of the active scope's list, collapses the form, and scrolls it into view.
- Cancel / `Escape` discards and collapses.

### 6.4 Reorder mechanic (hand-rolled — no Material)

- Drag starts on the grip (§5.2) via `Listener(onPointerDown/Move/Up)`. The dragged row is lifted into an `Overlay` (dragging visual §5.7) following the pointer on the Y axis.
- The vacated slot and the insertion target render as a **drop-gap placeholder**: height `52`, radius `AionRadius.lg` (12), `1.5px dashed c.primary.withOpacity(0.45)`, fill `c.primary.withOpacity(isDark ? 0.10 : 0.06)`, bottom margin `8`.
- Other rows animate to their new positions with `AnimatedPositioned` (`160ms Curves.easeInOut`). On drop, the list order commits and persists.
- **Inherited rows are not drag targets** and cannot be picked up from a type scope; only extension rows reorder there.

## 7. Validation & error states

All inline; no dialogs, no toasts. Destructive/blocked feedback uses `c.danger` and `AionColorsHubTokens.errorRing(isDark)`.

### 7.1 Duplicate display name (add or rename)

- The offending field takes the **error border** (`1.5px c.danger`) + **error ring** (`AionColorsHubTokens.errorRing(isDark)` = `c.danger.withOpacity(isDark ? 0.30 : 0.16)`, spread `3`, blur `0`).
- A message line below: `▲` (`c.danger`, 11px) + text (`c.textSecondary`, 12px, `height: 1.4`, `text-wrap: pretty`) — e.g. `A status named "In Review" already exists in this scope.`
- Confirm is disabled until resolved.

### 7.2 Role-invariant banner (blocked delete / role clear)

A full-width banner rendered at the top of the status list when the user attempts to break the role invariant (§1.3).

- **Container:** `Row(gap: 9, crossAxisAlignment: start)`, padding `EdgeInsets.fromLTRB(13, 12, 13, 12)`, radius `AionRadius.md` (10), bottom margin `8`.
- **Fill:** `c.danger.withOpacity(isDark ? 0.14 : 0.08)`. **Border:** `1px c.danger.withOpacity(isDark ? 0.34 : 0.24)`.
- **Content:** `▲` (`c.danger`, 13px) + message (`AionText.bodySm`-weight, 13px, `c.textSecondary`) — e.g. `Each Base role must always have exactly one holder. Assign the Done role to another status before removing this one.`

### 7.3 Disabled-delete explanation (per row)

- The row's delete sits disabled (§5.4). On hover/tap it explains via a small tooltip **and** an inline `ⓘ`-led note under the meta line: `ⓘ` (`c.textMuted`, 11px) + note (`c.textMuted`, 12px) — e.g. `In use by 4 tickets and holds the Done role — reassign first.`
- Reasons composited in priority order: in-use count, then sole-role-holder.

### 7.4 Coverage

| Trigger | Treatment |
|---|---|
| Duplicate display name | §7.1 field error ring + message; confirm disabled |
| Delete sole role holder | §7.2 banner + §5.4 disabled delete + §7.3 note |
| Delete in-use status | §5.4 disabled delete + §7.3 note |
| Clear sole holder's role to None | §7.2 banner; dropdown keeps prior value |
