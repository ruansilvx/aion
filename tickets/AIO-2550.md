# V1 Release Readiness

# Proposal: v1 Release Readiness

## What

Five scoped fixes that together make cutting an actual v0.1.0 release
defensible, for a first release scoped to **one person, Windows-primary,
each machine independent** (per the `/brainstorm`-style scoping session
that produced this proposal — see Non-goals for what that explicitly
rules out):

1. **A real app icon.** Every platform still ships Flutter's default
   template icon (`assets/icons/aion_icon.png`, feeding both
   `windows/runner/resources/app_icon.ico` and the Linux AppImage).
   Replace it with real Aion artwork and regenerate the Windows `.ico`.
2. **Decouple the Linux build from the release gate**, so a Linux-side
   failure can't block a Windows-only release — matching this project's
   explicit "not blocking on Linux for now" stance. (The actual
   tag-push dry run this enables has to happen *after* this change is
   merged — see Non-goals — so it isn't one of this cycle's tasks.)
3. **Workflow-status UI wiring.** `tickets_board_view.dart`,
   `tickets_list_screen.dart`, `ticket_filter_popover.dart`,
   `ticket_columns_popover.dart`, `ticket_metadata_section.dart`, and
   `ticket_selection_bar.dart` all still read the hardcoded 6-status
   `defaultWorkflowStatuses` list instead of `WorkflowConfigCubit`'s
   live, per-project state. Wire each to it directly so a
   renamed/added/removed status actually shows up everywhere a status
   can be seen or picked.
4. **Automation-confidence validated live, especially `auto`.** Run a
   real pass with `AutomationConfidence.auto` covering both of its
   current real consumers — `TicketsCubit.advanceSddStage` and coding
   execution's reactive `AgentOverageDetectedEvent → gated` override —
   and make an explicit, documented call on the known no-timeout gap on
   `gated` proposals (ticket CRUD tool calls, mid-task branching) rather
   than leaving it an implicit risk.
5. **End-to-end native Windows verification, extended past what's
   already been confirmed.** `native-windows-verification-pass`
   (archived) verified ticket creation, git projection, Board
   drag-and-drop, and Trash restore live on Windows — but never a full
   coding-execution cycle. Run one: Task ticket → agent run → PR opened
   via `gh pr create` → notification-center entry.

## Why

None of these block *building* Aion — they block trusting a cut release
to actually work when the developer relies on it outside a dev-loop
session. Items 1–2 are packaging/presentation; item 3 is a real
functional gap the moment the shipped default statuses get renamed;
items 4–5 are about the two subsystems doing something unattended
(automation) or externally consequential (opening a real PR) actually
being exercised for real before the first release, not just reviewed as
code.

## Non-goals

Explicitly out of scope for this release, per the scoping conversation
that produced this proposal:

- **Every mobile/web-only gap** (on-device LLM, Firebase AI Logic proxy,
  Apple/Android tool-calling, mobile-only providers) — not this
  release's target platform.
- **Multi-provider expansion** (Ollama, OpenAI, OpenAI-compatible,
  Firebase AI Logic, live model-list discovery, per-provider
  enabled/disabled state, cross-provider per-ticket override, a real
  `readOnly` tool-access tier) — two working providers (Claude Agent SDK
  + Anthropic Messages API) is enough for one person.
- **A predictive budget/usage-window consent gate** — the reactive path
  gets validated by item 4 above; the predictive one stays future work,
  consistent with `project.md` §5's existing "sufficient at personal
  scale" reasoning.
- **A formal accessibility audit** (screen-reader + keyboard
  walkthrough) — personal-scale, low priority for a one-person release.
- **Bulk reparent/bulk type edit, page-side link creation, an
  "AI-reviewed manual changes" gate, retroactive link backfill, a
  `duplicates` Board callout, notification-center pagination/retention**
  — all completeness polish on already-shipped features, not release
  blockers.
- **Cross-device sync / "clone existing project" onboarding** —
  confirmed out of scope: each machine is independent for this release,
  so `TicketDbReconstructionService`'s missing UI wiring and the
  cross-device git push/pull open question both stay unbuilt.
- **Node.js auto-discovery/bundling, `agent_bridge` auto-install** —
  already documented as a one-time manual setup step
  (`project.md`'s Bootstrap & Dependency Notes); acceptable for a
  single-developer release.
- **macOS build/verification** — no macOS job exists in the release
  pipeline at all; adding one is new CI work, not verification, and is
  not this release's platform target.
- **Actually cutting the `v0.1.0` tag itself, and the dry run that
  depends on it.** A tag push against real `main` content requires this
  change to already be merged — pushing one mid-cycle would be testing
  against a branch, not the release. This change gets the pipeline and
  the app into a state where that dry run is worth running; running
  `/prepare-release`, pushing the tag, and confirming the resulting
  GitHub Release all happen afterward, as a manual follow-up once
  `/archive`'s PR lands (not a `tasks.md` item here — see `tasks.md`'s
  closing note).

Approved: 2026-08-24. 0 new tokens to add to `aion_colors.dart` — every
color in the Claude Design export resolves to an existing `AionColors`

Revises the "no new visual components" premise this gate was originally
written under: `BoardColumn`'s header and `MoveToStatusMenu`
(`tickets_board_view.dart`) have no status dot today (confirmed — no
`BoxShape.circle` anywhere in that file); design.md §3/§4 add one, fully
specified, not left open. Separately, today's dot-color logic is
duplicated three ways (`ticket_selection_bar.dart`'s `_statusDotColor`,
plus a private `_StatusAccentDot` independently duplicated in both
`ticket_columns_popover.dart` and `ticket_filter_popover.dart` — each
one's own doc comment admits it can't be shared), not the two design.md
§2 credits itself with replacing; its per-widget specs (§5/§6) correctly
cover all four, only its own summary sentence undercounts. Net effect:
this change now includes one small, fully-specified new visual element
(a role-keyed status dot, replacing three duplicated name-matching
implementations with one shared function), not zero — see `tasks.md`'s
`design.md §2/§3/§4` citations on T4/T6/T8/T9.

One non-blocking implementation note, outside `AionColors`'s scope so
not a gate condition: §4.1/§5/§7/§8.2's panel shadow is a hand-written
`BoxShadow` that doesn't reuse the existing `AionShadows.overlay(c,
isDark)` token, built for exactly this case. Worth using the existing
token in `/apply` unless the visual difference is deliberate.
