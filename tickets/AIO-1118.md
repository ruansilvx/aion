# Mid Task Chat Branching

# Proposal: Mid-task/issue chat branching

## What

Lets any `chat` ticket branch mid-conversation into a child `chat` when the
AI recognizes a blocking sub-issue, and lets that child chat fold its
resolution back into the parent when it's done — realizing `project.md`
§2's Branch/Merge Semantics decision at the `chat`-ticket granularity for
the first time.

Two new pieces make this possible:

1. **A generic, provider-agnostic bidirectional tool-calling layer**,
   added to the existing `AgentModelClient`/`AgentRequest`/`AgentEvent`
   contract. Today a model call is one-shot: a prompt goes in, text comes
   out, the run ends. This adds a second capability class — app-defined
   tools the model can call mid-run, with the app executing them and
   feeding a result back so the model keeps reasoning in the same turn.
   Both providers (Claude Agent SDK bridge, Anthropic Messages API)
   implement it.
2. **Two app-defined tools built on that layer**: `branch_ticket` and
   `close_branch`, symmetric halves of one lifecycle, both gated by the
   existing `AutomationConfidence` (`auto`/`gated`/`manual`) pattern.

See `aion-arch/ideas/mid-task-chat-branching.md` for the exploration that
led here.

## Why

`tickets.md`'s known-gaps section states it plainly: "No mid-task/issue
`chat` branching — `chat` tickets remain leaves; nothing spawns a
chat-under-chat... a stage-triggered chat runs start-to-finish with no
interruption/branch path." Every SDD-stage chat and coding-execution chat
today has exactly one way to handle a blocking sub-issue discovered
mid-conversation: push through anyway, or fail the whole turn. Neither is
right when the sub-issue is real but doesn't invalidate the parent
conversation's own thread.

`project.md` §2 already settled *what* branching means in the abstract
(branching creates a subticket; closing folds its resolution into the
parent, not a literal diff merge; the subticket stays archived-but-linked,
never deleted) — but that decision has had no concrete mechanism for
`chat` tickets specifically, and `project.md` §5's SDD-chat-persona
reasoning explicitly called "mid-task issue branching" out as deliberately
out of scope for `sdd-ticket-execution`, deferred pending its own design.
This change is that design.

## Scope

**In scope:**

- A new tool-calling axis on `AgentModelClient`/`AgentRequest`/
  `AgentEvent`, independent of `ToolAccessTier` (which stays about file/
  git/bash access) and `ModelPhase` (which stays about reasoning weight).
  Implemented for both `ClaudeAgentSdkClient` (via a new Node↔Dart stdio
  delegation round-trip in `agent_bridge/index.mjs`) and
  `AnthropicMessagesApiClient` (via the standard `tool_use`/`tool_result`
  multi-turn loop).
- `branch_ticket` — callable by the model on any `chat` whose own parent
  isn't itself a `chat` (so a branch can't itself be branched — see
  Non-goals). Creates a child `chat` ticket and (depending on
  `AutomationConfidence`) either does so immediately or surfaces a
  proposal the user confirms/rejects.
- `close_branch` — callable by the model on a branch chat (one whose
  parent *is* a `chat`) once it judges the sub-issue resolved. Posts a
  system-authored summary comment onto the *parent* chat's transcript —
  the "fold into documentation" `project.md` §2 describes, adapted to a
  chat ticket's comment-thread-as-content shape — and closes the branch.
- A new `AutomationContext.chatBranching` confidence setting, governing
  both tools symmetrically, surfaced in Settings alongside the existing
  SDD-stage/coding-execution automation rows.
- A `TicketTypeHierarchy.canParent` change: `chat` may now parent `chat`
  (previously an absolute leaf, per both `chat`'s and `resource`'s shared
  "can never parent anything, including each other" rule — `resource`
  keeps that rule unchanged; only `chat` gains this one narrow exception).
- A depth-cap invariant enforced at the `TicketsCubit` level (not in
  `TicketTypeHierarchy`, consistent with this project's existing "type-
  level rules live in the enum extension, instance-level invariants live
  in the Cubit" split): a chat already parented by another chat cannot
  itself be branched.
- A minimal confirm/reject UI surface in the chat transcript for `gated`
  proposals — a banner mirroring the existing Design Sync retry
  validation bar's placement and shape.

**Out of scope (explicit deferrals):**

- Migrating Release Planning's existing `RELEASE PLAN:` text-marker
  parsing onto this same tool-calling mechanism. Flagged during
  brainstorming as inevitable, but a separate follow-up — this change
  only builds the generic layer and its two branching-specific tools.
- Any additional app-defined tools beyond `branch_ticket`/`close_branch`
  (e.g. a future `create_release`). The layer is generic enough to support
  them later; none are added here.
- Unbounded branch nesting (branch-of-a-branch). Deliberately capped at
  one extra level — see Non-goals.
- A read-only (`ToolAccessTier.readOnly`) tier for file/git/bash access.
  Unrelated axis, tracked separately in `providers.md`'s known gaps — not
  needed here since app-defined tools are orthogonal to file-system tool
  access.
- Chat follow-up turns still carry no cross-turn conversation history
  outside of a single tool-call round trip (see `tickets.md`'s existing
  known gap) — this change's internal tool loop keeps context *within* one
  `runChatTurn` call (prompt → tool call → tool result → continued
  reasoning → final reply), but does not change how a *separate* human
  follow-up message is assembled.

## Non-goals

- **No unbounded branch nesting.** Only a chat whose own parent is not
  itself a chat may be branched. A branch chat is a true leaf — depth is
  capped at exactly one extra level below whatever chat originally spawned
  it (an SDD-stage or coding-execution chat, always parented by a work-item
  ticket). This keeps leaf-detection (used by the estimate/timeSpent
  rollup and Board leaf-card rendering) handling one well-known extra case
  rather than arbitrary recursion.
- **No timeout on a `gated` proposal.** If a proposal is surfaced and the
  user never confirms or rejects it, the underlying model run simply stays
  open indefinitely, visibly waiting in the UI. Consistent with this
  project's "sufficient at personal scale" precedent elsewhere (no budget/
  usage-window enforcement either) — worth revisiting if it proves
  annoying in practice, not solved here.
- **`AutomationConfidence.manual` disables AI-initiated branching, full
  stop.** Per its existing definition ("never surfaces proactively; the
  user must initiate the action themselves via an always-available
  control"), and since this change's trigger is AI-initiated only (no
  user-invoked "branch this" button is built here), `manual` confidence
  means the model's `branch_ticket`/`close_branch` calls are declined
  automatically, with no proposal ever shown. A user-invoked manual
  trigger is a natural follow-up, not built here.
