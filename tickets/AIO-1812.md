# Design: Release preparation and tagging

## 1. Core layer — `ProjectStackDetector` extension

`aion/lib/core/build/project_stack_detector.dart` currently exposes only
`DetectedStack` (display name + guidance-text commands, never read by
Aion's own code — see `proposal.md`'s Why). This change adds a sibling,
programmatically-consumed capability to the same class rather than
growing `DetectedStack` itself, which stays exactly what it is today
(prompt guidance text) — conflating the two would blur that class's single
responsibility.

```dart
/// Where a project's own release version lives, and how to read/rewrite
/// it. Returned by [ProjectStackDetector.detectVersionFile] — `null` when
/// the detected stack (or no stack) has no supported version file this
/// round (see table below).
class DetectedVersionFile {
  const DetectedVersionFile({
    required this.file,
    required this.currentVersion,
    required this.kind,
  });

  final File file;
  final String currentVersion; // e.g. "1.4.2"
  final VersionFileKind kind;
}

enum VersionFileKind { pubspecYaml, packageJson, cargoToml, pyprojectToml }
```

New methods on `ProjectStackDetector`:

- `DetectedVersionFile? detectVersionFile(String rootPath)` — reuses the
  existing marker-file detection, then reads+extracts the current version
  per `VersionFileKind`.
- `Future<void> writeVersion(DetectedVersionFile detected, String newVersion)`
  — rewrites just the version field, preserving every other byte of the
  file.

**Per-stack support this round** (the other two `_markers` entries stay
detected for guidance text only, unchanged from today — no version-file
support added for them):

| Marker | `VersionFileKind` | Read/write strategy | Notes |
|---|---|---|---|
| `pubspec.yaml` | `pubspecYaml` | Regex: `^version:\s*(.+)$` (multiline), replace in place | Aion's own stack — this is the one exercised by the originating idea's dry run |
| `package.json` | `packageJson` | `dart:convert` JSON decode/re-encode, `"version"` top-level key | Safer than regex — real JSON |
| `Cargo.toml` | `cargoToml` | Locate the `[package]` section, regex the first `version = "..."` line before the next `[section]` | Naive TOML handling, scoped to avoid matching a dependency's own `version =` line |
| `pyproject.toml` | `pyprojectToml` | Locate `[project]` section, same strategy as Cargo | PEP 621 layout only — `[tool.poetry]`-style projects are not handled this round, documented as a known gap |
| `go.mod` | — (no `DetectedVersionFile`) | n/a | Go modules have no in-file semver — `go.mod`'s `go 1.x` line is a language-version pin, not the app's release version. `detectVersionFile` returns `null`; Prepare Release still tags, but skips the version-bump step and flags this in the draft review UI |
| `requirements.txt` | — (no `DetectedVersionFile`) | n/a | No project-metadata version field exists in this file format at all |

For the two unsupported stacks, `ReleaseDraftScreen` shows "No version
file detected for this project — the tag will be created without a
version bump" instead of a version field, rather than silently skipping
the bump unexplained.

## 2. Core layer — `GitRepositoryClient` tag support

Two additions, mirroring the existing `_runChecked` shape used by
`push`/`createWorktree`:

```dart
/// Runs `git tag -a <tagName> -m <message>` in [rootPath].
Future<void> tag(String rootPath, String tagName, String message) async {
  await _runChecked(['tag', '-a', tagName, '-m', message], rootPath);
}

/// Runs `git push origin <tagName>` in [rootPath].
Future<void> pushTag(String rootPath, String tagName) async {
  await _runChecked(['push', 'origin', tagName], rootPath);
}
```

Both throw `ProcessException` on failure (annotated `tag`, `-1`
pattern the class already uses for other checked operations), surfaced by
`TicketsCubit.confirmRelease` the same way `_runCodingExecution` surfaces
a `GitHubCliClient.openPullRequest` failure — a normal error path, not a
special case.

## 3. New domain entity — `ReleaseDraft`

`aion/lib/features/tickets/domain/entities/release_draft.dart`:

```dart
class ReleaseDraft extends Equatable {
  const ReleaseDraft({
    required this.releaseTicketId,
    required this.linkedTicketIds,
    required this.changelogMarkdown,
    required this.suggestedVersion,
    this.detectedVersionFile,
  });

  final String releaseTicketId;
  final List<String> linkedTicketIds;
  final String changelogMarkdown;     // AI-drafted, editable before confirm
  final String suggestedVersion;      // AI-suggested semver bump, editable
  final DetectedVersionFile? detectedVersionFile; // null → no version-bump step
}
```

Plain data — no persistence, no drift table. It only exists in memory
between `prepareReleaseDraft`/`autoCreateReleaseTicket` and
`confirmRelease`; the release is either confirmed and tagged, or the
draft is discarded on cancel, matching the "draft everything, confirm
before pushing" decision — nothing about a rejected draft needs to
survive.

## 4. `TicketsCubit` additions

All three methods live in `tickets_cubit.dart` alongside `_createEpicSpec`
(same "AI drafts content from linked tickets, guarded by optional
dependencies" shape) rather than a new dedicated Cubit — release
preparation reuses the exact same dependencies (`_providerRegistry`,
`_linkRepository`, `_gitClient`, `_projectRootPath`) `_createEpicSpec`
and `_runCodingExecution` already centralize on this Cubit, and splitting
it out would just duplicate that wiring for no separation of concern that
actually holds (this is ticket-domain logic operating on `release`
tickets, same as `_createEpicSpec` operates on `epic` tickets).

### 4.1 `prepareReleaseDraft` — curated mode / shared draft step

```dart
/// Drafts a [ReleaseDraft] for the `release` ticket [releaseTicketId]:
/// fetches its `relatesTo`-linked epic/story/task/bug tickets (via
/// [TicketLinkRepository.getLinksForTicket]), assembles their title/
/// type/status into a prompt (same shape as [_createEpicSpec]'s context
/// assembly), resolves [ModelPhase.capable] (mechanical writeup of
/// already-decided work, not a fresh judgment call — matching
/// [_createEpicSpec]'s own tier rationale), and runs one non-tool
/// [AgentModelClient.run] call requesting changelog prose plus a
/// suggested semver bump. Also calls
/// [ProjectStackDetector.detectVersionFile] on [_projectRootPath] to
/// populate [ReleaseDraft.detectedVersionFile]. Returns `null` (no
/// error emitted — caller shows an inline message) if constructed
/// without a [ProviderRegistry]/[TicketLinkRepository], or if
/// [releaseTicketId] doesn't resolve to a `release`-type ticket.
Future<ReleaseDraft?> prepareReleaseDraft(String releaseTicketId) async { ... }
```

Failure during the model call emits
`TicketsError(reason: TicketsErrorReason.releasePreparationFailed)` (new
enum value, see §4.4) and returns `null` — the release ticket itself is
untouched either way, mirroring `_createEpicSpec`'s "the source ticket's
own state never depends on this call succeeding" behavior.

### 4.2 `autoCreateReleaseTicket` — auto mode's population step

```dart
/// Auto mode's ticket-population step (see `proposal.md`). Reads the
/// Cubit's cached `_workflowStatuses` for the shared-base status whose
/// `role == WorkflowStatusRole.done` (looked up here, not in the
/// repository — a pure function over already-loaded config, per
/// `WorkflowStatusRepository`'s own "invariant logic lives in Cubits"
/// convention), queries every live `epic`/`story`/`task`/`bug` ticket at
/// that status (`getAllTicketsByType`, filtered client-side by status —
/// no dedicated repository query added for this, since the result set
/// is bounded by ticket count, not something warranting a new SQL path),
/// then subtracts every ticket already `relatesTo`-linked to *any*
/// existing `release` ticket (via `getLinksByTypes([TicketLinkType.relatesTo])`
/// cross-referenced against `getAllTicketsByType([TicketType.release])`'s
/// ids). Creates a new `release` ticket ("Release — <today's date>"),
/// links every surviving candidate via [createTicketLink], and returns
/// the new ticket. Returns `null` if there is nothing unreleased to
/// bundle (surfaced by the caller as "nothing to release").
Future<Ticket?> autoCreateReleaseTicket() async { ... }
```

The Inbox's "Cut a release" card calls this, then immediately calls
`prepareReleaseDraft` on the result — auto mode is purely a different
population path feeding the same draft step, not a second draft
mechanism.

### 4.3 `confirmRelease` — the actual write/tag/push

```dart
/// Applies a reviewed [draft] (its [ReleaseDraft.changelogMarkdown]/
/// [ReleaseDraft.suggestedVersion] may have been hand-edited since
/// [prepareReleaseDraft] returned it — this call trusts the caller's
/// copy, does not re-fetch or re-draft). Writes a new
/// `## [<version>] - <date>` section into the target project's
/// `CHANGELOG.md` (Keep a Changelog format, created if absent — mirrors
/// `aion/CHANGELOG.md`'s own documented convention in
/// `aion-arch/specs/release.md`, generalized to any managed project as
/// this feature's own opinionated default) under `## [Unreleased]`, then
/// — only if `draft.detectedVersionFile` is non-null —
/// [ProjectStackDetector.writeVersion]s the bump. Stages and commits
/// both files (`GitRepositoryClient.add`/`.commit`,
/// `"chore(release): v<version>"`), tags
/// (`GitRepositoryClient.tag('v<version>', changelogMarkdown)`), and
/// pushes both the commit and the tag (`GitRepositoryClient.push` then
/// `.pushTag`) — in that order, so a failed tag push never leaves an
/// untagged commit stranded on `origin` with no way to retry cleanly (a
/// re-run of `confirmRelease` after a push failure re-attempts from a
/// clean, already-committed state). Throws normally on any step's
/// failure — caught by the caller (`ReleaseDraftScreen`), which keeps
/// the draft on screen for retry rather than discarding it, since a
/// mid-sequence failure (e.g. `pushTag` failing after `tag` already
/// succeeded locally) is exactly the "rollback plan" gap the originating
/// idea flagged as an open question; this change doesn't add automatic
/// rollback, but does keep the draft alive so the user isn't forced to
/// redraft from scratch after a transient failure (e.g. no network).
Future<void> confirmRelease(ReleaseDraft draft) async { ... }
```

### 4.4 `TicketsErrorReason` addition

`tickets_state.dart`: add `releasePreparationFailed`, alongside the
existing `specWriteFailed` — same shape, mapped to a new l10n toast string
in `tickets_board_view.dart`'s existing reason→toast switch.

## 5. UI

### 5.1 `ReleaseSummarySection` (new widget)

`aion/lib/features/tickets/presentation/widgets/release_summary_section.dart`.
Feature-level composition, not a `design_system/` promotion — it's tied to
`release`-ticket business logic (the Prepare Release trigger), failing
the "no feature entity/enum baked into its body" bar for promotion.

```
ReleaseSummarySection
├── SectionHeader("Linked work")
├── LinkedTicketsSection            // reused design_system molecule —
│                                   // same rows Documentation-mode's own
│                                   // Linked Tickets section already
│                                   // renders elsewhere, just hosted here
│                                   // for a type that gets no Documentation-
│                                   // mode block of its own today
└── AppButton("Prepare Release", onPressed: _onPrepareRelease)
    // disabled + tooltip when linkedTicketIds is empty
```

`_onPrepareRelease` calls `TicketsCubit.prepareReleaseDraft(ticket.id)`,
shows `AppSpinner` in-flight, then pushes `ReleaseDraftScreen` with the
result (or shows an inline error banner on `null`/failure).

### 5.2 `TicketDetailScreen` wiring

For `ticket.type == TicketType.release`, render `ReleaseSummarySection`
in the exact slot the excluded-type comment in
`aion-arch/specs/tickets.md` describes as absent today ("after the
Content block") — this is the only ticket-type-conditional branch this
change adds to that screen; every other type's rendering is untouched.

### 5.3 `ReleaseDraftScreen` (new screen)

`aion/lib/features/tickets/presentation/screens/release_draft_screen.dart`,
pushed via `Navigator.push` (no new `go_router` route — this is a
transient review step reached only from `ReleaseSummarySection`, not
something deep-linked to, matching how other in-flow confirmation steps
in this codebase stay off the router).

```
ReleaseDraftScreen
├── AppTextField(multiline, controller: changelogController)
│     // pre-filled with draft.changelogMarkdown, freely editable
├── AppTextField(controller: versionController)
│     // pre-filled with draft.suggestedVersion, freely editable —
│     // hidden (replaced by the "no version file detected" notice from
│     // §1) when draft.detectedVersionFile is null
├── Row
│    ├── AppButton("Cancel", secondary) → Navigator.pop, draft discarded
│    └── AppButton("Confirm & Tag", primary) → _onConfirm
```

`_onConfirm` shows `AppConfirmDialog` (the same molecule already used
elsewhere for irreversible actions) with the exact tag name and target
branch before calling `TicketsCubit.confirmRelease` — this is the
explicit-confirmation gate the brainstorm settled on ("confirm before
pushing, don't automate the whole thing"). On success, pops back to the
release ticket's detail screen; on failure, stays on screen with an error
banner and the same editable draft (see §4.3's retry rationale).

### 5.4 `InboxScreen` — "Cut a release" launcher

A fifth card alongside the existing four (`brainDump`/
`whatNextGuidance`/`releasePlanning`/`qa`), **not** a new `InboxPurpose`
enum value — `InboxPurpose` is specifically "which purpose-specific chat
spawned this chat ticket" (per its own dartdoc), and auto mode spawns no
chat at all. It fires immediately (matching "What's next"'s existing
"fire on tap, brief in-flight state" pattern, not the expand-in-place
text-input pattern brain dump/Q&A use):

```dart
Future<void> _cutReleaseAuto() async {
  setState(() => _inFlight = InboxAction.cutRelease); // new local enum,
                                                        // mirrors existing
                                                        // in-flight tracking
  final ticket = await context.read<TicketsCubit>().autoCreateReleaseTicket();
  if (!mounted) return;
  setState(() => _inFlight = null);
  if (ticket == null) {
    // inline "nothing to release" message, no navigation
    return;
  }
  context.go(ticketDetailRoute(ticket)); // same navigation `TicketsCubit`
                                          // detail routes already use
}
```

Since `InboxScreen`/`InboxCubit` and `TicketsCubit` are both inside
`features/tickets/`, calling `context.read<TicketsCubit>()` from
`InboxScreen` is not a cross-feature violation — see `proposal.md`'s
"Decision made during this proposal" for why this ruled out the
originally-considered Settings-screen placement.

# Aion — Release Preparation & Tagging: Component Spec

Extends the base [Aion Design System Spec](./Aion%20Design%20System%20Spec.md), the [Inbox Spec](./Aion%20Inbox%20Spec.md) (§3–§4, the launcher grid this feature adds a fifth card to), the [Linked Ticket Relationships Spec](./Aion%20Linked%20Ticket%20Relationships%20Spec.md) (`LinkedTicketsSection` / `LinkRow`, **reused as-is**), the [Signal and Release Types Spec](./Aion%20Signal%20and%20Release%20Types%20Spec.md) (`release` ticket type, `typeRelease` accent), and the [Ticket Deletion Spec](./Aion%20Ticket%20Deletion%20Spec.md) (§3, the `AppConfirmDialog` shell reused for the tag confirmation).

Mockups: [Aion Release Preparation Mockups](./Aion%20Release%20Preparation%20Mockups.dc.html).

This feature gives Aion a native, in-app release path — draft a changelog and version bump with AI assistance, review and edit it, then commit, tag, and push. Two entries funnel into one review screen:

- **Curated** — a manually-populated `release` ticket. Its detail screen gains a **`ReleaseSummarySection`** (§1): the linked work being released plus a **Prepare Release** trigger.
- **Auto** — a fifth **"Cut a release"** card in the Inbox launcher grid (§2): one tap, no curation, for a lightweight patch. Aion mints the `release` ticket itself from unreleased work.

Both land on **`ReleaseDraftScreen`** (§3) — the only new screen — where the drafted changelog and version are editable, and **Confirm & Tag** opens a final confirmation naming the exact tag and target branch (§4) before anything is written or pushed. Nothing is tagged without that second, explicit confirmation.

**Hard constraint — no Material widgets or types anywhere.** Every surface is `DecoratedBox` / `Container` (decoration only, non-Material) / `Padding` / `Row` / `Column` / `Stack` + `Positioned` / `GestureDetector` / `MouseRegion` / `FocusableActionDetector` / `AnimatedSize` / `AnimatedOpacity` / `AnimatedScale` / `RotationTransition` / `CustomPaint` / `OverlayEntry` + `CompositedTransformFollower` / `SingleChildScrollView`. No `Card`, `ElevatedButton`, `TextButton`, `Scaffold`, `AppBar`, `ThemeData`, `ColorScheme`, `ListTile`, `SnackBar`, `CircularProgressIndicator`, `DropdownButton`, `InkWell`, `Chip`, or `Tooltip`. Spinners are `AppSpinner` (`CustomPaint` arc), toasts `AppToast`, dialogs the existing overlay shell, text inputs `AppTextField` (a bare `EditableText`/`TextField` inside a transparent `Material` ancestor, per the app-wide exception documented in the base spec — the field chrome itself is `DecoratedBox`).

**Themes: Arctic (light) and Obsidian (dark).** Every dimension, `EdgeInsets`, radius, gap, stroke, duration, and text style in this spec is **identical between themes** — only color token values differ, and every color below is a named token that already resolves per theme. Hex pairs are given as `Arctic / Obsidian` for reference only; implement against the token. Per-component theme deltas are called out explicitly where they exist (§8.2); everywhere else the two themes are identical apart from token resolution.

Translucent fills are always `token.withOpacity(x)` — never hardcoded ARGB. `fillAlpha` = `fillAlphaArctic` `0.11` / `fillAlphaObsidian` `0.16`.

### 0.1 Surfaces added

| # | Surface | Kind |
|---|---|---|
| 1 | `ReleaseSummarySection` (`release` ticket detail) | **new** component — §1 |
| 2 | Inbox "Cut a release" launcher card | **new** fifth entry in the existing grid — §2 |
| 3 | `ReleaseDraftScreen` (`/releases/draft`) | **new screen** — §3 |
| 4 | Tag/branch confirmation dialog | **new content** in the existing confirm-dialog shell — §4 |
| 5 | Push-failure error banner (on `ReleaseDraftScreen`) | **new** component — §5 |
| 6 | "No version file detected" notice | **new** component — §6 |
| 7 | "Nothing to release" inline Inbox message | **new** component — §7 |

### 0.2 Async contract

Three calls drive every in-flight and error state below:

```dart
Future<ReleaseDraft> prepareReleaseDraft(String releaseTicketId);   // §1.3.5 in-flight
Future<ReleaseDraft?> autoCreateReleaseTicket();                    // §2.4 in-flight; null → §7
Future<void> confirmRelease(ReleaseDraft edited);                   // §3.7 in-flight; throws → §5

class ReleaseDraft {
  final String releaseTicketId;
  final String releaseKey;          // "AIO-51"
  final String changelog;           // markdown, AI-drafted, user-editable
  final String? suggestedVersion;   // null → no supported version file → §6
  final String? versionFilePath;    // "go.mod" | "requirements.txt" | null
  final String tagName;             // "v0.8.0" — derived from the edited version, live
  final String targetBranch;        // "main"
  final List<TicketRef> linkedWork;
}
```

`tagName` is **derived, never typed**: it is `'v' + version.trim()` recomputed on every keystroke in the version field, and it is the string the confirmation dialog names (§4.2). When `suggestedVersion` is `null`, no tag is derivable and Confirm & Tag is disabled (§3.7, disabled state).

### 0.3 Tokens

**No new colors.** Every fill, border, and text color resolves to an existing `AionColors` token or an existing `AionColorsHubTokens` helper:

| Use | Token / helper | Arctic / Obsidian |
|---|---|---|
| Release accent (chips, tag pill, section motif) | `typeRelease` | `#D8402C / #F26A4B` |
| Tag pill fill | `outcomeTileFill(typeRelease, isDark)` | `typeRelease @ 0.11 / 0.16` |
| Primary action (Prepare Release, Confirm & Tag) | `primary` / `primaryHover` | `#2E86D4 #1E6DB6 / #9366FF #A886FF` |

| "No version file" notice fill / border | `noticeFill(isDark)` / `noticeBorder(isDark)` | per helper |
| Success (tag pushed) | `success` | `#1E9E76 / #33D19B` |

**One new type token** — the version field is a semver string read digit-by-digit; the mono family has no size above `11` (`key`, `caption`, `time`), and setting a version in `AionText.bodySm` (Manrope 13.5) loses the digit alignment every other identifier in Aion gets:

```dart
// AionText — add
static const versionInput = TextStyle(
  fontFamily: _mono, fontSize: 15, fontWeight: FontWeight.w600, letterSpacing: 0.15, height: 1.3);
```

Used in exactly three places: the version field's input text (§3.5), the derived tag preview (§3.6), and the tag name inside the confirmation dialog (§4.2). Nothing else in this spec needs a new style — `h2`, `dialogTitle`, `body`, `bodySm`, `cardTitle`, `label`, `button`, `chip`, `caption`, `key`, `time`, `inboxCardLabel` cover the rest.

**No new radius or spacing tokens.** Radius: `sm` (6) chips/tag pill, `md` (10) buttons/notices/banner, `lg` (12) cards & fields (11 in screen forms per base spec §2.5), `xl` (16) dialog card, `iconBtn` (11) header buttons, `iconBtnSm` (8) close targets. Spacing: `sp4`–`sp32` only.

## 1. `ReleaseSummarySection`

The section a `release`-type ticket's detail screen renders in the slot where epics/stories render `_SddStageSection` — today a `release` ticket renders nothing there.

```dart
class ReleaseSummarySection extends StatefulWidget {
  final List<TicketRef> linkedWork;      // may be empty → §1.4
  final bool preparing;                  // prepareReleaseDraft in flight → §1.3.5
  final VoidCallback onPrepare;
}
```

### 1.1 Container & layout

| Property | Value |
|---|---|
| Widget | `Column` inside `Padding`, seated on the detail scroll body |
| Width | fills the detail content width (`double.infinity`) |
| Padding | `EdgeInsets.fromLTRB(22, 15, 22, 18)` — matches the sibling detail sections |
| Top divider | `1px solid border` (`#D6E0EA / #232C40`), full-bleed above the padding |
| Fill | none (inherits `background`) |
| Radius / shadow | none — sections are divider-separated, never carded (base spec §1.8) |
| Layout | `Column`, `crossAxisAlignment: stretch`, `gap: AionSpacing.sp16` (16) |
| Children | eyebrow (§1.2) → `LinkedTicketsSection` (§1.2) → Prepare Release button (§1.3) |

### 1.2 Eyebrow + linked work

- **Eyebrow:** `"RELEASE SCOPE"` (pre-uppercased), `AionText.caption` (JetBrains Mono 11 / w600, tracked), color `textMuted` (`#8496A6 / #6B7690`). `gap: 14` to the list below (the section gap of 16 minus the caption's optical overhang — matches the "SDD STAGE" eyebrow).
- **Linked work:** the existing **`LinkedTicketsSection` molecule, rendered as-is.** Its rows, ID badges, type chips, priority badges, relationship indicators, hover actions, radius, and padding are **not redesigned or re-derived here** — pass `linkedWork` and let it own its geometry. This section contributes only the eyebrow above it and the button below it.
- One `release`-specific composition choice: `allowedTypes` is passed as a single-element list, so rows show no retype affordance (per Linked Ticket Relationships §6.1) — a release's scope is a containment relation, not a switchable one. Remove remains available.

### 2.1 Grid position and layout

The grid is a 2×2 on wide viewports, a vertical stack on narrow. Five entries make the wide grid **2 + 2 + 1**, with the fifth card in the last row rendered **full-width** (spanning both columns), not half-width beside a gap.

- *Why:* a lone half-width card in row 3 leaves a visible hole and reads as a loading slot. A full-width fifth row reads as intentional and gives the one-tap patch path slightly more presence than the curated four above it, which matches its role.

Shown in the Inbox, below the launcher grid, when `autoCreateReleaseTicket()` returns `null`. No navigation, no toast, no dialog — the user stays where they tapped.

### 7.1 Slot & lifecycle
