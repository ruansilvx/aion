# Ticket Delete Entry Points

# Proposal: Ticket Delete Entry Points (List & Board Views)

## What

Add delete entry points for tickets to `TicketsListScreen`'s row
(`TicketListTile`) and `TicketBoardView`'s card (`TicketBoardCard`/
`_CardVisual`), reusing the exact confirm-then-delete flow already
shipped for `TicketDetailScreen` (see the archived `ticket-deletion`
change). Extracts the existing `TicketOverflowMenu` widget out of
`ticket_detail_screen.dart` into a shared
`presentation/widgets/ticket_overflow_menu.dart` so all three screens
import one implementation instead of duplicating it. Makes
`TicketsCubit.deleteTicket` context-aware so it restores the correct
screen state (list/board vs. detail) after a delete succeeds or is
blocked by children, instead of assuming the caller is always
`TicketDetailScreen`.

## Why

`aion-arch/specs/tickets.md`'s Known Gaps section (carried over from
the `ticket-deletion` change, which explicitly deferred this) states
deletion has no entry point on the list or board views — the only way
to delete a ticket today is to open it, then use its header `⋮` menu.
That's real friction for a personal-use ticket tracker with a flat,
fast-moving backlog: removing a stray or duplicate ticket currently
costs a full navigation round trip. This was the single highest-
priority open item flagged by `/what-next`.

## Scope

**In scope:**
- Delete entry point on `TicketListTile` (list view row).
- Delete entry point on `TicketBoardCard` (board view card), alongside
  the existing `MoveToStatusMenu`.
- Extraction of `TicketOverflowMenu` into a shared widget file so it's
  reusable across all three screens without screen-to-screen imports.
- `TicketsCubit.deleteTicket` updated to restore list/board state (not
  `TicketDetailLoaded`) when the delete was triggered from a
  list-shaped state, both on success and on the "blocked by children"
  path.
- Accessibility label update: the overflow trigger's semantic label
  becomes ticket-id-parameterized (`"More actions for {ticketId}"`) so
  multiple triggers on one screen (many rows/cards) are distinguishable
  to screen readers — same pattern already used by `MoveToStatusMenu`.

**Out of scope (explicitly deferred):**
- Bulk / multi-select delete — a materially larger feature (new
  selection state across both views); worth its own proposal.
- Swipe-to-delete or any other faster/lower-friction trigger gesture.
  This proposal deliberately keeps the same explicit
  tap-through-menu-then-confirm friction the detail screen already
  has, since deletion is still permanent (no undo/trash).
- Undo / soft-delete / trash mechanism — a separate known gap,
  unaffected by this change.
- Any change to cascade-vs-block behavior on tickets with children —
  unchanged, still blocks.
- Any change to `ticket_links` handling — unchanged.

## Known gaps this closes

From `aion-arch/specs/tickets.md`:
> Deletion (`TicketDetailScreen` only, via its header `⋮` menu) is the
> only entry point — no delete affordance exists on `TicketsListScreen`
> or `TicketBoardView`.

Undo/soft-delete/trash and bulk delete are separate, still-open gaps,
unaffected by this change.
