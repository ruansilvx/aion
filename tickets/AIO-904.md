## ADDED

### `Ticket` entity — two new fields

Two new nullable fields, alongside `estimate`/`timeSpent` in the
existing fields table:

| Field | Type | Notes |
|---|---|---|
| `estimateRollup` | `int?` | Derived: this ticket's own `estimate` plus the recursive sum of every live descendant's effective value. `null` iff this ticket has zero live children. Never user-editable; written only via `TicketRepository.updateRollup`. |
| `timeSpentRollup` | `int?` | Same shape as `estimateRollup`, for `timeSpent`. |

### Rollup computation and persistence

Implements the **Rollup invariant** already recorded in this file
(current-state `tickets.md`, ahead of any rollup existing): rollup
totals derive from the structural `parentId` tree only, never from
`ticket_links`.

`domain/utils/ticket_rollup_calculator.dart`'s `computeRollups`
(pure, `O(n)`, no Flutter dependency) computes, for every ticket with
at least one live child, `own value + sum(effective value of each
direct live child)`, where a child's effective value is its own rollup
if it has children, its raw own value otherwise — full recursion, not
one level. A ticket with no live children, and a ticket whose own value
and every descendant's effective value are all `null`, both produce
`null` (not `0`) for that field.

`TicketRepository.updateRollup(String id, {required int?
estimateRollup, required int? timeSpentRollup})` persists the computed
pair independently of `updateTicket`/`copyWith`, matching
`updateEmbedding`/`updateSyncStatus`'s existing "derived value, not a
user edit, doesn't perturb `updatedAt`" pattern.

### Rollup recompute triggers (immediate, upward-walking)

`TicketsCubit` owns a private `_recomputeRollupChain` helper (per this
project's Cubit-holds-domain-logic convention), fired
fire-and-forget from four call sites, always **immediately** after the
triggering write succeeds — never lazily on next view:

- `updateTicket` — when the persisted `estimate`/`timeSpent` actually
  changed, recomputes starting at the edited ticket itself (covers the
  case where the edited ticket has its own children) and walks upward.
- `updateTicketParent` — after a successful reparent, recomputes
  starting from both the moved ticket (reaches the *new* parent chain,
  since its `parentId` now points there) and the *old* parent id
  (reaches the old chain directly) — both sides update in one call.
- `trashTicket` / `trashTickets` — recomputes starting from each
  explicitly-trashed ticket's parent (mirrors the existing "explicitly-
  requested ids only, not enumerated cascaded descendants" scope
  simplification `_triggerGitProjection` already applies at these call
  sites).

`TrashCubit` gets the symmetric trigger:

- `restore` — recomputes starting from the restored ticket's parent.

Every recompute re-derives the affected ancestor chain from the live
tree (via `TicketRepository.getAllTickets()`, which already excludes
trashed tickets) rather than incrementally adding/subtracting — always
correct regardless of how many tickets moved/changed/were
trashed/restored in the triggering operation, and skips writing/
projecting an ancestor whose computed rollup didn't actually change.

**Not a trigger:** hand-edited `.md` files. `TicketMarkdownReconciler`
only ever reconciles `resource`/`page` tickets, which structurally can
never have a ranked-type (`epic`/`story`/`task`/`bug`) descendant or
ancestor (see this file's existing Structural type-compatibility
table) and never carry an `estimate`/`timeSpent` value in the first
place (no UI exposes those fields on `resource`/`page`). A hand-edited
file can therefore never contain a rollup-relevant change — this is a
structural fact of the existing git-projection model, not a
scope decision made independent of it.

### Batched git-projection commits

`TicketGitProjector` gains `projectBatch(List<Ticket> ancestors, String
rootPath, String eventLabel)`: writes and stages every ticket in
`ancestors` to its own Markdown file, then makes **one** commit
covering the whole batch (skipped if nothing changed, same
`hasChanges` guard `project` already uses). Used exclusively for a
rollup recompute's cascading ancestor rewrites — one triggering edit
that touches N ancestors produces exactly one commit, not N. The
existing `project` method (one file, one commit, used by the four
pre-existing events: created/status-changed/trashed/restored) is
unchanged.

### Markdown frontmatter — two new keys

`TicketMarkdownTemplate.fieldOrder` gains `estimateRollup`/
`timeSpentRollup`, appended at the end (per this file's own
already-documented ordering rule — never inserted next to a
semantically related existing key). `TicketMarkdownSerializer` writes
both; they parse back via the same generic `fieldOrder` loop
`parse()` already runs, using the same `int?` conversion `estimate`/
`timeSpent` already use.

### Drift schema — version 9

`TicketsTable` gains `estimate_rollup`/`time_spent_rollup` (INTEGER,
nullable). `AppDatabase.schemaVersion` becomes 9. Migration
(`if (from < 9)`) adds both columns via `addColumn`, then runs a
one-time backfill: computes `computeRollups` over every existing live
ticket and writes the results back, so an upgraded local database shows
correct rollups immediately rather than only after the next edit
touches each subtree. A fresh `onCreate` install has no rows to
backfill.

### UI — rollup display

- `TicketMetadataSection` — when a ticket's `estimateRollup`/
  `timeSpentRollup` are non-null, shows the rollup total read-only
  alongside (not replacing) the existing editable own-value
  `InlineEditableField<int?>`s.
- `TicketListTile` — shows a compact, read-only rollup indicator when
  `estimateRollup` is non-null. Unchanged for a leaf ticket.
- `TicketBoardCard` — same as `TicketListTile`.

Exact visual treatment is set by this change's Claude Design session
(see `proposal.md`'s Design gate) and recorded in this change's
`design.md` once pasted.

## MODIFIED

### `TicketMarkdownReconciler` — one new "Known limitation" doc note

Alongside the existing `parentId`/`deletedAt` "Known limitation" notes,
a third documents that a hand-edited `estimateRollup`/`timeSpentRollup`
value in a `resource`/`page` file's frontmatter is parsed (for
round-trip completeness) but never applied — `_apply` has no
`copyWith`-based path for either field, and, per the ADDED section
above, `resource`/`page` tickets can never carry a rollup-relevant
value regardless. Behavior is unchanged; this is a doc-only addition
for future-reader clarity, matching the existing two notes' own stated
purpose.
