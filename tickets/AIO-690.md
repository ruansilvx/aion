# Spec Delta: Decision Graph Rule Builder

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/providers.md` text — every distinctive symbol/behavior this delta names is still present and accurate (39/42 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Relative to `aion-arch/specs/providers.md` (`core/automation/`,
`features/providers/presentation/`). See `proposal.md`/`design.md` for
full rationale.

## ADDED

- `DecisionFieldType`/`DecisionFieldSpec`/`decisionFieldCatalog`/
  `decisionFieldsFor` (`core/automation/decision_field_catalog.dart`) —
  the field vocabulary a rule-builder condition picks from. Ships two
  entries: `attemptField` (`integer`, `codingExecutionRetry`),
  `sessionOverageDetectedField` (`boolean`, `codingExecution`) — the
  same two signals `DecisionEvalContext` already carries.
- `DecisionRuleOperator`/`operatorsFor` (same file) — `equals |
  notEquals | greaterThan | greaterThanOrEqual | lessThan |
  lessThanOrEqual`; `operatorsFor(DecisionFieldType)` returns all six for
  `integer`, `[equals, notEquals]` for `boolean`.
- `ruleBuilderConditionId`, `ruleBuilderConditionSpec`,
  `defaultRuleConditionParams`, `isRecognizedConditionId`,
  `decisionNodeTitle`, `decisionNodeSummary` (same file) — the
  rule-builder's picker-integration and node-display helpers, generalizing
  the fixed catalog's existing `decisionConditionSpecById`/
  `conditionParameterSummary` pattern to also cover a rule-builder node.
- A third `DecisionNode.conditionId` shape:
  `conditionId == 'ruleBuilder'` with `conditionParams == {'field':
  String, 'operator': String, 'value': int | bool}` — evaluated by a new
  case in `decision_graph_evaluator.dart`'s condition registry
  (`_evaluateRule`), reading the named field via a new `_fieldAccessors`
  map and comparing it to `value` per `operator`. Defaults to `false`
  (never blocks automation) for an unrecognized field, unrecognized
  operator, or a currently-`null` field value.
- `DecisionNodeForm`'s condition picker gains a "Custom rule" entry
  (appended after the real catalog, only when
  `decisionFieldsFor(context)` is non-empty). Selecting it shows a
  field/operator/value trio (two `SelectionMenu` pickers plus a typed
  value control — `AppTextField` for `integer`, a `SelectionMenu<bool>`
  for `boolean`) in place of the fixed-catalog parameter loop.

## MODIFIED

- `GraphCanvas`'s node-chrome layer (`decision_graph_editor_screen.dart`)
  and `DecisionOutlineList`'s row chrome (`decision_outline_list.dart`):
  their title/parameter-chip text and "is this node valid" check now
  route through `decisionNodeTitle`/`decisionNodeSummary`/
  `isRecognizedConditionId` instead of a bare
  `decisionConditionSpecById(conditionId)` lookup — without this, a
  rule-builder node would render its raw `conditionId` string and be
  flagged as an incomplete/error node in both panes.
- Both panes' chained-child-creation seeding (`_createChainedChild` in
  `decision_outline_list.dart`; the equivalent closure in
  `decision_graph_editor_screen.dart`) gains a
  `conditionId == ruleBuilderConditionId` branch that seeds via
  `defaultRuleConditionParams(context)` instead of
  `defaultConditionParams(spec)`.

## UNCHANGED (explicitly, per design.md §6)

- `DecisionNode`/`DecisionBranch`/`DecisionGraph`/`DecisionOutcome`
  entities, `DecisionGraphRepository` interface,
  `DriftDecisionGraphRepository`, the two drift tables and their schema
  version — `conditionId`/`conditionParamsJson` already accept
  arbitrary values; no migration.
- `DecisionGraphConfigCubit` — condition-agnostic CRUD/invariant
  enforcement, no changes.
- `TicketsCubit`'s `_evaluateDecisionGraph` and every
  `AutomationContext` call site — condition-agnostic, reads only the
  returned `DecisionOutcome`.
- `decision_condition_catalog.dart`'s existing two entries
  (`attemptExceedsMax`, `sessionOverageDetected`) and every seeded
  baseline graph — unmodified; the rule builder is an additional picker
  option, not a replacement.
