# Workflow Skill Attachments

# Proposal: Workflow Skill Attachments (Phase 2)

## Why

`aion-arch/ideas/configurable-workflow-and-automation-engine.md` (status:
`explored`) phased the workflow-automation-engine vision into three
proposals after a grounded `/explore` pass. Phase 1
(`configurable-ticket-workflow`, archived) made `TicketStatus`/`SddStage`
project-defined data instead of fixed enums, but deliberately shipped
**no skill attachment of any kind** — a status or stage can be renamed,
reordered, or remapped onto an existing gate, but nothing can be
configured to *run* automatically when a ticket enters it. This proposal
is Phase 2: any-named-skill attachment to a `WorkflowStatus` or
`SddStage`, confidence-gated by the existing static `AutomationConfidence`
enum. Phase 3 (wholly new precondition/gate types) remains out of scope.

A follow-up `/explore` spike (2026-08-19, folded into the idea file)
resolved the one real technical unknown blocking this proposal: whether
`.claude/skills/` discovery actually works through `agent_bridge`'s
prompt-string pipe at all. It does, with zero `agent_bridge` changes,
in both of `TicketsCubit`'s existing execution modes. This proposal's
design section builds directly on that confirmed mechanism.

Today, the only automated behavior on a status/stage transition is
hardcoded: `inProgress`-role entry starts coding execution
(`_runCodingExecution`), and every `SddStage` entry spawns a stage chat
running a hand-written per-stage prompt (`_assembleStageContext`). A
project with a custom `bug`-only "Needs Repro" status (Phase 1's own
motivating example) has no way to make entering that status *do*
anything — the idea file's whole Phase 2 premise.

## What

### Two attachment kinds, one underlying mechanism

Both kinds resolve to the same primitive: an `AgentRequest` run through
the already-existing `AgentModelClient`, its reply persisted into a
spawned chat ticket via `ChatCubit.runChatTurn` — exactly the pattern
`_createStageChat`/`_runStageChatTurn` already use for every `SddStage`
transition today. Only prompt construction and `toolsEnabled` differ:

- **Aion-native prompt/workflow template.** A project authors a named
  template (plain text with `{{ticket.title}}`-style placeholders,
  substituted against the triggering ticket's fields). Runs text-only
  (`toolsEnabled: false`), matching every SDD-stage chat today.
- **Delegated skill.** A project names an existing skill under the
  active coding agent's own `.claude/skills/` directory. The attachment
  fires by sending the literal `/<skill-name>` slash-command text as the
  prompt — chosen over relying on the model autonomously noticing a
  natural-language description match (also confirmed working by the
  spike), because an automation feature needs a deterministic trigger,
  not one contingent on the model happening to connect a hint to a
  skill. Runs tool-enabled (`toolsEnabled: true`, `workingDirectory` set
  to the project checkout), since a skill may need to read or edit the
  project to do its job.

### Attaching to a `WorkflowStatus`

Any project-defined status — shared-base **or** a per-type extension
(e.g. a `bug`-only "Needs Repro" status) — may hold at most one skill
attachment. This is new automated behavior: nothing fires today when a
ticket enters an arbitrary status. Firing is confidence-gated (see
below) and hooked into `updateTicketStatus`/`updateStatusForTickets`,
symmetric to the existing `executionTrigger`-role check already there.

### Attaching to an `SddStage`

Each of the five fixed `SddStage` values may hold at most one skill
attachment, **overriding** that stage's hardcoded
`_assembleStageContext` prompt for both attachment kinds — the
attachment's rendered template or delegated-skill prompt is used in
place of today's per-stage hand-written text, inside the same existing
`_createStageChat`/`_runStageChatTurn` flow. A stage with no configured
attachment behaves exactly as it does today, byte-for-byte — consistent
with Phase 1's "today's hardcoded behavior is the default baseline"
precedent.

### Confidence gating

Reuses the existing static `AutomationConfidence` (`auto | gated |
manual`) enum only — no new computed signal, resolving
`automation-confidence-decisions` the same way Phase 1's brainstorm
already concluded. Unlike the five existing `AutomationContext` values
(each a fixed enum key in `shared_preferences`), attachment confidence
is **per-attachment**, stored as a field alongside the attachment
itself — the open-ended "any status, any stage" shape doesn't fit a
fixed-enum-keyed store. New attachments default to `gated`, matching
`AutomationSettingsRepository`'s existing "surfaces a suggestion rather
than acting silently" default philosophy.

- `auto` — fires immediately and silently on entry, unawaited.
- `gated` — surfaces a confirmation banner on the ticket's detail
  screen before firing; declining leaves the status/stage change intact
  but never runs the attachment.
- `manual` — never fires automatically; an always-available "Run
  attached skill" control on the ticket detail screen triggers it.

`SddStage` transitions with **no** configured attachment are unaffected
by any of this — they keep firing unconditionally, exactly as today.
Confidence gating only applies once a project actually attaches
something.

### New Settings surface

Extends `WorkflowStatusSettingsScreen` (Phase 1) rather than adding a
new screen: each `StatusRow` (any scope) and each `SddStageRenameRow`
gains an "Attach skill" affordance opening an inline
kind/name/confidence form. A lightweight new template-management
surface (list + create/edit/delete) backs the Aion-native-template kind,
reached from that same form.

## Non-goals

- **No multiple attachments per status/stage.** At most one. Sequencing
  or branching multiple automated actions off a single transition is
  out of scope.
- **No template conditionals or logic** — plain `{{variable}}`
  substitution only, no loops/branches inside a template body.
- **No new computed-confidence signal** — already resolved during
  Phase 1's brainstorm; not revisited here.
- **No new `AutomationContext` value or `AutomationSettingsRepository`
  change.** Attachment confidence lives on the attachment record itself.
- **No app-defined tool exposure (`AgentRequest.tools`) to attachment
  runs.** Unlike coding-execution or chat-branching turns, an attachment
  run gets the provider's own file/git/bash access
  (when tool-enabled) but no `branch_ticket`-style app tools.
- **No pluggable gate *types*** — Phase 3's scope entirely. This
  proposal only adds a new kind of *effect* (run a skill), gated by the
  existing closed `auto/gated/manual` enum, not a new kind of
  *precondition*.
- **No verification that delegated-skill invocation works for any
  `AgentProvider` other than the Claude Agent SDK.** The spike tested
  only that provider; a future non-Claude provider isn't guaranteed to
  support `.claude/skills/`-style discovery the same way (see
  `aion-arch/ideas/pluggable-provider-abstraction.md`).
- **No migration/backfill concerns** — this is additive data (a new
  optional attachment per status/stage); no existing `WorkflowStatus` or
  `SddStage` row changes shape.
