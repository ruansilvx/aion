# Spec Delta: Documentation Section

**Reconciled 2026-09-03:** cross-checked against the current `aion-arch/specs/tickets.md` text — every distinctive symbol/behavior this delta names is still present and accurate (8/8 identifiers confirmed verbatim; the rest are prose/filename references, not drift). No content changes needed.

Delta against `aion-arch/specs/tickets.md`. Read alongside `proposal.md`
and `design.md` in this change folder.

## ADDED

- A new "Documentation" screen (`/workspace/documentation`), reachable via
  an icon button on the ticket list screen's header (same pattern as the
  existing Trash entry point). Shows a collapsible tree of `page`/
  `resource` tickets, root-level docs at top, `page` tickets expandable to
  show nested sub-pages/resources.
- `page` tickets can now parent other `page` and `resource` tickets
  (Notion-style nesting), enforced via `TicketTypeHierarchy.canParent`.
- Full-text/semantic search across `page`/`resource` tickets from the
  Documentation screen's search field, ranked by cosine similarity over
  each ticket's existing `embedding` column (brute-force scan, consistent
  with the app's existing embedding-storage approach — this is a new
  query capability, no new storage).
- Each `page`/`resource` ticket's detail view gains two new sections:
  - **Linked tickets** — board tickets (`epic`/`story`/`task`/`chat`)
    this doc is linked to via `TicketLink`, shown bidirectionally (the
    linked board ticket's own detail view also shows this doc under its
    existing related-tickets UI).
  - **Backlinks** — other `page`/`resource` tickets that have an explicit
    `TicketLink` to this one. Derived from the same `TicketLink`
    mechanism used for board-ticket links, not from parsing inline
    content references.
  - `page` tickets additionally gain a **Sub-pages** section listing
    direct `page`/`resource` children.
- A one-time, idempotent startup migration: any non-trashed `resource`/
  `page` ticket whose `parentId` points at an `epic`/`story`/`task`
  ticket has that relationship converted into a `TicketLink` (type
  `relatesTo`) and its `parentId` cleared. Runs once per install, gated
  by a persisted flag; failures are logged, non-blocking.
- `TicketRepository.getTicketsByParent(String? parentId, {required List<TicketType> types})`
  and `TicketRepository.getAllTicketsByType(List<TicketType> types)` —
  new dumb query methods, no business logic.

## MODIFIED

- `TicketTypeHierarchy.canParent`:
  - Previously: `resource`, `page`, and `chat` were all unconditional
    leaves — any `epic`/`story`/`task` could parent any of the three,
    and none of the three could parent anything.
  - Now: `epic`/`story`/`task` can still parent `chat`, but can **no
    longer** parent `resource` or `page`. `page` can now parent `page`
    and `resource`. `resource` and `chat` remain full leaves (cannot
    parent anything, including each other).
- The main ticket list screen (`TicketsListScreen`) no longer shows
  `resource`/`page` tickets, and its type-filter dropdown no longer
  offers `resource`/`page` as filter options. (The Kanban board view was
  already `task`/`story`-only and is unaffected.)
- `getValidParentCandidates`/`getValidParentCandidatesForType` — no
  logic change, but their *results* change as a consequence of the
  `canParent` update above: `page`/`resource` no longer offer
  `epic`/`story`/`task` as valid parents, and `page` now appears as a
  valid parent candidate for other `page`/`resource` tickets.

## REMOVED

- Nothing removed outright; `resource`/`page` tickets are relocated in
  the UI (list/board → Documentation section) and in their structural
  parent options (work items → other pages), not deleted or disabled.
  Existing `TicketLink`, comment, sync-status, and git-projection
  behavior for `resource`/`page` tickets (documented elsewhere in
  `tickets.md`) is unchanged by this delta.

## Known gaps carried forward (not resolved by this change)

- Inline `[[wikilink]]`-style content-reference backlinks (as opposed to
  explicit `TicketLink` backlinks, which this change does add) — out of
  scope, see `proposal.md`'s scoping decision #2.
- Resource file upload/preview — separate idea
  (`upload-and-visualize-files-for-resource-tickets.md`), not addressed
  here.
- No page-nesting depth limit is enforced by this change — left as an
  open question, flagged in the source idea file.
